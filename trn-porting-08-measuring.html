0この回の狙い

最終回は測定の話です。移植の成果を数字で語る段になって、測り方を間違えていたことに気付くと、それまでの議論が全部やり直しになります。

この回で扱うのは 2 種類の測定です。性能と正しさ。どちらにも、この環境固有の落とし穴があります。筆者は両方で実際に間違えたので、その形をそのまま残します。

一言でいうと
性能について: このスタックは非同期実行が既定なので、ホスト側のストップウォッチは「積む時間」と「実行する時間」の遅い方を測ります。カーネルが小さいと前者が律速し、数字はカーネル時間を反映しません。正しく測る手段はランタイムのデバイスモード計測です。
正しさについて: cosine 類似度を一致の証拠にしてはいけません (fp32 では 1 を超える値が出ます)。相対誤差で語り、さらに不変条件で縛ります。
1. 非同期実行がストップウォッチを壊す 2. 汚染を見抜く兆候 3. 正しく測る手段 4. 汚染された比は使えない 5. cosine は一致の証拠にならない 6. fp32 の一致は bf16 の一致ではない 7. 不変条件で正しさを縛る 8. GPU と比べるときに揃えるもの 9. チェックリスト

1非同期実行がストップウォッチを壊す

最初の落とし穴です。素朴に書いた計測コードは、ほぼ確実にこれを踏みます。

この経路では非同期実行が既定で有効です。デバイスへの呼び出しはキューに積まれ、ホスト側はすぐ戻ります。結果が必要になった時点で待ち合わせが起きます。

ここで、次のような素朴な計測を書きます。

for _ in range(3):
    compiled(*args)              # ウォームアップ
t0 = time.perf_counter()
for _ in range(20):
    out = compiled(*args)        # 20 回まわす
_ = out.cpu()                    # 最後だけホストに取り出す
per_call = (time.perf_counter() - t0) / 20

これは間違いです。ただし機構は素朴な直感とは少し違います。キューが投入順に実行されるなら、最後の out.cpu() はそれまでに積んだ 20 回ぶん全部の完了を待ちます。だからデバイスの実行時間が丸ごと計測から漏れるわけではありません。

本当の問題は、測っているのが「積む時間」と「実行する時間」の遅い方になることです。カーネルが数十マイクロ秒しかない場合、ホスト側で呼び出しを組み立てるコストが律速になり、得られる数字はカーネル実行時間ではなく発行スループットを反映します。

得られるのは 2 つの帯の長い方。カーネルが小さいと上の帯 (発行) が律速する

2汚染を見抜く兆候

計測が汚染されているかどうかは、数字の形から分かります。この嗅覚が一番役に立ちます。

いちばん効く兆候はこれです。仕事量を増やしたのに時間が動かないとき、それは計算を測っていません。

系列長を 4 倍にすれば、計算量は少なくとも 4 倍、2 乗の計算なら 16 倍になります。それで時間が数パーセントしか動かないなら、測っているのは計算ではありません。呼び出しの組み立てが律速していると考えるべきです。

具体的な桁感を出しておきます。公開イメージ上で、2.6 MB 級の入出力を持つ部分グラフ 1 個について、デバイスモードでのカーネル実行時間は 0.063 ms でした。一方、同じ呼び出しをホスト側から見ると、入力の書き込みと出力の読み出しを含めて 1.88 ms かかります (内訳は第 7 回 §7)。つまりこの規模のグラフでは、ホスト側から見える時間の 96% 以上が計算以外です。素朴なストップウォッチがカーネル時間を反映しないのは、こういう比率のときです。

他にも次のような兆候があります。

兆候疑うべきこと
仕事量を増やしても時間が横ばい呼び出しの組み立てが律速している
1 回目だけ極端に遅いコンパイルかキャッシュの読み込みが混ざっている
ばらつきが平均と同じ桁ホスト側の別の要因 (GIL、割り込み) が支配している
演算の個数が多い実装だけ、素朴な計測と大きく違わない発行コストが演算数に比例して積み上がるため、偶然近い値に見えている

最後の行は罠です。演算が縦に並ぶ実装では、発行コスト自体が演算数に比例して増えます。だから素朴な計測でも「仕事量に応じて増えているように見える」数字が出ます。増えているから正しい、とは言えません。

3正しく測る手段

この環境で信頼できる方法を挙げます。

もっとも確実なのは、ランタイムのデバイスモード計測です。第 7 回で触れた Python API に、ウォームアップ回数と計測回数を指定できるベンチマークがあります。これはデバイス側のイベントを使うので、ホスト側の発行時間が混ざりません。

実際に使うと、標準偏差が平均の 1% 未満に収まることがあります。ただしばらつきの小ささは正しさの証拠ではありません。発行時間だけを測っていても安定した数字は出ます。ばらつきは必要条件にすぎず、この計測を信頼する根拠は、デバイス側のイベントを使う機構そのものと、仕事量を変えたときに時間が計算量に整合して動くこと (前節の兆候の裏返し) に置きます。

ホスト側で測る必要がある場合は、毎回の反復で完了を待ち合わせます。結果をホストに取り出すか、明示的な同期を入れます。ただしその場合、測っているのは「計算 + 待ち合わせ + データ移動」であって、カーネル実行時間ではありません。何を測っているかを明示して報告することが重要です。

第 7 回の内訳表がその実践例です。カーネルだけ、呼び出しまで、入力書き込みまで、出力読み出しまで、と段階を分けて出しました。こうすると読み手が自分の用途に合う数字を選べます。

4汚染された比は使えない

「絶対値は捨てて比だけ使う」という妥協が成立しないことを説明します。ここが実務でいちばん誘惑の強い妥協です。

2 つの実装を比べたいとき、絶対値が信用できなくても比なら意味があるのではないか、と考えたくなります。しかし成立しません。理由は、分子と分母が別々の理由で、別々の度合いに汚染されるからです。

前節の構図を思い出してください。カーネルが小さい実装では、ホスト側の発行コストが支配します。一方、演算が縦に長く並ぶ実装では、発行コストが演算数に比例して積み上がります。この 2 つを素朴な計測で比べると、前者は実際より大きく、後者もまた別の理由で大きく出ます。どちらがどれだけ歪むかは事前に分かりません。

ここから引く教訓: 汚染された計測から得た比は、大きさが信用できないだけでなく、向きが保たれる保証もありません。歪みの度合いを事前に見積もれないので、「比だけ使う」は安全な妥協ではありません。正しく測るまで、性能については何も言わないのが確実です。そして一度出した数字はアンカーになります。あとで訂正しても、最初の数字を基準に議論が進んでしまいます。

実務的な運用としては、デバイスモードで測れないうちは性能の話を保留し、代わりに「動いた」「数値が合った」という正しさの結果だけを報告するのが健全です。正しさの結果は測定方法に依存しないので、後から覆りません。

5cosine は一致の証拠にならない

正しさの測定に移ります。ここは筆者が実際に間違えた箇所です。

移植の数値検証で、参照実装との一致を cosine 類似度で報告するのはよく見る形です。しかしこれには 2 つの問題があります。

問題 1: 1 を超えます。大きなテンソルを平坦化して fp32 で cosine を計算すると、丸め誤差で 1.00002 のような値が出ます。cosine は定義上 1 を超えないので、これは計算の誤差です。「1.00002 なので一致している」と書いた瞬間に、その報告は根拠を失います。

問題 2: 鈍感です。cosine は方向だけを見るので、スケールが全体的にずれていても高い値が出ます。層ごとの比較で「cosine 0.999 だから大丈夫」と判断して、実は係数が 2 倍違っていた、ということが起こり得ます。

代わりに使うのは相対誤差です。ここでの定義は、最大絶対誤差を参照値の最大絶対値で正規化したものです (要素ごとの相対誤差ではありません。要素ごとに取ると、値が小さい要素で分母が小さくなり、はるかに厳しい指標になります)。これならスケールに依存せず、桁で議論できます。

rel = (got - ref).abs().max() / ref.abs().max()

そしてゼロという値の意味を大事にします。相対誤差が厳密に 0 なら、それは「近い」ではなく「同じ」なので、主張の強さがまったく違います。たとえば同じ NEFF を 2 回実行した結果は 0 になるべきで、0 でなければ実行環境か照合の側に問題があります。期待値がゼロである検証を工程に置くのは、非常に強い設計です。近い値を許す検証は閾値の議論になりますが、ゼロを期待する検証は議論の余地がありません。

6fp32 の一致は bf16 の一致ではない

精度に関する切り分けの話です。ここを混ぜると、移植のバグと数値ノイズが区別できなくなります。

移植の正しさのゲートは fp32 で置くべきです。理由は、bf16 では数値ノイズによってトークンが反転するので、一致率が移植の正しさを反映しなくなるからです。

特にランダムな小さい重みで作ったテスト用モデルでは、logits の上位候補が近接します。構造を持たない乱数なので、ほぼ同点の候補が並ぶのです。この状態で bf16 の丸めが入ると、トークンは簡単に入れ替わります。これは移植のバグではありません。

したがって工程はこうなります。fp32 で層ごとの一致を取り、それをゲートにする。bf16 の評価は実重みで行う。実重みなら logits に構造があるので、上位候補の差が意味のある大きさになります。

逆向きの罠もあります。小さいランダム重みで通ったから安心、とはなりません。第 4 回で見た指数の溢れは、実重みのスケールでだけ起きました。小さい重みは「反転しやすい」が「溢れにくい」ので、両方向のテストが要ります。

7不変条件で正しさを縛る

参照実装との比較だけでは足りません。サービング固有の正しさを縛る道具が要ります。

サービングでは、同じ入力に対して処理の分割の仕方が変わっても結果が変わってはいけないという性質が要求されます。これを不変条件として書けます。

もっとも効くのは次の形です。

prefill(L)  の出力  ==  prefill(k) してから decode(L-k) した出力

プロンプト全体を一度に処理した結果と、途中まで処理してから 1 トークンずつ進めた結果は一致すべきです。この検証は、状態の持ち回りが正しいかを直接突きます。第 3 回で見た「decode だけ壊れる」型のバグは、参照実装との比較では prefill で差が出ないので見逃されますが、この不変条件は捕まえます。

他にも次のような不変条件が使えます。

不変条件何を捕まえるか
パディングを変えても結果が変わらないマスクの作り方の間違い
バッチに他の要求を混ぜても、自分の結果が変わらない状態やキャッシュの取り違え (継続バッチングのバグ)
バケットが切り替わっても結果が連続する形状ごとのグラフの不整合
並列度を変えても結果が一致する重み分割と集団通信の間違い

これらは参照実装を必要としません。自分の実装の内部整合だけで検証できるので、参照実装が手元で動かない状況でも使えます。移植の初期に用意しておく価値が高い道具です。

8GPU と比べるときに揃えるもの

最後に、比較の公平性について。ここを外すと、数字が政治的な意味を持ってしまいます。

Trainium と GPU を比べるとき、揃えるべきものが 4 つあります。

  1. 計測方法。片方をデバイスイベントで測り、もう片方をホストのストップウォッチで測ると比較になりません
  2. 比較の単位。単発の演算と、融合された高性能カーネルを比べるのは構造的に不公平です。層単位、あるいはモデル単位で比べます
  3. 形状とデータ型。実運用の形状 (prefill のチャンク長、decode の 1 トークン + 状態、実際のバッチ) と実運用の型 (多くの場合 bf16) で測ります
  4. 相手が最適化されている領域かどうか。これが一番見落とされます。相手側に手で調整されたカーネルが存在する演算では、素直な実装のまま比較しても勝てません。逆に相手側も素直な実装なら、公平な勝負になります
4 番目の含意
「この演算は相手側に専用カーネルがあるか」は、比較の前に調べるべき事実です。たとえば状態空間モデルの選択的スキャンは、GPU 側で専用カーネルが揃っている領域です。そこに素直な実装をぶつけて負けたとしても、それはハードウェアの結論ではなく実装の成熟度の結論です。両者を区別して報告しないと、読み手を誤らせます。

9チェックリスト

シリーズの締めとして、数字を出す前に確認する項目を並べます。

性能を報告する前に

  1. デバイスモードで測ったか。ホスト計時なら、何を含む区間か明示したか
  2. 仕事量を変えたときに時間が妥当に動くか確認したか
  3. ばらつき (標準偏差) を出したか
  4. 形状とデータ型は実運用に寄せたか
  5. 比較相手の実装成熟度に触れたか
  6. サービング全体の数字が必要なら、ウォームアップ完了後に測ったか (ログで再コンパイルが走っていないことを確認する)。バケットの境界をまたぐ入力長の分布で測らないと、パディングの損失が数字に出ない

正しさを報告する前に

  1. 相対誤差で語っているか。cosine を根拠にしていないか
  2. fp32 でゲートを置き、bf16 は実重みで見ているか
  3. 重み読み込みの未初期化が 0 件であることを確認したか
  4. prefill と decode の不変条件を通したか
  5. 実重みのスケールで溢れが起きないことを確認したか
シリーズ全体のまとめ
移植コストは 3 層 (計算の表現・サービング契約・状態の契約) に分かれ、コンパイル経路を替えて下がると確認できたのはコスト層① (計算の表現) だけです。コスト層①を下げる経路はプラグインの公開ソース上で追跡されていますが未出荷で、プロセス内で差し替える道はライブラリ側の対応待ち、プロセスを分ける橋は運搬コストが未解決です。だから当面は、既存の経路で移植し、その中で数式の構造を選ぶことが性能を作ります。そして何をするにしても、測り方を先に固めることが全部の前提になります。

出典と確認方法: 非同期実行が既定であること、Neuron ランタイムのデバイスモード計測 API の存在は、公開されているコンテナイメージとドキュメントで確認できます。第 2 節の数字は公開イメージ上での測定です (第 7 回 §7 と同じ部分グラフ)。第 5 節の cosine の挙動、第 6 節の bf16 でのトークン反転、第 7 節の不変条件はいずれも筆者が公開プラグイン上で確認したものです。

確認時点: 本稿の記述は 2026-09-01 時点のものです。対象はプラグイン 0.21.0.1.0.0 と 0.24.0.1.1.0 の公開ソースおよび公開コンテナイメージ、公開パッケージインデックスから取得できるランタイム兼カーネル基盤ライブラリ (2.11.0.1.0.1284 / 2.12.0.1.0.1284)、コンパイラ 2.26 / 2.27 系、低レベルカーネル言語 0.5.0 / 0.6.0、PyTorch 2.11.0 です。バージョンが上がれば名前も挙動も変わりうるので、正はソースと配布物です。

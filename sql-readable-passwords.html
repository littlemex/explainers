リーダブルパスワード ― パスワードを読める形で保存

パスワードは「読めない形」ではなく「本人の入力かどうかを確認はできるが、元の文字列には戻せない形」で保存する

← SQL シリーズ目次へ

この回の前提: 第 01 回 アンチパターンとは何か (サンプル DB の accounts テーブルの構造)

この回が答える問いは「ログインのためのパスワードをデータベースにどう保存すれば安全か」です。結論を先に言うと、平文での保存も、後で元に戻せる暗号化 (可逆暗号) も不正解です。正しいのは、入力されたパスワードが正しいかどうかは確認できるが、保存した値から元のパスワードには戻せない「一方向で遅いハッシュ化」です。この回では、なぜ単純なハッシュ (md5) でも不十分なのか、そしてなぜハッシュ化は SQL の中で行うより先にアプリケーション側で行うべきなのかを、実際に計測した時間とログの仕組みから確認します。

1. 目的 ― 何をしたかったのか

ログイン機能を作るとき、データベースには「次にユーザーが同じパスワードを入力してきたとき、それが正しいかどうかを判定するための情報」を保存しておく必要があります。ここで初心者がやりがちなのは、「とりあえずユーザーが入力した文字列をそのまま保存する」という発想です。文字列をそのまま保存すれば、ログイン時の確認は 入力 = 保存した値 という単純な比較で済むため、実装としては一番簡単に見えます。

しかし、この「比較のために元の文字列をそのまま持っておく」という目的と、「漏えいしたときに被害を最小限にする」という目的は、真正面からぶつかります。この回のテーマは、この 2 つの目的を両立させる方法です。

2. アンチパターン ― どう書いてしまい、何が壊れるか

2.1 平文で保存する

最も単純なアンチパターンは、ユーザーが入力したパスワードの文字列を、そのまま列に保存することです。サンプル DB の accounts テーブルに password_plain という列を追加し、2 人のユーザーに同じパスワードを設定してみます。

ALTER TABLE accounts ADD COLUMN password_plain text;
UPDATE accounts SET password_plain = 'Summer2026!' WHERE account_name = 'alice';
UPDATE accounts SET password_plain = 'Summer2026!' WHERE account_name = 'bob';
SELECT account_name, password_plain FROM accounts WHERE account_name IN ('alice','bob');

 account_name | password_plain
--------------+----------------
 alice        | Summer2026!
 bob          | Summer2026!

この状態で、バックアップファイルが 1 つ流出したり、読み取り権限を持つ別のロールから SELECT されたりすると、全ユーザーのパスワードがそのまま読めてしまいます。被害はこの 1 つのサービスだけでは終わりません。多くの人が複数のサービスで同じパスワードを使い回しているため、ここで漏れたパスワードが別のサービスへのログインにそのまま使われてしまう (クレデンシャルスタッフィング) という二次被害も起こります。

図: 平文で保存すると、漏えいした瞬間に全ユーザーのパスワードがそのまま使える状態になる。

2.2 単純で速いハッシュ (md5) を使う

「平文はまずい」と気づいた人が次にやりがちなのが、md5() のような単純なハッシュ関数に通してから保存することです。しかし md5 には 2 つの問題があります。1 つ目は、同じ入力に対して必ず同じ出力を返すことです。実際に alice と bob に同じパスワードを設定した状態で md5 を計算すると、2 人とも同じハッシュ値になります。

SELECT account_name, md5(password_plain) AS md5_hash FROM accounts WHERE account_name IN ('alice','bob');

 account_name |             md5_hash
--------------+----------------------------------
 alice        | e56f3bb5392369b6468e744ab1da078b
 bob          | e56f3bb5392369b6468e744ab1da078b

ハッシュ値が同じということは、攻撃者が「よく使われるパスワードの md5 値を事前に全部計算した表 (レインボーテーブル)」を持っていれば、保存されているハッシュ値から元のパスワードを逆引きできてしまうということです。しかも、同じハッシュ値を持つ 2 人のユーザーは同じパスワードを使っていることまで分かってしまいます。

2 つ目の問題は、md5 の計算が非常に速いことです。実際に、10 万回の md5 計算にかかる時間を計測してみます。

\timing on
SELECT count(*) FROM (SELECT md5('try-' || g::text) FROM generate_series(1, 100000) g) s;

 count
--------
 100000
Time: 9.509 ms

10 万回のハッシュ計算が 9.509 ミリ秒、つまり 1 回あたり約 0.0001 ミリ秒で終わります。これは「ある 1 人のパスワードを、よくある候補のリストと総当たりで比較する」という攻撃を、専用のハードウェアを使わなくても高速に実行できてしまうということです。

図: md5 は同じ入力に同じ出力を返すため、事前計算した対応表 (レインボーテーブル) で逆引きしやすい。

2.3 自分で実装した可逆暗号を使う

「ハッシュだと元に戻せないから不便」と考えて、独自の可逆な暗号化 (例えば単純な XOR や、固定鍵の対称鍵暗号) を使ってしまうケースもあります。これは「暗号化の鍵さえ守れば安全」という前提に立っていますが、アプリケーションのソースコードや設定ファイルに鍵が書かれていることが多く、鍵が漏れた瞬間に全パスワードが平文に戻ってしまいます。ログイン用のパスワードは、そもそも「元に戻す」という操作自体が不要であり、不要な機能 (復号) を持たせること自体がリスクです。

3. 見つけ方 ― どんな兆候で気づくか

既存のデータベースで「パスワードらしき列が、ハッシュ関数を通さずに保存されていないか」を確認するには、列名から探すのが手早い方法です。information_schema.columns を使うと、テーブルを定義した本人以外でも機械的に洗い出せます。

SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public' AND column_name ~* 'pass(word)?'
ORDER BY table_name, column_name;

 table_name |  column_name   | data_type
------------+----------------+-----------
 accounts   | password_hash  | text
 accounts   | password_plain | text

この結果だけでは「ハッシュ化されているか」までは分かりませんが、列名の候補を絞り込んだうえで、実際に値を数件サンプリングして見れば判断できます。ハッシュ化されていれば $2a$08$... のような固定長の記号列になり、平文であればそのまま読める文字列になります。あわせて、アプリケーションのログや監視ツールに生の SQL 文が残っていないかも確認します。PostgreSQL では log_statement を all にすると実行されたすべての SQL 文がそのままログに出力されるため、もしログイン処理のパスワード比較を SQL の中で直接書いていると、入力された平文パスワードがログファイルに残ってしまいます。この設定は共有環境のログ出力量に直接影響するため、確認は本文の値を変えずに SHOW log_statement; で現状を見るだけに留めます。

4. 使ってよい場合

ログインのためのパスワードを可逆な形 (平文や復号可能な暗号) で保存してよい場合はありません。一方で、「後から元の値をアプリケーションが取り出す必要がある秘密」は、パスワードとは別の種類の情報であり、こちらは可逆暗号を使うのが正しい選択です。例えば、ユーザーに代わって外部サービスを呼び出すための API トークンは、呼び出すたびにアプリケーションがその値を使う必要があるため、一方向のハッシュにしてしまうと二度と使えなくなります。

CREATE TABLE api_credentials (
  account_id bigint PRIMARY KEY REFERENCES accounts(account_id),
  encrypted_token bytea NOT NULL
);
INSERT INTO api_credentials (account_id, encrypted_token)
SELECT account_id, pgp_sym_encrypt('third-party-api-token-xyz', 'app-level-encryption-key')
FROM accounts WHERE account_name = 'alice';
SELECT account_id, pgp_sym_decrypt(encrypted_token, 'app-level-encryption-key') AS token
FROM api_credentials;

 account_id |           token
------------+---------------------------
          1 | third-party-api-token-xyz

この例では pgcrypto の pgp_sym_encrypt/pgp_sym_decrypt を使い、暗号化鍵はアプリケーション側の設定として管理します (鍵自体をデータベースに保存すると、暗号化している意味がなくなります)。「検証できればよく、元の値は不要」ならハッシュ、「後で元の値そのものが必要」なら可逆暗号、という目的の違いで手段を選びます。

5. 解決策 ― PostgreSQL での正しい書き方

パスワードは「遅いハッシュ関数」に「ソルト (入力ごとに変える乱数)」を加えて保存します。PostgreSQL では pgcrypto 拡張の crypt() と gen_salt('bf', cost) で bcrypt 方式のハッシュを計算できます。

CREATE EXTENSION IF NOT EXISTS pgcrypto;
ALTER TABLE accounts ADD COLUMN password_hash text;
UPDATE accounts SET password_hash = crypt(password_plain, gen_salt('bf', 8))
WHERE password_plain IS NOT NULL;
SELECT account_name, password_hash FROM accounts WHERE account_name IN ('alice','bob');

 account_name |                        password_hash
--------------+--------------------------------------------------------------
 alice        | $2a$08$CnkuHTLhauzpdK0vCy/Mvuu/ktu14mpCaSOnWSuBdQtZDuMvF7JVC
 bob          | $2a$08$3f73IU.ANgo31aQL3o1vQuVKhbfZzRk/xWQy.GZK51Ur61BORDBv.

alice と bob は同じ平文パスワードですが、ハッシュ値は完全に別物です。これは gen_salt('bf', 8) が呼び出すたびに新しいランダムなソルトを生成し、それをハッシュ化の前に平文と混ぜ込んでいるためです。実際に同じ平文で 2 回計算しても、毎回違う値になることを確認できます。

SELECT crypt('Summer2026!', gen_salt('bf', 8)) AS try1,
       crypt('Summer2026!', gen_salt('bf', 8)) AS try2;

                             try1                             |                             try2
--------------------------------------------------------------+--------------------------------------------------------------
 $2a$08$xnpTshjXpe/OpsmuK44vLu0EZ0A6Zdn2L5938MZunI3ZI6GyBO67O | $2a$08$MlDk55BZ3OOD0mW6XGRTKO9ayBv/4g1tM.RQiZuM6JODPocm6jklm

bcrypt のハッシュ文字列には、使われたアルゴリズムの版・コスト係数・ソルト自体がすべて含まれています。そのためログイン確認では、保存済みのハッシュ値をそのままソルトとして crypt() に渡し、結果が保存値と一致するかを比較します。

SELECT account_name FROM accounts
WHERE account_name = 'alice' AND password_hash = crypt('Summer2026!', password_hash);
 account_name
--------------
 alice

SELECT account_name FROM accounts
WHERE account_name = 'alice' AND password_hash = crypt('wrong-password', password_hash);
 account_name
--------------
(0 rows)

ここで重要な注意点があります。この回で crypt() を SQL の中で実行して見せたのは、bcrypt の仕組みを確認するための実験です。実際のアプリケーションでは、平文のパスワードをそのまま SQL 文に埋め込んで DB サーバーに送ること自体を避けるべきです。SQL 文の実行時には log_statement の設定 (all など) 次第で、実行された SQL 文がそのままサーバーログに残り得ます。pg_stat_statements は定数部分を $1 のようなパラメータ記号に正規化して記録するため、通常はここに平文そのものは残りませんが、サーバーログに残る以上、ログの保管場所・ログ監視ツール・ログのバックアップへのアクセス権を持つ人には平文が見える可能性があります (ストリーミング/論理レプリケーションは WAL 上の変更結果だけを送るため、実行した SQL 文そのものはレプリカ側には残りません)。実務では、ハッシュ化そのものをアプリケーション側のコード (bcrypt や argon2 のライブラリ) で行い、データベースに送るのは計算済みのハッシュ値だけにするのが安全です。

図: ハッシュ化をアプリ層で行えば DB に送る SQL 文自体に平文が含まれない。SQL の中で crypt() を呼ぶと、その SQL 文自体に平文が残る。

6. PostgreSQL エンジンで考慮しておくこと

6.1 bcrypt のコスト係数は速度と耐性のトレードオフ

gen_salt('bf', cost) の cost を上げるほど、1 回のハッシュ計算にかかる時間が増えます。実際に cost=8 と cost=12 で計算回数あたりの時間を比べます。

SELECT count(*) FROM (SELECT crypt('try', gen_salt('bf', 8)) FROM generate_series(1, 100) g) s;
Time: 1389.396 ms  -- 100 回。1 回あたり約 13.9 ms

SELECT count(*) FROM (SELECT crypt('try', gen_salt('bf', 12)) FROM generate_series(1, 20) g) s;
Time: 4578.821 ms  -- 20 回。1 回あたり約 229.0 ms

md5 は 10 万回で 9.509 ミリ秒 (1 回あたり約 0.0001 ミリ秒) でした。これに対し bcrypt (cost=8) は 1 回あたり約 13.9 ミリ秒で、同じマシン上の比較で md5 の 1 回あたりの計算時間の約 14 万倍かかります。cost=12 ならさらに桁が上がり、1 回あたり約 229.0 ミリ秒です。この「遅さ」は、正規のログイン 1 回では気にならない程度 (数十ミリ秒) ですが、攻撃者が何百万回も試す総当たり攻撃には大きな負担になります。ただしコストを上げすぎると、正規のログインのたびにサーバーの計算資源を消費するため、ログイン体験とサーバー負荷のバランスを見て決める必要があります。この数字はローカルの 1 コアで計測した値であり、実際の攻撃者が専用のハードウェアや並列計算を使う場合はさらに条件が変わります。

6.2 データベースロール自体のパスワードは SCRAM-SHA-256

ここまでは「アプリケーションのユーザー」のパスワードの話でしたが、PostgreSQL に接続するための「データベースロール」のパスワードは、PostgreSQL 自身が password_encryption パラメータに従って保存方式を決めます。PostgreSQL 10 で SCRAM-SHA-256 という方式そのものが使えるようになりましたが、既定値が md5 から scram-sha-256 に切り替わったのは PostgreSQL 14 からです (PostgreSQL 10〜13 では明示的に設定しない限り既定は md5 のままでした)。

SHOW password_encryption;
 password_encryption
---------------------
 scram-sha-256

CREATE ROLE sql20_demo_user LOGIN PASSWORD 'Summer2026!';
SELECT rolname, substring(rolpassword from 1 for 14) AS rolpassword_prefix
FROM pg_authid WHERE rolname = 'sql20_demo_user';
     rolname     | rolpassword_prefix
-----------------+--------------------
 sql20_demo_user | SCRAM-SHA-256$

pg_authid.rolpassword の先頭が SCRAM-SHA-256$ であることから、PostgreSQL が自動的に SCRAM という方式でロールのパスワードを保存していることが分かります。SCRAM はチャレンジレスポンス方式の認証プロトコルで、平文のパスワードがネットワーク上にも流れない仕組みです。これはデータベースへの接続認証という PostgreSQL 自身の機能であり、この回で説明したアプリケーションのユーザーパスワード (bcrypt で自前実装する部分) とは別の仕組みである点に注意してください。pg_authid はスーパーユーザーのみが読めるカタログです。

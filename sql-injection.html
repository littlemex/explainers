SQL インジェクション ― 文字列連結で SQL を組む

ユーザーが入力した文字列を SQL 文にそのまま貼り合わせると、入力そのものが SQL の一部として実行されてしまう

← SQL シリーズ目次へ

この回の前提: 第 20 回 リーダブルパスワード (SQL 文がログや監視ツールにそのまま残ることがあるという考え方)

この回が答える問いは「ユーザーが入力した文字列を使って検索条件を作るとき、どう書けば安全か」です。結論を先に言うと、入力された文字列を SQL 文の文字列としてそのまま貼り合わせてはいけません。入力は必ず「値」として SQL エンジンに渡し、SQL の構文そのものとは混ざらないようにします。この回では、実際に文字列連結で組んだ関数が入力ひとつで全件取得や別の文の実行まで許してしまうことを実機で確認し、プレースホルダ ($1) や format() を使った正しい防ぎ方を見ます。

1. 目的 ― 何をしたかったのか

検索ボックスやログインフォームでは、ユーザーが入力した文字列を使って「この値に一致する行を探す」という SQL を実行する必要があります。SQL 文はもともと固定の文字列として書きますが、そこにユーザーの入力という「毎回変わる部分」をどう組み込むかが問題になります。一番素直な発想は、SQL 文の文字列の中に入力値をそのまま文字列として差し込んでしまうことです。これなら実装は数行で済み、動作も直感的に理解できます。

2. アンチパターン ― どう書いてしまい、何が壊れるか

2.1 文字列連結で動的 SQL を組む

サンプル DB の accounts テーブルから、名前で検索する関数を文字列連結で作ってみます。

CREATE OR REPLACE FUNCTION vulnerable_find_account(p_name text)
RETURNS SETOF accounts AS $$
BEGIN
  RETURN QUERY EXECUTE 'SELECT * FROM accounts WHERE account_name = ''' || p_name || '''';
END;
$$ LANGUAGE plpgsql;

SELECT account_id, account_name FROM vulnerable_find_account('alice');
 account_id | account_name
------------+--------------
          1 | alice

普通の入力ではこれで問題なく動きます。しかし、入力の中に SQL の構文として意味を持つ文字 (シングルクォート) が含まれていると、組み立てられる SQL 文の構造自体が変わってしまいます。x' OR '1'='1 という文字列を渡すと、組み立てられる SQL は ... WHERE account_name = 'x' OR '1'='1' になり、'1'='1' は常に真なので WHERE 条件全体が常に真になります。

SELECT account_id, account_name FROM vulnerable_find_account('x'' OR ''1''=''1');
 account_id | account_name
------------+--------------
          1 | alice
          2 | bob
          3 | carol
          4 | dave

本来 1 件しか返らないはずの検索が、1 つの入力だけで全 4 件を返してしまいました。ログイン確認であれば「パスワードを知らない相手がログインに成功してしまう」ことに直結します。

図: 入力の中の引用符が文字列リテラルを閉じてしまい、続きの文字が SQL の構文として解釈される。

2.2 セミコロンで別の文そのものを注入する (文のスタッキング)

さらに危険なのは、セミコロンを使って「もう 1 つの SQL 文」自体を注入するケースです。PL/pgSQL の EXECUTE はセミコロンで区切られた複数の文をまとめて実行できてしまいます。

SELECT count(*) AS tags_before FROM tags;
 tags_before
-------------
           6

DO $$
BEGIN
  EXECUTE 'SELECT 1; DELETE FROM tags';
END;
$$;

SELECT count(*) AS tags_after_injection FROM tags;
 tags_after_injection
----------------------
                    0

最初の文は SELECT 1 という無害な文ですが、セミコロンに続く DELETE FROM tags も実際に実行され、tags テーブルの 6 件が 0 件になりました。検索条件のつもりで渡した入力が、丸ごと別の破壊的な SQL 文として実行されてしまう、という典型的な攻撃です。

図: セミコロンで区切った 2 つ目の文も実際に実行され、無関係なテーブルのデータが削除される。

3. 見つけ方 ― どんな兆候で気づくか

PL/pgSQL の関数の定義は pg_proc.prosrc に文字列として保存されています。ここに「文字列連結 (||) と EXECUTE が近くに出てくる」という単純な正規表現をかけるだけで、文字列連結で動的 SQL を組んでいる疑いのある関数を機械的に洗い出せます。

SELECT p.proname,
       (p.prosrc ~ 'EXECUTE') AS uses_execute,
       (p.prosrc ~ '\|\|.*EXECUTE|EXECUTE.*\|\|') AS looks_like_concat_sql
FROM pg_proc p
JOIN pg_language l ON l.oid = p.prolang
WHERE l.lanname = 'plpgsql' AND p.pronamespace = 'public'::regnamespace
ORDER BY p.proname;

         proname         | uses_execute | looks_like_concat_sql
-------------------------+--------------+-----------------------
 safe_find_account       | t            | f
 safe_order              | t            | f
 safer_find_account      | f            | f
 vulnerable_find_account | t            | t
 vulnerable_order        | t            | t

この回で作った 5 つの関数のうち、文字列連結で EXECUTE している vulnerable_find_account と vulnerable_order だけが looks_like_concat_sql で true になりました。プレースホルダや format() を使っている関数は false です。この検査はあくまで疑いのある箇所を絞り込むためのヒントであり、最終的には関数の定義を実際に読んで確認する必要があります。あわせて、アプリケーションのコードレビューでは「ユーザー入力を受け取る変数が、SQL の文字列の中で + や文字列結合で繋がれていないか」を確認するのが実務上の基本的なチェック項目です。

4. 使ってよい場合

「ユーザー入力をそのまま文字列連結で SQL に貼り合わせる」ことが許される場面はありません。しかし、動的 SQL (実行時に文字列として SQL を組み立てる仕組み) 自体は、正しく使えば便利な手段です。例えば「ORDER BY に使う列名をユーザーが選べるようにしたい」というケースでは、列名は値ではなく識別子なので、プレースホルダ ($1) には渡せません。この場合は動的 SQL を使う必要がありますが、組み込む文字列を 許可リストで検証し、識別子として安全にエスケープ してから組み立てれば安全に実現できます (次の節で実機で確認します)。つまり「動的 SQL を使うかどうか」ではなく、「組み込む文字列をどう検証し、どう組み立てるか」が安全かどうかを決めます。

5. 解決策 ― PostgreSQL での正しい書き方

5.1 値はプレースホルダ ($1) で渡す

最も基本的な対策は、入力を SQL の文字列の中に貼り合わせず、プレースホルダとして渡すことです。PL/pgSQL では EXECUTE ... USING を使います。

CREATE OR REPLACE FUNCTION safe_find_account(p_name text)
RETURNS SETOF accounts AS $$
BEGIN
  RETURN QUERY EXECUTE 'SELECT * FROM accounts WHERE account_name = $1' USING p_name;
END;
$$ LANGUAGE plpgsql;

SELECT account_id, account_name FROM safe_find_account('alice');
 account_id | account_name
------------+--------------
          1 | alice

-- 同じ攻撃文字列を渡しても、ただの 1 つの値として扱われるので 0 件
SELECT account_id, account_name FROM safe_find_account('x'' OR ''1''=''1');
 account_id | account_name
------------+--------------
(0 rows)

さらに、動的 SQL そのものが不要であれば EXECUTE を使わず、普通のクエリとして書くのが一番安全です。PL/pgSQL 内の通常の SQL 文に書いた変数は、もともとプレースホルダとして扱われます。

CREATE OR REPLACE FUNCTION safer_find_account(p_name text)
RETURNS SETOF accounts AS $$
BEGIN
  RETURN QUERY SELECT * FROM accounts WHERE account_name = p_name;
END;
$$ LANGUAGE plpgsql;
SELECT account_id, account_name FROM safer_find_account('x'' OR ''1''=''1');
 account_id | account_name
------------+--------------
(0 rows)

psql から直接 PREPARE/EXECUTE を使っても同じ仕組みを確認できます。

PREPARE find_by_name (text) AS SELECT account_id, account_name FROM accounts WHERE account_name = $1;
EXECUTE find_by_name('bob');
 account_id | account_name
------------+--------------
          2 | bob

EXECUTE find_by_name('x'' OR ''1''=''1');
 account_id | account_name
------------+--------------
(0 rows)

図: プレースホルダでは SQL の構文と渡す値が最初から分離されており、値の中身が構文に影響しない。

5.2 識別子は format('%I')/quote_ident で、許可リストと組み合わせる

列名のように「値ではなく識別子」を動的に組み込む必要がある場合は、プレースホルダが使えません。この場合は format('%I', ...) や quote_ident() で識別子として安全にエスケープし、さらに許可リストでその値自体が期待通りかを確認します。

SELECT quote_ident('normal_col') AS q1, quote_ident('weird col; DROP') AS q2;
     q1     |        q2
------------+-------------------
 normal_col | "weird col; DROP"

SELECT format('%I', 'weird col; DROP') AS fmt_i;
       fmt_i
-------------------
 "weird col; DROP"

quote_ident() や %I は、渡された文字列全体をダブルクォートで囲んだ「1 つの識別子」として扱うようにエスケープします。weird col; DROP はセミコロンを含んでいますが、ダブルクォートで囲まれた 1 つの識別子名として解釈されるため、実行時には「そんな列は存在しない」というエラーになり、別の文として実行されることはありません。ただし、そもそも存在しない列名を許可してしまうのは使い勝手の面でも良くないため、実務では許可リストでの事前検証と併用します。

CREATE OR REPLACE FUNCTION safe_order(p_col text)
RETURNS SETOF accounts AS $$
BEGIN
  IF p_col NOT IN ('account_id', 'account_name', 'email') THEN
    RAISE EXCEPTION 'invalid sort column: %', p_col;
  END IF;
  RETURN QUERY EXECUTE format('SELECT * FROM accounts ORDER BY %I', p_col);
END;
$$ LANGUAGE plpgsql;

SELECT account_id, account_name FROM safe_order('account_name') LIMIT 2;
 account_id | account_name
------------+--------------
          1 | alice
          2 | bob

-- 許可リストに無い値 (注入文字列を含む) は実行前に拒否される
-- NOTICE:  rejected as expected: invalid sort column: account_id; DELETE FROM tags

値を文字列として埋め込む場合は format('%L', ...) を使います。%L は値の中のシングルクォートを正しく二重化してエスケープするため、攻撃文字列を渡しても組み立てられる SQL 文の構造は壊れません。

SELECT format('SELECT * FROM accounts WHERE account_name = %L', 'x'' OR ''1''=''1') AS built_sql;
                           built_sql
----------------------------------------------------------------
 SELECT * FROM accounts WHERE account_name = 'x'' OR ''1''=''1'

出力を見ると、攻撃文字列全体が 1 つのリテラル ('x'' OR ''1''=''1') として組み立てられており、文字列を閉じて条件を割り込ませることができていません。とはいえ、値に対しては基本的にプレースホルダを使うべきで、%L は「どうしても動的に文字列を組み立てる必要がある」場合の最終手段として使います。

図: 許可リストでの事前検証と format('%I') によるエスケープを組み合わせて、動的な識別子を安全に扱う。

6. PostgreSQL エンジンで考慮しておくこと

プレースホルダや許可リストは「SQL が注入されても実行されない」ようにする対策ですが、もう 1 つの層として「仮に注入が成功しても被害を小さくする」ための権限設計があります。アプリケーションが接続するロールには、そのアプリケーションが本当に必要な権限だけを与えます。

CREATE ROLE sql21_readonly LOGIN PASSWORD 'readonly-pass';
GRANT CONNECT ON DATABASE sql_21 TO sql21_readonly;
GRANT USAGE ON SCHEMA public TO sql21_readonly;
GRANT SELECT ON accounts TO sql21_readonly;

検索機能にしか使わないロールであれば SELECT だけを許可し、INSERT/UPDATE/DELETE の権限は与えません。実際にこのロールで書き込みを試すと拒否されます。

-- SET ROLE で sql21_readonly に切り替えてから実行 (実際のアプリでは専用の接続文字列を使う)
SET ROLE sql21_readonly;
INSERT INTO accounts (account_name, email) VALUES ('mallory','mallory@example.com');
ERROR:  permission denied for table accounts

SELECT account_name FROM accounts LIMIT 2;
 account_name
--------------
 alice
 bob

RESET ROLE;

この権限は PostgreSQL のロールベースの権限システムが SQL の実行時に必ず確認するため、アプリケーションのコードにバグがあっても、データベース側の権限という独立した層で被害を抑えられます。仮にどこかで対策が漏れて注入が成立しても、このロールでは DELETE FROM tags のような書き込み文は実行できません。プレースホルダ・許可リスト・最小権限は互いを補い合う層であり、どれか 1 つで十分と考えないことが大切です。

ラウンディングエラー ― 小数に float を使う

0.1 という何気ない数字も、2 進数の浮動小数点では正確には表せません。金額や時間のような「ぴったりでなければ困る」値には、別の型を使う必要があります

この回の前提: 第 01 回 アンチパターンとは何か(この回の読み方とサンプル DB)

金額や作業時間のような小数を保存するのにrealやdouble precision(浮動小数点型)を使うと、見た目はただの数字でも、値を足し合わせたり比較したりした瞬間に、ごくわずかなズレが出ます。結論を先に言うと、これは実装のミスではなく、2 進数で小数を表す仕組みそのものの性質です。0.1という 10 進数の値は、2 進数では無限小数になり、どこかで切り捨てるしかありません。この回では、実際にこのズレを手元の PostgreSQL で再現し、金額や正確さが必要な小数にはnumeric(p,s)を使うべき理由を確かめます。

1. 目的 ― 何をしたかったのか

バグ管理システムのaccounts.hourly_rate(時給)や、支払い記録の金額のような小数を保存したいとします。プログラミング言語の多くでは、小数はまずfloatやdoubleという型で扱うのが当たり前になっているため、データベースの列も同じ感覚でrealやdouble precisionにしてしまうことがあります。「小数を保存したい」という目的自体は当然ですが、どの型を選ぶかによって、後で痛い目を見るかどうかが決まります。

2. アンチパターン ― どう書いてしまい、何が壊れるか

実際にreal、double precision、numeric(9,2)の 3 種類の列を持つテーブルを作り、同じ値を入れて比べます。

CREATE TABLE payments (
  payment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  account_id bigint NOT NULL REFERENCES accounts (account_id),
  amount_f   real,              -- 単精度浮動小数点 (誤った設計)
  amount_d   double precision,  -- 倍精度浮動小数点 (誤った設計)
  amount_n   numeric(9,2)       -- 正しい設計 (後の章で使う)
);

INSERT INTO payments (account_id, amount_f, amount_d, amount_n) VALUES (1, 0.1, 0.1, 0.1);
SELECT amount_f, amount_d, amount_n FROM payments WHERE payment_id = 1;

 amount_f | amount_d | amount_n
----------+----------+----------
      0.1 |      0.1 |     0.10
(1 row)

この時点では 3 つとも「0.1」に見え、何の問題も無さそうです。0.1という 10 進数の値は、2 進数では0.0001100110011...のように無限に続く循環小数になり、real(32 ビット)やdouble precision(64 ビット)という決まった桁数の中には収まりません。どこかで切り捨てられた、0.1 に非常に近いだけの別の値が保存されています。

図: 10 進数の 0.1 は、2 進数の浮動小数点では無限小数になり、決まった桁数に収めるために切り捨てが起きる。

2.1 1 件だけ見ても誤差は見えない

保存した値をそのままnumericにキャストして桁数を増やしても、誤差があるようには見えません。

SELECT amount_f::numeric(30,20) AS amount_f_exact, amount_d::numeric(30,20) AS amount_d_exact
FROM payments WHERE payment_id = 1;

     amount_f_exact     |     amount_d_exact
------------------------+------------------------
 0.10000000000000000000 | 0.10000000000000000000
(1 row)

これは、PostgreSQL が浮動小数点を表示するときに「その値に戻ってこられる最短の 10 進表記」を使うためで、0.1という入力に対する最短表記はそのまま0.1になります。さらに、浮動小数点をnumericへ直接キャストする際もこの短い表記を経由するため、1 件だけを見ても問題が無いように見えてしまいます。本当の誤差は、同じ値を何度も足し合わせたときに姿を現します。

2. アンチパターン (続き)

2.2 同じ値を 10 回足すと 1.0 にならない

SELECT (sum(x) = 1.0::double precision) AS float_sum_equals_one
FROM (SELECT 0.1::double precision AS x FROM generate_series(1, 10)) t;

 float_sum_equals_one
----------------------
 f
(1 row)

-- numericなら10回足すとちょうど1.0になる
SELECT (sum(x) = 1.0::numeric) AS numeric_sum_equals_one
FROM (SELECT 0.1::numeric AS x FROM generate_series(1, 10)) t;

 numeric_sum_equals_one
------------------------
 t
(1 row)

double precisionの 0.1 を 10 回足した合計は、見た目の 1.0 とはビットレベルで一致しません。numericは 10 進数をそのまま 10 進数で扱うため、0.1 を 10 回足すとちょうど 1.0 になります。

2.3 等価比較ができない

有名な「0.1 + 0.2 は 0.3 と等しくない」という現象も実機で確認できます。

SELECT (0.1::double precision + 0.2::double precision) = 0.3::double precision AS float_eq;

 float_eq
----------
 f
(1 row)

-- textにキャストすると、numericにキャストした時には隠れていた誤差がそのまま見える
SELECT (0.1::double precision + 0.2::double precision)::text AS float_sum_as_text;

  float_sum_as_text
---------------------
 0.30000000000000004
(1 row)

興味深いのは、同じ計算結果を::numeric(30,20)に直接キャストすると、またきれいな0.30000000000000000000に戻ってしまう点です。

SELECT (0.1::double precision + 0.2::double precision)::numeric(30,20) AS float_sum_as_numeric;

  float_sum_as_numeric
------------------------
 0.30000000000000000000
(1 row)

-- numericの0.1+0.2は最初から正確に0.3
SELECT (0.1::numeric + 0.2::numeric) = 0.3::numeric AS numeric_eq;

 numeric_eq
------------
 t
(1 row)

つまり、浮動小数点の誤差を確かめたいときに::numericへ直接キャストすると、誤差が丸められて見えなくなってしまいます。誤差を正しく確認するには::textにキャストするか、=による直接の比較結果を見る必要があります。これ自体も、浮動小数点をデバッグする際に踏みやすい落とし穴です。

図: 浮動小数点の誤差を確認するなら、テキストへのキャストや直接の等価比較を使う。numeric への直接キャストは誤差を隠してしまうことがある。

2.4 大量データでの集計誤差(本物の計測)

同じ 0.1 を 100,001 件分合計すると、本来の正しい答えは 10,000.10 です。

INSERT INTO payments (account_id, amount_f, amount_d, amount_n)
SELECT 1, 0.1, 0.1, 0.1 FROM generate_series(1, 100000);

SELECT sum(amount_f)::numeric(30,10) AS total_float_real,
       sum(amount_d)::numeric(30,10) AS total_float_double,
       sum(amount_n)                 AS total_numeric
FROM payments;

 total_float_real | total_float_double | total_numeric
-------------------+---------------------+---------------
   9998.6600000000 |   10000.1000000188 |      10000.10
(1 row)

100,001 件(各 0.1)の合計は、キャッシュが温まった状態で実測すると、real(単精度)では9998.66となり、正しい答えの 10000.10 から1.44もズレました。double precision(倍精度)では10000.1000000188となり、見た目はほぼ正しいものの、小数点以下 8 桁目から誤差が残っています。numeric(9,2)だけが10000.10とぴったり一致しました。単精度のrealは仮数部が 24 ビットしかなく、10 万件を超える加算を繰り返すと誤差が無視できない大きさまで積み重なることが、この実測で分かります。

図: 100,001 件規模の実測で、real ・ double ・ numeric の集計誤差を比較する。

3. 見つけ方 ― どんな兆候で気づくか

既存のデータベースの中に、小数をrealやdouble precisionで持っている列が無いかは、information_schema.columnsのdata_typeを調べれば機械的に検出できます。

SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND data_type IN ('real', 'double precision')
ORDER BY table_name, column_name;

 table_name | column_name |    data_type
------------+--------------+------------------
 payments   | amount_d     | double precision
 payments   | amount_f     | real
(2 rows)

この問い合わせで見つかった列が、金額・在庫数・時間のように「ぴったり」であることが期待される値を保持しているなら、numeric(p,s)への変更を検討する対象になります。

4. 使ってよい場合

realやdouble precisionは、科学計測のデータ(気温、センサーの測定値)、座標、統計量のように、値そのものに観測誤差が含まれていて「相対的な精度」が問題になる場面では正当な選択です。こうした値では、2 進数表現による誤差は、そもそも測定自体に含まれる誤差よりもずっと小さく、実用上問題になりません。また、浮動小数点はnumericよりも演算が速いため(後述)、大量の科学計算を高速に行いたい場面にも向いています。問題になるのは、金額や在庫数のように「1 円単位でぴったり合っていないと困る」値に浮動小数点を使うことです。

5. 解決策 ― PostgreSQL での正しい書き方

5.1 numeric(p,s) で精度と小数点以下の桁数を宣言する

numeric(p,s)は、全体の桁数p(precision)と小数点以下の桁数s(scale)を指定して、10 進数をそのまま 10 進数で保持する型です。2.1〜2.4 で見たとおり、numeric(9,2)で保存した 0.1 は、何回足しても、どうキャストしても、正確に 0.1 として扱われます。

SELECT amount_n, amount_n::numeric(30,20) AS amount_n_exact FROM payments WHERE payment_id = 1;

 amount_n |     amount_n_exact
----------+------------------------
     0.10 | 0.10000000000000000000
(1 row)

サンプルのバグ管理データベースのaccounts.hourly_rateやbugs.hoursが最初からnumeric(9,2)で定義されているのも、時給や作業時間という「ぴったりでなければ困る」値だからです。

5.2 money 型は使わない

PostgreSQL には金額専用のmoney型もありますが、これも推奨しません。moneyを整数で割ると、小数点以下 2 桁から先が四捨五入ではなくゼロ方向に切り捨てられ、誤差が生まれます。

SELECT 10.00::money / 3 AS one_third;

 one_third
-----------
     $3.33
(1 row)

SELECT (10.00::money / 3) * 3 AS reconstructed; -- 10.00に戻らない

 reconstructed
---------------
         $9.99
(1 row)

$10.00 を 3 で割って 3 倍しても、$10.00 には戻らず$9.99 になってしまいました。1 セント(0.01 ドル)が消えています。PostgreSQL の公式ドキュメントは、moneyを整数で割ったときの挙動を「Division of a money value by an integer value is performed with truncation of the fractional part towards zero」(moneyを整数で割ると、小数部分はゼロ方向に切り捨てられる)と明記しています。これは四捨五入ではなく、常に値を小さくする方向にしか動きません。整数ではなくnumericや浮動小数点で割った場合は四捨五入になるため、同じ割り算でも割る数の型によって結果がずれることがあります。

SELECT 1.00::money / 6 AS div_by_integer, 1.00::money / 6.0 AS div_by_numeric;

 div_by_integer | div_by_numeric
-----------------+----------------
          $0.16 |          $0.17
(1 row)

$1.00 を 6 で割ると、本来の値は$0.1666...です。整数の6で割った場合はゼロ方向に切り捨てられて$0.16になりますが、6.0(numericとして解釈される)で割った場合は四捨五入されて$0.17になり、同じ割り算のはずなのに結果が 1 セントずれます。moneyは内部的には整数(通貨の最小単位の整数倍)として実装されており、桁数もlc_monetaryという実行時の地域設定に依存します。金額の計算には、桁数を自分で明示でき、割り方(切り捨てか四捨五入か)も自分で選べるnumeric(p,s)を使うべきです。

図: money 型は整数で割るたびに小数点以下 2 桁から先をゼロ方向に切り捨てるため、割って掛け直すと元の金額に戻らない。

6. PostgreSQL エンジンで考慮しておくこと

6.1 numeric の丸めは「0 から遠ざかる方向」で、銀行家の丸めではない

「データベースの丸めは銀行家の丸め(偶数への丸め)だ」という話を聞いたことがあるかもしれませんが、PostgreSQL のnumericに対するround()は、実機で確かめると 0.5 のちょうど中間の値を常に 0 から遠ざかる方向に丸めます。

SELECT round(0.5::numeric), round(1.5::numeric), round(2.5::numeric), round(3.5::numeric);

 round | round | round | round
-------+-------+-------+-------
     1 |     2 |     3 |     4
(1 row)

0.5→1、1.5→2、2.5→3、3.5→4 と、すべて大きい方向に丸められています。これは偶数への丸め(2.5→2 になるはず)ではありません。対照的に、同じ中間値をdouble precisionに対してround()すると、多くの環境では偶数への丸め(銀行家の丸め)になります。

SELECT round(0.5::double precision), round(1.5::double precision), round(2.5::double precision), round(3.5::double precision);

 round | round | round | round
-------+-------+-------+-------
     0 |     2 |     2 |     4
(1 row)

こちらは 0.5→0、1.5→2、2.5→2、3.5→4 と、すべて近い方の偶数に丸められています。PostgreSQL の公式ドキュメントも「For numeric, ties are broken by rounding away from zero. For double precision, the tie-breaking behavior is platform dependent, but "round to nearest even" is the most common rule.」(numeric では 0 から遠ざかる方向に丸め、double precision での丸め方はプラットフォーム依存だが、多くの場合は偶数への丸めになる)と明記しています。同じround()という関数名でも、型によって丸め方の規則そのものが違うという点は見落としやすい罠です。

図: numeric の丸めは 0 から遠ざかる方向、double precision の丸めは(多くの環境で)近い方の偶数という、逆の規則になっている。

6.2 numeric は real/double より計算コストが高い

numericは任意精度の 10 進演算をソフトウェアで実装しているため、CPU が直接サポートする 2 進浮動小数点より計算コストが高くなります。テーブルからの集計ではディスク I/O の影響が大きすぎて差が埋もれてしまうため、generate_seriesで 100 万回の掛け算と合計だけを行い、計算そのもののコストを比較します。

EXPLAIN (ANALYZE, BUFFERS)
SELECT sum(x::double precision * 1.000001::double precision) FROM generate_series(1, 1000000) x;
 Execution Time: 174.790 ms

EXPLAIN (ANALYZE, BUFFERS)
SELECT sum(x::numeric * 1.000001::numeric) FROM generate_series(1, 1000000) x;
 Execution Time: 197.744 ms

100 万回の掛け算と合計で、double precisionは 174.790 ミリ秒、numericは 197.744 ミリ秒でした。複数回実測したところ、差の大きさは実行ごとに 1 割弱から 2 倍近くまで大きくばらつきましたが、numeric が double precision と同じか遅いという方向は常に一貫していました。倍率そのものは環境と負荷で変わるので、目安以上の意味は持たせないでください。この差は、金額のような正確さが必要なデータに対して払う対価であり、2.4 で見た誤差を避けられることを考えれば、多くの場面で許容できるコストです。

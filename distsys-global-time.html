グローバル時刻と外部一貫性 ― TrueTime ・ HLC ・ Calvin が「順序」をどう作るか

物理時計のズレをゼロにはできない以上、3 つの実在システムがそれぞれ別の代償を払って「正しい順序」を作っている

← 分散システム シリーズ目次へ

この回の前提: 第 13 回 一貫性モデル、第 15 回 時間と順序、第 25 回 合意 Paxos / Raft、第 34 回 不可能性とビザンチン障害

異なる機械の物理時計は、どれだけ NTP で合わせても必ず数 ms 〜 数十 ms のズレを残す。そのズレがある限り、「どちらの出来事が先に確定したか」という外部一貫性 (external consistency, 実世界の時間の前後関係とシステムが記録する順序が一致すること) を素朴な方法では保証できない。Google の Spanner はズレの範囲を明示してその分だけ待つ (TrueTime と commit wait) ことで解決し、HLC (Hybrid Logical Clock) は論理時計と物理時計を 1 つの値に融合して待たずに因果関係を保ち、Calvin は時計そのものに頼らず実行前に全員で順序を決め切ってしまう。この回では、3 つの実在するシステムが同じ問題にどう異なる代償を払って答えたかを、一次文献の記述に基づいて確認する。

1. 外部一貫性とは何か、なぜ物理時計だけでは作れないのか

第 13 回で見た線形化可能性は「どのノードで読んでも最新の書き込みが見える」ことを保証しますが、複数のトランザクションに割り振る順序そのものが、実世界の時間の流れと一致している保証まではしません。外部一貫性 (external consistency) は、トランザクション $T_1$ が実世界の時間として $T_2$ の開始より前に完了していたなら、システムが記録する順序 (コミットタイムスタンプ) も必ず $T_1 < T_2$ になることを要求する、より強い性質です。

素朴には「各サーバーのローカル時計を読んでタイムスタンプにすればよい」と考えたくなりますが、これは成立しません。NTP (Network Time Protocol) で同期していても、サーバー間の時計には数 ms 〜 数十 ms のズレが残ります。$T_1$ が時計の進んだサーバーで確定し、$T_2$ が時計の遅れたサーバーで開始されると、実世界では $T_1$ が先でも、記録されたタイムスタンプ上は $T_2$ の方が小さい値になってしまうことがあります。

図: 実世界では T1 が先でも、ノード間の時計のズレでタイムスタンプの大小が逆転しうる。

2. TrueTime と commit wait ― ズレの範囲を認めてその分だけ待つ

Google の Spanner (OSDI 2012 論文) は、時計のズレをゼロにしようとするのではなく、ズレの範囲そのものを API で明示するという逆転の発想を取りました。TrueTime API の中心は TT.now() で、これは単一の時刻ではなく区間 [earliest, latest] を返します。この区間は、呼び出しが実際に起きた絶対時刻を必ず含むことが保証されます。区間の半幅を $\epsilon$ (エプシロン、不確かさの大きさ) と呼び、論文の実運用環境では GPS クロックとセシウム原子時計を各データセンターに設置し、$\epsilon$ は 1 ms から 7 ms の間をのこぎり波状に変動し、平均すると概ね 4 ms 程度に収まると報告されています。

この区間を使って、Spanner は 2 つのルールで外部一貫性を作ります。Start ルール: 書き込みトランザクションのコミットタイムスタンプ $s$ は、コミット要求を受け取った時点の TT.now().latest 以上の値に決める。Commit Wait ルール: コミットレコードを確定させて他のノードに見せる前に、TT.after(s) が真になるまで待つ。つまり「このタイムスタンプ $s$ は確実に過去になった」と言える時刻まで、結果を外部に公開しない。これにより $s$ は必ずトランザクションの実際のコミット完了時刻よりも小さくなり、後から始まる別のトランザクションは必ずより大きいタイムスタンプを得ます。論文は、この待ち時間が平均で $2\epsilon$ 程度になると報告しています。

図: s を latest から取り、公開前に待つことで、s は必ず実際のコミット時刻より小さくなる。

3. HLC ― 待たずに因果関係を保つ

TrueTime は専用の GPS / 原子時計というハードウェアと、commit wait という待ち時間のコストを払います。Kulkarni, Demirbas らの HLC (Hybrid Logical Clock) 論文は、特別なハードウェアも待ち時間も無しに、第 15 回で見た Lamport の論理時計の利点 (因果関係 $e \to f \Rightarrow hlc(e) < hlc(f)$ を保つ) と、物理時計の利点 (値が実時間に近く、人間にも扱いやすい) を両方得ようとしました。

素朴に「ローカル時刻と論理時計の大きい方を取る」だけでは、物理時計の値と論理カウンタの値が混ざってしまい、ズレが無限に蓄積するという反例が論文で示されています。HLC はこれを避けるため、値を $(l, c)$ の組で持ちます。$l$ は「これまでに見た物理時刻の最大値」を表し、$c$ はその $l$ が変化しなかったときだけ増える因果関係用のカウンタです。イベントごとに $l$ を自分のローカル時刻と相手から受け取った $l$ の大きい方に更新し、$l$ が変わらなかった場合だけ $c$ を増やします。この結果、$l$ は常に物理時刻に近い値を保ちながら ($O(1)$ の整数 2 つで表現でき)、因果関係の順序も壊れません。

ただし HLC は TrueTime と同じ保証を与えるわけではありません。$hlc(e) < hlc(f)$ が成り立っても、$e$ と $f$ が本当に因果関係にあるとは限らず (一方向の含意しか成り立たない)、Spanner のように「必ず過去になるまで待つ」commit wait の代わりはできません。CockroachDB は HLC を採用しつつ、読み取り時に生じうる不確実性区間に対しては、トランザクションの再試行で対処する設計を取っています。

図: l は物理時刻に近い値を保ち、c は l が変わらない間だけ因果の順序を記録する。

4. Calvin ― 時計を使わず、実行前に順序を決め切る

TrueTime も HLC も「時計を使って順序を作る」という前提を共有していますが、Yale 大学の Calvin (SIGMOD 2012 論文) はこの前提自体を外しました。Calvin はシステムを sequencer (シーケンサ) ・ scheduler (スケジューラ) ・ storage の 3 層に分けます。sequencer は 10 ミリ秒ごとの epoch (エポック) 単位でクライアントからのトランザクション要求を集め、そのバッチを (非同期または ZooKeeper を使った Paxos ベースの同期で) 全レプリカに複製します。この時点で、どのトランザクションをどの順序で実行するかというグローバルな実行順序がすでに全レプリカで一致しています。

scheduler 層はこの確定した順序に従って決定論的ロックを取ります。通常の 2 相ロックとの違いは、ロックを要求する順序そのものを sequencer が決めた順序と一致させ、ロックの許可も要求された順序を守って与える、という 2 つの制約が追加されている点です。これにより、全レプリカが同じ入力を同じ順序で実行すれば、ネットワークの遅延や障害のタイミングが多少ずれても、最終的な状態は必ず一致します。順序の合意は実行前に 1 回で済んでいるため、トランザクションのコミット時に参加者間で合意を取り直す 2 相コミットが不要になります。

代償は、各トランザクションが読み書きする対象 (read/write set) を実行前にあらかじめ宣言しておく必要があることです。何を読むかが実行結果に依存するようなトランザクションは、この前提と相性が悪く、別の工夫が必要になります。また 10 ミリ秒という epoch の単位は、どのトランザクションも少なくともそのバッチ分の待ち時間を前払いすることを意味します。

図: 順序の合意を実行前に 1 回済ませることで、コミット時の合意が要らなくなる。

5. 3 つを並べる ― 何に代償を払っているか

TrueTime、HLC、Calvin はいずれも「物理時計はズレる」という同じ事実から出発していますが、代償を払う場所がそれぞれ異なります。TrueTime は GPS / 原子時計という専用ハードウェアと、commit wait というコミット後の待ち時間を払います。HLC は特別なハードウェアも待ち時間も不要ですが、保証できるのは一方向の因果関係のみで、Spanner ほど強い外部一貫性の保証は単独では作れません。Calvin は時計への依存そのものを無くす代わりに、各トランザクションの読み書き対象を実行前に宣言する制約と、epoch 単位の実行前の待ち時間を払います。

「どれが優れているか」という問いには意味がありません。アプリケーションがどの制約を飲めるか (専用ハードウェアを置けるデータセンターかどうか、読み書き対象を事前に宣言できる設計かどうか) によって、選ぶべきものが変わります。

図: 同じ問題に対して、代償を払う場所と種類がそれぞれ異なる。

6. 実システムでの使われ方

Cloud Spanner は TrueTime と commit wait を基盤に、複数リージョンに分散したまま外部一貫性のある読み書きトランザクションを提供します。CockroachDB は専用ハードウェアを前提にできない一般的なクラウド環境向けに HLC を採用し、クロックの不確実性区間に関わる読み取りについてはトランザクションの透過的な再試行で対処する設計を公式に説明しています。Calvin は商用データベースそのものではありませんが、決定論的な実行順序の事前合意によって 2 相コミットを避けるという設計思想は、後続の分散データベース研究に広く影響を与えました。

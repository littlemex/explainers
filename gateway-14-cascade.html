第 14 章 入れ子は、ルーティングをエスカレーションの問題に変える

この章の 3 行 能力が入れ子だと節約の形は 1 つに決まる。安い層で試して、落ちたら投げ直す。 そこでずっと計算していなかった構成を測った。箱を 1 段も挟まない「安い API から高い API へ」が 20 件を $5.9960 で解き、箱入りの最良が $5.0412。箱の寄与は 1 タスク 4.8 セント、15.9%である。 そしてその 15.9% はオラクルを前提にした数字で、本番にオラクルは無い。

入れ子だと、節約の形は 1 つしか残らない

第 12 章で 3 層の能力が厳密な入れ子だと分かった。第 3 章で外していた 9 件も加えて 24 件を測り直し、 通信の失敗で終わった 4 件を除いた有効 20 件でも反例は 1 件も出なかった。箱が解けた課題は必ず安い API も解け、安い API が解けた課題は必ず高い API も解けている。20 件で 0 件なので真の割合の上限は おおよそ 15% と言える。

入れ子には強い含意がある。ルーティングでは品質が上がらない。箱は上の層が取りこぼしたものを 拾えないので、どう賢く振り分けても到達できる上限は「一番強い層を単体で使ったとき」のままである。 残る効果は費用だけで、しかも費用を下げる形も 1 つに決まる。安い層で試して、駄目なら上に投げ直す。 先に難易度を予測して振り分ける必要はない。箱に投げること自体が、いちばん精度の高い難易度の探りになる。

ずっと計算していなかった構成: 箱を 1 段も挟まない

ここまでの章はすべて「箱から始める」構成を値付けしてきた。ところが箱を使わない 2 段構成、 つまり安い API で試して落ちたら高い API に投げ直す形を、一度も計算していなかった。固定費ゼロ、 キャパシティ計画ゼロ、上限を突き抜ける心配ゼロの構成である。

その 15.9% で機械代が払えるのか

箱は使われていようといまいと時間あたり $15.2174 を請求する。1 タスク 4.8 セントの節約でそれを 回収するには、毎時 319 タスクを通し続ける必要がある。

実測では箱の 1 エピソードが中央値 76 秒・平均 105 秒だった。同時に走らせる本数で割ると 到達できる本数はこうなる。

結果でまったく区別できず、価格だけが 20 倍違う集合が実在した 後から測った 8 件では、3 層が同じ 8 件を解き、同じ 1 件を落としている。品質の差は 1 件も無い。 一方で請求は $0.3283 対 $0.9634 対 $6.4415 で、いちばん安い層といちばん高い層が 20 倍離れている。 この集合ではモデルを選ぶ理由が価格しかない。統合値が箱の側に動いたのは、こういう集合が 母集団に含まれていたからである。

ここで注意しておくと、これは「後から測った 9 件のほうが簡単だった」という話でもある。 安い API も高い API もそこでは取りこぼしが減っているので、箱だけが得意だった集合ではない。 入れ子は破れていない。

そして 15.9% は、オラクルを前提にした数字である

上の表のすべてに共通する前提を書いておく。どの段でも「落ちたことが分かる」と仮定している。 ベンチマークではそれが成立する。エピソードが終わったあと、そのリポジトリ自身のテストがパッチを判定 するからである。

本番にそのテストは無い。あればモデルに投げていない。だから 15.9% は 「実装できる方針の値段」ではなく「実装できない方針の上限」であって、実際に手に入るのは そのうち検出器が拾えるぶんだけになる。

その検出器を探した結果が第 15 章である。先に結論を書いておくと、3 系統とも事前に決めた基準を 満たさなかった。

この章で言えないこと

20 件である。入れ子は「この 20 件でそうだった」という事実で、確率の主張ではない。 3 つの対比較のうち有意水準 5% を切るのは箱と高い API の間だけで、箱と安い API の間は解けた数では 分離できていない。分離できているのは価格だけである。

箱の 1 タスク 4.8 セントは限界費用である。箱が仕事で埋まっているときのトークン単価で 計算した数字で、稼働率が前提にある。エピソードの合間に遊んでいる箱は、それでも時間あたり $15.2174 を 請求する。これは請求書ではない。

レイテンシを 1 秒も測っていない。箱を先に試す構成は、API の試行が始まる前に中央値 76 秒の 箱の時間を積む。対話的な用途ではこれが費用とは無関係に失格の理由になりうるが、この章の表には その軸が入っていない。

可用性の損失が両側にある。高い API は 24 件のうち 4 件で、ゲートウェイが HTTP 200 と空の応答を 返してエピソードが終わった。うち 1 件は $9.2452 を課金したあと 28 手目で死んでいる。 箱の側も、15 件を走らせている途中でノードの containerd が落ちて 2 つの複製が別ノードへ移り、 モデルを読み込む 5 分間の全リクエストを失って 3 件をやり直した。どちらもモデルの性質ではないが、 本番では再試行を通じてカスケードの算術を変える。この章はそれを数えていない。

箱を挟まない構成も同じ問題を抱えている。$5.9960 もオラクルの数字で、安い API が落ちたことを 知る必要がある。それでもこちらを基準線に置くのは、固定費が無いからである。判断を間違えたとき、 箱なしの構成が無駄にするのは API 呼び出し 1 回だが、箱入りの構成は呼び出し 1 回と、借りてしまった 機械の時間を無駄にする。

第 31 章 業界はどこで判定を外に出しているか

この章の 3 行 ここまでの判定器 (J-lens ゲート) を、どこに配線するかを考える前に、業界がすでに判定をゲートウェイの 外に出すためにどんな型を使っているかを実コードから確定させる。Envoy の ext_proc と Gateway API Inference Extension (GIE) の EndpointPicker (EPP) はエンドポイント単位の状態しか 扱えず、ここまでの門が読む「prefill 後の残差」は、EPP が呼ばれる時点にはまだ存在しない。

1. 実コードから確定した型

Envoy の ext_proc (external processing、外部プロセスにリクエスト処理を委譲する拡張点) と、その上に立つ Kubernetes Gateway API Inference Extension (GIE) の EndpointPicker (EPP) は、 LLM サービングのルーティングを実際に外部化している数少ない業界標準である。EPP の拡張点を型として 書き出すとこうなる。

要素型・内容
入力Request{RequestId, TargetModel, Prompt, Headers} と、候補となる エンドポイントの一覧
拡張点 1Filter — 候補を絞り込む
拡張点 2Scorer — 各エンドポイントを [0, 1] に正規化して採点する。 重みは設定側が持つ
拡張点 3Picker と ProfileHandler — 採点を集約して 1 つを選ぶ
出力PickResult{Endpoint, Fallbacks, MutatedBody, ExtraHeaders}
呼ばれるフェーズProcessingRequest_RequestHeaders / _RequestBody
宛先の伝達選ばれた Pod の IP を x-gateway-destination-endpoint ヘッダに書く

既存の scorer は queue-scorer (待ち行列の長さ)、kv-cache-utilization-scorer (KV キャッシュの使用率)、prefix-cache-scorer (プレフィックスキャッシュのヒット予測)、 lora-affinity-scorer (LoRA アダプタとの適合) の 4 つで、すべてがエンドポイント単位 (どの Pod/レプリカが空いているか、キャッシュを持っているか) の量である。

図: EPP は誰の「前」に立っているか

EPP はエンジンより手前で呼ばれるので、prefill 後の残差はまだ存在しない。

2. 決定的な食い違い

EPP はエンジンの上流で呼ばれるので、第 23 章の門が読む量はその時点に存在しない 第 22〜25 章の門はどれもprefill を終えたモデルの内部残差を読む。EPP の拡張点が呼ばれるのは リクエストのヘッダ・本文を見た直後で、まだどのエンジンにも到達していない。 つまりこの門を業界標準の EPP プラグインとしてそのまま実装することはできない — 読みたい量を生む処理そのものが、EPP の後で初めて起こる。

3. 和解の形

手段できること限界
ExtraHeaders / MutatedBody観測をリクエストに乗せて運ぶ まだ観測が存在しない段階では空である
Fallbacksエスカレーション先を先に用意しておく 「読んでから決める」ではなく「決めてから読む」順序になる
2 リクエスト方式1 回目で prefill だけ行い門を読み、2 回目で decode を委譲する prefix cache (直前の文脈をキャッシュしておく仕組み) が効くことが前提。効かないと prefill を 2 回払う

もっとも自然な妥協は、エンジン側 (プラグインではなく vLLM 等の内部) に第 1 段の門を実装し、 決定をヘッダで EPP 側に伝え返すという向きである。これは EPP の標準的な拡張点の想定とは逆方向の データフローで、GIE の plugin 面には、結果を方策へ書き戻す拡張点 (PostResponse など) が無い。つまり「エンジンが判定し、ルータがそれを使う」という向きの配線は、 現行の GIE の型には収まらない。

4. 公開実測からの警告: 1 本の軸だけを見ると混雑を作る

lora-affinity 単独 0.92 req/sec 対 複合スコアリング 1.24 req/sec 公開されている実測では、lora-affinity-scorer だけでルーティングすると 0.92 req/sec しか出ず、複数の scorer を組み合わせると 1.24 req/sec に上がる、と報告されている。 単一の軸だけを見るスコアラーは、他の軸 (待ち行列や KV キャッシュの使用率) を無視して混雑を作る。 第 22〜30 章の判定器を EPP に足す場合も、単独の軸として置くのではなく、既存の scorer と 同じ重み付けの枠に載せる必要がある。

この章が主張しないこと

ここで確定させたのは EPP と ext_proc の型と、既存 scorer の性質だけであり、 第 1 段の門を実際にエンジン側に実装して EPP と組み合わせる実験はまだ行っていない。

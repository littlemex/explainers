VLIW ── 静的スケジューリング

1 つの長い命令に複数演算を詰め、並列化の判断をハードからコンパイラへ移す

0この章の狙い

01 章で描いた「静的 ⇆ 動的」の軸。この章は、静的側の代表格 VLIW を、コンパイラが実際に演算を詰める様子を動かしながら理解します。

一言でいうと
VLIW（Very Long Instruction Word、超長命令語）は、1 個のとても長い命令の中に、複数の演算ユニットへの操作をまとめて詰め込むアーキテクチャです。「どの演算をどのサイクルにどのユニットで実行するか」を、実行時のハードではなくコンパイル時にコンパイラが決め切り、それをそのまま命令（バンドル）にエンコードします。ハードは依存チェックも順序入れ替えもしないと割り切れるので単純・低電力。代償は、性能がコンパイラの巧拙に直結し、埋められないスロットが NOP になってコードが膨らむこと。この割り切りが見事に当たる領域が深層学習で、その先に MN-Core があります（07 章）。

1バンドル ── 命令の中の並列

VLIW 命令は、各機能ユニットに対応する固定の「スロット」に分かれています。

1 つの VLIW 命令（バンドル）は、たとえば「ALU で加算、別の ALU で減算、乗算器で積、ロードユニットでメモリ読み出し」を同時に指示する、複数スロットの塊です。コンパイラが並列に実行できる独立な演算を見つけられなければ、そのスロットには NOP（何もしない）が入ります。

┌─── 1 つの VLIW 命令（バンドル）= 1 サイクルで同時実行 ───┐
│ ALU0 │ ALU1 │ MUL │ MEM │ BR │
├──────────────┼──────────────┼──────────────┼──────────────┼───────┤
│ add r3,r1,r2 │ sub r6,r4,r5 │ mul r9,r7,r8 │ ld r10,[r11] │ NOP │
└──────────────┴──────────────┴──────────────┴──────────────┴───────┘

スーパースカラ CPU も 1 サイクルに複数命令を発行しますが、その割り当てを実行時にハードが動的に決めます。VLIW は同じ割り当てをコンパイル時に確定させ、命令に焼き込む。「賢いハード＋素朴な命令列」か、「素朴なハード＋賢いコンパイラが作り込んだ命令列」か、の違いです（01 章）。

2【体験】コンパイラはこう詰める

ハードウェアは両方とも同じ（乗算器 ×2、メモリ ×2 の 4 スロット、命令はプログラム順に発行するインオーダー機）です。違うのは命令の順序だけ。一方は素朴な順序（積の直後にその書き出しを置いたソースそのまま）、もう一方はコンパイラが並べ替えた後。差はすべてコンパイラの並べ替えによるもので、ハードの幅の違いではありません。積のレイテンシは 3。実行を押すと 1 サイクルずつ進みます。素朴な順序では、各書き出しが直前の積の完成（積を発行した 3 サイクル後）まで発行できず空転する点に注目してください。

# ハード共通: MUL×2, MEM(load/store)×2 の 4 スロット・インオーダー発行
# 素朴な順序: 積のすぐ後に書き出しを置いている
o0 = v0 * w0 [MUL,3];  store o0 [MEM,1]  # store は o0 の完成(発行の3サイクル後)まで待つ
o1 = v1 * w1 [MUL,3];  store o1 [MEM,1]  … o5 まで
# コンパイラの並べ替え後: 積 o0..o5 を先に、その後 store o0..o5
演算を発行 ストール（次の演算のレイテンシ待ちで進めない） NOP（空きスロット）

示しているのは、同じプログラムでも、コンパイラが依存とレイテンシを読んで独立演算を並べ直すだけで必要サイクル数が縮むという事実です。VLIW ハードはこの詰めた命令列を流すだけで並列性を得ます。逆に、コンパイラが下手に詰めれば NOP だらけになり、ハードの並列度は活きません ── だから VLIW はコンパイラが主役なのです。

3レイテンシ隠蔽という仕事

ロードや乗算は、結果が出るまで数サイクルかかります。その待ち時間をどう埋めるかがコンパイラの腕です。

上のデモで「コンパイラなし（素朴な順序）」を実行すると、各書き出しが直前の積の完成（レイテンシ 3）を待って stall（空転）していたはずです。インオーダー発行のハードは、後ろにある独立な積を勝手に前へ持ってこられないため、待つしかありません。コンパイラが積をすべて先に、書き出しを後に並べ替えておけば、積のレイテンシの裏で次々と別の積を発行でき、空転が消えます。ある演算の結果待ちの時間に依存の無い別の演算を差し込む ── これがレイテンシ隠蔽で、静的スケジューリングの中核の仕事です。デモの 2 つは全く同じハードウェアで、違いは命令の順序だけ。速さの差はコンパイラが生んでいます。

コンパイラの重責。 インターロック（ハードによる依存待ち）を持たない露出パイプライン型の設計では、コンパイラが固定レイテンシを 1 サイクルでも読み違えると、まだ出ていない結果を使って計算が壊れます。一方、キャッシュミスのように実行時にしか分からない可変レイテンシは静的に読めないため、実機の多くはメモリ待ちを検出して全体をストールさせるインターロックを持ちます（Itanium 等はロードにインターロックを備え、この場合は正しさは保たれ性能だけが落ちます）。いずれにせよ VLIW コンパイラはハードの動作モデルを正確に持ち、サイクル単位で命令を並べる必要があり、この難しさが開発コストの高さの正体です。

より高度な技法 ── ループ反復をまたいで並列化するソフトウェアパイプライニング、分岐を消すプレディケーション、実行されやすい経路を直線化するトレーススケジューリングなど ── は、次章 04 で扱います。

4代表例と長所・短所

製品 / 系統用途備考
Intel Itanium（IA-64 / EPIC）サーバ CPUVLIW の思想を汎用 CPU に持ち込んだ野心作。厳密には古典 VLIW と異なり、ストップビットによる並列指定やインターロックを持つ EPIC 方式。バイナリ互換とコンパイラ依存の難しさで商業的には苦戦
TI C6000 系 DSP信号処理VLIW が最も成功した領域。規則的なループが多い DSP と好相性

Transmeta Crusoe / Efficeon低電力 CPU内部は VLIW、x86 を実行時にプロファイルしながら動的翻訳する（動的翻訳＋静的発行のハイブリッド）
一部の AI アクセラレータ深層学習規則的な行列演算に静的スケジューリングで電力効率を追求（Hexagon NPU 系、MN-Core など。なお TPU はシストリック＋別方式、GPU は SIMT で VLIW ではない）
長所短所
ハードが単純で電力効率が高い（掘る回路が要らない）／性能が予測可能／コンパイラは全体を見渡して大域最適化できる NOP でコードが肥大／ユニット数やレイテンシが変わると再コンパイルが要り互換性が弱い／キャッシュミス等の動的遅延を静的に隠せない／コンパイラが極めて難しい
なぜ汎用 CPU では主流にならなかったのか。 分岐が多く、メモリアクセスが不規則で、既存バイナリ互換が必須な汎用ワークロードでは、上記の短所が致命的でした（Itanium の苦戦が象徴）。一方、DSP や一部の深層学習アクセラレータのように計算パターンが規則的・分岐が少なく・専用コンパイラと一体で提供できる領域では、VLIW 的な静的スケジューリングが電力効率で大きく優位に立ちます。

5なぜ深層学習と相性が良いか

VLIW の弱点（分岐・不規則アクセス・互換性）が、密な行列積が支配的な範囲では問題になりにくいからです。

この「なぜ深層学習が静的側に寄れるのか」という議論は 01 章 §5 で詳しく扱いました（行列積主体で分岐が少なく、形が既知でアクセスが見通せ、毎回コンパイルが前提。ただし GPU が主流な理由や MoE 等の動的性という留保も 01 章に記載）。ここでは VLIW 固有の含意を 1 つだけ加えます。VLIW の「命令に並列と順序を焼き込む」形式は、この規則的なワークロードと特に相性が良いという点です。

だからこそ、MN-Core は VLIW 命令フォーマットを採用し、命令ワードで演算を明示的にスケジュールする設計を選びました。キャッシュも分岐予測も持たず、全サイクルをコンパイラが決める ── VLIW 思想を極限まで押し進めた姿と、その公式の説明は、次の 07 章で詳しく見ます。

フィア・オブ・ジ・アンノウン ― NULL を値として扱う

NULL は「0」や「空文字列」と同じ値ではなく、「分からない」という状態である。これを普通の値のように比較・演算すると、行が静かに消えたり結果が静かに壊れたりする

この回の前提: 第 05 回 キーレスエントリ (NOT NULL 制約と外部キーの基本)

「未割当の担当者を探す」つもりで書いた NOT IN が、何も間違っていないように見えて 0 行を返すことがあります。結論を先に言うと、原因はほぼ必ず NULL です。PostgreSQL の NULL は「真」でも「偽」でもない第 3 の状態 (不明) を表し、比較や論理演算に 1 つでも混ざると、結果全体が静かに不明へ倒れることがあります。この回では、実際に PostgreSQL 18 で三値論理の真理値表、NOT IN の罠、集約や文字列結合での NULL の伝染を確かめ、COALESCE や IS DISTINCT FROM でどう防ぐかを見ます。

1. 目的 ― 何をしたかったのか

バグ管理システムの bugs.hours (作業時間) や bugs.assigned_to (担当者) のように、「まだ値が決まっていない」という状態を表したい列があります。SQL はこの「値が無い」状態を表すために NULL という特別な印を用意しています。NULL は 0 でも空文字列でもなく、「その値が何であるかが分からない」ことを示す印です。

この「分からない」という状態を、0 や空文字列のような普通の値として比較・演算してしまうと、見た目には正しそうな SQL が静かに間違った結果を返します。この回では、その具体的な壊れ方と、壊れないための書き方を確認します。

2. アンチパターン ― どう書いてしまい、何が壊れるか

2.1 三値論理 ― NULL は「真」でも「偽」でもない

SQL の論理式は真 (true)・偽 (false) に加えて、不明 (NULL) という第 3 の結果を持ちます。これを三値論理と呼びます。実際に確認します。

SELECT true AND NULL AS t_and_n, false AND NULL AS f_and_n,
       true OR NULL AS t_or_n, false OR NULL AS f_or_n, NOT NULL AS not_n;
 t_and_n | f_and_n | t_or_n | f_or_n | not_n
---------+---------+--------+--------+-------
 (NULL)  | f       | t      | (NULL) | (NULL)

false AND NULL は「もう一方が何であれ偽」なので false に確定し、true OR NULL も「もう一方が何であれ真」なので true に確定します。しかし true AND NULL や false OR NULL のように、結果が「分からない方の値」次第で変わる場合は、答えも NULL (不明) のままになります。

ANDtruefalseNULL
truetruefalseNULL
falsefalsefalsefalse
NULLNULLfalseNULL

最も誤解されやすいのが等価比較です。

SELECT NULL = NULL AS eq, NULL <> NULL AS neq, NULL IS NULL AS isnull;
 eq     | neq    | isnull
--------+--------+--------
 (NULL) | (NULL) | t

NULL = NULL は true ではなく NULL (不明) です。「分からない値」と「分からない値」が等しいかどうかは、やはり分からないからです。NULL かどうかを確かめるには、専用の述語 IS NULL を使う必要があります。

図: SQL の論理式は true / false に加えて NULL (不明) という第 3 の結果を持つ。

2.2 アンチパターン ― NOT IN サブクエリに NULL が混ざる罠

サンプル DB の bugs には、まだ誰にも割り当てられていない行があります (assigned_to が NULL)。

SELECT bug_id, assigned_to FROM bugs ORDER BY bug_id;
 bug_id | assigned_to
--------+-------------
      1 |           2
      2 |           3
      3 |      (NULL)
      4 |           3
      5 |           2

「一度もバグを割り当てられていない担当者」を探すつもりで、次のように書きます。実際のデータでは alice (account_id=1) と dave (account_id=4) がそれに当たるはずです。

SELECT account_id, account_name FROM accounts
WHERE account_id NOT IN (SELECT assigned_to FROM bugs)
ORDER BY account_id;
 account_id | account_name
------------+--------------
(0 rows)

0 行です。エラーにもならず、静かに間違った (空の) 結果を返しています。原因は NOT IN の内部の仕組みです。x NOT IN (a, b, c) は x <> a AND x <> b AND x <> c と同じ意味で評価されます。サブクエリの候補の中に NULL が 1 つでもあると、その行との比較 (x <> NULL) が必ず NULL になり、三値論理の AND の性質により、全体の結果も確定して false にはならず NULL (不明) になります。WHERE 句は結果が true の行だけを残すので、NULL と評価された行は全部消えます。

直すには、サブクエリから NULL を明示的に除外します。

SELECT account_id, account_name FROM accounts
WHERE account_id NOT IN (SELECT assigned_to FROM bugs WHERE assigned_to IS NOT NULL)
ORDER BY account_id;
 account_id | account_name
------------+--------------
          1 | alice
          4 | dave

NULL を除いた途端、正しく alice と dave の 2 行が返りました。NOT IN のサブクエリに NULL を含む列を渡すのは、PostgreSQL に限らず標準 SQL 全体に共通する古典的な罠です。

図: NOT IN は AND の連鎖であり、候補に NULL が 1 つでもあると比較全体が不明になる。

2.3 アンチパターン ― 集約と文字列結合での NULL の伝染

bugs.hours には NULL (まだ作業していない) の行が 2 件あります。

SELECT bug_id, hours FROM bugs ORDER BY bug_id;
 bug_id | hours
--------+-------
      1 | (NULL)
      2 |  3.50
      3 |  0.25
      4 |  8.00
      5 | (NULL)
SELECT count(*) AS count_star, count(hours) AS count_hours,
       sum(hours) AS sum_hours, avg(hours) AS avg_hours FROM bugs;
 count_star | count_hours | sum_hours |     avg_hours
------------+-------------+-----------+--------------------
          5 |           3 |     11.75 | 3.9166666666666667

count(*) は行数そのものなので 5 ですが、count(hours) は NULL を無視して 3 になります。avg(hours) は 11.75 ÷ 3 = 3.9166... であり、11.75 ÷ 5 ではありません。集約関数は既定で NULL を「無かったもの」として無視するため、「平均」のつもりが「NULL でない行だけの平均」になっている点に注意が必要です。

文字列結合 (||) も NULL に触れると、結果全体が NULL になります。

SELECT account_id, 'rate: ' || hourly_rate AS label FROM accounts ORDER BY account_id;
 account_id |    label
------------+-------------
          1 | rate: 50.00
          2 | rate: 45.00
          3 | rate: 60.00
          4 |      (NULL)

dave (account_id=4) は hourly_rate が未設定 (NULL) なので、'rate: ' || NULL の結果は 'rate: ' ではなく行全体が NULL になります。レポートやラベル生成でこれに気付かず、NULL のまま画面に表示してしまう事故はよく起こります。

図: 'rate: ' || NULL は 'rate: ' にはならず、結合結果そのものが NULL になる。

3. 見つけ方 ― どんな兆候で気づくか

NULL を許している列と、実際にどれだけ NULL が入っているかは、カタログと統計情報から機械的に確認できます。

SELECT table_name, column_name, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public' AND is_nullable = 'YES'
ORDER BY table_name, column_name;
 table_name |   column_name    | is_nullable
------------+-------------------+-------------
 accounts   | first_name        | YES
 accounts   | hourly_rate       | YES
 accounts   | last_name         | YES
 bugs       | assigned_to       | YES
 bugs       | hours             | YES
 bugs       | priority          | YES
 ...

実際にどれくらいの割合で NULL が入っているかは、ANALYZE 後の統計情報 pg_stats.null_frac で分かります。

ANALYZE bugs;
SELECT attname, null_frac FROM pg_stats
WHERE tablename = 'bugs' AND attname IN ('hours','assigned_to','priority');
   attname   | null_frac
-------------+-----------
 assigned_to |       0.2
 hours       |       0.4
 priority    |       0.2

hours は 5 行中 2 行 (40 %) が NULL でした。この列を使う WHERE 句や || 結合、NOT IN サブクエリがコードの中に無いかを、この一覧を手がかりに点検します。

4. 使ってよい場合

NULL 自体は無くすべきものではありません。本当に「まだ決まっていない」「対象が存在しない」ことを表したいときは、NULL が最も自然な表現です。bugs.hours (まだ作業していない) や bugs.verified_by (まだ検証されていない) はその例です。

一方で、「候補の集合から選ぶ」性質の列 (第 11 回で見た priority のような列) は、NULL を「未設定」として許すよりも、参照テーブルに 'UNSET' や 'TRIAGE_NEEDED' のような明示的な値を 1 つ用意したほうが、NOT IN や集約での事故を避けられる場合があります。「NULL を使うべきか、明示的な値を使うべきか」は、その列を NOT IN や文字列結合、集約でよく扱うかどうかで判断するとよいでしょう。

5. 解決策 ― PostgreSQL での正しい書き方

5.1 COALESCE で NULL の伝染を止める

COALESCE(a, b, ...) は、左から順に最初に NULL でない値を返す関数です。文字列結合の前に挟むことで、2.3 節の事故を防げます。

SELECT account_id, 'rate: ' || COALESCE(hourly_rate::text, '未設定') AS label
FROM accounts ORDER BY account_id;
 account_id |    label
------------+--------------
          1 | rate: 50.00
          2 | rate: 45.00
          3 | rate: 60.00
          4 | rate: 未設定

dave の行も 'rate: 未設定' と正しく表示されるようになりました。

5.2 IS DISTINCT FROM ― NULL を含めても結果が常に確定する比較

= は NULL が絡むと結果が NULL になりますが、IS DISTINCT FROM (と IS NOT DISTINCT FROM) は NULL も普通の値として比較し、結果が必ず true か false に確定します。

SELECT bug_id, assigned_to,
       assigned_to = 2 AS eq2,
       assigned_to IS DISTINCT FROM 2 AS dist2
FROM bugs ORDER BY bug_id;
 bug_id | assigned_to | eq2    | dist2
--------+-------------+--------+-------
      1 |           2 | t      | f
      2 |           3 | f      | t
      3 |      (NULL) | (NULL) | t
      4 |           3 | f      | t
      5 |           2 | t      | f

bug_id=3 (assigned_to が NULL) の行は、= 2 では結果が NULL になりますが、IS DISTINCT FROM 2 では「NULL は 2 とは違う値である」と正しく true と判定されます。WHERE 句で「NULL も含めて確実に除外・抽出したい」ときに使える書き方です。

5.3 NULLS NOT DISTINCT ― UNIQUE 制約での NULL の扱い方を選ぶ

標準 SQL の UNIQUE 制約は、NULL を「分からない値」として特別扱いし、NULL どうしは重複とみなしません。

CREATE TABLE unique_demo_default (a int, b int, UNIQUE (a,b));
INSERT INTO unique_demo_default VALUES (1, NULL);
INSERT INTO unique_demo_default VALUES (1, NULL);
SELECT * FROM unique_demo_default;
 a | b
---+------
 1 | (NULL)
 1 | (NULL)

同じ (1, NULL) の行が 2 件入ってしまいました。これが意図通りでない場合、PostgreSQL 15 以降では NULLS NOT DISTINCT を付けて、NULL も重複として扱うよう指定できます。

CREATE TABLE unique_demo_notdistinct (a int, b int, UNIQUE NULLS NOT DISTINCT (a,b));
INSERT INTO unique_demo_notdistinct VALUES (1, NULL);
INSERT INTO unique_demo_notdistinct VALUES (1, NULL);
ERROR:  duplicate key value violates unique constraint "unique_demo_notdistinct_a_b_key"
DETAIL:  Key (a, b)=(1, null) already exists.

2 回目の INSERT が、今度は制約違反として拒否されました。どちらの挙動が正しいかはアプリケーションの意図次第であり、PostgreSQL はどちらも選べるようにしています。

5.4 NOT NULL 制約 ― そもそも入れさせない

最も確実な対策は、NULL を許す必要が無い列に NOT NULL 制約を付けることです。サンプル DB の bugs.summary はもともと NOT NULL で、NULL を入れようとすると INSERT 自体が拒否されます。

INSERT INTO bugs (summary, reported_by) VALUES (NULL, 1);
ERROR:  null value in column "summary" of relation "bugs" violates not-null constraint
DETAIL:  Failing row contains (6, 2026-10-25, null, null, null, 1, null, null, NEW, null, null).

6. PostgreSQL エンジンで考慮しておくこと

NULL は値として何かを格納するのではなく、行の中に「この列は NULL である」という印を立てるだけです。PostgreSQL の公式ドキュメントによると、1 行のデータ (タプル) の固定ヘッダの直後にNULL ビットマップという領域があり、そこに列ごとに 1 ビットずつ「NULL かどうか」が記録されます (ビットマップ自体は、1 行の中に NULL の列が 1 つも無い場合は存在しません)。

実際に、NULL を含む行と含まない行で pg_column_size を比べると、NULL を含む行の方が小さくなりました。

CREATE TABLE null_size_demo (a int, b int, c int, d int, e int, f int, g int, h int, i int);
INSERT INTO null_size_demo VALUES (1,2,3,4,5,6,7,8,9);
INSERT INTO null_size_demo VALUES (1,NULL,3,NULL,5,NULL,7,NULL,9);
SELECT a, pg_column_size(null_size_demo.*) AS row_size FROM null_size_demo;
 a | row_size
---+----------
 1 |       60
 1 |       52

9 列すべてに値がある行は 60 バイト、4 列が NULL の行は 52 バイトでした。NULL の列は実データを持たないため、その分だけ行が軽くなります。これは「NULL は空文字列や 0 とは違い、領域を使わない特別な印である」ということを、サイズの差として確認できる例です。

図: タプルの固定ヘッダの直後に NULL ビットマップがあり、NULL の列は実データ領域を使わない。

まとめると、NULL は「分からない」を正確に表現できる便利な仕組みですが、三値論理のルールを知らずに比較・演算・集約に混ぜると、エラーにならずに結果だけが静かにずれます。IS NULL・COALESCE・IS DISTINCT FROM を使い分け、本当に NULL が要らない列には NOT NULL を付けることが、事故を防ぐ基本です。

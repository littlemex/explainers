ファントムファイル ― 画像をファイルに置きパスだけ持つ

画像をファイルシステムに置き、DB にはパスの文字列だけを持たせると、削除・トランザクション・権限のどこかで DB とファイルがずれる。bytea であれば、行が消えると画像データも一緒に消える

この回の前提: 第 11 回 サーティワンフレーバー (スキーマへの埋め込みとテーブルによる管理の違い)

バグ報告に添付するスクリーンショットのような画像を、どこに置くべきでしょうか。「ファイルシステムに保存し、DB にはパス (文字列) だけを持たせる」という設計は自然に見えますが、DB の行とファイルという 2 つの別々のライフサイクルを、アプリケーションのコードだけで同期させ続けることを意味します。結論を先に言うと、PostgreSQL には画像のような二値データを行の一部として持つ bytea 型があり、これを使えば削除もトランザクションも DB の仕組みにそのまま乗ります。この回では、パス方式 ・ bytea ・ large object の 3 つを実機で比較します。

1. 目的 ― 何をしたかったのか

バグ管理システムでは、バグ報告にスクリーンショット画像を添付したいという要望が自然に出てきます。サンプル DB の screenshots テーブルは、まさにこの用途のために bug_id・image_id・screenshot_image・caption という列を持っています。

ここで問題になるのは「画像の実データをどこに置くか」です。画像は数十 KB から数 MB になることがあり、テキストの列とは性質が違います。アプリケーションを書く人の多くは「DB は構造化データ、画像はファイルシステムか外部のオブジェクトストレージ」という分担を自然に思いつきます。これ自体は多くの場面で合理的な設計ですが、分担した 2 つの保管場所のライフサイクルを誰がどう同期させるかを決めずに進めると、様々な不整合が生まれます。

2. アンチパターン ― どう書いてしまい、何が壊れるか

まず、画像の実データはファイルシステムに書き、DB には text 型のパスだけを持つ設計を試します。

CREATE TABLE screenshot_paths (bug_id int PRIMARY KEY, file_path text NOT NULL);

2.1 DELETE はファイルまで消してくれない

実際にファイルを書き込み、パスを DB に記録してから、DB の行だけを削除してみます。

echo "fake screenshot bytes" > /path/to/demo_files/bug42.png
INSERT INTO screenshot_paths VALUES (42, '/path/to/demo_files/bug42.png');
DELETE FROM screenshot_paths WHERE bug_id = 42;

DB 側は 0 行になりましたが、実際にファイルの存在を確認すると、ファイルはディスクに残り続けていました。

rows_left
-----------
        0
(1 row)

[結果] ファイルはまだディスクに残っている (孤児ファイル)

図: DB の行を消しても、ファイルシステム上の画像は消えずに孤児として残る。

2.2 ファイルの書き込みはトランザクションの外で起きる

逆方向のずれも起きます。ファイルを書いてから DB に INSERT し、その後 ROLLBACK すると、DB の行は無くなりますが、ファイル自体はファイルシステムの操作として既に確定しているため残ります。

echo "fake screenshot bytes for bug 99" > /path/to/demo_files/bug99.png
BEGIN;
INSERT INTO screenshot_paths VALUES (99, '/path/to/demo_files/bug99.png');
ROLLBACK;
rows_after_rollback
---------------------
                  0

[結果] DB側の行は無くなったのに、ファイルだけが残っている

つまりこの設計では、「DB にはあるがファイルが無い」「ファイルはあるが DB に行が無い」のどちらの不整合も起こり得ます。バックアップについても同様で、pg_dump は PostgreSQL のデータベースだけをバックアップし、ファイルシステム上の画像ディレクトリまでは含みません。DB をある時点に復元すると、その時点より後に書かれた画像ファイルや、その時点で既に削除されていたはずの画像ファイルとの間でずれが生まれます。

3. 見つけ方 ― どんな兆候で気づくか

パスや URL らしき列名を information_schema.columns から機械的に探せます。

SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND column_name ~* '(_path|_url|filename|file_name)$';
    table_name    | column_name | data_type
------------------+-------------+-----------
 screenshot_paths | file_path   | text

この一覧に出てきた列に対して、「この列が指す先が消えたとき、誰が・いつ掃除するのか」をコードベース全体から確認するのが次の調査です。削除処理のコードの中に、ファイル削除の呼び出しが DB の DELETE と同じトランザクション境界に無い (例外処理やリトライの経路でファイル削除だけ抜け漏れる) パターンは実際によく見つかります。

4. 使ってよい場合 ― bytea / large object / 外部ストレージを公平に比べる

画像のような二値データの保管には、少なくとも 3 つの選択肢があります。どれが絶対的に正しいということはなく、ファイルの大きさとアクセス頻度、整合性をどこまで厳密に守りたいかで向き不向きが変わります。実際に PostgreSQL 18 で 3 つを試して比較しました。

4.1 bytea + TOAST

bytea は行の列として二値データを持つ型です。値が大きくなると PostgreSQL は自動的に TOAST という仕組みで、本体の行とは別の隠しテーブルに値を圧縮して退避させます。これを確認するため、圧縮されにくい (ランダムに近い) データを 2 種類の大きさで入れてみました。

INSERT INTO toast_demo VALUES (1, <48バイトの非圧縮データ>);
INSERT INTO toast_demo VALUES (2, <6400バイトの非圧縮データ>);
SELECT id, octet_length(data), pg_column_size(data) FROM toast_demo;
 id | logical_bytes | stored_bytes
----+---------------+--------------
  1 |            48 |           49
  2 |          6400 |         6400

さらに、この列の TOAST 用の隠しテーブルを直接調べると、48 バイトの行 (id=1) はそこに現れず、6400 バイトの行 (id=2) だけが外部テーブルに分割されて保存されていました (4 つのチャンクの合計が 6400 バイトと一致)。小さい値は行の中に収まり、大きい値だけが自動的に外出しされる、という仕組みがそのまま確認できます。

4.2 large object (lo)

PostgreSQL には古くからある lo (large object) という仕組みもあります。行には oid 型で large object の ID だけを持ち、実データは pg_largeobject という共通のカタログに保存されます。ストリーミング読み書き (lo_read/lo_write) ができるのが利点ですが、実際に試すと、参照していた行を消しても large object 自体は消えないことが分かりました。

INSERT INTO lo_demo VALUES (1, lo_from_bytea(0, 'fake png bytes'::bytea));
SELECT count(*) AS lo_rows_before FROM pg_largeobject_metadata
  WHERE oid = (SELECT image_loid FROM lo_demo WHERE id = 1);
DELETE FROM lo_demo WHERE id = 1;
SELECT count(*) AS lo_rows_after_delete FROM pg_largeobject_metadata;
 lo_rows_before
----------------
              1
(1 row)

 lo_rows_after_delete
-----------------------
                     1
(1 row)

[結果] DELETE 後も pg_largeobject_metadata から該当の large object が消えていない

図: large object は行とは別のライフサイクルを持ち、参照されなくなっても自動では消えない。

4.3 権限も bytea と large object で挙動が違う

テーブルに GRANT SELECT しただけで、bytea の列は読めました。

GRANT SELECT ON toast_demo TO sql12_reader;
-- sql12_reader で接続
SELECT id, data FROM toast_demo WHERE id = 3;
 id |                 data
----+---------------------------------------
  3 | \x76697369626c6520746f20726561646572

ところが large object は、テーブルへの GRANT とは別に、large object そのものへの権限管理を持っています。lo_demo テーブルへの SELECT 権限だけを渡しても、参照先の large object の内容までは読めませんでした。

GRANT SELECT ON lo_demo TO sql12_reader;
-- sql12_reader で接続
SELECT lo_get((SELECT image_loid FROM lo_demo WHERE id = 2));
ERROR:  permission denied for large object 24879

これは実運用で見落としやすい「権限の不整合」です。テーブルの行が見えるのに画像の内容だけが読めない (あるいは逆に、画像だけ想定外に読める) という事故の種になります。

4.4 外部オブジェクトストレージが向く場合

この回では実機で試せる範囲 (PostgreSQL のローカル環境) を優先したため、外部のオブジェクトストレージそのものは動かしていませんが、公平に比較のために挙動を整理します。ファイルが数十 MB から GB 級になる、あるいは画像をアプリケーションサーバーを経由せずクライアントへ直接配信したい場合は、DB の外にデータを置く方が向きます。ただしその場合も、この回で見た 2 方向のずれ (DB にあるがファイルが無い / ファイルはあるが DB に行が無い) は原理的に残るため、「DB の行をコミットする前にオブジェクトストレージへの書き込みが完了したことを確認する」「参照されなくなったオブジェクトを掃除するバッチ (ガーベジコレクション) を別途用意する」という運用上の仕組みを、アプリケーション側で自分で作る必要があります。

方式削除の追従権限管理向く規模
bytea + TOAST行の削除に自動で追従 (実測: 削除後 TOAST 行 0 件)テーブルの GRANT だけで足りる数 KB 〜 数 MB
large object追従しない (実測: 行削除後も残存)large object 単位の別管理が必要巨大だが DB 内に置きたい場合
外部オブジェクトストレージ自分でガーベジコレクションを作る必要ストレージ側の ACL 管理が別に要る数十 MB 〜、CDN 配信したい場合

5. 解決策 ― PostgreSQL での正しい書き方

このバグ管理システムのスクリーンショットのように、1 件が数十 KB から数百 KB 程度に収まる画像なら、サンプル DB にもともと用意されている screenshots テーブルの形、つまり bytea 列 + 通常の外部キー (ON DELETE CASCADE) が素直な選択です。

-- screenshots.screenshot_image は bytea、bugs への外部キーには
-- ON DELETE CASCADE がすでに設定されている (sample_schema.sql)
INSERT INTO screenshots (bug_id, image_id, screenshot_image, caption)
VALUES (1, 1, <50個のmd5を連結した800バイトのデータ>, 'crash dialog');

DELETE FROM bugs WHERE bug_id = 1;
SELECT count(*) FROM screenshots WHERE bug_id = 1;
 screenshots_left_for_bug1
---------------------------
                         0

バグの行を削除すると、スクリーンショットの行も自動的に削除されました。これは screenshots テーブルの bug_id 列に REFERENCES bugs (bug_id) ON DELETE CASCADE が設定されているためで、bytea のデータ自体もその行の一部 (または TOAST の中) なので、行が消えれば一緒に消えます。パス方式や large object 方式で見た「どちらか一方だけが残る」という事故が、原理的に起こりません。

サイズの上限は CHECK 制約で運用上の安全弁として設定できます。

ALTER TABLE screenshots ADD CONSTRAINT screenshots_size_check
  CHECK (octet_length(screenshot_image) <= 1048576);

実際にこの上限を超えるデータを入れようとすると、INSERT 文の時点で拒否されます。

ERROR:  new row for relation "screenshots" violates check constraint "screenshots_size_check"

図: bytea 方式では画像データが行の一部であるため、既存の外部キーの CASCADE がそのまま効く。

6. PostgreSQL エンジンで考慮しておくこと

\d+ で列ごとの TOAST 方式 (storage) を確認できます。

                Table "public.toast_demo"
 Column |  Type   | ... | Storage  | ...
--------+---------+ ... +----------+ ...
 id     | integer | ... | plain    | ...
 data   | bytea   | ... | extended | ...

bytea の既定は extended で、「圧縮する」「必要なら外部テーブルに退避する」の両方を許可します。他に main (圧縮はするが外部テーブルへの退避は最後の手段)、external (圧縮せず外部テーブルへ)、plain (TOAST を使わない、固定長型向け) があります。画像のように元から圧縮済みのバイナリ (JPEG/PNG) では、PostgreSQL 側の圧縮がほとんど効かないことが多いため、圧縮を省略した external を指定して CPU を節約する選択肢もあります。

TOAST は行の削除と一体で動きます。実際に 6400 バイトの行を削除すると、対応する TOAST テーブルの行数は 0 件になりました。

DELETE FROM toast_demo WHERE id = 2;
NOTICE:  toast_rows_after_delete = 0

これに対して large object は、PostgreSQL がまだ TOAST を持っていなかった時代からある機能で、今も「行の大きさの上限を超えるような巨大なデータをストリーミングで読み書きしたい」という場面のために残っています。実際にこの回のデモで作った large object は、片付けないと増え続けました。

SELECT count(*) FROM pg_largeobject_metadata;
 orphaned_large_objects
------------------------
                      2

これを手動で掃除するには、どの行からも参照されなくなった large object の ID を自分で見つけて lo_unlink する処理を書くか、PostgreSQL の contrib ツール vacuumlo を定期的に実行する運用が必要です。これは bytea にはない、large object を選んだ場合だけの追加の運用コストです。

まとめると、PostgreSQL では「行の一部として持てるサイズの二値データなら bytea、それでも足りない巨大なデータだけ large object かオブジェクトストレージ」という順番で検討するのが実務的です。どちらを選んでも、ファイルシステムへの素朴なパス保存のように「DB とファイルの 2 つのライフサイクルを自分で手動同期する」という選択は避けられます。

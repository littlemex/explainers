この回の前提: 第 20 回 Lean 4 はプログラミング言語でもある

前回 (第 20 回) は theorem と by, rfl だけで最小限の証明を書きました。今回は Lean のタクティク (証明を進める命令) を増やし、証明のどこまでを機械に任せられるかを見ます。「0 を足しても値は変わらない」という同じ事実でも、0 が足し算のどちら側にあるかで rfl (計算するだけ) で終わるか、induction (帰納法) が必要になるかが変わることを確かめ、さらに omega と decide という人が手順を考えなくてよい自動タクティクも使います。

1. induction で場合分けをする

Lean の自然数 Nat は、第 05 回で見た帰納法の対象そのもので、0 (Nat.zero) と「ある数の次の数」(Nat.succ n) の 2 つの作り方しかありません。足し算もこの 2 つの場合に分けて定義します。ライブラリの + とは独立に、自分で足し算 myAdd を定義してみます。

def myAdd : Nat → Nat → Nat
  | n, .zero => n
  | n, .succ m => .succ (myAdd n m)

この定義は2 番目の引数 (右側) で場合分けしています。だから myAdd n 0 = n は定義の最初の場合そのものなので、計算するだけ (rfl) で終わります。ところが myAdd 0 n = n は、場合分けしているのが n 側なのに n が具体的な数でなければ定義を 1 歩も展開できません。n についての帰納法が必要です。

theorem myAdd_zero_left (n : Nat) : myAdd 0 n = n := by
  induction n with
  | zero => rfl
  | succ n ih =>
    show Nat.succ (myAdd 0 n) = Nat.succ n
    rw [ih]

induction n with は、n の作り方 2 つ (zero と succ) それぞれについてゴールを分けます。succ の場合では、1 つ小さい数 n について既に証明が成り立つという仮定 ih (induction hypothesis, 帰納法の仮定) が手に入り、それを rw (rewrite, 書き換え) で使ってゴールを閉じます。

図: 定義がどちらの引数で場合分けされているかが、rfl で済むか induction が要るかを決める。

2. simp で式を整理する

simp (simplify, 簡約) は、@[simp] という目印がついた既知の等式を、ゴールに繰り返し当てはめて式を整理するタクティクです。core の標準ライブラリには、ライブラリの + について n + 0 = n のような等式が既に証明され @[simp] がついています。だから自分で induction を書かなくても、simp がそれを使って片付けてくれます。

theorem simp_example (n : Nat) : n + 0 + 0 = n := by
  simp

これは「induction の手間が消えた」わけではありません。誰かが一度 n + 0 = n を induction で証明し、それを @[simp] として登録した結果を、simp が借りてきて何度も当てはめているだけです。1 回だけ証明された定理を、以後は何度でもタクティク 1 語で再利用できることが simp の価値です。

3. omega と decide: 考える手順ごと自動で片付ける

omega は、足し算・引き算・大小比較 (+ - < ≤ = など) だけでできた命題なら、人が場合分けや書き換えの手順を考えなくても、まとめて自動で証明を組み立てるタクティクです。

theorem omega_example (n : Nat) (h : n > 3) : n + 1 > 4 := by
  omega

decide は、計算すれば真偽がその場で決まる命題 (decidable な命題) に対して、実際にその計算を実行し、結果が真なら「計算してみたら真だった」ということ自体を証明として使います。

example : (2 + 3 = 5 : Prop) := by decide
example : ¬ (7 < 3) := by decide

induction や simp は「どういう手順で証明するか」を (多少は) 人が指定する必要があります。omega と decide は、ゴールが自分の扱える範囲 (omega なら線形算術、decide なら具体的に計算できる命題) に収まっているかどうかだけを人が判断すれば、残りは全部機械がやってくれます。ただし扱える範囲は狭く、たとえば変数同士の掛け算を含む命題は omega の範囲外ですし、「すべての n について」という全称命題は具体的な計算に落とせないので decide の範囲外です。そこでは induction に戻る必要があります。

図: 自動化が強いタクティクほど、人の作業は減るが届く範囲は狭くなる。

Mathlib は、こうした仕組みの上に積み上がった巨大な数学ライブラリで、数十万におよぶ定理と、ring や linarith といった追加の自動化タクティクを提供します。このシリーズでは core だけを使いますが、実際の Lean プロジェクトではこうした強い自動化を日常的に使い、人は「何を証明するか (どういう定理を立てるか)」に集中し、「どう証明するか」の細部は自動化に委ねる、という分業が進みます。

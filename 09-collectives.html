NeuronLink と EFA ― データ移動の階段をもう1段延ばし、通信を計算の裏に隠す

0この記事の狙い

第1回から第8回まで、話はすべて単一チップ・単一 NeuronCore の中で完結していました。今回はその境界を越え、複数チップに分かれたモデルがどう協調して動くかを見る、このシリーズの最終回です。

一言でいうと
単一チップのメモリ階層で学んだ「速い所は小さい・遅い所は大きい・往復を減らす」という考え方が、そのままチップ間ネットワークにもう1層拡張されます。SBUF↔HBM の往復を減らす発想と同じ理屈で、チップ間の通信(collective)も「減らす」「隠す(計算と重ねる)」ことで速くする ― それが本章の核心です。
先に結論。モデルが複数チップに分割されると、各チップは自分の担当分を計算した後、他チップの結果と合算・共有する必要があります(collective 通信)。これを愚直にやると通信の間だけ計算が止まる。ワークショップでは、通信をカーネルの内側から発行し計算の裏で進める(comm/compute overlap)というアプローチが扱われます。これは第7回で見た「タイル単位のパイプライン」の発想を、チップとチップの間に広げたものです。
1. 単一チップから複数チップへ ― もう1層の階段 2. 【体験】ring all-reduce ― 2周(足し込み→配布)で全員が合計を持つ 3. collective の種類と関連パターン ― all-reduce・all-gather・halo exchange 4. 【体験】計算と通信のオーバーラップ 5. in-kernel collectives ― カーネルの内側から通信を発行する 6. まとめ ― シリーズの結び

対象は AWS Trainium2。本記事に具体的な実測数値は含まれず、以下の図・数値はすべて概念値・相対値です。第1回「ハードウェア階層」で見た容量と帯域の非対称、そして第7回で見た「エンジンを遊ばせないパイプライン」の発想が、本章の土台になります。

1単一チップから複数チップへ ― もう1層の階段

第1回で見た「HBM は大きくて遅い、SBUF は小さくて速い」という地図に、もう1段外側の層を書き加えます。

大きなモデルは1チップの HBM に載りません。だからモデルを複数チップに分割し(例えば行列積の重みを分けるテンソル並列、バッチを分けるデータ並列)、各チップが自分の担当分だけを計算します。ただし分割した計算は、途中で他チップの結果と合わせる必要が出てきます。この「チップ間でデータを合わせる・共有する」操作が collective 通信です。

チップ同士をつなぐ経路は主に2種類あります。

  • NeuronLink ― チップとチップを直結する高速リンク(scale-up)。1インスタンス内のチップ間に加え、Trn2 UltraServer 構成では複数インスタンスにまたがる scale-up ドメインを形成します(公開済み)。
  • EFA (Elastic Fabric Adapter) ― サーバーをまたぐネットワーク(scale-out)。OS バイパス対応の NIC で、AWS 独自の SRD プロトコルにより低レイテンシ・高スループットの通信を実現します。
用語の補足。本記事では分かりやすさのため「チップ」という言葉で通信の単位を表しますが、collective 通信の実体上の単位はランク(rank)であり、これは(論理)NeuronCore に対応します。Trainium2 は 1 チップに複数の NeuronCore を持つため、チップ間だけでなくチップ内のコア間でも同じ collective の仕組みが使われます。

第1回の「オンチップ(SBUF)は速いが小さい、HBM は大きいが遅い」という非対称が、チップの外にもそのまま続きます。近い(小さい範囲)ほど速く、遠い(大きい範囲)ほど遅いという同じ形の階段が1段延びるだけです。

層範囲役割
PSUM1 チップの内側行列積の出力・蓄積先(第1回)
SBUF1 チップの内側計算エンジンが直結する作業台(第1回)
HBM1 チップの内側そのチップの大容量倉庫(第1回)
NeuronLink複数チップ(UltraServer構成では複数インスタンスにまたがる)チップ間の高速リンク(scale-up)
EFA複数サーバー(ノード)間ノード間のネットワーク(scale-out)
ここが本章の軸。単一チップの中で「HBM への往復を減らす」ためにカーネル融合(第2回)やタイリング(第5回)を使ったのと同じ発想で、チップ間でも「通信そのものを減らす」「通信を計算の裏に隠す」ことが速度の鍵になります。地図が1段外へ伸びただけで、戦い方の骨格は変わりません。

2【体験】ring all-reduce ― 2周(足し込み→配布)で全員が合計を持つ

この記事の「絵で覚えて帰ってほしい1枚」その1です。複数チップが持つ部分和を、全チップが同じ合計を持つ状態まで導く様子を見ます。

all-reduce は、各チップが持つ部分的な値(例えば勾配や部分和)を全チップ分足し合わせ、その合計を全チップに配る操作です。テンソル並列やデータ並列で、分割した計算を最後に統合する場面で必要になります。

実現方法の1つが ring(リング)アルゴリズムです。チップを円環に並べ、各チップは隣のチップにだけデータを渡す。all-reduce は概念上「reduce-scatter(合算しながら結果を分散配置、N-1 ステップ)」+「all-gather(分散した結果を全員に配布、N-1 ステップ)」の2周構成で実現できます。1チップが送信するデータ量はおおよそ元データの2倍で、チップ数 N が増えても1チップあたりの総通信量はほぼ一定のまま保たれるのが利点です(一方でステップ数に比例するレイテンシは O(N) で伸びるため、チップ数が非常に多い大規模構成ではツリーや階層型など別のアルゴリズムが使われます)。以下のデモは2周構成の骨格を示す簡略版です。

チップ(円環に配置) リングを流れる部分和 合算が完了した値

各チップは最初、自分だけの部分和(概念値・相対値)を持っています。①の reduce フェーズでは、各チップが自分の持つ値を隣のチップへ送り、隣から受け取った値と自分の値を足すを繰り返し、リングをほぼ一周する間に合計値が1か所に集まります。続く②の broadcast フェーズでは、その合計値をもう一周かけて全チップへ配布します。この2周構成(足し込み→配布)を経て、全チップが同じ合計値を持つ状態(all-reduce 完了)にたどり着くのが、ring all-reduce の骨格です。

実際のワークショップでは、この合算アルゴリズム自体はランタイムとフレームワーク(collective ライブラリ)が実行します。カーネル開発者が書くのは「どのチップの集まり(replica group)で、どの演算(足し算等)の collective を呼ぶか」という宣言です。リング/ツリーといった具体的な経路の選び方は、通信ライブラリが担う実装詳細ですが、「データがどう巡って合算されるか」の直感を持っておくと、通信コストの見積もりや後述のオーバーラップ設計がしやすくなります。

3collective の種類と関連パターン ― all-reduce・all-gather・halo exchange

all-reduce だけが collective ではありません。「何を」「どこまで」共有するかによって、いくつかの型があります。

  1. all-reduce: 全チップの値を1つに合算し、その合算結果を全チップに配る。前章のリングの例そのもの。テンソル並列の出力射影後などで使う。
  2. all-gather: 各チップが持つ別々のかけらを、全チップが全部のかけらを集めた状態にする(合算はしない、集めるだけ)。分割して持っていたデータを、後段の計算のために全員が全体を持つ必要があるときに使う。
  3. reduce-scatter: all-reduce の「配る」部分を「各チップが結果の一部だけを持つ」形に変えたもの。全体を合算しつつ、結果自体は再分割して各チップの負担を抑える。例えば 4 チップなら、各チップが持つ結果は全体の 1/4 のサイズで済む。

もう1つ、隣接チップとだけ通信する軽量なパターンが halo exchange です。畳み込みや空間分割のように、各チップがデータの一部(タイル)を担当し、その境界(halo)部分だけを隣接チップと交換する。all-reduce/all-gather/reduce-scatter のような collective プリミティブそのものではなく、近傍とのポイントツーポイント通信(collective_permute 等)を組み合わせて実現する通信パターンです。境界だけを隣とやり取りするので通信量を絞れます。第5回(タイリング)で見た「必要なデータだけを SBUF に載せる」という発想が、チップ間でも「必要な境界データだけを交換する」という形で再登場します。

共通する発想。all-reduce/all-gather/reduce-scatter/halo exchange のどれも、「本当に必要な範囲・量だけを、必要な相手とだけやり取りする」という一点に尽きます。全チップと全データを交換するのが一番単純ですが最も高コストで、halo exchange のように隣接だけに絞れるなら、その方が通信コストは小さくなります。

4【体験】計算と通信のオーバーラップ

この記事の「絵で覚えて帰ってほしい1枚」その2です。第7回で見た「タイル単位のパイプライン」の発想を、チップ間の通信に広げます。

愚直な実装では、通信している間は計算が止まります(逐次実行)。QKV 射影を計算 → 結果を all-reduce で合算 → 合算が終わるまで次の計算を待つ、という具合です。通信には NeuronLink や EFA の転送時間がかかるので、これをただ待つのは第7回で見た「エンジンが遊んでいる」状態そのものです。

そこで、通信をバックグラウンドで進めながら、その裏で別の計算を進めるようにします。例えば、あるレイヤーの all-reduce が進んでいる間に、次のレイヤーで使うデータの計算を始めてしまう。理想的には計算時間と通信時間の合計ではなくmax(計算時間, 通信時間)に近づき、全体の所要時間(ウォールクロック時間)が短くなります。ただし実際には計算と通信は DMA やメモリ帯域の一部を共有するため、両者とも単独実行時よりやや遅くなるのが実情です。通信時間が計算時間より長い(通信バウンドな)場合は、通信を完全には隠しきれません。

計算 (Tensor Engine 等) 通信 (NeuronLink / EFA)

オーバーラップなしでは、計算バーと通信バーが交互に並び、通信中は計算バーが完全に途切れます。合計の長さ=計算時間の総和+通信時間の総和。オーバーラップありに切り替えると、通信バーが計算バーの裏に重なって進み、全体の所要時間が理想的には max(計算, 通信) に近づきます。同じ量の計算と通信をこなしていても、全体の長さ(概念値・相対値)が縮むのが見て取れます(このデモは理想化した図であり、実際は帯域共有により多少の遅れが生じます)。

第7回とのつながり。第7回では「タイル i の計算中にタイル i+1 の転送を進める」二重バッファでエンジンを遊ばせませんでした。ここでは「あるチップの計算中に別のチップとの通信を進める」という、同じオーバーラップの発想をチップ間に広げただけです。スコープが単一チップの中からチップの外へ移っても、「待ち時間を他の作業で埋める」という骨格は変わりません。

5in-kernel collectives ― カーネルの内側から通信を発行する

前章の「オーバーラップ」を実現する仕組みの正体を見ます。誰が、どこから通信を指示するかが鍵です。

2章で見た ring all-reduce の「隣とだけデータをやり取りする」という経路そのものはランタイムが実装する詳細でしたが、その通信をいつ発行するかはカーネル側の裁量です。in-kernel collectives は、まさにこの「いつ」をタイル単位まで細かく制御する仕組みです。

通信を呼び出す経路には大きく2つあります。

  • フレームワークレベルの collective(host-driven): PyTorch の torch.distributed 経由で、オペ単位で all-reduce 等を指示する。コンパイラ/ランタイムがオペ同士のオーバーラップを担う。
  • in-kernel collectives(device-initiated): NKI カーネルの内側から直接通信を発行する。タイル単位の細かい粒度で、計算と通信を明示的に重ねられる。

両者の違いは「ホストが介在するかどうか」ではなく、通信を制御する粒度と主体にあります。host-driven はオペ単位でコンパイラ/ランタイムが自動的にオーバーラップを図るのに対し、in-kernel collective はカーネル記述者がタイル単位で計算と通信の重なりを明示的に組み立てられる、という違いです。比喩で言うと、host-driven collective は「電話会議をオペ(用件)ごとにまとめてかける」ようなもので、in-kernel collective は「一言ずつのやり取りを他の作業の合間に挟み込む」イメージです。カーネルの内側から通信を出せるからこそ、前章のオーバーラップがより細かい粒度で実現できます。

collective の対象となるチップの集まりは replica group という単位で表現されます。例えばテンソル並列(TP)とコンテキスト並列(CP)を組み合わせる場合、TP のグループは「隣り合う番号の集まりが多い」、CP のグループは「一定間隔おきの番号の集まりが多い」といった実装依存の慣例が見られますが、並列化の設計そのものがグループの形を決めます。カーネルはこの集まりの中の「どの操作(合算・収集など)を、どの集まりに対して行うか」を宣言する形で通信を組み立てます。なお in-kernel collectives の具体的な API 名・対応する collective 種別・replica_groups の指定方法は SDK バージョンに依存する部分が大きく、詳細は SDK ドキュメントで確認してください。

第2回とのつながり。PSUM から SBUF への退避で活性化関数を「ついでに」済ませたのと同じ発想で、in-kernel collectives は通信を計算の一部として組み込むことを可能にします。データがどこにあるか(SBUF かHBM か)、通信がどこから発行されるか(ホストかカーネル内か)を細かく制御できるほど、往復や待ち時間を削る余地が広がる ― これがシリーズ全体を通じて繰り返されてきたテーマです。

6まとめ ― シリーズの結び

「単一チップの内側」から始まった本シリーズが、最後にチップの外へたどり着きました。全9回を1枚に整理します。

論点要点
もう1層の階段SBUF/HBM の非対称が、NeuronLink(チップ間)・EFA(ノード間)へそのまま延びる
all-reduce各チップの部分和をリング等で巡らせ、全チップが同じ合計を持つ状態にする
collective の種類all-reduce/all-gather/reduce-scatter/halo exchange ― 必要な範囲・相手だけに絞るほど軽い
オーバーラップ通信を計算の裏に隠す。第7回のタイル間パイプラインをチップ間に広げた形
in-kernel collectivesカーネル内側から通信を発行し、ホスト経由より細かい粒度でオーバーラップできる
結論。複数チップに分割されたモデルは、collective 通信で結果を合わせる必要があります。単一チップで学んだ「速い所は小さい・遅い所は大きい・往復を減らす」という地図がチップ間にもう1層延び、「通信を減らす(halo exchange のように範囲を絞る)」「通信を隠す(計算とオーバーラップさせる)」という2つの打ち手が、チップ間でも効きます。

本シリーズは、第1回の単一エンジン・単一メモリ階層の地図から始まり、第2回でRoofline とカーネル融合という測る/減らす道具を手に入れ、第3回のFlashAttentionで融合の本命を見て、第4回でプロファイラという共通言語を得て、第5回のタイリング・第6回のデータレイアウトで単一カーネルの中身を整え、第7回のソフトウェアパイプラインでエンジンを遊ばせない設計を学び、第8回の低精度化で1要素あたりのコストそのものを軽くし、そして第9回の今回、複数チップ間の通信でスコープをチップの外まで広げました。単一エンジンから、単一カーネル、単一チップ、そしてチップ間へ ― スコープを内から外へ段階的に広げてきたのが、このシリーズ全体の一貫した歩みです。

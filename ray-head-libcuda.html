Ray head と libcuda.so.1
なぜ CPU ノードに置いた指揮役が GPU ドライバを要求するのか

miles GRPO テストケース (PR #1225) の Known Issues 3 の解説 · 図 4 点
先に結論
GPU を 1 枚も使わないプロセスが、起動しただけで GPU ドライバのファイルを要求します。そのファイルはコンテナイメージの中には無く、GPU を要求したコンテナにだけホストから注入されます。head は GPU を要求しないので注入されず、そこに置かれた指揮役は OSError: libcuda.so.1 で死にます。対処は「head にドライバを持たせる」ではなく「指揮役が head に置かれないようにする」で、その手段が num-cpus: '0' です。禁止ではなく、資源が足りないから選ばれないという形で効かせています。

1. まず配置。head は CPU ノードに置く

Ray のクラスタには head と worker がいます。head は指揮役で、ジョブの受付とアクターの配置を決めるだけで、行列積を 1 回もしません。GPU ノードは 1 台あたり H200 が 8 枚載っていて時間単価が高いので、そこに指揮役を住まわせるのは無駄です。だからこのマニフェストは head を CPU プールに置き、worker だけを GPU プールに置きます。

2. 問題は、GPU を使わないプロセスがドライバを要求すること

miles の指揮役アクター、たとえば RolloutManager は GPU を 1 枚も使いません。ところが起動時に megatron.core を import します。これが transformer_engine を引き込み、さらにその中で libcuda.so.1 を dlopen します。GPU の枚数として num_gpus=0 を指定していても関係ありません。計算のために開くのではなく、モジュールを読み込む時点で開くからです。

3. 対処は 2 通りあり、後者を選んだ

ドライバを head に持たせる道と、ドライバを要求するアクターを head に置かせない道があります。前者は GPU ノードに head を戻すか、head に GPU を 1 枚割り当てることを意味します。どちらも「指揮役のために計算資源を 1 枚専有する」ので、後者を選びました。

手段は head の rayStartParams に num-cpus: '0' と書くことです。Ray はアクターが要求した資源を持たないノードにそのアクターを置きません。RolloutManager は num_cpus=1 で作られるので、CPU を 0 個しか広告していない head は候補から自動的に外れます。禁止リストではなく、足りないから選ばれないという形で効かせているのが要点です。

この方法の限界が 2 つあります

限界 1: num_cpus=0 をちょうど要求するアクターは、CPU 0 の head でも候補に残る
0 個の要求は 0 個の広告で満たせてしまいます。miles の MultiLoRAController がまさにこれで、しかも head に固定される設計です。ただしこのテストケースのレシピはそれを作らないので、実際には当たりません。当たる構成に手を伸ばすときは、この段が効かなくなることを知っておく必要があります。
限界 2: --pin-rollout-manager-to-head は原理的に満たせない
miles には RolloutManager を head に固定するオプションがあります。CPU を 0 個しか広告しない head では、num_cpus=1 のアクターをそこに置けません。EXTRA_TRAIN_ARGS 経由で渡せてしまうので、渡すと配置できずに止まります。

4. NVIDIA_VISIBLE_DEVICES=none は解決にならない

「GPU デバイスは見せずにドライバだけ入れる」ための値として none があります。head にこれを与えれば済むように見えますが、成り立ちません。この値を理解するのは古い注入方式だけで、GPU Operator が設定する CDI モードでは空のデバイス名として解決され、pod がそもそも起動しません。実測では、コンテナツールキット 1.18.1 の環境で none は StartError になりました。

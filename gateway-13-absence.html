第 13 章 文脈に無いことを聞かれたとき、箱は静かに嘘をつく

この章の 3 行 第 10 章のしきい値は費用だけの議論で、その対象になるトラフィックには品質の数字が 1 つも無かった。 疑っていた故障 (キャッシュ越しに指示や前置きを見失う) は2 段階の難易度で全層 100%、起きなかった。 代わりに別の差が出た。文脈に無いことを聞かれると、箱は書式を守ったまま答えを発明し (50 回中 45 回)、 API は書式を破って拒否する。そしてそれを検出する仕組みは、作らないことにした。

なぜこれを測ったか

第 10 章の結論は「再利用のある prefill 重めのトラフィックを箱に流せ」だった。だがこれは 完全に費用の議論で、しかもその対象になる族はこのシリーズで唯一、品質の数字を持っていない族だった。 値段だけを見て層を推薦し、そこで何が出てくるかを確かめていない、というのはそのまま穴である。

探す故障は具体的に決めた。会話の後半のターンは入力の 80〜90% がキャッシュ読みになる。だから静かに 壊れうるのは 2 つで、1 ターン目の指示が 6 ターン目でも効いているかと、 再計算されなくなった前置きをまだ読んでいるかである。各ターンで前置きに埋めた事実を 1 つ聞き、 TAG: <token> という固定の行で答えさせて、書式と中身を別に採点した。 行を出さなくなったら指示を忘れており、行は出すが違う値なら読むのをやめている。

採点の較正に使った対照書式中身
規則どおりに答える台本1.001.00
流暢だがタグ行が無い答え0.000.00
タグ行はあるが値が違う答え1.000.00

3 行目が肝心である。書式は通り中身は落ちるという状態が作れることが、2 つが本当に別の測定である 証拠になる。第 5 章で学んだとおり、層を測る前に物差しを測っておく。

疑っていた故障は起きなかった

12,000 トークンの共有前置きに事実を 6 つ埋め、6 ターンの会話を 5 本。層ごとに 30 ターンを採点した。

層ターンキャッシュ読み書式中身
箱 (Qwen3.6-35B-A3B)3079.1%100%100%
gemma-43011.0%100%100%
claude-haiku-4-5300.0%100%100%

6 ターンすべてで 1.00。指示の劣化も取得の失敗も無く、層の差も無い。箱は入力の 79% を キャッシュから読みながら 100% を維持した。この測定がまさに疑うために作られた性質である。

そこで難しくした。前置きを 24,000 トークン、事実を 12 個、10 ターンにし、さらに各事実の 直前におとりを置いた。1 文字違いの「古い方」のトークンで、最初に見つけた答えらしきものを 拾うと間違うように配置してある。

層ターンキャッシュ読み書式中身おとりを拾った
箱5087.7%100%100%0.0%
gemma-4502.8%100%100%0.0%
claude-haiku-4-5500.0%100%100%0.0%
2 段階とも天井なら、それは設計の失敗ではなく答えである 24k の共有前置きから、隣に 1 文字違いのおとりを置かれた状態で事実を 1 つ取り出すことは、 この 3 層のどれにとっても難しくない。そしてキャッシュから読んでも難しくならない。 この軸は決着したので、測るのをやめた。箱に品質の問題があるとすれば場所が別である。
100% を意味あるものにしたのは対照だった 同じ実験を事実を前置きから抜いた状態でもう一度回すと、全層の中身が 0% に落ちる。 これがあって初めて「取り出していた」と言える。無ければ、質問文から答えを推測できていた可能性を 排除できず、100% という数字に意味が無かった。

そして対照が、探していなかった差を見つけた

その「事実を抜いた」対照を 50 ターンに増やしたところ、層の差がはっきり出た。ただし 見ていた欄ではなかった。

層答えられない問いでの書式そこでのキャッシュ読み何を出したか
箱90.0% (50 中 45)96.3%整った形の発明されたトークン。無い事実が ZR-6584 のところに ZR-6585
gemma-40.0%21.5%UNKNOWN、unknown、<module-01>
claude-haiku-4-52.0% (50 中 1)0.0%UNKNOWN、unable to determine - not in document
箱の書式スコアが高いのは、褒め言葉ではなく信号である 文脈に無いことを聞かれたとき、箱は出力契約を守り続け、空欄を捏造で埋めた。 API 側は拒否するために書式を破った。だから箱の 90.0% という書式スコアは、 規律ではなく故障の指標である。箱はこれを、入力の 96.3% をキャッシュから読みながらやっている。

1 違いを見つめる価値がある。無いトークンは ZR-6584 で、箱が出したのは ZR-6585 だった。質問の形から答えの形を再構成している。そして厳格な出力書式は、 この故障を見つけにくくする方向に働く。下流で TAG: を読むシステムには、 正解でも捏造でも構文的に完璧な答えが届く。

箱の故障は静かで、API の故障はうるさい。うるさいほうが安く処理できる これは費用の議論からは出てこないルーティングの含意である。文脈の外を聞かれ得るトラフィックでは、 故障が例外として上がってくるか、正しい答えのふりをして通過するかが変わる。

「無ければ知らないと言え」と書いても、ほとんど効かない

上の表への当然の反論はこうである。契約が箱に「文書に無い」と言う手段を与えていなかった。 拒否するには書式を破るしかなく、箱は書式を守る方を選んだだけではないか。そこで規則自体に逃げ道を 書き込んで回し直した — 「そのモジュールのビルドトークンが上の参考資料に出てこない場合は、 かわりに正確に TAG: UNKNOWN と書け。トークンを推測するな。」

層答えられない問いで拒否したなお整った形で答えた答えられる問いの正答誤って拒否した
箱0% → 24.0%90.0% → 76.0%100% → 100%0%
gemma-40% → 100.0%0% → 0%100% → 100%0%
claude-haiku-4-50% → 94.0%2.0% → 6.0%100% → 100%0%

明示的に推測を禁じても、箱の捏造は 90% から 76% に下がるだけである。差し出した逃げ道を 使ったのは 50 ターン中 12 回。gemma-4 は 50 回全部、claude-haiku-4-5 は 47 回使った。

逃げ道は無料なのに、箱は使わない 答えられる側では 3 層すべてが 100% 正答を維持し、誤った拒否は 1 件も無かった。つまり 「知らないと言ってよい」と伝えることに副作用が無い。副作用が無いのに効果も薄いという結果なので、 この節は都合の悪い方向に閉じた。プロンプトの書き方は検証器の代わりにならない。 「推測するな」という規則を、箱は 4 回に 1 回しか守らない。

捏造の中身も数えた

対照には既知の不完全さがある。台本の助手ターンには本物のトークンが入っているので、答えられない側でも 1 つ前のターンの答えは履歴に見えている。だから「発明」と「履歴からの写し」を分けて数えた。 箱の整った形の誤答 38 件のうち、31 件 (81.6%) はどこにも出てこないトークンで真の発明、 7 件 (18.4%) が履歴にあるトークンの写しだった。

読みは 5 分の 4 で成立し、残りの 5 分の 1 は別の故障だが運用上の帰結は同じである — 構文的に完璧な誤答が届く。なお、より綺麗な対照 (助手ターンをプレースホルダにする) を作れば、 発明の割合は下がるのではなく上がる。

検出する仕組みは、作らないことにした

ここまで来れば対策は自明に見える。出力に現れるトークンらしき文字列は、すべて要求の文脈に そのまま出現していなければ返さない。実験の題材の上ではこれは grep 1 本である。

だがこのシリーズは、同じくらい正しく見えたゲートを既に 2 つ引き下げている — 第 5 章の 要約の捏造ゲート (正当な丸めを失格にした) と、散文のゲート (正しい見出し付き Markdown を弾いた)。 そこで規則を決めた。これを殺しうる実験を先に走らせ、通ってから作る。3 本走らせ、3 本目が答えを変えた。

kill 1 — 算術。発火しない

検出が当たったら上位の API に投げ直すとする。すると箱は自分の無駄になった呼び出しと API の 呼び出しを二重に払うので、文脈外の質問がある割合を超えると箱の利点が消える。その割合を解けばよく、 本番データは要らない。答えは箱を使う価値がある水準ではどこでも払えるで、しかも TAG: UNKNOWN に差し替える方針なら 2 回目の呼び出しが無いので交差点そのものが無い。 この計算は当時いちばん安い層 (gemma-4) を基準にしていて、その層は後に比較対象から外れて基準は上がったので、 この kill はますます発火しない。

kill 2 — 抽出器。発火し、範囲を決めた

「トークンらしき文字列」を定める正規表現こそが、題材への依存が隠れる場所である。だから 照合とは切り離して、抽出器だけを実文書にかけた。

コーパス文字数狭い文法2 文字広げた文法
GovReport、実際の政府文書 80 本4,004,8070307
技術文書の英語散文173,9454 (自分の題材の引用)4
Python のソース236,0661 (自分の定数)1

文法を 2 文字広げるだけで、誤検出が 0 件から 307 件になる。しかも 307 件の中身は予想どおりで、 GAO-19、COVID-19、MD-715、SS-18 — すべて実在の識別子であり、 いくつかは文脈に無くてもモデルが正しく書けるものである (知っているから)。

つまりこの検査が働くのは、識別子が不透明で文法が狭いときだけである。それは捏造の性質ではなく、 題材のトークン書式の性質である。正直な適用範囲はこう狭い。

認可された証拠から逐語で写すことが契約になっている
「閉じた世界の抽出フィールド」に限り、新規の未裏付けリテラルを検出する。

検出しないもの: 存在する値の選択誤り、未裏付けの言い換え、計算間違い、捏造された散文。
適用してはならないもの: 数値、数量、日付、パス、記号、生成コード
             — 新しい値を作ることが正当な場所。

kill 3 — 文脈の密度。発火し、これが決めた

いちばん鋭い反論はこうだった。実験の題材はトークンが疎で、写せるものが何も無いから発明が最大化される。 豊かな文脈には写せる材料があるので、密度が上がるにつれ捏造が「発明」から「写し」へ移るなら、 この検査は題材が過剰に代表している故障を捕らえ、実トラフィックが持つ故障を見逃す。 検出率が、気にする価値のある文脈ほど下がる関数になる。

測った。同じ 24k の前置きに、聞かれない 150 個の別部品のトークンを埋めて密度だけ上げた。

文脈ターン箱が拒否整った形で答えたうち文脈からの写し発明検出率
疎 (他のトークン 0 個)5024.0%76.0%038100.0%
密 (他のトークン 150 個)6015.0%85.0%104180.4%
反論は向きとして裏づけられ、しかも箱の挙動そのものが悪化した 写せる材料を与えると、箱は拒否が減り (24% → 15%)、捏造が増え (76% → 85%)、 捏造の 5 分の 1 が検査に見えない写しになる。検出率は 100% から 80.4% に落ちた。 実際のエージェントの文脈 — リポジトリ、文書群、ツールスキーマ — は識別子らしき文字列を 150 個よりはるかに多く含むので、検出率はさらに下がる。どこまで下がるかは測っていない。 測ったのは傾きの向きだけである。

動かして見えること

  • 検査が 100% 効くのは、写せる材料が何も無い文脈だけである。そういう文脈は実運用にほぼ無い。
  • 密度を上げると、箱は拒否を減らして捏造を増やす。検査の性能が落ちる方向と、 モデルの挙動が悪くなる方向が同じである。
  • 逃げ道を伝えていない疎な文脈では、箱の書式スコアは 90.0% だった。 上の 2 状態はどちらも逃げ道を伝えた後の数字である。

決定 — 作らない

本番の検証器は作らない。動かないからではなく、検出できる範囲が 2 つの条件で挟まれていて、 どちらも不利な方向に動くからである。フィールドが写し契約下の不透明な識別子でなければならない (kill 2 が示した狭い面) こと、そして検出率が文脈に写せる材料が増えるほど落ちる (kill 3) こと。 実際の文脈は、まさに材料が増える方向にある。

訂正 — 「箱にだけ検証器が要る」は間違いだった 最初の記述は「文脈外の質問が来るトラフィックでは、箱には API に不要な検証器が要る」だった。 助言者が反対し、そちらが正しい。claude-haiku-4-5 も、逃げ道を伝えた状態で答えられない問いの 6% で整った形のトークンを出す。だから箱だけを検証する設計は 6% で漏れる。 出典の裏づけを硬い不変条件にするなら、それは代替経路が何であってもそこに適用される。 「片方だけ信用しない」という設計は、信用した側の漏れ率をそのまま受け入れる設計である。
逃げ道として当てにしていた層が、経路から消えた この表で 100% 拒否していたのは gemma-4 である。だが gemma-4 は bedrock-mantle 経由でしか提供されておらず、このプロジェクトが本番トラフィックを流せる経路には無い。 だから「文脈外を聞かれ得るトラフィックは gemma-4 に流す」という緩和策は使えない。 残る現実的な相手は claude-haiku-4-5 で、そちらは 94% 拒否・6% 漏れである。 測定として正しい層と、流せる層は別物である。

結局どうするのか

  1. 文脈の外を聞かれ得る仕事は、出力を機械が無検査で受け取る経路に置かない。 検出器が無いので、これは技術ではなく配置の判断になる。
  2. 逃げ道は必ず契約に書く。効果は薄い (箱で 24%) が、副作用は測って 0 だった。 無料の 24% を捨てる理由が無い。
  3. 厳格な出力書式は、この故障を隠す方向に働くと知っておく。TAG: が埋まっていることは 何の保証でもない。書式検査を品質検査と読み替えないこと。
  4. 出典の裏づけを不変条件にするなら、全層に等しく適用する。片方だけ検証する設計は、 もう片方の漏れ率を上限として受け入れている。

この章が言っていないこと

対照は層ごとに 50 ターン、1 つのプロンプト形、1 つの出力契約である。拒否の差はこの n で 行動に移せる強さだが、他の形に一般化はしていない。

この章は指示の保持と前置きの取得しか測っていない。箱の散文、推論、道具呼び出しの正しさが API と同等かは、ここでは何も測っていない。道具呼び出しについては第 11 章が別に扱っている。

2 段階での天井は限界ではなく結果である。この軸がこれらの層を分離しないという意味であって、 課題の選び方が悪かったという意味ではない。有用な帰結は測るのをやめることである。

kill 3 は傾きの向きしか示していない。150 個で 80.4% まで落ちたという 1 点があるだけで、 実際の文脈で検出率がどこに着地するかは測っていない。

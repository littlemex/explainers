第 01〜14 回で、CRD の形・コントローラーの書き方・admission という関所を学んだ。この回は視点を変え、実際に CRD とコントローラーを手で全部書くのではなく、kubebuilder(CRD とコントローラーの土台を自動生成する CLI)がどんなファイル一式を作り、何がどこに配置されるかを見る。説明には、実際に kubebuilder init と kubebuilder create api だけを実行した生成直後のプロジェクト(ロジックは未実装)を使う。

kubebuilder は、マーカー(コードの上に書く短い注釈)から CRD の YAML や RBAC の YAML を自動生成し、複数のコントローラーを 1 つのプロセス(manager)にまとめて動かす土台を作る。生成直後からあるテストは envtest(本物の API サーバーと etcd だけを起動し、他のコントローラーはいない)と e2e(本物のクラスタ)の 2 層で、モックだけで動く単体テストは生成されない。

1. kubebuilder が生成するものの地図

kubebuilder init(プロジェクトの骨格を作る)と kubebuilder create api(1 つの CRD とそのコントローラーの型を作る)を実行すると、次のようなディレクトリが生成される。ここでは、これまでの回と同じ Widget CRD(lab.crd-series.example/v1、この連載の実験用 CRD と同じ group と kind)で kubebuilder init と kubebuilder create api --group lab --version v1 --kind Widget を実際に実行し、ロジックを何も書いていない生成直後の状態を確認した(kubebuilder v4.15.0、controller-runtime v0.24.1)。

  • api/v1/*_types.go: CRD の Go の型(第 05 回で見た spec/status の定義)。生成直後の spec は Foo *string という例のフィールドだけ、status は Conditions []metav1.Condition だけで、どちらもコメントで「ここを編集して自分のフィールドを追加する」と案内されている。zz_generated.deepcopy.go は DeepCopy(オブジェクトの複製)の実装で、手で書かず controller-gen が自動生成する。
  • internal/controller/*_controller.go: CRD の Reconciler(第 09 回の Reconcile ループ)の型と SetupWithManager。生成直後は // TODO(user): your logic here だけが入っている。同じディレクトリに suite_test.go(envtest のセットアップ)と *_controller_test.go(envtest の API サーバーを使って Reconcile を呼ぶテスト。中身は「単体テスト」ではない、5 節で見る)も生成直後から用意されている。
  • cmd/main.go: manager(後述)を起動するエントリポイント。
  • config/crd/・config/rbac/・config/manager/・config/samples/: CRD の YAML、RBAC(権限)の YAML、Deployment の YAML、サンプルの CR。すべて kustomize(複数の YAML 断片を重ね合わせて 1 つの構成に組み立てる、オーバーレイ方式のツール)でまとめる前提の断片。
  • test/e2e/*_test.go: e2e テストの土台。実は kubebuilder create api より前の kubebuilder init の時点で、CRD を 1 つも作っていなくても生成される。
  • PROJECT: どの CRD(group/version/kind)をこのプロジェクトが持っているかを記録する、kubebuilder 自身のための設定ファイル。

図: 実際に kubebuilder init と kubebuilder create api を実行して生成した Widget プロジェクトのディレクトリ構成。

2. マーカー → controller-gen → CRD YAML / RBAC YAML

第 05 回で見た +kubebuilder:validation:Enum のようなマーカーに加え、RBAC 用のマーカー(例: +kubebuilder:rbac:groups=...,resources=...,verbs=get;list;watch;create;update;patch;delete。RBAC は role-based access control: 誰が何をしてよいかを役割で管理する Kubernetes の権限の仕組みで、ここでは Reconciler を動かす ServiceAccount[Pod がクラスタに対して名乗る、人間のユーザーとは別のアカウント]に与える権限を指す)がある。生成直後の internal/controller/widget_controller.go を見ると、このマーカーは Reconciler の型定義の後、Reconcile メソッドの直前に書かれている。Makefile の manifests ターゲットは controller-gen(Go の型定義のフィールドと json タグ、そしてマーカーを読んで YAML を書き出すツール)を呼び、config/crd/bases/ に CRD の YAML、config/rbac/role.yaml に RBAC の YAML を生成する。CRD のスキーマは、フィールドの Go の型(*string や []metav1.Condition など)と json タグがあってはじめて組み立てられ、マーカーはそこに制約を書き足す役目。generate ターゲットは同じ controller-gen を使って DeepCopy のコードを生成する。つまり、スキーマ・検証・権限をコードの型定義とマーカーという 1 箇所にまとめて書き、YAML への変換は手で書かない。

図: Go の型定義とマーカーから、controller-gen が CRD と RBAC の YAML を生成する(make manifests)。

3. manager ― 複数コントローラーをまとめて動かす

生成された cmd/main.go は、ctrl.NewManager で 1 つの manager(複数のコントローラーの実行環境をまとめて持つプロセス)を作る。1 つのプロジェクトに複数の CRD があれば、WidgetReconciler のような Reconciler を SetupWithManager で同じ manager にいくつでも登録できる。複数台の manager を同時に動かす(可用性を上げるため)場合、どのコントローラーがどの Pod で動いているかに関わらず、同じオブジェクトを 2 台が同時に Reconcile してしまうと競合が起きる。これを防ぐのが leader election(複数台の中から 1 台だけを「リーダー」として選び、リーダーだけが実際に Reconcile する仕組み)で、生成直後の main.go にも既に --leader-elect フラグと LeaderElectionID が書かれている(既定では無効、フラグで有効化する)。

図: 1 つの manager の中に 2 つの Reconciler。複数台の manager が動くときは leader election で 1 台だけが実際に動く。

4. metrics・health probe・Events

生成された main.go は、mgr.AddHealthzCheck("healthz", healthz.Ping) と mgr.AddReadyzCheck("readyz", healthz.Ping) を登録し、--health-probe-bind-address(既定 :8081)で HTTP の health probe(Kubernetes の liveness/readiness probe が叩くエンドポイント)を公開する。healthz.Ping は常に OK を返すだけの関数で、確認できるのは「manager のプロセスが生きているか」だけで、個々の Reconcile が正しく進んでいるかまでは分からない。さらに --metrics-bind-address で、Prometheus(メトリクスを集める定番のソフト)が読める形式の指標を公開できる(既定では無効で 0、config/default/kustomization.yaml で有効化する前提)。これらはコントローラー自身のロジックとは別に、kubebuilder が土台として先に用意してくれる。一方、Events(第 09〜10 回で触れた、オブジェクトに紐づく短期間の記録)は生成直後のコードには一切出てこず、必要になったら自分でコントローラーに追加する。追加するときは、controller-runtime のドキュメントが非推奨としている旧 API(mgr.GetEventRecorderFor が返す record.EventRecorder)ではなく、mgr.GetEventRecorder(name) が返す events.EventRecorder(k8s.io/client-go/tools/events)を使うのが今の推奨。

図: health probe と metrics は manager が土台として用意し、Events はコントローラーのロジックの中から出す。

5. テストの層 ― 生成直後にあるのは envtest と e2e の 2 つ

生成直後のプロジェクトに実際にあるのは、internal/controller/suite_test.go(envtest を起動するセットアップ)と internal/controller/*_controller_test.go(その envtest が立てた本物の API サーバーに対して、Ginkgo/Gomega で CR を作って Reconcile を呼ぶテスト)、そして test/e2e/*_test.go(e2e テスト)の 2 層。*_controller_test.go という名前から「単体テスト」に見えるが、中身は k8sClient(envtest が用意した、本物の API サーバーに繋がるクライアント)を使っているので、モックも何も起動しない単体テストではなく envtest 側のテスト。モックや外部依存を一切使わない、本当の意味での単体テストは生成直後には無く、必要なら自分で追加する。Makefile の test ターゲットは setup-envtest(本物の API サーバーと etcd のバイナリを手元に用意するツール)を経て、この envtest のテスト一式(*_controller_test.go を含む)を実行し、test-e2e ターゲットは test/e2e/ を別枠で実行する。

envtest は「API サーバーと etcd だけ」なので、他のコントローラー(組み込みの kube-controller-manager など)が本来やってくれる GC や PV のバインドは起きない。第 10 回で見た ownerReferences による GC のテストを envtest だけで完結させようとすると、GC コントローラー自身が動いていないため、削除してもテスト内では消えない結果になる。

図: 単体テストは生成直後には無く自分で足す。envtest(suite_test.go + *_controller_test.go)は API サーバーと etcd だけ。e2e は本物のクラスタ全体。

まとめと次の回

kubebuilder は、マーカーから CRD・RBAC の YAML を生成し、複数のコントローラーを 1 つの manager にまとめ、leader election・health probe・metrics という運用の土台をあらかじめ用意してくれる。テストは生成直後からある envtest・e2e の 2 層に、必要なら自分で単体テストを足す形になる。envtest は「本物の API サーバーと etcd だけ」という特有の制約(他のコントローラーがいない)を理解して使う必要がある。

これで第 01〜15 回の「仕組みの地図」「CRD を書く」「コントローラーを書く」「API サーバーを拡張する」という 4 つの段階が終わった。第 16〜18 回では、ここまでに学んだすべてを本物の題材 SharedFilesystem / SharedFilesystemClaim に適用し、題材選び・設計・実装と実機検証を行う。

図: マーカー・manager・テスト(envtest・e2e、単体は自分で足す)が、CRD とコントローラーを書くための土台。

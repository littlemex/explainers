DEEPEP と EFA ・ 18

vLLM が動いた。犯人は vLLM 自身だった

4 つの計測器を 1 つずつ潰し、最後に残った場所を捕まえたら、そこは DeepEP でもエミュレータでもなかった

← シリーズ目次

1症状

vLLM で DeepEP V2 を使うと、起動の途中で Python の中が壊れていた。

vLLM で DeepEP V2 を使うと、起動の途中 (モデルの読み込み直後) で Python の中でセグフォルトしていました。一度だけ、最後まで動いた回もありましたが、答えは perturbed is perturbed is … という壊れた文字列でした。DeepEP を使わない対照は Paris. と正しく答えます。

2犯人を絞った順番 (消去法)

1 つの計測器は、見える範囲が決まっている。範囲を 1 つずつ潰していく。

調べた場所使った道具結果
(a) エミュレータAddressSanitizer 付きでビルド報告なし。ヒープ上の 512 バイトの窓への書き込みは、すべて正当だった
(b) DeepEP 本体AddressSanitizer 付きでビルド報告なし
(c) GPU 側compute-sanitizer (範囲外アクセスを調べる道具)違反なし
(d) 第 17 回の D7 (窓の登録解除漏れ)窓の登録・登録解除のログ窓の破棄が起きていないので、当てはまらない

ここまでで、エミュレータ・DeepEP の host 側・GPU カーネルの 3 つが外れました。残る場所は、それ以外のどこかです。

3決め手

CPython 自身のデバッグ用メモリ管理が、両ランクで同じ場所を捕まえた。

CPython のデバッグ用メモリ管理 (PYTHONMALLOC=debug、Python が確保した領域の前後を見張って、余分な書き込みを捕まえる仕組み) を使うと、両ランクで同じ場所が引っかかりました。56 バイトとして確保した領域の直後の 8 バイトが上書きされていて、その領域を解放したのは vLLM の _check_gin_support でした。

4原因

vLLM が申告したバージョンと、実際に受け取る構造体の大きさが合っていなかった。

vLLM 0.28 は、NCCL の通信路の性質を受け取る構造体 (ncclCommProperties) を、ctypes (C の構造体を Python から使う仕組み) で定義しています。その定義はNCCL 2.31 より前の並び (56 バイト) のままでした。ところが vLLM は NCCL を呼ぶときに「自分は NCCL 2.31 以上だ」と申告します。

NCCL 2.31 は、申告されたバージョンをそのまま信じて、2.31 で増えたフィールドまで書き込みます。構造体全体としては 144 バイトです。つまり、vLLM が確保した 56 バイトの後ろに、88 バイトが余分に書き込まれていました。捕まった 8 バイトは、ちょうどオフセット 56 にある commHash (ハッシュ値を入れる場所) に当たります。

NCCL 側にも防ぐ手はありました。構造体の先頭には size (呼び出し側が用意した構造体の大きさ) を書く場所があります。NCCL がそこを見て、申告されたバージョンではなく、実際に用意された大きさに合わせて書き込んでいれば、この事故は起きませんでした。

5証明

この定義だけを直したら、症状は消え、答えも正しくなった。

vLLM のこの定義だけを、NCCL 2.31 と同じ 144 バイトに直しました。すると、それまで毎回起きていたセグフォルトが消え、2 回中 2 回とも起きませんでした。vLLM は DeepEP V2 とエミュレータの上で初めて起動を完了し、答えは Paris.\n\nThe capital of the United States is Washington, D.C. … になりました。これは、DeepEP を使わない対照の答えと1 文字も違いません。

9 月に見えていた perturbed is perturbed is … という壊れた答えも、同じヒープ破壊で説明がつきます。壊れた回だけ最後まで走り、それ以外は途中でセグフォルトしていた、という関係です。

6教訓

「落ちるのは呼んだ直後」でも、犯人はその名前とは限らない。

「落ちるのは DeepEP を呼んだ直後」だからといって、犯人が DeepEP とは限りません。計測器ごとに見える範囲が決まっているので、見える範囲を 1 つずつ潰していくと、最後に残った場所が犯人になります。今回は、エミュレータ・DeepEP・GPU カーネルの 3 つを潰して初めて、vLLM 自身という場所が残りました。

7意味すること (誇張しない)

これは vLLM 側への報告事項であり、範囲を正しく書く。

これはvLLM への報告事項です。DeepEP V2 を NCCL 2.31 以上で使う vLLM の利用者全員に関係しうる問題です。今回確かめたのはvLLM 0.28 と NCCL 2.31 から 2.32 の組み合わせで、本物の EFA 上ではまだ確認していません。

訂正。関係するのはvLLM 0.28 の利用者です。vLLM 0.30.0 では、上流ですでに直っています (どの版でこの修正が入ったかは未確認)。0.30.0 の該当箇所には、今回ここで突き止めたのと同じ原因がコメントで書かれていました ―― NCCL は size ではなく申告された version で書き込むので、定義より新しい version を申告しないこと、という趣旨です。つまり私たちが特定した原因は、上流の修正と一致していました。「vLLM への報告事項」という言い方はやめます。0.28 を使っている人は、0.30.0 以上に上げれば済みます。

8あふれることと、落ちることは別

88 バイトの書き込みがあふれるのは条件がそろえば毎回起きる。だが、それで落ちるかどうかは運任せの部分がある。

あふれた書き込み自体は、条件 (NCCL 2.31 以上に、旧い 56 バイトの定義で申告する) がそろえば毎回起きます。ですが、それでプロセスが落ちるかどうかは、あふれた先にたまたま何が置かれているかで決まります。あふれた先が壊しても実害の無い場所なら、何も起きずに見えます。検証機 (RTX PRO 6000) では、あふれた先が壊せる場所だったため、毎回落ちました。

9H100 (p5) で vLLM 0.30.0 を確認

別の世代の GPU でも、直った版なら壊れないことを確かめた。

H100 (p5) で、vLLM 0.30.0 を DeepEP V2 とエミュレータの上で 3 回回しました。3 回とも、対照と同じ Paris. の答えになりました。デバッグ用メモリ管理 (PYTHONMALLOC=debug) で見ても、あふれは 0 件でした。

10おまけ: 最初の生成が遅い件

止まっていたのではなく、初回の準備に時間がかかっていた。

起動が完了したあと、最初の生成には 2 分以上かかりました。これは、初回だけ発生するカーネルのその場コンパイル (JIT) などの準備によるもので、止まっていたわけではありません。2 回目以降の生成はこの時間を必要としません。

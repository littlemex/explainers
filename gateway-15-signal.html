第 15 章 「いつ箱の答えを採るか」を言う信号が、どこにも無い

この章の 3 行 第 14 章の 15.9% はオラクル前提だった。実装するには箱のパッチを採ってよいと言う信号が要る。 基準を数字を見る前に決めてから 3 系統を試し、3 系統とも落ちた。 エピソード内の信号は最良 0.77、自己一貫性は精度ではなく算術で死に、安い層による判定は 0.78 で 誤りが全部危険側だった。そしていちばん自然な信号は符号ごと逆を向いていた。

まず、何を満たせば合格なのかを数字より先に決めた

この種の探索はやり方を間違えると必ず何かが「見つかる」。20 件のデータに対していくつも規則を試し、 いちばん良かったものを報告すれば、それは発見ではなく選び方の産物である。だから読み方を先に固定して 記録に残した。以下はすべて分離を 1 度も見る前に決めたことである。

いちばん重要な決定は極性だった。当初は「失敗検出器」を作るつもりでいたが、費用が非対称である。 箱が失敗したのに採ってしまうと誤ったパッチが出荷される。逆に成功したのに投げ直しても、 損は API 呼び出し 1 回ぶん (平均 $0.679) で済む。

だから作るべきものは「高精度の成功検出器」である 既定はエスカレーション。採るのは、安価な十分条件が立ったときだけ。十分条件は臆病でよいので、 失敗検出器より作りやすい。基準はkeep-precision 1.00 — 採った件は全部が実際に解けていること。 この極性の反転は 2 つの外部モデル (Fable と GPT-5.6 sol) が独立に指摘したもので、 分離を見る前に事前登録へ書き足した。

合わせて決めたこと。信号は 5 つに閉じ、単変量のしきい値だけとする (20 件でモデルを当てはめれば それは乱数生成器である)。本命の仮説を 1 つ名指しする。指標は AUC でなく金額で、 しかも品質を揃えたときだけ請求額を比べる。この最後の 1 行は第 12 章の反省から来ている。

系統 1: エピソードの中にある信号

箱の走行そのものが残す情報 — 自分で終わったか、上限に当たったか、パッチを出したか、手数、 パッチの大きさ — で採否を決められるか。統合 20 件での成績である。

規則 (これを満たしたら採る)採ったうち解けていた誤って採ったkeep-precision
手数の上限に当たっていない131030.77
本命の仮説: 自分で終わった かつ 自前テストが緑12930.75

すべての規則に誤って採った件がある。最良が 0.77 で、基準の 1.00 には届かない。 開発用の 12 件だけで見ると 0.62 と 0.57 で、もっと悪かった。

後から測った 8 件では両方 1.00 になった。それは発見ではない 後から測った集合では箱が 8 件すべてを解いている。正解率が 100% の集合では、どんな規則でも keep-precision は 1.00 になる。事前登録には「そこで 1.00 が出ても、それはサンプリングの偶然であって 発見ではない」と先に書いてあった。実際にそうなったので、そう報告している。

そしていちばん自然な信号は、符号ごと逆を向いていた

「モデル自身が走らせたテストが通っていたら採る」は、いちばん素直な十分条件である。 箱は 12 件すべてでテストを走らせていたので、信号は存在した。向きが逆だった。

箱の自前テストの最終結果件数実際に解けていた
緑104 (40%)
赤22 (100%)

この集合の正解率は 6/12 なので、緑を採るのは当てずっぽうより悪い。赤が 2 件しかないので統計の 主張はできないが、向きの理由は標本数に依存しない構造にある。

採点するテストは、定義上そのチェックアウトに入っていない SWE-bench が判定に使うのは fail_to_pass、つまり修正前に落ちていて修正後に通るべきテストである。 それはリポジトリの作業コピーには置かれていない。だからそこに在るテストが緑になったことの意味は 「何も壊していない」であって、「報告されたバグを直した」ではない。自前テストが緑になった時点で 終わるモデルは、頼まれた仕事の 1 歩手前で止まっている。実際 4 件がそれをやった。

これは 1 つの助言を訂正する結果でもある。この解析を最優先にした理由は「コードの仕事では リポジトリのテストは本番の信号の代用ではなく本番の信号そのものだ」という指摘だった。一般論としては 正しい。このベンチマークの形では構造的に成り立たない。

系統 2: 自己一貫性は、精度を測る前に算術で落ちた

次の候補は同じ課題を箱に k 回解かせて、答えが一致したときだけ採るである。 箱は時間課金で遊んでいるのだから、サンプルを増やすのはほぼ無料に見える。ここで 信号の予算を先に計算した。信号にかけてよい金額は、その信号が守ろうとしているもの全体 — 20 件で $0.9548、1 件 4.8 セント — を超えられない。

候補費用箱なし 2 段に対して
箱を 3 回走らせて一致で採る箱の請求 × 3+14.1%
2 回、しかも完全な一致信号を仮定して箱の請求 × 2−0.9%

払える k の上限は 2.06 である。2 本目のエピソードの費用が、構成全体の節約より大きいからで、 完全な一致信号を仮定しても天井が −0.9% しかない。一致が良い信号かどうかとは無関係に落ちるので、 実験はしていない。これは箱の経済についての結果であって、手法についての結果ではない。

系統 3: 安い層にパッチを 1 回だけ判定させる

予算内に収まる候補が 1 つ残った。安い API に、報告文と箱のパッチだけを見せて可否を答えさせる。 実測で 1 件 $0.0075、20 件で予算の 16% である。パッチと正解はすべて保存されているので、 新しいエピソードは 1 本も要らない。手元のデータに対する 1 回ずつの呼び出しで評価できる。

判定器に見せるものも先に固定した。報告文とパッチだけである。隠しテスト、正解パッチ、 箱の走行記録、テストの結果はいずれも渡さない。渡せば、本番では計算できない信号について 都合の良い評価をすることになる。答えは最後の行に VERDICT: FIXED または VERDICT: NOT_FIXED の 1 行、読めない答えは投げ直し扱いとした。 読めない判定器が偶然パッチを採ってしまってはいけない。

聞き方は 1 回書いて凍結した。読み手が確かめられるように全文を出しておく。

You are reviewing a proposed fix for a reported bug in a Python repository.

You are given the bug report and a unified diff. Decide whether the diff, as written, fixes the
behaviour the report describes. You cannot run anything; judge from the report and the diff alone.

Be strict in one specific way: a diff that changes something related, or that adds a guard without
changing the behaviour the report is about, does not fix it. A diff that is empty does not fix it.

Think briefly, then end your reply with exactly one of these two lines and nothing after it:

VERDICT: FIXED
VERDICT: NOT_FIXED
採った投げ直した
箱は実際に解けていた140
箱は解けていなかった42

失敗しやすい構造的な理由が、前の章の表に書いてあった

判定器は解答者より細かい問いを、より少ない情報で問われている。この 20 件を、安い API 自身は 16 件しか解けない。その同じモデルに、リポジトリも無く、何も実行できず、採点テストも見せずに 「修正」と「惜しい失敗」を判別させるのは、本人が最後までできない課題より難しい。 できると期待する理由が最初から無かった、という読み方になる。

もっと厳しい聞き方は、あえて試していない 「もっと厳しく判定させれば精度が上がるのでは」は当然の次の一手で、やらないことにした。 いくつも聞き方を試していちばん良かったものを報告するのが、事前登録がまさに防いでいる手続きである。 やるなら別の事前登録と、別の取り置き集合が必要になる。いま言えるのは、 唯一予算に収まる系統について、正直に固定した最初の 1 手が 0.78 だったということである。

無料の信号のほうがましだった。それでも 1.00 ではない

同じ事前登録で「パッチが報告文に出てくるファイルを触っているか」も名指ししてあった。費用ゼロで、 採った 7 件のうち 6 件が正解、precision 0.86 である。判定器より良い。それでも 1.00 ではなく、 しかも採れる件数が 3 分の 1しかないので、守れる節約もそれだけ小さい。

ここまでで箱について言えること

第 14 章の 15.9% は、達成可能な流量 (毎時 319 タスク、箱のスループットの内側) で成立する額である。 それでも推奨は「このトラフィックでは自前サービングをしない」で変わらない。塞いでいるものが 算術から検出器に移っただけで、3 系統とも事前に決めた基準で落ちた。

結論が変わる条件を 4 つだけ挙げる。議論ではなく検証できる形にしてある。

  1. 毎時 320 タスクを超える持続的な流量が、前置きを再利用する形のトラフィックで実在すること。
  2. リポジトリのテスト以外から来る検証信号。テストの中にある信号は構造的に使えないと分かった。
  3. 箱の解決集合が部分集合でないトラフィック族。そこで初めて箱は費用ではなく能力の論拠を持つ。
  4. API が値段では満たせない要件 — データの所在、レイテンシ、隔離環境など。

この章で言えないこと

20 件で、うち解けているのは 14 件である。誤って採った件が 0 だったとしても、その時点で 言えるのは受け入れ誤り率の上限がおおよそ 15% ということで、本番の保証にはまったく足りない。 仮に誤ったパッチ 1 件の損害を $100、投げ直しを $0.679 とすると、採ってよい条件は成功確率 99.3% 以上に なる。この規模の標本でそれを示すことは原理的にできない。事前登録にもそう書いてある。

3 系統が落ちたことは、信号が存在しないことの証明ではない。閉じたのは 「エピソード内の記録」「箱の反復サンプル」「安い層による 1 回の判定」の 3 つで、 静的解析、リンタ、型検査、CI のようにまだ試していないものが残っている。 それらは第 14 章の表に入っていない費用を持つので、同じ予算の枠で先に値付けする必要がある。

判定器の 0.78 は 1 つの聞き方の結果である。上に書いたとおり、聞き方を変えれば数字は動く。 動かした結果を報告するには別の取り置き集合が必要で、この章はそれを持っていない。

箱が悪いモデルだという話はしていない。箱は 20 件のうち 14 件を、高い API の 1 割以下の 単価で解いている。ここで落ちているのは構成であって、モデルの順位ではない。

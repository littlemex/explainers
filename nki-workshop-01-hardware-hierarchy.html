NKI WORKSHOP ・ 01

Trainium のハードウェア階層をビジュアルに理解する

Chip・NeuronCore・HBM / SBUF / PSUM ― 容量と帯域の差を、絵と公式スペックで腹落ちさせる

0この記事の狙い

NKI (Neuron Kernel Interface) で高性能なカーネルを書くには、まずハードウェアのメンタルモデルが要ります。どのメモリがどれだけ速く・どれだけ入るのか、データはどう動くのか。ここでは AWS Trainium2 の 3 層メモリ階層 (HBM / SBUF / PSUM) と計算エンジンの関係を、絵と実測値で腹落ちさせます。

一言でいうと
Trainium は「小さくて速い」オンチップメモリ (SBUF / PSUM) と「大きくて遅い」HBMの 3 層で、その間を DMA エンジンが運びます。それぞれ容量と帯域が大きく違い、この非対称が後続のカーネル最適化すべての土台になります。この記事で「速度と容量の地図」を頭に入れれば、以降の最適化がすべて「この地図の上でデータをどう動かすか」に見えてきます。
1. Chip / Device / Core の関係 2. NeuronCore の中身 ― 4 つのエンジン 3. 3 層メモリ階層 ― HBM / SBUF / PSUM 4. 【体験】容量と帯域の地図 5. HBM ― 大きくて遅い倉庫 6. SBUF ― 2D の作業台 7. PSUM ― Tensor Engine 専用の集計台 8. データはこう流れる (DMA) 9. 【体験】partition を使い切る 10. GPU との決定的な違い 11. まとめ

対象は AWS Trainium2 (TRN2, NeuronCore v3)。数値は NKI Workshop の資料・実測に基づきます。GPU の内部構造には深入りしません (別記事で扱います)。

1Chip / Device / Core の関係

まず用語を揃えます。「デバイス」「コア」「インスタンス」は別物です。

Trainium は階層で数えます。一番外から見ると:

  1. Device (チップ): 1 枚の Trainium2 チップ。公式スペックで FP8 dense 約 1,299 TFLOPS (≈ 1.3 PFLOPS)、96 GiB の HBM を持ちます。※ BF16 (dense) では約 667 TFLOPS (≈ 0.67 PFLOPS)。1.3 PFLOPS と 0.67 PFLOPS の差は LNC・クロック等の集計基準の違いではなく、精度 (データ型) の違い (FP8 か BF16 か) によるものです。NKI アーキテクチャガイドでは NeuronCore-v3 の Tensor Engine を コアあたり FP8 158 / BF16 79 dense TFLOPS としており、8 コアぶんにすると 158×8 ≈ 1,264、79×8 ≈ 632 とチップ公称値 (1,299 / 667) におおむね一致します (端数はコアあたり値の丸めと集計条件の差)。要するに、値の大小はどの精度で数えるかで決まり、LNC の束ね方には依存しません。
  2. NeuronCore (物理コア): 1 デバイスの中に 8 個の物理コアがあります (TRN2/TRN3)。2 コアが 1 つの HBM スタックを共有します。
  3. LNC (Logical NeuronCore): 既定は LNC2 で、2 つの物理コアを 1 つの論理コアとして扱います。だから neuron-ls は 8 でなく 4 コアと表示します。なぜ束ねるのかは 06 章で扱います。
  4. Instance: 複数デバイスをまとめたもの (例: 16 デバイス)。今回のワークショップは trn2.3xlarge (単一デバイス) を使います。

言葉だけだと入れ子の関係が掴みにくいので、1 枚の図にします。クリックすると各階層がハイライトされます。

Instance Device (チップ) NeuronCore 2 コアで 1 HBM スタックを共有

クリックした階層の説明: 図の各層をクリックしてみてください。

この記事で主役になるのは 1 つの NeuronCore の内側です。カーネルは基本この単位で動き、メモリ (SBUF / PSUM) も計算エンジンもこのコアに属します。「まず 1 コアを使い切る」がカーネル最適化の出発点です。以降、この記事で「1 コア」と書くときは物理 NeuronCoreを指します (LNC でまとめた論理コアではありません)。

2NeuronCore の中身 ― 4 つのエンジン

NeuronCore は「1 つの万能プロセッサ」ではなく、役割の違う専用エンジンの集まりです。

Trainium はディープラーニング専用にゼロから設計されており、必要な演算ごとに専用ハードウェアブロックを持ちます。汎用の 1 コアが何でもこなすのではなく、行列積・要素演算・活性化・カスタム演算をそれぞれ別のエンジンが担当します。

エンジン役割ひとこと
Tensor Engine行列積 (MatMul)・transpose・broadcast128×128 の systolic array。FLOP の約 90% がここ
Vector Engine (profiler では Pool)reduction、要素ごと演算、tensor-tensor 演算合計・max など。SBUF の partition に並列接続
Scalar Engine (Act)活性化関数、区分多項式マイクロコードで機能追加できる
GP-SIMD Engineカスタム演算・descriptor 生成など8 個の SIMD プロセッサ。汎用の受け皿
Tensor Engine は 128×128 の systolic array。行列積を、格子状に並んだ 128×128 個の積和演算器 (PE) にデータを流し込んで解きます。片方の行列を格子に固定 (stationary) して保持し、もう片方を流し込む (moving) と、各 PE が積和を次々にリレーしていく ― この「データが格子を流れる」動きが systolic (心臓の拍動のような) と呼ばれる所以です。下の図でその流れを見ます。NKI からはこの行列積が nki.isa.nc_matmul という 1 命令として使えます (格子への載せ方・流し方の最適化は 06 章で扱います)。
stationary (格子に固定) moving (流れ込む入力) PE (積和・稼働中) PSUM (出力)

実物は 128×128 の PE が並びますが、ここでは動きが見えるように一部 (6×6) を描いています。複数の PE が同時に光っている部分が「並列に積和が進んでいる」ことを表します。

設計思想。これらは独立にスケジュールされ、並列に動きます。Tensor Engine でタイル行列積をしている「その裏で」Vector Engine が別の reduction を回す ― というエンジン間パイプラインでチップを使い切るのが狙いです。だから「1 つのエンジンだけ速くする」のではなく「全エンジンを同時に働かせる」のが性能の鍵になります。

NeuronCore 全体像 ― データはこの上を流れる

ここまでの登場人物 (エンジンと 3 種のメモリ、DMA) を 1 枚の図にまとめます。「再生」を押すと、行列積 1 回ぶんのデータの流れが流れます。以降の章はすべて、この地図のどこかの話をしています。

HBM SBUF PSUM エンジン DMA が運ぶデータ

流れを、実際に「何が」流れているかまで具体化すると: (①) DMA が 重みタイル W と 活性タイル X を HBM から SBUF へ運ぶ。(②) Tensor Engine が SBUF 上の 2 入力 (W と X) を読んで行列積を計算する。(③) 結果の 部分和 (partial sum) が PSUM に蓄積される。(④) Vector / Scalar が PSUM の部分和を読み、必要なら活性化などを施しながら SBUF へ退避する (退避後のデータが出力 Y)。(⑤) DMA が出力 Y を SBUF から HBM へ書き戻す。計算エンジンは HBM を直接触れず、必ず SBUF を経由します。この記事の主題はメモリなので、以降はエンジンより「データがどこに置かれ、どう運ばれるか」に集中します。

33 層メモリ階層 ― HBM / SBUF / PSUM

Trainium のメモリは 3 層。上に行くほど小さく速く、下に行くほど大きく遅い ― この非対称が全ての制約の源です。

PSUM # Tensor Engine 専用の集計台。最小・最速・2 MiB。TE出力先はPSUMのみ、蓄積はTE固有
↕ (Vector / Scalar も並列アクセス可。GpSimd は非対応)
SBUF # オンチップの作業台 (SRAM)。2D。全エンジンが直結
↕ (DMA エンジンが運ぶ)
HBM # 大きな倉庫。1D フラット。DMA しかアクセスできない

3 つの「大きさ」と「速さ」の関係を、TRN2 の実数で並べます。

メモリ種類容量 (TRN2)速さ / アクセス誰が触れる
HBM大容量 DRAM96 GiB / デバイスDMA ピーク 約 435 GB/s (1コア)DMA エンジンのみ
SBUFオンチップ SRAM28 MiB / コア (224 KiB × 128 partition)桁違いに高速・全エンジン直結全 compute engine + DMA
PSUMオンチップ SRAM128 part × 8 bank × 512 要素 (計 2 MiB)最速・Tensor Engine 蓄積用行列積の蓄積は TE 固有 / Vector・Scalar もアクセス可 (GpSimd 不可)
ここが最重要の直感。SBUF は HBM よりずっと速いが、ずっと小さい (容量は 96 GiB 対 28 MiB = 約 3500 倍の差)。だから「必要なデータだけを SBUF に載せ、計算し、書き戻す」というやりくりが要る。この容量と帯域の非対称こそが、カーネル最適化で戦う相手です。次章で地図として体感します。
注: 一般論として、HBM (DRAM) のアクセスは数百 ns オーダー、オンチップ SRAM (SBUF/PSUM) は ns オーダーで、レイテンシで 2 桁ほど差がある。帯域でもオンチップが大きく上回る。ここでの「速い/遅い」はこの意味で、具体的な絶対値は世代・アクセスパターンに依存する。

4【体験】容量と帯域の地図

3 層の「容量」と「速さ」を対数スケールで並べます。バーの長さの違いが、そのまま設計の制約になります。

HBM SBUF PSUM

「容量で見る」と HBM (96 GiB) が圧倒的に大きく、SBUF・PSUM はごくわずか。「速さで見る」と関係が逆転し、オンチップの SBUF / PSUM が HBM を大きく上回ります。大きい所は遅く、速い所は小さい ― この綱引きが、後続のすべてのカーネル最適化テクニック (タイリング、SBUF 常駐、フュージョン) の動機になります。

5HBM ― 大きくて遅い倉庫

まず一番下の層、HBM から。

HBM (High Bandwidth Memory) はデバイスの大容量メモリ (TRN2 で 96 GiB) で、モデルの重み・活性・入出力などすべての大きなデータの置き場です。PyTorch (torch-neuronx / torch_xla) で tensor.to(xm.xla_device()) のようにデバイスへ転送すると、データはここに載ります。

HBM の 2 つの重要な性質。
(1) 1D フラットメモリ ― 単純な一次元の並び。
(2) DMA エンジンからしかアクセスできない ― 計算エンジン (Tensor / Vector など) は HBM を直接読めません。必ず一度 SBUF に運んでから計算します。

「高帯域」の名の通り帯域は大きいですが、オンチップ SRAM と比べれば遅い。デバイス全体の HBM 帯域は公式値でチップ全体 約 2.9 TB/s。この記事で扱う 435 GB/s は、他のコアがアイドルな条件で単一 NeuronCore が 16 個の DMA エンジンを全部使い切って到達した実測上のピークです。8 コアが同時にこの値を出せるわけではなく、合計はチップ全体の 2.9 TB/s で頭打ちになります (435×8 ≈ 3.5 TB/s は超えられない)。1 コアぶんの帯域にどこまで近づけるかが、メモリバウンドなカーネルの成否を分けます (8 章)。

この 435 GB/s は 1 個のエンジンの値ではなく、16 基の DMA エンジンの合計です。内訳を式で見ると、なぜこの数字になるかが分かります。

# TRN2: DMA エンジン1基あたり約27.2GB/s × 16基
16 × 27.2 GB/s ≈ 435 GB/s # 1コアのHBMピーク(概算)
# TRN3 は1基あたりの帯域が伸びる
16 × 38.4 GB/s ≈ 614 GB/s # TRN3の1コアHBMピーク(概算)

補足: 1 基あたりの帯域も概算値であり、実際の達成帯域はタイル形状やアクセスパターンに依存します (9 章)。partition 次元を絞ると、この 16 基のうち動くエンジン数そのものが減る点は 9 章で体感します。

6SBUF ― 2D の作業台

SBUF は Trainium で最も「クセ」のあるメモリです。ここの構造がカーネル設計を強く縛ります。

SBUF (State Buffer) はオンチップの汎用スクラッチパッド (SRAM) で、計算エンジンが実際に読み書きする作業台です。HBM と違い 2D 構造を持ちます。

注: ここで挙げる 28 MiB / PSUM 2 MiB / 435 GB/s は物理コアあたりの値です。既定の LNC2 では NKI から見える 1 論理コアは物理 2 コア分で、これらのリソースはおおむね 2 倍見えます (詳細は 06 章)。

# SBUF の形 (TRN2)
partition 次元 (P) : 128 レーン # 固定。ここが超重要
free 次元 (F) : 各レーン 224 KiB 連続 # TRN3 は 256 KiB
合計 : 約 28 MiB / コア # TRN3 は 32 MiB

この 128 という partition 次元が Trainium の随所に効いてきます。理由は 2 つ:

  1. 全 compute engine が partition に並列接続されている。だから partition 次元の演算は「幅を増やしてもコストがほぼ一定」 (64 幅も 128 幅も同じ時間)。逆に partition を 128 未満しか使わないと、その分だけ FLOP を捨てています。
  2. DMA エンジンも partition のサブセットを担当する。少ない partition しか使わないと、使える DMA エンジンも減り、帯域を取りこぼします (9 章で体感)。
覚えておくべき合言葉は「partition 次元 (128) を使い切れ」。テンソルの形を 2 のべき乗・128 に寄せると、計算も DMA も素直に速くなります。逆に中途半端な形 (例: 51) は遅くなり、64 に丸めるだけで 30% 速くなることもあります。SBUF に載りきらないデータを詰め込むと、コンパイラが HBM へあふれさせ (spill)、性能が激しく落ちる点にも注意です。

partition 数 (128) は世代を通じて固定ですが、1 レーンあたりの容量は世代が進むごとに増えています。傾向として押さえておく価値があります。

世代1 レーンあたりSBUF 合計 (128 レーン)
TRN1 / Inf2192 KiB約 24 MiB
TRN2224 KiB約 28 MiB
TRN3256 KiB約 32 MiB

TRN2 の 28 MiB は公式値。TRN1/Inf2 の 24 MiB、TRN3 の 32 MiB は公開情報ベースの参考値で、世代とともに 1 レーンあたり容量が増える例として挙げています (将来世代の予測ではありません)。

7PSUM ― Tensor Engine 専用の集計台

3 層目の PSUM は、Tensor Engine の行列積の「出力受け皿」に特化した小さなメモリです。

PSUM (Partial Sum buffer) は、Tensor Engine が行列積の部分和を蓄積するための専用バッファです。総容量は 2 MiB (128 partition × 8 bank × 2 KB/bank、fp32 で 512 要素/bank)。

# PSUM の形と制約 (TRN2)
構造 : 128 partition × 8 バンク × 512 要素/バンク (fp32)、合計 2 MiB
型 : FP32 アキュムレータ
出力先 : Tensor Engine の行列積結果は PSUM にしか書けない
蓄積 : 行列積結果を足し込める (accumulate) のは Tensor Engine 固有
アクセス : Vector / Scalar エンジンも PSUM を読み書き可。# GpSimd は PSUM 非対応

行列積のデータの流れはこうです。Tensor Engine が SBUF の 2 つの入力を読んで計算し、結果をPSUM に蓄積。その後、Vector か Scalar エンジンが PSUM から SBUF へ退避 (evict) します。PSUM そのものは各エンジンからアクセスでき、Tensor Engine に固有なのは「行列積の結果をハードウェアで足し込める (accumulate できる)」点です。

退避はフュージョンのチャンス。PSUM から SBUF へコピーする「ついで」に、活性化関数や reduction を一緒に済ませられます。Tensor Engine が matmul した結果を SBUF に戻す途中で活性化を掛ければ、別途エンジンを回す往復が消える ― これが NKI で手書きカーネルを書く大きな動機の一つです。

なお「8 バンクを全部埋めれば速い」は誤解になりがちで、実際はバンクを早く空ける (drain) 方が速いことが多いです (この詳細は別記事のマイクロベンチマークで扱います。07 章で回収)。

8データはこう流れる (DMA)

層と層の間でデータを運ぶのが DMA エンジン。ここの効率が、メモリバウンドなカーネルの速度を決めます。

DMA (Direct Memory Access) エンジンは、HBM ↔ SBUF および SBUF ↔ SBUF のデータ移動を担当します (NeuronCore あたり 16 個)。逆に、compute engine が SBUF を読むのや、PSUM の出し入れは DMA ではありません。

# カーネル内の典型的なデータフロー
HBM  —DMA→  SBUF  —Tensor Engine→  PSUM
PSUM  —Vector/Scalarで退避→  SBUF  —DMA→  HBM

DMA には固定のオーバーヘッド (トリガー・descriptor 生成・キュー投入) があります。だから小さな転送を大量にやると、オーバーヘッドばかりで帯域が出ません。逆に大きな連続転送なら、オーバーヘッドを償却できて帯域を使い切れます。

DMA を速くする 2 つの鉄則。
(1) partition 次元を最大化 (128) ― 16 個の DMA エンジンを全部働かせる。
(2) free 次元を大きく (連続転送を大きく) ― partition あたり 4 KiB 以上 (DMA エンジン1基は8 partition 分を担当) を目安に、128 partition なら合計 512 KiB 以上でオーバーヘッドを償却。
実測での効き方 (NKI Workshop の DMA ベンチ)。同じ 256 MB のコピーでも、タイルの形で achieved 帯域が激変します。
・128×512 の小タイル → 約 224 GB/s (ピークの約 52%)
・128×8192 の大タイル → 約 424 GB/s (約 97%)
・128×16384 → 約 427 GB/s (約 98%、この構成の実質上限)
タイルの形を変えるだけで帯域が大きく変わる。DMA エンジンはどちらの形でもほぼ動いているのに、小さい転送は「忙しいのに遅い」。これが「geometry (形) が性能を決める」という Trainium の本質です (数値は特定条件での実測例)。

9【体験】partition を使い切る

同じ要素数のテンソルでも、SBUF 上の「形」で使える DMA エンジンの数が変わります。partition 次元の効きを見ます。

partition 次元 (P)
4使用 partition
1 / 16働く DMA エンジン
6%DMA 帯域の利用率(概念)

スライダーを動かすと、使う partition 次元に応じて働く DMA エンジンの数が変わります。4 partition しか使わないと DMA エンジンは 1 個しか動かず、帯域を 16 分の 1 に絞ってしまう。128 partition まで広げると 16 個全部が働き、帯域を使い切れます。free 次元を 4096 要素に固定したまま partition だけを 4×4096 から 128×4096 に広げると achieved 帯域が桁違いになる ― これが「partition を使い切れ」の意味です (free 次元が小さいと、たとえ 128 partition を使っても 8 章の転送サイズの目安に届かず帯域を使い切れません)。

補足: 図の「利用率」は partition の使い方が帯域に効くことを示す概念値で、実測の絶対値ではありません。実際は free 次元の大きさ (8 章) も同時に効きます。

10GPU との決定的な違い

GPU を触ってきた人ほど、ここで頭を切り替える必要があります。GPU の詳細には踏み込まず、思想の違いだけを押さえます。

最大の違いはオンチップ SRAM が「キャッシュ」か「スクラッチパッド」かです。

用語を正確に。「SBUF はオンチップ SRAM なんだから、GPU の L2 キャッシュと同じでは?」と思うかもしれません。物理的な素材 (SRAM) は同じですが、管理方式が根本的に違います。
・キャッシュ (cache): ハードウェアが自動で中身を出し入れする。どのデータが載っているかはタグで管理され、ヒット/ミスはプログラムから透過的 (見えない)。ソフトは「どこに何を置くか」を指定できない。
・スクラッチパッド (scratchpad): 番地を持つ普通のメモリで、載せる・降ろすを全部ソフトが明示的に命令する。自動のヒット/ミスは無い。
SBUF は後者 (スクラッチパッド)の代表例です。だから正しくは「Trainium はキャッシュを持たない」ではなく「ハードウェア管理のキャッシュを持たず、代わりにソフトウェア管理のオンチップメモリを持つ」です。
注: 厳密には、自由に読み書きできる汎用スクラッチパッドと呼べるのは主に SBUF。PSUM は「Tensor Engine の行列積の出力受け皿」という用途に強く縛られた専用バッファで、汎用スクラッチパッドとは性格が異なる (7 章参照)。
補足: GPU にも shared memory (scratchpad) はあり、「GPU=キャッシュのみ」ではありません。違いは、GPU では L1/L2 キャッシュ+ハードウェア prefetch が併存するのに対し、Trainium は全メモリ移動が DMA として明示的で、ハードウェア管理キャッシュそのものを持たない点です。
観点GPU (一般論)Trainium
オンチップメモリハードウェア管理のキャッシュ (L2 等)ソフトウェア管理のスクラッチパッド (SBUF/PSUM)
データ移動自動 (prefetch・キャッシュ再利用)明示的 (どのデータをいつ載せるか自分で書く)
最適化の焦点キャッシュヒット率を上げるデータの置き場と移動を設計する
制御の主体ハードウェアがよしなにあなた (と一部コンパイラ)
Trainium はハードウェア管理キャッシュを持ちません。SBUF も PSUM も SRAM ですが、自動プリフェッチもキャッシュ再利用も無いソフトウェア管理のスクラッチパッドです。「どのテンソルをいつ SBUF に載せ、いつ HBM に戻すか」を、あなたが NKI で明示的に書きます。これは意図的な設計で、ユーザーに最大限の制御を与えてピーク性能を引き出させるためです。
だから NKI はブラックボックスではない。「よしなにキャッシュしてくれる」を期待すると詰まります。逆に言えば、データの所在を完全に把握・制御できるので、フュージョン (SBUF 上で処理を繋げて HBM 往復を消す) や精度制御を自分で設計でき、コンパイラ任せを超える性能を出せます。GPU の「キャッシュ職人」から Trainium の「データ物流の設計者」へ、発想を切り替えるのが第一歩です。

階層Device (96GiB HBM) > NeuronCore ×8 (2コアで1 HBMスタック共有) > 既定 LNC2 で論理4コア

GPUとの違いハードウェア管理キャッシュを持たず、ソフト管理スクラッチパッド (SBUF/PSUM)。データの置き場と移動を全部ソフトで明示管理
結論。Trainium の性能は「小さくて速いオンチップ (SBUF/PSUM) と、大きくて遅い HBM の間で、いかにデータを賢く動かすか」に尽きます。partition 次元 (128) を使い切り、大きな連続転送で DMA 帯域を稼ぎ、SBUF 上で処理を繋げて HBM 往復を減らす。GPU と違ってハードウェア管理キャッシュが自動で助けてくれない代わりに、スクラッチパッドをすべて自分で設計できる。この「容量と帯域の地図」が、以降の NKI カーネル最適化すべての土台になります。

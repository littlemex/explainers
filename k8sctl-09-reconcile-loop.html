K8S CUSTOM CONTROLLER ・ 第 09 回

Reconcile ループの中身

何がきっかけでも、結局は「今の状態を読み直して差を埋める」関数が呼ばれるだけ

← カスタムコントローラー自作 シリーズ目次へ

第 03 回で、コントローラーは「今の状態を見て、望む状態との差を埋め続ける」調整ループ(reconcile loop)だと学んだ。この回ではその中身を、controller-runtime(controller-runtime: コントローラーを作るための Go の共通基盤ライブラリ)のソースコードに実在する名前で分解する。

この章の結論: Reconcile 関数は「何が起きたか」を渡されるのではなく「どのオブジェクトを見ろ」という名前だけを渡される。中身は informer(インフォーマー: API サーバーを一覧+監視し続けてキャッシュを作る仕組み)が用意したキャッシュを自分で読みに行く。だから同じ名前が何度積まれても、workqueue(ワークキュー: 処理待ちの名前を並べる待ち行列)が重複をまとめ、1 つの名前が同時に 2 回処理されることはない。

1. API サーバーを毎回叩かない: informer とキャッシュ

Reconcile はオブジェクトの数が増えるほど、また更新が増えるほど頻繁に呼ばれる。そのたびに API サーバーへ問い合わせていたら、対象が多いクラスタでは API サーバー側が先に音を上げる。そこで controller-runtime は informer を使い、対象の種類(例: Widget)を「まず一覧し、その後は変化だけを受け取る(List + Watch)」という形でまとめてローカルのキャッシュに複製する。

Builder の .For(&v1.Widget{}) を呼ぶと、裏側で Widget 用の informer が立ち上がり、cache(キャッシュ)に Widget の今の状態が複製される。コントローラーのコードが mgr.GetClient().Get(...) で読むとき、実際に読んでいるのはこのキャッシュで、読み取りのたびに API サーバーへは通信しない。書き込み(Create / Update / Delete)だけは直接 API サーバーへ飛ぶ。

図: API サーバーの変化は informer がキャッシュに写し、Reconcile はキャッシュだけを読む。

2. workqueue: 同じキーはまとめる、処理中のキーは並行処理されない

informer が変化を見つけると、変わったオブジェクトの名前(正確には namespace と name の組、キー)を workqueue に積む。controller-runtime v0.24.1 の既定の queue(pkg/controller/priorityqueue に実在。古い版や素の client-go の workqueue では dirty/processing という名前だったのと同じ役割を、items(次に処理する分の対応表)と locked(今まさに取り出されて処理中のキーの集合)という形で持つ)は、キーごとに 1 件しか保持しない。同じキーで AddWithOpts が重なっても 1 件にまとまる。同じ Widget が短時間に 5 回更新されても、処理が始まる前なら 1 回の Reconcile にまとめられる(ソースで確認: controller-runtime v0.24.1 の pkg/controller/priorityqueue/priorityqueue.go)。

さらに重要なのは、あるキーが locked に入っている(今まさに Get で取り出され Reconcile が実行中の)あいだに同じキーがまた積まれても、2 つめの Reconcile は始まらない。再度の Add は items を更新するだけで止まり、今動いている Reconcile が Done(完了)を呼んで locked から外れた時点で items に残っていれば、そこで初めて次の回が積まれる。つまり同じ Widget に対して 2 つの Reconcile が同時に走ることはない。

失敗した時は AddRateLimited で間隔を伸ばして再試行する。既定のレートリミッタは 5 ミリ秒から始めて最大 1000 秒(約 16.7 分)まで倍々に伸びる指数バックオフ(exponential backoff: 失敗するたびに次の再試行までの待ち時間を倍々に伸ばす作法。失敗が続くほど間隔を広げ、サーバーを叩き続けないようにする)で、成功すると Forget で間隔がリセットされる(controller-runtime v0.24.1 のソースで確認)。

図: dirty が重複を吸収し、processing が同時実行を防ぐ。

3. Reconcile(ctx, req) (ctrl.Result, error) が「名前だけ」を受け取る理由

実際のシグネチャ(controller-runtime v0.24.1 のソースで確認):

func (r *WidgetReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error)

ctrl.Request の中身は types.NamespacedName、つまり namespace と name の組だけ。どのフィールドが書き換わったかは一切渡されない。これは第 03 回で説明したレベルトリガー(level-triggered: 変化の内容そのものではなく「今の状態」を見るやり方)の実装そのもの。Reconcile は呼ばれるたびに「この名前のオブジェクトをキャッシュから読み直し、望む状態と比べて、足りない分だけ埋める」を最初からやり直す。

だから Reconcile を呼ぶきっかけが作成イベントでも更新イベントでも再試行でも、関数の中身を変える必要がない。むしろ変えてはいけない。イベントの種類で分岐するコントローラーは、再起動直後にイベントそのものを取り戻せず状態を見失う。

ここまでの材料を組み合わせると、Reconcile の骨組みはだいたいこの形になる(第 10・11 回で削除中の分岐と子の作成、status の書き方を詳しく見る)。

func (r *WidgetReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var w v1.Widget
    if err := r.Get(ctx, req.NamespacedName, &w); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }
    // ここに: 削除中かの判定(第10回)、子の作成(第10回)、status の更新(第11回)
    return ctrl.Result{}, nil
}

図: きっかけの種類は捨てられ、同じ 1 つの関数が毎回フルに読み直す。

4. For / Owns / Watches で何を見るか

ctrl.NewControllerManagedBy(mgr) で Builder を作り、.For(&v1.Widget{}) で「これを調整する対象」を登録する。ソースのコメントには、これは内部で Watches(source.Kind(cache, &Widget{}, &handler.EnqueueRequestForObject{})) を呼ぶのと同じだとある。

.Owns(&corev1.ConfigMap{}) は「自分が作った子を見る」。子が変わったら、その子の ownerReferences(第 10 回)をさかのぼって親の Widget の名前を workqueue に積む。

.Watches(&corev1.ConfigMap{}, handler.EnqueueRequestsFromMapFunc(fn)) は、所有していない任意のオブジェクトの変化を、好きな対応表(fn の型は func(context.Context, client.Object) []reconcile.Request、ソースで確認)で Widget の名前に変換して積む。1 つの変化から複数の Widget の名前を返すこともできる。どの経路でキーが積まれても、先は同じ 1 本の workqueue で、呼ばれる Reconcile も同じ関数。

図: 見る先が 3 種類あっても、積まれるキーと呼ばれる関数は 1 つにまとまる。

5. Result{RequeueAfter} とエラー返しの違い

Reconcile は (ctrl.Result, error) を返す。ctrl.Result は構造体なので nil は返せない。ctrl.Result{}, nil(ゼロ値の Result)ならこのキーの作業は完了で、次に動くのは informer が次の変化を見つけた時だけ。ctrl.Result{RequeueAfter: 30 * time.Second}, nil は、今は完了しているが 30 秒後に自分からもう一度見に行きたい(外部 API の状態をポーリングしたい時など)という意味で、この間隔はレート制限とは別経路で積まれる。error を返すと失敗として扱われ、AddRateLimited により前述の指数バックオフで再試行される。

両方を同時に設定(error も RequeueAfter も non-zero)すると、controller-runtime は error を優先し RequeueAfter を無視する。ソースのログ文面に "RequeueAfter and Requeue will always be ignored if the error is non-nil" とそのまま書かれている(controller-runtime v0.24.1 の pkg/internal/controller/controller.go で確認)。ポーリングだけしたいなら error を返してはいけない。

図: error が入っていると RequeueAfter は常に無視され、バックオフ側が勝つ。

6. キャッシュは少し古いかもしれない、という前提で書く

informer のキャッシュは watch イベントの到着を待っているので、API サーバーの最新状態より一瞬遅れることがある(ネットワークの遅延や再接続中など)。だから Reconcile の中で「このリソースはまだ無いはずだ」と思って Create しても、本当はもう誰か(別の Reconcile 実行、あるいは人間)が作っていて AlreadyExists が返ることがある。第 03 回で触れた冪等性(何回実行しても同じ結果になること)が守られていれば、AlreadyExists はそのまま無視してよい失敗ではないが、プロセスを止めるような異常でもない。ただし「もう目的が達成されている」とは限らない。既にある ConfigMap が自分の望む内容になっているか、自分が ownerReferences で所有しているものかは保証されないので、次の Reconcile(読み直し)で中身と所有者を確かめる必要がある。

逆方向もある。書き込みの結果はキャッシュに即時反映されない。同じ Reconcile 呼び出しの中で書いた直後に同じキャッシュを読み直しても、古い値が返ることがある。

図: キャッシュの遅れを前提にすれば、AlreadyExists は想定内の結果になる。

7. まとめと次の回

Reconcile は「何が起きたか」でなく「今どうなっているか」だけを見る関数。informer がキャッシュを作り、workqueue が同じ名前の重複と同時実行をつぶし、Result と error が「いつまた呼ぶか」を決める。次の第 10 回では、コントローラーが作った子をどう結びつけ(ownerReferences)、消すときにどう後片付け(finalizer)するかを見る。

図: この章で見た一本道。

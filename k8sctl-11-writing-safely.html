K8S CUSTOM CONTROLLER ・ 第 11 回

書き込みの作法

複数のコントローラーと人間が同時に同じオブジェクトへ書き込む時代の流儀

← カスタムコントローラー自作 シリーズ目次へ

第 10 回では、作った子をどう親に結びつけ、消すときにどう後片付けの時間を確保するかを見た。この回は、そうして作った・消したオブジェクトに、人間や他のコントローラーと取り合いにならないよう安全に書き込む作法を見る。

この章の結論: Kubernetes のオブジェクトは、誰か 1 人だけが書くわけではない。古い情報を元に上書きしてしまわないよう resourceVersion(リソースバージョン: 書き込みのたびに変わる版の印。同じかどうかの比較にだけ使う、回数ではない)で楽観的排他(先に書いた方が勝ち、後から追いついた方は衝突として弾かれる仕組み)を効かせ、Patch や Server-Side Apply で「自分が管理するフィールドだけ」を送る。そして、内容が本当に変わる時だけ書く。内容が同じなら resourceVersion もイベントも変わらないが、毎回違う値(現在時刻など)を書けば話は別で、それが無駄な Reconcile の呼び戻しを生む。

1. resourceVersion と楽観的排他

すべての Kubernetes オブジェクトは metadata.resourceVersion という値を持ち、書き込みが成功するたびに更新される。これは etcd(Kubernetes がデータを保存する場所)のクラスタ全体のリビジョンに由来する不透明な文字列で、「何回書き換えられたか」という回数ではなく、1 ずつ増える保証もない。意味があるのは「前に読んだ値と今の値が同じか違うか」の比較だけ。2 人(あるいは 2 つのコントローラー)が同じオブジェクトを同時に Get して、それぞれ別の変更を加えて Update しようとすると、先に書けた方の resourceVersion が進み、後から書こうとした方は「自分が読んだ時点の resourceVersion と、今サーバーにある resourceVersion が違う」ことを検出されて 409 Conflict(409 は「衝突している」を意味する HTTP のエラー番号)で弾かれる。これを楽観的排他(optimistic concurrency: 普段は衝突しないと楽観して、衝突した時だけ検出して弾く方式)と呼ぶ。

弾かれたコントローラー側がすべきことは、エラーを握りつぶさず、もう一度 Get からやり直すこと。古いオブジェクトに自分の変更だけを上書きで強行すると、相手の変更を消してしまう。

図: 先に書けた方が勝ち、後から追いついた方は衝突として弾かれる(rv=5→6 は説明用の例の数字で、実際の値が 1 ずつ増えるとは限らない)。

2. Get → 変更 → Update のリスクと Patch の違い

Get → 変更 → Update は、取得した丸ごとのオブジェクトを resourceVersion と一緒に送り直す。カスタムリソースへの Update は resourceVersion を伴わない書き込みを受け付けないので、相手の変更を気づかずに踏みつけることはない。むしろ Update の弱点は逆方向にある: 自分が触っていない、相手が変えたフィールド(たとえば自分は spec.image だけを変えたのに、相手が spec.size を変えていた)とも resourceVersion の不一致で 409 Conflict になり、無関係な変更とまでぶつかって Get からのやり直しが増える。

対して Patch は差分だけを送る。client.MergeFrom(obj)(controller-runtime v0.24.1 の pkg/client/patch.go で確認)は、変更前と変更後のオブジェクトを比較して JSON Merge Patch の差分を作る。自分が触っていないフィールドはそもそも送信データに含まれないので、別のフィールドの変更とは衝突せずに通る。ただし Patch(MergeFrom)は既定では resourceVersion を確認しないため、同じフィールドを両方が触っていた場合は検知なしで後勝ちになり、相手の変更を踏みつける。JSON Merge Patch は配列を丸ごと置き換える仕様なので、finalizers や conditions のような配列フィールドを Patch で触ると、相手が追加した別の要素を消してしまうこともある。配列を安全に触るには client.MergeFromWithOptions(obj, client.MergeFromWithOptimisticLock{})(確認済み: pkg/client/patch.go)で resourceVersion チェックを足すか、要素の追加・削除のような操作に向く JSON Patch を使う。

図: Patch は触っていないフィールドを送信データに含めない。

3. Server-Side Apply: field manager という考え方

Server-Side Apply(SSA: サーバー側適用。クライアントが「自分はこのフィールドを管理する」と宣言し、API サーバー側がフィールドごとの持ち主を記録する仕組み)は、Patch よりさらに進んで、フィールドの持ち主を field manager(フィールド管理者)という単位で metadata.managedFields に記録する(公式ドキュメント)。例えば kubectl が spec の一部を管理し、別のコントローラーが status の一部を管理する、という共存が成り立つ。注意点として、既定の kubectl apply はクライアント側で差分を計算する古い方式(client-side apply)で、Server-Side Apply ではない。SSA として動かすには kubectl apply --server-side と明示する必要がある。

2 人の field manager が同じフィールドに違う値を Apply しようとすると、ここでも 409 Conflict になる。解決策としては、強制上書きして単独管理者になる(force-conflicts)、自分の宣言からそのフィールドを外して管理権を放棄する、両者が同じ値で合意して共有管理者になる、の 3 つが選べるが、公式ドキュメントはコントローラー(人間が叩く kubectl ではなく自動で動くプログラム)には常に force-conflicts を使うことを勧めている。コントローラーは自分が管理するフィールドについて「自分が最新の望む状態を知っている」立場なので、衝突したら自分の値で確定させるのが筋に合う。

controller-runtime では client.Client インターフェースが持つ Apply(ctx, obj, opts...) メソッドを r.Client.Apply(ctx, obj, &client.ApplyOptions{FieldManager: "widget-controller"}) のように呼ぶ(確認済み: v0.24.1 の pkg/client/interfaces.go の Client インターフェース定義と pkg/client/client_test.go の使用例)。ここで渡す obj は通常の Widget 構造体ではなく、runtime.ApplyConfiguration という Apply 専用の型でなければならない。手書きの構造体をそのまま渡すことはできず、client.ApplyConfigurationFromUnstructured(u) で unstructured オブジェクトから作る、または型ごとに生成された ApplyConfiguration を使う。

図: 別々のフィールドを持てば共存できるが、同じフィールドを両方が Apply すると 409 になる。

4. controllerutil.CreateOrUpdate の使い方

「無ければ作る、あれば必要なら直す」という定型処理には controllerutil.CreateOrUpdate(ctx, c, obj, f MutateFn) (OperationResult, error) が使える(v0.24.1 の pkg/controller/controllerutil/controllerutil.go で確認)。内部では Get して無ければ(f を適用した上で) Create、あれば f を適用した結果が元と同じか比べて、違う時だけ Update する。差分が無ければ本当に何も送らない。

ソースのコメントに明記されている注意点: MutateFn の中で status のようなサブリソースを変更しても、その変更は捨てられる(Note: changes made by MutateFn to any sub-resource (status...), will be discarded.)。これは CreateOrUpdate が status だけを特別に除外しているからではなく、CreateOrUpdate が最後に呼ぶのは普通の Update(本体宛て)で、第 08 回で見たとおり status サブリソースが有効な間は本体への書き込みが status を無視するため。status を書きたい時は次のセクションの Status().Update / Status().Patch を別途呼ぶ必要がある。

図: 本体は無ければ作り差分があれば直すが、status への変更だけは別経路が必要。

5. status の更新は Status().Update / Status().Patch

第 08 回で見たとおり、status サブリソースを有効にした CRD では、本体への Update/Patch で status を書いても無視される。status を書くには、client の StatusClient インターフェースが持つ Status() SubResourceWriter(v0.24.1 の pkg/client/interfaces.go で確認)を経由する。

err := r.Client.Status().Update(ctx, widget)
err := r.Client.Status().Patch(ctx, widget, patch)

SubResourceWriter には Update と Patch の両方があり、使い分けは本体への Update/Patch と同じ考え方: 丸ごと送るか、差分だけ送るか。status は観測結果の集約なので、複数のコントローラーが同じ CR の status を分担して書くことは少ないが、それでも resourceVersion の衝突は起こりうる。

図: status サブリソースは専用の書き込み口を通る。

6. 差分が無ければ書かない

第 08 回の実測で見たとおり、送った内容が保存済みの内容と完全に同じ更新は、API サーバーのストレージ層で no-op(何もしない)と判定される。resourceVersion は変わらず、informer への watch イベントも出ない。つまり「本当に中身が同じ Update」を Reconcile の最後で毎回呼んでも、それ自体が無限に Reconcile を呼び戻す原因にはならない。

ただし、これは「見た目は同じ Update を書いている」つもりでも、実際には毎回違う値になっていないか注意が必要という意味でもある。たとえば status.conditions の lastTransitionTime を状態が変わっていなくても毎回「今の時刻」で上書きしていたり、ログや再試行回数のようなカウンタを status に書いていたりすると、送る内容は毎回本当に変わるので resourceVersion は進み、watch イベントが出て、また Reconcile が呼ばれる無駄なループになる。また、中身が完全に同じでも、API サーバーへの往復・admission webhook の呼び出し(第 12 回)・監査ログの記録は毎回発生するので、「変化が無いなら呼ばない」を徹底する価値はある。対策は単純で、書く前に「今の値と書こうとしている値が同じか」を比較し、同じなら Update も Patch も呼ばない。controllerutil.CreateOrUpdate が本体についてこれを自動でやってくれるのも、この理由による。

図: 内容が本当に同じなら no-op で止まる。毎回違う値を書くときだけ呼び戻しのループになる。

7. まとめと次の回

resourceVersion による楽観的排他が「古い情報の上書き」を防ぎ、Patch と Server-Side Apply が「自分が管理する分だけ」を安全に送る手段を与える。status はサブリソース専用の書き込み口を通し、変える必要が無いなら何も書かないことで無駄な watch イベントと無駄な Reconcile を減らせる。次の第 12 回では、こうした書き込みが API サーバーを通る際に、途中でどう検査・変形されるか(admission と webhook)を見る。

図: この章で見た関係と次回の橋渡し。

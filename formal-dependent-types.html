依存型 ― 型だけでバグを消す

長さを型に持つベクトルで、空の配列から先頭を取り出すバグを実行前に消す

この回の前提: 第 20 回 Lean 4 はプログラミング言語でもある、第 21 回 Lean のタクティクと自動化

前回までで induction や simp, omega, decide を使い、命題の証明をタクティクで進めました。今回は少し見方を変えます。証明を書くのではなく、型そのものにルールを埋め込んで、間違ったプログラムをそもそも書けなくする依存型 (dependent types) を見ます。空っぽの配列から先頭の要素を取り出す、という典型的なバグを例にします。

1. 型が値に依存するとはどういうことか

これまでの List α のような型は、要素の型 α には依存しますが、要素が何個あるか (リストの長さ) という値には依存しません。長さ 0 のリストも長さ 100 のリストも、型は同じ List α です。依存型とは、型が α のような型だけでなく、n のような具体的な値にも依存する型のことです。Lean の公式資料には、リストと「その長さが n であるという証明」を組にした、値 n に依存する型の例が載っています。

def Tuple (α : Type) (n : Nat) :=
  { as : List α // as.length = n }

この Tuple α n は n の値ごとに別の型になります。Tuple α 0 と Tuple α 3 は見た目は似ていますが、Lean にとっては違う型です。今回はこれと同じ考え方を、証明を組として持たせる代わりに、ベクトルの構造そのものに長さを埋め込む形で使います。

2. 長さを型に持つベクトル Vec

自分で Vec α n という型を定義します。n は要素数で、nil (空) は長さ 0、cons (先頭に 1 個追加) は長さを 1 つ増やします。

inductive Vec (α : Type) : Nat → Type where
  | nil : Vec α 0
  | cons : {n : Nat} → α → Vec α n → Vec α (n + 1)

ここで head (先頭の要素を取る関数) の型を、長さ 0 のベクトルではなく長さ n+1 のベクトルだけを受け取るように書きます。

def head {α : Type} {n : Nat} (v : Vec α (n + 1)) : α :=
  match v with
  | Vec.cons a _ => a

要素 3 個のベクトルを実際に作り、head を使ってみます。

def v3 : Vec Nat 3 :=
  Vec.cons 10 (Vec.cons 20 (Vec.cons 30 Vec.nil))

#eval head v3             -- 10

v3 の型は Vec Nat 3 です。cons を 1 回使うごとに長さが 1 増えるので、cons 30 nil は長さ 1、cons 20 (...) は長さ 2、cons 10 (...) は長さ 3 になります。この match には nil の場合が書かれていません。それでもこの定義は Lean に受理されます。なぜかというと、nil : Vec α 0 の長さは 0 であり、head が要求する長さ n + 1 とは決して一致しないからです。nil という場合は、型の上でそもそも起こり得ないと Lean が判断し、場合分けを省略してよいことになります。これが「テストではなく型検査で消えるバグ」の具体的な姿です。List α のままでは、空リストを渡されても型だけでは防げず、実行してみてようやく失敗に気づくか、戻り値を Option α にして「無いかもしれない」ことを呼び出し側に押し付けるしかありません。

図: List α は長さに関わらず 1 つの型。Vec α n は長さごとに別の型になり、空を型レベルで締め出せる。

3. Fin n: 範囲が保証された添字

配列の添字 (インデックス) でも同じ考え方が使えます。Lean core にある Fin n は「0 以上 n 未満の自然数」を表す型で、中身は値 val と「val < n である」という証明 isLt の組です。

def one : Fin 3 := ⟨1, by decide⟩
#eval one.val             -- 1

⟨1, by decide⟩ は、値 1 と「1 < 3 である」という証明をセットにして Fin 3 の値を作っています。証明の部分は decide が計算して確かめてくれます。ここで範囲外の値、たとえば 5 を使おうとすると何が起きるでしょうか。

def badIdx : Fin 3 := ⟨5, by decide⟩

5 < 3 は偽なので、decide はその場で証明に失敗し、このコードはコンパイルが通りません。範囲外の添字は、実行して初めてエラーになるのではなく、そもそも Fin 3 の値として組み立てることができません。checks/22/VecBad.lean には、この例と、長さ 0 のベクトルを head に渡そうとする例をまとめてあります。どちらも、実行する前の型検査の段階で Lean に拒否されます。

Vec α n も Fin n も、仕組みは同じです。どちらも「値 (長さや添字) を型の一部にする」ことで、本来は実行してみないと分からなかった制約を、コンパイルの時点で検査できる制約に変えています。第 18 回で見た「命題は型、証明はプログラム」という対応も思い出してください。ここでの isLt : val < n という証明は、まさに「val < n という命題の証明」が、値として Fin n の中に詰め込まれている例になっています。

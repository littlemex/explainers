研究過程シリーズ 第7回 ｜ 2026-08-13 時点

1 何を作ったか

一言でいうと 「AI が書いた検算ルールを、採用する前に機械が審査する仕組み」。汎用の入力チェッカーでも OCR ツールでもありません。

AIが検算ルールを書く
決まった形(DSL)で
→
登録ゲート
使う前に機械が審査
→
合格→採用 / 不合格→理由コード

審査は3点。①読む範囲を守っているか(宣言した欄以外を見ない) ②空回りでないか(どんな間違いも見つけられない飾りルールを拒否) ③正しい伝票で黙るか(正解データで誤発火しない)。全部機械が判定します。

2 触ってみる: 登録ゲート

ルールを選ぶと、審査結果(実際のコマンド出力に相当)が出ます。合格は緑、不合格は理由コード付き。

これは実装した CLI vgv check rules.json golden.json が返す JSON を模したものです。

3 2つのコマンド

コマンド役割返すもの
vgv check ルール 正解データルールを採用前に審査ルールごとに ACCEPT / REJECT＋診断コード(不合格があれば終了コード1)
vgv apply ルール 伝票伝票にルールを適用pass / fail / inapplicable と、fail 時は犯人の範囲(blame)

不合格の理由は、人にもプログラムにも読める安定した診断コードで返します。AI がこのコードを読んで自分のルールを直す、という自己修正ループに使えます。

コード意味
SCOPE_VIOLATION宣言した範囲外のフィールドを読んだ
VACUOUSどんな入力でも発火しない空回りルール
GOLDEN_FIRE正しい伝票で誤発火した(仕様バグ)
MALFORMEDJSON/文法が壊れている
TYPE_MISMATCHフィールドが期待する型(数値等)に解決できない

4 保証すること / しないこと

保証する(決定論的)
構造的な欠陥——読む範囲の逸脱・空回り・正解での誤発火——は確実に落とす。そして正しいルールを誤って弾かない(統制実験で誤拒否0)。安価で、毎回同じ答え。
保証しない(正直に)
忠実性オラクルではない。「論理は間違いだが構造的にはクリーン」なルールは通ってしまう(第4回)。OCR/VLM の誤読そのものも解かない(第6回)。だから最後は人やレビューと二段で使う。

1. コードの地図

kubebuilder が作った骨組み(第 15 回)に層を置き、cmd/main.go がそれらを組み立てて起動する。下の層は上の層を知らない。api は型と名前だけ、driver はドライバごとの事実だけ、sharepath はパスの規則だけ、volume は「この PVC ならこういう PV になる」を計算するだけで、どれも API サーバーと話さない。prepare はファイルシステムの上でディレクトリを 1 つ作るだけで、これも API サーバーを知らない。API サーバーと話すのは controller だけだ。間違えると危ない計算(パスの検査、PV の形、読み取り専用の付け方)を、クラスタ無しの単体テストで確かめられる。

2. ディレクトリを作る Pod

share に provision があると、チームのディレクトリは初めて使うときに作る。ここには 3 つの難しさがある。1 つめは権限だ。他人の持ち物のディレクトリを作るには root が要るが、root の Pod はできるだけ何もできないようにしたい。2 つめは途中で止まったときだ。作りかけのディレクトリ(持ち主や権限がまだ決まっていない)が本当の名前で見えると、そこを誰かに使われうる。3 つめは、既にあるものを壊さないことだ。

権限は、root(UID 0)のまま CAP_CHOWN(持ち主を変える権限)だけを残し、他の特権をすべて外した。普通のユーザーに特権を 1 つ足す方法は使えない。Kubernetes はプログラムを起動するときに足した特権を引き継がせる設定(ambient capability)をしないので、起動した瞬間に失われるからだ。Pod はサービスアカウントのトークンを持たず、読み取り専用のルートファイルシステムで動き、マウントするのは作るディレクトリの親だけだ。この形は Pod Security の baseline(最低限の安全基準)に収まるので、コントローラーの namespace をその水準にした。

手順は次のとおりで、すべてファイル記述子(開いたファイルを指す番号)を通して行うので、途中で名前を差し替えられても別のものを触らない。親の持ち主が root で、グループや他人が書けないことを最初に確かめる。そうでない親は断る(InsecureParent)。

図: 仮の名前は本当の名前から決まる(.sharedfs-tmp- + 名前のハッシュ)。点で始まる名前は share のパスに使えないので、仮のディレクトリが PV で配られることは無い。

最初の作り方は、権限 0000(誰も読めない)でディレクトリを作り、それを「作りかけの印」にするものだった。ところが本番と同じ権限(root で CAP_CHOWN だけ)のコンテナで試すと、自分で作った 0000 のディレクトリを開けなかった。root でも、権限の検査を飛ばす特権(CAP_DAC_OVERRIDE)を外すと、普通のユーザーと同じく権限に従うからだ。結果は毎回 PermissionDenied だった。作り方を図の形に変えると、同じコンテナで試験が全部通った。もう 1 つ、親が setgid(中に作ったものが親のグループを受け継ぐ印)で、そのグループが root のものでない場合、権限に setgid を付けようとしても黙って落とされることが同じコンテナで分かった(2770 のつもりが 0770)。先に持ち主を root:root に渡す手順を足すと 2770 になった。どちらも、直す前に失敗し、直した後に通ることを確かめている。

終わった Pod の結果は、終了コードではなく、Pod が書く結果の JSON(終了メッセージ)で読む。中身は決められた結果の名前のどれかでなければ信じない。失敗したら、30 秒から始めて倍々に、最大 1 時間まで間を空けてやり直す。親ディレクトリが無いと Pod はマウントで止まったままになるので、3 分の時間切れを付け、どこで止まったか(スケジュールされない、イメージが取れない、マウントできない)を理由に書く。

3. 係の reconcile 1 回で起きること

係のコントローラーの Reconcile は、第 09 回で見たとおり「PVC の名前」だけを受け取り、今の状態を読み直して判断する。PVC に PV の名前が既に入っていれば、取り上げの判定(第 17 回の第 4 節)に進む。まだ入っていなければ、自分宛ての印が付いた PVC についてだけ、次の順に確かめる。どこかで止まったら PV は作らず、Event で理由を伝えて 30 分後にもう一度見る。

図: 上から順に確かめ、最初に当てはまらなかった理由を伝える。ディレクトリを作る share では、記録の Prepared が True になるまで PV を作らない。

2 つ細かい点がある。1 つめは、share が変わった直後だ。share のコントローラーがまだ新しい中身を検査していない(observedGeneration が古い、第 08 回)間は、古い判定を伝えないように、Event を出さずに 2 秒後に見直す。2 つめは、テナントに見せる情報の量だ。share が Ready でない理由の詳しい説明には、元の PV の名前や他の share のパスが入る。それは管理者の情報なので、PVC の Event には理由の名前だけを書く。

キャッシュ(第 09 回)の古さにも気を付ける。PV の名前は PVC の UID から決まるので、作った直後にキャッシュが古くて「まだ無い」と見えても、もう一度作ろうとして「もうある」と返れば、それで成功とみなせる。消す判断(取り上げ)の直前は、キャッシュではなく API サーバーから直接読む。元に戻せない操作は、古いかもしれない情報では行わない、という一つの方針だ。

まとめ: シリーズを通して

第 01 回の「Kubernetes は望む状態の台帳」から始めて、最後は本物の FSx のディレクトリを namespace ごとに配るコントローラーまでたどり着いた。振り返ると、CRD は台帳に新しい欄を足すだけで、それだけでは何も動かない(第 04 回)。動かすのはコントローラーで、それは「今の状態を読み直し、差を埋め、何度やっても同じ結果になる」ループだった(第 03・09 回)。スキーマ、CEL、既定値、status、finalizer、所有関係、admission、バージョンは、どれもそのループを安全にするための部品だった。そして部品の使い分けは、規則が「1 つの CR だけで決まるか」「他のオブジェクトに依存して後から変わるか」「誰が書けるかの問題か」で決まった(第 17 回)。

作ってみて一番効いたのは、コードの前に実機で前提を確かめたこと、利用者に新しい CR を覚えさせず Kubernetes の普通の申し込み(PVC と StorageClass)に乗ったこと、元に戻せない操作ほど条件を絞り直接読み直してから行ったこと、そしてテストの層ごとに「見えないもの」を自覚し、見えないものは本番と同じ条件の層で確かめたことだ。

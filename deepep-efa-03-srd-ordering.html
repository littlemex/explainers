SRD は何を保証しないのか

順序保証のない配送のうえで、upstream のカーネルが立っている仮定はどこで折れるか

← シリーズ目次

0この回の主題

EFA 対応の全ての設計判断は、この回で挙げる制約表から導かれます。逆に言えば、この表を覚えれば実装の理由づけは自分で再構成できます。

一言でいうと
EFA の SRD は「届くが、順番は約束しない」配送です。加えて GPU 起動経路 (EFA-GDA) では signal が 番号指定のカウンタだけで、strong signal が無く、端点あたり 512 本という上限があります。upstream の scale-out カーネルは「末尾ポインタを 1 つ進めれば、その手前は全部届いている」という強い仮定で書かれていて、この仮定は上の 3 つのどれとも噛み合いません。だから カーネルを別実装で置き換えるという選択になります。

1SRD とは何か

EFA が提供する転送方式です。名前の 3 語がそれぞれ性質を表しています。

語意味結果
Scalableコネクションを張らない。宛先ごとの状態を持たないので、数万端点規模でも状態が爆発しない大規模で有利。ただし RC のような「接続の順序」という概念自体が無い
Reliable再送する。パケットが落ちても失われないアプリは損失を扱わなくてよい
Datagramデータグラム。順序は保たない複数経路に散らして帯域を稼ぐ (multipath) 代わりに、到着順は入れ替わる

順序を捨てているのは欠陥ではなく設計です。ネットワーク内の複数経路に同時に散らせば帯域と輻輳耐性が上がり、その代償として到着順が乱れます。InfiniBand の RC は逆の選択 (単一経路・順序保証) をしていて、DeepEP のような「片側 put + 末尾ポインタ」型のプロトコルはその選択に乗っかって書かれています。

2「順序保証がない」の粒度

ここを曖昧にすると設計を間違えます。乱れるのは 2 つの粒度で、対策が違います。

  • メッセージ間の順序。 put A を出して put B を出したとき、B が先に完了しうる。これは分かりやすい話で、「順に置いたから順に見える」という前提が崩れます。
  • 1 つのメッセージの中の順序。 1 回の RDMA write は複数パケットに分割されて飛びます。SRD はそれらを別経路に散らすので、後ろのバイトが先に受信メモリに置かれることがあります。つまり「先頭に置いたフラグが見えたから、以降のバイトも揃っている」も成り立ちません。

    • 2 番目の粒度が効いてくることが、後の回で見る「in-band header だけでは足りない」理由になります。そして、この 2 つの乱れの外側に 1 つだけ守られる約束があります。

    用語をここで揃えておきます。以降「完了通知」と「signal」は同じものを指します。EFA-GDA では受信側のカウンタが 1 つ進むことが完了通知であり、DeepEP から見るとそれが signal だからです。第 4 回以降は signal という語だけを使います。

    守られる約束
    そのメッセージの完了通知は、そのメッセージの全バイトが置かれた後に上がる。EFA-GDA の signal は「受信端点の FI_REMOTE_WRITE カウンタが 1 増える」ことで実現されており、NCCL 側の実装コメントも「EFA の FI_REMOTE_WRITE カウンタは inbound write ごとにちょうど 1 回 tick する」と書いています。つまり 個々のメッセージ単位の完了はアトミックに観測できる。この 1 点だけが、順序なし配送のうえでプロトコルを組める足場です。

    3EFA-GDA の制約表

    aws-ofi-nccl の公開ドキュメント (doc/gin-getting-started.md) と NCCL 内の EFA-GDA 実装から読み取れる制約です。

    制約内容出典
    順序メッセージ間・メッセージ内ともに順序保証なしSRD の性質
    strong signal非対応。「signal が見えたなら先行 put も完了」は成立しないgetting-started の Limitations、実装の supportsStrongSignals = false
    VA signal非対応。signal は番号 (indexed) 指定のみで、任意の登録アドレスを signal にはできない同上 (supportsVASignals = false)。実装にも「INDEXED signals only」の assert がある
    signal 本数デバイスあたり signal + counter で 512 までgetting-started の Limitations
    signal の加算カウンタは inbound write ごとに +1 のみ。+N は N 回の write に展開されるNCCL 実装のコメント
    1 put の上限1 GiB (EFA_GDA_MAX_WRITE_SIZE)。超えると分割されるNCCL 実装
    完了の観測CQ を読まない設計。ハードウェアカウンタを見る。カウンタは 2^31 で wrap するので絶対値比較は禁止NCCL 実装のコメント (EFA_CNTR_MASK)
    環境要件P5en / P6-B200 / P6-B300、libfabric 2.6.0+、rdma-core 64.0amzn0+、EFA driver 3.3.0+、NVIDIA driver の PeerMappingOverride=1、GDRCopy 2.5+getting-started

    PeerMappingOverride=1 が必要な理由は端的で、EFA の MMIO 領域を GPU の番地空間にマップする操作を、NVIDIA ドライバが既定で拒否するからです。GPU が doorbell を叩くというのは物理的にそういう操作だ、ということがこの要件から逆算できます。

    そして「signal 512 本」という数字は、この後ずっと効いてきます。signal が有限資源だからこそ、DeepEP fork には予算計算のためのヘッダが 1 つ新設されている (第 5 回)。理由は EFA-GDA の実装を見ると分かります。signal 1 本ごとに専用の端点 (queue pair) が作られているのです。NCCL の device handle 定義 (gin_efa_gda_dev.h) には、宛先の選び方がこう書かれています。

    targetSlot 0     -> peer の DATA 端点     (FI_REMOTE_WRITE を bind しない = 相手に観測されない)
targetSlot 1+s   -> peer の signal 端点 s (その端点の FI_REMOTE_WRITE が tick する)

    つまり signal 付き put は、ペイロードそのものを「signal 番号 s に対応する相手の端点」へ宛てて書く。別途 signal メッセージを送るのではありません。だから「その write が完了した」= 「signal が +1 された」が同義になり、§2 の守られる約束がそのまま signal の意味になります。ここは後の回の正しさの議論の核心なので、覚えておいてください。

    4upstream カーネルの同期方式

    DeepSeek 版 (upstream) の scale-out カーネルはどう同期しているのか。コードから読み取ります。

    hybrid_dispatch.cuh の送信側は、トークンを受信側のスロット列に詰めながら、一定間隔で「ここまで書いた」という末尾位置を相手に知らせます。その手段がこれです。

    // hybrid_dispatch.cuh の送信側 (抜粋・簡略)
const auto signaled_tail = pack2(finish_flag, stored_scaleout_tail);
gin.red_add_rel<ncclTeamTagRail>(tail_ptr, signaled_tail - old_signaled_tail, lane_idx);

    red_add_rel は「release 意味づけつきの遠隔加算」です。実装 (common/handle.cuh) を見ると、相手が NVLink で届く範囲なら GPU のアトミック加算に落ち、RDMA を跨ぐ場合は ncclGin_VASignalAdd になります。つまり「登録済みメモリの任意アドレスに対する遠隔アトミック加算」です。

    受信側はこの末尾を polling し、末尾より手前のスロットは全部届いているものとして読み進めます。

    const auto signaled_tail = ptx::ld_acquire_sys<int64_t>(tail_ptr);
unpack2(signaled_tail, finish_flag, tail_idx);
// tail_idx 未満のスロットを消費する

    図 1: 末尾ポインタ方式は「1 つの値で n 個のスロットの到着を代表させる」圧縮。その圧縮が成り立つ条件が順序保証

    5どこで折れるか (3 か所)

    §3 の制約表と §4 の方式を突き合わせると、3 か所で噛み合いません。どれも致命的です。

    #upstream が要求するものEFA-GDA の実際症状
    1VA signal (任意の登録アドレスへの遠隔加算)非対応。indexed signal のみ初期化時に能力不足で拒否される。あるいは ncclGin_VASignalAdd が assert で落ちる
    2strong 順序 (末尾の加算が、それが代表する put の後に見える)非対応静かにデータが壊れる。tail が先に見えて未着スロットを読む
    3遠隔アトミック加算そのものsignal カウンタは +1 の inbound write イベントのみ。任意値の加算はできない末尾位置という「値」を運べない。到着「回数」しか運べない

    3 番目が実は最も設計に効きます。EFA-GDA で相手に伝えられるのは「回数」だけで、「位置」ではない。 upstream は末尾位置という値を送っていました。EFA では数を数えるしかない。だから受信側は「何個届いたか」から「どこまで有効か」を再構成する仕組みを別に用意しなければなりません。それが次の回の in-band header です。

    2 番目が最も危険
    1 と 3 は初期化や assert で目に見えて失敗します。2 は失敗しません。確率的に、負荷が高いときだけ、間違ったデータを読みます。順序に依存したプロトコルを順序保証のない網に載せたときの典型的な壊れ方です。だから「動いた」は根拠になりません。順序が乱れたときにどうなるかを能動的に試す仕組みが必要になります ― これが第 7 回の emulator の動機です。

    6デモ: 到着順シミュレータ

    3 種類の受信判定を、同じネットワークモデルの上で走らせます。ネットワークは SRD を模して、メッセージ間もメッセージ内も順序を乱します。ただし「完了通知はそのメッセージの全バイトが置かれた後」という §2 の約束だけは守ります。

    SRD 上の受信判定シミュレータ

    「1 回まわす」を押すと、パケットと signal の到着順、受信側の判定が出ます。

    モデル: 各送信元が 1 つの part を 1 メッセージで送る。メッセージは npkt 個のパケットに割れ、パケットごとに独立な遅延で届く (順序の乱れが遅延の散らばりを決める)。header はパケット 0 に入る。signal (= 到着数) はそのメッセージの全パケットが置かれた後に +1 される (第 3 回 §2 の「守られる約束」)。末尾ポインタの更新はデータの後に発行されるので、乱れ 0 なら最後のパケットの直後に着き、乱れが入ると追い越す。失敗の定義: 受信側が「この part は揃った」と判定した時点で、実はまだ届いていないパケットが 1 つ以上ある。

    試すと分かることを先に書きます。

    方式順序の乱れ = 0順序の乱れ > 0理由
    末尾ポインタ失敗しない失敗する末尾の加算はデータの後に発行されるので、順序が保たれるなら安全。乱れると追い越す
    in-band header のみ失敗する失敗するheader はメッセージの先頭側にあるので、順序が完全に保たれていても残りのバイトはまだ来ていない
    header + 到着数失敗しない失敗しない次回で示す包含関係が成り立つ

    2 行目が重要です。header を入れるだけでは、順序が完全でも足りません。 header は「この part を送った」と「何トークン入っている」を運べますが、「もう全部置き終わった」は運べない。それを運ぶのは signal だけです (デモで 1 メッセージのパケット数を 1 にすると header のみでも緑になります ―― メッセージが分割されないなら header の可視性が完了と同義になるからです。実際のトークンは 1 パケットに収まりません)。

    逆に signal だけでも足りません。signal は回数しか運ばないので、何トークンが有効なのかが分からない。2 つ揃って初めて成立する、という構造が次回の主題です。

    1 行目の意味も押さえてください。末尾ポインタ方式は「順序が保たれる網では正しい」。upstream は間違っていません。乱れ 0 で緑になるのがその証拠です。EFA で折れるのは、前提が違うからです。

    7なぜ「順序を戻す」解ではないのか

    素直な発想として「受信側で並べ替えれば upstream のカーネルがそのまま動くのでは」があります。なぜその道を採らないのかを整理します。

  • 並べ替える主体がいない。 順序を戻すにはバッファリングと再組み立てが必要で、それをやるのは CPU かカーネルです。CPU を経路に戻すと GPU 起動通信の意味が消えます。カーネルにやらせると、結局「到着を数えて再構成する」ことになり、それは順序なし前提のプロトコルと同じ実装です。
  • strong signal は網の性質。 「先行する全ての put の完了」を保証するには、NIC が put 間の依存を追跡するか、ソフトが完了を待ってから signal を出すしかありません。後者は毎回 round trip を追加するので、レイテンシで負けます。
  • 順序を捨てたから速い。 multipath で帯域を稼ぐのが SRD の設計目的です。順序を戻すのは、その利得を返上する行為です。

    • したがって正しい方向は、プロトコルを順序に依存しない形に書き直すことです。DeepEP fork がやっているのは正確にそれで、既存カーネルの修正ではなく 2001 行の別実装を並置し、環境変数で選ぶ形にしています。次の回でその中身を読みます。

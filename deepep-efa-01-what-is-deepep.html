MoE の dispatch と combine、そして「通信ライブラリなのにカーネルが NIC を直接叩く」という構図

シリーズ全体の目的は「AWS EFA 上で DeepEP を動かすために何を実装しているのか」を理解することです。ただしその前に、DeepEP がそもそも何をしていて、なぜ普通の集団通信ライブラリでは足りないのかを押さえる必要があります。

EFA 対応の中身は、結局のところ「ネットワークが順序を保証しないなら、どうやって受信側は到着を知るのか」という 1 点に収束します。その問いが立つ理由は DeepEP の設計そのものにあります。DeepEP は通信を CPU に委ねず、GPU のカーネルが自分で NIC に仕事を積みます。だから「NIC の性質」がカーネルのアルゴリズムに直接漏れてきます。

一言でいうと
DeepEP は MoE (Mixture-of-Experts) の all-to-all を専用実装したライブラリです。扱うデータの形が「送信先ごとに量が違い、量が実行時に決まる」ので、既存の AllToAll API では表現できません。そして最大の特徴は、通信を GPU カーネルの中から発行することです。この設計が性能を出す代わりに、NIC の順序保証や signal の種類といった低レベルの性質がアルゴリズムの前提条件になるという代償を払っています。EFA 対応の全ての苦労はここから来ます。
1. MoE の通信はなぜ特殊なのか 2. dispatch と combine 3. なぜ NCCL の AllToAll では足りないのか 4. GPU が NIC を叩くという選択 5. scale-up と scale-out、そして hybrid 6. V1 と V2 ― 何が入れ替わったのか 7. この先の読み方

1MoE の通信はなぜ特殊なのか

MoE では、各トークンが「自分に必要な専門家 (expert)」を実行時に選びます。専門家は GPU 群に分散して置かれているので、トークンは自分が選んだ専門家がいる GPU まで移動しなければなりません。

密な Transformer の FFN なら、全トークンが同じ重みを通ります。通信は要りません。MoE では 1 トークンが top-k 個の専門家を選び、専門家は rank をまたいで分散しています。したがって「トークンを、選ばれた専門家のいる rank へ送る」通信が層ごとに 2 回発生します。行きが dispatch、帰りが combine です。

この通信が厄介なのは、送信量が実行時にしか決まらないことです。ルーティングはゲートの出力なので、「rank 3 へ 812 トークン、rank 5 へ 47 トークン」といった偏りが毎ステップ変わります。しかも top-k なので 1 トークンが複数の宛先に複製されます。

図 1: MoE の all-to-all は「宛先ごとの量が実行時に決まる不均衡な all-to-all」。量そのものを先に交換しないと受信バッファも決まらない

2dispatch と combine

MoE 層 1 つにつき、通信は 2 回です。行きと帰りで求められる性質が違います。

dispatch (行き)combine (帰り)
やることトークンを選ばれた専門家の rank へ送る専門家の出力を元の rank へ返し、top-k 個を重み付き加算する
データ量top-k 複製で増える減る (k 個を 1 個に畳む)
精度FP8 に落とせる (入力は量子化耐性がある)BF16 が要る (総和なので誤差が乗る)
受信側の仕事専門家ごとに連続並びへ整列 (GEMM がそれを要求する)宛先トークンごとに加算 (reduce)
学習時の裏側backward は combine になるbackward は dispatch になる

combine が単なる「逆向きの送信」ではなく reduce を伴うことは重要です。同じトークンに対する k 個の専門家出力が別々の rank から届き、受信側でそれを足し合わせます。つまり combine の受信側は「どのバイト列がどのトークンの何番目の寄与か」を知っていなければなりません。この対応表をどう持つかが、後の回で EFA 対応の設計を左右します。

3なぜ NCCL の AllToAll では足りないのか

「不均衡な all-to-all」自体は AllToAllv 相当で表現できます。それでも専用ライブラリが要る理由は 3 つあります。

  • 量を知るための往復が 1 段増える。 受信側は「自分に何トークン来るか」を知らないと受信バッファを決められません。素直に書くと「量の all-to-all」→「データの all-to-all」の 2 段になり、間に CPU 同期が入ります。1 層あたり 2 回、層数分だけこれを繰り返すので、この往復のレイテンシがそのまま推論の遅延になります。
  • 計算と重ねられない。 集団通信の API 呼び出しは「開始して終了を待つ」形なので、専門家の GEMM と通信を細かく重ねるのが難しい。DeepEP はトークンをチャンクに割って流し、届いた分から順に GEMM に流す構造を採ります。
  • SM を食う。 通信カーネルが GPU の SM を占有すると、その分だけ計算に使える SM が減ります。DeepEP V2 の売りは「同じ性能をより少ない SM で」です (公開 README の実測では SM90 + CX7 の EP 8×2 構成で 12 SM、EP 8×4 で 6 SM)。

    • この 3 つを同時に満たすために、DeepEP は集団通信の抽象を捨てて、片側通信 (put) と signal の組み合わせでプロトコルを自分で書きます。「送信側が受信側のメモリに直接置き、置いたことを別の手段で知らせる」という形です。そしてこの「知らせる手段」が、EFA では手薄になっている、というのがシリーズ全体の主題になります。

    4GPU が NIC を叩くという選択

    DeepEP の通信は CPU が仲介しません。GPU のカーネルが直接 NIC の送信キューに仕事を積みます。この方式を GPU-Initiated Networking (GIN) と呼びます。

    図 2: 同じ「片側 put」でも、記述子を誰が書くかで検証しやすさが変わる。左は CPU 側にソフトウェアの層があり、右は GPU が NIC の記述子形式を直接知っている

    右の方式の代償は明確です。NIC の記述子形式と完了通知の作法が、カーネルのソースコードに入り込みます。 ベンダが違えば記述子が違い、順序保証が違い、使える signal の種類が違う。DeepEP V1 はこの代償を素直に払っていて、実際に Mellanox 固有の構造体をカーネルから書いていました (第 2 回で具体的に見ます)。EFA 対応の本質は、この結合をどこで切るかという設計問題です。

    5scale-up と scale-out、そして hybrid

    DeepEP は 2 種類の「近さ」を区別します。ノード内 (NVLink) と ノード間 (RDMA) です。この区別は API 名にもコードにも一貫して現れます。

    語意味DeepEP / NCCL 内の呼び名
    scale-upノード内。GPU 同士が load/store で直接相手のメモリを読める範囲ncclTeamLsa (LSA = load/store accessible)、scaleup_rank_idx
    scale-outノード間。RDMA が必要な範囲ncclTeamRail、scaleout_rank_idx
    rail各ノードの同じ位置の GPU を束ねた集合。ノード間通信はこの中で行い、ノード内で横に配るNCCL_GIN_CONNECTION_RAIL

    rank 番号は rank = scaleout_rank_idx * num_scaleup_ranks + scaleup_rank_idx の形で分解されます。総 rank 数が LSA サイズと rail サイズの積になっていることは、初期化時に実際に検査されています (csrc/kernels/backend/nccl.cu の EP_HOST_ASSERT(num_ranks == ncclTeamLsa(comm).nRanks * num_rdma_ranks))。

    ここから hybrid mode という言葉が出てきます。トークンをノード間に送るとき、宛先ノードの全 GPU に個別に RDMA するのではなく、rail 内の相手 1 つに送り、そこからノード内で NVLink 経由で横に配る方式です。ノード間のトラフィックが GPU 数分の 1 に減ります。この「ノード間 1 hop + ノード内 1 hop」の 2 段構えを担うのが hybrid kernel で、EFA 対応の作業対象はまさにこの hybrid kernel です。ノード内だけの経路 (direct mode) は NVLink しか使わないので、NIC の性質と無関係です。

    ここを押さえる
    以降「hybrid」「scale-out」と書いてあるところが、RDMA が絡む = EFA の性質が効いてくる箇所です。EP_HYBRID_KERNEL という環境変数が後で出てきますが、それが選ぶのはこの scale-out カーネルの実装です。

    6V1 と V2 ― 何が入れ替わったのか

    DeepEP には世代があり、EFA が視野に入ったのは V2 で通信バックエンドが入れ替わったからです。

    V1 (legacy)V2 (現行)
    ノード間バックエンドNVSHMEM (IBGDA)NCCL Gin backend
    API高スループット用と低レイテンシ用で別ElasticBuffer に統合
    SM 数多い (V3 相当の学習で 24)少ない (同 4-6)
    チューニングauto-tuningSM 数と QP 数を解析的に決める
    コンパイル一部インストール時全て JIT (実行時)
    EFA実質不可能 (第 2 回で理由を示す)バックエンド差し替えで可能

    V1 のコードは csrc/kernels/legacy/ 以下に残っています。V2 は csrc/kernels/elastic/ と deep_ep/include/deep_ep/impls/ です。ディレクトリ名の elastic が V2 を指すので、EFA 関連の変更を追うときはこちらだけ見ればよい、と覚えておくと迷いません。

    V2 が「NVSHMEM から NCCL Gin へ」乗り換えたのは、EFA のためではありません。公開 README が挙げる理由はヘッダオンリーで軽いこと、既存の NCCL communicator を再利用できることです。しかし結果として、NIC 依存部分がバックエンドという交換可能な層に押し込まれた。それが EFA 対応の扉を開けました。次の回はその扉の構造を見ます。

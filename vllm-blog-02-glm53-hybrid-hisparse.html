一言でいうと
agentic なワークロードでは、長い文脈を持つリクエストが何十本も同時に走り、しかも文脈が伸び続けます。GPU のブロックプールは固定なので、いずれ新しいブロックが取れなくなります。従来の逃げ道は 2 つで、preempt (KV を捨てて後で再 prefill、TTFT を丸ごと払い直す) かオフロード (ホストへ退避するが、dense attention は全トークンが GPU に居ることを要求するので同時実行数は GPU メモリに縛られたまま) でした。ここで sparse-MLA の性質が効きます。indexer が上位 K トークンだけを選び、そこにしか attend しないのなら、GPU に置いておく必要があるのもそれだけです。HiSparse は選ばれたトークン以外を CPU へ落とし、1 リクエストが必要とする GPU メモリに実効的な上限を作ります。Hybrid HiSparse はさらに、余裕があるうちは GPU に置いたままにし、圧力がかかったときだけこの仕組みを使います。結果として 8 枚の H200 というこのモデルには厳しい構成で、従来は不可能だった 100 万トークンの文脈が動き、同時実行数が大きく伸びます。

1なぜ agentic だと詰まるのか

agentic なワークロードの特徴は「同時リクエストが多く、それぞれの文脈が長く、しかも伸び続ける」ことです。GPU のブロックプールは固定なので、いずれ同時に走っているリクエストが新しいブロックを取れなくなります。

これまでの対処は 2 つあり、それぞれ代償がありました。

対処やること代償
preemptリクエストを 1 本選び、その KV を捨てて、後で再び prefill するそのリクエストは追い出されるたびに TTFT を丸ごと払い直します
オフロードブロックをホストメモリへ退避するdense attention は全トークンが GPU 上に居ることを要求するので、同時実行数は結局 GPU メモリに縛られたままです
補足ここが第 1 回との違いです。第 1 回の階層オフロードは「捨てて再計算する」より「下の階層から読み戻す」ほうが安いという取引でした。ただしその枠組みでも、実際に attend する瞬間には全トークンが GPU に戻っている必要があります。だから「同時に何本走らせられるか」の上限は動きません。今回の話はその前提そのもの、つまり「全トークンが GPU に居る必要があるか」を問い直します。

2上位 K しか読まないという性質

sparse-MLA の KV キャッシュでは、indexer が上位 K トークンを選び、そこにしか attend しません。HiSparse はこの振る舞いを利用して、選ばれたトークン以外の KV をすべて CPU へ落とします。

これで何が変わるか。1 リクエストが必要とする GPU メモリに実効的な上限ができます。文脈が 10 万トークンでも 100 万トークンでも、attend するのは上位 K 個です。常駐量が文脈長から切り離されるのが、この手法の核心です。

ただし正確に言うと、GPU に残り続けるものもあります。indexer の KV です。原文の記述をそのまま押さえます。

データどこに置くか文脈長とともに伸びるか
sparse-MLA の KV (本体)圧力次第で CPU へ落とせる。GPU 側は上位 K に相当する分だけ伸びない (上限がつく)
indexer の KVGPU 常駐のまま伸びる。ただし全体としてはずっと小さく、IndexShare により sparse-MLA 4 層あたり indexer は 1 層

hybrid が付く理由

HiSparse をいつでも効かせると、余裕があるときでも CPU-GPU 転送を払うことになります。そこで Hybrid HiSparse は容量があるうちは KV を GPU に置いたままにし、圧迫されたときにだけ上記の仕組みを適用します。

そしてもう 1 つ、原文が強調している性質があります。hot buffer のページはトークン単位で索引されるので、1 ページが多数の異なる CPU ブロックから引いたトークンを保持できます。結果として文脈の広い範囲にまたがる削減になります。

補足この「1 ページに別々の CPU ブロック由来のトークンが混ざる」という点が、素朴なページ単位のキャッシュとの決定的な違いです。ページ単位で入れ替えると、1 つのトークンが欲しいだけでも 1 ページ分を運ぶことになります。トークン単位で詰められるなら、上位 K が文脈全体に散らばっていても、必要な行だけを集めた密なページが作れます。sparse attention は「散らばった少数」を読むので、この粒度でなければ節約が成立しません。

3【デモ】2 リクエストで何が起きるか

原文の 1 枚目の図が、この手法の価値をいちばん短く示しています。1 つのプールと、伸び続ける 2 本のリクエスト。3 つの方式で何が起きるかを並べたものです。

preempt: B のスロットは解放され、B の KV は消える。従来のオフロード: B の KV はホスト上に生き残るので再 prefill は要らないが、その全部が再び GPU に収まるまで B は走れないので、A が単独で decode する。hybrid sparse offload: 各リクエストがその場で最も冷たいページを手放し、同じスロットが新しい末尾と hot ページとして貸し出され、両方が decode を続ける。

このデモはページ数を単位にした模式です。原文の図と同じ状況 (1 つのプール ・ 2 本の伸びるリクエスト ・ 3 方式) を、ページ数の算術だけで再現しています。ページの大きさ ・ 上位 K の値 ・ 実際の転送時間は入っていません。示しているのは「どの方式で誰が decode を続けられるか」という可否の構造だけです。

原文の言い方が的確です。hot ページは KV ページと同じブロックプールから貸し出され、しかも同じ KV キャッシュのテンソルの中に住むので、sparse MLA のカーネルからは普通のページに見えます。そして hybrid sparse に固有の性質として、一部のトークンが hot バッファにあり、別の一部がまだ GPU 常駐のページにあるという状態が許され、CPU から読み戻す量が減ります。

43 つの居住状態

居住 (residency) はページ単位で追跡されます。圧力が上下するにつれて、リクエストは 3 つの状態の間を移動します。

どのパネルでも同じ 6 個の上位 K トークンに輪が付いています。変わるのはその居住場所だけ。実線の矢印はミスで、1 行を hot ページへコピーしている。破線の矢印はhot ヒットで、コピーなしで再利用されている。
図の出典: GLM 5.3 Optimizations, Part 1 (vLLM 公式ブログ)

状態何が起きているか
完全常駐
full residency		sparse-MLA の KV はすべて GPU 常駐のまま。同時に、完了した prefix のページは先回りしてホストメモリに実体化されます
混在
mixed residency		リクエストの末尾は GPU に留まり、古いページは CPU にだけ存在し、indexer がそれらのページから欲しがった行は hot バッファに座ります。ブロックテーブルには実ブロックと null のプレースホルダが並んで入り、末尾は決して evict されません
非常駐
no residency		CPU にしか存在しない prefix を再利用する新しいリクエストは、プレースホルダと 1 枚の hot ページから始まります。行は indexer が選ぶにつれて到着するので、履歴全体ではなくモデルが実際に attend する分だけを払います

混在状態を解く 1 つの融合カーネル

ここが実装の要点です。1 つの融合カーネルが上位 K を解決します。

行の居場所やること
GPU 常駐のページにあるその場で読む
hot バッファにある読んで、LRU のエントリを更新する
どちらにも無い (ミス)pinned なホストメモリから 1 行だけ LRU のスロットへコピーする
そしてこの一文が重要です。decode の経路上で CPU の判断を待つものは何もないので、CUDA グラフとして capture できる状態が保たれます。
補足なぜこれが重要かを足します。decode は1 トークンごとにカーネルを何十回も起動する処理で、起動のオーバーヘッドが支配的になりやすい領域です。だから vLLM は decode の 1 ステップを CUDA グラフに焼いて起動コストを消します。ところが「CPU が次に何をコピーするか決める」処理がグラフの中に入ると、グラフに焼けません。この設計はミスの処理を「pinned ホストメモリから 1 行を LRU スロットへ」というデータ依存だが制御依存でない形に押し込めていて、それによって CUDA グラフとの両立を保っています。「速い仕組みを作った」ではなく「既にある速さを壊さない形で作った」というのが、この節の読みどころです。

5【デモ】圧力を上げて状態を動かす

3 つの状態を 1 本のリクエストで追います。圧力を上げると古いページが CPU へ落ち、ブロックテーブルに null のプレースホルダが並び、indexer が選んだ行が hot バッファへ入ります。末尾は決して落ちません。

KV の圧力 0%
GPU 常駐 hot バッファに乗っている行 CPU にだけある (テーブルは null) 末尾 (evict しない)

このデモは状態遷移の模式です。ページ数 ・ 上位 K の個数 ・ hot バッファの行数は説明のための小さな値で、GLM 5.3 の実際の設定ではありません (原文は上位 K の具体値を書いていません)。「圧力」も 0 から 100% の抽象量で、実際には GPU ブロックプールの空き具合から決まります。デモが再現しているのは規則だけです。末尾は落ちない、落ちたページはテーブルで null になる、indexer が求めた行だけが hot に入る、hot にある行はコピーなしで読める。

「indexer を 1 回動かす」を何度か押すと、hot バッファのヒット率が上がっていくのが見えます。原文が hot バッファの既定を上位 K の 2 倍の行数にしている理由がここにあります。ヒット率を高く保ちながら、バッファ自体は小さく抑えるという設計です。

6hot buffer は特別な確保ではない

3 つの状態がすべて成立する理由は 1 つです。hot バッファが別枠の確保ではないこと。

hot バッファのページは普通の KV キャッシュブロックです。常駐ページと同じプールから、vLLM の Hybrid Memory Allocator (HMA) を通して貸し出され、リクエストが最初に必要としたときに取り、必要でなくなったら返します。常駐ページ上の行でも hot バッファ上の行でも、resolver は HMA の行 ID を渡し、HMA が 1 つの stride でまとめて gather します。そしてあるリクエストが解放したブロックが、別のリクエストの hot バッファ容量になれます。
補足この設計判断の意味を、第 1 回の「正規レイアウト」と並べて読むと構造が見えます。第 1 回はホスト側の形を構成から独立させて、共有できる相手を増やす話でした。今回はhot バッファの形を通常のページと同じにして、カーネルを変えずに済ませる話です。どちらも「新しい種類のメモリを作らない」という同じ方針です。もし hot バッファが別テンソルだったら、sparse MLA のカーネルは 2 種類のメモリを見分けて別々に読む必要があり、gather を 1 つの stride で済ませられません。容量の融通も効きません。「同じプール ・ 同じテンソル」という制約が、性能と運用の両方を買っています。

7圧力が来る前に備える

HiSparse は圧力が来る前に準備します。ここも設計が細かい。

タイミングやること
キャッシュ可能な prefix ページが完成したときCPU メモリへのコピーをキューに入れつつ、GPU からの提供は続けます
後で GPU キャッシュが埋まったときそのページはもう一度コピーせずに GPU のスロットを手放せます
圧力がもっと新しいページに先に届いたときその GPU スロットはコピーがキューに入った時点で再利用可能になります
転送が完了したときその CPU 上のコピーがprefix 再利用に使えるようになります

実装の軽さも書かれています。hisparse-glm ブランチは、forward パスの後に、すべての sparse-MLA 層をまとめて 1 回の launch でコピーします。コピーはモデルの GPU ストリーム上で順序づけられるので、同期が単純で安全に保たれます。

補足「コピーをキューに入れた時点でスロットが再利用可能になる」という一文は、第 1 回の t2 で解放する話と同じ形です。遅い経路の完了を待たずに、希少な資源を先に返す。第 1 回はホストへのコピー完了で GPU を返し、ここではコピーのキュー投入で返しています。より踏み込んでいるのは、順序づけをストリームに任せているからです。「いつ安全に返せるか」を時刻ではなくストリームの順序で保証するのは、GPU プログラミングで繰り返し出てくる型です。

8他の機構との合成

Hybrid HiSparse は共有 HMA プール上の居住方策であり、vLLM の他の KV 機構と並ぶ connector です。だからスタックの残りはこれまでどおり動きます。

相手どう噛み合うか
他のキャッシュグループ通常の prefix キャッシュ ・ 転送 ・ オフロードをそのまま使う
indexer の KVHiSparse は触りません。標準の OffloadingConnector が通常のブロック粒度のストレージで独立にオフロードできます
P/D 分離からの取り込みprefix が常駐に収まらないとき、ホスト側に着地できます
speculative decodingステップごとに再生できる resolver のプランを通して動き、リクエストの hot 状態を共有します
TP 間の共有MLA の KV はTP rank をまたいで同一なので、pinned なホストプールは DP レプリカごとに確保して、そのローカルな TP rank 間で共有します。TP rank 0 が共有コピーを書き、どの rank も読める。CUDA event がストリームの順序を保つ
補足最後の行は地味ですが効きます。MLA は KV を低ランクの潜在表現に圧縮するので、TP で分割されず全 rank が同じものを持ちます。ということは、ホスト側に8 枚分のコピーを持つ必要がない。1 枚が書いて 7 枚が読むだけです。第 1 回の consolidated I/O が「8 本の小さな I/O を 1 本にまとめる」話だったのに対し、こちらはそもそも重複が存在しないという MLA 固有の性質を使っています。アーキテクチャの性質が、そのままメモリ予算の 8 分の 1 になる例です。
MTP との干渉が明記されています。MTP (speculative decoding) は同時実行をさらに制限しうると原文は書いています。理由はhot バッファが検証トークンを一度に全部収める必要があることで、公開時点では 1 つの hot バッファを (num_speculative_tokens + 2) × 上位 K に見積もる必要があります。これはバッファを縮める作業を進めているので変わりうるとされ、公式の計算機もこの分をまだ織り込んでいません。9 節の実測で MTP3 の方が MTP なしより同時実行数が少ないのは、この制約が数字に出たものと読めます。

HiSparse 384 GiB + offload 128 GiB ・ MTP3 同 ・ MTP なし Offloading 512 GiB ・ MTP3 同 ・ MTP なし

いちばん雄弁なのは下の段です。設定同時実行を 8 → 16 → 24 → 32 と上げていったとき、実際に走っていたリクエスト数の平均は、オフロードのベースラインでは 4.8 → 4.8 → 4.9 → 4.9 (MTP3) と完全に頭打ちになります。設定をいくら上げても、走れる本数が増えません。一方 HiSparse は 7.1 → 11.9 → 18.1 → 18.9、MTP なしなら 6.8 → 13.7 → 19.7 → 25.5 まで伸びます。1 節で述べた「dense attention は全トークンの常駐を要求するので同時実行数が GPU メモリに縛られる」という制約が、そのまま数字になっています。

上の段で throughput が伸びるのも同じ理由です。同時に走れる本数が増えるので、GPU 1 枚あたりの論理トークンスループットが上がります。逆にベースラインは設定を上げると throughput が落ちます (MTP3 で c8 の 7,410 から c16 で 2,577、c24/c32 では 1,000 前後まで)。走れない本数を積んだぶん、待ち行列と再 prefill のコストが増えている形です。

数値の出どころ。デモの数値は原文の図に描かれている値をそのまま読み取ったものです。下の段の占有率は図に数字が直接書かれています。上の段の座標は図の目盛りから復元した値なので、末尾の桁には読み取り誤差が入ります (傾向と大小関係は保たれます)。正確な数字は原文の図を見てください。また 4 つの構成は commit が異なります (HiSparse MTP3: e8ef1e07bd、HiSparse no-MTP: 8fc4636fb6、offloading MTP3: 80cb71c9ff、offloading no-MTP: e8ef1e07bd)。

10【デモ】交差点はどこにあるのか

原文には公式の同時実行数の計算機が埋め込まれていて、自分の構成での見積りができます (全画面で開く)。ここではそれと重複しないように、1 つの問いだけに絞ったデモを置きます。なぜ短い文脈では通常常駐の方が多く詰め込めるのか。

原文の説明がこうです。hot バッファはリクエストごとに固定の GPU コストを足すので、短い文脈では通常の常駐の方が多くのリクエストを収められます。文脈が長くなると、sparse-MLA の常駐に上限をつけることで HiSparse の方が多くの同時実行を維持できます。つまりどこかで必ず交差します。

HBM の空き 200 GB
sparse-MLA KV 60 KB/tok
indexer KV 6 KB/tok
hot バッファ 200 MB/req
通常の GPU 常駐 Hybrid HiSparse 交差点

これは読者が入れる仮定値による計画上の目安で、原文の計算機の代わりではありません。計算しているのは 2 本の式だけです。通常常駐は「1 リクエストあたり (sparse-MLA KV + indexer KV) × 文脈長」、HiSparse は「1 リクエストあたり indexer KV × 文脈長 + hot バッファの固定費」。実行時のワークスペース ・ 長さの偏り ・ スケジューリングの挙動は入っていません。原文も自分の計算機について「これは計画のための見積りで、保証されるサービング上限ではない」と明記しています。MTP による hot バッファの増加も入れていません (8 節の (num_spec + 2) × 上位 K)。
補足この 2 本の式を並べると、交差点の位置が何で決まるかが読めます。通常常駐は傾きが (sparse-MLA + indexer) の直線、HiSparse は切片が hot バッファ ・ 傾きが indexer だけの直線です。だから交差点はhot バッファの固定費を、sparse-MLA の傾きで割った長さのあたりに来ます。hot バッファを大きくすると交差点は右へ動き (短い文脈での不利が増え)、sparse-MLA の 1 トークンあたりが重いモデルほど交差点は左へ動きます (長文脈での利得が早く来る)。原文が「hot バッファを増やすと容量の一部を hot キャッシュの被覆率に替えることになる」と書いているのは、この直線の切片を動かす話です。

12読むときに気をつける点

以下はこの記事の読み解きで、原文の主張ではありません。

論点読み方
効く前提はモデル側にあるこの手法が成立するのはsparse-MLA という「上位 K しか読まない」構造があるからです。dense attention のモデルにはそのまま適用できません。GLM 5.3 の IndexShare (4 層あたり indexer 1 層) も、GPU に残る側を小さくする条件として効いています
indexer KV は伸び続ける原文が明記しているとおり、indexer の KV は GPU 常駐のまま文脈長とともに伸びます。だから「文脈長から完全に切り離される」わけではなく、切り離されるのは sparse-MLA の本体だけです。10 節のデモで HiSparse 側の直線に傾きが残るのはこのためです
MTP との取引実測で MTP3 の同時実行 (18.9) が MTP なし (25.5) より低いのは、hot バッファが検証トークンを全部収める必要があるためです。interactivity は MTP3 の方が高い (c1 で約 257 対 約 90) ので、1 ユーザーの速さと同時実行数を交換している形です。どちらを取るかは運用の判断になります
単一の測定条件モデル 1 つ ・ ハードウェア 1 構成 ・ ワークロード 1 種類 (OpenHands の多ターン) です。初回 74,160 トークン + 以降 753 トークンという形は prefix 再利用が強く効く条件で、agentic の代表ではありますが一般の形ではありません
100 万トークンの主張「従来このハードウェアでは不可能だった 100 万トークンの文脈で動く」は可否の主張で、その長さでの性能の数字は示されていません。掲載されている測定は 142K の受け入れ上限の下で行われています
commit が構成ごとに違う4 つの系列でビルドが 3 種類あります (HiSparse no-MTP だけ別 commit)。厳密な A/B ではありません。原文は commit を全部開示しているので、そこは追跡可能です
まだ広く使えないv0.30 で広く提供する計画で、現時点では固定 commit のビルドが必要です。NVIDIA GPU 限定で、hot バッファのサイズ規則も変わる予定と書かれています
計算機の限界原文の計算機自身が「計画のための見積りで、保証されるサービング上限ではない」と述べ、実行時ワークスペース ・ リクエスト長の偏り ・ スケジューリングで実際の同時実行数は下がりうるとしています。MTP の hot バッファ増もまだ織り込まれていません

この設計から持ち帰れる形。第 1 回が「希少な資源の占有を、遅い経路のレイテンシから切り離す」話だったのに対し、今回は「モデルが実際に読む量まで、常駐の要求を落とす」話です。attention が疎なら、常駐も疎でよい。そのうえで hybrid が付くのは、疎にする操作それ自体にコスト (CPU-GPU 転送) があるので、必要になるまで払わないという判断です。この 2 つ、「上限を作る」と「必要になるまで払わない」は独立した設計判断で、組み合わせて初めて「短い文脈でも損しないし、長い文脈では勝つ」という形になります。

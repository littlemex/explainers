← 証拠のない主張を消していく

第 1 章 主張を 4 つ取り下げ、証拠を 2 つ足した日

競合の実装を読み直したら、差別化として書いていた 2 つが相手側に既にあった。書き直しの日誌と、その日に測った数字。

結論から

1 日の成果は、機能が増えたことではなく、支えを失った主張が減ったことだった。 そのうえで、これまで最大の弱点だった「デプロイ実経路の証拠がない」を実測で埋め、 ノート PC だけで実 Bedrock を叩ける経路を作った。

取り下げた 4 つの主張

この製品の設計文書には、汎用ゲートウェイ (LiteLLM) との比較が書いてあった。 書いた時点では正しかったが、相手が 2026 年に呼び出し前予約を出荷したことで、 4 つの主張が成立しなくなっていた。

取り下げた文置き換えた内容
彼らの billing と idempotency は best-effort である 相手は呼び出し前予約を実装済み。fail-closed、7 スコープ、敵対的な max_tokens のクランプまである。差は「予約があるか」ではなく「強制の状態がどこにあるか」
彼らのルーティングは静的ルールと負荷分散である 複雑度ルータも品質ティアも節約ベースラインもある。こちらはルーティングの品質で競争せず、外部の判定が予算の下で許されるかを決める役割に限定する
これは彼らが構造的に作れない数字である 節約額の算出自体は固有でない。差は計算の形で、入力を全部引数で受ける純粋関数なので第三者が再計算できる
吸収に要する期間は数週間 対 四半期から 1 年である 他プロジェクトの開発速度を外から見積もることはできない。追うべきは速度ではなく境界の明確さ
取り下げ方に型がある 「弱める」のではなく、取り下げた文の隣に、残る狭い主張を書く。 今回残ったのは「保証の階層が違う」という主張である。相手も予約している。 違うのは、強制の状態が追いつくキャッシュにあるか、金の移動と同じ権威ある保存先にあるか。 この形にすると相手が機能を足しても崩れない。
確かめていないことは、確かめていないと書く 相手のカウンタがキャッシュ喪失時に上限を維持するかは、こちらでは検証していない。 だから「失敗する」とは書かない。書いたのは「確認した経路では予約残高が プロセス内 + Redis のキャッシュに依存している。喪失時の挙動は未検証」までである。 根拠にしたのが相手のコード内コメントであって挙動の再現ではない、という点も含めて。

デプロイ実経路での初計測

この製品の最大の弱点は、一番強い証拠が in-process の ASGI とモックの DynamoDB 止まりだったことだった。 つまりデプロイした実体を外から叩いた証拠がゼロ。そこを埋めた。

やり方は素朴で、自分で発行した API キーを使って、公開されている配信網のホスト名に 素の HTTP を投げる。応答ヘッダで経路が確定する。

Via: 1.1 <id>.cloudfront.net (CloudFront)
X-Amz-Cf-Id: AsuWA_durJDHi2CHdRI0iWEOhovSRFmotcnU8kLZ2VZMKAKaInI7Dg==
X-Amz-Cf-Pop: SFO53-P12
server: uvicorn

配信網を通ってアプリに届いていることが、推認ではなくヘッダで確定した。そのうえで 3 つの API を叩いた。

API結果実測クライアントが受けた usage
Anthropic Messages2001,226 ms入力 13 / 出力 4
OpenAI Chat Completions2001,112 ms入力 13 / 出力 4
OpenAI Responses2003,876 ms入力 12 / 出力 5

そして台帳から読み戻した。サーバ側の記録が、クライアントが受け取った値と完全に一致していた。 さらにリクエストで送った別名 claude-haiku-4-5 が、記録側では実効モデル us.anthropic.claude-haiku-4-5-20251001-v1:0 に解決されていた。 モデル解決がサーバ側で起きている証拠になる。

ついでに分かった 2 つ

権限のないサブコマンドを叩いたら 403 Missing permission が返った。 CLI には出ているがサーバ側で拒否されるので、権限の強制がユニットテストだけでなく実経路で効いている。

API キーを失効させたら直後に 401、5 秒後も 20 秒後も 401 だった。キャッシュ遅延なしで即時に効く。

ノート PC だけで実 Bedrock を叩く

これまでの入口は「9 スタックの CDK をデプロイして月額 42 ドル」だった。 興味深い性質を 1 分で見せられる製品にとって、それは最初の一歩として間違っている。 そこで、肝を残したまま入口を作った。肝とは実 Bedrock を叩くことである。 モックで代替したら、モック程度の価値しかない。

コード変更ゼロで成立した botocore は AWS_ENDPOINT_URL_DYNAMODB という環境変数を標準で解釈する。 これを置くと DynamoDB のクライアントだけがローカルを向き、 Bedrock のクライアントは AWS に解決されたままになる。つまり 「状態はローカル、推論は本物」が設定 1 つで実現する。認証も新しい抜け道を作らず、 本番と同じ形式の利用者行と API キー行をローカルのテーブルに書いて、production と同じ経路を通す。

実際に走らせた出力がこれである。

== Anthropic Messages (/v1/messages) ==
  status: 200
  ledger record: requested='claude-haiku-4-5'
                 resolved='us.anthropic.claude-haiku-4-5-20251001-v1:0'
                 input_tokens=13 output_tokens=4
  token quota moved (credit_used): 17 (before=85, after=102)

3 経路すべて同じように通り、トークン数もクォータの増減も台帳から読み戻した値である。 テーブル 23 個と GSI 11 個の作成、権限と既定テナントの seed、API キーの発行まで通り、エラーはゼロだった。

走らせないと分からなかった欠陥 3 経路目が 503 で落ちた。原因は CODEX_ENABLED=true という環境変数が compose に入っていなかったこと。README には「3 経路を叩く」と書いてあったので、 約束が破れる状態だった。設計を読んでいるだけでは出てこない種類の欠陥である。

デモ: 時間はどこに消えていたのか

ローカルで動かしたら 1 リクエストが 20 秒以上かかった。デプロイ実経路では同じ呼び出しが 1 秒台である。 デバッグログを疑ったら外れで、答えはゲートウェイ自身が出していた計測行にあった。

reserve_ms=9485.2  settle_ms=3866.3  upstream_ms=1571.7  unaccounted_ms=8.1

Bedrock は 1.6 秒しか使っていない。予約と精算、つまり状態を置く側が支配的だった。 この時点で書いた結論は「ローカルの時間は信じるな」だった。

それは間違った教訓だった。後日 JDK を入れて本物の DynamoDB Local で同じ呼び出しを測ったら、 数字がまるごと入れ替わった。

状態を置く先予約精算推論合計
DynamoDB Local 2.x13.7 ms13.3 ms1,217.2 ms1,255.6 ms
代役 (moto)9,485.2 ms3,866.3 ms1,571.7 ms約 14,900 ms
デプロイ実経路未計測未計測未計測1,112 ms

本物なら台帳は 1.26 秒のうち 27 ms で、支配しているのは推論である。 デプロイ実経路の 1,112 ms とほぼ同じ形をしている。予約だけで約 690 倍の差を作っていたのは代役だった。

教訓を書き換えた 正しくは「ローカルの時間を信じるな」ではなく「代役の時間を信じるな」である。 前者だとローカルモードの価値を自分で削ってしまうし、事実として誤っている。 代役の数字は「膨らんでいる」のではなく意味がない。複数項目トランザクションと 条件付き更新の再試行は、代役が本物から最も外れる場所だからである。

予約と精算の重さを動かす

状態を置く先が遅いと、推論の速さは体感に効かなくなる。スライダを動かすと 1 リクエストの内訳が変わる。実測した 3 点 (本物の DynamoDB Local / 代役の moto / デプロイ実経路) をプリセットとして置いてある。

内訳を実測したのは 1 番目と 2 番目である。3 番目は合計 1,112 ms しか測っていないので、 内訳はこのデモの上で合計を合わせただけの値であり、実測ではない。

動かして見えること

状態を置く先が速いと合計は推論に近づき、遅いと推論の速さは見えなくなる。 本物の保存先なら台帳は 27 ms で、支配しているのは推論である。 だから代役の環境で測った時間を製品の性能として読んではいけない。逆に言えば、 本物のローカルなら読んでよい。ここを一緒くたに「ローカルは信じるな」と書いたのが 最初の誤りだった。そして、この 3 分割が最初から出ているおかげで、 遅いときに 3 つのどれかを当てにいける。推測でなく特定になる。 なおこの計測行を出しているのは /v1/chat/completions だけで、残り 2 経路には無い。

CI に載せた初日に、CI が欠陥を 4 つ見つけた

認証情報の要らない経路を CI に載せた。壊れても誰も気づかない経路だからである。 そして初回の実行で落ちた。返ってきたのはこれだった。

botocore.exceptions.ClientError: An error occurred (UnrecognizedClientException)
when calling the DescribeTable operation:
The Access Key ID or security token is invalid.

AWS が偽の鍵を拒んだように見える。だから「環境変数が効かず実 AWS に飛んでいる」と考えた。 確かめる方法は簡単で、偽の鍵で実 AWS を叩いて文言を見比べればいい。

実 AWS  : The security token included in the request is invalid.
CI に出た: The Access Key ID or security token is invalid.

文言が違う。つまり返したのは AWS ではなく、ローカルの保存先だった。 接続先は合っていて、拒まれていたのは鍵の文字列そのものだった。 JDK を入れて本物の DynamoDB Local を手元で立て、鍵を変えながら総当たりしたら境界が出た。

渡した access key id結果
AKIAIOSFODNN7EXAMPLE通る
abc123通る
ci-local / ci_local / ci.local / ci local拒否

規則は「英数字以外を含む鍵を拒否する」だった。DynamoDB Local は access key id をデータベースのファイル名に使うので、ファイル名にできない文字を弾く。 CI が渡していたのは ci-local-placeholder で、ハイフンが入っていた。

エラーメッセージが別人のふりをすると、原因の捜索先ごと間違える この文言は AWS からの拒否としか読めない。だから最初の仮説は全部 「なぜ実 AWS に飛んだのか」の方向に向いた。文言を実物と突き合わせるまでは、 接続先が正しいことすら分からなかった。

そして CI は、CI 自身の不備ではなく成果物の欠陥を 3 つ道連れで暴いた。

露出した欠陥意味
スクリプトはバックエンドの package を import するのに、手順書がホスト側の依存を要求していなかった Docker だけ持っている読者は必ず失敗する。make up が先に確認して、 3 手先の ImportError ではなく打つべき pip コマンドを出すようにした
ゲートウェイの容器に資格情報が 1 つも渡っていなかった テーブル作成が直っても、次の認証チェックで落ちていた。 compose が既に mount している ~/.aws に書くことで、mount 自体も検証される形にした
認証しない保存先なのに、署名のために資格情報が必要だった AWS アカウントを持たない読者は make up すら通らない。 無い場合は AWS 公開の例示鍵に自動で落ちて、そう言うようにした
ついでに、実 AWS を壊しうる穴が 1 つ埋まった 元のガードは「環境変数が設定されているか」しか見ていなかった。 この変数を解釈しないほど古い botocore なら、変数は黙って無視され、 スクリプトはローカルの宛先を表示したまま実 AWS アカウントに 23 個のテーブルを作る。 今は botocore が実際に解決した宛先を見て、AWS のホスト名なら止まる。

健康に見えるのに、書き込みが全部失敗している保存先

資格情報を直しても CI は落ち続けた。次の症状はこうである。

botocore.exceptions.ReadTimeoutError:
  Read timeout on endpoint URL: "http://dynamodb-local:8000/"
amz-sdk-request: attempt=6; max=10

ここで 3 回目の推測をやめて、コンテナ環境を作り直して手元で同じものを動かすことにした。 すると保存先のログに答えがあった。

WARNING: [sqlite] cannot open DB[1]: [14] unable to open database file
WARNING: [sqlite] SQLiteQueue[shared-local-instance.db]: stopped abnormally,
                  reincarnating in 3000ms

容器の中を見たら所有者が合っていなかった。

$ id
uid=1000(dynamodblocal) gid=1000(dynamodblocal)
$ ls -ld /home/dynamodblocal/data
drwx------. 2 root root 4096 /home/dynamodblocal/data

image にはこのディレクトリが存在しない。だから volume を割り当てる側が新規に作り、 その所有者は root になる。中のプロセスは uid 1000 なので、自分のデータベースファイルを開けない。

最悪なのは、それでも HTTP には答えてしまうこと JVM が起動した時点で TCP も HTTP も応答するので、容器は健康に見える。 壊れているのは操作だけで、しかも失敗ではなくタイムアウトと再試行になる。 ゲートウェイは起動時に権限表を書き込もうとしてここに当たり、数分間再試行し続ける。 外から見えるのは「起動しない」だけで、ログには読み取りタイムアウトしか出ない。

そして直した後ろに、もう 1 つ別のバグが隠れていた。CI はスタックを全部同時に立ち上げてから テーブルを作っていた。ゲートウェイは起動時に権限表を seed するので、テーブルが無い状態で起動すると 書き込み先が無い。そしてその失敗は警告にとどめて起動を続ける設計なので、 権限表が空のまま動き続け、認証済みのリクエストすべてに 403 を返す。 どこにも理由が出ない。

直し方は「順序を直す」ではなく「順序を 1 箇所にする」だった make up は最初から正しい順序だった。保存先を起動し、待ち、テーブルを作り、 それからゲートウェイをビルドして起動する。CI はその手順を言い換えて再実装していたので、 言い換えた側だけが間違っていた。だから CI が make up をそのまま呼ぶようにした。 文書化されたコマンドを実行するジョブは、文書とずれることができない。

自分が 6 回外した記録

6 回、事実でないことを断定した。訂正のきっかけは毎回実物を読むか動かすかだった。

断定した内容実際
文書間で p99 の数字が矛盾している 矛盾ではなかった。一方はトランザクションの p99、他方は end-to-end の p99 で、別の metric を並べていただけ。問題は数字ではなく metric 名の欠落だった
相手には self-hosted の認識がゼロだ 偽。パス検索で見つからなかったから断定したが、実際は 5 系統の接続先がある。正しく言えるのは「エンジン内部状態を使ったルーティングは確認できていない」まで
読み戻し API の 404 は文書と実挙動の差だ 正しい挙動だった。ドル建ての動きは予約が pool されたときだけ走るので、プールを設定していないテナントでは課金行が存在しない。バグはどこにもなかった
CI が落ちたのは localhost が IPv6 に解決されたからだ 外れ。接続は届いていて、返ってきたのは DynamoDB の API エラーだった。ログを読まずに、両ジョブが同じステップで落ちたという間接的な事実だけで断定していた
自分が入れた資格情報の変更は今回の失敗の原因ではない 原因だった。しかも再現するものを間違えていた。壊れている条件ではなく修正後の条件で再現を試したので、当然通ってしまい「除外できた」と結論した。再現は条件を合わせないと反証にならない
依存監査が落ちたのは 4 つの脆弱性 advisory のせいだ 外れ。その 4 つは元から除外設定に入っていた。真の原因は 1 つの crate が crates.io から yank されたことで、これは脆弱性ではない。ジョブの出力を読む前に手元で走らせて推測した
教訓は「間接的な証拠で断定するな」だった 4 回とも、パス検索・文書の突き合わせ・落ちたステップの一致という間接的な証拠で断定していた。 実装の呼び出し箇所を 1 つ開くか、コマンドを 1 回打てば数分で分かることばかりだった。 証拠に段位を付ける仕組みをこの製品が持っているのは、たぶん同じ失敗を通ったからだと思う。

まだ言えないこと

この製品が一番大事にしている性質は「並行して叩いても予算を 1 円も超えない」ことである。 ところがそれを検証するには小さい予算を設定する管理権限が必要で、今回の検証では手が出ていない。 自分の残高は 77 ドル相当あり、それを使い切る形での検証もできない。第 2 章の宿題である。

形式証明についても線を引いた。証明されているのは状態遷移のモデルに対してであって、 実装でも DynamoDB の挙動でもない。文書からも「double-counting cannot occur」という書き方を消して、 「モデル化された遷移が二重計上しないことを機械検査した」に下げた。

compose の経路は埋まった。コンテナ環境を作り直して手元で通したところ、 make up でイメージのビルドから起動まで完走し、make demo で 3 経路すべてが実 Bedrock から 200 を返し、トークン数も実効モデルも容器の中の台帳から 読み戻せた。CI も緑になっている。ただし手元で使ったのは nerdctl なので、 docker compose のビルダ自体は CI だけが通している。 compose ファイルは同じでもビルド実装は別物なので、片方が他方の代わりにはならない。

そして台帳が競合下でどう振る舞うかは、ローカルモードでは原理的に検証できない。 DynamoDB Local は単一ノードでスロットリングもパーティション競合もないからである。 一番大事にしている性質がまさに抜けているので、そこを曖昧にすると意味がない。

この章で壊しておきたい誤解

「比較表は書いたら終わり」ではない。技術文書で最も腐りやすいのは競合比較で、 腐ったまま置くと、腐っていない部分の信用まで持っていかれる。読み手が 1 つ確かめて古いと分かると、 形式証明や証拠の段位という本当に効いている主張も信じる理由がなくなる。 古い比較を残すコストのほうが、取り下げるコストより高い。

「悪い数字は隠すもの」でもない。末尾の p99 が目標を外していることを、 測定手順ごと公開したままにした。良い数字だけを出すプロジェクトより、 悪い数字を手順つきで出すプロジェクトのほうが信用される。数字は改善対象であって、恥ではない。

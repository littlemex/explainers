正規化のルール

正規化は性能を犠牲にする作業ではありません。実機では索引付きの JOIN 1 回のコストは数十ミリ秒の差に収まり、犠牲になるのは更新異常だけです

この回の前提: 第 15 回 アンビギュアスグループ (主キーへの関数従属という考え方の基礎)

「正規化すると JOIN が増えて遅くなる」という話をよく聞きますが、これは半分だけ正しい誤解です。正規化が本当に防いでいるのは性能問題ではなく更新異常 (1 つの事実を複数の場所に重複して持つことで、更新のたびに矛盾が生まれる危険) です。この回では、1 つのバグ管理システムの例を使って 1NF から 5NF まで同じパターン (重複を許す表 → 更新で矛盾が起きる実演 → 分解して解決) を繰り返し確認し、最後に「JOIN と単一テーブルのどちらが速いか」を実機で測って誤解を正します。

1. この回で解く問題 ― なぜ正規化には段階があるのか

関係 (リレーション) とは、重複する行を持たず、各列が単一の値を持つ表のことです。コッド (E. F. Codd) が 1970 年に提案した関係モデルでは、データを表として表現し、集合演算で操作することで、データの物理的な保存方法とアプリケーションを分離できることが示されました。正規化とは、この関係モデルの上で「1 つの事実は 1 つの場所にしか書かない」という目標に近づけていく、段階的なルールの集まりです。

段階が複数あるのは、「同じ値が重複して登録されている」という問題の形が何種類もあり、それぞれ違う条件で見つけて、違う分解で解決する必要があるからです。関数従属 (列 A の値が決まれば、列 B の値も一意に決まるという関係。A → B と書く) という考え方が、1NF から BCNF までの共通の判定基準になります。4NF はこの関数従属を「値が決まれば複数の値の集合が決まる」という多値従属に一般化したもの、5NF はさらに「3 つ以上の関係に分解しても情報が保たれるか」という結合従属性に一般化したものです。1NF から 5NF までは、「どんな形の従属関係 (関数従属・多値従属・結合従属性) が、どんな更新異常や復元不能を生むか」を 1 つずつ潰していく手順だと捉えると理解しやすくなります。

2. 仕組み ― 1NF から 5NF まで、同じ型の壊れ方を追う

1NF ― 列は原子値を持つ (カンマ区切りを許さない)

第 1 正規形 (1NF) は、各列が分割できない単一の値 (原子値) を持つことを要求します。タグをカンマ区切りの文字列で 1 列に詰め込むと、この条件が崩れます。

CREATE TABLE bugs_unnormalized (bug_id bigint PRIMARY KEY, summary text, tag_list text);
INSERT INTO bugs_unnormalized VALUES (1, 'crash when saving', 'crash,save');

-- 「crash タグが付いたものを探す」は文字列の部分一致に頼るしかない
SELECT bug_id, summary FROM bugs_unnormalized WHERE tag_list LIKE '%crash%';

1NF を満たす形 (タグを行として持つ tags(bug_id, tag) テーブル) なら、値そのもので一致できます。

SELECT b.bug_id, b.summary FROM bugs b JOIN tags t ON t.bug_id = b.bug_id WHERE t.tag = 'crash';

図: 1NF は 1 列に複数の値を詰め込まず、行に分解することを求める。

2NF ― 複合キーの一部にしか従属しない列を分離する

第 2 正規形 (2NF) は、複合キー (複数の列からなる主キー) を持つ表で、非キー列がキーの一部だけに従属する「部分従属」を禁止します。bugs_products(bug_id, product_id, product_name) で product_name を直接持つと、product_name は product_id だけに従属するのに、キー全体 (bug_id, product_id) に結び付けられてしまいます。

INSERT INTO bugs_products_2nf VALUES
  (1,1,'Open RoundFile'), (2,1,'Open RoundFile'), (4,3,'ReConsider'), (5,1,'Open RoundFile');
UPDATE bugs_products_2nf SET product_name = 'Open RoundFile Pro' WHERE bug_id = 1 AND product_id = 1;
SELECT DISTINCT product_id, product_name FROM bugs_products_2nf ORDER BY product_id;
--  product_id |    product_name
-- ------------+---------------------
--           1 | Open RoundFile       -- bug_id=2,5 の行はまだ古い名前
--           1 | Open RoundFile Pro   -- bug_id=1 の行だけ更新された
--           3 | ReConsider           -- product_id=3(別の製品)は無関係なので変化なし

1 件だけ名称を変更したところ、同じ product_id = 1 のはずの製品名が実機で 2 種類に分裂しました。解決策は product_name を products テーブル側に置き、bugs_products を交差テーブル (キーの組だけを持つ表) にすることです。

3NF ― 推移的従属を分離する

第 3 正規形 (3NF) は、非キー列が別の非キー列を経由して間接的にキーに従属する「推移的従属」を禁止します。bugs(bug_id, assigned_to, assigned_dept) で assigned_dept を直接持つと、assigned_dept は bug_id ではなく assigned_to だけに従属しているのに、bug_id に結び付けられています。

INSERT INTO bugs_3nf_violation VALUES (1,2,'QA'), (2,3,'DEV'), (4,3,'DEV');
UPDATE bugs_3nf_violation SET assigned_dept = 'SRE' WHERE bug_id = 2 AND assigned_to = 3;
SELECT DISTINCT assigned_to, assigned_dept FROM bugs_3nf_violation ORDER BY assigned_to;
--  assigned_to | assigned_dept
-- -------------+---------------
--            2 | QA
--            3 | DEV   -- bug_id=4 の行はまだ古い部署
--            3 | SRE   -- bug_id=2 の行だけ更新された

社員 3 の異動を 1 行だけ反映すると、同じ社員のはずなのに部署が 2 種類に分裂しました。解決策は assigned_dept を employees テーブル側に移し、1 回の更新で全員に反映されるようにすることです。

図: 部分従属(2NF)も推移的従属(3NF)も、同じ事実が複数行に重複し、片方だけ更新すると矛盾する点は共通している。

BCNF ― 候補キーでない列が他の列を決めてしまう場合

ボイス・コッド正規形 (BCNF) は 3NF をさらに厳しくした基準で、「ある列の集合が他の列を決めるなら、その列の集合は候補キー (一意性を保証できる最小の列集合) でなければならない」ことを要求します。履修 enrollments_bcnf(student, course, instructor) で、この学校では講師 1 人が 1 講座しか持たない (instructor → course) とすると、instructor は候補キーではないのに course を決めてしまい、BCNF 違反になります。

INSERT INTO enrollments_bcnf VALUES ('alice','sql101','carol'), ('bob','sql101','carol'), ('carol_student','ml201','dave');
SELECT DISTINCT instructor, course FROM enrollments_bcnf;
--  instructor | course
-- ------------+--------
--  carol      | sql101   -- alice, bob の行で2回重複して登録されている
--  dave       | ml201

(student, instructor) と (instructor, course) に分解すると、重複が消え、さらに「まだ誰も学生を持たない講師」を先に登録できるようになります (挿入異常の解消)。

INSERT INTO instructor_course VALUES ('erin', 'go301'); -- 学生ゼロの新講座を登録できる

図: BCNF 分解は候補キーでない列が他列を決める構造を切り離し、重複と挿入異常を解消する。

4NF ― 互いに無関係な多値従属を分離する

第 4 正規形 (4NF) は、1 つのキーに対して互いに無関係な複数の値の集合 (多値従属) を 1 つの表に詰め込むことを禁止します。社員のスキルと担当案件が互いに無関係なら、employee_skills_projects(employee, skill, project) に両方を持たせると、情報を欠落させないために全組み合わせを書く必要が生まれます。

-- alice は skill{sql,python} と project{api,batch} を独立に持つ
-- → 2×2=4行を書かないと組み合わせの一部が欠ける
SELECT count(*) FROM employee_skills_projects_4nf; -- 4

-- 4NF分解: employee_skills と employee_projects に分ける
SELECT (SELECT count(*) FROM employee_skills) + (SELECT count(*) FROM employee_projects) AS fourth_nf_rows; -- 4

この例では行数はどちらも 4 行で変わりませんが、スキルや案件の数が増えるほど、1 枚の表では組み合わせの数が掛け算 (スキル数 × 案件数) で増えるのに対し、分解した 2 枚の表では足し算 (スキル数 + 案件数) で済む差が開いていきます。

5NF ― 3 つ以上のテーブルに分解しても情報が保たれるか

第 5 正規形 (5NF) は、3 つ以上の独立した関係に分解しても元の情報が完全に復元できるか (結合従属性, join dependency) を扱います。Fagin (1979) の代理店・会社・製品の例を使い、3 行のデータを 3 つの二項関係に分解して再結合する実験をしました。

INSERT INTO agent_company_product VALUES
  ('agent1','companyA','productX'), ('agent1','companyB','productY'), ('agent2','companyA','productY');
-- 3つの二項関係 (agent,company) (company,product) (agent,product) に分解して再結合
SELECT ac.agent, ac.company, cp.product
FROM ac_pair ac JOIN cp_pair cp ON cp.company = ac.company
JOIN ap_pair ap ON ap.agent = ac.agent AND ap.product = cp.product;
--  agent  | company  | product
-- --------+----------+----------
--  agent1 | companyA | productX
--  agent1 | companyA | productY   -- 元の3行には無い組み合わせ(幽霊行)
--  agent1 | companyB | productY
--  agent2 | companyA | productY

元のデータは 3 行だったのに、3 分解して再結合すると (agent1, companyA, productY) という元には無かった行が 1 つ増え、4 行になりました。この関係では「代理店・会社・製品」の 3 つ組という事実そのものが独立した情報であり、2 項関係 3 つだけでは復元できません。こうした関係を安全に分解するには、結合従属性が成り立つかどうかを確認する必要があり、成り立たない関係は 3 つ組のまま 1 つの表に保つのが正しい選択です。

図: 結合従属性が成り立たない関係を無理に 3 分解すると、再結合時に元には無かった行が増える(spurious tuple)。

3. どこで壊れるか ― 「正規化すると遅くなる」という誤解

正規化への典型的な批判は「JOIN が増えて性能が落ちる」というものです。これを実機で検証するため、30 万行のバグ一覧に対して、報告者の名前とメールアドレスを埋め込んだ非正規化版 (bugs_wide, 1 枚のテーブル) と、bugs と accounts を分けた正規化版 (504 件のアカウントに JOIN) で、同じ集計クエリの実行時間を比較しました。両方に status 列の索引を張った状態での結果です。

EXPLAIN (ANALYZE, COSTS off) SELECT count(*) FROM bugs_wide WHERE status = 'NEW';
-- Aggregate (actual time=39.408..39.409 rows=1.00 loops=1)
--   ->  Bitmap Heap Scan on bugs_wide ... rows=299903.00 loops=1)
-- Execution Time: 39.440 ms

EXPLAIN (ANALYZE, COSTS off)
SELECT count(*) FROM bugs b JOIN accounts a ON a.account_id = b.reported_by WHERE b.status = 'NEW';
-- Aggregate (actual time=60.373..60.375 rows=1.00 loops=1)
--   ->  Hash Join (actual time=3.758..50.075 rows=299903.00 loops=1)
-- Execution Time: 60.397 ms
構成行数実行時間
非正規化 (単一テーブル)299,903 件一致 (全 300,006 行)39.440 ms
正規化 (JOIN, 索引あり)299,903 件一致60.397 ms

索引を張った状態での差は約 21 ミリ秒 (60.397 − 39.440)、比率で約 1.53 倍でした。JOIN 自体は確かに追加のコストを生みますが、「JOIN があるから壊滅的に遅い」というほどの差ではありません。この差の正体は、504 件しかない accounts テーブルをハッシュ表に組み立てる手間であり、索引を適切に使えば JOIN のコストは線形以下に抑えられます。正規化による性能への影響は実在しますが、測った上で許容できる範囲かどうかを判断するべきものであり、最初から避ける理由にはなりません。

図: 索引付きの JOIN は、単一テーブルに対して壊滅的な遅さにはならない。

4. シニアの書き方 ― 非正規化してよい条件

正規化を崩してよいのは、導出できる値をキャッシュとして持つ場合に限られます。コメント数のような、他のテーブルから集計すれば必ず算出できる値を、読み取りを速くするために列として持つのは合理的な設計です。ただし、これを安全に行うには 2 つの条件が必要です。

1 つ目は、追加した瞬間に実測値でバックフィル (初期値の一括補充) することです。列を追加した直後は既定値 (多くは 0) が入るだけで、既存データの実際の件数を反映していません。実機で、バックフィルを忘れた状態でトリガーだけ足すとどうなるかを確認しました。

ALTER TABLE bugs ADD COLUMN comment_count int NOT NULL DEFAULT 0;
-- (ここでバックフィルを忘れてトリガーだけ足すと)
INSERT INTO comments (bug_id, author, comment) VALUES (1, 1, 'one more note');
SELECT bug_id, comment_count FROM bugs WHERE bug_id = 1;      --  1 (新規分だけ)
SELECT bug_id, count(*) FROM comments WHERE bug_id = 1 GROUP BY bug_id; -- 3 (本当の件数)

バックフィルを忘れると、既存の 2 件のコメントが数えられず、comment_count が実際の件数より小さいまま食い違いました。UPDATE で一度だけ実測値を埋めてからトリガーを張ると、一致します。

UPDATE bugs b SET comment_count = (SELECT count(*) FROM comments c WHERE c.bug_id = b.bug_id);
-- バックフィル後に同じ操作を行うと
SELECT bug_id, comment_count FROM bugs WHERE bug_id = 1; -- 3 (一致)

2 つ目は、同期の手段をトリガーのように自動的で見落としの余地が無いものにすることです。アプリケーションコードの各所で個別に更新する方式は、1 箇所でも更新を忘れると 2NF/3NF 違反と同じ矛盾が再発します。導出値のキャッシュは「正規化されたデータから再計算すれば必ず正しい値が得られる」という保証と、「バックフィル済みで自動的に同期される」という運用の 2 つが揃って初めて安全な非正規化になります。

UPSERT と MERGE ― 冪等な書き込み

「無ければ作り、あれば更新する」という操作を SELECT してから INSERT する形で書くと、2 つの処理が同時に動いた瞬間に重複エラーになります。結論を先に言うと、PostgreSQL の INSERT ... ON CONFLICT と MERGE はどちらもこの競合を 1 つの文の中で解決しますが、実際に 2 つの psql セッションを同時に走らせて確かめると、競合が起きた後の振る舞いが違います。ON CONFLICT は競合した相手の行に合わせて自動的に UPDATE 側に切り替わるのに対し、MERGE は競合すると素の INSERT と同じ重複キーエラーで止まります。

この回で答えるのは「同じ行が無ければ作り、あれば更新する」という日常的な処理を安全に書く方法です。結論は、SELECT してから INSERT するという素朴な書き方は、2 つの処理が同時に走ると必ず競合し得るということ、そして PostgreSQL が用意している INSERT ... ON CONFLICT と MERGE (PostgreSQL 15 以降) は、どちらも 1 つの文で競合を解決しますが、2 つの処理が本当に同時に重複した場合の振る舞いが違うということです。この違いは、実際に 2 本の psql セッションを同時に動かして確認しました。

1. この回で解く問題 ― SELECT してから INSERT する間に割り込まれる

「バグを見ている (watch している) 人の数を記録したい」という要件を考えます。bug_watchers(bug_id, account_id, watch_count) というテーブルに対して、「まだ watch していなければ 1 件追加し、既に watch していれば回数を 1 増やす」という操作です。素朴に書くと「まず存在を確認する SELECT」と「無ければ INSERT する」という 2 つの文に分かれます。

この 2 つの文の間に、別の接続が同じキーに対して先に INSERT してコミットすると何が起きるかを、実際に 2 つの psql セッションで確認しました。セッション A が先に INSERT してまだコミットしていない状態で、セッション B が「存在しない」という結果の SELECT を見てから INSERT を実行した実機の結果です。

時刻セッション Aセッション B
t0BEGIN; INSERT (bug_id=3) 実行 (未コミット)-
t1 (0.5 秒後)pg_sleep(2) で待機中SELECT count(*) → 0 件 (A はまだ見えない)
t1 直後(待機中)INSERT (bug_id=3) を実行 → A の行待ちでブロック
t2 (2 秒後)COMMITブロック解除 → ERROR: duplicate key value violates unique constraint

B の SELECT は「0 件」という正しい (当時の) 結果を返しましたが、その直後に実行した INSERT は、A がコミットするまでブロックされ、A のコミット後に重複キー違反で失敗しました。「確認してから実行する」という 2 段階の操作は、確認した瞬間と実行する瞬間がずれている限り、安全ではありません。

図: SELECT で「無い」ことを確認しても、その後の INSERT までの間に別の接続が割り込める。

2. 仕組み ― INSERT ... ON CONFLICT DO UPDATE/NOTHING と EXCLUDED

INSERT ... ON CONFLICT は「挿入しようとして、一意制約に引っかかったら代わりにこうする」を 1 つの文で書く仕組みです。DO NOTHING は競合したら何もしない、DO UPDATE は競合した既存の行を更新します。DO UPDATE の SET 句では、挿入しようとしていた (まだ入っていない) 行を EXCLUDED という名前の擬似テーブルで参照できます。

-- DO NOTHING: 既に watch 済みなら何もしない
INSERT INTO bug_watchers (bug_id, account_id, watch_count) VALUES (3, 1, 99)
ON CONFLICT (bug_id, account_id) DO NOTHING;

-- DO UPDATE + EXCLUDED: 既存の watch_count に、挿入しようとした値を足す
INSERT INTO bug_watchers (bug_id, account_id, watch_count, last_watched) VALUES (3, 1, 1, now())
ON CONFLICT (bug_id, account_id)
DO UPDATE SET watch_count = bug_watchers.watch_count + EXCLUDED.watch_count,
              last_watched = EXCLUDED.last_watched
RETURNING bug_id, account_id, watch_count, last_watched;

DO NOTHING を試したときは実行結果が INSERT 0 0 (実際には 1 行も変更されなかった) になり、既存の watch_count は 99 に書き換わらず元の値のままでした。DO UPDATE では EXCLUDED.watch_count (今回挿入しようとした 1) を既存の値に足し込み、watch_count が 1 から 2 に増えました。RETURNING を付けることで、挿入されたのか更新されたのかにかかわらず、最終的な行の内容をその場で受け取れます。

図: EXCLUDED は「挿入しようとしていた行」、テーブル名は「既にある行」を指す。

3. 仕組み ― MERGE (PostgreSQL 15 以降) と RETURNING / merge_action() (17 以降)

MERGE は ON CONFLICT よりも表現力が高く、「一致したら更新」「一致しなかったら挿入」だけでなく、条件を付けて「一致していて、かつある条件を満たすなら削除する」のように複数の分岐を 1 つの文に書けます。ON CONFLICT と同じ「無ければ追加、あれば回数を増やす」を MERGE で書いた例です。

MERGE INTO bug_watchers t
USING (SELECT 4::bigint AS bug_id, 1::bigint AS account_id) s
ON t.bug_id = s.bug_id AND t.account_id = s.account_id
WHEN NOT MATCHED THEN INSERT (bug_id, account_id, watch_count) VALUES (s.bug_id, s.account_id, 1)
WHEN MATCHED THEN UPDATE SET watch_count = t.watch_count + 1
RETURNING merge_action(), t.bug_id, t.account_id, t.watch_count;
実行merge_action()watch_count
1 回目 (まだ無い)INSERT1
2 回目 (もうある)UPDATE2

merge_action() (PostgreSQL 17 で追加) は、INSERT・UPDATE・DELETE のうちどの分岐が実行されたかを文字列で返します。ON CONFLICT には「どちらが実行されたか」を直接返す仕組みが無いので、このログを残したい場合は MERGE の方が便利です。

MERGE は WHEN 句を複数書けるので、条件によって挿入・更新・削除を切り替えられます。watch_count が 5 以上になったら代わりに行を削除する、という分岐を追加した例です。

MERGE INTO bug_watchers t
USING (SELECT 4::bigint AS bug_id, 1::bigint AS account_id) s
ON t.bug_id = s.bug_id AND t.account_id = s.account_id
WHEN MATCHED AND t.watch_count >= 5 THEN DELETE
WHEN MATCHED THEN UPDATE SET watch_count = t.watch_count + 1
WHEN NOT MATCHED THEN INSERT (bug_id, account_id, watch_count) VALUES (s.bug_id, s.account_id, 1)
RETURNING merge_action(), t.bug_id, t.account_id;

watch_count を事前に 5 にしてから実行すると、実際に merge_action() が DELETE を返し、該当の行が削除されて 0 件になりました。ON CONFLICT には DO UPDATE と DO NOTHING の 2 択しかなく、このような条件分岐での削除は書けません。

図: MERGE は条件ごとに複数の WHEN 句を並べ、挿入・更新・削除のどれを行うかを分岐できる。

4. 仕組み ― ON CONFLICT と MERGE、並行実行での違い (2 セッションの実機検証)

ここからがこの回の核心です。「2 つの接続が同時に同じ新しいキーを挿入しようとしたら何が起きるか」を、ON CONFLICT と MERGE それぞれについて、実際に 2 本の psql セッションを同時に走らせて確認しました。やり方は、セッション A が BEGIN した中で対象の行を挿入し、pg_sleep(3) でコミットを 3 秒遅らせている間に、セッション B が同じキーに対して同じ文を実行する、というものです。

4-1. ON CONFLICT DO UPDATE の場合

-- セッション A (先行)
BEGIN;
INSERT INTO bug_watchers (bug_id, account_id, watch_count) VALUES (1, 1, 1)
ON CONFLICT (bug_id, account_id) DO UPDATE SET watch_count = bug_watchers.watch_count + 1;
SELECT pg_sleep(3);
COMMIT;

-- セッション B (1 秒後に開始、同じ文)
INSERT INTO bug_watchers (bug_id, account_id, watch_count) VALUES (1, 1, 1)
ON CONFLICT (bug_id, account_id) DO UPDATE SET watch_count = bug_watchers.watch_count + 1;

実機の結果、B の文は 約 1.96 秒ブロックされた後、エラーにならずに成功し、watch_count は 2 になりました (\timing on で計測、A がコミットするまでの残り時間とほぼ一致)。B は A がコミットするまで待たされ、A のコミット後に「もう行が存在する」と分かった時点で、自動的に DO UPDATE の分岐に切り替わって処理を完了しています。

4-2. MERGE の場合

-- セッション A (先行、MERGE で同じキーを新規挿入)
BEGIN;
MERGE INTO bug_watchers t USING (SELECT 2::bigint bug_id, 1::bigint account_id) s
ON t.bug_id=s.bug_id AND t.account_id=s.account_id
WHEN NOT MATCHED THEN INSERT (bug_id, account_id, watch_count) VALUES (s.bug_id, s.account_id, 1)
WHEN MATCHED THEN UPDATE SET watch_count = t.watch_count + 1;
SELECT pg_sleep(3);
COMMIT;

-- セッション B (1 秒後に開始、同じ MERGE 文)
MERGE INTO bug_watchers t USING (SELECT 2::bigint bug_id, 1::bigint account_id) s
ON t.bug_id=s.bug_id AND t.account_id=s.account_id
WHEN NOT MATCHED THEN INSERT (bug_id, account_id, watch_count) VALUES (s.bug_id, s.account_id, 1)
WHEN MATCHED THEN UPDATE SET watch_count = t.watch_count + 1;

こちらも B は A のコミットまで約 1.96 秒ブロックされましたが、ブロックが解けた直後に次のエラーで失敗しました。

ERROR:  duplicate key value violates unique constraint "bug_watchers_pkey"
DETAIL:  Key (bug_id, account_id)=(2, 1) already exists.

B の MERGE 文は、実行を始めた時点ではまだ A の行が存在しなかったので WHEN NOT MATCHED (INSERT) の分岐を選びました。しかしブロックが解けて実際に挿入しようとした時点では、A が既にコミットして同じキーの行を作っていたため、選んだ分岐 (INSERT) をやり直さず、素の INSERT と同じ重複キーエラーで失敗しました。最終的に watch_count は 1 のままで、B の更新は反映されませんでした。

方式B のブロック時間ブロック解除後の結果
INSERT ... ON CONFLICT DO UPDATE約 1.96 秒成功 (watch_count=2、自動的に UPDATE 側に切り替わる)
MERGE (WHEN NOT MATCHED / WHEN MATCHED)約 1.96 秒重複キーエラー (選んだ分岐をやり直さない)

PostgreSQL の公式ドキュメントも、この違いを明確に書いています。分離レベルの章 (13.2.1 節) は、MERGE が INSERT を実行しようとして、一意インデックスに競合する行が並行して挿入された場合には一意性違反のエラーが発生すると説明したうえで、「MERGE は MATCHED の判定をやり直すことでこのようなエラーを避けようとはしない (原文: MERGE does not attempt to avoid such errors by restarting evaluation of MATCHED conditions)」と明記しています。つまり、WHEN NOT MATCHED という判定を下した時点と、実際に書き込む時点との間に矛盾が生まれても、MERGE はその判定をやり直さず、エラーとして表面化させてリトライに委ねる設計です。これに対して ON CONFLICT DO UPDATE は、公式ドキュメントが「高い並行実行下でも INSERT か UPDATE のどちらかの結果を保証する」と書いているとおり、まさに「挿入しようとしたら競合した」という状況そのものを扱うために設計されており、競合した場合の代替処理 (DO UPDATE/DO NOTHING) まで含めて 1 つの文の意味に組み込まれています。

図: 実機で確認した、ON CONFLICT と MERGE の並行実行時の振る舞いの違い。

5. どこで壊れるか ― よくある間違い

間違い 1: SELECT で確認してから INSERT する

節 1 で確認したとおり、「存在を確認する SELECT」と「結果に基づく INSERT」を別の文に分けると、2 つの接続が同時に動いたときに確認結果と実行結果がずれます。これは単純なミスではなく、文を分けている限り常に存在するレースです。「本番ではほとんど同時に動かないから大丈夫」という判断は、同時アクセスが増えた瞬間に崩れます。

間違い 2: MERGE を「ON CONFLICT の上位互換」だと思い込む

節 4 で確認したとおり、MERGE は競合が起きても ON CONFLICT のように自動で代替の分岐に切り替わりません。MERGE で「無ければ挿入、あれば更新」を安全に行いたい場合は、一意制約があることを前提に、重複キーエラーを呼び出し元でキャッチしてリトライする仕組みをアプリケーション側に用意する必要があります。「MERGE を使ったから競合は解決済みだ」という思い込みは、高い同時実行数の下で本番のエラーとして表面化します。

間違い 3: ON CONFLICT の対象列を一意制約と一致させていない

ON CONFLICT (列名, ...) に指定する列の組は、実際に一意制約または一意インデックスが存在する組と一致していなければなりません。一致していない場合、PostgreSQL は「このような一意制約または排他制約が存在しない」というエラーを返します。複合主キーやユニーク制約が複数ある表では、どの制約に対して競合を解決したいのかを明示する必要があります。

図: 2 つの文に分かれた「確認してから実行」は、常に割り込みの余地を残す。

6. シニアの書き方 ― 判断の基準

1. 「無ければ作り、あれば更新する」は必ず 1 つの文で書く。SELECT してから INSERT する 2 段階の書き方は、同時実行数がどれだけ少なくても理論上のレースを含みます。INSERT ... ON CONFLICT か MERGE のどちらかに最初から寄せます。

2. 単純な「1 つのキーに対する挿入か更新」なら ON CONFLICT を選ぶ。競合した場合に自動で代替処理に切り替わる挙動が欲しいなら ON CONFLICT が素直です。merge_action() のような「どちらが実行されたか」のログが必要な場合や、条件によって挿入・更新・削除を切り替えたい場合は MERGE を選びます。

3. MERGE を使うなら、重複キーエラーのリトライを自分で用意する。高い同時実行数の下で同じ新しいキーに複数の書き込みが集中する可能性があるなら、MERGE の重複キーエラーを想定し、アプリケーション側で再試行するか、ON CONFLICT に切り替えます。「エラーが出ないはず」という前提でコードを書かないことが、この回で一番言いたいことです。

K8S CUSTOM CONTROLLER ・ 第 03 回

コントローラーとは何か

調整ループ、Deployment から Pod までの連鎖、そして冪等性

← カスタムコントローラー自作 シリーズ目次へ

第 01 回で「望む状態を実現するのはコントローラーだ」と地図に描いた。第 03 回では、組み込みのコントローラーを例に、コントローラーが実際に何を見て何をしているのかを具体的に見る。ここで理解する型は、第 09 回以降で自分のコントローラーを書くときにそのまま使う。

コントローラーの正体は、「今の状態を見る → 望む状態と比べる → 差があれば現実を変える」を、延々と繰り返すだけのプログラムだ。これを調整ループ(reconcile loop: 望む状態と今の状態の差を埋め続ける繰り返し)と呼ぶ。Kubernetes はこのループを、変化の通知ではなく「今の状態そのもの」を基準に動かすよう設計されている。

1. コントローラー = 調整ループ

Kubernetes の公式ドキュメントは、コントローラーを「クラスタの状態を監視し、現在の状態を望む状態に近づけるために変更を加える制御ループ」として説明している。もう少し具体的に言うと、コントローラーは少なくとも 1 つの型(例えば Deployment)を見張り、その型のオブジェクトが持つ spec(望む状態)フィールドを読む(Controllers)。公式の言葉では「Each controller tries to move the current cluster state closer to the desired state」であり、現在の状態を望む状態へ近づけることそのものがコントローラーの仕事になる。

この「見る → 比べる → 近づける」を繰り返す仕組みを調整ループ(reconcile loop)と呼ぶ。1 回のループでやることは小さいが、それを止めずに繰り返すことで、クラスタの状態が常に望む状態へ引き寄せられていく。

図: このループは止まらず繰り返される。1 回で完璧に合わせる必要はない。

2. Deployment → ReplicaSet → Pod の連鎖

組み込みのコントローラーがどう動くかを、具体例で見る。Deployment を 1 つ作ると、それ自体は Pod を直接作らない。Deployment コントローラーがそれを見て ReplicaSet を作り、さらに ReplicaSet コントローラーがそれを見て、指定された数だけ Pod を作る。1 回の kubectl apply の裏で、実は 2 段のコントローラーが順番に反応している。

この連鎖のおかげで、Pod を手動で消しても ReplicaSet コントローラーが気づいて新しい Pod を作り直す。「誰が何個欲しいと言っているか」を各段で持っているからこそ、途中の 1 個が消えても全体として望む状態に戻る。

図: 1 つの apply の裏で 2 段のコントローラーが順に反応する。

3. レベル基準(level-based)とエッジ基準(edge-based)

通知の受け取り方には 2 つの考え方がある。エッジ基準(edge-based: 「2 から 5 に変わった」という変化そのものを基準にする)と、レベル基準(level-based: 変化の経緯は無視して「今は 5 である」という状態そのものを基準にする)だ。Kubernetes の API の作法を定める文書は、はっきりとこう書いている。

"the system's behavior is level-based rather than edge-based. This enables robust behavior in the presence of missed intermediate state changes."
(kubernetes/community: API Conventions)

同じ文書は、値が 2 → 5 → 3 と、2 回の PUT(PUT: HTTP でオブジェクトの内容をまるごと置き換える操作)で変わったとき、途中の 5 を一度も反映しなくても、最終的に 3 に合わせられれば構わないと述べている。コントローラーが途中の変化通知を 1 回見逃しても、次にループが回ったときに「今の値は 3 だ」と見て正しく追従できるのは、このレベル基準の設計のおかげだ。エッジ基準だと、見逃した変化は永久に失われてしまう。

図: レベル基準は「今の値」だけを見るので、通知の見逃しに強い。

4. 冪等性が必須な理由

調整ループは何度も繰り返し呼ばれる。同じ入力で 2 回呼ばれても、1 回しか呼ばれなかったときと同じ結果になる性質を冪等(idempotent: 何回やっても同じ結果になること)と呼ぶ。コントローラーのコードは、必ず冪等に書く必要がある。

なぜか。ネットワークの揺れや再起動で、同じイベントに対して調整ループが 2 回動いてしまうことは普通に起きる。「Pod を 1 つ作る」という処理が、呼ぶたびに別名で Pod を作る実装(例えば名前を自動生成する)になっていれば、2 回目の実行で同じ Pod がもう 1 つ作られてしまい、気づかないうちに意図しない数の Pod が並ぶことになる。冪等な処理なら、「すでにあるなら何もしない」という判断が常に正しい答えになる。なお、Pod の名前を毎回固定にしておけば、2 回目の作成リクエストは API サーバーに Already Exists として拒否されるので、個数は増えない。決まった名前で作ることも、冪等性を実現する代表的な手段の一つだ。

図: 「作る」ではなく「ある状態にする」と考えると冪等になりやすい。決まった名前で作るのも有効な手段の一つ。

まとめと次の回

コントローラーは「見る・比べる・近づける」を繰り返す調整ループであり、Kubernetes はその判断の基準を変化の通知ではなく今の状態(レベル基準)に置くことで、通知の見逃しに強い設計を実現している。そしてどのコントローラーも冪等でなければ、繰り返し呼ばれるたびに結果が狂う。第 04 回では、この「コントローラー」と、それが見張る対象である CRD・CR、さらに両者を組み合わせたオペレーターという言葉の違いを整理する。

図: この 2 つの性質が、次回以降の CRD・コントローラーの設計すべての土台になる。

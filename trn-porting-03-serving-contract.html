サービング契約 ― 移植とは何を実装することか

KV キャッシュへの読み書き作法、並列分割、重み読み込み、デバイス上サンプリング

← シリーズ目次

0この回の狙い

「モデルを移植する」という言葉の中身を、実装すべき項目のリストに変換します。この回が実装者にとってのシリーズの本体です。

第 1 回で、KV ブロックの割当と解放という管理は vLLM 本体が持ち、実体のテンソルはプラグインのランナーが確保し、形はモデルが申告する、と書きました。では自分が書くモデルは何を担うのか。答えは 「割り当てられた KV キャッシュ領域に、自分で正しく読み書きすること」です。この作法の集まりをここではサービング契約と呼びます。

契約という言葉を使う理由は、これが「実装の自由な部分」ではないからです。ランナーが特定の引数でモデルを呼び、モデルは特定の形で応答しなければならない。守らないと、動かないか、静かに間違った答えを出します。後者が本当に怖い部分です。

一言でいうと
モデルが実装すべきは 5 つです。(1) レジストリ登録と設定からの生成、(2) KV キャッシュの形の申告と受け取り、(3) prefill と decode で作法が違う forward、(4) テンソル並列を意識した重み読み込み、(5) デバイス上サンプリングとの接続。このうち (2) と (3) が Trainium 固有の勘所で、(4) が最も静かなバグを生みます。
1. 契約の全体像 2. レジストリと設定からの生成 3. KV キャッシュの形を申告する 4. prefill と decode は別の作法 5. forward の引数と戻り値 6. 並列化つきレイヤを使う 7. 重み読み込みが一番静かに壊れる 8. デバイス上サンプリング 9. 実装チェックリスト

1契約の全体像

誰が誰を呼ぶのかを図にします。ここで「ランナー」と呼ぶのは、第 1 回でプラグインが差し替える部品として挙げた ModelRunner です。矢印の向きを覚えると、どこに何を書くべきかが自然に決まります。

左が呼ぶ側、右が実装する側。起動時に 3 回、毎ステップに 1 回の呼び出しがある

2レジストリと設定からの生成

最初の 2 つは形式的ですが、ここを外すと「モデルが見つからない」で終わります。

プラグインのモデルレジストリは、Hugging Face の設定にある architectures の文字列と、自分のモデルクラスを対応づけるリストです。公開レジストリに実際に並んでいる LlamaForCausalLM や Qwen3ForCausalLM のような文字列がキーになります。ここに登録しないと、そのアーキテクチャは存在しないものとして扱われます。

次に、設定オブジェクトから自分のモデルを組み立てるファクトリを書きます。ここで踏みやすい落とし穴が 1 つあります。Hugging Face の設定オブジェクトを辞書に変換すると、別名 (alias) で定義されているフィールドが落ちることがあります。層数やアーキテクチャのパターン文字列がこれで消えると、既定値にフォールバックして、まったく違う形のモデルが黙って組み上がります。

この失敗の見え方: 層数が既定値になり、重みを読む段で「対応する重みが無い」パラメータが大量に残ります。エラーメッセージは重み読み込みの側に出るので、原因が設定変換にあることに気付きにくい。設定を読んだ直後に、層数と主要な次元をログに出して目で確認するのが安全です。

3KV キャッシュの形を申告する

ここから Trainium 固有の話です。KV キャッシュは vLLM 本体が確保しますが、形はモデルが決めます。

起動時、ランナーはモデルに「各層の KV はどんな形か」を問い合わせます。モデルは層ごとに、KV ヘッド数、ヘッド次元、データ型、そしてスライディングウィンドウやチャンクサイズといった付帯情報を返します。

ここで層ごとに違う形を返せるのが重要です。全層が同じ attention なら一様ですが、層の種類が混ざるアーキテクチャ (attention の層と、attention でない層が交互に来るもの) では、attention の層だけが KV を要求します。この不均一を申告できる設計になっています。

申告が済むと、ランナーはブロック単位で確保した大きなテンソルをモデルに渡します。形は [ブロック数, KV ヘッド数, ブロックサイズ, ヘッド次元] の並びです。ただし次元の順序は attention backend の定義が正なので、実装時はそこを確認してください。順序を取り違えても要素数が合ってしまう組み合わせ (ブロックサイズとヘッド次元が同値など) では例外が出ず、精度だけが崩れます。書き込んだ直後に 1 ブロックを読み戻し、自分が書いた値と一致するかを確認するテストを最初に書いておくのが安全です。モデルはこの箱を各層に配り、以降は自分で読み書きします。

モデルは連続バッファではなく、間接参照で KV に触る。Hugging Face 実装と持ち主が逆になる理由がこの構造

ここが「汎用フォールバックを作れない」理由
Hugging Face の実装は KV キャッシュを自分で持ちます (毎ステップ連結して伸びる形)。一方この契約では、キャッシュの実体は外から渡され、モデルはそこに間接的に読み書きします。データの持ち主が逆なので、Hugging Face の forward をそのまま呼ぶ受け皿にはなりません。作るなら KV へのアクセスを差し替える汎用のアダプタ層が必要で、現状のプラグインはそれを持っていません。第 1 回で触れた「レジストリが列挙式である」理由がこれです。

4prefill と decode は別の作法

同じ層の同じ数式でも、prefill と decode でデータの動きが違います。ここを 1 つの関数で書こうとすると破綻します。

prefill は「書く」、decode は「集めて読む」。形状も非対称なので、同じカーネルが両方で使えるとは限らない

この非対称性から、実務上とても刺さる注意点が出ます。prefill 用に作られた attention カーネルが decode の形状で正しく動くとは限りません。prefill では query と key の長さが同じなので、因果マスクは正方の三角行列になります。decode では query が 1 個、key が履歴全部なので、マスクは 1 行の形になります。同じ作り方をすると意味が変わります。

実際に遭遇する形: prefill は正しいのに decode の出力だけが崩れ、生成が繰り返しに落ちる。原因が数式ではなくマスクの形にあるので、層ごとの数値比較をしても prefill では差が出ず、切り分けに時間がかかります。decode を専用の実装に分けて、prefill と decode の整合性を不変条件として検証するのが確実です。検証方法は第 8 回で扱います。

5forward の引数と戻り値

具体的な呼び出し形を押さえます。ここを外すと、そもそもランナーから呼ばれません。

ランナーはモデルを、トークン列、位置、attention のメタデータ、サンプリング用の位置情報、サンプリングのパラメータ、といった引数で呼びます。メタデータの中に、prefill で「どこに書くか」を示す情報と、decode で「どこから読むか」を示すブロック表が入っています。

# 呼び出しの形 (2026-09-01 時点。名前と順序はバージョンで変わるのでソースを正とする)
logits = model(
    input_ids,           # このステップで処理するトークン
    positions,           # 各トークンの位置
    attn_metadata,       # スロット指示 (prefill) とブロック表 (decode) を含む
    sampling_positions,  # logits を取り出す位置
    sampling_params,     # 温度 / top-k / top-p など。常にテンソルで渡す
    ...
)

# モデル側が実装するもの
model.get_kv_spec(...)     # 層ごとの KV の形を申告する
model.bind_kv_cache(...)   # 確保済みの KV テンソルを受け取って層に配る
model.load_weights(...)    # チェックポイントを並列分割して載せる
Model.from_configs(...)    # 設定オブジェクトからモデルを組み立てる

戻り値は logits です。デバイス上サンプリングを使う構成では、サンプリングまでグラフに含めてトークンを返します。

正は必ずソースで確認する
引数の名前と順序はバージョンで変わります。正を確認する場所は 2 つで、参照実装の forward 定義 (vllm_neuron/model/llama3/ や vllm_neuron/model/qwen3/) と、ランナー側の呼び出し箇所 (vllm_neuron/vllm/worker/neuron_model_runner.py) です。この 2 つを突き合わせれば、その版で何を受け取り何を返すべきかが確定します。KV の申告と受け取りは get_kv_spec と bind_kv_cache、重み読み込みは load_weights、設定からの生成は from_configs という名前で参照実装に並んでいます。レジストリは vllm_neuron/model/registry.py、移植手順そのものはリポジトリの docs/design/framework/model_bringup.md と docs/model-dev/onboarding-models.md にあります。
筆者が実際に踏んだ初手のミス: 自分の手元で数値検証するために書いた forward の形と、ランナーが呼ぶ形が違う。手元では (tokens, positions, state, is_decode) のような素朴な形で組んで数値が合うところまで進み、実際に起動したら引数が合わずに落ちる。先に参照実装の forward の引数列を写してから中身を書くのが遠回りに見えて速いです。

6並列化つきレイヤを使う

テンソル並列を自分で書くのではなく、用意されている部品を使います。どの部品がどの分割を担うかを覚えます。

プラグインは並列化を織り込んだ基本レイヤを提供します。出力側の次元で分割する線形層 (列並列)、入力側で分割して最後に足し合わせる線形層 (行並列)、語彙次元で分割する埋め込み、そしてサンプラです。

加えて、カーネル呼び出し層が attention や MLP や MoE を提供します。これらはサービングのデータレイアウトを引数の契約に持っています。たとえば attention のカーネルは、prefill 用と decode 用が分かれており、paged KV の形を前提にしています。

ここで移植の実感を書いておくと、「Hugging Face の実装を読みながら、同じ数式をこの語彙で書き直す」のが作業の姿です。行数の大半は数式ではなく、分割の面倒と形の整合です。

シーケンス並列が入ると足し合わせの位置が変わる

シーケンス並列を使う構成では、prefill の入口でトークン方向に分割し、出口で集め直します。ブロック単位で見ると、attention や MLP のブロックに入るところで all-gather、出るところで reduce-scatter が入り、行並列の all-reduce がこの対に置き換わります。密な MLP と MoE で通信の入る位置が違うので、参照実装をそのまま真似ると、片方だけ通信が足りない、あるいは二重になる、という間違いが起きます。

7重み読み込みは静かに壊れる

筆者が 2 つのモデルを移植した中で、最も発見に時間がかかったのがこの領域でした。ここのバグは「動くが精度が悪い」という形で出るので、切り分けのコストが構造的に高くなります。

チェックポイントの重みは、モデル定義が期待する並びとは違う形で保存されています。だから読み込み時に変換が入ります。変換の内容は、テンソル並列のランクごとに「自分の担当ぶんだけを切り出す」ことと、融合されたテンソルを境界で正しく分けることです。

融合テンソルの分割は境界を意識する

典型は 2 つです。1 つは QKV が 1 つのテンソルに融合されている場合。もう 1 つは MLP のゲートとアップが 1 つのテンソルに融合されている場合です。

後者が特に危ないので具体的に書きます。ゲートとアップが [2I, H] の形で縦に積まれているとき、これを単純に行方向で等分割してランクに配ると、あるランクはゲートだけ、別のランクはアップだけを持つことになります。正しくは、ゲートの領域とアップの領域をそれぞれ独立に切り出してから連結します。

融合テンソルの分割。左の誤りは例外を出さないので、精度の劣化としてだけ現れる

そのほかの落とし穴

落とし穴症状対処
重みを共有する語彙埋め込みと出力層 (tied embeddings)片方だけ読み込まれ、もう片方が初期値のまま読み込み後に参照を貼り直す
チェックポイントの接頭辞がモデルによって違う全パラメータが未初期化のまま残るチェックポイント側のキーから接頭辞を自動判定する
meta デバイス上でモデルを作ってから読む読み込み漏れが例外にならず、初期化されていないテンソルが残る読み込み後に「未初期化が 0 件」を必ず検査する
正規化層の重みを 1 で初期化するか 0 で初期化するか実装によって (1 + w) を掛ける流儀がある。取り違えると二重に効く参照実装の数式を確認する。dtype も明示する
切り出し前のテンソルに対して転置や連続化を呼ぶ遅延読み込みのオブジェクトにメソッドが無くて落ちる先に実体化してから変換する
KV ヘッド数が並列度より少ない、または割り切れない起動時エラー、あるいは KV ヘッドの複製漏れで decode だけ崩れる参照実装の KV ヘッド複製の扱いを確認し、サポートする並列度を先に決める
語彙サイズが並列度で割り切れない埋め込みの分割で形が合わない語彙パディングの有無と、logits 側でのパディング除去を確認する
位置埋め込みの周波数を低精度で計算する、または回転の適用形式を取り違える短い入力では合うのに、長い系列と実重みで劣化する周波数テーブルは fp32 で作る。適用形式 (交互に並べるか半分に割るか) はテンソル操作の単位で照合する
ここで効く自衛策は 1 つだけ
読み込み直後に「パラメータ総数・読み込み済み件数・未初期化件数」を全ランクで出す。未初期化が 1 件でもあれば止める。この検査があるだけで、上の落とし穴のほとんどが「精度劣化」ではなく「起動時エラー」に変わります。精度の問題として現れたものを後から切り分けるコストは、この検査を書くコストの数十倍です。

8デバイス上サンプリング

最後の接続です。ここをグラフに含めるかどうかで、性能の性質が変わります。

サンプリング (温度、top-k、top-p) をデバイス上で行う構成が推奨されています。理由は単純で、logits をホストに戻さずに済むからです。語彙サイズが大きいと logits は巨大なので、これを毎ステップ往復させると帯域が効きます。

実装としては、モデルの最後にサンプラを繋ぎ、グラフの出力を token にします。投機デコードを使う場合は、採択判定もデバイス上の純粋なテンソル演算として書かれ、同じグラフに入ります。

移植時の注意は、サンプリングのパラメータが常にテンソルとして渡されるように書くことです。「指定が無ければ None」という分岐を作ると、最初のリクエストで別のグラフが必要になって再コンパイルが走ります。値の有無で分岐せず、無効を表す値を渡す設計にします。同じ考え方は構造化出力のマスクにも使われていて、全部 True のマスクを渡すことで分岐を消しています。

9実装チェックリスト

この回の内容を、手を動かす順序に並べ替えます。

  1. 既存の対応モデルを無改造で通す。参照実装をそのままの構成で起動し、生成まで確認する。ここで詰まる問題は移植と無関係なので先に潰す。あわせてコンパイルキャッシュの置き場 (永続ボリューム) をこの時点で決める
  2. 設定を読む。層数と主要な次元をログに出して目視確認する
  3. 正規化・位置埋め込みを参照実装の数式どおりに書く。重みの初期化流儀と dtype を確認する
  4. attention を書く。prefill と decode を分ける。KV の書き込みと読み出しを契約どおりに行う
  5. MLP または MoE を書く。集団通信の入る位置が密と疎で違うことに注意する
  6. デコーダ層とバックボーンを組む。層の種類が混ざる場合は KV の申告を不均一にする
  7. 出力層と重み読み込み。融合テンソルの境界、共有重み、接頭辞の自動判定。未初期化 0 件の検査を入れる
  8. レジストリ登録。ここまでで初めて起動できる
  9. CPU で数値検証。参照実装との層ごと比較。ここを実機の前にやる (第 5 回)
  10. 実機でコンパイルと生成。まずテンソル並列度 1 で通す。落ちた段を第 2 回の表で切り分ける
  11. 並列度を上げる。並列度 1 で生成が正しいことを確認してから上げ、「並列度を変えても結果が一致する」で重み分割と集団通信を検証する (第 8 回 §7)
  12. 不変条件の検証。prefill 一括と prefill + decode の結果が一致するか (第 8 回 §7)

各工程には完了条件を対にしておくと、次に進んでよいかの判断が読者の勘に委ねられません。たとえば attention なら「prefill と decode をそれぞれ単体で参照実装と fp32 相対誤差 1e-5 以下で一致」、重み読み込みなら「未初期化 0 件、かつ数個のパラメータを名前指定でチェックポイント原本と直接比較して一致」。工程名だけをチェックリストにすると、通っていないものを通ったことにしてしまいます。

この順序の要点は、CPU での数値検証を実機より前に置くことです。実機でのコンパイルは時間がかかり、しかもコンパイルの成否は数値の正しさを何も保証しません。数式の間違いを実機で探すのは、最も高い場所で最も安いバグを探す行為になります。

出典と確認方法: 契約の各要素 (KV の申告と受け取り、forward の引数、並列化レイヤ、重みローダ、デバイス上サンプリング) は vllm-project/vllm-neuron の公開ソースと、同リポジトリのモデル追加手順および設計ドキュメントに記述があります。落とし穴として挙げた項目は、公開ドキュメントに記載のあるものと、筆者が公開プラグイン上で 2 つのモデルを移植する過程で遭遇したものを含みます。頻度の主張はしていません (n=2 なので母集団の話はできません)。挙げているのは「例外を出さず精度劣化としてだけ現れるので発見コストが構造的に高い」という性質です。

確認時点: 本稿の記述は 2026-09-01 時点のものです。対象はプラグイン 0.21.0.1.0.0 と 0.24.0.1.1.0 の公開ソースおよび公開コンテナイメージ、公開パッケージインデックスから取得できるランタイム兼カーネル基盤ライブラリ (2.11.0.1.0.1284 / 2.12.0.1.0.1284)、コンパイラ 2.26 / 2.27 系、低レベルカーネル言語 0.5.0 / 0.6.0、PyTorch 2.11.0 です。バージョンが上がれば名前も挙動も変わりうるので、正はソースと配布物です。

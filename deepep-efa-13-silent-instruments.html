1道具が届いていない沈黙

この回は、答えではなく答えを取り損ねた回数についての記録です。1 日で 7 回、同じ形の誤りをしました。

emulator の参照経路 (2 rank の再現テスト) は通っています。dispatch と combine、自己記述 payload の検証、8 反復、6 種類の順序モード、すべて緑です。通らないのは vLLM 経路だけで、その追跡に 1 日を使いました。

結果として本物の欠陥は 3 つ見つかりました。しかしそれ以上に繰り返したのは、道具が自分の理由で答えを出せない状態を、対象についての答えと読むことでした。

道具自分の理由で黙っていた原因私がそれをどう誤読したか
compute-sanitizer既定の --launch-timeout が 10 秒で、torch の読み込みに間に合わない「attach できない環境」
compute-sanitizer既定の --print-limit で 173 件中 165 件が隠れた「無害な 8 件しか出ていない」
core dumpulimit -c のハード上限が 0 で、|| true が失敗を隠した「crash が core を残さない」
再現タスクplugin を使うだけで作らないので 13 時間古いバイナリを測っていた「修正が stall を動かした」
実行チェーンbuild が落ちて && で止まり、sanitizer 実行が一度も起動しなかった「sanitizer が attach しない」
ASANloadable チェックが libasan を preload せず、検査自体が失敗(この 1 回は誤読の直前に気づいた)
ASANDeepEP に到達する前に死んでいた「黙ったから私の書き込みは無罪」(撤回)

共通しているのは、動いているように見えて測っていない状態です。どれも「失敗を握り潰して先へ進む」形をしていて、後続の観測をまるごと無意味にします。測定を足す前に、その測定器が今回ちゃんと働いたかを確認する行を先に書くべきでした。

2診断を破壊する upstream の欠陥

1 日のうち 10 時間は、DeepEP のデストラクタが例外を投げることに費われました。

vLLM は起動中に crash します。症状は run ごとに cudaErrorIllegalAddress と SIGSEGV を行き来し、backtrace は CPython のフレームばかりで、私は「非決定的な同根の症状」と読んでいました。core を開いて初めて機構が見えました。

#4  abort ()
#7  __cxa_call_terminate ()
#10 _Unwind_Resume ()
#11 deep_ep::symmetric::GPUSymmetricMemory::~GPUSymmetricMemory ()

これは segfault ではありません。~GPUSymmetricMemory が NCCL_CHECK(ncclMemFree(ptr)) を呼び、失敗すると throw します。すでに別の例外が unwinding している最中の throw は std::terminate に行きます。_Unwind_Resume がデストラクタの下にあることが全てです。

問題は abort ではなく、元の例外が破壊されることです。ElasticBuffer 構築時のあらゆる失敗が、理由を失った abort として現れます。顧客が起動失敗を報告してきても、ログには何も残りません。私が到達できたのは EC2 に sudo があり ulimit のハード上限を上げられたからで、通常の環境ではできません。

デバイス側の fault の後は ncclMemFree が失敗するのは当然です。poisoned context は以降のすべての呼び出しを失敗させます。つまりこの throw は診断を失うだけで、何も買っていません。報告して継続する形に直しました。基底クラスが noexcept(0) を宣言して throw を許可していますが、許可されていることと有用であることは別です。

3環境変数 1 個

マスクを外した次の失敗は、traceback の末尾に平文で書かれていました。

NCCL WARN Multiple Ranks are using the same GPU/Partition.
  Set NCCL_MULTI_RANK_GPU_ENABLE=1 to enable
RuntimeError: NCCL error: invalid usage

vLLM は 2 つの data-parallel rank を 1 枚の GPU に載せ、NCCL 2.31.2 は既定でそれを拒否します。ncclCommInitRank が DP グループ構築中に落ちるので、DeepEP に到達する前の失敗です。

再現テストは rank ごとに別の NCCL_HOSTID を与えて回避していました。vLLM は両 rank を 1 つの環境の中に spawn するので、launcher が設定した値を共有します。ハーネスが偶然回避していた制約で、コードの性質ではありませんでした。

4再現テストのカバレッジが狭かった

今日見つけた自分の欠陥 10 件のうち 4 件は、ローカルからは原理的に見えません。

私の欠陥再現テストが見られない理由
pinned pool の signal スロットが staging スロット 63 と重なる3 スレッドしか走らず、最後のスロットに到達しない
mapping が lead offset を覆っていない登録するウィンドウが全部ページ境界から始まる
同じ番地のウィンドウを二重に pin/map する同じ番地を二度登録しない
deregister 済みウィンドウが解放済み base を返し続ける実行中にウィンドウを解放しない

これはハーネス 1 つの性質であってコードの性質ではありません。それに寄りかかったテストはテストではありません。そこで算術を gdrapi.h 依存のクラスから外へ出し、GPU なしで列挙できる形にしました。lead offset をページ全体に刻み、全スロットを主張し、加算が wrap する長さも拒否する。1841 checks です。

そして mutation test で最初に打った変異が間違っていました。retire() は base を null にし同時に bytes も 0 にするので、null チェックだけ外しても境界チェックが拒否します。テストは通り、私は「テストが効いていない」と判断しました。正しい変異は「retire を何もしない関数にする」— 修正前の実際の状態です。それで 4 件落ちます。どのガードが実際に仕事をしているかを特定してからでないと、テストを信じることはできません。

5撤回した診断

正しく見えた推論を 2 つ取り下げました。両方とも、証拠 1 個から書き手を特定しようとしたものです。

packed (finish, tail) 説

core のレジスタが %rsi = 0x100000001 を dereference して落ちていました。これは 32 ビットの 1 が 2 つ packed された値で、DeepEP の scale-out signalled tail の形そのものです。私は「ウィンドウへの書き込みが解放済みヒープに着地した」と結論しました。

次の core では %rsi = 0x0 でした。破壊値は run ごとに違います。0x100000001 は packed pair として解釈できますが、破壊値の 1 サンプルであって署名ではありません。一貫しているのは fault アドレスの領域だけです。

retire 修正が原因という説

その診断から WindowTable の retire 経路を実装しました。修正自体は正しく、mutation test も付いています。しかし deregMrSym は vLLM の実行で一度も呼ばれていません (0 回)。呼ばれなければ retire は走らないので、この障害には無関係です。

この調査で「正しいが原因でない修正」を 5 回入れました。理由は明白で、ヒープ破壊をプロセスが最終的に死んだ場所から逆算していたことです。ここでの逆算は繰り返し外れました。残っている crash の書き手は、まだ特定できていません。

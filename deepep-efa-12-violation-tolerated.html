1通っただけでは何も言えない

エミュレータの価値は「DeepEP が動く」ことではなく、「壊れるべきときに壊れる」ことです。

dispatch と combine が通ったので、次は較正です。順序のモードを 6 種類用意してあり、そのうち violate-i1 はわざと契約を破るものです。EFA が唯一保証する性質、「signal はそれを運んだ put の全バイトが着いた後にしか見えない」を破ります。

期待は明確でした。srd は通り、violate-i1 は落ちる。これが揃って初めて、エミュレータは順序について何かを言えます。

結果は全モード通過でした。violate-i1 も含めて。

これは結果ではありませんでした。テスト側に 2 つの欠陥があり、その手前に本物の結論が隠れていました。

2欠陥その 1: データを見ていなかった

再現スクリプトは torch.randn を投げ、dispatch が返ったことだけを確認していました。ところが signal が payload より先に見えたときの症状はハングではありません。バイトが着いていないバッチを受理させるので、結果が間違うだけです。データを一度も見ないテストは、これを永久に見ません。

payload を自己記述型にしました。token t の全要素が整数 t、rank 1 では負。すると正しく届いた行には 2 つの性質が成り立ち、どちらも安く確認できます。

  • 行が定数である。ちぎれた書き込みや欠けた書き込みはこれを破ります
  • 値が token 数未満の整数である。別の場所から来たバイトはこれを破ります

整数を 128 未満にしたのは bfloat16 の要求です。仮数が 8 ビットなので 127 は正確に表せますが 1000 は表せません。dtype が丸めるパターンを選ぶと、検査そのものが自分の理由で落ちます。

カーネルが埋めなかった行は正当にゼロなので値の検査から外し、そのうえで「全行ゼロ」を明示的に失敗にしました。壊れた実行が満たせる検査は検査ではありません。

3欠陥その 2: 敵が本気でなかった

violate-i1 は signal を「早く出してよい」状態にするだけで、実際に選ぶかどうかは乱数任せでした。だからほとんどのステップで payload が先に出て、違反はめったに回線に乗りません。

ときどきしか発火しない否定テストは、2 つを区別できません。「backend が違反に耐えた」と「そもそも違反が起きなかった」。DeepEP がこのモードを無傷で通ったのは、まさにこの理由でした。

いまは決定的に signal を優先します。契約を破る名前のモードは、破れるときに必ず破らなければいけません。スケジュールのテスト側も「64 seed のうち少なくとも 1 つで破れる」から「64 全部で破れる」に締めました。これが敵とコイントスの違いです。

4両方直したら、DeepEP が正しかった

mode srd,         8 iterations: 0 not constant, 0 not integral, 0 out of range
mode violate-i1,  8 iterations: 0 not constant, 0 not integral, 0 out of range

全ステップで違反を強制しても、破損は 1 件も出ません。理由はカーネルの中にあります。

早すぎる signal が無害になる仕組み。門番は counter ではなく in-band の header です。

受理は payload バッファの中にある header で門番されています。signal が先に着くと landed は上がりますが、num_valid は有効な header の数を数えるのでまだ 0 です。だから待ちは空振りに成立し、何も受理されず、header が現れるまで poll が続きます。

5より鋭い形も試した

1 反復では、違反のもっと危ない形を出せません。

counter は累積で、カーネルは反復ごとに基準値を取ります。つまりある反復で走りすぎた count は、次の反復が landed を計算するときにもまだ先を走っています。誰のものでもないバイトを持つバッチが受理されうる、という筋です。

8 反復を連続で回して、こちらも到達しないことを確認しました。REPRO_ITERATIONS は残す価値があります。1 反復は「耐えたカーネル」と「起きなかった実行」を区別できないからです。

結論。DeepEP の unordered カーネルは I1 違反に耐えます。EFA backend はこのカーネルに対してこの保証を提供する必要がありません。契約より頑健だということです。

ただしこれは構成についての主張で、カーネル一般についての主張ではありません。2 rank・GPU 1 枚ずつ・kNumParts = 1・kNumSubParts = 1・128 token・192 channel。part が複数ある形は、counter とそれを正当化する header のあいだにもっと余地があります。

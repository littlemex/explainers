1AgentX が示すワークロードの形

まず数字から入ります。AgentX は SemiAnalysis が公開したベンチマークで、実際の agentic コーディングのトレースから作られています。原文が挙げる 4 つの統計が、この記事の全体を規定します。

統計値何を意味するか
セッションの長さ中央値 43 ターン1 回の会話ではなく長く続く往復が単位
入力と出力の非対称入力の中央値 142K トークンに対し出力は 444 トークン読む量が書く量の 300 倍以上。attention と KV が支配的になる
prefix の再利用キャッシュのヒット率 96% 超リクエストのほとんどは既に見た文脈。計算し直す価値がない
subagent44% のセッションに 1 つ以上。該当セッションでは中央値 4 rollout文脈が分岐して合流する。単純な直線ではない

なぜこの形になるのか、原文の説明が明快です。各ターンは最新のツール結果を積み上げた文脈の末尾に足して、全体をまたモデルに送ります。だから入力は伸び続け、1 ターンが足す新しい prefill は短く、リクエストのほとんどはエンジンが既に見た prefix になります。subagent はその文脈から fork するか、新規に始まり、結果は最終回答の前に親へ合流します。

補足この 4 つの統計が、後の節すべての理由になっていることを先に押さえておくと読みやすくなります。96% の再利用があるから KV キャッシュを捨てずに階層化する価値があり (4 節 ・ 5 節)、入力が出力の 300 倍だから attention の並列化が効き (6 節)、短い append と長い新規 prefill が混ざるから head-of-line blocking が起きます (7 節)。そしてセッションが長く続くから、次のターンが来たときにキャッシュがどの GPU にあるかが routing の決め手になります (12 節)。スタック全体の最適化に見えて、実は 4 つの統計への応答です。

2【デモ】セッション全体のトークン会計

「ヒット率 96%」という数字が実際にどれだけの計算を消しているのかを、セッション 1 本の合計で数えます。原文の対話ページはターンごとの内訳を見せるので、ここでは合計と倍率という別の切り口にします。

ターン数 43
最終的な入力長 142K
1 ターンの出力 444 トークン
キャッシュのヒット率 96%
キャッシュから再利用 (計算しない) 実際に prefill する decode で生成する

スライダーの既定値は AgentX の中央値ですが、計算はこの記事の単純な会計です。ターンごとに入力が線形に伸びると仮定して合計を出しています (実際の伸び方はセッションによって違います)。ヒット率はエンジンが達成した実測値で、ここでは「その割合が再計算されなかった」という意味に読み替えて使っています。原文の 96% はキャッシュヒット率そのもので、この会計式は原文にはありません。
既定値で見ると分かるのは、セッション 1 本で読まれる入力の合計が、最終的な文脈長の何十倍にもなることです。43 ターンで文脈が 142K まで伸びるなら、単純な合計は約 300 万トークン。ここで 96% がキャッシュから来るなら、実際に prefill するのは 10 万トークン台まで落ちます。agentic serving のコストがキャッシュの効き方でほぼ決まるのは、この桁の違いからです。11 節のコスト比較が「理論上のキャッシュヒット率を仮定している」と注記されているのも、同じ理由で数字が大きく動くからです。

33 つの課題と 3 つの plane

ワークロードの形から、3 つの課題が出てきます。原文の整理をそのまま押さえます。

課題中身
prefix キャッシュへの圧力多ターンのセッションは毎ターン、それまでの会話全体を再生します。多数のセッションを同時に走らせるには、ターンの間に KV をオフロードする必要がある。しかも大規模になると、KV の管理 ・ prefix キャッシュ ・ オフロードがGPU をまたぎ、P/D 分離されたインスタンスをまたぎ、レプリカをまたいで効率よく動かないといけない
実行効率長文脈と厳しいレイテンシ要求。より多くのトークンを、1 トークンあたりより多くの仕事をして、より短い時間で処理する必要がある。並列化 ・ カーネル ・ スケジューリング ・ speculative decoding を新しいリクエストの形に合わせて作り直す
P/D 比の決定文脈長とキャッシュヒット率がセッションと subagent の間で大きくばらつき、routing はキャッシュ親和性と負荷を両立させる必要がある。スループット最適な P/D 比を見つけるのが難しく、しかも同時実行数によって動く

図 3: agentic serving のためのフルスタック最適化。データ面が分散共有 KV キャッシュを管理し、実行面が各モデルを適切な並列化とカーネルに対応づけ、制御面が適切な P/D 比とリクエストのスケジューリングを調整する。
図の出典: vLLM x AgentX (vLLM 公式ブログ)

補足3 つの plane という分け方は、「何を最適化の単位にするか」の違いで読むと整理しやすいです。データ面はバイトを扱い、キャッシュがどこにあるかを決める。実行面は1 ステップの時間を扱い、そのステップの中でどう並列化するかを決める。制御面はリクエストの流れを扱い、どのインスタンスにいくつ流すかを決める。この 3 つは互いに独立ではなく、12 節の「負荷分散がセッション固定の routing に負けた」という失敗は、制御面の判断がデータ面の状態を知らずに下されたときに起きるという例になっています。

4データ面 — 1 つのページ、1 つのプール

KV キャッシュの管理は PagedAttention 以来 vLLM の中心にあります。agentic な長文脈はその容量をさらに圧迫し、hybrid なモデルが確保をさらに複雑にします。sliding window や線形 attention と full attention が混ざると、キャッシュブロックのサイズも寿命も違うからです。

vLLM の hybrid KV cache manager が採る芯は単純です。一様なメモリページを確保の基本単位にして、1 つの共有ブロックプールで管理する。

図 4: vLLM の hybrid KV cache manager。1 つのページサイズがすべての attention 型に対応し、1 つのブロックプールがそれらの間で共有される。
図の出典: vLLM x AgentX (vLLM 公式ブログ)

共有プールにすると、attention 型ごとに容量を静的に分割するのではなく、必要に応じて動的に再割り当てできます。これが効くのは、full attention の KV は系列長とともに伸びるのに、sliding window や再帰状態は寿命もスケーリング規則も違うからです。だから最適な分割は、同時実行数 ・ 文脈長 ・ prefix 再利用のパターンによって変わります。

DeepSeek V4 で見えた断片化

抽象は新しいアーキテクチャに当たるたびに更新されます。原文が挙げる具体例が分かりやすい。DeepSeek V4 の初期の KV レイアウトは、種類の違うキャッシュを 3 つのサイズのバケットに断片化し、92 個の別々のテンソルを確保していました。

問題新しい packed layout
断片化がパディングでメモリを無駄にする1 ブロックあたり 1 つの連続した確保に、全キャッシュグループと全層を格納する (92 個の断片ではなく)
P/D 転送と KV オフロードに非効率ディスクリプタと P/D 転送のオーバーヘッドが減る
—FP4 indexer を有効にしたときより小さい確保単位が使えるようになり、KV キャッシュのメモリを約 10% 節約
原文にはこのレイアウトを見るための対話ページがあります。DeepSeek V4 の KV キャッシュレイアウト で、断片化した 92 テンソルと packed layout の対比が見られます。
補足第 1 回の「正規レイアウト」と第 2 回の「hot バッファは通常のブロック」に続いて、ここでも同じ方針が出てきます。形を 1 つに揃えると、下流の全部が単純になる。92 個のテンソルは「モデルの構造をそのままメモリに写した」形で、素直ではありますが、転送 ・ オフロード ・ ディスクリプタという下流の仕組みが全部その複雑さを引き受けることになります。1 ブロック 1 確保に畳むと、下流は「ブロック」だけを知っていればよくなります。

5データ面 — 階層化と保持方策

GPU メモリの容量を超えて、しかもエンジンをまたいで prefix キャッシュを残すために、vLLM は Mooncake Store を分散 KV キャッシュプールとして統合しています。ここでは agentic 向けに足された機能が並びます。

項目内容
アーキテクチャの網羅KV オフロードは一級市民のまま。sparse attention ・ compressed attention ・ 線形 attention を含む新しいアーキテクチャを完全にサポートし、非同期スケジューリング ・ P/D 分離 ・ speculative decoding ・ 並列化も機能と性能を保つ
階層化分散 KV プールをディスクと CPU 専用ノードまで広げる。Mooncake Store の standalone-store モードで、外部の Mooncake クライアントが CPU プールとディスク階層を所有し、vLLM のワーカーは純粋な要求者になる。各ノードで standalone クライアントを立てれば、CPU メモリとディスクでプールを自由に拡張できる
router との統合Dynamo や llm-d と統合済み。どのインスタンスでもキャッシュヒットが得られるので、routing の方策が単純になる
性能最適化hybrid モデルはattention 型ごとにキーを作って別々に lookup するので CPU のオーバーヘッドが増える。より効率的なデータ構造 ・ 非同期 lookup ・ スケジューラのクリティカルパスから仕事を外す ・ 送受信の並列化で削減した

セッションを意識した prefix キャッシュの保持

ここが agentic 固有の工夫です。線形層や sliding window 層を full attention と併せ持つ hybrid モデルでは、prefix を再利用するために、再利用の境界で線形状態や sliding window のキャッシュを保存しておく必要があります。ところが全トークンでこのスナップショットを取るのは高すぎます。そこで 2 つの方策を組み合わせます。

方策いつ保存するか何を捕まえるか
interval-based retention各ターンのプロンプト末尾のキャッシュと線形状態を自動で保存する後続のターンと fork した subagent。これらは典型的に、以前のターンの文脈を再生して延長する
Marconi 風の選択的保持ある prefix が 2 回目に観測されたときにチェックポイントを残す。保持済みチェックポイントの無い既知の prefix に出会ったら、足りない状態を再計算してその境界で保存する共有される prefix はターンの内側で終わることが多いので、interval 方式では捕まらない再利用

この 2 つで、大規模な agentic ワークロードで、過大なストレージを使わずに高いヒット率を保ちます。

補足2 つ目の方策が面白いのは、「1 回目は諦める」という判断です。全境界で保存すればヒット率は最大になりますが、コストが爆発します。2 回目に観測されたものだけを保存するのは、再利用の有無をデータに答えさせる形です。しかも 2 回目の時点では再計算が必要で、そのコストを払ってでもチェックポイントを作る価値がある、という判断が入っています。「使われるかどうか分からないものを保存しない」という規律で、キャッシュ設計として一般に応用できる形です。

6実行面 — 並列化はモデルに従う

並列化の軸は複数あります (TP ・ DP ・ EP ・ PP ・ CP)。原文の主張はこうです。最適な並列化はモデルのアーキテクチャ、ハードウェアのトポロジ、ワークロードのパターン、レイテンシ SLO によって決まる。代表的な 2 モデルで具体例が示されます。

Kimi K3 — MLA には DCP が効く

Kimi K3 は MLA (multi-head latent attention) と KDA (Kimi Delta Attention) を持ちます。MLA は KV を 1 つのヘッドの潜在空間に圧縮するので、素の TP はその潜在キャッシュを全 rank に複製してしまい効率が悪い。代わりに効くのが DCP (decode context parallelism) で、キャッシュを系列方向に分割し、各 rank が KV 状態の 1/N を持ちます。

DCP の利点理由
decode レイテンシが下がるMLA の attention は memory-bound で、コストが文脈長とともに伸びます。agentic な prefix が伸びるほど attention が decode ステップの中で占める割合が大きくなるので、それを rank 間で分割するとステップが短くなる
スループットと KV 容量が上がるKV の複製を避けられるので、KV の受け入れで詰まらずにより多くの系列を同時に走らせられる

図 6: Kimi K3 では DCP8 が TP8 より低い decode レイテンシを達成し、より高い同時実行数までスケールする。
図の出典: vLLM x AgentX (vLLM 公式ブログ)

DCP の代償と、その削り方

DCP の代償は通信の増加です。KV が系列で分割されるので、MLA の decode 層ごとに、attention の前に query の gather、後に部分出力の reduction が必要になります。原文はここを踏み込んで削っています。

やったこと効果
NCCL の操作を迂回する。peer GPU が直接 load/store できる symmetric-memory バッファを使う。query は attention カーネルが消費するバッファへ直接 multicast し、各 GPU は部分出力と LSE 統計をpeer の受信スロットへ直接書き込み、各 rank が online softmax でローカルに統合するこれらの GPU 間書き込みを計算と同じカーネルに融合し、既定の DCP8 実装に比べて1 層あたり約 13% のレイテンシ削減

図 7: symmetric memory を使った DCP4 での MLA decode 経路。各ステップが 1 つのカーネルに融合され、既定の NCCL all-gather ・ staging コピー ・ all-to-all ・ unpack の各段を置き換えている。
図の出典: vLLM x AgentX (vLLM 公式ブログ)

scale-up ドメインが広いと答えが変わる

NVL72 級のシステムでは、データ並列を伴う広い EP (DEP) が DCP より良くスケールし、同じ decode レイテンシ SLO でより高いスループットを出せます。理由は明快で、マルチノードの大きな DCP では、分割した attention の通信コストが、節約した計算を上回るからです。DEP はリクエストとその KV を異なるデータ並列 rank に割り当てるので、DCP の attention collective を回避しつつ MoE の expert を rank 間で分割します。

図 8: Kimi K3 では、rank あたりのバッチサイズが 3 を超えると DEP16 が DCP8 より良くスケールする。
図の出典: vLLM x AgentX (vLLM 公式ブログ)

DeepSeek V4 — TP が効かない 3 つの理由

DeepSeek V4 も MLA 型の KV を持つので TP では複製されます。加えてcompressed sparse attention のせいで、TP のヘッド分割が計算として非効率になります。原文の 3 つの理由をそのまま押さえます。

理由中身
compressorcompressor 経路は圧縮された位置ごとに 1 つの共有 KV 表現しか作らず、ヘッドごとの独立な状態を作らない。だから TP は KV ヘッド方向に計算を分割できず、全 rank が compressor の仕事を繰り返します
indexerindexer は 64 ヘッドを持つが、トークンごとに 1 つの大域的な top-k 選択しか作らない。現在の TP 経路は全 rank に indexer 全体を複製するので、top-k の前の密なスコア reduction は避けられるが仕事は重複します
sparse MLAsparse MLA を支配しているのはattention の算術ではなく、top-k の KV エントリの走査と gather。TP はこの memory-bound な仕事の多くを全 rank で繰り返し、分割されるのは安いヘッド方向の計算だけ

補足この節の教訓を 1 行にすると「並列化はモデルの構造に従う」で、原文自身が 12 節でそう書いています。同じ MLA 系でも、K3 では DCP が勝ち、V4 では DEP が勝つ。違いを作っているのは「分割したい仕事が本当に分割できる形をしているか」です。K3 の MLA は系列方向に素直に切れるのに、V4 は compressor と indexer が系列やヘッドで切れない共有物を作るので、切っても全員が同じ仕事を繰り返します。並列化の設計は、モデルのどの軸が独立かを先に見つける作業だと読めます。

7【デモ】head-of-line blocking を解く

agentic なトラフィックは2 種類のリクエストが混ざります。長い prefix を再利用して短い prefill だけを足す頻繁な append 型と、数万トークンにわたるたまに来る新規の長い prefill です。ここから 2 つのスケジューリング問題が出ます。

1 つ目。vLLM の chunked-prefill スケジューラは既定で FIFO なので、1 本の長い prefill がトークン予算を毎ステップ丸ごと取り続け、同じ rank に並んだ短いターンはその prefill が終わるまで 1 度もスケジュールされません。これが head-of-line blocking です。

図 9: prefill キューでの head-of-line blocking (1 rank のキューのセッション表示)。左: chunk の上限が無いと、長い prefill が予算を丸ごと取り、キャッシュ済みの短いターンが待たされる。右: 512 トークンの上限があると、短いターンが毎ステップ加われて、より早く decode を始められる。
図の出典: vLLM x AgentX (vLLM 公式ブログ)

対処は 1 つのスケジューリング方策です。--long-prefill-token-threshold で、1 リクエストが 1 ステップに積めるトークン数に上限をかけます。512 トークンにすると、長い prefill が同じバッチに短いターンの席を残します。

効果は大きい。B300 上の DeepSeek V4 Pro で、1 GPU 秒あたりの総トークン数 (TPGS) が最大 93% 増え、P90 の interactivity が約 2.3 倍になります。代償はその長いリクエスト自身の TTFT が伸びることで、TTFT に敏感な配備では上限を大きくすべきだと原文は書いています。

下のデモは、この方策を 1 ステップずつ進めるものです。上限をかけると、短いターンがいつ decode を始められるかを見てください。

このデモはトークン予算の算術による模式です。1 ステップの予算 ・ 上限 ・ リクエストの長さは操作できますが、実際のステップ時間 ・ カーネルの挙動 ・ decode の速度は入っていません。示しているのは「上限をかけると短いターンが何ステップ目に decode を始められるか」という順序の構造だけです。+93% や 2.3 倍という数値は原文の実測で、このデモから出るものではありません。

8【デモ】DEP の prefill を揃える

2 つ目のスケジューリング問題は DEP 固有です。MoE の all-to-all 通信は rank を歩調を揃えて進ませる (lockstep) ので、prefill の仕事を処理している rank がグループ全体を遅くします。しかも prefill が rank ごとに違うステップで到着すると、この罰が繰り返し払われます。

対処は --prefill-schedule-interval で、N ステップごとにだけ prefill を受け入れるようにします。カウンタはデータ並列 rank の間で揃えられています。これでprefill の仕事が rank をまたいで同じステップに集まり、残りのステップはまるごと decode に使える割合が増えます。

図 10: DEP8 グループでの prefill スケジュールの周期。左: prefill が別々のステップに到着し、lockstep のグループを繰り返し止める。右: 間隔を 4 にすると、prefill が周期のステップに集まり、その間のステップは decode だけになる。
図の出典: vLLM x AgentX (vLLM 公式ブログ)

DEP の rank 数 8
prefill の間隔 (1 = 制御なし) 4
prefill の到着頻度 20%
prefill を含むステップ (グループ全体が遅くなる) decode だけのステップ

このデモは到着の模式です。prefill の到着をランダムに生成し、間隔の制御があるときは次の周期ステップまで待たせるという規則だけを実装しています。ステップ時間の差 ・ all-to-all の実際のコスト ・ 待たせたことによる TTFT の増加は入っていません。数えているのは「decode だけのステップが全体の何割になるか」だけです。原文はこの方策の効果を数値で示していないので、ここでも数値の主張はしていません。
補足この 2 つの方策 (7 節と 8 節) は逆方向を向いていることに注意すると理解が深まります。7 節は長い prefill を細かく刻んで、他の仕事に席を譲らせる。8 節はprefill をまとめて同じステップに集める。前者はインスタンスの内側で混ぜるための操作、後者は rank をまたいで揃えるための操作です。「混ぜる」と「揃える」が同時に成立するのは、粒度が違うからです。1 ステップの中では混ぜ、ステップの並びとしては揃える。この 2 段の見方が、この節の設計の要点です。

9制御面 — P/D の rate matching

原文の言い方が厳しくて良いところです。1 つのエンジンを最適化するだけでは、分散配備の最良のレイテンシ-コスト点は見つからない。GPU を増やしても、分離しても、自動的にフロンティアは改善しない。prefill と decode の処理速度が釣り合っている (rate-matched) 必要があります。

段やること出てくるもの
第 1 段: 飽和プロファイリングprefill だけ / decode だけの配備を別々にベンチマークし、並列化の戦略 (TP か広い EP か) と配備の規模 (8 / 16 / 32 GPU) を掃引しながら、スループットが飽和するまで同時実行数を上げる飽和表: (並列化, 規模) の各構成での最大 prefill / decode req/s
第 2 段: P/D 掃引各構成の第 1 段の飽和点から P/D 比を導出し、組み合わせた分離配備で同時実行数を掃引して動作範囲全体の指標を集める実際の運用点の候補

そして原文はこの手順を「エージェント的なワークフローで自動化できる標準化された 2 段階の方法」だと書いています。

補足この手順の要点は「比率を先に決めない」ことです。P/D 比を勘で決めて掃引すると、探索空間が (比率 × 同時実行数 × 並列化 × 規模) に膨らみます。先に prefill と decode を別々に飽和させておけば、比率は割り算で出ます。しかも原文は「最適な P/D 比は同時実行数によって動く」と 3 節で述べているので、1 点で決めた比率が別の負荷で最適とは限りません。第 2 段で同時実行数を掃引するのは、その動きを表として持っておくためです。

12効かなかった 3 つ

原文の中でいちばん価値のある節です。「失敗した考えはすべて探索空間を狭める」という書き出しで、もっともらしい直感が end-to-end の測定を生き延びなかったケースが 3 つ並びます。

1. パイプライン並列 (PP) は暖まったターンに合わない

効く場合効かない場合
長くて新規のプロンプト。大きな prefill がパイプラインの各段を埋めるだけの仕事を供給するので、通信コストが小さくスループットがほぼ線形にスケールするagentic なターンの大半。system プロンプトと過去のターンは既にキャッシュされていて、新しいリクエストが足すのは数百から数千トークンだけ。パイプラインを効率よく埋めるだけの新規計算が無く、バブルが利得の多くを食う

原文の結論の書き方が丁寧です。「PP が効かないという教訓ではない。冷たく計算の重い prefill には効く。ただし agentic セッションを支配する、暖かく prefix の多いターンでは既定にすべきではない。」

2. DCP は DeepSeek V4 へ素直に移らない

DCP は純粋な MLA のモデル (DeepSeek R1 ・ Kimi K2.5 ・ K2.7) とhybrid MLA のモデル (Kimi K3) では効きます。ところが DeepSeek V4 で同じ利得を実現するのはずっと難しい。理由は attention スタックの複雑さで、compressed sparse attention と highly compressed attention には indexer ・ 追加の compressor ・ 主 attention が含まれ、context parallelism はこれら全部の副層を分割して調整しなければなりません。

そして結果が正直です。通信と計算の重ね合わせに大きく投資し、対応するカーネルも最適化したうえで、DCP は DEP を超えるのではなく、ようやく並んだ。原文の結論は「並列化はモデルのアーキテクチャに従わなければならない。ある潜在 attention モデルで成功した戦略が、別のモデルに一般化するとは限らない」です。

3. 負荷分散は性能を保証しない

集約された DEP 配備で、rank 間の KV キャッシュ使用量に大きな偏りが観測されました。自然な対応は、キューの深さ ・ 実行中のトークン数 ・ 現在の KV 使用率でリクエストを分散させることです。ところが AgentX での実験では、これらの方策はすべて、単純なセッション固定の routing に負けました。

なぜ負けたのか中身
キャッシュの局所性agentic セッションはターン間の間隔が短いものが多く、次のターンは prefix がまだ前の GPU に常駐しているうちに次のターンが来る
移動のコストは 0 ではないセッションを空いている rank に移すと、prefix が分散 KV プールに保存されていても、KV キャッシュを取り直すことになります。転送は非同期で計算と重なるが無料ではない
容量を食うprefetch されたブロックは一時的に GPU の KV 容量を占め、行き先の rank が受け入れられる系列数を減らします
結論。「システムはより均衡したキューを達成しながら、より少ない同時リクエストしか処理しないことになりうる。ターン間の間隔が短いワークロードでは、瞬間的な負荷を完璧に均衡させることより、セッションの局所性を保つことの方が価値がある。routing の判断は、キューにある仕事の量だけでなく、各ワーカーに既に常駐している状態を考慮しなければならない。」
補足3 つの失敗は同じ形をしています。「一般に良いとされる手法を、このワークロードの形を見ずに適用した」。PP は仕事が十分にあることを前提にし、DCP は分割できる軸があることを前提にし、負荷分散はリクエストが状態を持たないことを前提にしています。agentic なトラフィックは 1 節の 4 つの統計のとおり、仕事が少なく (append が短い) ・ 軸が単純でなく (compressor が共有) ・ 状態を持つ (prefix が特定の GPU にある)。前提が全部外れているので、3 つとも外れたという読み方ができます。

13これから

次の一手は「agentic な構造をスタック全体で明示的にする」ことだと原文は書いています。各層の例が挙げられています。

層やろうとしていること
制御面1 ターン目のリクエスト (prefix キャッシュを埋めるための長い新規 prefill が必要) と 2 ターン目以降 (高いキャッシュ再利用と比較的短い append prefill) で routing を明示的に分ける。head-of-line blocking を避けられ、両側でエンジンの構成と並列化を別々にできる (たとえば PCP と CPP を使い分ける)
実行面 ・ データ面: agent hintsagentic なフレームワークやハーネスが、リクエストと一緒にヒントを運ぶ。セッションの構造 ・ 分岐しうる点とキャッシュの位置 ・ ツール呼び出しのレイテンシ ・ セッションのライフサイクル。まず標準化された API でこれを受け取り、次にスケジューリングやキャッシュの追い出し方策に使う
programmable KV cache配置 ・ 保持 ・ 複製 ・ 追い出しの方策はワークロードごとに違う。prefetch ・ eviction ・ soft-pinning をユーザーが制御できるインターフェース
session-based KV cache managementターン間の空き時間を使って、次のターンを処理しそうなワーカーへ保持した KV 状態を先に移しておく。転送レイテンシを隠し、冷たい再開を減らす
補足この 4 つは全部「エンジンが知らない情報を、外から渡す」方向を向いています。12 節の 3 つ目の失敗と対になっていて、routing がデータ面の状態を知らないと判断を間違えるのなら、解は 2 つあります。知らせるか、判断する場所を移すか。agent hints と programmable KV cache は前者 (アプリの知識をエンジンへ)、session-based な管理は後者 (エンジンが先に動いて状態を寄せる) です。どちらも「暗黙の構造を明示にする」という同じ方針です。

論点読み方

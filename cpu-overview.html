BUILD A CPU ・ 第 01 回

Beginner

CPU とは何をする機械か ― 命令を繰り返し回す装置

CPU は「次にやることを 1 つ読み、やって、また次を読む」を 1 秒間に数十億回繰り返すだけの機械。この回ではその繰り返しの輪と、輪を回す部品の地図を描く

← CPU 自作シリーズ 目次へ

この回の前提: 不要 (このシリーズの第 1 回)

CPU (Central Processing Unit, 中央処理装置) がしていることは、驚くほど単純です。メモリに並んだ「命令」を 1 つずつ読み、その命令が何を表しているかを解読し、実行し、結果をしまう。これを最初の命令から最後の命令まで、電源が入っている限り延々と繰り返すだけです。この回では、この繰り返しの輪 (サイクル) がどんな部品でできているかを地図として描き、この先 23 回でその地図のどの部分を詳しく見ていくかを示します。題材には、実際に 1 人の開発者が公開している 16 ビットの自作 CPU 「rj32」と、それを設計するための無料の回路シミュレータ「Digital」を使います。

1. 命令を回す輪 ― fetch ・ decode ・ execute ・ writeback

結論を先に言うと、CPU がしていることはこの 4 ステップの繰り返しだけです。命令を読む (fetch) → その命令が何をする命令かを解読する (decode) → 実際に計算や判断を行う (execute) → 結果をレジスタやメモリにしまう (writeback)。この 1 周りを 1 命令ぶんの仕事として、プログラムの最後まで延々と繰り返します。

図: CPU の仕事は fetch → decode → execute → writeback の輪を 1 命令ずつ回すこと。輪が 1 周したら次の命令に進む。

プログラムとは、この輪に流し込む「次に何をするか」の指示をメモリに順番に並べたものです。CPU 自身は何をすべきか最初から知っているわけではなく、毎回この輪を回してメモリから読んだ値 (命令) に従って動くだけです。これが「ノイマン型」と呼ばれる、プログラムをデータと同じようにメモリに置いて実行するという考え方の出発点です。

2. プログラムカウンタ ― 「次はどこを読むか」の覚え方

輪を回すには「次に読む命令がメモリのどこにあるか」を覚えておく場所が必要です。この役目を持つレジスタ (小さな記憶場所) をプログラムカウンタ (Program Counter, PC) と呼びます。fetch のたびに CPU は PC が指すアドレスから命令を読み、次に備えて PC を次の命令の位置へ進めます。rj32 でも、architecture 図の一番上に置かれた `PC` がこの役目を担っています。

図: PC はクロックが進むたびに次の命令の番地を指す。足し算や代入は PC を 1 つ進めるだけだが、jump 命令は PC を指定した番地に書き換える。

ほとんどの命令では、fetch が終わった時点で PC は単純に 1 つ先へ進みます。しかし jump のような命令は、writeback の段階で PC そのものを書き換えます。つまり PC は「普段は自動で 1 ずつ増える、必要なときだけ命令が直接書き換えられる特別なレジスタ」です。ループや条件分岐は、この PC の書き換えルールだけで実現されています。

3. 部品の地図 ― rj32 全体図

輪を回す 4 ステップを、実際の部品に当てはめたのが次の図です。これは rj32 の公開されている構成図を、部品の名前と配線をそのまま保って描き直したものです。

図: rj32 の部品地図。プログラムメモリとデータメモリが分かれている (ハーバード型) こと、Registers と ALU の間を複数のバスで結んでいることが特徴。この図の各部品は第 09 回 (メモリ) ・第 08 回 (レジスタファイル) ・第 07 回 (ALU) ・第 11 回 (デコーダ) で 1 つずつ詳しく扱う。

この図からすでに分かることが 2 つあります。1 つはプログラムメモリとデータメモリが別の箱になっていることです。これは命令とデータを別の記憶に置く「ハーバード型」という設計 (詳しくは第 09 回) で、rj32 はこちらを選んでいます。もう 1 つは、レジスタファイルと ALU を結ぶ配線が複数本の「バス」であることです。1 本の線で全部をやり取りするのではなく、読み出し用・書き込み用の線を分けることで、1 クロックの中で複数のレジスタに同時にアクセスできるようにしています (詳しくは第 06 回)。

最後に、同じ地図の上で 1 命令が実際にどの線を通るかを追ってみます。add r3, r1 (r3 に r1 を足す) という命令は、Registers から 2 つの値を読み出し、ALU で足し算をし、結果をまた Registers に書き戻すだけなので、Data Memory には触れません。

図: 同じ地図でも、命令の種類によって実際に使う部品は変わる。add 命令は Program Memory からの fetch を除けば Registers と ALU だけで完結し、Data Memory は素通りする。

4. Digital というシミュレータでできること

この地図の部品 1 つひとつは、いきなり基板に半田付けするのではなく、Digital という無料の回路シミュレータの上で組み、動作を確かめてから少しずつ育てていきます。Digital には編集モードとシミュレーションモードの 2 つの状態があり、再生ボタンを押すとシミュレーションが始まり、配線の色でその瞬間の 0 と 1 の値が分かるようになります。

図: Digital では配線 → シミュレーション → テストケースによる自動検査 → (必要なら) Verilog/VHDL への書き出しという順で設計を進める。第 20 回で FPGA への書き出しを扱う。

Digital のもう 1 つの柱が階層設計です。半加算器のような小さな回路を 1 つのファイルに保存すると、それを「部品」として別の回路ファイルの中で何度も再利用できます。rj32 の `rj32.dig` という最上位ファイルも、内部では `fetch.dig` や `execute.dig` といった小さな回路ファイルを部品として呼び出す形で組まれています。大きな回路を一枚の絵に全部描くのではなく、意味のある単位で箱に分けて名前を付けることが、後から読み返せる設計の土台になります。

5. 実装のポイント ― 最初に何から作るか

自分で CPU を作り始めるとき、最初から 32 個の命令を一気に実装しようとするのが最もよくある失敗です。rj32 の `intro/` フォルダを見ると、実際の進め方は「スイッチ 1 個の動作確認」→「トランジスタで NOT/NAND を作る」→「論理ゲートを組み合わせる」→「組み合わせ回路」→「順序回路」→「バス」という非常に小さな単位の積み上げになっています。この回で見た fetch ・ decode ・ execute ・ writeback の輪も、最初は nop (何もしない命令) だけを繰り返し読んで PC が正しく進むことを確認する、という最小の回路から始めるのが安全です。

図: Digital の公式マニュアルに載っている半加算器 → 全加算器 → 4 ビット加算器という組み立て順。CPU 全体もこの考え方の延長で、小さな .dig ファイルを部品として積み上げて作る。

もう 1 つの実装上の注意は、Digital が部品 (サブ回路) をファイル名だけで探す、という点です。回路ファイルが他の .dig ファイルを読み込むとき、保存されているのはファイル名だけで、フォルダの位置は保存されません。シミュレータは実行時にサブフォルダを全部探してそのファイル名を見つけますが、同じ名前のファイルが別の場所に 2 つあると、どちらを使うか決められずエラーになります。部品を増やしていく自作 CPU では、ファイル名の衝突を避けることが地味だが重要な設計ルールです。

EAV ― 属性名を行に持たせる

行ごとに違う属性を持たせたくて「属性名」と「属性値」だけの表に全部を流し込むと、型・必須・外部キーというデータベースが本来守ってくれるものを、自分の手で手放すことになります

← SQL シリーズ目次へ

この回の前提: 第 05 回 キーレスエントリ(外部キーがデータベースに何を守らせているか)

「商品ごとに持たせたい項目が違う」「将来どんな属性が増えるか分からない」という要望に対して、attr_name と attr_value という 2 列だけの表を作り、行を増やすだけで属性を増やせるようにする設計を EAV (Entity-Attribute-Value, 実体 ・ 属性 ・ 値) と呼びます。結論を先に言うと、これは ALTER TABLE を避けられる代わりに、型チェック、NOT NULL、外部キーというデータベースが無料で提供してくれる保証を全部手放し、1 件のデータを読むたびに自分でピボット(行を列に組み替える処理)を書く設計です。この回では、実際に EAV の表を作って何が壊れるかを確かめ、PostgreSQL で本当に属性が可変なときにどう書くべきかを見ます。

1. 目的 ― 何をしたかったのか

バグ管理システムに、バグの種類ごとに違う付加情報を持たせたいとします。クラッシュ系のバグにはスタックトレースが欲しく、UI 系のバグにはOS とブラウザが欲しい、というように、バグの種類が増えるたびに必要な項目が増えていきます。素直に bugs テーブルに列を追加していくと、新しい種類のバグが出るたびに ALTER TABLE が必要になり、ほとんどの行でその列が NULL のまま、という列がどんどん増えていきます。

「それなら列を増やすのをやめて、属性そのものを行として持てばいい」という発想から生まれるのが EAV です。bug_id(実体, Entity)、attr_name(属性名, Attribute)、attr_value(値, Value)の 3 列だけの表を 1 つ作れば、新しい属性はテーブル定義を変えずに行を INSERT するだけで増やせます。目的そのものは正当で、「属性の種類を事前に決め切れない」という状況は実務でよくあります。問題は、この目的を 3 列の表という形で実現してしまう点にあります。

2. アンチパターン ― どう書いてしまい、何が壊れるか

実際に EAV のテーブルを作って、サンプルのバグ管理データベースに属性を足してみます。

CREATE TABLE bug_attributes (
  bug_id     bigint NOT NULL REFERENCES bugs (bug_id) ON DELETE CASCADE,
  attr_name  text NOT NULL,
  attr_value text,
  PRIMARY KEY (bug_id, attr_name)
);

INSERT INTO bug_attributes (bug_id, attr_name, attr_value) VALUES
  (1, 'os',             'macOS 15'),
  (1, 'browser',        'Safari 18'),
  (1, 'severity_score', '8'),
  (2, 'os',             'Windows 11'),
  (2, 'severity_score', '3'),
  (4, 'os',             'Ubuntu 24.04'),
  (4, 'severity_score', 'high');

これだけ見ると自然な設計に見えますが、実際に使っていくと次の 5 つの問題が同時に出てきます。

図: 通常のテーブルは 1 件を 1 行で表すが、EAV は 1 件を属性の数だけの行に分けて表す。

2.1 型が守られない

attr_value はすべて text 列です。そのため「severity_score は数値のはず」という前提は、データベースのどこにも書かれていません。実際に 4 件目は数値ではなく文字列 'high' を入れてしまいましたが、挿入は何の警告もなくそのまま成功します。

SELECT bug_id, attr_name, attr_value FROM bug_attributes WHERE attr_name = 'severity_score' ORDER BY bug_id;

 bug_id |   attr_name    | attr_value
--------+----------------+------------
      1 | severity_score | 8
      2 | severity_score | 3
      4 | severity_score | high
(3 rows)

この状態で sum(attr_value::numeric) のように集計しようとすると、3 件目まで正しく変換できても 4 件目の 'high' でエラーになります。列が numeric であれば、この種の値はそもそも挿入の時点で拒否されます。

SELECT sum(attr_value::numeric) FROM bug_attributes WHERE attr_name = 'severity_score';

ERROR:  invalid input syntax for type numeric: "high"

2.2 列名の表記ゆれをデータベースが防げない

attr_name はただの文字列なので、タイプミスをデータベースは検出できません。severity_score を serverity_score と打ち間違えて挿入してみます。

INSERT INTO bug_attributes (bug_id, attr_name, attr_value) VALUES (2, 'serverity_score', '5');

SELECT bug_id, attr_name, attr_value FROM bug_attributes WHERE bug_id = 2 ORDER BY attr_name;

 bug_id |    attr_name    | attr_value
--------+-----------------+------------
      2 | os              | Windows 11
      2 | serverity_score | 5
      2 | severity_score  | 3
(3 rows)

通常の列であれば、存在しない列名を INSERT 文に書いた瞬間に column "serverity_score" of relation "bugs" does not exist のようなエラーで止まります。EAV では属性名が値の一部なので、このタイプミスは新しい属性として素直に保存され、bug_id=2 には「severity_score」が 2 つの違う名前で存在する状態になってしまいます。

2. アンチパターン (続き)

2.3 必須の属性を強制できない

「crash タイプのバグには必ず severity_score が無ければならない」のような必須条件は、通常なら列に NOT NULL を付けるだけで守れます。EAV では属性が行なので、「ある行が存在しないこと」を検出するには、持っているはずの全バグに対して LEFT JOIN を書き、一致しない行を探すしかありません。

SELECT b.bug_id, b.summary
FROM bugs b
LEFT JOIN bug_attributes a ON a.bug_id = b.bug_id AND a.attr_name = 'os'
WHERE a.bug_id IS NULL
ORDER BY b.bug_id;

 bug_id |           summary
--------+-----------------------------
      3 | button label typo
      5 | login fails with long email
(2 rows)

この問い合わせ自体は動きますが、これは「挿入時に守られる制約」ではなく「後から気づくための検出クエリ」です。bug_id=3 と 5 に os が無いことは、誰かがこのクエリを実行するまでデータベースの中では何の矛盾にもなりません。

2.4 外部キーが張れない

EAV の最大の構造的な問題はここです。attr_value は 1 つの text 列ですが、その値が何を参照すべきかは attr_name によって変わります。たとえば attr_name='verified_by' のときは accounts.account_id を参照すべきですが、別の行で attr_name='related_product' なら products.product_id を参照すべきです。1 つの列に対して「状況によって参照先が変わる外部キー」は PostgreSQL の REFERENCES では宣言できません。

INSERT INTO bug_attributes (bug_id, attr_name, attr_value) VALUES (1, 'verified_by', '999');

SELECT ba.bug_id, ba.attr_name, ba.attr_value, a.account_name
FROM bug_attributes ba
LEFT JOIN accounts a ON a.account_id = ba.attr_value::bigint
WHERE ba.attr_name = 'verified_by';

 bug_id |  attr_name  | attr_value | account_name
--------+-------------+------------+--------------
      1 | verified_by | 999        |
(1 row)

account_id=999 のアカウントは存在しないため、JOIN の結果は account_name が空になります。しかし bug_attributes への INSERT 自体はエラーにならず成功しています。これは、挿入の時点で参照整合性を守る外部キーが、この列には原理的に張れないことを意味します。

図: attr_value は 1 本の text 列なので、行ごとに違う参照先 (accounts / products) を持たせることができず、PostgreSQL の外部キーが張れない。

2.5 1 行を再構築するのにピボットが要る

通常のテーブルなら「1 件のバグの情報」は 1 行の SELECT で取れます。EAV では 1 件のバグの情報が複数行に分かれているため、属性ごとに列へ組み替えるピボットが必要です。PostgreSQL では FILTER 句を使った条件付き集約でこれを書けます。

SELECT bug_id,
  MAX(attr_value) FILTER (WHERE attr_name = 'os')             AS os,
  MAX(attr_value) FILTER (WHERE attr_name = 'browser')        AS browser,
  MAX(attr_value) FILTER (WHERE attr_name = 'severity_score') AS severity_score
FROM bug_attributes
GROUP BY bug_id
ORDER BY bug_id;

 bug_id |      os      |  browser  | severity_score
--------+--------------+-----------+----------------
      1 | macOS 15     | Safari 18 | 8
      2 | Windows 11   |           | 3
      4 | Ubuntu 24.04 |           | high
(3 rows)

属性が 3 個ならまだ書けますが、属性が 20 個に増えれば FILTER 句も 20 個書く必要があり、新しい属性を増やすたびにこのクエリ自体を書き直すことになります。これは「テーブル定義を変えずに属性を増やせる」という EAV の売りを、「属性を増やすたびにすべての読み取りクエリを書き直す」という別の保守コストに付け替えているだけだと分かります。

実行計画を比べると、この小さなデータでは両方とも 1 ミリ秒未満で終わりますが、やっていることの複雑さは全く違います。通常のテーブルからの 1 行取得は主キーのインデックスを 1 回たどるだけで済みます。

EXPLAIN (ANALYZE, BUFFERS)
SELECT bug_id, summary, status FROM bugs WHERE bug_id = 1;

 Index Scan using bugs_pkey on bugs  (cost=0.15..8.17 rows=1 width=72) (actual time=0.002..0.003 rows=1.00 loops=1)
   Index Cond: (bug_id = 1)
   Index Searches: 1
   Buffers: shared hit=2
 Planning Time: 0.012 ms
 Execution Time: 0.005 ms

一方、EAV のピボットは bug_attributes を全件(この例では 9 行)読んでから bug_id ごとにグルーピングする必要があり、行数が増えるほどこの「全件読んでからまとめる」処理のコストが膨らんでいきます。

EXPLAIN (ANALYZE, BUFFERS)
SELECT bug_id,
  MAX(attr_value) FILTER (WHERE attr_name = 'os') AS os
FROM bug_attributes GROUP BY bug_id;

 HashAggregate  (cost=32.28..34.28 rows=200 width=104) (actual time=0.011..0.012 rows=3.00 loops=1)
   Group Key: bug_id
   Batches: 1  Memory Usage: 32kB
   Buffers: shared hit=1
   ->  Seq Scan on bug_attributes  (cost=0.00..18.10 rows=810 width=72) (actual time=0.001..0.002 rows=9.00 loops=1)
         Buffers: shared hit=1
 Planning Time: 0.017 ms
 Execution Time: 0.015 ms

この回のデータは 9 行しかないため実測の差はまだ現れていませんが、属性の種類と行数が増えるほど、「1 行取得」と「全件走査してからグルーピング」の差は開いていきます。重要なのは速度そのものより、クエリの形そのものが属性の数に比例して複雑になっていく点です。

3. 見つけ方 ― どんな兆候で気づくか

既存のデータベースに EAV の匂いがあるテーブルが無いかは、information_schema.columns を見れば機械的に探せます。「列がちょうど 2 〜 3 本で、その名前が attr_name / attr_value / key / value / name のような汎用的な語である」というテーブルを拾い出します。

SELECT c.table_name, array_agg(c.column_name ORDER BY c.ordinal_position) AS columns
FROM information_schema.columns c
WHERE c.table_schema = 'public'
GROUP BY c.table_name
HAVING array_agg(lower(c.column_name)::text)
    && ARRAY['attr_name','attr_value','attribute','value','key','prop_name','prop_value']
ORDER BY c.table_name;

   table_name   |            columns
----------------+-------------------------------
 bug_attributes | {bug_id,attr_name,attr_value}
(1 row)

この問い合わせは PostgreSQL のメタデータを保持する information_schema.columns ビューを素直に使っています。列名の集合と、よくある EAV の語彙との重なり (&& 演算子) を見ているだけなので、どのテーブルがどの行にあるかを事前に知らなくても機械的に検出できます。実務では、これに「列数がちょうど 3 〜 4 本」という条件を足すと、意図的に名前が違う EAV テーブルも見つけやすくなります。

もう 1 つの兆候は、アプリケーションのコードの中に「属性名の文字列リスト」に対して FILTER や CASE WHEN を書いたピボット処理が散らばっていることです。新しい属性を 1 つ増やすために、テーブル定義ではなくアプリケーションコードの複数箇所を直す必要があるなら、それは EAV が後ろにある兆候です。

4. 使ってよい場合

「属性の集合を設計時点で決め切れない」という要望自体は正当です。たとえば、外部のプラグインが独自のカスタム項目を追加できるシステムでは、どんな属性名が来るかをデータベースの設計者が事前に列挙できません。このような、本当に形が事前に決まらず、属性ごとに読み書きの単位が疎(1 件のエンティティに対して数個の属性しか無いことが多い)なケースは、3 列の EAV テーブルが検討の出発点になり得ます。

ただし PostgreSQL では、この正当な要望に対する答えはほぼ常に「3 列の EAV テーブル」ではなく、次の章で説明する jsonb 列です。jsonb は 1 件のエンティティを 1 行のまま保ちながら、属性の集合を自由に増減できるため、EAV が持つ「1 件を読むのに複数行をピボットする」という欠点を避けられます。したがって、実務で素の EAV テーブルを選ぶ理由は、PostgreSQL 以外の、jsonb のような半構造化型を持たないデータベースを前提にした古い設計を引き継いでいる場合がほとんどで、新規に PostgreSQL で設計するなら jsonb を先に検討すべきです。

5. 解決策 ― PostgreSQL での正しい書き方

「種類によって持つ属性が違う」という状況には、昔からある設計パターンが 4 つあります。どれも EAV のように行で属性を表すのではなく、型・必須・外部キーを保ったまま属性の違いを表現します。

5a. シングルテーブル継承 (Single Table Inheritance)

すべてのサブタイプを 1 つのテーブルにまとめ、種類を表す判別列 (discriminator, ここでは bug_type) と、どのサブタイプにも対応できるだけの NULL 許容列を持たせる方式です。

ALTER TABLE bugs ADD COLUMN bug_type text;
ALTER TABLE bugs ADD COLUMN stack_trace text;
ALTER TABLE bugs ADD COLUMN os text;
ALTER TABLE bugs ADD COLUMN browser text;

UPDATE bugs SET bug_type = 'crash', stack_trace = 'NullPointerException at Save.save()' WHERE bug_id = 1;
UPDATE bugs SET bug_type = 'ui' WHERE bug_id IN (2, 3, 5);
UPDATE bugs SET bug_type = 'crash', stack_trace = 'IndexOutOfRangeException at Search.run()' WHERE bug_id = 4;
UPDATE bugs SET os = 'macOS 15', browser = 'Safari 18' WHERE bug_id = 3;

ALTER TABLE bugs ADD CONSTRAINT crash_needs_stack_trace
  CHECK (bug_type <> 'crash' OR stack_trace IS NOT NULL);

SELECT bug_id, bug_type, stack_trace, os, browser FROM bugs ORDER BY bug_id;

 bug_id | bug_type |               stack_trace                |    os    |  browser
--------+----------+-------------------------------------------+----------+-----------
      1 | crash    | NullPointerException at Save.save()      |          |
      2 | ui       |                                           |          |
      3 | ui       |                                           | macOS 15 | Safari 18
      4 | crash    | IndexOutOfRangeException at Search.run() |          |
      5 | ui       |                                           |          |
(5 rows)

EAV では「crash なら stack_trace が必須」という条件を強制する手段がありませんでしたが、ここでは CHECK 制約で宣言でき、違反する行は挿入時にデータベースが拒否します。

INSERT INTO bugs (summary, reported_by, status, bug_type)
VALUES ('crash without trace', 1, 'NEW', 'crash');

ERROR:  new row for relation "bugs" violates check constraint "crash_needs_stack_trace"

欠点は、サブタイプの種類が増えるほど NULL だらけの列が増えていくことで、サブタイプの数が多い場合には向きません。

5b. 具象テーブル継承 (Concrete Table Inheritance)

共通の親テーブルを持たず、サブタイプごとに完全に独立したテーブルを作る方式です。

CREATE TABLE crash_bugs (
  bug_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  summary     text NOT NULL,
  reported_by bigint NOT NULL REFERENCES accounts (account_id),
  stack_trace text NOT NULL
);
CREATE TABLE ui_bugs (
  bug_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  summary     text NOT NULL,
  reported_by bigint NOT NULL REFERENCES accounts (account_id),
  os          text NOT NULL,
  browser     text NOT NULL
);
INSERT INTO crash_bugs (summary, reported_by, stack_trace)
  VALUES ('crash when saving', 1, 'NullPointerException at Save.save()');
INSERT INTO ui_bugs (summary, reported_by, os, browser)
  VALUES ('button label typo', 3, 'macOS 15', 'Safari 18');

SELECT bug_id, summary, 'crash' AS bug_type FROM crash_bugs
UNION ALL
SELECT bug_id, summary, 'ui' AS bug_type FROM ui_bugs
ORDER BY bug_type, bug_id;

 bug_id |      summary      | bug_type
--------+--------------------+----------
      1 | crash when saving | crash
      1 | button label typo | ui
(2 rows)

それぞれの列には NOT NULL を自然に書けるので、EAV の「必須を強制できない」問題は解決します。一方で、2 つのテーブルの bug_id はそれぞれ独立した identity 列なので、両方とも 1 から始まり値が重複します。「すべてのバグを一覧する」や「bug_id だけでどのバグか特定する」には UNION ALL と、どちらのテーブル由来かを示す追加の列が常に必要になります。

図: 具象テーブル継承はテーブルごとに連番が独立するため、同じ bug_id の値が別の行を指す。

5c. クラステーブル継承 (Class Table Inheritance)

共通部分だけを持つ親テーブルと、サブタイプごとの差分だけを持つ子テーブルを分け、子テーブルの主キーをそのまま親テーブルへの外部キーにする (1 対 1 の関係) 方式です。

CREATE TABLE bugs_cti (
  bug_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  summary     text NOT NULL,
  reported_by bigint NOT NULL REFERENCES accounts (account_id),
  bug_type    text NOT NULL CHECK (bug_type IN ('crash', 'ui'))
);
CREATE TABLE bug_crash_details (
  bug_id      bigint PRIMARY KEY REFERENCES bugs_cti (bug_id) ON DELETE CASCADE,
  stack_trace text NOT NULL
);
CREATE TABLE bug_ui_details (
  bug_id  bigint PRIMARY KEY REFERENCES bugs_cti (bug_id) ON DELETE CASCADE,
  os      text NOT NULL,
  browser text NOT NULL
);

SELECT b.bug_id, b.summary, b.bug_type, c.stack_trace, u.os, u.browser
FROM bugs_cti b
LEFT JOIN bug_crash_details c ON c.bug_id = b.bug_id
LEFT JOIN bug_ui_details u ON u.bug_id = b.bug_id
ORDER BY b.bug_id;

 bug_id |      summary      | bug_type |             stack_trace             |    os    |  browser
--------+--------------------+----------+--------------------------------------+----------+-----------
      1 | crash when saving | crash    | NullPointerException at Save.save() |          |
      2 | button label typo | ui       |                                      | macOS 15 | Safari 18
(2 rows)

bug_id は親テーブル 1 つだけが発行するので、具象テーブル継承の「同じ番号が複数の意味を持つ」問題は起きません。また子テーブルの列には NOT NULL を書けるので、サブタイプごとの必須項目も守れます。欠点は、1 件のバグを取り出すのに親 + 子テーブルへの JOIN が常に要ることと、サブタイプが増えるたびに新しい子テーブルを作る必要があることです。

5d. 半構造化 (jsonb)

属性の集合が本当に事前に決め切れない場合、PostgreSQL では jsonb 列が最も素直な答えになります。1 件のエンティティは 1 行のまま保たれ、属性はその行の中の JSON ドキュメントとして持てます。

CREATE TABLE bugs_flex (
  bug_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  summary     text NOT NULL,
  reported_by bigint NOT NULL REFERENCES accounts (account_id),
  bug_type    text NOT NULL,
  details     jsonb NOT NULL DEFAULT '{}'::jsonb
);
INSERT INTO bugs_flex (summary, reported_by, bug_type, details) VALUES
  ('crash when saving', 1, 'crash', '{"stack_trace": "NullPointerException at Save.save()"}'),
  ('button label typo', 3, 'ui', '{"os": "macOS 15", "browser": "Safari 18"}');

SELECT bug_id, bug_type, details ->> 'stack_trace' AS stack_trace, details ->> 'os' AS os
FROM bugs_flex ORDER BY bug_id;

 bug_id | bug_type |             stack_trace             |    os
--------+----------+--------------------------------------+----------
      1 | crash    | NullPointerException at Save.save() |
      2 | ui       |                                      | macOS 15
(2 rows)

EAV と違い、1 件のバグの情報は常に 1 行として読めます。属性を増やすのに ALTER TABLE も不要で、属性名の表記ゆれも JSON のキー名としてそのまま残ります (EAV と同じ弱点が残る点は正直に書きますが、少なくとも 1 行の中に収まるため、ピボットは要りません)。

jsonb の中の値で検索したいときは GIN インデックスを使います。20 万行の合成データ (generate_series で生成、本物の計測) で確認します。

INSERT INTO bugs_flex (summary, reported_by, bug_type, details)
SELECT 'synthetic bug ' || g, 1, 'ui',
       jsonb_build_object('os', (ARRAY['macOS 15','Windows 11','Ubuntu 24.04'])[1 + (g % 3)],
                           'browser', (ARRAY['Safari 18','Chrome','Firefox'])[1 + (g % 3)])
FROM generate_series(1, 200000) AS g;
UPDATE bugs_flex SET details = details || '{"ticket_ref":"RARE-0001"}'::jsonb WHERE bug_id = 100;
ANALYZE bugs_flex;
-- 合計 200,002 行。インデックス無しで、20 万行中 1 行だけに一致する条件を検索する
EXPLAIN (ANALYZE, BUFFERS)
SELECT bug_id FROM bugs_flex WHERE details @> '{"ticket_ref":"RARE-0001"}';

6. PostgreSQL エンジンで考慮しておくこと ― INHERITS は使わない

PostgreSQL には古くからテーブル継承 (INHERITS) という機能があり、「親テーブルの列を引き継いだ子テーブルを作る」ことができます。これは EAV の代わりとして使いたくなりますが、実機で確かめると親の制約が子に及ばないことが分かります。

CREATE TABLE base_demo (id int PRIMARY KEY, name text);
CREATE TABLE child_demo (extra text) INHERITS (base_demo);
INSERT INTO base_demo VALUES (1, 'a');
INSERT INTO child_demo (id, name, extra) VALUES (1, 'dup', 'x');

SELECT tableoid::regclass AS from_table, id, name FROM base_demo*;

 from_table | id | name
------------+----+------
 base_demo  |  1 | a
 child_demo |  1 | dup
(2 rows)

base_demo.id には PRIMARY KEY を付けていますが、子テーブル child_demo に同じ id=1 を挿入してもエラーになりませんでした。PostgreSQL の公式ドキュメントはこれを継承機能の既知の制限として明記しています。

"A serious limitation of the inheritance feature is that indexes (including unique constraints) and foreign key constraints only apply to single tables, not to their inheritance children."
― PostgreSQL 18 Documentation, 5.11.1. Caveats

図: 親テーブルの PRIMARY KEY は子テーブルの行には適用されず、親子をまたいだ一意性は保証されない (実機で確認済み)。

さらに、現在の公式ドキュメントはテーブル分割の用途についても「組み込みの宣言的パーティショニング (PARTITION BY) が大半のケースに適しており、継承によるパーティショニングはより柔軟さが必要な特殊な場合の代替手段」という位置づけを明記しています。つまり INHERITS は、EAV の代わりとしても、テーブル分割の第一候補としても、現在の PostgreSQL では推奨されていません。属性の違いを表現したいなら 5 章の 4 パターン、行数を分割したいなら宣言的パーティショニング (第 09 回で扱います) を使うのが PostgreSQL 18 時点での素直な選択です。

分散ロック・リース・フェンシングトークン ― ロックを持っている確信は裏切られる

分散ロックは GC ポーズやネットワーク遅延で保持者の思い込みが崩れる。守るべきは資源側であり、単調増加するフェンシングトークンだけがその崩れを安全に検出できる。

結論から言うと、分散ロックは「自分がロックを持っている」というクライアント側の思い込みだけでは安全にならない。GC ポーズやネットワーク遅延はどれだけ続くか上限を仮定できないため、資源側がフェンシングトークンという単調増加する番号を検証する仕組みが要る。この回では Kleppmann の議論に沿って、その理由と実装(ZooKeeper ・ etcd)、実例(チケット予約のホールド)まで見る。

1. この回で解く問題 ― なぜ分散ロックが要るのか

結論から言うと、分散ロックは「複数のノードが同時に同じ資源を触ると壊れる」という状況で、同時に触っていいのは 1 ノードだけに制限するための仕組みである。1 台のマシンの中でのロック (mutex) と違い、分散ロックはロックを持つプロセス自体が死ぬ・固まる・ネットワークから切れるといった、ロックの管理者から見分けがつかない故障を相手にする必要がある。

ByteByteGo が挙げる分散ロックの代表的な使い道は 6 つある。リーダー選出 (ある時点でリーダーになれるノードを 1 台に絞る、第 25 回の Raft が解決する問題と同じ構造)、タスクスケジューリング (分散 cron で同じジョブを複数のワーカーが同時に実行しないようにする、第 30 回で扱う)、リソース割り当て (ファイルシステムやハードウェアデバイスなど共有資源への同時アクセス制御)、マイクロサービス間の協調 (複数のデータベースをまたぐ更新を順序立てて行う)、在庫管理 (同じ商品を複数の購入者が同時に買おうとしたときの在庫更新)、セッション管理 (1 人のユーザーのセッションを 1 台のサーバーだけが更新する) である。これらは全て「同時に 2 台が触ると数が合わなくなる、または矛盾した状態になる」という同じ形の問題を持つ。

図: リーダー選出・タスクスケジューリング・在庫管理など、用途は違っても「同時に 1 ノードだけ」が必要な点は共通している。

2. 「ロックを持っている」という思い込みが崩れる具体的シナリオ

分散ロックは 1 台のマシンの中の mutex とは違う。クライアントがロックを取得し、共有ストレージ (HDFS や S3 など) のファイルを読み、書き換えて、書き戻し、最後にロックを解放する ― という手続きを考える。ロックには期限 (リース) を付けるのが普通で、これはクラッシュしたクライアントがロックを永遠に持ち続けるのを防ぐためである。問題は、クライアントがロックを持ったまま長時間停止してしまい、その間にリースが期限切れになるケースである。

停止の原因は特殊なものではない。GC (ガベージコレクション) の「stop-the-world」停止は数分に及ぶことが知られており、これは十分にリースを失効させる長さである。HBase は実際にこの問題を抱えていたことが知られている。また、プロセスの停止でなくても、ネットワーク上でパケットが遅延するだけで同じことが起きる ― GitHub で実際に発生した障害では、パケットが約 90 秒ネットワーク上で遅延した。書き込みの直前にロックの期限をチェックしても解決にはならない。GC はスレッドをどの瞬間でも止めることができ、それは「チェックした直後、書き込む直前」という最悪のタイミングでも起こり得るからである。

class LockService:
    def __init__(self):
        self.token = 0

    def acquire(self):
        self.token += 1
        return self.token


class Storage:
    def __init__(self):
        self.value = None

    def write_without_fencing(self, data):
        self.value = data


lock_service = LockService()
storage = Storage()

token_for_client1 = lock_service.acquire()

token_for_client2 = lock_service.acquire()
storage.write_without_fencing("written by client2")

storage.write_without_fencing("written by client1 after a long GC pause")

print(storage.value)

このコードを実行すると、クライアント 1 が GC ポーズの後に書き込んだ値が最後に残り、クライアント 2 の更新を踏み潰してしまう。クライアント 1 は自分のリースが切れたことに気づかず、「自分だけがロックを持っている」という前提のまま書き込みを行う。これが分散ロックを「持っている」という確信そのものが裏切られる典型的なパターンである。

3. フェンシングトークン ― 資源側がロック保持者を信じない設計

Martin Kleppmann は、ロックを使う目的を 2 つに分けて考えるべきだと指摘する。効率のためのロックは、同じ仕事を 2 回やってしまうことを防ぐためのもので、失敗しても被害は「少し余計なコストがかかる」程度で済む。正しさのためのロックは、複数のプロセスが互いの作業を踏み潰してデータを壊すことを防ぐためのもので、失敗するとファイルの破損やデータの消失といった深刻な被害につながる。この 2 つを区別しないまま「ロックをかけたから安全」と思い込むのが最初の罠である。

正しさのためにロックを使う場合、修正は単純である。資源への書き込み要求ごとに、フェンシングトークンという番号を含める。この番号は、ロックサービスがクライアントにロック (リース) を与えるたびに増える番号である。クライアント 1 がロックを取得してトークン 33 を受け取り、長いポーズに入ってリースが失効する。クライアント 2 がロックを取得してトークン 34 を受け取り、ストレージサービスへの書き込みにトークン 34 を添える。その後クライアント 1 が復帰してトークン 33 付きの書き込みを送るが、ストレージサービスは既にトークン 34 を見た後なので、33 という古いトークンの書き込みを拒否する。鍵は、ストレージサービス側が「自分が見た最大のトークンより小さいトークンの書き込みは拒否する」という能動的な役割を持つことである。

図: トークンは単調増加し、ストレージ側が自分の見た最大トークンより古い書き込みを拒否する。これで GC ポーズ後の書き込みも安全に弾ける。

ZooKeeper をロックサービスに使う場合は、zxid (トランザクション ID) や znode のバージョン番号をそのままフェンシングトークンとして使える。重要なのは、この仕組みはロックサービスだけでは実現できず、資源 (ストレージ) 側がトークンを検証する役割を引き受ける必要があるという点である。

4. リースと時計 ― Redlock をめぐる論争

リース (lease) は期限付きのロックで、TTL (有効期限) を過ぎると自動的に失効する。これはクラッシュしたクライアントがロックを永遠に持ち続ける事態を防ぐための、妥当な設計判断である。しかし、TTL は物理的な時間で測られる点に注意が要る。ロックサーバーとクライアントはそれぞれ自分の時計で時間の経過を測っており、サーバーが「もう失効した」と判断していても、クライアントはまだ「自分はロックを持っている」と思い込んでいる状況が普通に起こり得る。

Redis の作者 antirez が提案した Redlock は、5 台の Redis インスタンスのうち過半数からロックを取得することでフォールトトレラントな分散ロックを実現しようとするアルゴリズムである。Kleppmann はこれを批判した。理由は 2 つある。1 つ目は、Redlock にはフェンシングトークンを生成する仕組みが無いこと ― ロックを取得するたびに増える番号を提供しないため、GC ポーズ後に書き込みが行われる race condition をそもそも防げない。2 つ目は、Redlock の安全性がプロセスの停止やネットワーク遅延が一定時間を超えないという仮定に依存している点で、これは非同期モデル (タイムアウトは単なる疑いの表明であり、相手が本当に死んでいる保証にはならないという前提) とは相容れない。この論争の実務的な結論は、Redlock は「効率のためのロック」には十分使えるが、「正しさのためのロック」としてフェンシングトークンの代わりにはならない、という点である。

図: ロックの使い道が「効率」か「正しさ」かで、求められる安全性のレベルが変わる。

5. ZooKeeper ・ etcd での実装

ZooKeeper のロックレシピは次のように動く。クライアントはロックノードの下に連番付きの一時ノード (ephemeral, sequential) を作成する。自分が作ったノードの連番が最小ならロックを取得したことになる。そうでなければ、自分より 1 つ小さい連番のノードに watch (監視) を設定して、そのノードが消えるのを待つ。ロックの解放は自分のノードを削除するだけでよい。この仕組みはポーリングやタイムアウトを使わず、ノードが削除された時だけ次の 1 クライアントが起きる (herd effect を避けられる) という利点がある。この連番そのものが単調増加するため、zxid や znode のバージョン番号と同様にフェンシングトークンとして使える。

etcd はリース (lease) という TTL 付きの仕組みを提供するが、etcd 自身の公式ドキュメントは重要な注意を与えている。リースの TTL は物理時間で測られるため、リース単独では相互排他を保証できない。etcd が実際に相互排他を実現しているのは、put/txn のような RPC でリビジョン番号 (revision) というバージョン番号による条件付き書き込み (compare-and-swap)を使っているからである。etcd の公式ドキュメントはこの点を明確に述べ、Kleppmann のフェンシングトークンという考え方について「etcd におけるフェンシングトークンとはリビジョン番号のことだと解釈している」と明言している。つまり etcd でも、安全性の根拠はリースではなく単調増加する番号そのものにある。

図: ZooKeeper も etcd も、実際の安全性は単調増加する番号(連番/リビジョン)が担っている。

6. どこで壊れるか・何を諦めるか・実システムでの例

分散ロックは「同時に 1 つだけ」という安全性を買う代わりに、可用性を犠牲にする場面がある。ロックサービス自体が過半数に届かず応答できなくなれば、ロックを取ろうとする全てのクライアントがブロックされる。これは第 25 回で見た Raft/Paxos のクォーラムの話と同じ構造の代償である。また、リースの TTL を短くしすぎると、正常に動いているクライアントの処理が TTL より長くかかっただけで誤ってロックを奪われ、逆に長くしすぎると故障したクライアントの検出が遅れる ― この長さの選び方には万能な正解が無く、運用でチューニングする対象になる。

チケット予約システムでは、座席に 5 分から 10 分ほどのホールド (一時確保) をかけてから決済に進む設計が一般的である。これはまさにリースの考え方そのもので、決済が時間内に終わらなければホールドは自動的に失効し、他の客がその席を取れるようになる。ここでも、決済確定の書き込みにはホールドを発行した時点の番号 (フェンシングトークンに相当する考え方) を一緒に確認することで、期限切れのホールドを持ったまま遅れて届いた確定要求が、別の客に再販された席を上書きしてしまう事態を防ぐ必要がある。分散 cron (第 30 回で詳しく扱う) でも、同じジョブを複数のワーカーが同時に実行してしまわないよう、ジョブの実行権をロックで 1 ワーカーに絞る設計が使われる。

図: チケット予約の座席ホールドはリースの実例であり、確定処理には番号の確認(フェンシングの考え方)が要る。

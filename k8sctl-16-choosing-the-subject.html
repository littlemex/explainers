第 01〜15 回で、CRD・CR・コントローラー・検証・既定値・status・finalizer・admission・バージョン・テストを一通り見た。ここからの 3 回は、実際に使う場所がある本物のカスタムコントローラーを一から作る。第 16 回は「何を作るか」を、実際の作業記録と実機の確認から決める。

結論から。作るのは「既にある FSx のファイルシステムを、namespace ごとに読み取り専用か読み書きで配る」CRD とコントローラー。手作業と事故の記録が最も多く、学んだ部品をほぼ全部使い、GPU なしで本物のマウントまで確かめられるからだ。コードを書く前に手で試したところ、「読み取り専用なら ReadOnlyMany」という自然な発想が実機では通らなかった。

1. どこから題材を探したか

作るものは「あとで実際に使うリポジトリに取り込めて、便利なもの」でなければ意味がない。そこで、想像で題材を考えるのではなく、実際の作業の記録から「人が手で繰り返している操作」を探した。調べたのは次の 3 つだ。

  • Zenn の本「eks-distributed-ai」の全 14 章。EKS(AWS のマネージド Kubernetes)の上で分散学習と推論を動かす手順書で、各章の「今後の課題」や「手で〜する必要がある」と書かれた箇所を拾った。
  • その本の実体である littlemex/distributed-ai の infra/eks と、日付付きの調査ディレクトリ。スクリプトの中で kubectl をループしている所、状態を待ち合わせている所を探した。
  • 作りかけのオペレーター littlemex/karpenter-tenant-pools。どこまで出来ていて何が残っているかを確かめた。

コントローラーが向いているのは、「あるべき状態」を宣言でき、それに向かって何度でも同じ作業を繰り返せる仕事だ(第 03 回)。逆に「一度だけ順番に実行して終わり」の作業は、Job(一回きりの処理を動かす仕組み)やスクリプトの方が向いている。この物差しで候補をふるいにかけた。

図: 実際の作業記録から手作業を拾い、3 つの物差しで 1 つに絞った。

2. 候補の比べ方

物差しは 3 つにした。1 つめは便利さ(distributed-ai に入れたとき、どれだけ手作業が減るか)。2 つめは教材としての良さ(第 01〜15 回で学んだ spec と status の分離、検証、既定値、finalizer、所有関係、watch などを自然に全部使うか)。3 つめはGPU なしで本物の動作を証明できるかだ。3 つめが大事なのは、高価な GPU を借りなくても「本当に動いた」と言える検証ができないと、作っても信用できないからだ。

候補と採点は次の表のとおり。採点は各 5 点満点で、上の 5 つは設計の相談相手として使った Fable 5.2(Anthropic の AI モデル)に調査結果を渡してつけさせたもの、最後の「使い捨てファイルシステム」だけは後から足した候補で筆者の採点だ。

候補何を自動化するか便利教材GPU なし落とした理由 / 選んだ理由

3. なぜ共有ストレージなのか

FSx for Lustre や FSx for OpenZFS は、本来たくさんのマシンから同時に読み書きするためのファイルシステムだ。Kubernetes からは CSI ドライバ(記憶装置ごとの接続部品)を通して、Pod の中のディレクトリとして見えるようにする。これをマウントと呼ぶ。ところが Kubernetes から見ると、静的な PV(PersistentVolume: 既にある記憶装置を指す札)は 1 つの PVC(PersistentVolumeClaim: 「この記憶装置を使いたい」という申し込み)としか結び付かない。しかも FSx の動的プロビジョニング(申し込みに応じて自動で用意する仕組み)は、申し込みのたびに新しい入れ物を作る。Lustre ならファイルシステムを丸ごと 1 つ、OpenZFS ならファイルシステムか、既存のファイルシステムの中の子ボリュームを作る。どちらにしても、既にあるデータを共有することにはならない。だから「既にある 1 つのファイルシステムを 2 つめの namespace からも使う」には、同じファイルシステムを指す PV をもう 1 本、手で作るしかない。

distributed-ai では、その手順が manifests/fsx-lustre-shared-pv/README.md に書かれている。元の PV から kubectl get pv -o jsonpath で 4 つの値を読み、テンプレートに埋めて PV と PVC を作る。PV には claimRef(この PV を使ってよい PVC の予約)を付ける。付けないと、別の namespace の PVC に横取りされうるからだ。

さらに厄介なのが、PVC を消して作り直したときだ。PV は消えずに残る設定(Retain)なので、古い PVC の UID(一意な番号)を覚えたまま Released という状態で止まり、新しい PVC を受け付けない。これを外すために scripts/05-release-pv.sh という 288 行のスクリプトがある。Zenn 本の共有ストレージの章も、この解放手順に紙幅を割いている。

実際のクラスタで見つかったこと。 検証に使った EKS 1.35 のテスト用クラスタでは、FSx for Lustre の共有 PV が、PVC がとっくに消えたまま Released で止まっていた。FSx for OpenZFS では、同じファイルシステムを指す PV が 2 本、同じ volumeHandle(ボリュームの識別子)のまま手で複製されていた。kubelet(ノードの管理役)は driver と volumeHandle の組でボリュームを見分けるので、この 2 本を同じノードで使うと取り違えが起きうる。手作業の跡は、記録の中だけでなく実物にも残っていた。

図: 左の 5 つの手作業を、右の 2 つの宣言に置き換える。どちらも「あるべき状態」が書けるので、コントローラーの形をしている。

この題材は第 01〜15 回の部品をほぼ全部使う。PV はクラスタ全体のオブジェクトで、namespace に属する Claim からは ownerReference(親子関係)を張れない(第 10 回)ので finalizer で後片付けする。PVC は同じ namespace なので親子関係を張れる。許可の判定は namespace のラベルや管理者の設定という「他のオブジェクト」に依存するので、webhook でなく reconcile で行うべきかを考える必要がある(第 12 回)。そして本物の FSx を CPU ノードにマウントすれば、GPU なしで本当の動作を確かめられる。

4. karpenter-tenant-pools はどうしたか

作りかけだった karpenter-tenant-pools は、namespace に置く AcceleratorPool から Karpenter の NodePool と EC2NodeClass を作るオペレーターだ。Zenn 本の GPU プールの章が「プールの宣言を namespace 単位で分離できる CRD に移す」と書いている、その答えにあたる。調べると、プール 1 つ分の reconcile、Server-Side Apply(第 11 回)でテナント境界にあたる項目を誰かが書き換えても取り戻す仕組み、CEL による検証、削除の順序は、設計書(ADR と呼ばれる決定記録が 6 本)どおりに実装されテストもあった。go build と go vet も通る。

一方で、管理者用の AcceleratorClass を扱うコントローラーそのもの、設計書が約束する Drifted 条件(設定のずれを知らせる印)、AWS の予約の照会、14 種のメトリクス、README などが参照しているドキュメント 6 本は、まだ無かった。つまり残っているのは「CRD の作り方」ではなく「運用の機能」で、この連載の最終章で一から作る題材には向かない。代わりに、計算資源(GPU ノード)の配布は tenant-pools、記憶装置の配布はこの連載で作るもの、という分担にした。両方が揃うと、チームごとに「自分の GPU ノード」と「共有データへの読み書き権」を宣言だけで持てる。

図: 計算資源と記憶装置を、それぞれ別のコントローラーが namespace 単位で配る。

5. コードを書く前に、手で確かめたこと

設計の土台になる事実は、コードを書く前に手作りの PV で確かめた。後から「前提が違った」と分かると、API の形から作り直しになるからだ。EKS 1.35 のテスト用クラスタで、FSx for Lustre(4800 GiB)と FSx for OpenZFS(256 GiB)を使い、CPU ノード 1 台に Pod を 2 つ置いて試した。

確かめたこと結果(実測)設計への影響
読み取り専用の PV を accessModes の ReadOnlyMany で作る両ドライバともマウント失敗(Volume capability not supported)読み取り専用は ReadWriteMany + マウントオプション ro で強制する
ro 付きの PV と付いていない PV を同じノードで同時にマウントro 側の書き込みは Read-only file system で失敗、rw 側は書ける1 つのファイルシステムを namespace ごとに rw と ro で配れる
予約済みの PV を、別 namespace の PVC が名前で指名Pending のまま(already bound to a different claim)claimRef の予約だけで横取りを防げる
PVC を消して同じ名前で作り直すPV は Released、新しい PVC は Pendingコントローラーが自動で直す必要がある
PV の claimRef.uid と claimRef.resourceVersion だけを消す5 秒以内に新しい PVC と結び付いた予約(namespace と名前)は残したまま直せる

最初の行は、想定が外れた例だ。「読み取り専用なら ReadOnlyMany」と考えたくなるが、accessModes はもともと PV と PVC を結ぶときの条件で、書き込みを止める仕組みではない。公式ドキュメントにも「access modes do not enforce write protection(ReadOnlyMany でも、ドライバが強制しなければ書けてしまう)」とある。しかもドライバのソースコード(aws-fsx-csi-driver の controller.go)を読むと、受け付ける方式は 2 つだけだった。最後の行の修復方法も大事だ。05-release-pv.sh は claimRef を丸ごと外して PV を Available(誰でも使える状態)に戻す(252〜256 行)。元の PV を次に使う namespace へ渡し直すという、このスクリプトの用途ではそれで正しい。しかし namespace ごとに予約した PV を配る用途では、予約が消えた瞬間に、どの namespace からでも名前で取れる状態ができてしまう。消すのを UID と resourceVersion だけにすれば、その穴は開かない。この 5 秒という結び付きの速さは、PV と PVC が両方揃った状態から直したときのもので、第 18 回で測る「Claim を作ってから使えるまでの時間」とは別の数字だ。

図: 同じ「Released を直す」でも、外す範囲で安全さが変わる。上は予約の無い窓が開き、下は開かない。

まとめと次の回

題材は、作業記録の中で最も手作業と事故が多く、学んだ部品をほぼ全部使い、GPU なしで本物の動作を証明できる「既存の共有ファイルシステムを namespace ごとに配る」に決めた。作りかけの GPU プールのオペレーターは、残りが運用の機能だったので役割分担の相手にした。そしてコードを書く前に、読み取り専用の実現方法と Released の直し方を実機で確かめ、1 つは想定が外れていたことが分かった。第 17 回では、この事実を土台に API とコントローラーの責任の分け方を設計する。

図: 設計より先に実測を置いたのは、API の形が実測の結果に依存するから。

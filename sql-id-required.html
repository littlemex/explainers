ID リクワイアド ― とりあえず id 列を付ける

交差テーブルに無条件で意味の無い id 列を付けると、本来主キーが守るはずの重複防止が外れてしまう

← SQL シリーズ目次へ

この回の前提: 第 01 回 アンチパターンとは何か (サンプル DB の bugs_products テーブル)

「どのテーブルにも id 列を付けておけば安心」という習慣は多くの場面で合理的ですが、すでに自然なキー (natural key) や複数列の組み合わせ (複合キー、composite key) が一意性を保証しているテーブルに、さらに意味の無い id 列を主キーとして追加すると、本来の一意性の保証が外れてしまいます。結論を先に言うと、問題が起きるのは「id 列を付けること」自体ではなく「id 列を付けたことで、本来守るべき自然キーの一意性制約を外してしまうこと」です。この回では、交差テーブルで実際にこの重複を再現し、見つけ方、使ってよい場合、そして PostgreSQL の identity 列・UUID の実務的な選び方を確認します。

1. 目的 ― 何をしたかったのか

多くの ORM やテーブル設計の手引きは「すべてのテーブルに id という名前の主キーを持たせる」ことを勧めます。これは一貫性があって扱いやすく、アプリケーションのコードを単純にできるという利点があるため、広く採用されている習慣です。この習慣をそのまま、bugs_products のような交差テーブル (bug と product の多対多の関係を表すテーブル) にも適用してみます。

2. アンチパターン ― どう書いてしまい、何が壊れるか

bugs_products は本来、(bug_id, product_id) という複合キーがそのまま主キーになっており、この組み合わせ自体に一意性制約がかかっています。ここに、習慣通り id 列を追加した版を作ってみます。

CREATE TABLE bugs_products_bad (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  bug_id     bigint NOT NULL REFERENCES bugs (bug_id),
  product_id bigint NOT NULL REFERENCES products (product_id)
);

INSERT INTO bugs_products_bad (bug_id, product_id) VALUES (1, 1);
INSERT INTO bugs_products_bad (bug_id, product_id) VALUES (1, 1); -- 同じ組をもう一度

SELECT * FROM bugs_products_bad ORDER BY id;

 id | bug_id | product_id
----+--------+------------
  1 |      1 |          1
  2 |      1 |          1

bug_id=1 と product_id=1 という同じ組が、id だけ違う 2 行として入ってしまいました。主キーが id だけになったことで、「同じ bug と同じ product の組を 2 回結び付けてはいけない」という、本来このテーブルが守るべき制約が消えてしまったのです。

図: 主キーを id だけにすると、本来一意であるべき (bug_id, product_id) の組が重複しても検出できない。

3. 見つけ方 ― どんな兆候で気づくか

外部キー列を 2 つ以上持つ「交差テーブルらしき」テーブルを、information_schema から一覧にします。

SELECT tc.table_name, array_agg(DISTINCT kcu.column_name) AS fk_columns
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
  ON tc.constraint_name = kcu.constraint_name AND tc.table_schema = kcu.table_schema
WHERE tc.constraint_type = 'FOREIGN KEY' AND tc.table_schema = 'public'
GROUP BY tc.table_name
HAVING count(DISTINCT kcu.column_name) >= 2;

   table_name      |                 fk_columns
--------------------+---------------------------------------------
 bugs               | {assigned_to,reported_by,status,verified_by}
 bugs_products      | {bug_id,product_id}
 bugs_products_bad  | {bug_id,product_id}
 comments           | {author,bug_id}

見つかった各テーブルについて、その外部キー列の組を覆う PRIMARY KEY か UNIQUE 制約があるかを確認します。

SELECT conname, contype, pg_get_constraintdef(oid)
FROM pg_constraint WHERE conrelid = 'bugs_products_bad'::regclass;

               conname                 | contype |              定義
----------------------------------------+---------+----------------------------
 bugs_products_bad_pkey                 |    p    | PRIMARY KEY (id)
 bugs_products_bad_bug_id_fkey          |    f    | FOREIGN KEY (bug_id) ...
 bugs_products_bad_product_id_fkey      |    f    | FOREIGN KEY (product_id) ...

bugs_products_bad には (bug_id, product_id) を覆う PRIMARY KEY も UNIQUE も無く、主キーは id だけです。この形 (外部キー列が複数あるのに、それらを覆う一意性制約が無いテーブル) が、このアンチパターンの兆候です。比較のため、正しく作られている bugs_products の制約も確認すると、PRIMARY KEY (bug_id, product_id) になっていることが分かります。

4. 使ってよい場合

すべてのテーブルに surrogate key (代用キー、意味を持たない連番や UUID の id) を付ける習慣そのものは、多くの場面で合理的です。accounts テーブルを例にすると、一意な値になりそうな email や account_name はユーザーの都合で変更されることがあり、これらを主キーにして他のテーブルから参照すると、メールアドレスが変わるたびに関連する行をすべて更新する必要が出てきます。このように、自然キーの候補が変更されうる場合や、複数列の複合キーを外部キーとして子テーブルに持たせると列数が増えて結合が煩雑になる場合は、意味を持たない surrogate key を主キーにする方が安定します。

問題になるのは、bugs_products のように自然キー (この場合は複合キー) がすでに安定して一意性を保証できるテーブルに、追加で意味の無い id を付け、しかもその id だけを主キーにしてしまう場合です。surrogate key を使うこと自体ではなく、自然キーの一意性制約を外してしまうことが問題なので、「id 列を追加しつつ、自然キーにも UNIQUE 制約を残す」のであれば、両方の利点を両立できます。

5. 解決策 ― PostgreSQL での正しい書き方

自然キーや複合キーがすでに一意性を保証しているテーブルでは、それをそのまま主キーにします。このサンプル DB の bugs_products は最初からこの形です。

CREATE TABLE bugs_products (
  bug_id      bigint NOT NULL REFERENCES bugs (bug_id) ON DELETE CASCADE,
  product_id  bigint NOT NULL REFERENCES products (product_id),
  PRIMARY KEY (bug_id, product_id)
);

この形には、重複を防げるという利点に加えて、もう 1 つの実務的な利点があります。列名がテーブル間で揃っているため、JOIN ... USING (列名) という簡潔な結合が書けます。

SELECT b.bug_id, p.product_name
FROM bugs_products AS bp
JOIN bugs AS b USING (bug_id)
JOIN products AS p USING (product_id)
ORDER BY b.bug_id, p.product_name
LIMIT 3;

 bug_id |  product_name
--------+----------------
      1 | Open RoundFile
      2 | Open RoundFile
      2 | ReConsider

USING (bug_id) は ON bp.bug_id = b.bug_id と書くのと同じ意味ですが、結合する両方のテーブルに同じ名前の列があることを前提にした簡潔な書き方です。bugs_products_bad のように無意味な id だけを主キーにしてしまうと、列名の対応関係そのものは変わりませんが、結合条件を考えるときに「この表の本当の識別子は何か」を id と自然キーの両方で意識する必要が出てきて、わかりやすさが下がります。

どうしても surrogate key の id も残したい場合 (例えばアプリケーションのコードを単純にするため) は、自然キーの一意性制約を手放さないことが重要です。

CREATE TABLE bugs_products_ok (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  bug_id     bigint NOT NULL REFERENCES bugs (bug_id),
  product_id bigint NOT NULL REFERENCES products (product_id),
  UNIQUE (bug_id, product_id)  -- 自然キーの一意性をここで守る
);

この形であれば、surrogate key による扱いやすさと、自然キーによる重複防止の両方が手に入ります。

6. PostgreSQL エンジンで考慮しておくこと

surrogate key を使う場合、PostgreSQL では GENERATED ALWAYS AS IDENTITY (SQL 標準の identity 列) と、昔から使われている serial (内部的には sequence + デフォルト値) の 2 つの選択肢があります。両者の違いは、明示的に値を指定した INSERT への振る舞いに表れます。

INSERT INTO t_serial (id, label) VALUES (999, 'explicit value via serial'); -- 成功する (警告も無い)

INSERT INTO t_identity (id, label) VALUES (999, 'explicit value via identity');
ERROR:  cannot insert a non-DEFAULT value into column "id"
DETAIL:  Column "id" is an identity column defined as GENERATED ALWAYS.
HINT:  Use OVERRIDING SYSTEM VALUE to override.

serial は明示的な値の挿入をそのまま受け入れてしまい、後から追加した自動生成の値とシーケンスの現在値がずれる (次の自動採番が既存の値と衝突する) 事故が起きやすくなります。GENERATED ALWAYS AS IDENTITY はこれを拒否し、どうしても明示的な値が必要な移行作業などでは OVERRIDING SYSTEM VALUE を明記させることで、事故を未然に防ぎます。新しく作るテーブルでは GENERATED ALWAYS AS IDENTITY を既定にするのが安全です。

型の選択では、int の identity 列は内部のシーケンスが 2,147,483,647 (約 21 億) で尽きます。実際にシーケンスをこの値まで進めてから insert すると、次のように失敗します。

SELECT setval(pg_get_serial_sequence('t_int_id','id'), 2147483647);
INSERT INTO t_int_id (label) VALUES ('one too many');
ERROR:  nextval: reached maximum value of sequence "t_int_id_id_seq" (2147483647)

21 億行は小規模なテーブルでは縁遠い数字ですが、イベントログや履行履歴のような増え続けるテーブルでは現実的な上限になるため、新しい identity 列は bigint を既定にしておくと安全です。

もう 1 つの surrogate key の選択肢が UUID です。PostgreSQL 18 で追加された uuidv7() は、生成した時刻の順にソートできる UUID (UUID バージョン 7) を作ります。従来の gen_random_uuid() (ランダムな UUID バージョン 4) と比べると、ソート順が意味を持つ点が異なります。

INSERT INTO t_uuid7 (label) VALUES ('first');
INSERT INTO t_uuid7 (label) VALUES ('second');
INSERT INTO t_uuid7 (label) VALUES ('third');
SELECT label, id FROM t_uuid7 ORDER BY id;

 label  |                  id
--------+--------------------------------------
 first  | 01a1727e-0eac-76ef-9e85-130f35a7233d
 second | 01a1727e-0ebb-7008-b6bc-77aed0de99da
 third  | 01a1727e-0eca-7cd9-8c70-c5dfb0225270

ORDER BY id だけで作成順になりました。これは uuidv7() の先頭ビットに生成時刻を埋め込んでいるためです。この性質は B-tree インデックスへの書き込みにも影響します。20 万行を gen_random_uuid() (v4) と uuidv7() (v7) で挿入して比較すると、次のようになりました。

図: 20 万行の挿入時間は v4 が 774.5 ms、v7 が 403.0 ms (約 1.9 倍)。主キー索引のサイズは v4 が 8,304 kB、v7 が 6,184 kB (約 1.3 倍)。どちらも実機で確認した値。

ランダムな v4 は B-tree の中のランダムな位置に挿入されるため、ページ分割 (page split) が増えやすく、索引が余分に膨らみます。時刻順の v7 はほぼ右端への追記になるため、ページ分割が少なく、索引サイズも小さく済みます。「ランダムな ID が欲しい (推測されにくい)」という要件と「挿入性能や索引サイズを抑えたい」という要件がぶつかる場合は、この性質の違いを踏まえて選んでください。

結局のところ、この回全体を通して伝えたいことは 1 つです。id を主キーにするかどうかという選択と、「本来守るべき一意性をどの列 (の組) が担うか」という設計は、別々に考える必要があります。id を主キーにしても、自然キーの一意性制約 (UNIQUE) を手放さない限り、このアンチパターンは起きません。

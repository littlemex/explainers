0この回の主題

前回のプロトコルは「part ごとに signal を 1 本使う」形でした。signal が有限なので、part 数も channel 数もその割り当てから逆算されます。fork に新設されたヘッダ 2 本 (gin_resource_alloc.cuh と qp_mapping.cuh) は、その算術のためだけに存在します。

一言でいうと
EFA-GDA の signal は 1 本ごとに queue pair を 1 つ消費します。デバイス予算は signal + counter で 512。DeepEP は QP 予算 256 を「context 数 c」で割り、1 context あたり (256 − 2c) / c 本という反比例の関係で signal を配ります。context を増やすと並列度は上がるが 1 本あたりの signal が減り、part が減る。この綱引きが 既定値 11 という数字と、176 rank というスケール上限を生んでいます。上限はハードウェアの数ではなく 割り当て方式の帰結です。
1. なぜ signal が queue pair を食うのか 2. 予算の算術 3. 既定値 11 の意味 4. channel を QP へ配る 5. 数え間違えると静かに hang する 6. デモ: 予算計算機 7. 176 rank の壁

1なぜ signal が queue pair を食うのか

「カウンタ 1 個なのにメモリ 8 バイトでは済まない」理由は、EFA-GDA の signal の実現方法にあります。

第 3 回で見たとおり、EFA-GDA では signal 付き put のペイロードそのものを「その signal 番号に対応する相手の端点」へ宛てて書きます。受信側はその端点の FI_REMOTE_WRITE カウンタを読みます。つまり signal 番号 = 受信側の端点 (queue pair) 番号です。NCCL 側の device handle 定義にも、signal ごとの端点ハンドル配列 (signal_handles[nSignals]) がそのまま並んでいます。

これで「デバイスあたり signal + counter で 512」という制限の意味が分かります。ハードウェアが作れる端点の数の制限です。8 バイトのカウンタをいくつ置けるかという話ではありません。

3 つの語を区別する
ここから先は GIN context、端点 (endpoint)、QP を使い分けます。DeepEP が num_allocated_qps と呼ぶのは GIN context の数です。1 つの GIN context の下に、EFA-GDA の plugin が data 端点、PutValue 端点、そして signal 番号ごとの端点を作ります。indexed signal の番号は、その context の中で端点を選ぶ番号です。予算式の 256 と 512 が別の数である理由もここにあります。256 は DeepEP が自分の設計定数として持つ QP 予算で、512 は EFA が signal と counter に対して課すデバイスあたりの上限です。

図 1: signal は「別に送るメッセージ」ではなく「宛先の選び方」。だから本数が端点数の予算に直結する

2予算の算術

deep_ep/include/deep_ep/common/gin_resource_alloc.cuh の定数と式です。

static constexpr int kTotalQPBudget       = 256;
static constexpr int kMaxGinContextBudget = 17;   // provider の上限
static constexpr int kMaxWarpsPerSM       = 4;    // ScaleOut warp / SM の設計値
static constexpr int kMaxSM            = (kTotalQPBudget - 2*kMaxGinContextBudget)/kMaxWarpsPerSM;  // = 55
static constexpr int kMaxScaleoutWarps = kMaxSM * kMaxWarpsPerSM;                                  // = 220

// 1 context あたりの indexed signal 本数
constexpr int gin_indexed_signals_for(int c) { return (kTotalQPBudget - 2 * c) / c; }

static constexpr int kMinGinContextCnt     = 2;
static constexpr int kMaxGinContextCnt     = 17;
static constexpr int kDefaultGinContextCnt = 11;   // → 21 signals/context
static constexpr int kMaxParts             = 4;

読み方は次のとおりです。context 1 つが QP 1 つを供給します。context を c 個作ると、残りの QP 予算を signal に配れます。式の分子から 2c を引いている理由はコードに書かれていません。ヘッダのコメントは「provider の現在の制限に対する回避策」とだけ述べています。context ごとに固定で 2 つの端点が要ると読むのが自然で、NCCL の device handle にも data と pvdata という 2 つの端点が並んでいるので辻褄は合いますが、これは私の推測です。予算式を動かすときは、この 2 が何を指しているのかを先に確かめるべきです。

そして「全ての合法な context 数で、ScaleOut warp 1 本ごとに専用 signal を割り当てられるか」を コンパイル時に検査しています。

constexpr bool all_gin_context_counts_cover_warps() {
    for (int ctx = kMinGinContextCnt; ctx <= kMaxGinContextCnt; ++ ctx)
        if (ctx * gin_indexed_signals_for(ctx) < kMaxScaleoutWarps) return false;
    return true;
}
static_assert(all_gin_context_counts_cover_warps(), "...");

コメントには「最も厳しいのは ctx = 13 と ctx = 17 で、どちらも 221 対 220 で signal 1 本しか余裕がない。kMaxSM / kMaxWarpsPerSM を上げたり context の範囲を広げたり kTotalQPBudget を下げるときは再検査せよ」と書かれています。1 本の余裕で成立している設計だと明記されているわけです。

3既定値 11 の意味

なぜ 11 なのか。コメントが理由を書いています。

「11 context → 21 signals/context。context と signal/context は gin_indexed_signals_for を通して反比例するので、QP を増やせば 1 本あたりの signal 予算は減る。等価な代替は {5, 6, 7, 8, 9, 14}。それ以外はどこかで part を失う。特に 12, 15, 16, 17 は 12 SM で part が 3 に落ちる。17 (provider の最大) は signal が 13 本しか残らず、SM ごとの QP 分割で最も混む QP に channel が 4 本乗る」。

ただしこの整数制約が絞るのは候補集合までです。part を 4 に保てる context 数は 11 だけではなく、コメント自身が {5, 6, 7, 8, 9, 14} を挙げています。その中から 11 を選ぶには、QP の並列度と context あたりの signal 数のどちらを取るかという性能上の判断が別に必要です。つまり「11 は制約だけから決まった」とは言えません。言えるのは、制約が候補を離散的な集合に絞り、その中から選ぶ話になっているということです。だから性能 PR で context 数を動かすときは、必ず part 数への影響も同時に見る必要があります (open PR #9 が既定を 11 → 13 に上げる提案をしているので、そこは論点になります)。

なお §6 の計算機に出荷されている式をそのまま写して 12 SM ・ channel/SM 4 で走らせると、part 4 を保てるのは {5, 6, 7, 8, 9, 11, 13, 14} になり、コメントの列挙 (13 を含まない) とわずかにずれます。コメントが別の channel/SM を前提にしている可能性が高いものの、この種の「文書化された主張と出荷された式のずれ」はホスト側テストで固定すべき対象そのものです。実際 open PR #9 は既定を 13 にする提案をしているので、この行がどちらの前提で書かれているかは論点になります。

part 数の決め方は compute_part_allocation です。「要求された channel/SM のもとで channels_per_context(...) * num_parts <= gin_indexed_signals_cnt を満たす最大の num_parts (上限 4) を選び、それでも収まらなければ channel/SM を 1 ずつ減らす」という貪欲な手続きです。予算が足りないときに落とすのは part、次に channelという優先順位がここに埋まっています。

4channel を QP へ配る

qp_mapping.cuh は channel (= ScaleOut warp) を QP に割り当てる整数計算です。CUDA から独立していて、ホストでもコンパイルできます。

方式は balanced contiguous partition です。n 個を q 個の箱に、連続ブロックで、大きさの差が 1 以内になるように配ります。

QP_MAPPING_HD constexpr QPSlot balanced_partition(int idx, int n, int q) {
    const int base = n / q;
    const int rem  = n % q;                // base+1 個持つ「大きい箱」の数
    const int split = rem * (base + 1);
    if (idx < split) return QPSlot{idx / (base + 1), idx % (base + 1), base + 1};
    const int d = idx - split;
    return QPSlot{rem + d / base, d % base, base};
}

この関数が返す bin が QP 番号に、local が その QP 内での signal 番号になります。同じ QP を共有する channel が (QP, signal id) の組で一意に区別される、という設計です。上位の channel_to_qp は 2 つの領域に分かれます。

条件割り当て意味
SM 数 ≤ 使える QP 数各 SM が自分の QP ブロックを持ち、その中で自分の channel を均すSM 間で QP を共有しない = 競合が少ない
SM 数 > 使える QP 数全 SM が全 QP を共有し、全体の channel を均す共有せざるを得ない

upstream の実装は剰余ベースで、channel 数が QP 数で割り切れないときに 末尾の QP が遊ぶことがありました。コメントに「4 channel / 3 QP で以前は {2,2,0} になり QP2 が idle だった」と具体例が書かれています。fork の変更でこれが {2,1,1} になります。割り切れる構成 (出荷されている 2 の冪の構成) では以前と 1 ビットも変わらないことも明記されていて、後方互換の主張が丁寧です。

約束されているのに存在しないテスト
qp_mapping.cuh の冒頭コメントには、こう書かれています ―― 「CUDA / NCCL の型を使わないので、出荷されているロジックそのものが tests/cpp/test_qp_mapping.cpp の unit test としてもコンパイルできる」。ところがそのファイルはリポジトリに存在しません (tests/ の中身は elastic/、legacy/、utils/ の 3 つで、cpp/ はありません)。第 7 回で述べるとおり、これは「EFA 無しでできる貢献」の最も分かりやすい入口です。

5数え間違えると静かに hang する

この算術の怖さは、間違えたときの症状が「エラー」ではないことです。コード自身がそう書いています。

channels_per_context() のコメントを引きます。「1 番目の領域は ceil(num_sms * channels_per_sm / avail) ではない。この形は過小に数える。他の SM が持っている余った QP は、この SM の channel を吸収できないからだ。これを使うと signal を少なく確保してしまい、カーネルは確保範囲の外の id に signal を送る ―― これは静かに失敗する。カウントが 1 つも届かず、dispatch は受信カウントが全部ゼロのまま CPU の待ちでタイムアウトする」。

つまり 予算計算の誤りは、範囲外への signal 送信という形で現れ、それは例外でもエラーでもなく「何も起きない」。同じ種類の注意書きは get_qp_mode の static_assert にもあります。「kNumQPs は 1 以上でなければならない。0 だと n / 0 になる。ホスト向けにコンパイルすればこの特殊化は SIGFPE で落ちるが、GPU では出力が壊れ、報告される fault は無かった」。実際にそれを踏んだ痕跡が open PR #4 (「single-node 経路で GIN context 数を解決する。kNumQPs == 0 が combine を壊す」) に残っています。

この回の教訓
予算の算術は 純粋な整数計算で、GPU も EFA も要りません。それなのに間違えると 実機で最も診断しづらい症状を出します。検証コストが最も低く、失敗コストが最も高い区画がここにあります。だから最初に固めるべきはここです。

7176 rank の壁

同じ予算式が、スケールの上限も決めています。open PR #5 がその指摘です。

初期化時に次の検査があります (csrc/kernels/backend/nccl.cu)。

EP_HOST_ASSERT(gin_config.gin_indexed_signals_cnt >= (num_rdma_ranks - 1) and
               "GIN indexed-signal budget cannot give each peer rail team a dedicated "
               "signal; reduce num_allocated_qps to raise the per-context signal count");

num_rdma_ranks は rail team の大きさ、つまり NVLink 域 (実質ノード) の数です。要求は域数に比例して増えるのに、供給 (256 − 2c)/c は域数に対して定数です。だから必ずどこかで交差します。PR #5 の表がその交点を示しています。

context 数signal/context通る域数拒否される域数
2126127128
11 (出荷既定)212223
17131415

1 域 8 GPU として、既定の 11 は 22 × 8 = 176 rank で止まります。DeepEP 本体が EP2048 を掲げているのに対して、この経路は 176 で頭を打つ。しかも上限は固定値ではなく QP 数とのトレードオフで、5・6・7 に落とせば 32 域以上に届きます。gin_resource_alloc.cuh が「part を失わない代替」として {5, 6, 7, 8, 9, 14} を挙げているので、そのトレードは part を犠牲にしません。

ただし QP を犠牲にします。PR #5 はそこを測っていて、8 × p6-b300 (64 rank、256 expert、4096 token、24 SM、GDAKI GIN) で num_allocated_qps を 11 → 5 に落とすと dispatch +1.9 %、combine +30.5 % (3241 → 4228 µs、combine 帯域 96.3 → 74.6 GB/s) と報告しています。「dispatch は 11 本のうち 6 本を失ってもほとんど気づかないが、同時並行のトラフィックが重い combine は効く」という非対称です。だから PR #5 の提案は QP を削るのではなく rail barrier を counting barrier に書き換えて、域ごとの専用 signal という要求そのものを外す方向です。

この PR の形は覚えておく価値があります。予算が足りないなら予算配分を変えるのではなく、要求の形を変える。第 4 回の gin_barrier の書き換え (rank ごとに 1 本ではなく (rank − 1) 本の compact indexing にする) も同じ発想です。signal は希少資源なので、プロトコル側が「本数に比例しない形」に自分を作り替えるのが、この実装群を通じた一貫した設計方針です。

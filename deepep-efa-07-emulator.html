DEEPEP と EFA ・ 07

EFA なしで検証する emulator は作れるのか

結論は作れる。ただし「EFA を再現する」ではなく「EFA が与える契約の下でプロトコルを詰める」と目標を書き換える必要がある

0結論を先に

判定
作れます。 決定的な理由は 2 つです。(1) NCCL の RMA plugin (ncclRmaPlugin_v14) は完全にホスト側だけの API で、CPU proxy 経路のデータ配置と signal 更新の両方がこの plugin を通ります。したがって 1 回の put をどの粒度でどの順に置くか、signal をいつ立てるかを、テスト側が完全に支配できます。(2) DeepEP のカーネルが呼ぶのは gin.put / readSignal というバックエンド中立の device API なので、proxy 経路でも unordered カーネルのソースはそのまま走ります。

ただし目標は書き換えるべきです。 「EFA を再現する」ではなく 「EFA-GDA が与える weak bundled-signal 契約の下で、DeepEP の unordered プロトコルを敵対的スケジュールで詰める」。WQE の生成や MMIO の順序やハードウェアカウンタの周回は emulator の対象外と最初に宣言します。そこは実機に残す。

この回の判定は、公開ソース (NCCL / aws-ofi-nccl / DeepEP fork) の該当箇所を直接読んで確認したものと、独立に 2 つの大規模モデル (Claude Fable 5 と GPT-5.6) に同じ事実を渡して評価させた結果が収束した部分を書いています。設計判断そのものは実機で動かして出したものではありません。ただし実験でしか決まらない 3 点のうち 2 点は 2026-09-04 に GPU の実機で確定させました (結果は §9)。残る 1 点は NCCL の device API を持つ GPU が必要で、まだ開いています。

13 案の判定

思いつく方式を 3 つに整理して、それぞれの判定を先に置きます。

案やること判定理由
Aソフトウェア SRD: ncclRmaPlugin_v14 を実装し、同一ホスト内のプロセス間を共有メモリまたは TCP で繋ぐ。progress ループで put を chunk 単位に分割・並べ替え・遅延させ、signal は「そのメッセージの全 chunk を置いた後」に立てる。実 GPU の実カーネルが走る本命。実現可能plugin がデータ配置と signal の両方を実行するので、順序を完全に支配できる。CUDA コードは 1 行も要らない
Bソフトウェア EFA NIC: efa_cuda_qp の doorbell を MMIO ではなく通常メモリにし、ホストのスレッドが送信キューの EFA WQE を解釈して転送する。NCCL の EFA-GDA device コードが実機同等に走る技術的には可能だが非推奨検証対象が DeepEP fork ではなく NCCL / AWS 側の device コードになる。WQE パーサを自作すると「emulator の解釈」と「実機の解釈」の二重管理になり、両方が同じ誤解をすると静かに通る
Cホストだけのハーネス: qp_mapping.cuh / gin_resource_alloc.cuh / header の pack・unpack / part の幾何は既にホストでコンパイルできる。受理述語を純関数に括り出し、敵対的な interleaving を網羅探索する最速。A と相補的GPU も EFA も不要。しかも「存在すると書いてあるのに無いテスト」がある。最初の PR はここ

A と C は競合しません。C はプロトコルの論理を、A は GPU 上の実装 (warp 分業・fence・shared memory のリング) を担当します。B が拾える追加分 (WQE の詰め方、doorbell の集約、カウンタの 2^31 周回) は DeepEP の外側の責務なので、そこは実機テストに残すのが役割分担として正しい。

2決定的な API 事実 (一次ソース)

この判定は次の 6 つの確認に立っています。どれも公開ソースで追え、5 と 6 は実機のインストール物でも確かめました。

#事実場所意味
1proxy 経路のホスト側データパスは RMA plugin に分離されている。iput / iputSignal(..., bool isStrongSignal, ...) / iget / iflush / test / rmaProgress だけで、CUDA を含まないnccl/src/include/plugin/rma/rma_v14.hホストコードだけで transport を差し替えられる
2GIN plugin が「自分は proxy 型」と名乗ると NCCL はそれをスキップし、内蔵 proxy を RMA バックエンド越しに使うnccl/src/plugin/gin.cc (該当する INFO ログつきの分岐)proxy 経路を差し替える正しい入口は RMA plugin だけ、と確定する
3proxy 経路では indexed signal の実体が GPU メモリ上の uint64 配列で、plugin の regMrSym で登録され、device が signal 付き put を出すと signalOff = (signalId + contextId * nSignalsPerContext) * 8 を計算して plugin の iputSignal が呼ばれるnccl/src/gin/gin_host_proxy.ccsignal の到着タイミングも plugin が握る。これが emulator の成立条件
4proxy バックエンドは supportsStrongSignals = true; supportsVASignals = true; をハードコードしているnccl/src/gin/gin_host_proxy.ccRMA plugin では EFA の「非対応」を能力面で名乗れない。能力交渉のテストは別手段が必要 (§4 の但し書き)
5EFA-GDA の device コードと efa-dp-direct のヘッダは NCCL のインストール対象に含まれる (${CMAKE_BINARY_DIR}/include/nccl_device/transport/net_efa_gda/... にコピーされ install(DIRECTORY) で入る)。2026-09-04 に実機で確認済み: nvidia-nccl-cu13 2.31.2 の wheel に gin/efa_gda/gin_efa_gda.h と transport/net_efa_gda/efa-dp-direct/include/ 一式が入っていたnccl/src/transport/net_efa_gda/efa-dp-direct/CMakeLists.txt と wheel の実物EFA を持たないマシンでも、DeepEP の JIT カーネルには EFA-GDA 経路がコンパイルされて入る。案 B が原理的に可能な理由でもある
6一方で plugin の ABI ヘッダは wheel に入っていない。nccl_rma.h / nccl_gin.h / nccl_net.h / nccl_common.h がすべて欠落し、あるのは nccl.h と nccl_device の木だけwheel の実物 (2026-09-04 実測)plugin をビルドするには NCCL のソースチェックアウトが別に必要。設計は変わらないがビルド手順が変わる

4 番目は、当初「plugin が false を返せば EFA と同じ能力面を見せられる」と考えたところの訂正です。RMA plugin にはそもそも能力申告の関数がありません (GIN plugin にはある getGinProperties が RMA の op-table には無い)。ただしこれは実用上の障害になりません。DeepEP の unordered 経路は自分から ginStrongSignalsRequired = false; ginVaSignalsRequired = false; を設定するので、より強い能力を持つバックエンドの上で走るのは正当です。失われるのは「ordered カーネルが EFA で拒否されることの確認」だけで、それは能力交渉のテストとして別に書けます。

3推奨アーキテクチャ (3 層)

1 つの emulator を作るのではなく、検証対象の性質に応じて 3 つに分けます。層が上がるほど忠実で、下がるほど速く網羅的です。

図 1: 実機に残すのは最上段だけ。下 3 層で「順序に起因する誤り」を決定的に潰す

層の分け方の根拠は第 4 回の不変条件です。I1 (weak signal 契約) は backend の責務なので層 2 の適合性テスト、I2 と I3 は DeepEP の責務なので層 1、予算の算術は層 0。責務の境界を層の境界に合わせると、失敗したときにどのリポジトリの問題かが自動的に決まります。

4層 2 の設計 ― 敵対的 RMA plugin

中心になる部品です。名前を仮に libnccl-rma-srdsim.so とします。

実装するもの

// エクスポートする 1 つのシンボル
ncclRma_v14_t ncclRmaPlugin_v14 = {
  .name = "srdsim",
  .init, .devices, .getProperties,
  .listen, .connect,            // OOB は Unix domain socket
  .createContext, .destroyContext,
  .regMrSym, .regMrSymDmaBuf, .deregMrSym,
  .iput, .iputSignal, .iget, .iflush,
  .test, .rmaProgress, .queryLastError, .finalize
};
関数実装方針
listen / connect同一ホスト前提なので Unix domain socket。ハンドルの交換にそのまま使う
regMrSymNCCL の symmetric memory は cuMem VMM ベースなので、cuMemExportToShareableHandle で得た POSIX FD を SCM_RIGHTS で相手に渡し、cuMemImportFromShareableHandle + cuMemMap で相手のバッファを自プロセスに写す。以後 相手の GPU メモリへ直接 cudaMemcpy できる
iput1 回の memcpy にしないこと。 chunk (実機の SRD MTU に相当する粒度、たとえば 8 KiB) に割り、スケジューラが決めた順序と遅延で置く。これが「1 メッセージ内の順序の乱れ」の再現
iputSignalペイロードの全 chunk を置き終えた後に、signal の位置へ加算する。ここを守るのが I1 の再現であり、破るモードを別に用意するのが I1 の反証テスト
rmaProgressスケジューラの心臓。保留中の chunk と signal を、seed 付きの決定的な順序で 1 ステップ進める

スケジューラのモード

モード挙動期待
inorder発行順にそのまま置くすべて緑。ここが緑にならないなら emulator 自体が壊れている
srdchunk とメッセージを乱すが、I1 は守る (signal は全 chunk の後)DeepEP unordered は緑。ordered は赤になるべき
replay記録したトレースを再生する反例の再現とデバッグ
violate-i1signal をペイロードより先に置く赤になるべき。赤にならなければ「I1 に依存していない」ことの証明になるので、それも情報
strict-budgetsignal id が確保範囲外なら即 abort実機の「静かに何も届かない」を決定的な即死に変換する
oversize1 put が 1 GiB を超えたら loudly failEFA-GDA が分割する条件を「検証」ではなく「検知」で代替する
敵対性は較正する
「SRD が保証しないことは全部やる、保証することは守る」に揃えるのが重要です。I1 を既定で破ると、実機では絶対に起きない偽陽性を量産します。逆に chunk を割らずに 1 回の memcpy で置くと、実機で起きる窓を再現しません。violate-i1 は「契約に依存していることの証明」のための別モードとして分離し、既定は srd にします。そして violate-i1 で見つかった不具合は「DeepEP の穴」ではなく「backend 適合性の負テスト」として分類する ―― これを混同すると、上流に出したときに信用を落とします。

5トポロジをどう偽装するか

1 台のマシンで scale-out 経路を踏ませる必要があります。ノード内だけだと NVLink 経路 (direct mode) になり、検証したいカーネルが走りません。

第 1 回で見たとおり、DeepEP は初期化時に num_ranks == ncclTeamLsa(comm).nRanks * num_rdma_ranks を検査します。したがって LSA team を小さくして rail team を 2 以上にするのが目標です。NCCL の公開ソースから、手段が 2 つ読み取れます。

手段根拠効き方
NCCL_HOSTID をプロセスごとに変えるsrc/misc/utils.cc が hostHash の算出をこの環境変数で上書きする同一マシンの GPU を「別ノード」に見せる。rankToNode が分かれ、LSA が縮む
NCCL_LSA_TEAM_SIZEsrc/dev_runtime.cc の NCCL_PARAM(LsaTeamSize, "LSA_TEAM_SIZE", 0)。computeLsaSize がこの値を gcd の初期値として使うノード内のサイズより小さくする方向にだけ効く。まさに欲しい向き

computeLsaSize には先に走る分岐があり、comm->p2pCrossClique && comm->nvlDomainSize == comm->nRanks のとき「単一 NVLink 域なので LSA を域全体に広げる」として lsaSize = nRanks にしてパラメータを無視します。ただしこの分岐はほぼ発火しません。条件の p2pCrossClique は comm->MNNVL && ncclParamMNNVLCrossClique() && nvlDomainSize > clique.size という積で、NCCL_MNNVL_CROSS_CLIQUE の既定値が 0 です (src/init.cc)。したがって明示的に有効化しない限り false で、しかも MNNVL はマルチノード NVLink の構成でしか true になりません。単一ノードの NVSwitch 機 (p5 や p6 の 1 ノード) では原理的に発火しないので、NCCL_LSA_TEAM_SIZE はそのまま効きます。

実測で確定 (2026-09-04)
4 GPU の箱で実際に測りました。何もしなければ LSA 4 / rail 1 で scale-out に到達できず、懸念は実在しました。NCCL_LSA_TEAM_SIZE=1 を入れると LSA 1 / rail 4 になり、送信元が 3 つ取れます。NCCL_LSA_TEAM_SIZE=2 でも NCCL_HOSTID の分割でも同様に到達できました。詳細は §9 の表にあります。

必要な GPU 数も見積もっておきます。第 4 回の「送信元間の集約」を叩くには、受信側から見た remote な送信元が 2 つ以上必要です。rail team のサイズが 3 以上、つまり LSA = 1 なら 3 GPU、LSA = 2 なら 6 GPU。2 GPU の開発機では退化した構成しか組めません。裏を返すと、層 1 (プロトコルモデル) が GPU 無しで送信元数を自由に取れることの価値がここで効きます。

GPU の種類にも条件があります。実測で分かったのは、NCCL の device API が無い GPU では GIN をそもそも踏めないことです。Tesla T4 (SM 7.5) は deviceApiSupport: no を返します。さらに DeepEP のカーネル自体が TMA を使うので SM 90 以上が別に必要で、L4 や L40S (SM 89) や A100 (SM 80) では JIT が通りません。つまり層 2 を実カーネルで回すには Hopper 以降が 3 枚という条件になります。層 0 と層 1 にはこの条件が一切かからない、というのがこの分割の実利です。

6fidelity のギャップ表

emulator の価値と限界を、同じ表の中で並べます。ここを曖昧にしたまま上流に出すと信用されません。

捕まえられるもの

バグの種類担当する層実機との比較
メッセージ間の並べ替えによる誤受理層 1 / 層 2実機では確率的。emulator では決定的
1 メッセージ内で header だけ先に見える窓層 2 (chunk 順序を指定)実機では負荷依存で稀。emulator では狙って作れる
I2 (signal を先に読む・acquire) の欠落層 1 (第 4 回のデモがその縮小版)実機では「たまに壊れる」。emulator では網羅
I3 (基準値と drain) の欠落層 1 / 層 2 (前 iteration の書き込みを遅延配送)実機で狙うのは困難
iteration の 31 bit 周回層 1 (初期値を境界に置く)実機では 2^31 回まわす必要があり事実上不可能
signal 予算の超過・範囲外 signal層 0 + 層 2 の strict-budget実機では「全部ゼロで timeout」。emulator では即死 + 原因表示
bit 詰めの溢れ (PR #12 の形)層 0実機では misroute か hang。ホストで秒で検出
幾何の退化 (空 part、1 トークン part。PR #2 の形)層 0同じ
ordered カーネルが順序なし網で壊れること層 2 の srd モード「なぜ別実装が必要か」を実証できる

捕まえられないもの (対象外と宣言する)

バグの種類理由
WQE の詰め方、doorbell の集約、送信キュー満杯時の挙動、ハードウェアカウンタの 2^31 周回EFA-GDA の device 経路を踏まない。案 B でのみ届くが、そこは NCCL / AWS の責務
PeerMappingOverride 下の MMIO 書き込み順序、PCIe の relaxed ordering、GDRCopy の flushハードウェアのメモリモデルそのもの
NIC の DMA から GPU の L2 への可視化タイミングに依存する fence 抜け層 2 でも別 GPU からの store なので時々出るが、実機の DMA のタイミング分布とは違う
実 SRD の multipath / 再送に起因する遅延分布依存の問題 (timeout 値の較正を含む)emulator の遅延はモデルにすぎない
性能・帯域・レイテンシの一切最初に宣言する。PR #8 / #9 の根拠には決してならない

7既存物では代替できない理由

「もう誰かが作っているのでは」という疑いは、先に潰しておく価値があります。候補を 5 つ検討しました。

候補判定理由
libfabric の tcp / shm / sockets provider代替にならないこれらは libfabric の API 契約を素直に満たすので、順序を守る。SRD の乱れを再現するどころか隠蔽する。partial な可視性を指定して注入することもできない
SoftRoCE (rxe)代替にならないRoCE の verbs 意味論のテストには有用だが、EFA の記述子でも SRD でもなく、EFA のハードウェアカウンタでも signal 端点でもない
aws-ofi-nccl の tests/functional/gin_*併用する (層 3 相当)GDAKI / EFA の GPU 経路を直接動かす backend 適合性テスト。DeepEP の状態機械も敵対的順序も対象外。ただし plugin の疎通確認に流用できる
nccl-tests の GIN device kernel (alltoall_perf -R 2 -D 3)併用する (層 2 のスモーク)plugin が正しく載ったかの確認には最適。DeepEP 固有の in-band header / part の prefix / 送信元共有カウンタ / token map は知らない
FI_HMEM の CPU fallback無関係「GPU メモリにどうアクセスするか」の問題であり、順序や weak signal の問題ではない

結論として、「順序を保証しない・weak な indexed signal だけ・ただし signal は自分の put の配置後」という SRD 形の契約を持ち、かつ配置順序をテスト側が支配できる transport は存在しません。新しく作る正当性はここにあります。

8最初の PR とその次

emulator 本体から始めてはいけません。信用を積む順序があります。

  • PR 1: 約束されているのに無いテストを実体化する。 tests/cpp/test_qp_mapping.cpp を追加します。qp_mapping.cuh のコメントが「このファイルで検証する」と明言しているのに存在しないので、レビューの論点がほとんど発生しません。内容は context 2..17、SM 1..最大、channel/SM 1..最大、notify QP の有無、part 1..4 を全列挙して、(a) (qp, signal_id) の一意性、(b) signal_id < gin_indexed_signals_cnt、(c) 最悪 occupancy が channels_per_context() と一致すること、(d) channels_per_context * num_parts <= budget、(e) 割り切れる構成で従来と同一の割り当てになること (後方互換の主張の検証)。GPU も EFA も不要で CI に載ります。これが「EFA 無しの検証」の実績第一号になります。
  • PR 2: header と幾何をホスト呼び出し可能にして、その不変条件テストを足す。 pack_scaleout_header / unpack_scaleout_header / part_size_at / part_offset_at / num_sub_parts_at を __host__ __device__ の純関数に揃え (qp_mapping.cuh と同じ流儀に揃える、という説明が既存の設計思想に乗ります)、roundtrip・境界値・31 bit 周回をテストします。同時に 受理述語も純関数に括り出します。これが層 1 の遷移関数になります。
  • PR 3: 既知バグの再現テスト。 PR #12 が指摘した bit 詰めの溢れを、層 0 のテストで再現してから修正を当てて緑にします。emulator の信用は「未知のバグを見つけた」より先に「既知のバグを再現できた」で立ちます。同じ形で PR #2 の「3 トークンを 4 part」も幾何のテストとして固定できます。
  • PR 4 以降: 層 1 のモデル。 DeepEP のリポジトリに置きます。プロトコル固有なので NCCL や aws-ofi-nccl に置くものではありません。送信元 2〜3、part 2、sub-part 2、iteration 2 程度に境界を切れば、到着イベントの順列は網羅探索できます。観測点が「header の可視性 × signal の数 × iteration の値」に射影できるので、実効的な状態数は小さく収まります。
  • 層 2 の plugin は独立リポジトリから始める。 理由は 2 つ。(a) RMA plugin の ABI は流動的です ―― NCCL のツリーには既に rma_v13.h / rma_v14.h / rma_v15.h が並んでいます。fork 本体に入れると版追従の負債を fork に押し付けます。(b) plugin 自体は DeepEP に依存しない汎用の NCCL テスト道具なので、実績が付いた後に nccl-tests か aws-ofi-nccl のテスト基盤への提案として持ち込む方が筋が通ります。DeepEP fork 側には CI 連携スクリプトと再現シナリオだけを置きます。
    • 説得の順序
    今の fork では open PR 全ての根拠が実機測定です。そこへ「実機なしの検証」を持ち込むには、まず既知の問題を実機なしで捕まえてみせるのが最短です。PR 1 から 3 までは emulator という言葉を出す必要さえありません。それでいて、3 つが揃った時点で層 1 の土台は完成しています。

    ここまで実際に作ったもの (2026-09-04)

    この順序どおりに層 0 と層 1 を書いて動かしました。数字は再現できるものだけ挙げます。

    層作ったもの結果
    0QP マッピングと予算の検査1,887,915 個の assertion が通る。ヘッダが自分について主張していること (channels_per_context が上界でなくちょうど最悪値であること、却下されている式が実際に過小に数えること、context 13 と 17 で signal 1 本しか余らないこと) はすべて成立
    0そのテストのミューテーション試験出荷ヘッダへの 1 か所改変 4 種すべてを検出。却下されている式に差し替えると「予算がちょうどである」性質が発火する。実機ならこれは診断不能な hang になる箇所
    0part 幾何と header codec の検査6,402 個の assertion。degenerate 分岐の超過が slot の予備枠より小さいという、2 ファイルにまたがって暗黙だった不変条件も固定した
    0combine の受信アドレス詰めの検査248,848 個の assertion。open PR が挙げていない第 2 の壊れ方を発見 (後述)
    1受理規則のモデル検査到達可能な観測状態を全数列挙。出荷されている読み順は 5 構成すべてで反例ゼロ (各構成最大 38,416 の順序つき状態対)。読み順を入れ替えた場合、I1 を破った場合、基準値が 1 足りない場合はどの構成でも反例が出る
    2SRD の配送スケジューラ60,000 seed で 2 操作のケースの合法な順序 2520 通りを 2520/2520 網羅し、違法な順序は 1 つも出さない。敵対者が「乱雑」ではなく「網羅的」であることの担保

    層 0 で見つかった第 2 の壊れ方は書き留めておく価値があります。token_map_at_dispatch の bit 詰めについて open PR は「slot が溢れると rank フィールドに漏れて misroute か hang になる」と指摘していますが、rank が 5 bit を超えると bit 31 が立って値が負になり、combine の epilogue が負のエントリを「未使用」として飛ばすので、寄与が黙って落ちます。misroute でも hang でもなく、reduce の項が 1 つ足りないだけです。さらにフィールドの合成が加算ではなく OR なので、slot の溢れは rank の最下位ビットが既に立っているとき合法なエントリと 1 ビットも違わなくなります。だから packed 値への実行時チェックでは意図を復元できず、instantiation 時に境界を検査するしかありません。

    9着手前に潰す 3 点

    この回の設計判断は公開ソースの読解から出したものです。そのうち 3 点は実験でしか白黒がつかないので分けて挙げてありました。2026-09-04 に GPU 4 枚の箱を 17.7 分だけ借りて 2 点を確定させたので、結果を先に置きます。

    実測の結論 (2026-09-04、g4dn.12xlarge = Tesla T4 4 枚、費用 1.15 ドル)
    #問い結果
    1単一ホストで rail team を 2 以上にできるかできる。何もしないと LSA 4 / rail 1 で到達不可 (懸念は実在した)。NCCL_LSA_TEAM_SIZE=1 で LSA 1 / rail 4
    2iputSignal が plugin に降りるかこの箱では判定不能。T4 は deviceApiSupport: no / ginType: none で、NCCL の device API がそもそも無い。SM 7.5 では GIN を踏めない
    3peer の window を別プロセスから書けるかプロセス境界は成立、peer access は不成立。export から map、書き込み、2 MiB 全バイト照合まで通り、落ちたのは別 GPU 向けの cuMemSetAccess だけ (この箱は P2P access が全ペア 0)

    3 番目の結果は設計を 2 つに割ります。1 ホストに複数 GPU を置く形では送信側が相手の window を map して書くので P2P と cuMem export の両方が必要ですが、1 GPU のホストを複数並べる形では受信側の agent が自分の window に書くので、どちらも要りません。しかも後者は各ホストが本物のノードなので rail team がホスト数になり、1 番目の問いも消えます。実機で失敗した 2 つをどちらも避けられるので、作るべきはこちらの形だと分かりました。

    2 番目が残ったことで、必要な GPU の条件も具体的になりました。NCCL の device API がある GPU が要ります。T4 (SM 7.5) には無く、DeepEP のカーネル自体は TMA を使うので SM 90 以上が別に必要です。そして送信元を 2 つ作るには rail が 3 以上要ります。この 3 条件を同時に満たす最も安い形が H100 1 枚のノードを 3 台並べる構成でした。

    付随して確定した事実が 2 つあります。EFA-GDA の device ヘッダは pip の wheel に入っています (nvidia-nccl-cu13 2.31.2 に gin/efa_gda/ と transport/net_efa_gda/efa-dp-direct/ の一式、backend の dispatch にも EFA_GDA の腕)。§2 の事実 5 が実物で裏付けられました。逆に plugin の ABI ヘッダは wheel に入っていません (nccl_rma.h ほかすべて欠落) ので、plugin のビルドには NCCL のソースチェックアウトが別に必要です。

    以下は元の 3 点です。実験の方法と、駄目だったときの逃げ道を残してあります。

    #確認すること方法駄目だった場合
    1
    解決    		単一ホストで rail team を 2 以上にできるか。computeLsaSize の p2pCrossClique && nvlDomainSize == nRanks の分岐を回避できるか2〜3 GPU のマシンで NCCL_HOSTID を分けて起動し、NCCL_DEBUG=INFO で LSA / rail のサイズを確認。NCCL_LSA_TEAM_SIZE の効きも見る層 2 は多ノード (EFA でなくてよい ―― TCP の 2 台でよい) が必要になる。層 0 / 層 1 の価値は変わらない
    2
    未解決    		proxy 経路で plugin が実際に iput / iputSignal を受け取るか。DeepEP の unordered カーネルが出す signal 付き put が plugin まで降りてくるか何もしない (呼ばれたらログを出すだけの) パススルー RMA plugin を作り、NCCL_RMA_PLUGIN で読ませて test_ep.py を単一ノード + fake node で回し、ログを見る順序の支配ができないので案 A は不成立。層 1 中心に切り替える
    3
    解決    		regMrSym を RDMA NIC 無しで実装できるか。NCCL が渡してくるバッファが cuMem VMM 由来か、共有可能なハンドルを取り出せるかパススルー plugin の regMrSym で cuMemRetainAllocationHandle / cuMemExportToShareableHandle を試し、成功するか確認ホストのステージングバッファ経由 (device → host → 相手 device) に落とす。忠実度は下がるが順序の支配は保てる

    3 つのうち 1 つでも駄目でも、層 0 と層 1 の価値は変わりません。そして層 0 と層 1 だけで、第 4 回で取り出した I2・I3・31 bit 周回・予算の算術・bit 詰めという 「実機で最も診断しづらい区画」はカバーできます。だからこの計画は、最悪の分岐でも無駄になりません。

    やめるべき唯一のシナリオ

    「WQE から MMIO からドライバまで含めて EFA なしで保証したい」という目標なら、案 B でも不十分です。その領域は実 EFA のテストを残すべきで、そこを emulator で埋めようとすると 偽の安心を製造します。逆に目標を「weak bundled-signal 契約の下でのプロトコル検証」に限定すれば、この計画には十分な価値があります。目標の書き換えを受け入れられるかが、着手の判断基準です。

分散レートリミッタ ― トークンバケツから原子的カウントまで

1 台のメモリで回数を数えるのは簡単だが、複数台に分散させた瞬間に「数え方」そのものが壊れる

この回の前提: 第 04 回 キャッシュ戦略、第 18 回 分離レベルと並行制御

レートリミッタ (rate limiter, 利用回数制限装置) は「1 人のユーザーが決められた回数を超えてリクエストを送れないようにする」仕組みです。目的は DDoS 攻撃のような大量リクエストからの防御、1 ユーザー 1 秒 1 件のようなスパム防止、そして下流の脆いサービスを守ること (レートリミットをかけることでクライアントがキャッシュを使うよう仕向ける効果もあります) です。1 台のサーバーでカウンタを持つだけなら単純ですが、サーバーを複数台に増やした瞬間、「誰が数えるか」「どの瞬間の値を正としてよいか」という分散システムそのものの難しさが現れます。この回では、まず 1 台で動くアルゴリズムを整理し、それを複数台に分散させたときに何が壊れ、実システムはどこで正確さを諦めているかを見ます。

1. この回で解く問題 ― なぜレートリミッタが要るのか

レートリミッタの目的は大きく 3 つあります。1 つ目は DDoS 攻撃のような大量リクエストからサービスを守ること。2 つ目はスパム防止で、例えば「1 ユーザーが 1 秒に送れるメッセージは 1 件まで」「1 つの IP から作れるアカウントは 1 日 5 件まで」のような濫用防止です。3 つ目は下流 (downstream) の壊れやすいサービスを保護することで、呼び出し回数に上限を課すことで、呼び出し側にキャッシュを使うよう仕向ける効果もあります。

上限を超えたリクエストに対しては、処理を拒否して HTTP 429 Too Many Requests を返すのが一般的です。これは「リクエストの内容が間違っている」という意味の 4xx エラーとは違い、「今は通せないので少し待ってから出し直してほしい」という時間的な制約を伝えるものです。

1 台のサーバーで「直近 1 秒に何件来たか」を数えるだけなら、メモリ上の変数を 1 つ持てば済みます。ところがサービスを複数台に増やした瞬間、この「数える」という一番単純な操作そのものが分散システムの問題になります。どの台が数えるのか、複数の台がそれぞれ数えた値をどう合算するのか ― これが本題です。

図: レートリミッタは上限内のリクエストだけを下流サービスへ通し、超えた分を 429 で拒否する。

2. 1 台で動く 4 つのアルゴリズム

トークンバケツ (token bucket) は、容量 C 個のバケツに一定の速さ r 個/秒でトークンを補充し、リクエスト 1 件につきトークン 1 個を消費します。トークンが無ければ拒否します。バケツに溜まっている分だけ一時的なバースト (急な集中) を許すのが特徴です。

リーキーバケツ (leaky bucket) はキューとして実装し、入ってきたリクエストを溜めつつ、一定の速さでしか外へ処理を出しません。トークンバケツと違い、出力は常に一定速度に均されるため、バーストはそのまま通さず平滑化します。

固定ウィンドウ (fixed window) は「直近 1 分間に何件来たか」を 1 分単位の箱で数える方式です。実装は最も簡単ですが、ウィンドウの境界をまたいだ瞬間に上限の約 2 倍のリクエストを通してしまう欠陥があります。

スライディングウィンドウ (sliding window) は固定ウィンドウの境界問題を解決します。各リクエストの時刻を記録して「直近 N 秒」を常にスライドさせながら数えるログ方式は正確ですが、メモリが件数に比例して増えます。前のウィンドウの件数を比率で重み付けして近似するカウンタ方式は、メモリを一定に抑えつつ境界問題をほぼ解消します。

図: 固定ウィンドウは境界をまたぐ瞬間、短時間に上限の約 2 倍のリクエストを許してしまう。

3. 複数台に分散すると「数える」が壊れる

アプリケーションサーバーを複数台に増やし、カウンタだけを 1 つの Redis に共有させたとします。素朴な実装は「現在値を GET して、上限未満なら INCR する」という 2 段階です。ここに競合状態 (race condition) が生まれます。上限 100 件のとき、2 台のサーバーがほぼ同時に GET して、どちらも現在値 99 を読み、どちらも「上限未満だ」と判断して INCR してしまうと、最終的な値は 101 になり上限を超えて許可してしまいます。第 18 回で見た「読んでから書く」操作がアトミック (不可分) でないと破綻する構図と同じです。

対策は、確認と加算を 1 回の不可分な操作にすることです。実務でよく使われるのは次の 2 つです。1 つ目は INCR 自体の戻り値で判定する 方法で、まず加算してから、戻ってきた新しい値が上限を超えていたら「この 1 件を拒否」と事後的に判定します。INCR はそれ自体が 1 つの不可分なコマンドなので、GET と INCR の間に他のリクエストが割り込む隙間がそもそも生まれません。2 つ目は Lua スクリプト による方法で、Redis はシングルスレッドでコマンドを処理するため、1 本のスクリプトの中に書いた「確認してから加算する」という複数ステップは、実行中に他のクライアントのコマンドが割り込まずに一括で終わります。

local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
  return 0
end
return 1

スライディングウィンドウログを Redis で実装する場合は、各リクエストの時刻をソート済み集合 (sorted set) に追加し、古い時刻を削除してから件数を数える、という複数コマンドの組み合わせになります。この一連の操作も Lua スクリプトか Redis のトランザクション (MULTI/EXEC) で包まないと、途中に他のリクエストが割り込んで数え間違える余地が残ります。

図: 確認と加算を 2 つのコマンドに分けると競合状態が生まれる。1 本の不可分な操作にすれば防げる。

4. レートリミッタを複数台に増やすと何を諦めるか

レートリミッタ自体を複数台に増やす方法は大きく 2 つあります。集中型ストア方式は、全台が 1 つの Redis のようなストアに問い合わせて確認・加算します。正確ですが、全リクエストがその 1 点を経由するためレイテンシが増え、ストアが落ちれば全体が止まる単一障害点になります。ローカル予算配分方式は、上限 (例えば 100 件/秒) をレートリミッタ 3 台にあらかじめ 33 件ずつ割り振り、各台が他台と通信せず自分の割り当てだけを見て判断します。レイテンシは低いままですが、トラフィックが台ごとに偏ると、1 台が早く枯渇して拒否し始める一方で別の台には余裕が残り続け、全体では本来の上限より少ない許可しかできない過小許可が起きます。

逆に、各台のローカルな使用量を定期的に中央へ同期する折衷方式を取ると、直前の同期から次の同期までの間は各台が「自分の割り当てはまだ残っている」と独立に判断し続けるため、同期の合間に複数台で合算すると上限を超えて許可してしまう過剰許可の瞬間が生まれます。実際のシステムの多くは、厳密な正確さを諦めて上限より少し低い安全マージンを設定し、低レイテンシな非同期同期を使うという割り切りをしています。

図: トラフィックの偏りに対し、ローカル予算配分は過小許可か過剰許可のどちらかに振れる。

5. 実システムでの設計判断

SDFC (System Design Fight Club) のレートリミッタに関する設計議論では、次のような現実的な論点が検討されています。スタンドアロンサービスか per-machine (各マシンに同居させるサイドカー) か という選択はレイテンシと精度/公平性のトレードオフであり、ユーザー ID 単位か IP 単位か という選択では、IP 単位は同じ社内ネットワークや CGNAT (ISP が複数ユーザーを 1 つの IP に集約する仕組み) の裏にいる複数ユーザーをまとめて 1 人として制限してしまう不公平さが論点になります。制限ルール自体の保管場所も、設定ファイル・専用のローカル Redis ストア・クライアントごとに柔らかくルールを変えられるビジネスルールエンジン (例: Drools) のどれを使うかという運用上の判断です。

実運用でよく併用される最適化が 2 つあります。リクエスト合流 (request collapsing) は、同一のリソースに対する多数の同時リクエストを検知し、実際の計算は 1 回だけ行って結果を待っている全クライアントに配る手法で、レートリミットとは別の仕組みですが下流保護という同じ目的を持ちます。クライアント側レートリミットは、クライアント自身が送信前に自分を絞ることで、そもそもサーバーに届くリクエスト数を減らす手法です。

設計判断の基準は「何を守るための制限か」です。決済ゲートウェイの不正利用防止カウンタのように、少しの数え間違いが不正利用の抜け道になる場合は正確さを優先して集中型ストアを選びます。一方、公開 API ゲートウェイのように多少のブレを許容できる場合は、低レイテンシを優先してローカル予算配分を選ぶのが合理的です。

この回の前提: 第 09 回 メモリとアドレス、第 16 回 ハザード

これまでの回では、レジスタファイルは読み書きが同じクロックで確定する前提で話を進めてきました。しかし外部のメモリやデバイスはそうとは限りません。アドレスを出してから値が返るまでに何サイクルもかかったり、相手がそもそも今は応答できなかったりします。この回では、CPU の外に出る配線を「バス」として抽象化し、相手の準備ができるまで待つための握手 (ハンドシェイク) の仕組みと、16 ビット単位のメモリから 1 バイトだけを取り出す難しさを、rj32 の実装を手がかりに整理します。

1. なぜ待ち合わせの仕組みが要るのか

結論を先に言うと、レジスタファイルの中は「同じクロックで確定する」世界ですが、CPU の外にある RAM やデバイスは「何サイクルかかるか分からない」世界です。両者をつなぐには、相手の準備ができるまで待つための合図、つまりバスの握手 (ハンドシェイク) が要ります。

第 08 回のレジスタファイルや第 07 回の ALU は、入力が決まればその同じクロック周期内に出力が確定しました。しかし外部の RAM は、アクセスのたびに 1 クロックで済むとは限りません。クロックが遅いメモリ、調停が必要な共有バス、今すぐ応答できないデバイスなど、相手の都合で遅れることがあります。CPU 側は「アドレスを出した」だけでは不十分で、「相手が受け取った」「相手が値を返した」ことを確認してから次に進む必要があります。

図: レジスタファイルは同じクロックで確定するが、外部メモリは何サイクル待つか分からない。だから握手が要る。

2. ロード・ストア命令とアドレス計算

rj32 には 4 つのロード・ストア系命令があります。load rd, [rs, imm4] はベースレジスタ rs に 4 ビット即値 imm4 を 2 倍して足したアドレスから 16 ビット語を読み、store [rs, imm4], rd は同じアドレスに書きます。loadb/storeb はその 8 ビット版です。

load  rd, [rs, imm4]    rd  <- mem[rs + imm4*2]
store [rs, imm4], rd    mem[rs + imm4*2] <- rd
loadb rd, [rs, imm4]    rd  <- memb[rs + imm4] & 0xff
storeb [rs, imm4], rd   memb[rs + imm4] <- rd & 0xff

ここでメモリは 16 ビット語単位の配列です。load/store はもともと語単位なので素直ですが、loadb/storeb は 1 バイトだけを読み書きしたいのに、メモリの最小単位は 2 バイト (1 語) しかありません。rj32 の docs/instructions.md 自身も、語単位の load/store については「メモリは現在語単位でインデックスされており、本来無視すべき下位 1 ビットが無視されていない」という実装の不完全さを記し、loadb/storeb についてはそれとは別に「まだ実装されていない (Not implemented yet)」とだけ明記しています。つまりバイト単位アクセスは、仕様としては素直に書けても、回路として素直には作れない部分だということです。

図: 16 ビット語メモリから 1 バイトだけを安全に書き換えるには、読み出してから書き戻すか、専用の書き込み許可線が要る。

3. バスの握手 ― Wishbone B4 の STB / CYC / ACK

「相手の準備ができるまで待つ」ための合図の付け方は、CPU の世界で決まった型があります。その代表が Wishbone という公開バス規格です。Wishbone B4 仕様が定める「classic standard SINGLE READ/WRITE cycle (標準の単発読み書きサイクル)」は、3 本の信号だけで握手を成立させます。

CYC_O (cycle, サイクル有効) ― マスター (CPU 側) が「これからバスサイクルを使う」ことを示す信号で、そのサイクルの最初から最後まで立てたままにします。STB_O (strobe, ストローブ) ― 1 回の転送そのものが有効であることを示す信号で、アドレスやデータ線はこの信号で修飾されます。ACK_I (acknowledge, 確認) ― スレーブ (メモリ側) が「転送を受け取った/データを用意した」ことを返す信号です。仕様は「STB_O はスレーブが ACK_I (または ERR_I、RTY_I) のいずれかを返すまで立てたままにする」と定めており、クロックの立ち上がりごとに ACK_I を確認し、立っていれば STB_O を下げます。これにより、マスターとスレーブの両方が転送の速さを調整できます。

図: 標準 READ サイクル。edge0 で CYC_O/STB_O を立てて要求、ACK_I が来るまで待ち、ACK_I を見た次の edge で CYC_O/STB_O を下げる。

WRITE サイクルも流れは同じで、違いは WE_O (write enable) を立て、アドレスと一緒にデータも DAT_O に出しておく点だけです。スレーブは ACK_I を返す代わりに、そのクロックでデータを取り込みます (ラッチ)。どちらの場合も、マスターは ACK_I を見てから次のサイクルへ進むので、スレーブがどれだけ待たせても (スレーブが「待機状態 (wait state)」を挿入しても) 正しく動きます。

4. rj32 のバス制御状態機械

rj32 の TODO.md には「標準のメモリバスインターフェース (wishbone?)」という項目が未完了のまま残っています。dig/wishbone.fsm は、その方向への実験として作られた状態機械で、信号名は公式の CYC_O/STB_O/ACK_I ではなく、rj32 独自の mem (メモリアクセス要求)・req・hold・ack・stall・done を使います。つまりこれは「Wishbone そのもの」ではなく「Wishbone が解く問題 (待ち合わせの握手) を rj32 なりに解こうとした実験」だと捉えるのが正確です。

状態は idle (待機) → wait (応答待ち) → done (完了) の 3 つを基本に、複数アクセスを続けて出すための hold (保留) 状態が加わります。mem が立つと idle から動き出し、ack が来れば即座に done へ、来なければ hold (次のアクセスを続ける予定がある場合) か wait (無い場合) で待ちます。ack が来るまでこのループを繰り返す点は、Wishbone の「ACK_I が来るまで STB_O を保持する」という規則と同じ考え方です。

図: rj32 の wishbone.fsm。ack が来るまで wait/hold に留まり、ack を見た瞬間に done へ進む ― Wishbone の ACK_I 待ちと同じ考え方。

5. どこで壊れるか ― パイプラインとの衝突

第 16 回で見た rj32 の 2 段パイプライン (fetch と execute) は、各段が 1 クロックで仕事を終える前提で組まれています。ところが load/store がバスの握手で複数クロックかかると、execute 段はその間ずっと同じ命令を抱えたまま進めなくなります。これが構造ハザードで、rj32 では stall という信号で fetch 段にも「今は進むな」と伝え、パイプライン全体を一時停止させて対処します。

rj32 自身の TODO.md には「Remove stall!!!!!」(stall を取り除け) という項目があります。つまり設計者自身も、全パイプラインを止めてしまう今の方式は作りやすいが荒い最初の一手であり、本来はバスで待っているアクセスだけを止めて他は進める、もっと細かい制御に置き換えたいと考えているということです。「動くものを一番簡単な方法でまず作り、後で磨く」という設計の順序がそのまま TODO に残っている例です。

図: load/store がバスで待たされると、rj32 は fetch 段まで含めてパイプライン全体を stall させる。

6. 実装のポイント

CYC と STB を混同しない。 Wishbone B4 の規則では、マスターが待機状態を作らないなら CYC_O と STB_O を同じ信号に兼用してよいとされています (PERMISSION 3.40)。ただしその場合でも両方の端子自体は用意する必要があり、アドレスやデータは STB_O が立っている間ずっと変化させてはいけません。ACK_I が来る前にアドレスを次の値に進めてしまうのが、握手を自分で実装するときに一番起きやすい間違いです。

バイト単位アクセスは後回しにしてよい設計判断。 rj32 の loadb/storeb が未実装のまま残っているのは手抜きではなく、優先順位の判断です。1 語を読んでから書き換えて書き戻す (read-modify-write) 方式は回路が単純ですが 1 回のバイト書き込みに読みと書きの 2 回分の時間がかかり、メモリ側にバイトごとの書き込み許可線 (Wishbone の SEL_O に相当する考え方) を持たせる方式は速いですがメモリの回路が複雑になります。どちらを選ぶかはメモリの構成と性能要件で決まるので、先に「とにかく動く語単位アクセス」を完成させてから決める、という rj32 の順序は妥当な判断です。

ACK が張り続ける場合にも壊れない状態機械にする。 Wishbone の規則 (RULE 3.55) は「スレーブが ACK_I を立て続けにしても、マスターは正常に動かなければならない」と定めています。状態機械を「ack パルスが来た瞬間だけを捉える」というエッジ検出の発想で作ると、ack が 2 クロック以上続いた場合に誤動作します。rj32 の wishbone.fsm で done 状態から戻る遷移に ack がそのまま条件として使われているのは、ack がどれだけ続いても状態が一意に決まるようにするための工夫です。

実際の SoC (チップ上にまとめた小さなコンピュータ全体) では、Wishbone のほかにも AXI-Lite や TileLink など似た役割の規格があり、どれも「CPU 側の要求信号」と「相手側の確認信号」を分けるという同じ骨格を持っています。CPU を FPGA に載せる (第 20 回) ときも、ブロック RAM や UART といった既製の部品はほぼ必ずこの形の握手で接続されます。

図: 1 バイトだけ書き換える 2 つの実装方針。rj32 はどちらも採用せず先送りにしている。

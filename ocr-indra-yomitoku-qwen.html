日本語 OCR を 3 つ並べてみた
Indra OCR 1.1 / Yomitoku / Qwen3.6-35B-A3B

結論から。まっすぐな文書ではどのエンジンもほぼ無傷だったが、ページを -12 度傾けた画像だけで差がはっきり出た。 Indra OCR 1.1 と Qwen3.6-35B-A3B は傾けた段落でも文字誤り率 (CER、認識結果と正解の文字列を何文字分書き換えれば一致するかの比率) が 0 % だったのに対し、Yomitoku は同じ画像で 58.4 % (正解 125 文字に対し 73 文字分のズレ) だった。原因は文字が読めなかったことではなく、 5 行の出力順がバラバラになったこと。

やったこと。Tokyo (ap-northeast-1) の自前 EKS クラスタ distai-eks に CPU 専用の pod を立てて Indra OCR 1.1 と Yomitoku を動かし、同じクラスタで既に稼働中の Qwen3.6-35B-A3B (vLLM, L40s GPU 2 枚) に同じ画像を HTTP で送った。 正解がわかっている自作の日本語画像 4 枚 (段落・表・請求書・回転画像) を読み取らせ、文字誤り率と所要時間を比べた。

1. 測ったのはこの 3 つ

Indra OCR 1.1 は datalab.to が出した軽量 OCR で、文字認識モデルは 1M パラメータ、前処理や並び替えまで含めた全体のパイプラインでも 7M パラメータしかない。GPU なしの CPU だけで動くことを売りにしていて、32 コアの AMD EPYC Genoa でページ 44 枚/秒を主張している。 Yomitoku は日本語に特化した OCR で、文字検出・文字認識・レイアウト解析・表構造認識という 4 つのモデルを組み合わせて動く。 Qwen3.6-35B-A3B は文字起こし専用ではなく、画像を読める大規模言語モデル (VLM) で、今回は「画像の文字をそのまま書き出して」と 指示するだけで OCR の代わりに使った。

公平な比較ではないことに注意。Qwen3.6-35B-A3B は GPU 2 枚を常時使って既に起動済みのサービスに 相乗りしただけ。Indra OCR と Yomitoku は「ゼロから CPU だけで動かす身軽さ」が売りなので、起動コストや GPU の有無まで含めると 前提が違う 3 者を並べていることになる。ここでの比較は「精度と速さの実測値」であって「どれを採用すべきか」の答えではない。

2. テスト画像は正解がわかっている自作の 4 枚

実際のスキャン文書ではなく、Pillow と Noto Sans CJK フォントで作った合成画像を使った。理由は単純で、正解の文字列を 最初から文字単位で持っているので、OCR の出力とズレなく比較できるから。「適当なベンチ」という位置づけなので、OmniDocBench のような 公式ベンチマークではなく、この 4 枚だけの簡易チェックだということは最初に明記しておく。

採点は、各エンジンの出力から | や #、<br>、HTML タグ、 コードフェンス (```) といった Markdown の飾りを取り除き、残った文字列から空白を全部消して正解文字列と比べた。 その文字列どうしの編集距離 (レーベンシュタイン距離、1 文字の挿入・削除・置換を 1 回として数える最短手数) を正解の文字数で割ったものが 文字誤り率 (CER) 。この採点スクリプト (run_bench.py) は作業中に 2 回バグを直している。1 つは Indra OCR が表を <table><tr><th> という生の HTML タグで返すのにそれを取り除いていなかった件、もう 1 つは Qwen が ときどき回答を ```markdown ... ``` で囲むのに気づかず、その飾りの分だけ余分に誤りとして数えていた件。 どちらも直した後は該当のスコアが 0 % まで下がった — つまり見かけの誤りはどちらも OCR の精度差ではなく採点側の正規化不足だった。

4. 回転画像だけで何が起きたか

rotated.png の正解は paragraph.png と同じ 5 行。Indra OCR と Qwen3.6-35B-A3B はこの 5 行をそのままの順番で正しく書き出した。 Yomitoku だけ、1 文字の誤認識 (「一号が」を「一号か」と読んだ) に加えて、5 行の出力順がバラバラになった。 文字そのものはほぼ読めているのに、編集距離で見ると「正解と全然違う場所に同じ文字列がある」状態になるため、CER が 58.4 % まで跳ね上がる。

気を付けること。これは「Yomitoku の文字認識が弱い」という話ではない。崩れたのは読み順 (レイアウト解析) で、Yomitoku 自身のオプションには読み順を --reading_order で明示指定する機能もある。今回は既定値 (auto) で 試しただけなので、回転耐性を正しく評価するにはこのオプションや前処理での回転補正も含めて追試すべき。

5. 表の読み取りでの小さな差

table.png では Indra OCR だけが 1 か所間違えた。4 列目のヘッダー「金額」が空欄になり、代わりに空の <th></th> が出力された。セルの中身 (24,000円 や 74,700円 などの数字) は全部正しく読めているので、見出し 1 語だけを取りこぼした格好。

6. 速さは前提が違う 3 者で測っている

応答時間を長さで比べると、Qwen3.6-35B-A3B が頭 1 つ速い。ただしこれは「GPU 2 枚を使って常時起動しているサービスに 1 枚送った」 時間であって、Indra OCR と Yomitoku は CPU だけの pod で、プロセスの起動やモデルの読み込みも含めて測っている。 特に Indra OCR は 1 枚ずつ起動すると 3 秒前後かかるが、4 枚を 1 つのプロセスにまとめて渡すと合計 1.68 秒まで縮み、 --timings で見える OCR 本体の処理は 1 枚あたり 114〜220 ms だった (ページを複数コアで並列処理するため)。 datalab.to 自身は 32 コアの AMD EPYC Genoa で 44 ページ/秒を主張しているが、今回使った Tokyo EKS の pod は CPU の上限を 4 コアに絞った m6a.4xlarge 上なので、そのスケールには届かない。それでも「軽い・速い」という傾向そのものは確認できた。

7. やっていないこと・次にやるべきこと

  • テスト画像は自作の合成画像 4 枚だけ。手書き文字、実際のスキャン文書特有のノイズ・汚れ・低解像度、縦書きの文書は 1 枚も試していない。
  • OmniDocBench のような公式ベンチマークは使っていない。あくまで正解が厳密にわかる自作チェックでの結果。
  • Yomitoku は既定の読み順設定 (auto) でしか試していない。--reading_order や GPU 実行 (-d cuda) での回転耐性は未確認。
  • Qwen3.6-35B-A3B へのプロンプトは 1 種類だけ。プロンプトを変えれば結果が変わる可能性がある。
  • 次にやるなら、実際にスキャンした日本語の請求書・申込書・手書きメモで同じ 3 方式を比べ、特に回転・傾き・低解像度といった 「崩れた入力」に対する耐性を確かめるのが優先度が高い。

まとめ。正立した日本語文書なら 3 方式とも十分実用的。差が出たのは回転画像で、Indra OCR (1M パラメータ) と Qwen3.6-35B-A3B は崩れず、Yomitoku だけ読み順が入れ替わった。Indra OCR は CPU だけで軽く速く動く点が際立ち、 Qwen3.6-35B-A3B は精度・速度ともに最良だが GPU の常時稼働が前提にある。

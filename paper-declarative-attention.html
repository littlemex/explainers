どこを読むかを、モデル自身に宣言させる

chain-of-thought に attention の計画を書かせる Declarative Attention を読む

← 論文理解シリーズの目次へ

0この記事は何を読み解くのか

「Declarative Attention」(KAIST AI と Google DeepMind、arXiv:2609.02737v1, 2026-09-02) は、長い文脈を読むときにどの部分に attention するかをモデル自身に宣言させて、推論エンジンがその宣言どおりに KV キャッシュの読み出しを削る、という提案です。

一言でいうと
attention の重みは文脈のごく一部に集中しているのに、モデルは毎ステップ KV キャッシュを全部読んでその一部を探しています。1M トークンの会話なら、返答の 1 トークンごとに全部を走査します。既存の対策は軽量なスコアで「読むべき場所」を予測しますが、そのスコア計算自体が毎ステップ $O(N)$ かかります。この論文の問いは単純です。そもそもモデルは、どこが関係あるか自分で分かっているのではないか。そこで chain-of-thought の中に <global> / <focus> / <local> というタグを書かせ、推論エンジンがそれをtool call のようにパースしてマスクを組みます。追加の学習はゼロ。既製モデルへの zero-shot で、decode 中の attended トークンが 52.0% / 31.1% 減、精度低下は 1.27pp / 2.75pp です。
項目値
解く問題長文脈の decode では KV キャッシュの読み出しレイテンシが支配的。Qwen-3.5-397B-A17B なら 1M トークンで1 ステップあたり約 15 GB の読み出しで、これは 17B の活性パラメータを読むのと同程度
既存手法との違い静的なヒューリスティック (recency / 過去の attention 量) は将来のクエリが要るトークンを当てられない。動的な proxy scan は当てられるが毎ステップ $O(N)$ の走査コストが残る。DA は選択コストを完全に消す ($O(N)$ の読みはモデルが宣言した global 期間だけに残る)
3 つのモード<global> は文脈全体を見て次に読む場所を探す。<focus magic_chunks="7"> は指定した断片だけを見る。<local> は文脈を一切見ず、自分の出力だけで考える
文脈の渡し方約 2,048 トークンごとに分割し、「magic chunk」という名前で tool 応答の形に見せる。実際に tool は呼ばれない。境界をモデルが post-training で慣れている特殊トークンに一致させるための工夫
実装vLLM の attention metadata builder にフックを入れ、KV ブロックテーブルを書き換えるだけ。カーネル改造もスケジューラ変更も無し。FlashAttention はそのまま動く
主結果15 の長文脈タスクで、Gemma-4-31B は attended トークン -52.0% ・ 精度 -1.27pp、Qwen-3.6-27B は -31.1% ・ -2.75pp
節約の出どころプロンプト形式だけの ablation (DA-nm) は attended トークンがむしろ vanilla より 66.2% 増える。マスクがそれを覆して -52.0% にする。節約はマスクから来ている
スケーリングモデルが大きいほど精度の差が縮む (Gemma は vanilla 比 29% → 99%)。文脈が長いほど絶対の節約が伸びる (短文脈で約 1M、最長 bin で約 21M トークン)

1なぜ decode で attention が主役なのか

前提を押さえます。1 トークン生成するたびに、Transformer はそれまでの全トークンの KV を HBM から読みます。長文脈ではこの読み出しが decode 時間を支配します。

論文が挙げる例が具体的です。Qwen-3.5-397B-A17B で 1M トークンの文脈を持つと、1 系列あたり約 15 GB の KV キャッシュを毎ステップ読むことになります。これは活性パラメータ 17B を読むのと同程度の帯域要求です。モデルを 1 回読むのと同じ重さのものを、文脈のために毎回読んでいるわけです。

しかも、その大半は要りません。attention のスコアはごく一部のトークンに集中します。問題はどこに集中するかが事前に分からないことです。真のスコアは attention 行列を計算し終わってからしか分かりません。ここで既存研究は 2 系統に分かれます。

図 1: 3 系統の位置関係。DA が消しているのは「どこを読むかを決めるコスト」そのもので、読む量の削減はその結果として付いてくる

人の読み方との対比。長い文書を読んで質問に答えるとき、人は1 語ごとに全文を読み返しません。論文の出発点はこの直観で、attention のスコアが実際にごく一部に集中しているという実証と合わせて、「全部読む」機構は認知的にも計算的にも過剰だと整理しています。DA はその過剰を、モデル自身の言葉で削ります。

2protocol — 3 つのモードと magic chunk

DA がモデルに要求するのは 2 つだけです。(i) attention の範囲が変わらない連続した区間に推論を区切ること、(ii) その範囲を決まったタグ構文で宣言すること。以下は論文の例です。

質問: Acme 社は創業から何年後に上場したか <global> 創業年と上場年が必要だ。会社沿革は Magic Chunk 2 にありそうだ。 </global> <focus magic_chunks="2">"Acme Corp was founded in 2003 in San Jose."</focus> <global> 上場年がまだ無い。Magic Chunk 7 が財務の節目を扱っている。 </global> <focus magic_chunks="7">"Acme Corp went public on the NYSE in 2011."</focus> <local>2011 - 2003 = 8 years.</local> <answer>8 years</answer>
モード文脈のうち何が見えるか役割
<global>全セグメント探索。全体を見渡して次にどこを読むかを決め、なぜそこが関係あるかを短く書く
<focus>タグで名指ししたセグメントだけ特定の領域での推論。必要な値をそこからverbatim で抜き出す
<local>何も見えない自己完結した推論。質問に対する計画と、抜き出した値からの最終的な合成

どのモードでも、質問と指示と自分のそれまでの出力は常に見えます。モードが変えるのは文脈領域の可視性だけです。そしていつ、何回、どの順でモードを使うかは protocol が縛りません。zero-shot で引き出すので、プロンプトはモードごとの使い方の指針を与えて足場を作るだけです。

なぜ「magic chunk」という名前なのか

focus モードを使うには、モデルが読みたい領域を名指しできる必要があります。そのためには、セグメントがどこで始まってどこで終わるかをモデルが追跡できないといけません。ここで論文の工夫が 2 つ入ります。

工夫中身理由
分割の位置約 2,048 トークンを目標に、上限を超えた単位だけを、いちばん粗い境界から順に切る。段落 (空行) → 改行 → 文末 → 節の区切り → 語境界意味の境界に合わせたい。語の内側で切れることは無い
提示の形各セグメントをtool 応答として見せる。assistant が get_magic_chunk を呼び、tool 応答が Magic Chunk N という見出しでテキストを返す形の会話を、あらかじめ組んでおく境界がモデルが post-training で何度も見た特殊トークンの上に乗る。慣れた境界のほうが追跡が正確

tool は実際には 1 回も実行されません。生成が始まる前に全セグメントが所定の位置にあります。「モデルが文書を magic chunk 単位で 1 つずつ取ってきた」という履歴に見せかけているだけです。名前を「magic chunk」にしたのも意図的で、文書自身の章や節と混同させないためです。

図 2: 左がプロンプト、右が生成テキストから導かれるマスク。行が推論ステップで、破線が読まないセグメント。F が focus で名指しされたセグメント

3実装 — テキストからマスクへ

宣言を効かせるには、生成の途中でマスクを差し替える仕組みが要ります。ここが「アイデア」と「速くなる実装」を分ける部分です。

state machine

DA の state machine は推論エンジンの横で走り、出力ストリームを読んでモード遷移を拾います。遷移するのは開きタグの閉じ括弧 > の文字で、対応する閉じタグで global に戻ります。既定状態は global です。

block 整列がすべてを決める

ここが実装上いちばん重要な洞察です。vLLM は KV キャッシュを16 から 32 トークンの固定ブロックで保持し、attention カーネルはブロック単位で読みます。だから、

散らばった個別トークンを落としても、メモリ読み出しは 1 バイトも減りません。時間が減るのはブロックまるごとを飛ばせたときだけです。そこで state machine はブロック粒度でマスクを掛け、保持する区間を外側に丸めます (モデルが宣言したトークンを絶対に落とさないため)。代償は区間の両端でせいぜい 1 ブロックずつ、つまり 2,048 トークンのセグメントに対して数十トークンです。結果はただのブロックリストなので、FlashAttention のような既存カーネルがそのまま動きます。

vLLM への統合はattention metadata builder へのフック 1 か所で、カーネル改造もスケジューラ変更もありません。各 decode ステップで、そのリクエストのKV キャッシュのブロックテーブルを書き換えるだけ。カーネルは単に読む量が減ります。

各 decode ステップでやること 1. 出力ストリームから現在のモードを決める (タグをパースするだけ) 2. モードから「見せるセグメント」を決める (global = 全部 / focus = 名指し / local = なし) 3. その範囲をブロック境界に外側へ丸める (宣言されたトークンを落とさない) 4. ブロックテーブルを書き換える (カーネルは変更なし)

トレードオフを先に書いておく

DA は「decode ステップを増やして、1 ステップあたりの attention コストを下げる」取引です。これが得になるかは配備の状況に依存します。論文はここを roofline wall-time という枠組みで整理していて、結論は大バッチ ・ 長文脈のサービングで最も効くというものです。

コスト成分何に比例するかDA で減るか
FFN と射影の行列積decode ステップ数と活性パラメータ。文脈長には依存しない。大バッチでパラメータ読み出しが償却され compute-bound になる減らない (ステップが増えるので少し増える)
global attention の KV 読み出し文脈長 × decode ステップ数。系列ごとの読み出しなのでバッチで償却されず memory-bound のままここだけ減る
効率的な層の読み出しステップ数のみ。SWA の窓や GDN の再帰状態は固定サイズ減らない (削る余地が無い)

4【体験】15 タスクの主結果

評価は 15 の長文脈ソース (RULER ・ LongBench v1/v2 ・ LooGLE ・ ZeroSCROLLS) で、単一スパンの検索と複数スパンの推論の 2 カテゴリに分かれます。文脈長は 6.4K から 1,071K まで。3 つの arm を比べます。

arm中身何を切り分けるか

DA-nm (no mask)DA と同じプロンプトだが、attention は完全な causal のままVanilla との差 = プロンプト形式だけの効果
DA同じプロンプト + マスクを効かせるDA-nm との差 = マスクだけの効果

集計値は Gemma で精度 87.01 → 85.74 (-1.27pp)、attended トークン 13.43M → 6.45M (-52.0%)。Qwen で 85.31 → 82.56 (-2.75pp)、22.54M → 15.52M (-31.1%) です。ただし集計はタスクごとのばらつきを隠します。

観察中身

絶対の節約が大きいタスクいちばん文脈が長いところ。code_repo で 41.8M (Gemma) と 52.0M (Qwen)、dialogue_history で 22.1M と 39.1M トークン
Qwen で増えるタスクもある5 つのソースで attended トークンがvanilla を上回ります (とくに qmsum と LBv2 の 2 つの QA)。DA の生成が長いぶんが 1 ステップの節約を食う
評価は LLM judge です。自由形式の生成なので完全一致では測れず、質問ごとに Gemini-3-Flash が厳格な受理基準を作り、それを thinking を有効にした Qwen-3.5-4B が適用します。judge の検証は丁寧で、2,993 応答のサンプルでフロンティア judge (Gemini-3.1-Pro) と個別判定が 98.53% 一致 ($\kappa=0.940$)、per-cell の精度の相関は $r=0.992$、不一致は対称 (McNemar $p=0.65$)、全体の差は -0.13pp です。形式の失敗は不正解として数えられます。

5【体験】節約はマスクから来る

この論文でいちばん効いている切り分けがここです。DA の数字は「プロンプトを変えたから」なのか「マスクを掛けたから」なのか。3 つの arm を 3 つの軸で見ると、答えは一意に決まります。

3 つの軸が示すことを順に並べます。

軸読み取れること
精度DA-nm はほぼ無損失。Gemma では vanilla と同点 (87.01 対 87.01)、Qwen でも 0.69pp 差。チャンク化されたプロンプト形式そのものは、ほぼ無料
decode ステップDA も DA-nm も vanilla より15 - 35% 多くステップを踏みます (Gemma 332 → 448 で +35%、Qwen 573 → 752 で +31%)。zero-shot protocol の副産物
attended トークンDA-nm は vanilla より増えます (Gemma +66.2%、Qwen +28.8%)。増えたステップを全 attention で走るからです。マスクを入れるとそこから 71.1% (Gemma) と 46.5% (Qwen) 削られ、vanilla より下に落ちます
この 3 段の動きが結論です。Gemma では vanilla より 66.2% 多いところから、マスクによって vanilla より 52.0% 少ないところまで動きます。つまり節約はプロンプトではなく完全にマスクから来ています。そして精度のコストも同じ場所から来ていて、DA-nm がほぼ無損失なので、-1.27pp (Gemma) と -2.06pp (Qwen) の大半はマスクが情報を隠したぶんです。利得と損失が同じ 1 つの機構に帰属するという、珍しく綺麗な切り分けになっています。

6規模と文脈長でどうスケールするか

zero-shot でこれをやらせるので、モデルの地力が protocol の成否を決めます。論文は 6 モデル (Gemma-4 の 31B / 12B / E4B、Qwen の 3.6-27B / 3.5-9B / 3.5-4B) で測っています。

指標小さいモデル大きいモデル読み方
vanilla 比の精度 (Gemma)E4B で 29%31B で 99%規模とともに単調に parity へ近づく
vanilla 比の精度 (Qwen)4B で 64%27B で 97%同じ傾向
focus の成功率 (Gemma)E4B で 58%31B で 99%タグが有効なチャンク参照として解決できた割合
focus の成功率 (Qwen)4B で 89%27B で 99%最大のモデルはほぼ完璧に protocol を守る
1 応答あたりの focus 試行数約 1.4 - 1.9 で、規模の傾向なし強いモデルは試行を減らすのではなく、より確実にパースさせることで勝っている
vanilla 比の attended トークンGemma は 46 - 48%、Qwen は 50 - 69%規模の傾向は無い。1 ステップの節約率は約 0.5 でほぼ規模不変で、総量の差は生成の長さから来る

いちばん小さい Gemma-4-E4B が vanilla 比 29% しか保てないのは、推論の失敗というより protocol を守れない失敗です。focus の成功率が 58% しかなく、パースできる答えを出せていません。論文の結論は「DA には最低限の地力が必要で、最小のモデルはまだそこに達していない」。逆に言えば、この手法はモデルが強くなるほど効く方向のスケーリングを持っています。

Gemma-4-12B だけ vanilla より attended トークンが多いという例外があります。原因はマスクの失敗ではなく、DA 応答の約 6% が 8K の生成上限まで終わらないことです。非終了の応答を両 arm から除くと vanilla の 98% まで下がります。Qwen-3.5-4B にも同じ効果が弱く出て (50% → 38%)、しかもこちらは vanilla 側でも非終了が起きるので、DA の性質ではなく小さいモデルの性質だと整理されています。

文脈が長いほど得になる

15 ソースをまとめて文脈長で bin に分けると、形はこうです。

文脈長vanilla 比の精度attended トークンの差
32K まで約 1pp 以内約 -1M トークン
最長の bin約 96% まで緩やかに低下約 -21M トークン

1 ステップの節約率が約 50% でほぼ一定なので、絶対の節約は生の文脈長に比例して伸びます。長文脈の decode がいちばん高くつくところで、いちばん効くという形です。一方で長文脈での精度低下はマスク由来だと分かります。DA-nm の線にはこの低下が現れません。

モードの使い方も文脈長で変わります。Gemma-4-31B では <global> が生成トークンの約 27% で、残り 73% が focus と local です。この 2 つは安いモードで、vanilla の 1 ステップに対してそれぞれ約 12% と 6% のトークンしか読みません (トークンあたり 76 - 99% の節約)。ただしglobal の割合は最長の bin で約 45% まで上がり、そこでの総節約に上限をかけます。

7【体験】roofline の内訳

attended トークンが半分になっても、実際の時間が半分になるとは限りません。論文は decode 時間を 3 成分に分けて、B200 1 枚での roofline 見積りを出しています。各成分をそれぞれのハードウェア上限で課金するという考え方です。

行列積 (compute-bound) global attention の KV 読み出し 効率的な層の読み出し (削れない床)

数字の形を追います。Gemma では global の読み出しが 1,100 GB から 528 GB へ半分以下に落ちます。ところが行列積は 22.9 → 30.9 ms、効率的な層は 49.7 → 67.1 ms と増えます。decode ステップが 35% 増えたぶんです。合計は 269.1 → 192.3 ms で 0.71 倍。

2 つのモデルで「どれだけ残るか」が違う理由。Qwen の効率的な層は GDN の再帰状態で、DA の attention 時間のうちわずか 5% です。だから global の削減がほぼそのまま通ります。一方 Gemma の効率的な層はSWA の床で、60 層のうち 50 層を占め、DA の attention 時間の 42% です。global 自体は半分以下に落ちているのに、この床が節約の上限を決めます。同じマスクでも、アーキテクチャの「削れない部分」の大きさで見返りが変わる、というのが実務的な教訓です。
これは実測の wall-clock ではありません。MFU 40% (compute-bound) と MBU 70% (memory-bound) を仮定した理論上の天井で、しかもprefill を除いています (phase-disaggregated なサービングでは別のプールで走るという前提)。DA が触るのは decode 側だけなので切り出しは妥当ですが、0.71 倍という数字は実装を回して測ったものではないと読む必要があります。

8【体験】この前提は将来も成り立つか

DA の価値は「global attention が decode コストの主役である」という前提に乗っています。ところが最近のアーキテクチャは、まさにそこを削りに来ています。論文はこの反論を自分で立てて、計算しています。

アーキテクチャ側の努力は本物です。大半の層を局所 ・ 線形 attention (SWA、GDN) に置き換え、各エントリを低ランク表現 (MLA) やトークン統合で縮め、読み出し自体を軽量な indexer で減らす。合わせて文脈トークンあたりの KV 読み出しバイト数は最大 2 桁下がっています。

それでも、1M トークンでは attention が decode 時間の大半を占めます。vanilla の global attention を残している Kimi-K3 は 94%、indexer ベースの疎な設計でも 56 - 97%。ただし表を切り替えると分かるとおり、この比率は文脈長に強く依存します。GLM-5.3-Flash は 1M で 56.49% ですが、128K では 14.25% まで落ちます。攻めた設計 + 短めの文脈では、DA が削れる余地は小さいということです。

agentic な運用についての論点。「エージェントは tool call で少しずつ文脈を取ってくるから、検索が既に問題を解いているのでは」という反論に対して、論文の答えは明確です。検索は「何を文脈に入れるか」を決め、DA は「入ったもののうち何を読むか」を決める。別の問題です。むしろ検索は DA が狙うコストを増やします。tool の結果は残りのエピソードの間ずっと文脈に居座るのに、それが関係あるのは要求したステップの周辺だけです。結果が積み上がるほど文脈は伸び、ターンをまたいで持ち越されます。agentic な文脈こそ DA の節約が最大になる領域という主張です。

9【体験】うまくいかない 6 つのタスク

ここは論文の付録にある内容ですが、手法の輪郭を理解するのに最も重要な部分です。主要スイートの 15 ソースは、DA が噛み合うタスクを選んだ結果で、噛み合わない 6 つは別に報告されています。

Vanilla DA-nm DA

この 6 つでは、精度が 63.28 → 54.26 に落ち、attended トークンは 38.62M → 45.97M とvanilla より増えます。主要スイートの結論とは逆向きです。論文はこれを 2 つの構造的な噛み合わなさに分類しています。

失敗の型中身例何が起きるか
分割で証拠が壊れる答えに必要な情報がセグメント分割を跨いで生き残らない全セグメントにまたがる数え上げ (cwe)、segmenter が割ってしまう表 (structured_data)精度が -30 / -21pp 崩壊する。1 ステップの attention は下がっているのに
出力長が文書に比例するセグメントや項目ごとに 1 単位の出力を出すタスク語頻度の列挙 (fwe)、セグメント毎の要約 (summ_screen_fd)、全文書の並べ替え (book_sum_sort)、例ごとの in-context learningdecode ステップが文書長に比例するので、1 ステップの節約があっても総量が積み上がる

論文の弁明にも筋があります。1 ステップあたりの attention は 6 つすべてで -39% から -67% 下がっています。機構は働いていて、噛み合っていないのは分解の仕方です。型 1 は表を割らない構造認識の分割と、focus をセグメント上で掃く map-reduce パターンで対処できる。型 2 は精度ではなく decode 長の問題で、長い出力を global ではなく focus の下で書かせれば 1 ステップのコストが抑えられる、と。

さらに 2 つのソースは完全に除外されています。RULER の qa_1 と qa_2 で、理由はタスクのプロンプトが中間推論を明示的に禁止していることです ("Only give me the answer and do not output any other words")。DA は CoT の中に宣言を書かせる手法なので、中間推論を禁じられると成立しません。cwe / fwe / vt でも同じ摩擦があると注記されています。この制約は zero-shot 版に固有ですが、「思考を書かせない」運用とは原理的に両立しないという性質は覚えておく価値があります。

10批判的に読む

どこが確かで、どこが確かでないかを分けます。

論点読み方
タスクスイートの選び方いちばん重要な論点です。15 ソースは DA が噛み合うタスクを選んだ結果で、噛み合わない 6 つは付録で、さらに 2 つは完全に除外されています。付録の 6 つでは精度 -9.02pp かつ attended トークン +19% と結論が反転します。開示は誠実 (数字も理由も分類も書いてある) ですが、ヘッドラインの -52.0% / -1.27pp はこの選択の後の数字です
wall-clock が実測されていない0.71 倍 / 0.77 倍はMFU 40% ・ MBU 70% を仮定した roofline の理論値です。vLLM 統合は実装されていて attended トークンは実測ですが、時間そのものは測られていません。カーネル起動やブロックテーブル書き換えのオーバーヘッド、実バッチでの干渉は入っていません
decode ステップの増加31 - 35% 増えます。roofline では行列積と局所読み出しが実際に増えています (Gemma で 22.9 → 30.9 ms、49.7 → 67.1 ms)。compute-bound 寄りの配備 (小さい文脈 ・ 小バッチ) では、この増加が節約を食い潰す可能性があります。論文もそれを「配備の状況に依存する」と書いています
thinking モードと併用できない「thinking タグの中では protocol に従えなかった」ため、全モデルで thinking を無効にしています。推論モデルの主力の使い方と衝突するので、実務ではここが最初の障害になります
global 比率が節約の天井最長の bin では global が生成の 45% を占めます。global では節約が定義上 0 なので、いちばん節約したい長さでいちばん global が増えるという逆行があります。zero-shot でモデルが決めているぶんなので改善余地とも読めますが、現状の数字はこの制約込みです
前提の耐用年数attention が decode 時間の大半という前提は、文脈長と設計に強く依存します。GLM-5.3-Flash では 1M で 56% ・ 128K で 14% です。攻めた KV 最適化 + 中程度の文脈という組み合わせでは DA の削り代が小さくなります
マスクが精度を削る量DA-nm がほぼ無損失なので、精度低下はほぼ全部マスク由来と切り分けられています。これは綺麗な結果ですが、同時に「宣言が外れたときに救う仕組みが無い」ことも意味します。宣言が誤ったセグメントを指したら、その情報は物理的に見えません
セグメント分割がヒューリスティック約 2,048 トークンを目標に境界の粗さ順で切るだけです。論文も「簡便のための近似」と書いています。表を割る失敗 (structured_data で -21pp) はここから来ています
zero-shot ゆえの不確定性モード構成も focus 試行数 (1.4 - 1.9) もモデルが勝手に決めた値で、タスクにとって最適とは限りません。論文はこれを「下限」の根拠として使っていて、主張としては妥当ですが、いま得られる数字が設計の結果ではないことは押さえるべきです
再現性本文にリポジトリの記載がありません。ただしプロンプト全文 ・ segmenter ・ vLLM 統合の詳細 ・ judge のプロンプトが付録にあり、変更点が「フック 1 か所」に局所化されているので移植は現実的です
この論文の良い点ablation (DA-nm) の設計が主張と正確に対応している。失敗タスクを分類して数字ごと出している。roofline を「実測ではない」と繰り返し明示している。judge を 2,993 応答でフロンティアモデルと突き合わせている。自分の主張を「下限」と呼ぶ節度も含めて、誇張の少ない書き方です

11まとめ

Declarative Attention の芯は 1 つの視点の転換です。どこを読むかを活性値から推測するのをやめて、モデルに言わせる。<global> で探し、<focus magic_chunks="7"> で読み、<local> で考える。推論エンジンはそのテキストを tool call のようにパースして、KV ブロックテーブルを書き換えるだけです。選択のコストがゼロになり、$O(N)$ の読み出しはモデルが宣言した global 期間だけに残ります。既製モデルへの zero-shot で attended トークンが 52.0% / 31.1% 減り、精度低下は 1.27pp / 2.75pp。節約はプロンプト形式ではなくマスクから来ていることが ablation で切り分けられていて、同じマスクが精度コストの大半も生んでいます。モデルが大きいほど差が縮み、文脈が長いほど絶対の節約が伸びる。ただし protocol と噛み合わない 6 つのタスクでは結論が反転し、wall-clock は測られていません。

実務に持ち帰れるもの

3 つあります。1 つ目、ブロック粒度で考える。散らばったトークンを落としてもメモリ読み出しは減りません。マスクの設計は KV キャッシュのブロック構造から出発すべきです。2 つ目、削れない床を先に測る。同じマスクでも SWA の床が 42% あるモデルと GDN が 5% のモデルでは見返りが違います。3 つ目、境界はモデルが慣れた形に置く。セグメントの区切りを tool 応答の特殊トークンに乗せるという工夫だけで、最大モデルの参照成功率が 99% に届いています。

どこがまだ空いているのか

いちばん大きいのはprotocol への post-trainingで、論文自身がそこを「下限である理由」として挙げています。モード選択の方策と、表を壊さない分解をモデルに教えられれば、9 節の失敗の両方に効きます。次にthinking モードとの共存。いまは併用できないので、推論モデルの主流の使い方から外れます。そして実測の wall-clock です。attended トークンの削減は実測されていますが、それが実バッチの時間になる部分はまだ理論値のままです。

観測性 (observability, 外部から見える手がかりだけで内部の状態を言い当てられる性質) の本質は、分散トレーシングで「このリクエストはどこで時間を使ったか」を、メトリクスで「全体として今どういう状態か」を、ログで「その瞬間に何が記録されたか」を答え、3 つを同じ相関 ID で結びつけ、最後に SLO (Service Level Objective, 内部の目標値) とエラーバジェットという 1 つの数値に落として「直すか・進むか」を機械的に決めることにある。ここでは分散トレーシングの文脈伝播とサンプリング、メトリクスのカーディナリティ、ログ集約、SLI/SLO/エラーバジェットの順に、具体的な数字とともに確認する。

1. なぜ観測性が要るのか

1 台のモノリスなら、落ちた瞬間のスタックトレースを 1 つ読めば原因まで辿れました。サービスが何十個に分かれ、1 つのリクエストがネットワークを何ホップも跨ぐようになると、どのサービスのどの処理が遅かったかは、どこにも 1 本の記録として残りません。観測性 (observability) とは、新しいコードを書き足して計測を追加しなくても、外部から見える手がかりだけで内部の未知の問いに答えられる性質を指します。あらかじめ決めた閾値だけを見張る「監視 (monitoring)」よりも範囲が広く、想定していなかった故障モードにも事後的に答えられることが目標です。

この問いに答えるための道具は 3 本柱に分かれます。トレースは「このリクエストはどこで時間を使ったか」という 1 回限りの経路の問いに答え、メトリクスは「過去 1 時間、全体の p99 レイテンシはどう動いたか」という集計の問いに答え、ログは「その瞬間、そのサービスで何が記録されていたか」という個々の出来事の問いに答えます。どれか 1 つで全部を代用することはできません。

図: 同じ 1 回のリクエストに対して、トレース ・ メトリクス ・ ログはそれぞれ別の問いに答える。

2. 分散トレーシングの trace / span と文脈伝播

Google は 2010 年の Dapper 論文で、社内の全サービスに共通の仕組みを後付けした経緯を報告しています。考え方は単純です。1 回のリクエスト全体に trace-id という 1 つの識別子を割り当て、その中の各サービスでの処理区間を span として記録します。各 span は開始 ・ 終了時刻を持ち、自分を呼んだ span を親として持つので、trace 全体は木構造になります。

この仕組みが機能するには、trace-id と呼び出し元の span-id をリクエストそのものに乗せてサービス間で伝播させる必要があります。これを各トレーシングベンダーが独自のヘッダ形式で実装していたため、別の計測ツールを使うサービスを跨ぐと trace が途切れていました。W3C Trace Context はこれを 1 本の HTTP ヘッダ traceparent に標準化し、version-trace_id-parent_id-trace_flags (例: 16 バイトの trace-id ・ 8 バイトの span-id ・ 1 バイトのフラグ) という固定形式で表現します。あるサービスがリクエストを受け取ると、受信した trace-id はそのまま引き継ぎ、自分が新しく発行した span-id を次のホップへの parent-id として載せ替えて転送します。

図: trace-id は全ホップで共通、span-id だけがホップごとに新しく発行され親子関係を作る。

3. サンプリングで「全部見る」コストを削る

なぜ全リクエストの trace を残さないのか。SDFC の distributed-tracing の課題設定に出てくる数字で考えます。1000 個のサービス、各サービス平均 100 台、各台で平均 100 QPS だと、全体で毎秒 1000 万リクエストが発生します。1 つの span が平均 5 〜 6 KB (タイムスタンプ、親子の ID、リクエスト / レスポンスの要約、ログ数件) だとすると、全件を 1 年保存するだけで 1.5 PB 近くに達します。しかもトレーシングは「本来の処理を邪魔しない (non-obtrusive)」ことが要件であり、記録自体が遅延を増やしては意味がありません。そこで down-sampling (間引き、例えば 1000 件に 1 件だけ残す 0.1 %) が標準で入っています。

サンプリングの判断をどこで行うかには 2 つの方式があります。head-based sampling は、リクエストの入口 (root span) でまだ結果が分からないうちに乱数で残すかどうかを決め、その決定を全ホップに伝播させます。安く一貫して決められますが、まれにしか起きない失敗を含むトレースも同じ確率で捨ててしまいます。tail-based sampling は、trace 全体が完了するまで各ホップの span を集約レイヤで一時的にバッファし、エラーになったものや著しく遅かったものを優先して残します。狙った事例を取りこぼしにくい代わりに、trace が終わるまでの保持コストと、分散した span を後から集めて判定するコストがかかります (OpenTelemetry のサンプリングの考え方に基づく)。

図: head-based は入口で即決、tail-based は結果が出るまで待ってから選ぶ。

4. メトリクスの集約とカーディナリティ爆発

メトリクスは「成功した回数」「CPU 使用率」のような数値を時系列として集計したものです。SDFC の metrics-service の課題設定では、Pinterest の実例として毎分 10 億個を超えるデータポイントを扱う規模が挙げられています。この量を生データのまま 1 件ずつ中央に送って集計するのは現実的ではなく、収集の近くで事前集約してから送る設計が前提になります。

収集方式には push (アプリ自身が収集サーバーへ送る。再送の責任と障害時に誰が気づくかの責任がアプリ側チームに残る) と pull (収集サーバーが対象を定期的に取りに行く。再送の責任は収集側に一元化されるが、対象が動的に増減する環境ではサービスディスカバリが必要になる) があります。Prometheus の公式ブログは「pull はスケールしない」という通説に対して、サービスディスカバリと組み合わせれば大規模な環境でも成立すると説明しています。

規模が出た後に必ず問題になるのがカーディナリティ (cardinality) です。メトリクス名とラベル (タグ) の値の組み合わせごとに、独立した 1 本の時系列が作られます。user_id や生の URL パスのように値の種類数が非常に多いラベルを付けると、組み合わせの数がラベル値の種類数に比例して爆発し、1 本のカウンタのつもりで実装したものが実運用では数百万本の時系列になり、保存と索引のコストが跳ね上がります。これがトレース / ログのような高カーディナリティなデータと、メトリクスのような低カーディナリティを前提にしたデータを、意図的に別のストレージに分けて扱う理由です。

図: ラベルに値の種類数が多い項目を入れると、時系列の本数が組み合わせの数だけ増える。

5. ログ集約と、3 本柱をつなぐ相関 ID

ログは個々の出来事をテキストで残す最も細かい記録です。ELK スタック (Elasticsearch ・ Logstash ・ Kibana) は代表的な集約の流れを示します。各ホストの Beats (Filebeat など軽量エージェント) がログを収集し、Logstash に送って変換 ・ 集約し (データ量が多い場合は Kafka を手前に置いて producer と consumer を切り離す)、Logstash が Elasticsearch に書き込んで全文検索可能な索引を作り、Kibana がその上で可視化と検索を提供します。SDFC の logging-service の議論でも、push (エージェント側が送信済みの位置=オフセットを管理) と pull (収集側がオフセットの管理を担う、Prometheus と同じ構図) の責任分担が論点として挙がっており、ローカルのログファイル自体は追記専用の WAL (write-ahead log) として扱われます。

3 本柱を別々のシステムに置いたままでは、障害対応のたびに人間が手で紐付けないといけません。これを解決するのが、trace-id のような相関 ID を、span だけでなくログの各行とメトリクスの代表サンプル (exemplar) にも一緒に埋め込むという約束です。メトリクスで異常な時間帯を見つけ、その時間帯の trace-id を持つ遅い trace を掘り、その trace-id で絞り込んだログを読む、という 1 本の調査の流れが初めて成立します。

6. SLI / SLO とエラーバジェット ― どこまで諦めるかを先に決める

ここまでの 3 本柱はすべて数値を生みますが、その数値を「合格か不合格か」に変換する仕組みが要ります。SLI (Service Level Indicator) は良し悪しを測る具体的な指標 (例: 成功したリクエストの割合、p99 レイテンシ)、SLO (Service Level Objective) はその SLI が満たすべき内部の目標値 (例: 99.9 %) です。対外的な契約である SLA (違反すると補償が発生する) は、通常この SLO よりも緩く設定されます。

SLO を 99.9 % と定めると、残りの 0.1 % がエラーバジェットです。月間なら約 43 分に相当し、これを「使い切ってよい予算」として扱います。予算が残っていればリスクのある変更を進めてよく、短時間で急速に消費している (バーンレートが高い) 兆候が出たらリリースを止めて信頼性の改善に回す、という意思決定の基準になります (Google の SRE book が示す運用)。これにより、メトリクスの個々の値のしきい値を超えるたびに鳴らすアラートではなく、「このペースで消費を続けるとバジェットが尽きる」という症状ベースのアラートに切り替えることができ、アラート疲れを避けられます。

止めずにスキーマを変える ― 1 本の ALTER TABLE が行列を作る

この回の前提: 第 36 回 ロックと分離レベル (表レベルロックの段階、トランザクション ID 待ちの構造)

「DDL は一瞬で終わるはずだから、本番中に流しても大丈夫」という判断は、ロックの強さと待ち行列の仕組みを見落としています。この回では、PostgreSQL 18.6 の実機で 2 本の psql セッションを動かし、ALTER TABLE が ACCESS EXCLUSIVE ロックを待つ間に無関係な SELECT までその後ろに並んでしまう様子、lock_timeout で待ちすぎを防ぐ方法、CREATE INDEX CONCURRENTLY の効果と失敗時の後始末、ADD COLUMN DEFAULT と列の型変更がいつ全行書き換えになるのかを、実測の時間とロックモードで確認します。

1. この回で解く問題 ― DDL が一瞬で終わるとは限らない

ALTER TABLE や CREATE INDEX の多くは、文そのものの処理時間は短くても、実行する前にロックを獲得するという手順を踏みます。対象のテーブルを他のトランザクションが使っている間は、DDL はそのロックが空くまで待ちます。問題は、DDL が要求するロックの多くが ACCESS EXCLUSIVE という最も強いロックで、これは通常の SELECT が持つ最も弱い AccessShareLock とも衝突することです。

さらに厄介なのは、DDL がロックを待っている間、その後に来た他のクエリまで、DDL の後ろに並んでしまうことです。これは特定の操作を飢餓させない (starvation を防ぐ) ための仕組みで、新しい要求は、今まさにロックを持っている側と衝突しなくても、既に待ち行列にいる要求と衝突するなら先に並んでいる要求を追い越せません。この回では、この行列の実態を実機のタイムスタンプで確認し、その根拠を PostgreSQL のソースコードのコメントでも裏付けます。

図: 強いロックを待つ DDL の後ろには、本来衝突しないはずの後続クエリまで並んでしまう。

2. 仕組み ― ロック待ちの行列に無関係な SELECT まで並ぶ

3 本のセッションを使います。s1 が 6 秒間行を読み続け、1 秒後に s2 が ALTER TABLE を実行し、さらに 1 秒後に s3 が無関係な 1 行だけの SELECT を実行します。

-- s1: 6 秒間 bugs を読み続ける (AccessShareLock)
BEGIN; SELECT pg_sleep(6) FROM bugs LIMIT 1; COMMIT;

-- s2 (1 秒後): 列を追加する (ACCESS EXCLUSIVE を要求)
SELECT clock_timestamp() AS s2_start;               -- 10:16:11.191831
ALTER TABLE bugs ADD COLUMN queue_test_col int;      -- s1 の間は待たされる
SELECT clock_timestamp() AS s2_done;                 -- 10:16:16.127316 (約 4.94 秒後)

-- s3 (さらに 1 秒後): bugs から 1 行だけ読むだけの、本来は s1 と衝突しない SELECT
SELECT clock_timestamp() AS s3_start;                -- 10:16:12.267695
SELECT bug_id FROM bugs LIMIT 1;                     -- ここで待たされる
SELECT clock_timestamp() AS s3_done;                  -- 10:16:16.129698 (約 3.86 秒後)

s2 は s1 の残り時間とほぼ同じ約 4.94 秒待たされました。これは予想どおりです。問題は s3 です。s3 の SELECT bug_id FROM bugs LIMIT 1 は AccessShareLock しか必要とせず、s1 が持っている AccessShareLock と衝突しません。それにもかかわらず、s3 は s2 とほぼ同時 (約 3.86 秒後) にしか結果を返しませんでした。理由は、PostgreSQL のロック管理が新しい要求を許可する前に 2 段階のチェックをしていることです。まず「既に待ち行列にいる要求と衝突しないか」を確認し、衝突するならその場で既存の保持者と衝突するかどうかに関わらず自分も待ち行列に並びます。衝突しなければ、次に「現在ロックを保持している側と衝突しないか」を確認します。s3 が到着した時点で、既に s2 の ACCESS EXCLUSIVE 要求が待ち行列にいたため、s3 は 1 段目のチェックで待ち行列入りが決まり、s1 との衝突を調べる段階にすら進みませんでした。これは PostgreSQL のソースコード (src/backend/storage/lmgr/lock.c の LockAcquireExtended) のコメントに明記された、後から来た要求が既存の待機者を飢餓させない (starvation を防ぐ) ための規則です。公式ドキュメントのロック関連ページはこの行列の順序規則そのものを解説していないため、この回ではソースコードのコメントと実機の結果の両方で確認したうえで述べています。実務でこれが起きると、1 本の長時間クエリと 1 本の DDL が重なっただけで、そのテーブルに対する全てのクエリが同じ長さだけ止まってしまいます。

3. シニアの書き方 ― lock_timeout で待ちすぎを防ぐ

本番環境でマイグレーションを実行する際、ロックが取れないまま何分も待たされるのは避けたい事態です。lock_timeout をセッション単位で設定すると、指定した時間内にロックを獲得できなければ、DDL 自身が諦めてエラーで終わります。重要なのは、lock_timeout が切れても相手の長時間クエリには何も影響せず、単に DDL 側がロックを諦めて何も変更せずに終了するという点です。これにより、本番で「気づいたら何分もロック待ちで全クエリが止まっていた」という事態を避け、リトライや時間帯の調整を判断する材料にできます。

SET lock_timeout = '2s';
ALTER TABLE bugs ADD COLUMN lock_timeout_test int;
-- 2 秒以内にロックが取れなければ、以下のエラーで終わる (列は追加されない)
-- ERROR:  55P03: canceling statement due to lock timeout

この lock_timeout はセッション単位の SET で設定できるため、他の利用者の接続やサーバー全体の設定には影響しません。マイグレーションツールの多くは、DDL の前に短い lock_timeout を設定することを推奨しています。

4. 仕組み ― CREATE INDEX CONCURRENTLY は書き込みを止めない代わりに遅い

50 万行の big_events テーブルで、通常の CREATE INDEX と CONCURRENTLY 付きを比較します。索引の構築中に別セッションから 1 行 INSERT してみます。

-- 通常の CREATE INDEX
SELECT clock_timestamp() AS ci_start;       -- 10:16:19.560332
CREATE INDEX idx_big_val_normal ON big_events (val);
SELECT clock_timestamp() AS ci_done;        -- 10:16:20.038772 (構築に約 0.48 秒)
-- 同時に実行した INSERT
--   write_start: 10:16:19.815536  write_done: 10:16:20.045980  (約 0.23 秒、ci_done まで待たされた)

-- CREATE INDEX CONCURRENTLY
SELECT clock_timestamp() AS cic_start;      -- 10:16:21.182087
CREATE INDEX CONCURRENTLY idx_big_val ON big_events (val);
SELECT clock_timestamp() AS cic_done;       -- 10:16:24.461976 (構築に約 3.28 秒、通常の約 6.9 倍)
-- 同時に実行した INSERT
--   write_start2: 10:16:21.441  write_done2: 10:16:21.444  (約 3 ミリ秒、ブロックされない)

通常の CREATE INDEX は ShareLock を取り、これは書き込み (RowExclusiveLock) と衝突するため、構築が終わるまで INSERT は待たされます (実測で約 0.23 秒)。CREATE INDEX CONCURRENTLY は ShareUpdateExclusiveLock という書き込みと衝突しないロックを使う代わりに、テーブルを 2 回走査し、構築中の変更を後から取り込む手順を踏むため、構築そのものには約 6.9 倍の時間がかかりました。しかしその間の INSERT はわずか 3 ミリ秒で完了しており、全く待たされていません。

CONCURRENTLY には代償もあります。構築の途中でエラー (例えば一意制約違反) が起きると、トランザクション全体を使い切った通常の CREATE INDEX のようにロールバックして元に戻るのではなく、INVALID な索引がカタログに残ります。重複データのある列に CREATE UNIQUE INDEX CONCURRENTLY を試すと、次のようになります。

CREATE UNIQUE INDEX CONCURRENTLY idx_bugs_ext_ref ON bugs (ext_ref);
-- ERROR:  23505: could not create unique index "idx_bugs_ext_ref"
-- DETAIL:  Key (ext_ref)=(EXT-1) is duplicated.

SELECT indexrelid::regclass, indisvalid, indisready FROM pg_index WHERE indexrelid='idx_bugs_ext_ref'::regclass;
--     indexrelid    | indisvalid | indisready
-- ------------------+------------+------------
--  idx_bugs_ext_ref | f          | f

\d bugs
--     "idx_bugs_ext_ref" UNIQUE, btree (ext_ref) INVALID

この INVALID な索引は、ディスク容量を使い続け、INSERT/UPDATE のたびに (無効なまま) 更新の対象にもなり続けます。放置せず DROP INDEX で明示的に消し、重複データを直してから再実行する必要があります。

DROP INDEX idx_bugs_ext_ref;
UPDATE bugs SET ext_ref = 'EXT-2' WHERE bug_id = 2;  -- 重複を解消
CREATE UNIQUE INDEX CONCURRENTLY idx_bugs_ext_ref ON bugs (ext_ref);  -- 成功、indisvalid=t

図: CONCURRENTLY は書き込みを止めない代わりに構築が遅く、失敗時の後始末も自分で行う必要がある。

5. 仕組み ― ADD COLUMN DEFAULT の高速化と NOT VALID 制約

PostgreSQL 11 以降、ADD COLUMN ... DEFAULT <定数> はテーブルを書き換えません。デフォルト値をカタログにメタデータとして記録するだけで、既存の行はディスク上では変わらず、読み取り時に仮想的にデフォルト値が補われます。50 万行の big_events で確認します。

ALTER TABLE big_events ADD COLUMN status text NOT NULL DEFAULT 'active';
-- Time: 4.828 ms                     ← メタデータのみ、全行書き換え無し

ALTER TABLE big_events ADD COLUMN created_at2 timestamptz NOT NULL DEFAULT clock_timestamp();
-- Time: 829.152 ms                   ← 約 172 倍遅い (volatile なデフォルトは書き換えが必要)

clock_timestamp() のような volatile (実行ごとに結果が変わる) なデフォルトは、各行に別々の値を書き込む必要があるため、1 つのメタデータでは表現できず、結局全行書き換えが走ります。高速化されるのは DEFAULT 'active' のような定数だけでなく、IMMUTABLE (入力が同じなら結果も必ず同じ) と STABLE (同一トランザクション内では結果が変わらない。current_date など) の式も対象です。実機で STABLE な自作関数を DEFAULT に指定しても約 1.5 ミリ秒で終わり、volatile の場合とは明確に違うことを確認しました。この 3 区分のどこに属するかで、1 つの値を全行で共有できるか (メタデータだけで済む) どうかが決まります。列を追加するときは、デフォルト式の volatility (不変性の区分) を意識する必要があります。

CHECK 制約を追加する場合も同様の考え方が使えます。NOT VALID を付けると、既存行の検証をスキップしてカタログの制約定義だけを追加するため、瞬時に完了します。検証は後から別の文で行い、こちらは書き込みをブロックしない軽いロックで済みます。

ALTER TABLE big_events ADD CONSTRAINT chk_status
  CHECK (status IN ('active','inactive')) NOT VALID;
-- Time: 1.013 ms                     ← 既存行は検証しない

ALTER TABLE big_events VALIDATE CONSTRAINT chk_status;
SELECT locktype, mode, granted FROM pg_locks WHERE pid=pg_backend_pid() AND relation='big_events'::regclass;
--  locktype |           mode           | granted
-- ----------+--------------------------+---------
--  relation | ShareUpdateExclusiveLock | t

VALIDATE CONSTRAINT が取る ShareUpdateExclusiveLock は、第 35 回で見た VACUUM と同じ強さです。これは他の SELECT や UPDATE と衝突せず、同種の保守作業 (別の VALIDATE や CREATE INDEX CONCURRENTLY) とだけ衝突します。つまり「制約を即座に追加し、検証は後で軽いロックのまま済ませる」という 2 段階に分ければ、本番中でも新しい CHECK 制約を安全に導入できます。

6. どこで壊れるか ― 列の型変更は書き換えの有無で速度が大きく変わる

ALTER TABLE ... ALTER COLUMN ... TYPE ... は、変更の内容によって全行書き換えが走るかどうかが変わります。同じ 50 万行のテーブルで、幅を広げるだけの変更と、型そのものを変える変更を比べます。

-- varchar(10) → varchar(20): 既存の値はそのままで表現できる (書き換え不要)
ALTER TABLE big_events ALTER COLUMN short_code TYPE varchar(20);
-- Time: 0.713 ms

-- int → bigint: ストレージ上の表現幅そのものが変わる (全行書き換えが必要)
ALTER TABLE big_events ALTER COLUMN seq_num TYPE bigint;
-- Time: 808.845 ms                   ← 約 1134 倍遅い

BEGIN;
ALTER TABLE big_events ALTER COLUMN seq_num TYPE int;
SELECT locktype, mode, granted FROM pg_locks WHERE pid=pg_backend_pid() AND relation='big_events'::regclass AND locktype='relation';
--  locktype |        mode         | granted
-- ----------+---------------------+---------
--  relation | ShareLock           | t
--  relation | AccessExclusiveLock | t
ROLLBACK;

varchar の幅を広げる変更は、既存の値がそのまま新しい型の制約を満たすため、PostgreSQL は書き換えをスキップできます (9.2 以降の最適化)。一方 int から bigint への変更は、ディスク上のバイト表現の幅そのものが変わるため、全ての行を新しい形式で書き直す必要があり、ACCESS EXCLUSIVE ロックを保持したまま時間のかかる処理が走ります。大きなテーブルでこの種の型変更を本番中に実行すると、書き換えが終わるまでテーブル全体への読み書きが止まります。

この問題への実務的な回避策は、新しい型の列を別名で追加し (ADD COLUMN)、アプリケーション側かトリガーで新旧両方の列を書き込むようにしてからバックフィルし、最後に古い列名を捨てて新しい列名に差し替える、という手順です。これは次の節で見る expand/contract パターンの一例です。

7. シニアの書き方 ― expand/contract で、1 回の切り替えを避ける

この回で見た対策 (lock_timeout、CONCURRENTLY、NOT VALID、書き換え不要な型変更) は、どれも「1 回の操作が長時間ロックを持つ時間を短くする」という共通の方針を持っています。もう一段上の判断が expand/contract (展張 ・ 収縮) パターンです。

列の意味や型を変えたいとき、「古い列を新しい列に直接書き換える」のではなく、次の順序に分けます。(1) expand: 新しい列や新しい制約を、既存のものを壊さない形で追加する (ADD COLUMN、NOT VALID の制約、CONCURRENTLY の索引)。(2) 移行: アプリケーションを新旧両方に対応させ、徐々に新しい方へ書き込みを移す。(3) contract: 古い列や制約が誰にも使われなくなったことを確認してから、安全に削除する。この 3 段階に分けることで、どの 1 回の DDL も短時間で終わり、ACCESS EXCLUSIVE を長時間持つ操作を避けられます。

この回で確認した実測をこの判断に当てはめると、ADD COLUMN DEFAULT <定数> と NOT VALID 制約は expand の段階で安心して使える道具 (数ミリ秒で終わる)、CREATE INDEX CONCURRENTLY は expand の段階で索引を追加する標準の方法 (遅いが書き込みを止めない)、volatile なデフォルトや型そのものの変更は、expand の中で直接行わず、新しい列を作ってバックフィルする側に回すべき操作、という位置づけになります。

図: expand/contract は、長時間ロックを持つ変更を避けるために変更を段階的に分ける設計方針。

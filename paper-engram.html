Engram を部品の単位まで分解する
「直前の 2〜3 語」で引く辞書を、モデルの中に埋め込む

結論から。Engram は、モデルの途中の層に「直前の 2 語・3 語の組」を見出しにした巨大な表を差し込む設計の変更である。行番号は語の番号の掛け算と割り算だけで決まり、計算の途中結果を待たない。だから表を GPU の外の DRAM に置き、前の層を計算している間に必要な行だけ取り寄せられる。表の中身は人が作るのではなく、ほかの重みと一緒に学習で直される。

このページでやったこと。DeepSeek の論文 "Conditional Memory via Scalable Lookup" と公開デモのコード engram_demo_v1.py を読み、1 語が表を引いて足し込まれるまでを 7 つの部品に分けた。部品ごとに、その計算を実際にブラウザの中で動かすデモを置いた。最後に、SemiAnalysis がこの設計を B200・B300 で動かした記事の結果を並べた。

1. どこに差し込むのか

普通の Transformer（今の LLM の基本の形）は、最初に語の番号から 1 行を引き、あとは同じ形の「ブロック」を何十段も通す。各ブロックは attention（前の語を見渡す部分）と MoE（入力ごとに選ばれた専門家が計算する部分）でできていて、それぞれの結果を残差の流れ（層から層へ受け渡される数の並び。各部品はここに自分の結果を足していく）に足す。

Engram は、一部のブロックだけ、attention の前にもう 1 つ部品を足す。論文の 27B モデルでは 2 層目と 15 層目である。デモのコードでは次の 1 行がそれに当たる。

if self.engram is not None:
    hidden_states = self.engram(hidden_states=hidden_states, input_ids=input_ids) + hidden_states
hidden_states = self.attn(hidden_states) + hidden_states
hidden_states = self.moe(hidden_states) + hidden_states

注目してほしいのは、Engram だけが input_ids（語の番号の列）を受け取っていることだ。attention と MoE は層の途中結果しか見ないが、Engram はそれに加えて元の語の番号を直接見る。これが後で出てくる「先読みできる」の出どころになる。

ここから先は、黒い Engram 箱の中身を 7 つの部品に分けて、1 つずつ動かしていく。

2. 部品 (1): 表記ゆれをまとめる

ふつうの LLM の語の区切り方（トークナイザー）は、元の文字列を完全に復元できるように作られている。そのため「Apple」と「␣apple」（前に空白が付いた apple）は別の番号になる。しかし辞書の見出しとしては、同じ意味の語が別々の行に散らばると、学習で直される回数が分かれて損をする。そこで論文は、見出しを作る前に番号をまとめ直す。

デモのコードでは、各語の文字列に次の変換を順にかけ、結果が同じ語を同じ番号にしている。NFKC（全角・半角などの見た目の違いを揃える）、NFD と StripAccents（アクセント記号を外す）、Lowercase（小文字にする）、空白の連続を 1 つにする、前後の空白を取る（ただし空白 1 文字だけの語は残す）。論文によれば、これで 128k 語の語彙が 23.43 % 減った。

デモ 1: 表記ゆれまとめ

カンマで区切って語を入れると、デモのコードと同じ順の変換をかけ、まとまった結果ごとに並べる。

「␣」は空白 1 文字の代わりに表示している記号で、中では本物の空白に置き換えて計算する。論文の付録 C の表では、「a」に 54 個、空白に 163 個の語がまとまった。

これは語の表そのものは変えない。モデルの入口にある普通の語の表は元の番号のまま使う。まとめ直した番号は、Engram の見出しを作るためだけに使う。

3. 部品 (2)(3): 組を作り、8 通りの計算で行番号にする

まとめ直した番号の列から、位置ごとに「直前の 2 語」と「直前の 3 語」の組を作る。すべての 3 語の組に 1 行ずつ用意すると、語彙の 3 乗、つまり 10 の 15 乗ほどの行が要り、とても置けない。そこでハッシュ（入力を決まった計算でかき混ぜ、決まった範囲の番号に押し込む方法）を使う。デモのコードの計算はこうである。

mix = tokens[0] * multipliers[0]
for k in range(1, n):
    mix = np.bitwise_xor(mix, tokens[k] * multipliers[k])   # 掛けて XOR で混ぜる
for j in range(num_heads_for_this_ngram):                  # 8 通り
    head_hash = mix % mod                                    # 素数で割った余り = 行番号

掛ける数（multipliers）は層ごとに乱数で決めた奇数で、学習の間ずっと固定である。割る数（mod）は表の行数で、8 個とも違う素数にしてある。デモの設定では 2 語用が 646,403 から 646,523 まで、3 語用が 646,537 から 646,619 までの素数である（コードと同じ手順で計算）。混ぜた値 mix は 1 つなのに、違う素数で割るので、8 個の行番号はばらばらになる。

デモ 2: 行番号の計算機

英文を入れると、語ごとに (1) のまとめ直しをして組を作り、デモのコードと同じ式で 2 語用・3 語用それぞれ 8 個の行番号を出す。

[注意] 本物は DeepSeek のトークナイザーの番号を使うが、ブラウザでは使えないので、語の文字列から作った説明用の番号で代用している。掛ける数も説明用の奇数である。割る数（素数）と計算式はデモのコードと同じ。文頭で前の語が無い位置は、埋め草の番号（pad）で埋める。

なぜ 8 通りも取るのか: ぶつかり対策

行の数は約 65 万しかないので、別の組が同じ行に当たる衝突は必ず起きる。1 通りだけだと、衝突した 2 つの組はまったく同じ中身を受け取り、区別できない。8 通りの割る数で別々の行を取ってつなげれば、8 個すべてが同時に衝突しない限り、受け取る中身の組み合わせは違ってくる。

デモ 3: 衝突の起こりやすさ

小さな表で試す。組の数と表の行数、取る通り数を変えると、「ほかの組と 1 通り以上で同じ行に当たった組」と「ほかの組と全部の通りで同じ行になった組（区別できない組）」の割合を数える。

通り数

通り数を 1 から 2 に上げるだけで「区別できない組」はほぼ消える。一方で「どこかで衝突した組」はむしろ増える。つまり 8 通りは衝突を減らすためではなく、衝突しても区別できるようにするためのものである。残った混ざりものは、5 節の門で弱める。

4. 部品 (4): 表から行を取ってつなげる

行番号が決まったら、表からその行を読む。デモのコードでは、2 語用 8 個と 3 語用 8 個の合わせて 16 個の小さな表を、1 本の大きな表に縦に並べて持っている。それぞれの表の始まりの位置（offsets）を行番号に足してから、1 回でまとめて読む。

shifted_input_ids = input_ids + self.offsets     # 16 個の表を 1 本に並べた中での位置
output = self.embedding(shifted_input_ids)      # まとめて 16 行を読む
embeddings = ... .flatten(start_dim=-2)          # 16 行を横につなげて 1 本にする

デモの設定では 1 行が 64 個の数で、16 行をつなげると 1,024 個の数になる。これが 1 語ぶんの「引いてきた記憶」である。論文の 27B モデルでは、つなげた長さ（d_mem）が 1,280 である。

デモ 4: 表の大きさと、1 語で読む量

設定を変えると、表全体の大きさと 1 語あたりに読む量を計算する。初期値はデモのコードの設定。

1 個の数の大きさ

読む割合は、ちょうど 1 表あたりの行数分の 1 になる（デモの設定で約 65 万分の 1）。1 語あたりに読む行の数は通り数と組の種類だけで決まり、表を何倍に広げても変わらない。論文が「O(1) で引ける」と言うのはこの意味である。SemiAnalysis によれば、実際の DeepSeek-V4.1-Flash は 2 か所の層でそれぞれ 24 行を読み、1 語あたり約 12.4 KiB、表全体は約 189 GiB である。12.4 KiB を 48 行で割ると 1 行あたり約 265 バイトになる（計算）。

5. 部品 (5)(6): 門で絞り、短い畳み込みでならす

引いてきた記憶は、文脈を見ずに語の番号だけで選んだものである。衝突で混ざったものかもしれないし、同じ語の並びでも文脈によって意味が違うかもしれない。そこで、いまの文脈（層の途中結果 h）と照らし合わせて、使うかどうかの開き具合 α を 0 から 1 の間で決める。論文の式 (3)(4) と、デモのコードは次の通り。

key   = W_K · e        # 引いた記憶 e から「見出し」を作る
value = W_V · e        # 引いた記憶 e から「中身」を作る
gate  = (RMSNorm(key) · RMSNorm(h)) / sqrt(d)
gate  = sign(gate) * sqrt(|gate|)                # デモのコードにある、値を穏やかにする一手
alpha = sigmoid(gate)                            # 0 から 1 の開き具合
out   = alpha * value

RMSNorm は数の並びの大きさを揃える操作で、揃えたあとの内積は「2 つの向きがどれだけ揃っているか」を表す。向きが揃えば α は 1 に近く、逆向きなら 0 に近い。

デモ 5: 門の開き具合

文脈 h と記憶の見出し key の向きの差（角度）を動かすと、デモのコードと同じ式で α を計算する。数の個数 d はデモの設定の 1,024。

向きの差

RMSNorm の学習される倍率は 1 と置いた。右のグラフの緑は、デモのコードの「平方根で穏やかにする」一手あり、灰色はそれが無い場合。d が 1,024 と大きいので、どちらも 90 度の近くで急に 0 と 1 が切り替わる。平方根はこの切り替わりを少しなだらかにする。

論文の図 7 では、この α が「Alexander the Great」「the Milky Way」「By the way」のような決まった言い回しを言い終えた位置で強く開くことが確かめられている。中国語でも「四大发明」のような熟語で開いた。

最後に、門を通した値を短い畳み込みでならす。畳み込みとは、少し前の位置の値も混ぜて足す計算である。論文の式 (5) は Y = SiLU(Conv1D(RMSNorm(Ṽ))) + Ṽ で、幅（kernel_size）は 4、間隔（dilation）は組の最大の長さの 3 である。つまり位置 t の出力は、t、t−3、t−6、t−9 の 4 か所の値を混ぜる。

デモ 6: どの位置を混ぜるか

位置を動かすと、その位置の出力に混ざる 4 か所が光る。未来の位置は混ぜない（因果的）。

位置 t

学習の始めは何もしない。論文によれば、畳み込みの重みはすべて 0 から始める。0 なら出力は SiLU(0) + Ṽ = Ṽ で、畳み込みは素通りになる。論文の部品を外す実験でも、畳み込みを外したときの悪化はわずかだった。効いたのは、門、表記ゆれのまとめ直し、残差の枝ごとに門を分けること（次節）の 3 つである。

6. 部品 (7): 残差の流れに足す、そしてどの層に置くか

論文の 27B モデルは、残差の流れを 4 本の枝に分けて持つ形（mHC）を使っている。Engram は表と W_V を 4 本で共有し、門を作る W_K だけを枝ごとに 4 つ持つ。だから 1 語につき、枝 4 本 × 2 か所の層で 8 個の α ができる。デモのコードの hc_mult = 4 と、ループの中の self.key_projs[hc_idx] がこれである。

どの層に置くかには、2 つの力が逆向きに働く。浅い層に置くほど、決まった言い回しを組み立てる手間を早く肩代わりできる。一方で深い層ほど、門に使う文脈 h が attention で多くの情報を集めていて、正しく絞れる。論文の実験では、1 か所だけなら 2 層目が最良で（損失 1.770）、1 層目より良く、深くするほど悪くなった。同じ 1.6B の表を 2 層目と 6 層目に分けると、さらに良くなった（1.768）。

7. 表を GPU の外に置いても待たない理由

ここまでの部品のうち、行番号を決める (1)〜(3) は語の番号だけで計算できる。論文 2.5 節の言い方では、MoE は層の途中結果で専門家を選ぶので、その層に来るまで何を読むか分からない。Engram の行番号は入力の語の列だけで決まるので、モデルを動かす前に分かる。そこで推論では、表をまるごと CPU 側のメモリ（DRAM）に置き、GPU が前の層を計算している間に、必要な行だけを GPU と CPU をつなぐ線（PCIe）で送っておく。

デモ 7: 取り寄せが間に合うか

Engram の前にある層の数と、行を送るのにかかる時間を動かす。上段は Engram（行番号が先に分かる）、下段は比較のための仮の場合（その層に来るまで分からない）。時間の単位は「1 層を計算する時間 = 1」とした。

Engram より前の層の数

行を送る時間

送る時間が前の層の計算時間に収まれば、GPU は一度も待たない。送る量は読む行の数だけで決まり、表の大きさには関係ないので、表を大きくしても待ち時間は増えない。論文はこれを実際に確かめている。H800 で、100B パラメータ分の表を全部 DRAM に置き、2 層目に Engram を入れて推論したところ、処理できる語数の低下は 4B のモデルで 1.9 %、8B のモデルで 2.8 % だった（論文 表 4 の値から計算）。

置き場所ごとの通り道

SemiAnalysis は実際のサーバーで、表を HBM（GPU の隣の速いメモリ）、DRAM、SSD の 3 か所に置いて比べた。HBM と DRAM は同じ GPU のプログラムが読み先を変えるだけで、DRAM の場合は UVA（GPU が CPU 側のメモリを自分のメモリのように直接読める仕組み）で読む。SSD は最適化していない試作で、GPU の計算の区切りごとに CPU が手作業で行を集めて送り返す。

論文と記事は、SSD について違うことを言っているように見える。論文 2.5 節は、よく使われる行だけを速いメモリに置き、めったに使われない行を SSD に置く段々の置き方を「可能性」として書いている。記事が試した SSD は、そうした工夫をしていない試作だった。記事は、SSD に移しても高い GPU とサーバーの残りはそのまま残るので、それで安いサーバー構成に替えられない限りお金は浮かない、と結論している。さらに記事は、門の値が大きい行がよく読まれる行とは限らないので、どの行を速いメモリに置くべきかの手がかりはまだ無い、とも書いている。

9. 表の中身はどうやって学習されるか

表の中身は、ほかの重みと同じく乱数から始まり、次の語を当て損ねた分を逆向きに伝えて少しずつ直される。ただし 1 語で読むのは 16 行だけなので、その語で読んだ行だけが直される。何度も出てくる言い回しの行ほど何度も直され、意味のある中身になっていく。論文によれば、表の重みは Adam という直し方で、学習の速さをほかの重みの 5 倍にし、値を小さく引き戻す仕組み（weight decay）は使わない。

デモ 8: 読んだ行だけが直される

「1 歩学習」を押すたびに、決まった言い回しの多い短い文章を 1 つ流し、読んだ行だけ色を濃くする（色の濃さ = 直された回数）。小さな表（素数 97 行と 101 行の 2 通り、2 語の組だけ）で試している。

学習のときは、表が大きすぎて 1 台の GPU に載らないので、表を GPU の台数で分けて持つ。論文によれば、前向きの計算では All-to-All（全台が全台と一斉にデータを交換する通信）で必要な行を集め、逆向きでは直す量を持ち主の GPU に送り返す。推論のときだけ DRAM に出す。

MoE の専門家をどれだけ表に回すか

総パラメータと 1 語あたりの計算量を固定したまま、MoE の専門家の一部を表に回すと、損失は U 字を描いた。論文 3.1 節の約 10B 規模の実験では、全部 MoE（ρ = 100 %）で 1.7248、ρ ≈ 80 % で 1.7109 と良くなり、ρ ≈ 40 % まで表に回しても全部 MoE と同程度だった。表に回しすぎると、今度は文脈に応じて計算する力が足りなくなって悪くなる。記憶は計算の代わりにはならない、というのが論文の読み方である。

10. 学習したあとは取り外せない

論文 6.3 節は、学習済みのモデルから推論のときだけ表の出力を消した。事実知識の試験は元の 29〜44 % しか点が残らず、読解は 81〜93 % 残った。論文自身が、学習と推論の形が食い違うので雑音が入る実験だと断っている。これは「表があるモデルが表にどれだけ頼っているか」を測ったもので、表なしで学習し直したモデルとの比較ではない。

SemiAnalysis は、CRUXEval（短い Python の関数の出力を当てる試験）で、正解の答えにモデルがどれだけ驚くか（損失。低いほど良い）を測った。表ありで 0.2848、表を消すと 0.3093。さらに、表を消したうえで MoE の専門家の選び方を「表があったときのまま」に固定すると 0.3375 と、もっと悪くなった。表を消すと専門家の選び方が変わり、失った分を少し取り返していた、ということである。記憶と専門家は「記憶が事実を持ち、専門家が考える」ときれいに分かれてはいない。

11. このページで扱っていないこと

  • DeepSeek-V4.1-Flash の Engram の実際の設定（通り数、行の大きさ、層の位置）。SemiAnalysis の記事は「1 層あたり 24 行」までを無料部分に書き、実装の詳細は有料部分に置いている。24 行を 2 語用・3 語用などにどう分けているかは確かめていない。
  • デモ 2 とデモ 8 の番号は説明用で、本物のトークナイザーの番号ではない。計算式と割る数の素数は、デモのコードと同じである。
  • デモのコード自身が「説明用で、本番には専用の CUDA カーネルや分散学習の対応が要る」と断っている。DeepSeek の本番の実装は公開されていない。
  • SSD の段々の置き方（よく読む行だけを速いメモリに置く）は、論文では可能性として書かれているだけで、実測はない。

まとめ。Engram は「直前の 2〜3 語」を見出しにした表を途中の層に差し込み、文脈との照らし合わせ（門）を通して足し込む。見出しから行番号を出す計算は語の番号だけで終わるので、表を GPU の外に置いて先に取り寄せられる。表は学習でほかの重みと一緒に作られ、専門家の選び方と絡み合うので、後から付けたり外したりはできない。

NEFF を境界にできるか ― 機構はある、運搬が高い

プロセスを分ければ衝突しない。ロードと実行の部品は揃っている。残る課題はデータ移動

← シリーズ目次

0この回の狙い

前回の結論は「プロセス内での差し替えは無理」でした。ではプロセスを分ければどうか。設計として成立するかを検討し、公開イメージで確認できる範囲を報告します。

アイデアは単純です。PrivateUse1 の衝突はプロセス内の話なので、片方のプロセスでコンパイルして成果物をファイルに出し、もう片方のプロセスでそれを実行すれば衝突しません。第 1 回で見たように NEFF はファイルとして存在し、名前つきの入出力を持ちます。つまり交換フォーマットの資格があります。

一言でいうと
機構は公開イメージの中にあります。Neuron ランタイムの Python バインディングが同梱されており、NEFF をファイルからロードして、入出力の契約を問い合わせて、テンソルを渡して実行できます。だから「片方でコンパイルして、もう片方で実行する」という分業は、部品としては揃っています。
ただし運搬が高い。ホストのバッファを経由するデータ移動が、カーネル実行時間の約 30 倍かかりました (2.6 MB 級の部分グラフ 1 個での実測)。層ごとに呼ぶ設計では成立しません。解消の鍵はテンソルをデバイス上で共有することで、そこは未検証です。
1. なぜ全体モデルの NEFF 注入は無理なのか 2. 部分グラフなら署名を自分で決められる 3. ランタイムの Python API 4. 実際にやってみる 5. 何が確認できて、何が未確認なのか 6. 位置名しか無いという実務的な壁 7. データ移動の代償を測る 8. 橋を完成させるための残工程 9. 判断 ― 作るべきか

1なぜ全体モデルの NEFF 注入は無理なのか

先に、似ているが成立しないアイデアを潰しておきます。ここを混同すると、成立する案まで否定してしまいます。

「モデル全体を別の経路でコンパイルして、その NEFF をサービング側に食わせる」。これは成立しません。理由は、モデル全体の NEFF の入出力署名が、サービング側の契約で完全に決まっているからです。

第 2 回と第 3 回で見た要素が、そのまま署名に焼き込まれています。KV キャッシュのエイリアス関係、バケットごとの固定形状、集団通信のグループ、サンプラとの切れ目。一方、Hugging Face のモデルをそのままコンパイルしたグラフは、自前のキャッシュを連結で伸ばす形で、ブロック表という概念を持ちません。署名が違うというより、キャッシュの管理モデルそのものが別です。

署名を手で合わせるハックを考えても、それは「サービング側のランタイムが期待する契約を手で再実装する」作業になります。第 3 回のリストを外部から再現することになるので、素直に移植するより難しくなります。

2部分グラフなら署名を自分で決められる

境界の所有権が逆になる、というのがこの回の勘所です。

モデル全体の署名はサービング側が握っています。しかしモデルの内側にある 1 つの層、あるいは層の一部の署名は、自分が決められます。たとえば SSM の混合部分について、状態を明示的に引数と戻り値に出した関数を定義すれば、その入出力は自分の設計物です。

同じ「NEFF を持ち込む」でも、署名を誰が握っているかで成否が反転する

ただし制約が付きます。ランタイムには、NEFF の実行中に別の NEFF を呼び出す仕組みが用意されていません。外側のモデルはバケットごとに 1 個の NEFF になるので、その内側から別の NEFF を呼ぶ手段がありません。だから委譲はホストへの往復を挟む形、つまりグラフの分断を意味します。第 2 回で見たように既定は分断を許さない設定なので、ここは意図的に緩める必要があります。

3ランタイムの Python API

橋の実行側に何が用意されているかを確認します。ここが空なら話は終わりです。

サービング用の公開イメージには、Neuron ランタイム (スタック第 4 層) の Python バインディングが同梱されています。以下この回で単に「ランタイム」と書くのはこの Neuron ランタイムを指します。低レベルカーネルの開発に使われるものですが、NEFF を扱う一般的な機能を持っています。

できることAPI の形
NEFF ファイルをロードするパスと、コア番号や集団通信の設定を渡す
入出力の契約を問い合わせる名前 → (要素数, データ型, 形状) の辞書が返る
エイリアス情報を見る入力を出力として使い回す指定の一覧
デバイス上にテンソルを確保するnumpy 配列から作る、既存のものに書き込む、読み出す
実行する入力名と出力名の対応でテンソルを渡す
カーネル実行時間を測るウォームアップ回数と計測回数を指定できるベンチマーク

最後の項目は橋とは別に重要で、ホスト側のストップウォッチでは測れない時間を測る唯一の手段です。第 8 回で詳しく扱います。

4実際にやってみる

手順を明示します。再現できる形にしておくと、この先の議論が意見ではなく事実の上で進みます。

境界はファイル。運ぶのは NEFF だけでは足りず、入力名の対応表と参照値が要る

  1. 焼く側のプロセス: 委譲したい部分グラフ (たとえば SSM の中核部分を、状態を明示的に引数と戻り値に出す形で書いたもの) を torch.compile で 1 回実行する。コンパイルの成果物として .neff ファイルが出る。キャッシュを空にしてから 1 回だけ実行すれば、生成されたファイルとグラフの対応が一意に決まる
  2. 成果物を持ち出す: .neff に加えて、入力そのものと、そのプロセスがデバイス上で得た出力を保存する。これが後で照合するための参照値になる
  3. 実行する側のプロセス: サービング用の公開イメージで、その NEFF をランタイムの API でロードする。入出力の契約を問い合わせて、形と型を確認する
  4. 入力を対応づける: NEFF の入力名は位置名なので、どの引数がどの名前かを対応づける (この点は次節で詳述)
  5. 実行して照合する: 出力を読み出し、保存した参照値と比べる

手順 1 の「キャッシュを空にしてから 1 回だけ」は地味ですが重要です。複数のグラフが焼かれると、どのファイルがどのグラフなのか分からなくなります。

5何が確認できて、何が未確認なのか

この設計の成否を分ける点を、確認済みと未確認に分けます。

確認できたこと。公開イメージ上で、ある部分グラフの NEFF をランタイムの API でロードし、入出力の契約を問い合わせ、テンソルを渡して実行し、結果を読み出すところまでは動きます。NEFF は自己記述的で、名前・形状・データ型・エイリアス情報を問い合わせられます。つまり「NEFF を交換フォーマットとして扱う」ことは、部品としては可能です。

未確認のこと。異なるコンパイラ世代・異なる環境で焼いた NEFF が相互運用できるかは、ここでは扱いません。NEFF はコンパイラ世代とランタイム世代に紐づくので、世代がずれれば話が変わります。橋を実装するなら、この相互運用性を自分の構成で先に確かめる必要があります。

設計として言えること。それでも境界の設計については判断できます。次の 2 節で、この境界を実務で使うときに必ず問題になる 2 点 (呼び出し規約と運搬コスト) を扱います。どちらも公開イメージだけで確認できる性質です。

6位置名しか無いという実務的な壁

小さいけれど、放置すると必ず事故になる問題です。

NEFF の入力は input0、input1 という位置名しか持ちません。元の Python 関数の引数名は残りません。だから「どの引数がどの名前に対応するか」を焼いた側が記録しないと、復元できません。

形状から推測できる場合もありますが、それは形状が全部違うときだけです。SSM の部分グラフを例に取ると、同じ形状の引数が 2 組できます。1 組は状態遷移に関わる係数、もう 1 組は出力の射影に関わる係数です。この 2 つを入れ替えても形状は合うので、エラーになりません。数値が静かに変わるだけです。

だから実運用の橋にするなら、焼く側が引数と入力名の対応表を成果物として出す必要があります。参照値との照合で総当たりに当てる方法は検証用には使えますが、運用には載せられません。

一般化すると: NEFF は「計算」を運びますが「呼び出し規約」を運びません。だから NEFF を交換フォーマットとして使うなら、署名のメタデータを別に定義して一緒に運ぶ必要があります。形状と型は NEFF から読めるので、足りないのは引数の順序と意味だけです。

7データ移動の代償を測る

この回の結論を決める数字です。機構が動くことと、実用になることは別でした。

公開イメージ上で、入力 2.63 MB、出力 2.62 MB の部分グラフ 1 個について、段階ごとに時間を測りました。カーネル実行時間はデバイスモード計測によるもので、ホスト側のストップウォッチでは測れない理由は第 8 回 §1 にあります。

この節が測っているのは API のデータ移動コストです。値はテンソルのサイズと転送の経路で決まり、その NEFF をどの経路でコンパイルしたかには依存しません。だから以下の内訳は、橋の設計を判断する材料としてそのまま使えます。

段階1 回あたりカーネル比
カーネル実行だけ (ランタイムのデバイスモード計測)0.0630 ms1.0 倍
実行の呼び出しまで含む (入力はデバイス上に常駐)0.1188 ms1.9 倍
入力の書き込みを含む (ホスト → デバイス)0.3647 ms5.8 倍
出力の読み出しまで含む (実際の 1 回)1.8819 ms29.9 倍

支配しているのは出力の読み出しです。2.62 MB に約 1.5 ms かかっており、実効で毎秒 1.7 GB 程度。この数字はハードウェアの帯域限界ではなく、使った API がホスト側のバッファ経由でコピーする実装であることの帰結です。だから「NEFF を境界にすると原理的に遅い」という話ではありません。転送手段を変えれば動く数字です。測定は 2.6 MB の部分グラフ 1 個・1 構成に限ります。

同じ 1 回の呼び出しを段階的に測ると、計算より運搬が支配していることが見える

この数字を層数で掛けると結論が出ます。層ごとに委譲する設計では成立しません。数十層のモデルで 1 トークンあたり数十 ms がデータ移動に消えます。

8橋を完成させるための残工程

正直に残りを列挙します。どれも実在する作業で、規模の見積もりが可能です。

  1. データ移動をデバイス上で完結させる。最大の項目。サービング側のテンソルとランタイム側のテンソルを、コピーせずに共有する必要があります。技術的に可能かどうかは未検証です。ここが解けないなら橋は成立しません
  2. カスタム演算として包む。サービング側のモデルの forward から呼べるようにする。グラフの分断が必要なので、分断を許す設定と組み合わせる
  3. 署名のメタデータを運ぶ。引数と入力名の対応表を、焼く側が出力する (第 6 節)
  4. 状態のエイリアスを扱う。状態を入力バッファに書き戻す指定を使う場合、その情報を橋の両側で整合させる
  5. バケットごとに焼く。形状ごとに NEFF が要るので、サービング側のバケット設計と対応づける
  6. 並列度に対応する。ランタイムの API はコア番号や集団通信の設定を受け取るので、テンソル並列に分割された部分グラフも射程に入ります

9判断 ― 作るべきか

技術的に可能かという問いと、作るべきかという問いは別です。後者に答えます。

まず、データ移動が解けるかどうかを確かめる前に、橋を作る判断はすべきではありません。解けなければ 30 倍の代償が居座るので設計として死んでいます。解ければ一気に現実的になります。この 1 点だけを先に確かめるのが合理的です。

次に、解けたとして作る価値があるかを考えます。ここで重要なのは、橋を作っても「どの演算を委譲するか決め、モデルを分割し、状態の受け渡しを設計する」作業は残るということです。1 モデルあたりの手間は、第 4 回の数式書き換えとそう変わらないかもしれません。

それでも価値があるとすれば、理由は 1 つです。転送・ロード・照合の機構は一度作れば再利用できます。ただし前節のとおり、分割の設計と状態の受け渡しの設計はモデルごとに残ります。再利用が効くのは機構の部分だけで、そこを過大に見積もると判断を誤ります。対応アーキテクチャを継続的に増やす必要がある状況では、それでもこの差が意味を持ちます。

逆風も明確です。第 6 回で見たとおり、プラグインの公開ソースはライブラリ側での対応を参照しています。対応版が出れば、自前で架けた橋は使い捨てになります。提供時期についての公開情報は執筆時点でありません。だから、時期の確認と並行して、時間を区切って組むのが正しい形になります。

出典と確認方法: Neuron ランタイムの Python API は、サービング用の公開コンテナイメージに同梱されているものを実際に呼び出して機能を確認しました。第 7 節の内訳も同じ公開イメージ上、単一 Trainium2 チップでの測定で、デバイス上に常駐させたテンソルを使い回す形で段階を分けて計測しています。2.6 MB 級の入出力を持つ部分グラフ 1 個・1 構成の測定なので、比率は規模によって変わります。異なる環境で焼いた NEFF の相互運用については本稿では扱っていません。橋を実装するなら、自分の構成で先に確かめる必要があります。

確認時点: 本稿の記述は 2026-09-01 時点のものです。対象はプラグイン 0.21.0.1.0.0 と 0.24.0.1.1.0 の公開ソースおよび公開コンテナイメージ、公開パッケージインデックスから取得できるランタイム兼カーネル基盤ライブラリ (2.11.0.1.0.1284 / 2.12.0.1.0.1284)、コンパイラ 2.26 / 2.27 系、低レベルカーネル言語 0.5.0 / 0.6.0、PyTorch 2.11.0 です。バージョンが上がれば名前も挙動も変わりうるので、正はソースと配布物です。

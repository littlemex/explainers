AIの読み取りを「検算する仕組み」を作る
— 研究シリーズ 第1回: 全体像

画像を読むAI(VLM)は間違える。だから信じずに、機械的に検算する。その検算器を強くしていく研究の記録。

研究過程シリーズ 第1回 ｜ 2026-08-12 時点

1 ひとことで言うと 中心アイデア

AIに請求書やレシートの画像を読ませると、たまに数字を読み間違えます。 その間違いを「AIをもっと賢くして直す」のではなく、読み取り結果が計算として辻褄が合うかを、後段の機械的な検算器でチェックするという研究です。

たとえるなら、AIが伝票を書き、経理担当(検算器)が「単価×個数＝金額になってる? 合計は合ってる?」と検算し、合わなければ差し戻す。AIを鵜呑みにせず、世界のルールで答え合わせします。

この研究の主役は「検算器」です。AIは題材(入力を出す係)にすぎません。

2 なぜ必要か 具体例で

AIはこう間違える

Widget A 数量2 × 単価1500 金額 = 3200 ← 本当は3000 Widget B 数量1 × 単価2000 金額 = 2000 合計 = 5200 ← 本当は5000

検算器が持つルール

金額 = 数量 × 単価 合計 = すべての金額の和 + 税 売り手 ≠ 買い手

→ 2×1500=3000 なのに3200 → 不合格。「A行の金額が怪しい」と指摘できる。

3 触って確かめる 実際のデータがどう検出されるか

数字を書き換えると、検算器がその場で判定します。プリセットで代表的なケースも試せます。(数量・単価は固定、金額と合計を編集)

品目数量単価金額(編集可)
Widget A21500
Widget B12000
税--
合計--
これが「見える死角」
全部の検算に合格(緑)しているのに、実は単価1500を1600と読み間違えています。金額も合計も辻褄を合わせて間違えたので、算術の検算では原理的に見抜けません。この種の誤りが実データで約35%ありました。

候補から選ぶ (検算器の使い方その2)

AIに「自信がない数字は候補を複数出して」と言わせ、全ルールを同時に満たす組合せを検算器に選ばせます。1個ずつ「一番自信のある値」を選ぶと全体で矛盾することがあります。

A行の金額の候補: 3200(自信60%) / 3000(自信40%) ｜ 合計の候補: 5200(自信55%) / 5000(自信45%)

4 作った検算の道具 すべてオフラインで動く

基本の検算
単価×個数=金額 / 合計 / 売り手≠買い手 を機械チェックし、違反を列挙。
候補から選ぶ
複数候補から全ルールを同時に満たす組合せを選ぶ。上のデモの②。
犯人特定
検算が失敗したとき、どの数字が原因かを「その値を直すと違反が消えるか」で特定。どこを読み直すべきか分かる。
検算器の強さテスト
わざと壊した伝票を、検算器がどれだけ捕まえるか測る。自分の弱点を数値で把握。

5 実データでぶつかった壁 正直に測る

本物のAI(Gemma 4B)がレシート35件を読んだ結果を検算しました。ここが一番大事な現実です。

指標数字意味
ざっくりの検出率64.8%甘く数えたときの見かけ上の値
厳密に数え直すと15.5%犯人を正しく特定できた分だけ数えると激減
整合的な誤読(死角)35.2%AIが計算の辻褄まで合わせて間違えた分。算術検算では原理的に捕まえられない
正直な現実
本当の検出力は 15.5%〜64.8%の間(幅で報告するのが誠実)。そして「辻褄を合わせた間違い」(上のデモで体験)は算術チェックでは絶対に捕まらない天井がある。つまり検算だけで品質保証はできない。

6 研究のねらい 検算器の「作り方」を規律する

そこでこの研究は、個別のOCRツールを磨くのではなく、「検算器そのものをどう作るか」を規律する仕組みを目指します。フォーマットが決まっている領域(帳票・回路図など)なら、「正しい形」を形式的に定義して適合を見られるからです。

単に既存ツールを使うだけでは
JSON Schema や SHACL など既存の適合チェックで書けることは新しくありません。そこで止まらないのが研究のねらい。
この研究がねらう新しさ
検算器の書き方を型で縛る。「どのフィールドを読んでよいか(footprint)」「必ず反例を持つこと(空回りの禁止)」を機械が強制。犯人特定や弱点測定を言語の標準機能にします。

7 実験と結果 この仕組みは正しいか?を数字で

この「検算器の書き方を縛る仕組み」を作り、本物のレシートデータで4つのチェックをしました。

試したこと結果やさしい意味
既存の4ルールを新方式で書けるか0/4 が手抜き全部きちんと書けた。表現力の壁に当たらなかった
昔の手書きルールと同じ判定をするか35件中0件ズレ完全に同じ挙動。おもちゃではなく本物の置き換え
健全性の自動チェック4本すべて合格「正しい伝票では黙る」「必ず反例を持つ」を機械が確認
読んではいけない場所を読むバグ定義時に自動拒否既存ツール(SHACL/OPA)には無い能力。ここが新しさの証拠
結論: このねらいは「筋が良い」と実データで確認
新方式は既存ルールを漏れなく表現でき、手書きと完全一致し、既存ツールにできない安全チェック(読む範囲の型強制)を実演できました。

8 結局、いい状況なの?

率直に言うと 「土台は健全、ねらいの手応えあり、ただし本当に役立つ証明はこれから」。

良い点

  • 仕組みが設計どおり動いている
  • 都合よく水増しせず、死角(35.2%)も正直に数値化
  • 既存ツールに無い能力を実データで実演

まだの点

  • 「辻褄を合わせた間違い」は原理的に捕まらない → 価値は検出率でなく監査可能性に置く
  • 本当に役立つ証明には、あと数個の実験が必要

9 次にやること

  1. この仕組みが「見逃していたバグ」を型レベルで弾く実例を増やす
  2. 実データが1秒未満で解けるか測る(速いなら難しい理屈は捨てて単純化)
  3. AIに検算ルール自体を書かせたとき、その「間違い率」を制約でどこまで下げられるか測る
  4. チェックデジットや個社ルールを試すため、合成請求書データを用意する

用語メモ: VLM=画像を読むAI / 検算器=ルールで検証する仕組み / footprint=そのルールが読んでよいフィールドの範囲 / 整合的誤読=計算の辻褄まで合った間違い(検算で捕まらない)。

キーレスエントリ ― 外部キーを使わない

外部キーを外してアプリ側だけで整合性を守ろうとすると、親を消した瞬間に存在しない行を指す孤児行が残る

← SQL シリーズ目次へ

この回の前提: 第 01 回 アンチパターンとは何か (サンプル DB の bugs / comments テーブル)、第 04 回 ID リクワイアド (主キーと一意性制約の関係)

「外部キー制約はパフォーマンスに響くし、どうせアプリ側でチェックしているから要らない」という判断は、少なくないチームで一度は検討されます。結論を先に言うと、アプリ側のチェックは必ずどこかで漏れ (バグ、競合、一括処理の見落とし) が起き、外部キーが無いデータベースはその漏れを止める最後の手段を失います。この回では、実際に外部キーを外した状態で親の行を削除し、参照先の無い行 (孤児行、orphan row) が残ることを実機で再現します。そのうえで、見つけ方、使ってよい場合、ON DELETE・DEFERRABLE、そして外部キーを追加するときに実際にどれだけ他の処理をブロックするかを確認します。

1. 目的 ― 何をしたかったのか

外部キー制約は、書き込みのたびに参照先の存在を確認するため、わずかなオーバーヘッドがあります。「どうせアプリケーションのコードで comment を作る前に bug の存在を確認している」という理由から、データベース側の外部キー制約を省略し、整合性の確認をアプリケーション側だけに任せる、という判断がされることがあります。

2. アンチパターン ― どう書いてしまい、何が壊れるか

実際に comments.bug_id の外部キー制約を外し、アプリケーション側の確認が漏れた状況を再現します。

ALTER TABLE comments DROP CONSTRAINT comments_bug_id_fkey;

SELECT comment_id, bug_id, comment FROM comments WHERE bug_id = 1;
 comment_id | bug_id |      comment
------------+--------+-------------------
          1 |      1 | reproduced on 2.1
          2 |      1 | also on 2.0

-- 「アプリ」が子の存在を確認せずに親を削除する
DELETE FROM bugs WHERE bug_id = 1;

-- 孤児行 (orphan row): 存在しない bug_id=1 を指す行がそのまま残る
SELECT comment_id, bug_id, comment FROM comments WHERE bug_id = 1;
 comment_id | bug_id |      comment
------------+--------+-------------------
          1 |      1 | reproduced on 2.1
          2 |      1 | also on 2.0

bug_id=1 の行は bugs テーブルからすでに削除されているのに、comments の 2 行は削除されずに残りました。これが孤児行です。さらに、アプリケーションのバグ (例えばタイプミスした bug_id をそのまま送ってしまう) も、外部キーが無ければそのまま書き込まれます。

INSERT INTO comments (bug_id, author, comment) VALUES (9999, 1, 'typo in bug id, app forgot to check');
SELECT comment_id, bug_id, comment FROM comments WHERE bug_id = 9999;
 comment_id | bug_id |               comment
------------+--------+--------------------------------------
          5 |   9999 | typo in bug id, app forgot to check

図: 外部キーが無いと、参照先の bugs の行が削除されても comments の行はそのまま残り、存在しない行を指す孤児行になる。

3. 見つけ方 ― どんな兆候で気づくか

まず、孤児行そのものを LEFT JOIN で直接検出できます。親が無い子の行を探す、最も直接的な方法です。

SELECT c.comment_id, c.bug_id
FROM comments c
LEFT JOIN bugs b ON b.bug_id = c.bug_id
WHERE b.bug_id IS NULL
ORDER BY c.comment_id;

 comment_id | bug_id
------------+--------
          1 |      1
          2 |      1
          5 |   9999

次に、既存のデータベース設計そのものから「外部キーが無い列」を探します。_id で終わる列名や author のような列名は、多くの場合に他のテーブルを参照する意図を持っていますが、それだけでは本当に外部キーが定義されているとは限りません。自分自身の主キー列 (参照される側であり、参照する側ではない) を除外した上で、実際に FOREIGN KEY 制約が付いているかを確認します。

SELECT c.table_name, c.column_name
FROM information_schema.columns c
WHERE c.table_schema = 'public'
  AND (c.column_name LIKE '%\_id' ESCAPE '\' OR c.column_name = 'author')
  AND NOT EXISTS ( -- 自分自身の主キー列は除外する
    SELECT 1 FROM information_schema.key_column_usage kcu
    JOIN information_schema.table_constraints tc
      ON tc.constraint_name = kcu.constraint_name AND tc.table_schema = kcu.table_schema
    WHERE tc.constraint_type = 'PRIMARY KEY' AND kcu.table_name = c.table_name AND kcu.column_name = c.column_name
  )
  AND NOT EXISTS ( -- 外部キー制約が無い列だけを残す
    SELECT 1 FROM information_schema.key_column_usage kcu
    JOIN information_schema.table_constraints tc
      ON tc.constraint_name = kcu.constraint_name AND tc.table_schema = kcu.table_schema
    WHERE tc.constraint_type = 'FOREIGN KEY' AND kcu.table_name = c.table_name AND kcu.column_name = c.column_name
  )
ORDER BY c.table_name, c.column_name;

 table_name | column_name
------------+-------------
 comments   | bug_id

この問い合わせは、comments.bug_id が「名前からは外部キーに見えるのに、実際には制約が無い」列として浮かび上がらせます。これが、外部キーを外してしまったテーブルを既存のデータベースから見つける具体的な方法です。

4. 使ってよい場合

外部キーを省略することが実務上合理的になる場面はいくつかあります。1 つは、参照先のテーブルが別のデータベースやシステムにある場合です。PostgreSQL の外部キー制約は同一データベース内のテーブル間でしか定義できないため、マイクロサービスで他のサービスが持つデータを参照するような場合は、そもそも制約を定義できず、整合性の確認はアプリケーション側 (または結果整合性を前提にした設計) に委ねることになります。もう 1 つは、大量データの一括投入のような場面で、投入中は一時的に NOT VALID の制約や制約自体を外しておき、投入完了後に VALIDATE CONSTRAINT で検証するという使い方です (この場合も、最終的には制約を有効にする前提です)。

一方、このサンプル DB のように同一データベース内で親子関係がある普通の業務テーブルについては、外部キーを省略する合理的な理由はほとんどありません。「パフォーマンスへの影響」を理由にする判断もよく聞かれますが、外部キーの検査自体は参照先の主キーインデックスを使った軽い処理であり、孤児行や参照ミスを防げなくなる代償の方がはるかに大きいのが通常です。

5. 解決策 ― PostgreSQL での正しい書き方

外部キーを付け直す際には、親が削除されたときに子をどう扱うかを ON DELETE で明示します。CASCADE は親と一緒に子も削除します。

ALTER TABLE comments ADD CONSTRAINT comments_bug_id_fkey
  FOREIGN KEY (bug_id) REFERENCES bugs (bug_id) ON DELETE CASCADE;

INSERT INTO comments (bug_id, author, comment) VALUES (2, 1, 'will cascade away');
DELETE FROM bugs WHERE bug_id = 2;
SELECT * FROM comments WHERE bug_id = 2;
(0 rows) -- CASCADE で comments の行も一緒に削除されている

ON DELETE には CASCADE (一緒に削除)・RESTRICT (子がある限り親の削除を拒否、既定に近い挙動)・SET NULL (子の参照列を NULL にする)・SET DEFAULT (子の参照列をデフォルト値にする) があり、業務上「親が消えたときに子をどう扱うべきか」に応じて選びます。bugs.assigned_to のように、担当者 (accounts) が退職してもバグの記録自体は残したい場合は SET NULL が自然です。

もう 1 つ重要な机上の制約が、DEFERRABLE INITIALLY DEFERRED です。既定では、外部キーは文を実行した直後にチェックされます。しかし「先に子の行を書き、同じトランザクションの中で後から親の行を作る」という順序が必要な場面 (相互に参照し合うデータの初期投入など) では、既定のチェック時点では一時的に制約を満たせません。

ALTER TABLE comments ADD CONSTRAINT comments_bug_id_fkey
  FOREIGN KEY (bug_id) REFERENCES bugs (bug_id) DEFERRABLE INITIALLY DEFERRED;

BEGIN;
  INSERT INTO comments (bug_id, author, comment) VALUES (500, 1, 'bug not created yet');
  INSERT INTO bugs (bug_id, summary, reported_by, status) OVERRIDING SYSTEM VALUE
    VALUES (500, 'created after its comment', 1, 'NEW');
COMMIT; -- 制約のチェックはここで初めて行われ、その時点では bug 500 が存在する

SELECT comment_id, bug_id FROM comments WHERE bug_id = 500;
 comment_id | bug_id
------------+--------
          7 |    500

図: DEFERRABLE INITIALLY DEFERRED では、制約の検査が各文の直後ではなく COMMIT の直前まで遅延される。

6. PostgreSQL エンジンで考慮しておくこと ― FK 追加時のロック

外部キーを後から追加する ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY は、既存データを検証する必要があるため、両方のテーブルに重めのロックを取ります。実際に pg_locks で確認すると、次のようになります。

ALTER TABLE comments ADD CONSTRAINT comments_bug_id_fkey2
  FOREIGN KEY (bug_id) REFERENCES bugs (bug_id) NOT VALID;

SELECT c.relname, l.mode, l.granted
FROM pg_locks l JOIN pg_class c ON c.oid = l.relation
WHERE c.relname IN ('comments','bugs') AND l.locktype = 'relation'
  AND l.mode <> 'AccessShareLock';

 relname  |         mode          | granted
----------+-----------------------+---------
 bugs     | ShareRowExclusiveLock |    t
 comments | ShareRowExclusiveLock |    t

NOT VALID を付けて既存データの検証を後回しにしても、ADD CONSTRAINT 自体は両テーブルに ShareRowExclusiveLock を取ります。このロックは同じテーブルへの INSERT・UPDATE・DELETE と競合するため、別セッションからの書き込みはこのトランザクションが終わるまで待たされます。実際に別セッションから SELECT と INSERT を試したところ、次のような違いが出ました。

図: 別セッションからの SELECT は 0.042 秒で即応答したが、INSERT は ADD CONSTRAINT のトランザクションがコミットされるまで 3.108 秒待たされた。どちらも実機で確認した値。

この待ちを避けるために、PostgreSQL は 2 段階に分ける方法を用意しています。まず NOT VALID で制約を追加し (既存データの検証をスキップするため、この ADD CONSTRAINT 自体は速く終わる)、その後に別のトランザクションで VALIDATE CONSTRAINT を実行します。

ALTER TABLE comments VALIDATE CONSTRAINT comments_bug_id_fkey2;

SELECT c.relname, l.mode, l.granted
FROM pg_locks l JOIN pg_class c ON c.oid = l.relation
WHERE c.relname IN ('comments','bugs') AND l.locktype = 'relation'
  AND l.mode <> 'AccessShareLock';

 relname  |           mode           | granted
----------+--------------------------+---------
 bugs     | RowShareLock             |    t
 comments | ShareUpdateExclusiveLock |    t

VALIDATE CONSTRAINT が取るのは ShareUpdateExclusiveLock (自分自身の同時実行は防ぐが、通常の INSERT・UPDATE・DELETE とは競合しない) です。実際に別セッションから INSERT を試したところ、0.044 秒で即座に成功しました。既存データが多いテーブルに外部キーを追加するときは、NOT VALID で短時間だけロックを取ってから、書き込みを止めずに VALIDATE CONSTRAINT で検証する、という 2 段階の手順が実務上の既定です (この手順は第 26 回でさらに詳しく扱います)。

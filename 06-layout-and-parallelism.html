NKI WORKSHOP ・ 06

データレイアウトと並列化 ― Trainium 上では全ては2D

どの軸を partition に置くか、どの軸を free に残すか。その一手が transpose の要不要と DMA 効率を決める

0この記事の狙い

第 1 回で SBUF は「128 partition × free」の 2D スクラッチパッドだと学びました。第 5 回はその上でタイルをどう敷き詰めるかを見ました。今回はもう一歩踏み込み「テンソルのどの軸を partition に、どの軸を free に置くか」という設計判断そのものを掘ります。

一言でいうと
Trainium 上では、どんなテンソルも最終的に2D (128 partition × free) の形に写像されます。この写像の選び方 (どの軸を partition に置くか) 次第で、transpose が要るかどうか、reduction が素直に書けるかどうか、DMA が速いかどうかが決まる。レイアウト設計とは、この写像を先に決めてから計算を組み立てる作業です。さらに視野を広げると、複数コア・複数チップへの並列化も「同じ写像の考え方をチップの外まで延長したもの」として理解できます。
1. 全ては2D ― 写像というメンタルモデル 2. 【体験】どの軸を partition に置くか ― transpose の要不要 3. reduction は free 軸に沿う ― ハード制約から逆算する 4. transpose のコストと、それを消す/隠す工夫 5. 【体験】access pattern ― 表現力のための API 6. 並列化への拡張 ― LNC と TP × SP = world 7. まとめ

対象は AWS Trainium2。数値はワークショップの講義・実測に基づく概算です。第 1 回「ハードウェア階層」(SBUF の 2D 構造・partition 128)と第 5 回「タイリング」を先に読むと理解が早いです。

1全ては2D ― 写像というメンタルモデル

出発点はこの一文です。Trainium 上で計算するとき、どんな形のテンソルも最終的に「128 partition × free」の2D にどこかで写像される。

第 1 回で見た通り、SBUF は 128 本の partition レーンと、各レーンに連なる free 次元で構成される 2D の作業台でした。3 次元・4 次元のテンソル (バッチ・ヘッド・シーケンス長・head dimension を持つ Q/K/V など) を扱うときも、最終的には 「どの軸を 128 本の partition レーンに割り当てるか」「残りをどう free 次元に並べるか」という 2 択に帰着します。

# 例: Q 行列 (head_dim × seq_len) を SBUF に置く
どちらを partition (128 レーン) に、どちらを free にするか
head_dim → partition, seq_len → free  # 一つの選択
seq_len → partition, head_dim → free  # もう一つの選択

この 2 択、どちらも「正しい」数学的には同じ行列を表現できます。しかし Trainium の計算エンジン (Tensor Engine が読む形、reduction が可能な軸) から見ると、片方は素直に計算でき、もう片方は余計な transpose が要ることがあります。レイアウト設計とは、この写像を計算の直前に決めるのではなく、テンソルがメモリに置かれる時点から意識して選ぶ作業です。

合言葉。「このテンソルの形は何か」ではなく「このテンソルのどの軸を 128 partition に、どの軸を free に置くか」で考える。この一問に答えを出すことが、レイアウト設計の実質すべてです。以降の章 (transpose コスト、reduction 制約、access pattern) は、すべてこの一問への答え方を掘り下げたものです。

2【体験】どの軸を partition に置くか ― transpose の要不要

この記事の「絵で覚えて帰ってほしい1枚」です。同じ Q・K 行列を、異なる軸で SBUF に置いた場合の違いを見比べます。

Self-Attention の QKᵀ を例にします。Q・K はどちらも head dimension × sequence length の形でデバイスメモリ (HBM) に置かれています。NKI ISA で SBUF にロードすると、デバイスメモリ上の先頭次元が、そのまま SBUF の partition 次元に自動的にマップされるという仕様があります。

partition (128 レーン) free 次元 余計な transpose (発生時のみ)

head_dim を先頭 (partition) に置いた場合: QKᵀ の縮約 (contraction) はまさに head dimension に沿って行われます。Q・K どちらも縮約したい軸がすでに partition 次元に来ているので、Tensor Engine はロードされたそのままの形を読んで matmul できます。明示的な transpose が不要です。seq_len を先頭 (partition) に置いた場合、縮約したい head dimension が free 側に回ってしまうため、matmul の前に余計な transposeを挟む必要が生じます。同じ計算結果でも、レイアウトの選び方一つで transpose の有無が変わるのが分かります。

この例が示す原則。縮約したい軸 (contraction dimension) を partition に置くと transpose が要らない。逆に、他の理由 (例えば別の演算で使いやすいから) で違う軸を partition に置くと、matmul の直前に transpose という「税金」を払うことになります。どちらの軸を partition に置くかは、後続の計算が何を縮約するかを先に見て決めるべきだ、という教訓です。

3reduction は free 軸に沿う ― ハード制約から逆算する

レイアウトを決めるとき、もう一つ効いてくるハード制約があります。「合計する軸」の置き場所です。

Vector Engine や Scalar Engine が行う reduction (合計・最大値などの集計) には、NKI ISA 上の制約があります。reduction は必ず free 軸に沿って行うという制約です。partition 方向をまたいで直接 reduction することはできません。

# reduction の制約 (ハード仕様)
reduction (max, sum, ...) は free 軸 に沿ってのみ実行可能
partition 軸 をまたぐ reduction は直接できない ← ここが制約

これが第 2 節のレイアウト選択にもう一つの判断基準を与えます。「このテンソルのどの軸を後で reduction したいか」を先に確認し、その軸を free に置くのです。Self-Attention の softmax がこの制約と偶然きれいに噛み合う例として知られています。softmax の row-wise な max・sum は sequence length 方向の reduction ですが、Q・K を head_dim-partition / seq_len-free で置いたレイアウトでは、sequence length がちょうど free 軸に来ているため、reduction がそのまま素直に書けます。

レイアウト設計の二段判定。(1) 後続の matmul がどの軸を縮約するか → その軸を partition に。(2) 後続の reduction がどの軸を畳みたいか → その軸を free に。2 つの要求が同じテンソルの中で競合することもある (縮約したい軸と reduction したい軸が両方 partition を欲しがる、等)。そのときは「どちらのコストが大きいか」を見て、片方に transpose という妥協を払う判断になります。

partition 軸をまたぐ集約が必要なら ― reduction を matmul に変換する

ここまでの制約は「畳みたい軸を free に置けば reduction は素直に書ける」という話でした。では、そもそもpartition 軸をまたいで集約したい場合 (128 本のレーンに分散した値を1つにまとめたい場合) はどうするのか。reduction 命令では直接できませんが、実務でよく使われる回避策があります。全要素が 1 の行列 (all-ones 行列) を stationary 側に置いた nc_matmul を使う、というものです。Tensor Engine の matmul は partition 軸に沿って内積を取る演算なので、stationary 側を全部 1 にしておけば、その内積はそのまま「partition 方向の足し算」になります。reduction をそのまま matmul に変換してしまう、という定石です。

# partition 軸をまたぐ集約を matmul で行う
stationary = all-ones 行列 (partition × 1、全要素 1)
moving    = データ (partition × free)
nc_matmul(stationary, moving) = onesᵀ @ データ
  → free 軸ごとに、partition 方向 128 本分を足し合わせた結果 (1 × free)

この「ones 行列との matmul で partition 方向の総和を作る」という技法は、layernorm の分散計算 (E[X²] − E[X]²) のように、partition 方向にまとめた統計量が必要な場面でも同じ形で使われています。

stationary と moving、どちらに何を割り当てるか

いま出てきた nc_matmul の2つの引数 (stationary, moving) には、割り当ての実践ルールがあります。第 1 回で見た通り、Tensor Engine は内部で LoadStationary と MultiplyMoving という2つの命令に分けて動作し、LoadStationary は MultiplyMoving より高速というハードウェア上の非対称性を持ちます。この非対称性から導かれる実践ルールが、free 軸が小さい方を stationary に、大きい方を moving に割り当てるという判断です。stationary 側は一度ロードすれば以降の計算で使い回されるため、小さい方をそこに置くほど LoadStationary の速さを活かせます。行列 × ベクトルの積 (autoregressive なトークン生成の decode で典型的に現れる、free 軸が極端に小さい形) では、ベクトル側を stationary に置くのが定石です。

この節のもう一つの合言葉。reduction が partition 軸をまたぐならall-ones 行列との matmulに変換する。nc_matmul の2引数を割り当てるときはfree 軸が小さい方を stationary に置く。どちらも「Tensor Engine の非対称な内部構造 (LoadStationary/MultiplyMoving) を逆算して使う」という、この章に一貫する発想の具体例です。

4transpose のコストと、それを消す/隠す工夫

レイアウトの選択を誤ると transpose が要る、と述べました。ではその transpose、実際どれくらい重いのか。そして軽くする手はあるのか。

Trainium に transpose 専用のエンジンはありません。transpose は Tensor Engine 上で (単位行列との積として) 実行され、結果は PSUM に蓄積されます。つまり transpose は matmul と同じ演算器を奪い合う「本来の計算ではない仕事」です。Self-Attention の最適化実演では、PV matmul の直前に value 行列を transpose する場面が、Tensor Engine の時間を有意に消費するボトルネックとして現れました。

効きどころの実例 (ワークショップの実測・概算)。value 行列の transpose を、そのまま FP32 で行うのではなく、先に BF16 へダウンキャストしてから transpose すると大きく速くなる傾向が確認されています。Tensor Engine は低精度ほど高いスループットを出せるため、transpose という「必要だが本質的でない仕事」を軽くできます。PSUM のアキュムレータは常に FP32 のままで、精度が必要な蓄積そのものには影響しません。

この「ダウンキャストして transpose」は、後続の第 8 回で扱う低精度化の考え方の先取りです。ここで持ち帰ってほしいのは、transpose のコストは「精度」でも調整できるという一点。レイアウト選択で transpose を無くせるならそれが一番ですが、無くせない transpose が残るなら、bf16 化や DMA transpose (専用のハードウェアパスを使った転置) でそのコストを削る、という二段構えです。

transpose 対策の優先順位。①レイアウト設計で transpose 自体を無くす (第 2 節)。②無くせない transpose は低精度化 (bf16 化) で高速化する。③大きな連続転置には専用の DMA transpose 機能を使う (第 1 回の DMA 帯域の話がそのまま効く領域)。「transpose は正しいレイアウトを得るために必要だが、あまり効率的な仕事ではない」と割り切り、まずレイアウトで消せないか検討するのが出発点です。

5【体験】access pattern ― 表現力のための API

標準的な numpy 風のスライシングでは表現できないレイアウトを記述する API が access pattern (.ap()) です。ここで大事なのは位置づけの誤解を避けることです。

SBUF は物理的には 1 次元のメモリです。そこに「128 partition × free」という 2D の意味を与えているのはアクセスの仕方に他なりません。access pattern API は、この読み出し方をネストしたループとして明示的に書く手段です。各次元は (stride, count) のペアで表現され、「stride だけ進んで、count 回繰り返す」を入れ子にしていきます。

# access pattern の記法イメージ (ネストループとして解釈)
t.ap(pattern=[[stride0, count0], [stride1, count1], ...])
# 先頭の (stride0, count0) は必ず partition 次元をストライドする
# かつ stride0 は free 次元の合計サイズでなければならない (ハード制約)

下のデモは、2 段の access pattern (partition 用のペアと free 用のペア) が SBUF 上のどのアドレスをどの順で読み出すかを 1 ステップずつトレースします。stride を変えると、同じ要素数でも読み出す順番と間隔が変わる様子が見えます。

free stride
partition (先頭ペア) 読み出し済みの要素 今読んでいる要素

ここで最も重要な位置づけの注意です。ワークショップでは 「access pattern はパフォーマンス API ではなく表現力の API」と明確に語られています。正しく表現できても速くなるとは限りません。特に transpose を access pattern で表現すると、小さな DMA が多発して遅くなりがちです (第 4 節の DMA transpose 専用パスの方が適しています)。access pattern の役割は「標準スライスでは書けない、strided/tensorized なアクセスを表現できる」ことそのものであり、速さはそこから生まれる二次的な結果に過ぎません。

使い分けの指針。連続アクセスなら標準スライスで十分。strided アクセスや、n個ごとに要素を取る、reinterpret cast (dtype を変えて再解釈する) のような、標準スライスで表現できないレイアウトが必要になったときに access pattern を使う。「表現できるから速い」ではなく「表現できないと書けない」が使う理由です。

6並列化への拡張 ― LNC と TP × SP = world

ここまでは 1 コア内のレイアウトの話でした。同じ「どの軸をどこに置くか」という発想は、コアをまたいだ並列化にもそのまま延長できます。

第 1 回で触れた LNC (Logical NeuronCore) を思い出してください。1 デバイスに 8 個ある物理コアを、既定では 2 個ずつ束ねて 4 個の論理コアとして扱います (LNC2)。LNC1 に切り替えると、束ねずに 8 個の物理コアとして扱えます。どちらが良いかは一様には決まらず、計算量が支配的なワークロードか、メモリ帯域が支配的なワークロードかによって選び方が変わります。小さいモデルでは LNC1 にして最小の並列度で済ませる方がコスト効率が良くなる場合がある、という判断がワークショップで語られています。

並列化の単位を組み立てる考え方。ワークショップでは tensor parallelism (TP) と sequence parallelism (SP) という 2 つの分割軸を掛け合わせて、実際に使用するコア数 (world) を決めるという考え方が語られています。TP × SP = world。TP はモデルの重み・計算を複数コアに分割する軸、SP はシーケンス長方向の分割軸で、両方を同時に使うこともできます。同じ TP・SP の値でも、LNC1 か LNC2 かで実際に使う物理コア数は変わるため、world をどう組むかは LNC 設定と一緒に考える必要があります。

これは第 2 節・第 3 節で見た「どの軸を partition に、どの軸を free に置くか」という問いのチップ間バージョンです。1 コア内では 128 partition レーンへの軸の割り当てが問題でしたが、複数コアに広がるとどの軸をどのコア群に分割するかが問題になります。collective 通信 (all-reduce・all-gather 等) を使うレプリカグループの組み方も、TP 群は連続したコア番号、SP/CP (context parallel) 群はストライドしたコア番号、というように分割の意図がグループのトポロジーに直結します。

この章で扱う範囲。並列化の具体的な規模 (何チップ・何ノードでどこまで伸びるか) はモデル・世代・構成に強く依存し、本稿では立ち入りません。ここで持ち帰ってほしいのは「1 コア内のレイアウト設計と、複数コアへの並列化は、同じ『軸をどこに割り当てるか』という問いの延長線上にある」という考え方の骨格だけです。

7まとめ

「データレイアウトと並列化」の論点を一枚に整理します。

論点要点
中心メンタルモデルTrainium 上ではどんなテンソルも最終的に2D (128 partition × free) に写像される。写像の選び方がレイアウト設計
partition の選び方後続の matmul が縮約したい軸を partition に置くと transpose が不要になる (Q/K の head dimension が好例)
reduction 制約reduction は free 軸に沿ってのみ可能というハード制約。畳みたい軸を free に置く
transpose コストTensor Engine 上の演算で「本質的でない仕事」。レイアウトで消す→消せなければ bf16 化/DMA transpose で軽くする
access pattern(stride, count) のネストループで SBUF の読み出しを表現する「表現力の API」。パフォーマンス API ではない
並列化への拡張LNC1/LNC2 でコアの束ね方が変わる。TP × SP = world という分割の組み立てが、レイアウト設計のチップ間版
結論。レイアウト設計の実質は「このテンソルのどの軸を 128 partition に、どの軸を free に置くか」という一問に答えることです。答えを出す基準は 2 つ ― 縮約したい軸は partition に (transpose を消すため)、畳みたい (reduction したい) 軸は free に (ハード制約を満たすため)。この 2 つが競合するときに transpose という妥協が生まれ、それは低精度化や専用 DMA パスで軽くできます。access pattern は、この設計を標準スライスの外側まで表現するための道具です。そして同じ「軸をどこに割り当てるか」という発想は、1 コアの中だけでなく、LNC の設定や TP × SP という複数コアへの分割にもそのまま延長されます。
次回はこのレイアウトの上に「エンジンを遊ばせない」ソフトウェアパイプラインと allocation を積み重ねます。

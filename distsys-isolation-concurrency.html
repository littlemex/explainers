分離レベルと並行制御 ― 座席を 2 人に売らないための仕組み

分離レベルは「どの異常を許し、どの異常を防ぐか」の契約であり、楽観ロックと悲観ロックはその契約を守るための 2 つの実装手段である

この回の前提: 第 13 回 一貫性モデル (線形化可能性と直列化可能性の違い)

同じ座席やアカウントを複数のトランザクションが同時に触ると、1 件ずつ順番に処理していれば起きない異常が生まれます。分離レベルは、この異常のうちどれを許し、どれを防ぐかを定めた契約です。結論を先に言うと、分離レベルを強くするほど異常は減りますが、同時に実行できる量が減るか、処理が待たされるかという代償が増えます。この回では ANSI SQL の 4 段階の分離レベルと、それぞれが実際に何を保証するのかを、座席予約やフラッシュセールの具体例で確認します。

1. この回で解く問題 ― 同時に動く取引が生む異常

1 件のトランザクションだけが順番に動いているなら、何の問題も起きません。問題が生まれるのは、複数のトランザクションが同じデータに同時に触るときです。ACID のI (Isolation, 分離性) は、この「同時実行」が引き起こす異常から、アプリケーションを守るための保証です。

SDFC の ticketmaster (座席予約) を例にします。人気イベントのチケットでは、同じ座席に対して複数人が同時に購入ボタンを押します。もし「座席の空き状況を読む」と「予約を書き込む」の間に他のトランザクションが割り込むと、lost update (更新の消失) という異常が起きます。トランザクション A が座席の状態を読み、まだ空いていると判断して予約を書き込もうとする間に、トランザクション B が先に同じ座席を予約してしまうと、A の書き込みが B の予約を上書きしてしまい、2 人に同じ座席を売ってしまいます。

こうした異常は「分離レベルを上げれば防げる」と言われますが、分離レベルを上げるほど同時に処理できる量は減り、待たされるトランザクションが増えます。つまりこの回のテーマは、どの異常をどこまで防ぐかという契約と、その契約を守るためにどれだけの代償を払うかのトレードオフです。

図: A が座席を読んだ後に B が予約を確定させ、その後 A が古い情報のまま書き込むと B の予約が消える (lost update)。

2. 仕組み ― ANSI SQL の 4 分離レベルと MVCC

データベースは「どの異常まで許すか」を段階的に選べるようにしています。ANSI SQL が定めた 4 つの分離レベルは、弱い方から次のように並びます。Read Uncommitted はまだコミットされていない他のトランザクションの変更も読めてしまう最も弱いレベル、Read Committed はコミットされたデータだけを読む (PostgreSQL の既定値)、Repeatable Read はトランザクション開始時点のスナップショットを最後まで保ち続ける、Serializable はすべてのトランザクションが実際には 1 本の順番で実行されたかのように振る舞うことを保証する、最も強いレベルです。

分離レベル ダーティリード 非再現リード ファントム
Read Uncommitted起こりうる起こりうる起こりうる
Read Committed防ぐ起こりうる起こりうる
Repeatable Read防ぐ防ぐ起こりうる
Serializable防ぐ防ぐ防ぐ

この表の中身を実装するのが MVCC (Multi-Version Concurrency Control, 多版型並行制御) です。1 つの行に対して複数のバージョンを保持し、各トランザクションには「自分が見てよいバージョンはどこまでか」を示すスナップショットを割り当てます。これにより、読み取りが書き込みをブロックせず、書き込みが読み取りをブロックしない形で、Read Committed や Repeatable Read を実現できます。

図: MVCC では各行に複数バージョンを保持し、各トランザクションは自分のスナップショット内のバージョンを読む。

3. 仕組み ― write skew という第 5 の異常

ANSI SQL の定義はダーティリード・非再現リード・ファントムの 3 種類しか数えていませんが、Berenson, Bernstein, Gray, Melton, O'Neil, O'Neil の 1995 年の論文 "A Critique of ANSI SQL Isolation Levels" は、この定義があいまいで異常の数も足りないことを指摘しました。その代表例が write skew です。

write skew は、2 つのトランザクションが別々の行を書き込むために、個々の行のロックやバージョン管理だけでは検出できない異常です。教科書的な例は「オンコール医師」です。病院の規則は「医師を 1 人もオフコールにしてはいけない (最低 1 人は on-call を維持する)」というものです。医師 A と医師 B がともに on-call のとき、A は「自分以外にも on-call の医師 (B) がいる」ことを確認してから自分を off-call にし、同時に B も「自分以外にも on-call の医師 (A) がいる」ことを確認してから自分を off-call にします。それぞれの確認は読み取り時点では正しいのに、2 つのトランザクションが両方コミットすると、誰も on-call ではなくなり、病院の規則を破ってしまいます。

この異常は PostgreSQL の公式ドキュメントでも明確に説明されています。Repeatable Read (スナップショット分離) は、個々の行の読み書きの一貫性は保証しますが、「2 つのトランザクションがまたがって初めて成り立つ制約」までは守りません。この種の制約を守るには、PostgreSQL の Serializable (SSI, Serializable Snapshot Isolation という述語ロックに基づく実装) を使う必要があります。

これを座席予約や宿泊予約に当てはめると、「個々の座席の二重予約」は 1 行のロックで防げますが、「販売した座席の合計が会場の定員を超えない」のような複数行にまたがる制約は、行ロックだけでは守れません。SDFC の hotel-booking の議論でも、航空業界ではオーバーブッキング (定員を超えた受け付け) は違法だが、ホテル業界では意図的に 10 % のオーバーブッキングを許容する設計もある、という対比が出てきます。つまり「write skew を防ぐべきか」自体が、業界のルールやビジネス要件によって変わる設計判断です。

図: write skew ― 別々の行を書くので行ロックでは検出できないが、2 つの行をまたいだ制約が破られる。

4. 仕組み ― 楽観ロックと悲観ロック

分離レベルは「どの異常を防ぐか」という契約でしたが、実際の衝突をどう処理するかには 2 つの方式があります。

悲観ロック (pessimistic locking) は、衝突が起きることを前提に、読む前にロックを取ってしまう方式です。SQL では SELECT ... FOR UPDATE が典型で、A がこの行をロックしている間、B は同じ行を読み書きしようとすると待たされます。確実に衝突を防げますが、ロックを持っている間は他のトランザクションを待たせるため、人気イベントのように競合が集中する場面ではボトルネックになります。

楽観ロック (optimistic locking) は、衝突は稀だという前提で、読むときにはロックを取らず、更新するときに「自分が読んだ時点のバージョンのままか」を確認する方式です。行にバージョン番号を持たせ、更新文を UPDATE ... WHERE id = ? AND version = ? のように書き、更新できた行数が 0 件なら「他の誰かが先に更新した」と判断してやり直します。ロックを長時間持たない分スループットは上がりますが、競合が激しいとやり直しが頻発します。

SDFC の ticketmaster の議論では、座席の確保は「決済が終わるまでロックを握り続ける」のではなく、座席に一時的な hold (保留) を 5 分から 10 分程度だけ置き、その間に決済が完了しなければ自動的に解放する設計が検討されていました。これは悲観ロックと楽観ロックのどちらとも異なる第 3 の実務的な解決で、「ロックは短く持ち、長い待ち時間が必要な処理 (決済) はロックの外に出す」という考え方です。

図: 悲観ロックは待たせて防ぐ、楽観ロックは衝突してからやり直す。どちらも衝突への対処方針が違うだけ。

5. どこで壊れるか ― 在庫 ・ 座席予約の設計判断

SDFC の flash-sale (限定セール) の要件は厳しく、「オーバーセル (在庫以上に売ってしまう) もアンダーセル (在庫を余らせて売り切れと表示する) も禁止」「決済は失敗することがある」というものです。ここで悲観ロックを素直に使うと、1 つの在庫行に 10 万人が同時に SELECT FOR UPDATE をかけるような状況になり、ロックの待ち行列がそのままボトルネックになります。SDFC の inventory の議論では、これを避けるために「在庫を一時的に hold する」と「hold を実際の販売として確定 (execute) する」を 2 段階に分け、hold の時点では強い一貫性で在庫を減らすものの、execute (決済成立の確認) は可用性を優先して後から処理する、という設計が検討されていました。

逆に楽観ロックを素直に使うと、人気商品に 10 万人が群がった瞬間、ほぼ全員が「バージョンが変わっていた」としてやり直しになり、再試行の嵐 (retry storm) が起きます。SDFC の flash-sale の議論では、この集中を避けるために、1 つの在庫カウンタではなく複数台に分散させたシャード化カウンタを使う案が出てきます。ただし在庫をシャードに分けると、在庫が残っているシャードと無くなったシャードが混在し、「在庫はあるのに自分が当たったシャードには無い」という新しい不公平が生まれます。この種の近似カウンタの設計は第 23 回で詳しく扱います。

どちらの方式でも、「競合の激しさ」と「処理 1 件あたりの時間の長さ」の 2 つの軸で向き不向きが決まります。悲観ロックは処理が短く競合がそこまで激しくない場合に向き、楽観ロックは読み取りが多く書き込みの競合が稀な場合に向きます。10 万人が同じ 1 行を争うような極端な競合には、どちらの方式も単体では向かず、ロックの対象をより小さい単位 (座席単位、シャード単位) に分散させる設計そのものが必要になります。

6. 実システムでの例

PostgreSQL は既定で Read Committed を使います。多くのアプリケーションはこれで十分ですが、write skew のような複数行をまたぐ制約を守りたい場面では、明示的に Serializable を指定する必要があります。Serializable は述語ロックによる衝突検出のコストがかかるため、「どの制約が本当に守られるべきか」を見極めて使う範囲を絞るのが実務的な判断になります。

SDFC の airline-ticketing の議論では、航空業界ではオーバーブッキングが法律で禁止されている一方、hotel-booking の議論では意図的に 10 % のオーバーブッキングを許容する設計が紹介されていました。同じ「座席 ・ 部屋を売る」という問題でも、業界ごとに「write skew や lost update をどこまで厳密に防ぐべきか」という要件自体が異なるという点は、設計の出発点として重要です。

SDFC の ticketmaster や payment-gateway の議論に出てくるauth (仮売上) → capture (確定売上) という 2 段階の決済フローも、この回で見た「ロックは短く持ち、時間のかかる処理はロックの外に出す」という考え方の実例です。座席や在庫を短時間だけ hold し、決済という時間のかかる処理は hold の外側で非同期に進めることで、ロックの保持時間を最小化しています。

まとめると、分離レベルは「どの異常を許すか」という契約、楽観 / 悲観ロックは「その契約をどう実装するか」という手段です。そして実際の設計では、この 2 つの選択だけでなく、ロックの対象をどの粒度でどれだけ短く持つかという工夫が、現実の競合をさばく決め手になります。

なぜ経路は差し替えられないのか ― 3 つの理由

土台を捨てられない。同じディスパッチキーに 2 つは登録できない。降ろし方が未出荷

← シリーズ目次

0この回の狙い

「プラグインのコンパイル経路を、素直な書き方が通る方に差し替えればよい」という発想がどこで詰まるのかを、構造として説明します。

この回の結論は時点依存です。ライブラリ側の 1 リリースで変わります。現在地を自分で確認する方法は 2 つあり、プラグインの feature matrix の torch.compile (native PyTorch) の行と、ランタイム兼カーネル基盤ライブラリの配布物に非 XLA の降ろし方のモジュールが含まれるかどうかです (§5 で具体的に扱います)。

第 4 回で、コンパイル経路を替えると第 1 層 (計算の表現) のコストが下がることを確認しました。ならば差し替えたい。プラグインには実際にそのためのスイッチらしきものが用意されています。しかしこれは動きません。理由が 3 つ重なっていて、そのうち 1 つは PyTorch のディスパッチ機構に由来する実装レベルの排他です。

一言でいうと
3 つが同時に成立しています。(1) スタック第 3 層のライブラリは捨てられない ― プラグインのカーネルライブラリ全体がその上に建っている。(2) 同じディスパッチキーを使う 2 つのランタイムは同一プロセスに入れられない ― PyTorch は 1 つのキーに backend fallback を 1 つしか許さず、外部実装は支援 API の都合で PrivateUse1 に集まる。(3) 非 XLA の降ろし方はまだ出荷されていない ― 公開インデックスの最新版にもそのモジュールが無い。
つまりプロセス内で経路を差し替える道は、ライブラリ側が対応版を出すまで存在しません。なお (2) は PyTorch の設計上どうしようもない制約ではなく、実装がどのキーを使うかの帰結です。どちらかが別のキーを使うか fallback の登録を避ければ解消しうる種類の問題で、ただしそれはライブラリ側の変更でしか起きません。
1. スイッチは存在する 2. 理由 1 ― スタック第 3 層は土台である 3. 理由 2 ― ディスパッチキーの衝突 4. 名前を分けているのは親切ではない 5. 理由 3 ― 非 XLA の降ろし方が未出荷 6. 何を待っているのかを明確にする 7. 計画への含意

1スイッチは存在する

まず事実確認です。プラグインには経路を選ぶ仕組みが入っています。だから「無い」わけではありません。

プラグインは環境変数でバックエンドを選べます。既定は現行の XLA 経路で、もう 1 つ native と名付けられた選択肢があります。この選択によって、torch.compile に渡すバックエンド名と、分散通信のバックエンド名が変わります。並列化レイヤの中にも、この選択で分岐する箇所があります。

公開されている feature matrix でも、コンパイルの項に 2 行が並んでいます。XLA バックエンドが対応済み、native PyTorch が未対応。つまり「やろうとしている」ことは公開されています。問題は、その配線の先がまだ繋がっていないことです。

2理由 1 ― スタック第 3 層は土台である

第 1 回で「スタック第 3 層は差し替え可能な部品ではなく地面だ」と書きました。その根拠をここで出します。

プラグインのカーネル呼び出し層を調べると、約 30 のファイルがスタック第 3 層の同じ関数 (wrap_nki) を import しています。低レベルカーネルをグラフに取り込むためのラッパです。対象は attention の全種類 (prefill 用、decode 用、マスクつき、スライディングウィンドウ、投影)、MoE の全種類 (ルーティング、並べ替え、ブロック単位、階層的な全対全通信)、集団通信、topk、累積和、正規化つき量子化。

加えて、プラットフォーム判定、並列トレース、並列コンパイル、実行コンテキスト、環境変数の読み出し、集団通信のオーバーライドもスタック第 3 層から来ています。

依存の向き。カーネル層は第 3 層に集中して依存している。だから第 3 層は交換部品ではない

したがって「スタック第 3 層を別の実装に置き換える」は、カーネルライブラリを失うことと同義です。attention も MoE も自前で書き直すなら、そもそもプラグインを使う意味が薄れます。

3理由 2 ― ディスパッチキーの衝突

ではスタック第 3 層を残したまま、もう 1 つのランタイムを足せばよいのでは。ここで PyTorch のディスパッチ機構に当たります。この節の結論は公開情報だけから導けます。

PyTorch には、CUDA や XPU のように標準で用意されていない外部アクセラレータのために予約されたディスパッチキーがあります。PrivateUse1 から PrivateUse3 までの 3 つです。だから枠自体は 1 つではありません。

それでも実際には衝突が起きます。公開されている事実を 3 つ並べると、結論が出ます。

  1. PyTorch は 1 つのディスパッチキーに対して backend fallback を 1 つしか許しません。2 つ目を登録しようとすると例外になります。これは PyTorch 本体の仕様です
  2. 外部バックエンドの支援 API は、実質 PrivateUse1 を前提に整備されています。デバイス名の改名 (rename_privateuse1_backend) やデバイスモジュールの登録がその例です。だから外部実装はこのキーに集まります
  3. 公開されているスタック第 3 層のライブラリは、この PrivateUse1 に登録します。公開イメージの中身を見れば確認できます

この 3 つから導かれるのは次の一点です。PrivateUse1 を使う別のランタイムを、同じプロセスに同居させることはできません。先に登録した方が勝ち、後から来た方は登録に失敗します。順序を入れ替えても対称に同じことが起きます。

枠は 3 つあるが、支援 API の都合で外部実装は同じキーに集まる。1 キーに fallback は 1 つなので同居できない

この制約の所在をはっきりさせておきます。これはPyTorch の設計上どうしようもない話ではありません。どちらかの実装が別のキーを使うか、fallback の登録を避ければ解消しうる種類の問題です。ただしそれはライブラリ側の変更でしか起きません。利用者の側で回避する手はありません。

4名前を分けているのは親切ではない

この衝突を知ると、プラグインのソースにあるある一行の意味が変わります。

プラグインの新しめの版には、torch.compile のバックエンド名を返す関数があり、そこにコメントが付いています。要約すると「この名前を意図的に neuron にしていない。neuron はもう一方のパッケージ用に予約しておき、それを別途インストールしても上流の意味論が保たれるようにする」。

最初に読んだときは、丁寧な名前空間の配慮に見えます。しかし前節を踏まえると読み方が変わります。この予約は、共存できないことを前提にした棲み分けと読むのが自然です。断定はできません (後方互換や上流の命名規約という別の動機もありえます)。ただし、少し古い版ではこの名前が neuron そのものだったという事実は、この読みを支持します。曖昧さを取り除くために改名されたわけです。

読み手にとっての教訓
ソースのコメントは、書かれている内容だけでなく「なぜそれを書く必要があったのか」を読むと情報量が増えます。名前を予約する必要があるのは、予約しないと衝突する相手が実在するときだけです。設計意図はしばしば、こういう防御的な一行に残ります。

5理由 3 ― 非 XLA の降ろし方が未出荷

では衝突しない形、つまりスタック第 3 層自身が非 XLA の経路を持てばよい。プラグインの公開ソースはまさにそれを参照しています。ただし、まだ手に入りません。

プラグインの新しい版は、native を選んだときスタック第 3 層の「native バックエンド」というモジュールを呼び出します。名前のとおり、スタック第 3 層が持つ非 XLA の降ろし方です。これなら衝突しません。同じランタイムの中で降ろし方が変わるだけですから。

問題は、そのモジュールが、公開パッケージインデックスから取得できる最新版に含まれていないことです。最新版のアーカイブを展開して中を確認すると、コンパイル関連のモジュールは XLA 経由の lowering、グラフ捕捉、キャッシュ、並列コンパイル、並列トレース、プラットフォーム判定、成果物管理、実行コンテキスト、スキーマ。native バックエンドはありません。

つまりプラグインのコードは、まだ出荷されていないモジュールを参照しています。feature matrix が未対応と表示しているのは、この状態を正確に反映しています。スイッチは配線済みだが、繋ぐ先が届いていない。

確認したこと結果
プラグインに native 経路のスイッチがあるかある (環境変数で選べる)
プラグインはスタック第 3 層に直接依存しているかしている。ランタイムバインディングを直接呼ぶ箇所が公開ソースにある
同じディスパッチキーを使う 2 つのランタイムを同居させられるかできない。1 キーに fallback は 1 つという仕様からの帰結 (§3)
スタック第 3 層の新しい版に非 XLA の降ろし方があるか公開インデックスの最新版にも無い (確認は最新版のみ)

6何を待っているのかを明確にする

「待ち」という結論は同じでも、何を待っているかを取り違えると計画が狂います。

ここまでの整理から、待っている対象がはっきりします。待っているのは「Native PyTorch のパッケージが公開配布されること」ではありません。スタック第 3 層のライブラリが非 XLA の降ろし方を含む版になることです。これはプラグインの公開ソースがそのモジュールを参照していることから導かれる読みで、提供時期についての公開情報は執筆時点でありません。

この区別が計画に効く理由は 2 つあります。

ひとつ。Native PyTorch 側が公開配布されても、それだけではサービングの移植は楽になりません。プラグインが呼ばないバックエンドは、サービングの利用者にとって存在しないのと同じです。逆に、スタック第 3 層が対応版を出せば、Native PyTorch 側の提供状況に関係なく、サービング経路のコスト層① (計算の表現) が下がります。

ふたつ。その日が来ても、移植は消えません。第 4 回の表のとおり、下がると確認できたのはコスト層① (計算の表現) だけです。コスト層② (サービング契約) はサービング設計に由来するので降ろし方とは無関係のはずで、コスト層③ (状態の契約) についても同様と見ていますが、こちらは経路 A (XLA) の機構に依存する解き方があるため推定にとどまります。だから「対応版が出れば Hugging Face のモデルがそのまま動く」という期待は、その日が来ても満たされません。

ここを曖昧にすると計画を誤ります。期待が「移植不要」に置かれていると、対応版が出た日に落胆が来ます。「独自の演算を低レベルカーネルで書かずに済むようになる見込みがある。ただしモデル実装は依然として必要」という形で、下がる層と残る層を分けて理解しておくべきです。

さらに 1 つ。対応版が出て消えるのは「通すための書き換え」だけです。実用的な性能に必要な数式の再構成は残ります (第 4 回 §8)。

7計画への含意

構造が分かったので、今できることと待つべきことを分けます。

今できる待ちが要る
正しさの検証を CPU で行うできる (CPU 実行モード、第 5 回)―
精度のベンチマークを取るできる (移植済みモデル)―
本番のスループットとコストを出すできる (移植済みモデル)―

表の最下行が次回の主題です。プロセスを分ければディスパッチキーの衝突は起きません。片方のプロセスでコンパイルし、もう片方で実行する。この道が本当に通るのか、通るとして代償は何かを第 7 回で測ります。

出典と確認方法: バックエンド選択のスイッチ、名前予約のコメント、カーネル層の依存関係は vllm-project/vllm-neuron の公開ソースで確認できます。スタック第 3 層のライブラリに非 XLA の降ろし方が含まれていないことは、公開パッケージインデックスから取得できる最新版のアーカイブ内容を列挙して確認しました (確認したのは最新版のみです)。1 つのディスパッチキーに backend fallback が 1 つしか登録できないこと、および PrivateUse1 を前提とした支援 API の整備状況については PyTorch の拡張ガイドを参照してください。

確認時点: 本稿の記述は 2026-09-01 時点のものです。対象はプラグイン 0.21.0.1.0.0 と 0.24.0.1.1.0 の公開ソースおよび公開コンテナイメージ、公開パッケージインデックスから取得できるランタイム兼カーネル基盤ライブラリ (2.11.0.1.0.1284 / 2.12.0.1.0.1284)、コンパイラ 2.26 / 2.27 系、低レベルカーネル言語 0.5.0 / 0.6.0、PyTorch 2.11.0 です。バージョンが上がれば名前も挙動も変わりうるので、正はソースと配布物です。

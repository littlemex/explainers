36% の帯域 ― 行列積を消してみて分かったこと

3 つのもっともらしい仮説を測って殺し、ループの構文がコンパイラに何を許可するかという答えに着地するまで

← シリーズ目次

0この回の狙い

第 10 回は開ループ到着が炙り出す静かな故障でした。この回は性能の帰属の話です。1 つの decode 用 MoE カーネルが出すべき帯域の 36% しか出ておらず、もっともらしい仮説を 3 つ測って殺したあとに、ようやく本当の原因に着きました。

扱うのは 1 つの問いです。4 つの構造的な書き換えが同じ数字を返すとき、それでも同じ仮説を疑い続けてよいのか。出てくるのは、行列積の融合・stationary と moving の入れ替え・indirect DMA という 3 つの死んだ仮説と、static_range と affine_range という 2 つのループ構文が DMA のソフトウェアパイプライン化に対して持つ、まったく違う契約です。

一言でいうと
4 つの書き換えが同じ数字を返したなら、動かしている変数はボトルネックではありません。そして疑わしい仕事があるとき、それを最適化するより先に、丸ごと消してみるほうが安く答えが出ます。行列積を消すのに 10 分かかり、それが 3 つの書き換えでも分からなかったことを決めました。
最終的な原因は、static_range で書かれたループは命令が並んでいるだけで、コンパイラに DMA を先読みしてよいという許可を与えていなかったことでした。

136% という数字はどこから来たか

帯域はスロープで測ります。1 点だけの数字は固定費に汚染されています

対象は decode フェーズで動く MoE カーネルです。トークン 1 個が、256 expert のうち router が選んだ top_k 8 個に配られます。1 expert・1 層・1 rank あたりの重みは gate [2048,128] と up [2048,128] と down [128,2048] を bf16 で持ち、合計 1.573 MB です。行列積 1 回あたりの演算強度は約 0.5 MAC/byte しかありません。この形はほぼ全区間が重みの読み込みで決まり、計算では待たされないはずのワークロードです。つまり帯域が出ればそのまま実行時間が決まる形をしています。

帯域は 1 点だけの計測では信用できません。1 回の呼び出しには固定費が乗るので、サイズを複数点振って、バイト数と時間の傾きから帯域を取り、固定費は切片に落とします。今回のすべての数値はこの方法で nki.benchmark の p50 をデバイス側で計測したものです。切片はどの構成でも正の値になりました。切片が負に出た計測は定常状態に達していないので下限として扱うべきですが、今回はその心配がありません。

元の実装 (static_range の完全アンロール、反復をまたいでアキュムレータを持ち越す形) の帯域は 51.4 GB/s でした。この回の終わりに測る、書き換えたあとのカーネルは 140.2 GB/s です。51.4 を 140.2 で割ると 36.7%、つまりこの回の見出しの数字になります。まず先にこの終着点を宣言してから、そこに着くまでに殺した仮説を順番に見ていきます。

2仮説 1 ― 行列積が細すぎる

Tensor Engine を持て余しているという、いちばん自然な疑い

元の実装は 1 expert につき 16 (gate) + 16 (up) + 4 (down) = 36 回の行列積を issue していました。gate と up はどちらも同じ [2048,128] の重みを、同じトークン 1 個に対して別々に掛けています。1 回ごとの行列積は幅が狭く、Tensor Engine の 128×128 systolic array を持て余しているという疑いは自然です。命令数が多いこと自体も、命令 1 個あたりに乗る固定費を積み重ねます。

gate と up は同じ入力トークンに対する別々の射影なので、重みを並べて 1 つの連続した [128,256] タイルにし、1 回の行列積で両方を出す形に融合しました。これで行列積の総数は 16 (融合した gate+up) + 4 (down) = 20 まで減ります。

版行列積の数帯域のスロープ呼び出し 1 回の固定費
融合前36基準106 µs
gate+up 融合後20約 1% しか動かない93 µs

スロープはほぼ動きませんでした。これは行列積の細さが主犯ではないという証拠です。ただし融合そのものは捨てませんでした。演算内容は変わらないのに命令数が減り、固定費が 106 µs から 93 µs まで下がったからです。細さの仮説を殺したことと、融合を残す判断は別の話です。

融合の途中で、レイアウトについて 1 つ誤解していたことにも気づきました。ベンダー提供の融合レイアウト [E, hidden, 2, I] は、gate と up のどちらか片方だけを select すると、その 1 回の read が stride 付きになります。ところが gate と up を両方いっしょに読むなら、この軸はただの連続領域です。レイアウトそのものが悪かったのではなく、その半分だけを使う書き方が悪かったということです。

3仮説 2 ― 動く側がトークン 1 個しかない

今度は理論そのものが誤っていました

Tensor Engine は片方の行列を格子に固定 (stationary) し、もう片方を流し込み (moving) ます。decode の 1 ステップはトークン 1 個なので、moving 側の行が 1 行しかありません。128×128 の格子に対して 1/128 しか使っていないという疑いです。stationary 側と moving 側をどちらにするかは選べるので、入れ替えて測りました。

結果は 4% 遅くなりました。速くもならず、期待した通りにも動きません。2 人の独立したレビュアーが、それぞれ別に同じ指摘をしました。どちらの割り当てでも、次元の 1 つは 1 のままです。トークン数が 1 という事実自体は入れ替えでは変わらないので、格子のどちらの軸にその「1」を置いても、動いていない次元があることに変わりはありません。理論の立て方自体が、入れ替えで何かが変わるという前提を置いていた点で誤っていました。

4% の悪化は「反証」以上の情報を持っています。もし理論が正しく PE 利用率が主犯なら、入れ替えは中立のはずで、悪化する理由がありません。悪化したこと自体が、この軸の入れ替えが性能に無関係な操作であることを示しています。

4仮説 3 ― indirect な expert 添字が動的な DMA 記述子を要求する

レビュアーの最有力候補が、別の実測で先に反証されていました

どの expert の重みを読むかはトークンごとに違うので、読み込みはindirect index によるギャザーです。静的な添字と違い、実行時に決まる添字は DMA の記述子をそのつど生成するコストを乗せるはずだ、というのがレビュアーの最有力候補でした。もっともらしい理論です。

ところが同じプロジェクトの別のマイクロベンチマークが、同じ indirect index の仕組みを使って 155 GB/s に達しているという実測を既に持っていました。今回のカーネルが詰まっている 51.4 GB/s よりずっと高い値です。indirect index という機構そのものが 51.4 GB/s しか出せない理由にはなり得ません。仮説 3 も殺れました。

3 つの仮説がすべて死にました。行列積を融合してもスロープはほぼ動かず、stationary と moving を入れ替えても改善はなく、indirect index という機構自体は別の実測で高い帯域を出せることが分かっています。4 つの構造的な書き換えが同じ数字を返したなら、動かしている変数はボトルネックではありません。ここで疑いの向きを変えました。

5決定的な実験 ― 行列積を消したら遅くなった

最適化する前に、消してみる

それまでの 3 つの仮説は、いずれも計算側の何かを直すという方向でした。だから最後に、計算そのものを丸ごと消してみました。static_range の同じループから行列積の呼び出しだけを取り除き、重みの読み込みだけを残します。演算が無いのだから、計算が律速だったならこの版は速くなるはずです。

版帯域
行列積あり (元の実装)51.4 GB/s
行列積を丸ごと削除47.0 GB/s

速くならず、むしろ遅くなりました。これが決定的でした。計算を消しても数字が動かない、あるいは悪化するということは、計算が上限を作っていたのではないということです。そして遅くなった側の実装が指しているのは、読み込みがパイプライン化されていないという事実です。計算をしている間に次の読み込みが進んでいたのではなく、読み込み自体がそもそも重なっていなかったので、計算を抜いても待ち時間は同じ場所に居座り続けます。むしろ命令列の形が変わったことで、スケジューラの並べ方がわずかに不利になった、というのが 47.0 という数字の説明です。

ここが仕事の消し方の価値です。3 つの構造的な書き換え (融合・入れ替え・indirect index の実測比較) では、それぞれ数字を 1% か 4% 動かすだけで、原因の在り処までは指してくれませんでした。計算を消すという 1 回の操作だけが「計算は主犯ではない」を直接示し、同時に「読み込み側を見ろ」という次の一手まで示しました。疑わしい仕事を最適化する前に消してみるのは、10 分で済み、3 つの書き換えより安く答えが出ます。

6static_range と affine_range ― パイプライン化を許可するのはどちらか

命令が並んでいることと、並べてよいと宣言することは別です

static_range はループを完全にアンロールします。命令はすべて静的に列に並び、コンパイラの list scheduler がその列を見ることができます。ただし「見える」ことと「入れ替えて重ねてよいと保証されている」ことは別です。アンロールされた命令列は、たまたま重ねられる部分があれば重なるという機会的な最適化の対象にしかなりません。反復という構造そのものは、アンロールした瞬間に消えているからです。

affine_range はこれと逆の情報をコンパイラに渡します。「この反復の間には依存が無い」という明示的な宣言です。この宣言があるからこそ、コンパイラは反復 i の計算をしている裏で反復 i+1 の読み込みを先に始めてよいと判断できます。これは機会ではなく許可です。

同じ量の読み込みと計算でも、コンパイラに重ねる許可があるかどうかで総時間が変わる

この許可の効果を単体で測るマイクロベンチマークを書きました。affine_range で書いたループの各反復が、スクラッチ行の互いに重ならないスライスに書き込むだけで、反復をまたぐ状態を一切持たない形です。197.0 GB/s に達しました。static_range + アキュムレータの 51.4 GB/s から見て 3.8 倍です。

この形を、実際の MoE カーネルに移植しました。ここで問題になるのが、元の実装がやっていた縮約です。gate や up の行列積は、隠れ次元 2048 を 128 幅のタイルに割って複数回に分け、その部分積を1 つのアキュムレータに足し込みながら進めます。このアキュムレータは反復 i の出力が反復 i+1 の入力になるという、まさに反復間の依存です。affine_range はその依存が無いと宣言する構文なので、アキュムレータを持ったまま affine_range に置き換えるのは、宣言を嘘にすることになります。コンパイラはその嘘を前提に並べ替えてよい立場にあるので、結果は遅いだけでは済まず、間違った答えになり得ます。

正しい移植は、宣言を本当にすることでした。縮約の各ステップに、スクラッチ行の中の自分専用の disjoint なスライスを持たせ、どの反復も他の反復のスライスを読みも書きもしないようにします。そして縮約の総和は、その読み込みが暮らしているループを抜けたあとにまとめて取ります。これで各反復は本当に独立になり、affine_range の宣言が事実と一致します。

この形に書き換えた実カーネルの帯域は 140.2 GB/s でした。static_range + アキュムレータの 51.4 GB/s から 2.7 倍、マイクロベンチマークが示した 197.0 GB/s の天井には届きませんが、これは実カーネルが実際の行列積と indirect index による読み込みを両方抱えているためで、マイクロベンチマークはそのどちらも持っていません。天井と実測の差は、まだ削れる何かが残っていることを示す数字であって、この回の主張を弱めるものではありません。

7往復のコストを払った 2 つの NKI の癖

正しい形に着地するまでに、遠回りをさせられた場所です

両方のレビュアーが、部分積の縮約は psum += nl.matmul(...) という素直な形で書けばよいと勧めました。この module tree では書けません。 += はタイルの上では定義されておらず、nl.add は PSUM 同士の 2 オペランドを拒否します。片方ずつなら通る操作が、組み合わせると通らないという形の落とし穴で、それぞれ実機かシミュレータで 1 往復かけて確認するまで気づけませんでした。だからこそ縮約は、ループの外でスクラッチ行を足し合わせるという、いま説明した形に落ち着いています。素直な PSUM 内蓄積が言語として書けないことが、s6 の書き換えの形を決めた直接の理由です。

NKI のシミュレータは indirect indexing を再現しません。スロット 0、2、3 を指す添字を渡しても、返ってくるのは常にスロット 0 の値です。スロットごとに異なるデータを仕込んだテストがシミュレータ上で通っても、それはシミュレータの挙動を測っただけで、カーネルの正しさは何も確認していません。indirect index を使うギャザーの正しさは、実機で確定させるしかありません。今回の MoE カーネルはまさに expert 添字による indirect index を使うので、この 1 点は特に注意して確認しました。

8この回の要点

計算を消すと遅くなり (赤)、独立を宣言できる形に書き換えると 2.7 倍になる (緑)

1. 帯域はスロープで測る。複数サイズを振り、傾きから帯域を、切片から固定費を出す。切片が負なら定常状態に届いていない下限として扱う。

2. もっともらしい仮説は 1 つずつ、変数を 1 つだけ変えて殺す。行列積の融合、stationary/moving の入れ替え、indirect index の実測比較。どれも単独で反証できる形にする。

3. 構造を変えても数字が動かないなら、その変数はボトルネックではない。4 つの書き換えが同じ数字を返したことが、疑いの方向を変える根拠になる。

4. 疑わしい仕事は最適化する前に消す。行列積を丸ごと削除する実験が 10 分で「計算は主犯ではない」を確定させた。

5. affine_range の「反復間に依存が無い」は、宣言するだけでなく本当にする。アキュムレータを disjoint なスライスと事後の総和に分解する。

6. NKI 独自の演算子の制約とシミュレータの限界は、SDK に対して先に確認する。 += の未定義、nl.add の PSUM 制限、indirect indexing を再現しないシミュレータの 3 つは、どれも往復して初めて分かった。

この回だけ持ち帰るなら。性能の帰属で詰まったとき、書き換えを 1 つ増やす前にその仕事を消してみてください。数字が動かなければ、それは犯人ではないという証拠で、しかも最も安く手に入る証拠です。そして NKI のループでは、命令が並んでいることとコンパイラに重ねる許可を与えることは別の話です。affine_range を選ぶなら、反復間の独立という宣言を、コードの形として本当にしてください。

出典と確認方法: ループ形の比較と帯域の数値は、筆者が一般提供されている Trainium2 インスタンス上で、公開されている Neuron SDK、公開されている NKI API、公開モデルを用いて計測したものです。計時は nki.benchmark によるデバイス側計測で、帯域は複数サイズの傾きから、固定費は切片から取っています。本稿で述べた NKI API の挙動 (+= がタイルに定義されていないこと、nl.add が PSUM 同士の 2 オペランドを拒否すること、シミュレータが indirect indexing を再現しないこと) は、公開 SDK に対して再現できます。static_range と affine_range がそれぞれパイプライン化に対して持つ契約は、本稿の実測に用いた SDK バージョンの挙動です。バージョンによって別名に統一されるなど挙動が変わり得るため、この点は特に手元の SDK ドキュメントで確認してください。制限公開の環境で得た数値は本稿には一切含めていません。

確認時点: 本稿の記述は 2026-09-06 時点のものです。バージョンが上がれば名前も挙動も変わりうるので、正はソースと配布物です。

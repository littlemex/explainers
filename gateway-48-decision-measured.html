Decision を NVIDIA で動かし、元のモデルとの差を同じ問題で測る
短い文脈では改善が見えず、長い文脈では確率が良くなった

この章の結論。Decision の Lux-9B は、元になった Qwen3.5-9B を学習させずに Prismyra で読んだ場合と比べて、 短い文脈の読解 (RACE、579 問) では正解率の改善が見えず (−1.2 ポイント、区間 [−3.2, +0.9]、事前の線では未決着)、確率の質はむしろ有意に悪くなりました。 ところが同じ問題を約 9,600 トークンの文章に埋めると向きが逆になり、Lux の方が正解率の落ちが小さく (8.9 対 13.4 ポイント)、確率の質は有意に良くなりました。

つまり Lux の方式 (追加学習・採点ヘッド・入力の書式をまとめたもの) で見えた得は「短い文章を読む力」ではなく、長い文章の中でも答えの確率が崩れにくいことでした。どの部分が効いたのかは、この比較では分けられません。 これは Prismyra が自分で見つけていた弱点 (長い文脈で生成に負ける) のちょうど裏返しで、Prismyra にとって試す価値のある候補を示しています。

1. 何を、何と比べたか

知りたいのは「Decision の方式 (追加学習・採点ヘッド・入力形式) は、元のモデルに比べて何を上げたのか」です。第 47 章で見たとおり、論文の点数は開発中に何度も見たベンチマークで、重みも後から決めたものです。 そこで開発者が選択に使ったと書いていない問題 (RACE) で、学習する前の同じモデルと比べることにしました。

  • Lux-9B (Decision 1.0)。学習済みの採点ヘッドで答える。同梱の温度 2.005 を適用。
  • 未調整の Qwen3.5-9B。Lux の初期化元 (decision_config.json の base_model)。Prismyra で、答えの文字 (A〜D、no/yes) の確率を最後の位置から読む。学習はゼロ。
  • 位置を知るための参考として、Nox-4B・Eos-0.8B と、Prismyra の標準モデル Qwen3.6-35B-A3B-FP8。

問題は Prismyra の評価コード (evals/tasks.py) で作り、JSON に固めて全員に同じ文字列を渡しました。 RACE は Prismyra の docs/ACCURACY.md と同じ seed 11 の 150 記事 579 問なので、Prismyra の公表値とも突き合わせられます。 Decision 側には、質問文を instructions、選択肢の本文を criteria の説明として、Decision 本来の形で渡しました。

[注意] この比較が言えることの範囲。 2 つの方式は、学習の有無だけでなく、答えを読むヘッド、プロンプトの書式、文脈の再利用の有無も違います。 だから差は「Decision の学習 + ヘッド + 入力形式」の合計で、学習だけの効果とは呼べません (レビューの 3 者全員が指摘)。 どの測定も 1 回ずつです。

2. NVIDIA への移植は本物と同じか

同梱コードは AMD の gfx942 以外で止まるので (第 47 章 §4)、カーネル設定を固定する部分だけを外し、 モデル本体 (code/decision_model.py) と温度はリポジトリの物をそのまま読み込む薄いローダーを書きました。 それで、リポジトリに同梱されている model-card-example.json の 5 問 (AMD 上で記録された実際の応答) を L40S で再現しました。

分かったことは 2 つです。L40S の上では、計算に使う数の精度 (bf16 は 16 ビット、fp32 は 32 ビット) を変えても確率は最大 0.0005 しか動かず、GDN の計算を PyTorch の素の実装と FLA の Triton カーネルで入れ替えても 1e-5 以内で一致しました。 つまり L40S の上では、計算の区切り方を変えない限り、精度を変えても安定しています。一方で AMD の参照とは確率が最大 0.020 違い、しかも 5 問とも L40S の方が少し自信が低い向きでした。 精度の違いだけではこの差は説明できませんが、AMD と L40S ではカーネルの設定や足し算の順序も違うので、原因は特定できていません (5 問とも同じ向きというのも、5 問だけでは弱い手がかりです)。答え (どれを選ぶか) は 5/5 一致していますが、確率の値を使う結論 (Brier・NLL・ECE) は、L40S に移植した版についての結果として読んでください。 事前に決めたとおり、参照が 5 問しかないので忠実度は「検証不能」と宣言し、以下はすべて「L40S に移植した Lux」の結果として書きます。

3. 短い文脈 ― 正解率の改善は見えず、確率は悪くなった

表の指標は 4 つです。正解率は高いほど良く、残りの 3 つはどれも小さいほど良い確率の質の物差しです。 Brier は、各選択肢に付けた確率と「正解なら 1、それ以外は 0」との差を 2 乗して選択肢全体で足し、問題ごとに平均したもの、NLL は「正解に付けた確率の対数」の符号を反転した平均で、自信満々に外すと大きく罰せられます。 ECE は「0.9 と言った問のうち実際に 9 割当たっているか」のずれの平均です。

主比較 (Lux − 未調整) は、正解率 −1.21 ポイント、95% 区間 [−3.21, +0.85] でした。 事前登録の線では、区間が ±2 の内側に収まらず、上限が 0 を越えているので「未決着」です。 少なくとも「Lux の方式で読解が伸びた」とは言えず、点推定はむしろ下を向いています。 確率の質は、Brier の差が +0.0242 [+0.0059, +0.0432]、NLL の差が +0.0509 [+0.0157, +0.0887] で、どちらも区間が 0 を含まず、Lux の方が悪い結果でした。 第 47 章の図 3 (論文の読解パネルでの伸びは +0.32 だけ) とも矛盾しません。どちらの測り方でも、読解の大きな改善は見えていません。

BoolQ は Decision の Kai の学習源で、読解パネルにも入っています。ここでは 89.00% 対 88.75% (差 +0.25 [−1.75, +2.25]) で、区間の上限が +2 を越えるので事前の線では未決着です (点推定はほぼ 0)。 Lux の学習データに BoolQ が入っているかは確認できていないので、ここから「覚えた・覚えていない」は言えません。 Nox-4B は同じ 9B の未調整モデルと比べて −10.19 [−13.24, −7.18] 下でした (規模の違いを含む比較です)。

参考の 35B は RACE 95.16%、BoolQ 89.50% で、Prismyra の公表値 (94.8%、89.5%) とほぼ一致しました。Lux はこの 35B に対して RACE で −2.07 [−3.96, −0.18] と有意に下です。

4. 長い文脈 ― ここで初めて Lux の方式が上回った

Prismyra の tasks.bury() で、RACE の 40 記事 157 問の本文を、同じデータセットの他の記事で囲んで約 10,000 トークン (Qwen3.5 のトークナイザ) まで伸ばしました。 正解の記事の位置は seed で決めた場所で、全システムで同じ文字列です。Lux が実際に読んだ 1 問あたりの長さは中央値 9,656 トークンでした。 比べる相手は、同じ 40 記事の短い版 (RACE の 579 問のうち最初の 40 記事) です。

長い文脈では正解率の落ち幅が Lux 8.9 ポイント、未調整 13.4 ポイントで、事前登録した「Lux の落ちが未調整の落ち +2 ポイント以内なら長文脈で頑健」を満たしました。 確率の質は Brier −0.0737 [−0.1291, −0.0208]、NLL −0.1539 [−0.2586, −0.0567] で、区間が 0 を含まずに Lux が良い結果です。 35B と比べても Brier −0.0854 [−0.1463, −0.0272] で、Lux が良い側にいます。

なぜそうなるのかは測っていませんが、仕組みの上での違いははっきりしています。 Prismyra の読み出しは、行の最後の 1 位置で「A」「B」などの文字の確率を読みます。 Lux のヘッドは、各選択肢の本文の最後の位置と行の最後の位置を両方読み、その組み合わせで採点します (第 47 章の図 2)。 選択肢の本文そのものに乗った表現を読むので、答えを 1 文字に写す段階で長い文脈に邪魔されにくい、という説明が立ちます。これは推測です。

選択肢を逆順に並べ直して、意味の上での答えが変わった問題の割合です。Decision の論文は 36 組だけで Lux 8.33% と報告していましたが、579 問では 4.7% でした。 長い文脈では文字の確率を読む 2 つが 15〜21% まで崩れ、Lux は 8.3% にとどまります (157 問・1 通りの並べ替えで、区間は計算していません)。ここも第 4 節と同じ向きです。 並べ替えは 1 通りだけなので、これは「この 1 つの並べ替えへの感度」であって、順序に対して不変かどうかは言えません。

6. Prismyra に返ってくること

この実験は Prismyra の弱点を外から照らしました。Prismyra の docs/ACCURACY.md は「長い文脈で、読み出しが生成に −5.0 ポイント負ける」ことを自分で見つけていて、原因を「取り出し方の違い」としていました。 今回、学習済みのヘッドを持つ方式が長い文脈で崩れにくいことが、別チームの重みで観測されました (ヘッドの効果だけを分けたわけではありません)。Prismyra の ACCURACY.md にも学習済みヘッドは「次の候補」として書かれています。 第 49 章で、Lux のヘッドを Prismyra と同じ「1 回だけ読む」仕組みに載せます。

あわせて、Prismyra を動かす途中で見つけた 2 つを記録します。

  • ローカルのディレクトリを渡すと起動できない。Prismyra("./models/Qwen3.5-9B") のようにローカルのディレクトリを渡すと、本体の読み込みには成功した後、出力の行列を取りに行く load_unembedding (prismyra/readout.py L102) が hf_hub_download にパスを渡して HFValidationError で落ちます。Hub のリポジトリ名を渡せば動きます。
  • L40S では既定の group=32 で 1,215 トークンの文脈を断る。35B の重みを載せた後の空きは 9.8 GiB で、受け付けの見積もりが 10.8 GiB (保持 1.3 + 回答 9.5) を求めるためです。断り方は正しく、文面に「group を小さく」と書いてあるので、group 8 で回しました。ACCURACY.md は L40S で測ったと書いているので、その後に受け付けの見積もりが厳しくなったことで、同じ機械での再現に設定が要るようになっています。

まだ言えないこと

  • どの数字も 1 回の実行です。L40S の bf16 のゆれ (最大 0.040〜0.059、第 49 章) は正解率を動かすほどではありませんでしたが、繰り返しの幅は測っていません。
  • 長い文脈で Lux が良い理由が「ヘッドの読み方」なのか「学習データ」なのかは、この比較では分けられません。未調整のモデルに Lux と同じヘッドの形だけを学習させる実験が要ります。
  • Kai・Lex・Sol は動かしていません (Kai と Lex は 1,024 トークンの上限で RACE の埋没に入らず、Sol は順序感度 38.89% が既に報告されているため優先度を下げた)。
  • Decision が得意なはずの「規則の判定」「組み合わせ」は、問題が配られていないので同じ条件で測れていません。今回の結論は読解の問題に限ります。

環境: 東京リージョンの EKS、g6e.12xlarge の L40S 1 枚、vllm/vllm-openai:v0.27.1 (torch 2.13.0+cu130)、Decision 側は transformers 5.17.0 と flash-linear-attention 0.5.2。
問題: Prismyra の evals/tasks.py (RACE-middle validation seed 11、BoolQ validation seed 11、bury(10000))。区間は記事単位の対応付きブートストラップ 10,000 回の 2.5〜97.5 パーセンタイル。
判定の線は結果を見る前に固定したもの (主比較: 区間下限 > 0 かつ点推定 ≥ +2 で優位、区間が ±2 の内側で同等、上限 < 0 で劣位、それ以外は未決着)。

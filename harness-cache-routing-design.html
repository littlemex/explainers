ハーネスとキャッシュまで含めた振り分けと、0.8B の LLM 蒸留
Fable 5.2 の 5 名レビューを 1 つの設計にまとめる

結論から。小さな言語モデル (0.8B は部品の数が約 8 億という意味。以下「生徒」) に、大きなモデル (「先生」) のまねを学ばせる (蒸留) とき、ハーネス (モデルの周りで答えを左右する設定の全部) とキャッシュ (前の計算の使い回し) をどう扱うかを決めました。(1) perigraph (何が動いたかを記録する、筆者の仕様) を、ハーネスとチューニングしたモデルの両方について「何が答えたか」を見分ける窓口にしました。重みのファイル、精度、動いているパッケージ、答えの取り出し方から識別子を作り、tierbook はそれを文字列として比べるだけです。切り替えはルーターが受け持ちます。(2)「何でもできる生徒」には測った根拠がまだ無く、根拠があるのは、答えの形が決まった仕事ごとに生徒を作り、迷ったら先生に回す形だけです。(3) 大きなモデルが仕事を分けて生徒に渡す形 (Leader) は、過去の実験で一度、事前に決めた合格条件 (関門) を通りませんでした。

この文書でやったこと。perigraph の仕様、tierbook の現状、これまでの実験記録、過去のプロジェクトの知見を確かめてから同じ資料として渡し、Fable 5.2 に 5 つの観点 (測定と統計、システムと配信、学習、仕事の形、懐疑的な読み手) でレビューさせました。5 名の立場がそろった点と分かれた点を並べ、1 つの設計と、関門つきの段階的な実験計画にまとめています。

モデルは 4 つの部分で表します。部分の名前は閉じた一覧で、送り手が勝手に増やせません。

チューニングの来歴は、学習した側が書く別の文書にする

チューニングしたモデルがどう作られたか (来歴、lineage) は、記録の中には入れません。配信する側は重みを持っていても、作られた経緯は持っていないからです。来歴は、学習した側が 1 つの成果物の識別子について書く文書にしました。項目は、対象の成果物 (subject)、親の成果物 (parent、元のモデルなら none)、作り方 (pretrained、sft、distillation、rl、merge、reserialisation の 6 つ)、使った問題の集まり (学習に使った trained_on と、選ぶのに見ただけの consulted)、何から学んだか (signal。蒸留と強化学習では必須で、先生の成果物の識別子か、採点器の指紋か、名前)、学習の仕組み (trainer) です。

来歴は誰にも確かめられないので、判定を断る理由にはなっても、許す理由にはなりません。合格の判定に使う問題が親までのどこかの trained_on に入っていれば、その判定を断ります。対象が観測した成果物と違う来歴は無いものとして読み、親の来歴が欠けていれば「分からない」であって「きれい」ではありません。「この問題は除いた」という項目は置いていません。その項目は、判定を許す方向にしか働かないからです。

受け手が断ること (4 つ足した)

  • loaded_by_us でない部分から作ったモデルの識別子や成果物の識別子。
  • 1 つの担当としてまとめた記録に、モデルの識別子が 2 つ以上あるか、識別子のある記録と無い記録が混ざっているときの判定。R12 と R13 の 93.4%、R14 の 97/100 がこれにあたります。
  • あるモデルの識別子に結び付けた主張を、その識別子を持たない記録に当てはめること。R5 の合格を R6 に当てはめた形です。
  • 違う記録係、または違う版の記録係が作ったモデルの識別子どうしの比較。比べたいときは成果物の識別子を使います。

反対に、モデルの識別子が無い記録を断ってはいけない、という決まりも足しました。Bedrock のように他社の API の向こうにあるモデルは重みが見えないので、識別子を作れません。それでも担当として判定はできます。ただし、その判定は重みのバイトには結び付いていない、と受け手が書きます。

3. キャッシュがあると、1 件の費用は「その前に何をしたか」で決まる

キャッシュとは、前のリクエストと同じ先頭部分 (prefix) の計算結果を取っておき、次のリクエストで使い回す仕組みです。使い回せた分は、API なら安い料金になり、自前の GPU なら計算の時間が減ります。同じ問いでも、直前にどこへ何を送ったかで値段が変わるので、「この担当は 1 件いくら」という固定の値段で振り分けを比べると、ずれます。

perigraph の仕様は、同じ中身でも、1 通の長いメッセージとして送るとキャッシュ率 0%、会話として少しずつ伸ばすと 99.9% だった、と SPEC.md 5 節に書いています。そのため、やり取りの回数が違う 2 つの担当を「同じ仕事の 2 つの値段」として比べることを禁じています。料金の内訳も 4 つに分けています。新しく読んだ入力、キャッシュから読んだ入力、キャッシュに書いた入力、生成した出力です [引用 perigraph spec/vocabularies.json の billed_legs]。

自前の GPU の箱では、事情が違います。料金の項目としてのキャッシュはなく、効くのは席と時間です。過去のプロジェクトでは、飽和した負荷で長い入力が 1 件同居すると、短いリクエストを 1 秒以内に返せる件数が 1 時間 225,730 件から 102,022 件に落ちました。負荷が容量の 10% なら、長い入力を分けて処理する設定で落ちませんでした。測ったのは長い入力の同居で、キャッシュそのものではありません。API のキャッシュは料金表の話、自前の箱のキャッシュは席の話なので、5 名のうち B は、この 2 つを 1 つの抽象にまとめないよう勧めています。

やり方中身気を付けること
強化学習の報酬にする生徒が自分で答えた問題は、その答えの正誤を報酬にする。生徒が先生に回した問題は、先生の答えの正誤から、先生に払う費用の分を引いたものを報酬にする。生徒は、先生が間違える問題で正しく答えることと、自分が間違えそうな問題を先生に回すことの両方で得をする費用をどれだけ重く見るかの係数を学習側が決めることになる。tierbook はこの係数を持たず、できた組み合わせをいつもどおり判定するだけ

学習の手順の案 (5 名の提案をまとめたもの)

  1. 先生の答えを、配信と同じハーネスで作る。システムプロンプト、ツールの定義、答えの取り出し方、生成の設定を、配信するときのものと 1 バイトも変えません。チャットの型の中身を整えて書き直すこともしない、という C の案です。
  2. 採点器を通った答えだけで学習させる。正解ラベルで学習した生徒が先生に並んだので、生成の仕事でも、プログラムで確かめられる採点器 (JSON の形、抽出した値の完全一致など) を通った答えだけを目標にします。これが「正解ラベル」の代わりになる、という C と D の案です。
  3. キャッシュは、学習データの並べ方の決まりとして扱う。変わらない部分 (指示とツールの定義) を前に、毎回変わる中身を後ろに置き、指示の言い換えでデータを増やすことはしません。その代わり、ハーネスを変えるたびに学習し直して、判定し直すことになります (C の案)。
  4. 生徒自身の答えで学ぶ回 (on-policy) は、1 回だけ試す。生徒に答えさせ、採点器で報酬を付け、語彙が同じなら先生の確率の分布にも寄せます。差が 0 をまたげば打ち切ります (C と E の案の折衷)。

判定で気を付けること (A の指摘)。採点役にモデルを使うと、証明書は「その採点役が良しとした割合」になり、正しさではなくなります。間違った答えを良しとする割合を f、正しい答えを駄目とする割合を r とすると、本当の正解率は (測った受理率 - f) / (1 - r - f) です。f は間違った答えの上でしか見積もれず、300 件の監査で間違いが 30 件、そのうち良しとされたのが 3 件なら、f の 95% の上限はおよそ 0.26 になる、と A は計算しています。先生と同じ系統のモデルを採点役にすると、先生に似ているかを測ることになります。そのため、最初の実験は完全一致で採点できる仕事にします。

5. 型の決まった仕事が先で、Leader が分けて渡す形はまだ立っていない

Leader とは、大きなモデルが仕事を小さな部分に分け、簡単な部分を小さなモデルに渡す役です。5 名の答えは「まず型の決まった仕事で生徒と組み合わせを作り、Leader は関門を通ってから」でそろいました。

根拠は 2 つあります。1 つ目は、過去のプロジェクトで Leader の前提が立たなかったことです。計画を足した効き +15.0 ポイントのうち 59% は、推論をまったくしなくても得られました。計画の文に答えが漏れていたからです。残りの差は有意でなく (p = 0.1755)、分ける役の費用は答えの 3.93 倍でした。MMLU-Pro という 1 つのベンチマークで測った結果です。2 つ目は先行研究で、振り分けで改善できた 29 問のうち 21 問は、仕事の種類ごとに 1 つのモデルを決め打ちするだけで取れた、と arXiv:2608.23023 が報告しています。

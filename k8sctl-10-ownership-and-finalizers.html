所有と後片付け

ownerReferences が自動で消し、finalizer が消える前に足止めする

← カスタムコントローラー自作 シリーズ目次へ

第 09 回で、Reconcile は名前だけを受け取り今の状態を読み直す関数だと見た。この回は、コントローラーが作った子のオブジェクトをどう親に結びつけ(ownerReferences)、消すときにどう後片付けの時間を確保するか(finalizer)を、実測した事実を交えて見る。

この章の結論: ownerReferences を付けておけば、親を消すと子も自動で消える(ガベージコレクション)。ただし namespace に属する親はクラスタ全体のオブジェクトを所有できない(実測で確認)。すぐに消えては困る後片付けがあるときは finalizer(ファイナライザ: 後片付けが済むまで削除を待たせる印)を付け、後片付けが終わったら自分でその印を外す。外し忘れるとオブジェクトは deletionTimestamp が付いたまま永遠に残り続ける。

1. ownerReferences と GC の基本

コントローラーが Widget のために ConfigMap を作ったとき、「この ConfigMap は Widget の子だ」と API サーバーに教えておくと、Widget を消すだけで子も自動的に消える。この仕組みを使うには、作った子の metadata.ownerReferences に親の情報(apiVersion, kind, name, uid)を入れる。手で書くのではなく controllerutil.SetControllerReference(owner, controlled, scheme, opts...)(controller-runtime v0.24.1 のソースで確認)を使うのが普通で、これが owner の GroupVersionKind(GVK、第 02 回)を正しく埋め、controller: true を立てる。

controller: true は「このオブジェクトの主要な所有者はこれだ」という印で、1 つの子につき controller: true の親は 1 つだけに制限されている。これは単なる推奨ではなく、API サーバー自身が検証で強制する(確認済み: k8s.io/apimachinery の pkg/api/validation/objectmeta.go の ValidateOwnerReferences が、2 つ目の controller: true を見つけると「Only one reference can have Controller set to true」で拒否する)。詳しい設計意図は公式ドキュメントも参照。もう 1 つのフィールド blockOwnerDeletion は、後述する foreground 削除の時だけ効く「この子が消えるまで親を消させない」という印。

図: 親を消すと GC が ownerReferences をたどって子も消す。

2. 消し方の 3 つ: background / foreground / orphan

親を削除するとき、どの順番で子を消すかは propagationPolicy で選ぶ(公式ドキュメント)。既定は background。

方式親の消え方子の消え方
Background(既定)すぐに消えるガベージコレクタが裏で後から掃除する
ForegrounddeletionTimestamp と foregroundDeletion finalizer が付き、blockOwnerDeletion:true の子が全部消えるまで残る(それ以外の子は親より先に消えるとは限らない)blockOwnerDeletion:true の子は親より先に消え、完了をブロックする
OrphanGC が子の ownerReferences を外し終えるまで残り、その後消える消えずに残る(ownerReferences だけ失われ孤立する)

図: 子を先に消すか後に消すかが Foreground と Background の違い。

3. namespace の壁

ownerReferences には 1 つ、見落としやすい制約がある。namespace に属する(namespaced な)オブジェクトは、クラスタ全体に属する(cluster-scoped な)オブジェクトを所有できない。EKS 1.35 のテスト用クラスタで実測した: namespace 付きの Widget d を親にして、同じ namespace の ConfigMap と、クラスタ全体のオブジェクトである ClusterRole の両方を子として作り、Widget d を削除した。ConfigMap は GC で消えたが、ClusterRole は残った。ClusterRole 上のイベントには次の警告が出ていた。

Warning OwnerRefInvalidNamespace clusterrole/crd-lab-d-child
ownerRef [lab.crd-series.example/v1/Widget, namespace: , name: d, uid: ...]
does not exist in namespace ""

namespace に属する親から PersistentVolume や ClusterRole のようなクラスタ全体のオブジェクトを所有させようとしても、GC はそれを「存在しない参照」として無視し、自動削除の対象にしない。クラスタ全体のオブジェクトを後片付けしたいなら、ownerReferences に頼らず、次のセクションの finalizer で自分のコードから明示的に消す必要がある。今回の実測はこの ownerReferences を直接セットして再現したもので、controllerutil.SetControllerReference(1 節で見たヘルパー)を使っていれば、この組み合わせはクラスタに書き込む前にクライアント側でエラーになっていた。制約はもう 1 つあり、どちらも namespace に属する場合でも、親と子の namespace が違うと(両方 namespaced でも)所有は成立しない(これも SetControllerReference がクライアント側で拒む)。クラスタ全体を所有できないのと、namespace をまたげないのは別々の制約で、どちらも同じ理由(所有は同じ namespace の中でしか意味を持たない)から来ている。

図: namespace の中の親はクラスタ全体の子を所有できない(EKS 1.35 のテスト用クラスタで実測)。

4. finalizer: 削除を待たせる仕組み

ConfigMap のような Kubernetes 内部のオブジェクトの後片付けは GC に任せられるが、「外部のクラウドリソースを先に消してから、このオブジェクトを消させたい」という場合は GC では届かない。そこで使うのが finalizer(ファイナライザ: 後片付けが済むまで削除を待たせる印。deletionTimestamp が「削除してほしいと頼まれた印」なのに対し、finalizer は「まだ終わっていない後片付けがある」という印で、両方そろって初めて実際に消える)。metadata.finalizers に文字列(例: lab.crd-series.example/cleanup)を入れておくと、削除リクエストが来ても API サーバーは即座には消さない。finalizer は削除が始まってから慌てて付けるのではなく、オブジェクトを初めて見た Reconcile(後片付けが必要になる前)で付けておく。削除要求が来てから付けようとしても、次のセクションで見るとおり削除予約中は新しい finalizer を追加できない。

EKS 1.35 のテスト用クラスタで実測した流れ: finalizer を付けた Widget を kubectl delete すると、オブジェクトは消えずに deletionTimestamp が付いた状態で残った。削除中でも spec の変更はできたが、削除中に新しい finalizer を追加しようとすると拒否された。

metadata.finalizers: Forbidden: no new finalizers
can be added if the object is being deleted

finalizer を controllerutil.RemoveFinalizer(obj, name)(戻り値 bool は変更があったかどうか)で外してから Update すると、Widget は即座に消えた(NotFound)。付け外しには controllerutil.AddFinalizer / RemoveFinalizer / ContainsFinalizer(すべて controller-runtime v0.24.1 のソースで確認)を使うのが普通で、コントローラーの Reconcile は「deletionTimestamp が付いているか」で後片付けの処理に分岐する。

図: finalizer が無くなった時点で実際に削除される(EKS 1.35 のテスト用クラスタで実測)。

5. finalizer が外れず namespace が Terminating で固まる典型と対策

finalizer を付けたコントローラーを、Reconcile のロジックのバグや RBAC 不足で外部の後片付けに失敗したまま放置したり、クラスタから削除してしまったりすると、finalizer を外す側のプログラムがいなくなる。その Widget は deletionTimestamp が付いたまま永遠に残り、その Widget を含む namespace も kubectl delete namespace で Terminating のまま固まる(namespace は中のオブジェクトが全部消えるまで消えない)。

対策は 2 段構えにする。1 つは、finalizer を付けるコントローラー自身を、外部リソースが既に無い場合にも必ず成功で終わるように書く(後片付け対象が既に存在しない時は成功として finalizer を外す。第 03 回で触れた冪等性と同じ考え方)。もう 1 つは応急処置として、固まったオブジェクトの finalizer を手動で空配列にする。metadata.finalizers は status サブリソースの対象ではないので、--subresource=status を付けずに本体への patch で書き換えられる(kubectl patch widget b --type=merge -p '{"metadata":{"finalizers":[]}}')。ただし手動で外すのは、後片付けをあきらめることと同義なので、外部リソースが残らないか確認してから行う。

図: 外す側がいなくなると、下流の namespace まで固まる。

6. まとめと次の回

ownerReferences は Kubernetes 内部のオブジェクト同士の後片付けを GC に任せる仕組みで、namespace をまたぐ所有はできない。finalizer は GC が届かない外部リソースの後片付けに時間を確保する仕組みで、外し忘れるとオブジェクトも namespace も固まる。次の第 11 回では、こうして作った・消したオブジェクトに安全に書き込むための resourceVersion・Patch・Server-Side Apply の使い分けを見る。

図: この章で見た関係と次回の橋渡し。

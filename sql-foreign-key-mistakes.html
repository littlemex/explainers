外部キーのミニ・アンチパターン

外部キー自体は正しい道具です。それでも参照側の索引の有無だけで、同じ親の削除が 456 倍遅くなることを実機で確認しました

この回の前提: 第 05 回 キーレスエントリ (外部キーそのものの基本と ON DELETE/ON UPDATE)

外部キー (子テーブルの列が、親テーブルのどの行を指しているかを DB に保証させる仕組み) を張ること自体は正しい判断です。ところが「張ってあるから安心」と思い込んで、参照する側 (子テーブル) に索引を作らない、型をきちんと揃えない、親側の一意制約を確認しない、といった小さな判断ミスを重ねると、後から効いてくる落とし穴になります。この回では、その中でも実務で最も効果が大きい「子テーブルの索引の有無で、親の DELETE がどれだけ変わるか」を PostgreSQL 18 の実機で測り、他のミニ・アンチパターンも 1 つずつ実際に動かして確認します。

1. 目的 ― 何をしたかったのか

外部キーは「子テーブルのこの列の値は、必ず親テーブルのどこかの行に存在する」という約束を、アプリケーションのコードではなく DB 自身に守らせるための制約です。アプリケーション側で毎回チェックを書く代わりに、DB が INSERT ・ UPDATE ・ DELETE のたびに自動で確認してくれるので、整合性の取り忘れによる孤立行 (親を失った子行) を構造的に防げます。

この約束を守るために、PostgreSQL は裏側でトリガーを使っています。子テーブルへの INSERT や UPDATE では「参照先の親が本当に存在するか」を確認するトリガーが走り、親テーブルの UPDATE や DELETE では「この行を参照している子がいないか (いる場合は CASCADE するか、エラーにするか)」を確認するトリガーが走ります。このトリガーが実際に何をスキャンするかが、この回のテーマです。

2. アンチパターン ― どう書いてしまい、何が壊れるか

2.1 参照側に索引が無い (本題)

PostgreSQL は、外部キーの親側の列には一意性を保証するための索引を要求しますが、子側の参照列には索引を自動で作りません。この結果、親テーブルの行を削除・更新するたびに走る「この行を参照している子はいないか」という確認が、子テーブルの全件スキャンになってしまうことがあります。

実機で、2,000 人の顧客 (customers_fk) と 30 万件の注文 (orders_fk, customer_id に外部キーのみで索引は無し) を用意し、注文が 1 件も無い顧客 (孤立させても安全な 200 人) のうち 25 人を削除しました。

EXPLAIN (ANALYZE, BUFFERS, COSTS off, TIMING on)
DELETE FROM customers_fk WHERE customer_id BETWEEN 1801 AND 1825;

-- Delete on customers_fk (actual time=0.039..0.039 rows=0.00 loops=1)
--   ->  Bitmap Heap Scan on customers_fk (actual time=0.015..0.016 rows=25.00 loops=1)
--         ...
-- Trigger for constraint orders_fk_customer_id_fkey: time=232.786 calls=25
-- Execution Time: 232.903 ms

削除そのものは 25 行で一瞬ですが、「本当に参照されていないか」を確認するトリガーだけで 232.786 ミリ秒 (25 回の呼び出し合計) かかりました。子テーブルに索引を追加し、別の 25 人をもう一度削除すると次の結果になりました。

CREATE INDEX ON orders_fk (customer_id);
EXPLAIN (ANALYZE, BUFFERS, COSTS off, TIMING on)
DELETE FROM customers_fk WHERE customer_id BETWEEN 1826 AND 1850;

-- Trigger for constraint orders_fk_customer_id_fkey: time=0.511 calls=25
-- Execution Time: 0.640 ms
子テーブルの索引トリガー合計時間 (25 回分)DELETE 全体の実行時間
無し232.786 ms232.903 ms
有り0.511 ms0.640 ms

トリガー時間だけで約 456 倍 (232.786 ÷ 0.511)、DELETE 全体の実行時間でも約 364 倍の差になりました。索引が無いと、親 1 行を消すたびに子テーブル (この実験では 30 万行) をシーケンシャルスキャンして「本当に参照されていないか」を確認するため、親の削除件数が増えるほど被害が線形に拡大します。

図: 子テーブルに索引が無いと、親の削除のたびに全件スキャンで参照を確認するため時間が跳ね上がる。

2.2 型不一致で外部キー自体が作れない

親の列が bigint、子の参照列が text のように型を揃えずに外部キーを張ろうとすると、PostgreSQL は制約の作成自体を拒否します。

CREATE TABLE bad_child (id bigint PRIMARY KEY, customer_ref text);
ALTER TABLE bad_child ADD CONSTRAINT bad_fk
  FOREIGN KEY (customer_ref) REFERENCES customers_fk (customer_id);
-- ERROR:  foreign key constraint "bad_fk" cannot be implemented
-- DETAIL:  Key columns "customer_ref" of the referencing table and "customer_id" of
--          the referenced table are of incompatible types: text and bigint.

2.3 親側に一意制約が無い

外部キーは「参照先が一意に決まる」ことを前提にしているため、親側の列に PRIMARY KEY や UNIQUE が無いと、制約自体を作れません。

CREATE TABLE loose_parent (code bigint, label text);
INSERT INTO loose_parent VALUES (1, 'a'), (1, 'b'); -- code=1 が重複
CREATE TABLE loose_child (id bigint PRIMARY KEY, code bigint REFERENCES loose_parent (code));
-- ERROR:  there is no unique constraint matching given keys for referenced table "loose_parent"

2.4 複合キーの列順を業務の検索パターンと合わせていない

複合外部キー ((order_id, line_no) のように複数列からなる外部キー) 自体は列の順序に関係なく機能しますが、子テーブル側に張る支援索引の列順は、実際の検索パターンに強く依存します。order_id だけで検索することが多いのに、索引を (line_no, order_id) の順で作ると、order_id 単独の条件では索引の先頭列が使えず、索引を活用できません。

CREATE INDEX shipments_bad_order_idx ON shipments (line_no, order_id);
EXPLAIN (ANALYZE, COSTS off) SELECT * FROM shipments WHERE order_id = 12345;
-- Seq Scan on shipments (actual time=0.473..3.582 rows=5.00 loops=1)
--   Rows Removed by Filter: 99995
-- Execution Time: 3.595 ms

-- 列順を (order_id, line_no) に変えると
-- Bitmap Heap Scan ... Execution Time: 0.095 ms

同じ 10 万行のテーブルで、列順を業務の検索パターンに合わせるだけで約 38 倍 (3.595 ÷ 0.095) 速くなりました。

2.5 循環参照と CASCADE の連鎖

チームとキャプテン (チームはキャプテンを参照し、キャプテンはチームに所属する選手) のように、2 つのテーブルが互いを参照する循環参照では、挿入の順番そのものが問題になります。チームを先に作ろうとしても、まだキャプテンが存在しないため、通常の外部キーなら即座に失敗します。

また ON DELETE CASCADE を連鎖させると、1 行の DELETE が何行に広がるか見えにくくなります。実機で、会社 1 社の削除が部署 20 ・ 社員 1,000 ・ タスク 1 万件まで連鎖する構成を作り、実際に削除してみました。

EXPLAIN (ANALYZE, COSTS off) DELETE FROM companies_fk WHERE company_id = 1;
-- Trigger for constraint departments_fk_company_id_fkey on companies_fk: time=0.071 calls=1
-- Trigger for constraint staff_fk_dept_id_fkey on departments_fk: time=0.493 calls=20
-- Trigger for constraint staff_tasks_fk_staff_id_fkey on staff_fk: time=8.247 calls=1000
-- Execution Time: 8.889 ms

会社 1 行の DELETE 文だけで、部署 20 行・社員 1,000 行・タスク 10,000 行、合計 11,021 行が静かに削除されました。1 行の削除リクエストのつもりで、実際には 1 万行以上が消えています。

図: ON DELETE CASCADE を連鎖させると、親 1 行の削除が子 ・ 孫 ・ ひ孫の行まで雪崩のように広がる。

3. 見つけ方 ― 索引の無い外部キー列をカタログから探す

既存のデータベースで「索引の無い外部キー列」を探すには、pg_constraint (制約の一覧) と pg_index (索引の一覧) を比較します。外部キーの先頭列が、その列から始まる索引を持っていない場合に抽出するクエリを実機で実行しました。con.conislocal (この行がこのテーブルに直接定義された制約かどうか) で絞っているのは、5 節で作るパーティション親テーブル (events_fk) への外部キーのように、参照先がパーティションテーブルだと PostgreSQL が内部的に「パーティションごとのクローン制約」(conislocal = false、\d には表示されない) を pg_constraint に増やすためです。これを除外しないと、同じ外部キーが重複して見えてしまうことを実機で確認しました。

SELECT con.conname, cl.relname AS child_table, att.attname AS fk_column
FROM pg_constraint con
JOIN pg_class cl ON cl.oid = con.conrelid
JOIN pg_attribute att ON att.attrelid = con.conrelid AND att.attnum = con.conkey[1]
WHERE con.contype = 'f'
  AND con.conislocal
  AND NOT EXISTS (
    SELECT 1 FROM pg_index i
    WHERE i.indrelid = con.conrelid AND i.indkey[0] = con.conkey[1]
  )
ORDER BY child_table;

--                 conname                 |  child_table  |  fk_column
-- -----------------------------------------+---------------+-------------
--  event_logs_fk_event_id_event_date_fkey  | event_logs_fk | event_id
--  players_fk_team_id_fkey                 | players_fk    | team_id
--  tasks_fk_assigned_to_assigned_dept_fkey | tasks_fk      | assigned_to
--  teams_captain_fkey                      | teams_fk      | captain_id

この実行結果は、実際にこの回で作った複合外部キー・循環参照・ON DELETE SET NULL の検証テーブルをそのまま検出しています。本番データベースでこのクエリを実行すれば、「親の DELETE が重くなりうる」子テーブルを洗い出せます。

4. 使ってよい場合

外部キーの保護を一時的に外してよい場面は限られます。大量データの初期ロード (ETL やバルクインポート) では、1 行ずつの検証コストを避けるために、外部キーを NOT VALID で追加し、ロード完了後に VALIDATE CONSTRAINT でまとめて検証する (次の節で実測) のが安全です。制約を完全に無効化する ALTER TABLE ... DISABLE TRIGGER ALL のような強い手段は、検証を忘れて不整合データが残るリスクがあるため、よほど管理された一時的なバッチ処理以外では避けるべきです。

また、子テーブルの索引を意図的に作らないのが許容されるのは、親テーブルの行が実質的に削除・更新されない (例えば追記専用のログの親テーブル) 場合に限られます。この回で実測したように、親の DELETE/UPDATE が発生する運用では、索引の欠如がそのまま実行時間に跳ねます。

5. 解決策 ― PostgreSQL での正しい書き方

子テーブルの参照列には必ず索引を作る

外部キーを張ったら、子テーブルの参照列に CREATE INDEX を追加することを既定の手順にします。この回の実測の通り、索引の有無だけでトリガー時間が約 456 倍変わりました。複合外部キーの場合は、業務で実際に使う検索条件に合わせた列順で索引を作ります(2.4 節の通り、列順を変えるだけで約 38 倍の差)。

NOT VALID → VALIDATE CONSTRAINT で検証を後回しにする

既にデータが入っているテーブルに外部キーを追加するとき、素直に ADD CONSTRAINT すると、既存の全行を検証してから制約が有効になります。NOT VALID を付けると検証をスキップして即座に制約を追加でき、その後 VALIDATE CONSTRAINT で既存行をまとめて検証できます。実機の 10 万行のテーブルで時間を比較しました。

ALTER TABLE shipments ADD CONSTRAINT shipments_order_fk_notvalid
  FOREIGN KEY (order_id, line_no) REFERENCES order_items (order_id, line_no) NOT VALID;
-- Time: 3.422 ms (既存行をスキャンしないので速い)

ALTER TABLE shipments VALIDATE CONSTRAINT shipments_order_fk_notvalid;
-- Time: 57.308 ms (既存 10 万行をスキャンして検証する分だけ時間がかかる)

NOT VALID で追加する段階は 3.422 ミリ秒で終わり、新しい書き込みからは直ちに制約が働きます。重い検証 (57.308 ミリ秒) は別のタイミングに切り離せるので、本番のロックを長く持つ時間を最小化できます。

DEFERRABLE INITIALLY DEFERRED で循環参照を解決する

チームとキャプテンの循環参照は、外部キーを DEFERRABLE INITIALLY DEFERRED (検査をトランザクションの最後まで遅らせる) にすることで、挿入の順番を気にせず書けるようになります。

ALTER TABLE teams_fk ADD CONSTRAINT teams_captain_fkey
  FOREIGN KEY (captain_id) REFERENCES players_fk (player_id)
  DEFERRABLE INITIALLY DEFERRED;

BEGIN;
INSERT INTO teams_fk (name, captain_id) VALUES ('red', 1);   -- まだ player_id=1 は存在しない
INSERT INTO players_fk (team_id, name) VALUES (1, 'alice');  -- ここで作られる
UPDATE teams_fk SET captain_id = 1 WHERE team_id = 1;
COMMIT; -- ここで初めて captain_id の存在チェックが行われ、成功する

通常の (DEFERRABLE を付けない) 外部キーで同じ順番の挿入を試すと、即座にエラーになることも実機で確認しました。

INSERT INTO teams_fk (name, captain_id) VALUES ('blue', 99999);
-- ERROR:  insert or update on table "teams_fk" violates foreign key constraint "teams_captain_fkey"
-- DETAIL:  Key (captain_id)=(99999) is not present in table "players_fk".

ON DELETE SET NULL (列指定) で複合外部キーの一部だけを外す (PostgreSQL 15 以降)

複合外部キーで親行が削除されたとき、既定では参照している列が全部 NULL になります。PostgreSQL 15 以降は ON DELETE SET NULL (列名) のように、NULL にする列を指定できます。実機で、担当者 (assigned_to) と部署 (assigned_dept) の複合外部キーのうち、assigned_to だけを NULL にする指定を試しました。

FOREIGN KEY (assigned_to, assigned_dept) REFERENCES employees_fk (employee_id, dept_id)
  ON DELETE SET NULL (assigned_to);

DELETE FROM employees_fk WHERE employee_id = 1;
SELECT * FROM tasks_fk;
--  task_id |  title  | assigned_to | assigned_dept
-- ---------+---------+-------------+---------------
--        1 | fix bug |             |            10   -- assigned_to だけが NULL になり、assigned_dept(10) は残った

パーティションテーブルを外部キーの参照先にできる (PostgreSQL 12 以降)

「パーティションテーブル (1 つの論理テーブルを複数の物理テーブルに分けたもの) は外部キーの親にできない」という制限は PostgreSQL 12 で解消されました。実機で、日付でパーティション分割したイベントテーブルを親に外部キーを張ったところ、問題なく機能しました。

CREATE TABLE events_fk (
  event_id bigint GENERATED ALWAYS AS IDENTITY,
  event_date date NOT NULL,
  label text,
  PRIMARY KEY (event_id, event_date)
) PARTITION BY RANGE (event_date);
CREATE TABLE events_fk_2026 PARTITION OF events_fk FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

CREATE TABLE event_logs_fk (
  log_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  event_id bigint, event_date date,
  FOREIGN KEY (event_id, event_date) REFERENCES events_fk (event_id, event_date)
);
-- パーティション化された親テーブルでも外部キーの作成・挿入が成功した

6. PostgreSQL エンジンで考慮しておくこと

外部キーのチェックは AFTER ROW トリガーとして実装されており、EXPLAIN (ANALYZE) の出力に Trigger for constraint ...: time=... calls=... という行として表示されます。この行は DELETE や UPDATE の本体の実行時間とは別に加算され、本体の処理が一瞬でも、トリガーの合計時間が全体の実行時間を支配することがあります。この回の実測では、DELETE 本体はミリ秒未満で終わっているのに、トリガーの合計時間 (232.786 ミリ秒) がほぼ全体の実行時間を占めていました。

また、ADD CONSTRAINT ... FOREIGN KEY は親テーブルと子テーブルの両方に対してロックを取得します。NOT VALID を使わずに大きなテーブルに外部キーを追加すると、検証のための全件スキャンの間、ロックを持ち続けることになり、他のトランザクションを長時間待たせる可能性があります。本番環境では NOT VALID で追加してから VALIDATE CONSTRAINT を別のタイミングで走らせる 2 段階の手順が推奨されます。

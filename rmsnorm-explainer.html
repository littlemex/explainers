RMSNorm をビジュアルに理解する

「平均を引かない」だけの正規化が、なぜ性能を落とさず実装をシンプルにできるのか

0この記事の狙い

RMSNorm は LLaMA・Gemma・Qwen など近年の主要オープン LLM の多くが採用する正規化層です (一方 GPT-2/3 系や BERT 系は今も LayerNorm)。数式は一見 LayerNorm とそっくりですが、たった一つの引き算を捨てたことで、計算とカーネル実装がシンプルになります。ここでは「絵と動き」でその差を腹落ちさせます。

一言でいうと
RMSNorm (Root Mean Square Normalization) とは、ベクトルを「二乗平均平方根 (RMS)」で割って大きさを揃えるだけの正規化です。LayerNorm がやっていた「平均を引いて中心を 0 に寄せる (centering)」を丸ごと省略し、スケールを整える仕事だけに絞りました。それでも精度はほぼ落ちず、計算とカーネル実装がシンプルになる。速さそのものより、この「性能同等 + 実装の簡潔さ」の費用対効果で選ばれています。

1なぜ正規化が要るのか — 大きさを揃える

まず「正規化層が何のためにあるのか」を素朴なイメージで揃えます。

ニューラルネットの層を深く積むと、各層を通るベクトル (アクティベーション) の大きさがどんどん暴れます。ある層では値が桁違いに大きくなり、別の層では潰れて小さくなる。この「スケールの暴れ」は勾配を不安定にし、学習を難しくします。

正規化層の仕事は、各トークンの特徴ベクトルを受け取って、その大きさを毎回そろえて次の層に渡すことです。ここで「そろえる」に何を含めるかが、LayerNorm と RMSNorm の分かれ道になります。イメージで言うと、LayerNorm は「偏差値化」(平均を引いてから広がりで割る)、RMSNorm は「原点からの距離で割るだけ」(平均を動かさず大きさだけ単位を揃える)、という違いです。

正規化のそろえ方には 2 つの操作があります。
(a) 中心をそろえる (centering): 平均を引いて、山の位置を 0 に動かす。
(b) 大きさをそろえる (scaling): 全体の広がりで割って、スケールを 1 に統一する。
LayerNorm は (a) と (b) の両方をやり、RMSNorm は (b) だけをやります。

2LayerNorm の数式を分解する

比較の土台として、まず LayerNorm を一行ずつ分解します。難しくありません。

入力を d 次元のベクトル x = (x₁, x₂, ..., x_d) とします (1 トークン分の特徴)。LayerNorm は次の順で計算します。

# 1. 平均を求める (centering に使う)
μ = (1/d) · ∑ᵢ xᵢ

# 2. 分散を求める (平均からのばらつき)
σ² = (1/d) · ∑ᵢ (xᵢ − μ)²

# 3. 平均を引いて割る → スケールγとバイアスβを掛け足す
yᵢ = γᵢ · (xᵢ − μ) / √(σ² + ε) + βᵢ

ポイントは 2 回、全要素を走査して和を取っていることです。1 回目は平均 μ、2 回目はその平均を使った分散 σ²。そして式のあちこちに −μ という「平均を引く」操作 (centering) が埋め込まれています。γ (スケール) と β (バイアス) は学習パラメータです。

注目すべき登場人物は 2 つ。「平均 μ」と「バイアス β」。RMSNorm はこの両方を持ちません。ただし μ の省略 (centering をやめる) と β の省略は本来は独立した設計判断です (bias 無し LayerNorm も存在します)。RMSNorm は標準定義でこの 2 つの簡素化を同時に採っている、と理解してください。次章で見ます。

3RMSNorm — 平均を捨てる

RMSNorm の発想は「centering は本当に必要か？ scaling だけで十分では？」という問いです。

RMSNorm を提案した論文 (Zhang & Sennrich, 2019) の仮説はシンプルです。LayerNorm が効く主因はスケールをそろえること (入力を定数倍しても出力が変わらない性質) であって、平均を引くこと (re-centering) の寄与は小さいのではないか。ならば μ の計算をまるごと省いてしまおう、というものです。論文はこれを理論的に断定したのではなく、多数のタスクで「LayerNorm と同等の性能」を実験的に示すことで仮説を裏づけました。その後の LLM 実務でも同等性を支持する結果が積み上がっています。

# 1. 二乗平均平方根 (RMS) だけを求める。平均μは計算しない
RMS(x) = √( (1/d) · ∑ᵢ xᵢ² + ε )

# 2. RMS で割って、スケールγを掛けるだけ。μ も β も無い
yᵢ = γᵢ · xᵢ / RMS(x)

補足: ε はゼロ割りを防ぐ数値安定化のための実装上の追加で、原論文の RMS の定義には現れません。LLaMA など実装では rsqrt(mean(x²)+ε) の形が一般的です。また Gemma のように γ を (1+γ) の形で持つ変種もあります。

LayerNorm と見比べてください。消えたものは 3 つです。

  1. 平均 μ の計算が消えた。全要素の和を取る走査が 1 回分まるごと不要になる。
  2. 各要素からの引き算 (xᵢ − μ) が消えた。この減算は分散の計算と正規化の両方に現れるので、実装によっては 2d 回。それがゼロに。
  3. バイアス β が消えた。足し込むパラメータが 1 セット減る (これは centering の省略とは独立した簡素化)。
分散 σ² と RMS の違いに注目。分散は平均からのばらつき (xᵢ−μ)² を測るので μ が要る。RMS は原点からの大きさ xᵢ² を測るので μ が要らない。「原点を基準にしていい」と割り切った瞬間に、平均の計算が丸ごと消える。これが RMSNorm の本質です。

4【体験】LayerNorm vs RMSNorm の動き

同じ入力ベクトルに両者を適用し、値がどう動くかを見ます。棒グラフの各バーが 1 次元の値です。切り替えて違いを体感してください。

入力 x 平均 μ の位置 正規化後 y

LayerNorm では、まず平均 μ (黄線) の分だけ棒全体が左右にシフト (centering) し、その後に高さがそろえられます。RMSNorm に切り替えると、黄線のシフトが起きません。棒はその場で高さだけ調整されます。平均を引かない = 分布の中心を動かさない、というのがこの「横シフトの有無」に現れています。

5計算コストを数える

「平均を捨てる」が演算量にどう効くかを、要素ごとの操作回数で正確に数えます。

次元 d のベクトル 1 本あたりに必要な主要演算を並べます。ここでは「全要素を何回なめる (走査する) か」が効きます。

ざっくり言うと、RMSNorm は集計するアキュムレータを 2 本から 1 本に減らし、d 回の減算をゼロにし、パラメータを半分にします。純粋な浮動小数点演算数 (FLOPs) で見ると、RMSNorm は LayerNorm のおおむね「3〜4 割減」程度です。ただし後述のとおり、この FLOPs 差がそのまま壁時計時間の短縮に直結するわけではありません (正規化は memory-bound で、そもそも正規化層の FLOPs はモデル全体では matmul に比べ小さい)。
ここで誤解しやすい点を先に潰します。正規化層はこの後 7 章で見るとおり memory-bound (メモリ帯域で律速) です。だから FLOPs が数十%減っても、それがそのまま実行時間の数十%短縮になるわけではありません。融合カーネルにすれば LayerNorm も RMSNorm も「入力を 1 回読んで結果を 1 回書く」だけで、動かすデータ量はほぼ同じだからです。RMSNorm の本当の勝ち筋は「メモリが減る」ことではなく、「計算とカーネル実装が単純になる」ことです。それを 7〜8 章で正確に見ます。まず次章で、演算量そのものの差を体感します。

但し書き (5章の注意を再掲)。これは算術操作の数の比較で、実行時間の比ではありません。正規化は memory-bound なので、この 3〜4 割の差がそのまま速度差になるわけではない点に注意してください。

7本当のボトルネックはメモリ

正規化層は「演算が軽くてメモリ移動が重い」典型的な memory-bound 処理です。ここが Fused Kernel が効く理由の核心です。

GPU で正規化のような処理を実行するとき、支配的なコストは掛け算の回数ではなく、データを HBM (GPU の主記憶) と計算コア (SM) の間で何往復させるかです。正規化は 1 要素あたりの計算がごく軽い一方、全要素を読み書きするので、メモリ帯域で律速される (memory-bound)。

フレームワークで演算子を素朴に合成 (eager 実行) すると、各ステップが別々の GPU カーネルになり、途中結果のベクトルを HBM に実体化しては読み直します。例えば x.pow(2).mean() → x / rms → x * γ をバラバラに実行するイメージです。

# 演算子を素朴に合成: 中間ベクトルの書き戻し・読み直しが何度も発生
HBM → x を読む → 二乗 → 中間ベクトルを HBM に書く
HBM → 読み直す → RMS で割る → HBM に書く
HBM → 読み直す → γ を掛ける → HBM に書く

この「読んでは書き、また読む」の往復が帯域を食い潰します。Fused Kernel (融合カーネル) は、これらのステップを1 つのカーネルにまとめ、ベクトルを一度だけ HBM から読み、オンチップの高速メモリ (レジスタ / 共有メモリ) の上で全部計算し、結果を一度だけ書き戻す実装です。行 (d 次元) は d=4096 程度ならオンチップに載るので、読み込み中に reduction も済ませられます。

ここが最重要の注意点です。この「融合で速くなる」は RMSNorm 固有の話ではありません。LayerNorm も融合できます。μ と σ² は Welford 法 (平均と分散を 1 回の走査で同時に更新していく古典的アルゴリズム) や ∑x・∑x² の同時集計で1 パスで計算でき、実際 PyTorch の nn.LayerNorm や Apex の FusedLayerNorm は昔から融合済みです。融合した LayerNorm と融合した RMSNorm では、HBM の往復回数 (読み 1 + 書き 1) は同じで、動かすデータ量もほぼ同じ。つまり「RMSNorm だからメモリが減って速い」わけではない、というのが正確な理解です。
では RMSNorm の勝ち筋は何か。メモリ量ではなく、カーネルの中身の単純さです。RMSNorm は集計するアキュムレータが ∑x² の 1 本だけ (LayerNorm は μ と σ² の実質 2 本)。並列リダクション (複数スレッドの部分和をまとめる処理) のマージが単純で、レジスタ使用も少なく、backward (逆伝播) の式も短く検証しやすい。だから融合カーネルを書きやすく・保守しやすい。速度差そのものは融合実装同士なら数%程度にとどまることが多いですが、この「実装の簡潔さ」がライブラリ普及と相まって効いてきます。

8【体験】Fused Kernel の効き方

演算子を素朴に合成した場合 (naive) と融合した場合 (fused) で、データが HBM とオンチップの間を何往復するかを見ます。往復の回数 = メモリ帯域の消費量だと思ってください。これは正規化一般の話で、LayerNorm でも RMSNorm でも同じ構図です。

HBM ↔ コア間のデータ移動 オンチップでの計算

非融合ではベクトルが HBM と計算コアの間を何度も往復します (読み書きのたびに赤い移動が発生)。融合に切り替えると、往復は「読み込み 1 回 + 書き戻し 1 回」だけになり、途中の計算はすべてオンチップ (緑) で完結します。memory-bound な処理では、この往復回数の削減がそのまま速度向上になります。ここで速くなっているのは「融合したこと」であって、LayerNorm→RMSNorm の差ではない点に改めて注意してください。LayerNorm も融合すれば同じ「読み 1 + 書き 1」になります。

実務での位置づけ。PyTorch などでは torch.compile や Triton、Apex の融合実装が、こうした融合を自動または手書きで行います。Apex に FusedLayerNorm があることが示すとおり、融合は LayerNorm にも普通に適用されています。RMSNorm はアキュムレータが 1 本で backward も短いため融合カーネルを書きやすい点が実務上の利点で、多くのライブラリ (例: flash-attn リポジトリ同梱の fused norm カーネルなど) で専用の fused RMSNorm 実装が提供されています。

【発展・読み飛ばし可】融合は正規化の「中」だけでは終わらない

ここは一段深い実装の話なので、初読では飛ばして構いません。実務でより効くのは正規化と、その前後の演算をまとめて 1 カーネルにする融合です。狙いは同じで、中間の activation を HBM に書き戻さずオンチップに留めることです。代表例:

  1. matmul → bias 加算 → 活性化関数 の融合 (epilogue 融合)。matmul の直後にバイアス加算や活性化を畳み込み、結果だけを書き出す。最も広く使われる形。
  2. 残差加算 → 正規化 の融合。pre-norm Transformer のブロック境界で、残差の足し込みと次の正規化をまとめる。
  3. 正規化 → 直後の射影 matmul の融合。RMSNorm の出力がそのまま QKV 射影や FFN の gate/up 射影の matmul に入るので、正規化結果を HBM に書かず流し込めば往復を減らせます (ただし matmul のタイル構造上、入力行を複数回参照するため往復が完全に消えるとは限りません)。
ここでも RMSNorm の簡潔さが効きます。正規化を隣の演算と融合するとき、正規化側の計算 (アキュムレータ 1 本、bias なし) が単純なほど、カーネルの prologue/epilogue (入口/出口の付随処理) に畳み込みやすい。「平均を捨てた」ことが、正規化単体の速さというより、周辺演算との融合のしやすさとして効いてくるわけです。ただし何とでも融合できるわけではなく、reduction (全要素を見ないと RMS が決まらない) の依存関係が融合の設計を制約する点は LayerNorm と共通です。

9まとめ — 引き算一つの費用対効果

RMSNorm が「平均を引かない」だけで得た 3 段のメリットを、一枚に整理します。

観点LayerNormRMSNorm
そろえる操作centering + scalingscaling のみ
集計するアキュムレータ2 本 (μ, σ²)1 本 (∑x²)
平均を引く減算d 回ありなし
学習パラメータγ, β (2d)γ のみ (d)
融合カーネル1 パス融合可 (Welford 等)1 パス融合可・中身がより単純
融合時のメモリ往復同じ (読み 1 + 書き 1)
精度への影響基準ほぼ同等 (多くの LLM で実証)
結論。RMSNorm は「centering を捨てる」というたった一つの割り切りで、(1) 要素ごとの演算をわずかに減らし、(2) 正規化層のパラメータを半減し (2d→d。ただしモデル全体では無視できる量)、(3) 集計するアキュムレータが 1 本になり 融合カーネルと backward が単純になる。しかも性能はほぼ維持できる。劇的な速度差ではなく、この「実装の簡潔さ + 性能同等」という費用対効果の良さゆえに、LLaMA・Gemma・Qwen など近年の主要オープン LLM の多くが採用しています。「本質は re-centering ではなく re-scaling だったのでは」という仮説が、実装のシンプルさという形で実を結んだ好例です。

中身の推定

エンコーダではなく、生成をやめた MoE に読み出しを付けたもの

← シリーズ目次

0この回で分かること

重みも論文も出ていないので、中身は外から推定するしかありません。 API を 1 万回叩いた外部の調査と公開ドキュメントを突き合わせると、当初の見立て (エンコーダ型) は たぶん違って、別の形が浮かびます。

一言でいうと
因果的な transformer (おそらく疎な MoE) を、生成をやめて確率の読み出しに付け替えたものという推定です。 state を 1 回だけ符号化し、質問ごとに枝を並列に伸ばし、枝の最後の表現から確率を直接読む。 prefill (入力を読む段) で終わり、1 トークンずつ書く段に進まない。 ここが「並列に答えが出る」の正体で、魔法ではなくやめただけです。
1. なぜエンコーダ型だと思ったか、なぜ違うか 2. 並列に見える理由 — prefill で終わる 3. state を共有し、質問を隔離する 4. なぜ疎な MoE が向くのか 5. 確実な部分と推測の部分 6. この推定が実験設計を変える

1なぜエンコーダ型だと思ったか、なぜ違うか

「文章を生成しない」「1 回の前向き計算で複数の判断を返す」「型が壊れない」と聞くと、 BERT のようなエンコーダに分類の出口を何本か付けた形を思い浮かべます。実際それは作れて、動きます (第 4 章以降で作って測ります)。

しかしそれだと説明できないことが 2 つあります。

観測エンコーダ型では説明しにくい理由
「最上位モデル並みの知能」を主張する数億パラメータ級のエンコーダに、最上位の生成モデルが持つ知識は入らない。事前学習の規模が違いすぎる
入力上限が約 32,000 トークンで、state と質問が枠を共有する分類器なら質問ごとに独立に投げればよく、枠を共有する理由がない。state の計算結果を使い回している構造を示唆する

公式ドキュメント自身も「事前学習された LLM の知識を保ったまま、生成された自信の申告を、 内部表現から直接読む決定確率に置き換える」という言い方をしています。 捨てたのは生成であって、土台の LLM ではないという読み方です。

2並列に見える理由 — prefill で終わる

ふつうの生成モデルの推論は 2 段あります。

  1. prefill (入力を読む段): 入力トークンは全部すでに分かっているので、位置をまとめて計算できる。 層は順に進むが、同じ層の中では並列。
  2. decode (1 トークンずつ書く段): 次のトークンは前のトークンを選ぶまで存在しないので、 どうしても順番待ちになる。ここが遅さと値段の正体。

ここで大事な区別があります。因果的な注意 (causal attention) は「どの位置がどの情報を使えるか」の話であって、 「入力をどの順に計算しなければならないか」の話ではありません。 prefill の時点で入力は全部手元にあるので、まとめて計算できます。

Jev の形は prefill と読み出しで終わり、decode に進まないと推定されます。 だから「答えが並列に出る」のであって、新しい並列化を発明したわけではありません。 "payments": 0.91 という文字列を 1 文字ずつ綴る仕事を、ニューラルネットからアプリのコードへ 移しただけです。

図 1. 生成モデルは prefill のあとに 1 トークンずつの順番待ちが続く。決定モデルは prefill と読み出しで終わる。 速さの正体は新しい並列化ではなく、遅い段をやめたこと。

3state を共有し、質問を隔離する

state が S トークン、質問が Q 個あるとします。質問ごとに別々のリクエストにすると、 state を Q 回読み直すことになります。同じ長い文章を何度も読むのは無駄です。

推定される形では、state を 1 回読んだ中間結果 (KV キャッシュ) を全部の質問が共有します。 各質問は自分の指示文と選択肢だけを足します。だから公式ドキュメントの 「約 32,000 トークンを state と質問で共有する」という書き方になり、 「質問を増やすと state の枠が減る」という制約が出てきます。

そして質問どうしはおたがいを見ません。これは効率のためだけでなく、 設計として意味があります。質問 1 の答えが質問 2 の答えに影響しないので、 あとから「どの判定が引っかかって人手に回ったのか」を 1 つずつ切り分けられます。

だから公式が勧める作法はこうなる。「この問い合わせを総合的に評価して」と 1 問で聞くのではなく、 「緊急か」「返金要求か」「規約違反か」と小さく割る。重みづけと最終判断は自分のコードで組み立てる。 質問は 1 回の呼び出しの中で並列に走るので、分けても遅くなりません。

4なぜ疎な MoE が向くのか

疎な MoE (Mixture of Experts) は、層ごとに用意した多数の「専門家」のうち少数だけを毎トークンで使う形です。 総パラメータは大きいのに、1 トークンあたりの計算は小さくなります。

この用途に向く理由は 2 つあります。

性質この用途で得になる理由
総容量は大きく、1 トークンの計算は小さい知識量は事前学習の規模で決まるので大きくしたい。一方 prefill しかしないなら計算は削りたい。両者の要求が同じ方向を向く
生成モデルでの弱点が効かないMoE は decode の 1 トークンごとに専門家の重みを読み直すのが重い。decode をしないなら、その弱点が丸ごと消える

2 つめが効いています。MoE を生成に使うときに払っていた代償が、生成をやめると払わなくてよくなる。 だから「この用途なら MoE でないほうが変」という言い方になります。

5確実な部分と推測の部分

推定を扱うときは、どこが公表で、どこが観測で、どこが推論なのかを分けておかないと、 あとで自分の推測を事実として引用してしまいます。

内容確からしさ
生成をしない。型付きの答えと確率を返す公表 (公式ブログ・ドキュメント)
state と質問が入力枠を共有し、上限は約 32,000 トークン公表 (公式ドキュメント)
質問は 1 回のクエリで並列に処理される公表。ただし内部の実装形は非公開
事前学習された LLM の知識を保っている公表に近い (公式が「retain the knowledge of a pretrained LLM」と書く)
state を 1 回符号化して質問の枝が共有する観測からの推論 (文脈長と質問数に対する遅延の伸び方)
因果的な transformer である推論。支持は強い
疎な MoE である推測。この推定でいちばん弱い部分。向いているという議論は立つが、直接の証拠はない
報酬の式、データの作り方、パラメータ数不明。公開されていない
この回で一番弱いのは MoE の部分です。「向いているから、そうでないほうが変」は動機の議論であって、 証拠ではありません。以降の実験では「MoE だと断定したから」ではなく 「生成をやめた大きな因果モデルに読み出しを付けるという形を試したいから」という理由で土台を選びます。 その形なら、MoE でも密なモデルでも同じ実験になります。

6この推定が実験設計を変える

当初はエンコーダ型 (DeBERTa 系、1.8 億パラメータ) で作って測りました。結果は第 4・5 章にあります。 結論を先に言うと、動いたけれど払う価値がありませんでした。

推定が正しいなら、その失敗のうち少なくとも一部は土台を間違えたことで説明できます。 分かったことのひとつは「効いているのは事前学習された表現で、追加学習ではない」でした (エンコーダを凍結して線形 1 枚だけ学習したほうが、1.8 億パラメータを丸ごと動かすより良かった)。 もし効いているのが表現なら、表現の質を上げる = 土台を大きくすることが最も直接的な介入になります。

やり直しの方向。土台を、生成をやめた大きな因果モデル (手元にある MoE) に替え、 最後の隠れ状態から読み出しを付ける。前向き計算は 1 回だけで、1 トークンも生成しない。 そのうえで測る対象を「正答率」から「どこまで自動化を任せられるか」に変える — 次の回で、なぜ測る対象まで変える必要があるのかを見ます。

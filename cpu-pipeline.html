1 個の命令が「読み出し → 解読 → 実行 → 書き戻し」を終えるまでの時間がレイテンシ (1 件あたりの処理時間)、単位時間に何件の命令を終わらせられるかがスループットです。パイプラインは、1 命令のレイテンシを短くする工夫ではなく、複数の命令の処理を 1 クロックずつずらして重ね、段ごとの部品を休ませずに働かせることでスループットを上げる工夫です。rj32 は fetch (読み出し) と execute (解読・実行・書き戻し) の 2 段だけの、ごく小さなパイプラインを持っています。

1. パイプラインが解く問題: スループットとレイテンシ

1 つの命令が「読み出し → 解読 → 実行 → 書き戻し」を通り終えるまでの時間をレイテンシと呼びます。これに対して、CPU が単位時間あたりに終わらせられる命令の数をスループットと呼びます。パイプラインが無ければ、1 つの命令が全部の段を通り終えてから次の命令が始まるため、スループットはレイテンシの逆数で頭打ちになります。パイプラインは、1 つの命令のレイテンシを短くする工夫ではありません。複数の命令を 1 クロックずつずらして重ね、各段の部品を毎クロック働かせ続けることで、レイテンシは変えずにスループットだけを上げる工夫です。

古典的な教科書の例として、命令を IF (読み出し) → ID (解読) → EX (実行) → MEM (メモリアクセス) → WB (書き戻し) の 5 段に分ける設計があります。各命令がどのクロックにどの段にいるかを、段を縦、クロックを横にした表に描くと、重なりがひと目で分かります。

図: 5 段パイプライン表。段を縦、クロックを横に取ると、複数の命令が同時に別の段を使っていることが見える。

2. rj32 の 2 段パイプライン表

rj32 の README が明記するとおり、パイプラインは fetch (命令メモリから命令を読み出す) と execute (命令を解読し、レジスタファイルから値を読み、ALU で実行し、結果を書き戻す) の 2 段しかありません。古典的な 5 段の ID ・ EX ・ MEM ・ WB を 1 つの execute 段に全部詰め込んでいる、という見方もできます。同じ表の描き方で rj32 の動きを描くと、段がぐっと少ないぶん、ある命令が execute にいる間に次の命令が fetch にいる、という 1 クロックだけのずれになります。

図: rj32 の fetch/execute 2 段パイプライン表。古典的な 5 段より段数は少ないが、重ね方の考え方は同じ。

3. 段の境目には何があるか: IR と PC

段と段の間で命令や値を 1 クロック分だけ持ち越す部品が、パイプラインレジスタです。rj32 では dig/fetch.dig の IR (16 ビットレジスタ) がこの役目を果たします。命令メモリから読んだ instr_i を IR に取り込み、その値を instr_o として execute 段へ渡します。もう 1 つの部品 PC (プログラムカウンタ、Digital の CounterPreset) も境目に立っていますが、向きが違います。PC の値は pc として execute 段へ渡される (fetch → execute) だけでなく、execute 段が計算したジャンプ先が result として execute → fetch の向きに戻ってきて、次の PC の値として取り込まれます。

図: instr_o ・ pc ・ result は dig/fetch.dig の実際のピン名。result は dig/execute.dig の実際の出力ピン名でもあり、段を逆方向に戻る唯一の信号。

この result が逆方向に戻るという事実が、第 16 回で扱う制御ハザードの根本原因です。fetch 段は execute 段の結果を待たずに次の命令を読み進めてしまうので、ジャンプのように result が PC を書き換える命令では、1 クロック前に読んでしまった命令が無駄になる場面が生まれます。

4. なぜ fetch は自分の段を持つのか: メモリの読み出し遅延

第 9 回で見たとおり、同期読み出しのメモリ (BRAM) はアドレスを渡してから実際にデータが出てくるまで 1 クロックかかります。これは設計者が選べる項目ではなく、クロックの立ち上がりでアドレスをラッチし、次の立ち上がりでデータが確定するという、同期メモリの動き方そのものです。rj32 の実験回路 experiments/dpram_pipeline.dig は、この性質を S_addr ・ S_rdy ・ S_vld (要求側の握手信号) と D_vld ・ D_addr ・ D_data ・ D_rdy (応答側の握手信号) という一般的な形で確かめたものです。アドレスを渡す側と、データを受け取る側の間に、最低 1 つのレジスタが挟まることを示しています。

図: 同期メモリはアドレスとデータの間に 1 クロックの遅れを持つ。fetch 段はこの遅れをそのまま受け持っている。

5. 段数を変えてもスループットの上限は変わらない

パイプラインが満員 (すべての段が常に別の命令で埋まっている) になった後は、段数が 2 段でも 5 段でも、理想的には毎クロック 1 命令が完了します。N 個の命令をすべて処理し終えるまでにかかるクロック数は、段数を S とすると、おおよそ N + (S − 1) クロックです。段数 S が大きいほど最初の 1 命令が完了するまでの「立ち上がり」の分だけ余計にかかりますが、N が十分大きければこの差は割合として消えていき、どちらも 1 クロックに 1 命令というスループットに近づきます。

では段数は何に影響するのでしょうか。段数が増えるほど 1 段が担う組み合わせ回路は小さくなり、1 段の中で信号が伝わりきるまでの時間 (クリティカルパス) が短くなるので、理論上はクロック周波数を上げられます。rj32 の execute 段はレジスタ読み出し ・ ALU 実行 ・ 比較 ・ 書き戻しを 1 クロックに詰め込んでいるため、この段の中の信号経路の長さがそのまま rj32 の最大クロック周波数の上限になります。段を増やして execute を分割すれば、各段は軽くなり周波数は上げられますが、段をまたいで値を受け渡す必要が生じ、その受け渡しこそが第 16 回で扱うハザードの土台になります。

図: 段数が違っても、命令数が多くなれば両方とも 1 クロックに 1 命令というスループットに近づく。

6. 実装のポイント

rj32 は意図的に段を増やさなかった。 段数を増やせば理論上はクロック周波数を上げられますが、増やした段の間で値を正しく受け渡す仕組み (フォワーディングやストール) を新たに作る必要が生まれます。rj32 は 2 段という最小の構成を選び、ハザードの種類を最初から絞ることで、仕組み全体を見通しやすく保っています。これは性能を最優先した設計ではなく、分かりやすさと、ice40 のような小さな FPGA (第 20 回) に収まる規模 を優先した設計判断です。性能を追うなら、第 23 回で見る CPI (命令あたりの平均クロック数) を下げるために、段数を増やしてクロック周波数を上げる方向に倒すこともできます。

「fetch を execute に統合すればもっと速いのでは」という誘惑。 2 段をさらに減らして 1 段にまとめられないか、と考えたくなるかもしれません。しかし第 4 節で見たとおり、同期メモリはアドレスとデータの間に 1 クロックの遅れを必ず持ちます。1 段にまとめても、この 1 クロックの遅れ自体は消えません。結局、命令メモリを読むという行為そのものに 1 クロックかかる以上、それを受け持つ段を外には出せないのです。段数を減らす設計変更は、この物理的な制約を迂回できる場合にだけ意味を持ちます。

図: 段数を増やすかどうかは、クロック周波数と受け渡しの複雑さのトレードオフになる。

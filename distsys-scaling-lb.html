スケーリングとロードバランサ ― 1 台を増やしても倒れない形にする

台数を増やす前に状態を外へ出さないと、増やした分だけ新しい壊れ方が増えるだけに終わる

この回の前提: 第 01 回 なぜ分散するのか、第 02 回 ソケットプログラミング入門

1 台のサーバで足りなくなったとき、最初に考えるのは「もっと大きい 1 台」(垂直スケーリング) です。しかしこれには物理的な上限があり、やがて「複数台に増やす」(水平スケーリング) に切り替える必要が出てきます。ところが台数を増やすだけでは何も解決しません。各サーバがリクエストの状態 (セッション情報など) を自分のメモリに抱えたままだと、ロードバランサがどのサーバにリクエストを振っても同じ結果にならず、1 台が落ちればそのユーザのデータだけが消えます。この回では、サーバをステートレス (状態を持たない) にしてロードバランサで束ねる仕組みと、ヘルスチェックやスティッキーセッションがどこで壊れるかを具体的に見ていきます。

1. 垂直スケーリングの限界と水平スケーリングへの切り替え

アクセスが増えてサーバが遅くなったとき、最初に試すのは垂直スケーリング (scale up)、つまり今あるサーバの CPU やメモリ、ディスクをもっと良いものに替えることです。手順が単純でアプリケーションのコードを変える必要がないため、まず試す選択肢として間違いではありません。

しかし垂直スケーリングには 2 つの壁があります。1 つは物理的な上限で、1 台に積める CPU コア数やメモリ量には必ず天井があります。もう 1 つはコストで、性能を 2 倍にするための値段は 2 倍では済まず、高性能な専用機ほど単位性能あたりの価格が跳ね上がっていきます。さらに、サーバが 1 台しかない限り、そのサーバが故障すればサービス全体が止まる単一障害点 (single point of failure) のままです。

そこで必要になるのが水平スケーリング (scale out)、つまり性能の高い 1 台を目指すのではなく、同じ役割のサーバを何台も並べて負荷を分け合う方法です。水平スケーリングは理論上、台数を増やすだけ処理能力を伸ばせますが、1 つ条件があります。どのサーバにリクエストが届いても同じ結果が返る必要があり、そのためにはサーバが「前回この人が誰で何をしていたか」を自分のメモリだけに持たない設計、つまり次の節で説明するステートレス化が前提になります。

図: 垂直スケーリングは 1 台を強くする方法で上限がある。水平スケーリングは台数を増やす方法で、ステートレスな設計が前提になる。

2. ステートレス化とロードバランサの基本的な仕組み

複数台に増やしたサーバの手前に置き、どのサーバに処理を振るかを決めるのがロードバランサ (load balancer, LB) です。LB には大きく 2 種類あります。L4 (トランスポート層) LB は IP アドレスとポート番号だけを見て振り分け先を決め、HTTP の内容は一切読みません。パケットをそのまま右から左に流すだけなので処理が軽く、毎秒数百万接続のような超高スループットに向きます。一方L7 (アプリケーション層) LB は HTTP ヘッダや URL パス、クッキーまで読んでから振り分けるため、「/api/ で始まるパスは API サーバへ」「特定のクッキーを持つユーザは同じサーバへ」といった内容に応じた判断ができますが、その分 1 リクエストあたりの処理コストは上がります。

振り分けの具体的な方式にも何通りかあります。ラウンドロビン は順番に 1 台ずつ均等に割り当てる最も単純な方式ですが、サーバの性能差やリクエストごとの処理時間の差を考慮しません。重み付きラウンドロビン はサーバごとに重みを設定し、性能が高いサーバに多めに割り振ります。最小接続数 (least connections) は今まさに処理中のリクエスト数が最も少ないサーバへ送るため、処理時間が長いリクエストが混ざっていても偏りにくくなります。

ここで前提になるのが、サーバがステートレス (stateless) であることです。ログイン中のユーザ情報のようなセッション状態をサーバ自身のメモリに持ってしまうと、2 回目以降のリクエストを別のサーバに振ったときにそのユーザの情報が無くなり、ログインが切れたように見えたり処理が失敗したりします。これを避けるには、セッション状態を各サーバのメモリではなく外部の共有ストア (Redis のような分散キャッシュや DB) に置き、どのサーバが応答しても同じ状態を参照できるようにします。

この「振り分け先を決める」計算自体は難しくありません。次のコードは最小接続数方式の考え方を Python でそのまま表したものです。

def least_connections(conn_counts):
    return min(conn_counts, key=conn_counts.get)

connections = {'server-a': 3, 'server-b': 1, 'server-c': 5}
print(least_connections(connections))

辞書 conn_counts はサーバ名をキーに現在の接続数を値として持ち、min に key=conn_counts.get を渡すことで接続数が最小のサーバ名を 1 回の走査で選び出しています。この例では server-b が選ばれます。実際の LB はこの選択をリクエストが来るたびに、かつ複数の LB インスタンス間で接続数の数え方をできるだけ揃えて実行します。

図: L4 LB は IP とポートだけで判断して高速、L7 LB は HTTP の内容まで読んで賢く振り分けられる分コストが高い。

3. ヘルスチェックの設計 ― 死んでいるサーバをどう見つけるか

LB がリクエストを振り分け続けるには、どのサーバが実際に応答できる状態かを常に知っておく必要があります。これを確認する仕組みがヘルスチェック (health check) です。方式は大きく 2 つあります。アクティブヘルスチェック は LB が一定間隔で各サーバの専用エンドポイント (例えば /health) に自分から問い合わせ、応答が無いか異常な応答コードが返ってきたサーバをプールから外します。パッシブヘルスチェック は専用の問い合わせをせず、実際の業務リクエストが連続して失敗したサーバを異常とみなして外す方式です。

ヘルスチェックの中身にも深さの違いがあります。プロセスが起動していて応答を返せるかだけを見る浅いチェック (basic check) と、そのサーバが依存している DB やキャッシュまで実際に呼び出して確認する深いチェック (deep check) です。深いチェックは「サーバは起きているが依存先の DB が死んでいるので実質使えない」という状態を検出できる一方、LB が何台も同時に深いチェックを打つと、その問い合わせ自体が DB への負荷になってしまう点に注意が必要です。

応答コードの意味も区別しておく必要があります。バックエンドが 5xx を返すのは「サーバは応答したが処理に失敗した」という意味で、ヘルスチェック的には異常と判断する根拠になります。これに対し LB 自身が返す 502 (Bad Gateway) や 504 (Gateway Timeout) は「LB がバックエンドに接続できなかった、または応答を待ちきれなかった」ことを示し、バックエンドが本当に死んでいるのか一時的に遅いだけなのかは別途調べる必要があります。404 は「そのパスにルートが無い」という意味で、サーバ自体が死んでいることを示す根拠にはなりません。

Kubernetes を使う場合は、LB (または Kubernetes のリーダー自身) の liveness probe / readiness probe と LB のヘルスチェックが二重に存在することもあります。liveness probe はコンテナを再起動すべきかを判断し、readiness probe はそのコンテナにトラフィックを送ってよいかを判断します。デプロイ直後は起動が完了していない Pod にトラフィックが流れないよう、readiness probe が整うまで LB 側のプールにも加えない設定が必要です。

図: アクティブヘルスチェックで応答が無いサーバを検出し、新しいリクエストの振り分け先から外す。

4. スティッキーセッションの代償と、どこで壊れるか

ステートレス化が難しい場面では、同じユーザのリクエストを常に同じサーバへ送るスティッキーセッション (sticky session, セッションアフィニティ) で代用することがあります。クッキーや送信元 IP のハッシュ値を使って毎回同じサーバを選ぶ方式です。しかしこれには代償があります。第 1 に、特定のサーバに重い処理をするユーザが偏って割り当たると、他のサーバが暇でもそのサーバだけ過負荷になり、ロードバランシングの本来の目的である負荷の分散が崩れます。第 2 に、割り当てられていたサーバが落ちると、そのユーザのセッション情報は丸ごと失われ、ログインし直しになります。ステートレス化してセッションを共有ストアに置いた場合は、どのサーバが応答しても同じ状態を参照できるため、この問題自体が起きません。

ヘルスチェックの運用でも壊れ方があります。深いチェックを多数の LB インスタンスが同時に実行すると、チェック自体が下流の DB やキャッシュへの小さなサンダリングハード (thundering herd, 一斉アクセスの集中) を引き起こすことがあります。また、デプロイ直後にアプリケーションの起動がまだ終わっていないのにヘルスチェックが早すぎるタイミングで始まると、正常に立ち上がる途中のサーバを誤って異常と判定し、プールから外してしまいます。

オートスケーリングにも時間差の問題があります。負荷の急増を検知してから新しいサーバを起動し、アプリケーションの起動とウォームアップ (キャッシュが温まっていない状態からの立ち上がり) が終わってヘルスチェックに応答できるようになるまでには数十秒から数分かかります。この間、既存のサーバだけで急増した負荷を受け続けることになり、スケールアウトが「間に合わない」ことがあります。逆にスケールインを急ぎすぎると、次の負荷の波に対応できる余裕を削ってしまいます。

図: セッションを特定サーバのメモリだけに置くと、そのサーバの障害でセッションが完全に失われる。

5. 実システムでの例 ― EC サイトの進化とクラウド LB

典型的な EC サイトが 1 台構成から成長していく過程を順番に見ると、この回で説明してきた要素がどの順番で必要になるかがわかります。まず商品説明と在庫を扱う在庫サービスと、ユーザ登録やログインを扱うユーザサービスがあるとします。最初はアプリケーションサーバと DB を 1 台に同居させ、負荷が増えたらアプリケーションサーバと DB サーバを分離します。さらに増えたら、アプリケーションサーバを複数台に増やして LB で束ねる、これがここまで説明してきたステップです。その後は、読み取り専用の複製 (リードレプリカ) で DB の読み取りを分散させたり、データを複数の DB に分割 (シャーディング) したり、キャッシュ層を挟んだりして、最終的にはサービスごとに独立してスケールできるマイクロサービス構成へ向かいます。つまりロードバランサは「1 台を超える」ための最初の一歩であり、後続の回で扱うレプリケーションやシャーディング、キャッシュはその先に積み上がる層です。

クラウドの実装としては、AWS のALB (Application Load Balancer) が L7 LB の代表で、URL パスやホストヘッダに基づくルーティング、HTTP ヘッダを使ったヘルスチェックの深さの調整ができます。NLB (Network Load Balancer) は L4 LB の代表で、送信元 IP を保持したまま転送でき、毎秒数百万接続規模の高スループットと低レイテンシが必要な場面で使われます。どちらを選ぶかは、振り分けの判断にアプリケーションの内容 (パスやヘッダ) が必要かどうかで決まります。

観点L4 (例: NLB)L7 (例: ALB)
判断に使う情報送信元 ・ 宛先 IP とポートURL パス ・ ヘッダ ・ クッキー
得意な場面超高スループット、低レイテンシ内容に応じた柔軟なルーティング
送信元 IPそのまま保持できるヘッダ (X-Forwarded-For 等) で伝える

どちらの LB を使うにせよ、この回の核心は変わりません。台数を増やす前にサーバをステートレスにし、ヘルスチェックで壊れたサーバを自動的に外す仕組みを用意しておくこと。これが無いまま台数だけを増やすと、増えた台数分だけ「どのサーバに当たるかで挙動が変わる」という新しい不具合の種が増えるだけになります。

K8S CUSTOM CONTROLLER ・ 第 05 回

CRD の骨格

group・names・scope・versions という 4 つの決め事と、構造的スキーマが API サーバーに新しい型を教える

← カスタムコントローラー自作 シリーズ目次へ

CustomResourceDefinition(CRD)は 1 枚の YAML で「新しい種類のモノ」を API サーバーに登録する。この回では、その YAML のどの部分が何を決めているかを、実験で使った Widget という型(第 04 回で登場)を題材に見ていく。

CRD は group(住所)・names(呼び名)・scope(持ち場)・versions(見せ方と保存の仕方)の 4 つを決める。さらに structural schema(構造的スキーマ: 全フィールドに型が決まっている形)によって、知らないフィールドを刈り込み(pruning)、表示列を増やせる。これは全部「保存のされ方」の話で、まだ誰も世界を動かしていない。

CRD が決めるもの: 住所・呼び名・持ち場

CRD オブジェクト自体は apiextensions.k8s.io/v1 の CustomResourceDefinition という型で、その spec に 4 つの決め事を書く。group は新しい型が属する住所(例: lab.crd-series.example)、names は複数形・単数形・Kind 名・短縮名(shortNames)・分類名(categories)、scope は namespace に属するか(Namespaced)クラスタ全体か(Cluster)。第 02 回で学んだ GVK(Group/Version/Kind)と GVR(Group/Version/Resource)は、この CRD の中身がそのまま材料になっている。

実験で使った Widget は、group: lab.crd-series.example、names: {plural: widgets, singular: widget, kind: Widget, shortNames: [wdg]}、scope: Namespaced という決め事を持つ。これが決まると、API サーバーの中に新しい REST の住所が 1 本生える。

図: CRD の 4 つの決め事(group・names・scope・versions)が合体して 1 本の REST パスになる

バージョン: served と storage

spec.versions には複数のバージョンを並べられる。各バージョンには served(クライアントに見せて使わせるか)と storage(etcd に実際に保存する形かどうか)という、別々の役目を持つフラグがある。storage: true は必ずちょうど 1 つだけで、クラスタが実際に持つデータの実体を決める。served は「API としてお客に見せる顔」で、複数のバージョンを同時に served にできる(例: v1 と v1beta1 を両方使えるようにしておき、徐々に v1beta1 を外す)。

実験用 Widget は v1 だけを持ち、served: true・storage: true という一番単純な形だった。複数バージョンを同時に served にしたときにデータがどう変換されるか(そして変換しない場合に何が起きるか)は、第 14 回で実測結果とともに扱う。

図: served は複数あってよいが、storage(新しく書き込む形)は常に 1 つ。v1beta1 は変換されて v1 の形で保存される。storage を切り替えても、切り替え前の古い形のデータはすぐには書き直されない(第 14 回)

構造的スキーマと刈り込み (pruning)

apiextensions.k8s.io/v1 では「構造的スキーマ(structural schema: すべてのフィールドに型が決まっている形)」が必須になっている(確認済み: Kubernetes 公式ドキュメント)。これにより、スキーマに書いていないフィールドは保存のときに自動で刈り込まれる(pruning)。

実測(EKS 1.35 のテスト用クラスタ): Widget の spec に存在しない unknownField を入れて kubectl apply(既定)すると、strict decoding error: unknown field "spec.unknownField" で拒否された(kubectl の既定が --validate=strict のため)。--validate=warn を付けると警告だけ出て作成され、保存された spec は {"image":"nginx","minReplicas":0,"replicas":1,"size":"small"} で、unknownField は刈り込まれて消え、既定値 3 つが埋まっていた。

刈り込みを止めたいときは x-kubernetes-preserve-unknown-fields: true を使う。これを付けてもスキーマ自体は構造的なままだが、付けた箇所だけはスキーマに無いフィールドが検証されずにそのまま保存されるようになる。表示や他のフィールドの検証、バージョン変換には影響しないが、検証をすり抜ける穴を作ることになるので、使う場所は狭い。

図: kubectl の既定は strict decoding で拒否、--validate=warn なら刈り込まれて作成される(実測)

追加の表示列 (additionalPrinterColumns)

kubectl get の表示は既定で NAME と AGE だけ。additionalPrinterColumns に jsonPath(jsonPath: オブジェクトの中の 1 つの値を指し示す書き方)を指定すると、好きな列を増やせる。これは表示だけの機能で、保存データや検証には影響しない。

実験用 Widget は Size(.spec.size)・Replicas(.spec.replicas)・Ready(.status.conditions[?(@.type=="Ready")].status)の 3 列を持つ。実測(EKS 1.35 のテスト用クラスタ): kubectl scale widget a --replicas=4(scale サブリソース: spec.replicas の増減だけを専用の操作で行える仕組み、第 08 回)で spec.replicas を変えた後、kubectl get wdg(wdg は Widget の shortNames に設定した短縮名)の表示は次のとおりだった。

NAMESIZEREPLICASREADY
asmall4True

Ready 列の値 True は、誰か(ここでは実験で手動で書いた status)が status.conditions に type: Ready の要素を実際に書き込んでいたから表示された。CRD に列の定義を書くだけでは、値は出てこない。第 04 回で見た「CRD だけでは何も動かない」という話がここにもつながる。

図: additionalPrinterColumns は jsonPath を通して既にある値を列に写すだけ

kubebuilder マーカーから CRD YAML が生まれる流れ

ここまでの YAML は人間が手で書いたものだが、kubebuilder を使う場合は少し違う道筋をたどる。Go の型(構造体)や、そのフィールドの直前に、+kubebuilder:... から始まるマーカー(1 つのマーカーは必ず 1 行のコメント)を書き、controller-gen というツールがそのマーカーを読んで CRD の YAML や RBAC(Role-Based Access Control: 誰が何を操作できるかを役割で決める仕組み)の YAML を自動生成する。人間は Go の型とマーカーだけを管理すればよく、型とスキーマが食い違う心配が減る。

実在するマーカーの例(確認済み: kubebuilder book のマーカー一覧と controller-tools v0.21.0 のソース pkg/crd/markers/): +kubebuilder:validation:Enum=small;large(size フィールドの直前に 1 行で書く、列挙の制約)、+kubebuilder:resource:path=widgets,shortName=wdg,scope=Namespaced(フィールドではなく、Widget 型の構造体定義そのものの直前に書く、names と scope を決めるマーカー)。検証・既定値・サブリソースのマーカーは第 06〜08 回で 1 つずつ実例とともに見る。

図: マーカーのコメントを controller-gen が読み、CRD の YAML を自動で組み立てる

まとめと次の回

CRD は group・names・scope・versions という住所と呼び名と持ち場を決め、構造的スキーマが型の形を固め、刈り込みが知らないフィールドを消し、additionalPrinterColumns が表示を増やす。ここまでは全部「保存のされ方と見え方」の話で、第 04 回で見たとおり、CRD だけでは誰も世界を動かさない。

次の第 06 回では、CRD のスキーマが持つ 2 種類の検証(OpenAPI の制約と CEL による検証)を、実際に拒否されたエラーメッセージとともに見ていく。

図: この回で決めた「保存のされ方」の上に、次回の検証が乗る

ロックと分離レベル ― 待たせるか、中止するか

並行実行の衝突は、ロックで待たせるか、分離レベルでコミット時にエラーを返すかのどちらかで解決される。どちらを選ぶかで、待ち時間とリトライの責任の持ち方が変わる

← SQL シリーズ目次へ

この回の前提: 第 35 回 MVCC と VACUUM (xmin/xmax、FOR KEY SHARE が FK 参照で使われること)

複数のトランザクションが同じ行や同じ表に同時に触るとき、PostgreSQL が取る手段は 2 種類あります。1 つはロックで待たせること、もう 1 つは分離レベルの保証に反する操作をコミット時にエラーで止めることです。この回では、PostgreSQL 18.6 の実機で 2 本の psql セッションを実際に動かし、行ロックの 4 つのモードの衝突、表レベルのロックの段階、ロック待ちの行列の正体、Read Committed の文ごとの再評価、Repeatable Read の直列化エラー、Serializable (SSI) による write skew の検出、デッドロックの自動検出、そして SKIP LOCKED とアドバイザリロックによる実務的な回避策を、実測のタイミングと実際のエラー文面で確認します。

1. この回で解く問題 ― 衝突を「待たせる」か「中止する」か

第 35 回で見た MVCC は、読み取りと書き込みが互いを待たないようにする仕組みでした。しかし書き込みと書き込みが同じ行に競合する場面では、誰かが待つか、誰かが諫められる必要があります。PostgreSQL はこれを 2 つの層で扱います。

ロックは「今すぐ衝突が起きないように、片方を待たせる」という層です。SELECT ... FOR UPDATE や通常の UPDATE は、対象の行に印をつけ、同じ行に触ろうとする他のトランザクションを待ち行列に入れます。分離レベルは「待たせてもなお防げない矛盾を、コミットの瞬間にエラーとして検出する」という層です。Repeatable Read や Serializable では、一度は処理が進んでも、コミット時に「この順序では成り立たない」と判定されればエラーが返ります。

この 2 つの層を正しく使い分けるには、どちらが「待つ」という代償を払い、どちらが「リトライする」という代償を払うのかを理解する必要があります。ロックは待ち時間を増やしますが処理は 1 回で済みます。分離レベルによるエラーはリトライが必要になりますが、ロックを持ち続ける時間は短く済みます。

図: 衝突への対処は「待たせる」ロックと「コミット時に中止する」分離レベルの 2 層に分かれる。

2. 仕組み ― 行ロックの 4 モードを実測で衝突させる

PostgreSQL の行ロックには FOR UPDATE、FOR NO KEY UPDATE、FOR SHARE、FOR KEY SHARE の 4 段階があります。第 35 回で見た「FK 参照が親行を FOR KEY SHARE でロックする」という挙動の意味が、ここでようやく繋がります。まず FOR UPDATE と FOR UPDATE を衝突させます。

-- セッション A: 6 秒間 FOR UPDATE を保持
BEGIN; SELECT bug_id FROM bugs WHERE bug_id=1 FOR UPDATE; SELECT pg_sleep(6); COMMIT;

-- セッション B: 1 秒後に同じ行へ FOR UPDATE
BEGIN;
SELECT clock_timestamp() AS b_start;              -- 09:59:54.073
SELECT bug_id FROM bugs WHERE bug_id=1 FOR UPDATE; -- ここで待たされる
SELECT clock_timestamp() AS b_acquired;            -- 09:59:59.028 (約 4.96 秒後)
COMMIT;

B は約 4.96 秒待たされました。これは A が 1 秒の時点でロックを取り、そこから 6 秒間保持したうちの残り約 5 秒にほぼ一致します。次に FOR SHARE と FOR SHARE を同じ行に対して試します。

-- セッション C: 4 秒間 FOR SHARE を保持 (B と同じ構造)
-- セッション D: 1 秒後に同じ行へ FOR SHARE
--  d_start:    10:00:02.232438
--  d_acquired: 10:00:02.233808   (約 1.4 ミリ秒)

D はほとんど待たされません。FOR SHARE は複数の読み手が同時に持てる読み取りロックで、互いに衝突しないからです。最後に、第 35 回で見た FK 参照の FOR KEY SHARE と、通常の列更新 (NO KEY UPDATE として扱われる) ・ FOR UPDATE の関係を確かめます。

-- A: FOR KEY SHARE を 3 秒保持 (FK 参照を模している)
-- B: 非キー列 (priority) を UPDATE する → NO KEY UPDATE として扱われる
--    start: 10:03:30.344242, done: 10:03:30.344756  (約 0.5 ミリ秒、ブロックされない)

-- 同じ状況で、こちらは FOR UPDATE を試す
--    start: 10:03:32.434944, done: 10:03:34.414582  (約 1.98 秒、ブロックされる)

非キー列への通常の UPDATE は内部的に NO KEY UPDATE という行ロックを取り、これは FOR KEY SHARE と衝突しません。だからこそ、FK 参照で親行が FOR KEY SHARE されている間も、その行の他の列を自由に更新できます。しかし FOR UPDATE は FOR KEY SHARE と衝突するため、約 2 秒 (A の残り保持時間) 待たされました。

FOR KEY SHAREFOR SHAREFOR NO KEY UPDATEFOR UPDATE
FOR KEY SHARE両立両立両立衝突
FOR SHARE両立両立衝突衝突
FOR NO KEY UPDATE両立衝突衝突衝突
FOR UPDATE衝突衝突衝突衝突

図: 4 つの行ロックは強さの順に並び、FK 参照に使われる KEY SHARE が最も弱く多くの操作と共存できる。

3. 仕組み ― 表レベルのロックも段階になっている

行ロックとは別に、どの文も実行時に表レベルのロックを取ります。これも強さの段階があり、pg_locks で実際に確認できます。

BEGIN; SELECT * FROM bugs LIMIT 1;
SELECT locktype, mode, granted FROM pg_locks WHERE pid=pg_backend_pid() AND relation='bugs'::regclass;
--  locktype |      mode       | granted
-- ----------+-----------------+---------
--  relation | AccessShareLock | t
ROLLBACK;

BEGIN; UPDATE bugs SET hours = hours WHERE bug_id = 1;
SELECT locktype, mode, granted FROM pg_locks WHERE pid=pg_backend_pid() AND relation='bugs'::regclass;
--  locktype |       mode       | granted
-- ----------+------------------+---------
--  relation | RowExclusiveLock | t
ROLLBACK;

BEGIN; CREATE INDEX tmp_idx_test ON bugs (summary);
SELECT locktype, mode, granted FROM pg_locks WHERE pid=pg_backend_pid() AND relation='bugs'::regclass;
--  locktype |   mode    | granted
-- ----------+-----------+---------
--  relation | ShareLock | t
ROLLBACK;

単純な SELECT は最も弱い AccessShareLock を取り、これは他のほぼ全ての操作と共存できます。通常の UPDATE は RowExclusiveLock を取り、これも他の DML とは共存できますが、ALTER TABLE のような構造変更とは衝突します。CREATE INDEX (非 CONCURRENTLY) は ShareLock を取り、この間はテーブルへの書き込みができなくなります。この強さの階段の頂点にあるのが ACCESS EXCLUSIVE で、ALTER TABLE の多くの操作や VACUUM FULL (第 35 回) が使います。表ロックの全段階と衝突表は、第 37 回で DDL のロック待ちを扱うときに詳しく見ます。

4. 仕組み ― ロック待ちの行列は「トランザクション ID 待ち」として実装されている

第 2 節の FOR UPDATE 対 FOR UPDATE の衝突の最中に、pg_locks を覗くと、待っている側 (session_B) が何を待っているのかが分かります。

SELECT a.application_name, l.locktype, l.mode, l.granted
FROM pg_locks l JOIN pg_stat_activity a ON a.pid=l.pid
WHERE a.application_name IN ('session_A','session_B')
  AND l.locktype IN ('transactionid','tuple')  -- relation の RowShareLock など共通の行は省いて絞る
ORDER BY a.application_name, l.locktype;

--  application_name |   locktype    |        mode          | granted
-- ------------------+---------------+----------------------+---------
--  session_A        | transactionid | ExclusiveLock        | t   ← A は自分の XID を排他的に保持
--  session_B        | transactionid | ShareLock            | f   ← B は A の XID への共有ロックを待っている
--  session_B        | tuple         | AccessExclusiveLock  | t

これは PostgreSQL の行ロックの実装上の特徴です。どのトランザクションも、自分の XID (トランザクション ID) に対する ExclusiveLock を、開始してから終了する (COMMIT/ROLLBACK) まで保持し続けます。ある行をロックしようとして、既に別のトランザクションがロックしていることが分かると、PostgreSQL は「その行をロックしているトランザクションの XID に対する ShareLock」を要求します。この要求は、相手のトランザクションが終了して XID の ExclusiveLock を解放するまで granted=f のまま待ちます。つまり「行の待ち行列」は、実装としては「相手のトランザクション ID が終わるのを待つ」という形で表現されています。

この仕組みはデッドロックの検出にも直結しています。第 7 節で見るデッドロックのエラーメッセージが waits for ShareLock on transaction ... という文面になっているのは、まさにこの XID 待ちの構造が表に出てきているためです。

図: 行ロックの待ちは、内部的には相手のトランザクション ID への ShareLock 要求として表現される。

5. 仕組み ― Read Committed は待った後に WHERE 句を再評価する

PostgreSQL の既定の分離レベルである Read Committed では、1 つの文が実行される中でブロックされて待たされた場合、再開した時点の最新のコミット済みデータに対して条件を再評価します。bug_id=4 (priority='HIGH') に対して、この再評価を実機で確かめます。

-- セッション B: 先に priority を 'LOW' に変更して 3 秒保持
BEGIN; UPDATE bugs SET priority='LOW' WHERE bug_id=4; SELECT pg_sleep(3); COMMIT;

-- セッション A: 1 秒後、まだ 'HIGH' だと思って同じ行を更新しようとする
BEGIN;
UPDATE bugs SET hours=5 WHERE bug_id=4 AND priority='HIGH'; -- B の行ロックで待たされる
SELECT bug_id, priority, hours FROM bugs WHERE bug_id=4;
COMMIT;

-- 実行結果
-- UPDATE 0                              ← 0 行が更新された
--  bug_id | priority | hours
-- --------+----------+-------
--       4 | LOW      |  8.00                ← hours は変わっていない

A の UPDATE 文は、B が行ロックを解放するまで待たされます。B が priority='LOW' にコミットした後、A の UPDATE は再開しますが、そこで WHERE 句 priority='HIGH' を最新のコミット済みの値で再評価します。もう priority は 'LOW' になっているため、この行はもう条件に一致せず、UPDATE 0 という結果になります。もし PostgreSQL が再評価をせず、A が待たされる前に確認した古い条件のまま書き込んでいたら、B の更新が消える「lost update (更新の消失)」が起きていたはずです。この再評価こそが、Read Committed のもとでも lost update を防いでいる仕組みです。

図: Read Committed は待たされた後、WHERE 句を最新のコミット済みデータで再評価してから書き込む。

6. どこで壊れるか ― Repeatable Read の直列化エラーと Serializable の write skew

Read Committed は文ごとに再評価することで衝突に対処しますが、Repeatable Read はトランザクション開始時点のスナップショットを最後まで保つため、再評価ができません。代わりに、コミット時に矛盾を検出してエラーにします。bug_id=2 の hours を 2 つの Repeatable Read トランザクションが更新する場面です。

-- B: 先に hours を +1 して 3 秒後に COMMIT
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT bug_id, hours FROM bugs WHERE bug_id=2;  -- hours=3.50 を読む
UPDATE bugs SET hours=hours+1 WHERE bug_id=2;
SELECT pg_sleep(3); COMMIT;

-- A: 1 秒後、同じスナップショット (hours=3.50) を見て +10 しようとする
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT bug_id, hours FROM bugs WHERE bug_id=2;  -- hours=3.50 (A のスナップショット)
UPDATE bugs SET hours=hours+10 WHERE bug_id=2;  -- B の行ロックで待たされた後...
COMMIT;

-- 実際のエラー文面 (VERBOSITY=verbose)
-- ERROR:  40001: could not serialize access due to concurrent update
-- LOCATION:  ExecUpdate, nodeModifyTable.c:2602

A は B の行ロックが解放されるまで待たされますが、Repeatable Read は自分のスナップショット (hours=3.50) を最後まで使い続けるため、Read Committed のように「最新の値で再評価する」ことができません。そこで PostgreSQL は、A のスナップショットより後に同じ行がコミットで変更されたことを検知し、SQLSTATE 40001 (serialization_failure) のエラーで A を止めます。A はロールバックされ、呼び出し側が最初からリトライする必要があります。

さらに深刻なのが write skew です。分散システムシリーズ第 18 回 分離レベルと並行制御 でも触れた「オンコール医師」の例を、PostgreSQL の実機で再現します。2 人の医師 (alice, bob) が両方 on-call (on_duty=true) の状態から始め、それぞれが「自分以外にも on-call がいるなら、自分は外れてよい」という規則で同時に外れようとします。

CREATE TABLE oncall (doctor text PRIMARY KEY, on_duty boolean NOT NULL);
INSERT INTO oncall VALUES ('alice', true), ('bob', true);

-- A と B が同時に SERIALIZABLE で実行
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM oncall WHERE on_duty;  -- 両方とも 2 を見る (まだ安全だと判断)
-- A: UPDATE oncall SET on_duty=false WHERE doctor='alice'; COMMIT;  → 成功
-- B: UPDATE oncall SET on_duty=false WHERE doctor='bob';   COMMIT;  → 失敗

-- B が実際に受け取ったエラー
-- ERROR:  40001: could not serialize access due to read/write dependencies among transactions
-- DETAIL:  Reason code: Canceled on identification as a pivot, during write.
-- HINT:  The transaction might succeed if retried.

SELECT * FROM oncall ORDER BY doctor;
--  doctor | on_duty
-- --------+---------
--  alice  | f
--  bob    | t          ← 不変条件 (最低 1 人は on-call) が保たれた

どちらの行も別々の行 (alice と bob) を更新しているため、行ロックだけでは衝突を検出できません。これが write skew です。Serializable (PostgreSQL では SSI, Serializable Snapshot Isolation という実装) は、述語ロック (predicate lock, 「どの行を読んだか」ではなく「どういう条件で読んだか」を記録するロックで、行をロックしないためブロックも起こさない) を使って、2 つのトランザクションの読み取りと書き込みの依存関係を追跡し、両方がコミットすると「1 本の順序で実行したことにできない」と判断して、どちらか一方 (この実行では B) を 40001 のエラーで中止しました。結果として alice=f, bob=t となり、「最低 1 人は on-call」という不変条件が保たれています。同じ実験を Repeatable Read で行うと、この検出は働かず、両方が成功して alice=f, bob=f という、誰も on-call でない状態になってしまいました。

図: 別々の行を更新する write skew を、SSI が読み書きの依存関係から検出して片方を中止する。

7. どこで壊れるか ― 2 つのトランザクションが互いを待つデッドロック

2 つのトランザクションが、2 つの行を逆の順序で更新しようとすると、どちらも相手の持つロックを待ち続け、永久に進めなくなります。これを実機で発生させます。

-- A: bug_id=1 → bug_id=2 の順でロックを取ろうとする
BEGIN; UPDATE bugs SET hours=1 WHERE bug_id=1; SELECT pg_sleep(2); UPDATE bugs SET hours=2 WHERE bug_id=2; COMMIT;

-- B: bug_id=2 → bug_id=1 の順でロックを取ろうとする (逆順)
BEGIN; UPDATE bugs SET hours=3 WHERE bug_id=2; SELECT pg_sleep(2); UPDATE bugs SET hours=4 WHERE bug_id=1; COMMIT;

-- 実際に発生したエラー (どちらか一方)
-- ERROR:  40P01: deadlock detected
-- DETAIL:  Process 3398 waits for ShareLock on transaction 5021; blocked by process 3399.
--          Process 3399 waits for ShareLock on transaction 5020; blocked by process 3398.
-- HINT:  See server log for query details.
-- LOCATION:  DeadLockReport, deadlock.c:1133

-- もう一方は正常に COMMIT する

A は bug_id=1 を先にロックしてから bug_id=2 を待ち、B は bug_id=2 を先にロックしてから bug_id=1 を待ちます。第 4 節で見た「XID への ShareLock 待ち」の構造がここで輪になり、A は B の XID を待ち、B は A の XID を待つという循環が生まれます。PostgreSQL は deadlock_timeout (既定 1 秒) ごとに待ち行列を検査し、この循環を検出すると、どちらか一方を SQLSTATE 40P01 (deadlock_detected) のエラーで強制的に中止します。中止された側はロールバックされ、もう一方はロックが外れて処理を続けられます。実務では、複数行を更新する処理の中で行をロックする順序をテーブル間 ・ 処理間で統一することが、デッドロックそのものを起こさないための基本的な対策になります。

図: A と B が逆順でロックを要求すると循環が生まれ、deadlock_timeout 後に検出されて片方が中止される。

8. シニアの書き方 ― ロック待ちを避ける設計とリトライすべき SQLSTATE

ジョブキューのように「複数のワーカーが同じテーブルから未処理の行を 1 件ずつ取る」場面では、単純な FOR UPDATE はワーカーを数珠つなぎに待たせてしまいます。ここで使うのが SKIP LOCKED です。

-- A: bug_id=1 の行を取って 3 秒間保持
BEGIN; SELECT bug_id FROM bugs ORDER BY bug_id FOR UPDATE SKIP LOCKED LIMIT 1; SELECT pg_sleep(3); COMMIT;
-- → bug_id=1 を取得

-- B: 1 秒後、同じ問い合わせを実行
BEGIN;
SELECT clock_timestamp() AS b_start;                                         -- 10:00:12.520655
SELECT bug_id FROM bugs ORDER BY bug_id FOR UPDATE SKIP LOCKED LIMIT 1;      -- bug_id=2 を取得
SELECT clock_timestamp() AS b_got_row;                                       -- 10:00:12.521338 (約 0.68 ミリ秒後)
COMMIT;

B は A がロックした bug_id=1 を待たず、ロックされていない次の行 bug_id=2 を 0.68 ミリ秒で取得しました。SKIP LOCKED はロック済みの行をスキップするため、ワーカーの数を増やしても互いを待たせずにキューを消化できます。順序を保証したい処理には使えませんが、ジョブキューのような「どれが先に処理されても構わない」場面では効果的です。

テーブルの行とは無関係に、アプリケーションが独自の単位でロックを取りたい場合には アドバイザリロック (advisory lock) を使います。バッチ処理の多重起動防止などによく使われます。

-- A: 整数 42 番のアドバイザリロックを取り、3 秒間保持
SELECT pg_try_advisory_lock(42) AS a_got_lock;   -- t
SELECT pg_sleep(3);
SELECT pg_advisory_unlock(42) AS a_released;      -- t

-- B: 1 秒後、同じ番号をロックしようとする (待たない版)
SELECT pg_try_advisory_lock(42) AS b_got_lock_while_a_holds;  -- f

pg_try_advisory_lock はロックが取れなければ即座に false を返し、待ちません。これにより「既に誰かが同じバッチを実行中なら、今回は何もせず終了する」という多重起動防止を、テーブルの行を汚さずに実現できます。待ってもよい場合は pg_advisory_lock を使います。

最後に、この回で見た 2 つのエラーの SQLSTATE をまとめます。40001 (serialization_failure, 第 6 節) と 40P01 (deadlock_detected, 第 7 節) は、どちらもトランザクション全体をロールバックするエラーで、アプリケーション側が同じ処理をもう一度やり直す (リトライする) ことを前提にした設計です。シニアの判断は、これらの SQLSTATE を補足して自動でリトライする層をアプリケーションに用意するか、あるいは Repeatable Read / Serializable を使う範囲を、本当に複数行の不変条件を守る必要がある処理だけに絞り、それ以外は Read Committed のままにしておくかのどちらかです。全てのトランザクションを Serializable にすると、リトライの実装が無い限りエラーが利用者に直接届いてしまいます。

図: SKIP LOCKED はテーブルの行の分配に、アドバイザリロックは行に紐付かない排他制御に使う。

この回の前提: 第 09 回 メッセージキューと Pub/Sub、第 17 回 障害検知とゴシップ、第 07 回 コンシステントハッシュ

1 件の書き込みを何人に、どの経路で届けるか。プッシュ (push, 書いた瞬間に配る) とプル (pull, 読まれた瞬間に集める) のどちらを選ぶかで、有名人のフォロワーが 100 万人いる「有名人問題 (celebrity problem)」の重さが変わる。チャットやプレゼンス表示も同じ軸で説明できる。

1. push、pull、ハイブリッド ― Twitter のタイムライン設計

Twitter のようなタイムライン (自分がフォローしている人の投稿を時系列に見る画面) を作る方法は大きく 2 つある。プッシュ型 (fan-out on write) は、誰かが投稿した瞬間にその人のフォロワー全員のタイムライン (受信箱) にコピーを書き込む。読み取りは自分の受信箱を見るだけで済み、高速。プル型 (fan-out on read) は、投稿はフォロー関係を気にせず 1 か所に保存し、タイムラインを開いた瞬間にフォローしている全員の投稿を集めてマージする。

プッシュ型には有名人問題がある。1,000 万人にフォローされているアカウントが投稿すると、1,000 万件の書き込みが一瞬で発生する。逆にプル型は、フォロー数が多い人ほどタイムラインを開くたびに多くの相手の投稿を集める必要があり、読み取りが重くなる。実務ではハイブリッドが定石で、フォロワー数が少ない通常のユーザーはプッシュ、フォロワー数が極端に多い有名人だけはプル (読み取り時に別経路でマージ) にする。

図: 有名人問題を避けるため、実運用はフォロワー数でプッシュ/プルを切り分けるハイブリッドに落ち着く。

2. WebSocket を張り続ける ― Slack のチャネル配信と再接続の嵐

チャットのようにリアルタイム性が要るサービスは、クライアントごとにWebSocket (双方向の持続的接続) を張り続ける。接続が切れたクライアントは再接続を試みるが、サーバ側の再起動やロードバランサの入れ替えなどで多数のクライアントが同時に切断されると、全員が一斉に再接続を試みて新規接続要求がサーバ群に押し寄せる再接続の嵐 (reconnection storm) が起きる。これを避けるため、再接続までの待ち時間に指数バックオフとジッタ (ランダムなばらつき) を入れ、クライアントごとに再接続のタイミングを散らすのが定石(第 10 回のリトライ設計と同じ発想)。

Slack のメッセージは、WebApp (API を受ける) → Admin Server (チャネル ID から担当の Channel Server を探す) → Channel Server (そのチャネルの履行済みの履歴を保持) という経路で送信され、Gateway Server (地域ごとに配置され WebSocket 接続を保持) と Envoy (サービスプロキシ) を経由して受信者に push される。チャネル数が膨大なため、Channel Server への割り当てにはコンシステントハッシュ (第 7 回) が使われる。1 台の Channel Server が落ちると、そのチャネルを張っていた WebSocket 接続全員が同時に切断され、再接続の嵐の種になる。

図: Slack のメッセージ経路。Channel Server の割当にコンシステントハッシュを使う。

3. オンライン表示 (presence) は配信そのものより鮮度管理が本体

「オンラインかどうか」の表示は、一見単純だが、WhatsApp のような 1 対 1/小グループと Discord のような大規模グループで必要な設計が変わる。小規模向けの素直な実装は、クライアントが一定間隔でハートビート (生存信号) を送り、それを Redis の Pub/Sub で直接関係者に配る方式。これは専用のメッセージストアを持たないシステムでも動く。

規模が大きくなると、全員に毎回配信するのはコストが高くなるため、変化があったときだけ配信する設計に寄っていく。具体的には、ハートビートを Redis に TTL (有効期限) つきで書き込み、TTL が切れて「消えた」ことを検知した時だけオンライン→オフラインへの変化を配信する。これにより、無変化の間は配信コストがかからない。逆にポーリング方式(クライアントが能動的に状態を問い合わせる)は、リアルタイム性を諦める代わりに配信の仕組みそのものを無くせるという選択肢にもなる。

図: 規模が増えるほど「毎回配信」から「変化だけ配信」への移行が合理的になる。

4. 順序と既読 ― タイムスタンプはどこで打つべきか

複数リージョンにまたがるグループチャットでは、クライアントの時計はずれているため、クライアント側のタイムスタンプで並べ替えると順序が乱れる。実務ではサーバ側でタイムスタンプを打ち、クライアントはそれに従って並べ替えるのが素直な対策になる。これは第 15 回で見る物理時計のずれの問題と同じ構造で、完全な解決(全順序の保証)には追加の合意機構が要るが、ユーザー体験としては「サーバ基準の順序」で十分なことが多い。

既読 (read receipt) は、メッセージ本体とは別の「誰がどこまで読んだか」という状態を持つ。配信と既読を同じ経路に乗せると、既読の更新頻度(読むたびに発生)がメッセージ配信の負荷に上乗せされるため、既読は別のテーブル・別の配信経路に分離して、まとめて (バッチで) 反映する設計が一般的。

5. Reddit がフォロー型ファンアウトを採らない理由

Reddit の投稿一覧 (TOP/NEW/HOT) は Twitter のフォロー型タイムラインとは違う配信方式を採る。Twitter はフォロー関係に沿って「新しい投稿が時系列の先頭に追加される」だけだが、Reddit の HOT や TOP の順位はスコア (投票数と時間経過の関数) によって頻繁に順位が入れ替わる。プッシュ型ファンアウトは「誰かの受信箱に一度書いたら基本そのまま読まれる」ことを前提にした最適化であり、頻繁に並び順が変わるランキングには向かない。Reddit はこの性質と、人気サブレディットに投稿が集中する「ホットパーティション」問題を踏まえ、フォロー型ファンアウトではなく投稿そのものの集計・ランキングを中心に据えた設計を採る。

6. 実システムの規模: Netflix のプッシュ通知

Netflix は 2 億 2,000 万人のユーザーに、iOS、Android、スマート TV、Roku、Amazon Fire Stick、Web ブラウザなど多種多様なクライアントへ通知を送る。設計は、時計・ユーザー操作・内部システムから発生したイベントをイベント管理エンジンが受け取り、優先度に基づいて複数のキューに振り分け、優先度別の処理クラスタが通知データを生成して Cassandra に保存し、最後に Android は FCM、Apple は APNs、Web、TV、その他デバイスは Netflix 独自の "Zuul Push" という送信先ごとに異なる外部ゲートウェイへ渡す、という流れになっている。優先度でキューを分けておくことで、重要度の低い通知が重要な通知の配信を遅らせない設計になっている。

図: Netflix は優先度別のキューで重要な通知を低優先度の通知から守る。

7. どこで壊れるか・何を諦めるか

  • 有名人問題: プッシュ型のまま対応すると書き込みが爆発する。フォロワー数の閾値でプル型に切り替えるハイブリッド化が必要。
  • 再接続の嵐: 1 台の Channel Server/Gateway Server 障害が、張られていた WebSocket 全員の同時切断を生む。指数バックオフとジッタが無いと復旧直後のサーバに再接続が集中し、二次障害を招く。
  • プレゼンスの鮮度と配信コストの両立: 毎回配信は鮮度は高いがコストが高く、ポーリングはコストは低いが鮮度が落ちる。TTL + 変化時配信は中間点だが、TTL の長さがそのまま「オフライン判定までの遅れ」になる。
  • クライアント時計への依存: クライアントのタイムスタンプで順序付けすると、時計のずれでメッセージの前後関係が乱れる。サーバ側タイムスタンプを基準にする必要がある。

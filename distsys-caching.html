キャッシュ戦略 ― 速さと整合性の引き換えをどう設計するか

キャッシュは読み取りを速くする代わりに「本当の値 (DB)」と「写しの値 (キャッシュ)」という 2 つの真実を生み、そのズレをどう扱うかが設計の本体になる

この回の前提: 第 03 回 スケーリングとロードバランサ

DB への問い合わせは、メモリ上の読み取りに比べて桁違いに時間がかかります。同じ値を何度も読むなら、一度読んだ結果を手近な速いストレージに置いておき、次回はそこから返せば済みます。これがキャッシュの基本的な発想です。しかしキャッシュを置いた瞬間、システムには「本当の値を持つ DB」と「その写しを持つキャッシュ」という 2 つの場所が生まれ、両者がズレたときにどう振る舞うかという新しい設計判断が発生します。この回では、キャッシュと DB をどう同期させるか、古いデータをどう追い出すか、そしてキャッシュ特有の障害パターンにどう備えるかを、OTP (使い捨てパスワード) 認証と気象センサーの実例で確認します。

1. なぜキャッシュが要るのか ― 速い記憶を DB の前に置く

DB (ディスクを使う永続的なデータストア) への問い合わせは、ネットワークのやり取りとディスクの読み取りを含むため、メモリ上だけで完結する読み取りに比べて桁違いに遅くなります。同じキーに対する読み取りが何度も繰り返されるなら、1 回目の結果をメモリ上の速いストア (Redis のような分散キャッシュや、アプリケーションサーバ自身のメモリ) に置いておき、2 回目以降はそこから返せば、DB への問い合わせ自体を減らせます。

キャッシュが向くのは、読み取りが書き込みより圧倒的に多い、かつデータの更新頻度が低い場面です。更新が頻繁なデータをキャッシュすると、キャッシュと DB のズレ (古いデータを読んでしまう) が起きやすく、同期の手間の方が利益を上回ることがあります。

具体例として、ログイン時に送られるOTP (使い捨てパスワード, one-time password) の検証を考えます。ユーザが入力した OTP が正しいかどうかは、発行から 1 分程度のごく短い期間だけ有効であればよく、恒久的に DB へ保存する必要はありません。そこで OTP とその有効期限、認証に関わる情報 (操作内容など) をキャッシュだけに TTL (time-to-live, 生存時間) 付きで保存する設計が使われます。例えばキャッシュ 1 台に 16 GB のメモリがあり、TTL を 300 秒、1 件あたりのデータサイズを 500 バイトとすると、TTL の間に保持できる最大件数は次のように見積もれます。

$$ \text{保持件数} = \frac{16 \times 10^9 \text{バイト}}{500 \text{バイト}} \approx 3.2 \times 10^7 \text{件} $$

TTL 300 秒の間にこの件数まで新規発行を受け止められるので、1 秒あたりに処理できる発行数の目安は $3.2 \times 10^7 \div 300 \approx 10$ 万件 / 秒となります。この計算はキャッシュ 1 台分のメモリ上限から負荷の上限を逆算する、容量設計の基本的な考え方です。

図: キャッシュに値があれば DB へ行かずに済み、読み取りの大半をメモリ上で処理できる。

2. 読み書きの同期方式 ― cache-aside ・ read-through ・ write-through ・ write-back ・ write-around

キャッシュと DB という 2 つの場所をどう同期させるかには、いくつかの決まった形があります。読み取り側では 2 通りです。cache-aside はアプリケーションが自分でキャッシュを確認し、無ければ DB から読んでキャッシュに書き込む方式で、最も広く使われます。read-through はキャッシュ自身が DB への読み取りを代行し、アプリケーションからはキャッシュだけを見ているように振る舞う方式です。

書き込み側は 3 通りです。write-through はキャッシュと DB の両方へ同時に書き込み、常にキャッシュを最新に保ちますが、書き込みのたびに両方への反映を待つ分遅くなります。write-back (write-behind) はまずキャッシュだけに書き込んで応答を返し、DB への反映は後でまとめて行う方式で、書き込みは速くなりますが、キャッシュが落ちると未反映のデータを失う危険があります。write-around は DB にだけ書き込み、キャッシュには触れない方式で、cache-aside と組み合わせて「書き込み時はキャッシュを汚さず、次に読まれたときに最新値がキャッシュに載る」という形で使われることが多くあります。

OTP の例では、発行時に DB を経由せずキャッシュへ直接書き込みます (TTL 付きの書き込みなので write-through や write-around という分類にはやや馴染みませんが、発想としては「キャッシュがそのまま正とみなせる短命データ」を扱う cache-aside の一種です)。次のコードは、より一般的な cache-aside の読み取りパターンを、TTL 付きの辞書ベースの簡易キャッシュで示したものです。

import time

class Cache:
    def __init__(self):
        self.store = {}

    def get(self, key):
        entry = self.store.get(key)
        if entry is None:
            return None
        value, expires_at = entry
        if time.time() > expires_at:
            del self.store[key]
            return None
        return value

    def set(self, key, value, ttl):
        self.store[key] = (value, time.time() + ttl)

def get_user(user_id, cache, db):
    value = cache.get(user_id)
    if value is not None:
        return value
    value = db[user_id]
    cache.set(user_id, value, ttl=300)
    return value

cache = Cache()
db = {'u1': 'Alice'}
print(get_user('u1', cache, db))
print(get_user('u1', cache, db))

1 回目の呼び出しではキャッシュが空なので DB から読み、300 秒の TTL でキャッシュに書き込みます。2 回目の呼び出しではキャッシュに値が残っているため、DB には一切アクセスしません。これが cache-aside の最小の形です。

図: 読み取りは cache-aside、書き込みは write-through / write-back / write-around から選ぶ。

3. 追い出し方式 ― 満杯になったら何を消すか

キャッシュのメモリには限りがあるため、新しいデータを入れる余地が無くなったら何かを消す必要があります。この「何を消すか」を決めるのが追い出し (eviction) アルゴリズムです。最も広く使われるLRU (Least Recently Used) は、最後に使われたのが一番古いデータから消します。直近使われたデータは再び使われやすいという経験則に基づいています。LFU (Least Frequently Used) は、アクセス回数そのものが少ないデータから消すため、たまに読まれるだけの古いデータでも頻繁に読まれていれば残ります。FIFO (First In First Out) はアクセス頻度を一切見ず、入れた順番が古いものから単純に消す、最も実装が軽い方式です。TTL は厳密には追い出しアルゴリズムではありませんが、各データに生存時間を設定し、期限が切れたら自動的に無効にする点で同じ役割を果たします。

OTP の例では TTL が中心的な役割を果たします。OTP そのものの有効期限は発行から 1 分程度と短く設定し、キャッシュのエントリ自体の TTL はそれより長い 5 分程度に設定することで、期限切れの OTP がキャッシュ上に残っていても検証時に「期限切れ」として弾けるようにします。また、同じ OTP に対して間違った入力が繰り返された場合に備え、エントリの中に失敗回数のカウンタを持たせ、一定回数を超えたら正しい OTP が入力されても認証を成立させない、という設計も組み合わせます。

図: LRU は最後に使われた時刻の古いデータを追い出し枠の先頭に置く。

4. キャッシュ特有の故障モード ― どこで壊れるか

キャッシュを挟むことで新しく生まれる障害パターンが 4 つあります。1 つ目はサンダリングハード (thundering herd) で、多数のキーが同じ瞬間に期限切れになり、そのすべてのリクエストが一度に DB へ直撃して DB を過負荷にする現象です。対策は、キーごとの TTL にランダムな揺らぎ (ジッタ) を加えて期限切れの瞬間を分散させることです。

2 つ目はキャッシュ貫通 (cache penetration, cache miss attack) で、そもそも DB にも存在しないキーへの問い合わせが繰り返されるケースです。キャッシュにも DB にも値が無いため、毎回 DB まで問い合わせが素通りしてしまいます。悪意のあるユーザがこの性質を悪用し、存在しないキーを大量に問い合わせることで DB に負荷をかける攻撃にもなり得ます。対策は 2 つあり、存在しないことが分かったキーに対して「無い」という結果自体を短い TTL でキャッシュする方法と、ブルームフィルタ (Bloom filter) という確率的なデータ構造を使って「そもそも存在しない可能性が高いキー」を DB へ問い合わせる前にふるい落とす方法です。

3 つ目はキャッシュブレークダウン (cache breakdown) で、全体のアクセスの大部分を占める 1 つのホットキー (hot key) がちょうど期限切れになった瞬間、そのキーへの大量のリクエストが一斉に DB へ向かう現象です。サンダリングハードの特殊ケースともいえ、対策としてはアクセスが極端に集中するキーには TTL を設定しない (期限切れという概念自体を無くす) という割り切りがよく使われます。4 つ目はキャッシュクラッシュ (cache crash) で、キャッシュ自体が落ちて全リクエストが DB に向かう現象です。サーキットブレーカー (一定数の失敗が続いたらキャッシュへのアクセス自体を一時的に諦める仕組み) やキャッシュのクラスタ化 (複数台構成で一部が落ちても全滅しない構成) で備えます。

図: サンダリングハードとキャッシュ貫通は、どちらもキャッシュを素通りして DB に負荷を集中させる。

5. 実システムでの例 ― OTP 認証と気象センサーのダッシュボード

OTP 認証の設計をもう一度まとめます。ユーザ名をキーに、OTP の値、発行時刻、紐づく操作の内容をまとめてキャッシュに保存し、エントリ全体の TTL を 5 分、OTP そのものの有効期限を 1 分とします。失敗回数のカウンタを同じエントリに持たせ、閾値を超えたら以後の入力を無条件に拒否します。この設計には明確な割り切りがあります。キャッシュが落ちた場合のフォールバックは「OTP を再発行してもらう」だけで、キャッシュの内容を他の場所から復元する仕組みは持ちません。つまりこの OTP ストアは意図的に耐障害性を持たせていません。短命で再発行が容易なデータだからこそ、この割り切りが成立します。

対照的な例が、多数の気象センサーからの温度データをもとに作る州全体のヒートマップ (気温分布を色で示した画像) です。センサー 1 つが画像の 1 ピクセルに対応するとすると、画像全体のサイズはセンサーの台数で決まる固定サイズになり、更新頻度もセンサーの送信間隔で決まる既知のペースになります。この「サイズが固定」「読み取りが大半」「更新頻度が緩やか」という性質は、まさに最初の節で述べたキャッシュが向く条件そのものです。そこで、最新のヒートマップ画像そのものをメモリ上 (ElastiCache のような分散キャッシュ) に丸ごと保持しておき、閲覧リクエストが来るたびに DB やオブジェクトストレージへ行かずにメモリから直接返す、という設計が使えます。センサーからの新しい値が届いたときだけ、該当するピクセルを更新してキャッシュ上の画像を書き換えます。

この 2 つの例は対照的な設計判断を示しています。OTP は「短命でキャッシュが正そのものであり、失っても再発行すればよい」という前提のもとキャッシュだけで完結させています。ヒートマップは「生成コストの高い派生データを、更新が来たときだけ書き換えながらメモリ上に保持する」という前提のもと、キャッシュを事実上の読み取り専用ストアとして使っています。どちらも「読み取りが多く、更新頻度が緩やか」という条件を満たしているからこそキャッシュが機能しており、更新が頻繁で読み取りと競合するような用途には同じ設計は持ち込めません。

観点OTP 認証気象ヒートマップ
データの寿命数十秒 ・ TTL で消える常に最新版 1 つを保持
キャッシュが落ちたら再発行してもらう (割り切り)センサーの最新値から再構築する
正とする場所キャッシュ自体が正センサー群のデータが正、画像はその派生物

キャッシュを入れるかどうかを決める判断は、結局この回で見てきた観点に戻ってきます。読み取りが書き込みより多いか、更新頻度は緩やかか、キャッシュを失ったときに許容できる代償は何か。この 3 つに答えられないままキャッシュを足すと、ヒット率やレイテンシといった指標を測る前に、サンダリングハードやキャッシュ貫通のような壊れ方の方を先に引き起こすことになります。

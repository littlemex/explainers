第 17 回 設計

← カスタムコントローラー自作 シリーズ目次へ

第 16 回で題材を「既存の FSx を namespace ごとに配る」に決め、読み取り専用の実現方法と Released の直し方を実機で確かめた。第 17 回は、それを API とコントローラーに落とす。何を CR にするか、生成する PV と PVC をどんな形にするか、どの条件で配り、どの条件で取り上げるか、3 つのコントローラーにどう責任を分けるかを決める。設計は Fable 5.2(Anthropic の AI モデル)との 5 往復のレビューで大きく変わったので、その変化も載せる。

結論から。CR は 2 種類。管理者が作る SharedFilesystem(どのファイルシステムを、どの namespace に、どの強さで配るか)と、利用者が作る SharedFilesystemClaim(使いたい)だ。守る約束は 1 つだけ。「許可が消えて猶予の 30 秒を過ぎたら、その namespace では新しいマウントができなくなる」。最初の設計は「拒否したら即削除」で、一瞬のラベル外れでそのチームの PVC が、元の PV が一瞬読めないだけで全チームの PVC が消える形だった。

1. CR を 2 種類に分ける理由

CR の数と形は「誰が書くか」で決まる。ファイルシステムを配ってよいかを決めるのは管理者で、使いたいと言うのは各チームだ。この 2 つを 1 つの CR に混ぜると、チームに「配ってよい先」まで書ける権限を渡すことになる。そこで 2 種類に分け、RBAC(誰がどの API を呼べるかの設定)で書き手を分ける。

CR置き場所(scope)書く人spec に書くこと
SharedFilesystemクラスタ全体管理者元になる静的 PV の名前(persistentVolumeRef、後から変更不可)と、許可の一覧 grants(namespace の選び方と、読み取り専用か読み書きか)
SharedFilesystemClaimnamespace利用者使いたい SharedFilesystem の名前と、欲しいアクセス(既定は ReadOnly)。spec 全体が変更不可で、変えたいときは作り直す
apiVersion: sharedfs.littlemex.github.io/v1alpha1
kind: SharedFilesystem
metadata: {name: training-data}
spec:
  persistentVolumeRef: {name: fsx-training}
  grants:
  - namespaceSelector: {matchLabels: {team: research}}
    access: ReadWrite

利用者は PV を一切触らない。Claim を作ると、コントローラーが Claim と同じ名前の PVC をその namespace に作るので、Pod はその PVC をマウントするだけだ。Claim の spec を丸ごと変更不可にしたのは、変更を許すと「マウント中の PV を作り直す」という難しい手順が要るからで(PV のボリュームの指定は作成後に変えられない)、作り直しで済むなら API から消すほうが単純で安全だ。変更不可は CEL の self == oldSelf(第 06 回)で書ける。

図: 書き手ごとに CR を分けると、権限の境界がそのまま RBAC になる。

「読み取り専用で配る先」と「読み書きで配る先」を分けたい場合、最初の設計では同じ PV を指す SharedFilesystem を 2 つ作る運用だった。レビューで「それでは名前がファイルシステムでなく許可の名前になっている」と指摘され、1 つの SharedFilesystem に許可の一覧(grants)を持たせる形に変えた。複数の許可に当てはまる namespace は、その中で一番強いアクセスを得る。

2. 生成する PV と PVC の形

Claim 1 つにつき、PV を 1 本と PVC を 1 つ作る。どの項目も「何を防ぐためにそうするか」が決まっている。

項目決めた値防ぐこと
PV の名前sfc-<Claim の UID>namespace と名前をつなげると、namespace a-b の Claim c と、namespace a の Claim b-c がどちらも a-b-c になる。UID(一意な番号)なら重ならず、名前から Claim を逆にたどれる
volumeHandle元の値 + -sfc- + Claim の UID同じ handle の PV が同じノードで取り違えられる。ドライバはマウントに handle を使わず volumeAttributes の接続先を使うことをソースで確認済み
claimRefnamespace と名前だけ別の namespace に横取りされる。uid は書かず、PV コントローラー(kube-controller-manager の中で PV と PVC を結ぶ役)に任せる
回収方針必ず RetainPVC が消えたときに、ドライバへファイルシステムの削除が頼まれうる
accessModes / マウントオプションReadWriteMany、読み取り専用なら ro を足す両ドライバが ReadOnlyMany を拒否する(第 16 回の実測)
PVC の storageClassName空文字 ""(未設定ではない)既定の StorageClass があるクラスタでは、未設定の PVC にその名前が入り、"" の PV と食い違って結び付かない(公式ドキュメントの規則。検証したクラスタには既定が無く、未設定でも結び付いた)
PVC の容量の申し込み1Gi と元の容量の小さい方4800Gi をそのまま申し込むと、namespace の容量の上限(ResourceQuota)に引っかかる

作る順番にも理由がある。まず同じ名前の PVC が既に無いか(あれば他人のものか)を確かめ、空いていれば PV を作り、最後に PVC を作る。名前が他人に取られているなら PV を予約しない。そして PV を先に作っておくと、PVC ができた最初の瞬間に PV コントローラーが予約済みの PV を見つけて結ぶ(bind する)。逆の順番だと、PV が後から現れても PVC 側は次の定期的な見直しまで待たされる。そこで PV を初めて作ったときは、PV コントローラーの手元に PV が届くよう 1 秒おいてから PVC を作る。最初の実装は逆で、これが Claim を作ってから使えるまでの時間を延ばしていた(第 18 回)。

PV と PVC で書き方も変えた。PV は Server-Side Apply(第 11 回)で書く。claimRef は SSA で項目ごとに持ち主を分けられる作りになっていて(ソースに +structType=granular とある)、namespace と名前はこのコントローラー、uid は PV コントローラーと、二者が互いの書いた値を消さずに同じ項目を共有できる。PVC はspec を作成時に決め、二度と書き換えない。後から書くのは、外された ownerReference の付け直しと、結び付き先を失った(Lost の)PVC の作り直しだけだ。SSA や CreateOrUpdate で書くと、同じ名前で他人が作った PVC を黙って自分のものにしてしまうからだ。

図: 同じ claimRef の中で、項目ごとに持ち主が違う。SSA だからこそ二者が消し合わない。

「この PVC は自分のものか」の判定にも落とし穴があった。最初は ownerReference(親子関係の印)で判定する設計だったが、ownerReference は PVC の持ち主であるテナントが自由に消せる。消されると「自分の PVC ではない」と誤認し、許可を取り上げたいときに消すべき PVC を見失う。そこで判定は PVC の spec.volumeName が sfc-<Claim の UID> を指しているかにした。Kubernetes のソースのコメントにも「PV と PVC の結び付きを決めるのは claim.VolumeName」とあり、テナントがこれを他の PV に向けても、その PV は予約が合わないので何も得られない。

3. 配る条件と、取り上げる条件

コントローラーが守る約束は 1 つにした。SharedFilesystem が無くなるか、その namespace への許可(またはその強さの許可)が無くなって猶予を過ぎたら、新しいマウントはできなくなる。この約束を守るには、許可が無くなったときに PVC を消す必要がある。ただし「拒否」にはいろいろな理由があり、全部で PVC を消すと危ない。元の PV が一瞬読めないだけで、全チームの PVC が消えてしまうからだ。そこで拒否の理由を 2 種類に分けた。

種類理由(Accepted 条件の reason)既にある PVC と PV
許可が無いNamespaceNotGranted(どの許可にも選ばれない)、AccessNotGranted(読み書きを頼んだが読み取り専用しか許されていない)、FilesystemNotFound(SharedFilesystem が無い)猶予の後に取り上げる
許可とは別の理由FilesystemDeleting、SourceNotFound、UnsupportedDriver、InvalidGrant などそのまま残す

SharedFilesystem が削除中(FilesystemDeleting)でも PVC を残すのは、管理者が誤って削除した場合に、使っているチームを巻き込まないためだ。SharedFilesystem の finalizer は、生成した PV が全部消えるまで本当の削除を待つ。管理者が本当に取り上げたいときは、許可を外せばよい。

許可の判定は、削除中かどうかや元の PV の検査よりも先に行う(ただし許可の書き方そのものが壊れている場合は、壊れていると報告するだけで取り上げない)。最初の設計では「SharedFilesystem が削除中か」を先に見ていたので、管理者が削除中の SharedFilesystem から許可を外しても取り上げが効かなかった。順番を入れ替えるだけで直る穴だった。

取り上げにはさらに 2 つの安全装置を付けた。1 つは猶予期間(既定 30 秒)だ。GitOps(Git の中身にクラスタを合わせる運用)の同期中にラベルが一瞬外れても、30 秒以内に戻れば何も消さない。取り上げの対象になった瞬間に、その期限(今の時刻 + 猶予)を Claim の status の withdrawAfter に書く。最初は「Accepted 条件が False になった時刻」から数えていたが、別の理由で既に False だった Claim ではその時刻が古く、ラベルが外れた瞬間に猶予ゼロで消える経路があると 4 回目のレビューで分かった。もう 1 つは消す直前の読み直しで、キャッシュ(第 09 回)ではなく API サーバーから namespace と SharedFilesystem を直接読み、まだ許可が無いと確かめてから消す。

図: 取り上げは即時ではない。猶予と読み直しの後に PVC を消し、Pod が止まって初めて PV まで消える。

取り上げても、動いている Pod は止まらない。 PVC を消しても、Kubernetes の pvc-protection(使用中の PVC を守る仕組み)が、その PVC を使う Pod が止まるまで本当の削除を待たせる。新しい Pod は起動できなくなるが、既に動いている Pod は書き続けられる。この限界は README に明記し、Claim の Ready 条件のメッセージに「まだマウントしている Pod の名前」を出すようにした。今すぐ止める必要があるなら、管理者が Pod を退去させる。

4. 3 つのコントローラーの責任分担

1 つのプログラム(manager、第 15 回)の中で、3 つのコントローラーを動かす。分け方の基準は「何をキーに動くか」と「何を書くか」だ。各コントローラーは自分の担当の status だけを書き、他人の status は書かない。

コントローラーキー書くもの責任
SharedFilesystemSharedFilesystem自分の status と finalizer元の PV が配れる状態かを表示する。自分を指す生成 PV が 1 本でも残っている間は、削除を待たせる
SharedFilesystemClaimClaimPV(SSA)、PVC(作成のみ)、Claim の status と finalizer許可を判定し、PV と PVC を作り、Released を直し、許可が消えたら取り上げ、削除時に片付ける
Orphan(孤児の回収)生成された PVPVC と PV の削除持ち主の Claim がもう無い PV を片付ける。起動時に全 PV を一度見直す

3 つめが必要な理由は、Claim の finalizer が働かない場合があるからだ。誰かが finalizer を手で外して Claim を消した、バックアップから Claim を戻したら UID が変わった、といった場合、PV は予約(namespace と名前)を持ったまま残る。後で同じ名前の namespace が作られると、許可されていないのにその PV を使えてしまう。PV をキーに動くコントローラーなら、Claim が無いことに気付いて片付けられる。PV の名前に Claim の UID が入っているので、PV を見るだけで「持ち主は誰だったか」が分かる。

Claim のコントローラーが元の PV の中身を、SharedFilesystem の status 経由ではなく元の PV から直接読むようにしたのも、レビューで変えた点だ。status を経由すると、2 つのコントローラーの間に「どの時点の status なら信じてよいか」という約束が必要になり、片方が更新を書く前にもう片方が古い値を読む、という食い違いの種になる。

図: 行の変化が、丸の付いた列のコントローラーを起こす(第 09 回の Watches)。PVC は ownerReference ではなく名前で Claim に結ぶので、他人の PVC が消えたときも Claim が気付ける。

5. 設計判断と、比べた案

第 01〜15 回で学んだ道具の中から、何を使い、何を使わなかったかを表にする。使わなかったものにも理由がある。

決めたこと比べた案理由
admission webhook は作らない許可の判定を validating webhook で行う1 つの CR だけで決まる規則(enum、既定値、変更不可)は CRD のスキーマと CEL で書ける(第 06・07 回)。許可は namespace のラベルや SharedFilesystem という他のオブジェクトに依存し、作った後にも変わる。webhook は Claim への書き込み(作成や更新)が来たときにしか呼ばれず、namespace のラベルが後から変わっても呼ばれないので、その変化に追いつけない。だから reconcile で毎回判定し、結果を condition に出す
ValidatingAdmissionPolicy も入れないテナントが PV を直接作るのを VAP で禁止するPV を書けるのは元々クラスタ管理者だけで、RBAC で足りる。雑な VAP は PV の bind を行う kube-controller-manager まで締め出しうる
許可のセレクタは空を禁止する(CEL)空のセレクタは「全 namespace」と読む打ち間違いで項目が消えると、意図せず全 namespace に開く。全 namespace に配りたいときは、明示的な書き方を求める
status は差分だけ送る(merge patch)全体を Update するfinalizer の付け外しと status の書き込みが、楽観的排他(第 11 回)で何度もぶつかっていた。resourceVersion を付けない差分(merge patch)は衝突を検出しない代わりに後から書いた方が勝つ。status を書くのはこのコントローラーだけなので、それで安全になる
ドライバの対応表はコードに置く設定ファイルで足せるようにする表の 1 行は「このドライバのマウントは volumeHandle に依存しない」という安全性の主張で、ソースと実機で確かめたもの。設定で EFS(handle からマウントするドライバ)を足されると、黙って壊れる
バージョンは v1alpha1 だけ最初から複数版と変換 webhook を用意する変えるべき点がまだ実際の利用で出ていない。第 14 回の通り、版を足すのは形を変える必要が出てからでよい

図: webhook を使わなかったのは、この題材の規則がどれも webhook 以外の置き場所に収まったから。

6. レビューで変わったこと

設計と実装は、Fable 5.2 に 5 回見せた。1 回目は題材選び、2 回目は実装前の設計書、3 回目は実装後に「敵対的(壊す手順を探す)」「責任の分け方」「本質と名前」の 3 つの観点で別々に、4 回目と 5 回目は直した後の確認だ。最初の設計から、少なくとも次の 7 点が変わった。どれも「動くが、ある手順を踏むと約束が破れる」種類の欠陥で、テストや実機で落ちたものではなく、コードを読むレビューで見つかった。

最初の設計どう破れるか今の設計
拒否したら PVC と PV を即削除元の PV が一瞬読めないだけで、全チームの PVC が消える許可が無い 3 つの理由だけで、猶予と読み直しの後に取り上げる
PVC の所有を ownerReference で判定テナントが ownerReference を消すと、取り上げるべき PVC を見失うspec.volumeName で判定する
削除中かどうかを許可より先に判定削除中の SharedFilesystem から許可を外しても、取り上げが効かない許可を最初に判定する
SharedFilesystem が消えたら何もしないfinalizer を手で外すと、許可元の無い PV が残り続けるFilesystemNotFound も取り上げの理由にする
猶予の起点が condition の時刻別の理由で既に拒否されていた Claim は猶予ゼロになるstatus の withdrawAfter で起点を持つ

テストの欠陥も 1 つ見つかった。envtest(第 15 回)でも、使用中の PVC と PV を守る保護用の finalizer は API サーバーが付ける。ところがそれを外す役(kube-controller-manager)が居ないので、そのままでは削除が終わらない。そこでテストが代わりに外す補助関数を書いていたが、それがこのコントローラー自身の finalizer まで外していた。そのため 3 つのテストが、コントローラーが何もしなくても通る状態になっていた。外すのを Kubernetes の保護用の finalizer だけに絞り、削除の順番は「Pod が使っている」状態を別の finalizer で真似して確かめるように直した。

図: 一番大きく変わったのは取り上げの判断。消す操作は元に戻せないので、条件を絞り、待ち、確かめてから行う。

まとめと次の回

CR は書き手ごとに 2 種類に分け、生成する PV と PVC の各項目は「何を防ぐか」から決めた。守る約束は「許可が消えて猶予を過ぎたら、新しいマウントはできない」の 1 つで、取り上げは許可が無い理由に絞り、猶予と読み直しの後に行う。動いている Pod は止めないという限界は隠さずに書く。webhook を使わなかったのは、この題材の規則が全部スキーマ・reconcile・RBAC に収まったからだ。第 18 回では、この設計を実装し、本物の FSx で 39 項目を確かめた結果を見る。

図: 第 18 回は、この 3 つがコードのどこにあるかをたどる。

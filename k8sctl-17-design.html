K8S CUSTOM CONTROLLER ・ 第 17 回

第 17 回 設計

パスごとに配る FilesystemShare、いつもの PVC で申し込む、取り上げの猶予、重なりの検査、4 つのコントローラー

← カスタムコントローラー自作 シリーズ目次へ

第 16 回で題材を「既存の FSx を namespace ごとに配る」に決め、読み取り専用の実現方法とディレクトリだけのマウントを実機で確かめた。第 17 回は、それを API とコントローラーに落とす。何を CR にするか、利用者は何を書くか、生成する PV をどんな形にするか、どの条件で配り、どの条件で取り上げるか、4 つのコントローラーにどう責任を分けるかを決める。

結論から。管理者が書くのは FilesystemShare(どのファイルシステムの、どのパスを、どの namespace に、どの強さで)だけで、利用者は新しい CR を覚えず、いつもの PVC を書く。コントローラーは share ごとに <名前>-rw と <名前>-ro の 2 つの StorageClass を作り、その申し込みを受け付ける係(外部プロビジョナー)になる。最初の形は「ファイルシステムを丸ごと、専用の Claim という CR で配る」だったが、学習や推論の実際の使い方(チームごとのディレクトリ、Helm や StatefulSet)に合わなかった。

1. 最初の形と、作り直した理由

最初に作った形(v1)は、CR を 2 種類に分けていた。管理者が書く SharedFilesystem(配ってよい先)と、利用者が namespace に書く SharedFilesystemClaim(使いたい)だ。Claim を作ると、コントローラーがファイルシステム全体を指す PV と PVC を作る。本物の FSx で一通り動いたが、LLM(大規模言語モデル)の学習と推論で 1 つのファイルシステムを分け合う実際の使い方と並べると、2 つの点で合わなかった。

使い方要るもの丸ごと配る形では
学習データ1 つの木(ディレクトリの集まり)を、多くのチームに読み取り専用でできる
推論用のモデルの重み1 つの木を、多くの推論用 namespace に読み取り専用でできる
チェックポイント(学習の途中結果)チームごとのディレクトリを、そのチームだけ読み書き読み書きを許すと、ファイルシステム全体を書き換えられる
Helm チャート、StatefulSet、一時ボリュームstorageClassName を書くだけで使える専用の Claim を知らない道具からは使えない

1 つめの問題は配る単位だ。読み書きを許したチームがファイルシステム全体を書き換えられるなら、チームごとのチェックポイントを安心して置けない。第 16 回で、Lustre はドライバを変えずにディレクトリだけをマウントできると分かったので、配る単位を「ファイルシステム」から「パス」に変えた。2 つめの問題は申し込みの形だ。Helm チャート(アプリの部品をまとめた雛形)、StatefulSet の volumeClaimTemplates、Pod と一緒に作られて消える一時ボリューム(generic ephemeral volume)は、どれも「StorageClass の名前を書いた PVC」を自分で作る。専用の Claim を間にはさむと、これらは一切使えない。そこで申し込みは普通の PVC にし、コントローラーは StorageClass の係(プロビジョナー)になることにした。

図: 変えたのは「配る単位」と「申し込みの形」の 2 つ。利用者が覚える CR は 0 個になった。

この作り直しで変わらなかったものもある。書き手を分けるという考え方(配ってよい先を決めるのは管理者だけ)、読み取り専用は ro のマウントオプションで強制すること、許可が消えたら猶予の後に取り上げることだ。書き手の分け方は、管理者が FilesystemShare を書き、利用者は自分の namespace の PVC だけを書く、という形でそのまま残る。

2. 管理者が書くもの、利用者が書くもの

FilesystemShare はクラスタ全体に置く CR で、管理者だけが書く。1 つの share は1 つのファイルシステムの 1 つのパスだ。パスの一部に {namespace} と書くと、申し込んだ namespace の名前に置き換わる。チームごとのチェックポイントのように「同じ形でチームごとに別の場所」を配りたいとき、share を 1 つ書くだけで済む。

apiVersion: sharedfs.littlemex.github.io/v1alpha1
kind: FilesystemShare
metadata: {name: checkpoints}
spec:
  persistentVolumeRef: {name: fsx-lustre}
  path: "checkpoints/{namespace}"
  provision: {gid: 1000, mode: "2770"}
  grants:
  - {namespaceSelector: {matchExpressions: [{key: example.com/team, operator: Exists}]}, access: ReadWrite}
項目意味なぜその形か
persistentVolumeRef既にある静的 PV(ファイルシステムの接続先を持つ)接続先の値を管理者が手で写さずに済む
path"/" か、[A-Za-z0-9._-] の区切り(. や - で始まらない)か {namespace}.. や隠しディレクトリ、オプションに見える名前を入口で断る。最大 32 区切り、全体で 1024 バイト
grantsnamespace の選び方と、ReadOnly か ReadWrite空のセレクタは「全部」と読まれるので CEL で禁止する(第 06 回)
provision任意。初めて使うときにディレクトリを作る持ち主と権限管理者が先に作る運用でもよい。path: "/" とは組み合わせられない

許可の一覧以外は、作った後に変えられない(CEL の self と oldSelf、第 06 回)。もう PV を配っている share のパスが後から変わると、既に配った PV と新しく配る PV が別の場所を指すことになるからだ。パスを変えたいときは、別の share を作る。

利用者が書くのは普通の PVC で、storageClassName に share の名前と -rw か -ro を付けるだけだ。team-a の PVC は checkpoints/team-a だけをマウントし、その上は見えない。

apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: ckpt, namespace: team-a}
spec:
  storageClassName: checkpoints-rw
  accessModes: [ReadWriteMany]
  resources: {requests: {storage: 1Gi}}

図: PVC は StorageClass を名指しするだけ。どのディレクトリになるかは、PVC の namespace と share のパスで決まる。

StorageClass は、許可にどの強さが含まれるかに関係なくいつも 2 つとも作る。片方しか無いと、許されない強さで申し込んだ PVC は「その StorageClass が無い」という理由で待たされ、本当の理由(許可が無い)が伝わらないからだ。share が使えない状態(Ready でない)でも作る。そうすれば PVC には「share が使えない」という理由が届く。

もう 1 種類、コントローラー自身が書く FilesystemShareDirectory がある。{namespace} を含む share のディレクトリについて、「最初に使った namespace の UID(一意な番号)」を記録する CR だ。namespace を消して同じ名前で作り直すと UID が変わるので、別のチームが前のチームのディレクトリを黙って受け継ぐことを防げる。これは第 4 節で使う。

3. 係として作る PV の形

Kubernetes では、StorageClass を名指しした PVC が来ると、PV コントローラー(kube-controller-manager の中で PV と PVC を結ぶ役)がその PVC に「この StorageClass の係はこれだ」という印(注釈 volume.kubernetes.io/storage-provisioner)を付ける。係はその印の付いた PVC を見つけて PV を作り、PV コントローラーが 2 つを結ぶ(bind する)。これを外部プロビジョナー(Kubernetes の外で書かれた、PV を用意する係)と呼ぶ。sharedfs は自分の印 sharedfs.littlemex.github.io が付いた PVC だけを扱う。PV のどの項目も「何を防ぐためにそうするか」が決まっている。

項目決めた値防ぐこと
PV の名前sfs-<PVC の UID>やり直しても同じ名前になるので、二重に作らない(作成が「もうある」で失敗したら成功とみなす)
volumeHandlesharedfs:<PVC の UID>ファイルシステムの ID に見えない値なので、ドライバ側の係が「自分のファイルシステム」と取り違えない。ドライバはマウントに handle を使わない(第 16 回でソースを確認)
マウント先mountname の後ろにパスを足す(<元の値>/checkpoints/team-a)そのディレクトリより上が見えない(第 16 回の実測)
注釈 pv.kubernetes.io/provisioned-bysharedfsPVC が消えた後の PV を PV コントローラーもドライバの係も触らず、消すのは sharedfs だけになる。ファイルシステムに削除が頼まれることが無い
回収方針Delete(消えるのは PV の札だけ)使い終わった PV が Released のまま溜まる。第 16 回の「Released の罠」がそもそも起きない
claimRefPVC の namespace、名前、UID動的に作った PV と同じく、その PVC 以外とは結び付かない
accessModesReadWriteMany を先頭に、PVC が頼んだものを後ろにkubelet は先頭の値をドライバに渡し、ドライバは ReadOnlyMany を断る(第 16 回)。一方で PV コントローラーは、PVC が頼んだ値が全部 PV に含まれないと結ばない
マウントオプション読み取り専用なら ro。元が flock なら localflock に変える読み取り専用の側が、ファイルシステム全体に効くロックを持てない
fsType書かないPod の fsGroup に合わせて、kubelet が共有ディレクトリの持ち主を丸ごと書き換えるのを防ぐ

PVC の中には、係が応えられない注文もある。selector(PV を選ぶ条件)、volumeMode: Block(ファイルでなく生のディスクとして使う)、dataSource(既存データの複製)、ReadWriteOncePod(1 つの Pod だけ)などだ。黙って無視すると頼まれていない PV を結んでしまうので、PV を作らずに Event(UnsupportedClaim)で理由を伝える。StorageClass には allowVolumeExpansion: false を付けるので、容量を増やす申し込みは API サーバーが断る。

図: 結ぶのは Kubernetes の PV コントローラーで、sharedfs は PV を作ることと、使い終わった PV の札を消すことだけを受け持つ。

4. 配る条件と、取り上げる条件

PVC に PV を作るのは、share の許可のうち 1 つが、その namespace を選び、かつ StorageClass の強さを許すときだけだ。読み書きの許可は読み取り専用も含む。許可を複数組み合わせて判定しないのは、パスと強さがいつも同じ share から来るようにするためだ。当てはまらなければ、PVC は Pending のまま Event(NotGranted)で理由を伝える。Event は約 1 時間で消えるので、待っている間は 30 分ごとに出し直す。

取り上げは、許可が消えたときに PVC を消すことで行う。ここで v1 から変わらない 2 つの安全装置を使う。1 つは猶予期間(既定 30 秒)で、GitOps(Git の中身にクラスタを合わせる運用)の同期中にラベルが一瞬外れても、戻れば何も消さない。もう 1 つは消す直前の読み直しで、キャッシュ(第 09 回)ではなく API サーバーから share と namespace を直接読み、まだ許可が無いと確かめてから消す。消すときは PVC の UID を前提条件に付けるので、同じ名前で作り直された別の PVC を間違って消すことも無い。

変わったのは、期限を書く場所だ。今の形では利用者の側に専用の CR が無いので、期限を PVC に書くことになる。しかし PVC はテナントが自由に書き換えられるので、期限を消し続ければ取り上げを先延ばしにできてしまう。そこで期限は PV の注釈(withdraw-after)に書く。PV を書けるのはクラスタの管理者だけだ。同じ理由で、PVC のラベルも判定に一切使わない。

図: 期限はテナントが書けない PV に置く。消すのは PVC だけで、ファイルは残る。

取り上げの理由は「許可が無い」ことに絞った。share が一時的に使えない(元の PV が読めない、ドライバの設定が危ない、など)ときは、新しい PVC に PV を作らないだけで、既に配った PV は取り上げない。元の PV が一瞬読めないだけで全チームの PVC が消えるのを避けるためだ。読み書きの PV を持つ namespace の許可が読み取り専用に下がった場合は、許可が無いのと同じに扱う。

namespace の作り直しにも備える。{namespace} を含む share では、ディレクトリを最初に使った namespace の UID を FilesystemShareDirectory に記録しておく。同じ名前の namespace が後から作られて PVC を出しても、UID が違うので PV を作らず、Event(NamespaceRecreated)で理由を伝える。管理者が記録を消せば、新しい namespace がそのディレクトリを使えるようになる。

取り上げても、動いている Pod は止まらない。 Kubernetes の pvc-protection(使用中の PVC を守る仕組み)が、その PVC を使う Pod が止まるまで本当の削除を待たせる。また、消した PVC は許可が戻っても作り直されない。間違ったラベル変更で PVC を失わないよう、猶予は運用に合わせて長めにできる。この 2 つは README に明記した。

5. share を使ってよいかの検査

share のコントローラーは、share が「PV を配ってよい状態か」を決め、Ready 条件(第 08 回)に理由と一緒に書く。Ready でない share の PVC には PV を作らない。検査は、穴があると誰かがファイルシステム全体に届いてしまうものから順に並べた。

検査落ちたときの理由(reason)無いと何が起きるか
元の PV が予約されているか(claimRef がある)SourceUnreserved予約の無い PV は、どの namespace の PVC からも名前で指名して結べる。ファイルシステム全体を許可なしで使われる
ドライバがディレクトリを扱えるかSubPathUnsupportedOpenZFS は根以外のパスを断る(第 16 回)。パスは "/" だけにする
CSIDriver の設定UnsafeDriverPolicyfsGroupPolicy: File だと kubelet が共有ディレクトリの持ち主を書き換える。一時ボリュームの方式(Ephemeral)が許されていると、Pod が PV なしで直接マウントできる
他の share との重なりOverlappingShare下で説明する
StorageClass の名前が空いているかStorageClassTaken他人が作った同名の StorageClass を自分のものとして使ってしまう

重なりの検査は、パス単位で配るようになって初めて必要になった。同じファイルシステムで、share A のパスが share B のパスを中に含み、A が読み書きを許しているとする。すると A の利用者は、B のディレクトリの名前を変えたり、B の利用者が読み込むファイル(たとえば学習の途中結果)を置き換えたりできる。そこで、読み書きを許す外側の share と内側の share の組は、片方を Ready にしない。{namespace} はどの名前にもなりうる区切りとして比べる。同じディレクトリを読み書き用と読み取り専用の 2 つの share で配るのは、データセットの普通の配り方なので許す。読み取り専用の外側は、警告を出すだけにする。

難しいのは「どちらを止めるか」だ。後から作った方を止める、という単純な決め方では穴が残る。share で後から変えられるのは許可の一覧だけなので、昔からある外側の share に、後から読み書きの許可を足せるからだ。そうすると、既に使われている内側の share が止まり、しかも外側は新しく読み書きの PV を配れてしまう。そこで外側の share には「初めて読み書きの許可を見た時刻」(status.readWriteSince)を記録し、重なりを後から持ち込んだ側を止めることにした。外側はその時刻、内側は作られた時刻で比べ、同じ秒なら UID で決める。どちらの share から判定しても同じ答えになり、使われている share が後から来た share に止められることは無い。

図: 後から重なりを持ち込んだのは外側なので、外側が止まる。既に配った PV はこの検査では取り上げない。

管理者が自分用にファイルシステムの根を読み書きで持ちたい場合もある。外側の share に注釈 allow-overlap: "true" を付けると、その share は検査から外れる。

6. 4 つのコントローラーの責任分担

1 つのプログラム(manager、第 15 回)の中で、4 つのコントローラーを動かす。分け方の基準は「何をキーに動くか」と「何を書くか」で、どの項目にも書き手は 1 人しかいない。

コントローラーキー書くもの責任
ShareFilesystemShareshare の status と finalizer、StorageClass(作成のみ)配ってよいかの検査、StorageClass の持ち主、使われている PV が残る間は削除を待たせる
Provisioner(係)PVCテナントの PV、ディレクトリの記録(作成のみ)、PV の期限の注釈、PVC の削除Pending の PVC に PV を作る。許可が消えた PVC を取り上げる
DirectoryFilesystemShareDirectory記録の status、下準備の Pod と専用の PVC と PVディレクトリを一度だけ作り、結果を書き、片付ける
Reclaim(回収)PVテナントの PV の削除Released になった sharedfs の PV を消す

ディレクトリを作る仕事を Directory に分けたのは、ファイルシステムに触る仕事を、Kubernetes のオブジェクトだけを読み書きする係から切り離すためだ。コントローラー本体はファイルシステムをマウントしない。ディレクトリが要るときだけ、そのディレクトリの親だけをマウントする短命の Pod を、コントローラー自身の namespace で動かす。この Pod は root(UID 0)だが、持ち主を変える権限(CAP_CHOWN)以外の特権をすべて外し、API に話しかける鍵(サービスアカウントのトークン)も持たない。中身は第 18 回で見る。

所有関係(第 10 回)も、この分け方に合わせた。StorageClass はクラスタ全体のオブジェクトなので、クラスタ全体の share を親にできる。下準備の Pod と PVC は namespace に属するが、親はクラスタ全体の記録でよい(逆向きは張れない)。テナントの PV は誰の子にもしない。PVC が消えたときに PV の札を消すのは、ガベージコレクション(GC)ではなく Reclaim の仕事だ。

図: 行の変化が、丸の付いた列のコントローラーを起こす(第 09 回の Watches)。下の行は、Pod の変化が Directory を、CSIDriver の変化が Share を起こす。share の変化は、判定が変わりうるときだけ伝える。

7. 設計判断と、比べた案

決めたこと比べた案理由
申し込みは普通の PVC専用の Claim CRHelm、StatefulSet、一時ボリューム、学習用のオペレーターがそのまま使える。将来ドライバ側が同じ機能を持てば、StorageClass を差し替えるだけで移れる
1 つの share は 1 つのパス1 つの share に複数のパスと、許可ごとのパスパスと強さがいつも同じ share から来るので、許可を組み合わせた判定が要らない。share の一覧がそのままデータの目録になる
admission webhook も ValidatingAdmissionPolicy も入れない他のオブジェクトを見る規則を webhook で1 つの CR で決まる規則はスキーマと CEL で書ける。許可や重なりは他のオブジェクトに依存して後から変わるので、reconcile で毎回判定し condition に出す(第 12・13 回)。下準備用の PV は専用の PVC にだけ UID で予約されるので、他の PVC は結べない

図: webhook を使わなかったのは、この題材の規則がどれも webhook 以外の置き場所に収まったから。

まとめと次の回

配る単位をファイルシステムからパスに、申し込みを専用の CR から普通の PVC に変えた。管理者は FilesystemShare を書き、利用者は StorageClass の名前を書いた PVC を出すだけで、コントローラーは係として、そのパスだけをマウントする PV を作る。取り上げは許可が無いときだけ、猶予と読み直しの後に行い、期限はテナントが書けない PV に置く。パス単位にしたことで新しく要った重なりの検査は、「後から持ち込んだ側を止める」で決めた。第 18 回では、ディレクトリを作る Pod の中身と実装、そして本物の FSx for Lustre で 49 項目を確かめた結果を見る。

図: 第 18 回は、この 3 つがコードのどこにあるかをたどる。

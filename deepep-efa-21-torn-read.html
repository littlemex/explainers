DeepEP が届き終わる前の記録を読んでいた (H4)

本物の検査をやっと走らせたら、DeepEP 自身の中に、まだ書き終わっていない記録を読んでしまう場所が見つかった。原因は特定し、直した (第 7 節)

1どうやって見つかったか

DeepEP 自身の検査を回すタスクが、9 月 6 日からほとんど何もテストしていなかった。

1 台のマシンで DeepEP 自身の検査を回すタスク (タスク 71) は、9 月 6 日から、その検査をほぼ引数無しで起動していました。原因は、行末のバックスラッシュ \ の後ろに、あとから足したコメントが挟まったことです。第 20 回の項目 33 で見た、タスク 90 と同じ形の壊れ方でした。

直して、検査を本来の引数で走らせたところ、特定の条件のときだけ失敗するようになりました。

2失敗する条件の一覧

1 台の中で 3 ランクに見立てて確かめると、順番が保たれるかどうかで、通る・通らないが分かれた。

この失敗は、GDRCopy の有無や MPS の有無には関係ありません。2 ランクの srd では 4 回中 2 回失敗し、同じ乱数の種で通った回と落ちた回があったので、タイミングも関わっています。

3何が間違っているか

再利用する経路だけが、間違った重みを返していた。

間違っていたのは、handle を再利用する側の dispatch (「キャッシュされた」経路) です。1 回の実行あたり1〜2 か所、エキスパートへの重み (top-k weights) が違っていました。

検査の中身を書き換えて、送信側が実際に渡した重みと、2 つの出力 (通常の dispatch とキャッシュされた dispatch) を 1 行ずつ比べました。通常の dispatch はすべての行で正しく、間違っているのはキャッシュされた dispatch だけです。しかも、間違った値はでたらめではありません。ランク 1 のトークン 192 が受け取った重みは、ちょうどランク 1 のトークン 768 の重みでした。そして、その同じ場所にある中身 (payload) は正しいトークン 192 のものでした。

言い換えると、中身は新しいのに、重みだけ前のものが残っているということです。これは、まだ届き終わっていない記録を、途中で読んでしまったときに起きる形です。

相手ごとの順番が保たれていれば安全だが、並び替えが起きると、後の回の通知だけが先に届いて、前の回の書き込みが終わる前に読んでしまう。

4証明

1 つの操作を「途中で切れない 1 かたまり」で送ると、失敗が消えた。

1 つの操作をまるごと 1 かたまりで送るように変えると (途中で記録が半分だけ書かれた状態を作れない)、srd は5 回中 5 回、通過しました。8 KiB のかたまりに分けると 7 回中 0 回、2 KiB のかたまりに分けると 2 回中 0 回です。

peer-seq は、1 つの操作の中のかたまりの順番も入れ替えますが、それでも通過します。つまり、間違いの原因は「自分の put を、その put 自身の通知より先に読んでいる」ことではありません。同じ相手への、後の回の操作から届いた何かを見たあとで、前の回の操作が運んだ記録を読んでいるのです。これが安全なのは、同じ相手への操作が届いた順番どおりに完了するときだけです。

5影響 (誇張しない)

今の AWS の実装では起きない。EFA の直接経路では起きうる。

AWS の現行の OFI plugin では、この問題は表に出ません。相手ごとの順番を保つからです (§2 の peer-seq と同じ形)。EFA の直接経路 (p5en・p6 系の EFA-GDA) では、SRD が順番を保たないので、起きる可能性があります。

DeepEP のどの行が原因かは、まだ特定できていません。手がかりは 1 つあります。キャッシュされた dispatch は「通知用の warp」を使わない形で動くため、channel と QP の対応、そして完了通知の番号の割り振りが、通常の dispatch (handle を作る側) とキャッシュされた dispatch (それを再利用する側) で違っています。

解明しました。原因は、まさにこの channel と QP の対応のずれでした。詳しくは第 7 節。

6除外したもの

エミュレータ側の不正でも、書き込みの重なりでも、検査自身の間違いでもない。

  • エミュレータが約束を破っている可能性 ―― 失敗するすべてのモードで、弱い通知の契約 (第 12 回・第 14 回で見た I1) は守られています
  • 2 つの書き込みが同じ相手の同じ場所に重なっている可能性 ―― 新しく作った検出の仕組みで調べても、重なりは見つかりませんでした
  • 検査自身の比べ方が間違っている可能性 ―― 古い回の行が紛れ込んでいるといった不具合は見つかりませんでした
  • 送信側が、送り終える前に送信用のバッファを書き換えている可能性 ―― 送り出す瞬間の中身を控えておき、届いた瞬間に読まれた中身と比べても、差はありませんでした

7原因が分かった: 合図の番号の取り合い

DeepEP 自身のコードの中に、しきり合わせの合図と、部品の合図が、同じ番号を取り合う場所があった。

どうやって見つけたか (順番に)

まず、2 つの見立てを消しました。「送信側が、送り終える前に送信用のバッファを書き換えていた」という見立ては、送り出す瞬間の中身を控えて届いた瞬間の中身と比べても差が無く、消えました。「検査そのものが間違っている」という見立ても、第 6 節のとおり消えました。

次に、DeepEP の受信側が守るべき決まり (invariant) に注目しました。「合図が届いた数 (landed) は、見えているヘッダーの数 (num_valid) を絶対に超えない」という決まりです。これが破れていないかを、その場で表示する検査を DeepEP 自身の GPU コードの中に差し込みました。

最初の 1 回目は、何も表示されませんでした。ところが、「この検査は動いています」という必ず出るはずの表示すら出ませんでした。調べると、DeepEP の JIT (その場でカーネルをコンパイルする仕組み) は、手元のチェックアウトではなく、インストール済みのパッケージの方のヘッダーを読んでいたのです。「何も出なかった」は「動いていない」の証拠にはなりません ―― これも第 20 回で繰り返し出てきた形の罠でした (項目 45)。

正しいヘッダーに検査を差し込み直すと、キャッシュされた dispatch のときだけ、すべてのランクで、channel 0 の part 0 と 1 だけ、landed 3 > num_valid 2 という表示が出ました。実行の最後に数を合わせ直す処理 (drain) も、合図が 1 個多い (3 個届いたのに 2 個のはず) と報告しました。毎回、必ず起きていました。

原因

DeepEP には、ランク同士のタイミングを合わせる「しきり」があります (gin_barrier_wo_local_sync)。この「しきり」はいつも QP 0 の上で、番号 0 から (ランク数 − 2) までの合図を使います。通常の dispatch は「通知用」の分を確保するので、データを運ぶ channel は QP 0 を使いません。ところがキャッシュされた dispatch には通知用の分が無いため、channel 0 の part の合図 (番号 0〜3) が、しきりと同じ QP 0 の同じ番号に乗ってしまいます。

QP 0 の番号を、しきり合わせと channel 0 の part 合図が取り合う。並び替えで、速いランクの次回のしきり合図が、遅いランクの channel 0 の数に先に紛れ込むと、受信側は 1 個早く「全部届いた」と判断してしまう。

先に自分の回を終えたランクが、次の回のしきり合わせの合図を出すと、まだ自分の channel 0 を実行中の遅いランクでは、その合図が自分の channel 0 の数として数えられてしまいます。並び替えが起きる環境では、この合図がデータより先に届くことがあり、受信側は「もう全部届いた」と1 個早く早合点して、届き切っていない記録を読んでしまいます。

これまでの観察すべてに説明がつく

  • キャッシュされた dispatch だけが失敗する ―― 通知用の分が無いのは、キャッシュされた dispatch だけだから
  • 相手ごとの順番が保たれていれば起きない ―― 順番が保たれていれば、しきり合わせの合図はデータより後に届く
  • 2 ランクだと失敗しにくい ―― 取り合う番号が「0 から ランク数 − 2」なので、2 ランクなら番号 0 だけしか取り合わない
  • 操作を 1 かたまりで送ると気づかれない ―― 早合点で受理された記録は、半分書きの記録ではなく前の回の完全な記録のままで、この検査では前の回もちょうど同じトークンの記録だったため、見た目には違いが出なかった

直し方

キャッシュされた dispatch でも、通常の dispatch と同じように QP 0 を確保するようにしました (patch 0011)。変えたのは定数 1 つ (kReserveNotifyQP = true) です。ホスト側の channel 数の決め方は、もともと同じ選択をしていました ―― GPU 側だけが取り残されていました。

結果。直したあと、srd は 3 ランクで3 回中 3 回、通過 (直前は 7 回中 0 回)。4 ランクと defer-one も通過します。差し込んだ検査は、どの起動でも黙って (何も表示せず) いるようになりました。この直した DeepEP の上で vLLM を動かすと、対照とまったく同じ答えを返し、128 本同時要求も 128 本すべて一致します。英語と日本語、両方の PR 文面を用意しました。

まだ終わっていないこと。順序を守るカーネルと、直接送る dispatch も、QP の決め方は同じ仕組みを使っています。これらが、キャッシュされた dispatch の中で、しきり合わせとぶつかるかどうかは、まだ測っていません。

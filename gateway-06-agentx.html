第 6 章 他人の物差しで測ったら、自分の結論が壊れた

この章の 3 行 SemiAnalysis の AgentX という公開ベンチを入れた。実際のコーディング会話 393 本を再生するもので、 入力が全トークンの 99.15% という私の測定を独立に裏づけた。そして「この箱では prefix caching が 構造的に使えない」という私の公開済みの結論が、設定ファイルのフラグ 1 個の書き忘れだったことが判明した。 正しく有効にすると最初の応答までが 11.5 倍速くなり、会話アフィニティのルーティングを足して合計 17.6 倍、 除外していた族が候補に戻った。

なぜ他人のベンチを入れるのか

理由は 2 つあって、1 つ目は道具ではなくデータである。

AgentX のコーパスは実際の Claude Code の会話 393 本、68,266 リクエスト。入力 68.9 億トークンに対して 出力 5,873 万トークン、つまり全トークンの 99.15% が入力。私は自前の SWE-bench エピソードで 99.5% を 測っていたが、それが「agentic coding の性質」なのか「私の作った足場の癖」なのか判断できなかった。前者だった。

2 つ目は比較可能性。彼らのフラグ、彼らのシナリオ、彼らの集計器で取った数字は、他のハードウェアで 公開された数字と同じ軸に乗る。私が自分で書いたループの数字は乗らない。だから模倣せず借りた — commit を 固定し、彼らの負荷生成器をサブモジュールとして持ち、起動フラグを値ごと逐語コピーし、統計は彼らの集計器を そのまま実行する。上に乗せたのは自分の担当分 (箱の時間単価と API 請求との比較) だけである。

開発者の 1 ターンが印字開始まで中央値 7 秒。そしてエンジン自身のカウンタが「何が律速でなかったか」を 言っていた — preemption 0、待ち行列の最大 0、KV 使用率は最大 14.9%。 箱は同じトークンを読み直すことだけで律速していた。処理した 258 万プロンプトトークンのうち 94.42% が、 キャッシュがあれば無料だったもの。5.6 分の窓のうち 5.2 分である。

ところが、それは能力の問題ではなくフラグの問題だった

「vLLM がこの構成には無理だと判断して切っている」と 2 回書いた。3 回目にエンジンのソースを読んだら、 vLLM 自身のコメントがこう言っていた。

# Hybrid models support prefix caching but keep it opt-in for now
# while the feature matures.
default_prefix_caching = (
    model_config.is_prefix_caching_supported and not model_config.is_hybrid
)

このモデルは is_prefix_caching_supported = True。つまり対応している。 is_hybrid = True なので既定がオフになるだけで、明示的に指定すれば入る。

そして私の設定ファイルは、無効にするときだけフラグを出し、有効にするときは何も出していなかった。 vLLM の該当引数の既定値は「指定なし」で、それは「モデルの既定に従う」を意味する。だから 「有効」と書いた設定は何も起こさず、エンジンは False と報告し続けた。

1 つのフラグを 3 回測った 1 回目は明示的にオフのまま測って「効かない」と書いた。2 回目は設定を「オン」にしたがフラグが渡らず、 やはり False のままだったので「エンジンが断っている」と書いた。3 回目でようやく本当にオンにした。

第 3 章で「設定の意図は効果の証拠にならない」と書いたのは私である。書いたうえで同じ罠に落ちた。 エンジンの実効値を出す仕組みまで作ったのに、「オフ」と出ている理由を確かめなかった。 手がかりも 1 本目に出ていて、prefix_cache_queries が「不一致」ではなく 0 だった。 これは非対応の姿ではなく、無効化された機能の姿である。

その 11.5 倍を信じる前に、答えが変わっていないか確かめる

相談した 2 つのモデルのうち片方が、真っ先にこう言った。「while the feature matures は飾りではない。 hybrid の prefix caching は attention の KV に加えて linear 層の圧縮された状態をブロック境界で 復元する必要がある。まさに成熟中だから opt-in なのだ。速くなった数字の上に設計を積む前に、 出力が変わっていないことを確かめろ」。

これは正しい警告である。復元を間違えてもエラーにならない — リクエストは成功して、答えだけが変わる。

そこで会話を 1 ターンずつ伸ばして (2 ターン目以降は必ず「途中まで復元」になる)、同じプロンプトを 2 回送り、 返ってきた文章を 1 文字ずつ比べた。キャッシュが無くても完全に同じ答えが返る保証は無い (FP8 の計算やバッチの 組み方で揺れる) ので、両方ともキャッシュに当たらない場合を対照群にした。

キャッシュヒットしたペア 22 件すべて、全 24 件すべてで完全一致 2,000 / 8,000 / 30,000 トークンの prefix、各 4 ターン。36,493 トークンのうち 35,904 トークンを キャッシュから復元したターンも含めて、答えは 1 文字も変わらなかった。報告することが何も無い、 というのが欲しかった結果である。

実測 84.96% は理論値 94.14% の 90.2%。足りない 1 割はエンジンではなくルーティングである。 2 つの replica が 1 つの窓口の後ろにいるので、会話の後続ターンが prefix を持たない側に飛ぶとミスする。 実行中の replica 別ライブヒット率は 86.2% と 66.1% に割れていた。同じ現象は正しさの検査でも見えていて、 連続する同一リクエストのキャッシュ読み数が 35,904 → 9,504 → 35,904 と振動していた。

スループットの改善が 1.38 倍しかない理由 遅延が 11.5 倍改善したのにスループットは 1.38 倍。これは失望ではなく、この測定が同時実行 1 で 遅延律速だからである。トレース再生は各ターンの応答を待って次を投げるので、計算量が 5.7 分の 1 に なったことは「最初の応答までの時間」に出て、「1 秒あたりの件数」には出ない。 それを見るには同時実行を上げた測定が必要で、それが次の作業になる。

足りない 1 割を取りにいく — 8 割はルーティングだった

実測 84.96% と理論値 94.14% の差 9.18 ポイントを「ルーティングのせい」と書いたが、 相談した 2 つのモデルが揃って「決めつけるな」と言った。追い出し (eviction)、暖機、ブロック境界、 プロンプトの正規化されていない部分も同じ差に住んでいる。だから測った。

AIPerf は X-Correlation-ID を送っていて、これは会話の全ターンで不変である (AgentX 自身のレシピもこれをキーにしている)。そこで 2 つの replica の前に nginx を 1 枚置き、 このヘッダで consistent hash を取る構成にした。

この実験が「偽の合格」になる道が 2 つあって、両方を先に潰した 1 つはストリーミングが止まること。nginx が応答をバッファすると「最初の応答までの時間」が 「全部書き終わるまでの時間」に化けて、比較が無意味になる。proxy_buffering off が必須。

もう 1 つはハッシュキーが届かないこと。nginx は空文字列を 1 つの upstream にハッシュするので、 ヘッダが無いと「完璧なアフィニティ」に見えて何も証明しない。だからキーを 1 リクエストずつログに出した。 最初の確認では 1 文字のキー 5 個が全部同じ replica に行って壊れたように見えたが、 実際に AIPerf が送る UUID 形式のキー 40 個では 21 対 19 に分かれた。5 サンプルの短いキーという テストが悪かったのであって、ルータは正しかった。

ルーティングは 9.18 ポイントのうち 7.57 ポイント、つまり 8 割を占めていた。残る 1.61 ポイントが まさに 2 つのモデルが挙げた要因で、いまはそれが「残り全部」になった (交絡ではなくなった)。

一番出るのは裾である。20 万トークンのプロンプトが prefix を持たない replica に飛ぶと 最初の応答まで 38 秒かかっていた。アフィニティを入れるとその事象自体が消えて、最悪でも 6.8 秒になる。

フラグ 1 個とルータ 1 枚で、最初の応答まで 6,932 ms → 393 ms = 17.6 倍 出発点は「この箱では prefix caching が構造的に使えない」という自分の公開済みの結論だった。

もっと大きな話 — 軸そのものが変わる

第 5 章の結論は「入力が短いほど箱 1 秒あたりの価値が高い」だった。あの曲面は再利用ゼロの単発 プロンプトで測っている。キャッシュが効く今、あの結論はどうなるのか。相談した 2 つのモデルが独立に 同じ答えを出した。軸が「入力長」から「再利用率」に置き換わるのではなく、両者が 1 つの量に潰れる。

実際に計算する量 = 固有の部分 + 共有 prefix × (1 − ヒット率)

つまりあの曲面は最初から「キャッシュに当たらないトークン数」の曲面だった。再利用ゼロで測ったから、 たまたま入力長と一致していただけである。AgentX の 55,038 → 9,654 はまさにこの変換で、 「9,654 トークンの仕事」は曲面上では 1 万トークン相当の経済性を持つはず — これは検証できる予言になる。

そして片方のモデルが、新しい第 2 軸を指摘した。キャッシュヒットは計算をゼロにするが、メモリはゼロに しない。20 万トークンの prefix を持つ会話は、ヒットしていても GPU のメモリを占有し続け、他の会話を 追い出す。しかもヒット率はリクエスト単体の性質ではなく、「次のターンが来るまでに追い出されないか」という システム状態の関数である。だから admission は「長さ 対 再利用率」ではなく、 「計算 対 メモリ常駐」の 2 軸で考えるのが正しい。

では、そのキャッシュはどれだけ抱えられるのか

ヒット率はリクエストの性質ではない。次のターンが来たときにそのブロックがまだ残っているかという システム状態の確率である。だから測るべきは「生存曲線」で、C 本の会話を輪番で叩きながら エンジン自身が返す cached_tokens を全ターン記録した。

プールの 3 割までなら完璧、5 割で崩れ始め、8 割でゼロになる。崖である。

膝の形が面白い。C=20 では中央値は 99.0% のままで、平均だけが 71.0% に落ちた — 17 ターンがちょうど 0%。 つまり「全会話が prefix の末尾を少しずつ失う」のではなく、ある会話は全部保ち、別の会話は全部失う。 追い出しはブロック単位の LRU で、1 つの会話のブロックは新しさの順で連続しているので、まとまって消える。 相談したモデルの片方は逆 (部分ヒットからなだらかに劣化する) を予測していた。

時間ではなく容量だった — 対照で確定させた この設計では C が 2 つのものを同時に決めてしまう。作業集合の大きさと、同じ会話が次に回ってくるまでの時間。 ギャップは 1.4 秒から 322 秒まで伸びていたので、崩壊は容量とも経年とも解釈できた。

そこで作業集合を C=12 に固定したまま、明示的に待ち時間を挿入した。中央値ギャップは 1.4 秒 → 50.0 秒 (36 倍) になり、ヒット率は 99.1% で変わらなかった。 キャッシュは古くならない。効くのは「他に何がどれだけ載っているか」だけである。
一番大事な罠 — 見るべきゲージが見えていない キャッシュが崩壊している最中、vllm:kv_cache_usage_perc は 2 つの replica で 21% と 31% しか示していなかった。私は最初これを読んで「プールは 7 割空いているのだから 容量のせいではない」と結論した。間違いだった。

このゲージは実行中のシーケンスの KV しか数えず、キャッシュ済みで待機中のブロックを数えない。 つまり「prefix キャッシュの追い出しを予測できそうに見える指標」が、実は予測できない。 これで監視画面を作ると、キャッシュが死んだ瞬間に「余裕あり」と表示される。 予測できるのは常駐トークン数の算術だけである (会話数 × プロンプト長 対 replica あたりのプール)。

実際の族に翻訳すると、上限はかなり小さい

コーパスの主ターンの入力は中央値 158,944 トークン (AgentX が p50 42,638 と報告するのは 短い subagent リクエストを含むため)。replica あたりの膝 104 万トークンに対して、

  • キャッシュが崩れ始めるまで replica あたり約 6 会話、箱全体で約 13 会話
  • 余裕を持って平坦域に留まるなら replica あたり約 4 会話、箱全体で約 8 会話

これが agentic 族のこのハードウェアでの実容量である。そして先の 1.76 倍という数字は 1 lane、 つまり平坦域のど真ん中で測っている — 箱にとっての最良ケースであって、 admission ルールには同時会話数の上限が必要になる。

この章で壊しておきたい誤解

よくある思い込み実際は
エンジンが「無効」と報告していれば、その機能は使えない無効な理由を確かめるまで何も言えない。既定オフの opt-in と非対応は、ログでは同じ顔をしている
設定ファイルに true と書けば有効になるフラグが実際にコマンドラインに出ているかは別問題。「指定なし」は「既定に従う」であって「有効」ではない
速くなったなら良いこと答えが変わっていないかを先に確かめる。復元の失敗はエラーにならず、成功したまま答えだけ変わる
キャッシュが効けばメモリも楽になる計算はゼロになるがメモリは占有し続ける。追い出されるかどうかが次のヒット率を決める
KV 使用率のゲージを見ればキャッシュの余裕が分かるそのゲージは実行中の KV しか数えない。21% と表示されている裏でキャッシュは全滅していた
キャッシュは時間が経つと古くなって効かなくなる経年では劣化しない (ギャップ 36 倍で不変)。効くのは他に何が載っているかだけ
容量を超えると全体のヒット率がなだらかに下がる会話単位で全か無か。ある会話は全部保ち、隣は全部失う
公開ベンチは自分のハードに合わないから意味がない絶対値は比較できなくても、コーパスと指標の設計が自分の測定の誤りを暴く

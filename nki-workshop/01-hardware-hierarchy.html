NKI WORKSHOP ・ 01

Trainium のハードウェア階層をビジュアルに理解する

Chip・NeuronCore・HBM / SBUF / PSUM ― 容量と帯域の差、そして「ソフトウェアが全部管理する」思想

0この記事の狙い

NKI (Neuron Kernel Interface) で高性能なカーネルを書くには、まずハードウェアのメンタルモデルが要ります。どのメモリがどれだけ速く・どれだけ入るのか、データはどう動くのか。ここでは AWS Trainium2 の 3 層メモリ階層 (HBM / SBUF / PSUM) と計算エンジンの関係を、絵と実測値で腹落ちさせます。

一言でいうと
Trainium は「小さくて速い」オンチップメモリ (SBUF / PSUM) と「大きくて遅い」HBMの 3 層で、その間を DMA エンジンが運びます。GPU と決定的に違うのは、ハードウェアが自動で中身を出し入れするキャッシュではなく、どのデータをいつどこに置くかを全部ソフトウェア (あなた) が明示的に管理するスクラッチパッドだということ。この記事で「速度と容量の地図」を頭に入れれば、以降のカーネル最適化がすべて「この地図の上でデータをどう動かすか」に見えてきます。

対象は AWS Trainium2 (TRN2, NeuronCore v3)。数値は NKI Workshop の資料・実測に基づきます。GPU の内部構造には深入りしません (別記事で扱います)。

1Chip / Device / Core の関係

まず用語を揃えます。「デバイス」「コア」「インスタンス」は別物です。

Trainium は階層で数えます。一番外から見ると:

  1. Device (チップ): 1 枚の Trainium2 チップ。BF16 で約 1.3 PFLOPS の dense 計算 (ワークショップ公称値)、96 GB の HBM を持ちます。※ 後述の単一 NeuronCore の実測ピーク 78.6 TFLOPS(bf16)を素朴に 8 コア倍すると約 0.63 PFLOPS で、公称の 1.3 PFLOPS とは集計基準 (LNC・クロック・数え方) が異なります。ここでは講義の公称値を採用します。
  2. NeuronCore (物理コア): 1 デバイスの中に 8 個の物理コアがあります (TRN2/TRN3)。2 コアが 1 つの HBM バンクを共有します。
  3. LNC (Logical NeuronCore): 既定は LNC2 で、2 つの物理コアを 1 つの論理コアとして扱います。だから neuron-ls は 8 でなく 4 コアと表示します。
  4. Instance: 複数デバイスをまとめたもの (例: 16 デバイス)。今回のワークショップは trn2.3xlarge (単一デバイス) を使います。
この記事で主役になるのは 1 つの NeuronCore の内側です。カーネルは基本この単位で動き、メモリ (SBUF / PSUM) も計算エンジンもこのコアに属します。「まず 1 コアを使い切る」がカーネル最適化の出発点です。

2NeuronCore の中身 ― 4 つのエンジン

NeuronCore は「1 つの万能プロセッサ」ではなく、役割の違う専用エンジンの集まりです。

Trainium はディープラーニング専用にゼロから設計されており、必要な演算ごとに専用ハードウェアブロックを持ちます。これをヘテロジニアス (異種混在) コンピュートアーキテクチャと呼びます。

エンジン役割ひとこと
Tensor Engine行列積 (MatMul)・transpose・broadcast128×128 の systolic array。FLOP の約 90% がここ
Vector Engine (DVE)reduction、要素ごと演算、tensor-tensor 演算合計・max など。SBUF の partition に並列接続
Scalar Engine (Act)活性化関数、区分多項式マイクロコードで機能追加できる
GP-SIMD Engineカスタム演算・descriptor 生成など8 個の SIMD プロセッサ。汎用の受け皿
設計思想。これらは独立にスケジュールされ、並列に動きます。Tensor Engine でタイル行列積をしている「その裏で」Vector Engine が別の reduction を回す ― というエンジン間パイプラインでチップを使い切るのが狙いです。だから「1 つのエンジンだけ速くする」のではなく「全エンジンを同時に働かせる」のが性能の鍵になります。

NeuronCore 全体像 ― データはこの上を流れる

ここまでの登場人物 (エンジンと 3 種のメモリ、DMA) を 1 枚の図にまとめます。「再生」を押すと、行列積 1 回ぶんのデータの流れが流れます。以降の章はすべて、この地図のどこかの話をしています。

HBM SBUF PSUM エンジン DMA が運ぶデータ

流れを言葉にすると: HBM から DMA が SBUF へ運び (①)、SBUF の 2 入力を Tensor Engine が読んで計算し (②)、結果を PSUM に蓄積 (③)。Vector / Scalar が PSUM から SBUF へ退避し (④)、最後に DMA が SBUF から HBM へ書き戻す (⑤)。計算エンジンは HBM を直接触れず、必ず SBUF を経由します。この記事の主題はメモリなので、以降はエンジンより「データがどこに置かれ、どう運ばれるか」に集中します。

33 層メモリ階層 ― HBM / SBUF / PSUM

Trainium のメモリは 3 層。上に行くほど小さく速く、下に行くほど大きく遅い ― この非対称が全ての制約の源です。

PSUM # Tensor Engine 専用の集計台。最小・最速・書込はTEのみ
↕ (Vector / Scalar エンジンで退避)
SBUF # オンチップの作業台 (SRAM)。2D。全エンジンが直結
↕ (DMA エンジンが運ぶ)
HBM # 大きな倉庫。1D フラット。DMA しかアクセスできない

3 つの「大きさ」と「速さ」の関係を、TRN2 の実数で並べます。

メモリ種類容量 (TRN2)速さ / アクセス誰が触れる
HBM大容量 DRAM96 GB / デバイスDMA ピーク 約 435 GB/s (1コア)DMA エンジンのみ
SBUFオンチップ SRAM28 MB / コア (224 KiB × 128 partition)桁違いに高速・全エンジン直結全 compute engine + DMA
PSUMオンチップ SRAM128 part × 8 bank × 512 要素最速・Tensor Engine 蓄積用書込=TE / 退避=Vector・Scalar
ここが最重要の直感。SBUF は HBM より桁違いに速いが、桁違いに小さい (96 GB 対 28 MB = 約 3400 倍の差)。だから「必要なデータだけを SBUF に載せ、計算し、書き戻す」というやりくりが要る。この容量と帯域の非対称こそが、カーネル最適化で戦う相手です。次章で地図として体感します。

4【体験】容量と帯域の地図

3 層の「容量」と「速さ」を対数スケールで並べます。バーの長さの違いが、そのまま設計の制約になります。

HBM SBUF PSUM

「容量で見る」と HBM (96 GB) が圧倒的に大きく、SBUF・PSUM はごくわずか。「速さで見る」と関係が逆転し、オンチップの SBUF / PSUM が HBM を大きく上回ります。大きい所は遅く、速い所は小さい ― この綱引きが、後続のすべてのカーネル最適化テクニック (タイリング、SBUF 常駐、フュージョン) の動機になります。

5HBM ― 大きくて遅い倉庫

まず一番下の層、HBM から。

HBM (High Bandwidth Memory) はデバイスの大容量メモリ (TRN2 で 96 GB) で、モデルの重み・活性・入出力などすべての大きなデータの置き場です。PyTorch で tensor.to("neuron") するとデータはここに載ります。

HBM の 2 つの重要な性質。
(1) 1D フラットメモリ ― 単純な一次元の並び。
(2) DMA エンジンからしかアクセスできない ― 計算エンジン (Tensor / Vector など) は HBM を直接読めません。必ず一度 SBUF に運んでから計算します。

「高帯域」の名の通り帯域は大きいですが、オンチップ SRAM と比べれば遅い。実測では、単一 NeuronCore の 16 個の DMA エンジンを全部使い切って ピーク約 435 GB/s。ここに近づけるかどうかが、メモリバウンドなカーネルの成否を分けます (8 章)。

6SBUF ― 2D の作業台

SBUF は Trainium で最も「クセ」のあるメモリです。ここの構造がカーネル設計を強く縛ります。

SBUF (State Buffer) はオンチップの汎用スクラッチパッド (SRAM) で、計算エンジンが実際に読み書きする作業台です。HBM と違い 2D 構造を持ちます。

# SBUF の形 (TRN2)
partition 次元 (P) : 128 レーン # 固定。ここが超重要
free 次元 (F) : 各レーン 224 KiB 連続 # TRN3 は 256 KiB
合計 : 約 28 MB / コア # TRN3 は 32 MB

この 128 という partition 次元が Trainium の随所に効いてきます。理由は 2 つ:

  1. 全 compute engine が partition に並列接続されている。だから partition 次元の演算は「幅を増やしてもコストがほぼ一定」 (64 幅も 128 幅も同じ時間)。逆に partition を 128 未満しか使わないと、その分だけ FLOP を捨てています。
  2. DMA エンジンも partition のサブセットを担当する。少ない partition しか使わないと、使える DMA エンジンも減り、帯域を取りこぼします (9 章で体感)。
覚えておくべき合言葉は「partition 次元 (128) を使い切れ」。テンソルの形を 2 のべき乗・128 に寄せると、計算も DMA も素直に速くなります。逆に中途半端な形 (例: 51) は遅くなり、64 に丸めるだけで 30% 速くなることもあります。SBUF に載りきらないデータを詰め込むと、コンパイラが HBM へあふれさせ (spill)、性能が激しく落ちる点にも注意です。

7PSUM ― Tensor Engine 専用の集計台

3 層目の PSUM は、Tensor Engine の行列積の「出力受け皿」に特化した小さなメモリです。

PSUM (Partial Sum buffer) は、Tensor Engine が行列積の部分和を蓄積するための専用バッファです。最もプログラマブルでなく、強い制約があります。

# PSUM の形と制約 (TRN2)
構造 : 128 partition × 8 バンク × 512 要素/バンク
型 : FP32 アキュムレータ # TRN3 は BF16 ダウンキャストも可
書込 : Tensor Engine のみ
退避 : Vector / Scalar エンジンのみ (SBUF へ)

行列積のデータの流れはこうです。Tensor Engine が SBUF の 2 つの入力を読んで計算し、結果をPSUM に蓄積。その後、Vector か Scalar エンジンが PSUM から SBUF へ退避 (evict) します。

退避はフュージョンのチャンス。PSUM から SBUF へコピーする「ついで」に、活性化関数や reduction を一緒に済ませられます。Tensor Engine が matmul した結果を SBUF に戻す途中で活性化を掛ければ、別途エンジンを回す往復が消える ― これが NKI で手書きカーネルを書く大きな動機の一つです。

なお「8 バンクを全部埋めれば速い」は誤解になりがちで、実際はバンクを早く空ける (drain) 方が速いことが多いです (この詳細は別記事のマイクロベンチマークで扱います)。

8データはこう流れる (DMA)

層と層の間でデータを運ぶのが DMA エンジン。ここの効率が、メモリバウンドなカーネルの速度を決めます。

DMA (Direct Memory Access) エンジンは、HBM ↔ SBUF および SBUF ↔ SBUF のデータ移動を担当します (NeuronCore あたり 16 個)。逆に、compute engine が SBUF を読むのや、PSUM の出し入れは DMA ではありません。

# カーネル内の典型的なデータフロー
HBM  —DMA→  SBUF  —Tensor Engine→  PSUM
PSUM  —Vector/Scalarで退避→  SBUF  —DMA→  HBM

DMA には固定のオーバーヘッド (トリガー・descriptor 生成・キュー投入) があります。だから小さな転送を大量にやると、オーバーヘッドばかりで帯域が出ません。逆に大きな連続転送なら、オーバーヘッドを償却できて帯域を使い切れます。

DMA を速くする 2 つの鉄則。
(1) partition 次元を最大化 (128) ― 16 個の DMA エンジンを全部働かせる。
(2) free 次元を大きく (連続転送を大きく) ― 転送あたり 32 KiB 以上、128 partition なら合計 512 KiB 以上でオーバーヘッドを償却。
実測での効き方 (NKI Workshop の DMA ベンチ)。同じ 256 MB のコピーでも、タイルの形で achieved 帯域が激変します。
・128×512 の小タイル → 約 224 GB/s (ピークの約 52%)
・128×8192 の大タイル → 約 424 GB/s (約 97%)
・128×16384 → 約 427 GB/s (約 98%、この構成の実質上限)
タイルの形を変えるだけで帯域が約 1.9 倍。DMA エンジンはどちらも約 90% 動いているのに、小さい転送は「忙しいのに遅い」。これが「geometry (形) が性能を決める」という Trainium の本質です。

9【体験】partition を使い切る

同じ要素数のテンソルでも、SBUF 上の「形」で使える DMA エンジンの数が変わります。partition 次元の効きを見ます。

partition 次元 (P)
4使用 partition
1 / 16働く DMA エンジン
6%DMA 帯域の利用率(概念)

スライダーを動かすと、使う partition 次元に応じて働く DMA エンジンの数が変わります。4 partition しか使わないと DMA エンジンは 1 個しか動かず、帯域を 16 分の 1 に絞ってしまう。128 partition まで広げると 16 個全部が働き、帯域を使い切れます。同じ 16K 要素のテンソルでも、4×4096 か 128×128 かで achieved 帯域が桁違いになる ― これが「partition を使い切れ」の意味です。

補足: 図の「利用率」は partition の使い方が帯域に効くことを示す概念値で、実測の絶対値ではありません。実際は free 次元の大きさ (8 章) も同時に効きます。

10GPU との決定的な違い

GPU を触ってきた人ほど、ここで頭を切り替える必要があります。GPU の詳細には踏み込まず、思想の違いだけを押さえます。

最大の違いはオンチップ SRAM が「キャッシュ」か「スクラッチパッド」かです。

用語を正確に。「SBUF はオンチップ SRAM なんだから、GPU の L2 キャッシュと同じでは?」と思うかもしれません。物理的な素材 (SRAM) は同じですが、管理方式が根本的に違います。
・キャッシュ (cache): ハードウェアが自動で中身を出し入れする。どのデータが載っているかはタグで管理され、ヒット/ミスはプログラムから透過的 (見えない)。ソフトは「どこに何を置くか」を指定できない。
・スクラッチパッド (scratchpad): 番地を持つ普通のメモリで、載せる・降ろすを全部ソフトが明示的に命令する。自動のヒット/ミスは無い。
SBUF / PSUM は後者 (スクラッチパッド)です。だから正しくは「Trainium はキャッシュを持たない」ではなく「ハードウェア管理のキャッシュを持たず、代わりにソフトウェア管理のスクラッチパッドを持つ」です。
観点GPU (一般論)Trainium
オンチップメモリハードウェア管理のキャッシュ (L2 等)ソフトウェア管理のスクラッチパッド (SBUF/PSUM)
データ移動自動 (prefetch・キャッシュ再利用)明示的 (どのデータをいつ載せるか自分で書く)
最適化の焦点キャッシュヒット率を上げるデータの置き場と移動を設計する
制御の主体ハードウェアがよしなにあなた (と一部コンパイラ)
Trainium はハードウェア管理キャッシュを持ちません。SBUF も PSUM も SRAM ですが、自動プリフェッチもキャッシュ再利用も無いソフトウェア管理のスクラッチパッドです。「どのテンソルをいつ SBUF に載せ、いつ HBM に戻すか」を、あなたが NKI で明示的に書きます。これは意図的な設計で、ユーザーに最大限の制御を与えてピーク性能を引き出させるためです。
だから NKI はブラックボックスではない。「よしなにキャッシュしてくれる」を期待すると詰まります。逆に言えば、データの所在を完全に把握・制御できるので、フュージョン (SBUF 上で処理を繋げて HBM 往復を消す) や精度制御を自分で設計でき、コンパイラ任せを超える性能を出せます。GPU の「キャッシュ職人」から Trainium の「データ物流の設計者」へ、発想を切り替えるのが第一歩です。

11まとめ

Trainium のハードウェア階層を一枚に整理します。

論点要点
階層Device (96GB HBM) > NeuronCore ×8 (2コアで1 HBMバンク共有) > 既定 LNC2 で論理4コア
エンジンTensor (matmul, FLOP の90%) / Vector / Scalar / GP-SIMD が並列動作
HBM大容量 (96GB)・1Dフラット・DMAのみ・ピーク約435GB/s(1コア)
SBUFオンチップSRAM・2D (128 partition × 224KiB)・28MB・全エンジン直結
PSUM128 part × 8 bank × 512・TE書込/Vector・Scalar退避・FP32蓄積
DMA16エンジン。partition最大化 + 大きな連続転送で帯域を使い切る
GPUとの違いハードウェア管理キャッシュを持たず、ソフト管理スクラッチパッド (SBUF/PSUM)。データの置き場と移動を全部ソフトで明示管理
結論。Trainium の性能は「小さくて速いオンチップ (SBUF/PSUM) と、大きくて遅い HBM の間で、いかにデータを賢く動かすか」に尽きます。partition 次元 (128) を使い切り、大きな連続転送で DMA 帯域を稼ぎ、SBUF 上で処理を繋げて HBM 往復を減らす。GPU と違ってハードウェア管理キャッシュが自動で助けてくれない代わりに、スクラッチパッドをすべて自分で設計できる。この「容量と帯域の地図」が、以降の NKI カーネル最適化すべての土台になります。

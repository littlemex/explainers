status と scale のサブリソース

望む状態と観測した状態を分け、別々の書き込み口を作る仕組み

← カスタムコントローラー自作 シリーズ目次へ

Mid パートの最後となるこの回では、CRD の spec(望む状態)と status(観測した状態)という 2 つの領域が、なぜ分かれているべきで、サブリソースという仕組みがどうそれを支えているかを見る。ここで整理した generation・observedGeneration・conditions という道具は、第 09 回以降のコントローラーの実装でずっと使い続ける。

spec は利用者が書く「望む状態」、status はコントローラーが書く「観測した状態」。status サブリソースを有効にすると、この 2 つの書き込み口が API レベルで分かれ、RBAC も分けられる。generation は spec の変更を数え、observedGeneration はコントローラーが「どの版の spec まで見たか」を status に書き込む、2 つの数字の対比になっている。

spec と status という 2 つの領域

Kubernetes のオブジェクトの多くは、spec(利用者が書く望む状態)と status(コントローラーが観測して書く今の状態)の 2 つに分かれる。この分け方は Kubernetes の API の約束事(API conventions)として広く守られている。第 03 回で見た「望む状態と今の状態の差を埋め続ける」という調整ループの話を、オブジェクト 1 つのレベルに落とし込んだものがこの分離と言える。

図: spec は利用者から、status はコントローラーから、別々の方向に書き込まれる

status サブリソースを有効にすると何が変わるか

CRD の subresources.status: {} を有効にすると、本体(/widgets/{name})への更新で status フィールドへの変更が無視されるようになり、/widgets/{name}/status という別の URL だけが status を書ける窓口になる。逆方向も対になっていて、/status への書き込みは status 以外(spec など)への変更を無視する。2 つの窓口はそれぞれ自分の担当フィールドしか見ない。

実測(EKS 1.35 のテスト用クラスタ): 本体に対して {"status":{"replicas":3}} を merge patch(マージパッチ: 送った部分だけを今のオブジェクトに重ね書きする、全体を送り直さない更新方法。第 11 回で詳しく扱う)すると patched (no change) が返り、status は無視された。--subresource=status を付けて同じ内容を patch すると、今度は status が実際に書けた。

図: 本体への patch は status を無視し、/status という別の窓口だけが status を書ける(実測)

RBAC で status を分ける

status サブリソースが有効だと、widgets と widgets/status は RBAC(Role-Based Access Control: 役割ごとの権限制御)の上で別々の resource として扱われる。ただし RBAC が区別できるのは resource 単位(widgets か widgets/status か)までで、「spec だけ書ける」のようなフィールド単位の権限は存在しない。widgets/status への write を利用者に与えないことで、「status を書けるのはコントローラーだけ」という分担を実現できる。たとえば「spec は書けるが status は書けない」利用者と、「status だけ書けるが spec は書けない」コントローラー用のサービスアカウントを、別々の Role で分けられる。これは「誰が望む状態を決め、誰が観測結果を書くか」という責任の分離を、権限の上でも裏付ける仕組みになっている。

コントローラーが実際に動くには、widgets/status の get・update・patch だけでは足りない。informer が一覧と監視を行うための widgets の get・list・watch も必要になる。さらに第 10 回で見る finalizer の付け外しは本体(widgets)への update・patch で行うので、finalizer を使うコントローラーは widgets の update・patch も持つ(その権限があれば spec も書けてしまう。フィールド単位の制限ができない以上、ここは「信頼してよいコントローラーにだけ渡す」運用で守るしかない)。

resource権限の例想定する主体
widgetsget, list, watch, update, patch (spec を含む全体)利用者、kubectl
widgetsget, list, watch(+ finalizer を使うなら update, patch も)コントローラーのサービスアカウント
widgets/statusget, update, patch (status だけ)コントローラーのサービスアカウント

図: resource 単位で分かれた責任。「status だけ書ける」はフィールド単位ではなく resource 単位の権限で表現する

generation と observedGeneration

metadata.generation は spec が変わるたびに増える番号で、API サーバーが自動管理する。status.observedGeneration はコントローラー自身が書く番号で、「どの版の spec まで見て反映したか」を表す。2 つを比べれば、コントローラーが最新の spec にまだ追いついていないかどうかが分かる。

実測(EKS 1.35 のテスト用クラスタ): status サブリソースが有効な状態で status だけを patch しても generation は 1 のまま変化しなかった。spec.replicas を変更すると generation が 1 から 2 に増えた。つまり status サブリソースが有効な間は、generation は spec の変更だけを数える(status サブリソースを持たない CRD では、本体への更新が status も一緒に書き換えるため、その場合は status の変更でも generation が増える)。

図: generation と observedGeneration を比べると、反映の遅れが分かる

conditions の作法

status の中でも、オブジェクトの状態を表す定番の形が conditions(配列)。Kubernetes の API conventions と、確認済みの k8s.io/apimachinery の metav1.Condition 型(pkg/apis/meta/v1/types.go)では、1 つの condition が type(種類。例: Ready)、status(True/False/Unknown のいずれか)、reason(機械で読める理由)、message(人が読む説明)、lastTransitionTime(最後に変わった時刻)、observedGeneration を持つ、という形に揃っている。実験用 Widget の Ready 列(第 05 回)もこの type: Ready を見ていた。

Go で condition を更新するときは、自分で配列を 1 件ずつ書き換えるのではなく、k8s.io/apimachinery/pkg/api/meta パッケージの meta.SetStatusCondition(&status.Conditions, newCondition)(確認済み: ソース pkg/api/meta/conditions.go)を使うのが定石。同じ type の条件があれば更新し、status が変わったときだけ lastTransitionTime を更新してくれる。

observedGeneration は 2 箇所に出てくるので混同しやすい。status.observedGeneration(前の節)はオブジェクト全体として「コントローラーがどの版の spec まで反映したか」を表すのに対し、status.conditions[].observedGeneration はその condition 1 件が「どの版の spec を見て判定したか」を表す。Ready の判定に使った spec の版と、status 全体を最後に反映した版がずれることもあるので、分けて持つ。

図: condition 1 件が持つ 6 つの項目

scale サブリソースと kubectl scale

subresources.scale は、どのフィールドが「望むレプリカ数」で、どのフィールドが「今のレプリカ数」かを specReplicasPath・statusReplicasPath で指定する仕組み。実験用 Widget は specReplicasPath: .spec.replicas、statusReplicasPath: .status.replicas を使っていた(第 05 回の CRD YAML)。これを有効にすると kubectl scale が Widget にも使えるようになる。Deployment などで使われる HPA(Horizontal Pod Autoscaler)まで使うには、さらに labelSelectorPath を指定し、コントローラーがそこにレプリカを選ぶラベルセレクタを書く必要がある(HPA は対象の Pod 数を数えるのにこのセレクタを使う)。

実測(EKS 1.35 のテスト用クラスタ): kubectl scale widget a --replicas=4 を実行すると、scale サブリソース経由で spec.replicas が 4 に変わった。kubectl get wdg の表示は a small 4 True になった。scale サブリソースは「レプリカ数という 1 つの値を、汎用の道具(kubectl scale や HPA)から触れるようにする」ための小さな窓だと言える。

図: scale は specReplicasPath が指すフィールドだけを書き換える(実測)

まとめと次の回

spec と status は役割が違うので書き込み口も分け、RBAC でも resource 単位で分けられる(フィールド単位の権限は無い)。generation は spec の版番号(作成時 1、status サブリソースが有効なら spec が変わるたびに +1)、observedGeneration はコントローラーがどこまで追いついたかを表し、両者を比べると遅れが分かる。conditions は type・status・reason・message・lastTransitionTime・observedGeneration という決まった形を持ち、scale サブリソースはレプリカ数だけを汎用の道具に差し出す窓になっている。

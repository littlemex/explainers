FFN から MoE へ ― ビジュアルに理解する

Transformer の計算の大半を占める FFN、それを「一部だけ使う」MoE、そして MegaBlocks が解いた GEMM の非効率

0この記事の狙い

Attention が注目されがちですが、Transformer のパラメータの多く (典型的な系列長では計算量の過半も) を占めるのは FFN (MLP) です (超長文脈では Attention の N² 項が支配的になります)。この FFN を「全部使わず一部だけ使う」ように拡張したのが MoE (Mixture of Experts)。ここでは FFN と MoE の違いを絵と数式で掴み、MoE を GPU で効率よく動かす鍵となった MegaBlocks の発想 (ブロックスパース) まで一気に理解します。

一言でいうと
FFN は「全トークンが同じ 2 層ネットを通る」密な計算。MoE は「多数の専門家 (expert) を用意し、各トークンは router が選んだ少数の expert だけを通る」疎な計算です。これで総パラメータを増やしても、1 トークンあたりの計算 (活性パラメータ) は増やさずに賢くできる。ただし「トークンごとに通る expert が違う」ことが GPU の得意な密行列積 (GEMM) を崩し、MegaBlocks はそれをブロックスパース演算で解決しました。

1FFN とは ― Transformer の働き者

まず FFN が Transformer のどこにいて、何をしているかを掴みます。

Transformer ブロックは大きく Attention と FFN (Feed-Forward Network / MLP) の 2 つの部品からなります。Attention が「トークン同士で情報を混ぜる」のに対し、FFN は各トークンを独立に受け取り、その中身を変換する役割です。トークン間の混ぜ合わせはせず、1 トークンずつ「考える」部分だと思ってください。

役割分担。Attention = トークン間で情報を集める (mixing)。FFN = 各トークンの中で非線形な変換をして表現力を持たせる (per-token processing)。この 2 つを交互に積むのが Transformer です。

地味に見えますが、FFN はTransformer ブロック内の重みの約 2/3 を占めることが多く (標準的な MHA・d_ff=4d のときの概算)、知識の多くがここに蓄えられていると考えられています。まさに Transformer の働き者です。

2FFN の数式

FFN の正体は、間を一度太らせる 2 層の全結合ネットです。

入力を d 次元のトークンベクトル x とします。FFN は次元を一度 4 倍ほどに広げてから、元に戻す 2 層の MLP です。

# 標準的な FFN (2層 MLP)。d_ff は通常 4d 程度
FFN(x) = W₂ · σ( W₁ x + b₁ ) + b₂

# 次元の流れ
x: (d)  →  W₁x: (d_ff=4d)  →  σで非線形  →  W₂: (d)

ここで W₁ (d_ff×d。d 次元を受けて d_ff 次元へ) が次元を広げる層、W₂ (d×d_ff) が元に戻す層、σ は活性化関数 (ReLU, GELU など)。真ん中で一度太らせて非線形を通すことで、豊かな変換を表現します。

直感。W₁ で「広い作業台に情報を展開」し、σ で「非線形に取捨選択」し、W₂ で「必要な情報だけ集約して元のサイズに戻す」。この「広げて→選んで→畳む」が FFN の仕事です。最近の LLM では活性化に SwiGLU を使い、ゲート用の重みを加えた 3 行列構成も多いですが、「広げて畳む」骨格は同じです。

3なぜ FFN が重いのか

FFN のパラメータ数と計算量を数えると、Transformer の主役級だと分かります。

FFN のパラメータは W₁ (4d×d) と W₂ (d×4d)、合わせて約 8d²。一方 Attention の射影 (Q,K,V,O) は約 4d²。つまり FFN だけで Attention の約 2 倍のパラメータを持ちます。

部品主なパラメータ概算
Attention (Q,K,V,O 射影)4 × d×d4d²
FFN (W₁, W₂)4d×d + d×4d8d²
ここが MoE の動機。モデルを賢くするには容量 (パラメータ) を増やしたい。でも FFN を単純に大きくすると、全トークンがその巨大な FFN を毎回通るので計算量も比例して爆発します。「パラメータは増やしたいが、1 トークンあたりの計算は増やしたくない」― この矛盾を解くのが次章からの MoE です。

4【体験】FFN のデータフロー

1 つのトークンが FFN を通る様子を見ます。次元が広がって、非線形を通り、また畳まれる流れを追ってください。

拡大率 d_ff/d
入力 x (d 次元) 中間 (d_ff 次元・広い) 出力 (d 次元)

左の入力 x が W₁ で広い中間層に展開され (青が増える)、活性化 σ で一部が刈られ、W₂ で元の次元に畳み戻されます。拡大率を上げると中間層が太くなり、表現力もパラメータも計算も増えることが見て取れます。全トークンがこの同じ経路を通るのが FFN です。

5MoE の発想 ― 全部使わない

FFN を「一つの巨大な専門家」ではなく「多数の小さな専門家の集まり」に置き換えます。

MoE (Mixture of Experts) は、1 つの大きな FFN の代わりに、同じ形をした FFN を多数 (expert) 並べ、各トークンには router (gating network) が選んだ少数の expert だけを通します。全 expert を使うのではなく、トークンごとに一部だけを活性化するのが核心です。

2 種類の「パラメータ数」を区別するのが最重要。
総パラメータ = 全 expert を合わせた重みの総量 (モデルの知識容量)。
活性パラメータ = 1 トークンが実際に通る重みの量 (1 トークンあたりの計算量)。
MoE は総パラメータを大幅に増やしつつ、活性パラメータ (=計算) はほぼ据え置きにできる。例: 総 8 expert でも各トークンは 2 つだけ通れば、計算は「2 expert 分」で済む。expert を数百〜数千に増やせば (Switch Transformer 等)、総パラメータは桁違いに増やせます。

これで「賢さ (容量) は増やしたいが計算は増やしたくない」という 3 章の矛盾が解けます。実際 Mixtral・DeepSeek・Qwen の MoE 版などが、この仕組みで巨大な総パラメータと現実的な推論コストを両立しています。

6MoE の数式 ― router と top-k

「どの expert を選ぶか」と「選んだ結果をどう混ぜるか」を数式で書きます。

expert が E 個あり、それぞれ FFNᵢ (i=1..E) とします。router は小さな線形層 W_g で、トークン x に対し各 expert への適性スコアを出し、softmax で重みにします。

# 1. router が各 expert へのスコアを出す
g = softmax( W_g x )  # (E 次元) 各 expert の重み

# 2. スコア上位 k 個の expert だけ選ぶ (top-k, 通常 k=1 or 2)
T = TopK(g, k)  # 選ばれた expert の添字集合

# 3. 選ばれた expert の出力を、router 重みで加重和
y = ∑ᵢ∈T gᵢ · FFNᵢ(x)

ポイントは 3 段目の和が、全 E 個ではなく選ばれた k 個だけを回ること。E=64 でも k=2 なら、計算は 2 expert 分。総パラメータは 64 expert 分あるのに、活性は 2 expert 分です。

補足: 上式のままだと選ばれた k 個の gᵢ の和は 1 になりません。実装では選ばれた k 個の重みを再正規化する (または top-k の logits にだけ softmax を取る) ものが多いです (Mixtral 等)。また router を放置すると特定 expert に偏るため、実際の学習では負荷分散のための補助損失 (load-balancing loss) を足して、トークンが expert 全体に散るよう促します。それでも次章のとおり分配は完全には揃いません。

ここに実装の落とし穴がある。数式は綺麗ですが、「トークンごとに選ばれる expert が違う」ため、実際の計算では「expert 1 には 5 トークン、expert 2 には 100 トークン、expert 3 には 0 トークン…」とバラバラの量が割り当てられます。この不均一さが、GPU の得意な計算 (揃ったサイズの行列積) と相性が悪い。8〜9 章の核心です。

7【体験】FFN vs MoE

複数のトークンを流し、FFN では全員が同じ経路を通るのに対し、MoE では router が各トークンを別々の expert に振り分ける様子を見ます。

トークン router expert

FFN では全トークンが1 つの経路に集中して通ります (密)。MoE に切り替えると、各トークンはまず router (橙) を通り、top-k で選ばれた expert (紫) にだけ流れます。expert ごとに受け取るトークン数がバラバラになる様子に注目してください ― これが次章の効率問題の元凶です。

8なぜ MoE は GPU で効率が出ないか

MoE の計算は「多数の小さくて不揃いな行列積の集まり」になり、GPU の得意技を活かせません。

GPU が最も速いのは GEMM (General Matrix Multiply / 大きな密行列積) です。大きく揃った行列積は演算強度が高く (データ移動に対して計算の割合が高く、メモリ待ちではなく計算で忙しい状態 = compute-bound)、何千ものコアを埋め尽くして使い切れます。FFN はまさにこの理想形です。

ところが MoE では、各 expert が受け取るトークン数が可変で不均一 (expert A に 100 個、B に 3 個、C に 0 個…)。素朴には「expert ごとに別々の小さな行列積をループ実行する」か、「揃ったサイズを要求する batched GEMM に載せるため無理やりサイズを揃える (次項の capacity)」ことになります。

小さく不揃いな行列積は GPU を持て余す。(1) 小さい行列積は GPU のコアを埋めきれず使用率が落ちる。(2) expert ごとにトークン数が違うので負荷が偏り、特に expert を複数 GPU に分散する場合は最も混んだ expert が全体の律速になる。(3) expert の数だけカーネル起動が要り、その回数自体もオーバーヘッド。結果、FFN なら少数の大きな GEMM で済む計算が、MoE ではバラバラで非効率になります。
(補足: サイズ不揃いの GEMM 群を 1 カーネルにまとめる grouped GEMM という技術は解決策側で、当時は MoE 向けの効率的な実装が普及していませんでした。)

従来の回避策 ― capacity factor と token drop

この不揃いを避ける従来手法は、各 expert の受け入れ枠を固定サイズ (capacity) に決め打ちし、揃った密テンソルに詰め込むものでした。しかしこれには両刃のトレードオフがあります。

  1. capacity を小さくする → 枠を超えたトークンはdrop される。ただし消えるのではなく MoE 層をスキップして residual 接続でそのまま次の層へ渡り、expert による変換だけを受けられない。計算は揃うが、変換を受けられない分精度が落ちる。
  2. capacity を大きくする → token drop は減るが、枠の余りをゼロ埋め (padding) するので無駄な計算が増える。

しかも「どこまで capacity を上げれば drop がゼロになるか」は構成依存で読めません。論文では、drop 完全回避に capacity factor 11 相当が必要な構成 (通常の 11 倍の枠 = 大量の padding) も報告されています。つまり padding 方式は根本解決になりません。どちらに振っても「精度」か「無駄計算」のどちらかを損なう ― この妥協を根本から無くしたのが MegaBlocks です。

9MegaBlocks ― ブロックスパース

「不揃いなトークンを、捨てず・埋めず、1 つの効率的な行列積にまとめる」。それがブロックスパースの発想です。

MegaBlocks の核心は、MoE の計算を block-sparse (ブロックスパース) 行列積として定式化することです。各 expert のトークンを固定枠に押し込む代わりに、可変サイズのまま、ブロック単位で疎な 1 つの大きな行列積に組み上げ、専用カーネルで一気に計算します。

ブロックスパースとは。ここには 2 階層の「ブロック」が出てきます。(1) MoE の expert 計算は、本来ブロック対角行列 (各 expert が対角の 1 つの領域) の積として書けます。この expert の領域は、担当トークン数に応じて行数が可変。(2) その領域を、GPU が扱いやすい 128×128 の固定タイルで敷き詰め、中身が非ゼロのタイルだけを計算します。expert 間の関係ないところ (ゼロのタイル) は計算しないので無駄がなく、各タイルは十分大きいのでGPU を効率よく使える。「行数可変の expert 領域」を「固定サイズのタイルの敷き詰め」で表現するのが肝で、密 GEMM の効率と疎な構造の無駄のなさを両取りします。

これにより MegaBlocks は dropless-MoE (dMoE) ― トークンを 1 つも捨てない MoE を実現しました。capacity factor 起因の悩み (大量の drop か padding か) が消えます (厳密には 128×128 ブロック境界への丸めでごく少量の端数パディングは残りますが、capacity 方式の無駄とは桁が違います)。

効果 (論文 arXiv:2211.15841 の実測値)。トークンを捨てないので精度を損なわず、padding の無駄計算もしないので速い。論文の高速化は「何と何を比べたか」で 3 通りあり、混同しないことが大切です。

比較対象比較の軸結果
vs Tutel (token-drop あり)MoE 実装どうし最大 約 40% 高速
vs Tutel (drop させない設定)MoE 実装どうし1.38〜4.35 倍 (大きいモデルほど拡大)
vs dense Transformer (Megatron-LM)アーキテクチャ比較 (同品質到達時間)1.8〜2.4 倍

上 2 行は同じ MoE 実装どうしの比較、3 行目は MoE 対 dense の比較 (MoE というアーキテクチャの利点込み) なので、比べているものが違います。2 行目が大きいのは、Tutel を drop させないと padding のメモリで小さいバッチしか回せなくなるためです。

さらに、ブロックスパースカーネル自体が論文の評価環境で、密な cuBLAS の batched 行列積の平均 98.6% のスループットを出します ― 疎にしたことによる性能ペナルティがほぼ無い。しかも capacity のチューニング自体からも解放されます。
なぜ専用カーネルが要るのか。既存の疎行列ライブラリは MoE に不向きでした。cuSPARSE の blocked-ELL は「全ブロック行で非ゼロブロック数が同一」を要求し、まさに避けたい不均一さと衝突します。Triton の blocksparse は「疎のパターンが不変」を前提としますが、MoE の割り当てはイテレーションごと・層ごとに変化します。そこで MegaBlocks は CUTLASS を拡張し、128×128 ブロックの専用 block-sparse GEMM カーネル (Blocked-CSR-COO エンコードや転置インデックス等の工夫つき) を自作して、動的に変わる MoE を実用速度で回せるようにしています。

10【体験】token drop/padding vs block-sparse

従来の「固定枠 (capacity)」方式と、MegaBlocks の「block-sparse」方式で、無駄計算と token drop がどう変わるかを見ます。

capacity
実トークンの計算 捨てたトークン (drop) ゼロ埋め (padding・無駄)

固定枠では、各 expert に同じ高さの枠を割り当てます。枠を超えたトークンは赤 (drop)、枠が余れば灰 (padding の無駄計算)。capacity スライダーを動かすと、小さくすると drop が増え、大きくすると padding が増えるトレードオフが見えます。block-sparse に切り替えると、実トークン (紫) だけをブロック単位で計算し、capacity 起因の drop も大量 padding も出ないことが分かります (実際にはブロック境界への丸めでごく小さな端数だけ残りますが、この図では簡略化しています)。

11まとめ

FFN から MoE、そして MegaBlocks までを一枚に整理します。

論点要点
FFN の役割各トークンを独立に非線形変換。重みの約 2/3 を占める働き者
FFN の数式W₂·σ(W₁x)。d → 4d → d と広げて畳む 2 層 MLP
MoE の発想多数の expert を用意し、router が選ぶ top-k だけ通す
MoE の利点総パラメータ (容量) を増やしつつ、活性パラメータ (計算) は据え置き
MoE の実装難expert ごとにトークン数が不均一 → 小さく不揃いな GEMM で GPU 非効率
従来の妥協capacity 固定。小=token drop で精度低下 / 大=padding で無駄計算
MegaBlocksblock-sparse 演算で不揃いを 1 つの効率的な行列積に。token を捨てない dropless-MoE
MegaBlocks の効果精度を落とさず高速化し、capacity チューニングも不要に (数値は 9 章)
結論。FFN は「全員が同じ大きな脳を通る」密な計算、MoE は「各自が得意な専門家だけを通る」疎な計算。MoE は容量と計算を切り離す賢い仕組みですが、その代償が「不揃いなトークン配分による GEMM の非効率」でした。MegaBlocks はブロックスパースという表現で、GPU の密 GEMM の速さと疎な構造の無駄のなさを両取りし、トークンを一つも捨てずに MoE を高速化しました。「疎な問題を、GPU が得意な密ブロックの集まりに翻訳する」という発想が核心です。

性能の式 ― 実行時間を決める 3 つの数と、1 つを削ると何が増えるか

「クロックが速い」「命令が少ない」だけでは速い CPU にならない。実行時間は 3 つの数の掛け算で決まり、片方を良くすると別の数が悪化することがある

「クロック周波数を上げれば CPU は速くなる」というのは半分しか正しくありません。1 つのプログラムを実行するのにかかる時間は、命令の数 ・ 1 命令あたりの平均クロック数 ・ 1 クロックの長さという 3 つの数の掛け算で決まります。そしてこの 3 つは独立ではなく、ISA の設計やパイプラインの段数を変えると、片方が良くなる代わりに別の数が悪化することがよくあります。この回では rj32 を例に、この式のどの項が何によって動くか、そしてキャッシュや分岐予測がなぜ要るようになるのかを確認します。

1. 性能の式 ― 3 つの数の掛け算

あるプログラムを実行するのにかかる時間は、次の 3 つの数の掛け算で決まります (計算機科学では古くから Iron Law とも呼ばれます)。

図: 実行時間は「命令数」「CPI (Cycles Per Instruction)」「クロック周期」の 3 つの掛け算。

CPI (Cycles Per Instruction) は「命令 1 個を実行するのに平均で何クロックかかるか」という数です。すべての命令がちょうど 1 クロックで終わるなら CPI は 1 ですが、何かの理由で余分なクロックがかかる命令が混じると CPI は 1 より大きくなります。クロック周期は、第 21 回で見た画素クロックと同じ考え方で、1 クロックの長さそのものです。この 3 つの数は独立ではなく、ISA (命令セット) の設計やパイプラインの段数を変えると、互いに影響し合います。次の節から、どの設計判断がどの項を動かすかを見ていきます。

2. 命令セットが動かす項 ― 命令数

命令セットの設計は、実行される命令の総数に直接効きます。第 22 回で見たように、rj32 の fmt_ri6 形式の即値は 6 bit (-32〜31) しか入らず、これを超える定数を使うと imm 命令が自動的に 1 つ追加されます。つまり即値の幅が狭いほど、同じ処理でも命令数が増えやすくなります。

図: 即値の幅が狭い ISA では、大きな定数を使うだけで命令数が増える。

第 13 回で見た rj32 の if.cc というスキップ方式も、命令数に影響します。条件分岐を「次の 1 命令をスキップする」という形にまとめているため、条件分岐のたびに新しいジャンプ先ラベルを作らずに済み、多くの場合は古典的な条件分岐命令より少ない命令数で済みます。一方で、命令セットを削って「少ない種類の命令だけ」にする (rj32 は 32 命令という上限を意識した設計) と、複雑な処理を少数の命令では表せず、同じ処理により多くの命令が必要になる場合もあります。命令セットの設計は、命令数を減らす方向にも増やす方向にも働くというのがここでの要点です。

3. パイプラインが動かす項 ― CPI とクロック周期

rj32 は README に書かれている通り、現在は fetch (取り出し) と execute (解読・実行・書き戻し) の 2 段のパイプラインです。何もハザードが起きなければ、1 クロックごとに 1 命令が完了するので CPI は 1 に近づきます。しかし実際には CPI を 1 より大きくする要因があります。docs/instructions.md には「スキップされた命令も、nop と同じように 1 クロックを消費する」とはっきり書かれています。つまり if.cc でスキップされた命令は、何も実行しないのに 1 クロックを使ってしまい、CPI を押し上げます。

段数を増やしてパイプラインを深くすると、1 段あたりの回路が担当する仕事が減るので、クロック周期を短くできます (第 07 ・ 11 ・ 12 回で見た、1 段の中の最長の経路がクロック周期を決める、という関係です)。しかし段数が増えるほど、第 16 回で見たハザード (前の命令の結果がまだ出ていないのに次の命令が必要とする、分岐の結果が確定する前に次の命令を読んでしまう、など) が起きやすくなり、ストールやフラッシュで CPI が上がりやすくなります。

図: スキップされた命令 B も execute 段のクロックを 1 回使い切り、何もしないまま 1 クロックを消費する。

図: 段数を増やすとクロック周期は短くなるが、CPI が上がりやすくなるという反対方向の効果が同時に起きる。

4. 本物の数字で確認する

rj32 の hdl/Makefile は、FPGA 向けの配置配線ツール (nextpnr) に対して --freq 12.5 という指定をしています。これは「12.5MHz で動くように配置配線してほしい」という目標値で、クロック周期にすると約 80ns (1 ÷ 12,500,000 秒) です。ここに、第 2 ・ 3 節で見た CPI の性質を当てはめて、実行時間を具体的に見積もってみます。

図: 12.5MHz ・ CPI≈1 の単純化した見積もりでは、100 クロックの実行に約 8 マイクロ秒かかる。

この見積もりが「単純化」であることが重要です。もしプログラムに load・store が多く含まれ、TODO.md に記録されている通りバスの応答を待つストールが実際に発生すれば、CPI は 1 より大きくなり、実行時間はこの見積もりより伸びます。性能の式の 3 つの数は、設計段階の意図だけでなく、実際に動かして測るまで本当の値が分からないという点を覚えておく必要があります。

5. キャッシュと分岐予測が要る理由

rj32 はキャッシュを持ちません。第 09 回で見たように、rj32 のメモリは FPGA に内蔵された小さなブロック RAM で、CPU と同じ基板の中にあり、同期読み出しの 1 クロック遅延さえ数えれば CPU のクロックにそのまま同期して読めます。これが成り立つのは、使えるメモリが小さく、しかも CPU と同じ速さで動くからです。

プログラムやデータが大きくなり、内蔵の小さなメモリに収まらず、外部の大きなメモリ (DRAM など) を使う必要が出てくると、話が変わります。外部メモリは容量が大きいほど、1 回のアクセスにかかる時間が CPU のクロック周期に比べて長くなりがちです (この差は「メモリの壁」としてよく知られています)。CPI の式に当てはめると、メモリアクセスのたびに大きなストールが入り、CPI が何十倍にも膨らんでしまいます。キャッシュは、よく使うデータを CPU の近くに置いた小さく速いメモリに保持することで、このストールの回数を減らす仕組みです。

図: メモリが大きくなるほどアクセス時間が伸び、CPI が膨らむ。キャッシュはこの膨らみを抑える。

分岐予測が要る理由も似ています。rj32 の if.cc は、スキップするかどうかを常に 1 クロックだけ使って確実に処理する方式で、予測を外して大きなペナルティを払うことがありません。しかしパイプラインの段数が増え、分岐の結果が確定するまでに何段もかかるようになると、「確定するまで待つ」こと自体が CPI を大きく膨らませます。分岐予測は、結果を待たずに「たぶんこっちだろう」と先読みして実行を続け、当たればストールを払わずに済ませる仕組みです。外れた時のペナルティは rj32 の確実な 1 クロックより大きくなり得ますが、当たる割合が十分高ければ平均の CPI は下がります。これは第 24 回で詳しく見ます。

6. 実装のポイント

(1) CPI は設計意図ではなく、実測で確かめる。 「2 段パイプラインだから CPI は 1 のはず」という考え方は、if.cc のスキップや TODO.md に残っているストールのような要因を見落とします。第 22 回で見た emurj の -trace のようなツールで実際に実行させ、何クロックかかったかを数えるのが、唯一の正しい確かめ方です。

(2) 1 つの項だけを見て設計を決めない。 「命令数を減らすために複雑な命令を追加する」という判断は、その命令の回路がクロック周期を決める経路 (クリティカルパス) を長くしてしまうと、命令数は減ってもクロック周期が伸び、掛け算の結果である実行時間はむしろ悪化することがあります。命令数 ・ CPI ・ クロック周期は別々に最適化できる項ではなく、3 つの掛け算の結果だけが意味を持つことを常に意識する必要があります。

(3) 「目標値」と「実測値」を混同しない。 hdl/Makefile の --freq 12.5 は配置配線ツールへの目標の指定であり、実際に合成した回路が必ずその周波数で動くという保証ではありません。性能を主張する時は、どちらの数字を使っているかを常に明示することが重要です。

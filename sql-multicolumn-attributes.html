マルチカラムアトリビュート ― tag1, tag2, tag3

1 つの行に複数の値を持たせたくて tag1、tag2、tag3 という列を並べると、検索も追加も削除も一意性の確認も、列の数だけ手間が増えていきます

この回の前提: 第 02 回 ジェイウォーク(1 つの列にカンマ区切りで複数の値を詰め込む設計がなぜ壊れるか)

「1 つのバグに複数のタグを付けたい」という要望に対して、tags1、tag2、tag3のように列を横に並べて増やす設計をマルチカラムアトリビュートと呼びます。結論を先に言うと、この設計は列の数を事前に決め打ちしてしまうため、検索・追加・削除・重複の防止のどれをやろうとしても、列の数だけ同じ処理を繰り返すか、列が足りなくなって詰まるかのどちらかに行き着きます。この回では実際にこの設計を作って何が壊れるかを確かめ、PostgreSQL で複数の値を持たせたいときの正しい書き方を見ます。

1. 目的 ― 何をしたかったのか

バグ管理システムで、1 件のバグに複数のタグ(crash、performance、auth のような分類)を付けたいとします。1 件のバグに付くタグの数は決まっていないため、「列を 1 本追加して、そこにタグを入れる」という素直な発想だけでは対応できません。

そこで「だいたい 3 つくらいあれば十分だろう」という見積もりのもとに、tag1、tag2、tag3という 3 本の列を bugs テーブルに追加する設計が生まれます。これなら 1 件のバグに最大 3 つまでタグを持たせられ、新しいテーブルを作らずに済みます。1 件に複数の値を持たせたいという目的自体は正当ですが、これを「列を複製する」という手段で実現してしまう点に問題があります。

2. アンチパターン ― どう書いてしまい、何が壊れるか

実際にtag1、tag2、tag3の 3 列を追加して、サンプルのバグ管理データベースにタグを入れてみます。

ALTER TABLE bugs ADD COLUMN tag1 text;
ALTER TABLE bugs ADD COLUMN tag2 text;
ALTER TABLE bugs ADD COLUMN tag3 text;

UPDATE bugs SET tag1 = 'crash', tag2 = 'save'        WHERE bug_id = 1;
UPDATE bugs SET tag1 = 'report'                       WHERE bug_id = 2;
UPDATE bugs SET tag1 = 'performance', tag2 = 'search' WHERE bug_id = 4;
UPDATE bugs SET tag1 = 'auth'                          WHERE bug_id = 5;

SELECT bug_id, summary, tag1, tag2, tag3 FROM bugs ORDER BY bug_id;

 bug_id |           summary           |    tag1     |  tag2  | tag3
--------+------------------------------+-------------+--------+------
      1 | crash when saving           | crash       | save   |
      2 | wrong total on report       | report      |        |
      3 | button label typo           |             |        |
      4 | slow search on large data   | performance | search |
      5 | login fails with long email | auth        |        |
(5 rows)

図: マルチカラム方式は列の数が上限を決め、従属テーブル方式はタグの数だけ行が増える。

2.1 検索: 3 列を OR でつながないと探せない

「performance というタグが付いたバグを探す」には、どの列に入っているか分からないため、3 列すべてを条件にする必要があります。

SELECT bug_id, summary FROM bugs
WHERE tag1 = 'performance' OR tag2 = 'performance' OR tag3 = 'performance';

 bug_id |          summary
--------+----------------------------
      4 | slow search on large data
(1 row)

タグの本数が 3 から 4 に増えたら、この条件も 4 つの OR に書き直す必要があります。アプリケーションのコードの中でタグを検索する箇所すべてに、同じ数の OR を埋め込むことになります。

2.2 追加: 列が埋まっていると新しいタグの入れ場所が無い

bug_id=1 に 3 つ目のタグ'regression'を付けて tag1、tag2、tag3 をすべて埋めた後、4 つ目のタグ'urgent'を付けたくなったとします。

UPDATE bugs SET tag1 = 'crash', tag2 = 'save', tag3 = 'regression' WHERE bug_id = 1;
SELECT bug_id, tag1, tag2, tag3 FROM bugs WHERE bug_id = 1;

 bug_id | tag1  | tag2 |    tag3
--------+-------+------+------------
      1 | crash | save | regression
(1 row)

3 本の列はすでに埋まっているため、4 つ目のタグを入れる列がありません。ALTER TABLEでtag4を追加するか、既存のタグをどれか諦めるかしかなく、どちらも設計時点では想定していなかった対応です。

2.3 削除: 列の中抜けが起きる

tag1 の'crash'を削除すると、その列が NULL になるだけで、tag2 や tag3 が詰め直されるわけではありません。

UPDATE bugs SET tag1 = NULL WHERE bug_id = 1 AND tag1 = 'crash';
SELECT bug_id, tag1, tag2, tag3 FROM bugs WHERE bug_id = 1;

 bug_id | tag1 | tag2 |    tag3
--------+------+------+------------
      1 |      | save | regression
(1 row)

1 件のバグが持つタグの集合は「tag1、tag2、tag3 のうち NULL でないものすべて」という形で、どの列が空いているかは行ごとに違います。「crash というタグが本当に無くなったか」を確認するにも、3 列すべてを見る必要があります。

2.4 一意性: 同じタグの重複をデータベースが防げない

同じ行の中で同じタグを複数の列に入れてしまうことも、データベースは防げません。

UPDATE bugs SET tag1 = 'auth', tag2 = 'auth' WHERE bug_id = 5;
SELECT bug_id, tag1, tag2, tag3 FROM bugs WHERE bug_id = 5;

 bug_id | tag1 | tag2 | tag3
--------+------+------+------
      5 | auth | auth |
(1 row)

'auth'というタグが同じ行に 2 回入ってしまいましたが、挿入も更新もエラーになりません。後の章で、この重複がタグ別の集計を狂わせる実例を確認します。

図: マルチカラム方式(上段)は列の本数だけ分岐が要るが、従属テーブル方式(下段)は常に 1 条件で済む。

3. 見つけ方 ― どんな兆候で気づくか

既存のデータベースの中にマルチカラムアトリビュートが無いかは、「同じ接頭辞に連番が付いた列が同じテーブルに複数ある」という条件でinformation_schemaから機械的に検出できます。

SELECT table_name, array_agg(column_name ORDER BY column_name) AS numbered_columns
FROM information_schema.columns
WHERE table_schema = 'public'
  AND column_name ~ '^[a-z_]+[0-9]+$'
GROUP BY table_name
HAVING count(*) >= 2
ORDER BY table_name;

 table_name | numbered_columns
------------+------------------
 bugs       | {tag1,tag2,tag3}
(1 row)

この問い合わせは、列名が「英字と連番」という形(正規表現^[a-z_]+[0-9]+$)に一致する列を集め、同じテーブルに 2 本以上あるものだけを残しています。phone1、phone2のような電話番号の列や、category1〜category3のような分類の列も同じ形で検出できます。

4. 使ってよい場合

「1 件に複数の値を持たせたい」という目的のうち、値の個数が本当に固定で、意味が列ごとに違う場合は、マルチカラムの形で持たせても問題ありません。たとえば「出荷元の郵便番号」と「配送先の郵便番号」のように、2 つの値がそれぞれ別の意味を持ち、入れ替えたり 3 つ目が増えたりすることが無いなら、origin_postal_codeとdestination_postal_codeという 2 本の列は正当な設計です。この回で問題にしているのは、tag1、tag2、tag3のように、列名の連番が「同じ意味の値を何個まで持てるか」という上限を表している場合です。値の個数に意味の違いが無く、単に「同じ種類の値がいくつかある」というときは、次の章の従属テーブルを使うべきです。

5. 解決策 ― PostgreSQL での正しい書き方

「1 件に複数の同じ種類の値を持たせたい」には、従属テーブル(親の行に従属する別のテーブル)を使います。サンプルのバグ管理データベースには、すでにこの形のtagsテーブルが用意されています。

CREATE TABLE tags (
  bug_id  bigint NOT NULL REFERENCES bugs (bug_id) ON DELETE CASCADE,
  tag     text NOT NULL,
  PRIMARY KEY (bug_id, tag)
);
CREATE INDEX ON tags (tag);

tagsテーブルは 1 件のバグにつき複数の行を持てるため、タグの個数に上限がありません。さらに主キーが(bug_id, tag)という組であるため、同じバグに同じタグを 2 回登録することもデータベース自身が防ぎます。

5.1 検索: 1 条件で済む

SELECT b.bug_id, b.summary FROM bugs b JOIN tags t ON t.bug_id = b.bug_id WHERE t.tag = 'performance';

タグがいくつに増えても、この条件文はWHERE t.tag = ?のまま変わりません。

5.2 追加: 行を INSERT するだけ

INSERT INTO tags (bug_id, tag) VALUES (1, 'urgent');
SELECT * FROM tags WHERE bug_id = 1 ORDER BY tag;

 bug_id |  tag
--------+--------
      1 | crash
      1 | save
      1 | urgent
(3 rows)

4 つ目、5 つ目のタグも同じINSERT文で増やせます。列を追加するALTER TABLEは不要です。

5.3 削除: 対象の行を DELETE するだけ

DELETE FROM tags WHERE bug_id = 1 AND tag = 'crash';
SELECT * FROM tags WHERE bug_id = 1 ORDER BY tag;

 bug_id |  tag
--------+--------
      1 | save
      1 | urgent
(2 rows)

削除してもほかのタグの行は影響を受けません。「中抜け」のような状態は最初から存在しません。

5.4 一意性: 複合主キーがそのまま保証する

bug_id=5 にはすでに'auth'というタグがあります。同じ組を再度挿入しようとすると、複合主キー(bug_id, tag)の一意性制約がこれを拒否します(わざとエラーになる例で確認します)。マルチカラム方式では防げなかった重複を、従属テーブルでは主キーの定義だけで防げます。

図: マルチカラム方式は列が別なので重複を検出できないが、従属テーブル方式は複合主キーがそのまま検出する。

6. PostgreSQL エンジンで考慮しておくこと

「列を 3 本に分けると、1 本の列で検索するより速いのでは」という疑問に、5 万件規模の合成データ(generate_seriesで生成、本物の計測)で答えます。bugsに 5 万件の合成行を追加し、タグも同じ件数だけ両方の方式に入れて、1 種類のタグ(50,000 件中 1 件だけに付く珍しいタグ)を検索する速度を比較します。

-- マルチカラム方式: tag1, tag2, tag3 それぞれにインデックスを作り、BitmapOrでまとめる
EXPLAIN (ANALYZE, BUFFERS)
SELECT bug_id FROM bugs WHERE tag1 = 'rare-tag' OR tag2 = 'rare-tag' OR tag3 = 'rare-tag';

 Bitmap Heap Scan on bugs (actual time=0.018..0.019 rows=1.00 loops=1)
   Recheck Cond: ((tag1 = 'rare-tag'::text) OR (tag2 = 'rare-tag'::text) OR (tag3 = 'rare-tag'::text))
   Buffers: shared hit=7
   ->  BitmapOr (actual time=0.014..0.014 rows=0.00 loops=1)
         ->  Bitmap Index Scan on bugs_tag1_idx (actual time=0.009..0.009 rows=1.00 loops=1)
         ->  Bitmap Index Scan on bugs_tag2_idx (actual time=0.002..0.002 rows=0.00 loops=1)
         ->  Bitmap Index Scan on bugs_tag3_idx (actual time=0.002..0.002 rows=0.00 loops=1)
 Execution Time: 0.026 ms

-- 従属テーブル方式: 1本のインデックスだけで検索する
EXPLAIN (ANALYZE, BUFFERS)
SELECT bug_id FROM tags WHERE tag = 'rare-tag';

 Bitmap Heap Scan on tags (actual time=0.009..0.009 rows=1.00 loops=1)
   Recheck Cond: (tag = 'rare-tag'::text)
   Buffers: shared hit=3
   ->  Bitmap Index Scan on tags_tag_idx (actual time=0.005..0.005 rows=1.00 loops=1)
 Execution Time: 0.016 ms

5 万件規模、キャッシュが温まった状態で、マルチカラム方式は 3 本のインデックスをBitmapOrで合成する必要があり 0.026 ミリ秒・バッファヒット 7 回、従属テーブル方式は 1 本のインデックスだけで済み 0.016 ミリ秒・バッファヒット 3 回でした。従属テーブル方式のほうが約 1.6 倍速く、必要なインデックスの本数も 3 本から 1 本に減っています。タグの本数がもっと増えれば、マルチカラム方式はインデックスの本数も検索条件の OR の数も増え続けますが、従属テーブル方式はどちらも変わりません。

さらに、2.4 で見た重複('auth'が 2 列に入った状態)がどう影響するかを、タグ別の集計で確認します。

-- 従属テーブル(重複が無い): 正しい集計
SELECT tag, count(*) FROM tags GROUP BY tag ORDER BY tag;
     tag     | count
-------------+-------
 auth        |     1
 ...

-- マルチカラム方式(bug_id=5でtag1=tag2='auth'の重複がある)
SELECT tag, count(*) FROM (
  SELECT tag1 AS tag FROM bugs WHERE tag1 IS NOT NULL
  UNION ALL SELECT tag2 FROM bugs WHERE tag2 IS NOT NULL
  UNION ALL SELECT tag3 FROM bugs WHERE tag3 IS NOT NULL
) t GROUP BY tag ORDER BY tag;
     tag     | count
-------------+-------
 auth        |     2
 ...

マルチカラム方式では、2.4 で作ってしまった重複がそのまま集計に乗り、'auth'の件数が実際の 2 倍(1 件のはずが 2 件)に数えられています。従属テーブル方式では主キー制約がそもそも重複を防いでいるため、この種の数え間違いは構造的に起こりません。

図: 5 万件規模の実測で、従属テーブル方式はマルチカラム方式よりも速く、インデックスも 1 本で済む。

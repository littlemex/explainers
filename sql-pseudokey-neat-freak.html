シュードキー・ニートフリーク ― ID の欠番を埋める

主キーの欠番は壊れた状態ではなく、トランザクションが正しく動いている証拠であり、埋める必要はない

← SQL シリーズ目次へ

この回の前提: 第 04 回 IDリクワイアド (identity 列とシーケンスの基本)

この回が答える問いは「主キーの番号に欠番 (歯抜け) ができたとき、それを詰め直すべきか」です。結論を先に言うと、詰め直すべきではありません。欠番はロールバックやキャッシュといった正常な仕組みが生み出す自然な結果であり、無理に詰め直そうとすると外部キーで参照している他の行を壊します。この回では、実際に欠番ができる 2 つの仕組みを実機で再現し、詰め直しがなぜ危険か、そして「連番が欲しい」という本当の要求には row_number() や業務番号という別の道具を使うべきことを確認します。

1. 目的 ― 何をしたかったのか

主キーに GENERATED ALWAYS AS IDENTITY のような連番を使うと、新しい行には次の番号が自動的に振られます。多くの人は、この番号が「1, 2, 3, 4, 5...」と欠けなく並んでいることを期待します。実際にテーブルを眺めていて 3 の次が 5 になっている (4 が無い) のを見つけると、「データが壊れているのでは」「詰めて見た目を整えたい」という気持ちになるのは自然なことです。

2. アンチパターン ― どう書いてしまい、何が壊れるか

2.1 ロールバックは取り消されず、欠番だけが残る

サンプル DB の products テーブルは現在 3 件 (id は 1, 2, 3) です。ここで、挿入したもののロールバックする操作をはさんでみます。

SELECT max(product_id) AS current_max FROM products;
 current_max
-------------
           3

BEGIN;
INSERT INTO products (product_name) VALUES ('Will Rollback') RETURNING product_id;
 product_id
------------
          4
ROLLBACK;

INSERT INTO products (product_name) VALUES ('After Rollback') RETURNING product_id;
 product_id
------------
          5

SELECT product_id, product_name FROM products ORDER BY product_id;
 product_id |    product_name
------------+---------------------
          1 | Open RoundFile
          2 | Visual TurboBuilder
          3 | ReConsider
          5 | After Rollback

ロールバックした行は無かったことになりましたが、その行に振られた番号 4 は消費されたままで、次の挿入は 5 から始まります。これは PostgreSQL の公式ドキュメントにも明記されている仕様で、nextval の呼び出しはトランザクションのロールバックの影響を受けません。複数のトランザクションが同時に番号を取りに来たときに、ロールバックのたびに番号を数え直していたら、お互いが足を引っ張り合って性能が大きく落ちてしまうためです。

図: ロールバックされた行の番号だけが消費され、次の行は 1 つ飛んだ番号から始まる。

2.2 CACHE はセッションをまたぐと穴を作る

シーケンスには CACHE という設定があり、1 回のアクセスで複数の番号をまとめて確保することで、何度も内部テーブルを更新するコストを避けられます。しかし、確保した番号を使い切る前にセッションが終了すると、その番号は失われます。CACHE 10 のシーケンスに対して、3 つの別々の接続 (psql の \c で再接続すると、サーバー側では新しいバックエンド接続になる) から 1 回だけ nextval を呼んだ結果が次のとおりです。

CREATE SEQUENCE demo_cache_seq CACHE 10;

-- 接続 A: nextval を 1 回呼ぶ
SELECT nextval('demo_cache_seq');
 nextval
---------
       1

\c (ここで新しいバックエンド接続になる)
-- 接続 B: nextval を 1 回呼ぶ
SELECT nextval('demo_cache_seq');
 nextval
---------
      11

\c (また新しいバックエンド接続になる)
-- 接続 A': nextval を 1 回呼ぶ
SELECT nextval('demo_cache_seq');
 nextval
---------
      21

接続 A は 1〜10 を確保したのに 1 しか使わずに終了し、2〜10 の 9 個が失われました。接続 B も同様に 11〜20 を確保して 11 だけを使っています。これは PostgreSQL の公式ドキュメントが明示している挙動そのもので、ドキュメントに載っている例 (cache=10 のとき、セッション A が 1..10 を確保して nextval=1 を返し、セッション B が 11..20 を確保して nextval=11 を返す) と、この回で実際に確認した結果が一致します。

図: CACHE で確保した番号のうち、使われなかった分はセッション終了とともに失われ、穴になる。

3. 見つけ方 ― どんな兆候で気づくか

欠番そのものは、連番と実際の値を比較すれば簡単に見つけられます。generate_series() で 1 から最大値までの連番を作り、実テーブルと左外部結合することで、存在しない番号だけを抜き出せます。

SELECT g.id AS missing_id
FROM generate_series(1, (SELECT max(product_id) FROM products)) AS g(id)
LEFT JOIN products p ON p.product_id = g.id
WHERE p.product_id IS NULL;

 missing_id
------------
          4

また、欠番ができやすい設定になっていないかを事前に確認するには、pg_sequences カタログビューで cache_size を見ます。1 より大きい値は、セッションをまたぐ使われ残りが発生しやすい設定です。

SELECT schemaname, sequencename, cache_size, last_value
FROM pg_sequences WHERE schemaname = 'public' ORDER BY sequencename;

 schemaname |      sequencename       | cache_size | last_value
------------+-------------------------+------------+------------
 public     | accounts_account_id_seq |          1 |          4
 public     | bugs_bug_id_seq         |          1 |          5
 public     | comments_comment_id_seq |          1 |          4
 public     | demo_cache_seq          |         10 |         30
 public     | products_product_id_seq |          1 |          5

さらに、列が GENERATED ALWAYS AS IDENTITY なのか、それとも詰め直しの余地がある普通の列なのかは pg_attribute.attidentity で確認できます。a は GENERATED ALWAYS、d は GENERATED BY DEFAULT、空文字は identity 列ではないことを示します。

SELECT c.relname AS table_name, a.attname AS column_name, a.attidentity
FROM pg_attribute a JOIN pg_class c ON c.oid = a.attrelid
WHERE c.relname IN ('products','legacy_orders') AND a.attnum > 0 AND NOT a.attisdropped
ORDER BY c.relname, a.attnum;

  table_name   | column_name  | attidentity
---------------+--------------+-------------
 legacy_orders | order_id     |
 legacy_orders | customer     |
 products      | product_id   | a
 products      | product_name |

4. 使ってよい場合

主キーの欠番を詰め直してよい場面はありません。ただし、「連続した番号を見たい」という元々の要求自体は正当なことが多く、それを別の手段で満たすのは問題ありません。たとえば、画面に「1 件目、2 件目、3 件目...」という表示用の連番を出したいだけであれば、主キーとは無関係にその場で振り直せる row_number() を使えば済みます。主キーの値そのものを連続させる必要はどこにもないのです。

5. 解決策 ― PostgreSQL での正しい書き方

5.1 詰め直しがなぜ危険かを実機で確認する

まず、詰め直しが本当に危険かどうかを確認します。products.product_id のように GENERATED ALWAYS AS IDENTITY で定義された列は、そもそも直接の UPDATE を PostgreSQL 自身が拒否します。

UPDATE products SET product_id = 99 WHERE product_id = 2;
ERROR:  column "product_id" can only be updated to DEFAULT
DETAIL:  Column "product_id" is an identity column defined as GENERATED ALWAYS.

これは identity 列が持つ組み込みの防御です。これを体感するために、同じ危険を identity の保護が無い素朴な bigint 主キーのテーブルで再現してみます。

CREATE TABLE legacy_orders (
  order_id   bigint PRIMARY KEY,
  customer   text NOT NULL
);
CREATE TABLE legacy_order_items (
  item_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id  bigint NOT NULL REFERENCES legacy_orders(order_id),
  item_name text NOT NULL
);
INSERT INTO legacy_orders VALUES (1,'alice'), (2,'bob'), (4,'carol');
INSERT INTO legacy_order_items (order_id, item_name) VALUES (2, 'widget');

ここで order_id には 3 が欠番です。誰も参照していない 4 番を 3 番に詰め直す操作は、一見何も問題なく成功します。

UPDATE legacy_orders SET order_id = 3 WHERE order_id = 4;
UPDATE 1
SELECT * FROM legacy_orders ORDER BY order_id;
 order_id | customer
----------+----------
        1 | alice
        2 | bob
        3 | carol

しかし 2 番は legacy_order_items から参照されています。これを空いている番号 5 に詰め直そうとすると、外部キー制約がそれを拒否します。

UPDATE legacy_orders SET order_id = 5 WHERE order_id = 2;
ERROR:  update or delete on table "legacy_orders" violates foreign key constraint "legacy_order_items_order_id_fkey" on table "legacy_order_items"
DETAIL:  Key (order_id)=(2) is still referenced from table "legacy_order_items".

「誰も参照していない番号なら詰めても安全」という判断は、その時点では正しくても、後から新しい参照行が増えれば成り立たなくなります。詰め直しという操作自体が、将来にわたって安全かどうかを保証できない時限爆弾になるのです。

図: 参照されている主キーの値を変更しようとすると、外部キー制約がそれを拒否する。

5.2 連番が欲しいだけなら row_number()、業務番号は別の仕組みで

表示用の連番であれば、主キーに触れずに row_number() ウィンドウ関数で振れます。主キーに欠番があっても、表示上は常に 1 から連続した番号になります。

SELECT row_number() OVER (ORDER BY product_id) AS display_no, product_id, product_name
FROM products ORDER BY product_id;

 display_no | product_id |    product_name
------------+------------+---------------------
          1 |          1 | Open RoundFile
          2 |          2 | Visual TurboBuilder
          3 |          3 | ReConsider
          4 |          5 | After Rollback

請求書番号のような「業務上意味のある番号」は、主キーとは別の列・別の採番規則として設計します。主キーは「行を一意に指し示すための内部的な値」であり、業務番号は「人間や外部システムが参照する、別の一意性のルールを持つ値」です。この 2 つを同じ列に混ぜてしまうと、どちらの要求 (効率的な内部参照 / 連続した業務上の意味) も満たせなくなります。

CREATE TABLE invoices (
  invoice_id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  invoice_number text UNIQUE NOT NULL,
  account_id     bigint NOT NULL REFERENCES accounts(account_id)
);
CREATE SEQUENCE invoice_number_seq;
INSERT INTO invoices (invoice_number, account_id)
VALUES ('INV-' || to_char(nextval('invoice_number_seq'), 'FM000000'), 1);

SELECT invoice_id, invoice_number FROM invoices;
 invoice_id | invoice_number
------------+----------------
          1 | INV-000001

このように分けておけば、内部的な主キーに欠番が出ても業務番号の運用ルール (連番である必要があるか、年度でリセットするか、など) を自由に設計できます。なお、公式ドキュメントも述べているとおり、本当に欠番の無い連番 (gapless) が必要な場合は、専用のカウンタ用テーブルを排他ロックして振る方法がありますが、これは複数のトランザクションが同時に番号を取りに来るたびに待ち行列ができるため、シーケンスより大きな性能上の代償を払うことになります。「欠番が無いこと」が本当に業務上の要件なのかを、まず疑うべきです。

6. PostgreSQL エンジンで考慮しておくこと

PostgreSQL の公式ドキュメントは、シーケンスについて「nextval と setval の呼び出しは決してロールバックされないため、シーケンスオブジェクトは『欠番の無い』番号付けが必要な場合には使えない」と明言しています。つまり欠番が出ることは不具合ではなく、シーケンスという仕組みそのものの前提です。ロールバックのたびに番号を巻き戻していたら、同時に動く他のトランザクションの番号発行をブロックしてしまい、同時実行性が大きく落ちます。欠番を許すことと引き換えに、ロックを取らずに高速に番号を発行できているのです。

同じ理由で CACHE も、複数セッションが同時に番号を取りに来る場面での競合を減らすための仕組みです。CACHE の値を大きくすると、シーケンスの内部テーブルへのアクセス回数は減って速くなりますが、セッションが番号を使い切らずに終了したときに失われる番号の最大数も増えます。欠番を気にして CACHE 1 に固定するのではなく、「欠番は起きてよい」という前提を受け入れたうえで、同時実行性と欠番の大きさのバランスで値を選びます。

主キーに GENERATED ALWAYS AS IDENTITY を使うと、この回で確認したとおり直接の UPDATE がそもそも拒否されます (OVERRIDING SYSTEM VALUE は INSERT 時に明示的な値を許可するための構文であり、既存行の値を書き換える手段ではありません)。これは「主キーの値は、行を識別するための内部的な値であり、人間が手で調整するものではない」という設計意図を、PostgreSQL がデータ型のレベルで強制していると理解できます。古い serial 型はこの保護を持たないため、新しく列を作るときは GENERATED ALWAYS AS IDENTITY を使うことで、詰め直しの事故そのものを未然に防げます。

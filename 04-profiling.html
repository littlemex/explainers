NKI WORKSHOP ・ 04

プロファイラの読み方 ― 測ってから最適化する

Eager から Compile、Compile+NKI へ。当て推量ではなく、プロファイルでボトルネックを一意に特定する

0この記事の狙い

第 2 回で Roofline とカーネル融合を、第 3 回で FlashAttention を見てきました。理論上のギャップと、それを消す手法は分かった。では実際に書いたカーネルが本当にそのとおり速いのか、まだどこが遅いのかは、どうやって知るのでしょうか。答えは「測る」ことです。

一言でいうと
最適化は当て推量ではできません。プロファイラで「いま何が起きているか」を測ってから、初めて手を動かす ― これが measure before optimize の原則です。この章では (A) Eager → Compile → Compile+NKI の 3 段階比較で host 側のオーバーヘッドを切り分ける方法、(B) エンジン別の稼働率を読んでボトルネックのエンジンを見分ける方法、(C) 第 2 回の hardware entitlement と実測のギャップを数値化して最適化の出発点にする流れ、の 3 つを扱います。
先に結論(NKI Workshop の実測の傾向)。同じ処理を 3 段階の実装で回すと、プロファイル上の見え方が段階的に変わっていきます。
・Eager 実行: 演算 1 つひとつが個別に dispatch (確保→起動→書き込み→host 復帰) され、実演算そのものよりdispatch のオーバーヘッドが支配的になりやすい。
・torch.compile: グラフ全体を融合してから実行するため、host 側の dispatch オーバーヘッドの大半が消える。
・Compile + NKI (カーネル融合): カーネル境界そのものを減らす (megakernel 化) ため、境界ごとの sync 待ちと DMA の再ステージングまで縮む。
(傾向はワークショップの実測に基づく概算。絶対値は条件により変わるため本文では相対的な傾向として扱います)
1. 【体験】Eager → Compile → Compile+NKI ― host overhead を消す 2. プロファイラの二階層 ― システムとデバイス 3. hardware entitlement とのギャップを測る 4. 【体験】エンジン別稼働率を読む 5. DMA キューと sync ― トレースの中身 6. 反復ループの実演 ― ビジーなエンジン、アイドルなエンジン 7. まとめ ― 測ってから最適化する

対象は AWS Trainium2。数値はワークショップの講義・実測に基づく概算です。第 2 回「Roofline とカーネル融合」と第 3 回「FlashAttention」を先に読むと理解が早いです。

1【体験】Eager → Compile → Compile+NKI ― host overhead を消す

最初の一歩は、同じ処理を 3 段階の実装で回し、プロファイル上の見え方の違いを比較することです。「刑事の捜査」のように段階を踏みます。

  1. Eager 実行: 各演算 (op) が個別に dispatch されます。確保 (alloc) → 起動 (launch) → HBM への書き込み → host への復帰、という手続きを演算ごとに繰り返す。この alloc / copy / kernel launch のオーバーヘッドが、実際の演算そのものより支配的になりやすい。
  2. torch.compile(backend="neuron"): グラフ全体を融合してから実行するため、host 側の dispatch オーバーヘッドの大半が消えます。ただし、コンパイル境界を跨ぐ eager 処理 (例: KV cache へのスライス代入) が aten::copy_ として残ることがあり、これは scatter_ 等で in-graph 化すると解消できます。
  3. Compile + NKI (カーネル融合): 別々の NKI カーネルを呼ぶたびに sync drain と DMA の re-staging (HBM 往復) が発生します。カーネル境界そのものを減らす (megakernel 化) と、この sync 待ちと re-staging が縮み、Arithmetic Intensity (演算/バイト) が跳ね上がります。
実演算 (compute) dispatch / host overhead (隙間)

3 つのボタンで段階を切り替えると、バーの全長 (相対的な所要時間) と色の比率 (演算と隙間の割合) が変わります。Eager は隙間 (オレンジ) が大半を占め、実演算 (緑) はごく一部。torch.compile に切り替えると隙間が縮み、Compile+NKI ではさらに縮んで、ほぼ演算だけの連続したバーになります。「再生」を押すと再生ヘッドが左から右へ流れ、いま隙間 (overhead) にいるか演算にいるかが下に表示されます。

読み方の原則。プロファイラの表は「次に何を直すべきか」を教えてくれます。aten::copy_ が支配的なら、コンパイル境界をまたぐ演算をグラフの内側に移す番。逆に model_default (NEFF の dispatch) が支配的で他がすべて小さいなら、host 側はもう十分に速く、デバイス側 (カーネルの内部) を見る番です。この判断がプロファイラの一番基本的な使い方になります。

2プロファイラの二階層 ― システムとデバイス

プロファイラには 2 つの階層があります。どちらを見るかで分かることが違います。

格言的な整理。システムプロファイラは「時間がどこへ行ったか」を教えます (host 側、CPU から見た視点)。デバイスプロファイラは「ハードウェアが何をしているか」を教えます (NeuronCore の内部、エンジンごとの視点)。前者を「空港の出発ロビー」(手続きと待ち時間)、後者を「実際に飛んでいる飛行機の中」(内部の稼働率) に例えられます。

システムプロファイラは PyTorch の torch.profiler.profile(...) で取得します。CPU と NeuronCore 両方のアクティビティを記録し、key_averages() で alloc / copy / kernel launch などに分類して集計できます。第 1 段の「Eager vs Compile」の違いは、主にこのシステムプロファイラで見えます。

デバイスプロファイラは、NKI カーネル単体、あるいはモデル全体を実行したときにデバイス上で生成されるトレース (profile.ntff 等) を読みます。UI (Neuron Explorer) で可視化するだけでなく、ディスク上の parquet ファイルを直接 pandas 等で読み込む方法もあり、これによりエージェントがプロファイルの数値を読み取って反復的に最適化するワークフローが可能になります。total_time、dma_active_time、tensor_engine_active_time、sync_engine_instruction_count、dma_transfer_count といったフィールドがそこに含まれます。

見た目の落とし穴。HBM スループットのグラフが「途切れる/存在しない」区間は、転送が無かった (ゼロ) と解釈してよいことが多いです。また、エンジンの実行区間の前後に現れるランダムな短いバーは、多くの場合ウォームアップであり、実計算ではありません。プロファイルを読むときはこの 2 点に注意すると誤読を避けられます。

コードとプロファイルイベントを結びつける「コードリンキング」という機能もあります。単一のカーネルファイルと NEFF/NTFF をまとめてアップロードした場合にのみ機能し、モデル全体のようなグローバルなコンテキストでは機能しないという制約があります。単体のカーネルを深掘りするときに使う道具と捉えておくと良いでしょう。

3hardware entitlement とのギャップを測る

第 2 回で「仕事量 ÷ ハード速度 = 理論上限」という考え方 (hardware entitlement) を学びました。プロファイラの実測値と、この理論上限を並べることで、初めて「あとどれだけ縮む余地があるか」が数値で言えるようになります。

やり方は第 2 回と同じです。やるべき仕事量 (FLOP) ÷ ハードウェアの速さ (FLOPS) = かかるべき時間。これを命令レベル (Tier1) と、カーネル全体レベル (Tier2) の両方で見積もり、プロファイラの実測とのギャップを取ります。

# 例: QK matmul と PV matmul (Attention の中心)
仕事量 = rows × cols × contraction_dim × 2  # ×2 は 乗算+加算
時間 = 仕事量 / エンジンのスループット  # これが理論上限 (Tier1/Tier2 entitlement)

# Attention 全体の entitlement (概念)
推定時間 ≈ QK matmul の時間 + PV matmul の時間 + softmax の時間  ← 3項を単純加算

この見積もりと、プロファイラが返す実測時間を並べると、「理論上 X のはずが実測 Y、ギャップは Z」という言い方ができるようになります。ギャップが大きいほど、まだ最適化の余地があるということです。第 3 回の FlashAttention のように、素朴な実装から始めて何段階か最適化を積むと、このギャップが徐々に縮んでいく ― という進み方になります。

Roofline との接続。第 2 回の Roofline も、実はこの entitlement と同じ道具の別の見せ方です。演算強度 (Arithmetic Intensity = FLOP ÷ 転送バイト数) を見て、ridge point (ハードウェア固有の折れ点) より低いか高いかで、compute-bound か memory-bound かを判定できます。ridge point の値自体もプロファイラから直接取得できるため、「紙と鉛筆の概算」と「実測のプロファイル」を同じ図の上で比較できます。

実際のワークフローはこう進みます。①CPU にオフロードされている演算を特定する、②既存のライブラリカーネルを適用できる箇所に適用する、③プロファイルを取得する、④Tensor Engine のギャップや DMA のスパース度を確認する、⑤最も効いているボトルネックを特定する。最後の一手は、多くの場合「仕事が多すぎる」か「エンジンが遊んでいる」かの二択に単純化して整理できます。仕事が多すぎるなら演算そのものを削る (アルゴリズム的な改善、低精度化)。エンジンが遊んでいるなら、次章以降で扱うタイリングやパイプライン化でその遊びを埋めます。

4【体験】エンジン別稼働率を読む

この記事の「絵で覚えて帰ってほしい 1 枚」です。NeuronCore は Tensor / Vector / Scalar / GP-SIMD という役割の違う専用エンジンの集まりで(第 1 回)、独立にスケジュールされ並列に動きます。プロファイラは「どのエンジンが今何をしているか」を可視化する道具です。

ビジー(稼働中) アイドル(遊休) ボトルネックとしてハイライト

横棒 1 本が 1 エンジンの稼働率 (相対・概念値) です。3 つのボタンで、典型的な 3 つのプロファイル像を切り替えられます。

  • 健全なプロファイル: 各エンジンがそれぞれの役割で高い稼働率を保ち、極端に遊んでいるエンジンが無い状態。
  • Vector がビジー / Tensor がアイドル: 第 1 回・第 3 回の Self-Attention の実演で実際に起きたパターン。softmax を担う Vector Engine が張り付いて busy な一方、行列積を担う Tensor Engine は次の入力を待って遊んでいる。これはstructural hazard ― あるエンジンの結果を別のエンジンが待つことで生じる、構造的な遊休です。
  • sync 待ちが多い: 複数のカーネル呼び出し (境界の多い構成) では、境界ごとに sync 命令が入り、全エンジンが同時にアイドルになる「drain」の谷が周期的に現れます。境界を減らす (megakernel 化) と、この谷自体が浅く・少なくなります。

いずれのパターンでも、一番稼働率の低いエンジンがボトルネックとは限らない点に注意してください。むしろ「ビジーすぎるエンジンが、他のエンジンを待たせている」ケースの方が多く、赤くハイライトされたエンジンが次に手を入れるべき箇所です。

読み方の型。①各エンジンの稼働率を並べて見る。②極端にビジーなエンジンと、極端にアイドルなエンジンを両方見つける。③アイドルな方を疑うのではなく、ビジーな方が何を作っていて、アイドルな方が何を待っているかを確認する。④「1 つずつ潰す」反復ループに入る (次章で実演)。

5DMA キューと sync ― トレースの中身

エンジンの稼働率の裏側で、DMA と sync が具体的に何を記録しているかをもう少し具体的に見ておきます。

第 1 回で見た DMA subsystem の内部動作をおさらいすると、DMA はトリガー → descriptor 生成 → キュー投入 → DMA 実行という手順を踏みます。プロファイラの DMA タイムラインは、このキューに何がどれだけ溜まっているか、転送 (transfer) が何件あったかを記録します。DMA transfer 数が多いことは、それ自体が悪いわけではありませんが、転送 1 件あたりのサイズが小さい (DMA フラグメンテーション) 場合は、固定オーバーヘッドの償却が効かず、achieved 帯域が落ちます。第 5 回のタイリングで、この転送サイズの設計を掘り下げます。

sync 命令数は、カーネル境界やエンジン間の待ち合わせのたびに挿入される同期の回数です。複数の NKI カーネルを個別に呼ぶ構成 (例: 4 つのカーネルに分かれた構成) と、単一の融合カーネル (megakernel) を比較すると、sync 命令数・カーネル境界の数・DMA フラグメンテーション・GP-SIMD のプロローグ (起動準備) の回数のいずれも、境界を減らした側で明確に少なくなります。

# Arithmetic Intensity (AI) = 演算数 ÷ 転送バイト数
AI が低い → memory-bound の傾向  # データ移動がボトルネック
AI が高い → compute-bound の傾向  # 演算そのものがボトルネック

# カーネル境界を減らす(融合)と AI が跳ね上がる傾向
複数カーネル呼び出し(境界多)  ← AI 低め
単一の融合カーネル(境界少)  ← AI 高め(HBM 往復が減る分だけ)

ここで効いてくるのが、PyTorch のオペレータとデバイスイベントの対応関係です。nn.Linear は Tensor Engine の matmul 命令に、softmax や reduction は Vector Engine の reduce/activation 系命令に、RMSNorm は tensor-tensor と reduce の組み合わせに対応します。プロファイル上のイベント名から「これは元のモデルのどの層に対応するか」を逆引きできると、直すべき箇所への距離が一気に縮まります。

6反復ループの実演 ― ビジーなエンジン、アイドルなエンジン

プロファイラの使い方は、1 回見て終わりではありません。「測る → 直す → もう一度測る」を繰り返す反復ループです。第 3 回の FlashAttention の実装を、実際にこの反復ループで最適化した例をおさらいします。

Self-Attention の実装をタイリングして融合したあと、プロファイルを取ると 2 つの改善余地が見つかりました。

  1. Vector Engine が非常にビジー: softmax の正規化 (row max の減算、指数関数、行合計) をすべて Vector Engine が担っており、負荷が集中していた。
  2. Tensor Engine がアイドル: Vector Engine の処理が終わるまで、次の matmul を始められない ― structural hazard による待ちが発生していた。

この 2 つを1 つずつ潰していきます。まず、softmax の除算をタイルごとに何度も行う代わりに、線形性を利用して除算を最後まで遅延させ、除算の回数そのものを減らす (アルゴリズム的な改善)。次に、正規化・指数関数・行合計という 3 つの操作を、Scalar Engine の 1 命令 (bias 適用 + activation + 並列 reduction) にまとめてオフロードし、Vector Engine の負荷を軽減する。さらに、PV matmul 前の value 行列の transpose を BF16 にダウンキャストし、Tensor Engine の transpose 自体を速くする (第 8 回の低精度化の先取り)。

この実演から持ち帰ってほしいこと。プロファイルは「次に何を直すべきか」を教えてくれますが、一度に全部は直しません。見つけた改善余地を 1 つずつ潰し、直したらもう一度測る。この反復こそが「measure before optimize」の実際の運用です。段階を飛ばして最初から最終形を目指すと、どの変更が何に効いたのか分からなくなります。
MFU が思ったほど上がらないこともある(クリックで展開)

高速化の大半が「複数エンジンを同時に働かせること」から来ている場合、Tensor Engine 単体の利用率 (MFU) 自体はさほど上がらないことがあります。これは KPI の意味を丁寧に解釈する必要があるという教訓で、MFU が低いからといって「まだ余地がある」と短絡的に判断せず、どのエンジンがボトルネックだったかを見て評価するべきです。

7まとめ

「測ってから最適化する」という原則を一枚に整理します。

論点要点
Eager→Compile→Compile+NKI3 段階を比較すると host dispatch overhead の縮み方が段階的に見える。alloc/copy/kernel launch の数が減っていく
二階層のプロファイラシステムプロファイラ=「時間がどこへ行ったか」(host)。デバイスプロファイラ=「ハードウェアが何をしているか」(NeuronCore 内部)
hardware entitlement仕事量÷ハード速度=理論上限。実測とのギャップを数値化することが最適化の出発点になる
エンジン別稼働率ビジーなエンジンとアイドルなエンジンを両方見る。アイドルの原因は多くの場合 structural hazard(他エンジン待ち)
DMA/syncDMA フラグメンテーション(小転送の多発)と sync 命令数(カーネル境界のたび)は、境界を減らす(融合)ほど縮む
反復ループボトルネックを1つずつ潰し、直すたびに再度測る。一度に全部を直そうとしない
結論。プロファイラは当て推量を消す道具です。(A) Eager→Compile→Compile+NKI の 3 段階比較で host 側のオーバーヘッドを切り分け、(B) エンジン別稼働率を読んでビジーなエンジンとアイドルなエンジンを見分け、(C) 第 2 回の hardware entitlement と実測のギャップを数値化してターゲットを持つ。この 3 つがあれば、「なんとなく遅い」から「理論上 X のはずが実測 Y、ギャップは Z、原因はこのエンジン」と言えるようになります。
プロファイルを読む力は、この記事だけで完結しません。ここで得た「どのエンジンが遊んでいるか」「どこで HBM を往復しているか」という診断結果が、次章以降 ― タイリング、データレイアウト、ソフトウェアパイプライン ― の対策そのものの入口になります。次回はまず、オンチップに載らないデータをどう分割するか、タイリングを掘り下げます。

AWS Trainium で LLM をサービングするとき、モデルを移植するとは何をすることなのか

← explainers トップへ戻る

GPU では Hugging Face のモデルをそのまま推論エンジンに載せられることが多いのに、Trainium では対応モデルが明示的に列挙されていて、そこに無いモデルには自分で実装を足す必要があります。この「足す」作業の中身を、スタックの構造から具体的に分解するシリーズです。実装する人には工程表として、経路を選ぶ人には判断材料として書いています。

このシリーズの結論を先に

移植コストは 3 層に分かれます。計算の表現 (その数式を、選んだコンパイル経路が受け付ける形で書けるか)、サービング契約 (paged KV への読み書きと並列分割の作法)、状態の契約 (attention の KV 以外の状態をどこに置くか)。

コスト層難しさを決めるものコンパイル経路を替えると
① 計算の表現コンパイラが受け付ける演算とグラフ構造の範囲下がる
② サービング契約サービングの設計 (paged KV・バケット・並列)変わらない見込み
③ 状態の契約ランナーが用意している状態の置き場変わらない見込み

だから「別のコンパイル経路にすれば移植が要らなくなる」は成り立ちません。下がる見込みがあるのは①だけです。しかも①の中で下がるのは「通すための書き換え」だけで、実用的な性能に必要な数式の再構成は残ります。そして現在地としては、プロセス内で経路を差し替える道はライブラリ側の対応待ち、プロセスを分けて橋を架ける道は運搬コストが未解決 (2.6 MB 級の部分グラフ 1 個での実測でカーネルの約 30 倍) です。

実装する立場なら、01 で地図を入れて、03 が本体です (チェックリストは §9)。詰まったら 02 §9 のエラー切り分け表。検証の工程は 05 §4-6 と 08。

現在地の確認方法は 2 つです。プラグインの feature matrix の torch.compile (native PyTorch) の行と、ランタイム兼カーネル基盤ライブラリの配布物に非 XLA の降ろし方のモジュールが含まれるかどうか (詳細は 06 §5)。この 2 つを見れば、本シリーズの時点依存の結論が更新されたかどうかが分かります。

 04 ・ コストの構造

ポーティングの 3 層モデル

行数は移植コストの代理変数にならない。既存のカーネル語彙に収まるモデルと収まらないモデルを並べ、素直な再帰がコンパイラに通らないときに数式そのものを書き換える作業を具体的に示す。経路を替えて消えるのは「通すための書き換え」だけで「速くするための書き換え」は残る理由も。最後に、重み不要でモデリングコードだけで答えられる「見積もりの 2 つの問い」に落とす。

 05 ・ 誤解を潰す

eager と compile ― 誤解と検証の最短経路

eager なら移植は要らないのか。答えは要る。境界は eager と compile の間ではなく、KV キャッシュとバッチングを誰が持つかにある。実装者にとっての本題は後半で、CPU の 2 モードから実機へという工程順序をここで固める。逆順は最も高くつく。

 06 ・ 経路差し替えの壁

なぜ経路は差し替えられないのか

経路を差し替えるスイッチは実装されているのに動かない。理由が 3 つ重なっていて、うち 1 つは PyTorch のディスパッチ機構に由来する。1 つのキーに backend fallback は 1 つしか登録できず、外部実装は支援 API の都合で同じキーに集まるので、同居できない。何を待っているのかを正確にする。

 07 ・ 橋を架ける

NEFF を境界にできるか ― 機構はある、運搬が高い

プロセスを分ければディスパッチキーは衝突しない。公開イメージには NEFF をロードして入出力契約を問い合わせ実行する API が同梱されており、部品は揃っている。全体モデルの注入が成立せず部分グラフなら成立する理由 (署名の所有権が逆になる) と、残る課題 ― 現状の API はホストのバッファ経由でコピーするため、データ移動がカーネルの約 30 倍 (2.6 MB 級の部分グラフ 1 個での実測)。

 08 ・ 測り方

この上で出した数字を信じてよい条件

実装でも判断でも、数字を出す前・受け取る前に読む回。非同期実行が既定なので、素朴なストップウォッチは「積む時間」と「実行する時間」の遅い方を測る。汚染を見抜く兆候は「仕事量を増やしても時間が動かない」。cosine を一致の証拠にしてはいけない理由 (fp32 で 1 を超える)。不変条件で正しさを縛る方法と、GPU と比べるときに揃えるもの。

第 1 章 値段の構造 — 安いモデルはいつ安いのか

この章の 3 行 モデルの値段は「読ませた量」と「書かせた量」で別々に決まり、出力のほうが 5 倍ほど高い。 だから同じ 1 リクエストでも、長文を読ませる仕事と長文を書かせる仕事では、どのモデルが安いかが入れ替わる。 自前の GPU は時間で課金されるので、この物差しでは測れない。別の物差しは第 3 章で作る。

トークンと、2 つの値段

モデルへの支払いは「トークン」という単位で数える。おおよそ単語や文字の断片で、日本語なら 1 文字が 1 トークン前後、英語なら 1 単語が 1 トークン強になる。100 万トークンは日本語で 60 万〜100 万文字ぐらい、 文庫本にして 5 冊前後だと思えばよい。

大事なのは、値段が入力と出力で別だということ。入力はモデルに読ませた文章で、出力はモデルが 書いた文章だ。多くのモデルで出力は入力の 5 倍前後高い。読むより書くほうが計算量が多いからで、 この非対称が以降ずっと効いてくる。

もう 1 つ、キャッシュ読みという値段がある。直前と同じ文章をもう一度読ませたとき、 提供側は前回の計算結果を取り置きしておけるので、10 分の 1 の値段で済ませてくれる。会話を何往復も するエージェントは毎回それまでの履歴を全部送り直すので、この割引が効くかどうかで費用が桁で変わる。 この段落は当初「自前の箱にはこの割引が使えない」と締めていたが、それは誤りだった。 箱自身の prefix cache も実測してあり (第 9 章)、キャッシュ読みトークンは 1 Mtok あたり $0.0188、 新規トークンの $0.2295 に対して 8.2% — API が付ける「10 分の 1」とほぼ同じ幅の割引を箱も持っている。 違うのは誰にでも同じ幅でつくわけではないことで、この割引が誰につき誰につかないかは第 7 章の主題になる。

デモ: 読ませる量と書かせる量を動かしてみる

下の 2 つのスライダーを動かすと、1 リクエストあたりの費用が変わる。まず API 同士を比べてほしい。 出力を長くしていくと差が開き、入力を長くしていくと差が縮む。これが「安いモデルは常に安い」ではない、 という最初の誤解つぶしになる。

1 リクエストの費用

動かして見えること

  • 出力を伸ばすと、値段の差はほぼモデルの出力単価の比になる。 書かせる仕事では premium と haiku の差は 10 倍に開く。
  • 入力を伸ばすと、差は入力単価の比に近づく。 premium と haiku の入力単価の比も 10 倍だが、 grok-4.6 のように出力が安く入力が高いモデルは順位が入れ替わる。
  • だから「どのモデルが安いか」は仕事の形で決まる。 「安いモデル」という言い方は、 どんな形の仕事についてなのかを言わないと意味を持たない。
ここで自前の GPU を並べないのはなぜか 自前の箱は時間で課金される。1 時間 15.2174 ドルで、リクエストが来ても来なくても同じ額が出ていく。 だから「1 リクエストいくら」は、その 1 時間に何件処理したかを決めない限り定まらない。 API の $/Mtok と箱の $/h を同じ表に並べると、以後ずっと単位の混乱を引きずることになるので、 ここでは並べない。第 3 章で、測ったスループットから箱の単価を導く手順を作る。

この章で壊しておきたい誤解

よくある思い込み実際は
安いモデルはどんな仕事でも安い入力と出力の比率で順位が入れ替わる。上のデモで grok-4.6 を長い出力で使うと premium 以外に勝つ場面がある
トークンは 1 種類の単位読む (prefill) と書く (decode) は別の工程で、計算の性質も値段も違う。第 3 章で自前の箱を測ると 19 倍の速度差が出る
同じ文章を何度送っても費用は同じAPI にはキャッシュ読みの割引がある。多ターンのエージェントではこれが主役になるが、全ての層に付いているわけではない (第 7 章)
自前の GPU は「1 リクエストいくら」で比べられる時間課金なので、稼働率と処理件数を決めない限り単価は存在しない

次の章へ

値段の構造がわかったので、次は品質の話になる。安いモデルに流していいのは「安いモデルでも解ける仕事」 だけだが、それはどうやって見分けるのか。そして見分けられたとして、いくら安くなるのか。 実際に測ったら、2 つ目の答えが予想よりずっと小さかった。

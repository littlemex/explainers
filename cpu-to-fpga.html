この回の前提: 第 09 回 メモリとアドレス、第 19 回 テストとデバッグ

これまでの回で組み立てた rj32 は、Digital というシミュレータの中で動く論理回路図でした。この回路図を実在する FPGA (Field-Programmable Gate Array、書き換え可能なチップ) の上で動かすには、図をテキストの Verilog に書き出し、シミュレータにしか無い部品を実際のチップの部品に置き換え、専用のツール群に通して配線情報 (ビットストリーム) に変換する必要があります。rj32 の開発者自身が公開している移植手順を手がかりに、この道のりと、そこで初めて現れる制約を見ていきます。

1. シミュレータの中だけでは終わらない

結論を先に言うと、Digital の画面の中で「正しく動いた」ことと、実在するチップの上で動くことの間には、まだ埋めなければならない溝があります。Digital のシミュレータは、配線の遅延や部品の個数を厳密に数えずに、論理的な動作だけを再現しています。実際の FPGA では、信号が配線を伝わる時間や、使える部品の数に限りがあり、どちらも有限です。

rj32 の開発者は、この溝を埋める手順を tutorials/digital_to_fpga101 という資料で公開しています。そこでは「Digital の回路図を Verilog に書き出す」「シミュレータ専用の部品を実チップの部品に差し替える」「専用のツール群でチップの配線情報に変換する」という 3 段階が踏まれています。

図: Digital の回路図から実チップに届くまでに、3 つの段階が必要になる。

2. Verilog への書き出しと部品の差し替え

Digital には回路図を Verilog (ハードウェア記述言語の 1 つ) に書き出す機能があります。書き出された hdl/rj32.v を見ると、ファイルの先頭に「Generated by Digital. Don't modify this file! (Digital が生成した。このファイルは変更しないこと)」という注記があり、内容も DIG_D_FF_AS_1bit や DIG_Counter_Nbit のように、Digital が内部で使っている部品名のままの、構造を保った Verilog になっています。

ところがシミュレータの中だけに存在する部品 (ブロック RAM の黒箱表示など) は、そのままでは実チップの資源に対応しません。そこで rj32 の hdl/mem.v は、プログラムメモリ用はクロックの立ち下がりで、タイルマップ用のメモリはクロックの立ち上がりで、それぞれ $readmemh で初期値を読み込んだ上で出力を確定させる、実際に合成できる形で手書きしています。チュートリアルのスライドはこれを「シミュレータ内蔵の回路を Verilog で上書きする (overriding embedded circuits)」と呼んでいます。

module prog_bram (
    input             clk_i,
    input       [7:0] addr_i,
    output reg [15:0] data_o
);
reg [15:0] mem [0:255];
initial $readmemh("./test.hex",mem);
always @(negedge clk_i) begin
    data_o <= mem[addr_i];
end
endmodule

図: Digital が出力した構造的な Verilog と、実チップ用に手書きした Verilog を組み合わせる。

3. FPGA の中身 ― LUT ・ フリップフロップ ・ BRAM

FPGA (Field-Programmable Gate Array) は、あらかじめ汎用的な部品をたくさん並べておき、使う人が「どう繋ぐか」を後から書き込めるチップです。主な部品は 3 種類あります。LUT (look-up table) は、数本の入力に対する出力をあらかじめ表にして書き込んでおける小さな記憶で、これで組み合わせ回路の論理式を表現します。フリップフロップは第 5 回で見たとおり、クロックの立ち上がりで値を確定させる記憶です。BRAM (ブロック RAM) は、LUT を並べて作るよりずっと効率よくメモリを実現できる専用の記憶ブロックです。

Yosys (合成ツール) の役割は、Verilog に書かれた論理 (AND や OR、加算器、レジスタなど) を、これら 3 種類の部品の組み合わせに変換することです。第 20 回の冒頭で見た hdl/mem.v のような「クロックエッジ (立ち上がりまたは立ち下がり) で出力が確定する、アドレス付きの記憶」という書き方を Yosys が認識すると、LUT を並べるのではなく、専用の BRAM ブロックに割り当てます。

図: FPGA の中にあらかじめ用意された 3 種類の部品に、設計を割り当てていく。

4. オープンなツールチェーンの各段階

rj32 のチュートリアルは、ice40 系の FPGA (IceSugar や IceBreaker のボード) 向けに、オープンソースのツール一式だけで Verilog からチップへの書き込みまでを完成させる手順を示しています。各段階は、前の段階の出力を次の段階が受け取る、はっきりした受け渡しの形になっています。

図: Verilog から実機書き込みまで、役割がはっきり分かれた 4 つの段階を順に通す。

5. クリティカルパスと最高クロック

Digital のシミュレータの中では、クロックの周波数をいくつにしても論理的には同じ結果になります。実チップでは、2 つのフリップフロップの間にある組み合わせ回路 (LUT の連なり) を信号が伝わるのに、必ずわずかな時間がかかります。その中でもっとも時間がかかる経路をクリティカルパスと呼び、クロックの周期はこの経路の遅延より長くしなければなりません。NextPNR (配置配線ツール) が「すべての回路がタイミング制約を満たすことを確認する」のは、まさにこのクリティカルパスの遅延を計算し、指定したクロック周波数で間に合うかを検証する作業です。

Digital 公式マニュアル 4.3 章は、BASYS3 ボード向けの書き出しについて「回路のクロック周波数が低ければ分周回路を自動で挿入するが、4.7MHz を超える場合は Artix-7 の MMCM (クロック生成専用の回路) を使う」と説明しており、乗算器を使わない設計なら 30MHz まで動かせるとも述べています。rj32 の hdl/README.md も「icezprog でプログラムする場合は Makefile から -Os (サイズ最適化) を外すこと。最適化するとタイミングが崩れてエラーになる」と注意しています。どちらも、クロックやタイミングの余裕が、シミュレータの外に出た途端に実在する制約として現れる例です。

図: クロック周期は、最も遅い経路 (クリティカルパス) が間に合う長さに合わせて決める。

6. 実装のポイント

自動生成ファイルは直接編集しない。 hdl/rj32.v の冒頭にある「Don't modify this file」という注記は、言葉どおりに受け取る必要があります。回路を直したいときは、必ず元の Digital の回路図を直してから再度書き出すのが正しい順序で、生成された Verilog を直接編集すると、次に書き出したときにその修正が跡形もなく消えます。

実チップに書き込む前に、必ずソフトウェアシミュレータで確認する。 チュートリアルのスライドは Verilator について「yosys よりも多くの問題を検出する、組み込みの lint 機能がある」と述べています。実際の FPGA に書き込んで動作を確認する前に、Verilator で高速に動かし、波形 (VCD/FST 形式) で信号の動きを見る方が、修正と再確認のサイクルがずっと速く済みます。これは第 19 回で見た「規模に応じた確認手段を選ぶ」という考え方の延長です。

ボードごとのピン配置ファイルを取り違えない。 rj32 の hdl/ には、icesugar ・ icezero ・ BlackIce MX それぞれに専用の .pcf ファイル (どの論理信号をチップのどの物理ピンに繋ぐかを書いたファイル) が用意されています。ボードが変われば配線も変わるため、違うボード用の .pcf を使うと、最悪の場合、意図しない物理ピンに信号が繋がってしまいます。

図: ボードごとに専用の .pcf を使う。取り違えは物理ピンの対応そのものを間違える。

最適化オプションがタイミングを壊すことがある。 hdl/README.md が注意している「-Os を外す」という指示は、サイズを小さくする最適化が、配線の組み方を変えてクリティカルパスを伸ばしてしまう場合があることを示しています。ソフトウェアの最適化と違い、ハードウェアの最適化は「速くなるはずの変更が実は遅くなる」という逆転が起こり得ることを覚えておく必要があります。

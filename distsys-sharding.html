パーティショニングとシャーディング ― データを割ると何が起こるか

1 台に収まらなくなったデータを割って複数ノードに分けると、「どこに何があるか」を決める規則そのものが新しい障害点になる

← 分散システム シリーズ目次へ

この回の前提: 第 01 回 なぜ分散するのか、第 05 回 レプリケーション入門。

結論を先に言うと、シャーディング (sharding, データ分割) とは「1 台に収まらないデータを複数のノードに分け、各ノードは全体の一部分だけを担当する」仕組みであり、その代償は「どのデータがどのノードにあるかを決める規則 (シャーディングアルゴリズム) の選び方が、負荷の偏りと、ノードを増減させるときの移動コストを決めてしまう」ことである。レプリケーション (第 05 回) は同じデータを複製して耐障害性と読み取りスケールを得る仕組みだったが、シャーディングはデータそのものを割って書き込みと容量のスケールを得る仕組みであり、両者は組み合わせて使われることが多い。

1. なぜパーティショニングが要るのか

ByteByteGo の a-crash-course-in-database-sharding は、シャーディングが解決する問題を 3 つに整理している。(1) 1 台に収まらないデータ量: 1 台のサーバーが保持できるデータ量には物理的な上限がある。(2) 1 台では処理しきれない要求数: 1 台のサーバーが処理できる秒間の要求数にも上限がある。(3) データが増えるほど増すクエリの遅延: テーブルの行数が増えるほど、1 回のクエリが調べる範囲が広がり遅くなる。

第 05 回のレプリケーションは「同じデータのコピーを複数ノードに持たせる」ことで読み取りと耐障害性をスケールさせたが、どのレプリカも結局全データを持つ必要があり、1 台あたりの容量・書き込み負荷の上限は解決しない。そこで、データそのものを分割し、各ノードが全体の一部分だけを担当するという発想が必要になる。これをシャード (shard, データの断片) と呼び、分割する操作をシャーディング または水平分割 (horizontal partitioning) と呼ぶ。

図: シャーディングは「全体のコピーを増やす」のではなく「全体を分割して各ノードが一部分だけ持つ」仕組み。

2. 垂直分割と水平分割 ― 2 つの切り方

ByteByteGo の vertical-partitioning-vs-horizontal-partitioning は、データの分け方には 2 つの軸があると整理している。

垂直分割 (vertical partitioning) ― テーブルの列を複数のテーブルに分ける。分割後のテーブルは行数は同じだが、列数が少なくなる。例えば利用者テーブルから、めったに使わない属性だけを別テーブルに切り出す、といった使い方になる。

水平分割 (horizontal partitioning, シャーディング) ― テーブルの行を複数のテーブルに分ける。分割後のテーブルは列数は同じだが、行数が少なくなる。各シャードは独立したデータストアとなり、利用者 ID の範囲などに応じて行が振り分けられる。

この回で主に扱うのは水平分割で、ByteByteGo は水平分割のメリットとして「水平スケーリングを後押しする」「1 つのクエリが調べる行数が減るため応答時間が短くなる」ことを挙げ、デメリットとして「複数シャードをまたいだ ORDER BY はアプリケーション側で結果をまとめ直す必要がある」「シャード間でデータ量が偏るホットスポット が起こり得る」ことを挙げている。

図: 垂直分割は列を減らす、水平分割(シャーディング)は行を減らす。

3. シャーディングアルゴリズム ― どの行をどのシャードに置くか

水平分割では、各行をどのシャードに置くかを決めるシャーディングキー (shard key, 分割の基準にする列) と、そのキーからシャード番号を決めるシャーディングアルゴリズム が必要になる。ByteByteGo の a-crash-course-in-database-sharding と top-4-data-sharding-algorithms-explained が挙げる代表的な方式は次の 3 つである。

範囲ベース (range-based) ― シャーディングキーの値の範囲でシャードを決める。例えば利用者 ID が 1〜1000 ならシャード 1、1001〜2000 ならシャード 2、という具合である。実装が単純で、範囲検索(ある期間のデータを全部取る、など)がシャード内で完結しやすい利点があるが、新しい ID ほど増え続けるようなキーだと、最新データを持つ 1 つのシャードだけが書き込みを集中して受けてしまう。

ハッシュベース (hash-based) ― シャーディングキーにハッシュ関数を適用し、shard_id = hash(key) % シャード数 のようにシャードを決める。範囲ベースより均等に散らばりやすいが、2 つの弱点がある。1 つはハッシュ関数の選び方が悪いと偏りが残ること、もう 1 つはシャード数 (N の値) を変えると、ほぼ全てのキーの行き先が変わってしまうことである。この再配置問題は次回(第 07 回)のコンシステントハッシュで扱う。

ディレクトリベース (directory-based) ― シャーディングキーとシャード番号の対応表(ディレクトリ、電話帳のようなもの)を別に持ち、そこを引いてシャードを決める。対応表を更新するだけでキーの再配置の自由度が上がる一方、その対応表自体が単一障害点やボトルネックになりやすい。

図: 範囲ベースは新規キーが集中しやすく、ハッシュベースはシャード数変更時に大量の再配置が起きる。

4. どこで壊れるか ― ホットスポット・再シャーディング・セカンダリインデックス

SDFC の pastebin の設計議論では、「ホットパーティションを避けるには、利用者 ID でパーティショニングしてはいけない」という指摘がある。もし利用者 ID をシャーディングキーにすると、大量に投稿する利用者や人気の利用者のデータが 1 つのシャードに集中し、そのシャードだけが過負荷になるホットスポット が発生する。pastebin の議論では、代わりに投稿そのものの ID であるpaste_key をパーティショニングキーにし、user_id はセカンダリインデックス (secondary index, 主キー以外の検索用索引) として扱う設計が選ばれている。

この設計には代償がある。「ある利用者の投稿を全部取得する」という問い合わせは、以前は 1 つのシャード内で済んだはずが、paste_key でシャーディングした結果、該当する投稿がどのシャードに散らばっているか分からないため、複数のシャードに問い合わせて結果を集約する(ファンアウト) 必要が生じる。これは「書き込みの均一性」と「ある種の読み取りのしやすさ」を交換する、典型的なトレードオフである。

a-crash-course-in-database-sharding はこのほかの壊れやすい点として、再シャーディング (resharding) ― シャード数を後から変える作業 ― が複雑で時間を要する点、複数シャードをまたぐJOIN やトランザクション が難しくなる点を挙げている。これらは「シャーディングキーを最初にどう選ぶか」という設計判断が、後からのやり直しコストを大きく左右することを意味する。

図: ホットスポットを避けて paste_key を選ぶと、user_id 検索は複数シャードへのファンアウトになる。

5. 実システムでの例 ― 読み取り重視と書き込み重視でシャード構成を変える

SDFC の distributed-DB-design の議論では、要件によってシャーディングの構成方針が変わることが整理されている。読み取り重視 (read-heavy) なワークロードでは、第 05 回のリーダー/フォロワー型レプリケーションを中心に、読み取りを捌くフォロワーを増やす構成が合う。書き込み重視 (write-heavy) なワークロードでは、読み取りレプリカを増やすより先にシャードの数そのものを増やすことで、1 シャードあたりの書き込み量を減らす方が効果的になる。議論の中では、Ticketmaster のようなチケット争奪戦や flash sale(短時間に注文が集中するセール)のような総全順序付け(total ordering)が必要で書き込みが極端に多いワークロードについて「Variation 1 の構成に従いつつ、シャードを大幅に増やし、読み取りレプリカは少なめにする」という方針が述べられている。

SDFC の tinyurl-revisited (短縮 URL サービス) の議論では、短縮 URL の主キーをどう設計するかという質問に対し、「主キー = パーティショニングキー + (任意の) ソートキー」という整理が示されている。短縮コードそのもの(例: defabc)をパーティショニングキーにすれば、短縮コードから元のURLを引く という最も頻度が高い読み取りが 1 つのシャード内で完結する。一方、利用者ごとに作成した短縮 URL の一覧を見せたい場合は、user_id をセカンダリインデックスとして別に持つ必要があり、これは pastebin で見た「ホットスポットを避けた結果、別の軸での検索が複数シャードへのファンアウトになる」という同じトレードオフの繰り返しである。

どちらの例にも共通するのは、「シャーディングキーの選び方は、どのクエリを速くしたいかというアクセスパターンの選択そのものである」という点だ。すべてのクエリを等しく速くするキーは存在せず、最も頻度が高い・最も遅延に敏感なクエリを 1 シャード内で完結させることを優先し、それ以外のクエリ(別の軸での検索・集計)はファンアウトの代償を払う、という設計判断になる。

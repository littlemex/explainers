順序を仮定しないプロトコル

in-band header と数え上げ signal。正しさが立っている 3 つの不変条件を取り出す

← シリーズ目次

0この回で読むもの

AWS fork が upstream に足した 2001 行 (hybrid_dispatch_unordered.cuh 1106 行 + hybrid_combine_unordered.cuh 895 行) の設計を読みます。行を追うのではなく、設計判断とその理由を取り出します。

一言でいうと
受信スロット列を コンパイル時に固定した part に分割し、さらに part を sub-part に割ります。送信の単位は sub-part で、各 sub-part の先頭に in-band header (書き込み済みフラグ・iteration 番号・トークン数・後続あり) を埋め、その sub-part を 1 回の put で送って 番号つき weak signal を 1 つ束ねる。signal 番号は part 単位なので、同じ part の sub-part は同じ番号を共有します。受信側は signal の到着数と header が見えている送信元の数を比べて「この part は完全に着地した」と判定します。この判定が正しいのは C ⊆ H という包含関係のおかげで、その包含関係は 3 つの不変条件に依存しています。fork のコードはその 3 つを全部満たしていますが、コード上に明記はされていません。
1. 送れるのは「位置」ではなく「回数」 2. part と sub-part への固定分割 3. in-band header のビット配置 4. 受信側の判定式 5. なぜ正しいのか (包含関係) 6. 正しさを支える 3 つの不変条件 7. デモ: 読む順序を入れ替えると壊れる 8. combine 側に波及したこと 9. 残る疑問 (31 bit の iteration)

1送れるのは「位置」ではなく「回数」

前回の制約 3 をもう一度置きます。EFA-GDA の signal で相手に伝えられるのは「+1 が何回起きたか」だけです。

upstream は「末尾位置」という値を送っていました。EFA では値を送れません。ではどうするか。位置をあらかじめ決めておいて、回数だけを送るのです。

受信スロット列を、コンパイル時に決まった境界で kNumParts 個に区切ります。区切りの位置は両者が知っているので、「part 2 の signal が 1 回来た」= 「part 2 の範囲にデータが 1 つ着いた」と読めます。あとは「その範囲に何トークン入っていたか」を別の手段で運べばよい。それがデータの中に埋め込む header です。

図 1: 位置を固定すれば、運ぶ情報は回数だけで足りる。part 0 が小さいのは立ち上がりのレイテンシ対策

part の大きさは part_size_at という constexpr 関数が決めます。先頭は kBatchSize/3 (最低 4)、末尾は kBatchSize、中間は残りを均等割り。「先頭を小さく」という設計が入っているのが目に見えます。

2part と sub-part への固定分割

part の数は自由には決められません。signal の予算が上限を決めます。

kNumParts は gin_alloc::constexpr_num_parts(...) というコンパイル時計算で決まります。入力は「この launch に割り当てられた 1 context あたりの indexed signal 本数」「SM 数」「QP 数」「channel/SM」です。要するに signal 予算が足りる範囲で part を増やす。予算が厳しければ part は 1 に落ちます。上限は kMaxParts = 4。

sub-part はさらに細かい分割で、既定 2 (EP_NUM_SUB_PARTS)。1 回の put が運ぶのはこの sub-part です (flush_part が sub-part ごとに header を書いて put を出します)。sub-part は同じ part の signal 番号を共有します。したがって「part k の signal が 3 回来た」は「part k に属する put が 3 つ完了した」という意味になり、sub-part 単位でも同じ数え上げが成り立ちます。Blackwell (SM100) では小さすぎる sub-part を作らないよう EP_SM100_MIN_SUB_TOKENS = 15 という下限が入っています。

この「予算からコンパイル時に幾何を決める」構造の弱点は、幾何が悪い方に張り付くケースがあることです。open PR #2 が指摘しているのはまさにそれで、「予算が最も緩いのは channel が最も少ないトークンしか持たないとき」なので、decode 形状 (小さいバッチ・少ない SM) では 3 トークンを 4 part に割って「1 トークンの put が 3 回 + 空の part 1 つ」になる、と書かれています。sub-part 側には既に下限があるのに part 側には無い、という非対称の指摘です。

3in-band header のビット配置

header は 64 bit 1 語です。データと同じ put で運ばれるので「in-band」です。

bit 63
書き込み済み
(符号ビットとして検査)
bit 62..32
iteration (31 bit)
bit 30..1
count = この part のトークン数 (30 bit)
bit 0
more
(後続あり)
// hybrid_dispatch_unordered.cuh
static constexpr int64_t kScaleoutHeaderWrittenBit = static_cast<int64_t>(1) << 63;

int64_t pack_scaleout_header(int iteration, int count, bool more) {
    return kScaleoutHeaderWrittenBit
         | (static_cast<int64_t>(iteration & 0x7fffffff) << 32)
         | (static_cast<int64_t>(count & 0x3fffffff) << 1)
         | (more ? 1 : 0);
}

bool unpack_scaleout_header(const int64_t& header, int iteration, int& count, bool& more) {
    count = (header >> 1) & 0x3fffffff;
    more  = (header & 0x1) != 0;
    return header < 0 and ((header >> 32) & 0x7fffffff) == (iteration & 0x7fffffff);
}

3 つの役割がこの 1 語に入っています。

フィールド解く問題
bit 63 (written)「このスロットに誰かが書いたのか、それともゼロ初期化のままか」。header < 0 という符号判定で見るのが上手いところ
iteration「これは今回の dispatch のデータか、前回の残骸か」。バッファを再利用するので、値が残っていても前回のものなら弾く
count「この part に何トークン入っているか」。upstream の末尾位置の代替
more「この後にまだ part が続くか」。最後の part を受信側が知るための終端マーカ

header の置き場所はトークンの metadata 領域の末尾です (TokenLayout::get_hdr_ptr())。with_scaleout_hdr が true のときだけ 8 バイト伸びる、という形でレイアウトに組み込まれています。put の先頭付近にあるので、「header が見えたからデータも揃っている」とは言えません。ここが前回のデモで確認したことです。

4受信側の判定式

実際のコードの構造をそのまま追います。順番が意味を持つので、順番も含めて読んでください。

// hybrid_dispatch_unordered.cuh の受信 (forward) 側 ・ 抜粋と簡略
// [1] iteration の開始時に、signal の基準値を snapshot する
for (int p = 0; p < kNumParts; ++ p)
    rx_part_base[p] = *gin.gin.getSignalShadowPtr(part_signal_id(p));

// [2] polling ループの中で、part ごとに
for (int k = 0; k < kNumParts; ++ k) {
    const int64_t landed = gin.gin.readSignal(part_signal_id(k)) - rx_part_base[k];  // ← signal を先に読む
    int num_valid = 0;
    for (int s = 0; s < num_subs; ++ s) {
        sub_valid[s] = is_remote_src and
            unpack_scaleout_header(read_batch_header(lane_idx, k, s),   // ← header は後で読む
                                   dispatch_iteration, sub_count[s], sub_more[s]);
        num_valid += __popc(ptx::gather(sub_valid[s]));   // 全 lane (= 全送信元) を横断して数える
    }
    const bool part_landed = landed >= num_valid;        // ← 判定

    for (int s = 0; s < num_subs; ++ s) {
        const bool through = prefix_alive and sub_valid[s] and part_landed;
        if (through) incremental_tail = sub_slot(k, s) + sub_count[s];
        if (through and not sub_more[s]) my_finished = true;
        prefix_alive = through;                           // ← 前が通っていないと先へ進めない
    }
}

読み取るべき点が 4 つあります。

  • landed は送信元で分かれていない。 part_signal_id(part) に送信元の index が入りません。signal は rail 全体で共有されます。gin_resource_alloc.cuh のコメントも「同じ signal が rail 内の全ノードで再利用されるので、signal 本数は channel 数に比例し、ノード数には比例しない」と明言しています。
  • num_valid は全送信元にわたる合計。 ptx::gather は warp の全 lane から値を集める操作で、lane = 送信元です。つまり「今 header が見えている (送信元, sub-part) の総数」を数えています。
  • 判定は 2 つの合計の比較。 個別に「この送信元は着いたか」を見るのではなく、集合の大きさを比べます。この一見乱暴な比較が正しい理由が次節です。
  • prefix_alive で前詰めを強制。 part 2 が着いても part 1 が未確定なら消費しません。スロット列を前から順に消費するので、tail を飛ばして進むことはできません。

    • 5なぜ正しいのか (包含関係)

    2 つの集合を置くと、判定式が「集合が一致していること」の言い換えだと分かります。

    ある時点で、part k について次の 2 つの集合を考えます。送信元 (正確には (送信元, sub-part) の組) を要素とします。

    集合定義コード上の量
    H今回の iteration の header が見えているものnum_valid = |H|
    C束ねた weak signal が届いている = put が完了しているものlanded = |C|

    ここで前回の「守られる約束」を使います。signal はその put の全データが置かれた後に上がる。 そして header はその put のペイロードの中にある。 したがって、

    signal が届いている ⇒ その put の全バイトが置かれている ⇒ header も見えている
    すなわち C ⊆ H が常に成り立つ。

    すると landed >= num_valid すなわち |C| ≥ |H| は、C ⊆ H と合わせて C = H を意味します。つまり判定が真になるのは、header が見えている全てのものが完了しているときだけです。集合が一致した瞬間しか通りません。

    私が最初に疑った反例は次のものでした。「送信元 A の header は見えているが A のデータは途中まで。一方 B の signal が先に届いた。すると landed = 1 ≥ num_valid = 1 で A を早期受理してしまう」。これは成立しません。B の signal が届いているなら B の header も見えているので、その瞬間の num_valid は 2 です。1 ≥ 2 は偽で、受理されません。途中までの A は num_valid を水増しする側にしか働かず、判定を保守的にします。

    図 2: 右端が起きなければ判定は健全。つまり正しさは「backend が weak signal 契約を守る」ことに賭けている

    6正しさを支える 3 つの不変条件

    §5 の議論は 3 つの前提を暗黙に使っています。3 つとも fork のコードは満たしていますが、コードにその理由は書かれていません。ここが検証対象の中心です。

    #不変条件コード上の根拠破れたら
    I1signal はその put の全データ配置後にのみ観測される (weak signal 契約)backend 側の性質。EFA-GDA では「signal 付き put は相手の signal 端点へ宛てた write そのもの」で、FI_REMOTE_WRITE は inbound write ごとに 1 回 tick するC ⊆ H が崩れ、早期受理でデータが壊れる
    I2受信側は signal を先に読み、header を後に読む。かつ signal 読みは acquirelanded = readSignal(...) が sub-part ループより前にある。readSignal の既定 memory order は cuda::memory_order_acquire (NCCL の gin.h)。header 側は ptx::ld_acquire_sysH のスナップショットが C より古くなり、|C| ≥ |H| が意味を失う (§7 のデモ)
    I3iteration の基準値 (rx_part_base) が正確。前 iteration の増分を今回に持ち込まない基準値は shadow pointer (ソフト側の期待値) から取る。さらに epilogue に「期待した増分が全部数えられるまで待つ」drain ループがある基準値がずれ、landed が水増しされて早期受理になる

    I3 の仕組みは見落としやすいので補足します。基準値はハードウェアカウンタの現在値ではなく getSignalShadowPtr の値、つまり「ここまで数えたと自分が思っている値」です。そして dispatch の終わりに次のループがあります。

    // epilogue shadow drain
const int64_t landed = gin.gin.readSignal(part_signal_id(k)) - rx_part_base[k];
if (landed >= expected_k) return true;   // 期待した増分が全部届くまで抜けない

    つまり iteration を抜ける前に、その iteration で発生するはずの signal を全部数え切ります。だから次の iteration の基準値は正確で、遅れて届いた前回分が今回の landed を汚すことがありません。これは「順序なし配送で iteration を回す」ために必須の仕掛けで、この drain を省くと確率的にデータが壊れるタイプの設計です。

    検証の的はここに絞られる
    プロトコルの正しさは I1・I2・I3 に還元されました。I1 は backend の契約なので backend 適合性のテスト、I2 と I3 は DeepEP 側のコードなので プロトコルのテストです。第 7 回の emulator はこの分割をそのまま実装の分割に写します。

    7デモ: 読む順序を入れ替えると壊れる

    I2 が本当に必要かを確かめます。判定式は同じままで、受信側が signal と header を読む順序だけ入れ替えます。

    読み出し順序の実験

    「3000 回まわす」を押すと、4 通りの組み合わせで誤受理率が出ます。

    モデル: 送信元 3、1 メッセージ = 4 パケット、header はパケット 0。判定は landed >= num_valid のまま固定。受信ループの 1 周では 2 つの読み出しが行われ、その間には他の読み出し (part × sub-part × 送信元の header ロード) の時間だけ隙間があります。このモデルではその隙間を有限の長さとして表現しています。header を先に読むと、その後の隙間の間に別の送信元のメッセージが着地して signal が増え、古い num_valid と新しい landed を比べてしまう。送信元を増やすほど誤受理が増える (2 → 3 → 4 で単調に増加する) のは、隙間の間に着地しうる送信元が増えるからです。実コードが signal を先に、しかも acquire で読んでいるのは、この窓を閉じるためです。

    結果は明快です。signal → header の順なら契約が守られている限り誤受理は 0。header → signal に入れ替えると誤受理が出ます。判定式は同じなのに壊れる。つまり landed >= num_valid という 1 行は、それ自体では不完全で、読む順序と組み合わせて初めて正しい。

    そして「契約を破る」を選ぶと、正しい読み順でも壊れます。これが I1 の必要性です。この 2 つの実験は、実機がなくても実行できるテストの原型です。第 7 回で、これを実際の CUDA カーネルに対して行う方法を設計します。

    8combine 側に波及したこと

    dispatch の受信レイアウトが変わると、帰りの combine が困ります。fork はそこに新しいハンドル項目を足しています。

    upstream の受信レイアウトはトークン番号で引ける形でした。順序が保証されているので「n 番目に届いたトークンは n 番目のスロット」と決まるからです。unordered ではそれが崩れ、スロット番号は送信側が決めて記録するしかありません。

    そこで dispatch が token_map_at_dispatch という [num_max_tokens_per_rank, num_topk] の int テンソルを書き出します。中身は (rank, slot, channel) を 5 / 14 / 12 bit に詰めた 1 語で、combine の epilogue がこれを読んで「自分のトークン T の k 番目の寄与はどこに落ちたか」を復元します。ホスト側 (csrc/elastic/buffer.hpp) にも、この項目を handle に載せて combine へ渡す配線が入っています。

    その bit 詰めが open PR #12 の対象
    pack_combine_recv_addr(rank, slot, channel) は 5 / 14 / 12 bit へシフトするだけで、実行時のマスクがありません。slot が 14 bit (16383) を超えると上位ビットが rank のフィールドへ漏れます。しかも channel は無傷なので、実行時の EP_DEVICE_ASSERT(channel == channel_idx) は通過してしまう。結果は「間違った rank へ reduce を送る」か「来ない相手を待って hang」です。PR #12 は 3 つの上限がコンパイル時定数であることを使って JIT 時の EP_STATIC_ASSERT に落とす提案をしています。これは EFA が無くても検出できる種類のバグで、第 7 回の最初の一歩の良い題材になります。

    もう 1 つの波及が proxy_ring.cuh です。combine では forward warp (reduce する側) と scale-out warp (put を出す側) を分け、shared memory 上のリング (ProxyPutDesc {send_ptr, recv_ptr, num_bytes, dst} の配列 + head / tail / done) で仕事を渡します。「proxy」という語が CPU proxy と紛らわしいですが、これは GPU 内の warp 間の受け渡しです。channel 数を決めるときに、TMA バッファとこのリングの両方が shared memory に収まるまで channel を減らすループがホスト側に入っています。

    9残る疑問 (31 bit の iteration)

    §5 の証明には穴が残ります。H の定義が「今回の iteration の header」であることに依存している点と、signal の値が単調であることに依存している点です。前者は当初「実機では踏めない」と評価していましたが、その評価は誤りでした。

    unpack_scaleout_header の iteration 比較は 31 bit マスク後の一致判定です。したがって iteration が 2^31 離れた値は区別できません。dispatch_iteration はバッファのホスト側で毎回 ++ されるカウンタなので、原理的には周回します。周回すると「前回の残骸」を「今回のもの」と誤認しうるので、H が「今回の put 集合」でなくなり、§5 の前提が崩れます。

    ここは当初「実機では踏めない」と書いていましたが、訂正します。まず、周回する前に別の問題があります。dispatch_iteration は csrc/elastic/buffer.hpp で mutable int、つまり符号つき整数として持たれており、++ dispatch_iteration が INT_MAX を超えるのは C++ の規格上 wrap ではなく 未定義動作です。そして到達時間も無視できません。decode の 1 step で層ごとに dispatch が走るので、60 層で毎秒 100 step なら毎秒 6000 回です。毎秒 1 万回として 2^31 回は 約 2.5 日。常駐する推論サービスなら普通に超えます。

    つまりこれは「論理的には存在するが踏めない欠陥」ではなく、長時間動かす前提なら実際に到達する欠陥です。直し方も難しくありません。host 側のカウンタを符号なし型にして wrap の意味を定義し、そのうえで stale header との衝突を検査すればよい。そして検査はモデル検査が最も得意な区画で、iteration の初期値を境界に置くだけで決定的に確かめられます。実機で 2.5 日回して待つ必要はありません。

    もう 1 つ、同じ性質の疑問があります。受理判定は landed = readSignal(...) - rx_part_base[k] という絶対値の引き算ですが、EFA-GDA で kernel が読む signal は NIC のハードウェアカウンタそのものです (GetSignalPtr が cntr_value と cntr_offset を返す)。そして同じファイルは「この完了カウンタは 2^31 で wrap するので、絶対値を比較してはならない。必ず差を取って 31 bit に丸めよ」と明記しています。DeepEP 側にその丸めはありません。ただし 1 つの signal 番号が 2^31 回増えるには (channel, part) ごとに 2^31 回の dispatch が必要なので、iteration の 31 bit と同じく実行では到達しません。境界値を直接置けるモデル検査でしか触れない区画という点も同じです。

    加えて、I3 の drain があるので「前回の残骸が signal を水増しする」経路は塞がれています。周回で起きるのは header の誤認の方で、それは num_valid を増やす向きに働くため、多くの場合は「早期受理」ではなく「待ち」に倒れます。つまり症状はデータ破壊より hang になりやすい。とはいえ「多くの場合」で片付けるべきではないので、検査項目として残します。

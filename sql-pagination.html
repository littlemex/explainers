ページネーション ― OFFSET を捨てる

「2 ページ目を見る」程度なら OFFSET で何の問題もありませんが、ページ数が深くなるほど遅くなり、しかもページを読んでいる間にデータが増減すると結果の行がずれます。この回では、30 万行のテーブルに対する実測で OFFSET のコストがどれだけ伸びるかと、キーセットページネーション (前のページの最後の行を手がかりにする方式) がなぜ速くずれないのかを確認します。

この回の前提: 第 13 回 インデックスショットガン (複合インデックスの列順) ・ 第 29 回 ウィンドウ関数で集合として考える (ROW_NUMBER)

この回で答えるのは「一覧画面の 2 ページ目、3 ページ目を表示する処理を、ページ数が増えてもデータが増減しても安全に書く方法」です。結論を先に言うと、LIMIT ... OFFSET N は N 件分を読み飛ばすという動作そのものに時間がかかり、ページを表示している間に行が増減すると前のページと重複したり、1 件飛ばされたりします。キーセットページネーション (前のページの最後の行の値を次のページの開始条件にする方式) は、この両方の問題を避けられます。これは実測で確認した事実です。

1. この回で解く問題 ― OFFSET は「数えて読み飛ばす」操作である

SELECT ... ORDER BY bug_id LIMIT 20 OFFSET 40 は、「bug_id の順に並べて、最初の 40 件を読み飛ばし、次の 20 件を返す」という意味です。重要なのは、読み飛ばす 40 件も実際には 1 件ずつ数えながら読んでいるということです。1 ページ目や 2 ページ目なら読み飛ばす件数は少なく問題になりませんが、「最後のページ」のように読み飛ばす件数が数十万件になると、その数十万件を数えるだけのコストがそのままページ表示の遅さになります。

もう 1 つの問題は、OFFSET が「順番の何番目か」という位置で指定されていることです。ページを表示している最中に誰かが行を削除したり追加したりすると、同じ OFFSET の値が指す位置が変わってしまい、前のページで見た行が今度は表示されなかったり、別の行が重複して表示されたりします。この 2 つの問題を、30 万行のテーブルに対する実際の実行結果で確認します。

図: OFFSET は指定した件数を実際に数えながら読み飛ばすため、件数が多いほど重くなる。

2. 仕組み ― OFFSET のコストは深さに比例する

30 万行の big_bugs テーブル (bug_id は主キーで連番) に対して、1 ページ目 (OFFSET 0) と、最後のページ (OFFSET 299980、1 ページ 20 件なら 15,000 ページ目) を EXPLAIN (ANALYZE, BUFFERS) で比較しました。

EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT bug_id, created_at, summary FROM big_bugs ORDER BY bug_id LIMIT 20 OFFSET 0;
-- Limit (actual rows=20) / Buffers: shared hit=4 / Execution Time: 0.603 ms

EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT bug_id, created_at, summary FROM big_bugs ORDER BY bug_id LIMIT 20 OFFSET 299980;
-- Limit (actual rows=20) → Index Scan (actual rows=300000)
-- Buffers: shared hit=3322 / Execution Time: 32.268 ms
ページ読んだバッファ数実行時間
1 ページ目 (OFFSET 0)40.603 ms
最後のページ (OFFSET 299,980)3,32232.268 ms

実行計画を見ると、最後のページを取るクエリは内側の Index Scan が actual rows=300000 と表示されています。LIMIT 20 で最終的に返す行は 20 件だけなのに、そこに至るまでに 30 万行をすべて数えながら通過しているということです。バッファ数で約 830 倍、実行時間で約 54 倍の差になりました (同一マシン、ウォームキャッシュでの実行)。ページが深くなるほど、この「数えながら通過する行数」が増え続けます。

図: OFFSET の値が大きいページほど、読み飛ばす行数が増え、コストも増える。

3. 仕組み ― ページ送りの間にデータが変わるとずれる

OFFSET は「順番の何番目か」という位置を指定するものなので、ページを見ている間に手前の行が増減すると、同じ OFFSET の値が指す位置がずれます。「2 ページ目 (OFFSET 20 LIMIT 20)」を取得し、その後 1 ページ目にある bug_id=5 の行を削除してから、もう一度同じ条件で「2 ページ目」を取得した実機の結果です。

-- 削除前の「2 ページ目」
SELECT bug_id FROM big_bugs ORDER BY bug_id LIMIT 20 OFFSET 20;
-- 21, 22, 23, ..., 40

DELETE FROM big_bugs WHERE bug_id = 5;

-- 削除後の「2 ページ目」(同じ OFFSET 20 LIMIT 20)
SELECT bug_id FROM big_bugs ORDER BY bug_id LIMIT 20 OFFSET 20;
-- 22, 23, 24, ..., 41

削除前は 21〜40 だった 2 ページ目が、削除後は 22〜41 になりました。bug_id=21 はどこにも表示されなくなり (1 ページ目に紛れ込んでいる)、代わりに 41 という前回は 3 ページ目にあった行が紛れ込んでいます。利用者から見ると、ページをまたいで同じ記事が消えたように見える不具合です。

同じ操作をキーセットページネーションで行うと、この問題が起きません。「bug_id > 20 の次の 20 件」という条件は、手前の行が増減しても意味が変わらないからです。

SELECT bug_id FROM big_bugs WHERE bug_id > 20 ORDER BY bug_id LIMIT 20;
-- 削除前: 21, 22, ..., 40

DELETE FROM big_bugs WHERE bug_id = 5;

SELECT bug_id FROM big_bugs WHERE bug_id > 20 ORDER BY bug_id LIMIT 20;
-- 削除後: 21, 22, ..., 40 (変わらない)

削除の前後で、どちらも 21〜40 のまま変わりませんでした。bug_id=5 という手前の行が無くなっても、「20 より大きい次の 20 件」という条件そのものには影響しないためです。

図: OFFSET は位置がずれると結果がずれるが、値による条件は手前の変化に影響されない。

4. 仕組み ― 複合キーのキーセットには行値比較を使う

並び順が主キー 1 列だけなら WHERE bug_id > 20 で済みますが、「優先度の日付順、同じ日付の中では bug_id 順」のように複数列で並べる場合、単純な AND では書けません。priority_date (日付だけ、時刻は持たない) で各日に 8 万件以上が集中する big_bugs で確認します。

SELECT priority_date, count(*) FROM big_bugs GROUP BY priority_date ORDER BY priority_date LIMIT 3;
--  2020-01-01 | 86399
--  2020-01-02 | 86400
--  2020-01-03 | 86400

1 日に 8 万件以上が同じ priority_date を持つので、「前のページの最後の行が priority_date='2020-01-04', bug_id=259500 だった」という手がかりだけでは、priority_date > '2020-01-04' では同じ日の残りの行を取り落とし、bug_id > 259500 だけでは日付をまたいだ比較にならず壊れます。ここで使うのが行値比較 (row value comparison) です。

EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT bug_id, priority_date FROM big_bugs
WHERE (priority_date, bug_id) > ('2020-01-04', 259500)
ORDER BY priority_date, bug_id
LIMIT 20;
 Limit (actual rows=20)
   ->  Index Only Scan using big_bugs_priority_date_bug_id_idx on big_bugs
         Index Cond: (ROW(priority_date, bug_id) > ROW('2020-01-04'::date, 259500))
         Heap Fetches: 20
 Buffers: shared hit=1 read=3
 Execution Time: 0.075 ms

(priority_date, bug_id) > ('2020-01-04', 259500) は「priority_date が 2020-01-04 より後、または priority_date が同じ 2020-01-04 で bug_id が 259500 より後」という意味になり、辞書順の比較と同じ規則です。(priority_date, bug_id) の複合インデックスがそのまま Index Cond として使われ、Index Only Scan (テーブル本体をほとんど読まない) で 4 バッファ ・ 0.075 ms と、OFFSET の深いページ (3,322 バッファ ・ 32 ms) とは比べ物にならない速さになりました。

並べ替えの列に同じ値 (タイ) が出る可能性がある限り、キーセットの条件には並べ替えに使っている列をすべて、同じ順序で含める必要があります。1 列だけを切り出して比較すると、タイの範囲内で行を取り落としたり、無限に同じ行を返したりします。

図: 行値比較は複数列を辞書順 (1 列目優先、同じなら 2 列目) で比較する。

5. どこで壊れるか ― よくある間違い

間違い 1: OFFSET に負の値を渡す

SELECT bug_id FROM big_bugs ORDER BY bug_id LIMIT 20 OFFSET -5;
-- ERROR:  OFFSET must not be negative

これは実際に PostgreSQL 18 で出たエラーです。「現在のページ番号 - 1」のような計算でページ番号の入力チェックを忘れると、1 ページ目より前を指定したときに負の OFFSET になり、画面には「不明なエラー」としてしか伝わらないことがあります。入力されたページ番号が 1 未満にならないよう、アプリケーション側でも検証しておく必要があります。

間違い 2: 行値比較の列の順序や型を ORDER BY と一致させない

SELECT bug_id FROM big_bugs WHERE (priority_date, bug_id) > (259500, '2020-01-04')
ORDER BY priority_date, bug_id LIMIT 20;
-- ERROR:  operator does not exist: date > integer
-- HINT:  No operator matches the given name and argument types.

行値比較の左右で列の順序を取り違えると (ここでは priority_date の位置に整数、bug_id の位置に日付を置いてしまった)、型が合わずにエラーになります。カーソルを組み立てるコードでは、ORDER BY に書いた列の順序とカーソルの値の順序を必ず一致させます。

間違い 3: タイになる列をカーソルに含めない

節 4 で見たとおり、priority_date だけをカーソルにすると、同じ日付の中の行の一部を取り落とします。並べ替えに使っている列が完全に一意でない限り、一意性を保証できる列 (主キーなど) をカーソルの最後に必ず加えることが安全な設計の条件です。

間違い 4: キーセットページネーションで「10 ページ目に飛ぶ」を実装しようとする

キーセットページネーションは「次のページ」「前のページ」には強いですが、「任意のページ番号に直接飛ぶ」機能とは相性が悪いです。任意のページに飛ぶ機能がどうしても必要なら、OFFSET の遅さを許容する (深いページへのジャンプは稀だと割り切る) か、ページ番号ごとの先頭キーを事前に計算しておくなど、追加の設計が必要になります。

図: ORDER BY の列順と行値比較の列順がずれると、型エラーや誤った結果になる。

6. シニアの書き方 ― 判断の基準と件数表示の扱い

1. ページ送りが「次へ」「前へ」中心ならキーセットを既定にする。SNS のタイムラインや検索結果のように、利用者が主に先頭から順にスクロールしていく画面では、キーセットページネーションの方が深いページでも速く、データの増減にも強くなります。

2. ページ番号を直接指定したい画面では OFFSET を使うが、深さに上限を設ける。管理画面の一覧のように「37 ページ目に飛ぶ」操作が必要な場合は OFFSET を使ってよいですが、ページ数が数千を超えるなら、利用者が実際にそこまで深く見に行くかどうかを見積もり、必要なら検索条件を絞らせるなどの UI 上の工夫を併用します。

3. 「全部で何件」の表示は、厳密さが必要かどうかで手段を変える。正確な件数が必要なら COUNT(*) を使いますが、30 万行のテーブルでも並列ワーカーを使ったシーケンシャルスキャンで十数〜数十 ms (実行ごとにばらつきがあり、今回の実機では 16〜70 ms の範囲だった) ・ 約 5,000 バッファかかりました (行数が増えればこのコストも増えます)。「だいたい何件」で十分な場合は、pg_class.reltuples (直近の ANALYZE 時点の推定行数、このテーブルでは実際の 300,000 件に対して 299,999〜300,000 件という推定値) を使えば、テーブルを読まずに即座に近似値が得られます。

-- 厳密な件数 (テーブルをスキャンする)
SELECT count(*) FROM big_bugs;
-- Execution Time: 十数〜数十 ms (30 万行、並列ワーカー使用、実行ごとにばらつきあり)

-- 近似の件数 (カタログの統計情報だけを読む)
SELECT reltuples::bigint AS estimated_rows FROM pg_class WHERE relname = 'big_bugs';
-- 即座に返る (テーブル本体を読まない)

reltuples は直近の ANALYZE (または autovacuum による自動統計更新) の時点の値なので、更新や削除が多い時間帯にはずれが生じます。「およそ 30 万件」という表示で十分な UI にはこちらを使い、正確な集計が必要な場面 (請求件数など) では COUNT(*) を使う、という線引きを決めておきます。

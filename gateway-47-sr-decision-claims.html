vLLM Semantic Router の 3 つの発表を、主張と実物で読む
Jev の形は公開重みになったが、読むのは今も質問ごとに全部

この章の結論。2026-09-18〜24 に vLLM Semantic Router (以下 SR。リクエストごとに送り先のモデルを選ぶ OSS のルータ) が 3 つを出しました。 リクエストを読み取る小さなモデル群 Vela 1.0、TypeSafe AI の Jev と同じ呼び方 (System One 形式) で答える公開重みのモデル Decision 1.0、そしてルータ本体の v0.4 Hermes です。

実物を読んで分かったことは 3 つです。 Vela はルータに既に入っていますが、Decision はまだ入っていません (本体への組み込みは「次の一手」と本人たちが書いています)。 Decision の同梱コードは AMD の GPU でしか起動しません (Lux・Nox・Sol は gfx942 という型番を、Kai・Lex は AMD 用の PyTorch を要求します)。評価に使った問題も配っていません。 そして論文自身が「質問ごとに文脈を読み直しているので、生成をやめただけでは速くならない」と書いています。 最後の点は、私が作った Prismyra がちょうど逆の設計をしている所で、第 49 章でこの 2 つを合体させます。

1. 3 つの発表は何で、ルータのどこに入るのか

SR は「このリクエストはどのモデルに送るか」を決めるルータです。 Hermes の説明では、リクエストはまず信号 (Signal。「分野は何か」「個人情報を含むか」などの読み取り結果) に変換され、 規則 (Decision。ここでは AND/OR の条件で経路を選ぶ規則エンジンのこと) が経路を 1 つ選び、 その経路のやり方 (Algorithm。1 モデルに送る、自信が無ければ上位に上げる、複数に聞いて審判に選ばせる、など) で実際にモデルを呼びます。

紛らわしいのは、ルータの「Decision」段と、今回のモデル「Decision 1.0」が同じ名前の別物だということです。 ブログ本文も「The Router's Decision stage is the policy engine running today; the Decision 1.0 model family above is a separate launch」と断っています。

この図で一番大事なのは点線です。Decision 1.0 がルータの中で振り分けを良くした、という測定は、今回読んだ公開資料の中には見当たりません。 Hermes のブログ自身が「The models and their interface are available now; native Decision integration in vLLM Semantic Router is the next step」と書いており (blog L88)、 ルータ本体のソース (src/) を Decision-1.0・Lux・noul・systemone で検索しても 1 件も出てきません。

2. Decision 1.0 の中身 ― 生成はしないが、質問ごとに全部を読み直す

Decision 1.0 は Jev の呼び方をそのまま真似ています。状態 (state。判断の材料になる文章) と、名前付きの質問をいくつか渡すと、質問ごとに選択肢の確率が返ってきます。 質問の型は 3 つで、Choice (選択肢から 1 つ選ぶ)、Noul (はい・いいえ。Boolean の言い換え)、Score (順序のある段階で採点) です。 文章を 1 文字も生成せず、モデルが入力を読み終えた時点の内部の数値から、選択肢ごとの確率を直接出します。

モデルは 2 系統あります。Kai と Lex (0.57B) は双方向のエンコーダ (前後の文脈を同時に見る型) で、質問の型ごとに 22 層の道筋を丸ごと 3 本持っています。 Eos・Sol・Nox・Lux (0.75B〜7.94B) は Qwen3.5 の言語部分をそのまま使い、単語を予測する出力層の代わりに学習した採点ヘッド (読み終えた内部の数値から、選択肢ごとに点を付ける小さな部品) を付けたものです。 名前の「9B」は実際には 7.94B、「0.6B」は 0.57B です (論文の表 1)。

採点ヘッドが読む場所を見ると、次の章の話がすぐ分かります。下の図は、1 つの状態に 3 つの質問をしたときに Lux が実際に作る入力です (code/decision_model.py の segments() と encode() をそのまま図にしました)。

つまり「生成しないから速い」は、この実装では示されていません。論文はそれを正直に書いていて、同梱の測定 (QUESTION-SCALING.md、AMD gfx942、旧い重み) でも 1 問 499 トークンのとき 1 問 33.17 ms、8 問 150.41 ms、32 問 600.74 ms と、ほぼ質問数に比例しています。 論文の「今後の方向」の 1 番目が「同じ先頭部分を 1 回だけ計算し、注意の KV と Gated DeltaNet の再帰状態を質問ごとに分岐させる」で、これは Prismyra がすでにやっていることです。

3. 点数の読み方 ― 3 つの版、後から決めた重み、読解だけ伸びていない

Lux の総合点は 3 つある

総合点は 100 点満点で、同じ Lux について版によって 3 つの値があります。論文の表 2 は 77.22、現行のモデルカードと metrics/benchmark.json は 77.40、ブログは 76.94 です。 JSON のパネルごとの正解率に公開された重みを掛けて自分で計算すると 77.40 になり、カードと一致しました。 論文は付録 A で固定した古いリビジョンを使っているので、論文とカードは別の版の Lux です。ブログの 76.94 と 84.10 は、論文にも 6 つのリポジトリにも見つかりませんでした。

重みは結果を見てから決めた、と本人たちが書いている

総合点は 5 つのパネルの重み付き平均で、重みは 30/25/15/15/15 です。 EVALUATION.md は「outcome-informed product-priority weights, chosen after observing benchmark results」、論文の付録 C は「The weights were chosen after observing results」と書いています。 旧い重み 25/25/15/15/20 と比べるとどう動くかを、同じ JSON から計算しました。

4. 自分の GPU で動かせるか

重みは Apache-2.0 で、誰でも落とせます。ただし同梱の推論コードは、AMD の GPU でしか起動しません。 Lux・Nox・Sol は、計算の部品 (Triton カーネル) の設定を AMD の MI300 系 (型番 gfx942) に合わせて固定しているので、GPU の型番を確かめてから読み込みます。Kai と Lex は PyTorch が ROCm 版 (torch.version.hip) でなければ止まります。

ほかにも欠けている物が 2 つあります。HTTP のサーバが無いので、ブログの curl の例は「自分で System One 互換のエンドポイントを立てたら」という仮定の話です。 そして評価の問題文・正解・予測は配られていません (benchmark.json にはパネルごとの正解数と区間だけ)。 54 タスクの点数を第三者が再計算できるのは、集計値から加重平均を検算するところまでです。

6. レビュー (AIR) で決めたこと

ここまでの読みと、次の章からの実験の計画を、Opus 5.5・GPT-6 Sol・GPT-6 Astra の 3 つに別々に渡して攻撃させました (3 つとも回答あり)。 3 者が独立に一致したのは次の 4 点で、実験の設計をこの通りに変えました。

  • 比べる相手は 1 つに絞る。学習の効き目を見るには、Lux と「Lux の元になった未調整の Qwen3.5-9B」を同じ問題で比べるしかない。ただしそれは「学習 + ヘッド + 入力形式」の合計の差で、学習だけの効果とは呼べない。
  • 合格線は結果を見る前に固定する。判定の線 (差の区間が 0 を含むか、±2 ポイントの内側か) を先に書いた。
  • 移植の忠実度を先に確かめる。参照出力が 5 問しかないなら「検証不能」と宣言し、以降の結果を「CUDA に移植した版の結果」と書く。
  • 振り分けの信号として見るなら、難しさの当たり具合 (AUC) を主指標にしない。全員が解ける問題と全員が解けない問題を当てても、振り分けの得にはならない。

Opus 5.5 だけが出した提案が 1 つあり、第 49 章の中心になりました。「Lux のヘッドが読むのは後ろの位置だけなのだから、先頭の状態を 1 回だけ計算しても答えは変わらないはずだ。それを確かめるほうが速度比較より情報が多い」という指摘です。

まだ言えないこと

  • Vela の 15 本の精度は、発表された数字 (分野の分類 85.15 など) を読んだだけで、自分では測っていません。第 50 章で使うのは分野の分類 1 本だけです。
  • Jev 本体は API キーが無いので呼んでいません。Jev の数字はすべて Decision 側が記録したもの (jev-1.13.0、2026-09-21 のリクエスト) の引用です。
  • ライセンスについて、Kai と Lex のトークナイザには Gemma の利用規約が付いています (mmBERT が Gemma 2 のトークナイザを使っているため)。学習データの一部は CC BY-SA です。商用で使う前には確認が要ります。

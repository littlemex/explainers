I/O 多重化 ― 1 スレッドで 1 万本の接続を相手にする

1 接続に 1 スレッドを使う設計はいつか限界に当たる。select / poll / epoll はその限界を超えるための仕組み

← 分散システム シリーズ目次へ

この回の前提: 第 02 回 ソケットプログラミング入門

第 02 回では、1 本のソケットを相手に recv() や send() を手で呼びました。しかし分散システムのサーバーは、同時に数百から数万本の接続を抱えます。「1 本の接続に 1 本のスレッドを割り当てる」という素朴な設計は、接続数が増えるとメモリとスレッド切り替えのコストで先に力尽きます。この回では、1 スレッドで大量の接続を同時に扱うための仕組みである I/O 多重化 (select / poll / epoll) と、それを核にしたイベントループの作り方、そして分散システムの至る所で出てくる「速い送信者と遅い受信者」の問題であるバックプレッシャーを見ていきます。

1. 1 接続 1 スレッドが壁に当たる ― C10K 問題

最も素朴なサーバーの作り方は、accept() で新しい接続を受け取るたびに、新しいスレッド (またはプロセス) を 1 本立ち上げて、そのスレッドの中で recv() を呼ぶというものです。recv() はデータが届くまで呼び出し元をブロッキング (停止させる) ため、1 本のスレッドは 1 本の接続だけを見ていれば済みます。実装が単純で分かりやすいのが利点です。

ところがこの設計は、同時接続数が増えると先に力尽きます。スレッドにはスタック用のメモリが必要で、OS がスレッドを切り替えるたびにコンテキストスイッチ (レジスタやスタックポインタの退避と復元) のコストがかかります。接続数が数百までなら問題になりませんが、数千 ・ 数万本の接続を同時に抱えようとすると、ほとんどのスレッドが「データなんて来ない」まま待っているだけなのに、メモリとスケジューラの負荷だけが積み重なっていきます。この壁は 2000 年前後にC10K 問題 (1 台のマシンで 1 万本の同時接続を処理できるか) という名前で広く議論されました。

図: 接続ごとに 1 スレッドを使うモデルは、待っているだけのスレッドの数に比例してコストが増える。

2. select / poll ― 複数の fd を 1 回の呼び出しで見張る

I/O 多重化 (I/O multiplexing) とは、「複数のソケット (ファイルディスクリプタ、fd) のうち、どれが読み書き可能になったか」を 1 回のシステムコールでまとめて問い合わせる仕組みです。これがあれば、スレッドを増やさずに 1 本のスレッドで多数の接続を見張れます。

select() は最も古い実装で、監視したい fd の集合をビットマスク (fd_set) として渡します。しかし select() が監視できる fd の番号には FD_SETSIZE (1024) という固定された上限があり、man page 自身が「現代的なアプリケーションには不合理に低い上限であり、この制限は変更されない」と明記しています。poll() はこの上限を取り払い、構造体の配列で任意の数の fd を監視できるようにした改良版です。

ただし select() と poll() には共通の弱点があります。どちらも呼び出すたびに監視対象の fd を毎回すべて OS に渡し、OS 側もその全部を毎回スキャンして「どれが準備できたか」を調べるという仕組みです。監視している fd の数を $n$ とすると、1 回の呼び出しのコストは $n$ に比例して増えます (準備ができている fd がどれだけ少なくても、全部を見る必要があります)。接続数が数千を超えると、この「全部を毎回見る」コストそのものがボトルネックになります。

図: select() / poll() は呼び出しごとに監視対象をすべてスキャンするため、数が増えるとコストが増える。

3. epoll / kqueue とイベントループ ― 動くサーバーで確認する

select() / poll() の「毎回全部スキャンする」という弱点を解決したのが、Linux の epoll と BSD 系 (macOS を含む) の kqueue です。考え方はどちらも同じです。監視したい fd を OS 側に一度登録しておけば、OS はその fd に変化がある度に内部の準備済みリストを更新しておき、アプリケーションが問い合わせたとき (epoll_wait()) には既に準備ができている fd だけを返します。監視対象の数 $n$ がどれだけ多くても、呼び出しのコストは「実際に準備ができた数」にしか依存しません。

epoll にはさらにレベルトリガ (既定) とエッジトリガ (EPOLLET) という 2 つの通知モードがあります。レベルトリガは「読めるデータが残っている限り、何度問い合わせても準備完了として通知される」モードで、エッジトリガは「状態が変化した瞬間にだけ 1 回通知される」モードです。エッジトリガを使う場合、1 回の通知で読めるだけ読み切らないと、残ったデータに気づけなくなるという注意点があります。

この仕組みの上に乗るのがイベントループです。1 本のスレッドが「準備ができた fd を問い合わせる → それぞれの fd に対応する処理を実行する → また問い合わせる」というループを回し続けます。Python の selectors モジュールは、OS ごとに epoll / kqueue / select を自動で選んで同じ API を提供してくれます。以下は実際に手元で実行して、2 つのクライアントから同時に接続できることを確認したイベントループ型のエコーサーバーです。

import selectors
import socket

HOST = "127.0.0.1"
PORT = 50009
sel = selectors.DefaultSelector()

def accept(sock):
    conn, addr = sock.accept()
    conn.setblocking(False)
    sel.register(conn, selectors.EVENT_READ, read)

def read(conn):
    data = conn.recv(1024)
    if data:
        conn.send(data.upper())
    else:
        sel.unregister(conn)
        conn.close()

def main():
    listener = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    listener.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    listener.bind((HOST, PORT))
    listener.listen()
    listener.setblocking(False)
    sel.register(listener, selectors.EVENT_READ, accept)
    while True:
        for key, _ in sel.select(timeout=2):
            callback = key.data
            callback(key.fileobj)

if __name__ == "__main__":
    main()

サーバーを 1 つ起動したまま、2 つのクライアントがそれぞれ別のテキストを送ると、サーバー側のスレッドは 1 本のままで両方に正しく応答が返ることを確認できました (実際に手元で実行した結果、クライアント A は b'HI FROM A'、クライアント B は b'HI FROM B' をそれぞれ正しく受け取りました)。ポイントは、accept() も recv() も setblocking(False) でノンブロッキングにしてあることです。もしここでブロッキングのままだと、1 つの接続の処理に詰まった瞬間、ループ全体が止まってしまいます。

図: イベントループは「準備できた fd を問い合わせて処理し、また問い合わせる」を 1 本のスレッドで回し続ける。

4. スレッド / プロセスモデルとイベントループの比較

C10K 問題への答えは、イベントループ 1 本だけではありません。実際の設計は大きく 3 通りに整理できます。1 接続 1 スレッド (または 1 プロセス) は実装が単純で、1 つの接続の処理が重くても他の接続をブロックしない (OS のスケジューラが切り替えてくれる) 利点がありますが、同時接続数に応じてメモリとスイッチングコストが積み重なります。1 スレッドのイベントループ はメモリ効率が良く、大量の待機中接続を安く抱えられますが、1 つの処理がうっかりブロッキング呼び出しをすると、ループ全体が止まってその間すべての接続が待たされます。

実務でよく使われるのは、この 2 つを組み合わせたハイブリッド型です。CPU コア数と同じくらいの数のイベントループを立てて (プロセスまたはスレッドとして並列に動かし)、それぞれのループが多数の接続を安くさばく、という構成です。nginx のワーカープロセスはこの形の代表例として知られています。どの形を選ぶかは、「1 件あたりの処理が I/O 待ちが多いか、CPU 計算が重いか」で変わります。I/O 待ちが多いなら 1 スレッドのイベントループで多くの接続をさばける一方、CPU 計算が重い処理は 1 本のイベントループを長時間止めてしまうため、ワーカーを複数に分けるか、重い処理だけ別スレッド / 別プロセスに切り出す設計が必要になります。

図: 1 接続 1 スレッド ・ 1 スレッドのイベントループ ・ 両者を組み合わせたハイブリッド型の 3 通り。

5. backlog と accept キュー

第 02 回で見た listen(sockfd, backlog) の backlog 引数には、実は 2 段階の待ち行列が関わっています。1 段目はSYN キュー (半開き接続の待ち行列) で、3-way ハンドシェイクの途中、つまり SYN は受け取ったが ACK がまだ返ってきていない接続がここに溜まります。2 段目はaccept キュー (完了済み接続の待ち行列) で、ハンドシェイクが完了したものの、アプリケーションがまだ accept() を呼んでいない接続がここに溜まります。

listen() の man page には、「backlog の上限に達した状態で新しい接続要求が来た場合、クライアントは ECONNREFUSED エラーを受け取るか、プロトコルが再送をサポートしていればその要求は黙って無視され、クライアント側の再試行で後から成功することがある」と明記されています。つまり、accept() を呼ぶ側の処理が遅れて accept キューが埋まると、新しいクライアントから見て「接続拒否」または「応答が来ない」という形で遅延が表面化します。

図: 接続は SYN キュー (ハンドシェイク中) → accept キュー (処理待ち) の順に進む。

6. バックプレッシャー ― 速い送信者と遅い受信者

イベントループで accept キューが埋まる現象は、実は分散システム全体で繰り返し出てくる、より一般的な問題の 1 つの現れです。送信者がデータを作る速度が、受信者がそれを処理する速度を上回ると、両者の間のどこかにデータが積み重なっていくという問題です。これをバックプレッシャー (backpressure, 背圧) と呼び、「積み重なる前に、送信者側に『もう送らないで』と伝え返す」仕組みの総称を指します。

イベントループの文脈では、処理が追いつかずソケットの受信バッファが溜まり続けると、OS は TCP の仕組み (受信ウィンドウのサイズ通知) を使って送信側に自然に「送る速度を落とすよう」伝えます。これはアプリケーションが何も実装しなくても TCP 自身が持っている最低限のバックプレッシャーです。しかしアプリケーション層では、これだけでは不十分な場面が多く、accept() を一時的に呼ぶのを止める、処理待ちのキューに上限を設けて超えたら新規受付を拒否する、上流に対して明示的に「遅くして」と伝える、といった設計が必要になります。この考え方は、この先の回で出てくるメッセージキューの可視性タイムアウトや、レートリミッタ、サーキットブレーカーといった仕組みの土台になります。

図: バックプレッシャーは、積み重なる前に受信側から送信側へ「遅くして」と伝え返す仕組み。

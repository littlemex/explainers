ここまで、TLA+ の仕組みを小さな例で見てきました。今回は、実際の大きなシステムで TLA+ がどう使われたかを、AWS (Amazon Web Services) の形式手法チームが書いた論文 "How Amazon Web Services Uses Formal Methods" (Newcombe ほか, CACM 2015) から見ます。小さな例とは違う、現実の規模での効き目と限界が書かれています。

1. なぜテストでは足りなかったか

S3 (Simple Storage Service) は 2006 年のローンチから 6 年で 1 兆個のオブジェクトを保存するまでに成長し、秒間 1.1 百万件のリクエストを扱うようになりました。論文は、このような規模のシステムでは「コードが到達しうる状態の数は天文学的 (astronomical)」であり、テストでは覆いきれない設計上のミスが残ると述べています。特に危険なのは、コードが忠実に設計を実装していても、その 設計自体 が稀な状況を正しく扱えていない場合です。こうした設計のバグは、深い設計レビューやコードレビュー、障害注入テスト、ストレステストをいくら重ねても見つからないことがある、と論文は率直に書いています。

図: テストは選んだシナリオの確認、TLC は指定した範囲を網羅的に探索するという違い。

2. DynamoDB と S3 で見つかった実際のバグ

DynamoDB は 2012 年 1 月に、複数のデータセンターにまたがる複製と強い一貫性を両立させる NoSQL データストアとして登場しました。開発したエンジニアはまず従来どおり手書きの非形式的な証明でレプリケーション機構を検証しましたが、それでも見逃す恐れが残ると考え、939 行の TLA+ 仕様を書いて TLC で検査しました。検査は 3 つのバグを見つけ、そのうち一部は最短の反例が 35 ステップ もかかる深いものでした。論文は「そのような複合的な事象が起こりにくいということは、バグへの防御にはならない」と述べ、AWS はそれと同程度に複雑な事象の組合せを実際に観測してきたと付け加えています。

S3 の低レベルの耐障害性ネットワーク通信アルゴリズム (804 行の PlusCal 仕様) では 2 つのバグが見つかり、その後提案された性能最適化の中にもさらにバグが見つかりました。別のデータの背後再配置アルゴリズム (645 行) では 1 つのバグが見つかり、さらに最初に提案された修正そのものにもバグが見つかりました。

図: 論文の表に示された、複数のシステムで見つかったバグの件数 (幅はバグ件数を表す)。

3. 設計の検証であってコードの検証ではない、そして学習期間

論文は、TLA+ を知ったエンジニアが必ず聞く質問を紹介しています。「実行可能なコードが、検証済みの設計を正しく実装していることはどうやって分かるのか」という質問です。論文の答えは率直です。「The answer is that we don't (私たちには分かりません)」。TLA+ が検証するのは抽象化された設計であり、実際のコードそのものではありません。

その代わりに論文は、形式手法で設計を正しくすることが「コードを正しくするための必要な第一歩」になると位置づけています。設計が壊れていればコードもほぼ必ず壊れており、設計の段階で間違いを減らすことが、結局はコード全体の正しさに向けた効果の高い入口になる、という考え方です。

学習にかかった期間についても具体的な数字が書かれています。入社したばかりの新人からプリンシパルエンジニアまで、ゼロから TLA+ を学んで実用的な成果を出せるようになるまでにかかった期間は「2 週間から 3 週間」で、中には週末や夜だけの自習で、助けも訓練も受けずに到達した例もあったそうです。執筆時点で、AWS の 10 個の大規模で複雑な実システムに TLA+ が適用され、7 つのチームが使うようになっていました。

図: TLA+ が保証するのは設計の範囲までで、コードがその設計どおりかは別の問題として残る。

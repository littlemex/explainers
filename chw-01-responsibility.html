責務分担の地図 ── 静的 vs 動的

並列性・依存解決・スケジュールを、実行時のハードとコンパイル時のコンパイラのどちらが担うのか

0この章の狙い

プロセッサ設計の根源的な問いは「やるべき仕事を、いつ・どこで・どの順で実行するかを誰が決めるか」です。この一点を軸に、シリーズ全体の地図を描きます。

一言でいうと
プログラムを速く走らせるには、独立した演算を並列に実行し、データを近くに置き、命令を良い順序で流す必要があります。この 3 つの判断を、実行時にハードウェアが動的にやる方向（スーパースカラなど、詳細は本文）と、コンパイル時にコンパイラが静的にやる方向（VLIW など）があります。前者は「賢いハード＋素朴な命令列」、後者は「素朴なハード＋賢いコンパイラが作り込んだ命令列」。どちらに寄せるかで、電力効率・性能の予測可能性・汎用性のトレードオフが決まります。一部の深層学習アクセラレータ（TPU や国産の MN-Core）はこの軸を静的側へ大きく振り切った設計です。ただし後述の通り、深層学習の主力である GPU はむしろ動的側にあり、「静的が成り立つこと」と「静的が勝つこと」は別の話だという点も、このシリーズで見ていきます。
1. 3 つの判断 ── 何を誰が決めるのか 2. 動的の極 ── ハードが実行時に掘る 3. 静的の極 ── コンパイラが前もって決める 4. 【体験】責務スペクトラム 5. なぜ深層学習は静的側へ寄るのか 6. シリーズの地図 7. まとめ

13 つの判断 ── 何を誰が決めるのか

性能を左右する判断は、大きく 3 つに分けられます。

判断内容動的にやると静的にやると
依存解決ある演算が別の演算の結果を待つ必要があるかハードがレジスタの生成・消費を実行時に追跡（スコアボードやレジスタリネーミングと呼ぶ回路）コンパイラがデータ依存グラフを解析し、命令の配置で保証
スケジュールどの演算をどのサイクルにどのユニットで実行するかハードが実行時に順序を入れ替える（アウトオブオーダー）コンパイラが命令列を並べ替えて確定（バンドル化）
データ移動必要なデータをいつ演算器の近くへ運ぶかハードのキャッシュが自動で出し入れコンパイラが明示的にスクラッチパッド（ソフトが中身を管理する高速メモリ）へ配置・転送

重要なのは、この 3 つは「やる／やらない」ではなく「誰がやるか」の問題だということです。どのプロセッサも同じ仕事をしますが、その判断を実行時のトランジスタに任せるか、コンパイル時のソフトウェアに任せるかが違うだけです。任せ方が、そのままハードの複雑さと電力に跳ね返ります。

なお、依存の中でもメモリ依存（別々のポインタが同じ番地を指すか＝エイリアシング）は静的に確定できないことが多いのが、静的方式の最大の弱点です。レジスタ依存はコンパイラが解析できますが、メモリのエイリアスは実行時にしか分からない場合があり、そこは保守的に扱わざるを得ません。

2動的の極 ── ハードが実行時に掘る

現代の高性能 CPU は、素朴な命令列を受け取り、その中の並列性を実行時に自力で発見します（以下「掘る」＝命令列に埋もれた並列性を実行時に発掘する、の意で使います）。

スーパースカラ CPU は 1 サイクルに複数命令を発行します。多くの高性能 CPU はこれにアウトオブオーダー実行を組み合わせ、後ろの独立命令を先に走らせます（スーパースカラでも順序を守るインオーダー実装もあり、両者は別概念です）。そのために、命令窓の中の依存関係を追跡する回路、レジスタの偽の依存を消すリネーミング、分岐先を予測する分岐予測器、外れたときに巻き戻す投機実行の仕組みを積みます。これらは並列性を掘るためだけの回路で、演算そのものはしていません。

動的方式の強みは汎用性と互換性です。分岐が多く、メモリアクセスが不規則で、実行時にしか分からない情報（キャッシュミスの有無など）が多いワークロードでも、ハードがその場で最善を尽くします。同じバイナリが、より賢い次世代 CPU に載せ替えるだけで速くなることさえあります。代償は、並列性を掘る回路が消費する電力と面積、そして性能が実行時の状況に揺らいで予測しにくいことです。

3静的の極 ── コンパイラが前もって決める

正反対の発想が、判断をすべてコンパイル時に済ませてしまう静的方式です。

VLIW（超長命令語）では、コンパイラが「どの演算をどのサイクルにどのユニットで実行するか」を決め切り、それを 1 つの長い命令（バンドル）にエンコードします。空間アーキテクチャ（シストリックアレイやデータフロー）では、演算器を格子状に並べてデータを流し、制御をほぼ持ちません。いずれもハードは依存チェックも順序入れ替えもしないと割り切り、その分のトランジスタと電力を演算器に回します。

コンパイラの重責。 静的方式では、コンパイラがレイテンシを 1 サイクルでも読み違えると、まだ出ていない結果を使って計算が壊れます（ハードが守ってくれない場合）。性能はコンパイラの品質に直結し、ユニット数やレイテンシが変わると再コンパイルが要ります。汎用計算では致命傷になりがちなこの弱点が、規則的な深層学習では問題になりにくい ── ここがすべての分かれ目です。

4【体験】責務スペクトラム

同じ小さなプログラム（6 演算）を 4 つの実行モデルで走らせ、完了までのサイクルと「誰が何を決めているか」を見比べます。各バーは演算で、横幅はレイテンシ（結果が出るまでの時間）です。

# 対象プログラム（各演算のレイテンシと依存）
a = load X [MEM, lat 2]
b = load Y [MEM, lat 2]
c = a * b [MUL, lat 3, needs a,b]
d = a + b [ALU, lat 1, needs a,b]
e = c + d [ALU, lat 1, needs c,d]
store e [MEM, lat 1, needs e]
MEM（load/store） MUL ALU
ハードウェアの複雑さ（並列性を掘る回路）
電力配分（電力のうち演算に回せる割合）
汎用性・互換性

前提: このデモで In-order は 1 発行、OoO は 2 発行（どの種類でも）、VLIW は型付きスロット（MEM/ALU/MUL）を同時に、データフローは演算器が十分にあると仮定してクリティカルパス（依存の連鎖で決まる到達下限）まで詰めます。つまり各モデルは幅も含めた「設計思想の束」であり、幅だけを揃えた単一条件の実験ではない点に注意してください。

見どころはサイクル数そのものではなく、同じ結果に至る「経路」の違いです。OoO はハードが実行時に順序を掘って並列化し、VLIW は同じ並列化をコンパイラが前もって命令に焼き込みます。両者の到達サイクルは近い一方、VLIW は依存追跡・リネーミング・リオーダバッファ（完了した結果を並べ直して確定させる緩衝装置）といった「掘るための回路」を積みません（フェッチ・デコード・レジスタファイルは両者とも必要です）。データフローは、演算器が十分にあれば到達し得る下限＝クリティカルパスを示します（現実には配線・メモリの制約で常には達しません）。「速さ」ではなく「速さを誰がどう作ったか」がこの軸の本質です。なお、このデモの規模では各方式の到達サイクルは近く、命令の順序入れ替えそのものの効果は見えにくいので、その効果は同一ハードで並べ替えの有無だけを比べる 03 章のデモで分離して示します。

5なぜ深層学習は静的側へ寄るのか

静的方式の弱点（分岐・不規則アクセス・互換性）が、密な行列積が支配的な範囲では問題になりにくいからです。

静的方式の弱点汎用計算では深層学習では
分岐が読めない頻繁で予測が要る行列積・畳み込み主体で分岐がほぼ無い
メモリアクセスが不規則ポインタ追跡など予測困難テンソルの形が既知で、アクセスがコンパイル時に見通せる
実行時情報に依存キャッシュミス等が動的計算グラフが静的で、全サイクルを事前に計画できる
互換性・再コンパイル既存バイナリ資産が重い専用コンパイラと一体で提供でき、毎回コンパイルが前提

ただし、現代の深層学習がすべて静的というわけではありません。MoE のルーティング、可変長系列、動的な形状、early-exit など、実行時にしか決まらない要素も増えています。ここでの主張は「密な行列積が計算の大半を占める範囲では静的スケジューリングの前提が成り立つ」という限定つきのものです。

つまり密な行列積が支配的なワークロードは、静的スケジューリングの前提条件（規則性・予測可能性・専用コンパイラ）を満たしやすい領域です。だからこそ、並列性を掘る回路を捨てて演算器と電力効率に全振りする設計が成り立ちます。TPU のシストリックアレイ、そしてキャッシュも分岐予測もアウトオブオーダーも一切持たない MN-Core は、この論理を突き詰めた先にあります（第 07・10 章）。
それでも GPU が主流なのはなぜか。 「静的が成り立つ」ことと「静的が勝つ」ことは別問題です。深層学習の市場を支配しているのは、ワープスケジューラ（多数のスレッド束を実行時に切り替えて遅延を隠す仕組み）やキャッシュ、動的発行を備えたかなり動的な GPU です。理由は、静的全振りが苦手な動的ワークロードへの柔軟性、成熟したコンパイラとライブラリ、巨大なエコシステムにあります。静的全振りが有利になるのは、あくまでワークロードが規則的で、専用コンパイラを一体提供できるという条件が揃うときです。この条件と代償は、以降の章で具体的に見ていきます。

章テーマ軸の位置

補足: 「静的 ⇆ 動的」は 1 本の軸に見えますが、実際には「命令スケジュール（VLIW）」「データ配置（スクラッチパッド）」「データ並列の露出（SIMD）」「空間配置（シストリックアレイ）」といった独立に選べる複数の設計判断の束です。1 本軸はそれらをまとめて眺めるための近似であり、実在のチップ（たとえば MN-Core は VLIW＋SIMD＋スクラッチパッドの組み合わせ）は複数の判断を個別に採用しています。

7まとめ

論点要点
核心の問い依存解決・スケジュール・データ移動を「誰が」決めるか
動的の極スーパースカラ / OoO。汎用性・互換性が高いが、掘る回路が電力を食い性能が揺らぐ
静的の極VLIW / 空間アーキ。ハードが単純で電力効率・予測可能性が高いが、コンパイラ依存で汎用性が低い
深層学習（密な行列積）規則的・分岐が少なく・専用コンパイラ前提 ── DSP と並び、静的側の前提を満たす代表例
この先MN-Core は静的側に全振りした設計。高い電力効率ゆえ 3D 積層まで一貫する（10 章）
結論。「速いプロセッサ」は一種類ではありません。並列性を掘る責務をハードに置くかコンパイラに置くかという一本の軸の上に、あらゆるアーキテクチャが並びます。このシリーズは、その軸を左（動的）から右（静的）へ歩き、深層学習アクセラレータがなぜ右端に立つのかを、動かして理解していきます。

タイムアウト・リトライ・冪等性 ― 「送った」と「届いた」は同じではない

応答が来ないとき、処理が成功したのか失敗したのかはクライアントには分からない。この不確実性を前提に、同じ処理を安全に繰り返せる形にしておく必要がある

この回の前提: 第 02 回 ソケットプログラミング入門、第 09 回 メッセージキューと Pub/Sub

ネットワーク越しに処理を依頼したとき、応答が返ってこなければ、成功したのか失敗したのかはクライアント側には分かりません。もう一度送れば直るかもしれませんが、もし 1 回目が実は成功していたら、同じ処理が 2 回実行されてしまいます。決済なら二重課金、注文なら二重発送です。この回では、いつ ・ どれだけ待って再送するか (リトライとバックオフ) と、同じ処理を何度実行しても結果が 1 回分と同じになるように作る性質 (冪等性) を、決済ゲートウェイの例で確認します。

1. なぜリトライが必要か ― 応答が無いときの不確実性

クライアントがサーバに処理を依頼し、タイムアウト (一定時間待っても応答が来ないと諦める仕組み) に達したとき、実際に起きていた可能性は 3 つあります。1 つ目は依頼そのものがサーバに届いていない場合で、この場合サーバは何もしていません。2 つ目は依頼は届いたが処理中にサーバが落ちた場合で、処理は途中で止まっているかもしれません。3 つ目は処理は正常に完了したが、その応答がクライアントに届く前に失われた場合で、この場合サーバ側では処理が完全に終わっています。

クライアントから見ると、この 3 つはすべて「応答が来ない」という同じ見え方になり、区別する手段がありません。ここで安全策として「応答が無いなら失敗したとみなして再送する」という判断をすると、3 つ目のケース (処理は実際には成功していた) では、同じ処理がもう一度実行されることになります。決済処理であれば二重課金、注文処理であれば二重発送です。つまりリトライは「失敗したかもしれない処理をやり直す」仕組みであると同時に、「実は成功していた処理を重複させる」危険も併せ持っています。この危険に対処する仕組みが、次の節で説明する冪等性 (idempotency) です。

図: 応答が無いという同じ見え方の裏に、処理が実際には完了している場合も含まれる。

2. リトライ戦略 ― いつ ・ どれだけ待って再送するか

再送のタイミングには何通りかの方式があります。線形バックオフ (linear backoff) は、再送までの待ち時間を一定間隔で増やしていく方式で、実装が単純です。しかし、同時に失敗した多数のクライアントが同じ間隔で再送すると、再送のタイミングが揃ってしまい、サーバに負荷が再び集中するリトライ嵐 (retry storm) を引き起こしやすくなります。線形ジッタバックオフ (linear jitter backoff) は、線形に増える待ち時間にランダムな揺らぎ (ジッタ) を加えることで、再送のタイミングを散らし、この集中を緩和します。

指数バックオフ (exponential backoff) は、待ち時間を 1 秒、2 秒、4 秒、8 秒のように倍々に増やしていく方式で、失敗が続くほど間隔を大きく空けるため、高負荷の状況での再送の衝突を大きく減らせます。ただし、一時的な障害であれば短い待ちで解決したはずの場面でも、不必要に長く待たせてしまう欠点があります。指数ジッタバックオフ (exponential jitter backoff) は指数バックオフにさらにランダムな揺らぎを加えた方式で、間隔を大きく空けつつ衝突も避けられるため、実務では最もよく使われます。

図: 指数バックオフは再送回数が増えるほど待ち時間が急激に伸び、高負荷時の衝突を線形バックオフより強く避ける。

3. 冪等性 ― 何度実行しても結果が 1 回分と同じになる性質

冪等性 (idempotency) とは、同じ処理を 1 回実行しても複数回実行しても、最終的な結果が変わらない性質を指します。HTTP の世界では、PUT (指定した内容でまるごと置き換える) や DELETE (指定したものを削除する) はもともと冪等です。10 回 DELETE を送っても、1 回目で削除され、残りの 9 回は「すでに無い」という同じ結果になるだけです。これに対し POST (新しい何かを作成する) は、何も工夫しなければ冪等ではありません。同じ内容の POST を 2 回送れば、2 つの別々のリソース (2 件の注文、2 回の決済) が作られてしまいます。

決済処理のように本来冪等でない操作を安全に再送できるようにする標準的な方法が冪等キー (idempotency key) です。クライアントが処理を依頼する際、その処理を一意に識別するキーを自分で生成して添えます (サーバ側で生成するキーでは、キーの発行自体がもう 1 回のネットワーク往復になり、その往復が失敗したときに同じ問題が再発するため、クライアント側で生成するのが基本です)。サーバは受け取ったキーを「処理済みキーの記録」と照合し、すでに同じキーで処理済みであれば、新たに処理を実行せず前回と同じ結果をそのまま返します。決済ゲートウェイでは、これを認可 (authorization) と確定 (capture) の 2 段階に分け、認可の時点で冪等キーを発行し、同じキーでの確定リクエストが何度来ても実際の課金は 1 回だけになるように設計します。

次のコードは、冪等キーを使った決済処理の最小の形を示したものです。

import threading

class PaymentProcessor:
    def __init__(self):
        self.processed = {}
        self.lock = threading.Lock()

    def charge(self, idempotency_key, amount):
        with self.lock:
            if idempotency_key in self.processed:
                return self.processed[idempotency_key]
            result = {'status': 'charged', 'amount': amount}
            self.processed[idempotency_key] = result
            return result

processor = PaymentProcessor()
print(processor.charge('key-1', 1000))
print(processor.charge('key-1', 1000))

1 回目の呼び出しでは key-1 が未処理なので課金を実行し、結果を記録します。2 回目の呼び出しでは同じキーが見つかるため、新たに課金せず記録済みの結果をそのまま返します。threading.Lock を使っているのは、同時に 2 つのリクエストが同じキーで到着した場合に、両方が「未処理」と判定して 2 回課金してしまう競合を防ぐためです。

図: 同じ冪等キーの 2 回目は、記録済みの結果を返すだけで新たな課金を行わない。

4. どこで壊れるか ― リトライと冪等性の限界

リトライ戦略にも冪等性にも、それぞれ壊れ方があります。1 つ目はリトライ嵐です。多数のクライアントが同時に障害を検知し、同じようなタイミングで再送を始めると、まだ回復していないサーバやその先の DB にさらに負荷を重ねてしまい、障害を長引かせることがあります。バックオフとジッタはこれを緩和しますが、再送の総数そのものに上限 (最大リトライ回数) を設けないと、障害が長引くほど再送の量が積み重なり続けます。

2 つ目はタイムアウトの不整合です。呼び出し元のタイムアウトがサーバ側の処理時間より短いと、サーバがまだ処理を続けているうちにクライアントが「失敗した」と判断して再送してしまい、同じ処理がサーバ側で並行して 2 つ走ることになります。呼び出しの連鎖が深い (A が B を呼び、B が C を呼ぶ) 場合は、途中の層のタイムアウトが外側の層のタイムアウトより長いと、外側がすでに諦めた後も内側の処理だけが無駄に動き続けるという無駄も生まれます。

3 つ目は冪等キーの記録自体の寿命と競合です。「処理済みキーの記録」を永久に保持できないことが多く、何らかの期限で削除されます。削除された後に遅れて届いた再送は「未処理」と判定されてしまい、冪等性が意図せず破れます。また、先のコード例で示したロックが無い実装では、同じキーを持つ 2 つのリクエストがほぼ同時に到着すると、両方が「まだ処理済みではない」と判定してしまい、ロックの意図 (同じキーの処理を 1 つに絞る) が果たされません。4 つ目はメッセージキューでの再処理です。多くのメッセージキューは「少なくとも 1 回届ける (at-least-once)」保証をするため、同じメッセージが複数回届くことを前提に、受信側のハンドラ自体を冪等に作る必要があります。

図: リトライ嵐は再送のタイミングが揃うことで起き、冪等キーの競合は同時到着によって起きる。

5. 実システムでの例 ― 決済ゲートウェイの認可 ・ 確定フロー

オンライン決済を仲介する決済ゲートウェイ (Stripe や PayPal のようなサービス) は、認可 (authorization) と確定 (capture) の 2 段階構成を使ってこの問題を解決しています。注文が確定する前の段階で、まずクライアントが一意な冪等キーを生成して認可リクエストに添えます。認可は「この金額を後で確定してよいか」をカード発行会社に確認する処理で、まだ実際の引き落としは起きません。続いて確定リクエストで、先ほどの認可に対応する冪等キーを使って実際の引き落としを指示します。注文処理の途中でネットワークが不安定になり、確定リクエストへの応答が届かずクライアントが再送しても、ゲートウェイは同じ冪等キーを見て「既に確定済み」と判断し、二重に引き落とすことはありません。

再送の間隔については、AWS のようなクラウド事業者の SDK が指数ジッタバックオフを既定の挙動として採用しています。クライアント側のライブラリは、一時的なエラー (ネットワークの瞬断やサーバの過負荷を示す応答コードなど) を検知すると、1 回目は短い間隔、2 回目はその倍、3 回目はさらに倍という形で間隔を広げながら、各間隔にランダムな揺らぎを加えて再送します。これにより、同時に失敗した多数のクライアントの再送タイミングが自然に分散され、復旧しかけているサーバに再送が集中して再び倒れる事態を避けられます。

この 2 つの仕組みは役割が異なります。バックオフとジッタは「いつ再送するか」というタイミングの制御であり、再送そのものを安全にするものではありません。冪等キーは「同じ処理が何回来ても結果は 1 回分」という安全性の保証であり、タイミングとは無関係です。実務では両方を組み合わせ、タイミングを散らしたリトライを、冪等性を持つ操作に対してだけ行う、という形に落ち着きます。冪等でない操作 (例えば一意制約の無い単純な POST による注文作成) に無条件でリトライを仕掛けると、この回で見てきた二重課金や二重発送がそのまま現実になります。

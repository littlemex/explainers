誰が WQE を書いているのか

ibverbs、libfabric、NVSHMEM、NCCL GIN、EFA-GDA。層の名前ではなく「記述子を書く主体」で整理する

← シリーズ目次

0この回で解く混乱

RDMA 周辺の用語は層が入り組んでいて、「ibverbs と libfabric はどちらが下か」「NVSHMEM と NCCL は競合か」といった問いに素直な答えがありません。しかし DeepEP の EFA 対応を理解するには、1 つの問いだけ立てれば足ります。

NIC に渡す記述子 (Work Queue Entry, WQE) を、最終的に誰がどの形式で書いているのか。 この問いで串刺しにすると、層の関係が一列に並びます。

一言でいうと
ibverbs と libfabric はどちらも NIC を操作するためのユーザ空間 API で、上下関係ではなく「同じ NIC を違う抽象で触る 2 つの入口」です。ただし GPU 起動通信ではデータ経路でどちらも使われません。GPU が WQE を直接書くからです。だから「どちらの API か」より「WQE の形式を誰が知っているか」が本質になります。DeepEP V1 は カーネルが Mellanox の WQE 構造体を直接書いていました。V2 はそれを NCCL GIN のバックエンドという層に押し出し、EFA では EFA-GDA バックエンドが EFA の WQE 形式を担当する。libfabric はその制御経路 (接続・メモリ登録) だけに残ります。
1. 制御経路とデータ経路を分ける 2. ibverbs と libfabric の関係 3. DeepEP V1 は mlx5 の構造体を直接書いていた 4. NCCL GIN という層 5. GIN の 4 つのバックエンド 6. plugin の ABI は 2 系統ある 7. EFA-GDA が libfabric をどう使うか 8. 一枚の地図

1制御経路とデータ経路を分ける

RDMA の話が混乱するのは、接続を作る話と 1 バイト送る話を同じ language で語るからです。この 2 つは実装上まったく別の場所にあります。

制御経路 (control plane)データ経路 (data plane)
やることデバイスを開く、queue pair を作る、メモリを登録する (鍵をもらう)、相手のアドレスを交換するWQE を送信キューに書き、doorbell を叩き、完了を観測する
頻度初期化時に数回1 通信ごと、毎マイクロ秒
実行主体常に CPUCPU (proxy) または GPU (GIN)
使う APIibverbs / libfabric / ドライバ拡張キューのメモリを直接書く (API を通らない)

データ経路が「API を通らない」というのがポイントです。RDMA の高速性はまさに、送信のたびにカーネルもライブラリ呼び出しも経由せず、ユーザ空間からマップされたキューに直接記述子を書くことで得られています (OS bypass)。ライブラリ (ibverbs の ibv_post_send など) は、その「キューに書く」処理をインライン関数として提供しているにすぎません。

したがって GPU にその処理をさせたければ、キューのメモリと doorbell レジスタを GPU の番地空間から見えるようにして、GPU 側のコードに同じバイト列を書かせればよい。これが GPU-Initiated Networking の全てです。

2ibverbs と libfabric の関係

よくある誤解は「libfabric は ibverbs のラッパー」です。実際は並列する 2 つの抽象で、EFA では両方が同じドライバに向かって別の顔を提供しています。

ibverbs (rdma-core / verbs)libfabric (OFI)
抽象の単位Queue Pair、Memory Region、Completion Queue。InfiniBand のハードウェアモデルをほぼそのまま写した APIEndpoint、Domain、Address Vector。「能力 (capability) を要求して、満たす provider を選ぶ」という形
EFA での立ち位置efa provider がユーザ空間ドライバとして存在し、efadv_* という EFA 固有拡張があるfi_efa provider。NCCL 用プラグイン (aws-ofi-nccl) が使うのはこちら
QP の種類EFA は SRD と UD のみ。RC (Reliable Connected) が無い能力の要求として表現される (FI_RMA、FI_HMEM など)

ここに DeepEP V1 が EFA で動かない理由の半分があります。EFA には RC queue pair がありません。 InfiniBand で当たり前に使う「順序保証つき信頼配送のコネクション」という部品が無く、代わりに SRD (Scalable Reliable Datagram) があります。SRD は再送してくれる (信頼配送) が、順序は保証しません。この 1 点が第 3 回のテーマです。

また EFA は Subnet Management のための umad インタフェースを持たないため、ibstat のような InfiniBand 前提のツールから見えません。DeepEP fork がリンク速度の検出を ibstat から /sys/class/infiniband/<dev>/ports/*/rate の sysfs 読みに変えたのはこの理由で、コメントにも「ibstat は umad を持たない provider (EFA など) を見られない」と明記されています (deep_ep/utils/envs.py)。この種の「InfiniBand を前提にした周辺コードの洗い出し」も EFA 対応の実務の一部です。

3DeepEP V1 は mlx5 の構造体を直接書いていた

「EFA では動かない」を抽象論で語る必要はありません。V1 のソースを見ればそのまま書いてあります。

V1 のノード間通信は NVSHMEM の IBGDA (InfiniBand GPU Direct Async) 経路を使います。DeepEP はその device 側コードを自分のカーネルに取り込んでいて、ファイル冒頭に NVSHMEM のどのヘッダから写したかまで書かれています (csrc/kernels/legacy/ibgda_device.cuh)。中身を見ると、こうなっています。

typedef struct mlx5_wqe_ctrl_seg  __attribute__((__aligned__(8))) ibgda_ctrl_seg_t;
...
nvshmemi_ibgda_device_qp_t* ibgda_get_rc(int pe, int id);
...
struct mlx5_wqe_raddr_seg   raddr_seg;
struct mlx5_wqe_inl_data_seg inl_seg;
...
__be32* dbrec_ptr = qp->tx_wq.dbrec;   // doorbell record を GPU から書く

mlx5_wqe_ctrl_seg、mlx5_wqe_raddr_seg は Mellanox / NVIDIA ConnectX のハードウェア記述子のレイアウトです。ibgda_get_rc は RC queue pair を取ってくる関数です。つまり V1 の GPU カーネルは、ConnectX の WQE 形式を知っており、RC QP の存在を前提にしている。EFA には RC が無く、WQE 形式も違うので、これは API の互換性の問題ではなく、カーネルのソースコードがハードウェアに直結しているという問題です。移植ではなく書き換えになります。

ここが分岐点
V1 を EFA に対応させるには、NVSHMEM に EFA transport を足し、さらに IBGDA 相当の GPU 起動経路を EFA 向けに用意し、そのうえで DeepEP のカーネルが書く WQE 形式を切り替えられるようにする必要があります。V2 が NCCL GIN に移ったことで、この 「WQE 形式を知っている場所」がカーネルの外に出た。だから EFA 対応が現実的な作業量になりました。

4NCCL GIN という層

NCCL 2.31 以降には、集団通信 API とは別に「device 側から片側通信を発行する API」があります。これが GIN です。

DeepEP V2 のカーネルが書くのはこういうコードです (実際の hybrid_dispatch_unordered.cuh より、引数を簡略化)。

gin.put<ncclTeamTagRail>(dst_ptr, src_ptr, num_bytes, dst_rank,
                        ncclGin_SignalAdd{signal_id, 1ull});
...
const uint64_t landed = gin.readSignal(signal_id);   // 既定で acquire ロード

ここには mlx5 も EFA も出てきません。出てくるのは put (相手のメモリに置く) と signal (相手側のカウンタを増やす) という 2 つの抽象だけです。そして signal には強さの区別があります。NCCL の device ヘッダ (src/include/nccl_device/gin.h) に定義されている型名がそのまま意味を語っています。

型保証
ncclGin_StrongSignalInc / StrongSignalAddこの signal が見えたなら、先行する全ての put が完了している
ncclGin_WeakSignalInc / WeakSignalAdd束ねられた その put だけが完了している
ncclGin_StrongVASignalInc など (VA 系)signal の置き場が「登録済みメモリ上の任意アドレス」。番号ではなくアドレスで指定する
ncclGin_SignalInc (無印)非推奨。Strong / Weak を明示せよ、とヘッダのコメントにある

この strong / weak と indexed / VA という 2 軸が、以降の全ての議論の座標になります。アプリケーションは初期化時に「自分は strong signal を要求する」「VA signal を要求する」と宣言し (ncclDevCommRequirements の ginStrongSignalsRequired / ginVaSignalsRequired)、バックエンドがそれを満たせなければ初期化が失敗します。

5GIN の 4 つのバックエンド

put と signal という抽象を、実際のハードウェアに落とす実装が複数あります。NCCL の enum にそのまま列挙されています。

src/include/nccl_device/net_device.h の ncclNetDeviceType:

値名前誰が WQE を書くか備考
2GIN_PROXYCPU。GPU は記述子を ring に積むだけNCCL 内蔵の汎用実装。IB でも EFA でも使える
3GIN_GDAKIGPU。Mellanox の WQE 形式IBGDA 系。ConnectX 前提
4GIN_GPIGPU別系統の GPU 起動実装
5GIN_EFA_GDAGPU。EFA の WQE 形式EFA 専用。実装は NCCL のツリー内にある

ここで注意すべきなのは、EFA-GDA の device 側実装は aws-ofi-nccl ではなく NCCL 本体に入っていることです。src/include/nccl_device/gin/efa_gda/gin_efa_gda.h がその本体 (966 行) で、EFA のハードウェア記述子を組む部分は src/transport/net_efa_gda/efa-dp-direct/ にある薄い層 (efa_cuda_dp_impl.cuh、efa_io_defs.h) が担います。ファイル冒頭の著作権表示は Amazon で、SPDX は Apache-2.0 です。

この配置は後で重要になります。これらは device ヘッダとしてインストール対象に含まれるので (efa-dp-direct/CMakeLists.txt がヘッダを ${CMAKE_BINARY_DIR}/include/nccl_device/transport/net_efa_gda/efa-dp-direct/include/ にコピーし、それが install(DIRECTORY ...) で入る)、EFA を持たないマシンでも、DeepEP の JIT カーネルには EFA-GDA の経路がコンパイルされて入っています。第 7 回の emulator 設計でこの事実を使います。

では aws-ofi-nccl は何をしているのか。制御経路とホスト側の管理です。libfabric で EFA のドメインとエンドポイントを開き、メモリを登録し、GPU が使うキューを作って、その番地を device handle に詰めて NCCL に返します。src/rdma/gin/nccl_ofi_gin_gdaki.cpp がその実装で、dev_handle_out->netDeviceType = NCCL_NET_DEVICE_GIN_EFA_GDA と needsProxyProgress = 0 (CPU の進行処理は不要) を設定しています。

6plugin の ABI は 2 系統ある

「NCCL のプラグインを書けばよい」と言うとき、どの ABI を指すかで作業量が桁違いに変わります。ここが後の emulator 設計の分岐点です。

GIN plugin (ncclGinPlugin_v14)RMA plugin (ncclRmaPlugin_v14)
ヘッダsrc/include/plugin/gin/gin_v14.hsrc/include/plugin/rma/rma_v14.h
選択する環境変数NCCL_GIN_PLUGINNCCL_RMA_PLUGIN
device 側コードplugin が持ち込む (createContext が GPU メモリに device handle を作る)不要。NCCL 内蔵の proxy device context を使う
データ経路の関数無し (device 側で完結)iput / iputSignal(..., bool isStrongSignal, ...) / iget / iflush / test / rmaProgress
能力の申告getGinProperties で supportsStrongSignals / supportsVASignals を返せるその関数が無い

この表の最後の行は、公開ソースを読んで確認できる重要な非対称です。さらに 2 つ、実装を決める事実があります。

  • GIN plugin が「自分は proxy 型だ」と名乗ると無視されます。 src/plugin/gin.cc に「external proxy plugin をスキップし、NCCL の GIN proxy を RMA バックエンド越しに使う」という分岐が実際に入っています。つまり proxy 経路を差し替えたいなら RMA plugin を書く以外にありません。
  • proxy バックエンドの能力申告は固定です。 src/gin/gin_host_proxy.cc が supportsStrongSignals = true; supportsVASignals = true; をそのまま書いています。RMA plugin を差し替えても、この 2 つを false に見せることはできません。

    • 逆に、proxy 経路で signal がどう実現されているかも同じファイルから読み取れます。NCCL は indexed signal の実体を GPU メモリ上の uint64 配列として確保し (nSignals * nContexts 個)、それを plugin の regMrSym で登録し、device が signal 付き put を出したときに signalOff = (signalId + contextId * nSignalsPerContext) * sizeof(uint64_t) を計算して plugin の iputSignal を呼びます。つまり proxy 経路では signal は「登録済みバッファへの通常の RMA 加算」であり、それを実行するのは pluginです。第 7 回でこの事実が emulator の設計を決めます。

    7EFA-GDA が libfabric をどう使うか

    「GPU が直接 NIC を叩くなら libfabric は不要ではないか」という疑問への答えです。制御経路にだけ残ります。

    aws-ofi-nccl の EFA-GDA 実装は、libfabric で efa-direct provider のドメインを開き、そのドメインに対して fi_open_ops(&dom->fid, FI_EFA_GDA_OPS, ...) を呼んで GDA 専用の操作テーブルを取得します (src/rdma/gin/nccl_ofi_gin_gdaki.cpp)。コード内のコメントは「libfabric 2.4 以降で proxy plugin は efa-direct fabric を選ぶ。各 rail のドメインが FI_EFA_GDA_OPS を公開する」と説明していて、fi_open_ops が失敗したときのエラーメッセージは「libfabric が古い、または proxy が efa-direct 以外の fabric を選んだ」となっています。

    メモリ登録も libfabric 側です。GPU メモリは FI_HMEM_CUDA + FI_MR_DMABUF で登録され、EFA のドメインは FI_MR_VIRT_ADDR を要求するので、WQE には絶対仮想アドレスが入ります。だから device handle には各 peer の base VA と rkey の表が載っていて、カーネルは「オフセットを渡し、base VA を足して絶対アドレスを作る」という形になります (NCCL 側のミラー定義 gin_efa_gda_dev.h のコメントにその通り書かれています)。

    まとめ方
    EFA-GDA において libfabric は「接続・登録・アドレス解決を行い、GPU に渡すキューの座標を教えてくれる存在」です。1 回の put のためには呼ばれません。したがって「libfabric provider を差し替えれば順序の性質を変えられる」という発想は、GPU 起動経路には効きません。逆に proxy 経路なら libfabric (あるいはそれを差し替えたもの) がデータ経路にいる、という非対称も覚えておいてください。

    8一枚の地図

    ここまでを 1 枚にします。太い線がデータ経路、細い線が制御経路です。

    図 1: 同じカーネルソースが 2 つの経路に落ちる。左は CPU がデータ経路にいるので差し替えやすく、右は GPU が NIC 形式を知っているので高速だが差し替えにくい

    この地図で押さえるべきは、カーネルのソースは 1 つで、バックエンドが 2 つあることです。DeepEP のプロトコルは put と signal だけで書かれているので、どちらのバックエンドでも同じソースが走ります。したがって「プロトコルの正しさ」を検証するのに、必ずしも GPU 起動経路のバックエンドが必要とは限りません。この観察が第 7 回の出発点です。

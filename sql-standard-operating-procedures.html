スタンダード・オペレーティング・プロシージャ ― 慣習でストアドに寄せる

ストアドプロシージャ自体は悪くありません。問題は「迷ったら全部ストアドに書く」という思考停止で、デプロイ・テスト・言語の限界・スケールの 4 つの場所で後から壊れます

この回の前提: 第 24 回 ディプロマティック・イミュニティ (SQL をバージョン管理やテストの対象として扱う考え方)

「ロジックは DB の中に置けば、どの言語からアクセスしても振る舞いが揃う」という理屈は正しいのですが、だからといって業務ロジックを丸ごとストアドプロシージャに寄せてしまうと、デプロイのしにくさ ・ テストのしにくさ ・ PL/pgSQL という言語の限界 ・ データベースサーバーの CPU を食い尽くすスケールの壁という 4 つの場所で後から苦しむことになります。この回では、PostgreSQL の FUNCTION と PROCEDURE の違い、volatility (関数の挙動の分類) の誤った宣言が引き起こす実害、SECURITY DEFINER と search_path が組み合わさったときの権限の乗っ取りを、実際に PostgreSQL 18 で動かして確認します。結論を先に言うと、ストアドは「複数行をまたぐ原子性がどうしても必要な処理」や「軽量な整合性維持」に絞って使うのが安全で、業務ロジックの本体はアプリケーション層に置くべきです。

1. 目的 ― 何をしたかったのか

ストアドプロシージャ (関数・プロシージャの形で DB の中に保存しておく処理のまとまり) を使う動機は主に 3 つです。1 つ目は振る舞いの一致で、Web アプリ・バッチ処理・管理画面など複数のクライアントが同じ DB を触るとき、ビジネスロジックをアプリ側に書くと実装ごとに微妙な差が生まれますが、DB の中に 1 つだけ置けば全クライアントが同じ処理を呼ぶことになります。2 つ目は権限の集約で、「この関数を実行してよいか」だけを管理すれば、テーブルへの直接アクセス権を個々のアプリケーションに配らずに済みます。3 つ目はネットワークの往復削減で、何度も往復が必要な処理を 1 回の呼び出しに畳み込めば、アプリケーションサーバーと DB の間の通信回数を減らせます。

これらの動機自体は正当です。問題は、この理屈を「だから業務ロジックは全部ストアドに書くべきだ」という慣習(スタンダード・オペレーティング・プロシージャ、標準的な業務手順)にまで広げてしまうことです。

2. アンチパターン ― どう書いてしまい、何が壊れるか

「全部ストアドプロシージャ」という方針を取ると、4 つの場所で具体的に壊れます。

デプロイのしにくさ

アプリケーションのコードは Git でバージョン管理し、CI でテストし、ロールバックも容易です。一方でストアドプロシージャは CREATE OR REPLACE FUNCTION を直接本番 DB に対して実行して差し替えることが多く、「どの時点のコードが今動いているか」をアプリのコードと同じやり方で追跡しにくくなります。本文と関数名だけがカタログに残り、変更履歴は別途管理しない限り残りません。

テストのしにくさ

アプリケーション層のコードはモック (本物の代わりに差し替える偽物) を使って依存を切り離し、1 つの関数だけを高速に検証できます。PL/pgSQL の関数は DB に実際に接続して実行するしかなく、外部 API を呼ぶような処理をストアドの中に混ぜてしまうと、テストのたびに本当に外部 API を呼ぶ羽目になります。

言語の限界

PL/pgSQL は SQL を手続き的に書けるようにした言語ですが、汎用プログラミング言語で当たり前にある、充実した標準ライブラリ・パッケージ管理・デバッガ・型システムの支援がありません。複雑な文字列処理や外部サービス連携を PL/pgSQL だけで書こうとすると、汎用言語で書くより多くのコード量と手間が掛かります。

スケールの壁

アプリケーションサーバーは台数を増やせば比較的素直に水平スケールしますが、データベースは書き込みの一貫性を保つ主系が 1 台(または少数)に限られることが多く、CPU を使い切るような重い処理をストアド側に置くと、その負荷が真っ先にデータベースサーバーの CPU を圧迫します。

図: アプリ層は台数を増やして水平にスケールできるが、書き込みを担うデータベースは主系 1 台の CPU に負荷が集中しやすい。

FUNCTION と PROCEDURE の違い: トランザクション制御

PostgreSQL の FUNCTION は、呼び出し元の SQL 文の内側で実行される部品であり、自分でトランザクションを終了すること (COMMIT や ROLLBACK) はできません。これに対して PROCEDURE は CALL 文で直接呼び出されたときに限り、内部で COMMIT や ROLLBACK を呼べます。これを利用して、20 万行をまとめて更新するバッチ処理を、5 万行ずつ区切って COMMIT しながら進める例を実際に実行しました。

CREATE OR REPLACE PROCEDURE close_old_bugs(batch_size int)
LANGUAGE plpgsql
AS $$
DECLARE
  updated int;
BEGIN
  LOOP
    UPDATE bugs SET status = 'FIXED'
    WHERE bug_id IN (
      SELECT bug_id FROM bugs WHERE status <> 'FIXED' LIMIT batch_size
    );
    GET DIAGNOSTICS updated = ROW_COUNT;
    COMMIT;
    EXIT WHEN updated = 0;
  END LOOP;
END;
$$;

CALL close_old_bugs(50000);
-- NOTICE:  200000 行を FIXED に更新した

一方、同じ COMMIT を FUNCTION の中で呼ぶと、PostgreSQL 18 の実機で次のエラーになりました。

CREATE FUNCTION close_old_bugs_fn(batch_size int) RETURNS void
LANGUAGE plpgsql AS $$
BEGIN
  UPDATE bugs SET status = 'FIXED' WHERE status <> 'FIXED';
  COMMIT;
END;
$$;
SELECT close_old_bugs_fn(1);
-- ERROR:  invalid transaction termination
-- CONTEXT:  PL/pgSQL function close_old_bugs_fn(integer) line 4 at COMMIT

図: FUNCTION は呼び出し元の文の内側に居続け、PROCEDURE は CALL 経由でのみ自分でトランザクションを終了できる。

3. 見つけ方 ― カタログからストアドへの依存の集中を探す

既存のデータベースで「ストアドに寄せすぎていないか」を調べるには、2 つのカタログ問い合わせが使えます。1 つ目は pg_proc から関数の本体の大きさ ・ 言語 ・ volatility (後述) ・ SECURITY DEFINER かどうかを一覧する方法です。以下は、この回で作った close_old_bugs (次項) と、5 節で作る為替変換関数 to_jpy_wrong・to_jpy_right を全部作り終えた後に実機で実行した結果です。

SELECT p.proname,
       pg_get_function_arguments(p.oid) AS args,
       l.lanname AS language,
       CASE p.provolatile WHEN 'i' THEN 'IMMUTABLE' WHEN 's' THEN 'STABLE' ELSE 'VOLATILE' END AS volatility,
       p.prosecdef AS security_definer,
       length(p.prosrc) AS body_chars
FROM pg_proc p
JOIN pg_language l ON l.oid = p.prolang
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public'
ORDER BY body_chars DESC;

--     proname     |         args          | language | volatility | security_definer | body_chars
-- ----------------+-----------------------+----------+------------+-------------------+------------
--  close_old_bugs | IN batch_size integer | plpgsql  | VOLATILE   | f                 |        361
--  to_jpy_wrong   | amount_usd numeric    | sql      | IMMUTABLE  | f                 |         81
--  to_jpy_right   | amount_usd numeric    | sql      | STABLE     | f                 |         81

2 つ目は、実際にどの関数がデータベースサーバーの CPU 時間を使っているかを調べる方法です。既定では呼び出し統計は取られていないので、track_functions = all を設定してから呼び出すと、pg_stat_user_functions で呼び出し回数と消費時間がわかります。実機で 20 万行を 5 万行ずつ更新する close_old_bugs を呼んだところ、1 回の呼び出しで合計 3524.768 ミリ秒 (約 3.5 秒、実行ごとに多少揺れますが数千ミリ秒の桁は毎回変わりません) を消費していることが確認できました。同じ統計には to_jpy_wrong (5 節の為替変換関数) の行も載りますが、これは索引作成時に 2 万行分の索引キーを計算し、さらにシーケンシャルスキャンで同じ 2 万行を再評価したため、合計 40,000 回の呼び出しとして記録されています。

SET track_functions = 'all';
CALL close_old_bugs(50000);
SELECT pg_stat_force_next_flush(); -- 統計はすぐには反映されないので明示的に確定させる
SELECT funcname, calls, total_time, self_time FROM pg_stat_user_functions ORDER BY total_time DESC;

--     funcname    | calls | total_time | self_time
-- ----------------+-------+------------+-----------
--  close_old_bugs |     1 |   3524.768 |  3524.768
--  to_jpy_wrong   | 40000 |     62.832 |    62.832

この 3.5 秒という時間は、データベースサーバーの CPU を 3.5 秒間専有したことを意味します。アプリケーションサーバーなら台数を増やして分散できますが、この処理は主系データベースの CPU 時間をそのまま食います。これが「スケールの壁」の具体的な現れです。

4. 使ってよい場合

ストアドプロシージャやトリガーが向いているのは、次のような場面に限られます。

複数行をまたぐ原子性がどうしても必要な処理: 複数のテーブルへの書き込みを 1 つの不可分な操作として扱いたいとき、アプリケーション側で複数回の往復に分けると途中状態が外から見えてしまう危険があり、DB の中で 1 回にまとめた方が安全な場合があります。軽量な整合性維持のためのトリガー: 集計列を最新に保つなど、単純で高速な処理に限ってトリガーを使うのは合理的です (詳しくは第 27 回で扱います)。パーティション管理の自動化: 古いパーティションの自動 DETACH のような、DB の構造そのものに関わる定型作業は DB 側に置く方が自然です。

逆に、外部 API との連携・複雑な分岐を伴う業務ルール・頻繁に変更される価格計算のようなロジックは、テストのしやすさと変更のしやすさを優先してアプリケーション層に置くべきです。

5. 解決策 ― PostgreSQL での正しい書き方

volatility の正しい宣言

PostgreSQL の関数には VOLATILE (何が起きるか予測できない既定値)・STABLE (同じ文の中では同じ入力に対して同じ結果を返すが、他の行の変化に依存してよい)・IMMUTABLE (入力だけで結果が完全に決まり、外部の状態に依存しない) の 3 段階があります。これを誤って宣言すると実害が出ることを、為替レート変換の例で確認しました。

CREATE TABLE exchange_rate (code text PRIMARY KEY, rate numeric NOT NULL);
-- 誤り: 本来は exchange_rate の行に依存するので STABLE が正しいのに IMMUTABLE と宣言
CREATE OR REPLACE FUNCTION to_jpy_wrong(amount_usd numeric) RETURNS numeric
LANGUAGE sql IMMUTABLE AS $$
  SELECT amount_usd * rate FROM public.exchange_rate WHERE code = 'USD_TO_JPY';
$$;
CREATE INDEX expenses_jpy_wrong_idx ON expenses (to_jpy_wrong(amount_usd));
-- この時点のレートは 150 円。索引の各エントリは「150 円のときの値」のまま固定される

UPDATE exchange_rate SET rate = 200.00 WHERE code = 'USD_TO_JPY';
-- レートが 200 円に変わった後、閾値 80000 で検索すると結果が食い違う

索引を経由すると古い (150 円ベースの) 値のまま判定され、0 件になりました。索引を使わずシーケンシャルスキャンで今の行から再計算すると、2 万行中 4,000 件が条件に合致しました。

経路使った値件数 (全 20,000 行中)
索引経由 (via_index_stale)レート 150 円のときの古い値0 件
シーケンシャルスキャン (via_seqscan_fresh)レート 200 円で今計算した値4,000 件

IMMUTABLE という宣言は「索引に一度焼き込んだ値を二度と見直さない」という約束を PostgreSQL に与えることになります。この約束を破る関数を IMMUTABLE と宣言すると、索引の中身が現実のデータと静かに食い違っていきます。正しくは STABLE と宣言するべきですが、STABLE や VOLATILE な式は索引式として使えないため、そもそも「参照先のテーブルに依存する値」を式索引のキーにしようとしたこと自体が設計の誤りだったことになります。

図: 索引は作成時の値を保持するだけで、参照先のテーブルが変わっても自動では追従しない。

SECURITY DEFINER と search_path の乗っ取り

SECURITY DEFINER は、関数を呼んだ人の権限ではなく、関数を作った人の権限で実行するという指定です。管理者権限を持つ人が作った SECURITY DEFINER 関数は、一般ユーザーが呼んでも管理者権限で動きます。ここで関数の本文がスキーマ名を付けない名前 (非修飾名) でテーブルを参照していると、呼び出し側の search_path (名前をどのスキーマから探すかの順序) によって、意図しない別オブジェクトを参照してしまう危険があります。実機で、一般ユーザーが自分のスキーマに同名の偽テーブルを作り、search_path を書き換えるだけで管理者権限の関数から偽のデータを読ませることに成功しました。

-- 管理者 (postgres) が作る、search_path を固定していない関数
CREATE FUNCTION get_hourly_rate(p_name text) RETURNS numeric
LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE r numeric;
BEGIN
  SELECT hourly_rate INTO r FROM accounts WHERE account_name = p_name;
  RETURN r;
END;
$$;
SELECT get_hourly_rate('alice'); -- 50.00 (本物の accounts.hourly_rate)

-- 一般ユーザー app_user_25 が自分のスキーマに偽物を作る
CREATE SCHEMA evil;
CREATE TABLE evil.accounts (account_name text, hourly_rate numeric);
INSERT INTO evil.accounts VALUES ('alice', 999999.00);
SET search_path = evil, public;
SELECT get_hourly_rate('alice'); -- 999999.00 (管理者権限のまま偽物を読んでしまった)

修正は、関数自身に search_path を固定させることです。

ALTER FUNCTION get_hourly_rate(text) SET search_path = public, pg_temp;
-- 修正後、app_user_25 が search_path を evil, public に変えても正しい値に戻る
SET search_path = evil, public;
SELECT get_hourly_rate('alice'); -- 50.00 (正しい値に戻った)
状況get_hourly_rate('alice') の戻り値
管理者自身が呼ぶ (search_path を汚していない)50.00 (本物)
攻撃者が search_path = evil, public に変更後999999.00 (偽物)
ALTER FUNCTION で search_path を固定した後50.00 (本物に戻った)

図: search_path を固定していない SECURITY DEFINER 関数は、呼び出し側の search_path に名前解決を乗っ取られる。

6. PostgreSQL エンジンで考慮しておくこと

CREATE INDEX 実行中は search_path が一時的に制限されるという事実を実機で踏みました。式索引の中で使う関数の本文にスキーマ名を付けずにテーブルを参照すると、通常の SELECT では解決できても CREATE INDEX の中では解決できず、「relation does not exist」というエラーになります。これは PostgreSQL の公式ドキュメントに明記されている仕様で、CREATE INDEX が実行されている間は search_path が pg_catalog, pg_temp に固定されるためです。式索引の中で使う関数の本文は、常にスキーマ名を明示するのが安全です。

-- スキーマ名を付けない場合、CREATE INDEX の中だけで失敗する
CREATE OR REPLACE FUNCTION to_jpy_wrong(amount_usd numeric) RETURNS numeric
LANGUAGE sql IMMUTABLE AS $$
  SELECT amount_usd * rate FROM exchange_rate WHERE code = 'USD_TO_JPY'; -- NG
$$;
CREATE INDEX ON expenses (to_jpy_wrong(amount_usd));
-- ERROR:  relation "exchange_rate" does not exist
-- (CREATE INDEX の実行中は search_path が pg_catalog, pg_temp に固定されるため)

PROCEDURE 内の COMMIT とサブトランザクションについても注意が必要です。PROCEDURE の中で COMMIT を呼ぶと、それまでの変更が本当に確定し、ロックも解放されます。ループの中で COMMIT を繰り返すバッチ処理は、1 回の巨大なトランザクションで長時間ロックを持ち続けるより安全ですが、途中で処理が失敗した場合、どこまで進んだ状態でコミットされているかをアプリケーション側で追跡できるようにしておく必要があります。

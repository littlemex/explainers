eager と compile ― 誤解と、検証の最短経路

eager なら移植は要らないのか。答えは「要る」。そこから検証の工程を組み立てる

← シリーズ目次

0この回の狙い

前半でよくある誤解を 1 つ丁寧に潰します。後半では、その区別から導かれる検証の工程を組み立てます。実機に上がる前に何を済ませられるかが、移植の総時間を決めます。

「Native PyTorch は eager で Hugging Face のモデルをそのまま動かせる。だから eager なら移植が不要で、compile にすると移植が必要になるのだろう」。この理解は自然ですが、間違っています。境界は eager と compile の間にはありません。

一言でいうと
compile が移植を要求するのではありません。プラグインの中では eager でも移植が要り、プラグインの外なら compile でも移植は不要です。本当の分かれ目は 「KV キャッシュとバッチングを誰が持つか」。持ち主が Hugging Face 側なら移植不要でサービングにならず、持ち主がサービング層なら移植が要ります。そのうえで eager には別の価値があり、それは正しさの検証を安く速く回すことです。

12 つの誤解を実物で潰す

両方向から確認します。片方だけ見ると誤解が残ります。

誤解 1: compile だから移植が要る

経路 B (Native PyTorch) は、Hugging Face のモデルをデバイスに置いてそのまま実行し、torch.compile もできる経路として説明されています。移植は要りません。つまり compile であること自体が移植を要求するわけではありません。

ただしこれはモデル一般に無条件で成り立つ性質ではありません。生成を 1 枚のグラフに収めるにはキャッシュを静的な形に構成することが前提で、毎ステップ連結して伸びる実装のままだと、分断や系列長ごとの再コンパイルが問題になります。モデルの書き方によって結果が変わる部分です。

誤解 2: eager なら移植が要らない

逆にプラグインの中を見ると、eager 実行に落とす設定があります。デバッグ用の指定で torch.compile を飛ばせます。ところがこれで動くモデルは、レジストリに登録された移植済みのモデルだけです。eager は「コンパイルを飛ばす」だけで、「モデル実装を代用する」ものではありません。

eagercompile
Native PyTorch 単体移植 不要移植 不要
プラグインの中移植 必要移植 必要

表が示すのは、境界が縦に走っているということです。eager と compile の横の軸ではなく、プラグインの内と外という縦の軸が移植の有無を決めています。

2本当の分かれ目

では縦の軸は何なのか。第 3 回で見た契約に戻ります。

左右で eager / compile の別はどちらも選べる。違うのはキャッシュの持ち主と、バッチングの有無

この図から、実務上の使い分けが自然に出ます。2 つは競合しません。役割が違います。左は正しさを安く確かめる場所、右は本番の数字を出す場所です。

そして第 4 回の 3 層モデルで言えば、左はコスト層② (サービング契約) と③ (状態の契約) を持たない代わりに、コスト層① (計算の表現) のコストが低い環境です。移植の初期段階で「数式が正しいか」だけを確かめたいとき、左は最短経路になります。

3eager の本当の価値

誤解を潰したうえで、eager が移植作業で果たす役割を書きます。ここは実際に効きます。

eager 実行の価値は 3 つあります。

  1. 「数式の誤り」と「コンパイルによる差」を分離できる。同じモデルを eager とコンパイル済みの両方で走らせて比べれば、食い違いがどちらに由来するか切り分けられます。プラグインの中でも enforce_eager でこの比較ができます
  2. コンパイル待ちが無い。1 回のコンパイルが分単位かかる環境で、数式の間違いを探すのに毎回コンパイルするのは効率が悪すぎます。eager は演算ごとに実行するので、その場で結果が見られます
  3. エラーが出た場所が分かる。コンパイル済みのグラフが落ちると、どの演算で落ちたのかを追うのが大変です。eager なら Python のスタックトレースがそのまま使えます

つまり eager はデバッグの道具として価値があります。プラグインの中の eager 設定も、まさにこの目的で用意されています。print を挟んで中を覗くための設定だと明記されています。

4CPU で回す 2 つのモード

アクセラレータを取らずに進める手段が 2 つあります。混同しやすいので違いを明確にします。

CPU 実行モードCPU コンパイルモード
何をするかCPU 上で実際に計算するコンパイルパイプラインを通す。実行はしない
分かること数値が正しいかコンパイルが通るか
分からないことデバイス固有の丸め、カーネル固有の挙動数値の正しさ (一切)
低レベルカーネルの扱いCPU の代替実装に自動で落ちる。シミュレータで精度も検証できる実行しないので関係しない
主な使いどき移植の初期。数式と層の統合を固める実機確保の前。形が通ることを確認する。並列に何台も回せる

この 2 つは同時には使えません。目的が直交しているからです。移植の工程では、まず CPU 実行モードで数値を固め、次に CPU コンパイルモードで形を通し、最後に実機に上げるという順序が最も無駄が少なくなります。

低レベルカーネルについては、CPU 実行モードで自動的に代替実装に落ちます。加えてカーネル用のシミュレータがあり、小さい形状なら精度の検証までできます。この検証基盤があることが、後述する「カーネルを人が手で書かない」という前提を成り立たせています。

特に効くのは下 2 段です。重みローダのユニットテストは、第 3 回で挙げた「静かに壊れる」バグをそのまま捕まえます。モジュール単位の比較は、attention と MoE のどちらが原因かを 1 回で分けます。

e2e の logits 検証には注意点があります。ランダムな小さい重みで bf16 の比較をすると、値が近接しているためトークンが簡単に反転します。これは移植のバグではなく数値ノイズです。だから正しさのゲートは fp32 での一致に置き、bf16 の評価は実重みで行うのが筋です。

6実機に上がる前にやること

この回の実用的な結論です。実機の時間は高いので、上がる前に済ませられることを列挙します。

  1. 小さいモデルで反復する。数 GB のモデルは読み込みだけで時間を取ります。作り方は単純で、設定の層数を 2 に書き換えてランダム初期化し、そのまま保存します。乱数のシードを固定して、参照実装と同じ重みを読ませるのを忘れないでください。この重みでは bf16 の比較をしない (後述の理由で意味がない) ことも決めておきます
  2. 参照実装を CPU で走らせられる状態にする。比較対象が無いと、出た数字が正しいかどうか判定できません。参照側が特定の環境を前提にしていて CPU で動かない場合は、必要な部分だけ差し替える手間をかける価値があります
  3. 層ごとの比較を用意する。e2e が合わないときに、どこから壊れたかを二分探索できるようにしておく
  4. 重み読み込みの検査を入れる。未初期化が 0 件であることを確認する (第 3 回)
  5. CPU コンパイルモードで形を通す。実機の前に、コンパイルパイプラインが通ることを確認する
逆順にやると何が起きるか: 実機で起動して、コンパイルに数十分かけて、生成が繰り返しになる。原因の候補が「数式」「重み分割」「並列分割」「カーネル」「精度」と 5 つ以上あり、どれも実機でしか試せないと思い込んで、1 回数十分の試行を何十回も回すことになります。実機は「他で確かめられないことだけ」を確かめる場所です。

7低レベルカーネルを人が書かない時代の前提

最後に、移植の将来像に関わる論点を 1 つ置きます。

第 4 回で見たように、性能を作るのは低レベルカーネルか、数式の再構成です。どちらも専門性が要る作業で、これが Trainium 移植の心理的な障壁になっています。

ここで見落とされがちなのは、そういう作業を機械に任せるには、まず検証基盤が要るという点です。生成されたカーネルが正しいかを自動で判定できなければ、生成できても使えません。これは必要条件であって十分条件ではありません。生成の能力、探索の広さ、コストはいずれも別の問題です。

その観点で、このスタックにはその必要条件が揃っています。カーネル用の CPU シミュレータがあり、eager 実行との比較ができ、テストが 4 段に整理されていて、CPU で数値を検証してから実機に上がる工程が推奨されています。「生成する」側の話をする前に、「検算する」側がすでに用意されているという順序は、この分野では珍しく健全です。

移植を人に依頼するか機械に任せるかという議論をするなら、まずこの検証基盤の上に工程を載せることが前提になります。第 8 回で、その検証をどう設計するかを扱います。

出典と確認方法: プラグインの eager 設定、CPU 実行モードと CPU コンパイルモード、カーネル用シミュレータ、テストの 4 段構成は vllm-project/vllm-neuron の公開ドキュメントに記述があります。経路 B (Native PyTorch) の性質は公開されている説明に基づく記述で、本稿では実測を伴いません。本シリーズの実測はすべて公開イメージと公開パッケージの構成で行っています。

第 33 章 API をプローブに使うときの罠

この章の 3 行 第 32 章の「黒箱は何も呼べない」という設計を、API 経由の判定器 (自前で重みを持たず、他社の API を プローブとして叩くタイプ) に当てはめると、罠がもう 1 段増える。呼び出しの引数そのものが 持ち出しチャネルになること、タイムアウトは欠測ではなく観測値であること、そして 第二意見の独立性は幻想でありうることの 3 つを扱う。

1. 呼び出しの引数が持ち出しチャネルになる

判定器に「自由な HTTP リクエストを組み立ててよい」という能力を与えると、それは 封ではない — リクエストのボディやヘッダに、判定器が知っているどんな情報でも埋め込んで 外部に送り出せてしまう。第 32 章の「黒箱は何も呼べない」という設計は、この経路をふさぐために そのまま引き継がれる。プローブは型付きの操作の列挙として宣言し、実際のリクエストを組み立てるのは ランタイム側にする — 判定器は「このプロンプトでこのモデルを呼んでほしい」と要求するだけで、 実際の HTTP リクエストを自分では作らない。

2. タイムアウトは欠測ではなく観測値である

難しい入力ほどタイムアウトするので、欠測が難易度と相関する API 呼び出しがタイムアウトしたとき、それを単純に「データが無い」として捨てると、 捨てているのはランダムな部分集合ではなく、難しい (時間のかかる) 項目に偏った部分集合である。 統計でいう MAR (missing at random、欠測がランダムであること) が成立しないので、 タイムアウトを欠測として扱う集計はそれ自体が偏った推定になる。 正しい扱いは、タイムアウトを「この項目は難しかった」という観測値そのものとして記録することである。

3. 第二意見の独立性の幻想

判定を複数の候補の一致で決める設計 (このシリーズの序盤で扱った quorum 方式) は、 候補が独立に間違うことを前提にしている。ブランドが違うだけで、実際には同じ基盤モデルから 蒸留された候補どうしは、この前提を満たさない。

これは第 27 章の残差コサイン 0.57 が、まさにその実例である Ornith-1.5-9B と empero-ai/Qwen3.8-9B-Distill は名前もブランドも別だが、 第 27 章で見たとおり系譜を共有している可能性が高く、宣言できるフィールドはすべて一致する。 こうした候補を「独立した第二意見」として quorum に入れると、誤りが相関するので一致することの 情報量は見た目より小さい。判定器を売買する市場でも、同じ現象が「別会社の判定器を 2 つ買えば 安心」という誤った直感を生む。

4. 費用も帰属先の階層を持つ

プローブにかかる費用を単純な合計として扱うと、どこで漏れているかが見えなくなる。 帰属先ごとに階層が違うことを区別する必要がある。

費用の種類帰属先の単位
現金 (API 料金)(エンドポイント, 時刻) のペア — 価格は時間帯・提供者によって動く
計算資源エンジンの実行実体 — 同じモデルでも実体ごとに負荷が違う
遅延候補 — 呼び出しごとの待ち時間で、現金や計算とは別に効いてくる

5. プローブが本番の資源を共有すると、対照群も汚染される

共有すると差分そのものが測れなくなる プローブ用の呼び出しが本番と同じレート制限のバケット・同じ GPU・同じキャッシュを共有すると、 プローブを実行すること自体が本番の挙動を変えてしまう。比較対象 (対照群) が、比較している本人の 行動によって動くので、そこで測った差分はもう「介入の効果」だけを表さない。 プローブは専用の資源枠 (別のレート制限バケット、別のキャッシュ名前空間) を持つ必要がある。

この章が主張しないこと

ここで挙げた 3 つの罠は、いずれも API 経由の判定器という設計を選んだ場合に生じる固有の問題であり、 自前で重みを持つ判定器 (第 22〜30 章) には当てはまらない。設計を選ぶ際の比較材料として書いている。

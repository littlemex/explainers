EXPLAINERS ・ skills ・ メタ

/skill-curate

得た知見を「どの skill に入れるか」判断し、実際にその skill を改善する

対象: 全 skill種類: メタ (skill を育てる skill)
← skills シリーズへ戻る

「この知見はどこの skill に足すのが良いかな」と相談すると、三層モデルで振り分け先を判定し、正しいファイルに実際に反映する。知見が消えたり間違った場所に積まれたりするのを防ぐための、skill を育てるための skill。

要点

発火条件残す価値のある知見を得て、どこに入れるか迷ったとき。Kaggle の学びが典型 (例: CV を X 単位で切ると LB と相関する、と分かった)。
入力新しい知見 (自然文)。
出力振り分け先の判定 + 具体的な差分 + その差分を反映した SKILL.md (必要なら解説 HTML と索引の同期)。

ステップ 1 ― 三層モデルで振り分ける

まずどの層に属する知見かを判定する。ここが判断の核心。

層こういう知見なら行き先
手順毎回同じ手で実行したい繰り返し作業 (5 手順以上・出力形式が固定・半減期 1 年以上)skill / サブコマンド (SKILL.md)
知識・判断すぐ陳腐化する事実や手法カタログ、判断基準 (例「今の最強モデルは X」)解説記事 (explainers。skill には入れない)
案件固有特定コンペ/プロジェクトだけで真な事実 (このコンペのスキーマや癖)その案件の CLAUDE.md

アンチパターンを拒否する: 半減期の短い手法カタログを skill にしない、案件固有の癖を横断 skill に入れない、既存プラグイン (nvidia-kaggle など) が既にやることを再実装しない。

ステップ 2 ― 手順なら、正しい skill とサブコマンドへ

手順だと判定したら、影響するワークフロー段階に対応する skill を選ぶ。Kaggle の知見なら /kaggle のサブコマンドに対応づける。

  • CV / split / リーク / CV-LB → /kaggle validation
  • 指標の癖 / 事後処理 → /kaggle metric
  • 実験記録 / ablation の規律 → /kaggle exp
  • アンサンブル / マージ → /kaggle ensemble
  • 提出時の落とし穴 → /kaggle sub-check
  • 自己対戦アリーナ → /kaggle sim-agent

どの skill にも合わなければ、無理に押し込まず新しい skill / サブコマンドを提案する (発火条件つきで)。

ステップ 3・4 ― 反映して索引を同期する

  • 差分を提示する (どのファイルのどの節に何を足すか)。既存 skill の文体・構造を保つ。
  • 検証済みの事実と仮説を書き分ける。未確認の数値 (クォータ等) を事実として書かない。
  • SKILL.md (正本) に反映する。
  • 変更がユーザー向け (新サブコマンド・発火条件の変更・新しい例) なら、解説 HTML と系列 index を同期する。暫定ならドラフトと明記。HTML に手順を複製せず索引に徹する。

実行例

# Kaggle で得た知見を渡す
/skill-curate CV を ConstructId 単位で切ると public LB とよく相関した

# → 判定と反映
層     : 手順 (CV 設計の一般則、半減期は長い)
行き先 : /kaggle validation の「やること」に追記
差分   : GroupKFold の項に「正しい実体単位を選ぶ (Eedi は ConstructId が最良)」を追加
同期   : skills/kaggle/03-validation.html のドラフトにも反映

境界と実体

このスキルは知見を振り分けて反映することに徹する。知見そのものの真偽検証や、外部への公開 (GitHub Pages への push) は別工程。公開は外向きの操作なので S3 中継 push で、実施前に確認する。

スキルの実体 (正本): .claude/skills/skill-curate/SKILL.md。

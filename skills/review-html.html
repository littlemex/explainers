/review-html

ブランチでも文書でも、1 枚の HTML に落としてレビューする

対象: PR・git range・ただのファイル出力: 自己完結 HTML 1 枚サーバ不要
← skills シリーズへ戻る

レビューしてほしいものを 1 枚の HTML にして渡す。行ごとにコメントを書き、読み終えたところは 済 で畳み、書き出すとマークダウンになる。差分は単語単位で色を付けるので、長い日本語の段落が「変わっていない」ように見えることがない。

要点

発火条件ブランチの差分を人間に通してもらうとき。まだコミットもしていない文書を読んでもらうとき。顧客に出す文面、記事の下書き、設計メモも同じ仕組みで扱う。
入力PR の URL、または明示した git range、または --files でファイルのパス。
出力~/tmp/review/ 以下に HTML 1 枚。何も serve せず、何もインストールしない。
解く問題GitHub の差分画面では、日本語の長い 1 行が丸ごと変更行になって何が変わったか分からない。レビューの指摘が会話に流れて、どの hunk への指摘だったか後から辿れない。

3 つの入力

# ブランチ。base branch とタイトルとレビュアーコメントを gh から読む
python3 harness/build_review.py --pr <PR URL> --repo <clone> --open

# range を明示する。rebase 済みや gh が使えないとき
python3 harness/build_review.py --range <a>..<b> --open

# git の外にあるファイル。全行を新規として表示する
python3 harness/build_review.py --files draft.md notes.md --title "draft" --open

range の既定は base の先端ではなく merge-base(origin/<base>, HEAD) からで、ブランチが始まった後に base に入ったコミットをそのブランチの仕事として見せない。終端は PR の head ではなく HEAD で、いま手元にあるものをレビューするための道具だという立場を取っている。

レビュアーが画面でやること

  • 行番号を押すとその行にコメントが付く。キーは file|side|lineno なので、再生成してもその行が動かない限りコメントは残る。
  • hunk のバッジを押すと hunk 全体へのコメントになる。
  • 済 を入れると、注釈と差分がまとめて畳まれる。未レビューだけ表示で判断が残っているものだけになる。キーは hunk の追加行のハッシュなので、前の hunk が消えても隣にマークが移らない。内容が編集された hunk はマークを失う。もう一度読む必要があるからそれが正しい。
  • 書き出すとマークダウンになる。行コメントはファイルごと行順にコードを引用して並び、hunk コメントはバッジ番号順に続く。レビューを投稿する形そのもの。

コメントと済は別の localStorage キーに入れてあるので、片方を消してももう片方は残る。2 つのレビューページが状態を共有することもない。

注釈は index ではなく anchor で当てる

hunk ごとの説明を JSON で書いて渡すと、差分の横に「これは何をする変更か」「なぜあるのか」が並ぶ。この JSON が hunk 番号ではなく 追加行に現れる文字列で当てにいくのが設計の中心である。

hunk 番号で当てると、hunk が 1 つ増えた・消えた瞬間に全部ずれる。しかもずれたことは画面に出ない。誤った説明が誤った差分に静かに貼り付く事故が、一度に十数 hunk 分起きたことがある。anchor は 1 つの hunk にしか当たらないことを検査して、0 個でも複数でも警告を出して注釈を落とす。当たらないより、間違って当たるほうが害が大きい。

hunk には必ず区分が付く。F は指摘への回答で、レビュアー自身の文をそのまま横に引用する。N は頼まれていないが必要だった変更、O は頼まれておらず必要でもない変更で、どちらも「なぜあるのか」を書かせる。レビュアーはこの区分を見てどれだけ疑うかを決めるので、区分を間違えると相手の時間を奪う。

正規表現で決まることは人間に見せない

追加行だけを対象に機械検査が走り、差分の上のパネルと該当行のバッジに出る。error は機械的に決まるもので、ページを渡す前に 0 にする。hint は人間が判断する候補にすぎない。

種類拾うもの
errorMarkdown の段落中の手動改行、解決しないリポジトリ内パス、存在しない見出しへのアンカー、Zenn の frontmatter 以外の絵文字、履歴に残った fixup!
hint読者向け文書に混ざった開発日誌、貼り付け前提のシェルブロック内の # コメント、<your-token> 型のプレースホルダ、日本語と半角英数字の境界のスペース抜け、JST のはずの UTC 表記、同じことを主張する 2 つのコミット

検査を足すときの基準は精度である。きれいなブランチに対して何も出ないところまで上げる。狼が来たと言い続ける検査は、検査が無いより悪い。

レビューパックで観点を持ち込む

「何を見るか」を分野ごとにまとめたパックを選んで足す。common は常に入る。各観点は機械で決まるかどうかを自分で宣言していて、決まるものは自動検査として走り、決まらないものはチェックリストの行として残る。

パック見るもの
commonどの成果物にも効く規律。段落中の手動改行、bash 3.2 で壊れる書き方、失敗を隠す export VAR="$(cmd)"、5xx でも 0 を返す curl -s、読者向け文書の開発経緯、環境固有値、既存の失敗を通過扱いにしないこと
distributed-aiEKS と Ray と GPU のリファレンス。暗黙のインフラ前提、禁止ではなく在庫として書かれた配置、未設定変数で崩れるレンダリング、成果物から読み戻していない数値
ml-measurement測定が主張を支えているか。公式 eval だけを真実とする、比較の前に較正する、run 数を揃える、ノイズ床を統計量の一部として扱う、選択に耐える下限、スループットに生成器の飽和と席数を添える
iac-terraform課金と可逆性。state を S3 に置く、孤児を残さない teardown、予約容量が窓の中でだけ解決すること、保護を黙って外さないこと
zenn-docZenn の記事と本。公開フラグは明示指示のときだけ、1 文書 1 文体、記法ルール、図が記事の階層をミラーすること、測ったことと測っていないことの区別
review-meta何を見るかではなく、どう問うか。この変更は主張する指摘に答えているか。その数値はどう測ったか。読者にこの段落は要るか。それは環境の性質か成果物の性質か

知っておく壊れ方

  • gh が未認証でも、手元の range からページは作られる。ただしタイトルも base branch もレビュアーコメントも無い。この空の結果を「レビューが付いていない PR」と読み間違えないこと。ページはそう言う。
  • いまの差分に無い行へのレビュアーコメントは、捨てずにそのファイルの先頭に並ぶ。ブランチがその指摘の先へ進んでいることが多いから。
  • ハーネスの最終行の警告数を見る。warnings=0 だけが人に渡してよい状態である。

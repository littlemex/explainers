EXPLAINERS ・ skills ・ Kaggle ・ 01

/kaggle brief

コンペの overview とルールを、そのまま戦える戦略 brief に変換する

段階: 問題理解類型: 全優先度: 1
← Kaggle スキル群へ戻る

コンペに join した直後に打つ。散らばったルール群を、指標・制約・類型・初手仮説がそろった 1 枚に落として、以降のすべてのスキルの入力を規格化する。

要点

発火条件新しいコンペに参加したとき。または戦略を見直したいとき。
前提nvidia-kaggle スキルで overview / rules / evaluation を取得できる状態 (KAGGLE_API_TOKEN 設定済み)。生データの取得はそちらに任せる。
入力コンペの slug または URL (例 pokemon-tcg-ai-battle)。
出力プロジェクト直下の BRIEF.md。中身は下記。

BRIEF.md に書き出すもの

  • 指標 ― 正確な数式、大きいほうが良いか、事後処理の余地 (閾値・ランク平均など)。検算は /kaggle metric へ渡す。
  • 提出形式 ― CSV (Simple) か Code competition か。Code ならネット遮断・GPU/時間の予算 (現行クォータはコンペページで確認。決め打ちしない)・エントリポイント (単一関数か、問題を 1 件ずつ受け取る推論サーバか、エージェント構成バンドルか)。
  • 制約 ― 外部データの可否、チーム・1 日あたりの提出上限。
  • 類型の判定 ― 予測系 / LLM 推論 / 対戦エージェント / エージェント構成バンドル のどれか、その根拠つき。どの後続スキルが効くかが決まる。
  • 類似の過去コンペ ― 名前と似ている理由。後で上位 writeup を引く材料になり、/kaggle retro の土台になる。
  • 初手仮説 ― 具体的な最初の賭けを 3〜5 個、優先順つき。

実行例

# コンペ参加直後に slug を渡す
/kaggle brief pokemon-tcg-ai-battle

# → BRIEF.md (抜粋)
指標      : 対戦のスキルレーティング (勝敗ベース、大きいほど良い)
提出形式  : シミュレーション型。agent(obs, cfg) を提出、1 日 5 提出・有効 2 件
類型      : 対戦エージェント型  → 次は /kaggle sim-agent
制約      : ローカル SDK 提供あり、自己対戦で反復可能
初手仮説  : (1) ルールベースの土台を先に固める
            (2) 自己対戦ハーネスで敗着を可視化
            (3) 相手の隠れ手を試合中に推定

類型が対戦エージェント型なら、CV 設計にあたる作業は /kaggle sim-agent が担う。予測系なら /kaggle validation へ続く。

パイプラインの位置

01 brief→ 03 validation / 10 sim-agent→ 05 exp ループ→ 07 sub-check→ 08 retro

brief は入口であり、出力の BRIEF.md が他スキルの入力契約になる。ここでの類型判定が、以降どの枝 (対戦型 / LLM 型) に進むかを決める。

境界と実体

生データの取得と提出そのものは既存の nvidia-kaggle スキルが担当する。/kaggle brief はその overview を解釈して戦略に変換する層で、API 呼び出しを再実装しない。

スキルの実体 (手順の正本): リポジトリの .claude/skills/kaggle/SKILL.md。このページは索引であり、手順の詳細は複製しない。

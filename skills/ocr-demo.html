/ocr-demo

AWS を使わず、このマシンだけで Indra OCR を試す

対象: PDF・PNG・JPG出力: ブラウザのローカル画面npm・AWS 不要
← skills シリーズへ戻る

打つと、ローカルのサーバーが立ち上がってブラウザが開く。付属の日本語サンプル PDF をその場で OCR できるし、自分の PDF/画像をアップロードして試すこともできる。AWS には一切繋がらない。

要点

発火条件PDF/画像の OCR をローカルで試したいとき。「OCR デモを起動して」「あの OCR 試したい」等。
入力付属の日本語サンプル PDF (段落・表・請求書の 3 ページ) か、自分の PDF/PNG/JPG。
出力ブラウザのローカル画面。Markdown / テキストのみ / JSON (行・座標つき) から選べる。
解く問題Indra OCR (1M〜7M パラメータの軽量 OCR モデル) を試すだけの用途に、AWS デプロイも npm インストールも要らない状態にする。
組み合わせバックエンドは Python 標準の http.server + indra-ocr のみ。UI はプレーン HTML/CSS/JS。元ネタは littlemex/samples の serverless/lambda-microvm-ocr (AWS Lambda MicroVMs で同じ OCR を動かす本番実装) のローカル版で、本体のコードは常にそちらの最新を見る。

使い方

スキルを打てば起動まで済む。手で叩くならこの 3 つ。

run.sh --background
run.sh --status
run.sh --stop

起動するたびに littlemex/samples を git pull するので、常に GitHub 上の最新版が動く。二度打っても二重に立ち上がらず、開いているブラウザを出すだけになる。既定ポートは 8765。

サーバーに launchd を使う理由

最初の実装は nohup python3 server.py & だった。手元で起動直後に確認すると動いていたので「できた」と報告したが、別のツール呼び出しで確認し直すとプロセスが消えていた。

原因は Claude Code の Bash ツールの仕様で、1 回のツール呼び出しが終わるとそのプロセスグループ全体を片付ける。nohup は端末からの切断からは守ってくれるが、ツール自身によるプロセスグループの掃除までは防げない。見かけ上は「起動成功」のログが出るのに、数分後には影も形もなくなる。

さらに厄介だったのは、この掃除が起きる前に別の古いテスト用プロセスが同じポートを握っていたこと。新しいプロセスは OSError: Address already in use で起動直後に落ちていたのに、古いプロセスが代わりに応答を返し続けたので、何度テストしても「動いている」ように見えた。launchctl print でジョブの実際の state を見るまで気づけなかった。

直し方は launchd に乗せること。launchctl bootstrap/kickstart で起動したジョブは launchd の子になり、Bash ツールのプロセスグループ掃除の対象から外れる。KeepAlive はあえて設定していない ― これは常時監視デーモンではなく、ユーザーが明示的に起動・停止するツールなので、止めたら本当に止まってほしい。

残っている限界

ポート 8765 が別プロセスに使われていると、launchd のジョブは起動直後に落ちる。このとき --status は正直に not running と答えるので (上の節の罠を踏まえて、見かけの成功で誤魔化さないようにしてある)、詰まったら ~/ocr-demo/server.log を見るか PORT=8080 を指定して起動し直す。

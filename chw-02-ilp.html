命令レベル並列性 (ILP) ── ハードが実行時に掘る

素朴な命令列に埋もれた並列性を、実行時のハードウェアが自力で発掘する仕組み

0この章の狙い

01 章で描いた「静的 ⇆ 動的」の軸。この章は、動的側の代表格である現代の高性能 CPU が、並列性をどう掘り出しているのかを見ていきます。

一言でいうと
命令レベル並列性 (ILP、Instruction-Level Parallelism) とは、隣り合う命令どうしの間にある「同時に実行してよい」余地のことです。現代の高性能 CPU は、コンパイラが渡してきた命令列を受け取り、その並列性を実行時に自力で発掘します。パイプライン化、スーパースカラ発行、そしてアウトオブオーダー (OoO、out-of-order) 実行を支える制御機構（ハザード検出・発行制御・レジスタリネーミングなど）は、演算そのものを 1 つも行いません ── すべて「並列性を掘るための回路」です。命令の並べ方をコンパイラに委ねる VLIW という方式（03 章で詳述）がある一方、ここではハードウェアがその判断の大部分を引き受けます（OoO 向けでもコンパイラの静的スケジューリングは併用されます）。その代償が、回路の複雑さと電力です。

1パイプラインとハザード

1 つの命令の処理を複数の段に分割し、段ごとに別の命令を同時に流すのがパイプライン化です。

典型例として、命令を「フェッチ (IF) → デコード (ID) → 実行 (EX) → メモリアクセス (MEM) → 結果の書き戻し (WB)」の 5 段に分ける、模式的なパイプラインを考えます (実機の段数や分割は設計ごとに大きく異なります)。各段は毎サイクル 1 つの命令を処理できるので、段が空くたびに次の命令を流し込めば、理想的には 1 サイクルに 1 命令が完了するようになります。

# 5 段パイプライン、命令が 1 サイクルずつ段を進む(模式)
命令1: IF  ID  EX  MEM  WB
命令2:    IF  ID  EX   MEM  WB
命令3:       IF  ID   EX   MEM  WB

この理想を崩すのがハザードです。同じ回路(演算器やメモリポート)を複数の命令が同時に欲しがる構造ハザード、後続の命令が前の命令の結果をまだ受け取れないデータハザード、分岐先が確定するまで次の命令を決められない制御ハザードの 3 種があります。

データハザードの多くはフォワーディング (forwarding、バイパスとも) ── EX 段で計算した結果を WB を待たずに次の命令の EX 段へ直接渡す配線 ── で解決できます。ただしロード命令の結果を直後の命令がすぐ使う (ロード-ユース) 場合は、メモリから値が返ってくるタイミングがフォワーディングの配線だけでは間に合わないことが多く、模式的には 1 サイクルのストール(空転)が入ります。

ここは概念図です。 実機のパイプライン段数、フォワーディングパスの有無、ロード-ユースの遅延サイクル数はマイクロアーキテクチャごとに異なります。ここでは「ハザードがあるとストールが生まれ、フォワーディングでそれを減らせる」という骨格だけを押さえてください。

2スーパースカラ ── 1 サイクル複数命令

パイプラインの各段の幅を広げ、1 サイクルに複数の命令を同時に流すのがスーパースカラです。

単純にフェッチ・デコード・実行の各段を並列に複数用意すれば、1 サイクルに 2 命令、3 命令を処理できます。ここで注意したいのは、スーパースカラであることと、順序を入れ替えて実行することは別の概念だという点です(01 章)。命令をプログラム順のまま複数発行（issue、命令を実行ユニットへ送り出すこと）するインオーダー・スーパースカラも存在し、これは「幅は広いが、依存待ちが起きたら後ろの命令も一緒に止まる」という性質を持ちます。順序入れ替えまで踏み込むアウトオブオーダー実行は、次節で扱う別の仕組みです。

インオーダー・スーパースカラは、独立な命令が隣り合っている場合には効果を発揮しますが、依存関係のある命令が並んでいると、幅を広げても発行できる命令が見つからず幅を活かせません。「幅を広げる」ことと「並べ替えて活かす」ことは別の仕事であり、後者を担うのが OoO です。

3アウトオブオーダー実行と Tomasulo 方式

プログラム順の後方にある独立な命令を、実行時に前へ繰り上げて実行するのが OoO です。その古典的な実現法が Tomasulo 方式です。

現代のアウトオブオーダー実行は、Tomasulo 方式 (R. M. Tomasulo が IBM System/360 Model 91 のために考案) に ROB を加えた構成が一般的です。現代の OoO として、次の要素をまとめて見ます。

要素役割
予約ステーション (reservation station)まだ実行できない命令を、必要なオペランドが揃うまで保持しておく待合室。オペランドが揃った命令から実行に回せる
レジスタリネーミング同じレジスタ名を使うだけの命令どうしを、実体としては別のレジスタに割り当て直し、本当は依存していない偽の依存 (WAR・WAW、後述) を消す
CDB (共通データバス、common data bus)演算器が出した結果を、それを待つすべての予約ステーションへ同時に配る配線
ROB (リオーダバッファ、reorder buffer)命令を実行順は入れ替えても、結果を確定 (リタイア) する順番はプログラム順に戻すための緩衝装置。※オリジナルの Tomasulo にはなく、精密例外を実現するため後年 (Smith & Pleszkun 系) に追加された拡張

命令には本来の依存(結果を使う、真の依存)のほかに、WAR (Write After Read、先に読んでから後で書く順を守る必要がある偽の依存) と WAW (Write After Write、書く順序だけを守る必要がある偽の依存) という、レジスタ名の再利用だけが原因の偽の依存があります。レジスタリネーミングはこの偽の依存を取り除き、本当は独立な命令を並べ替えて実行できるようにします。ROB は、こうして順序が乱れた実行結果を、外部(レジスタファイルやメモリ)から見えるタイミングだけはプログラム順に戻す役割を持ち、これによって例外処理や分岐ミス時の巻き戻しが正しく行えます。

これは並列性を掘る回路であり、演算そのものではありません。 予約ステーション・リネーミング用のレジスタファイル・CDB・ROB は、いずれも「どの命令をいつ流すか」を実行時に決めるためだけの回路です(01 章)。演算器そのものの面積・電力は変わらないのに、これらの制御回路がチップの相当な部分を占め、消費電力の相当な割合を持っていく、という点が OoO の代償です(具体的な割合は世代・実装により大きく異なるため数値は割愛します)。

4分岐予測と投機実行

分岐先が確定するまで待っていては、パイプラインもスーパースカラも空転してしまいます。そこで「たぶんこっちだろう」と予測して先に進みます。

分岐予測器は、過去の分岐の傾向(実行履歴)からその先の分岐がどちらへ飛ぶかを推測し、CPU はその予測に基づいて投機的に命令を実行し始めます。予測が当たれば、分岐先が確定するのを待つ時間を丸ごと節約できます。予測が外れた場合は、投機的に実行してしまった命令の結果を捨てて、正しい分岐先からやり直す巻き戻し (フラッシュ) が発生します。予測ミスのペナルティは、パイプラインが深く投機の範囲が広いほど大きくなります。

分岐予測器も投機実行のための巻き戻し機構も、並列性を掘るための回路という点で予約ステーションや ROB と同じ仲間です。分岐先は実行時にしか分からない ── この静的方式の弱点を、予測が当たっている限りハードが埋めてくれます。しかし予測が外れれば、投機した分の電力と時間を丸ごと捨てることになります。この「賭けに勝てば速い、外れれば無駄になる」という性質そのものが、動的方式の予測不能性の源泉です(01 章)。

5【体験】同じプログラムを 3 つの発行方式で

6 個の命令(依存関係あり、レイテンシ＝結果が出るまでのサイクル数もさまざま)を、発行の仕方が違う 3 つのモデルで流します。ハードウェアの回路自体は増えていく一方(概念的なメーターで示す)、その分だけサイクル数がどう縮むかに注目してください。

# 対象プログラム(各命令のレイテンシと依存)
i1: a = ld X    [MEM, lat 2]
i2: b = a + 1  [ALU, lat 1, needs a]
i3: c = ld Y    [MEM, lat 2]
i4: d = c * 2  [MUL, lat 3, needs c]
i5: e = 5 + 6  [ALU, lat 1]   # どの命令にも依存しない独立命令
i6: f = d + e  [ALU, lat 1, needs d,e]
MEM(load) MUL ALU
並列性を掘る回路の複雑さ(概念値)

注目してほしいのは i5 です。他のどの命令にも依存しない完全に独立な命令なのに、インオーダーではプログラム順で 5 番目の自分の順番が来るまで実行されません。プログラム順を守るインオーダー発行では、前にある i4（オペランド c の到着を待つ乗算）が発行できるようになるまでの待ちに巻き込まれ、後ろの i5 まで足止めされてしまうからです。アウトオブオーダーは i5 を早い段階で前に繰り上げ、i4 のレイテンシ待ちの裏で処理を進めます。同じプログラム・同じ演算器数でも、発行方式だけで完了サイクルが変わる ── これが「ハードが並列性を掘る」ことの具体例です。ちょうど VLIW が同じ並べ替えをコンパイル時に済ませてしまうのと対比してください(03 章のデモ)。

前提: MEM・MUL・ALU はそれぞれ 1 ユニットのみと仮定した模式的なモデルです。インオーダー系は「その回のプログラム順の先頭から、依存が満たされている命令だけを、幅の上限まで発行し、未準備の命令が来たら止まる」という単純な規則で発行順を決めています。OoO は幅の上限まで、依存が満たされた命令から優先的に(プログラム順に関わらず)発行します。

6まとめ

論点要点
ILP とは命令列に埋もれた「同時に実行してよい」余地
パイプライン処理を段に分けて重ねる。ハザードがストールを生み、フォワーディングが多くを解決する
スーパースカラ1 サイクルに複数命令を発行。順序を守るインオーダーと、入れ替える OoO は別概念
OoO(Tomasulo)予約ステーション・リネーミング・CDB・ROB で、偽の依存を消し順序を入れ替え、リタイアだけプログラム順に戻す
分岐予測・投機実行時にしか分からない分岐先を予測して先取り。外れれば巻き戻しコストを払う
代償これらすべてが「並列性を掘るための回路」であり、演算そのものではない電力・面積を食う
静的側との対比。 ここで見た予約ステーション・リネーミング・分岐予測は、すべて実行時にハードウェアが担う判断です。次の 03 章の VLIW は、この同じ並べ替えの判断をコンパイルの時点で確定させ、そのまま命令に焼き込むことで、これらの回路そのものを丸ごと持たずに済ませます。同じ目的地(独立な命令を並べて速く実行する)へ、正反対の経路で辿り着く 2 つの方式として読み比べてみてください。

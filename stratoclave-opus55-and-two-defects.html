Opus 5.5 に切り替え、自前ゲートウェイに載せる途中で欠陥 2 つが出た
「成功したのに消える昇格」と「レビュー済みの値段が無い」

結論から。モデルを 1 つ増やすだけの作業のはずが、成功と表示されるのに何も起きない欠陥に当たった。自前の LLM ゲートウェイ (stratoclave) でモデルを有効化すると API は 200 (成功) を返すのに、そのモデルはどこからも見えない。原因は権限 1 行の欠落で、しかも設計が「読めなかったら前の状態を保つ」という安全側の作りだったせいで、外からは「有効化していない状態」と区別できなかった。

この文書でやったこと。stratoclave の CLI を最新に入れ替え、Claude Code 自身と自前ゲートウェイの既定モデルを Opus 5.5 に切り替え、レビュー用に Fable 5.1 と GPT-6 を呼べるようにした。その過程で欠陥を 2 つ見つけて直し、1 つは直せない理由をはっきりさせて残した。

1. 数字の要約

この文書の主張はすべて実際に動いている環境で測ったものである。plan (実行計画) やモック (偽物で代用する試験) は実機の検証と認めない、という自分の決めごとに従っている。

2. 何をしたか ― 3 つの場所でモデルを切り替えた

「Opus 5.5 に切り替える」は 1 か所の設定変更では終わらない。同じ言葉が指す場所が 3 つあり、経路がそれぞれ独立しているからである。

まず CLI を最新にした。入っていた実行ファイルは 5 週間前のビルドで、版番号は最新と同じ 0.2.0 のままだったので番号では古さが分からない。ソースと比べると CLI に触る変更が 17 件入っていた。入れ替え後にコマンド一覧へ limit-raise が現れたので、別物に変わったことが目に見える形で確かめられた。

次に Claude Code 自身の既定モデルを Opus 5.5 にした。書き換えたのは 3 か所で、利用者全体の設定、この作業リポジトリの設定、そして新規プロジェクト用のひな形である。リポジトリ側の設定が利用者設定を上書きするので、1 か所だけ直しても効かない。

100 万トークンの窓は別扱いになっている。Bedrock のモデル名に [1m] を付けて直接呼ぶと、Opus 5 でも Opus 5.5 でも「権限が無い」と断られる。これは名前の一部ではなく、要求の中で「長い窓を使う」という指定を添える仕組みだからである。実際にその指定を添えて呼ぶと Opus 5.5 でも応答が返ったので、既定を claude-opus-5-5[1m] にしても窓は失われない。

3. レビューを頼む相手を 1 本の道具にまとめた

今後「Fable に見てもらって」「Codex に見せて」と言われたら、その時点で最も強いモデルを使う、という決めごとになった。今の顔ぶれは Anthropic 系が Fable 5.1、OpenAI 系が GPT-6 Sol か GPT-6 Astra、そして既定のレビュー担当が Opus 5.5 である。

これまで呼び出し口はモデルごとにファイルを丸ごと複製していた。opus5_ask.py は fable5_ask.py の写しで、違いはモデル名の 1 行だけだった。今回 4 モデルに増えるところで、複製を 4 本に増やすのをやめ、--model で選ぶ 1 本のエンジンにまとめた。

短い名前実際に呼ぶモデル役割
fable (既定)global.anthropic.claude-fable-5-1Anthropic 系の敵対レビュー担当
solglobal.openai.gpt-6-solOpenAI 系。系統が違うので突き合わせに価値がある
astraglobal.openai.gpt-6-astra同上。Sol と交換可能
opusglobal.anthropic.claude-opus-5-5既定のレビュー担当。Fable が拒否したときの逃げ先でもある

4 つすべてに実際に問いを投げて応答を確認した。そのとき OpenAI 系だけの落とし穴が出た。temperature (答えのばらけ具合を決める指定) を送ると拒否される。「This model doesn't support the temperature field」という明示的な拒否なので黙って無視されるわけではないが、他のモデルと同じ書き方では動かない。道具側でこの指定を既定で送らないようにし、OpenAI 系に付けた場合は Bedrock を呼ぶ前に手元で止めるようにした。

Fable が黙って空を返したときの見分け方。安全性の判定に引っかかると、エラーではなく「成功だが中身が 0 文字」で返ってくる。見分けるのは inputTokens=0、つまり入力がそもそも受け付けられていないという事実で、この症状は出力の上限を増やしても直らない。道具の警告文が「考える処理が予算を使い切った、上限を増やせ」と誤診していたので、入力トークンが 0 のときは別の文言を出すようにした。

4. 自前ゲートウェイにモデルを載せる経路は 5 段ある

ここから難関である。自前ゲートウェイは「自分のカタログに無いモデル名は受け付けない」設計なので、Bedrock で呼べるだけでは足りない。設計上の売りはカタログを増やすのにソフトウェアの配布が要らないことで、経路は 5 段になっている。

1 段目の発見は運用コマンドで、サーバ側に呼び口が無い。手元から実行してアカウントの Bedrock を一覧し、値段表を 1 件ずつ読んで 83 件を記録した。このとき出る key=v1:<長い文字列> は選ばれた値段そのものの指紋なので、2 つのモデルの指紋が一致すれば値段が同じ、と判断に使える。

3 段目の検証は本当に 1 回モデルを呼ぶ。Opus 5.5 が 66 マイクロドル、Fable 5.1 が 165 マイクロドル (1 マイクロドルは 100 万分の 1 ドル) で、台帳に着地した。「呼べる」ではなく「呼んで請求まで通る」を確かめる作りである。

5. 欠陥 1 ― 成功を返してから消える有効化

有効化の API は 200 (成功) を返し、応答の中には今書いたばかりのモデルの情報が入っている。ところが 75 秒待ってもモデル一覧に出てこない。更新窓の 60 秒は越えている。権限付与を頼むと「そんなモデル系列はレジストリに宣言されていない」と断られる。

原因はサーバのログにだけ出ていた。有効化された項目を読む関数は、テーブル全体を走査する読み方 (Scan) を使う。これは意図的で、関数自身の説明にも「索引を使った問い合わせではない。テーブルの索引設計は別の担当のもので、この行の種類は後から足されたものだから」と書かれている。そしてサーバにはそのテーブルを走査する権限が付いていなかった。

見分けられる唯一の手がかりはサーバのログにある。

composed_registry_activated_half_unreadable
 error='activated-entry store unreachable listing entries: AccessDeniedException
   ... not authorized to perform: dynamodb:Scan on ... table/stratoclave-promotion-candidates'
 note='keeping the last known-good activated set (fail-static)'

直し方は許可リストにこのテーブルを 1 つ足すだけである。足して再配備すると、同じ有効化が 1 更新窓以内に一覧へ現れ、権限付与も通った。原因の特定と修正が一対一で対応しているので、症状が消えただけではないと言える。

許可リストにはこの付与を「あってもよい」ではなく「無ければ落ちる」という形で試験も足した。元の試験は別のテーブル (RBAC の元データ) を戻したら落ちるようになっていたが、必要な付与を落としたときは何も起きなかった。同じ形の事故がもう一度起きないようにするには両方向を押さえる必要がある。なお試験の説明文は「5 つのテーブル」と書いて 6 つ並べていたので、数ではなく規則 (この一覧のテーブルには必ず走査する呼び出し元が居る) を書くように直した。

6. 欠陥 2 ― カタログは配布が要らないが、値段は要る

有効化が通っても、まだ普通の利用者には使わせられない。昇格したモデルは「権限が必要」という扱いになるので、組織に対して使用権を付与する必要がある。その付与が断られた。

{"detail":"no reviewed floor row exists for pricing_key='opus-5-5'.
 This is not a price disagreement -- nobody has reviewed a price for this key yet."}

値段は 2 つの層で決まる。下限 (floor) はソフトウェアのイメージの中にあるファイルで、人間が目で見て決めた値である。もう 1 つは DynamoDB に置く上書きで、これは実際の値段が動いたときに追いかけるための層である。

これは正しい設計だと考える。下限は人間が見た数字であり、誰も値付けしていない種別に使用権を出せば、その時に上書き層が言っている値で請求することになる。上書き層は外部の値段情報で自動更新される対象なので、そこだけを根拠に請求を始めるのは危うい。

だから 4 種別の下限をイメージ内のファイルに書き、イメージを焼き直して配備した。上書き層に先に入れていた同じ値は、同じ数字を 2 か所で持つと必ずずれるので空の集合を発行して外した。外した後も課金が正しく着地することを実際に呼んで確かめている。

7. 値段は全部測った ― そして 4 つとも独自の種別にした

値段の種別 (pricing key) はその中で最も高いメンバーの値段で課金される作りになっている。だから既存の種別に相乗りさせると、安いモデルが過大請求になる。逆に既存の種別を下げると、古いモデルが過小請求になる。

種別入力出力キャッシュ読みキャッシュ書き独自にした理由
opus (Opus 5 など)5.5027.500.556.875既存
opus-5-54.4022.000.225.50全項目が opus より安い。相乗りは過大請求
fable (Fable 5)11.0055.001.1013.75既存
fable-5-111.0055.000.27513.75キャッシュ読みが 4 分の 1。相乗りは 4 倍で課金
gpt-6-sol2.2011.000.22未掲載値段表が別の商品なので独自
gpt-6-astra11.0055.001.10未掲載同上

単位は 100 万トークンあたりのドルで、すべて Bedrock の値段表 API を 2026-09-23 に読んだ実測である。Opus 5.5 は Opus 5 より 2 割安い (入力 5.50 対 4.40、出力 27.50 対 22.00)。キャッシュ読みは 0.55 対 0.22 で 6 割安い。

GPT-6 のキャッシュ書きだけは実測ではない。この系列の値段表には「キャッシュ書き」の項目が存在しない。この経路では書かれたキャッシュのトークンは通常の入力トークンとして課金されるので、入力と同じ値をレビュー済みの初期値として置いた。0 にすると実際に発生する課金が無料に見えてしまうからである。この文書で唯一、測定ではなく判断で決めた数字である。各行の注記にもその旨を書いた。

既存の GPT-5.6 Sol の下限は古くなっている。リポジトリは 5.50 / 33.00 と書いているが、値段表の現在の値は 4.40 / 22.00 だった。値段は下がる方向に動く、というのはこのファイル自身の注記にも書かれている前提である。既に課金しているモデルが居る種別の訂正は、それ自身の根拠を伴う別の変更なので今回は触っていない。

8. 動いている箱を縮ませないための注意

配備には落とし穴がある。今動いている箱は CPU 4096・メモリ 8192・処理係 4 本・リクエスト数による自動増減の目標 300 で動いている。ところがコード側の既定値はそれより小さく、リクエスト数の目標は既定値が無い。素で配備すると差分がそのまま適用される。

防ぎ方は 1 つで、配備の前に差分を全部読み、稼働中の値と突き合わせる。差分に Cpu や Memory や処理係の本数が出てこなくなるまで値を明示してから配備した。実際の差分は、新しいテーブル 2 つとその権限、監視 2 件、環境変数 2 個だけに収まった。

9. GPT-6 は自前ゲートウェイに載らない ― 回避せず理由を書く

GPT-6 Sol と GPT-6 Astra は候補までは作れたが、有効化できない。3 段目の検証が、通信様式のうち片方しか実装していないからである。

検証は Bedrock の共通の呼び方を使っており、GPT-6 はその呼び方でも実際に応答する。だが wire_protocol が指しているのはゲートウェイがそのモデルを客に出すときの経路で、OpenAI 系は OpenAI 互換の別の口から出している。だから検証もその口で 1 回呼んで、その応答からトークン数を読まないと「請求が着地する」を確かめたことにならない。

これは 1 行足して済む話ではなく、お金を扱う経路に新しい通信手段を足す機能追加である。予算を確保し、課金を着地させ、判定を保存する。だから今回は回避せず、穴として書いて残した。レビュー用に GPT-6 を使うこと自体は Bedrock を直接呼ぶ道具で今日からできているので、実務は止まらない。

10. やっていないこと、まだ開いていること

  • GPT-6 の検証経路は未実装のまま。候補は作ったが有効化していないので、自前ゲートウェイ越しには使えない。
  • GPT-5.6 Sol の古い下限価格は直していない。既に課金しているモデルが居る種別なので別の変更にする。
  • サーバ側のテストに順序依存の失敗が 2 件ある。3,576 件が通り 1 件落ちたが、落ちた 1 件はテスト自身のコメントに「既知の順序依存の失敗で、まだ根本原因が分かっていない」と書かれている。単体では通り、収集順を変えると別の 1 件が落ちる。自分の変更が増やした失敗はゼロだが、既存の赤を「無関係だから良い」とは書かない。順序依存の汚染そのものが別途直す対象である。
  • GPT-6 のキャッシュ書きの値は測定ではなく判断である。値段表に項目が現れたら測り直す。
  • インフラ側のテストは全件 (33 スイート・255 件・skip 1) 緑である。

まとめ。Opus 5.5 への切り替えは 3 つの経路すべてで終わり、Fable 5.1 と GPT-6 はレビュー用にすぐ使える。自前ゲートウェイには Opus 5.5 と Fable 5.1 が載り、普通の利用者のトークンで応答することまで確かめた。途中で見つけた 2 つの欠陥のうち、権限 1 行の欠落は「成功したように見える」形で昇格を無効化していたのがいちばん重い発見で、直したうえで同じ事故が再発しないよう試験を両方向に変えた。

実測はすべて 2026-09-23、AWS アカウント 776010787911 の us-east-1 で稼働中の stratoclave に対して行った。 変更したファイルは iac/lib/ecs-stack.ts、iac/test/ecs-stack-scan-allowlist.test.ts、 backend/mvp/defaults/pricing.json。ブランチは fix/promoted-model-stays-invisible。 値段は Bedrock の ListFoundationModelAgreementOffers を mvp.pricing_feeds.dimensions.select 経由で読んだ値。 検証の課金は Opus 5.5 が 66 マイクロドル、Fable 5.1 が 165 マイクロドル。

1本物の backend は何をしているか

前回の結論は「CUDA の転送では届かない」でした。届く手段は、模倣している相手が既に使っていました。

GDRCopy は GPU の BAR 領域をホストのアドレス空間へ写し、CPU が普通のストア命令でデバイスメモリを書けるようにします。CUDA には何も積みません。だからカーネルが先に並んでいるキューが存在しません。

これは aws-ofi-nccl がまさにこの種の書き込みに使っている機構です。つまり乗り換えると、エミュレータはより忠実になります。回避策が正攻法を押しのけるときの、いつもの取引とは逆向きです。

ただし書き換える前に確かめることが 4 つあり、それぞれが次を通す門になっています。1 つでも落ちれば設計が成立しません。だから transport を触る前に、40 行の probe で順番に測りました。

24 つの門

段問い結果
1普通の cuMemAlloc を pin して map できるかOK
2ncclMemAlloc が作る仮想メモリ確保を pin して map できるかOK
3その mapping への CPU 書き込みで、すでに spin しているカーネルが解放されるかOK ・ 0 ms
4payload の書き込みが、それを知らせる flag より先に見えるかOK

3 段目が答えです。93 秒ブロックした CUDA copy と同じことを、BAR 書き込みは 0 ms で達成します。カーネル側は ld.acquire.sys で読ませました。DeepEP が header と indexed counter に対して実際にやっていることと同じで、結果を良く見せる弱い読み方は選んでいません。

4 段目も同じくらい大事です。エミュレータの唯一の硬い契約は「signal はそれを運んだ put の全バイトが着いた後にしか見えない」で、write-combining な mapping でもこの順序が保たれるかは仮定してよいことではありません。gdr_copy_to_mapping を順に 2 回呼ぶ形で保たれました。

3自分の probe が嘘をついた

2 段目は最初の実行で落ちました。落ちた理由はメカニズムではなく、私のテストでした。

gdr_pin_buffer on a cuMemCreate/cuMemMap allocation returned 22 (Invalid argument)

probe が作った仮想メモリ確保に allocFlags.gpuDirectRDMACapable が立っていませんでした。このフラグが、nvidia_p2p_get_pages が受け取る VMM メモリと拒否する VMM メモリを分けている唯一の違いです。

これは危ない失敗の形でした。「GDRCopy は VMM 確保を map できない」というメカニズムについての結論を、テストの不備から引き出していました。そのまま信じれば計画は死んでいました。NCCL 自身の allocator はこのフラグを立てますし、DeepEP の symmetric allocator は要求します。つまり登録されるウィンドウには常に立っているので、probe が合わせるべきでした。

いまの probe は、失敗が誰のせいか分かる材料も出します。デバイスの GPU_DIRECT_RDMA_WITH_CUDA_VMM_SUPPORTED、ポインタ自身の IS_GPU_DIRECT_RDMA_CAPABLE、gdrcopy の runtime と driver の両バージョン。古い gdrdrv と新しいカーネルモジュールの組み合わせも、同じ説明のない EINVAL に見えるからです。

4実装で効いている 3 つの判断

絶対値を書くから、原子性が要らない

BAR 書き込みは GPU に対して原子的ではありません。それでも signal counter を書けるのは、値が累積の絶対値だからです。NCCL は NCCL_NET_MR_FLAG_SIGNAL_NEVER_RESET を立て、リセットはオフセットを覚えることで論理的に行います。つまりこの plugin が唯一の書き手で、走行合計をそのまま置くだけで正しくなります。

map は登録時に 1 回だけ

gdr_pin_buffer は BAR の口を gdr_map まで遅らせずにその場で確保します。だから使用量を減らす方法は部分範囲の pin しかなく、データパスで pin するのは、空にしようとしている経路に別の driver 操作を戻す行為です。このカードの BAR は 128 GB で、ウィンドウは 1.82 GB。節約する理由がありません。

CUDA 経路は残すが、黙って落ちない

gdrdrv の無いホストでは CUDA copy に落ちます。ビルドと実行の両方がどちらを使ったかを言います。2 つは 93 秒違うので、黙った fallback は原因のない性能退行に見えます。

5通った

=== 3 pass, 0 fail out of 3 (mode inorder, combine 0) ===
=== 5 pass, 0 fail out of 5 (mode inorder, combine 1) ===

DeepEP の elastic dispatch と combine が、EFA インスタンスなしでエミュレータ上を通りました。データパスから CUDA が消え、payload・signal・送信側の読み出しがすべて BAR mapping 経由になりました。

6途中で私が作った deadlock

前回の修正が次の停止の実行犯でした。凍結時のスタックが名指しします。

#4  cuMemFreeHost () from libcuda.so.1
#5  PinnedStaging::get () at layer2/nccl_rma_srdsim.cc

ページ固定メモリの確保と解放は、NVIDIA がコンテキストを暗黙に同期する操作として挙げているものです。つまりコンテキストが静かになるのを待ちます。そのコンテキストには DeepEP の forwarding カーネルがいて、そのバッファが運ぶバイトを待って spin しています。待ちは終わりません。

「フレームには上限があるから 1 回成長したら落ち着く」という理屈は正しく、そして無関係でした。解放が 1 回あれば足ります。初回だけ確保する形にしても、窓が全フレームから各スレッドの初回に狭まるだけで閉じません。閉じるのは、resident な何かが現れる前に確保を済ませたときだけです。

いまは登録時に 1 ブロック予約し、原子的なインクリメントで配ります。解放はしません。スレッドの終了時に cuMemFreeHost が走るのは最悪の瞬間で、プロセスの寿命ぶんの有界なリークのほうが安い取引です。

7計測を静かに無効にした事故

4 回分の測定が、13 時間前のバイナリに対するものでした。

再現タスクは plugin の共有オブジェクトを使うだけで、作りません。だから plugin を編集して再現タスクだけを回すと、前のビルドを測ります。しかも何も教えてくれません。気づいたのは、採取したスタックの行番号が前回と 1 行も違わなかったからで、実行の中の情報ではありませんでした。

これは間違った数字ではなく、間違った確信を作ります。あとから気づく方法もありません。だから再現タスクは、ソースが共有オブジェクトより新しいときに致命的として止まり、どのファイルが新しいかを言います。この gate はその後 1 日に 3 回発火して、そのたびに無駄な測定を防ぎました。

付随して、リンク順の失敗も 1 つ。-lgdrapi を -DSRDSIM_WITH_GDRCOPY の隣、翻訳単位より前に置いたのでリンカが無視しました。共有オブジェクトはきれいにビルドされ、dlopen で undefined symbol: gdr_open と言って落ちます。定義は翻訳単位より前、ライブラリは後ろです。

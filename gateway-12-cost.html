第 12 章 書式を揃えて測り直した、解決 1 本あたりの費用

この章の 3 行 第 11 章で書式を揃えたので、3 つの層を同じ条件で並べ直した。能力は 3 層が厳密な入れ子で、 箱が解けたものは必ず安い API も解け、安い API が解けたものは必ず高い API も解けた。 費用は逆順で、箱は解決 1 本あたり安い API の 38%。ただしその安さは箱に考えさせない設定に依存する ことがわかった。考えさせると出力が 3.4 倍・請求が 1.90 倍になり、解けた数は増えない。

並べる前に、揃っていなかったものが 2 つあった

この章の表は 4 行だが、そこに至るまでに条件が 2 回揃っていなかった。どちらも 「相手を弱くしたまま勝った」という形の間違いで、片方は測定対象の制約、もう片方は自分の設定ミスである。

1 つ目。安い API から推論を奪っていた

ゲートウェイの /v1/chat/completions は、関数ツールの宣言と reasoning_effort の併用を 拒否する。none なら通る。それで測ると gpt-5.6-terra は別のモデルになっていた。

推論を切ると解ける数が 9 から 5 に落ちるだけでなく、4 手に 1 手はツールを呼ばずに文章で答えた。 これは「安い API は書式を守れない」ではなく「推論を奪うと守れなくなる」という話で、比較の相手として使えない。 だからハーネスに 2 本目の通信形式 (Responses API) を実装して、推論を high のまま関数ツールを 使えるようにした。

付随して見つけたこと chat completions の拒否メッセージは「/v1/responses を使え」と案内するが、このゲートウェイが 実際に提供しているのは /openai/v1/responses で、案内どおりの裸のパスは 404 だった。

2 つ目。箱に考えさせていなかった。これは自分の設定ミス

箱の vLLM は --default-chat-template-kwargs={"enable_thinking": false} で起動していた。 つまり箱は考えずに答え、API は出力の 80% を推論に使っていた。1 つ目でこちらが拒否したのと 同じ非対称を、逆向きに自分で作っていたことになる。

chat_template_kwargs はリクエストごとに上書きできるので、再デプロイなしで箱の arm を 測り直した。結果は次の節の表に 2 行として入れてある。順位は動かなかったが、「なぜ箱が安いのか」の 読み方は変わった。

12 件を層ごとに並べる

解けた 解けなかった

上の行で緑のマスは、下の行でも必ず緑になっている。箱が解けて安い API が解けなかったタスクは 0 件、 安い API が解けて高い API が解けなかったタスクも 0 件。

入れ子だと何が言えるかは第 2 章と同じで、ルーティングで品質は上がらない。箱は API が 取りこぼしたものを拾えないので、どう賢く振り分けても上限は「一番強い層を単体で使ったとき」のまま。 残る効果は費用だけになる。

費用は逆順で、箱は解決 1 本あたり安い API の 38%

$0.0952 対 $0.2489 で 2.61 倍安い。ここで重要なのは、この 2.61 倍が 「箱に考えさせない設定」での数字だということである。設定を API 側と揃えて両方に考えさせると $0.2175 対 $0.2489 になり、差は 14% しか残らない。

だから「ローカル GPU だから安い」ではない 箱が安いのは、このトラフィックでは考える必要がなく、API 側は自分の正答率のために推論を買っているからである。 推論を必要としないトラフィックを見つけたことが安さの正体で、GPU の所有はその条件が揃ったときに効く。

「思考は役に立たない」ではなく「思考が 40 手に収まらない」かもしれない 思考オンは同じ 40 手の上限の中で 3.4 倍のトークンを使って 1 件落とした。上限を上げれば結果が変わる 可能性は残っている。上限は上げていないので、この表は「この予算での結果」であってモデルの性質ではない。

上のデモを 4 通り動かすと、この章でいちばん意思決定に効く数字が出る。実測 12 件で、 箱を先に試して落ちたら投げ直したときの総額である。

解決 1 本あたりでは箱は安い API の 38% だったのに、実際に安い API へ投げ直す形にすると節約は 5.8% しか 残らない。理由は単純で、箱が落ちた 6 件では箱の請求が丸ごと無駄になり、そのうえで安い API に 全額払うことになるからである。安さは「箱が通ったときの安さ」であって、「箱に投げたときの安さ」ではない。

思考オンで安い API へ投げ直すと、箱を使わないほうが安い +32.8% になる。箱の思考が請求を 1.90 倍にしたうえ、落ちる件数が 1 件増えて無駄になる分も増えるので、 節約が符号ごと反転する。層を足すこと自体が費用を増やす領域があるということで、 第 2 章の「節約には上限がある」より一段強い話になっている。

高い API を投げ直し先にすると −42.2% で、こちらは大きい。第 2 章で見た構造がそのまま効いていて、 高い API は 1 本が高いので、箱で拾える簡単な仕事を先に抜くと消える額が大きい。 つまり箱の価値は「安い API の代わり」ではなく「高い API の前段」にある。

この章で言えないこと

12 件である。入れ子は「この 12 件でそうだった」という事実であって、確率の主張ではない。 3 つの対比較のうち有意水準 5% を切るのは箱と高い API の間だけ (不一致 7 件、両側 p = 0.016) で、 箱と安い API の間は不一致 3 件の p = 0.250 だから、解けた数では両者を分離できていない。 分離できているのは価格だけである。

箱の $0.0952 は限界費用である。これは箱が仕事で埋まっているときのトークン単価で計算した数字で、 第 10 章のしきい値 (前置き再利用のあるトラフィックで毎時およそ 3,295 リクエスト) を超えて初めて成立する。 エピソードの合間に遊んでいる箱は、それでも時間あたり $15.2174 を請求する。これは請求書ではない。

手数の上限が縛るのは箱だけである。箱は 1 本 30.8 手を使い、15 件のうち 6 件は 40 手の上限に 達してパッチを出したまま失敗した。安い API は 15 件すべてを自分で終えている。上限を上げると 箱の数字だけが動くので、6/12 という値はこの予算での結果である。

キャッシュのヒット率は揃えていない。入力トークンのうちキャッシュ読みだった割合は箱 87.0%、 安い API 91.2%、高い API 78.5% で、それぞれの層の実際のキャッシュ単価で値付けしている。 つまりこれは「同じキャッシュ状態で比べた費用」ではなく「実際にかかった費用」である。

そして、この章の数字は 2 回書き直されている。1 回目は箱の書式が壊れたまま測ったもの (第 11 章)、2 回目は安い API から推論を奪ったまま測ったもの、3 回目が上の表である。 同じ実験で相手の設定を 2 回間違えたという事実そのものが、層をまたぐ比較でいちばん壊れやすいのは モデルではなく条件の揃え方だということの記録になっている。

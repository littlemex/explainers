ポリモーフィック関連 ― 1 つの列で複数の親を指す

「どの種類の親にも添付できる」仕組みを、1 つの列に親の種類と ID を詰めて作ると、その列は外部キーを持てない、どの参照先も保証されない列になります

← SQL シリーズ目次へ

この回の前提: 第 06 回 EAV(1 本の共有列が行ごとに違う意味を持つと、外部キーが張れなくなる構造)

添付ファイルやコメントのように、「複数の種類の親のどれにでも付けられるもの」を作りたいとき、parent_type(親の種類)とparent_id(親の ID)という 2 列を持たせ、parent_typeの値によってparent_idが指すテーブルを変える設計をポリモーフィック関連と呼びます。結論を先に言うと、これは第 06 回の EAV と同じ根本原因を持つ設計です。1 本の列の意味が行によって変わるため、PostgreSQL の外部キーという「この列の値は必ずあのテーブルの行を指す」という保証を、宣言できなくなります。この回では実際にこの設計を作って何が壊れるかを確かめ、PostgreSQL で親の種類が複数あるときの正しい書き方を見ます。

1. 目的 ― 何をしたかったのか

バグ管理システムに添付ファイルの機能を加えるとします。バグにはクラッシュログを、商品には製品ロゴを、アカウントにはアバター画像を添付したいというように、添付ファイルは複数の種類の対象に付けられるようにしたいとします。

素直に考えると、添付ファイルごとに別のテーブル(bug_attachments、product_attachments、account_attachments)を作るのは面倒に見えます。「添付ファイルという概念は 1 つなのだから、テーブルも 1 つにまとめたい」という発想から、1 つのattachmentsテーブルに「この添付ファイルはどの種類の、どの ID の親に属しているか」をparent_typeとparent_idの 2 列で持たせる設計が生まれます。親の種類が増えても新しいテーブルを作らずに済むという目的自体は理解できますが、これを実現する手段に問題があります。

2. アンチパターン ― どう書いてしまい、何が壊れるか

実際にポリモーフィック関連のテーブルを作って、何が起きるかを確かめます。

CREATE TABLE attachments (
  attachment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  parent_type   text NOT NULL,
  parent_id     bigint NOT NULL,
  file_name     text NOT NULL,
  uploaded_at   timestamptz NOT NULL DEFAULT now()
);

INSERT INTO attachments (parent_type, parent_id, file_name) VALUES
  ('bug',     1, 'crash_log.txt'),
  ('bug',     2, 'report_before.png'),
  ('product', 1, 'logo.png'),
  ('account', 3, 'avatar.png');

図: parent_id という 1 本の列が、parent_type の値によって 3 つの違うテーブルのどれかを指す。REFERENCES は 1 つの参照先しか持てない。

2.1 外部キーが張れない

parent_idはどの行についても同じbigint列ですが、その値が何を参照すべきかはparent_typeの値によって変わります。PostgreSQL のREFERENCESは 1 つの列に対して 1 つの参照先テーブルしか宣言できないため、この列には外部キーを張れません。実際に存在しない bug を指す行を挿入してみます。

INSERT INTO attachments (parent_type, parent_id, file_name) VALUES ('bug', 999, 'orphan.txt');

SELECT a.attachment_id, a.parent_type, a.parent_id, a.file_name
FROM attachments a
LEFT JOIN bugs b ON a.parent_type = 'bug' AND b.bug_id = a.parent_id
WHERE a.parent_type = 'bug' AND b.bug_id IS NULL;

 attachment_id | parent_type | parent_id | file_name
---------------+-------------+-----------+------------
             5 | bug         |       999 | orphan.txt
(1 row)

bug_id=999 のバグは存在しませんが、挿入は何のエラーも無く成功しました。孤立した行があることに気づくには、このように parent_type ごとに LEFT JOIN を書いて検出するしかありません。

2.2 取得には CASE WHEN での分岐が要る

通常の JOIN なら 1 本の FK をたどるだけですが、ポリモーフィック関連では参照先が parent_type によって変わるため、親の情報を取り出すには parent_type で分岐したサブクエリを書く必要があります。

SELECT a.attachment_id, a.parent_type,
  CASE a.parent_type
    WHEN 'bug'     THEN (SELECT summary FROM bugs WHERE bug_id = a.parent_id)
    WHEN 'product' THEN (SELECT product_name FROM products WHERE product_id = a.parent_id)
    WHEN 'account' THEN (SELECT account_name FROM accounts WHERE account_id = a.parent_id)
  END AS parent_label
FROM attachments a
ORDER BY a.attachment_id;

 attachment_id | parent_type |     parent_label
---------------+-------------+-----------------------
             1 | bug         | crash when saving
             2 | bug         | wrong total on report
             3 | product     | Open RoundFile
             4 | account     | carol
             5 | bug         |
(5 rows)

5 件目(先ほどの孤立した行)は parent_label が空になりますが、これはエラーではなく「見つからなかった」という結果として静かに返ります。親の種類が増えるたびに、この CASE 文をアプリケーションの全てのクエリで書き直す必要があります。

2.3 parent_type の表記ゆれも防げない

parent_typeはただの文字列なので、大文字小文字の違いもデータベースは区別してしまいます。

INSERT INTO attachments (parent_type, parent_id, file_name) VALUES ('Bug', 1, 'typo_type.txt');

SELECT DISTINCT parent_type FROM attachments ORDER BY parent_type;

 parent_type
-------------
 account
 bug
 Bug
 product
(4 rows)

'bug'と'Bug'はアプリケーションのコードからは別の値として扱われ、この行はどの CASE WHEN 分岐にも一致しなくなります。列の値がテーブルの一部である EAV と同様、ここでも表記ゆれを防ぐ仕組みが列定義には存在しません。

3. 見つけ方 ― どんな兆候で気づくか

既存のデータベースの中にポリモーフィック関連が無いかは、「*_typeという文字列の列と*_idという数値の列が同じ接頭辞で対になっていて、その*_id列に外部キーが 1 本も無い」というテーブルをinformation_schemaから探すことで機械的に検出できます。

SELECT c1.table_name, c1.column_name AS type_column, c2.column_name AS id_column
FROM information_schema.columns c1
JOIN information_schema.columns c2
  ON c1.table_schema = c2.table_schema AND c1.table_name = c2.table_name
  AND regexp_replace(c1.column_name, '_type$', '') = regexp_replace(c2.column_name, '_id$', '')
WHERE c1.table_schema = 'public'
  AND c1.column_name LIKE '%\_type'
  AND c2.column_name LIKE '%\_id'
  AND NOT EXISTS (
    SELECT 1 FROM information_schema.key_column_usage k
    JOIN information_schema.table_constraints tc
      ON tc.constraint_name = k.constraint_name AND tc.constraint_schema = k.constraint_schema
    WHERE tc.constraint_type = 'FOREIGN KEY'
      AND k.table_name = c2.table_name AND k.column_name = c2.column_name
  )
ORDER BY c1.table_name;

 table_name  | type_column | id_column
-------------+-------------+-----------
 attachments | parent_type | parent_id
(1 row)

このクエリは、列名の接頭辞をregexp_replaceで揃えて同じ組だけを対にし、さらにinformation_schema.key_column_usageとtable_constraintsを結合して、その列に外部キー制約が本当に 1 つも無いことを確認しています。外部キーがちゃんと張られている通常の列(たとえばbugs.statusとbug_statusへの参照)はこの検出から除外されるため、誤検出が少なくなります。

4. 使ってよい場合

「複数の種類の対象に同じ機能を付けたい」という目的自体は正当です。ただし、その対象の種類が 2〜3 種類程度に限られ、かつ将来増える見込みが薄いなら、5 章で見る交差テーブルや排他的 FK 列のような、PostgreSQL の外部キーを保ったまま書ける設計で十分間に合います。ポリモーフィック関連を検討してよいのは、対象の種類が本当に多く(数十種類以上)、かつ個々の参照整合性よりも「1 つのテーブルに集約できることの単純さ」を優先する、ログやイベント記録のような用途に限られます。この場合でも、参照整合性をアプリケーション側で諦めたことを明確に認識し、孤立した行を定期的に検出する運用を別に用意する必要があります。

5. 解決策 ― PostgreSQL での正しい書き方

「複数の種類の親に同じようなものを付けたい」という要望には、正しい外部キーを保ったまま書ける設計が 4 つあります。

5a. 交差テーブル (親の種類ごとに中間テーブルを分ける)

parent_type/parent_idという汎用列をやめ、添付ファイル本体のテーブルと、親の種類ごとの中間テーブル(交差テーブル)に分けます。

CREATE TABLE attachment_files (
  attachment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  file_name     text NOT NULL,
  uploaded_at   timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE bug_attachments (
  bug_id        bigint NOT NULL REFERENCES bugs (bug_id) ON DELETE CASCADE,
  attachment_id bigint NOT NULL REFERENCES attachment_files (attachment_id) ON DELETE CASCADE,
  PRIMARY KEY (bug_id, attachment_id)
);
CREATE TABLE product_attachments (
  product_id    bigint NOT NULL REFERENCES products (product_id) ON DELETE CASCADE,
  attachment_id bigint NOT NULL REFERENCES attachment_files (attachment_id) ON DELETE CASCADE,
  PRIMARY KEY (product_id, attachment_id)
);

SELECT b.bug_id, b.summary, f.file_name
FROM bug_attachments ba
JOIN bugs b ON b.bug_id = ba.bug_id
JOIN attachment_files f ON f.attachment_id = ba.attachment_id
ORDER BY b.bug_id;

 bug_id |      summary      |   file_name
--------+--------------------+---------------
      1 | crash when saving | crash_log.txt
(1 row)

bug_attachments.bug_idは通常の bugs への外部キーなので、存在しない bug_id を挿入しようとすると普通にエラーで拒否されます(わざとエラーになる例で確認します)。欠点は、親の種類が増えるたびに中間テーブルを 1 つ追加する必要があることです。

5b. 逆方向参照 (親側が 1 件の添付ファイルを指す)

「1 つの親に対して添付ファイルが 1 件まで」のような 1 対 1(または 1 対多だが代表 1 件だけでよい)の関係なら、添付ファイル側から親を指すのではなく、親側が添付ファイルを指すように向きを逆にできます。こうすれば参照先は常に 1 つの具体的なテーブル(attachment_files)になり、ごく普通の外部キーで書けます。

ALTER TABLE bugs ADD COLUMN cover_attachment_id bigint REFERENCES attachment_files (attachment_id);
UPDATE bugs SET cover_attachment_id = 1 WHERE bug_id = 1;

SELECT bug_id, summary, cover_attachment_id FROM bugs WHERE bug_id = 1;

 bug_id |      summary      | cover_attachment_id
--------+--------------------+----------------------
      1 | crash when saving |                    1
(1 row)

この方式は「1 つの親が複数の添付ファイルを持つ」場合には向きません(bugs の 1 列では複数の attachment_id を持てないため)。代表画像やカバー画像のように、親から見て「ちょうど 1 件」で十分な関係に限って使えます。

図: 添付ファイル側から親を指すのではなく、親側が添付ファイルを指すようにすると、通常の外部キーが使える。

5c. 共通の親テーブル (commentable な対象をまとめる代理キー)

複数の種類の親に、本当に「同じ添付先」として振る舞ってほしい場合は、共通の代理キーを発行する親テーブルを 1 つ用意し、bugs と products の両方がその代理キーを 1 対 1 で持つようにします。添付ファイルはこの共通の代理キーだけを参照すればよくなります。

CREATE TABLE commentable_entities (
  entity_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  entity_kind text NOT NULL CHECK (entity_kind IN ('bug', 'product'))
);
ALTER TABLE bugs ADD COLUMN entity_id bigint UNIQUE REFERENCES commentable_entities (entity_id);
ALTER TABLE products ADD COLUMN entity_id bigint UNIQUE REFERENCES commentable_entities (entity_id);

CREATE TABLE entity_attachments (
  entity_id     bigint NOT NULL REFERENCES commentable_entities (entity_id) ON DELETE CASCADE,
  attachment_id bigint NOT NULL REFERENCES attachment_files (attachment_id) ON DELETE CASCADE,
  PRIMARY KEY (entity_id, attachment_id)
);

SELECT ce.entity_kind, b.summary, f.file_name
FROM entity_attachments ea
JOIN commentable_entities ce ON ce.entity_id = ea.entity_id
JOIN bugs b ON b.entity_id = ea.entity_id
JOIN attachment_files f ON f.attachment_id = ea.attachment_id;

 entity_kind |      summary      |   file_name
-------------+--------------------+---------------
 bug         | crash when saving | crash_log.txt
(1 row)

この方式なら中間テーブルはentity_attachmentsの 1 つだけで済み、親の種類が増えてもcommentable_entitiesを参照する列を追加するだけで対応できます。欠点は、bugs や products を取得するたびに、本来不要な entity_id という代理キーの管理が常に必要になることです。

5d. 排他的 FK 列 + CHECK(num_nonnulls) (複数の NULL 許容 FK 列から 1 本だけ選ぶ)

親の種類が少数(3 種類程度)に決まっているなら、添付ファイルのテーブルに親の種類ごとの NULL 許容な外部キー列を複数持たせ、「ちょうど 1 本だけが埋まっている」ことを CHECK 制約で強制する方式が書けます。PostgreSQL には、引数のうち NULL でないものの個数を返す組み込み関数num_nonnullsがあります。

CREATE TABLE attachments_exclusive (
  attachment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  file_name     text NOT NULL,
  bug_id        bigint REFERENCES bugs (bug_id) ON DELETE CASCADE,
  product_id    bigint REFERENCES products (product_id) ON DELETE CASCADE,
  account_id    bigint REFERENCES accounts (account_id) ON DELETE CASCADE,
  CONSTRAINT exactly_one_parent CHECK (num_nonnulls(bug_id, product_id, account_id) = 1)
);
INSERT INTO attachments_exclusive (file_name, bug_id) VALUES ('crash_log.txt', 1);
INSERT INTO attachments_exclusive (file_name, product_id) VALUES ('logo.png', 1);
INSERT INTO attachments_exclusive (file_name, account_id) VALUES ('avatar.png', 3);

SELECT attachment_id, file_name, bug_id, product_id, account_id FROM attachments_exclusive ORDER BY attachment_id;

 attachment_id |   file_name   | bug_id | product_id | account_id
----------------+---------------+--------+------------+------------
              1 | crash_log.txt |      1 |            |
              2 | logo.png      |        |          1 |
              3 | avatar.png    |        |            |          3
(3 rows)

bug_id、product_id、account_id はそれぞれ通常の外部キーなので、存在しない ID を指そうとすれば普通に拒否されます。さらに、2 本以上を同時に埋めようとしたり、どれも埋めなかったりすると、exactly_one_parentという CHECK 制約が違反として拒否します(わざとエラーになる例で確認します)。各列に個別のインデックスを張れば、型ごとの検索も素直なインデックスの対象になります。

CREATE INDEX ON attachments_exclusive (bug_id);
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM attachments_exclusive WHERE bug_id = 1;

 Seq Scan on attachments_exclusive  (cost=0.00..1.04 rows=1 width=64) (actual time=0.002..0.003 rows=1.00 loops=1)
   Filter: (bug_id = 1)
   Rows Removed by Filter: 2
 Execution Time: 0.005 ms

この例ではテーブルが 3 行しかないためプランナはインデックスではなく Seq Scan を選びましたが、これは「テーブルが小さいので全件読んだほうが速い」という正しい判断です。行数が増えれば、bug_id に対する検索はこのインデックスを使う Bitmap/Index Scan に切り替わります。欠点は、親の種類が増えるたびにこのテーブル自体に列を追加する必要があり、種類が多くなると NULL 許容列が増えすぎることです。

図: num_nonnulls を使った CHECK 制約が、複数の FK 列のうちちょうど 1 本だけが埋まっていることを保証する。

6. PostgreSQL エンジンで考慮しておくこと ― 交差テーブルは遅くならない

「parent_type/parent_id の共有列をやめて交差テーブルに分けると、JOIN が増えて遅くなるのでは」という疑問が出ます。これを 5 万件規模の合成データ(generate_seriesで生成、本物の計測)で確かめます。bugsに 5 万件の合成行を追加し、attachments(共有列方式)とbug_attachments+attachment_files(交差テーブル方式)の両方に同じ件数のデータを入れて、同じ 1 件を検索する速度を比較します。

-- 共有列 (parent_type, parent_id) への複合インデックス経由
EXPLAIN (ANALYZE, BUFFERS)
SELECT file_name FROM attachments WHERE parent_type = 'bug' AND parent_id = 30006;

 Index Scan using attachments_parent_type_parent_id_idx on attachments (actual time=0.007..0.007 rows=1.00 loops=1)
   Index Cond: ((parent_type = 'bug'::text) AND (parent_id = 30006))
   Buffers: shared hit=3
 Execution Time: 0.016 ms

-- 交差テーブル経由 (本物の外部キーを持つ)
EXPLAIN (ANALYZE, BUFFERS)
SELECT f.file_name FROM bug_attachments ba
JOIN attachment_files f ON f.attachment_id = ba.attachment_id
WHERE ba.bug_id = 30006;

 Nested Loop (actual time=0.018..0.019 rows=1.00 loops=1)
   ->  Index Only Scan using bug_attachments_pkey on bug_attachments ba (actual time=0.011..0.012 rows=1.00 loops=1)
         Index Cond: (bug_id = 30006)
         Heap Fetches: 1
   ->  Index Scan using attachment_files_pkey on attachment_files f (actual time=0.004..0.005 rows=1.00 loops=1)
         Index Cond: (attachment_id = ba.attachment_id)
   Buffers: shared hit=6
 Execution Time: 0.029 ms

5 万件規模、キャッシュが温まった状態で、共有列方式は 0.016 ミリ秒・バッファヒット 3 回、交差テーブル方式は 0.029 ミリ秒・バッファヒット 6 回でした。交差テーブル方式のほうが JOIN が 1 回増える分バッファのアクセス数は多いものの、どちらも同じ桁(1 ミリ秒未満)の実行時間であり、「交差テーブルにすると遅くなる」というのは実測では支持されません。差が出るとすれば、参照整合性を保つために払う追加の JOIN のコストよりも、EAV やポリモーフィック関連が引き起こす孤立行の調査やアプリケーション側の CASE 文の保守コストのほうが、実務上はずっと大きくなります。

もう 1 つ注意すべき点は、交差テーブル方式ではbug_attachments_pkeyのような複合主キーがIndex Only Scan(インデックスの情報だけで答えを返せる場合に使われる走査)の対象になっていることです。これは(bug_id, attachment_id)という複合主キーがその列だけで答えを返せる場合に起きる、PostgreSQL のインデックスの最適化です。ただし、実測のHeap Fetches: 1が示すとおり、この計測では Index Only Scan を選んでいてもテーブル本体への参照が 1 回発生しています。PostgreSQL は行の可視性(そのバージョンの行を今の問い合わせから見てよいか)を可視性マップ(ページ単位で「全員から見える」と記録する仕組み)で管理しており、5 万件を一括 INSERT した直後はこのマークがまだ更新されていないため、Index Only Scan を選んでもテーブル本体を 1 回参照する必要がありました。

-- VACUUM で可視性マップを更新すると、同じクエリの Heap Fetches が 0 になる
VACUUM bug_attachments;
EXPLAIN (ANALYZE, BUFFERS)
SELECT f.file_name FROM bug_attachments ba
JOIN attachment_files f ON f.attachment_id = ba.attachment_id
WHERE ba.bug_id = 30006;

 Nested Loop (actual time=0.015..0.015 rows=1.00 loops=1)
   ->  Index Only Scan using bug_attachments_pkey on bug_attachments ba (actual time=0.009..0.009 rows=1.00 loops=1)
         Index Cond: (bug_id = 30006)
         Heap Fetches: 0
   ->  Index Scan using attachment_files_pkey on attachment_files f (actual time=0.004..0.004 rows=1.00 loops=1)
         Index Cond: (attachment_id = ba.attachment_id)
   Buffers: shared hit=6
 Execution Time: 0.024 ms

VACUUMで可視性マップを更新した後に同じクエリを実行すると、Heap Fetchesが 0 になり、テーブル本体への参照が無くなりました。共有列方式の複合インデックスも同様に Index Scan が使われていますが、こちらはfile_nameという主キーに含まれない列を返す必要があるため、VACUUM をしても Index Only Scan にはなりません。

図: 5 万件規模の実測では、交差テーブル方式も共有列方式と同じ桁の速度で検索できる。

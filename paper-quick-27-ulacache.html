GPU と CPU のメモリに通し番号をつけ、同じ履歴の重複を減らして同時に書ける数を増やす

元の論文: Zhu, Cao et al., "UlaCache: Unified Logical Addressing for Sparse LLM Serving"

ひとことで言うと、「スパースアテンション（毎回、過去の語の一部だけを選んで読むしくみ）を使う LLM では、選ばれなかった過去の語のメモ（KV キャッシュ）も捨てられず、メモリを圧迫する。UlaCache は GPU と CPU のメモリ全体に変わらない通し番号（論理アドレス）をつけてまとめ、同じ履歴の写しを何か所にも持たないようにした。その結果、同じ量の GPU・CPU メモリで、投機的デコードを使ったときの最高の書き出し速度が、これまでで最も良いしくみ HiSparse を H200 と B300 の両方、DP と TP の両方で上回った（具体的な倍率は、今回読んだ本文のテキストからは数字が抜け落ちていたため、元の論文で確認してください）」という研究です。

見つけた場所: arXiv 週報 2026-10-29

何が困っていたのか

LLM が文章を書くとき、過去に読んだ語ごとに「キーと値」というメモを取っておきます。これが KV キャッシュです。たくさんの文章を同時に書く（バッチ処理、まとめて計算して効率を上げること）ほど速くなりますが、文章ごとに KV キャッシュが必要なので、文脈が長く、同時に書く数が多いと GPU のメモリが足りなくなります。

スパースアテンションは、毎回読む KV の量を減らします。でも、次の語では別の過去の語が選ばれるかもしれないので、選ばれなかった履歴も残しておかなければなりません。つまり、読む量は減っても、しまっておく量は減りません。

CPU のメモリを使って置き場所を増やす方法はすでにありましたが、論文は次の問題を指摘しています。

  • HiCache や LMCache は、前に計算した文章の頭の部分（プレフィックス）を CPU にしまい、使うときに GPU に戻します。計算のやり直しは減りますが、書いている最中の文章の履歴は結局 GPU の場所を使うので、同時に書ける数は増えません
  • HiSparse は、書いている文章の履歴を全部 CPU に置き、選ばれた分を GPU に写して使います。GPU にある分は CPU にあるものの写しなので、GPU の場所は「速く読むため」には役立っても、「しまえる履歴の量」は増やしません
  • HiSparse は文章 1 本ごとに GPU の取り分を固定しています。同時に書く文章が少なく GPU が空いていても、その取り分を超えた分は CPU から取ってこなければなりません
  • MLA（キーと値を、全部のヘッドで共有する小さな形に縮める方式）を使うモデルを TP（アテンションのヘッドを複数の GPU に分けて計算する方式）で動かすと、どの GPU も同じ履歴を丸ごと持ちます。8 台の TP では、履歴用の場所の大部分が写しで埋まっていたと論文は示しています

UlaCache のやり方

手順 1: すべての置き場所に通し番号をつける

GPU の KV 置き場と、必要なら CPU の KV 置き場をひとまとめにし、論理アドレスという変わらない番号をつけます。推論エンジン（モデルを動かすソフト、ここでは SGLang）はこの番号だけを使います。実際のデータが GPU と CPU の間で移動しても、UlaCache が「番号から実際の場所への対応表」を書き換えるだけなので、エンジン側の番号は変わりません。

手順 2: DP と TP で置き方を変える

  • DP（GPU ごとに別々の文章を受け持つ方式）では、各 GPU が自分の GPU と CPU の置き場をまとめて使います。選ばれたデータが CPU にあれば、まず GPU に移してからアテンションで読みます
  • TP では、グループ内の GPU が履歴を別々の部分に分けて持ちます。全部の GPU が同じ履歴を持たないので、GPU 全体でしまえる量が増えます。計算する GPU は、選ばれた KV を手元の小さな置き場（ローカル GPU バッファ）に写してから使います。前の語で写したものが残っていればそのまま使い、足りない分だけを自分や他の GPU から取ってきます
  • 同じ選び方を共有する層では、どれを取ってくるかの計画を 1 回だけ作って使い回し、今の層を計算している間に次の層のデータを先に取ってきます
  • TP では、どの語を選ぶかを決める索引（インデクサー）のキーも GPU ごとに分け、それぞれが自分の分だけ点数をつけ、最後に点数を集めて上位を選びます

手順 3: PB-LRU で GPU に何を残すか決める

CPU も使うとき、GPU の置き場はすべての文章で共有されます。何を GPU に残し何を CPU に追い出すかは LRU（いちばん長く使われていないものから追い出すルール）に近い方法で決めます。続けて書く語では、同じ過去の語が何度も選ばれやすいからです。

  • PB-LRU（並列バケット LRU）は、1 回ずつの使用順を正確に並べる代わりに、同じ回に使われた場所を同じ「バケット（入れ物）」にまとめます
  • 最近のバケットがいくつか輪のように並び、1 回ごとに進みます。古くなったバケットの中身は「コールド（しばらく使われていない）」バケットに移ります。このときデータ自体は GPU に残ったままで、印だけが変わります
  • 各バケットはビットマップ（GPU の場所 1 つにつき 1 ビットの、入っているかどうかの印の列）で表し、多数の GPU のスレッドで同時に調べ、更新します
  • CPU から来るデータには、まず空いている場所、次にコールドバケット、次に古い順の最近のバケットから場所を選びます。今使っているバケットは選ばないので、今の計算に必要なデータは追い出されません。上の段のまとめのビットマップで、空の区域を飛ばして探します

手順 4: データを動かしてから対応表を書き換える

CPU から GPU にデータを入れるとき、追い出すデータはちょうど空いた CPU の場所に入れ替えで移します。新しい CPU の場所を用意しなくて済みます。全部の移動が終わってから対応表を書き換え、完了の合図を出します。アテンションはこの合図を待つので、まだ届いていないデータを読むことはありません。

何を測ったのか

GLM-5.3 を H200 と B300 の GPU で動かし、重みと KV キャッシュは FP8（8 ビットの数）で持ちました。比べる相手は、KV を全部 GPU に置くふつうの SGLang と、CPU も使う HiSparse です。投機的デコード（下書きを先に作り、本体がまとめて確かめるしくみ）には、2 歩先まで下書きする MTP（複数の語を一度に予想する方式）を使いました。

また、B300 の TP で投機的デコードなしのとき、UlaCache の最高速度は SGLang の最高速度の何倍かが示されていますが、この値も今回の本文テキストでは抜けていました。しまえる履歴が増えて同時に書ける本数が増え、1 回のモデル計算をより多くの文章で分け合えたことが速さの理由だと論文は説明しています。

うまくいかない場面・残された課題

  • 同時に書く本数が少ないときは、KV を全部 GPU に置く SGLang より遅いままです
  • TP で索引の点数を GPU 間で集める通信は、特に同時に書く本数が少ないときに負担になると論文は述べています
  • 追い出しがほとんど起きないときは、バケットの印を管理する手間がある分、ふつうの LRU のほうが速いです
  • バケットを進めるとき、古くなるバケットの中身を処理するので、最悪の場合は GPU 置き場全体を調べることになります
  • 同時に書く本数が増えると、共有の GPU 置き場を取り合うのでヒット率は下がります
  • 投機的デコードは下書き用のメモリも使うため、速さと同時に書ける本数が一緒に増えるとは限りません
  • 試したのは GLM-5.3、Multi-LexSum の文章、毎回いちばん確からしい語を選ぶ書き方（グリーディ）に限られます。また、全部の文章の読み込み（prefill）を終えてから書き始める測り方です

インフラを作る人にとっての意味

CPU メモリを足すとき、それが「計算のやり直しを減らす」のか「しまえる履歴を増やす」のかで、同時に書ける本数への効き方がまったく違う、という点が大事です。GPU と CPU、複数の GPU の間で同じ履歴の写しを持たないように配置し、文章ごとの固定の取り分をやめて共有にすれば、同じメモリ量でより多くの文章を同時に扱えます。そのためには、データが動いても変わらない番号と、追い出しの判断を GPU 上で並列に速く行うしくみが必要になる、というのが論文の設計の考え方です。

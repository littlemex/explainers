サーティワンフレーバー ― 値の候補を列定義に埋め込む

値の候補を列の定義や型そのものに埋め込むと、新しい値を増やすたびにスキーマを書き換えてロックを取る必要が生まれる。参照テーブルと外部キーなら、値の追加はただの 1 行 INSERT で済む

この回の前提: 第 05 回 キーレスエントリ (外部キーで参照整合性を守る基本)

「状態」や「優先度」のように、取りうる値の種類が決まっている列を見ると、つい列の定義そのものに候補を書き込みたくなります。CHECK (priority IN ('LOW','MEDIUM','HIGH')) や PostgreSQL の enum 型がその代表です。結論を先に言うと、この書き方は値が増える・減る・並び順を変えるたびにスキーマの変更が必要になり、しかも変更の種類によって取るロックの強さが違います。この回では、実際にローカルの PostgreSQL でロックの強さを測りながら、候補の集合は参照テーブル + 外部キーに持たせるべき理由を確認します。

1. 目的 ― 何をしたかったのか

バグ管理システムの bugs テーブルには priority という列があり、取りうる値は "LOW"・"MEDIUM"・"HIGH" のように、あらかじめ決まった少数の候補に限定したいとします。自由入力の text 列のままだと、"high" や "Hi" のような表記ゆれが入り込み、集計やフィルタが正しく動かなくなります。

この問題を解決するために、列の定義そのものに候補の一覧を書き込む、という発想が生まれます。PostgreSQL では主に 2 つの方法があります。1 つは CHECK (priority IN ('LOW','MEDIUM','HIGH')) という制約、もう 1 つは CREATE TYPE priority_enum AS ENUM ('LOW','MEDIUM','HIGH') という列挙型 (enum) です。どちらも「入力ミスを防ぐ」という目的そのものは正しく達成します。問題は、この候補の一覧を どこに書くか です。

2. アンチパターン ― どう書いてしまい、何が壊れるか

候補の一覧を列定義や型定義そのものに埋め込むと、新しい候補 (例えば "CRITICAL") を追加したくなったとき、データの行を 1 件追加するのではなく、スキーマそのものを書き換える 必要が出てきます。実際に両方の方式を PostgreSQL 18 で試して確認します。

2.1 CHECK (IN ...) 方式

まず priority 列に CHECK 制約を追加します。

ALTER TABLE bugs ADD CONSTRAINT bugs_priority_check
  CHECK (priority IN ('LOW','MEDIUM','HIGH'));

この制約の実体をカタログ関数 pg_get_constraintdef で見ると、IN (...) という書き方は内部的に = ANY (配列) に変換されて保存されていることが分かります。

       conname       |                            pg_get_constraintdef
---------------------+-----------------------------------------------------------------------------
 bugs_priority_check | CHECK ((priority = ANY (ARRAY['LOW'::text, 'MEDIUM'::text, 'HIGH'::text])))

この状態で "CRITICAL" を優先度に設定しようとすると、制約違反で拒否されます。同じ形の CHECK 制約を持つ別のテーブルで実際に試すと、次のエラーになりました。

INSERT INTO t_check_demo VALUES ('CRITICAL');
ERROR:  new row for relation "t_check_demo" violates check constraint "t_check_demo_v_check"
DETAIL:  Failing row contains (CRITICAL).

新しい値を使えるようにするには、制約を一度 DROP してから、候補を増やした新しい定義で ADD するしかありません。

図: 候補の一覧が制約の定義文に書き込まれているため、新しい値はデータではなくスキーマの変更になる。

2.2 enum 型方式

次に enum 型に置き換えます。

CREATE TYPE priority_enum AS ENUM ('LOW','MEDIUM','HIGH');
ALTER TABLE bugs ALTER COLUMN priority TYPE priority_enum
  USING priority::priority_enum;

enum の値と並び順は pg_enum カタログに保存されています。enumsortorder という数値が、比較 ・ ORDER BY の基準になります。

 enumlabel | enumsortorder
-----------+---------------
 LOW       |             1
 MEDIUM    |             2
 HIGH      |             3

新しい値を末尾に追加するのは軽い操作です。

ALTER TYPE priority_enum ADD VALUE 'CRITICAL' AFTER 'HIGH';

既存の値の間に挿入することもできますが、そのときの enumsortorder は整数ではなく、周りの値の間を取った小数になります。実際に 'BLOCKER' を 'HIGH' と 'CRITICAL' の間に挿入すると、以下のようになりました。

 enumlabel | enumsortorder
-----------+---------------
 LOW       |             1
 MEDIUM    |             2
 HIGH      |             3
 BLOCKER   |           3.5
 CRITICAL  |             4

図: 実測。'BLOCKER' を HIGH (3) と CRITICAL (4) の間に入れると enumsortorder=3.5 になった。

この enumsortorder の順で ORDER BY も比較演算子も動きます。実際に bug_id=1 の優先度を 'CRITICAL' に更新してから ORDER BY priority すると、アルファベット順ではなく宣言順に並びます (NULL は既定で最後)。

 bug_id | priority
--------+----------
      3 | LOW
      2 | MEDIUM
      4 | HIGH
      1 | CRITICAL
      5 | (NULL、未設定)

この方式にも、値を増やす・並べ替えるたびに ALTER TYPE という DDL (スキーマを変更する文) が必要という同じ問題が残ります。しかも PostgreSQL 公式ドキュメントは「既存の値を enum 型から削除することはできず、並び順を変更することもできない。できるのは型を削除して作り直すことだけ」と明記しています。実際に削除を試すと専用のエラーになります (dropping an enum value is not implemented)。

3. 見つけ方 ― どんな兆候で気づくか

既存のデータベースに「値の候補を定義に埋め込む」アンチパターンがあるかは、カタログから具体的に探せます。

3.1 IN (...) 形の CHECK 制約を探す

このクエリは pg_constraint を conrelid で pg_class に結合しているため、情報スキーマ自身が持つドメイン制約 (yes_or_no など、テーブルの列ではなく型に付く制約で conrelid が 0) は結合の時点で自動的に除外されます (実機で確認済み)。public スキーマへの限定は、拡張機能や他スキーマにあるテーブルの制約を除き、自分のアプリケーションのテーブルだけに絞り込むためのものです。

SELECT c.conrelid::regclass AS table_name, c.conname,
       pg_get_constraintdef(c.oid) AS definition
FROM pg_constraint c
JOIN pg_class cl ON cl.oid = c.conrelid
WHERE c.contype = 'c' AND cl.relnamespace = 'public'::regnamespace
  AND pg_get_constraintdef(c.oid) LIKE '%= ANY%';
 table_name |       conname       |                                 definition
------------+---------------------+-----------------------------------------------------------------------------
 bugs       | bugs_priority_check | CHECK ((priority = ANY (ARRAY['LOW'::text, 'MEDIUM'::text, 'HIGH'::text])))

3.2 列の型が enum になっている箇所を探す

SELECT c.relname AS table_name, a.attname AS column_name, t.typname AS enum_type
FROM pg_attribute a
JOIN pg_type t ON a.atttypid = t.oid
JOIN pg_class c ON a.attrelid = c.oid
WHERE t.typtype = 'e' AND c.relnamespace = 'public'::regnamespace AND a.attnum > 0;
 table_name | column_name |   enum_type
------------+-------------+---------------
 bugs       | priority    | priority_enum

どちらのクエリも、設計の問題を人の目でコードを読んで探す代わりに、カタログから機械的に一覧できる点が実用的です。レビューの自動チェックに組み込みやすい形です。

4. 使ってよい場合

CHECK (IN ...) や enum がいつも悪いわけではありません。使ってよい条件は、値の集合が本当に固定で、説明文や優先順位、SLA のような追加の属性を持つ必要がない場合です。例えば、関数の引数に渡す "ASC"/"DESC" のような並び方向や、曜日のようにアプリケーションのロジック自体がその値を前提にコンパイルされていて、値が増えたら当然コードの再デプロイが必要になるような場合です。こうした場合、enum には測定できるメリットがあります。

実際に enum 型と text 型で 1 件あたりの保管サイズを比べると、次のようになりました (同じ priority_enum 型と text 型に同じ文字列を入れて pg_column_size で計測)。

 enum_high | text_high | enum_medium | text_medium
-----------+-----------+-------------+-------------
         4 |         8 |           4 |          10

enum は値の文字数に関係なく常に 4 バイト固定であるのに対し、text は "HIGH" (4 バイトに対して 8 バイト) より "MEDIUM" (6 文字) の方が大きい 10 バイトになりました。行数が数百万件を超えるような列では、この差が積み重なります。

ただし、この回のテーマである priority は、説明文やランクのような追加属性を持たせたくなる可能性が高く、ビジネス側の都合で値が増えたり並び順が変わったりする列です。このような列は、次の 5 節で見る参照テーブルの方が向いています。

図: 値が本当に固定で属性も不要なときだけ、列定義への埋め込みが向く。

5. 解決策 ― PostgreSQL での正しい書き方

このサンプル DB の bug_status テーブルは、すでに参照テーブル方式を採用しています。status 列は bug_status (status) への外部キーで、新しい状態を増やすには bug_status に 1 行 INSERT するだけです。priority 列にも同じ形を適用します。

CREATE TABLE priorities (
  priority    text PRIMARY KEY,
  rank        integer NOT NULL UNIQUE,
  description text
);
INSERT INTO priorities (priority, rank, description) VALUES
  ('LOW', 1, '次のリリースでよい'),
  ('MEDIUM', 2, '計画中のリリースで対応'),
  ('HIGH', 3, '今のスプリントで対応'),
  ('CRITICAL', 4, '緊急パッチが必要');

ALTER TABLE bugs ALTER COLUMN priority TYPE text USING priority::text;
ALTER TABLE bugs ADD CONSTRAINT bugs_priority_fkey
  FOREIGN KEY (priority) REFERENCES priorities (priority);
DROP TYPE priority_enum;

新しい優先度 "BLOCKER" を増やすのは、priorities への 1 行 INSERT だけで済みます。

INSERT INTO priorities (priority, rank, description) VALUES ('BLOCKER', 5, '本番停止中');
 priority | rank |      description
----------+------+------------------------
 LOW      |    1 | 次のリリースでよい
 MEDIUM   |    2 | 計画中のリリースで対応
 HIGH     |    3 | 今のスプリントで対応
 CRITICAL |    4 | 緊急パッチが必要
 BLOCKER  |    5 | 本番停止中

並び順も rank 列で自由に変えられ、型の再定義は一切不要です。説明文のような追加の属性も、参照テーブルの列として自然に持てます。

図: priority 列は priorities テーブルへの外部キーになり、既存の bug_status と同じ形になる。

6. PostgreSQL エンジンで考慮しておくこと

3 つの方式が、値の追加のときに実際にどのロックを取るかを pg_locks で測りました。

方式値を増やす操作実測したロック
CHECK (IN ...)ADD CONSTRAINT (既存行を検証)bugs に AccessExclusiveLock
enumALTER TYPE ... ADD VALUEpg_type の型オブジェクトに ExclusiveLock (bugs 自体には取られない)
参照テーブル + FKINSERT 1 行bugs には 0 件 (ロックなし)

CHECK 制約を NOT VALID なしで追加すると、PostgreSQL は既存の全行が新しい制約を満たすか検証するため、検証が終わるまで bugs テーブルへの読み書きも含めて全部ブロックする AccessExclusiveLock を取ります。実際に BEGIN; ALTER TABLE bugs ADD CONSTRAINT ... CHECK (...); SELECT * FROM pg_locks WHERE relation='bugs'::regclass; を実行すると、AccessExclusiveLock が確認できました。

enum への ADD VALUE は印象とは違って軽い操作です。ロックの対象は bugs テーブルではなく、型そのもの (pg_type のエントリ) です。これは PostgreSQL の公式ドキュメントが明記する通り、むしろ注意すべき点は別にあります。同一トランザクション内で ADD VALUE した直後に、その新しい値を同じトランザクション内で使おうとするとエラーになります。 実際に試すと次のエラーになりました。

BEGIN;
ALTER TYPE t_enum_demo ADD VALUE 'CRITICAL';
INSERT INTO t_enum_tbl VALUES ('CRITICAL');
ERROR:  unsafe use of new value "CRITICAL" of enum type t_enum_demo
HINT:  New enum values must be committed before they can be used.

参照テーブルへの INSERT は、bugs テーブルには一切触れないので、bugs に対するロックは 0 件でした。これが 3 つの方式の中で最も並行実行に優しい形です。なお、enum の比較は BEFORE/AFTER で末尾以外に値を追加すると、元からある値同士の比較より遅くなることがあると公式ドキュメントに記載があります (この回のサンプル規模では測定できる差ではありませんが、挙動として押さえておく価値があります)。

CHECK 制約にも、ロックを短くする逃げ道があります。ADD CONSTRAINT ... CHECK (...) NOT VALID という書き方で追加すると、既存行の検証をその場では行わないため、ACCESS EXCLUSIVE ロックを取る時間そのものは一瞬で済みます (ロックの強さは同じ AccessExclusiveLock ですが、検証をスキップする分だけ短時間で終わります)。そのうえで、別のトランザクションで ALTER TABLE bugs VALIDATE CONSTRAINT ... を実行すると、既存行の検証自体は行われますが、このときに取られるロックは実際に ShareUpdateExclusiveLock でした。このロックは SELECT や INSERT/UPDATE/DELETE をブロックしない弱いロックです。

ALTER TABLE bugs ADD CONSTRAINT bugs_priority_check_notvalid
  CHECK (priority IN ('LOW','MEDIUM','HIGH','CRITICAL','BLOCKER')) NOT VALID;
-- 別のトランザクションで:
ALTER TABLE bugs VALIDATE CONSTRAINT bugs_priority_check_notvalid;
 relation |           mode
----------+--------------------------
 bugs     | ShareUpdateExclusiveLock

つまり、どうしても CHECK (IN ...) に近い書き方をやめられない事情があるとしても、NOT VALID と VALIDATE CONSTRAINT を分けるだけで、長時間の検証中に他のトランザクションを止めずに済みます。この手法は制約の追加に限った話であり、値の候補自体が増えたり並び順が変わったりする問題は解決しません。候補そのものの管理には、やはり 5 節の参照テーブルが向いています。

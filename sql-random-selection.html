ランダムセレクション ― ORDER BY random() の罠

ORDER BY random() LIMIT n は、欲しい行数がいくつであっても表全体を読んで並べ替える。50 万行の表では 66 ms かかった全件ソートを、用途に応じた 4 つの代替手段でどこまで削れるかを実機で確かめる

← SQL シリーズ目次へ

この回の前提: 第 01 回 アンチパターンとは何か (サンプル DB の構造)、第 13 回 インデックスショットガン (インデックスと EXPLAIN の読み方)

「おすすめ商品をランダムに 1 件見せたい」「QA 用にランダムな行を抽出したい」という要望に対して、多くの人が最初に書くのは ORDER BY random() LIMIT n です。結論を先に言うと、この書き方は表の行数に関係なく表全体を 1 回読んで並べ替えるため、表が大きくなるほど重くなる書き方です。この回では、その重さを実機の EXPLAIN で確認したうえで、用途別に使い分ける 4 つの代替手段 (TABLESAMPLE SYSTEM / BERNOULLI、tsm_system_rows、ID 範囲の乱数、OFFSET 乱数) を、それぞれの速さと偏りの実測つきで見ていきます。

1. 目的 ― 何をしたかったのか

「表の中からランダムに 1 件、あるいは数件を選びたい」という要望は、トップページのおすすめ表示、A/B テストの対象抽出、QA のための抜き取り確認など、様々な場面で出てきます。やりたいことは単純で、「全部の行が選ばれる確率を均等にしたい (あるいは、どの程度均等かを分かった上で選びたい)」ということです。

SQL にはそのための組み込み関数 random() があるため、最初に試すのは次の書き方になります。

SELECT product_id, product_name FROM big_products ORDER BY random() LIMIT 5;

意味は分かりやすく、結果も正しくランダムです。問題は「どうやってランダムにしているか」という実装の中身にあります。

2. アンチパターン ― 欲しい行数に関係なく全件を読んで並べ替える

50 万行の big_products 表で ORDER BY random() LIMIT 5 を実行し、実際の読み取り量を確認します。

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT product_id, product_name FROM big_products ORDER BY random() LIMIT 5;

 Limit  (cost=17739.82..17739.83 rows=5 width=30) (actual time=66.051..66.052 rows=5.00 loops=1)
   Buffers: shared hit=3188
   ->  Sort  (cost=17739.82..18989.82 rows=500000 width=30) (actual time=66.049..66.050 rows=5.00 loops=1)
         Sort Key: (random())
         Sort Method: top-N heapsort  Memory: 25kB
         Buffers: shared hit=3188
         ->  Seq Scan on big_products  (cost=0.00..9435.00 rows=500000 width=30) (actual time=0.032..30.583 rows=500000.00 loops=1)
               Buffers: shared hit=3185
 Execution Time: 66.069 ms

Seq Scan が rows=500000 と表示しているとおり、欲しいのはたった 5 行なのに表の全行 (50 万行、3185 ページ分) を読んでいます。各行に対して random() を 1 回呼んで並べ替えのキーを作り、その後ソートして先頭 5 件を選ぶという流れです。top-N heapsort によって、メモリ上に保持するのは上位 5 件分だけに抑えられていますが、それでも全行を読んで random() を呼ぶコストは避けられません。LIMIT の数を 5 から 1 に変えても、1000 に変えても、読む行数は変わらず 50 万行のままです。

図: LIMIT で絞っても、ソートキーを作るための全件読み取りは避けられない。

この問い合わせの重さは、表の行数が増えるほど線形に増えていきます。50 万行で 66 ms だったものが、500 万行になれば単純計算で 10 倍近い時間がかかるようになり、トップページのような頻繁に呼ばれる場所に置くと、表の成長と共に静かに重くなっていく問い合わせになります。

3. 見つけ方

この問い合わせはエラーにならず結果も正しいため、本番で性能が問題になるまで気づかれないことが多いアンチパターンです。見つけるには 2 つの方法があります。

1 つ目はコードの中を order by random() や ORDER BY RANDOM() で検索することです。大文字小文字を無視した正規表現 order\s+by\s+random\s*\(\s*\) で、アプリケーションのコードや保存済みの SQL ファイルを検索すれば、該当箇所を機械的に洗い出せます。

2 つ目は EXPLAIN の出力の中に Sort Key: (random()) という行が無いかを確認することです。この行が Seq Scan の上に乗っている場合、その問い合わせは表の全行を読んで並べ替えていることが確定します。pg_stat_statements (shared_preload_libraries が必要な拡張) が有効な環境では、正規化された問い合わせテキストに random() を含むものを集計し、呼び出し頻度と平均実行時間を一覧にすることで、優先して直すべき箇所を絞り込めます。

4. 使ってよい場合

ORDER BY random() がいつも悪いわけではありません。次のような場合は、わざわざ代替手段に切り替える必要はありません。

1 つ目は、表が小さく、呼び出し頻度も低い場合です。数百行から数千行程度の表であれば全件スキャンのコストはごく小さく、1 日に数回しか実行しないバッチ処理であれば、わざわざ複雑な代替手段を使う理由がありません。

2 つ目は、サンプリングではなく、完全に均等な抜き取りが要件として必要な場合です。この回で紹介する代替手段は速度と引き換えに何らかの偏りを持ちます。法律や社内規定で「全行が完全に同じ確率で選ばれることを保証する」ことが求められる抜き取り検査のような場面では、遅くても ORDER BY random() (または行単位でランダムに選ぶ TABLESAMPLE BERNOULLI) の方が安全な選択です。

5. 解決策 ― 用途に応じた 4 つの代替手段

5.1 TABLESAMPLE SYSTEM ― ページ単位で速いが隣接した行が固まる

TABLESAMPLE SYSTEM (割合) は、表をページ (ディスク上の 1 ブロック、既定 8KB) の単位でランダムに選び、選ばれたページの行をすべて返します。ページそのものを読むかどうかしか判定しないため、全件を読む必要がありません。

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT product_id, product_name FROM big_products TABLESAMPLE SYSTEM (1);

 Sample Scan on big_products  (cost=0.00..178.00 rows=5000 width=22) (actual time=0.005..0.396 rows=4867.00 loops=1)
   Sampling: system ('1'::real)
   Buffers: shared hit=31
 Execution Time: 0.539 ms

読み取りページ数はわずか 31 で、実行時間は 0.539 ms でした。ORDER BY random() の 66.069 ms と比べて 2 桁近く速く、1 % 指定でおよそ 4867 行 (50 万行の約 0.97 %) が選ばれています。ただし、速さの代償として「隣接する行がまとめて選ばれる」偏りがあります。割合を 0.1 % に下げて、選ばれた product_id を昇順に並べてみます。

SELECT product_id FROM big_products TABLESAMPLE SYSTEM (0.1) ORDER BY product_id LIMIT 40;

 379941
 379942
 379943
   ...(中略、379944〜379979 まで連番)...
 379980

40 件すべてが 379941 から 379980 まで連続した id でした。これは「ランダムな 40 件」ではなく「たまたま選ばれた 1 つのページに入っていた 40 件」です。同じ時期に挿入された行が同じページに収まりやすいテーブルでは、SYSTEM サンプリングの結果は時期的に偏ったサンプルになります。

図: SYSTEM サンプリングはページを選ぶだけなので、1 ページ分の行がまとめて (隣接したまま) 返る。

5.2 TABLESAMPLE BERNOULLI ― 行単位で偏りは小さいが全件を読む

TABLESAMPLE BERNOULLI (割合) は、行 1 件ごとに独立したコイン投げで採否を決めます。ページをまとめて取るか捨てるかではなく、1 行ずつ判定するため、SYSTEM のような隣接の偏りはありません。

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT product_id, product_name FROM big_products TABLESAMPLE BERNOULLI (1);

 Sample Scan on big_products  (cost=0.00..3235.00 rows=5000 width=22) (actual time=0.002..4.380 rows=5099.00 loops=1)
   Sampling: bernoulli ('1'::real)
   Buffers: shared hit=3185
 Execution Time: 4.526 ms

読み取りページ数は 3185 で、表全体のページ数とほぼ同じです。つまり BERNOULLI は ORDER BY random() と同じく全件を読みますが、読んだ後にソートをしない分、4.526 ms と ORDER BY random() の 66.069 ms より速く済みます。割合を 0.02 % にして結果の product_id を見ると、SYSTEM のときとは違い、値がばらばらに散らばっていることが分かります。

SELECT product_id FROM big_products TABLESAMPLE BERNOULLI (0.02) ORDER BY product_id LIMIT 20;

 1027, 1154, 3482, 6363, 11252, 24364, 25074, 26935, 28946, 30293, ...

BERNOULLI は SYSTEM より遅いものの、行の抜き取りに偏りが入らないという意味では ORDER BY random() に近い性質を持ちます。「数 % 程度を抜き取って統計を取りたいが、全件を読む時間は惜しくない」という場面に向いています。

5.3 tsm_system_rows ― 割合でなく行数そのものを指定する

TABLESAMPLE SYSTEM (割合) は割合から推定した行数しか保証しません (小さい表では 0 行になることもあります)。contrib 拡張の tsm_system_rows を有効にすると、SYSTEM_ROWS(行数) という指定で欲しい行数そのものを指定できます。

CREATE EXTENSION IF NOT EXISTS tsm_system_rows;
EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT product_id, product_name FROM big_products TABLESAMPLE SYSTEM_ROWS(5);

 Sample Scan on big_products  (cost=0.00..4.05 rows=5 width=22) (actual time=0.003..0.004 rows=5.00 loops=1)
   Sampling: system_rows ('5'::bigint)
   Buffers: shared hit=1
 Execution Time: 0.007 ms

 product_id
------------
     112099
     112100
     112101
     112102
     112103

読み取りはわずか 1 ページ、0.007 ms で、要求どおり正確に 5 行が返りました。ただし内部の仕組みは SYSTEM と同じくページ単位なので、結果を見ると分かるように、やはり隣接した 5 件 (112099 から 112103) が返っています。「行数を正確に指定したい」という問題は解決しますが、「隣接した行が固まる」という偏りの問題は解決しません。

5 (続き). ID 範囲の乱数と OFFSET 乱数

5.4 ID 範囲の乱数 ― インデックスで一気に絞れるが欠番に偏る

主キーが連番の数値であれば、「最小値から最大値の間の乱数を作り、その値以上で最小の行を 1 件取る」という方法が使えます。

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT product_id, product_name FROM big_products
WHERE product_id >= (SELECT floor(random() * (500000-1) + 1)::bigint)
ORDER BY product_id LIMIT 1;

 Limit  (cost=0.45..0.48 rows=1 width=22) (actual time=0.009..0.009 rows=1.00 loops=1)
   Buffers: shared hit=4
   ->  Index Scan using big_products_pkey on big_products (cost=0.42..5818.10 rows=166667 width=22) (actual time=0.009..0.009 rows=1.00 loops=1)
         Index Cond: (product_id >= (InitPlan 1).col1)
 Execution Time: 0.015 ms

主キーのインデックスを使った Index Scan になり、読み取りはわずか 4 バッファ、0.015 ms です。欠番 (削除された行) が無い間はほぼ均等に行が選ばれますが、削除によって id に欠番ができると、欠番の直後の行に選ばれる確率が集中します。これを確かめるため、product_id が 100001 から 200000 までの 10 万行 (全体の 20 %) を削除し、同じ方法で 2000 回乱数を引いてみます。

DELETE FROM big_products WHERE product_id > 100000 AND product_id <= 200000;

-- 2000 回引いた結果の着地点を数えて多い順に並べる
 picked_id | count
-----------+-------
    200001 |   373
     59449 |     2
     45438 |     2
     87544 |     2
    272780 |     2

2000 回のうち 373 回 (18.65 %) が product_id = 200001 (削除した範囲のすぐ後ろの行) に集中しました。削除した範囲は全体の 20 % (10 万 / 50 万) なので、ほぼその比率どおりに「欠番の直後の 1 行」へ乱数が吸い込まれていることが分かります。それ以外の行はそれぞれ 1〜2 回程度しか選ばれていません。退会したユーザーや削除された商品のように、欠番が生まれる現実のテーブルでこの方法を使うと、生き残った特定の行だけが不自然に多く選ばれ続けます。

図: 欠番の幅がそのまま、欠番直後の 1 行が選ばれる確率に上乗せされる。

5.5 OFFSET 乱数 ― 偏りは小さいが OFFSET の大きさがコストになる

行数を数え、0 からその行数未満までの乱数を OFFSET に渡して 1 行取る方法です。欠番があっても「存在する行の中から数えて何番目か」で選ぶため、ID 範囲の乱数のような欠番への集中は起きません。

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT product_id, product_name FROM big_products ORDER BY product_id OFFSET 250000 LIMIT 1;

 Limit  (cost=8092.42..8092.45 rows=1 width=22) (actual time=24.657..24.658 rows=1.00 loops=1)
   Buffers: shared hit=2279
   ->  Index Scan using big_products_pkey on big_products (cost=0.42..16184.42 rows=500000 width=22) (actual time=0.007..17.837 rows=250001.00 loops=1)
 Execution Time: 24.661 ms

欠番の偏りは避けられますが、OFFSET に渡した数だけインデックスをたどって読み飛ばす必要があるため、コストは OFFSET の値に比例します。50 万行の表で中央付近 (25 万) を指定すると 24.661 ms かかりました。OFFSET が 0 に近ければ速く、表の後半に近づくほど遅くなるという、乱数の値によって実行時間が大きくばらつく書き方でもあります。このコストの構造は、深いページ送りが遅くなる第 32 回のページネーションの問題と同じ根を持ちます。

方法50 万行での実測行単位の偏り向いている場面
ORDER BY random()66.069 ms無し (基準)小さい表、低頻度のバッチ
TABLESAMPLE SYSTEM0.539 ms (全件取得)隣接行が固まる大量サンプルの統計用途 (個々の偏りは問題にならない)
TABLESAMPLE BERNOULLI4.526 ms (全件取得)無し偏りを避けつつ数 % を抜き取りたい
tsm_system_rows0.007 ms隣接行が固まる正確な行数が必要、偏りは許容
ID 範囲の乱数0.015 ms欠番に集中削除が無い (または稀な) 表から 1 行
OFFSET 乱数0.015〜24.661 ms (OFFSET依存)小さい削除がある表から偏りを抑えて 1 行

6. PostgreSQL エンジンで考慮しておくこと

6.1 random() をサブクエリに包むと 1 回しか評価されない罠

複数件のランダムな値を一度に作ろうとして、random() を外側の行を参照しないスカラサブクエリに包むと、PostgreSQL は「外側の行に依存しない計算」と判断し、InitPlan として1 回だけ計算してキャッシュします。random() 自体は毎回違う値を返す VOLATILE な関数ですが、サブクエリとして括られた途端にこの最適化の対象になります。

-- 生の random(): 2000 行それぞれで評価される
SELECT count(DISTINCT r) FROM (SELECT random() AS r FROM generate_series(1,2000)) s;
 count
-------
  2000

-- サブクエリに包むと 1 回しか評価されない
SELECT count(DISTINCT r) FROM (SELECT (SELECT random()) AS r FROM generate_series(1,2000)) s;
 count
-------
     1

2000 行生成しても、サブクエリに包んだ方は全行が同じ乱数値になりました。前節の「ID 範囲の乱数」を使って複数件を一度に取ろうとする場合、このままではどの行も同じ乱数から計算された同じ id に集中してしまいます。回避するには、外側の行の値を式の中に実際に混ぜ込み、サブクエリを外側の行に相関させる必要があります (本文中の検証では + (g - g) のように常に 0 になる式を使って、外側の行番号 g への参照を作りました)。

図: 相関の無いサブクエリに包んだ random() は InitPlan として 1 回だけ評価され、全行で同じ値になる。

6.2 tsm_system_rows は contrib 拡張であること

SYSTEM_ROWS は PostgreSQL 本体にはビルトインされていない、tsm_system_rows という contrib 拡張が提供する機能です。使う前に CREATE EXTENSION tsm_system_rows; が必要で、権限を持つロールか、スーパーユーザーがデータベースごとに有効化しておく必要があります。

6.3 OFFSET 乱数は MVCC のスナップショットの中で数える

OFFSET 乱数の母数にする行数は、通常 count(*) で数えますが、この値は数えた瞬間のスナップショットに基づきます。行数を数えてから OFFSET を実行するまでの間に別のトランザクションが行を挿入・削除すると、数えた行数と実際の行数がわずかにずれ、OFFSET が本来より僅かに前後の行を指すことがあります。これは致命的な偏りにはなりませんが、常に完全に正確な母数ではないことは意識しておく必要があります。

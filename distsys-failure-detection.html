障害検知とゴシップ ― 「死んでいる」と「遅い」はどう見分けるか

ネットワークの外からは故障と遅延を区別できない。タイムアウトの長さと伝播の速さの調整が、検知の速さと誤検知の少なさのトレードオフを決める

この回の前提: 第 05 回 レプリケーション入門 (フォロワーの故障という考え方)、第 14 回 クォーラムと Dynamo 型レプリケーション (ゴシップでメンバーシップを管理する発想)

1 台のマシンなら、プロセスが死んだかどうかは OS が教えてくれます。分散システムではそうはいきません。相手から応答が返ってこないとき、相手が本当に死んでいるのか、ただネットワークが混雑して遅れているだけなのかを、外から直接確かめる方法は無いのです。この回では、ハートビート (一定間隔で送る生存確認) とタイムアウトの基本から、固定の閾値を使わない phi accrual 検出器、そして全ノードが総当たりで監視し合う無駄を避けるゴシッププロトコルと SWIM まで、「故障かもしれない」をどう判断に落とし込むかを見ていきます。

1. この回で解く問題 ― 「死んでいる」と「遅い」は外から同じに見える

結論を先に言うと、ネットワークの外側からは故障と遅延を区別できません。だから故障検知は「本当に死んでいるか」を確かめる作業ではなく、限られた観測から「故障とみなすか」を決める作業になります。

1 台のマシンの中でプロセスが落ちると、OS がそれを検知して終了コードを返してくれます。ところが別のマシン上のプロセスを見る場合、間に挟まるのはネットワークだけです。観測側に届く情報は「応答が来た」か「決めた時間内に応答が来ない」かの 2 択しかありません。

「応答が来ない」の裏には複数の原因がありえます。相手のプロセスが本当にクラッシュした、相手は生きているがパケットが途中で失われた、相手は生きているがガベージコレクションや CPU 飢餓で一時的に応答できない、などです。これらを観測側が外から直接見分ける手段は無いというのが、この回の出発点です。

故障検知器 (failure detector) の仕事は、この「区別できない」状況から実用的な判断 (故障とみなす/まだ生きているとみなす) を作り出すことです。判断を早めるほど誤検知 (false positive, 実際は生きているのに故障と判定すること) が増え、判断を遅めるほど検知が遅れて本当の故障を見逃す時間が延びます。この速さと正確さのトレードオフが、この回を通して繰り返し出てきます。

図: 「本当に故障」と「生きているが遅い」は、観測側には同じ「無応答」として届く。

2. 仕組み ― ハートビートとタイムアウトで故障を疑う

最も基本的な仕組みはハートビート (heartbeat, 心臓の鼓動のように一定間隔で送る生存確認) です。送り方には 2 種類あります。push 型は監視される側が「生きてます」を定期的に送り続ける方式、pull 型は監視する側が定期的に「生きてますか」と聞きに行く方式です。push 型は実装が単純で監視対象が増えても送信側の負荷は増えませんが、pull 型は聞く側がタイミングを制御できるので障害注入や負荷調整がしやすくなります。

受け取ったハートビートは「タイムアウト $T$ 秒 (あるいは $N$ 回連続) 届かなければ故障とみなす」という固定ルールで判定するのが最も単純な形です。$T$ を短くすれば検知は速くなりますが、ネットワークが少し混雑しただけでも故障と誤判定する偽陽性 (false positive) が増えます。$T$ を長くすれば偽陽性は減りますが、本当に故障してから検知するまでの時間が延びます。この調整には「正解」が無く、サービスが許容できる誤検知の代償と検知遅延の代償を比べて決めるしかありません。

SDFC の health-check-endpoint の議論では、この仕組みを大規模に運用したときの別の問題が出てきます。ロードバランサやオーケストレータがインスタンスの数だけヘルスチェックを送ると、インスタンス数が増えるほどチェック自体がサービスへの負荷になります。対策として、個々の監視者が直接チェックに行くのではなく、チェック結果を集約してキャッシュする集中型の watchdog サービスを挟む、あるいはチェックの頻度にレート制限をかける、といった設計が議論されています。

図: push 型ハートビートは一定間隔で届き、タイムアウト T を超えた空白が故障判定の起点になる。

最小構成の push 型ハートビートは UDP ソケットだけで作れます。送信側は一定間隔で短いパケットを送り続け、受信側はソケットのタイムアウトを使って「次のパケットが来るまで待てる上限」を決めます。

import socket
import time

def run_server(host, port, timeout_seconds):
    sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    sock.bind((host, port))
    sock.settimeout(timeout_seconds)
    alive = True
    while True:
        try:
            data, addr = sock.recvfrom(64)
            if not alive:
                print("recovered:", addr)
            alive = True
        except socket.timeout:
            if alive:
                print("suspected dead: no heartbeat for", timeout_seconds, "seconds")
            alive = False

def run_client(host, port, interval_seconds):
    sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    while True:
        sock.sendto(b"ping", (host, port))
        time.sleep(interval_seconds)

3. 仕組み ― 固定の閾値を捨てる: phi accrual 失敗検出器

固定タイムアウトには弱点があります。ネットワークの遅延のばらつきは時間帯や経路で変わるのに、1 つの $T$ を決め打ちすると、ばらつきが大きい環境では誤検知が多発するか、逆に検知が遅すぎるかのどちらかに振れてしまいます。

phi accrual 失敗検出器は、二値の「生きてる/死んでる」判定を、連続値の「疑わしさ」に置き換える考え方です。直近のハートビートの到着間隔を履歴として記録し、その分布から「最後に届いてからの経過時間が、過去の傾向に対してどれくらい異常か」を $\phi$ (phi) という値で表します。$\phi$ が大きいほど「もう届いているはずの時間をかなり過ぎている」ことを意味し、上位のアプリケーションは自分の用途に応じた閾値 (例えば $\phi > 8$ なら故障とみなす、など) を選べます。固定の $T$ を 1 つだけ決めるのではなく、環境ごとのばらつきを自動的に取り込める点がこの仕組みの利点です。

図: phi accrual は固定の閾値ではなく、過去の到着間隔の分布に対する「今の空白の異常さ」を連続値で返す。

4. 仕組み ― 全対全を避ける: ゴシップと SWIM

ノード数が $N$ のクラスタで、全ノードが全ノードを直接ハートビートで監視すると、通信量は $N^2$ に比例して増えます。数百台を超えるクラスタでは、これだけで無視できない負荷になります。

ゴシップ (gossip, 噂話) プロトコルは、この総当たりを避けます。各ノードは自分が知っている最新のメンバーシップ情報 (誰が生きているか) を、毎ラウンド少数のランダに選んだ相手にだけ伝えます。伝えられた相手はさらに次のラウンドで別の少数に伝える、というように、知っている人数がラウンドごとに倍増していくため、情報はおよそ $\log N$ ラウンドでクラスタ全体に伝わります。これは噂が口コミで広がる速さと同じ仕組みです。

SWIM (Scalable Weakly-consistent Infection-style process group Membership protocol) は、このゴシップにさらに工夫を加えたプロトコルです。あるノード A が別のノード B に直接 ping を送って応答が無いとき、A はすぐに故障と決めつけません。代わりに、ランダムに選んだ他の数台のノードに「B に ping してほしい」と頼む間接 ping を行います。間接 ping も失敗した場合、B を「疑わしい (suspect)」状態としてゴシップで広め、一定時間内に誰からも B の生存報告が無ければ「確定故障 (confirm)」に進めます。この疑い状態を経由する段階があることで、一時的な遅延だけで故障と確定してしまう前に訂正の機会が生まれます。

図: ゴシップは各ラウンドでランダムな相手に伝え、知っている人数が倍増していくことで短時間で全体に伝わる。

5. どこで壊れるか ― 偽陽性とグレー障害

ここまでの仕組みはすべて、タイムアウトを短くするほど検知が速くなり偽陽性 (false positive) が増え、長くするほど偽陽性は減るが検知が遅れる、という同じトレードオフの上に立っています。偽陽性が増えると、まだ生きているノードを故障と誤判定して不要なフェイルオーバーを起こしたり、クォーラムを失って不必要にスプリットブレイン (第 26 回で詳しく扱う分裂状態) に近づいたりします。

SDFC の online-presence-indicator の議論はこのトレードオフの身近な例です。チャットアプリのオンライン表示はハートビート (多くは pub/sub 経由) の有無に依存しますが、「オフライン」と表示するまでの待ち時間を短くすると、一瞬の電波不良でも「オフライン → オンライン」のちらつきが頻発します。逆に待ち時間を長くすると、本当に接続が切れた後もしばらく「オンライン」と表示され続けます。どちらの値を選んでも、どちらかの不満は残ります。

さらに厄介なのはグレー障害 (gray failure) です。これはノード全体が死ぬのではなく、一部の機能だけが遅い、あるいは一部のリクエストだけが失敗する状態を指します。監視システム (ヘルスチェックのような軽い自己診断) は「健全」と報告しているのに、実際のクライアントは遅延やエラーに苦しんでいる、という観測者と被害者のズレが起きやすいのが特徴です。ハートビートという仕組み自体は「相手が完全に止まっているか」を見るのには向いていますが、「相手の一部だけが調子が悪い」状態の検知には弱いという限界があります。この種の障害は第 36 回のメタ安定障害・グレー障害・テールレイテンシでさらに深く掘り下げます。

図: T を短くすれば偽陽性が増え、長くすれば検知が遅れる。両方を同時に減らすことはできない。

6. 実システムでの例

Kubernetes の liveness / readiness probe は、ここで見たハートビート (pull 型) とタイムアウトの考え方をそのまま運用の仕組みに落とし込んだものです。チェックの間隔と、何回連続で失敗したら不健全とみなすかを運用者が設定でき、それがそのまま検知の速さと偽陽性の少なさのトレードオフの調整つまみになります。

SWIM のようなゴシップ型のメンバーシッププロトコルは、HashiCorp 社の Serf や Consul など、大規模なノード集合のメンバーシップ管理が必要な実装で使われている考え方です。全対全のハートビートでは通信量が破綻する規模のクラスタで、ゴシップによる伝播はスケールする選択肢になります。

SDFC の health-check-endpoint では、個々のサービスが直接ヘルスチェックに応答する単純な設計から出発し、チェックの量自体がサービスへの負荷になる問題に対して、チェック結果を集約してキャッシュする集中型の watchdog サービスへと発展させる議論がされていました。これは「誰が誰を監視するか」というハートビートの経路そのものを設計対象にする必要があることを示しています。

まとめると、故障検知は「正解を知る」仕組みではなく、「限られた観測から実用的な判断を作る」仕組みです。タイムアウトの長さ、ゴシップの伝播範囲、間接 ping の有無は、すべて検知の速さと誤検知の少なさを取引するためのつまみだと捉えると、個々の設計判断の理由が見えてきます。

分岐・ジャンプ・スキップ・サブルーチン ― if.xx で次の一命令を飛ばす

rj32 には「条件分岐」命令が存在しない。あるのは「次の 1 命令を飛ばすかどうかを決める」命令と「無条件に跳ぶ」命令の組み合わせだけである

この回の前提: 第 10 回 命令セットの設計、第 12 回 データパスを 1 命令ずつ追う

CPU は何もしなければプログラムカウンタ (PC, 次に実行する命令のアドレスを持つ部品) を 1 ずつ増やして命令を順番に読むだけの機械です。if 文やループ、関数呼び出しを実現するには、この「PC を 1 増やす」という既定の動きをどこかで書き換える仕組みが必要になります。rj32 はこれを「条件に応じて次の 1 命令を無視する (スキップする) 命令」と「PC を直接書き換える命令 (ジャンプ・コール)」という 2 種類の命令の組み合わせだけで実現しています。多くの教科書が最初に説明する「条件と飛び先を 1 つの命令に詰め込む分岐命令」は、rj32 には存在しません。

1. PC の次をどう決めるか

クロックが 1 つ進むたびに、CPU は次に実行する命令のアドレスを 1 つ決めます。何もしなければ既定の動きは「PC に 1 を足す」だけです。rj32 ではこの既定の動きを、3 つの方法だけで上書きできます。スキップ (次の 1 命令だけを無効化する。PC 自体は変わらず普通に +1 される)、ジャンプ (PC にまったく別のアドレスを入れる)、コール (ジャンプと同時に、戻ってくるためのアドレスをレジスタに保存する) の 3 つです。条件を見て飛び先を変える「条件分岐」という独立した仕組みは無く、スキップとジャンプを組み合わせて作ります。

図: rj32 で PC の既定動作 (+1) を上書きする 3 つの方法。条件分岐という独立した命令種別は存在しない。

2. 「比較して次を飛ばす」という条件分岐の作り方

多くの教科書は、条件分岐命令を「比較の条件と飛び先アドレスを 1 つの命令に詰め込んだもの」として説明します。rj32 の instructions.md が定義する if.eq ・ if.ne ・ if.lt ・ if.ge ・ if.ult ・ if.uge の 6 命令は、条件を見るところまでしか行いません。たとえば if.lt rd, rs の動作は「S ← !(rd < rs)」、つまり条件を満たさなかったときに S (スキップフラグ) を立てるという意味です。S が立っていると、次の 1 命令はまるごと無視され、何もしない命令 (nop) として 1 クロックだけ消費されます。

したがって「rd が rs より小さいときだけ target へ跳ぶ」という条件分岐は、rj32 では次の 2 命令の組にして書きます。

if.lt rd, rs   ; rd < rs なら S=0 (スキップしない)
jump  target   ; rd < rs のときだけ実行される。rd >= rs なら S=1 でスキップされる

命令名と条件の向きはそのまま素直に対応します。「rd が rs より小さいときに跳びたい」なら if.lt をそのまま使えばよく、条件をひっくり返す必要はありません。間違えやすいのはむしろ逆で、「スキップする」という言葉の響きから「条件が成立したときにスキップする」と思い込んでしまうことです。実際は 条件が成立したときはスキップされず、次の命令がそのまま実行されるのであって、スキップが起きるのは条件が成立しなかったときです。then 節と else 節の両方を持つ分岐を作るときは、どちらを「素直に jump で跳ぶ側」にしてどちらを「その場に居残る側」にするかで、同じ条件をそのまま使うか、反対の条件 (if.lt の反対は if.ge) を使うかが決まります。

図: 条件判定 (if.xx) と制御の移動 (jump) が 2 つの命令に分かれているのが rj32 の特徴。

条件が成立する場合と成立しない場合で、クロックごとに何が確定するかを並べると違いがはっきりします。S フラグは if.eq の結果を受けて次のクロックの頭で確定し、そのクロックの間だけ次の命令の実行を無効にします。

図: S フラグは if.eq のクロックの間に確定し、次のクロックで jump を実行するか無効化するかを決める。

3. ジャンプ・サブルーチン呼び出し・戻り

jump には 2 つの形があります。レジスタ版 jump rd は PC ← rd で絶対アドレスへ跳び、即値版 jump imm11 は PC ← PC + imm11 で現在位置からの相対アドレスへ跳びます。どちらも無条件です。call はこの 2 つの跳び方に加えて、戻ってくるためのアドレス (呼び出した命令の次の番地、PC + 1) を r0 レジスタへ保存します。

rj32 の 16 本のレジスタ (r0〜r15) のうち、ハードウェアとして特別な役割を持つのは r0 だけです。呼び出し規約上の別名は ra (return address) で、call が戻り先をここに置くことと対応しています。サブルーチンから戻る return という命令は実在せず、jump r0 と等価な疑似命令として用意されています。「跳ぶ」命令を再利用して「戻る」を表現している点が、専用の return 命令を持つ ISA との違いです。

図: call が戻り先を r0 (ra) に残し、本体の最後の jump r0 がそこへ跳んで戻る。

4. スタックは回路ではなく「約束」でできている

rj32 の 32 命令には push や pop という専用命令がありません。r15 を sp (stack pointer) として使うのも、r14 を bp (data base pointer) として使うのも、instructions.md が定める呼び出し規約という約束であって、ハードウェアが r15 を特別扱いしているわけではありません。スタックへの積み下ろしは、既にある add ・ sub ・ store ・ load の組み合わせで自分で作ります。

sub   sp, 2          ; スタックを 1 ワード分 (2 バイト) 伸ばす
store [sp, 0], r3     ; 呼び出し先で使う r3 (callee saved) を退避
...
load  r3, [sp, 0]     ; 使い終わったら元に戻す
add   sp, 2           ; スタックを縮める

この約束が必要になる最大の理由は、r0 が戻り先を 1 つしか保持できないことです。サブルーチンの中でさらに別のサブルーチンを call すると、新しい戻り先が r0 に上書きされ、最初の戻り先が消えてしまいます。だからネストした呼び出しをする関数は、自分が呼ばれた直後に r0 をスタックへ退避し、戻る直前に読み戻す、という手順を自分のコードに書く必要があります。レジスタ表にある「呼び出し元で退避する (caller saved)」「呼び出され側で退避する (callee saved)」という区別も、この手作りのスタック操作をどちらの責任にするかという約束です。

図: push/pop 命令は無いので、sub でスタックを伸ばし store/load で値を置くという手順をコード側が自分で書く。

5. 実装のポイント

なぜ比較と飛び先を 1 命令に詰め込まなかったか。 rj32 の命令はすべて 16 ビット固定長です。算術命令と同じ ri6 形式 (rd 4 ビット + imm6 6 ビット + op 4 ビット + fmt 2 ビット、合計 16 ビット) を使う if.xx は、比較用のレジスタ指定と小さな即値だけで桁を使い切ります。もし条件判定と飛び先の両方を 1 命令に詰めようとすると、レジスタ指定の分だけ飛び先の即値に回せる桁が削られ、近くにしか跳べない分岐になってしまいます。2 命令に分けることで、jump 側は imm11 という専用の 11 ビット をまるごと飛び先に使え、if.xx 側は add や sub と同じ比較器をそのまま再利用できます (比較器の再利用は第 7 回の ALU の話とつながります)。

図: 16 ビット固定長の中で比較と飛び先の両方を 1 命令に詰めると、どちらかの桁が削られる。

スキップは「当たっても外れても 1 クロック」。 instructions.md は「スキップされる命令は 1 クロックを消費する (nop と同じ扱い)」と明記しています。つまり if.xx 自体の 1 クロックに加えて、次の命令のために必ずもう 1 クロックが使われます。条件が成立して jump が実際に実行される場合も、成立せずに無視される場合も、消費するクロック数は同じです。教科書の分岐予測の話で出てくる「分岐しなければ得をする」という前提は、rj32 のスキップ方式には当てはまりません。

接頭命令を巻き込む。 imm ・ addc ・ subc は次の 1 命令に状態を渡す接頭命令です (第 14 回で詳しく扱います)。スキップされる対象がこの接頭命令で始まっていた場合、instructions.md は「接頭命令とその次の本体の命令の両方がスキップされる」と定めています。もし実装が単純に「次の 1 ワードだけを無視する」と作ってしまうと、接頭命令だけがスキップされて本体の命令がそのまま実行されてしまい、想定外の値で実行されるという欠陥になります。「1 命令をスキップする」のつもりが「1 ワードをスキップする」になっていないか、という点が実装時に取り違えやすい箇所です。また、スキップ中は割り込みも無効化されており、比較から着地までの間に CPU の状態が割り込みで割り込まれて中途半端になることを防いでいます。

仕様書自身が認める未完成の箇所。 instructions.md には jump について「レジスタへのジャンプは現在オペコード 4 になっており、修正が必要」、call について「レジスタ呼び出しは現在動作しない」という注記があります。これは実装の粗探しではなく、仕様書が自分の未完成部分を隠さずに書いているという良い例です。自作 CPU を進めるときも、動いていない組み合わせを「後で直す」とコードに埋めるのではなく、ドキュメントに注記として残しておくと、後で自分や他の人が同じ落とし穴にはまりません。

6. ジャンプは常に 1 クロックの穴を開ける

第 15 回で見るように、rj32 は命令を読み出す段と実行する段がずれて動いています。jump や call が実行されるとき、実行段がまだ飛び先を計算している間に、読み出し段はすでに「跳ばなかった場合の次の番地」の命令を読み進めてしまっています。この読み間違えた 1 命令をどう処理するかは第 16 回のハザードの主題です。ここで覚えておきたいのは、rj32 には分岐予測 (飛ぶかどうかを事前に当てる仕組み) が無く、ジャンプは常に 1 クロックの穴を作るという点です。現代の CPU は、この穴をできるだけ埋めようとして分岐予測や投機実行に多くの回路を使っていますが (第 24 回)、rj32 の時点では「穴が開くことを受け入れて、毎回同じだけ待つ」という最も単純な選択をしています。

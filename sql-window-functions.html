ウィンドウ関数で集合として考える ― 1 行ずつのループを手放す

自己結合や相関サブクエリで「前の行」や「同じグループの中での順位」を求めるコードは、行数が増えるほど遅くなり、フレームの既定値を誤解すると答えまで変わります。結論を先に言うと、PARTITION BY と ORDER BY で「どの行の集まりの中で、どの順番で」を宣言し、フレーム (ROWS/RANGE/GROUPS) で「その中のどこからどこまでを見るか」を宣言すれば、1 回のスキャンで同じ答えを安全に、しかも速く出せます。

この回の前提: 第 15 回 アンビギュアスグループ (DISTINCT ON や window 関数を使った「各グループの代表行」の取り方) ・ 第 28 回 実行計画を読む (EXPLAIN (ANALYZE, BUFFERS) の読み方)

この回で答えるのは「同じグループの中で順位を付けたい」「前の行や次の行の値を見たい」「累計や移動平均を出したい」というときに、自己結合やサブクエリで 1 行ずつ処理するコードを書いてしまう問題です。結論は、ウィンドウ関数は行をまとめてしまう GROUP BY とは違い、行を 1 行ずつ残したまま、各行に対して「その行から見える範囲 (フレーム)」の集計値をくっつける仕組みだということです。この範囲の決め方を PostgreSQL 18 の実際の実行結果で確認します。

1. この回で解く問題 ― 行をまとめずに「周りの行」を見たい

GROUP BY は「同じキーの行をまとめて 1 行にする」操作です。しかし実務では「行はまとめたくないが、同じグループの中での順位や、前の行との差や、ここまでの累計は知りたい」という要求がよく出てきます。たとえばバグ管理のサンプル DB (accounts, bugs) で、「担当者ごとに、報告日順に累計の作業時間 (hours) を出したい」「同じ担当者の前回の報告から何日空いたかを知りたい」といった要求です。

こうした要求を SQL に慣れていない人が書くと、しばしば「同じ担当者で、報告日がこの行以下のものを数える」という相関サブクエリや、自分自身との JOIN (自己結合) になります。これは行ごとに「その行から見て過去の行をもう一度スキャンする」処理になるため、行数が増えるほど遅くなります。ウィンドウ関数はこの「行ごとに周りを見る」という操作を、1 回のソートと 1 回のスキャンで済ませる仕組みです。

図: 自己結合は行ごとに過去を再スキャンする (右肩上がりに重くなる)。ウィンドウ関数はソート済みの列をなぞる 1 回の通過で済む。

2. 仕組み ― PARTITION BY と ORDER BY で「どの集合の中の何番目か」を宣言する

ウィンドウ関数は 関数名(...) OVER (PARTITION BY ... ORDER BY ...) の形で書きます。PARTITION BY は「どの行の集まりの中で計算するか」を決めます。何も指定しなければテーブル全体が 1 つの集合になり、PARTITION BY reported_by と書けば「同じ担当者の行だけの集合」になります。これは GROUP BY の「まとめる単位」と同じ考え方ですが、行は 1 行にまとまらず、元の行数のまま残ります。

ORDER BY は「その集合の中で、どの順番に行を並べて処理するか」を決めます。順番が決まることで初めて「前の行」「ここまでの累計」「何番目か」が意味を持ちます。担当者 1 (alice) の作業時間 (hours) を報告日順に累計した実行結果です。

SELECT bug_id, reported_by, date_reported, hours,
       SUM(hours) OVER (PARTITION BY reported_by ORDER BY date_reported, bug_id
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_rows
FROM bugs WHERE reported_by = 1 AND hours IS NOT NULL ORDER BY date_reported, bug_id;

bug_id 6, 7, 10, 11, ... の 8 行はまとめられず、そのまま 8 行として残っています。各行には「その行を含めてそこまでの合計」がくっついているだけです。これが「集合として考える」という意味で、GROUP BY のように情報を失わずに集計値を得られます。

図: PARTITION BY が行をレーンに分け、ORDER BY がレーンの中の順番を決める。行はまとめられず残る。

3. 仕組み ― フレーム (ROWS/RANGE/GROUPS) と既定値の罠

ORDER BY で順番が決まっても、「その行から見て、どこからどこまでを集計するか」はまだ決まっていません。この範囲をフレームと呼び、ROWS BETWEEN ... AND ... のように書きます。PostgreSQL の公式ドキュメントによれば、フレームの指定を省略すると、ORDER BY がある場合は RANGE UNBOUNDED PRECEDING AND CURRENT ROW が既定値になり、ORDER BY が無い場合はパーティション全体が既定値になります。この既定値の違いに気づかず書くと、2 つの罠にはまります。

罠 1: ORDER BY の有無でフレームの意味が変わる

担当者 3 (carol) の 3 件の作業時間に対して、ORDER BY を付けた SUM と付けない SUM を同時に実行した結果です。

SELECT reported_by, bug_id, hours,
       SUM(hours) OVER (PARTITION BY reported_by) AS total_no_order,
       SUM(hours) OVER (PARTITION BY reported_by ORDER BY date_reported, bug_id) AS running_with_order
FROM bugs WHERE reported_by = 3 AND hours IS NOT NULL ORDER BY bug_id;
bug_idhourstotal_no_orderrunning_with_order

ORDER BY を付けない total_no_order は 3 行とも同じ 1.35 (パーティション全体の合計) です。ORDER BY を付けた running_with_order は行ごとに違う値になり、最後の行でようやく全体の合計 1.35 と一致します。「累計を出したいのに全部の行が同じ値になる」という不具合のほとんどは、この既定値の切り替わりに気づいていないことが原因です。

罠 2: ORDER BY の値が同じ (タイ) 行があると ROWS と RANGE の答えが変わる

担当者 1 の 2026-01-20 には 2 件の報告 (bug_id 10 と 11) があり、どちらも同じ日付です。ROWS は「物理的に何行目までか」で数え、RANGE は「ORDER BY の値が同じ行 (ピア) をまとめて同じ枠に入れる」という違いがあります。

SUM(hours) OVER (... ORDER BY date_reported, bug_id ROWS  BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_rows,
SUM(hours) OVER (... ORDER BY date_reported        RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cum_range
bug_iddate_reportedhourscum_rowscum_range
102026-01-206.009.5010.50
112026-01-201.0010.5010.50

ROWS に ORDER BY date_reported, bug_id のように 一意になるまで並べ替えキーを追加しておけば、どちらが先かが一意に決まり、9.50 → 10.50 という素直な積み上げになります。一方 RANGE は ORDER BY date_reported だけ (タイが残る) でも、同じ日付の 2 行を 1 つのピア集合として扱い、両方の行に同じ合計 10.50 を返します。「同じ日の最後の 1 件だけ合計が増える」という挙動を期待して RANGE を使うと、タイがある限り全員同じ値になるので意図と食い違います。逆に「同率の行は同じ累計でよい」という意味ならこれは正しい挙動です。どちらを使うかは、タイをどう扱いたいかという要件そのものです。

図: ROWS はタイがあっても 1 行ずつ進むが、ORDER BY に一意なキーが無いと順序は不定。RANGE は同じ値の行をまとめて同じ枠に入れる。

罠 3: GROUPS は「行数」ではなく「ピア集合の数」で区切る

GROUPS は ROWS と RANGE のどちらとも違う、3 番目のフレーム単位です。PostgreSQL の公式ドキュメントによれば、GROUPS モードのオフセットは「現在行のピア集合 (ORDER BY の値が同じ行の集まり) から、指定した数だけ前または後ろのピア集合」を意味します。ROWS は物理的な行数で数え、RANGE は ORDER BY の値そのものの範囲 (数値の差など) で数えますが、GROUPS は「タイのある行をまとめて 1 単位」として、その単位の個数で数えます。担当者 1 の作業時間に対して、ROWS BETWEEN 1 PRECEDING AND CURRENT ROW と GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW を同時に計算した実行結果です。

SELECT bug_id, date_reported, hours,
       SUM(hours) OVER (PARTITION BY reported_by ORDER BY date_reported
             ROWS BETWEEN 1 PRECEDING AND CURRENT ROW) AS rows_1prec,
       SUM(hours) OVER (PARTITION BY reported_by ORDER BY date_reported
             GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW) AS groups_1prec
FROM bugs WHERE reported_by = 1 AND hours IS NOT NULL ORDER BY date_reported, bug_id;

bug_id 10 (2026-01-20) を見ると、rows_1prec は「直前の 1 行 (bug_id 7) + 自分」で 1.50+6.00=7.50 です。これは bug_id 11 が同じ日付でも物理的にまだ後ろの行なので数えません。groups_1prec は「直前の 1 ピア集合 (2026-01-07 の 1 行) + 自分のピア集合 (2026-01-20 の 2 行、bug_id 10 と 11 の両方)」をまとめて数えるので 1.50+6.00+1.00=8.50 になり、同じ日付の bug_id 11 の方にも同じ 8.50 が付きます。さらに bug_id 12 (2026-01-21) では、groups_1prec の「直前の 1 ピア集合」は 2026-01-20 の 2 行 (6.00 と 1.00) になるので、6.00+1.00+4.00=11.00 と、同じ日に複数行あっても 1 グループとしてまとめて数えます。「直前の N 回の報告」ではなく「直前の N 回の報告日」を数えたい (同じ日にまとめて報告された分は 1 回分として数える) ときに、GROUPS が本来の出番です。

4. 仕組み ― 順位系関数と LAG/LEAD

フレームを使わずに、行の順序だけから値を取る関数もあります。代表的なのが順位を付ける 3 つの関数と、前後の行の値を取る LAG/LEAD です。各担当者が報告したバグの件数で順位を付けた実行結果です (carol と dave はどちらも 3 件で同数)。

SELECT a.account_name, COUNT(*) AS n,
       ROW_NUMBER() OVER (ORDER BY COUNT(*) DESC, a.account_name) AS rn,
       RANK()       OVER (ORDER BY COUNT(*) DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY COUNT(*) DESC) AS drnk
FROM bugs b JOIN accounts a ON a.account_id = b.reported_by
GROUP BY a.account_name ORDER BY n DESC, a.account_name;

carol と dave の件数は同じ 3 件ですが、3 つの関数は同率の扱いが違います。ROW_NUMBER は同率でも必ず連番 (3, 4) を付けるので、重複が無い代わりに「同率なのに順位が違う」ように見えます。RANK は同率に同じ順位 (3, 3) を付けますが、次の順位は 1 つ飛んで 5 にはならず、ここでは 2 人しかいないので表には出ていませんが、3 位が 2 人いれば次は 5 位になります。DENSE_RANK も同率に同じ順位を付けますが、次の順位は詰めて 4 になり、順位の欠番を作りません。「上位 3 名を表示したい」というとき、同率が 2 人いる境界で RANK を使うと 4 位が消え、ROW_NUMBER を使うと同率の 1 人が切り落とされるので、要件に応じて選ぶ必要があります。

LAG は「1 つ前の行の値」、LEAD は「1 つ後の行の値」を、自己結合をせずに直接取れます。担当者 1 の報告日の間隔を調べた実行結果です。

SELECT reported_by, bug_id, date_reported,
       date_reported - LAG(date_reported) OVER (PARTITION BY reported_by ORDER BY date_reported, bug_id) AS days_since_prev
FROM bugs WHERE reported_by = 1 ORDER BY date_reported, bug_id;

図: 同率をどう扱うかで 3 つの関数の答えが分かれる。「上位 N 名」の境界で同率があると結果が変わる。

5. 仕組み ― gaps-and-islands と FILTER 句

gaps-and-islands (隙間と島) は、連続した値や日付の集まりを「島」としてグループ化する古典的な問題です。たとえば「担当者ごとに、7 日以上間隔が空いたら新しい活動期間 (島) とみなして集計したい」という要件です。これは LAG で前の行との差を取り、その差が閾値を超えた行に「新しい島の開始」フラグを立て、そのフラグを SUM で累積すれば、フラグが立つたびに 1 つ増える「島の番号」になります。

WITH marked AS (
  SELECT reported_by, bug_id, date_reported,
         date_reported - LAG(date_reported) OVER (PARTITION BY reported_by ORDER BY date_reported, bug_id) AS gap
  FROM bugs
), flagged AS (
  SELECT *, CASE WHEN gap IS NULL OR gap > 7 THEN 1 ELSE 0 END AS new_island
  FROM marked
), islands AS (
  SELECT *, SUM(new_island) OVER (PARTITION BY reported_by ORDER BY date_reported, bug_id) AS island_id
  FROM flagged
)
SELECT reported_by, island_id, MIN(date_reported) island_start, MAX(date_reported) island_end, COUNT(*) bugs_in_island
FROM islands GROUP BY reported_by, island_id ORDER BY reported_by, island_id;

これは WHERE で絞り込んでいない全件の結果 (7 行) です。担当者 1 の報告は 1/5〜1/7、1/20〜1/21、2/14〜2/16 の 3 つの島に分かれています。1/7 から 1/20 までは 13 日空いているので新しい島になり、1/21 から 2/14 までは 24 日空いているのでまた新しい島になります。担当者 3 と 4 はそれぞれ報告が 1 つの島にまとまっています (間隔が 7 日を超えていないため)。SUM の累積という同じ仕組みが、累計の計算にも島の番号付けにも使えることが分かります。

FILTER 句 は集約関数に条件を付けて、1 回の GROUP BY で複数の条件別集計を 1 行にまとめられる書き方です。

SELECT a.account_name, COUNT(*) AS total,
       COUNT(*) FILTER (WHERE b.status = 'FIXED')       AS fixed,
       COUNT(*) FILTER (WHERE b.status = 'IN PROGRESS') AS in_progress
FROM bugs b JOIN accounts a ON a.account_id = b.reported_by
GROUP BY a.account_name ORDER BY a.account_name;

6. どこで壊れるか ― よくある間違い

間違い 1: 「前の行の値」を相関サブクエリや自己結合で取る

センサーの測定値を 30 万行 (readings テーブル、50 個のセンサーに均等に分散) 用意し、1 つのセンサー分 6,000 行に対して「直前の測定値」を 2 つの書き方で取りました。1 つは相関サブクエリ (自己結合と同じ性質)、もう 1 つは LAG です。

-- 相関サブクエリ: 行ごとに過去を再スキャンする
SELECT cur.sensor_id, cur.ts, cur.value,
       (SELECT prev.value FROM readings prev
        WHERE prev.sensor_id = cur.sensor_id AND prev.ts < cur.ts
        ORDER BY prev.ts DESC LIMIT 1) AS prev_value
FROM readings cur WHERE cur.sensor_id = 1;

-- LAG: 1 回のソートで済む
SELECT sensor_id, ts, value, LAG(value) OVER (PARTITION BY sensor_id ORDER BY ts) AS prev_value
FROM readings WHERE sensor_id = 1;

EXPLAIN (ANALYZE, BUFFERS) で比較すると、相関サブクエリは外側 6,000 行それぞれに対して内側の Index Scan Backward を 1 回ずつ (loops=6000) 実行し、読んだバッファ数は約 25,900 ブロックでした。LAG を使った方は 1 回のソートと 1 回のスキャンで済み、読んだバッファ数は約 1,950 ブロックでした。同じ 6,000 行に対してバッファの読み取り数で約 13 倍の差になり、実行時間も複数回の実行でおおよそ 20〜36 ms 対 3〜4 ms (約 7〜10 倍) でした (ウォームキャッシュ、同一マシンでの複数回実行)。行数を増やすほど相関サブクエリ側は loops の回数も増えるので、差はさらに開きます。

間違い 2: ウィンドウ関数の結果を WHERE 句でそのまま絞り込む

SELECT sensor_id, ts, value, RANK() OVER (PARTITION BY sensor_id ORDER BY value DESC) AS rnk
FROM readings
WHERE rnk = 1;
-- ERROR:  column "rnk" does not exist

これは実際に PostgreSQL 18 で出たエラーです。WHERE は行を絞り込んだ後に集約や GROUP BY が走り、ウィンドウ関数はさらにその後に計算されるという実行順序 (FROM → WHERE → GROUP BY → HAVING → ウィンドウ関数 → SELECT → ORDER BY) のため、WHERE の時点ではまだ rnk という列は存在しません。ウィンドウ関数の結果で絞り込みたい場合は、サブクエリか CTE に包んで外側で絞り込みます (WITH ranked AS (...) SELECT * FROM ranked WHERE rnk = 1)。CTE の使い分けは次回の第 30 回で扱います。

間違い 3: フレームの既定値を知らずに累計がパーティション全体になる

節 3 で見たとおり、ORDER BY を書き忘れると (あるいは書いたつもりで打ち間違えると) フレームがパーティション全体に変わり、「累計」のつもりの列が全行同じ値 (合計) になります。レビューでウィンドウ関数を見たら、まず OVER (...) の中に ORDER BY があるか、フレームが ROWS か RANGE かを確認する価値があります。

図: 相関サブクエリは行ごとに過去を再スキャンするため読み取りバッファ数が大きい。LAG は 1 回の通過で済む。

7. シニアの書き方 ― 判断の基準

「行をまとめずに、周りの行の値や順位が欲しい」と思ったら、まず自己結合や相関サブクエリを書く前にウィンドウ関数で書けないかを考えます。目安は次の 3 つです。

1. 「集合の中の何番目か」を聞かれたら PARTITION BY + ORDER BY。「担当者ごとの累計」「グループの中で何番目に古いか」のように、グループと順序の 2 つの軸が出てきたら、ウィンドウ関数の出番です。

2. フレームは毎回、明示的に書く。既定値 (RANGE UNBOUNDED PRECEDING AND CURRENT ROW、または ORDER BY 無しならパーティション全体) に頼らず、累計なら ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW、移動平均なら ROWS BETWEEN 2 PRECEDING AND CURRENT ROW のように自分が意図した範囲を書きます。ORDER BY にタイが残る列を使うときは、タイのある行を 1 件ずつ数えたいなら ROWS で一意な並び順にし、タイを 1 回分としてまとめて数えたいなら GROUPS (直前の報告「回数」ではなく「報告日の数」を数えたいときなど)、タイをまとめつつ値そのものの範囲で区切りたいなら RANGE を選びます。

3. 「上位 N 件」の境界では同率の扱いを先に決める。ROW_NUMBER (必ず N 件、同率の一部が切り落とされる)、RANK (同率は全員含むが次の順位が飛ぶ)、DENSE_RANK (同率は全員含み、順位は詰まる) のどれが要件に合うかを、コードを書く前に言葉で決めておきます。

性能面では、ウィンドウ関数は内部で 1 回のソート (または既にソート済みのインデックスの利用) を必要とします。PARTITION BY と ORDER BY に使う列の複合インデックスを用意しておくと、ソートそのものを省略できる場合があります (第 28 回の実行計画の読み方を参照)。節 6 の readings テーブルには (sensor_id, ts) の複合インデックスがすでにあり、これはちょうど LAG の PARTITION BY sensor_id ORDER BY ts と同じ並びです。プランナがそのインデックスを使う Index Scan を選んだ場合の実行計画です。

-- プランナにインデックスの利用を強制して確認する (本番のチューニング手段ではなく確認用)
SET enable_bitmapscan = off;
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT sensor_id, ts, value, LAG(value) OVER (PARTITION BY sensor_id ORDER BY ts) AS prev_value
FROM readings WHERE sensor_id = 1;
RESET enable_bitmapscan; RESET enable_seqscan;
 WindowAgg  (cost=1.84..7911.61 rows=5570 width=50) (actual rows=6000.00 loops=1)
   Window: w1 AS (ORDER BY ts)
   Buffers: shared hit=1936
   ->  Index Scan using readings_sensor_id_ts_idx on readings  (cost=0.42..7828.06 rows=5570 width=18) (actual rows=6000.00 loops=1)
         Index Cond: (sensor_id = 1)
         Buffers: shared hit=1936
 Execution Time: 2.060 ms

節 6 で見た Bitmap Heap Scan → Sort → WindowAgg (計画全体で Sort ノードが入る) と比べて、ここでは WindowAgg の直下が Index Scan のままで、間に Sort ノードがありません。(sensor_id, ts) の並びがすでに PARTITION BY/ORDER BY の並びと一致しているため、プランナがソートを省略できたということです (enable_bitmapscan/enable_seqscan はここでは確認のためだけにオフにしており、本番のチューニング手段ではありません)。巨大なパーティションを 1 つだけ作ってしまう (PARTITION BY を付け忘れる) と、全行を 1 つの集合としてソートすることになるので、意図したグループ単位になっているかも確認します。

深層学習コンパイラスタック

静的を成立させる巨大なソフト ── フレームワークからチップ命令までの旅

0この章の狙い

07 章で見た MN-Core のように、ハードから制御を剥がすほど、その分の判断はどこかへ移らなければなりません。移った先がコンパイラです。この章は、その巨大なソフトウェアの内部を覗きます。

一言でいうと
深層学習コンパイラスタックとは、PyTorch や JAX で書いたモデルの計算グラフ（演算をノード、テンソルの受け渡しを辺とするグラフ）を、GPU や MN-Core のような実チップの命令列まで、何段もの中間表現(IR、Intermediate Representation)を経て段階的に具体化していくソフトウェア群です。各段で「演算をどう融合するか」「ループをどう並べ替えるか」「データをどこに置くか」を決めます。汎用コンパイラ(C を機械語にする類)との違いは、テンソル全体を見渡した大域最適化(演算融合・メモリ計画・自動スケジューリング)を担う点です。07 章で見た「静的方式が成り立つ」ためには、この巨大なソフトが要のピースとして必要になります。
1. なぜ DL 専用コンパイラが要るか 2. 多段 IR と lowering 3. MLIR・LLVM・XLA・TVM・Halide 4. 演算融合という主役技 5. MN-Core のスタック 6. 【体験】融合前 / 融合後 7. まとめ

1なぜ DL 専用コンパイラが要るか

C コンパイラも命令を並べ替え、レジスタを割り当てます。それでも深層学習には専用のコンパイラスタックが別に育ちました。

汎用コンパイラは、基本的には 1 つの関数やループの中の最適化(命令スケジューリング、レジスタ割り当てなど。04 章)が主戦場です。一方、深層学習のワークロードは巨大な計算グラフ全体を相手にします。「この行列積の直後の加算と活性化関数を 1 つのカーネルにまとめられないか」「この中間テンソルはオンチップに置いたままにできないか」「このループはどう分割すればアクセラレータのメモリ階層に収まるか」──こうした判断は、テンソルの形・依存関係・ハードウェアのメモリ階層を同時に見渡さないと下せません。07 章で見たとおり、制御をハードから剥がすほど、こうした判断の総量はコンパイラ側で増大します。この章は、その判断を担う多段のソフトウェアの姿を追います。

2多段 IR と lowering

1 段で高レベルのグラフから低レベルの命令まで一気に変換するのは無理があります。段階を分けるのがコンパイラの定石です。

DL コンパイラスタックは、抽象度の異なる複数の中間表現(IR)を積み重ねます。おおまかには、次のように具体化(lowering、抽象度を下げること)が進みます。

# 抽象度が高い順(典型例。実装ごとに段数・名称は異なる)
グラフ / テンソル演算 # MatMul, Conv, ReLU … op 単位。融合・大域スケジュールを検討
↓ lowering
ループ / タイル # op をループネストへ展開。タイル分割・メモリ配置を決定
↓ lowering
ハード命令 # 命令選択・レジスタ/スクラッチパッド割り当て・命令スケジュール

各段には、その抽象度でしか見えない最適化があります。演算融合はグラフ段でしか判断できませんが、レジスタ割り当てはハード命令段でしか決まりません。段を分けることで、それぞれの最適化を扱いやすい粒度で実装できます。

3MLIR・LLVM・XLA・TVM・Halide

「複数の抽象度を 1 つの枠組みで扱う」という発想を体系化したのが MLIR です。

プロジェクト位置づけ要点
LLVM低レベル・後段汎用コンパイラの共通基盤。DL スタックの多くが最終段のコード生成に利用
MLIR複数抽象度「方言(dialect)」という仕組みで、グラフレベルからループレベルまで複数の IR を 1 つの拡張可能な枠組みに載せる。Google 発、現在は LLVM プロジェクト傘下
XLAグラフ〜ループTensorFlow/JAX 向け。HLO(High Level Operations / Optimizer と展開される)という IR 上で演算融合などを行う
TVMグラフ〜ハード命令Relay(グラフ IR。近年は後継の Relax へ移行中)・TE/TIR(テンソル式・ループ IR)を経由。AutoTVM・Ansor による自動スケジューリング探索を持つ
Halide概念的基盤「アルゴリズム(何を計算するか)とスケジュール(どう計算するか)を分離する」という考え方を画像処理向けに提示し、多くの DL コンパイラに影響

polyhedral 最適化は、ループネストをアフィン変換(添字を 1 次式で書き換える写像。線形項に加え定数のずれを許す)で表現し、タイル化や融合を数理的に導出する手法です(Polly、Pluto など)。規則的なループが多い DL ワークロードでは有効な場面がありますが、すべての DL コンパイラが採用しているわけではありません。自動スケジューリング(TVM の AutoTVM/Ansor など)は、人手のチューニングの代わりに多数のスケジュール候補を機械的に探索・計測して選ぶ手法です。

4演算融合という主役技

DL コンパイラの効き所の中でも、演算融合(operator fusion)は特に効果が大きい最適化の 1 つです。

行列積の直後に bias 加算、その直後に ReLU ── というように、DL モデルには小さな演算が連続することが多くあります。素朴に実行すると、各演算がそれぞれ入力を読み、結果を DRAM(または広い階層のメモリ)に書き戻します。演算融合は、この連続する演算を 1 つのカーネル（ここでは、ひとまとまりに実行される演算単位。05 章の「1 スレッド分のコード」とは別の粒度の呼び方）にまとめ、中間結果をオンチップのレジスタやスクラッチパッド(06 章)に留めたまま次の演算に渡します。DRAM への往復が減るぶん、実効的な帯域と電力効率が上がります。大きな行列積そのものは演算量が支配的（compute-bound）ですが、その前後に要素ごとの小さな演算（bias 加算・活性化など）が挟まると、それらはメモリ往復が支配的になりやすく、融合による効果が大きくなりがちです。

融合できるかは形次第。 すべての演算列が自由に融合できるわけではありません。要素ごとの演算(bias, 活性化など)は融合しやすい一方、行列積のように出力の各要素が広い範囲の入力に依存する演算は、融合の仕方によって再計算やメモリ配置の制約が生じます。どこまで融合するかは、コンパイラがメモリ容量・再利用・並列度を見ながら決める判断です。

5MN-Core のスタック

07 章の MN-Core に戻ります。MN-Core 2 ホワイトペーパーの記述に基づき、その多段 IR を見てみます。

入力は PyTorch や JAX から ONNX（フレームワーク間でモデルを受け渡すための共通フォーマット）へエクスポートできる形式を前提にしています。「ONNX にエクスポートできる形であれば対応可能」という方針で、ユーザーコードの改変を最小化することを重視しています。

PyTorch / JAX → ONNX →
  L3IR(DNN op レベル。SIMD 並列化戦略、Global Layout Planner、再計算スケジューラ)
  ↓
  L2IR / Generic Conv(ndarray op レベル。最適化された DNN op 実装)
  ↓
  L1IR(MN-Core op レベル。メモリ割り当て・スケジューリング・命令パッキング)
  ↓
  チップ実行

API はホワイトペーパー記載のコード例で次のように示されています。

import mncore
train_step = mncore.compile(model_with_loss, backward=True, optimizer=optimizer)

これにより、Forward・Backward・Optimizer Step を一体でコンパイルし、まとめて実行します。「必要な計算とデータを適切に PE・MAB・L1B・L2B(07 章の階層)に対してマッピングする必要があるが、これをユーザーが手で書くのは一般的に困難」であり、その自動化がこのスタックの役割だとホワイトペーパーは説明しています。汎用計算(非 AI/HPC)向けには OpenACC のサブセットと OpenCL のサブセットを別途開発中とされています。

未公表の部分。 各段の lowering がどのような具体的アルゴリズムで命令パッキングやスケジュールの探索を行っているか(04 章のリストスケジューリングやモジュロスケジューリングに相当する内部手法)は、公開されている一次情報(ホワイトペーパー、SDK Hub ドキュメント)には記載がありません。ここでは「未公表」として扱い、憶測で補いません。

6【体験】融合前 / 融合後

MatMul → Add(bias) → ReLU という 3 段の演算列を、融合しない場合と融合する場合で比べます。

演算(カーネル) DRAM 往復(書き戻し/読み出し) オンチップに留まるデータ
融合なしでは、MatMul の出力・Add の出力がそれぞれいったん DRAM に書き戻され、次の演算がそれを読み直します。融合すると、3 つの演算が 1 つのカーネルにまとまり、中間結果はオンチップのメモリに留まったまま次の演算に渡ります。この例（中間結果を再計算しない融合）では演算の回数は変わらないのに、DRAM トランザクションだけが減るのがポイントです。ここでの往復回数は説明のための模式的な数え方であり、実際のコンパイラは融合の可否をメモリ容量やデータ依存を見て個別に判断します。

7まとめ

論点要点
役割フレームワークの計算グラフを、多段 IR を経てチップ命令へ具体化する
代表的な枠組みMLIR(複数抽象度)・LLVM(後段)・XLA/TVM(DL 特化)・Halide(発想の源流)
効き所演算融合による DRAM 往復の削減、自動スケジューリング、polyhedral 最適化
MN-CoreL3IR → L2IR → L1IR の多段 lowering。PE/MAB/L1B/L2B へのマッピングを自動化
代償07 章で剥がした制御の分だけ、コンパイラ側の判断量が増える
結論。静的側に振り切ったハードウェアが実際に性能を出せるのは、この巨大なコンパイラスタックが「誰が何をどこで実行するか」を全部代わりに決めているからです。次章では、この高い電力効率を持つハードウェアが、物理的にどう実装されるか ── 3D 積層という実装技術に話を進めます。

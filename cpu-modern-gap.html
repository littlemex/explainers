自作 CPU と現代 CPU の距離 ― 骨格は変わらない、総復習

スーパースカラ・アウトオブオーダー・投機実行・多段キャッシュ。名前は難しいが、どれも rj32 で見た仕組みを「賭けて増やす」方向に伸ばしただけで、骨格 (命令を取り出し・解読し・実行し・書き戻す) は変わらない

この回の前提: 第 01〜23 回のすべて (このシリーズの総復習です)

rj32 のような CPU と、手元のパソコンやスマートフォンに載っている現代の CPU の間には、クロック周波数や命令数で何百倍もの差があります。しかし、その差を生んでいる技術 (スーパースカラ・アウトオブオーダー実行・投機実行・多段キャッシュ) は、どれも魔法ではなく、このシリーズで見てきた仕組みを「1 つずつ増やす」「賭けに出る」方向に発展させたものです。最終回では、この距離を 1 つずつ測り、最後に「それでも変わらない骨格」が何かを確認します。クイズは第 01〜23 回の知識を組み合わせて答える総復習です。

1. それでも変わらない骨格

第 01 回で見た通り、CPU の仕事は「命令を取り出し (fetch) → 解読する (decode) → 実行する (execute) → 結果を書き戻す (writeback)」の繰り返しです。rj32 も、手元のパソコンに載っている現代の CPU も、この骨格は変わりません。違うのは、この 4 つの仕事のそれぞれを、1 クロックにどれだけ、どれくらい賭けてやるかという量の問題です。

図: 骨格 (4 つの仕事) は同じで、それぞれの仕事をどれだけ並列に・どれだけ賭けて行うかが違う。

この回では、この「賭けて増やす」方向への発展を 4 つ (スーパースカラ・アウトオブオーダー実行・投機実行・多段キャッシュ) に分けて、それぞれが rj32 の何を発展させたものかを確認します。

2. スーパースカラ ― 1 クロックに複数命令

第 23 回で見た性能の式の CPI (Cycles Per Instruction) は、rj32 のような単純なパイプラインでは良くても 1 止まりです。1 クロックに fetch できる命令は 1 個、execute できる命令も 1 個だからです。スーパースカラは、decode や execute の回路を複数用意し、1 クロックに複数の命令を同時に処理できるようにする設計です。この時 CPI は 1 より小さくなり得るので、通常は逆数のIPC (Instructions Per Cycle) という言い方で「1 クロックに平均何命令処理できたか」を表します。

図: 実行ユニットを複数用意すれば、1 クロックで複数命令を同時に進められる。

第 07 回で見た ALU や第 08 回のレジスタファイルは、rj32 では 1 組しかありません。スーパースカラはこれを複数組に増やし、第 11 回のデコーダにも「同時に複数命令を解読する」という仕事を追加します。回路の規模は増えますが、骨格そのもの (デコードして ALU で実行する) は変わりません。

3. アウトオブオーダー実行 ― 命令の順番を入れ替える

rj32 は第 15 回で見た通り、命令を書かれた順番通りに処理する「イン・オーダー」の CPU です。そのため、第 17 回で見たようにロード命令がメモリの応答を待っている間、後ろの命令は全部足止めされます。たとえ後ろの命令がそのロード命令の結果を全く必要としなくても、順番を守るために待たされてしまいます。

図: 順番を守る必要がない命令を先に実行することで、待ち時間を無駄にしない。

ただし、これには代償があります。第 08 回で見た rj32 のレジスタファイルは「読み 2 ポート・書き 1 ポート」という単純な構成でした。アウトオブオーダーで複数の命令が同時に進むと、同じレジスタへ別々の命令が別々の時点で書き込むという状況が起きやすくなり、「後から来た命令の結果を先に書いてしまう」ような間違った上書きを防ぐ必要が出てきます。これを解決する代表的な技法がレジスタリネーミング (同じ名前のレジスタを、実際には複数の実体に割り当て直す仕組み) です。骨格 (レジスタファイルに書き戻す) は同じですが、管理の複雑さが大きく増えます。

4. 投機実行 ― 当たるとは限らない賭けに出る

第 23 回で見た通り、rj32 の if.cc によるスキップは「確定するまで律儀に 1 クロック待つ」という、外れのない確実な方式です。パイプラインの段数が増え、分岐の結果が確定するまでに何段もかかるようになると、この「確定を待つ」だけで大きな時間を失います。投機実行は、確定を待たずに「たぶんこちらだろう」と予測した方向へ先に実行を進めてしまう技法です。

図: 確実に 1 クロック払う方式と、当たれば得・外れれば大きく損する賭けの方式の違い。

当たる割合が十分高ければ、平均するとこの賭けは得になります。しかし外れた時のペナルティは、パイプラインの段数が深いほど大きくなります。これは第 23 回の性能の式のうち、CPI の平均値をどちらの方向に動かすかという話で、骨格としては「次にどの命令を fetch するか」という第 1 回から変わらない判断を、確定前に先回りしているだけです。

5. キャッシュ階層 ― 何段もの踏み台

第 23 回で見た通り、rj32 がキャッシュ無しで済んでいるのは、使っているメモリが小さく CPU と同じ速さで読み書きできる内蔵ブロック RAM だからでした。現代の CPU が扱うプログラムやデータは、この内蔵メモリには到底収まりません。キャッシュ階層は、1 段の「小さいが速いメモリ」では足りない時に、速さの違う何段ものメモリを踏み台のように重ねる仕組みです。

図: 上に行くほど小さく速く CPU に近い。rj32 の BRAM はこのピラミッドの頂点 1 段だけに相当する。

各段の役割は、第 23 回で見た「よく使うデータを近くに置く」という考え方を繰り返しているだけです。頂点 (L1) に収まらなければ 1 段下 (L2) を探し、そこにも無ければさらに下 (L3、そして外部メモリ) を探します。段数が増えるのは、CPU と外部メモリの速度差があまりに大きくなり、1 段だけでは「近くて速い」と「大きい」を同時に満たせなくなったからです。

6. 実装のポイント

(1) 複雑さは「組み合わせ」で増える。 スーパースカラ・アウトオブオーダー・投機実行は、それぞれ単独でも設計が難しい技術ですが、同時に使うと「どの命令をどの順番で、当てにいくか」の組み合わせが爆発的に増えます。第 19 回で見た rj32 のテストケースや、第 22 回で見た emurj によるソフトウェアでの先行検証という方針は、現代の CPU ではさらに重要になります。実機 (シリコン) に焼き込んでから間違いに気づくコストが、rj32 を FPGA に書き込み直すコストとは比較にならないほど大きいからです。

図: 確かめる場所が実機・量産に近づくほど、1 回の間違いのコストが跳ね上がる。

(2) 骨格が変わらないことは「簡単になる」ことを意味しない。 fetch ・ decode ・ execute ・ writeback という骨格、命令数×CPI×クロック周期という性能の式、メモリアドレス空間という考え方は、rj32 でも現代の CPU でも共通です。しかし、この回で見た 4 つの技術はどれも、骨格の「中身」を賭けや並列化で複雑にするもので、設計・検証のコストはその複雑さの分だけ増えます。

(3) 自分で作れる CPU から、距離は測れるようになった。 rj32 のような小さな CPU を自分で組み立てる経験は、スーパースカラや投機実行を積んだ CPU を作れるようにするわけではありません。しかし、このシリーズを通して見てきた骨格 (今回の第 1 節) を知っていれば、現代の CPU の技術解説を読んだ時に「それは骨格のどの部分を、どう賭けて増やしたものか」という距離を測れるようになります。それが、このシリーズの最終的な到達点です。

第 4 章 問いを反転させ、最初の実測を取る

この章の 3 行 箱は買ってあるので、問いは「API に勝てるか」ではなく「品質を保ったままどれだけ吸わせられるか」。 節約は入力トークンで稼ぐ構造なので、狙うべきは長い文章を読ませて短く答えさせる検証可能な仕事 — と書いたが、これは第 5 章で実測に否定される。日本語レビュー分類で最初の実測を取ったら箱が勝ったが、 評価設計に欠陥があり、絶対値は使えなかった。

問いを反転させる

ここまで私は箱を「API と 1 件あたりの費用で競わせて負ける層」として扱っていた。これは目的の 取り違えである。自前のサーバを持つ理由は費用を固定することで、正しい問いはこうなる。

net_offload_value = Σ aᵢ [ pᵢ·C_apiᵢ − C_validateᵢ − L_penaltyᵢ ] / Σ aᵢ·S_boxᵢ

  aᵢ         : その仕事を箱に流すか (0 か 1)
  pᵢ         : 箱がその族の品質フロアを満たす確率
  C_apiᵢ     : 箱に流さなければ API に払っていた額
  C_validateᵢ: 箱の答えを検証する費用
  L_penaltyᵢ : 遅くなったことの損失
  S_boxᵢ     : その仕事が箱を占有する秒数

分子は「消せた API 支出」、分母は「使った箱時間」。つまり箱の 1 時間で API 支出を最大いくら消せるかを 最大化する。箱自身の 1 件あたり費用は、この式のどこにも出てこない。

失敗したときの「二重払い」について 箱に投げて品質フロアを満たさず、API に投げ直した場合、両方に払うので損だと考えたくなる。しかし API だけで運用していた場合も API 費用は払っていたので、差分で見れば失敗したタスクの節約額は 0 であって、マイナスではない。二重に失われるのは「無駄にした箱時間」と「遅れた時間」で、式では 分母と L_penalty に入る。

何を吸わせるべきか — 価格構造が答えを持っている

ここで私はもう一度間違えた。「単発で短い入力の分類」を第一候補にしたのだが、価格構造がそれを 否定する。

箱 (2 replicas)claude-haiku-4-5箱が何倍安いか
入力 $/Mtok0.2361.004.2 倍
出力 $/Mtok4.125.001.2 倍
キャッシュ読み使えない0.10負ける

節約は入力トークンで稼ぐ構造になっている。出力では 18% しか安くないので、リクエストあたりの 節約額はほぼ入力の長さに比例する。短い入力の分類が第一候補なのは「品質が測りやすく検証が安いから」で、 お金が大きいからではない。

本命は単発・長入力・短出力・検証可能、たとえば長い文書からの一括抽出である。箱は 37,792 トークンの 文章に対して 16 並列だと最初の応答まで 31 秒かかるが、バッチ処理ならそれは問題にならない (L_penalty がほぼ 0)。管理すべきは KV の予算 (434 万トークン) だけになる。

この段落は後の実測で否定された (第 5 章で訂正) 「節約額が入力長に比例するから長文が本命」という推論は、比例するという前半は正しく、結論が誤りである。 目的関数は節約額を箱時間で割っている。入力を 300 から 18,141 トークンに伸ばすと 1 件あたりの節約額は 52 倍になるが、箱時間は 82 倍になる。割り算の答えは逆を向く。測定器の欠陥を 2 つ外したあとの実測では、 箱 1 時間あたりに消せる API 支出は入力 60 トークンで $76.83、300 で $67.18、600 で $51.06 に対して、 20,000 では $24〜32 だった。短いほど高い。さらに品質を掛けると長文族は箱代を割り込む (ただし優先度スケジューリングで隙間だけに流すなら限界費用が 0 に近づくので、この判定は未決着)。 第 5 章で入力長 9 点、出力長 3 点の曲面と、2 つの測定器の欠陥を出す。
順族なぜそこか
1a検証可能な短入力の分類配管を通すため。品質が測りやすく検証が安い。結果としてここが本命だった (第 5 章)
1bバッチの長文抽出ここが本命。節約額が入力長に比例し、遅延に鈍感 → 実測で最下位付近。箱 1 時間あたり $24〜32 で、短入力の半分以下
2スキーマ検証つきの抽出 (対話的)抽出は分類より事故る。値のずれ、根拠の位置ずれ、欠落
3短文・定型の翻訳採点は自動化しやすいが、出力長 ≒ 入力長なので節約は 18% 止まり
4低リスクの整形要約、固定形の OCROCR は品質以前に箱時間が未計測

最初の実測 — 日本語レビューの 3 クラス分類

公開データセットから日本語のレビュー 48 件を取り、長さと正解ラベルで層別に選んだ。同じ 48 件を 箱と haiku の両方に投げ、同じプロンプト、温度 0 で答えさせて、正解ラベルと文字列一致で採点した。

箱 (Qwen3.6-35B-A3B)claude-haiku-4-5
正解数38 / 48 = 0.79236 / 48 = 0.750
費用$0.00279 (稼働率 100% 換算)$0.01620
所要時間8 秒82 秒
両方正解 箱だけ正解 haiku だけ正解 両方不正解

第 2 章の SWE-bench とは向きが逆になった。箱だけが正解したものが 2 件、 haiku だけが正解したものが 0 件。差は +4.2 ポイントで、費用は 5.8 倍安い。

ところが、この数字の絶対値は使えない ミスの内訳を見ると、両層の全ミスが「ニュートラル」だった。ポジティブとネガティブは両方とも 100% 正解している。このデータセットの正解ラベルは星の数から作られていて、3 つ星のレビューは 人間でも判断が割れる。つまりこの suite が測っていたものの大半は「3 つ星を当てられるか」だった。

結果として絶対値はタスクの定義を記述していて、モデルを記述していない。一方で対応あり差分は 生き残る — 両方が同じ 48 件、同じプロンプトを見ているからである。この非対称性が、次の節の理由になる。

デモ: なぜ「対応あり」でなければ判定できないのか

「箱を使っていいか」を統計的に言うには 2 つの言い方がある。この 2 つは別の問いで、 必要な件数がまったく違う。スライダーで件数を動かして見比べてほしい。

同じデータ、2 つの問い

問い A: 箱の正解率は 0.85 以上か

—
正解率 0.792 を観測したときの下限
—

問い B: 箱は haiku より 2 ポイント以上悪くないか

—
同じ件で比べた差の下限
—

動かして見えること

  • 問い A はどれだけ件数を増やしても厳しい。正解率 0.792 を観測している以上、 0.85 という床は下限が届く前に真の値が足りていない。仮に真の値が 0.90 でも、95% の下限が 0.85 を 超えるには 200 件近く必要になる。払える件数では「いいえ」しか言えない設計である。
  • 問い B は 48 件でも判定できる。同じ件で比べると、両方が正解した件と両方が外した件は 差について何も語らない。情報を持つのは不一致の件だけで、近い性能のモデル同士ではそれが 全体の 1 割ほどしかない。だから差は個々の正解率よりずっと精密に推定できる。
  • 信頼水準を下げると通りやすくなる。これはごまかしではなく、損失の大きさに合わせた設計である。 誤って箱に流しても検証器が捕まえて API に投げ直すので、失うのは箱時間と少しの遅延だけ。 有界な損失に 95% を要求するのは、永遠に測って何も出荷しない設計になる。だから片側 80% を 既定にし、その値を隠さず宣言している。
この 2 つを混同しないこと 問い B が通っても、問い A を証明したことにはならない。言えるのは「このベンチマークの中で haiku より劣らない」であって、「絶対品質が 0.85 以上」ではない。運用でどちらが必要かは、 その仕事が何を要求するかで決まる。

まだ言えないこと

この 48 件は公開データセットで、実際に流したい業務のデータではない。pᵢ は 「箱が実際に捌くトラフィック上で品質フロアを満たす確率」として定義されているので、この数字は 配管が通ったことの証明であって、ルーティングを変える根拠にはならない。次にやるのは、 正解が星の数ではなく判断であるような 2 クラス版に差し替えること、そして本命のバッチ長文抽出に進むこと。

順序の規律も 1 つ決めてある。品質 pᵢ が確定しないまま費用のパラメータだけ揃えても、 目的関数の分子は符号すら決まらない。だから品質を測るまで routing は変えない。

この章で壊しておきたい誤解

よくある思い込み実際は
買ってある箱に流すなら品質条件は緩めていい遊休時間の活用であって、品質フロアの免除ではない。式の pᵢ が消えるわけではない
失敗して API に投げ直すと二重に払うので損差分で見れば節約額 0。失うのは箱時間と遅延
短い仕事から流すのが得節約は入力長にほぼ比例する。短い仕事は測りやすいが儲からない
38 対 36 なら箱のほうが日本語レビュー分類に強い測っていたのは星から作ったラベルへの適合。絶対値は使えず、対応あり差分だけが残る
件数を増やせばどんな主張も証明できる絶対品質と比較優位は別の問い。前者は払える件数では届かない

K8S CUSTOM CONTROLLER ・ 第 04 回

CRD・CR・コントローラー・オペレーターの違い

4 つの言葉を整理し、コントローラー無しの CRD が何をするかを実測で確かめる

← カスタムコントローラー自作 シリーズ目次へ

「CRD」「CR」「コントローラー」「オペレーター」という 4 つの言葉は、似たような場面で出てくるせいで混同されやすい。第 04 回ではこの 4 つを整理し、コントローラーをまだ書いていない状態の CRD が実際に何をして何をしないのかを、実測の Widget(この連載で実験に使う CRD)で確かめる。

CRD は新しい型を API サーバーに登録するだけの宣言で、それだけでは保存や検証ができるようになるだけで、現実の世界を変える処理は何も起きない。CR はその型の実際の 1 つ 1 つの実物、コントローラーは CR を見て世界を変える別のプログラム、オペレーターは特定のソフトウェアの運用知識をコントローラーに詰め込んだもの、という 4 段の積み重ねになっている。

1. CRD: 新しい型を登録する宣言

CustomResourceDefinition(CRD)は、「この名前・この構造を持つ、新しい種類のオブジェクトを API サーバーに追加してほしい」という宣言そのものだ。公式ドキュメントはこう説明している。

"When you create a new CustomResourceDefinition (CRD), the Kubernetes API Server creates a new RESTful resource path for each version you specify."
(Custom Resource Definitions)

つまり CRD を 1 つ作ると、API サーバーに新しい REST の住所(第 02 回の GVK/GVR)が生える。この時点で起きているのは「住所が追加された」ことだけで、その住所に何を置くか(CR)や、置かれた物を見て何をするか(コントローラー)はまだ何も決まっていない。

図: CRD は住所を増やすだけで、まだ何も動かしていない。

2. CR: その型の実物

CRD が増やした住所に、実際にデータを置いたものがカスタムリソース(Custom Resource: CR)だ。このシリーズでは実験用の CRD として、group lab.crd-series.example、kind Widget を使う。image・size・replicas といったフィールドを持つ CR を 1 つ作ると、それが Widget という型の「実物」になる。

CR は Pod や Deployment のような組み込みのオブジェクトと、扱われ方のうえでは何も特別ではない。kubectl get・kubectl apply・kubectl delete がそのまま使え、第 02 回で見た metadata(name, uid, resourceVersion, ...)もまったく同じ形で付く。

図: 1 つの CRD(型)に対して、CR(実物)は何個あってもよい。

3. コントローラー: CR を見て世界を変える別プログラム

CRD と CR だけでは、何も実行されない。Widget という型と、その実物が存在するだけで、「Widget が指定した数だけ何かを動かす」という処理そのものは、別に書かれたプログラム(コントローラー、第 03 回)が CR を見張って初めて実行される。コントローラーは CRD の一部ではなく、CRD とは独立に作る・デプロイする、まったく別のソフトウェアだ。

図: コントローラーは CRD の一部ではなく、別にデプロイする独立したプログラム。

4. オペレーター: 運用知識を詰めたコントローラー

オペレーター(Operator)は、新しい仕組みではなく、ここまでの 3 つの組み合わせに名前を付けたパターンの呼び方だ。公式ドキュメントは「Operators are software extensions to Kubernetes that make use of custom resources to manage applications and their components. Operators follow Kubernetes principles, notably the control loop」と説明している(Operator pattern)。つまりオペレーターとは、CRD(型)・CR(実物)・コントローラー(調整ループ)の 3 点セットを使って、特定のソフトウェア(データベースなど)の運用知識(バックアップの取り方、安全な更新の手順など)をコードに落とし込んだものを指す。

4 つの言葉の関係を 1 枚の図にまとめると、次のようになる。

図: CRD → CR → コントローラーという積み重ねの先に、オペレーターという呼び方がある。

5. CRD だけ入れると何が起きるか(実測)

ここまでは言葉の整理だったが、実際にコントローラーを 1 つも起動せずに Widget という CRD だけを入れたら何が起きるのか。EKS 1.35 のテスト用クラスタで実測した。

やったこと起きたこと
未知フィールド unknownField を付けて kubectl apply拒否された(strict decoding error)。--validate=warn なら警告付きで作成され、未知フィールドは刈り込まれ(pruning)、既定値 3 つが埋まった
enum(あらかじめ決めた選択肢の中からしか選べない制約)外の値 size: huge を指定拒否された(Unsupported value)。スキーマの検証はコントローラー無しでも働く
本体の更新で status.replicas を merge patch(送った差分だけを既存の内容に上書きする更新の仕方)無視された(patched (no change))。status サブリソースが有効なため、--subresource=status を使わない限り誰も書けない
finalizer を付けて delete削除予約の状態(deletionTimestamp 付き)で残った。外す人が誰もいないので、そのままでは消えない

つまりコントローラーが無くても、保存・検証・既定値埋め・表示(printer columns)という「台帳の中の処理」は API サーバーだけでちゃんと動く。ただし、それはあくまで台帳の中の話であり、現実の世界で何かを起動したり変更したりする処理は一切起きない。実際、この実験の間 Ready の条件(status の conditions)が自然に現れることは一度も無かった。それを書くのはコントローラーの役目であり、起動していない以上、誰もそこを書かない。

図: CRD は台帳の形を決めるだけで、台帳を動かすのはコントローラー。

6. Webhook と ValidatingAdmissionPolicy はどこにいるか

第 05・06 回で扱うスキーマの検証の前後に、API サーバーには「保存する前にもう 1 段判定を挟む」仕組みがある。公式ドキュメントによれば、リクエストはまずmutating admission webhook(第 12 回: 値を書き換えられる、別プログラムへの問い合わせ)を通り、次にスキーマによる検証(構造・既定値埋め・CEL(Common Expression Language: 短い式でルールを書ける言語)、第 05・06 回)を受け、最後にvalidating admission(第 12 回の validating webhook と第 13 回の ValidatingAdmissionPolicy(VAP)。どちらも値は書き換えず、合否だけを判定する)を通ってから etcd に保存される。この順序のおかげで、validating 側は「書き換えがすべて終わった後の、最終的な内容」を見て判定できる。

図: mutating webhook → スキーマ検証 → validating(VAP・webhook)→ etcd の順。詳しくは第 12 回で描き直す。

まとめと次の回

CRD は型を登録する宣言、CR はその実物、コントローラーは CR を見て世界を変える別プログラム、オペレーターはその 3 つに運用知識を詰めた呼び方だった。コントローラーが無くても API サーバーは保存・検証・既定値・表示までをこなすが、実際に何かを「動かす」部分は一切起きない。第 05 回では、CRD というスキーマの骨格そのものを詳しく見ていく。

図: 第 05 回からは、この一番左の箱(CRD)の中身に入っていく。

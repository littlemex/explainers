ナイーブツリー ― 親 ID だけで木を表す

親 ID だけの隣接リストは木を表せるが、固定の深さで結合するクエリは想定より深い枝を取り逃がす

← SQL シリーズ目次へ

この回の前提: 第 01 回 アンチパターンとは何か (サンプル DB の comments テーブル)、第 02 回 ジェイウォーク (1 列に複数の意味を詰め込む問題の考え方)

コメントへの返信のように「親子関係が何階層にもなる」データを表すとき、最も素朴な方法は parent_id 列を 1 つ持たせることです。これを 隣接リスト (adjacency list) と呼び、PostgreSQL でも標準的に使われる正しい設計です。問題は、この隣接リストを「固定の深さで結合する」クエリで読もうとしたときに起こります。結論を先に言うと、隣接リストそのものは悪くありませんが、深さを決め打ちした結合では想定より深い木を取り逃がし、WITH RECURSIVE を使わない限り任意の深さを安全には扱えません。この回では、その失敗を実機で再現し、見つけ方、WITH RECURSIVE による正しい読み方、そして木の持ち方そのものを変える 3 つの代替案 (path enumeration、入れ子集合、閉包テーブル) を比較します。

1. 目的 ― 何をしたかったのか

バグ管理システムのコメント欄に「返信」機能を付けたいとします。あるコメントに対して、別のユーザーが返信を付け、その返信にさらに返信が付く、という構造です。これは親子関係が何段にもなる木構造 (tree) で、1 件のコメントが 0 件以上の「子コメント」を持つという関係を表現する必要があります。最も自然な実装は、comments テーブルに「どのコメントへの返信か」を示す parent_comment_id 列を 1 つ追加することです。

2. アンチパターン ― どう書いてしまい、何が壊れるか

実際に parent_comment_id を追加し、bug_id=1 のコメントにスレッドを作ります。

ALTER TABLE comments ADD COLUMN parent_comment_id bigint REFERENCES comments (comment_id);

INSERT INTO comments (bug_id, author, comment, parent_comment_id) VALUES
  (1, 3, 'can you share your repro steps?', 1),  -- id 5, 1 への返信
  (1, 1, 'sure, steps attached',           5),  -- id 6, 5 への返信
  (1, 2, 'confirmed, same here',           6),  -- id 7, 6 への返信
  (2, 1, 'which report exactly?',          3);  -- id 8, 3 への返信

図: bug_id=1 のコメントスレッド。id=1 を根として、id=5 ・ id=6 ・ id=7 が順に深くなる返信の木を作る。id=7 は根から数えて 4 階層目にある。

ここで「スレッドを根からすべて表示する」という、ごく普通の要件を固定の深さの自己結合 (self-join) で書いてみます。

SELECT c1.comment_id AS lvl1, c2.comment_id AS lvl2, c3.comment_id AS lvl3
FROM comments c1
LEFT JOIN comments c2 ON c2.parent_comment_id = c1.comment_id
LEFT JOIN comments c3 ON c3.parent_comment_id = c2.comment_id
WHERE c1.parent_comment_id IS NULL
ORDER BY lvl1, lvl2, lvl3;

 lvl1 | lvl2 | lvl3
------+------+------
    1 |    5 |    6
    2 |      |
    3 |    8 |
    4 |      |

この結果には id=7 が出てきません。 id=6 の子である id=7 は根 (id=1) から数えて 4 階層目にあり、3 段しか結合していないこの SQL では構造的に届かないのです。深さが分からないデータに対して、あらかじめ結合の段数を決め打ちすることはできません。段数を増やしても「もっと深いスレッドが来たら」という不安は消えず、これが隣接リストを素朴な結合だけで読もうとしたときの核心的な限界です。

3. 見つけ方 ― どんな兆候で気づくか

既存のデータベースの中から、隣接リストで木を表している列を探すには、自己参照の外部キー (参照元と参照先が同じテーブルである外部キー) を information_schema から探します。

SELECT
  tc.table_name, kcu.column_name,
  ccu.table_name AS foreign_table, ccu.column_name AS foreign_column
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
  ON tc.constraint_name = kcu.constraint_name AND tc.table_schema = kcu.table_schema
JOIN information_schema.constraint_column_usage ccu
  ON tc.constraint_name = ccu.constraint_name AND tc.table_schema = ccu.table_schema
WHERE tc.constraint_type = 'FOREIGN KEY' AND tc.table_schema = 'public'
  AND tc.table_name = ccu.table_name
ORDER BY tc.table_name;

 table_name |    column_name    | foreign_table | foreign_column
------------+--------------------+---------------+----------------
 comments   | parent_comment_id | comments      | comment_id

この結果が返ってきたら、その列は木構造 (あるいは少なくとも階層構造) を表している可能性が高いという兆候です。見つけたら、そのテーブルを読んでいる既存のクエリの中に、この回で見たような固定段数の自己結合が無いか、あるいは最大深さを仮定したアプリケーション側のループが無いかを確認します。

4. 使ってよい場合

隣接リストという持ち方自体は、PostgreSQL においても標準的で正しい選択です。使ってよい、というより多くの場合はまずこれを選ぶべきです。1 行の追加・削除・1 つの親の付け替えが、常に 1 行の更新で済むという書き込みの単純さは、他のどの持ち方にも無い利点です。問題になるのは「固定段数の結合で読む」という読み方だけであり、読み方を直せば隣接リストのまま解決できます。

PostgreSQL は WITH RECURSIVE という再帰共通テーブル式 (recursive CTE) を使えます。基本の形は「起点の行 (base case)」と「そこから 1 段先の子を取る規則 (recursive case)」を UNION ALL で結びます。

WITH RECURSIVE thread AS (
  SELECT comment_id, bug_id, parent_comment_id, comment, 1 AS depth
  FROM comments
  WHERE parent_comment_id IS NULL AND bug_id = 1          -- base case: 根
  UNION ALL
  SELECT c.comment_id, c.bug_id, c.parent_comment_id, c.comment, t.depth + 1
  FROM comments c
  JOIN thread t ON c.parent_comment_id = t.comment_id     -- recursive case: 1 段先の子
)
SEARCH DEPTH FIRST BY comment_id SET ordercol
SELECT comment_id, parent_comment_id, depth, comment
FROM thread
ORDER BY ordercol;

 comment_id | parent_comment_id | depth |             comment
------------+--------------------+-------+----------------------------------
          1 |                    |     1 | reproduced on 2.1
          5 |                  1 |     2 | can you share your repro steps?
          6 |                  5 |     3 | sure, steps attached
          7 |                  6 |     4 | confirmed, same here
          2 |                    |     1 | also on 2.0

今度は 4 階層目の id=7 も正しく出てきます。SEARCH DEPTH FIRST BY ... SET ordercol は、結果を深さ優先 (親のすぐ下に子をまとめる) の順序で並べるための列を自動的に作る構文で、ツリー表示のような「親子をまとめて見せたい」場面で役立ちます。

図: WITH RECURSIVE は根を取る base case から始め、1 段ずつ子を取る recursive case を、新しい行が出なくなるまで繰り返す。

隣接リストの唯一の実務的な危険は、親子関係に循環ができてしまうと WITH RECURSIVE が無限に繰り返されることです。PostgreSQL 14 以降は CYCLE 句で、同じ行が再び現れたらそこで安全に止めることができます。

-- 1 -> 3 -> 2 -> 1 という循環を作った状態で
WITH RECURSIVE t AS (
  SELECT node_id, parent_id, 1 AS depth FROM scratch_nodes WHERE node_id = 1
  UNION ALL
  SELECT n.node_id, n.parent_id, t.depth + 1
  FROM scratch_nodes n JOIN t ON n.node_id = t.parent_id
)
CYCLE node_id SET is_cycle USING path
SELECT node_id, parent_id, depth, is_cycle FROM t ORDER BY depth;

 node_id | parent_id | depth | is_cycle
---------+-----------+-------+----------
       1 |         3 |     1 | f
       3 |         2 |     2 | f
       2 |         1 |     3 | f
       1 |         3 |     4 | t

4 回目に node_id=1 が再び現れた時点で is_cycle が t (true) になり、そこで展開が止まります。CYCLE 句を付けなければ、この問い合わせは行を無限に生成し続けようとします (深さの上限を自分で WHERE depth < N のように入れない限り、永久に終わりません)。循環を業務上許さないデータ (親子関係が絶対にループしてはいけない組織図など) では、CYCLE 句を使うか、アプリケーション側で循環を作る更新自体を拒否する仕組みが必要です。

5. 解決策 ― それでも足りないときの 3 つの持ち方

WITH RECURSIVE は隣接リストの読み取りを正しくしますが、「部分木をまたいだ検索を高頻度で行う」「木全体を 1 回の問い合わせで取り出したい」といった場面では、再帰そのもののコストが気になることがあります。ここでは、木の持ち方自体を変える 3 つの代替案を、同じ bug_id=1 のスレッドで確認します。

解決策 B: path enumeration (経路列挙、ltree 拡張)

各行に「根からそのノードまでの経路」をそのまま保存する方法です。PostgreSQL では contrib の ltree 拡張がこれを型として提供します。

CREATE EXTENSION IF NOT EXISTS ltree;
ALTER TABLE comments ADD COLUMN thread_path ltree;
-- 根は自分の id だけ、子は親の経路に自分の id を連結する
UPDATE comments SET thread_path = comment_id::text::ltree WHERE parent_comment_id IS NULL;
-- (子ノードも同様に親の thread_path || comment_id で埋める)

SELECT comment_id, parent_comment_id, thread_path FROM comments ORDER BY comment_id;

 comment_id | parent_comment_id | thread_path
------------+--------------------+-------------
          1 |                    | 1
          5 |                  1 | 1.5
          6 |                  5 | 1.5.6
          7 |                  6 | 1.5.6.7
          8 |                  3 | 3.8

CREATE INDEX comments_thread_path_gist ON comments USING gist (thread_path);
SELECT comment_id FROM comments WHERE thread_path <@ '1'::ltree;      -- id=1 の子孫すべて
SELECT comment_id FROM comments
  WHERE thread_path @> (SELECT thread_path FROM comments WHERE comment_id = 7); -- id=7 の祖先すべて

経路がそのまま列に入っているため、子孫を取るのも祖先を取るのも再帰を書かずに済み、gist インデックスを使った高速な検索ができます。代償は、ノードを別の親の下に移動させるときに、そのノード以下の経路をすべて書き換える必要があることです。

解決策 C: 入れ子集合 (nested sets)

各ノードに「自分の部分木がカバーする区間」を lft・rgt という 2 つの数値で持たせる方法です。

CREATE TABLE comment_nested (comment_id bigint PRIMARY KEY, lft int NOT NULL, rgt int NOT NULL);
INSERT INTO comment_nested VALUES
  (1, 1, 8), (5, 2, 7), (6, 3, 6), (7, 4, 5), (2, 9, 10), (3, 11, 14), (8, 12, 13), (4, 15, 16);

-- id=1 の子孫すべて (1つの BETWEEN で済む)
SELECT comment_id FROM comment_nested
WHERE lft BETWEEN (SELECT lft FROM comment_nested WHERE comment_id = 1)
              AND (SELECT rgt FROM comment_nested WHERE comment_id = 1)
ORDER BY lft;
-- → 1, 5, 6, 7

子孫の取得も祖先の取得も、再帰もインデックス型拡張も使わずに単純な数値比較で済むのが利点です。代償はその逆で、ツリーのどこかにノードを 1 つ挿入するだけで、挿入位置より右側にあるすべての lft・rgt を更新しなければならず、書き込みが重く複雑になります。

解決策 D: 閉包テーブル (closure table)

「祖先・子孫のすべての組」を 1 行ずつ別のテーブルに持つ方法です。

CREATE TABLE comment_closure (ancestor_id bigint, descendant_id bigint, depth int, PRIMARY KEY (ancestor_id, descendant_id));
INSERT INTO comment_closure VALUES
  (1,1,0),(5,5,0),(6,6,0),(7,7,0), (1,5,1),(1,6,2),(1,7,3),(5,6,1),(5,7,2),(6,7,1);

SELECT descendant_id FROM comment_closure WHERE ancestor_id = 1 ORDER BY descendant_id; -- 1,5,6,7
SELECT ancestor_id   FROM comment_closure WHERE descendant_id = 7 ORDER BY ancestor_id; -- 1,5,6,7

子孫も祖先も、普通の WHERE と索引だけで取れ、ノードの挿入・移動も「そのノードに関係する行を入れ替えるだけ」で済むため、入れ子集合より書き込みが素直です。代償は、ノード数が N、深さが D のとき、関係の行数が最大で N × D 程度まで増えることで、テーブルが大きくなりやすい点です。

操作隣接リスト+WITH RECURSIVEpath enumeration (ltree)入れ子集合閉包テーブル
子孫をすべて取る再帰 (段数ぶん繰り返す)索引で 1 回BETWEEN で 1 回索引で 1 回
祖先をすべて取る親を順に辿る再帰索引で 1 回BETWEEN で 1 回索引で 1 回
ノードを 1 つ追加1 行 INSERT1 行 INSERT右側全体を更新祖先の数だけ INSERT
部分木を別の親へ移動1 行 UPDATE配下の経路を再計算区間全体を再計算関係する行を入れ替え
必要な追加の仕組み無し (標準 SQL)ltree 拡張 + GiST無し (数値列のみ)追加テーブル 1 つ

どれを選ぶかは「読み取りと書き込みのどちらが多いか」「木がどれくらい深く・大きくなるか」で決まります。読み取りが多く木があまり動かないなら path enumeration か閉包テーブル、書き込み (特にノードの移動) が多いなら隣接リスト + WITH RECURSIVE が素直です。入れ子集合は読み取りの単純さでは優れますが、書き込みの重さから実務での採用は限定的です。

6. PostgreSQL エンジンで考慮しておくこと

13 万 1,071 行 (深さ約 17 のバランス 2 分木) を generate_series で作り、葉に近いノード (自身を含む部分木が 127 件、子孫は 126 件) の部分木を取得する速さを、隣接リスト + WITH RECURSIVE と path enumeration (ltree + GiST インデックス) で比較しました。

-- WITH RECURSIVE (隣接リスト)
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF) WITH RECURSIVE d AS ( ... ) SELECT count(*) FROM d;
 Recursive Union ...
 Execution Time: 0.252 ms

-- ltree の GiST インデックス (path enumeration)
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF) SELECT count(*) FROM big_tree WHERE path <@ (...);
 Bitmap Heap Scan on big_tree
   ->  Bitmap Index Scan on big_tree_path_gist
 Execution Time: 0.103 ms

図: 13 万行の木で自身を含め 127 件の部分木を取得した実行時間。ltree の GiST インデックスは約 2.4 倍速い。どちらも実機の EXPLAIN (ANALYZE, BUFFERS) で確認した値。

この差が生まれる理由は、WITH RECURSIVE が「1 段ごとに自己結合を繰り返す」処理であるのに対し、path <@ ... は 1 回のインデックス探索で完了する点にあります。深さが増えるほど、再帰の繰り返し回数も増えるため、この差は木が深くなるほど広がりやすくなります。ただし、対象の部分木が木全体の大部分 (この検証では半分) を占めるような、選択性の低い条件では、PostgreSQL のプランナは GiST インデックスではなく並列シーケンシャルスキャンを選ぶこともあり、インデックスが常に有利とは限りません。

なお、CYCLE 句や SEARCH 句は PostgreSQL 14 で追加された構文です。それより古いバージョンでは、同じ結果を array_append で経路を手動で積み上げ、IS NOT NULL や = で循環を自分で検出するという、より長いクエリを書く必要があります。また、ltree は contrib に同梱されている拡張であり、CREATE EXTENSION ltree; を 1 回実行するだけで有効になりますが、スーパーユーザーまたは適切な権限が必要です。

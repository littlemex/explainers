ValidatingAdmissionPolicy と MutatingAdmissionPolicy

webhook を書かずに、CEL だけで関所の判定を済ませる。

← カスタムコントローラー自作 シリーズ目次へ

第 12 回では、admission(受け入れ判定)の中に webhook(外部プログラムへの問い合わせ)を割り込ませる方法を見た。webhook は強力だが、別プロセスを立てて TLS 証明書を管理し、落ちたらクラスタ全体に影響するという重い代償を払う。この回では、同じ admission の関所に、webhook を立てずに CEL(Common Expression Language: 式を書くだけで真偽を判定する言語。第 06 回で CRD のフィールド検証に使った)だけで判定を割り込ませる ValidatingAdmissionPolicy(VAP)と MutatingAdmissionPolicy(MAP)を見る。

VAP は、API サーバーの中で CEL の式を直接評価して許可・拒否を決める仕組みで、公式ドキュメントによれば Kubernetes v1.30 で安定版(Stable)になった。書き換え版の MAP も同じ考え方だが、公式ドキュメントによれば v1.36 で安定版になったばかりの新しい機能で、EKS 1.35 のテスト用クラスタではまだベータの機能フラグが無効で使えなかった(実測)。

1. webhook を書かずに判定する

webhook は外部のプログラムを別途作って運用する必要がある(第 12 回)。VAP はこの外部プロセスを無くし、CEL の式を API サーバーに登録するだけで admission の validating の段階に判定を追加できる。webhook のように HTTPS 通信・TLS 証明書・timeoutSeconds を気にする必要がなく、API サーバーのプロセス内で CEL を評価するので、呼び出しのたびにネットワークを挟まない。第 06 回で CRD の x-kubernetes-validations として使った CEL と同じ言語だが、VAP はオブジェクト自身だけでなく、あらかじめ渡しておいた「パラメータ」や呼び出し元の情報(request.userInfo など)も参照できる点が CRD の CEL より広い。

図: webhook は API サーバーの外に判定を飛ばす。VAP は同じ判定を API サーバーの中で CEL として評価する。

2. Policy と Binding に分かれている理由

公式ドキュメントは、VAP が原則 3 つのリソースから成ると説明している。ValidatingAdmissionPolicy は「どんな判定ロジックか」という抽象的な式を持つ本体、パラメータリソース(任意の CRD や ConfigMap)はその式を具体的な値で補う情報源、ValidatingAdmissionPolicyBinding は「この Policy を、どのリソース・どの namespace に適用するか」という適用範囲を決める。Policy 本体を 1 つ作っておけば、Binding を複数作ることで「この namespace ではこのパラメータで」「別の namespace では別のパラメータで」と、同じロジックを使い分けられる。Binding が 1 つも無ければ、Policy は何にも適用されず何もしない。

Policy の spec.paramKind はパラメータに使うリソースの種類(apiVersion と kind)を指定する。公式ドキュメントが明記しているとおり、CRD だけでなく ConfigMap のようなネイティブ型も使える。Binding の paramRef で実際にどのオブジェクトをパラメータとして使うかを指定する。CEL の式の中では params という変数でこのパラメータの値を参照できる。

kind: ValidatingAdmissionPolicy
metadata:
  name: widget-no-large
spec:
  paramKind: {apiVersion: v1, kind: ConfigMap}
  matchConstraints:
    resourceRules:
      - apiGroups: ["lab.crd-series.example"]
        resources: ["widgets"]
  validations:
    - expression: >-
        object.spec.size != 'large' ||
        request.userInfo.username.startsWith('system:')
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: widget-no-large-binding
spec:
  policyName: widget-no-large
  validationActions: [Deny]

図: Policy は判定ロジック本体、Binding は適用範囲(どのリソース・どの namespace)を決める。1 つの Policy に複数の Binding を結びつけられる。

3. matchConstraints と namespaceSelector(実測の例)

Policy の spec.matchConstraints は「この Policy がそもそも対象にするリソースの種類」を決める(例: Widget の CREATE/UPDATE)。Binding 側の matchResources.namespaceSelector は、ラベルで絞り込んだ namespace だけに適用範囲を狭める。EKS 1.35 のテスト用クラスタで実測した例では、「object.spec.size != 'large' または呼び出し元が system: から始まるユーザー」という式の VAP を、ラベル付きの namespace だけに Binding で絞って適用した。size が large の Widget を一般ユーザーが作成しようとすると ValidatingAdmissionPolicy 'widget-no-large...' with binding '...' denied request: large widgets are reserved と拒否され、small の Widget は通った。--dry-run=server で試しても同じく拒否された(admission は dry-run でも走る、という第 12 回の原則どおり)。

図: matchConstraints でリソース種別を絞り、namespaceSelector でさらに namespace を絞る。両方に一致したときだけ Policy が評価される。

4. validationActions: Deny / Warn / Audit

Binding の validationActions は必須の指定で(省略すると Binding の作成自体が拒否される)、CEL の式が「違反している」と判定したときに何をするかを決める。公式ドキュメントによれば、Deny(リクエストを拒否する)・Warn(警告ヘッダー: HTTP レスポンスに乗せて kubectl などのクライアントがそのまま表示できる警告文を返すが通す)・Audit(監査ログ: API サーバーが「誰が何をしたか」を記録する仕組みに記録するだけで通す)の 3 つがあり、Deny と Warn は同時に指定できない(同じ失敗を API の応答本文と警告ヘッダーの両方に重複して出すだけになるため)。Warn や Audit を使うと、「本当に拒否する前に、まずどれだけのリクエストが引っかかるか様子を見る」という段階的な導入ができる。

図: 同じ違反判定でも、Deny は拒否、Warn は警告つきで通す、Audit は記録だけして通す。

5. MutatingAdmissionPolicy はまだ若い機能

MAP は VAP の書き換え版で、CEL の式で Object{...} のようなパッチを組み立ててオブジェクトを変更する。公式ドキュメントによれば、v1.30 でアルファとして登場し、v1.36 で安定版になった。つまり VAP(v1.30 で安定版)より 6 バージョン分新しく、クラスタのバージョンによっては機能フラグが有効でないことがある。EKS 1.35 のテスト用クラスタで実測したところ、kube-apiserver が外部に出している内部メトリクス(機能フラグごとに有効/無効を 0/1 で示す)kubernetes_feature_enabled{name="MutatingAdmissionPolicy",stage="BETA"} が 0(無効)で、kubectl get mutatingadmissionpolicies を叩くと「the server doesn't have a resource type "mutatingadmissionpolicies"」というエラーになった。「CEL で書き換えたい」という要件があっても、クラスタのバージョンによっては webhook(第 12 回)に頼らざるを得ない場合がある、ということ。

機能の新しさはクラスタごとに運用チームが有効化しているかどうかにも依存する。「ドキュメントに書いてあるから使える」とは限らず、まず対象クラスタで機能フラグと API の存在を確認するのが実務での作法。

図: VAP は v1.30 で安定版、MAP は v1.36 で安定版。バージョンの新しい MAP は無効化されているクラスタもある。

まとめと次の回

CRD 内の CEL(第 06 回)・VAP・webhook(第 12 回)は、同じ「許可するか拒否するか」でも見える範囲と運用の手間が違う。CRD の CEL はそのオブジェクト自身しか見えないが追加のリソースが要らず最も軽い。VAP はパラメータリソースと namespace オブジェクトまでなら見られ、webhook より運用が軽い(VAP 自体は v1.30 で安定版なので、バージョン依存が問題になるのは MAP のほう)。webhook は任意のオブジェクトや外部 API まで何でも見られる代わりに、外部プロセスの可用性と TLS 証明書の運用が付いてくる。

選択肢他オブジェクトを読めるか追加で運用するものいつ選ぶか
CRD の CEL読めない(self/oldSelf のみ)なしフィールド同士の整合性だけで十分なとき
VAP(CEL)パラメータリソースと namespace オブジェクトだけ読めるPolicy + Binding(+パラメータ)webhook は重いが、CRD の CEL だけでは視野が足りないとき
webhook任意のオブジェクト・外部 API も可Pod・Service・TLS 証明書複雑な相関判定や外部システムとの連携が必要なとき

次の第 14 回では、CRD の「複数バージョン」をテーマに、served と storage の違い、そして変換方式を誤ると起きるデータ消失(実測)を見る。

図: CRD の CEL・VAP・webhook は視野の広さと運用コストのトレードオフ。

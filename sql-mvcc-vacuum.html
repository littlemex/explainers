MVCC と VACUUM ― 行は上書きされない

UPDATE も DELETE も既存の行を書き換えず、新しい版を増やすだけである。古い版を回収して空間を取り戻すのが VACUUM の仕事で、これが滞ると肥大化と周回問題が起きる

← SQL シリーズ目次へ

この回の前提: 第 34 回 JSONB の使い所と使わない所 (生成列と pg_stat_user_tables の基本的な読み方)

「UPDATE は行の値をその場で書き換える」という直感は、PostgreSQL では成り立ちません。UPDATE も DELETE も、既存の行には触れず、条件を満たす新しい版を追加するだけです。古い版は、どのトランザクションからも見えなくなった後に、VACUUM という別の処理が回収します。この回では、PostgreSQL 18.6 の実機で xmin/xmax という行の版番号、pageinspect 拡張で見える物理的な証拠、pg_stat_user_tables の dead tuple の増減、そして VACUUM が古い版を回収する様子を順に確かめ、肥大化 (bloat) ・ 自動 VACUUM の閾値 ・ 長いトランザクションが VACUUM を止める理由 ・ XID 周回と凍結までをつなげて見ます。

1. この回で解く問題 ― 「上書き」ではなく「新しい版の追加」

PostgreSQL は MVCC (Multi-Version Concurrency Control, 多版型並行制御) という方式で並行実行を実現しています。MVCC の核心は、1 つの行に対して複数の「版 (バージョン)」を同時に保持できることです。あるトランザクションが行を読んでいる間に、別のトランザクションが同じ行を更新しても、読んでいる側は自分が開始した時点の版を読み続けられます。読み取りが書き込みを待たず、書き込みも読み取りを待たない、という設計の土台がこれです。

この設計を実現するために、PostgreSQL の各行 (正確にはタプル) には xmin (この版を作ったトランザクション ID) と xmax (この版を無効にしたトランザクション ID、まだ無効化されていなければ 0) という隠れた列があります。UPDATE は、古い版の xmax に自分の ID を書き込み (これで古い版はこれ以降のトランザクションから見えなくなる)、新しい値を持つ新しい版を xmin = 自分の ID で挿入します。DELETE も同様に、行の xmax を自分の ID にするだけで、新しい版は作りません。どちらも「書き換え」ではなく「版の追加、または無効化」です。

この仕組みの裏側には代償があります。古い版はすぐには消えず、テーブルの中に残り続けます。これを回収するのが VACUUM です。VACUUM が滞ると、誰からも見えない古い版 (dead tuple) がテーブルに積み重なり、テーブルが肥大化 (bloat) し、検索が遅くなります。この回では、この「版が増える」「VACUUM が回収する」という 2 つの動きを、実際の xmin/xmax の値と EXPLAIN に相当する VACUUM VERBOSE の出力で確かめます。

図: UPDATE は旧版の xmax を更新トランザクションの ID にし、新版を xmin = 自分の ID で追加する。旧版は VACUUM まで残る。

2. 仕組み ― xmin と xmax を実機で見る

sample_schema.sql を読み込んだ直後の bugs テーブルで、隠れた列 xmin ・ xmax ・ 物理的な位置を示す ctid を見てみます。

SELECT bug_id, xmin, xmax, ctid FROM bugs ORDER BY bug_id;
--  bug_id | xmin | xmax | ctid
-- --------+------+------+-------
--       1 | 2893 | 2896 | (0,1)
--       2 | 2893 | 2896 | (0,2)
--       3 | 2893 | 2894 | (0,3)
--       4 | 2893 | 2896 | (0,4)
--       5 | 2893 | 2896 | (0,5)

まだ 1 度も UPDATE していないのに xmax が 0 ではありません。「xmax が 0 でなければ削除された行」という理解は不正確です。この bugs の行は bugs_products や comments から外部キーで参照されており、子テーブルへの INSERT 時に親行へ FOR KEY SHARE ロックが取られ、そのロックの印が xmax に書き込まれています。pageinspect 拡張の heap_page_items で行の生の情報 (infomask というビットの集まり) を見ると、これが削除ではなく「ロックのみ」であることが分かります。

CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT lp, t_xmin, t_xmax, t_infomask,
       (t_infomask & 16)  <> 0 AS xmax_is_keyshare_lock,  -- HEAP_XMAX_KEYSHR_LOCK = 0x0010
       (t_infomask & 128) <> 0 AS xmax_is_lock_only        -- HEAP_XMAX_LOCK_ONLY   = 0x0080
FROM heap_page_items(get_raw_page('bugs',0)) ORDER BY lp;
--  lp | t_xmin | t_xmax | t_infomask | xmax_is_keyshare_lock | xmax_is_lock_only
-- ----+--------+--------+------------+-----------------------+-------------------
--   1 |   2893 |   2896 |        403 | t                     | t
--   2 |   2893 |   2896 |        403 | t                     | t
--   3 |   2893 |   2894 |        403 | t                     | t
--   4 |   2893 |   2896 |        403 | t                     | t
--   5 |   2893 |   2896 |        403 | t                     | t

xmax_is_lock_only が全行で真であることから、この xmax は「この版を削除した」印ではなく「この版をロックしているトランザクションがいる」という印だと分かります。実務では「xmax が 0 でない行が増えた」というだけで「DELETE が多発している」と誤読してしまう場面がありますが、この infomask のビットまで見ないと、ロックと削除は区別できません。

図: xmax が 0 でなくても、infomask の LOCK_ONLY ビットが立っていれば削除ではなくロックの印。FK 参照は親行をこの形でロックする。

3. 仕組み ― UPDATE は版を増やし、VACUUM が回収する

bug_id = 3 の行を 1 回 UPDATE し、前後の xmin ・ xmax ・ ctid を比べます。

UPDATE bugs SET priority = 'HIGH' WHERE bug_id = 3;
SELECT bug_id, xmin, xmax, ctid FROM bugs WHERE bug_id = 3;
--  bug_id | xmin | xmax | ctid
-- --------+------+------+-------
--       3 | 2898 |    0 | (0,6)

SELECT relname, n_live_tup, n_dead_tup, n_tup_upd, n_tup_hot_upd
FROM pg_stat_user_tables WHERE relname='bugs';
--  relname | n_live_tup | n_dead_tup | n_tup_upd | n_tup_hot_upd
-- ---------+------------+------------+-----------+---------------
--  bugs    |          5 |          1 |         1 |             1

UPDATE 後の bug_id=3 は xmin=2898 という新しい版になり、物理的な位置も ctid=(0,3) から (0,6) に変わりました。しかし古い版は消えていません。n_dead_tup (死んでいる版の数) が 0 から 1 に増え、これがテーブルの中に残っている古い版の数です。n_tup_hot_upd も 1 で、この更新が HOT 更新 (Heap Only Tuple) として処理されたことが分かります。HOT 更新は、更新対象の列がどの索引にも含まれておらず、かつ同じページに新しい版を置く空きがある場合に使われる最適化で、索引側を更新しなくて済む分、通常の更新より軽く済みます。

SELECT lp, t_ctid, t_xmin, t_xmax FROM heap_page_items(get_raw_page('bugs',0)) ORDER BY lp;
--  lp | t_ctid | t_xmin | t_xmax
-- ----+--------+--------+--------
--   1 | (0,1)  |   2893 |   2896
--   2 | (0,2)  |   2893 |   2896
--   3 | (0,6)  |   2893 |   2898   ← 旧版。t_ctid が新版 (0,6) を指す
--   4 | (0,4)  |   2893 |   2896
--   5 | (0,5)  |   2893 |   2896
--   6 | (0,6)  |   2898 |      0   ← 新版。これが今の bug_id=3

この heap_page_items の結果が、MVCC の「上書きしない」を直接示す物理的な証拠です。行スロット 3 (lp=3) は消えておらず、t_xmax=2898 (更新したトランザクションの ID) を持ちながら、t_ctid で新しい版の場所 (lp=6) を指しています。これは HOT 更新の連鎖をたどるための仕組みで、索引はまだ古いスロット 3 を指したままでも、索引から辿った先でこのポインタを追って最新の版 (lp=6) に到達できます。

4. 仕組み ― VACUUM は回収するがファイルは縮めない

ここで VACUUM (VERBOSE) を実行すると、古い版が回収されます。

VACUUM (VERBOSE) bugs;
-- tuples: 1 removed, 5 remain, 0 are dead but not yet removable
-- new relfrozenxid: 2893, which is 15 XIDs ahead of previous value

SELECT relname, n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname='bugs';
--  relname | n_live_tup | n_dead_tup
-- ---------+------------+------------
--  bugs    |          5 |          0

tuples: 1 removed が、先ほど増えた 1 件の dead tuple が回収されたことを示しています。n_dead_tup も 0 に戻りました。重要なのは、VACUUM が回収するのは「行スロットを再利用可能にする」ことであり、ファイル自体を小さくするわけではないという点です。次の節でこれをテーブルのサイズで確認します。

5. 仕組み ― fillfactor が HOT 更新率を左右し、肥大化が残る

HOT 更新が使えるかどうかは、ページの中に新しい版を置ける空きがあるかどうかに左右されます。fillfactor (ページを何 % まで詰めて書き込むか、既定は 100) を変えた 2 つのテーブルで、同じだけ行を入れて同じ UPDATE をかけ、HOT 更新率を比べます。

CREATE TABLE ff_full (id int PRIMARY KEY, payload text) WITH (fillfactor=100);
CREATE TABLE ff_room (id int PRIMARY KEY, payload text) WITH (fillfactor=70);
INSERT INTO ff_full SELECT g, repeat('x', 100) FROM generate_series(1,2000) g;
INSERT INTO ff_room SELECT g, repeat('x', 100) FROM generate_series(1,2000) g;
-- 挿入直後のサイズ: ff_full 280 kB, ff_room 400 kB (fillfactor 70 は最初から 30% の空きを確保する分大きい)

UPDATE ff_full SET payload = repeat('y', 100);
UPDATE ff_room SET payload = repeat('y', 100);
SELECT relname, n_tup_upd, n_tup_hot_upd, round(100.0*n_tup_hot_upd/n_tup_upd,1) AS hot_pct
FROM pg_stat_user_tables WHERE relname IN ('ff_full','ff_room');
--  relname | n_tup_upd | n_tup_hot_upd | hot_pct
-- ---------+-----------+---------------+---------
--  ff_full |      2000 |             0 |     0.0
--  ff_room |      2000 |           900 |    45.0

fillfactor=100 の ff_full は、挿入時にページを 100 % まで詰めてしまっているため、UPDATE で新しい版を置く空きが元のページに無く、HOT 更新率は 0 % になりました。全ての行が別のページに新しい版を作る必要があり、テーブルサイズも 280 kB から 552 kB とほぼ倍増しています。一方 fillfactor=70 の ff_room は最初から 30 % の空きを確保していたため、更新の 45 % が同じページ内の HOT 更新で済み、サイズの増加も 400 kB から 624 kB に収まりました。更新が多い列を含むテーブルでは、fillfactor を下げて空きを確保しておくことが、索引の更新コストと肥大化の両方を抑える実務的な対策になります。

VACUUM (VERBOSE) ff_full;              -- tuples: 2000 removed, 2000 remain
SELECT pg_size_pretty(pg_relation_size('ff_full')) AS full_after_vacuum;
--  full_after_vacuum
-- -------------------
--  552 kB                 ← 通常の VACUUM では縮まない

VACUUM FULL ff_full;
SELECT pg_size_pretty(pg_relation_size('ff_full')) AS full_after_vacuum_full;
--  full_after_vacuum_full
-- ------------------------
--  280 kB                 ← VACUUM FULL はテーブルを書き直して縮める

通常の VACUUM は 2000 件の dead tuple を回収しましたが、テーブルのサイズは 552 kB のまま変わりません。回収した空間は「次の INSERT や UPDATE が再利用できる空き」として記録されるだけで、ファイルそのものは縮みません。これに対して VACUUM FULL はテーブル全体を新しいファイルに書き直すため、サイズは 280 kB まで戻ります。ただし VACUUM FULL はテーブルに ACCESS EXCLUSIVE ロック を取るため、実行中はそのテーブルへの読み書きが全て待たされます。本番環境で気軽に実行してよい操作ではなく、第 37 回で扱う「止めずにスキーマを変える」話と地続きの制約です。

図: fillfactor の低さが HOT 更新率を上げ肥大化を抑える。VACUUM FULL は縮むがロックの代償が大きい。

6. 仕組み ― autovacuum はどの時点で動き出すか

手動の VACUUM を毎回実行するのは現実的ではないため、通常は autovacuum という背景プロセスが自動で実行します。発火するかどうかの基準は次の式です。

dead tuple 数 > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples

このサーバーの既定値を確認します。

SHOW autovacuum_vacuum_threshold;     --  50
SHOW autovacuum_vacuum_scale_factor;  --  0.2
SHOW autovacuum_naptime;              --  1min

既定では、1 万行のテーブルなら 50 + 0.2 × 10000 = 2050 件の dead tuple が積もるまで autovacuum は動きません。更新が頻繁な小さいテーブルでは、これでは遅すぎることがあります。ここではサーバー全体の設定を変えず、このテーブルだけ ALTER TABLE ... SET (...) で閾値を下げ、実際に自動発火するところまで実機で待ちます。

CREATE TABLE av_demo (id int PRIMARY KEY, val int);
INSERT INTO av_demo SELECT g, g FROM generate_series(1,200) g;
ALTER TABLE av_demo SET (autovacuum_vacuum_threshold = 5, autovacuum_vacuum_scale_factor = 0.0);
UPDATE av_demo SET val = val + 1 WHERE id <= 50;  -- dead tuple 50 件 (閾値 5 件を超える)

SELECT relname, n_dead_tup, autovacuum_count FROM pg_stat_user_tables WHERE relname='av_demo';
--  relname | n_dead_tup | autovacuum_count
-- ---------+------------+------------------
--  av_demo |         50 |                0

-- autovacuum_naptime (既定 1 分) の次の巡回を待つ
SELECT relname, n_dead_tup, last_autovacuum, autovacuum_count FROM pg_stat_user_tables WHERE relname='av_demo';
--  relname | n_dead_tup |        last_autovacuum        | autovacuum_count
-- ---------+------------+-------------------------------+------------------
--  av_demo |          0 | 2026-10-25 09:40:21.180266+00 |                1

約 1 分後、autovacuum_count が 0 から 1 に変わり、n_dead_tup が 50 から 0 に戻りました。last_autovacuum にタイムスタンプが入ったことからも、人手を介さずに autovacuum が実際に動いたことが確認できます。閾値をテーブル単位で調整できることは、更新頻度がテーブルごとに大きく違う実務でよく使う手段です。ジョブキューのように頻繁に UPDATE/DELETE される小さいテーブルほど、既定値のままでは dead tuple が溜まりやすく、個別に閾値を下げる価値があります。

図: dead tuple 数が閾値を超えると、次の巡回のタイミングで autovacuum が自動的に動く。

7. どこで壊れるか ― 長いトランザクションが VACUUM を止める

VACUUM は「どのトランザクションからも見えなくなった版」しか回収できません。もし古いスナップショットを持ったトランザクションがまだ開いていれば、その版はまだ「見える」可能性があるため、VACUUM は手を付けられません。これを 2 つの psql セッションで実機で再現します。1 本目のセッションで REPEATABLE READ のトランザクションを開いたまま 12 秒間保持し、その間にもう 1 本のセッションで UPDATE と VACUUM を実行します。

-- セッション A (バックグラウンドで保持)
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM bugs;      -- ここでスナップショットが固定される
SELECT pg_sleep(12);
COMMIT;

-- セッション B (こちらで実行)
SELECT pid, state, backend_xmin FROM pg_stat_activity WHERE pid <> pg_backend_pid();
--  pid  | state  | backend_xmin
-- ------+--------+--------------
--  1801 | active |         3078

UPDATE bugs SET priority = 'LOW'  WHERE bug_id = 3;
UPDATE bugs SET priority = 'HIGH' WHERE bug_id = 3;
VACUUM (VERBOSE) bugs;
-- tuples: 0 removed, 7 remain, 2 are dead but not yet removable
-- removable cutoff: 3078, which was 2 XIDs old when operation ended

セッション A の backend_xmin=3078 より新しい版は、A からはまだ見える可能性があるため回収できません。VACUUM の出力 2 are dead but not yet removable が、この「回収できない dead tuple」の数です。removable cutoff: 3078 は、VACUUM がこの時点で安全に回収できる限界の XID が、まさにセッション A の backend_xmin と同じ値で止まっていることを示しています。

-- セッション A が COMMIT した後、もう一度 VACUUM
VACUUM (VERBOSE) bugs;
-- tuples: 2 removed, 5 remain, 0 are dead but not yet removable

セッション A が抜けた後は、同じ 2 件が tuples: 2 removed として回収されました。実務でこれが問題になるのは、バッチ処理やレポート生成で長時間トランザクションを開いたままにするコードや、idle in transaction のまま放置された接続です。こうした長時間のトランザクションが 1 本あるだけで、他のテーブルの VACUUM まで巻き込んで止めてしまうことがあります。

図: セッション A のスナップショットが残っている間、B の VACUUM は対象の版を「回収できない」まま残す。

8. シニアの書き方 ― XID 周回を理解し、凍結に任せる

xmin ・ xmax はトランザクション ID (XID) で、32 bit の符号付き整数として循環します。古い XID と新しい XID の大小比較は「半分より近い方が新しい」という円環の比較で行われるため、約 20 億回トランザクションが進むと、かつて「未来」だった XID が「過去」に見えてしまう 周回 (wraparound) が起きます。これを防ぐ仕組みが 凍結 (freeze) です。凍結された行は特別な印が付き、XID の大小比較を経由せず常に「確定して見える」行として扱われます。

SELECT relname, age(relfrozenxid) AS xid_age, relfrozenxid FROM pg_class WHERE relname = 'bugs';
--  relname | xid_age | relfrozenxid
-- ---------+---------+--------------
--  bugs    |     187 |         2893

VACUUM (FREEZE, VERBOSE) bugs;
-- frozen: 1 pages from table (100.00% of total) had 5 tuples frozen
-- new relfrozenxid: 3080, which is 187 XIDs ahead of previous value

SELECT relname, age(relfrozenxid) AS xid_age_after_freeze FROM pg_class WHERE relname = 'bugs';
--  relname | xid_age_after_freeze
-- ---------+----------------------
--  bugs    |                    0

age(relfrozenxid) は「このテーブルの中で最も古い未凍結の XID が、現在から何トランザクション前か」を表します。普段の VACUUM では、十分に古い版だけを vacuum_freeze_min_age (既定 5000 万) を基準に凍結しますが、VACUUM FREEZE は今すぐ全行を凍結します。凍結された行は、pageinspect の infomask で確認できます。

SELECT lp, t_xmin, t_infomask, (t_infomask & 768) AS frozen_marker  -- 256+512
FROM heap_page_items(get_raw_page('bugs',0)) WHERE t_xmin IS NOT NULL ORDER BY lp;
--  lp | t_xmin | t_infomask | frozen_marker
-- ----+--------+------------+---------------
--   1 |   2893 |       2819 |           768
--   2 |   2893 |       2819 |           768
--   4 |   2893 |       2819 |           768
--   5 |   2893 |       2819 |           768
--   8 |   3079 |      11011 |           768

5 行とも t_infomask 自体の値は違いますが (HASNULL など他のビットの有無で変わる)、HEAP_XMIN_COMMITTED (256) と HEAP_XMIN_INVALID (512) の 2 つのビットが両方立つ (合計 768) という組み合わせは共通しています。この 2 つのビットが同時に立つことは普通ならあり得ない (committed と invalid は矛盾する) ため、PostgreSQL はこの組み合わせを「凍結済み」の印として再利用しています。これが、凍結された行は xmin の値を見ずに常に可視と判定できる理由です。

実務でのシニアの判断は、XID 周回そのものを手動で管理しようとしないことです。autovacuum は autovacuum_freeze_max_age (既定 2 億) に達する前に、通常の巡回とは別に強制的な凍結 VACUUM を実行します。シニアが見るべき指標は age(relfrozenxid) がこの上限にどれだけ近づいているか、そして第 7 節で見た「長いトランザクションが VACUUM を止めていないか」です。大きなテーブルで age(relfrozenxid) が上限に近づいているのに autovacuum が進まない場合、原因はほぼ必ず「止まっている長いトランザクション」か「autovacuum がスケジュールに追いつけないほど更新が多い」のどちらかです。

図: XID は循環するため、凍結された行だけが円環の比較から外れて常に可視と判定される。

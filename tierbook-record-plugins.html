perigraph の記録を「差し込む」: vLLM・vSR・stratoclave を改造せずに tierbook でつなぐ
タグで運ぶのは目印だけ、記録はバイトを持つ場所で作る

結論から。stratoclave のタグや OTel で運んでよいのは「どのリクエストか」を示す目印 (リクエスト ID) だけで、記録そのもの (何が周りにあり、何が答えたか) は、リクエストの中身と重みのバイトを実際に持っている場所で作らないと正しくならない。その場所は vLLM の中にあり、vLLM には改造なしで差し込める公開の口が 3 つあった。だから vLLM・vSR (vLLM Semantic Router)・stratoclave のどれにもパッチは要らず、tierbook には「リクエスト ID で突き合わせて文字列を比べるだけ」の部品 tierbook bind を足した。

この文書でやったこと。4 つの案を Fable 5.2 と 6 往復で比べて設計を決め、vLLM 用のプラグイン・vSR の記録を読む変換器・tierbook bind・Prismyra の修正を作り、東京クラスタの L40S 1 枚で、改造していない vLLM 0.27.1 と改造していない vSR を通して確かめた。vSR を通った 40 件すべてで、vSR が送ったバイトの指紋と vLLM が受け取ったバイトの指紋が一致した。

1. タグで運べないもの

最初の問いは「stratoclave の既存のタグでよいのでは」だった。stratoclave には呼び出し側が付けるタグ (x-sc-task-tag、64 文字まで) や、呼び出しをまとめる ID (x-sc-group-id など) がすでにある。運ぶ道はある。問題は、運ぶ中身を誰が作るかだった。

perigraph の記録は「その場でバイトを持っていた者が計算した指紋」でなければ識別子に使えない (perigraph の決まりでは in_the_request と loaded_by_us だけが識別子を作れる)。呼び出し側が計算してタグに載せた指紋は、途中の vSR が書き換えた後のリクエストを表さない。下の図の赤い箱がその場所で、実際に vSR は頼んでいなくても max_tokens の名前を変えた。

x-sc-task-tag を使わない理由はほかにもある。このタグは「どの仕事か」を表す課金の欄に入る。プロンプトを一語直すたびに変わる指紋を入れると課金の集計が細切れになる。形が崩れたタグは黙って捨てられる決まりなので、記録が欠けても気づけない。tierbook には「欠けているのに同じとみなす」ことが一番困る。

Fable 5.2 と 6 往復した (設計 3 回、パッチを許す場合の組み合わせ 1 回、実装のレビュー 2 回)。表の「記録の確かさ」は、tierbook から見たときに perigraph のどの扱いになるかを書いた。

案やること記録の確かさ壊れる場面判定
(i) 呼び出し側で計算してタグに載せるSDK で指紋を作り、ヘッダや OTel で運ぶ呼び出し側の申告にとどまる。途中の書き換えの後を表さないvSR の書き換え、再送、キャッシュ使わない (拒否のきっかけにだけ使える)
(ii) 残っている記録から tierbook が計算し直すvSR に本文を保存させ、tierbook が読み直す保存した本文が送信後のものなら in_the_requestプロンプトを保存する (秘密が残る)、長い本文は切られるvLLM が置けない相手 (外部の API) のときだけ
(iii) 最後の 1 段に差し込むvLLM の公開の口にプラグインを入れる。vSR と stratoclave は設定だけ本文は in_the_request、重みは loaded_by_usLoRA と複数 GPU の分割 (理由つきの空欄にした)採用
(iv) 本体にパッチを当てるvSR (追加約 1,000 行) と stratoclave (463 行のファイル) に記録を作るコードを足すvSR のパッチは送信後なので正しい。stratoclave のパッチは vSR の手前なので古い上流が動くたびにパッチの当て直しと自前の image の作り直しvSR は不要になった。stratoclave は外部 API の最後の 1 段のときだけ残す

途中で「決まった版に当てるパッチなら使ってよい」と方針が広がった。そこで「パッチは継ぎ目が本当にないところだけ」という条件で組み直した。結果としてパッチは 0 本になった。vSR には知らない項目を通す設定がなく、perigraph_template は 400 で拒否される。ただ、これを通すパッチを持つ費用は行数ではなく「自前の vSR の image を作り続けること」で、得られるのは部品の印 1 つだけだった。だから vSR を通る経路では印を送らない、と決めた (印は not_provided と記録される)。

3. vLLM の改造なしの差し込み口

vLLM 0.27.1 のソースを読むと、外から足せる口が用意されていた。どれも vLLM 自身が「外から足すための口」として公開しているもので、パッチではない。

口どこで動くか使い道ソース (vLLM v0.27.1, 6e448d0)
vllm.general_pluginsすべてのプロセス (API サーバ、エンジン、ワーカー)起動のたびに一度呼ばれ、下の読み込み器を登録するvllm/plugins/__init__.py
register_model_loader と --load-format perigraph重みを読み込むワーカー読み込み器を差し替え、読んだファイルとその型を、読み込んだその場で記録するmodel_loader/__init__.py#L69
--middlewareAPI サーバ受け取ったリクエストのバイトから周りの部品の指紋を取り、応答に記録の番号を 1 つ付けるcli_args.py#L301

重みの指紋は、読み込み器が読む直前に各ファイルを開いておき、その開いたものを通して後から計算する。途中でファイルが差し替わったら (同じ場所に別のファイルが置かれたら) 記録しない。読み込んでいないファイル (古い分割ファイルなど) は指紋に入らない。数値の型も、設定ではなく読み込み後の重みそのものから数える。

応答のヘッダに識別子そのものは載せない。識別子は「この system 文を使ったか」を確かめる手がかりになる (候補を全部 hash して比べられる) ので、外から呼ぶ相手にはリクエストごとの番号だけを返す。

4. tierbook は突き合わせるだけ

tierbook に足した tierbook bind は、記録の中身を読まない。各システムの記録を、そのシステムの側にある変換器が「hop 行」(リクエスト ID・本文の指紋・識別子の文字列だけの 1 行) に直し、tierbook はそれをリクエスト ID で結んで、文字列が等しいかだけを見る。tierbook がプロンプトや vSR の記録の形を知らないまま、腕の識別子が埋まる。

「受け取った番号 = その記録」の検査は、レビューで足した。vSR が 1 つ目の行き先で失敗して別の行き先に回したとき、vLLM には「失敗した 1 件の記録」が残る。番号で結ばないと、その記録の識別子が別の行き先の答えに付いてしまう。呼び出し側は応答の x-perigraph-record を対応表に書くだけでよく、--require-record を付けると番号のない呼び出しを拒否する。

5. 実機で出た識別子

同じ 20 問を 3 通りの道で聞いた。モデル側の識別子は 3 つとも同じで、周りの識別子は 3 つとも違った。直接と vSR 経由の違いは max_tokens の名前だけで、vLLM はどちらも同じ上限として扱う。分け過ぎは安全な側の誤りだが (違うものを同じとみなすよりよい)、この分け方を続けると「直接測った腕」と「vSR 経由で測った腕」が永遠に比べられない。perigraph の提案 0005 に選択肢を書いた。

6. vSR の調査で見つかったことへの対応

見つかったこと対応
vSR が残すのは送信バイト全体の指紋だけそれで足りた。vLLM 側の受信バイトの指紋と等しいかを見る「照合」に使う。識別子は vLLM 側で作る
vSR は知らない項目を 400 で拒否する (perigraph_template が通らない)設定で変えられないことをソースで確かめた (DefaultPolicy() が固定)。パッチは持たず、vSR を通る経路では印を送らない。上流への提案の材料にする
Prismyra の chat の入口が system 文を無視する (60 問中 60 問が同じ答え)無視は Prismyra の決まりどおり (学習した問いの文で答える作り) だった。悪かったのは「無視した」と言わないこと。応答に「使った部分」と「使わなかった部分」を必ず書くようにし、Prefer: handling=strict を付けると使わない system 文や tools を 422 で断るようにした。perigraph には提案 0004 (答えた側が「読まなかった部品」を宣言する) を書いた
chart は configMap.applyValuesRevision を変えないと設定が入れ替わらない今回も設定を変えるたびに値を変えて入れ替えた。vSR の記録は既定でメモリにしかなく、設定を入れ替えると消えるので、変える前に読み出した (vSR の README に書いた)

7. まだ残っていること

stratoclave のブランチは作り直していない。feat/perigraph-harness (push 済み、未マージ) は「vSR の手前で指紋を取る」ので vSR 経由では使えない。外部の API に送る最後の 1 段としてだけ働くよう、経路ごとの設定・JSONL への書き出し・送る前に perigraph_template を外す、の 3 点の作り直しが要る。今回は手を付けていない。

残りなぜ残ったか
Prismyra の修正を main に入れるブランチまで push した。GPU のテスト (tests/test_gpu.py の 48 件) が、別のジョブが GPU を 15 GB 使っていて 33 GB を確保できず全部エラーになった。GPU 以外の 755 件は通った。全部が緑になるまで main に入れない
サーバ側の既定値 (--chat-template、generation_config.json の既定) が識別子に入らないリクエストにも重みの読み込みにも出てこないため。プラグインの README に「ここだけが違う 2 台は同じ識別子になる」と書いた。識別子に入れるには perigraph の版を上げる必要がある
複数 GPU の分割 (tensor / pipeline parallel) と LoRAどちらも理由つきの空欄にした。GPU 1 枚では分割を試せない
image に焼いて動かす今回は既存の vLLM の横に pip install --target で入れて動かした。distributed-ai の chart と image の経路ではまだ動かしていない
直接と vSR 経由の識別子のずれ (提案 0005)名前の別名を同じとみなすか、運用者が「同じ腕」と宣言するか、の判断が要る

まとめ。タグは目印を運ぶ道として使い、記録はバイトを持つ最後の 1 段で作る。vLLM は公開の口 3 つで改造なしに両方の半分を出せ、vSR は自分の記録の指紋で「同じものを送った」と示せ、tierbook は突き合わせて文字列を比べるだけで済んだ。パッチは 0 本。

シー・ノー・エビル ― エラーを見ない

PostgreSQL では 1 つのエラーでトランザクション全体が中断状態になり、以降のコマンドはすべて無視される

← SQL シリーズ目次へ

この回の前提: 第 21 回 SQL インジェクション (PL/pgSQL の EXECUTE と DO ブロックの基本)

この回が答える問いは「SQL の実行結果 (成功か失敗か) を確認しないと、何が起きるか」です。結論を先に言うと、PostgreSQL では 1 つの文が失敗すると、そのトランザクションは「中断状態」になり、COMMIT までの残りのコマンドはすべて実行されずに無視されます。エラーを戻り値として確認しない書き方をしていると、本当は 1 件も処理されていないのに、アプリケーションは「成功した」と思い込んでしまいます。この回では、この中断状態を実機で再現し、SQLSTATE や GET STACKED DIAGNOSTICS でエラーを正しく捕まえる方法を見ます。

1. 目的 ― 何をしたかったのか

複数の SQL 文をまとめて実行するとき、途中の 1 文が失敗したらどうなるかを正しく理解しておく必要があります。多くのプログラミング言語では、例外を投げた関数の呼び出し元で catch しなければプログラムが止まりますが、SQL の実行結果 (成功したか、何件処理されたか) を毎回確認するのは面倒に感じられ、省略してしまいがちです。この回では「確認を省略すると何が起きるか」を実際に確かめます。

2. アンチパターン ― どう書いてしまい、何が壊れるか

トランザクションの中で 1 つの文が失敗すると、PostgreSQL はそのトランザクション全体を「中断状態 (aborted)」にします。中断状態になると、COMMIT または ROLLBACK が来るまで、以降のどんなコマンドも実行されずに同じエラーを返します。

BEGIN;
INSERT INTO accounts (account_name, email) VALUES ('alice', 'dup@example.com');
ERROR:  duplicate key value violates unique constraint "accounts_account_name_key"
DETAIL:  Key (account_name)=(alice) already exists.

INSERT INTO accounts (account_name, email) VALUES ('eve', 'eve@example.com');
ERROR:  current transaction is aborted, commands ignored until end of transaction block

SELECT count(*) FROM accounts;
ERROR:  current transaction is aborted, commands ignored until end of transaction block

COMMIT;
ROLLBACK

ここで重要なのは、2 番目の INSERT (eve の挿入) 自体には何の間違いもないことです。それでも「トランザクションが中断状態である」という理由だけで実行が拒否されています。さらに最後の COMMIT も、中断状態のトランザクションに対しては自動的に ROLLBACK として扱われます。実際に、このやり取りの後で eve が保存されているか確認すると 0 件です。

SELECT count(*) AS eve_rows_after_ignored_errors FROM accounts WHERE account_name = 'eve';
 eve_rows_after_ignored_errors
--------------------------------
                              0

アプリケーションのコードが、各文の実行結果 (エラーかどうか) を確認せずに「次の文を投げて、最後に COMMIT を呼ぶ」という処理だけを行っていた場合、開発者は eve の登録が成功したと思い込んでしまいます。実際には最初のエラーの時点で、それ以降の処理は何も行われていません。

図: 最初のエラーの後、トランザクションが終わるまで以降のすべてのコマンドが無視される。

3. 見つけ方 ― どんな兆候で気づくか

アプリケーションがエラーを無視していないかを完全に外側から判定することはできませんが、pg_stat_database でデータベース全体のロールバック率を見ると、エラーがどれくらい頻発しているかの手がかりになります。

SELECT datname, xact_commit, xact_rollback,
       round(100.0 * xact_rollback / GREATEST(xact_commit + xact_rollback, 1), 2) AS rollback_pct
FROM pg_stat_database WHERE datname = current_database();

 datname | xact_commit | xact_rollback | rollback_pct
---------+-------------+----------------+--------------
 sql_23  |          25 |              0 |         0.00

通常の運用でロールバック率が高いデータベースは、アプリケーションが頻繁にエラーを起こし、気づかずに (あるいは気づいても特に対処せずに) ロールバックさせている可能性があります。あわせて、エラーが起きたときに実行された SQL 文そのものをログに残すかどうかは log_min_error_statement で決まります。

SHOW log_min_error_statement;
 log_min_error_statement
--------------------------
 error

この設定が error であれば、エラーレベルが ERROR 以上の問題が起きたとき、その原因となった SQL 文自体もログに記録されます。エラーの発生有無だけでなく、どの SQL が原因だったかまで追跡できるようにしておくことが、問題に気づくための前提になります。

4. 使ってよい場合

「エラーを無視する」ことそのものが許される場面はありませんが、「想定内の失敗を、明示的な方法で無視する」のは正しい設計です。例えば「既に同じ名前のアカウントがあれば、何もしない」という仕様であれば、ON CONFLICT DO NOTHING で明示的にその意図を書きます。

INSERT INTO accounts (account_name, email) VALUES ('alice', 'dup5@example.com')
ON CONFLICT (account_name) DO NOTHING;
INSERT 0 0

SELECT count(*) AS alice_rows FROM accounts WHERE account_name = 'alice';
 alice_rows
------------
          1

INSERT 0 0 という結果からも、0 件が挿入されたことが分かります。これはエラーではなく、「重複した場合は何もしない」という仕様が正しく実行された結果です。重要な違いは、見ないふりをして「たまたまエラーが起きなかった」のではなく、「この種類の失敗は想定済みで、こう処理する」と明示的に書いてあることです。

5. 解決策 ― PostgreSQL での正しい書き方

5.1 SQLSTATE と SQLERRM でエラーの種類と内容を確認する

PL/pgSQL では、エラーを EXCEPTION WHEN 句で捕まえられます。SQLSTATE はエラーの種類を表す 5 文字のコードで、unique_violation のような条件名に対応しています。

DO $$
BEGIN
  INSERT INTO accounts (account_name, email) VALUES ('alice', 'dup2@example.com');
EXCEPTION WHEN unique_violation THEN
  RAISE NOTICE 'caught SQLSTATE=%, message=%', SQLSTATE, SQLERRM;
END;
$$;

NOTICE:  caught SQLSTATE=23505, message=duplicate key value violates unique constraint "accounts_account_name_key"

SQLSTATE の値 23505 は一意性制約違反を表すコードで、unique_violation という条件名と対応しています。この条件名を WHEN に指定することで、「重複エラーだけを捕まえ、それ以外のエラーはそのまま伝える」という選択的な処理ができます。あらゆるエラーを無差別に WHEN OTHERS で握りつぶすのではなく、想定している種類のエラーだけを指定することが大切です。

5.2 GET STACKED DIAGNOSTICS でさらに詳しい情報を得る

エラーメッセージだけでは、どの制約・どのテーブルが原因かを機械的に取り出しにくいことがあります。GET STACKED DIAGNOSTICS を使うと、エラーの詳細情報を個別の変数として取得できます。

DO $$
DECLARE
  v_message text; v_detail text; v_constraint text; v_table text;
BEGIN
  BEGIN
    INSERT INTO accounts (account_name, email) VALUES ('alice', 'dup3@example.com');
  EXCEPTION WHEN unique_violation THEN
    GET STACKED DIAGNOSTICS
      v_message = MESSAGE_TEXT, v_detail = PG_EXCEPTION_DETAIL,
      v_constraint = CONSTRAINT_NAME, v_table = TABLE_NAME;
    RAISE NOTICE 'message=%, detail=%, constraint=%, table=%', v_message, v_detail, v_constraint, v_table;
  END;
END;
$$;

NOTICE:  message=duplicate key value violates unique constraint "accounts_account_name_key",
         detail=Key (account_name)=(alice) already exists.,
         constraint=accounts_account_name_key, table=accounts

CONSTRAINT_NAME や TABLE_NAME まで個別に取得できるため、エラーをログに書くときや、監視システムに送るときに、文字列を正規表現で解析するような脆い処理をせずに済みます。

5.3 失敗を局所化する (部分的な復帰)

PL/pgSQL の入れ子になった BEGIN ... EXCEPTION ... END ブロックは、内部で暗黙的に SAVEPOINT を切るのと同じ効果を持ちます。これにより、1 か所の失敗が、取引全体を中断状態にすることを防げます。

DO $$
BEGIN
  INSERT INTO accounts (account_name, email) VALUES ('frank', 'frank@example.com');
  BEGIN
    INSERT INTO accounts (account_name, email) VALUES ('alice', 'dup4@example.com');
  EXCEPTION WHEN unique_violation THEN
    RAISE NOTICE 'inner failure recovered, continuing: %', SQLERRM;
  END;
  INSERT INTO accounts (account_name, email) VALUES ('grace', 'grace@example.com');
END;
$$;

NOTICE:  inner failure recovered, continuing: duplicate key value violates unique constraint "accounts_account_name_key"

SELECT account_name FROM accounts WHERE account_name IN ('frank','grace') ORDER BY account_name;
 account_name
--------------
 frank
 grace

frank と grace はどちらも正しく保存されています。alice の重複だけが内側のブロックで局所的に失敗し、外側の処理は中断されずに続きました。素の SQL (psql から直接) でも、同じ考え方を SAVEPOINT/ROLLBACK TO で実現できます。

BEGIN;
INSERT INTO accounts (account_name, email) VALUES ('henry', 'henry@example.com');
SAVEPOINT before_risky;
INSERT INTO accounts (account_name, email) VALUES ('alice', 'dup6@example.com');
ERROR:  duplicate key value violates unique constraint "accounts_account_name_key"
ROLLBACK TO before_risky;
INSERT INTO accounts (account_name, email) VALUES ('irene', 'irene@example.com');
COMMIT;

SELECT account_name FROM accounts WHERE account_name IN ('henry','irene') ORDER BY account_name;
 account_name
--------------
 henry
 irene

ROLLBACK TO before_risky によって、トランザクションの状態は SAVEPOINT を置いた時点まで巻き戻り、中断状態も解除されます。これにより henry と irene の両方が正しく保存され、COMMIT も成功しています。

図: SAVEPOINT とROLLBACK TO により、1 か所の失敗だけを巻き戻してトランザクション全体を救う。

6. PostgreSQL エンジンで考慮しておくこと

PostgreSQL がトランザクションを中断状態にする理由は、データの整合性を守るためです。1 つの文が失敗した後も平然と残りの文を実行してしまうと、「本来は依存関係のある一連の処理のうち、途中だけが成功した」という中途半端な状態が生まれかねません。中断状態という仕組みは、「ここまでの変更はまだ確定していない」ことを強制的に思い出させ、開発者に ROLLBACK か、エラーを踏まえた修正を要求します。この挙動は不便に見えますが、「気づかないまま一部だけ実行される」事故を防ぐための安全装置です。

アプリケーションの接続ライブラリの多くは、SQL 実行でエラーが起きると例外 (exception) を投げる設計になっています。言語やライブラリによっては、この例外を catch してログに出すだけで処理を継続できてしまうため、「catch してはいるが、何もしていない」という見た目だけの対処が生まれやすい場所でもあります。この回で確認した SQLSTATE ・ GET STACKED DIAGNOSTICS ・ ON CONFLICT ・ SAVEPOINT は、いずれも「エラーを握りつぶす」のではなく「エラーの種類を見て、適切に反応する」ための道具です。どの道具を使うにしても、エラーを catch すること自体がゴールではなく、catch した後に正しい分岐 (想定内なら処理を続ける、想定外なら呼び出し元に伝える) をすることがゴールだという点は変わりません。

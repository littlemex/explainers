既定値 (defaulting)

← カスタムコントローラー自作 シリーズ目次へ

第 06 回で見た検証は「書いた値が正しいか」を見る仕組みだった。この回で見る既定値(defaulting)は、その逆で「書かなかった値をどう埋めるか」を決める仕組み。驚くのは、既定値が入るタイミングが作成時だけではないこと。

スキーマに default を書いておくと、値を省略したときに API サーバーが自動で埋めてくれる。しかもこれは作成時だけでなく、更新時、さらには保存データをそのまま GET で読み出す瞬間にも働く。既存のデータを一切書き換えていなくても、スキーマに default を後から追加するだけで、読み出した結果には新しい値が現れる。

既定値とは何か、なぜ要るか

CRD のスキーマのフィールドに default を書くと、その値を省略したときに自動で埋められる。実験用 Widget は size: {enum: [small, large], default: small}、replicas: {minimum: 0, maximum: 10, default: 1}、minReplicas: {minimum: 0, default: 0} を持つ(第 05 回の CRD の YAML)。

既定値が無ければ、利用者は毎回すべてのフィールドを書かなければならないし、人によって「省略したら 0 にする」「省略したら 1 にする」のような思い込みがバラバラになりかねない。スキーマに default を書けば、クラスタ全体で「省略した場合の値」が 1 つに決まる。kubebuilder で CRD を作る場合、この default は YAML に直接書くのではなく、Go の struct のフィールドに付けるマーカー // +kubebuilder:default=1 から controller-gen が生成する(第 05 回で見たマーカー → CRD YAML の流れと同じ)。

図: 省略されたフィールドは、スキーマの default で自動的に埋まる

既定値はいつ入るか: 作成時・更新時・読み出し時

既定値が入るタイミングは 3 つある(公式ドキュメント): API サーバーへのリクエスト(作成・更新)の中で、etcd から読み出すとき(保存バージョンの既定値で)、そして mutating admission plugin が何か変更を加えた後(admission webhook が使うバージョンの既定値で、第 12 回)。つまり、GET で読むだけの操作にも既定値は働く。

実測(EKS 1.35 のテスト用クラスタ): スキーマに tier: {type: string, default: gold} を後から追加したところ、何も書き換えていない既存の Widget b を GET すると、spec に "tier":"gold" が入っていた。etcd に保存されている実データは変わっていないのに、読み出した結果には新しい既定値が現れる。

図: 保存データは変わっていないのに、読み出し時に既定値が足される(実測)

pruning・default・required・nullable の関係

値の省略には 2 つの形がある。フィールドをそもそも書かない場合と、明示的に null を書く場合。公式ドキュメントによれば、nullable を指定していない(または false)フィールドに null を書くと、まず pruning でその null が刈り込まれ(フィールドが無かったことになる)、その後に default が適用される。nullable: true のフィールドに明示的に null を書いた場合は、pruning で消されずに null のまま保たれ、default は適用されない。

default は「値が無いフィールド」を埋める仕組みなので、required(必須)なフィールドに default がある場合、省略しても default で埋まり、その後の required のチェックでは「ある」と判定される。実験用 Widget では image が required だが default は無いため、省略すると埋めるものが無く拒否される。一方 size は default があるため、省略しても拒否されない。

フィールドを省略default があれば埋まるdefault があれば埋まる
明示的に null を書くpruning で消え、default が入るnull のまま保たれ、default は入らない

図: null → pruning → default の順で処理される

誰が埋めるか: スキーマの default と Go 側のコード

既定値を埋める方法は、スキーマの default だけではない。コントローラーの Go コードの中で「値が空なら 1 を使う」のように埋めることもできる。しかし、この 2 つは効果が違う。スキーマの default は API サーバーが返す値そのものに効く(作成・更新時は保存もされ、前の節で見たとおり読み出し時にも補われる)ので、kubectl を使う人も、別のコントローラーが使う client-go も、直接 REST API を叩く人も、全員が同じ値を見る。Go コードの中だけで埋める場合は、そのコントローラーが読んだときだけ値が補われ、保存データや他のクライアントから見える値は空のままになる。

そのため、「クラスタ全体で省略時の意味を 1 つに揃えたい」ような値はスキーマの default に、「コントローラーの実装の都合で一時的に使う値」は Go 側のコードに、という分担が自然になる。

図: 効く範囲がスキーマの default のほうが広い

webhook や Policy で入れる既定値との違い

既定値を入れるもう 1 つの手段が、mutating webhook や MutatingAdmissionPolicy(CEL で書く、webhook を立てずに値を変える仕組み)。これらはスキーマの default より自由度が高い。webhook はコードを自由に書けるので、任意の他のオブジェクトを読んでから値を決めるような複雑な既定値も作れる。MutatingAdmissionPolicy は CEL の中で参照できる対象がパラメータ用のリソースや namespace などに限られ、webhook ほど自由ではない。webhook は別のプログラムを立てて管理する必要があり、落ちているとリクエストが失敗する危険もある(API サーバーの中で CEL を評価する MutatingAdmissionPolicy にはこの危険が無い)。スキーマの default は API サーバー自身が処理するので、こうした外部依存が無い。両者の詳しい比較は第 12・13 回で扱う。

図: webhook だけが外部プロセスへの依存を持つ(MutatingAdmissionPolicy は API サーバーの中で CEL を評価する)

まとめと次の回

既定値は作成時だけでなく、更新時、そして読み出し時にも入る。nullable でないフィールドに書いた null は pruning で先に取り除かれ、default がその後を埋める(スキーマに存在しない未知フィールドを刈り込む pruning 本来の仕組みと同じ土台の上で動く)。required なフィールドも default があれば省略できる。クラスタ全体で意味を揃えたい値はスキーマの default に、他のオブジェクトを見てから決めるような複雑な既定値は webhook に任せる、という分担がある。

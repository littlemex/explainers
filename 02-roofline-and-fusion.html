Roofline とカーネル融合 ― なぜ手でカーネルを書くのか

理論上限を「測り」、メモリ往復を「消す」。その実例として RMSNorm と QKV 射影の融合まで

0この記事の狙い

第 1 回でハードウェアの階層 (速いオンチップ / 遅い HBM) を学びました。今回は「その地図の上で、なぜわざわざ手でカーネルを書くのか」を一歩深掘りします。答えになる実測を先に見せます。

一言でいうと
高速化の鍵は「遅い HBM への往復を減らす」の一点です。それを (A) ギャップを測る物差し Roofline、(B) 往復を消す手法 カーネル融合、(C) 実例 RMSNorm と QKV 射影の融合、の順で解き明かします。同じ数式・同じ答えでも、往復を消すだけで桁違いに速くなる ― それが手でカーネルを書く理由です。
先に結論 (NKI Workshop の実測)。小さな Llama 風モデルの推論で、同じ計算を 3 通りの実装で回すと:
・素の PyTorch 演算 (base): 24 tok/s
・NKI カーネル化 (core): 78 tok/s
・RMSNorm + QKV 射影 + RoPE + Attention + KV cache + 出力射影を 1 つのカーネルに融合 (megakernel): 410 tok/s (base 比 約 17 倍)
(small モデル・128 プロンプト・greedy・torch.compile・Trn2.3xlarge)

対象は AWS Trainium2。数値は NKI Workshop の講義・実測に基づく概算です。前提となる第 1 回「ハードウェア階層」を先に読むと理解が早いです。

1【体験】Roofline ― 計算律速かメモリ律速か

最適化の第一歩は「今どっちで詰まっているか」を知ること。それを 1 枚で示すのが Roofline モデルです。

処理の速さの上限は 2 つの要因で決まります。計算エンジンの速さ(compute)とメモリからデータを運ぶ速さ(memory)。どちらが上限になるかは、演算強度 (Arithmetic Intensity) = 「運んだ 1 バイトあたり何回演算するか」で決まります。

演算強度 (FLOP/byte)
メモリ律速の坂 (帯域で頭打ち) 計算律速の天井 (演算器で頭打ち) いまの処理

スライダーで演算強度を動かすと、赤い点が屋根の上を移動します。ridge point (折れ点) より左はメモリ律速 ― データ待ちで演算器が遊んでいる。右は計算律速 ― 演算器を使い切っている。左にいるなら打ち手は「データ移動を減らす」、右にいるなら「演算そのものを速く/減らす」。どっちのゾーンにいるかで、やるべきことが正反対になります。だからまず Roofline で現在地を知るのです。

演算強度が低い処理 (要素ごとの演算・正規化・小さな行列積) は左=メモリ律速に落ちやすい。演算強度が高い処理 (大きな行列積) は右=計算律速になりやすい。ridge point はハードウェアが決めるので、プロファイラが「あなたの処理の演算強度」と「ridge point」を教えてくれます。

2ハードウェアエンタイトルメント ― 理論と実測のギャップ

Roofline の「天井」は、紙と鉛筆で数値として見積もれます。これがハードウェアエンタイトルメント (理論上限) です。

やり方は物理の「距離 ÷ 速さ = 時間」と同じ。やるべき仕事量 (FLOP) ÷ ハードウェアの速さ (FLOPS) = かかるべき時間です。

# 例: 4096×1024 と 1024×4096 の行列積 (BF16, Tensor Engine)
仕事量 = 4096 × 1024 × 4096 × 2 ≈ 34 GFLOP  # ×2 は 乗算+加算
速さ = 78.6 TFLOPS  # Tensor Engine の bf16 ピーク (第1回: 1コアあたり BF16 dense で78.6 TFLOPS、FP8なら158 TFLOPS)
時間 = 34e9 / 78.6e12 ≈ 437 マイクロ秒  # これが理論上限

この見積もりは「本来これくらいで終わるはず」というターゲットを与えます。実測がこれに近ければ、もう触る必要はありません。遠ければ、そのギャップが「手で最適化する余地」そのものです。

この「仕事量 ÷ 速度 = 時間」の計算過程を可視化します。行列積 A (M×K) × B (K×N) のサイズをスライダーで変えると、① 仕事量 (FLOP) の数え方、② それを 78.6 TFLOPS で割る、③ 出てくる理論上限時間、が連動します。

核心は「出力の要素数 (M×N) それぞれに、K 回の積和 (=2K FLOP) がかかる」= 2·M·K·N FLOP。これをハードの速さ 78.6 TFLOPS で割れば時間が出ます。行列を大きくすると仕事量が増え、時間も比例して伸びるのが見て取れます。この見積もりが「本来これくらいで終わるはず」というターゲットになり、実測との差が手で最適化する余地です。

これが動機になる理由。「なんとなく遅い」ではなく 「理論上 X μs のはずが実測 Y μs、ギャップ Z μs」と言える。ワークショップの Attention チュートリアルでは、理論上限 ~150μs に対し素朴な実装が約 850μs。最適化を積んで約 240μs まで縮めました。ギャップが数値で見えるから、どこまで縮むか・あと何をすべきかが分かるのです。

もう一つの例: Attention 全体の見積もり (クリックで展開)

QKᵀ と (スコア)V の 2 つの行列積が各約 54μs (128×4096²×2 ÷ 78.6 TFLOPS)、合わせて約 109μs。さらに softmax を Vector Engine (bf16 で約 2 TFLOPS) で約 41μs。合計約 150μsがこの Attention のエンタイトルメント。matmul は Tensor Engine が速いので軽く、要素ごとの softmax が相対的に効くのが分かります。

3ギャップの正体 ― メモリ往復

「メモリ律速」と診断された。ではデータ移動を減らすには? ここでカーネル融合が登場します。

汎用フレームワークは演算を1 つずつ別々に実行します。各演算は「HBM から SBUF に読む → 計算 → HBM に書き戻す」を繰り返す。演算が 3 つあれば、中間結果が3 回 HBM に降りて、また昇ってくる。第 1 回で見たとおり HBM は遅く、この往復こそがギャップの主因です。

# 融合なし: 演算ごとに HBM を往復
演算1 → HBM に中間結果を書く → 読み直す → 演算2 → 書く → 読む → 演算3

# 融合あり: 中間結果を SBUF に留めたまま繋げる
演算1 → (SBUF 上) → 演算2 → (SBUF 上) → 演算3 → 最後に1回だけ HBM へ

カーネル融合 (kernel fusion) とは、複数の演算を 1 つのカーネルにまとめ、中間結果を遅い HBM に書き戻さず、速い SBUF (オンチップ) に留めたまま次の演算に渡すことです。往復が消えるぶん、メモリ律速な処理が一気に速くなります。特に中間結果が SBUF に収まらず HBM へあふれる (spill) のを防げるのが大きい。

4【体験】カーネル融合 ― 往復を消す

この記事の「絵で覚えて帰ってほしい 1 枚」です。融合前後で、中間結果が HBM を往復するか SBUF に留まるかを見比べてください。

HBM (遅い) SBUF (速い・オンチップ) 中間結果の移動

融合なしでは、演算 1・2・3 のあいだで中間結果がHBM まで降りて、また昇るのを繰り返します (赤い往復)。融合ありに切り替えると、入力を 1 回読んだあとはSBUF の上だけで 3 演算を繋げ、結果を 1 回書き戻すだけ。HBM 往復の回数が激減します。第 1 回の「HBM は遅い、SBUF は速い」がそのまま効いてくる場面です。

5実例 ― RMSNorm と QKV 射影の融合

抽象論を、Transformer で実際に隣り合う 2 つの処理で具体化します。前章のアニメが、そのまま現実の層で起きます。

Transformer の各ブロックの入口では、RMSNorm (正規化) の直後に QKV 射影 (行列積) が続きます。RMSNorm の中身は 2 種類の処理でできています。

  1. reduction (集計): ベクトルの全要素の二乗を合計する (二乗平均平方根 RMS を出すため)。全要素を「なめて」1 つの値に畳む処理。
  2. element-wise (要素ごとの演算): その RMS で各要素を割り、スケールを掛ける。要素ごとに独立。

この RMSNorm は演算強度が低く、単体ではメモリ律速 (第 1 章の Roofline で左側)。だから素朴に「RMSNorm を実行 → HBM に書く → 読み直して QKV 射影」とやると、往復で損をします。

やってはいけない例 (ワークショップの "bad" 実装)。RMSNorm を 3 回に分けて (3-pass: 二乗和 → 正規化 → スケール) それぞれ HBM 往復すると、遅い実装の見本になります。ワークショップではこれを「what not to do」として比較に使っています。
良い実装。RMSNorm の reduction と element-wise を 1 パスで SBUF 上に済ませ、その出力を HBM に降ろさず、そのまま QKV 射影の行列積に流し込む。正規化の結果という中間テンソルが HBM を往復しない。前章のアニメの「演算1→2→3 を SBUF 上で繋ぐ」が、まさに「RMSNorm → 射影」で起きています。

数式で書くと、1 本のトークンベクトル x (d 次元) に対して次の流れです。融合とは、この一連の計算を途中結果を書き出さずに左から右へ一気に通すことに他なりません。

# RMSNorm (reduction → element-wise)
ms = (1/d) ∑ᵢ xᵢ²  ← reduction: 全要素の二乗を1つに畳む
x̂ᵢ = xᵢ / √(ms + ε) · gᵢ  ← element-wise: 各要素を割ってスケール

# QKV 射影 (行列積) ― 正規化後の x̂ をそのまま入力に
Q = x̂ W_q   K = x̂ W_k   V = x̂ W_v  ← matmul

下の図で、この数式が 1 ステップずつどう計算されるかを追えます。ボタンで進めると、二乗和 → RMS で割る → スケール g → 重み W_q との行列積で Q が出る、が順に光ります。正規化後の x̂ を HBM に書き出さず、そのまま行列積の入力にするのが融合です。

入力 x reduction (二乗和→RMS) 正規化後 x̂ 重み W_q と行列積 → Q

ここで効くのが第 1 章の Roofline です。RMSNorm は演算強度が低くメモリ律速 (要素を 1〜2 回触るだけ) なので、途中結果を HBM に往復させると損が大きい。だから正規化の出力 x̂ を降ろさず、演算強度の高い行列積 (QKV 射影) の入力に直結させる ― これが「融合」の中身です。

ワークショップの megakernel はこれをさらに推し進め、RMSNorm + QKV 射影 + RoPE + Attention + KV cache 更新 + 出力射影という 1 ブロック丸ごとを単一カーネルに融合しました。ブロック内の中間結果が一度も HBM に降りない。これが冒頭の base 比 17 倍の正体です。

融合には工夫が要る (この先は後続の章で)

reduction は「全要素を見ないと答えが出ない」ため、どのエンジンでどの順に計算し、どこで同期するかに設計が要ります。また行列積のタイルサイズ、レイアウト、bf16 の非結合性(足す順番で結果が変わる性質)による数値誤差など、踏み込むべき論点が続きます。これらは第 3 回以降で扱います。この記事では「隣り合う処理を融合すると往復が消えて速い」という発想が現実の層でそのまま効く、という一点を持ち帰ってください。

6まとめ

「なぜ手でカーネルを書くのか」への答えを一枚に整理します。3 つの話が 1 本につながります。

論点要点
Roofline演算強度 (FLOP/byte) で計算律速かメモリ律速かが分かる。ゾーンで打ち手が正反対
エンタイトルメント仕事量 (FLOP) ÷ ハード速度 (FLOPS) = 理論上限。実測との差が最適化の余地
ギャップの正体メモリ律速の主因は、遅い HBM への中間結果の往復
カーネル融合複数演算を 1 カーネルにまとめ、中間結果を SBUF に留めて HBM 往復を消す
RMSNorm + QKV 射影の融合正規化 (reduction + element-wise) の出力を降ろさず行列積へ。実際の隣接層で効く
実測インパクトブロック丸ごとの融合 (megakernel) で base 比 約 17 倍 (410 vs 24 tok/s)
結論。(A) Roofline で「理論上これだけ速いはず」というターゲットと実測のギャップを定量化する。ギャップの主因は遅い HBM への往復 (メモリ律速)。(B) カーネル融合で、中間結果を SBUF に留めて往復を消す。(C) その発想は RMSNorm + QKV 射影のような現実の隣接処理でそのまま効き、ブロック丸ごとの融合で 17 倍に届く。
汎用フレームワークは演算を 1 つずつ実行するので、この往復を自動では消せない。「理論上限が見えていて、原因も分かっているのに、自動では埋まらない」― そのギャップを自分の手で埋めるのが、カーネルを書く理由です。次回はこの融合の本命 FlashAttention を掘り下げます。

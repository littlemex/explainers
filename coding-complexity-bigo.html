CODING ・ シリーズ 第 2 回

計算量と Big-O ― 増え方だけを測る言葉

$O$ は速さではなく増え方の上限。定数を捨てた理論が、なぜ実測とつながるのか

← コーディング基礎 シリーズ目次へ

計算量は「このコードは何秒かかるか」を言う言葉ではありません。入力を大きくしたときにコストがどう増えるかだけを言う言葉です。この回では $O$・$\Theta$・$\Omega$ の定義に立ち返り、最悪・平均・償却という別の軸を切り分け、そして「定数倍を捨てる」という一見乱暴な約束が、なぜ実測と噛み合う唯一の形になるのかを見ます。各節にはブラウザ上で動くデモが付いていて、最後の 2 つはあなたのマシンで実際に時間を測ります。

1. $O$ が言っているのは「増え方の上限」だけ

まず定義です。関数 $f(n)$ と $g(n)$ について、

$f(n) = O(g(n)) \iff$ ある定数 $c > 0$ と $n_0$ が存在して、すべての $n \ge n_0$ で $f(n) \le c \cdot g(n)$

この定義には注目すべき点が 3 つあります。第一に、「存在すれば真」です。$c$ と $n_0$ を 1 組見つけられれば主張は成立し、どんな $c$ でもよいので定数倍は主張に影響しません。第二に、「$n \ge n_0$ で」という限定があります。小さい $n$ で $f$ が $c \cdot g$ を上回っていても構いません。第三に、これは不等号 ($\le$) の主張です。つまり $O$ は上限であって、ぴったりの見積もりである必要がありません。

言い換えると、$f(n) = O(g(n))$ は「$f$ は最終的に $g$ の定数倍を超えない範囲でしか増えない」という増え方についての約束であり、$f$ の値そのもの、まして実行時間の秒数については何も言いません。$=$ という記号を使う慣習が誤解を招きますが、これは等式ではなく「$f$ は $O(g)$ という集合に属する」という意味です。だから $O(n) = O(n^2)$ のように左右を入れ替えて書くことはできません。

図: 有限個の例外 (左の赤い領域) は許される。$O$ は「十分大きい $n$ での増え方」だけを見る

デモ 1 ・ 定数 $c$ と $n_0$ を自分で探す

$f(n) = 3n + 40$ を固定し、比較相手 $g$ と定数 $c$ を選びます。$c \cdot g(n)$ が $f(n)$ を上から押さえ切る最小の $n_0$ を自動で探します。$n_0$ が見つかれば $f = O(g)$ が真、どんな $c$ でも見つからなければ偽です。

読み取り。$g = n$ では $c$ を $3$ より大きくすればどこかで必ず押さえ切れます ($c = 3$ ちょうどでは $40$ の差が永久に残る)。$g = n^2$ は緩すぎる上限ですが定義は満たすので真。$g = \log_2 n$ と $g = 1$ はどれだけ $c$ を上げても比 $f/g$ が発散するため偽になります。「$c$ をいくら大きくしても足りない」ことが偽の正体です。

2. $O$・$\Theta$・$\Omega$ ― 上限・下限・ぴったり

3 つの記号は不等号の向きの違いにすぎません。

記号条件 (十分大きい $n$ で)日本語使いどころ
$f = O(g)$$f \le c \cdot g$上限 (これより速く増えない)「最悪でもこの程度」を保証する
$f = \Omega(g)$$f \ge c \cdot g$下限 (少なくともこれだけ増える)「これ以上速くはできない」を言う
$f = \Theta(g)$$c_1 g \le f \le c_2 g$両側 (増え方が一致)見積もりがぴったりだと主張する

ここで最も多い誤解は、$O$ を「最悪ケース」、$\Omega$ を「最良ケース」と読んでしまうことです。この 2 つはまったく別の軸です。記号は「ある 1 つの関数を上から/下から押さえる」話で、ケースは「そもそもどの入力についての関数を考えるか」という話です。だから「最良ケースの実行時間は $O(1)$」も「最悪ケースの実行時間は $\Omega(n)$」も、どちらも意味のある正しい形の主張になり得ます。

$O$ は上限なのでいくらでも緩めることができます。二分探索の最悪比較回数は $\Theta(\log n)$ ですが、$O(n)$ とも $O(n^2)$ とも $O(2^n)$ とも書けて、すべて真です。ただし情報としては役に立ちません。「$O(\cdot)$ で答えよ」と言われたとき暗黙に期待されているのはできるだけタイトな上限であり、正確に言いたいなら $\Theta$ を使うべきです。論文やライブラリのドキュメントで $\Theta$ が使われているときは「この見積もりは緩めていない」という主張が込められています。

捨ててよいもの、捨ててはいけないもの

  • 低次の項は捨てる。$n^2 + 100n + 5000 = \Theta(n^2)$。$n$ が大きいところでは最高次だけが効きます。
  • 定数倍は捨てる。$500n = \Theta(n)$。
  • $\log$ の底も捨てられる。$\log_{10} n = \log_2 n / \log_2 10$ なので底の違いは定数倍。だから $O(\log n)$ に底を書きません。
  • 指数の中の定数倍は捨てられない。$2^{2n} = 4^n$ は $2^n$ の定数倍ではないので $2^{2n} \ne O(2^n)$。「定数倍は無視」を機械的に適用すると事故が起きる代表例です。

デモ 2 ・ 主張の真偽当て (8 問)

それぞれの主張が真か偽かを選ぶと、理由が展開します。「上限は緩くてよい」「$\Theta$ は両側」という 2 点だけで大半が判定できます。

読み取り。判定はほぼ比 $f(n)/g(n)$ の行き先で決まります。比が有限の値に収まるなら $\Theta$、$0$ に行くなら $O$ だが $\Theta$ ではない、$\infty$ に行くなら $O$ ですらない。記号の暗記より比の極限で考える方が速くて間違えません。

3. 最悪・平均・最良 ― 記号とは独立した「もう一つの軸」

計算量を語るときには、独立した 2 つの選択をしています。

  1. どの入力を代表とするか(最悪ケース・平均ケース・最良ケース)。これで $n$ から実行コストへの関数が 1 つ決まります。
  2. その関数をどう押さえるか($O$・$\Theta$・$\Omega$)。

この 2 つは掛け算のように組み合わせられ、$3 \times 3 = 9$ 通りの主張がすべて意味を持ちます。

図: 「どの入力か」と「どちら向きの押さえか」は別の選択。混同が最も多い誤りの源

平均ケースには落とし穴があります。平均を取るには入力の確率分布を仮定する必要があり、その仮定はコードからは読み取れません。「線形探索の平均比較回数は $(n+1)/2$」は「探す値が必ず存在し、その位置が一様分布である」という仮定の下での結論です。見つからないケースが多い現場では平均は $n$ に近づきます。平均計算量はアルゴリズムの性質ではなく、アルゴリズムと入力分布の組の性質です。

デモ 3 ・ 線形探索の比較回数を 20,000 回シミュレーションする

長さ $n$ の配列を先頭から走査して目的の値を探し、比較回数の分布をヒストグラムにします。「見つかる確率」を下げると平均がどう動くかを見てください。

読み取り。見つかる確率が $100\%$ なら平均は $(n+1)/2$ に一致し、分布は一様です。確率を下げると「$n$ 回フルに比較して失敗」の柱だけが伸び、平均は $n$ 側に寄ります。最悪ケース $\Theta(n)$ はどちらでも変わらないのに、平均は仮定次第で 2 倍動く。ここが平均計算量の弱点であり、最悪ケースが好んで使われる理由です。

4. 償却計算量 ― 確率を使わない「平均」

可変長配列 (Python の list、Java の ArrayList、C++ の vector) の末尾追加は「$O(1)$」と説明されます。しかし中身は固定長の配列で、容量が満杯になった瞬間には新しい配列を確保して全要素をコピーします。この 1 回だけは $\Theta(n)$ かかります。それでも $O(1)$ と言えるのはなぜか。

答えは償却計算量 (amortized complexity) という第三の見方です。1 回の操作を単独で見るのではなく、$n$ 回の操作の合計コストを $n$ で割る。容量を 2 倍ずつ増やすなら、コピーが起きるのは容量が $1, 2, 4, 8, \dots$ を超えた瞬間だけで、$n$ 回の追加で発生する総コピー回数は

$1 + 2 + 4 + \cdots + 2^{k} \lt 2n$

と、$n$ の定数倍に収まります。だから 1 回あたりの平均は定数、すなわち償却 $O(1)$ です。

平均計算量との決定的な違い。償却計算量は確率を一切使いません。「運が良ければ速い」ではなく「どんな操作列であっても、合計はこの範囲を超えない」という最悪ケースの主張です。したがって「$n$ 回の追加が全体で $O(n)$」は入力分布の仮定なしに保証されます。一方、平均計算量は分布の仮定に依存します。償却は保証、平均は期待。この差は、たとえばリアルタイム制約のあるコードで決定的に重要になります (償却 $O(1)$ でも、個々の操作の最悪は $\Theta(n)$ のままなので、1 回の遅延を許せない用途では別の対策が必要です)。

デモ 4 ・ 可変長配列の追加コストを 1 回ずつ観測する

追加を進めると、コピーが発生した回だけコストの柱が跳ね上がります。緑の折れ線が「ここまでの 1 回あたり平均コスト」です。成長戦略を切り替えると、償却 $O(1)$ が戦略の性質であることが見えます。

読み取り。倍々 (定数倍) 戦略では、柱の高さは伸びても出現間隔も同じ比率で伸びるので平均は定数に落ち着きます。$+1$ や $+16$ のような固定量の増加では、柱の高さだけが伸びて間隔が伸びないため平均が右肩上がりになり、追加 1 回あたり $\Theta(n)$、$n$ 回で $\Theta(n^2)$ に悪化します。「容量を何倍にするか」ではなく「倍にするか、足すか」が計算量の分かれ目です。

5. コードから計算量を読む ― 数えるのは最内側の実行回数

ループの計算量は「ループの深さ」ではなく最内側の文が何回実行されるかの総和で決まります。二重ループだから $n^2$、とは限りません。

// (a) 内側の開始位置が i に依存する
for (int i = 0; i < n; i++)
  for (int j = i; j < n; j++)
    work();                      // 実行回数 = n + (n-1) + ... + 1 = n(n+1)/2

// (b) 内側が掛け算で伸びる
for (int i = 1; i < n; i *= 2)
  work();                        // 1, 2, 4, ... と進むので約 log2 n 回

// (c) 内側の回数が n/i
for (int i = 1; i <= n; i++)
  for (int j = 0; j < n / i; j++)
    work();                      // n/1 + n/2 + ... + n/n = n·H(n) ≈ n ln n

(a) は等差の和なので $\Theta(n^2)$ です。定数倍 $1/2$ は落ちるため、素朴な二重ループと同じ階級になります。(b) は $i$ が指数的に伸びるので $\Theta(\log n)$。(c) は調和級数 $H(n) = 1 + 1/2 + \cdots + 1/n \approx \ln n$ が現れて $\Theta(n \log n)$ になります。見た目は (a) と同じ二重ループですが、階級が 1 つ下がります。

デモ 5 ・ 計算量を当てて、実際のカウントで検算する

それぞれのコードの計算量を選ぶと、正誤とともに実際に最内側を数えた回数を $n$ を 4 倍ずつ増やしながら表示します。$n$ を 2 倍にしたとき回数が何倍になるかを見れば、階級は自分で確かめられます。

読み取り。各表は $n$ を $4$ 倍ずつ増やしています。カウント比は $\Theta(n)$ なら約 $4$、$\Theta(n\log n)$ なら $4$ より少し大きい値、$\Theta(n^2)$ なら約 $16$、$\Theta(\log n)$ なら「$+2$ 増える」だけ (比ではなく差が一定) になります。比を見るだけで階級が判別できるという性質は、次の節で実測時間に対しても使います。

6. なぜ定数倍を捨てるのか ― 捨てているのは「移植できない情報」

定数倍を無視するのは手抜きではありません。定数倍はマシンの性質であって、アルゴリズムの性質ではないからです。同じコードでも CPU、コンパイラ、メモリ帯域、キャッシュ、言語処理系が変われば定数は簡単に $10$ 倍動きます。つまり定数は別の環境に持ち運べない情報です。一方、増え方の階級は環境が変わっても変わりません。理論から定数を落とすのは、環境をまたいで再利用できる部分だけを残す操作なのです。

そして階級の差は、$n$ が大きくなると定数倍では絶対に埋まりません。$1000n$ と $n^2$ を比べると、$n = 10^6$ では後者が $1000$ 倍遅い。マシンを $10$ 倍速くしても、$n$ が $10$ 倍になれば $n^2$ 側は $100$ 倍重くなるので追いつけません。階級の差はハードウェアで買えない。これが「まずオーダーを下げろ」と言われる理由です。

デモ 6 ・ $n$ を動かして階級ごとの絶望的な差を見る

$1$ 秒間に $10^9$ 回の基本操作をこなせるマシンを仮定して、各階級の操作回数と所要時間を表示します。スライダで $n$ を $2$ 倍ずつ動かしてください。

読み取り。$n$ が $10^6$ 前後になると、$n \log n$ までは実用、$n^2$ は数分から数十分、$2^n$ は宇宙年齢を超えます。$n$ が小さいうちはどの階級も一瞬なので差が見えず、ある規模を超えると一気に破綻する。この非対称性が、小さなテストデータでは問題が見つからない理由です。

デモ 7 ・ 定数倍が勝つ領域 ― 交差点はどこか

$A \cdot n^2$ (単純だが階級が悪い) と $B \cdot n \log_2 n$ (階級は良いが 1 ステップが重い) を比べます。オーダーの良い側が実際に速くなるのは、交差点より右だけです。

読み取り。$A = 1, B = 50$ なら交差点は $n \approx 440$ 付近で、それより小さい入力では $n^2$ 側が速い。だから実際のライブラリのソートは小さい区間では挿入ソートに切り替えます。$O$ は「$n$ が十分大きければ」という前提付きの主張であり、自分の $n$ が交差点のどちら側にあるかは実測でしか分かりません。オーダーだけで実装を選ぶのも、実測だけで階級を無視するのも、どちらも間違いです。

7. 定数は、定数ですらない ― メモリ階層が隠れている

「定数倍は環境で決まる」よりさらに厄介な事実があります。同じマシン、同じコード、同じ操作回数でも、アクセスする順序を変えるだけで実行時間が数倍変わります。CPU はメモリから 1 要素ずつ読むのではなく、連続した数十バイトをキャッシュラインとしてまとめて読み込むためです。隣を順に読めば 1 回の読み込みが複数要素分の仕事になり、遠くへ飛びながら読めば毎回無駄になります。

基本操作の回数はまったく同じなので、計算量の階級は $\Theta(n)$ で変わりません。それでも時間は変わります。つまり$O$ が無視しているはずの「定数倍」は、実は入力サイズやアクセスパターンによって変動する量です。ここが「計算量だけ見ていれば速さが分かる」という考えが破綻する地点です。

デモ 8 ・ 同じ $\Theta(n)$ で時間が何倍変わるかを実測する

$N \times N$ の行列 (1 次元配列として確保) の全要素を合計します。行方向に連続して読む版と、列方向に飛びながら読む版で、足し算の回数は完全に同一です。あなたのブラウザで実際に計測します。

未計測です。ボタンを押すと、確保・ウォームアップを含めて数秒かかります。

読み取り。$N$ を小さくすると比が $1$ に近づき、大きくすると開きます。差が出始める境目があなたのマシンの最終レベルキャッシュのおよその容量です (配列全体が収まっていれば、飛び飛びに読んでも追加の運搬が起きない)。両者の階級は同じ $\Theta(n)$ ($n = N^2$) なので、この境目も倍率も計算量の言葉では表現できません。計算量は「$n$ を増やしたときの伸び方」を答える道具で、「どちらの実装が速いか」を答える道具ではない、という役割分担がここに現れます。

8. 理論と実測の橋 ― 比を測ると定数が消える

ここまでで「定数は環境依存で当てにならない」「階級は環境に依らない」という 2 つを見ました。この 2 つを実測側でつなぐ具体的な手法が倍化テスト (doubling test) です。

実行時間が $T(n) \approx C \cdot n^p$ の形だと仮定します。$C$ は未知の定数 (マシン・言語・キャッシュの全部込み) で、これを知る手段はありません。しかし $n$ を $2$ 倍にして比を取ると、

$\dfrac{T(2n)}{T(n)} \approx \dfrac{C \cdot (2n)^p}{C \cdot n^p} = 2^p$

と$C$ が約分で消えます。残るのは指数 $p$ だけ。つまり測った比を $\log_2$ に通せば $p \approx \log_2\bigl(T(2n)/T(n)\bigr)$ として階級そのものを実測から取り出せます。比が約 $2$ なら線形、約 $4$ なら二乗、約 $2.1{-}2.3$ なら $n \log n$、約 $1$ なら対数か定数。

図: 定数倍を捨てるという約束は、実測側の「比を取る」という操作とちょうど対応している

デモ 9 ・ あなたのマシンで倍化テストを走らせる

$n$ を $2$ 倍ずつ増やしながら実際に時間を測り、比と推定指数 $p$ を出します。カーネルを切り替えて、事前に分かっている階級と一致するかを確かめてください。

未計測です。数秒かかります。
実測の注意。JIT のウォームアップ、GC、タイマ解像度、他プロセスの影響で 1 回の測定は容易にぶれます。このデモは各サイズを複数回走らせて最小値を採用し (最小値は外乱が最も少ない試行に近いため)、小さすぎる $n$ は測定の下駄が乗るので比の推定から外しています。実測で階級を判定するときは、1 点ではなく複数点の比の一貫性を見るのが基本です。

読み取り。$\Theta(n\log n)$ の比は $2$ より少し大きい値 ($n = 10^6$ 付近で約 $2.1$) にしかならず、実測で $n$ と $n\log n$ を区別するのは難しいのが分かります。逆に $n$ と $n^2$ は比 $2$ と $4$ で明確に分かれます。実測から言えるのは「階級の桁」であって、$\log$ の有無のような細かい差ではありません。

9. そもそも $n$ とは何か ― 入力サイズの定義で結論が変わる

最後に、計算量の主張で最も静かに間違えられる点です。$O(\cdot)$ の中の $n$ は入力サイズ、原則として入力を表現するのに必要なビット数を指します。「配列の要素数」を $n$ と呼ぶのは、要素 1 個のサイズが定数と見なせる文脈での便宜です。

整数 $N$ が素数かどうかを $2$ から $\sqrt{N}$ まで試し割りする素朴な判定は「$O(\sqrt{N})$」と書かれます。速そうに見えますが、入力は整数 $N$ ひとつで、その入力サイズは桁数 $b \approx \log_2 N$ ビットです。$\sqrt{N} = 2^{b/2}$ なので、入力サイズを基準にすると指数時間です。だから $2048$ ビットの整数には手が届かず、RSA が成り立ちます。

このように「数値そのもの」を $n$ に取ると多項式に見えるアルゴリズムを擬多項式時間 (pseudo-polynomial) と呼びます。ナップサック問題の動的計画法 $O(nW)$ も同じ構造で、$W$ が容量の値なので、$W$ の桁数に対しては指数です。

デモ 10 ・ 「$O(\sqrt{N})$」が指数時間である様子

整数のビット数 $b$ を動かします。$1$ 秒に $10^9$ 回の試し割りができるとして、素朴な素数判定にかかる時間を表示します。ビット数を $2$ 増やすと仕事が $2$ 倍になる、つまり指数です。

読み取り。$b = 64$ で数秒、$b = 128$ で数百年、$b = 256$ では宇宙年齢を遥かに超えます。同じアルゴリズムが「$N$ について $O(\sqrt N)$ (多項式)」でありながら「入力サイズについて指数」。$n$ を何と決めたかを言わない計算量の主張は、意味が確定していません。

10. まとめ ― 計算量を見るときのチェックリスト

問い確認すること間違えるとどうなるか
$n$ は何か要素数か、値か、ビット数か擬多項式を多項式と誤認し、実装が現実の入力で止まる
どのケースか最悪・平均・償却のどれか。平均なら仮定した分布は何か平均の $O(1)$ を保証と誤解し、最悪ケースで落ちる
どの記号か$O$ (上限) か $\Theta$ (ぴったり) か緩い上限を根拠に「これ以上速くできない」と誤って結論する
何を数えたか時間か空間か。基本操作は何を 1 と数えたか比較 $O(n\log n)$ なのにメモリが $\Theta(n)$ 追加で必要な点を見落とす
自分の $n$ はどこか交差点より右か左か小さい入力しか来ない場所で、複雑で遅い「良いオーダー」を採用する
定数はどこから来たかキャッシュ・メモリ確保・定数係数同じ階級の実装の速度差を計算量で説明しようとして混乱する

この回の核心を 1 行にすると、「$O$ は増え方だけを言う。だから環境をまたいで使えるし、だから秒数は答えない」ということです。そして増え方だけを見るという約束は、実測側で比を取るという操作と正確に対応しています。理論と実測は別々の世界ではなく、$T(2n)/T(n)$ という 1 本の割り算でつながっています。

awsome 1 — 分散 AI リファレンス実装の基本構成

AWS の分散 AI リファレンス実装 awsome-distributed-ai は、クラスタの作り方と、その上で動かす中身を分けて置く。この回は、どこに何があり、repo のファイルがどうやって「押すだけで動く URL」になるのかを追う。

結論から

このリポジトリの中心にあるのは 2 つの分離である。1 つは「クラスタの作り方」と「その上で動かす中身」の分離、 もう 1 つは「repo の中のファイル」と「利用者が押す URL」の分離である。前者を決めているのが architectures/ と examples/ の置き場の規則、後者を決めているのが .github/template-publish-manifest.yml という 1 枚の名簿だ。

この 2 つを知らないまま作業すると、同じ失敗を踏む。テンプレートを書いたのに利用者の手元では deploy できない、あるいは実験用のスクリプトをアーキテクチャ側に置いてしまって、次の人が どこまでがクラスタの責務か分からなくなる。

architectures と examples の線引き

architectures/ にはオーケストレータ 1 つに 1 ディレクトリが置かれる。ParallelCluster、PCS、 SageMaker HyperPod の Slurm 版と EKS 版、そして素の EKS である。どれも中の作りは同じ形で、 テンプレート本体が assets/、パラメータや運用の説明が docs/、検査と手順書が tests/ に入る。

examples/ は目的で場所が決まる。枠組みを見せたいなら training/、特定のモデルや応用なら use-cases/、サービングなら inference/<エンジン>/ である。分離推論の例は最後のところに置かれる。

境界の決め方 「クラスタが用意しておくもの」はアーキテクチャ側、「実験が持ち込むもの」は例の側。モデル重みを置く 共有ストレージや GPU ドライバはアーキテクチャ側が持ち、Dockerfile や実行スクリプトは例の側が持つ。 この線を引いておくと、例を 1 つ足すときにインフラを触らずに済む。
新規追加の前に既存を拡張する 配置規則には「似たディレクトリを並べて増やすな」と明記されている。新しいディレクトリが正当なのは、 依存関係か実行の形が既存と本質的に違うときだけで、そのときは最も近い既存のものを名指しして、 なぜ拡張では足りないかを PR に書くことが求められる。既存の兄弟を後からまとめ直すのも禁止されている。

repo のファイルが URL になるまで

ここがこのリポジトリで一番見落としやすい仕組みだ。テンプレートを repo に足しただけでは、誰も deploy できない。 利用者が押すのは S3 に公開されたファイルの URL であって、GitHub 上のファイルではない。 その橋渡しをするのが公開の名簿である。

名簿は 1 本のテンプレートにつき 2 行だ。source が repo の中の場所、key が公開先での名前である。

bucket: awsome-distributed-ai
prefix: templates/
entries:
  - source: architectures/amazon-eks/assets/eks-gpu-cluster-deploy-all.yaml
    key: amazon-eks/eks-gpu-cluster-deploy-all.yaml

この 2 行で s3://awsome-distributed-ai/templates/amazon-eks/eks-gpu-cluster-deploy-all.yaml に置かれる。 main に変更が入ると workflow が走り、名簿どおりにファイルを集め、shell と CloudFormation を検証し、 変わったアーキテクチャの検査を回してから S3 へ同期する。権限は専用の最小権限ロールを OIDC で引き受ける形で、 公開用のバケット書き込みとテンプレート検証しかできない。

入れ子のテンプレートが成立する条件

親テンプレートは中身を持たず、子を URL で取ってくる。その URL は親のパラメータ S3BucketName と S3KeyPrefix から組み立てられる。だからこの 2 つの既定値が、名簿の公開先と 一致していなければならない。ワークショップのように主催者のバケットから配る場合は、この 2 つを 上書きして親を deploy する。逆に、上書きを忘れて主催者のバケットから親だけを取ると、 子は公開版から降ってくる。stack は成功するのに、検証したものとは別のものが出来上がる。

名簿に載せ忘れた子は、repo にはあるのに URL には無い この失敗は自分で踏んだ。テンプレートを 4 本登録したあと、5 本目 (ノード AMI を焼く子) を足したときに 登録を忘れた。手元では自分のバケットに同期して試していたので最後まで気づかず、公開版だけが壊れる状態だった。 検査で落とせる種類の間違いなので、テンプレートが名簿に載っているかを機械で確かめるのが正しい。

古いキーは消せない

名簿の冒頭には、平坦な (アーキテクチャ名で区切られていない) 古いキーを意図的に残す、という注意が書かれている。 既に deploy 済みの stack はそのキーを覚えており、stack の更新やノード入れ替え時のブートストラップが そこを読む。消すと動いている環境が壊れるので、参照が無くなったと確認できたものだけを obsolete_keys に書いて消す。公開したものは、公開した時点で契約になるということだ。

PR に求められるもの

テンプレートの節は固定で、Test Results には実 AWS での end-to-end の証拠を貼ることが要求される。 機能に影響しない変更は docs-only と書く。ここが厳しいのは、インフラのテンプレートは 「文法が通る」ことと「実際にクラスタが立つ」ことの間が非常に遠いからだ。

文法検査が通るのは、ほとんど何も保証しない validate-template は条件分岐を評価しない。ノードを 0 台で deploy すれば、GPU に関わる部分は 1 行も実行されない。台数を 0 にした検証は通ってしまうが、インターフェース構成もドライバも 確かめていない。だから節の名前が Test Results であって Test Plan だけではない。

この構成で何が楽になるか

やりたいこと触る場所触らない場所
新しい推論の例を足すexamples/inference/<エンジン>/アーキテクチャ側。クラスタの作り方は既にある
GPU の型を増やすそのアーキテクチャの assets/ と互換表例。ノードの形が変わっても manifest は同じ
ワークショップで配る主催者のバケットと親の 2 パラメータテンプレート本体。書き換えずに配布元だけ差し替える
イメージを焼くami/アーキテクチャ側。焼いた ID を渡す口だけがある

次回に続く話

この回は地図だけを扱った。次は EKS のリファレンス実装を eksctl の定義から CloudFormation の 1 クリックに置き換えた作業を、実測とともに追う。そこで出てくるのは、ドライバが GPU を列挙しない インスタンスファミリ、device plugin に公式の add-on が無いこと、そして 「成功をどう判定するか」を間違えると GPU の無いクラスタが成功として返ってくるという話である。

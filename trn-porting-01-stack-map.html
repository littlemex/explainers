スタックの地図 ― 誰が何を持っているのか

vLLM 本体・プラグイン・ランタイム兼カーネル基盤・Neuron ランタイムと NEFF。4 層と 2 経路を先に押さえる

← シリーズ目次

0このシリーズの狙い

AWS Trainium で LLM をサービングするとき、モデルを「移植する」という作業が発生します。その作業が何なのかを、スタックの構造から具体的に説明するのがこのシリーズです。

Trainium 上の推論には、GPU に慣れた人が最初につまずく段差があります。GPU なら Hugging Face のモデルクラスをそのまま vLLM に渡して動くことが多いのに、Trainium では対応モデルが明示的に列挙されていて、そこに無いモデルは自分で実装を足す必要があります。この「足す」作業の中身が見えないと、工数の見積もりも、どの経路に賭けるべきかの判断もできません。

このシリーズは、その中身を層ごとに分解します。第 1 回は地図です。誰がどの責務を持ち、コードのどこに住んでいるのかを先に決めておかないと、以降の議論が「どの層の話をしているのか分からない」状態になります。

一言でいうと
Trainium 推論スタックは 4 層です。上から vLLM 本体、ハードウェアプラグイン、ランタイム兼カーネル基盤のライブラリ、そして Neuron ランタイムと NEFF という実行バイナリ。移植作業の大半はスタック第 2 層 (プラグイン) にモデル実装を書くことで、その実装はスタック第 3 層が提供するカーネルと契約に対して書かれます。「Native PyTorch にすれば移植が要らなくなる」という期待がどこまで当たるかは、この地図のどの層が入れ替わるのかで決まります。
1. 4 層の地図 2. 第 1 層 ― vLLM 本体は何を手放していないか 3. 第 2 層 ― プラグインの中身 4. 第 3 層 ― ランタイム兼カーネル基盤 5. 第 4 層 ― NEFF とランタイム 6. 2 つのコンパイル経路 7. 対応モデルが列挙式であることの意味 8. このシリーズの読み進め方

扱う対象は、コミュニティ管理のハードウェアプラグイン vllm-project/vllm-neuron と、その公開コンテナイメージです。記述はプラグインの公開ソースおよび公開されているパッケージインデックスで確認できる範囲に限っています。

14 層の地図

最初に全体像を置きます。各層の名前と責務を覚えるだけで、以降の話の見通しが立ちます。

4 層。上ほど汎用、下ほどハードウェア固有。移植で手を動かすのは第 2 層だが、書き方の制約は第 3 層と第 4 層から降ってくる

この図で覚えてほしいのは、スタック第 3 層が「差し替え可能な部品」ではなく「地面」であるという点です。名前だけ見るとこの層はコンパイラのバックエンドに見えるので、別のバックエンドに交換できそうに思えます。しかし後の章で見るように、スタック第 2 層のカーネル呼び出し層はほぼ全ファイルがこの層の関数を import しています。地面を入れ替えると、その上の建物も一緒に建て替えることになります。

2第 1 層 ― vLLM 本体は何を手放していないか

プラグイン方式なので、vLLM 本体は「全部差し替わる」わけではありません。何が残るかを知っておくと、移植で自分が実装しなくてよいものが分かります。

ハードウェアプラグインは、vLLM の vllm.platform_plugins というエントリポイントで自分を登録します。プラグインが差し替えるのは Platform、Worker、ModelRunner、AttentionBackend、そしてデバイス間通信の担当です。逆に言えば、それ以外は vLLM 本体の実装がそのまま動きます。

担当誰が持つか移植で書く必要があるか
受付制御・継続バッチング (continuous batching) のスケジューリングvLLM 本体書かない
KV ブロックの割当・解放 (論理的な管理)vLLM 本体書かない
KV キャッシュの実体テンソルの確保プラグインのランナー書かない
KV キャッシュの形の申告モデル実装書く
OpenAI 互換の API サーバvLLM 本体書かない
モデルの forwardプラグイン内のモデル実装書く
KV キャッシュの実体への読み書きモデル実装の forward の中書く
重みの読み込みとテンソル並列の分割モデル実装の weight loader書く
NEFF へのコンパイルスタック第 3 層書かない

ここが「移植」という言葉の輪郭です。スケジューリングやブロック管理という難しい部分は貰える。代わりに、モデルの計算と、KV キャッシュという共有資源への読み書き作法は自分で書く。第 3 回でこの作法を「サービング契約」として細かく分解します。

3第 2 層 ― プラグインの中身

移植で触るディレクトリを先に把握します。名前と役割が結びついていれば、他人のモデル実装を参照実装として読めるようになります。

vllm_neuron/
├── vllm/            第 1 層への差し込み (platform, worker, model_runner, attention, sample, ...)
├── model/           モデル実装。registry.py に列挙されたものだけが動く
│   ├── registry.py  対応モデルの一覧 (ここに登録しないと存在しない)
│   ├── llama3/      参照実装。量子化バリアントも同居
│   ├── qwen3/       参照実装 (小さめ)
│   └── ...
├── nn/              並列化つきの基本レイヤ (列並列 / 行並列 / 埋め込み / サンプラ)
├── functional/      カーネル呼び出し層。attention, moe, collectives ほか
├── fx_passes/       グラフ書き換え (デバイス / エイリアス / インプレース / NKI / 集団通信)
├── parallel/        テンソル並列・エキスパート並列の配線
└── utils/           重み読み込み、実行器、その他

移植で新規に作るのは model/<新しいモデル>/ だけです。ただしその中身は nn/ と functional/ を呼ぶ形で書きます。ここが重要で、Hugging Face の実装をコピーしてくる作業ではありません。同じ数式を、この 2 つのディレクトリが提供する語彙で書き直す作業です。

規模の感覚として、参照実装のひとつは設定 74 行・ファクトリ 80 行・モデル本体 1075 行の合計およそ 1,200 行です。別の参照実装はモデル本体が 2177 行あり、これに量子化バリアントと重みローダ群が加わります。ただしこの行数を「定型作業の量」と読むと見積もりを外します。理由は第 4 回で扱います。

4第 3 層 ― ランタイム兼カーネル基盤

この層の役割が一番誤解されやすいので、ここで正確にしておきます。

この層のライブラリは、名前からはコンパイラのバックエンドに見えます。実際にそれも担当しています。torch.compile に渡すバックエンドの実装、コンパイルキャッシュ、並列コンパイル、プラットフォーム判定はここです。

しかし役割はそれだけではありません。この層は次の 3 つを同時に持っています。

  1. PyTorch のデバイスとしての自分の登録。PyTorch には外部アクセラレータ用に予約されたディスパッチキーがあり、その筆頭が PrivateUse1 です。デバイス名の改名やデバイスモジュールの登録といった周辺の支援 API が実質このキーを前提に整っているので、外部実装はここに集まります。この層もそこに自分を登録して「Neuron デバイス」になります。第 6 回の主題です。
  2. 低レベルカーネル (NKI で書かれたもの。以下、低レベルカーネル) をグラフに取り込む口。スタック第 2 層の functional/ にある約 30 のファイルが、この層の wrap_nki という関数を import しています。attention の全種類、MoE の全種類、集団通信、topk、cumsum、正規化つき量子化。つまりスタック第 2 層のカーネルライブラリ全体がこの層の上に建っています。
  3. 集団通信の実装。テンソル並列の all-reduce や reduce-scatter をデバイス上で行う部分。
ここが後で効きます。「コンパイル経路を別のものに差し替える」という発想は、この層のうち (1) だけを見ていると自然に思えます。しかし (2) を見ると、差し替えはカーネルライブラリを失うことを意味します。第 6 回で、この層を別の実装に置き換えようとすると PyTorch のディスパッチャレベルで衝突が起きることを示します。

5第 4 層 ― NEFF とランタイム

最下層には、コンパイル結果の実行バイナリと、それを走らせるランタイムがあります。この層の性質が、上の層の設計をかなり強く縛ります。

NEFF (Neuron Executable File Format) は、コンパイル済みの実行単位です。ファイルとしてディスクに存在し、名前つきの入力と出力を持ちます。実際に中身を問い合わせると、次のような情報が返ります。

inputs : {'input0': (size=524288, dtype='float32', shape=[32, 4096]),
          'input1': (size=8192,   dtype='float32', shape=[1, 2048]), ...}
outputs: {'output0': (size=524288, dtype='float32', shape=[32, 4096]),
          'output1': (size=2097152, dtype='float32', shape=[64, 8192])}
alias  : {}

ここから 3 つの性質が読み取れます。

形状が固定です。NEFF は特定の形状に対してコンパイルされています。だから系列長やバッチサイズの組み合わせごとに別の NEFF が必要になります。これが「バケット化」と呼ばれる設計の理由で、第 2 回で扱います。

入力の名前が位置名です。input0、input1 という並びしか持っていません。元の Python 関数の引数名は残りません。この一点が、NEFF を他所から持ち込んで再利用しようとしたときに実務的な壁になります。第 7 回で扱います。

エイリアス情報を持ちます。上の例では空ですが、入力バッファを出力として使い回す (donated buffer) 指定がここに載ります。KV キャッシュや状態の持ち回りは、この仕組みの上に成り立ちます。

62 つのコンパイル経路

同じ torch.compile という入口から、性質の違う 2 つの経路が伸びています。この 2 本を混同すると議論が噛み合いません。

入口は同じ torch.compile。出口はどちらも NEFF。違うのは途中の降ろし方と、周りに何が付いているか

経路 A (XLA) は現在のサービング用の既定です。第 2 回で分解します。経路 B (Native PyTorch) は、Hugging Face のモデルをデバイスに置いてそのまま実行でき、torch.compile も使えるものとして説明されています。ATen 演算のカバレッジが広く、素直に書いたコードが通りやすい、とされています。この経路は執筆時点で公開配布されていないので、本シリーズは経路 B の実測を扱いません (詳細は第 4 回 §8)。

ここで注意すべきなのは、この 2 本は「新旧」ではなく「別の目的の道具」だという点です。経路 B (Native PyTorch) は継続バッチングも paged KV キャッシュも持ちません。つまり経路 B 単体はサービングスタックではありません。逆に経路 A (XLA) はサービングの仕組みを全部持っていますが、そのぶん通る書き方が制限されます。

プラグインの公開 README の feature matrix には、この 2 本が別の行として並んでいます。torch.compile (XLA backend) が対応済み、torch.compile (native PyTorch) が未対応。つまり「経路 B (Native PyTorch) をサービングの下敷きにする」ことは、プラグイン側でも追跡されている項目であって、まだ出荷されていません。この状態が何を意味するかは第 6 回で詳しく見ます。

7対応モデルが列挙式であることの意味

GPU との一番大きな体験差はここです。仕組みとして理解しておくと、驚かずに済みます。

プラグインのモデルレジストリは、対応モデルを Python のリストとして持っています。つまり汎用の Hugging Face フォールバック経路がありません。レジストリに載っていないアーキテクチャは、そのプラグインにとって存在しません。

なぜこうなっているのか。答えは第 3 回と第 4 回の内容ですが、先に一言でいうと、モデルの forward が KV キャッシュという共有資源への読み書き作法を自分で担っているからです。汎用の Hugging Face 実装はその作法を知りません。共通の受け皿を作るには KV アクセスを差し替えるアダプタ層が要り、現状のプラグインはそれを提供していません。

この構造から出てくる素朴な疑問
「では経路 B (Native PyTorch) なら Hugging Face のモデルがそのまま動くのだから、それをサービングに使えばよいのでは」。この疑問はまっとうで、シリーズの後半 (第 5 回から第 7 回) がその答えです。結論を先に言うと、経路 B に替えても移植は要ります。ただし移植のうちある一層のコストは確かに下がります。どの層が下がってどの層が残るのかを、第 4 回で 3 層に分けて整理します。

8このシリーズの読み進め方

全 8 回の構成と、それぞれで答えたい問いを並べます。

回主題答えたい問い
01 (本稿)スタックの地図誰がどの責務を持つのか
02コンパイル経路の解剖Python から NEFF まで何が起きるのか。なぜ形状ごとに NEFF が要るのか
03サービング契約移植とは具体的に何を実装することか
04ポーティングの 3 層モデル移植コストはどこに宿るのか。アーキテクチャによって何が変わるのか
05eager と compileeager にすれば移植は要らないのか
062 つのランタイムは同居できない経路を差し替えるとは何をすることなのか。なぜ待ちが発生するのか
07NEFF を境界にするプロセスを分けて橋を架けられるか。代償は何か
08測り方この上で測った数字を信じてよいのはどんなときか

実装を書く立場なら第 3 回と第 4 回が本体です。経路の選択を判断する立場なら、まず第 4 回 (コストがどこに宿るか、見積もりの 2 つの問い) を読んでください。判断の道具はこの回にあります。そのうえで第 5 回から第 7 回 (なぜ待ちが発生するのか、回避策の現在地) に進むのが早いです。第 8 回は、どちらの立場でも数字を出す前・受け取る前に読んでおく回です。

出典と確認方法: プラグインの構成・レジストリ・FX パス・feature matrix は vllm-project/vllm-neuron の公開ソースで確認できます。行数は同リポジトリの該当時点のソースを数えたものです。NEFF の入出力情報は、公開コンテナイメージに同梱されている Neuron ランタイムの Python バインディングで実際に問い合わせた結果です (第 7 回に手順)。

確認時点: 本稿の記述は 2026-09-01 時点のものです。対象はプラグイン 0.21.0.1.0.0 と 0.24.0.1.1.0 の公開ソースおよび公開コンテナイメージ、公開パッケージインデックスから取得できるランタイム兼カーネル基盤ライブラリ (2.11.0.1.0.1284 / 2.12.0.1.0.1284)、コンパイラ 2.26 / 2.27 系、低レベルカーネル言語 0.5.0 / 0.6.0、PyTorch 2.11.0 です。バージョンが上がれば名前も挙動も変わりうるので、正はソースと配布物です。

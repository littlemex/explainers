ストレージエンジンと分散 DB ― B-tree と LSM-tree はどこで差がつくか

読み取りが多いか書き込みが多いかという一点が、索引構造とレプリケーション方式のほぼすべてを決める

← 分散システム シリーズ目次へ

この回の前提: 第 05 回 レプリケーション入門、第 18 回 分離レベルと並行制御

「読み取りが多いか、書き込みが多いか」でストレージエンジンの正解は変わる。B-tree は読み取りが速く、LSM-tree (Log-Structured Merge Tree) は書き込みが速いという一点に、分散データベースの設計判断の多くが帰着する。Discord がメッセージ保存を MongoDB → Cassandra → ScyllaDB と乗り換えた理由も、この一点から説明できる。

1. 書く前に記録する ― WAL という土台

どのストレージエンジンを選んでも、まず最初に必要なのは WAL (Write-Ahead Log, 先行書き込みログ) です。データ本体 (B-tree のページや LSM-tree のメモリ内テーブル) を更新する前に、まず「これから何をするか」を追記専用のログファイルに書き切ってから、本体の更新に進みます。

こうする理由は単純です。本体の更新はページの一部だけ書けた状態でクラッシュする (部分書き込み) 可能性がありますが、追記専用のログは末尾に 1 行足すだけなので壊れ方がシンプルです。再起動時には WAL を先頭から読み直し、本体に反映されていない分だけを再生 (replay) すれば、クラッシュ直前の状態を復元できます。これは第 25 回で見た Raft のログ複製や、第 33 回で見るステートマシン複製とも同じ発想です。

図: WAL は「本体更新より先に書く」ことで、クラッシュ時も再生だけで復元できる形にする。

2. B-tree と LSM-tree ― 読みが速いか、書きが速いか

B-tree はほぼすべての RDBMS (PostgreSQL, MySQL の InnoDB など) が採用する索引構造です。データはディスク上の固定サイズの「ページ」にソート済みで保持され、キーを探すときはルートから子ページへとページ単位で降りていきます。更新は対象ページをその場で (in-place) 書き換えます。読み取りはどのキーでも同じ深さをたどるだけなので速く安定していますが、ランダムな位置のページ書き換えが多数のディスクシークを生みやすく、書き込みは相対的に重くなります。

LSM-tree は Cassandra, LevelDB, RocksDB, ScyllaDB など多くの NoSQL が採用します。書き込みはまずメモリ内のソート済み構造 (メモリテーブル) に追記するだけで確定し、それが一定量に達すると、ソート済みのまま丸ごとディスクに「SSTable」として書き出します (この時点ではディスクへのランダムな書き換えが発生しない)。読み取りは新しい SSTable から古い SSTable へ順に探す必要があり、SSTable の数が増えるほど 1 回の読み取りで調べる場所が増えます (読み取り増幅)。古い SSTable 群を定期的にマージして数を減らす処理をコンパクション (compaction) と呼び、これは同じデータを何度も読み書きし直す書き込み増幅 (write amplification) の代償を伴います。存在しないキーの探索を早期に打ち切るため、各 SSTable にブルームフィルタ (Bloom filter) を添えて「このキーは絶対に無い」を高速に判定するのが定石です。

図: B-tree は読み取り安定・書き込み重め、LSM-tree は書き込み軽量・読み取りは SSTable 数に依存。

3. レプリケーションログは「ストレージエンジンのログ」をそのまま再利用できる

第 5 回で見たリーダー/フォロワー型のレプリケーションは、何を転送するかで実装が変わります。statement-based (SQL 文そのものを転送) は NOW() や自動採番のような非決定的な関数が混ざると値がずれる弱点があります。WAL shipping (WAL をそのままフォロワーに送る) はストレージエンジン内部の物理フォーマットに依存するため、エンジンのバージョン間で互換性が崩れやすい一方、実装は単純です。logical (row-based) replication は「どの行がどう変わったか」を物理フォーマットと独立に記述するため、ストレージエンジンの内部実装を変えても複製の仕組みを維持できます。

LSM-tree 採用のシステムでリーダーレス (leaderless) レプリケーション (第 14 回で見る Dynamo 型) を組み合わせる設計がよく見られるのは偶然ではありません。LSM-tree の追記主体の書き込みパスは、複数ノードが並行に書き込みを受け付けてもコンフリクトの検出・解消 (バージョンベクタや LWW) と相性がよく、書き込みが集中するワークロードでスループットを出しやすいためです。

4. SDFC の「分散データベース設計」に見るワークロード別の選択

SDFC (システム設計の練習題材集) の distributed-DB-design は、同じ「分散データベースを設計せよ」という問いに対し、ワークロードの違いで 3 つの別解を用意しています。

読み取り重視 (read-heavy): 単一リーダー + B-tree。スナップショット分離 (MVCC) とバージョンベクタで、逐次一貫性に近い振る舞いを狙う。DynamoDB や Spanner のような構成が例として挙がる。

書き込み重視 (write-heavy): リーダーレス + LSM-tree。Cassandra/Riak/ScyllaDB 的な構成で、因果一貫性までを目標にし、書き込み衝突は Riak や Cosmos DB のような解消規則に委ねる。

Ticketmaster のようなフラッシュセール (全順序 + 書き込み超過): 単一リーダー + LSM-tree という組み合わせ。全順序が要件になるため単一リーダーを維持しつつ、書き込み量そのものに応えるため LSM-tree を選び、シャーディングで負荷を分散する。読み取り重視の構成と比べ、読み取りレプリカは減らしてよい (読み取りはそもそも少ない) というのが設計上の判断点です。

5. 実例: Discord が MongoDB → Cassandra → ScyllaDB と乗り換えた理由

Discord のメッセージ保存は、この回の論点がそのまま実際の障害として表れた事例です。2015 年、単一の MongoDB レプリカで開始し、約 1 億件のメッセージでメモリにインデックスが収まらなくなりレイテンシが不安定化、Cassandra (LSM-tree) に移行しました。2017 年には 12 ノードで数十億件を保存し、2022 年初頭には 177 ノードで数兆件規模に成長しましたが、ここで再びレイテンシが不安定になります。

原因は LSM-tree の特性そのものでした。LSM-tree は書き込みより読み取りが相対的に重く、同時接続者数の多いチャンネルでは読み取りが集中してホットスポットが生じます。さらにコンパクション (SSTable の再マージ) がノードの CPU ・ディスク I/O を消費し、ガベージコレクションの一時停止がレイテンシのスパイクを生んでいました。Discord は ScyllaDB (Cassandra 互換、C++ 実装) へ再移行し、p99 読み取りレイテンシは 40〜125ms から 15ms に、p99 書き込みレイテンシは 5〜70ms から 5ms に改善しています。これは「LSM-tree を選べば書き込みは解決するが、読み取りとコンパクションの運用コストは別問題として残る」ことを示す実例です。

図: Discord の移行はデータ構造(LSM)を変えずに実装(Cassandra→ScyllaDB)を変えて改善した事例。

6. どこで壊れるか・何を諦めるか

  • コンパクション嵐: 書き込みが集中する時間帯にコンパクションが重なると、CPU/I/O を奪われて読み書き両方のレイテンシが跳ねる。コンパクションのスケジューリングと帯域制限が運用上の要点になる。
  • トゥームストーン (削除マーカー) の蓄積: LSM-tree での削除は「削除済み」を示す特別な値 (tombstone) の追記であり、実データの即時消去ではない。コンパクションでまとめて消えるまでは残り続け、削除が多いワークロードでは読み取り増幅の原因になる。
  • B-tree の書き込み増幅: ページ単位の書き換えは、1 件の小さな更新でもページ全体 (典型的に 4KB〜16KB) を書き直すため、書き込みが集中すると不利になる。
  • 読み取り/書き込みの比率を見誤る: SDFC の distributed-DB-design が示すように、同じ要件でも読み書き比率で最適なエンジン・レプリケーション方式が入れ替わる。「流行っているから LSM-tree」という選択は、読み取り重視のワークロードでは裏目に出る。

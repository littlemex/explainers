2 進数と CPU の計算 ― 桁上がりとオーバーフローは別物

CPU の中の数はすべて 0 と 1 の並び。負の数は「2 の補数」という決め方で表され、足し算がうまくいかなくなる「桁上がり」と「オーバーフロー」はまったく別の現象として扱われる

この回の前提: 第 03 回 組み合わせ回路

第 03 回で見た全加算器は、1 ビットの足し算を繰り上がり付きで行う部品でした。この回ではその部品を実際の CPU の計算にどう使うかを見ます。rj32 は 16 ビットの数しか扱えない小さな機械です。負の数をどう表すか、16 ビットという枠をあふれたときに何が起きるか、そしてその「あふれ」が 2 種類ある (桁上がりとオーバーフロー) ことを、rj32 の実際の命令セットで確認します。

1. 2 進数と 16 進数 ― 同じ数の違う書き方

CPU の中にあるのは電圧の高い (1) か低い (0) かだけです。rj32 は 16 ビット (0 と 1 が 16 個) でひとつの数を表します。16 個の 0/1 を人間がそのまま読むのは大変なので、4 ビットずつまとめて 1 桁の16 進数 (0〜9, A〜F) に置き換えて書くのが習慣です。$2^4=16$ なので、2 進数 4 桁と 16 進数 1 桁がぴったり対応します。

図: 16 進数は 2 進数 4 桁をまとめて 1 文字で書く、人間向けの省略記法。CPU 内部の値そのものは変わらない。

rj32 の命令エンコーディング (第 10 回) やメモリアドレスは、ドキュメント中でもすべて 16 進数で書かれています。これは表記の都合であり、CPU の回路が「16 進数で考えている」わけではありません。回路にとっての実体は、あくまで 16 本の配線それぞれの 0/1 です。

2. 2 の補数 ― 引き算を足し算の回路だけでやる

第 03 回で作った全加算器は足し算しかできません。引き算専用の回路をもう 1 セット作らずに済ませるため、CPU は負の数を2 の補数 (two's complement) という決め方で表し、「引く」ことを「2 の補数にしてから足す」ことに変換します。

決め方は単純です。16 ビットのうち、最上位ビットが 1 の並びは負の数として読みます。ある数 $N$ を負にするには、全ビットを反転させて 1 を足します ($-N = \overline{N} + 1$)。これは Digital のコンポーネント一覧にもNegation (2th complement) という専用部品として載っている、標準的な操作です。

図: 2 の補数では、数は輪になって並ぶ。0 から時計回りに +1 していくと、最上位ビットが 1 の側 (1111, 1110, …) は負の数として読む。0 の両隣が +1 と -1 になっている。

この輪の表現のおかげで、CPU の足し算回路は「足す数が正か負か」を気にする必要がありません。$3 + (-1)$ は、ビット列としては単純に $0011 + 1111$ を足すだけで、輪を 1 周余分に回って $0010 = 2$ が出てきます。あふれた分 (1 周分) は後で説明する桁上がりとして処理されます。

3. 桁上がりとオーバーフロー ― 「あふれ」は 2 種類ある

16 ビットの計算結果が 16 ビットの枠に収まらないとき、何が起きているかは符号なし (unsigned) として見るか、符号付き (signed) として見るかで違う名前がつきます。Digital の Adder 部品の定義では、キャリー出力 $c_o$ は「結果に繰り上がり (overflow) があれば 1」と説明されますが、これは符号なしの枠からあふれたという意味での桁上がりです。符号付きの数を扱うときに意味のある「オーバーフロー (符号が壊れる)」とは別の現象だと区別して理解する必要があります。

図: 桁上がりは「符号なしの枠からあふれた」、オーバーフローは「符号付きの符号が壊れた」。片方が起きても、もう片方は起きないことがある。

rj32 の命令セットには、桁上がりを運ぶ C (キャリー) フラグはありますが、符号付き専用の独立したオーバーフローフラグはありません。負の数の加減算で符号が正しいかどうかは、次節で見る if.lt / if.ge といった符号付き比較命令の結果から判断する必要があります。

4. 符号付き・符号なし比較とフラグ ― 同じビット列でも答えが変わる

CPU の回路は、16 本の配線に入っている 0/1 のパターンそのものしか見ていません。そのパターンを「符号付きの数」として読むか「符号なしの数」として読むかは、命令が決めることです。rj32 の docs/instructions.md には、まったく仕組みの似た比較命令が符号付き版と符号なし版の 2 組用意されています。

  • if.lt rd, rs ― S <- !(rd < rsval) (符号付きで比較)
  • if.ult rd, rs ― S <- !(rd < rsval) (符号なしで比較)

同じ「less than」でも、符号付きか符号なしかでビットパターンの解釈が変わるため、答えが逆になることがあります。

図: 0xFFFF というビット列は符号なしでは最大値 65535、符号付きでは -1。使う比較命令 (if.lt か if.ult か) を間違えると、意図と逆の答えが出る。

第 03 回で見たとおり、比較は基本的に引き算 (rd - rsval) の結果を見て判定します。C (キャリー) フラグは「次の命令にキャリーがあるかどうか」を伝える役目で、docs/instructions.md の定義にあるとおり、addc/subc のような接頭命令が使い終わると役目を終え、次の命令の後にリセットされます。rj32 では比較のたびに専用の「大小関係フラグ」を保持するのではなく、その都度 if.xx 命令が内部で引き算を行い、結果に応じてS (スキップ) フラグを立てるという設計です。

5. addc と subc ― 16 ビットを超える数を足す

rj32 のレジスタは 16 ビットなので、1 回の add では 65535 までの数しか扱えません。もっと大きな数 (64 ビットなど) を足したいとき、docs/instructions.md が示す方法は、下の桁から順に足し、桁上がりを次の桁に持ち越すという、筆算と同じ考え方です。これを行うのが addc (キャリー付き加算) と subc (キャリー付き減算) です。

図: instructions.md に実例がある 64 ビット加算。addc が 3 回続いたあとの add だけがキャリーを引き継ぎ、その後ろの add は独立した計算に戻る。

ここで注意が必要なのは、C フラグが「次の 1 命令だけ」に効くという寿命の短さです。docs/instructions.md には「キャリーフラグは、それを使った命令が終わると、次の命令のためにリセットされる」と明記されています。addc・subc が並んでいる間はキャリーが途切れずに伝わりますが、途中に全く無関係な命令を 1 つでも挟むと、キャリーの情報は失われます。

6. 実装のポイント ― キャリーとオーバーフローを混同しない

自分で ALU やテストプログラムを作るとき、最も起きやすい間違いは「桁上がりが起きていないから計算は正しい」と思い込むことです。符号付きの数を扱っているときは、桁上がり (C フラグ) が立っていなくても、オーバーフロー (符号が壊れる現象) は起こりえます。第 3 節の図のとおり、0x7FFF + 1 では C フラグは立たないのに、符号は正から負に反転してしまいます。rj32 にはオーバーフロー専用のフラグが無いため、符号付きの計算結果が正しいかどうかを確認したいプログラムは、if.lt / if.ge のような符号付き比較命令を使って自分でチェックする必要があります。

図: C フラグの有無だけでは符号付き計算の正しさは分からない。符号付き専用のオーバーフローフラグが無い rj32 では、比較命令で自分で確かめる必要がある。

もう 1 つの実装上の注意は、addc・subc が「割り込みを受け付けない」命令であることです。docs/instructions.md によれば、これらの命令の最中に割り込みが起きるとキャリーの状態が失われてしまうため、意図的に割り込み禁止として設計されています。複数ワードの演算をまたぐ命令列を書くときは、途中に割り込みが入らないことを前提にしてよい、という設計上の約束を踏まえておく必要があります。

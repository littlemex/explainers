DEEPEP と AWS EFA

順序を仮定しない all-to-all

MoE の通信ライブラリを、順序保証のないネットワークの上で正しく動かすとはどういうことか

← explainers トップへ戻る

DeepEP は MoE の dispatch と combine を GPU カーネルから直接 NIC を叩いて実行する通信ライブラリです。そのやり方は速い代わりに、NIC の性質がアルゴリズムの前提条件になります。AWS の EFA は順序を保証しない配送 (SRD) を使うので、既存のカーネルが立っている仮定が折れます。このシリーズは amazon-contributing/DeepEP が何をどう書き替えたのかを一次ソースから読み解き、最後に「EFA インスタンスなしでその正しさを検証できるか」を判定します。

はじめての人へ: 3 分で全体像

この分野は用語が多いので、先に言葉を使わずに全体像を置きます。ここを読んでから各回に入ると、専門用語が「すでに知っている話の名前」として入ってきます。

1. そもそも何を速くしたいのか

大きな言語モデルの一種に、質問ごとに担当を決める作り方があります。すべての計算を全員でやる代わりに、入ってきた語ごとに「この語はあの担当へ」と振り分けます。担当のことを expert (エキスパート) と呼び、この作り方を MoE と呼びます。

たとえ: 大きな相談窓口を想像してください。来た相談を受付が読んで、税務の相談は税務担当へ、法務の相談は法務担当へ回します。全員が全部の相談を読むより速い。ただし相談を配る作業と返ってきた回答を集める作業が新しく必要になります。

この「配る」が dispatch、「集める」が combine です。担当は別の GPU にいるので、配ると集めるは機械と機械の間の通信になります。DeepEP はこの 2 つだけを専門に速くするライブラリです。

2. なぜネットワークの性質が問題になるのか

速くするために、DeepEP はGPU から直接ネットワーク機器へ書き込みます。CPU を通しません。速い代わりに、ネットワーク機器の性質がそのままアルゴリズムの前提になります。

たとえ: 荷物を 10 個送るとします。多くの宅配は送った順に届くとは約束しません。AWS のネットワーク (EFA) もそうで、必ず届くが、順番は約束しないという配り方をします。10 個目が 3 番目に着くことがあります。

ここで受信側の困りごとが出ます。「もう届いたか」をどう知るかです。荷物そのものを見ても、まだ届いていない箱と、届いたけれど中身が空の箱を区別できません。

3. 元のやり方と、なぜ折れるのか

DeepEP のもとの作り方は「ここまで届きました」という数字を 1 つ送ります。10 と書いてあれば 1 から 10 まで全部届いた、という約束です。1 つの数字で 10 個分の到着を代表させる、うまい圧縮です。

ただしこの圧縮は順番が守られることに立っています。順番が乱れると、10 が先に着いて 4 がまだ来ていない状態が起こり、受信側は来ていない 4 番を読んでしまいます。エラーにはなりません。静かに間違った答えが出ます。

デモ: 順番が乱れると、2 つの判定はどう違うか

送る側は荷物 10 個を出し、最後に「10 個送りました」という知らせを 1 通出します。届く順番は約束されないので、この知らせが荷物を追い越すことがあります。左は知らせを信じる元のやり方、右は届いた荷物を数える fork のやり方。何回か押してみてください。

元のやり方: 知らせが来たら全部そろったとみなす

まだ何も届いていません

fork のやり方: 届いた個数を数える

まだ何も届いていません

何度か押すと、左が赤くなる回のほうが多いことに気づくと思います。11 通の届き方をランダムに 20 万通り試すと、91.0 パーセントの順番で元のやり方は穴を読みます。数える方式は 20 万通りすべてで一度も早く読みませんでした。つまりこれは珍しい不運ではなく、順番の約束がないネットワークでは普通に起こることです。

右のやり方が地味に見えるのが大事な点です。順番に依存しない情報は「何個来たか」という数だけで、位置の情報は使えません。だから fork は「置き場所は先に決めておいて、個数だけを送る」という形に書き替えました。シリーズの中身はほぼこの一手の帰結です。

4. このシリーズの読み方

用語がわからなくなったら 用語集 に 17 語まとめてあります。まず第 1 回で「配る・集める」の中身を見て、第 3 回で「順番が約束されない」の正確な意味、第 4 回で書き替えた後の仕組み、という順に読むと素直につながります。

このシリーズの結論を先に

EFA 対応の中身は 1 つの問いへの回答です。「順序が保証されないなら、受信側はどうやって到着を知るのか」。upstream は末尾ポインタ 1 つで n 個のスロットの到着を代表させる圧縮を使っていて、その圧縮は順序保証に立っています。EFA では成立しません。

AWS fork の答えは 「位置は固定し、回数だけを送る」です。受信スロット列をコンパイル時に part へ分割し、データの中に in-band header (書き込み済みフラグ・iteration・トークン数・後続あり) を埋め、part 全体を 1 回の put で送って 番号つき weak signal を束ねます。受信側は signal の到着数 ≥ header が見えている送信元の数 で「完全に着地した」と判定します。

問いupstream の答えEFA での答え
どこまで有効か末尾ポインタという値を遠隔アトミック加算で送る位置を固定し、in-band header の count で運ぶ
もう届いたか末尾より手前は届いていると仮定するweak signal の到着数を数える
必要な signalVA signal + strong 順序番号つき weak signal だけ

この判定が正しいのは C ⊆ H (signal が届いたものは header も見えている) という包含関係のおかげで、包含関係は 3 つの不変条件に依存します。I1 = weak signal 契約、I2 = signal を先に acquire で読む、I3 = iteration の基準値が正確。fork のコードは 3 つを満たしていますが、どこにも明記されていません。

そして emulator は 作れます。NCCL の RMA plugin は完全にホスト側だけの API で、CPU proxy 経路のデータ配置と signal 更新の両方がそこを通るからです。ただし目標は「EFA を再現する」ではなく 「EFA が与える契約の下でプロトコルを詰める」に書き換える必要があります。WQE や MMIO やハードウェアカウンタは実機に残します。

この判定のうち実験でしか決まらない部分は、3 点すべて実機で確定しました。rail team はホストを分ければ knob 無しで欲しい形になる、別プロセスの GPU window へ書く仕組みは成立する (落ちるのは別 GPU 向けの権限設定だけで、ホストを分ければそこも要らない)、そして NCCL は自作の RMA plugin を実際に読み込んで communicator に割り当てる ― emulator が差し込もうとしている継ぎ目は実在します。

同時に設計が 1 か所訂正されました。RMA plugin だけでは DeepEP は走りません。カーネルに入る前に railedGinType != NONE を assert し、fork の逃げ道でその assert を越えても次のゲートで止まります。emulator は GIN plugin も名乗る必要があると実機が教えました。ソースを読んだだけでは出なかった訂正で、これが実機に払った金額の見返りです。

そして検証に必要なハードウェアが安くなりました。DeepEP のカーネルがコンパイルできる arch は 3 つだけ (sm_90 / sm_100 / sm_120) で、g5 や g6e は TMA を持たないので設定では届きません。しかし g7e.2xlarge 1 台 (GPU 1 枚、on-demand、EFA 不要) で、H100 3 台と同じ地点まで通ります。NCCL_HOSTID でノード分割を演じ、3 ランクが 1 枚の GPU を共有します。詳細は 08。

そのうえで、借りた H100 クラスタが出した最も重要な事実は判定そのものより emulator の動機を書き換えるものでした。実 EFA ハードウェアを持つ Hopper クラスタでも、fork が狙う GIN EFA-GDA backend は今日のベンダ plugin に存在しません (aws-ofi-nccl 1.18.0 は GIN の記号を 1 つも持たず、NCCL は globalGinSupport 0 と報告します)。emulator は EFA インスタンスを起動できない人のための代用品ではなく、backend が出荷されるまでこのプロトコルを検証できる唯一の手段です。

01 ・ 全体像

DeepEP とは何をするライブラリか

MoE の dispatch と combine がなぜ普通の all-to-all では書けないのか。そして「通信ライブラリなのに GPU カーネルが NIC を直接叩く」という設計が、NIC の性質をアルゴリズムの前提条件に変えてしまう構図。scale-up / scale-out / rail / hybrid の語もここで固める。

 02 ・ 層の地図

誰が WQE を書いているのか

ibverbs と libfabric は上下関係ではなく並列する 2 つの入口で、GPU 起動通信ではどちらもデータ経路にいない。V1 が mlx5 の WQE 構造体をカーネルから直接書いていた事実を見て、V2 の NCCL GIN が何を外に出したのかを確定させる。plugin ABI が 2 系統ある話も。

 03 ・ 制約 ・ デモ

SRD は何を保証しないのか

順序が乱れる粒度は 2 つ (メッセージ間と、1 メッセージの中) で、守られる約束は 1 つだけ。EFA-GDA の制約表と、upstream の末尾ポインタ方式が折れる 3 か所。3 種類の受信判定を同じ網の上で走らせるデモつきで、「header だけでは足りない」ことを確かめる。

 04 ・ 設計の本体 ・ デモ

順序を仮定しないプロトコル

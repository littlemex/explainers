DEEPEP と AWS EFA

順序を仮定しない all-to-all

MoE の通信ライブラリを、順序保証のないネットワークの上で正しく動かすとはどういうことか

← explainers トップへ戻る

DeepEP は MoE の dispatch と combine を GPU カーネルから直接 NIC を叩いて実行する通信ライブラリです。そのやり方は速い代わりに、NIC の性質がアルゴリズムの前提条件になります。AWS の EFA は順序を保証しない配送 (SRD) を使うので、既存のカーネルが立っている仮定が折れます。このシリーズは amazon-contributing/DeepEP が何をどう書き替えたのかを一次ソースから読み解き、最後に「EFA インスタンスなしでその正しさを検証できるか」を判定します。

はじめての人へ: 3 分で全体像

この分野は用語が多いので、先に言葉を使わずに全体像を置きます。ここを読んでから各回に入ると、専門用語が「すでに知っている話の名前」として入ってきます。

1. そもそも何を速くしたいのか

大きな言語モデルの一種に、質問ごとに担当を決める作り方があります。すべての計算を全員でやる代わりに、入ってきた語ごとに「この語はあの担当へ」と振り分けます。担当のことを expert (エキスパート) と呼び、この作り方を MoE と呼びます。

たとえ: 大きな相談窓口を想像してください。来た相談を受付が読んで、税務の相談は税務担当へ、法務の相談は法務担当へ回します。全員が全部の相談を読むより速い。ただし相談を配る作業と返ってきた回答を集める作業が新しく必要になります。

この「配る」が dispatch、「集める」が combine です。担当は別の GPU にいるので、配ると集めるは機械と機械の間の通信になります。DeepEP はこの 2 つだけを専門に速くするライブラリです。

2. なぜネットワークの性質が問題になるのか

速くするために、DeepEP はGPU から直接ネットワーク機器へ書き込みます。CPU を通しません。速い代わりに、ネットワーク機器の性質がそのままアルゴリズムの前提になります。

たとえ: 荷物を 10 個送るとします。多くの宅配は送った順に届くとは約束しません。AWS のネットワーク (EFA) もそうで、必ず届くが、順番は約束しないという配り方をします。10 個目が 3 番目に着くことがあります。

ここで受信側の困りごとが出ます。「もう届いたか」をどう知るかです。荷物そのものを見ても、まだ届いていない箱と、届いたけれど中身が空の箱を区別できません。

3. 元のやり方と、なぜ折れるのか

DeepEP のもとの作り方は「ここまで届きました」という数字を 1 つ送ります。10 と書いてあれば 1 から 10 まで全部届いた、という約束です。1 つの数字で 10 個分の到着を代表させる、うまい圧縮です。

ただしこの圧縮は順番が守られることに立っています。順番が乱れると、10 が先に着いて 4 がまだ来ていない状態が起こり、受信側は来ていない 4 番を読んでしまいます。エラーにはなりません。静かに間違った答えが出ます。

デモ: 順番が乱れると、2 つの判定はどう違うか

送る側は荷物 10 個を出し、最後に「10 個送りました」という知らせを 1 通出します。届く順番は約束されないので、この知らせが荷物を追い越すことがあります。左は知らせを信じる元のやり方、右は届いた荷物を数える fork のやり方。何回か押してみてください。

元のやり方: 知らせが来たら全部そろったとみなす

まだ何も届いていません

fork のやり方: 届いた個数を数える

まだ何も届いていません

何度か押すと、左が赤くなる回のほうが多いことに気づくと思います。11 通の届き方をランダムに 20 万通り試すと、91.0 パーセントの順番で元のやり方は穴を読みます。数える方式は 20 万通りすべてで一度も早く読みませんでした。つまりこれは珍しい不運ではなく、順番の約束がないネットワークでは普通に起こることです。

右のやり方が地味に見えるのが大事な点です。順番に依存しない情報は「何個来たか」という数だけで、位置の情報は使えません。だから fork は「置き場所は先に決めておいて、個数だけを送る」という形に書き替えました。シリーズの中身はほぼこの一手の帰結です。

4. このシリーズの読み方

用語がわからなくなったら 用語集 に 17 語まとめてあります。まず第 1 回で「配る・集める」の中身を見て、第 3 回で「順番が約束されない」の正確な意味、第 4 回で書き替えた後の仕組み、という順に読むと素直につながります。

このシリーズの結論を先に

EFA 対応の中身は 1 つの問いへの回答です。「順序が保証されないなら、受信側はどうやって到着を知るのか」。upstream は末尾ポインタ 1 つで n 個のスロットの到着を代表させる圧縮を使っていて、その圧縮は順序保証に立っています。EFA では成立しません。

AWS fork の答えは 「位置は固定し、回数だけを送る」です。受信スロット列をコンパイル時に part へ分割し、データの中に in-band header (書き込み済みフラグ・iteration・トークン数・後続あり) を埋め、part 全体を 1 回の put で送って 番号つき weak signal を束ねます。受信側は signal の到着数 ≥ header が見えている送信元の数 で「完全に着地した」と判定します。

問いupstream の答えEFA での答え
どこまで有効か末尾ポインタという値を遠隔アトミック加算で送る位置を固定し、in-band header の count で運ぶ
もう届いたか末尾より手前は届いていると仮定するweak signal の到着数を数える
必要な signalVA signal + strong 順序番号つき weak signal だけ

この判定が正しいのは C ⊆ H (signal が届いたものは header も見えている) という包含関係のおかげで、包含関係は 3 つの不変条件に依存します。I1 = weak signal 契約、I2 = signal を先に acquire で読む、I3 = iteration の基準値が正確。fork のコードは 3 つを満たしていますが、どこにも明記されていません。

そして emulator は 作れます。NCCL の RMA plugin は完全にホスト側だけの API で、CPU proxy 経路のデータ配置と signal 更新の両方がそこを通るからです。ただし目標は「EFA を再現する」ではなく 「EFA が与える契約の下でプロトコルを詰める」に書き換える必要があります。WQE や MMIO やハードウェアカウンタは実機に残します。

この判定のうち実験でしか決まらない部分は、3 点すべて実機で確定しました。rail team はホストを分ければ knob 無しで欲しい形になる、別プロセスの GPU window へ書く仕組みは成立する (落ちるのは別 GPU 向けの権限設定だけで、ホストを分ければそこも要らない)、そして NCCL は自作の RMA plugin を実際に読み込んで communicator に割り当てる ― emulator が差し込もうとしている継ぎ目は実在します。

同時に設計が 1 か所訂正されました。RMA plugin だけでは DeepEP は走りません。カーネルに入る前に railedGinType != NONE を assert し、fork の逃げ道でその assert を越えても次のゲートで止まります。emulator は GIN plugin も名乗る必要があると実機が教えました。ソースを読んだだけでは出なかった訂正で、これが実機に払った金額の見返りです。

そして検証に必要なハードウェアが安くなりました。DeepEP のカーネルがコンパイルできる arch は 3 つだけ (sm_90 / sm_100 / sm_120) で、g5 や g6e は TMA を持たないので設定では届きません。しかし g7e.2xlarge 1 台 (GPU 1 枚、on-demand、EFA 不要) で、H100 3 台と同じ地点まで通ります。NCCL_HOSTID でノード分割を演じ、3 ランクが 1 枚の GPU を共有します。詳細は 08。

検査の数は安心の量ではありませんでした。アサーション 210 万回・網羅検査 3 本・証明 12 本を積んでも、この開発で実際に時間を奪った欠陥は1 件も引っかかりません。すり抜けたものは全部「止まった」で、止まったことは 1 つの状態を見ても分かりません (「悪い状態にならない」と「いつか進む」は別の軸です)。そこで emulator にわざと遅く・偏って・片側だけ止まるノブを足し、時間の上限を主張するテストを 90 項目書きました。過去の欠陥を入れ直して落ちることを要求するところまでやると、4 回のうち 3 回は私のテスト側が間違っていました。詳細は 09。

そして emulator が通りました。ただしそこへ行くには、差し込み方そのものを取り替える必要がありました。ホストのスレッドが CUDA の転送で、すでに走っていて自分を待っているカーネルにバイトを届ける ― この形はこの driver では成立しません。専用に確保したメモリを専用の非ブロッキング stream で 1 MB 転送しても93 秒返らず、最後に 719 を返します。カーネルはその copy が運ぶバイトを待ち、copy はカーネルが終わるのを待つからです。BAR mapping への CPU 書き込みなら同じ状況で 0 msで、しかもそれは aws-ofi-nccl が実際に使っている機構なので、乗り換えると emulator はより忠実になりました。詳細は 10 と 11。

訂正 (2026-09-24)。「この形はこの driver では成立しない」は言い過ぎでした。常駐カーネルがいるだけなら、同じプロセスからの CUDA コピーも 1〜2 ms で届きます。止まるのは cuMemFree / cuMemFreeHost や cuModuleLoadData のような、そのカーネルの終了を待つ呼び出しが同じコンテキストの中で並行しているときだけです (確定。2 つ目のコンテキストからは止まりません)。詳細は 14 と 15。

較正は片側しか取れていません。わざと契約を破る violate-i1 を全ステップで強制し、payload を自己記述型にして 8 反復回しても、破損は 1 件も出ません。受理が counter ではなく in-band の header で門番されているので、早すぎる signal は空振りに成立して再 poll になるだけです。つまり DeepEP の unordered カーネルは契約より頑健で、この構成では検出すべき違反が存在しません。ここへ来る前にテスト側の欠陥が 2 つあり、どちらも「通った」を結果に見せていました。詳細は 12。

撤回 (2026-09-24)。この検査は combine の合計が正しい値かを照合していませんでした。送信元ごとの乱数から経路を独立に再計算するオラクルに変えると、violate-i1 は 2 回目以降の反復で combine が 128 個中 126 個誤ります。「契約より頑健」は撤回します。詳細は 14。

vLLM 経路はまだ通っていません。そこで見つかった最も重いものは DeepEP 側の欠陥で、~GPUSymmetricMemory が unwinding 中に throw して std::terminate に行きます。abort そのものではなく元の例外が破壊されることが問題で、ElasticBuffer 構築時のあらゆる失敗が理由を失った crash になります。顧客が起動失敗を報告してもログには何も残りません。もう 1 件は環境で、1 GPU に 2 rank を載せる形は NCCL_MULTI_RANK_GPU_ENABLE=1 が要ります。そして同じ 1 日に、道具が自分の理由で黙っているのを対象の答えと 7 回読み違えました。詳細は 13。

そのうえで、借りた H100 クラスタが出した最も重要な事実は判定そのものより emulator の動機を書き換えるものでした。実 EFA ハードウェアを持つ Hopper クラスタでも、fork が狙う GIN EFA-GDA backend は今日のベンダ plugin に存在しません (aws-ofi-nccl 1.18.0 は GIN の記号を 1 つも持たず、NCCL は globalGinSupport 0 と報告します)。emulator は EFA インスタンスを起動できない人のための代用品ではなく、backend が出荷されるまでこのプロトコルを検証できる唯一の手段です。

訂正 (2026-09-24)。これは aws-ofi-nccl 1.18.0 だけの話でした。1.20.0 (2026 年 4 月) から GIN が 2 経路 (proxy と GDAKI) 入っています。ただし RDMA プロトコルと GDRCopy 2.5 以上が必須で、GDRCopy が無いと初期化が失敗します。RDMA 書き込みが無い EFA 世代では SENDRECV プロトコルが選ばれ、GIN は拒否されます。「存在しない」は古い情報で、「存在するが動く条件が狭い」が今の状態です。emulator と本物の EFA-GDA backend を並べる比較は、まだ一度もできていません。詳細は 14。

そして答え合わせの機械を作ると、前回の「耐える」が壊れました。各行がどの token・どの送信元・何回目かを運ぶ自己記述 payload に加えて、受信側が送信元ごとの乱数から経路を独立に再計算し、combine の合計を正確な値と照合するオラクルを作りました。正しい経路は dispatch が 256 行中 256 行、combine が 128 個中 128 個で一致します (3 回とも)。わざと壊す試験はこのオラクルを見逃しません ―― 7 回に 1 回データを壊すと 256 行中 21 行が不一致、11 回に 1 回データを捨てると DeepEP がタイムアウトし、violate-i1 は 2 回目以降の combine で 128 個中 126 個を誤ります。誤りはいつも「相手 1 台分の値だけが前の回のまま残っている」形でした。GDRCopy を使わず CUDA コピーに戻すと DeepEP が止まる理由も、今回初めて絞れました。犯人は解放 (free) ではなく、DeepEP の JIT が dispatch の途中で呼ぶ cuModuleLoad がエミュレータの 2 本のコピーと待ち合っていたことです。詳細は 14。

そして自分専用のコンテキストに移すと、GDRCopy なしで動きました。cuModuleLoad も cuMemFree 系と同じ「コンテキスト単位のロック」だと確定したので (RTX PRO 6000 で 19.7 秒、H100 で 20.8 秒、2 つ目のコンテキストは止まらない)、コピーを自分専用のコンテキストから出すように変えました。RTX PRO 6000 の 1 台では、GDRCopy なしの 3 反復・20 反復、カーネル方式の到着通知、GDRCopy ありの 4 通りが全部一致します。ただし無料ではありません。H100 の 2 ホストでは、GDRCopy ありが全設定を約 90 秒で通るのに対し、GDRCopy なしは 1 設定あたり約 30 秒で約 30 倍遅く、原因は 2 つ目のコンテキストが常駐カーネルと GPU を時分割していて、待つたびにその代金を払っていることでした。本物の EFA は GIN 自体は立ちます (ginType: proxy(2)) が、DeepEP のバッファ作成時に aws-ofi-nccl 側の口の選び方が原因で拒否され、比較はまだできていません。詳細は 15。

そして待つのをやめると、45 分でも終わらなかった経路が 570 秒で通りました。2 つ目のコンテキストは完了を待つたびに時分割の代金を払うので、GDRCopy を使わないプロセスに限って、受信のコピー・到着通知・送信の読み出しを完了を待たずに出すようにしました。コピーと通知を 1 本のストリームにまとめ、通知の合計はロックの中で相手のデータより後に取り出し、送信は通信路ごとの待ち行列を送り出した順のまま流すことで、順序は崩れません。H100 の 2 ホストでは、GDRCopy ありの 85 秒と比べて約 6.7 倍遅いものの、全設定が 570 秒で通ります。20 反復・枠不足・カーネル方式の到着通知のいずれでも答え合わせは一致し、I1 違反も検出されます。途中で、窓の登録解除中に解放済みメモリへ書き込む穴も見つけて塞ぎました。最初に試した受信側だけ 8 枠にする案は、レビューで見つかった 3 つの穴 (カウンタの二重減算、登録解除の待ちの順序、300 µs 残る待ち) のために取り下げています。violate-i1 と待たない配達を組み合わせたときに時々起きる後片付け中のヒープ破壊は、2 つの仮説を試して両方否定し、原因不明のまま記録しています (約束どおりの試験では起きません)。詳細は 16。

そしてその落ちる原因が分かりました。壊れたヒープの中身に、切り出される前の管理情報が書き戻されていたこと、AddressSanitizer がエミュレータ自身の欠陥 (グローバル変数への書き込み、直したが症状は止まらず) を 1 つ見つけたこと、落ちた時点で窓の登録 28 件に対し登録解除が 0 件だったこと、という 3 つの手がかりから、DeepEP 側の後片付け漏れに行き着きました。DeepEP の NCCL コンテキストにはデストラクタが無く、destroy() を呼ばずにバッファが捨てられると、通信路は生きたまま窓の登録だけが残り、解放された領域が新しいスレッド用ヒープに再利用され、そこへエミュレータが書き込み続けてヒープを壊します。失敗経路でも destroy() を呼ぶように変えると、8 回中 0 回に落ちました (直前は 5 回中 2 回)。本物の EFA の NIC がどう振る舞うかは未測定です。DeepEP 側の直し方は、最初に考えた「デストラクタで窓の登録を解除する」案をレビューで危険と判断して取り下げ (通信路はこのコンテキストの持ち物ではない、まだ GPU で動く処理が窓を使っているかもしれない、登録解除に失敗してもメモリは結局解放されてしまう、という 3 つの理由)、「finalize() が済んでいなければ NCCL を一切呼ばずメモリも解放しない」案を採用しました。これで、失敗する回を 8 回回して落ちたのは 0 回、デストラクタがメモリを残したのは 16 ランク中 11 でした。DeepEP への PR の下書きとして用意していますが、提出はまだしていません。詳細は 17。

そして vLLM 自身が動くようになりました。vLLM で DeepEP V2 を使うと起動途中でセグフォルトしていた原因を、エミュレータと DeepEP 本体を AddressSanitizer で調べ、GPU 側を compute-sanitizer で調べ、第 17 回の D7 を確かめて、1 つずつ外していきました。決め手は CPython 自身のデバッグ用メモリ管理で、両ランクとも同じ場所 (56 バイトの確保の直後の 8 バイト) が壊れていました。犯人は vLLM 0.28 自身です。NCCL の通信路の性質を受け取る構造体を、NCCL 2.31 より前の 56 バイトの並びで定義したまま、NCCL には「2.31 以上だ」と申告していたため、NCCL 側が 144 バイト分書き込み、88 バイトが確保領域の外へあふれていました。この定義だけを直すと、セグフォルトは 2 回中 2 回とも起きず、vLLM は DeepEP V2 とエミュレータの上で初めて起動を完了し、対照と 1 文字も違わない正しい答えを返しました。9 月に見えていた壊れた答えも、同じ壊れ方で説明がつきます。以前の回で「DeepEP 側のホストメモリ破壊が残っていて止まっている」と書いていた箇所は誤りで、原因は vLLM 側でした。関係するのはvLLM 0.28 の利用者で、vLLM 0.30.0 では上流ですでに直っています (同じ原因を防ぐコメントが入っている)。あふれる書き込み自体は条件がそろえば毎回起きますが、それで落ちるかどうかはあふれた先に何があるかで決まり、検証機では毎回落ちました。H100 で 0.30.0 を 3 回回すと、3 回とも対照と同じ答えで、あふれも 0 件でした。詳細は 18。

そして 1 台の中の 2 ランクから、実機 2 台をまたぐ 1 ランクずつへ広げました。H100 を 1 枚ずつ積んだ 2 台に vLLM の data parallel のランクを 1 つずつ置き、DeepEP V2 のノード間通信をエミュレータに運ばせると、OLMoE-1B-7B が対照と 1 文字も違わない答えを返しました。途中で見つけたのは、NCCL の進捗スレッドがエミュレータの getenv の中で落ちる欠陥です。getenv はロックなしで環境変数の一覧をたどり、DeepEP はバッファを作るときに setenv を呼ぶため、繰り返し通る場所で毎回読んでいたのが仇になりました。最初の 1 回だけ読む形に直すと、次の回で成功しました (どちらも 1 回ずつの観測です)。これで、EFA の無い環境でも DeepEP V2 の本物の推論ワークロードを複数ノードにまたがって答えの正しさまで確かめられますが、中身は TCP で速さは比べられず、本物の EFA との比較はまだできていません。GDRCopy 無しの待たない配達 (第 16 回) でも、この 2 台構成で同じ答えが返り、全体で 489 秒でした。詳細は 19。

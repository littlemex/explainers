レプリケーション入門 ― 複製はなぜ遅れ、なぜ消えるのか

データを複数ノードにコピーするだけなら簡単だが、「いつ複製するか」の選び方が遅延・消失・読み取りの不思議な挙動を生む

この回の前提: 第 01 回 なぜ分散するのか、第 03 回 スケーリングとロードバランサ。

結論を先に言うと、レプリケーションとは「同じデータを複数のノードに持たせて、1 台が壊れても失わず、読み取りを分散できるようにする仕組み」であり、その代償として「どのノードを読んでも必ず最新の値が返るとは限らない」という新しい問題を引き受けることになる。この回では、最も基本的なリーダー/フォロワー (leader/follower) 型の複製を取り上げ、同期・非同期という複製タイミングの選択が、遅延・読み取りの不整合・フェイルオーバー時のデータ消失にどうつながるかを見る。

1. なぜレプリケーションが要るのか

データベースを 1 台だけで運用すると、2 つの限界にすぐぶつかる。1 つ目は耐障害性で、その 1 台のディスクが壊れたり、データセンターが停電したりすれば、サービス全体のデータが読めなくなる。2 つ目は読み取りの負荷で、注文確認・履歴表示のような読み取り要求は書き込みより圧倒的に多いことが普通だが、1 台のサーバーが処理できる読み取り量には上限がある。

この 2 つを同時に解決する最も素朴な方法が、同じデータをコピーしたレプリカ (replica, 複製) を複数のノードに置くことである。1 台 (元データを持つノード) が壊れても他のレプリカにデータが残り、読み取り要求を複数のレプリカに分散すれば 1 台あたりの負荷も下がる。ByteByteGo の read replica pattern では、Amazon のような通販サイトで注文を作成する処理 (書き込み) は primary (プライマリ, 元データを持つノード) に送り、注文詳細や履歴の表示 (読み取り) は replica (レプリカ) から読む構成が紹介されている。

図: DB 1 台から Leader/Follower 構成に複製すると、耐障害性と読み取りスケールの両方が手に入る。

2. リーダー/フォロワー構成の仕組み

最も基本的な複製方式はリーダー/フォロワー (leader-follower, 主系/従系) 型である。1 つのノードをリーダー (primary, プライマリとも呼ぶ) に決め、データを変更する命令 (INSERT, UPDATE, DELETE) はすべてリーダーに送る。リーダーはその変更を自分のデータに適用したあと、変更内容をフォロワー (follower, レプリカ) に送って同じ変更を適用させる。読み取りはリーダーでもフォロワーでも行える。

書き込み経路を 1 本のリーダーに固定する理由は単純で、複数のノードが同時に同じ行を書き換えようとすると「どちらの書き込みが正しいか」という競合が発生する。リーダーを 1 つに絞れば、その競合はリーダーの中だけで解決すればよくなり、フォロワーは「リーダーが決めた順番をそのまま追いかけるだけ」の役割に単純化できる。

ByteByteGo の read replica pattern の実装編 (how-to-implement-read-replica-pattern) では、どのクエリをリーダーに送り、どのクエリをフォロワーに送るかを振り分ける方法として、(a) アプリケーションのコードに振り分けロジックを書き込む方法と、(b) データベースミドルウェア をアプリケーションと DB の間に挟んで振り分けを任せる方法の 2 つを挙げている。ミドルウェア方式はアプリケーション側がトポロジを意識しなくて済む利点があるが、ミドルウェア自身が単一障害点になりやすく、追加のネットワークホップ分のレイテンシが乗るという代償がある。

図: 書き込みは必ずリーダーを通す。リーダーはその変更をフォロワーに送って同じ状態を再現させる。

3. 同期・非同期・準同期 ― いつ複製するかの選択

リーダーが書き込みを受け取ったあと、クライアントに「書き込み成功」と応答するタイミングには 3 つの選び方がある。

同期複製 (synchronous) ― リーダーは、少なくとも 1 台 (または全台) のフォロワーが変更を受け取って確認 (ack) を返すまで、クライアントへの応答を待つ。フォロワーに確実にデータが届いた状態を保証できるので安全だが、フォロワーが遅い・落ちていると書き込み自体が止まってしまい、可用性が下がる。

非同期複製 (asynchronous) ― リーダーは自分の適用が終わった時点で即座にクライアントへ「成功」と応答し、フォロワーへの複製はバックグラウンドで進める。書き込みの応答が速く、フォロワーの遅延がリーダーの可用性に影響しないが、複製が完了する前にリーダーが壊れると、その書き込みはフォロワー側には存在しないまま消えてしまう危険がある。

準同期複製 (semi-synchronous) ― 全フォロワーではなく、決めておいた一部 (多くは 1 台) のフォロワーからの ack だけを待ち、残りは非同期で追いかけさせる。同期ほど可用性を落とさずに、少なくとも 1 つのコピーには確実に書き込みが残っているという保証を得る、中間的な選択である。

図: 同期はフォロワーの ack を待ってから応答、非同期はリーダー側の適用だけで即応答する。

4. レプリケーション遅延が壊すもの ― read-your-writes と単調読み取り

非同期複製や、同期でも一部のフォロワーだけを待つ構成では、フォロワーの内容がリーダーより少し古い時間帯が必ず生まれる。これをレプリケーション遅延 (replication lag) と呼ぶ。遅延が数十ミリ秒でも、タイミングが悪いと利用者が「おかしな挙動」として体感してしまう。

ByteByteGo の read replica pattern で挙げられている例はこうだ。Alice が注文を確定すると、Order Service はその注文をリーダーに書き込む。直後に Alice が注文状況を確認すると、その読み取りがまだ更新を受け取っていないフォロワーに向けば、Alice は自分がついさっき確定した注文が「存在しない」ように見えてしまう。これはread-your-writes 一貫性 (自分の書いた結果は自分には必ず見える、という期待) が破られた状態である。

似た問題に単調読み取り (monotonic reads) の違反がある。1 回目の読み取りで新しい値が見えたのに、2 回目の読み取り (別のフォロワーに向いた) で古い値に「戻って見える」現象で、同じ利用者が時間を遡ったように感じてしまう。

ByteByteGo が挙げる緩和策は、(1) 最新性が重要な読み取りはリーダーに直接送る、(2) 書き込み直後の読み取りだけリーダーに送る、(3) フォロワーがリーダーにどれだけ追いついているかを確認し、追いついていればフォロワーから読み、遅れていればリーダーから読むか失敗を返す、という 3 つである。

図: 複製完了前にフォロワーへ向いた読み取りは、直前の自分の書き込みを見られない。

5. フェイルオーバーで書き込みが消える理由

リーダーが故障すると、システムはフォロワーの中から新しいリーダーを選び直す。この切り替えをフェイルオーバー (failover) と呼ぶ。問題は、非同期複製の場合、故障した旧リーダーがクライアントに「成功」と応答した書き込みの中に、どのフォロワーにもまだ届いていなかったものが含まれている可能性があることだ。

新リーダーに選ばれたフォロワーは、自分が持っているデータを正として動き出す。つまり旧リーダーだけが知っていた「未複製の書き込み」は、どこにも残っていないため、クライアントから見ると確定したはずの書き込みが消えるという結果になる。これは「可用性のために非同期を選ぶと、フェイルオーバー時のデータ消失というコストを引き受ける」というトレードオフであり、第 08 回で扱う CAP 定理の A (可用性) を優先した設計が持つ典型的な代償でもある。

同期複製であればこの消失は起きない (応答を返した時点でフォロワーにも確実に届いているため) が、代わりにフォロワーが 1 台でも遅れると書き込みの応答そのものが止まる。準同期複製はこの消失範囲を「ack を返した 1 台が同時に全滅する」という低い確率の事象に縮小するが、ゼロにはできない。

図: 非同期複製では、応答済みの書き込みがフォロワーに届く前にリーダーが落ちると、その書き込みは消える。

6. 実システムでの選び方

多くのリレーショナルデータベースは、既定では非同期複製を使う。書き込みのスループットと応答速度を優先し、フェイルオーバー時の消失リスクは運用側が許容する設計である。一方で、より強い保証が欲しい場合に、1 台のフォロワーだけを同期にする準同期複製のオプションを提供する製品も多い。どちらを選ぶかは「応答速度と可用性」と「フェイルオーバー時の消失リスク」のどちらを優先するかという、業務要件そのものに依存する判断になる。

ByteByteGo の read replica pattern 実装編が指摘するとおり、読み取りの振り分けをアプリケーションのコードに直接書くか、データベースミドルウェアに任せるかという選択も、この文脈でのもう一つの設計判断である。ミドルウェアはアプリケーションを DB トポロジから解放する一方、ミドルウェア自体の高可用化という新しい運用課題を生む。

制約で正しさを守る ― アプリの検証だけでは足りない

「アプリケーションコードで入力チェックをしているから大丈夫」という考え方は、そのアプリ以外の経路 (別のサービス、バッチ処理、psql での手作業) から書き込みが入る可能性がある限り成立しません。この回では CHECK ・ DOMAIN ・ 生成列 ・ EXCLUDE 制約 ・ 部分一意インデックスという、PostgreSQL がデータそのものに正しさを縛り付ける仕組みを、実際に制約を破ろうとしたときのエラーで確認します。

この回の前提: 第 26 回 外部キーのミニ・アンチパターン (NOT VALID や DEFERRABLE などの制約の基礎) ・ 第 11 回 サーティワンフレーバー (CHECK 制約の初出)

この回で答えるのは「入力値の正しさを、アプリケーションのコードだけで守ってよいか」という問いです。結論は、アプリのコードはそのアプリを経由した書き込みしか検証できないが、データベースの制約はどの経路から書き込まれても必ず検査されるということです。CHECK ・ DOMAIN ・ 生成列 ・ 範囲型 + EXCLUDE 制約 ・ 部分一意インデックスという 5 つの道具を、実際に制約を破ろうとしたときに PostgreSQL 18 が返したエラーで確認します。

1. この回で解く問題 ― アプリの外から書き込まれたらどうなるか

「作業時間 (hours) は 0 以上でなければならない」という規則を、アプリケーションの入力フォームでチェックしているとします。これで安全だと思えるかもしれませんが、同じテーブルには他にも書き込みの経路があります。管理者が psql で直接 UPDATE する、別のバッチ処理が値を書き換える、将来追加される別のサービスがこのテーブルに直接書き込む、といった経路です。アプリのコードは、そのアプリを経由しない書き込みを一切検査できません。

この問題を解決するのが、データベース側の制約 (constraint) です。制約はテーブルの定義そのものに縛り付けられているので、INSERT や UPDATE がどの経路から来ても、必ず同じ検査を通過しなければコミットできません。この回では、単純な範囲の制約 (CHECK) から、複数の行をまたいだ「時間の重なりを禁止する」制約 (EXCLUDE) まで、PostgreSQL が提供する制約の道具を順番に見ていきます。

図: アプリの検証は 1 つの経路しか守らないが、制約はテーブルへのすべての経路を守る。

2. 仕組み ― CHECK と DOMAIN

CHECK 制約は、1 行の中の列の値に対する条件を列単位・行単位で宣言します。bugs.hours (作業時間) が負の値にならないようにした実機の結果です。

ALTER TABLE bugs ADD CONSTRAINT bugs_hours_nonneg CHECK (hours >= 0);
UPDATE bugs SET hours = -1 WHERE bug_id = 1;
-- ERROR:  new row for relation "bugs" violates check constraint "bugs_hours_nonneg"

この制約が付いた後は、アプリのコードを経由しているかどうかに関わらず、hours に負の値を書き込もうとする行は必ず拒否されます。

同じ形式の制約を複数の列や複数のテーブルで繰り返し使いたい場合は、DOMAIN (ドメイン) を使うと、制約込みの型を 1 回定義して使い回せます。メールアドレスらしい形式を要求するドメインを作り、accounts.email の型として使った実機の結果です。

CREATE DOMAIN email_address AS text CHECK (VALUE ~ '^[^@\s]+@[^@\s]+\.[^@\s]+$');
ALTER TABLE accounts ALTER COLUMN email TYPE email_address;
UPDATE accounts SET email = 'not-an-email' WHERE account_id = 1;
-- ERROR:  value for domain email_address violates check constraint "email_address_check"

CHECK 制約はそのテーブルの中だけで有効ですが、DOMAIN は型そのものに制約が付くので、別のテーブルで同じ email_address 型の列を作れば、同じ検査がそのテーブルにもそのまま適用されます。「メールアドレスらしい形式」のような、複数のテーブルで繰り返し必要になる検査は DOMAIN に寄せておくと、検査のルールが 1 か所に集約されます。

図: CHECK は 1 つのテーブルに付くが、DOMAIN は型として複数のテーブルをまたいで再利用できる。

3. 仕組み ― 生成列 (STORED と PostgreSQL 18 の VIRTUAL)

生成列 (generated column) は、同じ行の他の列から計算した値を列として持たせる仕組みです。「アプリ側で毎回計算して書き込む」のではなく、「データベースに計算のルールそのものを登録する」ことで、計算忘れや計算ミスを無くします。bugs.summary の文字数を、STORED と、PostgreSQL 18 で追加された VIRTUAL の両方で定義した実機の結果です。

ALTER TABLE bugs ADD COLUMN summary_len_stored int GENERATED ALWAYS AS (length(summary)) STORED;
ALTER TABLE bugs ADD COLUMN summary_len_virtual int GENERATED ALWAYS AS (length(summary)) VIRTUAL;
SELECT bug_id, summary, summary_len_stored, summary_len_virtual FROM bugs WHERE bug_id = 1;
bug_idsummarysummary_len_storedsummary_len_virtual
1crash when saving1717

どちらも同じ値 (17 文字) を返しますが、計算されるタイミングが違います。pg_attribute.attgenerated という内部カタログを見ると、STORED は s、VIRTUAL は v という区別が付いていることが確認できます。

SELECT attname, attgenerated FROM pg_attribute
WHERE attrelid = 'bugs'::regclass AND attname IN ('summary_len_stored','summary_len_virtual');
--  summary_len_stored  | s
--  summary_len_virtual | v

STORED は書き込み時に計算してディスクに保存するので、読み取り時の計算コストは掛かりませんが、書き込み時に計算コストが掛かり、ディスク容量も消費します。VIRTUAL は読み取るたびに計算するので、ディスク容量を消費しない代わりに、読み取りのたびに計算コストが掛かります。STORED と VIRTUAL のどちらも書かずに GENERATED ALWAYS AS (...) だけを書くと、PostgreSQL 18 では VIRTUAL が既定になります (実機で attgenerated が v になることを確認済み)。PostgreSQL 17 以前は生成列が STORED しか無かったので、この既定の変化は書き方を変えていないつもりでも挙動が変わる落とし穴になります。どちらも、UPDATE でその列に直接値を書き込もうとすると拒否されます。

UPDATE bugs SET summary_len_stored = 999 WHERE bug_id = 1;
-- ERROR:  column "summary_len_stored" can only be updated to DEFAULT
-- DETAIL:  Column "summary_len_stored" is a generated column.

「summary を変更したのに文字数の列を更新し忘れる」という不整合が、生成列を使うことで構造上発生しなくなります。これは単なる自動計算の便利機能ではなく、「この列の値は必ずこの式から導出される」という正しさの宣言そのものです。

図: STORED は書き込み時に計算して保存、VIRTUAL は読み取り時にその場で計算する。

4. 仕組み ― 範囲型と EXCLUDE 制約で予約の重なりを防ぐ

CHECK 制約は 1 行の中だけを検査しますが、「同じ会議室の予約時間が重なってはいけない」という規則は、複数の行をまたいだ比較が必要です。これを 1 つの制約として宣言できるのが EXCLUDE 制約です。PostgreSQL の範囲型 (tsrange など) と組み合わせ、「同じ room_id で、かつ時間帯が重なる (&&) 行があってはならない」と宣言します。

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_bookings (
  booking_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id int NOT NULL,
  during tsrange NOT NULL,
  booked_by bigint NOT NULL REFERENCES accounts(account_id),
  EXCLUDE USING gist (room_id WITH =, during WITH &&)
);

room_id のような等値比較 (=) を GiST インデックスの中で使うには、contrib 拡張の btree_gist が必要です。範囲の重なり判定 (&&) はもともと GiST が得意とする演算ですが、通常の等値比較はそうではないため、btree_gist がその橋渡しをします。実際に予約を入れてみた結果です。

INSERT INTO room_bookings (room_id, during, booked_by) VALUES
  (101, '[2026-04-01 10:00, 2026-04-01 11:00)', 1);   -- 成功
INSERT INTO room_bookings (room_id, during, booked_by) VALUES
  (102, '[2026-04-01 10:00, 2026-04-01 11:00)', 2);   -- 成功 (別の room_id なので重ならない)
INSERT INTO room_bookings (room_id, during, booked_by) VALUES
  (101, '[2026-04-01 11:00, 2026-04-01 12:00)', 3);   -- 成功 (同じ room_id だが時間が重ならない)
INSERT INTO room_bookings (room_id, during, booked_by) VALUES
  (101, '[2026-04-01 10:30, 2026-04-01 10:45)', 4);   -- 失敗
ERROR:  conflicting key value violates exclusion constraint "room_bookings_room_id_during_excl"
DETAIL:  Key (room_id, during)=(101, ["2026-04-01 10:30:00","2026-04-01 10:45:00")) conflicts with
         existing key (room_id, during)=(101, ["2026-04-01 10:00:00","2026-04-01 11:00:00")).

4 番目の予約は、同じ room_id=101 で、既存の予約 (10:00〜11:00) と時間が重なる (10:30〜10:45) ため、挿入する前に拒否されました。エラーメッセージには、どの既存の行と衝突したかまで表示されています。アプリ側で「既存の予約を検索して重なりを確認してから挿入する」というコードを書くと、第 31 回で見た check-then-act のレースがそのまま発生しますが、EXCLUDE 制約はこの検査と拒否を 1 つの INSERT 文の中で、データベース側がアトミックに行います。

図: EXCLUDE 制約は、同じ room_id の中で時間帯が重なる行の挿入を拒否する。

5. 仕組み ― 部分一意インデックス

「accounts の中で、既定の管理者として選ばれているのは必ず 1 人以下」という規則は、is_default_admin という真偽値の列全体に一意制約を付けるだけでは実現できません。false の行は何行あってもよく、true の行だけが 1 行以下であるべきだからです。これを実現するのが部分一意インデックス (partial unique index、WHERE 句付きの一意インデックス) です。

ALTER TABLE accounts ADD COLUMN is_default_admin boolean NOT NULL DEFAULT false;
CREATE UNIQUE INDEX accounts_one_default_admin ON accounts (is_default_admin) WHERE is_default_admin;

UPDATE accounts SET is_default_admin = true WHERE account_id = 1;
-- 成功: account_id=1 が true、他の 3 人は false
UPDATE accounts SET is_default_admin = true WHERE account_id = 2;
-- ERROR:  duplicate key value violates unique constraint "accounts_one_default_admin"
-- DETAIL:  Key (is_default_admin)=(t) already exists.

このインデックスは WHERE is_default_admin という条件に合う行 (true の行) だけを対象にしているので、false の行はインデックスに含まれず、何行あっても一意制約の対象外です。true の行が 2 行目になろうとした瞬間だけ、一意制約が働いて拒否されます。普通の一意制約では「全ての行で値が重複してはいけない」としか書けませんが、部分一意インデックスは「ある条件に合う行の中でだけ重複してはいけない」という、より細かい正しさを表現できます。

図: WHERE 句付きの一意インデックスは、条件に合う行だけを一意性の対象にする。

6. どこで壊れるか ― よくある間違い

間違い 1: 制約を付けずにアプリ側の検証だけに頼る

節 1 で見たとおり、アプリのコードはそのアプリを経由した書き込みしか検証できません。別のサービスやバッチ処理が同じテーブルに書き込む計画が将来出てきた時点で、アプリ側の検証はすり抜けられます。「今は 1 つのアプリしか書き込んでいないから大丈夫」という判断は、将来の経路の増加に対して脆くなります。

間違い 2: 複数行をまたいだ規則を 1 行の CHECK で表現しようとする

CHECK 制約は 1 行の中の列の値しか参照できません。「同じ会議室の予約が重ならない」のような複数行をまたいだ規則を CHECK で書こうとすると、サブクエリを使った CHECK は許可されておらずエラーになります。このような規則には EXCLUDE 制約や、トリガーによる検証が必要です。

間違い 3: 生成列に使う式が IMMUTABLE でない関数を含む

生成列の式には、同じ入力に対して常に同じ結果を返す (IMMUTABLE な) 関数しか使えません。now() のような現在時刻に依存する関数を生成列の式に使おうとすると、エラーになります。生成列は「この行の他の列から導出できる値」のためのものであり、外部の状態に依存する値には向きません。

図: 1 行の中の規則か、複数行をまたぐ規則かで、適した制約の種類が変わる。

7. シニアの書き方 ― 制約はアプリの検証より強い理由

アプリケーションの入力検証は「利用者に分かりやすいエラーメッセージを早い段階で返す」という役割において重要ですが、それだけではデータの正しさを保証する役割を果たせません。制約が無いテーブルは、どれだけアプリ側の検証を頑張っても、アプリ以外の経路からの書き込みに対して無防備なままです。

1. 業務上「絶対に成立してはいけない」規則は、必ずデータベースの制約として書く。「負の時間はあり得ない」「同じ会議室の予約は重ならない」のような、ビジネス上の不変条件は、アプリのコードではなく制約として表現します。

2. アプリの検証とデータベースの制約は、役割分担であって二択ではない。アプリ側の検証は、利用者に早く分かりやすいフィードバックを返す役割を担い、データベースの制約は、どんな経路からでも最終的な正しさを保証する役割を担います。両方があって初めて、使いやすさと正しさの両方が手に入ります。

3. 複数行をまたぐ規則こそ、制約で守る価値が高い。1 行の中の検証はアプリ側でもそれなりに書けますが、「2 つの行の値が同時に満たすべき関係」は、アプリのコードで正しく書くのが難しく、しかもレース (第 31 回で見た check-then-act の競合) が入り込みやすい領域です。EXCLUDE 制約のような、データベースが複数行を一度に見て検査する仕組みは、この種の規則に向いています。

Kubernetes は「望む状態」の台帳

API サーバーと etcd、コントローラー、kubelet はそれぞれ何を見て動いているのか

← カスタムコントローラー自作 シリーズ目次へ

このシリーズは全 18 回。「CRD (Custom Resource Definition: Kubernetes に新しい種類の物を登録するための宣言) とコントローラーの違いすら分からない」ところから始めて、最後には自分で CRD とコントローラーを設計・実装できるようになることを目指す。第 01 回では、細かい文法より先に、Kubernetes 全体がどういう仕組みで動いているかの地図を描く。

Kubernetes に何かを頼むというのは、作業の手順を渡すことではない。「こうなっていてほしい」という希望を台帳(etcd)に書き込むことに等しい。頼んだ瞬間には何も動いていない。希望を実現するのは、台帳を見ている別のプログラム(コントローラーや kubelet)であり、それらは頼んだ人とは無関係に、台帳を見ては動き、また見ては動く、という繰り返しをずっと続けている。

1. 命令型と宣言型

ソフトウェアに仕事をさせる方法は大きく 2 つある。1 つは命令型(imperative: どう動くかを 1 手順ずつ指示する)で、「コンテナ(container: アプリとその実行環境を 1 つにまとめた、起動の最小単位)を 1 つ起動せよ」「もう 1 つ起動せよ」「もう 1 つ起動せよ」と、やることを順番に命令する。もう 1 つは宣言型(declarative: どうなっていてほしいかを記述する)で、「コンテナが 3 つある状態にせよ」と結果だけを伝え、そこへ至る手順は相手に任せる。

Kubernetes の kubectl にも実は両方の顔がある。公式ドキュメントは kubectl run・kubectl scale のように、その都度「起動せよ」「台数を変えよ」と操作を直接指示するコマンドを「命令型コマンド」と呼ぶ(Managing Kubernetes Objects Using Imperative Commands)。YAML ファイル(YAML: 人が読み書きしやすい、インデントで構造を表すデータ形式)を使う場合でも、kubectl create -f file.yaml のように「作成せよ」と操作そのものを指定する使い方は、公式には「命令型のオブジェクト管理」に分類され、まだ命令型の側にいる。これに対して kubectl apply -f file.yaml は、ファイルの内容を正としたうえで「作成するか更新するか」の判断そのものを kubectl 自身に委ねる使い方で、これが「宣言型のオブジェクト管理」と呼ばれる理由だ。ただし Kubernetes というシステム全体の設計思想は宣言型が土台で、このシリーズで作るコントローラーも「今の状態を見て、望む状態に近づける」という宣言型の考え方をそのまま使う。

図: 命令型は手順の列、宣言型は結果の状態とそれを維持する繰り返しの矢印。

2. 誰が何を見ているか(全体の地図)

Kubernetes クラスタには主に 4 種類の役が登場する。API サーバー(kube-apiserver: HTTP(ウェブなどで使われる通信の約束事)の API を外に公開する窓口。公式には「The core component server that exposes the Kubernetes HTTP API」(Kubernetes の HTTP API を外に公開する中核のコンポーネントサーバー)と説明されている)、etcd(API サーバーが持つ全データの、一貫性が保たれた key-value(名前と値を対にして保存する単純な方式)の保存場所)、コントローラー(controller: API サーバーが持つ情報を見て、現実をそれに近づけるプログラム)、kubelet(各ノード(node: クラスタを構成する 1 台のマシン)で「Pod(1 つ以上のコンテナをまとめて動かす、Kubernetes の最小の実行単位)が確実に動いている状態」を保つプログラム)だ(Kubernetes Components)。

重要なのは、コントローラーも kubelet も、API サーバーから最初に一覧をまとめて受け取り、その後は変更だけを流してもらう(list + watch という方式。詳しくは第 09 回)という形で、常に台帳の中身を把握し続けている点だ。一定時間おきに尋ね直しているわけではなく、彼らは誰かから直接指示を受けるのでもなく、台帳の中身を見て自分の判断で動く。

図: あなたは API サーバーにしか話しかけない。実際に動くのはコントローラーと kubelet。

3. kubectl apply は何をして、何をしないか

kubectl apply -f deployment.yaml を実行すると、何が起きるだろうか。実際に起きるのは「YAML の内容を API サーバーに送り、API サーバーがそれを検証して etcd に保存する」ことだけだ。Pod が実際に起動する、コンテナイメージが取得される、といった現実の変化は、この 1 回の呼び出しの中では起きていない。

保存された情報を見て「Deployment(deployment: 同じ Pod を指定した数だけ動かし続けることを宣言する、組み込みの型)が 3 レプリカ欲しいと言っている、今は 0 個しかない」と気づき、ReplicaSet(replicaset: 指定した数だけ Pod のコピーを保つことだけを担当する、Deployment の下請けの型)や Pod を作るのは別のプログラム(コントローラー、第 03 回)だ。その Pod をどのノードに置くか割り当てるのは kube-scheduler、Pod の中でコンテナイメージを取得して実際に起動するのはさらに別のプログラム(kubelet)だ。kubectl apply の呼び出しは、その両方よりずっと先に、しかも一瞬で終わっている。

このズレがあるからこそ、kubectl apply が成功しても Pod が Running になるまでには数秒から数十秒のタイムラグがある。この間、Pod は Pending という状態で、kube-scheduler によるノードの割り当てや、kubelet によるコンテナイメージの取得を待っている。コマンドの成功は「台帳への書き込みが受理された」ことしか保証しない。

図: コマンドが返ってきた時点では、現実はまだ何も変わっていない。

まとめと次の回

Kubernetes を操作するとは、台帳(etcd)に望む状態を書き込むことであり、実現は別のプログラムに委ねられている。この「見る・比べる・近づける」という繰り返しの型は、このシリーズ全体を貫く最重要の前提になる。第 02 回では、台帳に書き込む「物」の住所(Group / Version / Kind)と型の仕組みを見ていく。

図: 「書く人」と「実現する人」は別。このシリーズではその両方を作る。

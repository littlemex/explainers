この回の前提: 第 01 回 なぜ分散するのか

前回、複数台になった瞬間にネットワークという新しい失敗の経路が増えることを見ました。この回では、そのネットワークを実際にプログラムから操作する最初の一歩、ソケット (socket) という API を手で動かします。結論を先に言うと、TCP が運ぶのは「メッセージの列」ではなく「ただのバイトの流れ」です。送信側が 3 回 send() を呼んでも、受信側は 1 回の recv() でその 3 回分をまとめて受け取ることがあります。この事実を知らずに書かれたコードは、開発環境では動くのに本番の負荷がかかった瞬間に壊れます。実際に動くコードで、この現象と対処法 (フレーミング) を確認します。

1. ソケットという API と 3-way ハンドシェイク

ソケット (socket) は「ネットワーク越しの通信の端点」を表す OS のオブジェクトです。TCP でサーバーを作る側は socket() で端点を作り、bind() で自分の IP アドレスとポート番号をその端点に割り当て、listen() で「接続を受け付ける状態」にし、accept() で実際に 1 件の接続が来るまで待ちます。クライアント側は socket() で端点を作ったあと connect() を呼ぶだけで、相手に接続を申し出ます。

connect() を呼んだ瞬間、OS 同士が裏で TCP の3-way ハンドシェイク (3 回の往復による接続確立) を行います。クライアントが接続要求 (SYN) を送り、サーバーがそれを受理したことと自分も接続したい意思を 1 つにまとめて返し (SYN-ACK)、クライアントが最後に確認 (ACK) を返した時点で接続が確立します。この 3 回の往復が終わるまで、サーバー側の accept() は戻ってきません。切断も同様に往復が必要で、通常はどちらか一方が close() を呼ぶと FIN が送られ、相手が ACK を返し、相手側も FIN を送って ACK が返るという 4 回のやり取り (4-way) で終わります。

図: accept() と connect() が戻るのは、3 回の往復 (SYN → SYN-ACK → ACK) が完了した後。

2. TCP はバイトの流れでしかない

ここがこの回で最も重要な事実です。TCP が送受信するのは「メッセージの列」ではなく、ただのバイトストリーム (バイトの流れ) です。送信側で send() を何回呼んだかという情報は、受信側には一切伝わりません。受信側の recv() は「今読める分だけ」を返すだけで、それが送信側の 1 回の send() と一致する保証はどこにもありません。

実際に手元で確認した例を見てください。クライアントが sendall(b"MSG1")、sendall(b"MSG2")、sendall(b"MSG3") と 3 回別々に送っても、サーバー側が recv(4096) を 1 回呼んだだけで、3 つ分が連結された 12 バイト b'MSG1MSG2MSG3' が丸ごと返ってくることがあります。

HOST = "127.0.0.1"
PORT = 50008

def main():
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as client:
        client.connect((HOST, PORT))
        client.sendall(b"MSG1")
        client.sendall(b"MSG2")
        client.sendall(b"MSG3")

if __name__ == "__main__":
    main()

上のクライアントを、recv(4096) を 1 回だけ呼ぶ単純なサーバーに接続すると、次のような出力になります (実際に手元で実行して確認した結果です)。

server got one recv() of 12 bytes: b'MSG1MSG2MSG3'

逆方向の崩れ方もあります。1 回の大きな send() が、受信側では複数回の recv() に分割されて届くことも普通に起こります。原因は OS のバッファリング、ネットワーク経路上のパケットサイズの上限 (MTU)、そして Nagle のアルゴリズム (小さな書き込みを一時的にまとめてから送る最適化) です。どちらの方向に崩れるにせよ、結論は同じです。送信側の呼び出し回数と受信側の呼び出し回数は対応しない。

図: 3 回の送信が 1 回の受信にまとまることもあれば、1 回の送信が複数回に分かれて届くこともある。

3. フレーミングで境界を作る ― 動くエコーサーバー

境界が無いなら、アプリケーション側で境界を作ってしまえばよい、というのが解決の方針です。最も単純で広く使われる方法が長さ前置フレーミング (length-prefix framing) です。送るデータの前に「これから何バイト送るか」を固定長 (ここでは 4 バイト) で書いてから本体を送ります。受信側は、まず固定長のヘッダーを 指定したバイト数になるまで 読み切り、そこから長さを取り出して、本体も同じように指定バイト数になるまで読み切ります。recv() は要求したバイト数より少なく返すことがあるため、「欲しい量になるまで繰り返し呼ぶ」補助関数が要になります。

以下は実際に手元で実行して動作を確認した、最小のエコーサーバーとクライアントです (localhost のみ、起動後すぐに終了します)。サーバーはフレームを 1 つ受け取るたびに大文字にして返すだけの単純な処理です。

import socket
import struct

HOST = "127.0.0.1"
PORT = 50007

def recv_exact(conn, size):
    buf = b""
    while len(buf) < size:
        chunk = conn.recv(size - len(buf))
        if not chunk:
            raise ConnectionError("peer closed before full message arrived")
        buf += chunk
    return buf

def recv_message(conn):
    header = recv_exact(conn, 4)
    (length,) = struct.unpack("!I", header)
    return recv_exact(conn, length)

def send_message(conn, data):
    header = struct.pack("!I", len(data))
    conn.sendall(header + data)

def main():
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as server:
        server.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        server.bind((HOST, PORT))
        server.listen(1)
        conn, addr = server.accept()
        with conn:
            while True:
                try:
                    data = recv_message(conn)
                except ConnectionError:
                    break
                send_message(conn, data.upper())

if __name__ == "__main__":
    main()
import socket
import struct

HOST = "127.0.0.1"
PORT = 50007

def recv_exact(conn, size):
    buf = b""
    while len(buf) < size:
        chunk = conn.recv(size - len(buf))
        if not chunk:
            raise ConnectionError("peer closed before full message arrived")
        buf += chunk
    return buf

def recv_message(conn):
    header = recv_exact(conn, 4)
    (length,) = struct.unpack("!I", header)
    return recv_exact(conn, length)

def send_message(conn, data):
    header = struct.pack("!I", len(data))
    conn.sendall(header + data)

def main():
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as client:
        client.connect((HOST, PORT))
        for text in ["hello", "distributed systems", "bye"]:
            data = text.encode("utf-8")
            send_message(client, data)
            reply = recv_message(client)
            print(f"sent {data!r} -> got {reply!r}")

if __name__ == "__main__":
    main()

サーバーを先に起動し、続けてクライアントを実行すると、次のように表示されます (実際に手元で実行した結果)。

sent b'hello' -> got b'HELLO'
sent b'distributed systems' -> got b'DISTRIBUTED SYSTEMS'
sent b'bye' -> got b'BYE'

struct.pack("!I", ...) の ! は「ネットワークバイトオーダー (ビッグエンディアン)」を明示する指定で、I は符号なし 4 バイト整数を意味します。送信側と受信側が異なる CPU アーキテクチャで動いていても、バイトの並び順の解釈がずれないようにするためのものです。

図: 長さ前置フレーミングは、本体の前に固定長のヘッダーでサイズを書くだけで境界を復元できる。

4. UDP との違い ― 境界はあるが届く保証は無い

TCP と対になるプロトコルが UDP です。UDP は面白いことに、TCP とちょうど逆の性質を持ちます。sendto() で送った 1 回分 (データグラム) は、相手に届けば recvfrom() の 1 回でそのまま丸ごと受け取れます。つまり UDP には TCP のような境界の崩れは起きません。ただし、その代わりに届く保証も、順番が守られる保証も一切ありません。 送ったデータグラムが途中で失われても、UDP 自身は再送してくれませんし、送信側にも気づく手段がありません。

この性質から、UDP は「1 件ごとの到達より、低遅延であることの方が重要な用途」(例: リアルタイム音声・動画、DNS の問い合わせ、一部のゲーム通信) で使われます。到達保証が必要なら、アプリケーション層で確認応答や再送の仕組みを自分で実装する必要があります。TCP は OS の中でこの「信頼性のための仕組み」を既にやってくれている代わりに、境界を失うという代償を払っている、と捉えると両者の関係が整理できます。

図: TCP は境界を失う代わりに到達を保証し、UDP は境界を保つ代わりに到達を保証しない。

5. 運用で踏みやすい穴

ここまでの内容を実際に動かすと、手元の実験では見えない落とし穴がいくつかあります。本番運用で必ず一度は出会う 4 つを挙げます。

TIME_WAIT ― close() を先に呼んだ側 (通常は切断を主導した側) のソケットは、接続を終えた後もしばらく TIME_WAIT という状態に留まります。これは、ネットワーク上に残っている古いパケットが新しい接続と混ざらないようにするための待機時間で、同じ IP とポートの組を短時間に大量に再利用する (短命接続を高頻度に張り直す) サーバーでは、使えるポートが尽きたように見える現象を引き起こします。

Nagle のアルゴリズム ― 小さなデータを何度も send() すると、OS がそれらを一時的にまとめてから送ろうとする最適化です。これ自体はネットワークの無駄な小パケットを減らす良い仕組みですが、遅延確認応答 (delayed ACK) と組み合わさると、小さなリクエスト / レスポンスを繰り返す通信で数十ミリ秒単位の見えない遅延を生みます。低遅延が必要な通信では TCP_NODELAY オプションでこの挙動を切ることがあります。

ポートとエフェメラルポート ― サーバー側は bind() で決まったポート番号 (例: 443) を使いますが、クライアント側は通常ポート番号を指定せず、OS が空いている番号を一時的に割り当てます。これをエフェメラルポート (ephemeral port, 一時的なポート) と呼びます。1 台のクライアントから同じサーバーへ同時に張れる接続数は、このエフェメラルポートの範囲によって上限が決まります。

半開き接続とキープアライブ ― 相手が FIN も RST も送らずに突然消える (電源断やケーブル切断など) と、自分側だけは「接続している」と思い込んだまま残ります。これが半開き接続 (half-open connection) です。これを検出するために、OS の SO_KEEPALIVE オプションで定期的に死活確認のパケットを送る仕組みがありますが、デフォルトの間隔は数時間単位と長いことが多く、分散システムでは多くの場合アプリケーション層で独自に短い間隔のハートビート (生存確認メッセージ) を送る設計が使われます。

図: 半開き接続では、片方だけが「接続している」と思い込んだ状態が続く。

Admission と webhook ― API サーバーの関所

リクエストは保存される前に、もう一段の審査を通る。

第 11 回までは、CRD の形(スキーマ・検証・既定値)と、コントローラー自身の書き方(Reconcile・所有・楽観的排他)を見てきた。この回は視点を変え、API サーバーがリクエストを受け取ってから etcd(Kubernetes がすべての状態を保存する場所)に書き込むまでの間に、誰がどんな審査をしているかを追う。

API サーバーは、認証と認可を通った後に「admission(受け入れ判定)」という関所を通す。admission には、内容を書き換える mutating(変更系)と、合否だけを判定する validating(検証系)の 2 段階があり、ここに割り込むのが webhook(API サーバーが外部のプログラムに「これを許可してよいか」を問い合わせる仕組み)。webhook の設定を 1 つ間違えると、クラスタ全体の操作が止まることがある。

1. リクエストはどこを通って etcd に着くか

kubectl apply を打った瞬間、リクエストは一直線に保存されるわけではない。公式ドキュメントによれば、admission controller(受け入れ判定を行う部品)は「リソースが保存される前、ただしリクエストが認証(authentication: あなたは誰か)と認可(authorization: あなたにその操作をする権限があるか)を通った後」に割り込む。admission はさらに 2 段階に分かれており、最初に mutating(変更系: 内容を書き換えてよい。拒否もできる)admission が全部走り、その後に validating(検証系: 書き換えは禁止で合否だけ判定する)admission が走る。どちらの段階でも、1 つでも拒否すれば即座にリクエスト全体が拒否され、利用者にエラーが返る。

CRD(第 05〜07 回)の構造的スキーマ検証・既定値埋め(defaulting)・未知フィールドの刈り込み(pruning)は、admission の 2 段階が始まる前の「デコード」の段階で行われる。だから mutating admission(webhook を含む)が受け取るオブジェクトは、すでに刈り込みと既定値が入った後の姿であり、第 07 回で見た「既定値は読み出し時にも入る」(EKS 1.35 のテスト用クラスタで実測)も、同じデコードの仕組みが読み出しのたびに働いている証拠。CEL(x-kubernetes-validations)による検証は、この構造的スキーマの検証の一部として行われ、mutating admission の後・validating admission の前に挟まる。第 06 回で見た「enum 違反があると CEL は評価されない」(同じく実測)は、この検証の中の話。

図: 認証・認可の後、デコード(刈り込み+既定値埋め)を経て、mutating admission → スキーマ検証(構造+CEL) → validating admission の順に etcd へ向かう。mutating・validating のどちらの admission も拒否でき、スキーマ検証の違反も拒否になる。

2. mutating webhook と validating webhook

webhook は、API サーバーが自分の中で判定を終わらせず、HTTPS で外部のプログラムに「このオブジェクトをどう扱うべきか」を問い合わせる仕組み。MutatingWebhookConfiguration と ValidatingWebhookConfiguration という 2 つの API で登録する。mutating webhook は JSON Patch でオブジェクトを書き換えて返せる(第 07 回の既定値埋めの一種とも言える)が、validating webhook と同じく allowed: false で拒否もできる。validating webhook は書き換えられず、許可(allowed: true)か拒否(allowed: false)だけを返す(1 節で見た順序のとおり、mutating が先、validating が後)。同じ段階に複数の webhook が登録されていれば、それらは直列に(順番に)呼ばれ、前の webhook が書き換えた結果を後の webhook が見られる場合がある。ただし呼ばれる順序そのものは保証されない。mutating webhook が何かを書き換えると、設定に reinvocationPolicy: IfNeeded があれば、それより前に呼ばれた mutating webhook がもう一度呼び直される(既定は Never)。

mutating webhookvalidating webhook
できること書き換え + 拒否許可 / 拒否の判定のみ
実行順序先(スキーマ検証より前)後(スキーマ検証より後)
典型例サイドカー注入、既定値の補完命名規則の強制、他オブジェクトを読んでの相関チェック

図: mutating webhook は内容を書き換えて次に渡す。validating webhook は内容を変えず、通すか止めるかだけを決める。

3. webhook の設定フィールド

webhook は外部プロセスへの呼び出しなので、落ちたとき・遅いときにどう振る舞うかを明示的に設定する。

  • failurePolicy: Fail(既定。呼び出しに失敗したらリクエストを拒否する)か Ignore(失敗しても通す)。公式ドキュメントの既定は Fail。
  • sideEffects: admissionregistration.k8s.io/v1 で指定できるのは None(副作用なし)と NoneOnDryRun(通常は副作用があるが dry-run 時は webhook 側で抑制する)の 2 つだけ(公式ドキュメントで確認)。dry-run(本当には保存しない試し実行)でも admission は走るが、webhook が None/NoneOnDryRun のどちらでも副作用を安全に扱えないと申告されている場合、dry-run リクエストはその webhook には送らず、呼び出さずに API 呼び出し自体を失敗させる。
  • timeoutSeconds: 1〜30 秒の範囲でしか指定できず(0 や 31 は登録時に拒否される)、既定は 10 秒。超えると failurePolicy に従って扱われる。webhook の応答が遅いほどリクエストが etcd に書き込まれるまでの時間が延び、その間に別のクライアントが先に書き込んで resourceVersion がずれる(第 11 回の楽観的排他で見た 409 Conflict)可能性も上がる。
  • matchConditions: CEL 式で「このリクエストのときだけ webhook を呼ぶ」を絞り込む。rules や objectSelector より細かい条件を書ける。
webhooks:
  - name: widget-defaulter.example.com
    sideEffects: None
    timeoutSeconds: 5
    failurePolicy: Fail
    matchConditions:
      - name: "exclude-system"
        expression: "!request.userInfo.username.startsWith('system:')"

図: webhook の呼び出しが timeoutSeconds を超えて失敗したとき、failurePolicy=Fail なら拒否、Ignore なら素通りする。

4. TLS が要る理由と、webhook が落ちたときの危険

API サーバーは webhook サービスに HTTPS で接続する。clientConfig.caBundle に証明書の発行元(CA: Certificate Authority)を渡し、証明書は <service>.<namespace>.svc という名前に対して発行されていなければならない。この証明書の発行・更新を手作業でやるのは煩雑なため、cert-manager(証明書の発行・自動更新を行うクラスタ内のソフト)を使い、証明書の更新で webhook が突然認証エラーを起こす事故を防ぐのが定石。

webhook の Pod が全部落ちている状態で failurePolicy: Fail のままだと、その webhook の対象になるすべてのリソース(Pod 作成など広く設定していれば、ほぼ全操作)が admission で拒否され続ける。webhook 自身の Pod を更新するときに、自分自身を対象にした webhook で止まる「自己ロック」はよくある事故。

図: API サーバーは caBundle で webhook サービスの証明書を検証する。webhook が応答しないと、failurePolicy=Fail の設定ではその対象リソース全体が止まる。

5. webhook でしかできないこと・やってはいけないこと

CRD のスキーマ検証や CEL(第 06 回)は、送られてきたオブジェクト自身(self/oldSelf)の中だけで判定する。webhook は外部プロセスなので、他のオブジェクトを読んでから判定できる(例: 「同じ namespace に同名の Secret があるか」「クラスタ全体の利用量が上限を超えていないか」)。第 13 回で見る VAP(ValidatingAdmissionPolicy)もパラメータリソースや namespace オブジェクトを読めるので、これは webhook だけの強みではないが、VAP が読めるのは決められたパラメータと namespace だけで、任意の名前のオブジェクトを自由に読みに行ける分だけ webhook のほうが広い。その代わり webhook は呼び出しごとにネットワーク越しの処理が走るため、リクエストの速度と可用性(落ちていないか)がクラスタ全体の速度と可用性に直結する。やってはいけないのは、webhook の中で重い処理(大きな一覧取得、別クラスタへの問い合わせなど)を行い timeoutSeconds を使い切ること、そして webhook 自身が作る・変更するリソースを webhook の対象に含めて無限ループを作ることの 2 つ。

図: webhook は API サーバーの外から他のオブジェクトを読めるが、その分だけ呼び出しのたびに待ち時間とクラスタの可用性への依存が増える。

まとめと次の回

リクエストは、認証・認可の後、デコード(刈り込み+既定値埋め)を経て、mutating(書き換え + 拒否も可)→ スキーマ検証(構造+CEL) → validating(合否判定)の順に進む。webhook は mutating と validating の 2 か所にだけ外部プログラムを割り込ませる仕組みで(スキーマ検証そのものには割り込めない)、failurePolicy・sideEffects・timeoutSeconds・TLS 証明書の設定を誤ると、クラスタ全体の操作を止めてしまう。次の第 13 回では、webhook を書かずに CEL だけで同じ関所の判定を API サーバーの中で完結させる ValidatingAdmissionPolicy と MutatingAdmissionPolicy を見る。

図: admission = mutating → スキーマ検証 → validating。webhook が割り込めるのは mutating と validating の 2 か所だけで、スキーマ検証そのものには割り込めない。

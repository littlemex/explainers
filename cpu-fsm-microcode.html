制御回路 (どの命令が来たらどの線を立てるかを決める回路) は、命令の種類が増えるほど複雑な組み合わせ回路になっていきます。有限状態機械 (finite state machine, 今の状態と入力から次の状態と出力を決める仕組み) として素直に描くと、32 命令ともなれば状態と遷移線だらけの図になってしまいます。rj32 はこれを避けるため、制御の中身を論理ゲートの集まりではなく ROM の表 (マイクロコード) として持ち、命令のたびに表の行を 1 つずつ辿っていく小さな専用回路 (マイクロコードシーケンサ) を 1 つだけ作っています。表を書き換えれば動作が変わる、という柔らかさが最大の利点です。

1. 有限状態機械とは何を整理する道具か

有限状態機械 (finite state machine, 以下 FSM) は、「今どういう状態にいるか」と「今どんな入力が来ているか」の 2 つだけから、「次にどの状態へ移るか」と「今どんな出力を出すか」を決める仕組みです。状態の数は有限個に限られていて、取りうる状態をすべて丸で描き、状態と状態の間を矢印でつなぎ、矢印の上に「この条件が来たら移る」という条件を書けば、動作の全体を 1 枚の図に収めることができます。第 5 回で見た D フリップフロップのような部品が、この「状態」を実際に 1 クロックの間だけ保持する役割を担います。

図: FSM は「状態」と「入力」から「次の状態」と「出力」を決める、クロックごとに 1 回動く仕組み。

CPU の制御回路もこの形に当てはめられます。第 11 回のデコーダ・制御回路は、1 つの命令が 1 クロックで終わる前提でハードワイヤード (命令のビットから制御線へ、状態を持たずに直接つながる組み合わせ回路) に組んでいました。しかし load や store のように、メモリからの応答を待つ必要がある命令は 1 クロックでは終わりません。複数クロックにわたる命令を扱うには、「今、命令のどの段階にいるか」という状態を持つ必要が出てきます。

2. Digital の FSM エディタで作った実例: クロック制御

Digital には、状態と矢印を直接描くと自動的に回路に変換してくれる FSM エディタがあります。rj32 の dig/clock.fsm はこのエディタで作られた実物で、CPU の命令そのものではなく、フロントパネルから CPU のクロックを操る「クロック制御」の状態機械です。stall (停止)・step (1 クロックだけ進める)・unstep (進めた後の後始末)・slow (遅いクロックで流し続ける) という 4 つの状態を持ち、stall から始まります。

図: dig/clock.fsm をそのまま状態遷移図にしたもの。4 状態 ・ 5 本の遷移で、CPU 本体のクロックの進み方を制御する。

各状態には stall という出力の値が結び付いています (stall ・ unstep は stall=1、step ・ slow は stall=0)。stall=1 のときは CPU 本体のクロックが止まり、stall=0 のときだけ実際にクロックが 1 つ進みます。利用者が「1 クロックだけ進めたい」ボタンを押すと step 信号が立ち、stall → step → unstep → stall と 1 往復して自動的に止まります。「流し続けたい」ボタンを押すと slow 信号が立ち、slow 状態に留まって低速なクロックを出し続けます。これは第 19 回で扱うデバッグ機能の土台になっている FSM です。

3. 状態機械を回路で描かず、ROM の表として持つ

命令ごとに状態機械を回路図として描いていくと、32 命令、しかも一部は複数クロックかかる rj32 では、状態と矢印だらけの巨大な図になってしまいます。マイクロコードは、この「状態と遷移」を回路の形ではなくROM の中の表として持つという考え方です。rj32 の microcode/microcode.asm は、32 ビット 1 行が「このクロックでは何をするか (value) ・ 次のクロックではどこに行くか (nextt ・ nextf) ・ どの条件で分かれるか (flags)」を表す、小さな専用アセンブリ言語です。

done WM_R | WRITE
; ↓ 展開されると
le(0`5 @ 0`5 @ 0`3 @ value`19)

done は「次のクロックは新しい命令の先頭 (アドレス 0) に戻る」という 1 行で終わるマイクロ命令、next value, flags, nextt, nextf は条件によって行き先が分かれる行、loop value, next は条件に関わらず同じ行へ戻り続ける行です。add や move のような 1 クロックで終わる命令はすべて done 1 行で書かれていますが、load や store はメモリの応答を待つ必要があるため next で自分自身 (loadwait) に戻るループを持っています。

図: microcode.asm の 1 行が組み立てる 32 ビット語。今やることと次の行き先が同じ 1 行の中にある。

4. マイクロコードシーケンサ: 次の行をどう選ぶか

dig/mcsequencer.dig (回路内部の名前は Sequencer) は、マイクロコード ROM の「次はどの行を読むか」というアドレスだけを決める小さな専用回路です。命令の先頭 (busy が立っていない、つまり前の命令が終わっている) では、読み出すアドレスは命令そのもの (op, 5 ビットの opcode) になります。命令の途中 (busy が立っている) では、1 つ前の行が指定した next_t か next_f のどちらかが次のアドレスになり、その選択は flags (ROM の行が指定する条件マスク) と実際のハードウェアの状態信号を比較する true? という回路が行います。選んだアドレスは step という 5 ビットのレジスタに保持され、次のクロックで ROM を読み直すために使われます。

図: Sequencer は ROM そのものではなく、次に読むアドレスを op か step のどちらから取るかだけを決める回路。

ここで注意したいのは、flags ・ fmask が選ぶ条件は、第 13 回で見た if.xx の比較条件 (eq ・ lt など、ALU の比較器の結果) とは別物だという点です。if.xx の条件は value フィールドの中にある cond という別のビットで選ばれ、プログラムから見える (ISA レベルの) 分岐に使われます。シーケンサの flags / fmask はプログラムからは見えない、ハードウェア内部の状態信号 (たとえばメモリが応答したことを示す FL_ACK) を見て、マイクロコードの中だけで「もう一度待つか、次に進むか」を決めるための、もう 1 段低いレベルの条件です。

5. add は 1 行で終わり、load は自分自身に戻り続ける

microcode.asm を見ると、add ・ move ・ xor のような ALU だけで完結する命令はどれも done 1 行で書かれています。done ADD | WRITE は「ALU に加算をさせて、その結果をレジスタに書き戻し、次のクロックは新しい命令の先頭 (op から読む) に戻る」という意味で、常に 1 クロックで終わります。一方 load は next MEM | ADD, FL_ACK, loaddone, loadwait という行から始まります。これは「メモリにアドレスを出して読み出しを要求し (MEM)、FL_ACK (メモリが応答したことを示す信号) を見て、応答済みなら loaddone へ、まだなら loadwait へ進む」という意味で、loadwait はもう一度同じ条件を見て自分自身に戻る 1 行です。応答が来るまで、この行を何度でも読み直します。

図: add は常に 1 クロック、load は応答が来るまで loadwait を回り続ける可変長のマイクロコード列。

6. 実装のポイント

設計は 2 ロム方式から 1 ワード方式へ進化した。 experiments/mc_seq_idea.dig には、今の mcsequencer.dig より前の試作が残っています。そこでは「何をするか」を決める Microcode ROM と、「次にどこへ行くか」を決める NextStep ROM が別々に用意され、条件も flag_1 から flag_4 という固定本数の入力線として個別に配線されていました。最終的な mcsequencer.dig では、次のアドレスを value と同じ 1 つの ROM 語の中 (nextt ・ nextf) に埋め込み、条件も flags / fmask という汎用のビットマスク比較に変えています。2 ROM 方式は「今の動作」と「次の遷移」を別々に考えられる分かりやすさがありますが、ROM が 2 つに増え、テストできる条件の本数も配線した本数に固定されます。1 ワード方式は ROM が 1 つで済み、どのハードウェア信号を条件にするかも fmask の値を変えるだけで差し替えられますが、1 行の中に「やること」と「行き先」が混ざるため、人間が読むときは done / next / loop というアセンブラのマクロ名に頼る必要が出てきます。

図: 試作は ROM を 2 つに分けて読みやすさを優先、最終版は 1 ワードに統合して汎用性と省面積を優先した。

ハードワイヤードとマイクロコードはどちらが速いか。 第 11 回のハードワイヤード制御 (命令のビットから制御線への組み合わせ回路) は、ROM を読む時間が無いぶん 1 命令を決めるのが速い一方、命令やその挙動を増やすたびに回路図を描き直す必要があります。マイクロコードは ROM の表を 1 行書き換えるだけで挙動を変えられますが、1 マイクロステップごとに ROM を読む時間がかかり、多クロックの命令はその分だけ実クロックを消費します。rj32 の control.dig は、実際にはこの両方を組み合わせたハイブリッドです。mcsequencer.dig が ROM の行を進める部分を担い、その周りに ack ・ busy ・ stall といった信号を扱う小さなハードワイヤード回路を配置しています。

ROM の行を書き間違えると、CPU が止まって見える。 loadwait のような自己ループを書くとき、next_t と next_f を取り違えると、本来進むべきところでいつまでも自分自身に戻り続けてしまいます。この種の誤りは論理合成のエラーにはならず、実際にシミュレータや FPGA で動かして「load 命令のところで永遠に止まる」という形で初めて見つかります。マイクロコードを書くときは、条件が成立したときと成立しなかったときのどちらが next_t でどちらが next_f かを、表の列の意味と合わせて必ず確認する必要があります。

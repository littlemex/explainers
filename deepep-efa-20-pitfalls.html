JSON に書いたコマンドを 1 本のシェルで流す、自作の実行器で踏んだ罠。

#何が起きたかなぜ誤読しかけたかどう防ぐか
1 訂正 (2026-09-26)。task_runner.sh は commands の要素をコメントかどうかで捨てたりしない。渡された要素をそのまま 1 行ずつ bash に渡すだけ。実際に起きたのは、行末が \ で終わるコメント行の次に if 文を書いたところ、bash がその \ を見て次の行までコメントに巻き込んだため、if 文が実行されず、変数が未定義のまま先に進んで落ちた 「# の後ろは行末まで」という思い込みがあり、コメント行の末尾の \ が次の行までコメントを伸ばすことに気づけない コメント行の末尾には \ を置かない。行末の \ の直後には、実行したいコマンドの行だけを置く
2 数値を読む関数が 0 を「未指定」と同じに扱うため、=0 で機能を切るつもりのスイッチが効かなかった 「非同期なし」のつもりで用意した比較用の 2 つの回 (A/B) が、実は両方とも非同期のまま動いていた 0 を有効な値として取るスイッチは、数値としてではなく文字列で比較する
3 実行器がリモートへ環境変数を渡すとき、値に空白が入っていると分割される 複数の値を渡したつもりでも、一部しか伝わっていないことに気づきにくい 複数値はカンマ区切りにして、タスク側で空白に戻す
4 段ごとの完了印が残っていると、その段は飛ばされて「OK」と表示される 「OK」の表示だけを見て、vLLM が実際に動いたと誤読しかけた。実際は前回の印を見て素通りしただけだった 再実行するときは強制オプションを使い、印を無視して実際に走らせる
5 出力を「先頭 N 行」で切ると、成否を示す行がその外側にあって見えなくなる 表示された範囲だけを見て、成功したと誤読しかけた 回数や成否は、ログ全体から数える
6 同じホストで 2 つのタスクを同時に走らせると、実行用の一時スクリプトを共有しているので壊れる 片方の失敗が、もう片方のタスクの内容そのもののせいだと誤読しかけた 同じホストで同時に走らせない、または一時スクリプトの名前をタスクごとに分ける
7 配備するとソースの更新時刻が新しくなり、「ビルドがソースより古い」検査に引っかかって止まる 検査で止まったのを見て、ソースかビルドの内容そのものに問題があると誤読しかけた 配備のあとは必ずビルドし直す
8 手元の検査を、配備と同じバックグラウンドの命令に混ぜると、エラーの行を見落とす まとめて後から見る出力の中に検査のエラーが埋もれ、「問題なし」と誤読しかけた 検査は前面で走らせて結果を見てから、配備する
9 行末のバックスラッシュの次の行がコメントだと、その行は「代入だけ」の行として働く そこに env などのコマンドを挟むと元の動きが変わるのに、見た目上はコメントが 1 行入っただけに見える 行末のバックスラッシュの直後にコメント行を置かない
29 使っていない時間で自動的に停止させる仕組み (24 時間使われなければ止める) が、起動した時点の印しか見ておらず、最後に使った時間ではなく起動してからの時間を数えていた 「使っていない時間」で止まるはずなのに、使っている最中に止まる余地が残っていることに気づきにくい 実行器がコマンドを流すたびに、この印を更新するようにする (preflight/setup/runner.sh の ssm_run_on)
30 同じ内容の要求をまとめて送る検査の中で、素の wait を書いたところ、要求を出したプロセスだけでなく vLLM のサーバ本体まで待ってしまい、サーバ側の強制タイムアウトまで戻ってこなかった。1 回の実行に 40 分かかり、「vLLM が終了しない」ように見えた 終わらないのを見て、vLLM 側の不具合だと誤読しかけた。実際は待つ対象を広く取りすぎていた wait は、要求を出したプロセスの PID だけを指定して待つ
31 手当ての確認 (項目 25 の cuobjdump の手当てを確かめるタスク) が、何も言わずに落ちた pipefail の下で find が該当なしのとき非 0 で終わり、それだけでその段全体が失敗として止まっていた。同じ形の罠を ls でも踏んでいる find の後ろに || true を付ける
33 訂正 (2026-09-26)。環境変数を付ける行が行末の \ で終わっていて、その次の行がコメントだったため、bash は A=1 B=2 # … という裸の代入だけの行として読み、vllm serve まで届かなかった。あとからサニタイザ用の設定を間に足したときは、\ が SAN="" という別の行に付いてしまい、環境変数はそちらに付いた \ の直後がコメントでも、コメントの中に隠れて次の行を巻き込んでいることは見た目から分からず、行の隙間に気づけない (項目 1 と同じ仕組み) 環境変数を付ける行の直後には、コメントを置かない。付けたい相手のコマンドの行と隙間を空けない
35 runner.sh の --env で渡した値は、リモートのシェルへクォートなしのまま届く。値に | が入っていると、パイプとして解釈される 複数の選択肢を 1 つの値として渡したつもりが、シェルの記号として動いてしまい、意図と違う挙動になる 選択肢はカンマ区切りで渡す (項目 3 と同じ考え方)
38 zsh で "--env X=Y" を変数に入れて展開すると、1 個の引用文字列として 1 つの引数になる。実行器は「知らない引数」として即座に失敗する 失敗が 0 秒で返ってきたので、わざと壊す陰性対照が一度も実行されなかったことに気づかず、「検査した」と誤読しかけた この引数は変数に入れず、直接そのまま書く
40 配備がタイムアウトを超えて止まるようになった。find と chown -R が、EFS 上の作業ディレクトリ全体 (vLLM の venv や JIT のキャッシュも含めて) を歩いていた 止まった時点でファイル数が急に増えているのを疑わず、配備そのものが重くなったと誤読しかけた。実際は毎回同じ処理を全体に対してやっていた 配備が展開した分だけを対象にする。直すと配備は 16 秒で終わる
41 zsh で set -- $cfg と書いても、空白で分割されない。4 つの設定を順に試すループのつもりが、どの回も実際には走っていなかった ループ自体はエラーを出さずに終わるので、4 通り全部を試したと誤読しかけた この種のループは bash のスクリプトから走らせる

B計測器と道具

計測器そのものの死角が、対象についての結論に見えてしまう罠。

#何が起きたかなぜ誤読しかけたかどう防ぐか
10 LD_PRELOAD で libcuda の関数を包む方式では、CUDA runtime (PyTorch や NCCL の中) の呼び出しが見えない。runtime は cuGetProcAddress で関数を取るため。差し替えようとしたら PyTorch が壊れた 「何も見えなかった」を「呼ばれていない」証拠として誤読しかけた。実際は計測器の死角だった CUPTI (driver が公式に呼び出しを通知する仕組み) に切り替え、「見えるはずのものが見える」ことを自己テストで先に確かめる
11 Ubuntu の apport は、同じプログラムのクラッシュを 1 件しか残さない 2 件目以降のクラッシュのコアが無いのを見て、「クラッシュしなかった」と誤読しかけた コアの出力先を変え、上限を prlimit で上げる (ハードリミットが 0 だと ulimit では上げられない)
12 gdb の下では、タイミングが変わって落ちなくなる不具合があった gdb 下で再現しないのを見て、「直った」と誤読しかけた コアを後から読む。タイミングを変えないので、この種の不具合を見失わない
13 AddressSanitizer と CUDA は、既定の設定だと CUDA の初期化で衝突する。AddressSanitizer は、計装したコードのヒープへの書き込みしか見ない 「何も報告が無い」を「そこには欠陥が無い」と誤読しかけた。実際は VMM の領域や、計装していないライブラリの書き込みが見える範囲の外だった protect_shadow_gap=0 を設定する。見える範囲を先に確認してから、報告の有無を判断する
14 CPython のデバッグ用メモリ管理 (PYTHONMALLOC=debug) は、あふれを解放の時点で捕まえる。確保元の記録 (PYTHONTRACEMALLOC) まで付けると、vLLM の起動が遅くなりすぎて、vLLM 自身の時間切れで止まった 起動が止まったのを見て、また別の欠陥が起きたと誤読しかけた。実際は計測器自体の重さが原因だった 必要な情報の量に応じて計測器の重さを選ぶ。まず PYTHONMALLOC=debug だけで試す
15 compute-sanitizer が出す大量の API エラーの多くは、NCCL の初期化時の、想定内の確認だった エラーの件数の多さを見て、GPU のメモリ違反が大量に起きていると誤読しかけた NCCL 初期化時の想定内の確認と、GPU のメモリ違反の報告を区別して読む
24 「答えが空でないか」だけの検査は、壊れた答えを素通りさせた。2 台の vLLM でわざと転送の約束を破ると、答えが a a a. the she things … になったのに、検査は OK を返した プロンプトと温度を固定しているので正解は決まっているのに、検査は「何か返ってきたか」しか見ていなかった 答えの頭が対照の正解 ( Paris) と一致するかを見る。そうすると、約束違反の回は失敗し、正しい回は通る
27 AddressSanitizer を先読み込みすると、vLLM が cuDNN を読み込めずに、何も言わずにワーカーが死ぬ 報告が 0 件でも「きれい」だと誤読しかけた。実際は「届いていない」だけだった DeepEP 自身の試験のように cuDNN を使わない入口で調べる
32 vLLM は実行するたびにランクごとのログを上書きする。加えて、シグナルで止められたワーカーはトレースバックを残さず、「see root cause above」としか出ない 失敗した 1 回のログを読もうとしたら、すでに次の回のログで上書きされて消えていた PYTHONFAULTHANDLER=1 を付けて実行し、失敗した回のログは別名で残す
34 「プラグイン (エミュレータ) が窓を登録した」ことを、「プラグインがトラフィックを運んだ」ことの証拠として読んでしまった。実際には、DeepEP はどちらの経路で送るにせよ窓を登録するので、登録件数だけでは何も分からない (第 19 回 §6) 登録が起きているのを見て、その先の通信も想定どおり動いていると誤読しかけた 実際に配達した件数を数える。さらに、わざとデータを壊す陰性対照を用意して、その検査が本当に効くこと自体を確かめる
36 NCCL のログは、この backend を RMA_SOCKET_PROXY と名乗る。ログの WARN 行に出る表示名は RMA/Socket で、この 2 つは違う文字列 RMA/Socket という表示名の方を探す検査を書いたところ、backend は実際に使われていたのに検査は失敗した ログに出る表示用の名前と、実際に検査すべき識別子 (RMA_SOCKET_PROXY) を混同しない
42 実行器は、検索パターンの中のバックスラッシュによる escape を取り除いてしまう。\[h4\] (文字そのものの [h4] を探すつもりの書き方) が [h4] という文字クラスになり、h か 4 を含む行なら何でも一致した 検査が「見つかった」と言うので、狙った行が見つかったと誤読しかけた。実際は無関係な行にも大量に一致していた 探したい行だけに現れる単語を使って探す。記号による一致には頼らない

C環境

環境固有の値は書かないが、環境の性質そのものが結論を誤らせた罠。

#何が起きたかなぜ誤読しかけたかどう防ぐか
16 EFA の SRD は IP ではないので、セキュリティグループに「自分自身のグループ宛て」の送信規則が要る。0.0.0.0/0 の送信規則だけでは届かない 通信が届かないのを見て、「EFA が壊れている」と誤読しかけた (9 月にそう書いた) セキュリティグループの送信規則に、自分自身のグループ宛てを追加する
17 p5 の EFA には、libfabric の fabric が 2 つある (efa と efa-direct)。どちらが選ばれるかで使える機能が変わる (第 15 回・第 16 回の aws-ofi-nccl の件) 同じインスタンスタイプ・同じ EFA デバイスなのに機能の有無が変わるのを見て、環境が不安定だと誤読しかけた どちらの fabric が選ばれているかを確認する
18 Deep Learning AMI の CUDA toolkit には cuobjdump が無く、DeepEP の JIT が理由を言わずに落ちる 理由の無い失敗を見て、DeepEP やコードそのものの欠陥だと誤読しかけた cuobjdump の有無を先に確認する
19 vLLM の起動の時間切れ (VLLM_ENGINE_READY_TIMEOUT_S) は、API サーバの起動から数える。コンパイルに時間がかかると、エンジンが動き出す前に切れる。最初の要求も、初回の JIT で 2 分以上かかることがある 時間切れやリクエストの遅さを見て、「止まっている」と誤読しかけた コンパイルにかかる時間を見込んで時間切れの値を設定する。最初の要求が遅いのは止まっているのではないと理解しておく
20 1 枚の GPU を 2 ランクで分けると、vLLM は相手ランクの使用分を差し引いて見積もる。そのため、片方の KV キャッシュが極端に小さくなる 片方のランクだけ KV キャッシュが小さいのを見て、設定ミスや別の欠陥だと誤読しかけた 1 枚の GPU を複数ランクで分けるときは、KV キャッシュの見積もりが相手の分を差し引いて計算されることを踏まえる
25 DeepEP をビルドし直すと、JIT のために用意した cuobjdump の手当て (項目 18) が効かなくなり、理由を言わずに落ちる不具合が再発した 一度直した問題なので、再発したときに新しい欠陥だと誤読しかけた DeepEP を作り直したら、手当ての手順も流し直す
28 Capacity Block (期間を確保した GPU) は、終了時刻まで持たない。2 台の p5 インスタンスは、終了時刻の約 30 分前、vLLM を回している最中に止まった。表示された理由は User initiated shutdown だった この理由の表示を見て、自分たちの側の操作が止めたと誤読しかけた 最後の実行は、終了時刻の 40 分前までに終える。この理由の表示を自分たちの側の原因として読まない
37 vLLM が落ちるかタイムアウトすると、タスクは親プロセスを止めるが、driver の呼び出しの中で止まっているワーカーは生き残る。ワーカー 2 個 (うち 1 個は 27 時間前のもの) が、GPU メモリ 32 GB を持ったまま残っていた venv の python は実体としてシステムの python を指すので、実行ファイルのパスだけでは「どの作業のプロセスか」が分からない プロセスがマップしているファイル (/proc/<pid>/maps) で判断する。タスク 115 が GPU 上のプロセスを一覧し、この作業スペースの孤児だけを止める
39 vLLM が NCCL を 2.31 から 2.32 に上げたあとも、plugin は古い 2.31 のヘッダーでビルドされ続けていた。ヘッダーを取得する手順が、記録用のファイルが存在するときはいつも素通りしていたため 手順自体は毎回成功と表示されるので、正しいヘッダーでビルドしていると誤読しかけた 使ったバージョンを記録に残し、バージョンが変わったら取得し直す
44 NCCL 2.32 にアップグレードすると、その nccl.h は cudaEvent_t を使う。手元だけで型を確認するための CUDA スタブヘッダーにはこの型が無く、そこが壊れた 失敗の場所が NCCL のヘッダーではなくスタブ側だったので、無関係な設定ミスだと誤読しかけた スタブヘッダーに cudaEvent_t を足す。バージョンを上げるたびに、スタブが新しいヘッダーの要求に追随しているかを見直す

D考え方

個別の罠の下に共通していた、3 つの姿勢。

#何が起きたかなぜ誤読しかけたかどう防ぐか
21 「見えなかった」を、対象が無かった証拠として使ってしまう 計測器の死角を、対象の不在と取り違える 見えるはずのものが見えることを、先に自己テストで確かめる
22 1 つの症状に対して仮説を 3 回立てて、3 回とも否定された 「直しても症状が変わらなかった」ことを、直した内容が間違っていた証拠だと誤読しかけた 否定された修正でも、それ自体として正しいものは残してよい。ただし「原因だった」とは書かない
23 原因を名指しできた 名指しした時点で「分かった」と思い込みかけたが、取り除いて消えることを見るまでは確認になっていない 対照実験 (原因だけを取り除く) で「消えること」まで示す。回数が少ないときは、割合ではなく観測として書く
26 複数の設定をまとめて確認すると、どの 1 つが選択肢を消しているかが分からず、疑う範囲が広がる 広い範囲を疑ったまま調べると、無関係な箇所まで疑って時間を使う 設定を 1 つずつ足して問い合わせると、「どの要求が選択肢を消しているか」を直接特定できる (第 15 回の FI_HMEM の特定に使った手法)
43 1 回通ったことは、正しさの証明にならない。乱数の種を固定した同じ回で、srd (2 ランク) が通った回と、後で落ちた回があった 1 回通ったのを見て、「直った」「もう大丈夫」と誤読しかけた 繰り返して、通った回数を数える。同じ種でも結果が変わるなら、タイミングも関わっている

D の 3 点は、A・B・C のすべての罠に共通する形をしています。見えなかったものを不在の証拠にしない。否定された修正も残す。名指しは対照実験で確かめる。この 3 つを守ると、個別の罠を踏んだあとの回復が速くなります。

Aタスク実行の仕組み

JSON に書いたコマンドを 1 本のシェルで流す、自作の実行器で踏んだ罠。

#何が起きたかなぜ誤読しかけたかどう防ぐか
1 commands の要素のうち # で始まるものは、中に改行やコードが入っていても丸ごと捨てられる。コメントと if 文を 1 つの要素にまとめたら、変数が未定義のまま実行されて落ちた コメントのつもりで書いた行が、実は if 文まで含んだ 1 要素になっていて、その全体が「コメント行」として捨てられているとは見た目で分からない コメントとコードは、必ず別の要素に分ける
2 数値を読む関数が 0 を「未指定」と同じに扱うため、=0 で機能を切るつもりのスイッチが効かなかった 「非同期なし」のつもりで用意した比較用の 2 つの回 (A/B) が、実は両方とも非同期のまま動いていた 0 を有効な値として取るスイッチは、数値としてではなく文字列で比較する
3 実行器がリモートへ環境変数を渡すとき、値に空白が入っていると分割される 複数の値を渡したつもりでも、一部しか伝わっていないことに気づきにくい 複数値はカンマ区切りにして、タスク側で空白に戻す
4 段ごとの完了印が残っていると、その段は飛ばされて「OK」と表示される 「OK」の表示だけを見て、vLLM が実際に動いたと誤読しかけた。実際は前回の印を見て素通りしただけだった 再実行するときは強制オプションを使い、印を無視して実際に走らせる
5 出力を「先頭 N 行」で切ると、成否を示す行がその外側にあって見えなくなる 表示された範囲だけを見て、成功したと誤読しかけた 回数や成否は、ログ全体から数える
6 同じホストで 2 つのタスクを同時に走らせると、実行用の一時スクリプトを共有しているので壊れる 片方の失敗が、もう片方のタスクの内容そのもののせいだと誤読しかけた 同じホストで同時に走らせない、または一時スクリプトの名前をタスクごとに分ける
7 配備するとソースの更新時刻が新しくなり、「ビルドがソースより古い」検査に引っかかって止まる 検査で止まったのを見て、ソースかビルドの内容そのものに問題があると誤読しかけた 配備のあとは必ずビルドし直す
8 手元の検査を、配備と同じバックグラウンドの命令に混ぜると、エラーの行を見落とす まとめて後から見る出力の中に検査のエラーが埋もれ、「問題なし」と誤読しかけた 検査は前面で走らせて結果を見てから、配備する
9 行末のバックスラッシュの次の行がコメントだと、その行は「代入だけ」の行として働く そこに env などのコマンドを挟むと元の動きが変わるのに、見た目上はコメントが 1 行入っただけに見える 行末のバックスラッシュの直後にコメント行を置かない

B計測器と道具

計測器そのものの死角が、対象についての結論に見えてしまう罠。

#何が起きたかなぜ誤読しかけたかどう防ぐか
10 LD_PRELOAD で libcuda の関数を包む方式では、CUDA runtime (PyTorch や NCCL の中) の呼び出しが見えない。runtime は cuGetProcAddress で関数を取るため。差し替えようとしたら PyTorch が壊れた 「何も見えなかった」を「呼ばれていない」証拠として誤読しかけた。実際は計測器の死角だった CUPTI (driver が公式に呼び出しを通知する仕組み) に切り替え、「見えるはずのものが見える」ことを自己テストで先に確かめる
11 Ubuntu の apport は、同じプログラムのクラッシュを 1 件しか残さない 2 件目以降のクラッシュのコアが無いのを見て、「クラッシュしなかった」と誤読しかけた コアの出力先を変え、上限を prlimit で上げる (ハードリミットが 0 だと ulimit では上げられない)
12 gdb の下では、タイミングが変わって落ちなくなる不具合があった gdb 下で再現しないのを見て、「直った」と誤読しかけた コアを後から読む。タイミングを変えないので、この種の不具合を見失わない
13 AddressSanitizer と CUDA は、既定の設定だと CUDA の初期化で衝突する。AddressSanitizer は、計装したコードのヒープへの書き込みしか見ない 「何も報告が無い」を「そこには欠陥が無い」と誤読しかけた。実際は VMM の領域や、計装していないライブラリの書き込みが見える範囲の外だった protect_shadow_gap=0 を設定する。見える範囲を先に確認してから、報告の有無を判断する
14 CPython のデバッグ用メモリ管理 (PYTHONMALLOC=debug) は、あふれを解放の時点で捕まえる。確保元の記録 (PYTHONTRACEMALLOC) まで付けると、vLLM の起動が遅くなりすぎて、vLLM 自身の時間切れで止まった 起動が止まったのを見て、また別の欠陥が起きたと誤読しかけた。実際は計測器自体の重さが原因だった 必要な情報の量に応じて計測器の重さを選ぶ。まず PYTHONMALLOC=debug だけで試す
15 compute-sanitizer が出す大量の API エラーの多くは、NCCL の初期化時の、想定内の確認だった エラーの件数の多さを見て、GPU のメモリ違反が大量に起きていると誤読しかけた NCCL 初期化時の想定内の確認と、GPU のメモリ違反の報告を区別して読む

C環境

環境固有の値は書かないが、環境の性質そのものが結論を誤らせた罠。

#何が起きたかなぜ誤読しかけたかどう防ぐか
16 EFA の SRD は IP ではないので、セキュリティグループに「自分自身のグループ宛て」の送信規則が要る。0.0.0.0/0 の送信規則だけでは届かない 通信が届かないのを見て、「EFA が壊れている」と誤読しかけた (9 月にそう書いた) セキュリティグループの送信規則に、自分自身のグループ宛てを追加する
17 p5 の EFA には、libfabric の fabric が 2 つある (efa と efa-direct)。どちらが選ばれるかで使える機能が変わる (第 15 回・第 16 回の aws-ofi-nccl の件) 同じインスタンスタイプ・同じ EFA デバイスなのに機能の有無が変わるのを見て、環境が不安定だと誤読しかけた どちらの fabric が選ばれているかを確認する
18 Deep Learning AMI の CUDA toolkit には cuobjdump が無く、DeepEP の JIT が理由を言わずに落ちる 理由の無い失敗を見て、DeepEP やコードそのものの欠陥だと誤読しかけた cuobjdump の有無を先に確認する
19 vLLM の起動の時間切れ (VLLM_ENGINE_READY_TIMEOUT_S) は、API サーバの起動から数える。コンパイルに時間がかかると、エンジンが動き出す前に切れる。最初の要求も、初回の JIT で 2 分以上かかることがある 時間切れやリクエストの遅さを見て、「止まっている」と誤読しかけた コンパイルにかかる時間を見込んで時間切れの値を設定する。最初の要求が遅いのは止まっているのではないと理解しておく
20 1 枚の GPU を 2 ランクで分けると、vLLM は相手ランクの使用分を差し引いて見積もる。そのため、片方の KV キャッシュが極端に小さくなる 片方のランクだけ KV キャッシュが小さいのを見て、設定ミスや別の欠陥だと誤読しかけた 1 枚の GPU を複数ランクで分けるときは、KV キャッシュの見積もりが相手の分を差し引いて計算されることを踏まえる

D考え方

個別の罠の下に共通していた、3 つの姿勢。

#何が起きたかなぜ誤読しかけたかどう防ぐか
21 「見えなかった」を、対象が無かった証拠として使ってしまう 計測器の死角を、対象の不在と取り違える 見えるはずのものが見えることを、先に自己テストで確かめる
22 1 つの症状に対して仮説を 3 回立てて、3 回とも否定された 「直しても症状が変わらなかった」ことを、直した内容が間違っていた証拠だと誤読しかけた 否定された修正でも、それ自体として正しいものは残してよい。ただし「原因だった」とは書かない
23 原因を名指しできた 名指しした時点で「分かった」と思い込みかけたが、取り除いて消えることを見るまでは確認になっていない 対照実験 (原因だけを取り除く) で「消えること」まで示す。回数が少ないときは、割合ではなく観測として書く

D の 3 点は、A・B・C のすべての罠に共通する形をしています。見えなかったものを不在の証拠にしない。否定された修正も残す。名指しは対照実験で確かめる。この 3 つを守ると、個別の罠を踏んだあとの回復が速くなります。

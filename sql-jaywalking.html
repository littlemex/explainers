ジェイウォーク ― カンマ区切りで複数の値を持たせる

1 つの列にカンマ区切りで複数の値を詰め込むと、結合・集計・参照整合性のすべてをデータベース本来の機能に頼れなくなる

この回の前提: 第 01 回 アンチパターンとは何か (サンプル DB の bugs / tags テーブルの構造、各回の読み方)

「1 つのバグに複数のタグを付けたい」という要件に対して、bugs テーブルに tags_csv text のような列を作り、'crash,save' のようにカンマで区切って詰め込んでしまう書き方を、このシリーズでは ジェイウォーク (jaywalking) と呼びます。結論を先に言うと、この書き方は少量のデータでは動いて見えても、検索・集計・参照整合性のどれもデータベース本来の機能では保証できなくなり、最終的にアプリケーション側で文字列処理を再発明することになります。この回では、この問題を実機の PostgreSQL で具体的に再現し、既存データベースからの見つけ方、PostgreSQL の配列型を使ってよい場合、そして交差テーブルによる解決策を確認します。

1. 目的 ― 何をしたかったのか

バグ管理システムでは、1 件のバグに複数のタグ (crash、ui、performance など) を付けたいという要件がよく出てきます。1 対多ではなく「多対多」(1 つのバグに複数のタグ、1 つのタグが複数のバグに付く) になるため、素朴に考えると「列を 1 つ増やして、そこにタグをカンマ区切りで詰め込めば、テーブルを増やさずに済む」という発想に行き着きます。実際にこの書き方は、テーブル設計を増やさずに済むという点で、少ない手間で要件を満たせたように見えます。

2. アンチパターン ― どう書いてしまい、何が壊れるか

実際に bugs テーブルに tags_csv text 列を追加し、'crash,save' のようなカンマ区切りの文字列を入れてみます。

ALTER TABLE bugs ADD COLUMN tags_csv text;
UPDATE bugs SET tags_csv = 'crash,save'         WHERE bug_id = 1;
UPDATE bugs SET tags_csv = 'report'             WHERE bug_id = 2;
UPDATE bugs SET tags_csv = 'ui,autosave'        WHERE bug_id = 3;
UPDATE bugs SET tags_csv = 'performance,search' WHERE bug_id = 4;
UPDATE bugs SET tags_csv = 'auth'               WHERE bug_id = 5;

この状態で「タグが save のバグを探す」という、ごく普通の検索をしてみます。カンマ区切りの中から 1 つの値を探す手段は、文字列の部分一致を見る LIKE しかありません。

SELECT bug_id, tags_csv FROM bugs WHERE tags_csv LIKE '%save%' ORDER BY bug_id;

 bug_id |   tags_csv
--------+-------------
      1 | crash,save
      3 | ui,autosave

bug_id 3 は、タグとして 'ui' と 'autosave' しか持っていません。'save' というタグは付いていないのに、'autosave' という文字列の中に 'save' という文字列が含まれているせいで、検索結果に混ざってしまいました。これが部分文字列の衝突です。LIKE は値の境界 (カンマの位置) を理解しないため、このような誤判定を防ぐ方法がありません。

図: LIKE はカンマという区切りの意味を理解しないため、'autosave' の内部に現れる 'save' も一致として拾ってしまう。

集計も同様に困難になります。「タグごとに何件のバグが付いているか」を数えるには、まず文字列をカンマで分解してから数え直す必要があります。

SELECT t.tag, count(*) AS n_bugs
FROM bugs b, unnest(string_to_array(b.tags_csv, ',')) AS t(tag)
GROUP BY t.tag
ORDER BY t.tag;

     tag     | n_bugs
-------------+--------
 auth        |      1
 autosave    |      1
 crash       |      1
 performance |      1
 report      |      1
 save        |      1
 search      |      1
 ui          |      1

この集計自体は実行できますが、よく見ると string_to_array と unnest という 2 つの関数を使って、文字列をいったん正規化された行の形に戻してから集計しています。つまり、保存するときに正規化しなかった代償を、読み出すたびに支払っていることになります。

さらに、tags_csv には外部キー制約を掛けられないため、どんな文字列でもチェックなしに入ってしまいます。

UPDATE bugs SET tags_csv = tags_csv || ',crsah' WHERE bug_id = 1;
SELECT bug_id, tags_csv FROM bugs WHERE bug_id = 1;

 bug_id |     tags_csv
--------+------------------
      1 | crash,save,crsah

'crsah' という誤字のタグが、何のエラーも警告も無く保存されました。もう 1 つ、区切り文字 (カンマ) そのものを値に含むデータが入ると、分解結果が壊れます。

UPDATE bugs SET tags_csv = 'needs re-work, ASAP' WHERE bug_id = 2;
SELECT string_to_array(tags_csv, ',') AS split_result FROM bugs WHERE bug_id = 2;

       split_result
---------------------------
 {"needs re-work"," ASAP"}

1 つのタグとして書いたつもりの 'needs re-work, ASAP' が、カンマの位置で 'needs re-work' と ' ASAP' という 2 つの意味のない断片に分解されてしまいました。なお、PostgreSQL の text 型自体には文字数の上限が無いため、古い書籍でよく言われる「列の長さ制限に収まらなくなる」という問題は PostgreSQL では直接には起きませんが、1 フィールドあたり 1 GB という上限はあり、実務上の問題は長さよりも、ここで見た「境界・集計・整合性」の 3 つに集約されます。

3. 見つけ方 ― どんな兆候で気づくか

既存のデータベースの中からジェイウォークの兆候を探すには、まず text 型の列を一覧にします。

SELECT table_name, column_name
FROM information_schema.columns
WHERE table_schema = 'public' AND data_type = 'text'
ORDER BY table_name, column_name;

実際に sql_02 データベースで実行すると、bugs.tags_csv を含む 15 件の text 列が返ります。この一覧だけでは、どの列がカンマ区切りの値を持っているかは分かりません。次に、怪しい列を 1 つずつサンプリングして、カンマを含む値がどれくらいあるかを確認します。

SELECT bug_id, tags_csv
FROM bugs
WHERE tags_csv LIKE '%,%'
ORDER BY bug_id;

 bug_id |      tags_csv
--------+--------------------
      1 | crash,save
      3 | ui,autosave
      4 | performance,search

このように、同じ列の複数の行でカンマを含む値が繰り返し現れる場合、その列はジェイウォークになっている可能性が高いという兆候です。1 回だけ偶然カンマが入っている (例えば自由記述のコメント欄) のか、毎回同じ区切り文字で複数の値を詰め込む運用になっているのかを、実際のデータで区別することが大切です。

4. 使ってよい場合

PostgreSQL には text[] という配列型があり、1 つの列に複数の値をそのまま持たせることができます。カンマ区切り文字列と違い、配列は値の境界をデータベース自身が管理するため、問題 1 (部分文字列の衝突) と問題 2 (集計のための再分解) の一部は解消します。

ALTER TABLE bugs ADD COLUMN tags_arr text[];
UPDATE bugs SET tags_arr = string_to_array(tags_csv, ',');
CREATE INDEX bugs_tags_arr_gin ON bugs USING gin (tags_arr);

SELECT bug_id, tags_arr FROM bugs WHERE tags_arr @> ARRAY['save'] ORDER BY bug_id;

 bug_id |  tags_arr
--------+-------------
      1 | {crash,save}

演算子 @> (含む) は要素の完全一致で判定するため、'autosave' が誤って混ざることはありません。集計も unnest で行に展開すれば書けます。

SELECT t AS tag, count(*) AS n_bugs
FROM bugs, unnest(tags_arr) AS t
GROUP BY t
ORDER BY t;

ただし、配列にも限界があります。最も重要な限界は、配列の要素 1 つずつに外部キー制約を掛けられないことです。実際に products.product_name (一意制約あり) への外部キーを tags_arr に追加しようとすると、次のエラーになります。

ALTER TABLE bugs ADD CONSTRAINT bugs_tags_arr_fkey
  FOREIGN KEY (tags_arr) REFERENCES products (product_name);

ERROR:  foreign key constraint "bugs_tags_arr_fkey" cannot be implemented
DETAIL:  Key columns "tags_arr" of the referencing table and "product_name" of
the referenced table are of incompatible types: text[] and text.

外部キー制約は列同士の型を 1 対 1 で比較する仕組みであり、text[] (配列) と text (単一の値) は型が噛み合わないため、そもそも制約を定義できません。つまり配列は「タグの集合を 1 列に持ちたいが、タグの語彙を他のテーブルで厳密に管理する必要は無い」という場合に向いた選択であり、「タグの語彙を tags のような参照テーブルで一元管理し、そこに無い値を拒否したい」という場合には向きません。また、配列は「このタグを持つバグ」のような検索 (多側からの検索) には強い一方、「この製品を使っているバグの一覧」のように結合を伴う分析的な使い方を頻繁にする場合は、正規化したテーブルの方が素直に書けます。

5. 解決策 ― PostgreSQL での正しい書き方

多対多の関係を正しく表す標準的な方法は、交差テーブル (intersection table) を用意することです。このサンプル DB には最初から tags テーブルがあり、bug_id と tag の組を 1 行ずつ持っています。

CREATE TABLE tags (
  bug_id  bigint NOT NULL REFERENCES bugs (bug_id) ON DELETE CASCADE,
  tag     text NOT NULL,
  PRIMARY KEY (bug_id, tag)
);
CREATE INDEX ON tags (tag);

この設計では、検索・結合・集計のすべてが標準的な SQL で素直に書けます。

SELECT b.bug_id, b.summary, t.tag
FROM bugs b
JOIN tags t ON t.bug_id = b.bug_id
ORDER BY b.bug_id, t.tag;

 bug_id |           summary           |     tag
--------+------------------------------+-------------
      1 | crash when saving            | crash
      1 | crash when saving            | save
      2 | wrong total on report        | report
      4 | slow search on large data    | performance
      4 | slow search on large data    | search
      5 | login fails with long email  | auth

SELECT tag, count(*) AS n_bugs FROM tags GROUP BY tag ORDER BY tag;

'save' を検索しても 'autosave' が混ざることはなく (値そのものが 1 行 1 値として保存されているため境界があいまいにならない)、タグごとの集計も GROUP BY だけで済み、bug_id には bugs への外部キーが効いているため、存在しないバグにタグを付けることもできません。tag 列自体をさらに正規化し、タグの語彙を管理する専用テーブル (tag_master(tag_name) のようなもの) に外部キーで縛れば、タイプミスのタグが入ることも防げます (この発展形は第 09 回のメタデータトリブルや第 11 回の 31 フレーバーと関連します)。

6. PostgreSQL エンジンで考慮しておくこと

交差テーブルを選ぶか配列を選ぶかの判断に、実際の性能差を加味しておきます。20 万行の合成テーブルに text[] 列を持たせ、GIN インデックスを使った包含検索と、同じ検索を強制的にシーケンシャルスキャンさせた場合を比較しました。

EXPLAIN (ANALYZE, BUFFERS, COSTS OFF)
SELECT bug_id FROM bugs_big WHERE tags_arr @> ARRAY['save'];

 Bitmap Heap Scan on bugs_big (actual time=1.332..5.318 rows=33334 loops=1)
   Recheck Cond: (tags_arr @> '{save}'::text[])
   ->  Bitmap Index Scan on bugs_big_tags_gin (actual time=1.168..1.168 rows=33334 loops=1)
 Execution Time: 6.307 ms

-- enable_bitmapscan / enable_indexscan を off にして強制的に Seq Scan させた場合
 Seq Scan on bugs_big (actual time=0.006..17.632 rows=33334 loops=1)
   Filter: (tags_arr @> '{save}'::text[])
   Rows Removed by Filter: 166666
 Execution Time: 18.628 ms

図: 20 万行の合成テーブルで、GIN インデックスを使った包含検索は 6.3 ms、強制的にシーケンシャルスキャンさせると 18.6 ms (約 3.0 倍)。どちらも実機の EXPLAIN (ANALYZE, BUFFERS) で確認した値。

サンプル DB のような数行のテーブルでは、PostgreSQL のプランナはそもそも GIN インデックスを使わず素直にシーケンシャルスキャンを選びます (テーブルが小さいとインデックスを経由する分のオーバーヘッドの方が大きくなるため)。インデックスの効果が表れるのは、この回のように行数が十分に増えてからです。実務では「今は数百行だから配列でもカンマ区切りでも困らない」という判断が、データが増えた後に問題を起こす典型的な入口になるため、将来の行数の見込みも含めて設計を判断してください。また、text[] に GIN インデックスを使う場合のデフォルトの演算子クラスは @>・<@・&& (含む・含まれる・共通要素がある) をサポートしており、等価比較だけでなく集合演算のような検索ができる点も、交差テーブルとの使い分けの基準になります。

最後に、この回で確認した 3 つの選択肢を整理しておきます。

操作カンマ区切り文字列text[] 配列交差テーブル (tags)
1 つの値で検索するLIKE で境界があいまい@> で要素の完全一致= で完全一致
値ごとに集計する毎回 unnest で再分解unnest で分解すれば可GROUP BY だけで可

配列は「値の境界を守りたいが、語彙の厳密な管理までは要らない」という中間的な要件に向いた選択であり、カンマ区切り文字列を置き換える最小限の一歩として有効です。語彙の管理や行をまたいだ集計・結合を本格的にしたい場合は、最初から交差テーブルを選ぶのが素直な解決策になります。

「このクエリ、なぜ遅いのか」という問いに答えるには、実行計画 (PostgreSQL がクエリをどう処理するかを決めた手順の木構造) を読めることが前提になります。この回はシニア編の土台として、EXPLAIN (ANALYZE, BUFFERS) の出力の各行を図で読み解き、PostgreSQL がどのスキャン方式・結合方式を選ぶかを実機で確認します。そのうえで最大の落とし穴である「推定行数と実際の行数のずれ」を、相関した 2 つの列を条件にしたクエリで再現し、CREATE STATISTICS で直すところまでを実機で確かめます。

1. この回で解く問題 ― 計画が読めないと何が起きるか

PostgreSQL は SQL を受け取ると、何も聞かずに「このやり方で実行する」という計画を 1 つ選びます。この計画は、統計情報 (テーブルの行数・値の分布など) から各ステップのコストを見積もり、最も安いと思われる方法を選ぶ、コストベースの最適化という方式で決まります。問題は、見積もりが外れることがあるという点です。見積もりが外れると、本来は索引を使うべき場面でテーブル全体を読んでしまったり、小さい方を先に処理すべき結合で逆の順番を選んでしまったりします。

実行計画を読めないと、こうした「見積もりの外れ」が本番で起きても、どこで何が狂っているのかが分からず、インデックスを闇雲に増やす (第 13 回で見たアンチパターン) のような対症療法に頼ることになります。実行計画を読むことは、遅いクエリを「何が実際に起きているか」から直す、シニアの土台になる技術です。

2. 仕組み ― EXPLAIN (ANALYZE, BUFFERS) の読み方

EXPLAIN だけだと見積もりしか出ませんが、ANALYZE を付けると実際にクエリを実行し、見積もりと実測を並べて表示します (本番相当のデータで実行されるため、更新系の文に付けるときは BEGIN; ... ROLLBACK; で囲むなど影響に注意が必要です)。BUFFERS を付けると、各ステップが何ページ (8 KB 単位のブロック) をメモリ上のキャッシュから読んだか (shared hit)、ディスクから読んだか (shared read) も表示されます。実機で単純な主キー検索を実行しました。

EXPLAIN (ANALYZE, BUFFERS, COSTS off) SELECT * FROM bugs_corr WHERE id = 12345;

Index Scan using bugs_corr_pkey on bugs_corr (actual time=0.066..0.068 rows=1.00 loops=1)
  Index Cond: (id = 12345)
  Index Searches: 1
  Buffers: shared hit=7
Planning:
  Buffers: shared hit=75
Planning Time: 0.610 ms
Execution Time: 0.124 ms

この出力を図のように分解できます。ノード名 (Index Scan using bugs_corr_pkey on bugs_corr) は使われた手法と対象、actual time はこのノードが最初の 1 行を返すまでの時間と全行を返し終えるまでの時間 (開始..終了、単位はミリ秒)、rows は 1 回の実行で返した行数の実測値、loops はこのノードが呼ばれた回数です。Index Cond は索引に渡された絞り込み条件、Buffers: shared hit=7 は 7 ページ分をすべてキャッシュから読めたことを示します (shared read が出ればディスクからの読み込みが発生したことになります)。木構造になった計画は、一番内側 (下側・右側) のノードから先に実行され、外側のノードがその結果を受け取って処理するという順番で実行されます。

図: EXPLAIN (ANALYZE, BUFFERS) の各項目は、ノード名・実測値・絞り込み条件・読み取り元の 4 つに分けて読む。

3. 仕組み ― Seq Scan / Index Scan / Index Only Scan / Bitmap Scan

PostgreSQL が 1 つのテーブルから行を取り出す方法は、実機で確認した通り大きく 4 種類あります。Seq Scan (全件スキャン) はテーブルを頭から全部読みます。少量のデータや、条件に合う行の割合が高い (選択度が低い) 場合はこれが最速です。Index Scan は索引を 1 件ずつたどってヒープ (本体の行データ) を読みに行きます。主キー検索のような、ごく少数の行だけが必要な場合に向いています。

EXPLAIN (ANALYZE, COSTS off) SELECT id FROM bugs_corr WHERE id BETWEEN 1000 AND 1010;

Index Only Scan using bugs_corr_pkey on bugs_corr (actual time=0.011..0.012 rows=11.00 loops=1)
  Index Cond: ((id >= 1000) AND (id <= 1010))
  Heap Fetches: 0

Index Only Scan は、必要な列が索引の中だけで完結する (ヒープを読まなくて済む) ときに使われます。実機で Heap Fetches: 0 となり、ヒープへのアクセスが本当にゼロだったことが確認できました。

EXPLAIN (ANALYZE, COSTS off) SELECT * FROM bugs_corr WHERE priority = 'HIGH';

Bitmap Heap Scan on bugs_corr (actual time=1.298..5.328 rows=50000.00 loops=1)
  Recheck Cond: (priority = 'HIGH'::text)
  Heap Blocks: exact=1274
  ->  Bitmap Index Scan on bugs_corr_priority_idx (actual time=1.191..1.191 rows=50000.00 loops=1)
        Index Cond: (priority = 'HIGH'::text)

Bitmap Scan は、条件に合う行がそれなりに多い (ここでは 20 万行中 5 万行、25 %) ときに使われます。まず索引で該当するヒープのページ番号をビットマップとして集め、それをページ番号順に並べ替えてから読みに行くことで、ディスクへのランダムアクセスをまとめて効率化します。Index Scan のように 1 件ごとにヒープへ飛ぶのではなく、ページ単位でまとめて読むのが特徴です。

図: 条件に合う行の割合(選択度)と、必要な列が索引だけで足りるかで、使われるスキャン方式が変わる。

4. 仕組み ― Nested Loop / Hash Join / Merge Join

2 つ以上のテーブルを結合するときも、PostgreSQL は 3 種類の方式から選びます。小さい bugs (5 行) と accounts (4 行) の結合を、それぞれ強制的に実行させて実機で比較しました。

-- Nested Loop (外側の各行ごとに、内側を索引で検索する)
Nested Loop (actual time=0.176..0.181 rows=5.00 loops=1)
  ->  Seq Scan on bugs b (actual time=0.025..0.025 rows=5.00 loops=1)
  ->  Index Only Scan using accounts_pkey on accounts a (actual time=0.030..0.030 rows=1.00 loops=5)

-- Hash Join (小さい側をハッシュ表に組み立て、大きい側を1回流してハッシュで突き合わせる)
Hash Join (actual time=0.031..0.033 rows=5.00 loops=1)
  Hash Cond: (b.reported_by = a.account_id)
  ->  Seq Scan on bugs b (actual time=0.007..0.007 rows=5.00 loops=1)
  ->  Hash (actual time=0.011..0.011 rows=4.00 loops=1)

-- Merge Join (両側を結合キーでソートしてから、先頭から同時に読み進める)
Merge Join (actual time=0.054..0.056 rows=5.00 loops=1)
  Merge Cond: (b.reported_by = a.account_id)
  ->  Sort (actual time=0.044..0.045 rows=5.00 loops=1)
  ->  Sort (actual time=0.007..0.008 rows=4.00 loops=1)

Nested Loop は外側の行 1 件ごとに内側を探しに行くので、外側が少なく内側に効く索引があるときに向きます。loops=5 という表示が、内側のノードが 5 回 (外側の行数ぶん) 呼ばれたことを表しています。Hash Join は小さい側をメモリ上のハッシュ表に組み立て、大きい側を 1 回だけ流して突き合わせるので、索引が無くても速く、等値結合 (=) に向いています。Merge Join は両側を結合キーでソート済みにしてから先頭から同時に読み進めるので、両方が元からソートされている (索引がある) ときにソートのコストを省けます。

図: 3種類の結合方式は、テーブルの大きさ・索引の有無・ソート済みかどうかで使い分けられる。

5. どこで壊れるか ― 推定行数と実行行数のずれ (相関した列)

PostgreSQL の見積もりは、既定では各列が互いに無関係であるという前提で計算されます。複数の条件を AND でつなぐと、各条件の選択度を掛け合わせるだけで全体の選択度を見積もります。ところが実際の列が互いに相関している (ある列の値が決まると、別の列の値もほぼ決まる) 場合、この前提が崩れ、見積もりが大きく外れます。

実機で、20 万行のテーブルに priority (HIGH/CRITICAL/LOW/MEDIUM が 25 % ずつ) と status (HIGH/CRITICAL の行は必ず NEW、LOW/MEDIUM の行は必ず FIXED) という、完全に連動する 2 列を用意しました。

SELECT priority, status, count(*) FROM bugs_corr GROUP BY 1,2 ORDER BY 1,2;
--  priority | status | count
-- ----------+--------+-------
--  CRITICAL | NEW    | 50000
--  HIGH     | NEW    | 50000
--  LOW      | FIXED  | 50000
--  MEDIUM   | FIXED  | 50000

EXPLAIN (ANALYZE, BUFFERS, COSTS on)
SELECT * FROM bugs_corr WHERE priority IN ('HIGH','CRITICAL') AND status = 'NEW';

Bitmap Heap Scan on bugs_corr  (cost=1040.69..3817.79 rows=50207 width=18) (actual time=1.584..9.604 rows=100000.00 loops=1)
  Recheck Cond: (priority = ANY ('{HIGH,CRITICAL}'::text[]))
  Filter: (status = 'NEW'::text)
  ->  Bitmap Index Scan on bugs_corr_priority_idx  (cost=0.00..1028.13 rows=100207 width=0)

実際に条件に合う行は 10 万行 (全 20 万行の 50 %) なのに、PostgreSQL の見積もりは rows=50207 でした。これは「priority が HIGH/CRITICAL である確率 (50 %)」と「status が NEW である確率 (50 %)」を無関係だとみなして掛け合わせた結果 (50 % × 50 % ≒ 25 %、20 万行の約 25 % が 50207 に近い) で、実際には 2 列が完全に連動しているため、本当の選択度は 50 % でした。約 1.99 倍 (100000 ÷ 50207) の過小評価です。

図: 列の独立を仮定した見積もりは、実際に相関がある列の組に対して大きく外れる。

6. シニアの書き方 ― ANALYZE と統計、CREATE STATISTICS で見積もりを直す

見積もりの材料になっているのは pg_stats に保存された統計情報で、ANALYZE 文を実行すると更新されます。実機で priority と status の統計を見ると、それぞれの列は正しく捉えられています (priority は 4 値で各 25 % 前後、status は 2 値で各 50 % 前後)。問題は、PostgreSQL の既定の統計が列単体の分布しか持たず、列同士の相関を記録していないことです。

PostgreSQL 10 以降は CREATE STATISTICS で、複数列の相関を明示的に記録できます。今回のように一方の列の値が他方を完全に決めてしまう関係には、dependencies (関数従属度) という種類の拡張統計が使えます。

CREATE STATISTICS bugs_corr_dep (dependencies) ON priority, status FROM bugs_corr;
ANALYZE bugs_corr;

EXPLAIN (ANALYZE, BUFFERS, COSTS on)
SELECT * FROM bugs_corr WHERE priority IN ('HIGH','CRITICAL') AND status = 'NEW';

Bitmap Heap Scan on bugs_corr  (cost=1053.76..3831.96 rows=100280 width=18) (actual time=1.423..9.345 rows=100000.00 loops=1)
  Recheck Cond: (priority = ANY ('{HIGH,CRITICAL}'::text[]))
  Filter: (status = 'NEW'::text)
  ->  Bitmap Index Scan on bugs_corr_priority_idx  (cost=0.00..1028.69 rows=100280 width=0)

CREATE STATISTICS を追加して ANALYZE を再実行すると、見積もりは rows=100280 まで改善し、実際の 100,000 行との差は 0.28 % まで縮まりました。実機で記録された依存度は {"2 => 3": 1.000000} (2 列目から 3 列目への関数従属度が 1.0、つまり完全に決まる) で、この関係を正しく捉えたことが確認できます。見積もりが大きく外れるクエリを見つけたら、まず条件に使われている列同士が相関していないかを確認し、相関があれば CREATE STATISTICS を検討するのが実務的な手順です。

どのクエリがどれだけ遅いかを継続的に追跡するには pg_stat_statements (実行されたクエリの統計を蓄積する拡張) や auto_explain (遅いクエリの実行計画を自動でログに出す拡張) が定番ですが、どちらも shared_preload_libraries に追加してサーバーを再起動する必要があります。今回の検証環境ではこの設定がされておらず、CREATE EXTENSION pg_stat_statements; を実行すると ERROR: pg_stat_statements must be loaded via "shared_preload_libraries" になることを実機で確認しました。本番でこれらを使う場合は、設定変更とサーバー再起動が必要になることを前提に計画してください。

CTE ・ LATERAL ・ 再帰を使い分ける ― 「名前を付けた一時テーブル」の正体

WITH 句は単なる見やすさのための別名ではなく、PostgreSQL 12 以降では「インライン化されるか、材料化 (マテリアライズ) されるか」という実行計画そのものに関わる選択です。LATERAL は FROM 句の中で前の表の行を参照する唯一の方法で、再帰 CTE は停止条件を自分で保証しない限り永遠に回ります。この回では、この 3 つを実機の実行計画とエラーメッセージで確認します。

この回の前提: 第 3 回 ナイーブツリー (WITH RECURSIVE の初出) ・ 第 29 回 ウィンドウ関数で集合として考える

この回で答えるのは「WITH で名前を付けたクエリは、ビューのように毎回素通りするのか、それとも一時テーブルのように一度だけ計算されるのか」「グループごとの上位 N 件を取るときに、なぜ普通の JOIN ではなく LATERAL が必要になるのか」「再帰 CTE はいつ止まるのか」という 3 つの疑問です。結論を先に言うと、CTE は PostgreSQL 12 以降は既定でインライン化 (呼び出し元に展開) されますが、複数回参照すると既定で材料化 (1 回だけ計算してメモリに置く) に切り替わり、この切り替わりを MATERIALIZED/NOT MATERIALIZED で明示できます。LATERAL は「右側の表が左側の行を見てよい」という唯一の仕組みで、再帰 CTE は自分で書いた停止条件以外に安全装置が無いので、書き忘れると statement_timeout に当たるまで本当に回り続けます。

1. この回で解く問題 ― WITH は「名前を付けた箱」でしかない

WITH 名前 AS (SELECT ...) という書き方 (共通テーブル式、CTE) は、長いクエリを読みやすい単位に分割するためによく使われます。しかし「読みやすくするためだけの別名」と理解していると、2 つの誤解が生まれます。1 つは「CTE は必ず 1 回だけ計算されて、その結果が使い回される」という誤解、もう 1 つは「CTE もサブクエリも結局同じように最適化される」という誤解です。どちらも PostgreSQL 12 以降では正確ではありません。

もう 1 つの問題は「グループごとに上位 N 件を取りたい」という定番の要求です。第 29 回で見た ROW_NUMBER() OVER (PARTITION BY ...) で書けますが、グループごとに違う条件 (違う LIMIT や、グループの値を使った絞り込み) を付けたい場合、ウィンドウ関数だけでは書きにくくなります。ここで必要になるのが LATERAL です。

3 つ目は再帰です。親子関係や「この行は別の行の重複である」といった連鎖をたどるには WITH RECURSIVE が必要ですが、再帰である以上「いつ止まるか」を自分で保証しなければ、円環データや書き忘れで無限に回り続けます。

図: CTE は書き方と参照回数によって、呼び出し元への展開か、1 回だけの計算かが切り替わる。

2. 仕組み ― CTE は既定でインライン化される (PostgreSQL 12 以降)

PostgreSQL の公式ドキュメントによれば、再帰的でなく、副作用 (データ変更) も無く、1 回しか参照されない CTE は、既定でサブクエリと同じようにインライン化 (呼び出し元に展開) されるとされています。これは PostgreSQL 12 で導入された挙動で、それより前のバージョンでは CTE は常に最適化の壁 (optimization fence) として働き、必ず 1 回だけ計算されていました。同じ bugs テーブルに対して、CTE をそのまま使った場合と MATERIALIZED を付けた場合の実行計画です。

EXPLAIN (COSTS OFF)
WITH recent AS (
  SELECT * FROM bugs
)
SELECT * FROM recent WHERE bug_id = 1;
 Index Scan using bugs_pkey on bugs
   Index Cond: (bug_id = 1)

外側の WHERE bug_id = 1 が CTE の内側まで押し込まれ (プッシュダウン)、bugs_pkey を使った Index Scan 1 発で済んでいます。recent という名前は実行計画のどこにも残っていません。これに AS MATERIALIZED を付けると挙動が変わります。

EXPLAIN (COSTS OFF)
WITH recent AS MATERIALIZED (
  SELECT * FROM bugs
)
SELECT * FROM recent WHERE bug_id = 1;
 CTE Scan on recent
   Filter: (bug_id = 1)
   CTE recent
     ->  Seq Scan on bugs

こちらは bugs テーブルをまず Seq Scan で全件読み、recent という一時的な結果をメモリに置いてから、その上で bug_id = 1 の絞り込みを掛けています。インデックスを使った絞り込みの機会が失われ、全件スキャンになっています。同じ 1 行を取るだけのクエリでも、MATERIALIZED を付けるかどうかでアクセスするデータ量が大きく変わります。

図: 既定 (インライン化) は絞り込みが内側まで届くが、MATERIALIZED は内側を先に固定してから絞り込む。

3. 仕組み ― 2 回以上参照すると既定が材料化に変わる、データ変更 CTE

CTE を複数回参照する場合は話が変わります。公式ドキュメントのとおり、2 回以上参照される CTE は、既定で材料化される (もう一度計算し直すのではなく、1 回だけ計算してその結果を再利用する) という挙動になります。担当者ごとの作業時間の合計 (totals) を自己結合した例です。

WITH totals AS (
  SELECT reported_by, SUM(hours) AS total_hours FROM bugs WHERE hours IS NOT NULL GROUP BY reported_by
)
SELECT t1.reported_by, t1.total_hours
FROM totals t1 JOIN totals t2 ON t1.reported_by = t2.reported_by
WHERE t1.total_hours > 0;
 Hash Join
   CTE totals
     ->  HashAggregate
           ->  Seq Scan on bugs
   ->  CTE Scan on totals t2
   ->  Hash
         ->  CTE Scan on totals t1

HashAggregate (集計) は 1 回しか出てきません。totals は 1 回だけ計算され、t1 と t2 という 2 つの参照はどちらもその結果を CTE Scan で読むだけです。ここに NOT MATERIALIZED を付けると、参照ごとに集計をやり直します。

WITH totals AS NOT MATERIALIZED ( ... )
...
 Hash Join
   ->  HashAggregate
         ->  Seq Scan on bugs
   ->  Hash
         ->  HashAggregate
               ->  Seq Scan on bugs bugs_1

今度は HashAggregate と Seq Scan on bugs が 2 回に増えています。totals という集計を 2 回計算し直しているためです。集計そのものが軽ければインライン化の方が速いこともありますが、集計や複雑な結合を含む重い CTE を何度も参照するなら、既定の材料化 (1 回だけ計算) の方が有利です。どちらが速いかは、CTE の中身が軽いか重いか、外側でどれだけ絞り込まれるかによって変わるので、実際に EXPLAIN で両方を確認するのが確実です。

データ変更 CTE ― 1 つの文で削除と挿入をつなぐ

CTE は SELECT だけでなく INSERT・UPDATE・DELETE の RETURNING 結果を次の CTE や外側のクエリに渡せます。「FIXED のまま 2026-02-01 より前に報告されたバグをアーカイブ用テーブルに移す」を、削除と挿入をまとめた 1 つの文で実行した結果です。

WITH moved AS (
  DELETE FROM bugs
  WHERE status = 'FIXED' AND date_reported < '2026-02-01'
  RETURNING *
)
INSERT INTO bugs_archive
SELECT * FROM moved;

実行前は 19 件のバグがあり、このうち条件に合う 5 件が bugs_archive に移動し、bugs には 14 件が残りました。1 つの文の中で完結するので、削除だけ成功して挿入が失敗する (あるいはその逆) という中間状態が生まれません。これは 2 つの文に分けて BEGIN/COMMIT で囲むのと似ていますが、1 文であること自体がアトミック性を保証してくれるので、トランザクション制御を書き忘れる余地がありません。

図: WITH moved AS (DELETE ... RETURNING) を INSERT に渡すことで、削除と挿入を 1 つの文にまとめる。

4. 仕組み ― LATERAL で「グループごとの上位 N 件」を書く

「各担当者の、直近 2 件のバグ報告だけを見たい」という要求を、サブクエリを FROM に書いて試すと、次のエラーになります。

SELECT a.account_name, b.bug_id
FROM accounts a
CROSS JOIN (
  SELECT bug_id FROM bugs WHERE reported_by = a.account_id ORDER BY date_reported DESC LIMIT 2
) b;
-- ERROR:  invalid reference to FROM-clause entry for table "a"
-- HINT:  To reference that table, you must mark this subquery with LATERAL.

通常のサブクエリは、それより前に FROM に出てきた表の行を見ることができません。各担当者ごとに違う account_id で絞り込みたいのに、サブクエリの中で a.account_id を参照できないので、この書き方は成立しません。LATERAL を付けると、エラーメッセージの指示どおりこの参照が許可されます。

SELECT a.account_name, b.bug_id, b.date_reported, b.summary
FROM accounts a
CROSS JOIN LATERAL (
  SELECT bug_id, date_reported, summary
  FROM bugs
  WHERE reported_by = a.account_id
  ORDER BY date_reported DESC, bug_id DESC
  LIMIT 2
) b
ORDER BY a.account_name, b.date_reported DESC;

4 人の担当者それぞれについて、直近 2 件 (全員ちょうど 2 件以上報告しているので、どの担当者も 2 行ずつ) が取れています。実行計画を見ると、この仕組みがどう動いているかが分かります。

EXPLAIN (COSTS OFF)
SELECT a.account_name, b.bug_id, b.date_reported
FROM accounts a
CROSS JOIN LATERAL ( ... LIMIT 2 ) b;
 Nested Loop
   ->  Seq Scan on accounts a
   ->  Limit
         ->  Sort
               ->  Bitmap Heap Scan on bugs
                     Recheck Cond: (reported_by = a.account_id)
                     ->  Bitmap Index Scan on bugs_reported_by_idx
                           Index Cond: (reported_by = a.account_id)

Nested Loop になっており、accounts の行を 1 行読むたびに、その account_id を使って内側 (bugs) を検索し、LIMIT 2 で止めています。PARTITION BY を使うウィンドウ関数は「全体を 1 回ソートしてから各グループの上位を取る」方式ですが、LATERAL は「グループごとに専用のインデックス検索を LIMIT 付きで実行する」方式です。グループ数が少なく、各グループに適したインデックスがある場合は LATERAL の方が有利になることがあります。

図: LATERAL の右側のサブクエリは、左側の表の行ごとに異なる値を参照しながら再評価される。

5. 仕組み ― 再帰 CTE の停止条件と CYCLE 句

WITH RECURSIVE は「最初の 1 回 (非再帰項)」と「前回の結果を使ってもう 1 回計算する (再帰項)」を UNION ALL でつなぎ、再帰項が 0 行を返すまで繰り返します。「このバグは別のバグの重複である」という連鎖 (bug_duplicates(bug_id, duplicate_of)) を作り、bug_id=22 から重複の連鎖をたどって根本の (もう重複先が無い) バグまで遡った実行結果です。

WITH RECURSIVE chain(start_id, bug_id, duplicate_of, depth) AS (
  SELECT bug_id, bug_id, duplicate_of, 1
  FROM bug_duplicates WHERE bug_id = 22
  UNION ALL
  SELECT c.start_id, d.bug_id, d.duplicate_of, c.depth + 1
  FROM bug_duplicates d
  JOIN chain c ON d.bug_id = c.duplicate_of
  WHERE c.depth < 20
)
SELECT * FROM chain ORDER BY depth;

22 → 21 → 20 → 15 とたどり、根本のバグは 15 だと分かりました。ここで止まっているのは bug_duplicates に bug_id=15 の行が無い (15 はもう重複先を持たない) ためですが、安全のため WHERE c.depth < 20 という明示的な深さの上限も入れています。これが「停止条件」です。

連鎖が循環している (A は B の重複、B は A の重複) 場合、深さの上限が無いと同じ行を永遠に行き来します。PostgreSQL 14 以降の CYCLE 句を使うと、同じキーに戻ってきたことを自動的に検出して止めてくれます。

WITH RECURSIVE chain(bug_id, duplicate_of) AS (
  SELECT bug_id, duplicate_of FROM bug_duplicates WHERE bug_id = 30
  UNION ALL
  SELECT d.bug_id, d.duplicate_of
  FROM bug_duplicates d JOIN chain c ON d.bug_id = c.duplicate_of
) CYCLE bug_id SET is_cycle USING path
SELECT bug_id, duplicate_of, is_cycle FROM chain;
bug_idduplicate_ofis_cycle
3031f
3130f
3031t

30 と 31 が互いを重複としている循環データに対し、3 回目に再び bug_id=30 に戻ってきた時点で is_cycle = t が立ち、そこで止まっています。深さの上限を自分で書く方法と比べて、CYCLE 句は「本当に同じ行に戻ってきたか」を正確に検出できる点が強みです。

単純な連番には再帰 CTE より generate_series

再帰 CTE は親子関係のような「木」をたどるのには向いていますが、1 から 100,000 までの連番のような、階層を持たない単純な繰り返しに使うのは不向きです。同じ 100,000 行を再帰 CTE と generate_series で作った実行結果です。

WITH RECURSIVE nums(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM nums WHERE n < 100000
)
SELECT count(*) FROM nums;
-- Execution Time: 22.760 ms (Recursive Union, WorkTable Scan loops=100000)

SELECT count(*) FROM generate_series(1, 100000);
-- Execution Time: 7.153 ms (Function Scan on generate_series)

どちらも 100,000 行を作りますが、再帰 CTE は 1 行進むごとに WorkTable Scan を 1 回評価するため loops=100000 になり、実行時間は約 22.8 ms でした。generate_series は専用の集合返却関数 1 回の呼び出しで済み、約 7.2 ms でした (いずれもウォームキャッシュでの実行)。約 3 倍の差であり、データに階層や連鎖の構造が無いなら、再帰を使う理由はありません。

図: 30 と 31 が互いを指す循環で、CYCLE 句が再訪を検出して無限に回らないようにする。

6. どこで壊れるか ― よくある間違い

間違い 1: 停止条件を書き忘れた再帰 CTE

深さの上限も CYCLE 句も付けずに再帰項を書くと、再帰項が 0 行を返すまで止まりません。statement_timeout を 500 ミリ秒に設定した上で、停止条件の無い再帰 CTE を実際に実行した結果です。

SET statement_timeout = '500ms';
WITH RECURSIVE nums(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM nums
)
SELECT count(*) FROM nums;
-- ERROR:  canceling statement due to statement timeout

これは実際に PostgreSQL 18 で発生したエラーです。n は増え続けるだけで、WHERE による上限も CYCLE 句も無いため、statement_timeout が無ければメモリか CPU を使い切るまで回り続けたはずです。再帰 CTE を書くときは、再帰項に必ず停止条件 (上限、または既に処理した行を除く条件) を入れることが前提になります。

間違い 2: 「CTE は 1 回しか計算されない」と思い込んで重い処理を複数回書く

節 3 で見たとおり、2 回以上参照される CTE は既定で材料化され 1 回だけ計算されますが、これは「絶対にそうなる」という保証ではありません。NOT MATERIALIZED を明示したり、CTE の中身が軽くプランナがインライン化を選んだりすると、参照の数だけ計算し直されることがあります。重い集計を含む CTE を複数回参照するコードをレビューするときは、EXPLAIN で集計ノードが何回出てくるかを数える価値があります。

間違い 3: LATERAL を使わずに「外側の値を使う内側のクエリ」を書こうとする

節 4 のエラーのとおり、LATERAL を付け忘れると「外側の行を参照できない」というエラーで即座に気づけます。気づきにくいのは、LEFT JOIN LATERAL と LEFT JOIN (LATERAL 無し) を間違えて使うケースです。右側に外側への参照が無ければ LATERAL を付けてもエラーにはなりませんが、意味のない (常に同じ結果を返す) サブクエリを書いてしまっていることに気づきにくくなります。

図: 停止条件が無い再帰は、statement_timeout のような外部の仕組みが無ければ止まらない。

7. シニアの書き方 ― 判断の基準

1. CTE を書くときは、材料化されてほしいかどうかを自分で決める。「重い集計を 1 回だけ計算してから複数回使い回したい」なら MATERIALIZED を明示し、「単純な絞り込みなのでインデックスを使った絞り込みを内側まで届けたい」なら素のまま (または NOT MATERIALIZED) にします。既定の挙動 (1 回参照ならインライン化、複数回参照なら材料化) に黙って従うのではなく、意図を明示することで、PostgreSQL のバージョンが変わっても挙動が変わらないコードになります。

2. 「グループごとに違う条件を適用したい」ときは LATERAL を検討する。ウィンドウ関数は「全体を 1 回ソートして、各グループの中で順位を付ける」という形に向いていますが、グループごとに異なるパラメータを使う検索 (「このカテゴリでは在庫がある商品だけ」など) には LATERAL の方が自然に書けます。

3. 再帰 CTE を書いたら、必ず停止条件を声に出して確認する。「このデータに循環が無いと保証できるか」「保証できないなら CYCLE 句か深さの上限を入れたか」をコードレビューの通過条件にします。階層を持たない単純な連番には、再帰ではなく generate_series を使います。

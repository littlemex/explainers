この回の前提: 第 06 回 パーティショニングとシャーディング。

結論を先に言うと、コンシステントハッシュ (consistent hashing) とは「サーバーの数が増えたり減ったりしても、動くデータの量をごく一部に抑える」ハッシュの割り振り方である。第 06 回で見たハッシュベースのシャーディング shard_id = hash(key) % N には、シャード数 N を変えるとほぼ全てのキーの行き先が変わってしまうという弱点があった。コンシステントハッシュはサーバーとキーを同じ「リング」の上に配置することで、この再配置の範囲を小さく閉じ込める。

1. 剰余ハッシュの再配置問題 ― なぜ単純な mod N は壊れるのか

ByteByteGo の consistent-hashing は、単純なハッシュ分割の問題を次のように説明する。サーバーの台数を N 台として serverIndex = hash(key) % N でどのサーバーに置くかを決める方式は、N が固定されている間はうまく機能する。問題は、新しい需要に対応してサーバーを追加したり、故障したサーバーを取り除いたりして N が変わったときに起こる。

具体例で確認する。N=3 のとき、あるキーのハッシュ値が 7 だとすると、7 % 3 = 1 なのでサーバー 1 に置かれる。ここでサーバーを 1 台追加して N=4 になると、同じキーは 7 % 4 = 3 となり、サーバー 3 に移ってしまう。これはこのキーだけの問題ではない。剰余を取る相手の数 (N) そのものが変わるため、ほぼ全てのキーで計算結果が変わり、サーバー台数の変化のたびに大量のデータが一斉に移動する「再配置の嵐」が起きる。

図: サーバーを 1 台増やすだけで、剰余の計算結果はほぼ無関係な値に変わり、大量のキーが移動する。

2. コンシステントハッシュのリング構造

コンシステントハッシュは、サーバーとキーの両方を同じリング (ring, 円環状の数直線) の上に配置する。やり方は次の通りである。(1) ハッシュ関数を使って各サーバーの名前や IP アドレスをハッシュ値に変換し、その値の位置にサーバーをリング上に置く。(2) 同じハッシュ関数で各キーもハッシュ値に変換し、リング上に置く。(3) あるキーがどのサーバーに属するかを決めるときは、そのキーの位置から時計回りに進んで最初に見つかったサーバー をその担当とする。

ByteByteGo の例では、key 0 がリング上で時計回りに進んだ先に server 0 があるため server 0 が担当し、key 1 は server 1 が担当する、という具合になる。重要なのは、この「時計回りに最初に見つかったサーバー」という規則そのものは、サーバーの台数が変わっても変える必要がないことである。

図: key 0 は時計回りに進んだ先の server 0 が担当し、key 1 は server 1、key 2 は server 2 が担当する。

3. サーバーを追加・削除したときに動く範囲

コンシステントハッシュの核心は、サーバーの台数が変わっても動くキーがごく一部に限られることである。ByteByteGo の例では、リング上の server 0 の左側(時計回りで server 0 の手前)に新しいサーバー s4 を追加すると、動くのは s4 と server 0 の間に位置していたキー k0 だけである。k1、k2、k3 はそれぞれ元から時計回りに進んだ先にあったサーバーがそのまま変わらないため、影響を受けない。

これは第 06 回で見た剰余ハッシュとの決定的な違いである。剰余ハッシュでは N が変わると割る数そのものが変わるため、ほぼ全てのキーの計算結果が無関係な値に変わる。コンシステントハッシュでは、新しいサーバーが「割り込む」位置の両隣のサーバーの間にあったキーだけが影響を受け、リングの他の部分は無傷のままである。サーバーを削除する場合も同様で、削除されたサーバーが担当していたキーだけが、時計回りで次に見つかるサーバーに移る。

図: 新サーバー s4 を挿入すると、s4 と server 0 の間にあった k0 だけが動き、他のキーは無傷のまま。

4. 偏りの問題と仮想ノード

リング上にサーバーをハッシュ関数で置くだけだと、サーバーの台数が少ないうちは、サーバー同士の間隔が偶然大きく偏ることがある。間隔が広いサーバーほどリング上の広い範囲を担当することになり、キーの数が偏って一部のサーバーだけ負荷が高くなってしまう。

この偏りを緩和する一般的な工夫が仮想ノード (virtual node) である。1 台の物理サーバーを、リング上の 1 点ではなく複数の点 として配置する。例えば 1 台のサーバーに 100 個の仮想的な位置を持たせれば、そのサーバーが担当する区間は 100 個の小さな区間の合計になり、1 つの区間が極端に大きくなる確率が下がる。物理サーバーを追加・削除するときも、その物理サーバーに属する仮想ノードの分だけ処理すればよく、リングの基本的な考え方は変わらない。

図: 1 台のサーバーをリング上の複数点に置くと、担当区間の偏りが小さくなる。

5. 実システムでの例と、他の手法との比較

ByteByteGo の consistent-hashing は、コンシステントハッシュを使う実システムの例として、Amazon DynamoDB と Apache Cassandra (リバランス時のデータ移動を最小化する)、Akamai のような CDN (エッジサーバー間でコンテンツを均等に分散する)、Google Network Load Balancer のようなロードバランサ (持続的な接続をバックエンドに均等に分散する) を挙げている。

コンシステントハッシュ以外にも、同じ「サーバー台数が変わっても再配置を抑えたい」という目的のための手法がある。Rendezvous hashing (ランデブーハッシュ、重み付け最大値ハッシュとも呼ばれる、Thaler と Ravishankar が 1996 年に提案) は、キーごとに全サーバーとの組み合わせのハッシュ値をそれぞれ計算し、最大値を出したサーバーを担当とする方式である。リングを使わない分、実装の見通しは良いが、サーバー台数が多いとキーを割り振るたびに全サーバー分のハッシュ計算が必要になる。

Jump Consistent Hash (ジャンプコンシステントハッシュ、Lamping と Veach が 2014 年に Google から発表) は、サーバーをリングに配置するのではなく、キーとサーバー台数から直接計算でシャード番号を求める方式で、リングや対応表を一切保持しない分メモリ効率に優れるが、サーバーに名前や重みを個別に付けて選ぶといった柔軟な使い方はしづらい。どちらの手法も、コンシステントハッシュと同じ「N の変化が一部のキーにしか影響しない」という性質を、別の実現方法で達成しようとするものである。

アンチパターンとは何か ― やってしまいがちな書き方を先に知っておく

アンチパターンとは、最初は妥当な解決策に見えて実際に動くのに、データや利用が増えたときに初めて問題を引き起こす書き方のことです

← SQL シリーズ目次へ

この回の前提: ありません。このシリーズの最初の回で、ここから第 38 回まで同じ 1 つのサンプル DB (バグ管理システム) を使って進みます。

このシリーズは全 38 回で、SQL の「やってしまいがちな書き方」とその直し方 (第 01〜27 回、アンチパターン編) を学んだあと、PostgreSQL の機能を使った「実務で強くなる書き方」 (第 28〜38 回、シニアの書き方編) に進みます。この第 01 回では、アンチパターンという考え方そのものと、全 38 回を通して使う共通のサンプル DB の構造、そして実機で SQL を確かめるための psql の使い方を押さえます。結論を先に言うと、アンチパターンは「分かりやすく間違っている書き方」ではなく「一見正しく動くのに後で壊れる書き方」であり、この後の回はすべて、その「後で壊れる理由」と「どう直すか」を実際の PostgreSQL で確かめていく構成になっています。

1. この回で解く問題 ― なぜ「動くコード」が後で問題になるのか

SQL を書き始めてしばらくすると、テストデータの数件では正しく動くのに、本番でデータや利用者が増えた途端に遅くなったり、想定外の結果を返したりする SQL に出会います。これは文法の間違いではありません。文法的には正しく実行でき、少量のデータでは正しい結果を返すからこそ、レビューでも気づかれにくいのです。このように「最初は妥当な解決策に見えて、規模が大きくなったときに問題を引き起こす書き方」のことを、このシリーズではアンチパターン (anti-pattern) と呼びます。

アンチパターン編の章立ては、Bill Karwin の『SQL アンチパターン 第 2 版』を参考にしています。参考にしたのは、各アンチパターンの名前と、「目的 → アンチパターン → 見つけ方 → 使ってよい場合 → 解決策」という章の構成です。解説の中身は書籍の要約ではなく、PostgreSQL の公式ドキュメントと論文、そして各回で実際に実行した SQL の結果から書き下ろしています。

図: アンチパターンは少量データでは正しい設計より書きやすく速く見えるが、規模が増えたある時点から急に壊れる。正しい設計は最初は多少手間でも安定して動き続ける。

この「ある時点から急に壊れる」という性質が、アンチパターンがレビューで見逃されやすい一番の理由です。だからこそ、このシリーズの各回は「どう直すか」だけでなく「どんな兆候が出たら気づけるか (見つけ方)」と「実はそれで構わない場合はどこまでか (使ってよい場合)」もセットで扱います。

2. 仕組み ― アンチパターンの 4 つの分類

このシリーズの第 02〜26 回で扱うアンチパターンは、大きく 4 つに分類できます。論理設計 はテーブルの構造そのものの誤り (第 02〜09 回、そして総まとめにあたる第 26 ・ 27 回)、物理設計 はデータ型やインデックスなど保存方法の誤り (第 10〜13 回)、クエリ は SQL の書き方そのものの誤り (第 14〜19 回)、アプリケーション開発 は開発プロセスや運用との付き合い方の誤り (第 20〜25 回) です。この 4 分類は、問題がどの段階で生まれるかという視点の違いだと考えると覚えやすくなります。

図: アンチパターンの 4 分類。問題が生まれる段階 (設計 → 保存方法 → 書き方 → 運用) が異なる。第 26 回 (外部キーのミニアンチパターン) と第 27 回 (正規化のルール) は論理設計のまとめにあたる。

3. 仕組み ― 各回の読み方 (アンチパターン編の章の型)

第 02〜26 回のアンチパターン編は、どの回も同じ型で構成されています。目的 (何を実現したかったのか) から始まり、アンチパターン (実際にどう書いてしまい、何が壊れるか) で問題を具体的に示し、見つけ方 で既存のデータベースからその兆候を見つける方法を示します。そのうえで 使ってよい場合 として「それでも構わない条件」を明確にし、最後に 解決策 として PostgreSQL での正しい書き方を示します。必要な回では、さらに PostgreSQL エンジンで考慮しておくこと を加えます。

この型のなかで特に重要なのが「見つけ方」です。多くの解説記事は「こう書くのが正しい」という解決策だけを示しますが、実務では既存のデータベースの中にすでにそのアンチパターンが潜んでいることのほうが多く、まずそれを見つける必要があります。このシリーズでは「見つけ方」の節で、information_schema や pg_catalog への具体的な問い合わせを載せ、実際に実行して兆候を探す方法を示します。

図: アンチパターン編の各回の型。「見つけ方」で既存データベースの兆候を確認してから「使ってよい場合」「解決策」に進む。

第 01 回・第 27 回・そして第 28〜38 回のシニアの書き方編は、この型とは少し異なり「この回で解く問題 → 仕組み → どこで壊れるか (よくある間違い) → シニアの書き方 (判断の基準)」という、問題・仕組み・間違い・判断の順で進みます。今読んでいるこの第 01 回自体が、その型の実例です。

4. 仕組み ― サンプル DB (バグ管理) を ER 図で読む

このシリーズは第 01 回から第 38 回まで、同じ 1 つのサンプル DB を土台にします。テーマは小さなバグ管理システムで、accounts (担当者)、bug_status (状態の一覧)、products (対象の製品)、bugs (バグ本体)、bugs_products (バグと製品の組)、comments (コメント)、screenshots (画面キャプチャ)、tags (タグ) の 8 つのテーブルからなります。まずこの全体像を ER 図 (Entity-Relationship Diagram, 実体関連図) で読めるようにしておきます。

ER 図を読む基本のルールは 2 つです。1 つは、各テーブルの箱の中で PK (Primary Key, 主キー) と書かれた列が、その行を一意に特定する列であること。もう 1 つは、箱と箱をつなぐ線が FK (Foreign Key, 外部キー) の関係を示し、線が伸びている先の列が「その行はどのテーブルのどの行を指しているか」を表すことです。多くの関係は「1 つの親に対して複数の子がある」という 1 対 N の関係ですが、bugs_products だけは bug_id と product_id の両方を外部キーとして持ち、bugs と products の 多対多 (N 対 N) の関係を実現する特別な役割 (交差テーブル、または中間テーブル) を持っています。

図: サンプル DB の中心となる 4 テーブル。bugs は reported_by ・ assigned_to ・ verified_by の 3 つの外部キーで accounts を参照し (accounts が 1、bugs が N)、status で bug_status を参照する。products は、この図の中では他のテーブルと直接結びつかない (次の図の bugs_products を介して bugs と結びつく)。

図: bugs にぶら下がる子テーブル。comments ・ screenshots ・ tags は bugs を外部キーで参照する bugs の子テーブル。bugs_products だけが bugs と products の両方を外部キーとして持ち、bugs と products の多対多 (N 対 N) の関係を仲介する交差テーブルである。

実際にこの関係を確認するには、psql の \d テーブル名 だけでなく、どのテーブルがどのテーブルを参照しているかを一覧にする問い合わせも使えます。information_schema を組み合わせると、次のように外部キーの一覧を得られます。

SELECT
  tc.table_name, kcu.column_name,
  ccu.table_name AS foreign_table, ccu.column_name AS foreign_column
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
  ON tc.constraint_name = kcu.constraint_name AND tc.table_schema = kcu.table_schema
JOIN information_schema.constraint_column_usage ccu
  ON tc.constraint_name = ccu.constraint_name AND tc.table_schema = ccu.table_schema
WHERE tc.constraint_type = 'FOREIGN KEY' AND tc.table_schema='public'
ORDER BY tc.table_name;

実際に sql_01 データベースでこれを実行すると、次の 10 行が返ります (bugs だけで 4 件の外部キーを持つことが分かります)。

 table_name    | column_name | foreign_table | foreign_column
----------------+-------------+---------------+----------------
 bugs           | reported_by | accounts      | account_id
 bugs           | assigned_to | accounts      | account_id
 bugs           | verified_by | accounts      | account_id
 bugs           | status      | bug_status    | status
 bugs_products  | bug_id      | bugs          | bug_id
 bugs_products  | product_id  | products      | product_id
 comments       | bug_id      | bugs          | bug_id
 comments       | author      | accounts      | account_id
 screenshots    | bug_id      | bugs          | bug_id
 tags           | bug_id      | bugs          | bug_id

多対多の関係も実機で確かめられます。bugs_products を経由して bug_id が 2 の行を見ると、Open RoundFile と ReConsider の 2 つの製品が結びついています。1 つのバグに複数の製品が、1 つの製品に複数のバグが結びつく、これが多対多です。

SELECT b.bug_id, b.summary, p.product_name
FROM bugs b
JOIN bugs_products bp ON bp.bug_id = b.bug_id
JOIN products p ON p.product_id = bp.product_id
ORDER BY b.bug_id, p.product_name;

 bug_id |        summary        |     product_name
--------+------------------------+----------------------
      1 | crash when saving      | Open RoundFile
      2 | wrong total on report  | Open RoundFile
      2 | wrong total on report  | ReConsider
      3 | button label typo     | Visual TurboBuilder
      4 | slow search on...      | ReConsider
      5 | login fails with...    | Open RoundFile

5. 仕組み ― psql の使い方と \d の読み方

このシリーズに載せている実行結果と実行計画は、すべて PostgreSQL 18.6 に psql で接続して実際に実行した出力です。手元で同じことを試すには、PostgreSQL 18 を用意し、回ごとに専用のデータベースを作って、下の「共通サンプル DB の定義」を読み込んでから各回の SQL を流します。コンテナを使う場合の手順は次のとおりです。

docker run -d --name sqlseries -e POSTGRES_HOST_AUTH_METHOD=trust -p 127.0.0.1:5432:5432 postgres:18
export PGHOST=127.0.0.1 PGPORT=5432 PGUSER=postgres
createdb sql_01
psql -d sql_01 -v ON_ERROR_STOP=1 -f sample_schema.sql
psql -d sql_01

POSTGRES_HOST_AUTH_METHOD=trust はパスワードなしで接続できる設定なので、127.0.0.1 にだけ公開して手元の練習にだけ使ってください。sample_schema.sql は次の折りたたみの中身をそのまま保存したファイルです。

6. どこで壊れるか ― 初心者がやりがちな誤解

アンチパターンという考え方そのものについて、初めて学ぶときによくある誤解が 3 つあります。1 つ目は、「アンチパターンと書かれている書き方は、例外なく絶対に使ってはいけない」という誤解です。実際には各回に「使ってよい場合」の節があり、要件や規模によっては合理的な選択になることもあります。例えば第 02 回で扱うカンマ区切りの値は、交差テーブルが原則の解決策ですが、PostgreSQL の配列型を使ってよい場合も正確に扱います。

2 つ目は、「見つけ方」の節を読み飛ばして「解決策」だけを覚えようとする誤解です。実務では、すでに存在するデータベースの中からアンチパターンの兆候を見つける作業のほうが、ゼロから正しく設計する作業よりも頻繁に発生します。この第 01 回で見た information_schema への問い合わせのように、各回の「見つけ方」は具体的な SQL として載せているので、実際に自分のデータベースに対して実行できることを確認してください。

3 つ目は、「アンチパターン編 (第 01〜27 回) とシニアの書き方編 (第 28〜38 回) は単に難易度が違うだけで、扱う範囲は同じだ」という誤解です。次の節で、この 2 つの編の違いを整理します。

7. シニアの書き方 (判断の基準) ― シリーズの位置づけと読み進め方

アンチパターン編 (第 01〜27 回) は「何をしてはいけないか」とその理由、そして直し方を中心に置いています。テーブル設計の誤り、データ型の誤り、SQL の書き方の誤り、運用との付き合い方の誤りという順で、どのレベルの読者にも共通して踏みやすい落とし穴を一通り確認します。第 27 回の正規化のルールは、この編全体 (特に論理設計) の理論的な裏付けとしてのまとめにあたります。

一方、シニアの書き方編 (第 28〜38 回) は、PostgreSQL に固有の機能を実務で使いこなすための内容です。EXPLAIN による実行計画の読み方、ウィンドウ関数、CTE と LATERAL、UPSERT と MERGE、ページネーション、制約による正しさの保証、JSONB、MVCC と VACUUM、ロックと分離レベル、ゼロダウンタイムでのスキーマ変更、接続とタイムアウトの運用まで、アンチパターン編の知識を前提に一段深い内容を扱います。どちらの編も PostgreSQL だけを対象にしますが、アンチパターン編は「避けるべき書き方」、シニア編は「PostgreSQL の機能を積極的に使った書き方」という向きの違いがあります。

図: シリーズ全 38 回の構成。第 01 回は入口、第 02〜27 回がアンチパターン編、第 28〜38 回がシニアの書き方編。どちらも PostgreSQL だけを対象にする。

読み進め方としては、SQL を書いた経験がまだ浅い場合は第 02 回から順番に読むことを勧めます。すでに実務で SQL を書いていて、特定の落とし穴 (例えば NULL の扱いや N+1 クエリ) に心当たりがある場合は、該当する回だけを先に読み、そのあとシニアの書き方編に進んでも構いません。各回の冒頭にある「この回の前提」には、読む前に知っておくとよい回へのリンクを載せているので、迷ったときはそこを確認してください。

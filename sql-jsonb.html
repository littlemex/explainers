JSONB の使い所と使わない所 ― 形が決まった瞬間に列へ戻す

jsonb は「形がまだ決まっていない附属データ」を飲み込むための避難所であり、同じ形が並び始めたら列と制約に戻すのがシニアの判断である

この回の前提: 第 33 回 制約で正しさを守る (CHECK ・ DOMAIN ・ 生成列の基本)

「どんな形のデータが来るか分からないから、とりあえず jsonb 列に入れておく」という判断は、短期的には正しいことが多いですが、そのまま運用を続けると検索も制約も効かないデータの沼になります。この回で確かめる結論は、jsonb は「列の形がまだ決まっていない間」を乗り切るための道具であり、同じキーの組が並び始めたら、式インデックスや生成列を使って実在の列に戻すのがシニアの判断だということです。PostgreSQL 18.6 の実機で、json と jsonb の違い、4 種類の演算子、GIN の 2 つの演算子クラス (jsonb_ops と jsonb_path_ops) の効き方の違い、そして正規化すべき兆候の見つけ方を順に確かめます。

1. この回で解く問題 ― 形が決まっていないデータをどこに置くか

バグ管理システムに、外部の連携先 (GitHub の Webhook、Jira の API、社内フォームなど) からの通知を取り込む場面を考えます。連携先ごとに送ってくる項目の数も名前も違い、今後も増えます。これを source_name、severity_score、os_name ... と連携先ごとに列を増やしていくと、第 09 回で扱った「メタデータトリブル」と同じ轍を踏みます。列を増やすたびにスキーマ変更が要り、使われない列が大量の NULL で埋まります。

ここで jsonb 列が受け皿になります。1 列に {"source":"github","severity_score":8.2,...} のような任意の構造を持たせ、連携先が増えてもスキーマ変更をしません。ただし、この自由さは無料ではありません。外部キーも CHECK 制約も、型チェックも、jsonb の中には素直には届きません。この回では、どこまでが jsonb に向いた自由さで、どこからが正規化すべき兆候なのかを、実際のデータと実行計画で線を引きます。

図: 連携先ごとに列を増やす設計は第 09 回の問題を再演する。jsonb は列を増やさないが、その自由さは検索と制約の弱さと表裏一体。

2. 仕組み ― json と jsonb は同じ構文で違うものを保存する

PostgreSQL には json と jsonb という 2 つの型があり、どちらも同じ JSON の構文を受け付けますが、保存の仕方が違います。json は入力された文字列をほぼそのまま (空白やキーの重複を含めて) 保存し、読むたびに再度パースします。jsonb は入力時に 1 度パースして、重複キーを排除し、順序を正規化した上で、効率よく辿れる分解済みの二値表現として保存します。実機で同じ入力を 2 つの型に入れると、この違いがそのまま見えます。

SELECT '{"a":1, "a":2, "b":3}'::json  AS as_json,
       '{"a":1, "a":2, "b":3}'::jsonb AS as_jsonb;
--        as_json        |     as_jsonb
-- -----------------------+------------------
--  {"a":1, "a":2, "b":3} | {"a": 2, "b": 3}

SELECT '{"a": 1,   "b":2}'::json::text  AS json_text,
       '{"a": 1,   "b":2}'::jsonb::text AS jsonb_text;
--      json_text     |    jsonb_text
-- -------------------+------------------
--  {"a": 1,   "b":2} | {"a": 1, "b": 2}

json は重複キー "a" を 2 つとも残し、空白もそのまま保存します。jsonb は重複キーを後の値で上書きして 1 つに畳み込み ("a": 2 だけが残る)、空白も正規化します。json は「元の文字列をそのまま保持したい」場合に向きますが、PostgreSQL の公式ドキュメントも、ほとんどの用途では問い合わせの効率が良く重複キーの曖昧さが無い jsonb を推奨しています。

図: json は原文保持優先、jsonb は検索効率優先。重複キーの扱いと索引が使えるかどうかが実務上の分かれ目。

3. 仕組み ― 取り出す演算子と絞り込む演算子は別物

bugs テーブルに custom_fields jsonb 列を追加し、GitHub ・ Jira ・ 社内フォームから来た通知を入れます。

ALTER TABLE bugs ADD COLUMN custom_fields jsonb NOT NULL DEFAULT '{}'::jsonb;
UPDATE bugs SET custom_fields =
  '{"source":"github","severity_score":8.2,"labels":["crash","regression"],
    "reporter_meta":{"os":"macOS","browser":"Safari"}}'::jsonb
  WHERE bug_id = 1;

値を 取り出す 演算子は -> (jsonb を返す) と ->> (text を返す) で、連結すると入れ子をたどれます。

SELECT bug_id,
       custom_fields -> 'source'                AS src_jsonb,
       custom_fields ->> 'source'                AS src_text,
       custom_fields -> 'reporter_meta' ->> 'os'  AS os,
       custom_fields #> '{reporter_meta,browser}' AS browser_path
FROM bugs ORDER BY bug_id;
--  bug_id | src_jsonb  | src_text |   os    | browser_path
-- --------+------------+----------+---------+--------------
--       1 | "github"   | github   | macOS   | "Safari"
--       2 | "jira"     | jira     | Windows | "Edge"
--       3 | "internal" | internal |         |
--       4 |            |          |         |
--       5 |            |          |         |

-> は jsonb のまま返すので連結できますが、文字列として使うには最後に ->> か #>> (パス版) で text に落とす必要があります。4 行目 ・ 5 行目には custom_fields を入れていないので、既定値の空オブジェクト {} のまま、どのキーを取り出しても NULL になります。これは第 14 回で見た「NULL と空文字は違う」の jsonb 版で、custom_fields = '{}' であることと「キーが無い」ことは別の状態です。

絞り込む 演算子は、取り出す演算子とは別の操作です。@> (包含: 右辺の構造を左辺が含むか) と ? (キーがトップレベルに存在するか)、そして jsonpath を使う @? と jsonb_path_query を確かめます。

SELECT bug_id FROM bugs WHERE custom_fields @> '{"source":"github"}';         -- bug_id=1
SELECT bug_id FROM bugs WHERE custom_fields ? 'severity_score';               -- bug_id=1,2,3
SELECT bug_id FROM bugs WHERE custom_fields @? '$.labels[*] ? (@ == "crash")'; -- bug_id=1
SELECT bug_id, jsonb_path_query(custom_fields, '$.reporter_meta.os') AS os
FROM bugs WHERE custom_fields ? 'reporter_meta';
--  bug_id |    os
-- --------+-----------
--       1 | "macOS"
--       2 | "Windows"

@> と ? は json 型には存在しません。実機で '{"a":1}'::json @> '{"a":1}'::json を実行すると operator does not exist: json @> json になります。絞り込みの演算子が使えることが、ほとんどの場面で jsonb を選ぶ最大の理由です。

図: 取り出す演算子は json でも使えるが、WHERE 句で絞り込む演算子は jsonb だけの機能で、ここに GIN 索引が効く。

4. 仕組み ― GIN 索引の 2 つの演算子クラスと式インデックス

絞り込みの演算子に索引を効かせるには GIN (Generalized Inverted Index, 汎用転置索引) を使います。jsonb 用の GIN には既定の jsonb_ops と、もう 1 つの jsonb_path_ops という 2 つの演算子クラスがあり、索引の大きさと対応する演算子が違います。bug_events に 20 万行 (generate_series で生成、GitHub ・ Jira ・ Zendesk ・ 社内フォームが 25 % ずつ) を入れて確かめます。

CREATE INDEX idx_events_payload_ops     ON bug_events USING gin (payload);
CREATE INDEX idx_events_payload_pathops ON bug_events USING gin (payload jsonb_path_ops);
SELECT pg_size_pretty(pg_relation_size('idx_events_payload_ops'))     AS ops_size,
       pg_size_pretty(pg_relation_size('idx_events_payload_pathops')) AS pathops_size;
--  ops_size | pathops_size
-- ----------+--------------
--  2760 kB  | 1640 kB

jsonb_ops はキーと値のそれぞれに索引項目を作るのに対し、jsonb_path_ops はキーと値を合わせたパス全体を 1 つのハッシュにして索引項目を作ります。同じ 20 万行で jsonb_path_ops は 1640 kB、jsonb_ops は 2760 kB で、約 1.7 倍の差が実測できました。ただし jsonb_path_ops が対応する演算子は @> ・ @? ・ @@ だけで、トップレベルのキー存在を問う ? には対応しません。jsonb_ops を落として jsonb_path_ops だけにした状態で ? を実行すると、索引が使えず Seq Scan に戻ります。

DROP INDEX idx_events_payload_ops; -- jsonb_path_ops だけが残る
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM bug_events WHERE payload ? 'reporter_meta';
-- Parallel Seq Scan on bug_events (... rows=66666.67 loops=3)
--   Filter: (payload ? 'reporter_meta'::text)
-- Execution Time: 18.704 ms

jsonb_ops を作り直すと ? は索引を使うようになりますが、この実験データでは全 20 万行が reporter_meta キーを持つため、絞り込み後も全件がヒットします。索引で行を絞ってもヒープを読む量は変わらないので、Bitmap Index Scan のオーバーヘッドが上乗せされ、Seq Scan の 18.7 ms より遅い 35.9 ms になりました。索引は「対応する演算子かどうか」だけでなく「実際に絞り込めるかどうか (選択度)」の両方が揃って初めて速くなります。

-- 索引無し、既定設定 (並列ワーカー 2 本が有効)
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM bug_events WHERE payload @> '{"source":"github"}';
-- Parallel Seq Scan, Execution Time 11.356 ms

-- GIN 索引を 2 つ作った後、同じ設定で再実行 (Bitmap Heap Scan は並列化されない)
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM bug_events WHERE payload @> '{"source":"github"}';
-- Bitmap Heap Scan on idx_events_payload_pathops, Execution Time 15.954 ms

-- 並列ワーカーを無効にして、索引無し/索引ありを同じ条件 (直列) で比べ直す
SET max_parallel_workers_per_gather = 0;
SET enable_bitmapscan = off; -- 索引無し側を測るときだけ
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM bug_events WHERE payload @> '{"source":"github"}';
-- Seq Scan (直列), Execution Time 20.750 ms
RESET enable_bitmapscan;
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM bug_events WHERE payload @> '{"source":"github"}';
-- Bitmap Heap Scan (直列), Execution Time 14.773 ms
RESET max_parallel_workers_per_gather;

一方、25 % だけが一致する @> '{"source":"github"}' には、もう 1 つ別の罠があります。bug_events は約 40 MB しかなく、全体がバッファキャッシュに乗っているため、既定の設定 (並列ワーカー 2 本が有効) で索引無しの Seq Scan を測ると、2 本のワーカーが分担して走査するぶん壁時計時間は短く、実機では 11.4 ms でした。続けて GIN の 2 つの索引を両方作ってから同じクエリを実行すると、プランナはより小さい jsonb_path_ops を選びますが、Bitmap Heap Scan は並列化されないため 16.0 ms となり、索引を作った方が遅くなりました。これは索引の作りが悪いのではなく、並列 Seq Scan という「索引以外の近道」が先に競合相手として現れたために起きる逆転です。並列ワーカーの有無をそろえて公平に比べるため SET max_parallel_workers_per_gather = 0; で両方を直列実行に揃えると、索引無しの Seq Scan は 20.8 ms、索引ありの Bitmap Heap Scan は 14.8 ms となり、索引の方が約 1.4 倍速いという、小さいながら安定した差が見えます。索引の効果を測るときは、選択度だけでなく「索引を使わない側が並列化で得をしていないか」も揃えて比べる必要があります。

クエリ一致率索引無し索引あり倍率
@> '{"source":"github"}' (既定設定)25 %11.4 ms (Parallel Seq Scan)16.0 ms (path_ops, 直列)1.4 倍遅い (索引無し側が並列で得をした)
@> '{"source":"github"}' (並列無効)25 %20.8 ms (Seq Scan, 直列)14.8 ms (path_ops, 直列)約 1.4 倍速い (公平な比較)
? 'reporter_meta'100 %18.7 ms (Seq Scan)35.9 ms (jsonb_ops)1.9 倍遅い

範囲検索 (> や BETWEEN) は GIN の @> では表現できません。severity_score のような数値を範囲で絞るには、キーを取り出して型変換した式に btree の式インデックス を作ります。

CREATE INDEX idx_events_severity_btree
  ON bug_events (((payload->>'severity_score')::numeric));
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM bug_events WHERE (payload->>'severity_score')::numeric > 9.5;
-- 索引無し: Parallel Seq Scan, Execution Time 19.589 ms (一致 9161 / 200000, 約 4.6 %)
-- 索引あり: Bitmap Index Scan,  Execution Time  4.046 ms (約 4.8 倍速い)

図: 同じ 20 万行で jsonb_ops は 2760 kB、jsonb_path_ops は 1640 kB (実測)。対応する演算子の範囲も違う。

5. どこで壊れるか ― 形が揃っているのに jsonb のまま運用する

jsonb の自由さは「形が決まっていない」間だけ価値があります。形が決まった後も jsonb に留め続けると、2 つの問題が起きます。

1 つ目は外部キーと CHECK 制約が届かないことです。 custom_fields->>'source' の値は github ・ jira ・ zendesk ・ internal の 4 つしかありませんが、jsonb の中の値に直接 FK は張れません。誤字の "gihub" が入っても、データベースは何も教えてくれません。

2 つ目は、実際には形が揃っているのに気づかないことです。 bug_events の 20 万行すべてで、トップレベルのキーの組を集計すると、次のようにただ 1 種類の形しかありませんでした。

SELECT (SELECT array_agg(k ORDER BY k) FROM jsonb_object_keys(payload) k) AS key_shape, count(*)
FROM bug_events GROUP BY 1 ORDER BY 2 DESC;
--                   key_shape                   | count
-- ----------------------------------------------+--------
--  {labels,reporter_meta,severity_score,source} | 200000

この問い合わせは「正規化すべき兆候を見つける」ための具体的な一手です。もし上位 1 ・ 2 種類の形が行数の大半を占めるなら、その形はもう決まっていると判断してよく、jsonb に留める理由は薄れます。実際の運用では、連携先の種類が 10 種類くらいに収まった後も jsonb のまま放置され、後から「source だけ絞り込みたい」「source に外部キーを張りたい」という要求が出て詰まる、という流れをよく見ます。

図: キーの組をグループ化して種類数を数えるだけで、形が決まっているかどうかが見える。

6. シニアの書き方 ― 判断の基準と列への戻し方

シニアの判断基準は「よく絞り込む条件になるキー」と「制約で守りたいキー」を、jsonb の外に出すことです。やめるのではなく、jsonb はそのまま残し、その上に式を使った 生成列 (GENERATED ALWAYS AS ... STORED) を重ねれば、JSON を送る側のコードは変えずに、受け取る側だけで列化できます。

CREATE TABLE event_sources (source text PRIMARY KEY);
INSERT INTO event_sources VALUES ('github'),('jira'),('zendesk'),('internal');

ALTER TABLE bug_events ADD COLUMN source text
  GENERATED ALWAYS AS (payload->>'source') STORED;
ALTER TABLE bug_events ADD CONSTRAINT fk_events_source
  FOREIGN KEY (source) REFERENCES event_sources (source);

SELECT source, count(*) FROM bug_events GROUP BY 1 ORDER BY 1;
--  source   | count
-- ----------+-------
--  github   | 50000
--  internal | 50000
--  jira     | 50000
--  zendesk  | 50000

source 列は jsonb から自動的に計算され、手で更新する必要がありません。この列に FK を張った瞬間、"gihub" のような誤字は event_sources に存在しないので INSERT 時に拒否されます。jsonb のままでは不可能だった制約が、列に昇格させた瞬間に戻ってきます。

配列のように「1 行の中に複数件ある」構造を取り出したい場合は、PostgreSQL 17 以降の JSON_TABLE が使えます。labels 配列を行に展開する例です。

SELECT jt.*
FROM bugs b, JSON_TABLE(b.custom_fields, '$' COLUMNS (
    source text PATH '$.source',
    severity_score numeric PATH '$.severity_score',
    NESTED PATH '$.labels[*]' COLUMNS (label text PATH '$')
  )) AS jt
WHERE b.bug_id = 1;
--  source | severity_score |   label
-- --------+----------------+------------
--  github |            8.2 | crash
--  github |            8.2 | regression

JSON_TABLE は jsonb_array_elements と LATERAL の組み合わせでも同じことができますが、COLUMNS 句に型を明示できるので、取り出した時点で型チェックが入ります。PostgreSQL 16 以前では JSON_TABLE 自体が無いので、jsonb_array_elements_text と LATERAL を使う必要があります。

まとめると、判断の基準は次の 3 つです。(1) 連携先ごとに形が違い、今後も増え続けるなら jsonb のまま。(2) あるキーで頻繁に絞り込む、または集計するなら、式インデックスか生成列で列に出す。(3) 値の範囲が決まっている、または他のテーブルと整合性を取りたいなら、生成列 + FK か CHECK で列に昇格させる。jsonb は「構造を決めないための道具」であって、「構造を決めた後も検索や制約を諦めるための道具」ではありません。

図: 形が決まらない間は jsonb、絞り込みが増えたら式インデックス、制約が要るキーは生成列に昇格させる。

アセンブラとコンパイラ ― ビット列を作る前に、まずエミュレータで確かめる

人間が書いた add r1, 5 のような文字列から、CPU が読む 16 bit のビット列を作る仕組みと、それを FPGA に焼く前に安く確かめる道筋

この回の前提: 第 10 回 命令セットの設計、第 13 回 分岐・ジャンプ・スキップ・サブルーチン

CPU がどれだけ正しく動いても、人間が 16 bit のビット列を手で並べてプログラムを書くのは現実的ではありません。アセンブラは、add r1, 5 のような読みやすい文字列を、CPU が読む 2 進数のビット列に機械的に変換する道具です。この回では、rj32 が実際に使っている customasm という汎用アセンブラの仕組み、ラベルの番地をどう計算するか、呼び出し規約の約束ごと、そして回路やハードウェアの手前でソフトウェアのエミュレータを使って先に確かめる、という開発の順序を見ていきます。

1. アセンブラがビット列を作る仕組み

第 10 回で見たように、rj32 の命令は 16 bit のビット列の中に、命令の種類 (op)・レジスタ番号 (rd, rs)・即値といった情報を詰め込んでいます。アセンブラの仕事は、人間が読み書きしやすい文字列 (add r3, 15 のような 1 行) を、この 16 bit のビット列に機械的に変換することです。rj32 は自分でアセンブラを書くのではなく、customasm という汎用のアセンブラに、cpudef.asm という「rj32 のルール」だけを書いたファイルを読ませる、という作り方をしています。

cpudef.asm には 2 種類のルールがあります。1 つは reg や op のような対応表 (レジスタ名 r3 は数字の 3、即値形式の加算命令 addi は番号 0 など)。もう 1 つは fmt_ri6 のような組み立て方のルールで、rd`4 @ value`6 @ op`4 @ 0b11 のように「この順番でビットを並べてくれ」と書いてあります。`4 は「4 bit に切り詰める」、@ は「隣に並べる (連結する)」という意味です。

図: 文字列 → 対応表で名前を数に変換 → ルールに従って並べる → 16 bit のビット列になる。

この作り方の利点は、アセンブラ本体 (customasm) は rj32 のことを何も知らなくてよいという点です。rj32 の命令セットが変わっても、変更するのは cpudef.asm だけで済みます。

2. ラベルと再配置 ― 番地をどう計算するか

jump mylabel や call fibonacci のように、プログラムはまだ番地が決まっていない名前 (ラベル) へ飛びます。ラベルが実際に何番地かは、プログラム全体を一度並べてみるまで分かりません。そこでアセンブラは、まず全命令を仮に並べて各ラベルの番地を確定させ (1 回目の通過)、その番地を使って実際のジャンプ命令のビット列を組み立てます (2 回目の通過)。

さらに rj32 のジャンプは絶対番地ではなく相対距離を命令に埋め込みます。cpudef.asm の定義は jump {value} => fmt_i11 jumpi, value - pc - 1 です。value は飛び先の番地、pc はこの jump 命令自身が置かれる番地で、「飛び先 − 自分の番地 − 1」という式が埋め込まれます。この「−1」は、rj32 の実行時に pc がジャンプ命令自身の番地ではなくすでに次の命令の番地に進んだ後の値であるために必要な補正です。アセンブラが計算に使う「組み立て時の pc」と、ハードウェアが実行時に使う「進んだ後の pc」がずれているので、この 1 だけ合わせてあげる必要があります。

図: 相対ジャンプは「実行時に pc が既に進んでいる分」を見越して −1 している。

もう 1 つ、アセンブラが番地を決める上で重要なのが#bankdef です。cpudef.asm はプログラム用の code バンク (0x0000 から)、初期値付きデータ用の data バンク (0x8000 から)、初期値なしのデータ用の bss バンクを別々に定義しています。これは第 09 回で見たハーバード・アーキテクチャ (命令メモリとデータメモリが別) を、アセンブラの番地の付け方としてそのまま反映したものです。

3. 呼び出し規約 ― 関数を呼ぶときの約束ごと

プログラムが複数の関数に分かれていると、関数を呼ぶ側 (caller) と呼ばれる側 (callee) の間で「どのレジスタに何を入れるか」を決めておかないと、互いのデータを壊してしまいます。この約束ごとが呼び出し規約 (calling convention) です。rj32 の docs/instructions.md は、16 本あるレジスタのうち r0 だけは特別で、残りの使い方を次のように定めています。

図: レジスタごとに「誰が保存するか」の役割が決まっているので、関数をまたいでも値が壊れない。

call 命令は jump と同じ相対番地の計算をしつつ、同時に「戻ってくるべき番地」を r0 に保存します (cpudef.asm の定義では jump {value} => fmt_i11 jumpi, value - pc - 1 に対し、call も同じ fmt_i11 形式を使って同様の番地計算をします)。関数から戻る return は jump ra という擬似命令にすぎません。この「呼び出し時に戻り先を自動で覚える」「戻る時はただ r0 へジャンプするだけ」というシンプルな仕組みの上に、ABI (呼び出し規約) という約束ごとが乗っています。

4. Go から rj32 へ ― NanoGo という道

ここまでは人間が直接アセンブリを書く前提でした。rj32 の README には、Go 言語のサブセットを rj32 向けにコンパイルする NanoGo という別プロジェクトがあることが書かれています。この回では NanoGo の内部構造までは踏み込みませんが、重要なのはどこまで積み上げても、最後に出てくるのは第 1 節で見た同じ 16 bit のビット列だという点です。

図: 高級言語を使っても、アセンブラが約束するビットの詰め込み方は変わらない。

この「上に何を積んでも、最後は同じ契約に合わせる」という構造は、第 1 節のアセンブラ自体が「cpudef.asm というルールさえ守れば customasm は rj32 を知らなくてよい」という構造と同じ考え方です。

5. エミュレータで先に確かめる

rj32 には、テキストのアセンブラとは別に、dig/assembler.dig という Digital の回路として作られた「Assembler」もあります。これは dest・src・value・tworeg といった入力と、add・move・jump といった選択を GUI 上で指定すると、回路のロジックが命令のビット列を組み立てて inst として出力する仕組みで、テストプログラムを 1 命令ずつ手で組み立てるのに使われます。テキストのアセンブラ (customasm) が「ファイルにまとめて書いて一括変換する」道具なのに対し、この回路は「今、この 1 命令だけを対話的に組み立てる」道具で、使う場面が違うだけで、やっていること (名前を数に変換し、決まった順序でビットを並べる) は同じです。

図: テキストのアセンブラと回路のアセンブラは、使う場面が違うだけで同じ仕事をする。

プログラムが書けたら、次に確かめる場所が重要です。rj32 の開発では、FPGA に焼く前に、まずソフトウェアのエミュレータで動作を確かめるという順序を踏みます。Makefile の testemu という手順は、これを 1 行で表しています。

図: customasm の出力をパイプでそのままソフトウェアエミュレータ emurj に渡し、実機 (FPGA) より先に動作を確かめる。

ソフトウェアのエミュレータは、FPGA の合成 (第 20 回) や実機への書き込みに比べて圧倒的に速く繰り返せます。命令の解釈を間違えていないか、ラベルの番地計算を間違えていないかといったバグは、わざわざ回路を合成してハードウェアで確かめるより先に、ソフトウェアで安く・速く・何度も試して潰しておくのが合理的です。

6. 実装のポイント

(1) 相対番地の「どちらの pc を使うか」を取り違えない。 第 2 節で見た value - pc - 1 の「−1」は、rj32 の実行時の pc がジャンプ命令自身の番地ではなく、すでに次の命令の番地に進んだ後の値であることに由来します。もし CPU 側のパイプライン段数や pc の更新タイミングを変えたら、アセンブラ側のこの補正値も合わせて見直す必要があります。ここは CPU 側の設計とアセンブラ側の計算式が暗黙に結びついている、見落としやすい箇所です。

(2) 即値がはみ出すと、アセンブラが命令をこっそり増やす。 fmt_ri6 の即値は 6 bit (−32〜31) しか入りません。cpudef.asm はこの範囲をはみ出す値が来ると、自動的に imm 命令を 1 つ前に挿入して補います。つまり「定数を少し大きくしただけ」で生成される命令の数が増え、それより後ろにあるラベルの番地がすべて 1 つずれる可能性があります。これが、アセンブラがラベルの番地を 1 回の通過では決められず、何度か計算をやり直す必要がある理由です。

(3) 先に安く確かめる場所を選ぶ。 命令の意味やラベルの計算を間違えた時、その発見場所が FPGA の実機であるほど、1 回の確認にかかる時間 (合成・配置配線・書き込み) が長くなります。customasm | emurj のようにソフトウェアだけで完結する確認を先に通し、問題が無くなってから実機に進む、という順序を守ることが、回路設計そのものと同じくらい重要な実装上の判断です。

p 系を毎回借りないと DeepEP を検証できない、という前提を測って崩す

0この回の問い

ここまでの回で emulator は動きました。ただし動かした場所は H100 を 3 台です。H100 は on-demand の在庫がゼロで Capacity Block しか取れず、1 日単位で数千ドルかかります。これでは DeepEP を組み込む側のライブラリ ― たとえば推論エンジン ― が「取り込んだら壊れていないか」を日常的に確かめられません。CI に載せることもできません。

そこで問いは 1 つです。検証はどこまで安いハードウェアに落とせるのか。

この問いは 2 つの独立した門に分かれます。どちらも測れるので、意見ではなく測定で答えます。

門問い測り方
ADeepEP のカーネルは、その GPU 向けにコンパイルできるのかGPU は要らない。コンパイラが拒否するかどうかで分かる
Bその GPU で NCCL の device API と GIN 経路が存在するのか実機が必要。1 台で 20 分

門 A が閉じているなら、その GPU は設定では届きません。門 A が開いていて門 B が閉じているなら、動かす手段が無い。両方開いていて初めて候補になります。

1門 A: どの GPU 向けにコンパイルできるか

ここで測り方を間違えると意味のない答えが出ます。最初に書いた測定は、カーネルのヘッダを #include して各 arch でコンパイルするものでした。全部通りました。そして意味がありませんでした。ヘッダを include しても template は実体化されず、命令が出るのは実体化のときだからです。

正しい測り方は DeepEP 自身が持っています。DeepEP はカーネルを実行時にコンパイルする仕組み (JIT) を持ち、template 引数を埋めたソースを生成します。そのソースはキャッシュに残っています。

#include <deep_ep/impls/hybrid_dispatch_unordered.cuh>
using namespace deep_ep::elastic;
static void __instantiate_kernel() {
    auto ptr = reinterpret_cast<void*>(&hybrid_unordered_dispatch_impl<true, false, true, false, true,
                                        24, 4, 4, 4, 3, 1, 7168, 56, 1024, 192, 6, 128, 8, ...>);
}

これを JIT 自身の flag で、arch だけ変えてコンパイルします。flag も推測すると失敗します (推測したときは全 arch が --expt-relaxed-constexpr の不在という同じ理由で落ち、arch の違いは何も見えませんでした)。DeepEP のソースから読んで揃えます。

ターゲットGPU とインスタンス結果
sm_80A100 / p4d拒否: Feature 'elect' requires .target sm_90 or higher
sm_86A10G / g5同じ理由で拒否
sm_89L4, L40S / g6, g6e同じ理由で拒否
sm_90H100 / p5通る (490,520 byte)
sm_100B200 / p6通る (395,264 byte)
sm_120RTX PRO 6000 Blackwell / g7e通る (394,880 byte)

拒否の理由は 4 つに集約されます。elect、.bulk_group、.cluster scope、.mbarrier::complete_tx::bytes。いずれも TMA と cluster 単位の同期で、Hopper 以降にしかありません。

「安い GPU 向けの逃げ道はないのか」と探すと、あります。そして使えません。DeepEP の setup.py には DISABLE_SM90_FEATURES という分岐があり、コメントは「A100 を優先」「FP8 と launch method と TMA を切る」と書いてあります。その分岐の末尾はこうです。

# Disable internode and low-latency kernels
assert False, 'Not implemented'

さらにこのフラグを見ているのは legacy カーネルの 3 ファイルだけで、V2 (elastic) では 0 ファイルです。つまり g5 や g6e に届かせるのは 非 TMA 版の dispatch と combine を書くという上流の実装作業で、設定の話ではありません。

2門 B: 安い GPU に NCCL の device API はあるのか

コンパイルが通っても、NCCL の device API が無ければ GIN 経路は作れません。ここは実機でしか分かりません。2 つ測ってあります。

GPUcompute capabilitydeviceApiSupport
Tesla T47.5no ― device API がそもそも無い
H1009.0yes
RTX PRO 6000 Blackwell12.0yes

そして plugin を積むと、Blackwell でもこうなります。

  deviceApiSupport    : yes
  ginType             : proxy(2)
  railedGinType       : proxy(2)
  ginConnectionType   : full
  hostRmaSupport      : yes
  gin backends usable : proxy(2)

門 B も開きました。

31 枚の GPU で 3 ランク動くのか

ここでもう 1 つ壁があります。DeepEP の scale-out 経路は rail team が 2 以上でないと走りません。3 ホスト構成ならホスト数がそのまま rail になりますが、安い GPU は 1 枚しか載っていません。1 ランクでは scale-out に入りません。

回避策は第 7 回で確認済みの手です。NCCL_HOSTID をランクごとに変えると、NCCL は同じ箱の中のプロセスを別ノードだと信じます。あとは 3 プロセスが 1 枚の GPU を共有できるかどうかです。

ここも測り方に注意が要りました。--num-processes 3 のように 1 プロセスから 3 つ子を作る形では駄目です。NCCL_HOSTID はプロセスごとに 1 回読まれるので、子は全員同じノード名を名乗り、rail は 1 のままになります。ランクごとに別プロセスを立てて、それぞれに違う NCCL_HOSTID を渡す必要があります。

H100 1 台で試すと動きました。そして g7e 1 台でも動きました。DeepEP がビルドされ、plugin が bind し、proxy(2) が立ち、dispatch カーネルが走り、simulator のログが 3,426 行流れます。3 ホスト構成とまったく同じ地点まで到達します。

この回の答え

DeepEP の検証は g7e.2xlarge 1 台に畳めます。GPU 1 枚、on-demand、EFA 不要、Capacity Block 不要。3 ホストの H100 で見えることと同じことが見えます。

そして残っている未解決のバグ (dispatch が完走せず、受信カウントが 0 のまま待つ) が 1 台でも 3 台でも、H100 でも Blackwell でも同一に再現します。ネットワークの問題ではないことがこれで確定し、しかも安い箱で追えるようになりました。

4ハードウェアの階段

検証の粒度ごとに必要なハードウェアを並べると、こうなります。

GPU なし ― ノート PC や普通の CI ランナー

fork のヘッダ 3 本の性質、受理規則のモデル検査、simulator 自身の正しさと異常系、plugin が NCCL の契約を守っているか、bit 詰めの証明。214 万件の assertion と 3 つの網羅列挙と 17 件のソルバ問い合わせが、NCCL のインストールもネットワークもなしで通ります

GPU 1 枚、sm_90 以降 ― g7e.2xlarge または p5.4xlarge

DeepEP の実カーネルを simulator の上で。3 ランクは 1 枚の GPU を共有し、NCCL_HOSTID がノード分割を演じます。EFA は使いません

GPU 1 枚、sm_89 以前 ― g5, g6, g6e

届きません。カーネルが TMA と cluster 同期を無条件に使い、fork の逃げ道は未実装。非 TMA 経路を書くという上流作業になります

実 EFA のあるクラスタ

EFA そのものと性能。ここは emulator の対象外だと最初から宣言してある領域で、マージ判定に使うものではありません

デモ: 何を確かめたいかで必要なハードウェアが決まる

確かめたい対象を選ぶと、必要な最小のハードウェアと、その理由が出ます。

5CI に何を載せるか

階段の 1 段目はそのまま CI に載ります。GPU の要らない層で、しかも回帰として意味のある層です ― bit 詰め、part の幾何、signal 予算の算術、受理規則。DeepEP の fork に当てるパッチは tests/cpp/Makefile を fork の中に置く形にしてあるので、ワークフローに 1 行足すだけになります。

層ハードウェアCI への向き
ホストのみなしコミットごとの門に向く。速く、決定的で、GPU の在庫に依存しない
GPU 1 枚 (sm_90+)g7e.2xlarge など夜間ジョブか手動実行に向く。GPU が要る以上コミットごとは重い
実 EFAp5 など門にしない。ファブリックはマージ判定の対象ではない

言い換えると、「DeepEP を触ったら H100 を借りる」から「DeepEP を触ったらまず GPU なしで 214 万件、必要なら 1 枚の安い GPU で実カーネル」に変わります。

6安い箱で測って初めて出た落とし穴

借り物のワークステーション 1 台で同じことをやると、専用に立てた箱では起きない問題が並んで出ました。どれも「環境の些事」に見えて、実際には測定を静かに間違わせるものです。

症状本当の原因
全 arch が同じ理由でコンパイルに失敗ヘッダを include しただけで template を実体化していなかった。arch の違いは何も測れていなかった
次も全 arch が同じ理由で失敗コンパイル flag を推測していた。DeepEP の JIT が使う --expt-relaxed-constexpr が無かっただけ
CUDA のヘッダが pip で入らないCUDA 13 の wheel は PyPI では 1.2 kB の空箱。名前はあるが中身が無い
ヘッダはあるのにビルドが nv/target で落ちる見つけた cuda_runtime.h は Triton 同梱の部分的なコピー。「最初に見つかった header」と「使える include ツリー」は別物
コンテナから CUDA を取り出したのに空/usr/local/cuda も、その中の include も symlink。docker cp はリンクだけ複製する
抽出手順が丸ごと飛ばされるスキップ判定に使うファイルに echo "" で改行だけ書いていた。test -s は 1 バイトを「中身あり」と見る
probe が古い NCCL のシンボルで落ちる既知の罠の再発。CUDA ヘッダ目的で torch を入れたら NCCL が 2.31.2 から降格した。前に記録したはずの罠に、自分で作った手順で落ちた

最後の 1 つが、この回でいちばん教訓のあるところです。一度記録した罠は、記録しただけでは防げません。いま NCCL の版はインストール手順の中で assert され、2.31 を下回ったらその場で止まります。記録ではなく検査に変えて初めて、同じ穴に落ちなくなります。

CPU の外側には、メモリだけでなくキーボードや画面、タイマーといった「デバイス」もつながります。デバイスとのやり取りで最初に出てくる問いは、「デバイスの準備ができたことを CPU はどう知るか」です。答え方は大きく 2 つあります。CPU が自分から何度も聞きに行くポーリングと、デバイスの方から CPU に声をかける割り込みです。この回では、両者の違いと、割り込みが起きた瞬間に CPU が何を守らなければならないかを、rj32 と Digital 付属のサンプル CPU を手がかりに整理します。

1. 聞きに行くか、呼ばれるまで待つか

結論を先に言うと、デバイスの準備を知る方法は「CPU が繰り返し聞きに行く (ポーリング)」か「デバイスが CPU に声をかける (割り込み)」の 2 つしかありません。前者は作るのが簡単ですが CPU の時間を無駄にし、後者は CPU の時間を節約できますが、呼ばれた瞬間に何を守るかという新しい難しさを持ち込みます。

キーボードのキーが押されたかどうかを知りたいとします。ポーリングなら、CPU は「押されたか」「押されたか」と毎クロックのように聞きに行くループを回します。割り込みなら、CPU は他の仕事を続け、キーボード側が「押された」という信号線を立てたときだけ CPU がその仕事を中断して対応します。

図: ポーリングは聞きに行く時間そのものが無駄、割り込みは中断と復帰の正しさが新しい課題になる。

2. デバイスをアドレスとして扱う

CPU がデバイスとやり取りする配線を、ロード・ストア命令が使うアドレス空間の一部に割り当ててしまう方法をメモリマップト I/O と呼びます。Digital 付属のサンプルでは GPI (汎用入力) / GPO (汎用出力) のような部品が用意されていて、readSelect.dig がアドレスの一部を見て「このアドレスは RAM ではなくこのデバイス宛てだ」と振り分けます。実際にこのサンプル CPU のアセンブリ (ProcessorIntr.asm) では、キーボードをポート 0xe、表示端末をポート 0xf として in/out 命令で読み書きしています。

一方 rj32 は、load/store が使う通常のメモリ空間とは別に、rcsr rd, csr/wcsr csr, rd という専用の命令で読み書きする、最大 16 個の CSR (control and status register) という小さな空間を持たせる設計を選んでいます。docs/instructions.md によれば、CSR はメモリのページ/バンク、割り込み、ユーザーモードからのレジスタ読み書きなどを制御する想定ですが、この命令自体はまだ実装されていません。

図: デバイスへのアクセスを「決まった番地・番号」に対応づける点は共通、経路を分けるかどうかが設計判断。

3. CPU の時間はどちらが得か

Digital のマニュアルは、キーボード部品の出力の 1 つをav (available, データあり) と呼び、「この出力は割り込みを起こすために使える」と説明しています。av をポーリングで読みに行くか、av を割り込み線に直結するかで、CPU の使われ方が大きく変わります。

ポーリングでは、CPU は av を読みに行く命令を本来の仕事の間に挟み込み続けます。キーが押される頻度が低いほど、その確認の大部分が「まだ押されていない」という無駄な答えに終わります。割り込みでは、CPU は av を見に行く必要が無く、av が実際に立った瞬間だけ、ハードウェアが自動的に CPU の実行を中断させます。

図: イベントが稀なら割り込みが得、イベントが頻発するならポーリングのほうが単純で済む場合もある。

4. 割り込みが起きた瞬間に何を守るか

割り込みの本当の難しさは「中断してよい場所」を正しく選ぶことにあります。rj32 の imm/addc/subc は、次の 1 命令に渡すための状態 (上位ビットやキャリー) を抱えたまま次のクロックに進む「接頭辞命令」です。docs/instructions.md は「これらの命令と、それが修飾する命令の間に割り込みが起きると状態が失われるため、その状態が完全に渡り終わるまで割り込みを無効にする」と明記しています。

rj32 はレジスタの読み書きを行う rets 命令 1 つで割り込みの出入りを兼ねています。K (kernel mode) フラグが立っているかどうかで、使うレジスタ集合 (ユーザー用とシステム用の 2 組) と PC がまるごと切り替わります。ユーザーモードで実行中の命令が「割り込み要求線が高い」「割り込みが有効」「その命令が中断可能」という 3 条件を満たすと、その命令は rets であるかのように振る舞い、K を立てて実行場所をシステム側に切り替えます。このとき PC を進めないのが肝心な工夫で、システム側から rets で user モードに戻ったときに、中断されたはずの命令そのものから再開できます。

図: rets 1 つで入りと戻りを兼ね、K フラグがレジスタ集合と PC をまとめて切り替える。PC を進めないことが復帰の正しさを支える。

5. rj32 と Digital サンプルの設計比較

rj32 と Digital 付属のサンプル CPU は、同じ問題 (割り込みへの出入り) を別の形で解いています。rj32 は専用の出入り命令を持たず、既存の rets を使い回して K フラグを反転させるだけです。これに対しサンプル CPU は ProcessorIntr.asm に見るとおり、enteri (割り込みに入る)・leavei (割り込みから出る準備)・reti (割り込みから戻る) という専用の 3 命令を持ち、割り込みサービスルーチンを固定アドレス (.org 2、つまりアドレス 2 番) に置きます。

サンプル CPU の回路 (ProcessorIntr.dig) には Bank-FF という部品があり、割り込み中だけ別のレジスタバンクに物理的に切り替えます。これは rj32 の K フラグによるユーザー/システム用レジスタの切り替えと同じ発想で、どちらも「割り込みハンドラがユーザーのレジスタの値を壊さないようにする」という同じ目的を、専用のレジスタバンクをもう 1 組持たせることで解いています。

図: 出入りの命令数は違うが、別レジスタ集合を持つという解決の骨格は同じ。

6. 実装のポイント

接頭辞命令の途中は必ず割り込みを禁止する。 rj32 の imm/addc/subc のように、次の 1 命令に状態を渡す命令がある設計では、その状態がレジスタのどこにも保存されていない (次の命令に渡されるだけの一時的なもの) ことが多く、途中で割り込むと静かに失われます。rj32 の docs/instructions.md が「このため割り込みを無効にする」と明記しているのは、拡張命令を持つ ISA を作るときに必ず踏む落とし穴だからです。

別レジスタバンクか、スタック退避かは速度と回路規模のトレードオフ。 rj32 も Digital サンプルも別バンク方式を選び、割り込みが起きても現在のレジスタの値をどこにも書き出さずに済むようにしています。退避の命令が要らない分、割り込みへの応答が速くなりますが、レジスタをまるごと 2 組持つのでレジスタファイルの回路は単純に 2 倍になります。小さな CPU でバンクを増やせない場合は、ソフトウェアでスタックに退避する方式を選ぶしかなく、その分応答は遅くなります。

固定ベクタは「どのデバイスが呼んだか」を教えてくれない。 rj32 (CSR 実装後の想定) も Digital サンプルも、割り込みが起きると決まった 1 つのアドレスにジャンプするだけで、複数のデバイスが同じ割り込み線を共有している場合、どのデバイスが原因かはハンドラが CSR やメモリマップト I/O を読みに行って自分で調べる必要があります。これは「ベクタ化されていない割り込み」の典型的な制約で、デバイスの数が増えるほどハンドラ内の判定コストが増えていきます。

レベル信号はどこかで確認・解除する。 Keyboard の av のような「データがある間ずっと高い」信号を割り込み線にそのまま使うと、ハンドラが読み出しを終えて av が下がるまで、割り込みがずっと要求され続けます。ハンドラの最初で必ず該当のデータを読み出す (または専用のクリア操作をする) ことを保証する設計にしないと、無限に同じ割り込みが再発してハンドラから抜けられなくなります。

図: av のようなレベル信号は、読み出して下げるまで解除されないことを設計に組み込む必要がある。

図 1: allowlist は費用の道具ではなかった

ただし完全に消えたわけではありません 許可の 6 要素のうち消えたのは「呼んでよいモデルの集合」だけです。残る 4 つ (親の予約、上限額、残り深さ、費用の帰属先) は予約の中身として必須のまま残ります。 理由は 2 つで、再入の停止 (深さ 0 になったら仮想名を拒否) と木の整合 (子の合計が親の上限を超えない) は、監査ラベルでは執行できないからです。 そしてその発行者は「予約を作る瞬間の課金層」以外にありえない — 3 名のうち 1 名が 「発行主体が不在で原理的に決まらない」と書いていましたが、再分類の後では答えが一意に定まりました。

4. 最後の検証で見つかった、いちばん重い欠落

設計から機能が 1 つ黙って消えていました 「答えを引き換える仕組み」が、危険な部分と一緒に機能ごと消えていました。 安いモデル 2〜3 個が同じ実モデルに解決したとき、同じ入力に同じモデルへ 2 回払います。 しかも退化配線で全分類を単一の仮想名に集約したので、ぶつかる確率はむしろ上がっています。 現状は記録なき穴です。
ただし直し方は「答えを再利用する」ではありません 2 者の検証が一致した点です。同じモデルの答えを 2 票として数えると、それは独立した 2 票ではなく、 測定した quorum とは別の方策になります。だから答えの再利用では解決しません。 正しい既定値は「証明書を作る時点で、同じ実行プロファイルの重複を拒否する」ことです。 つまり穴の直し方は運用ではなく証明書の生成規則にあります。

4b. 以前合意していたのに、設計から落ちていたもの (5 件)

これは「潰れていない指摘」とは別の category です。一度は合意されたのに、設計をまとめる過程で 静かに抜け落ちたものです。抜けたことに誰も気づかないので、上の穴リストよりも危険です。

落ちたものいつ合意したか落ちたことで何が壊れるか
席の要求がベクトルであること 「席はスカラーでは表せない」と実測で確定 (入力長・最大出力・KV キャッシュ・要求クラス) 窓口が acquire(モデル, 期限) だけになり長いリクエストと短いリクエストを区別できない。 過剰な受け入れを防げない
再入の禁止そのもの 「親を持つリクエストが仮想名を対象にしたら課金層が無条件で拒否」 残り深さは止まることを保証するだけで、子が仮想名を対象にすること自体を禁止していない。 深さが有限でも再入で余計な課金は起こせる
予約が対象を束縛すること 実行プロファイル・証明書 id・主体・費用帰属・見積り id を予約が持つこと 予約の型にこれらが無く、予約を作る呼び出しに証明書も見積りも渡されていない。 字面どおりでは「版が一致するときだけ通す」が実装不能
分類器のキャッシュを無効化すること 「別モデルのキャッシュ回答が返ると精度床は測定と無関係な分布のものになる」 責務表・不変条件・穴リストのどこにも書かれていない。 一度は「見落とされやすい実在の穴」として指摘されていた
予約に期限と回収があること 「予約が漏れると最終的に全部拒否になる」 席には期限があるのにお金の予約には期限が無い。 判断層が途中で死ぬと予約が残り続け、やがて全部拒否に進む
さらに 2 件、宣言と穴リストが正面から矛盾しています 1. 不変条件は「確定と取消は id で冪等」と無条件に宣言していますが、 穴リストは「プロセスを跨ぐ冪等性は持たない」と書いています。 どちらかが嘘で、宣言の範囲を「単一プロセス内」に限るか、v1 に戻すかの二択です。
2. 突合は検出だけが割り当てられ、是正が誰にも割り当てられていません。 差額を誰の財布に計上するか、いつ新規の予約を止めるか、誤請求を誰が飲むかが未決です。

5. 実装の順番 (検証済み)

[A] 予約の木と fail-closed な予約      ← 起点。全員がこの型に依存
 ├→ [C] quorum の枝ごとの独立予約と取消  ← A を最初に酷使する消費者。ここで意味論が確定する
 ├→ [B] 一致の判定規則の pin と適用域ゲート ← 自由記述は quorum 経路を拒否
 └→ [D] 日次の突合                      ← A と C の履歴が無いと突合対象が無い。最後
[E] 証明書外経路への監査ラベル           ← A と疎結合。並走でよい

手戻り最小の順は A → C → B → D で、E は並走。C を B より先にする理由は、 取消と実際の現金の乖離が C で初めて具体化し、D の差分レポートの形が C の出力に依存するからです。

upstream の返答を待たずに始められるもの A・B・C・E の 4 件は完全に着手可能。D だけは分割で、台帳の書き出しと窓の論理と差分の形は着手でき、 枝単位の provider 明細の対応付けと差分の解釈だけが待ちになります。
配備の条件が 1 つあります (着手条件ではありません) 「Envoy の再試行予算をゼロ」は開発を止めませんが、v1 にトラフィックを流す前に必須です。 通信層の再試行が生きたまま流すと「1 回の呼び出し = 1 つの予約」が通信層で破られます。

8. 文言の修正が 2 箇所

修正 1: 動かせない前提の書き方 「課金は fail-closed で原子的」は台帳については真、実際の現金については偽です。 前提の文言を「原子性の対象は台帳」に書き直さないと、次の検討で誰かが偽の不変条件を再導出します。 実際の現金の上限は、上の Issue 2 件が返るまで存在しません。
修正 2: 必要な席の数 「quorum の最小数に届かなければ棄権」の最小数を N (全部) と明記する必要があります。 N 未満で走った結果は証明書に pin した構成と違うので、証明書経路の結果として返してはいけません。 ここを曖昧にすると「容量の不足がモデル選択を変える」を実質的に許すことになります。

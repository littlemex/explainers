tierbook の構成
stratoclave・vLLM Semantic Router との実際の接合

この文書が答えること。質問をどのモデルに回すかを決める仕組みは、実際には 3 つの別プロジェクトが 3 つの別の仕事をして成り立っています。どれが何を持っていて、 境界にどんな項目が流れるのかを、実際のコードの名前で示します。

図はすべて手元の実物を読んで描いています (stratoclave v1.5.0、tierbook の依存グラフは計算した実測、vLLM 側の設定は 実際に生成される構造)。想像で描いた線は 1 本もありません。

1. 登場する 3 つのプロジェクト ― 仕事が重なっていません

gateway

stratoclave

お金の正本を持つ汎用 AI Gateway。誰の依頼か確認し、予算を先に押さえ、 呼び出し、実際の使用量で精算し、台帳に追記します。

品質は主張しません。設計文書に Quality is NOT asserted here と明記されています。

router

vLLM Semantic Router

依頼を見て分類し、モデル名を 1 つ選ぶ。接続そのものは Envoy が持ち、 分類は外部処理(ext_proc)として動きます。

自前の多要素選択器を持っていますが、tierbook はそれを使いません(理由は 4 章)。

evidence

tierbook

証拠の正本。「この振り分けが得だったと本当に言えるか」を判定し、 言えないときは言えないと拒否します。

stratoclave が主張しないと明言した品質の側を、ちょうど埋めます。

3 つが噛み合う一文。stratoclave の設計文書はこの流れをこう書いています ― routing judgment (VSR) → execution → ledger-precision charge → span_id reconciliation → a counterfactual savings figure a CFO can audit。「いくら安くなったか」は監査できる形で出ます。 そこに「その安さは品質を落としていないと言えるのか」が抜けていて、それが tierbook です。

2. 実コンポーネント構成 ― 1 件の依頼が通る道

いちばん重要な線が 1 本あります。stratoclave のモデル定義には served_by という項目があり、値は "bedrock" / "vllm" / "semantic-router" の 3 つだけです。そして「実体を持たない仮想モデル」は served_by="semantic-router" でなければならないと検証で強制されており、 sr_pool_ref で具体的なモデルではなくルーターのプールを名指しします。

つまり「賢く振り分ける」は、gateway から見れば 1 つのモデル名です。 利用者は普通にモデルを 1 つ指定し、その裏で振り分けが起きます。 この一段があるので、振り分けの中身を差し替えても利用者側は何も変えなくて済みます。

3. 2 つの台帳 ― 同じ 1 件を、違う目的で記録する

ここが構成のいちばんの要点です。台帳が 2 つあり、片方は「お金の正本」、もう片方は「証拠の正本」です。 どちらかに寄せると壊れます。

stratoclave の台帳tierbook の台帳
正本として持つものいくら請求したか(charge of record)なぜそう決めたか、そこから何が言えるか
答える問いこの依頼を受けていいか / 料率は凍結されたか / 精算は着地したかこの記録は、いま主張しようとしている内容を支えられるか
拒否するもの凍結できない料率 / 再計算できない請求設定を名乗らない比較 / 単独で出された率 / 合格した検査 1 つだけの報告
品質について主張しないと明記(Quality is NOT asserted here)ここが担当
結び付ける鍵(run_id, span_id) — 同じ 1 件を両側から指せる

なぜ分けるのか ― 混ぜたときに何が壊れるか

お金の台帳に品質の判定を持たせると、請求が判定に依存します。 品質の判定は後から変わります(測り直す、母集団を変える、基準を追加する)。 請求が後から変わってはいけません。逆に、証拠の台帳にお金の正本を持たせると、 「言えない」と言うたびに請求が止まります。止めてはいけません ― 判定できないことは、請求しない理由ではありません。

potential と realized を混ぜない

stratoclave は「助言しただけ」と「実際に効いた」を厳密に分けて記録します。 これは段階的な導入(Shadow → Canary → Full)のためで、最初の 2 週間は 振り分けを相談するが実行はしない状態で走ります。

この分離は tierbook 側の要求と同じ形です。tierbook も 「その方策を実際に走らせた結果」と「走らせていれば得られたはずの結果」を混ぜません。 混ぜた数字は実測でも予測でもない第三の何かになり、どちらとしても使えなくなります。

4. 境界に流れる項目 ― 実名で

境界ごとに、実際に何が渡るかです。すべて実物のコードから取りました。

境界 A ― tierbook → Semantic Router(設定を配る)

# tierbook export-vsr が生成する v0.3 設定の骨格
{
  "providers": {
    "defaults": { "default_model": "…" },   # 分類できなかった依頼はここへ
    "models": [ { "backend_refs": [ … ] } ]     # 素のアドレスではなく参照
  },
  "routing": {
    "strategy": "priority",                       # 多要素の採点は使わない
    "modelCards": [ { "quality_score": … } ],    # 記録のためだけ。採点入力ではない
    "signals": { "domains": [ {…} ] },            # 素の文字列ではなくオブジェクト
    "decisions": [ {
      "rules": { "operator": "AND",
                 "conditions": [ { "type": …, "name": … } ] }
    } ]
  }
}

router 自身の選択器を、意図的に使っていません。 router には「品質・遅延・費用に重みを付けて選ぶ」機能があります。tierbook はそれを使わず、 1 つの分類に対してモデルを 1 つ名指しする形だけを出します。理由はコードにこう書いてあります ― その場の統計で選ぶと、誰も約束していない証拠で選んだことになり、事故のあと誰も検証できない。 だから quality_score は記録のためだけに入っていて、採点の入力ではありません。

境界 A で拒否される 4 つ

状況なぜ黙って通さないか
コンパイル済みの項目が無い分類既定でも最安でもなく何も出しません。分類されなかった依頼は router 自身の既定モデルへ行き、それは運用者が意図して設定した先です
provisional な項目専用のフラグ無しでは出しません。出すときは設定ファイルの説明文にその事実が残ります
2 段構えの連鎖連鎖として出せません。先頭だけ出すと安全網が黙って外れます。router は「失敗したら次へ」を観測できないからです
分類ラベルが宣言されていない分類ラベルの集合は運用者が選んだ分類器のものです。推測で対応づけると、別の traffic についての証拠で振り分けます

4b. 推論エンジンの内側 ― 生成を始める前に止める

ここまでは「どのモデルに回すか」でした。もう一段内側に、 「安いモデルが読み込みだけした時点で、自分で降りる」という仕組みがあります。 これは vLLM の公式の拡張点だけで作ってあり、fork していません。

3 つ目の拡張点が無いので、回避策で動かしています。 「行き先ではなく行動を返す」ための通路が拡張点に存在しません。 仕方なく答えの文章に決まった文字列を混ぜて合図にしています。1 ビット伝えるのに生成を数回ぶん使い、 両側が同じ文字列を知っている必要があります。珍しい 1 語では足りませんでした ― 候補 4 つとも、24 万語の語彙で 1 語になりませんでした。コードには 「本来はこう直すべき」も一緒に書いてあります(回避策を設計と勘違いさせないため)。

行き先を返さないのは意図です。「私は降りる」だけを返し、 どこへ回すかは呼び手側の標準の選択器が決めます。エンジンが行き先を決めると、 そのエンジンが第 2 のルーターになり、業界標準の仕組みが既に持っている endpoint 選択・待ち行列・故障切り替えを作り直すことになります。

ここが 2 章の図と繋がります。降りたあとの行き先選びは Semantic Router の仕事で、そこに tierbook が配った設定が効きます。

5. tierbook の内部構造 ― 依存の向きが 1 つに揃っている

38 モジュールありますが、依存の向きに例外がありません。下の図は実際の import を機械的に数えて作ったもので、 手で描いたものではありません。

葉に何が置いてあるか ― ここが設計の芯です

葉に置いたものなぜ 1 か所でなければならないか
費用の単位(ドル / トークン / GPU 秒)2 か所にあると「費用とは何か」で食い違うまで編集 1 回
測定条件(プロンプトの本文のハッシュ)「簡潔」という同じ呼び名で本文が違うものを 2 つ持てないように
正規分布の分位点表5 個の値の表が 2 つあると、5% の意味で両者が食い違う
「何についての信号か」判定器の側と方策構築の側が同じ語彙を検査する必要がある
「その数はいつ確定したか」比較の設定と、検定の帰無で同じ区別が必要

6. 誰が何を持たないか ― 線引きが構成の本体です

3 つのプロジェクトが「これは自分の仕事ではない」と明示的に決めていることのほうが、 持っているものより重要です。線が曖昧だと、同じ物が 2 か所にでき、片方だけ直されます。

これは誰の仕事か持つ側持たない側の理由
行き先の探索・待ち行列の採点・故障切り替え・世代管理Semantic Routertierbook が作り直すと価値ではなく追随の負債が増える
料率の凍結・予約・精算・請求の正本stratoclavetierbook が持つと「判定できない」と言うたびに請求が止まる
品質の測定と評価利用者(機構は stratoclave が提供)gateway は可能にする機構を出したら完成。適用は使う人の責務
その品質の主張が支えられるかの判定tierbookgateway が主張しないと明言している空白
どのモデルをどう載せるか利用者箱とモデルは一対一ではない。1 台に複数載せられ、台数も変わる

「機構は出した、適用は使う人」という線が繰り返し出てきます。 stratoclave 側の文書はこれを最も強く書いていて、「品質未測定」という但し書きは欠陥ではなく、 責務境界を正直に示す正しい設計だと明言しています。tierbook もこの線を守っており、 だから quality_score を router の採点入力にしません ― それは利用者が測って納得すべき数字で、機構が勝手に重み付けするものではありません。

穴を 3 つ、はっきり書きます

  • GPU 秒での費用が測れていません。トークン数は費用の弱い代理で、 トークンで勝っている方策が GPU 秒で負けることがあります。測るには負荷が必要で、問題数を増やしても取れません。
  • いちばん欲しい信号がありません。振り分けが得かを決めるのは 「高い方が正解する確率」−「安い方が正解する確率」で、1 番目の項を予測できる物が誰にもありません。 「難しいか」は測れて(隠れ状態で 0.69〜0.77)、「回すと得か」は空席です。
  • 「行動を返す通路」が推論エンジンに無い。合図の文字列で回避しています。 これは上流に出すべき要望としてコードに書いてあります。

構成を一文で。 Semantic Router が「どこへ送るか」を持ち、stratoclave が「いくら請求したか」を持ち、 tierbook が「その安さは品質を落としていないと言えるのか」を持つ。 3 つが served_by="semantic-router" と sr_pool_ref と (run_id, span_id) の 3 つの項目で噛み合っていて、 どこにも同じ物が 2 つありません。

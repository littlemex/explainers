この回の前提: 第 37 回 止めずにスキーマを変える (ロックの待ち行列、トランザクション ID 待ちの構造)

この回は、PostgreSQL をアプリケーションの裏側で動かし続けるための運用面の総まとめです。PostgreSQL 18.6 の実機で、接続が OS のプロセスであること、3 種類のタイムアウト (statement_timeout ・ idle_in_transaction_session_timeout ・ transaction_timeout) がそれぞれ何を区別して止めるのか、pg_stat_activity の wait_event でロック待ちとスリープを見分ける方法、そしてコネクションプーリングのトランザクションモードがなぜ PREPARE のようなセッション状態を壊すのかを、実際のエラーと切断で確認します。

1. この回で解く問題 ― 接続は無料ではなく、待たせ方にも種類がある

アプリケーションから PostgreSQL への 1 本の接続は、サーバー側では 1 つの OS プロセスとして起動します。接続を増やすことは、単にソケットを増やすことではなく、プロセスを増やすことです。各プロセスは work_mem のようなセッション単位のメモリを必要とする場面があり、サーバーが受け付けられる接続数には max_connections という上限があります。接続を使い切った状態で新しい接続を試みると、サーバーは新しい接続そのものを拒否します。

接続を使い続ける中でも、処理が止まる理由は一様ではありません。1 つの重いクエリが時間を使っているのか、トランザクションの中で誰かがロックを持ったまま何もしていないのか、同じ行を他のトランザクションが先にロックしているのか。これらは原因も対処法も違うため、pg_stat_activity で「今何が起きているか」を区別して見る必要があります。

図: 接続はプロセスとして資源を消費し、その状態は pg_stat_activity から観察できる。

2. 仕組み ― 接続の内訳と上限を実機で見る

pg_stat_activity には、クライアントからの接続だけでなく、PostgreSQL 自身が内部的に動かしているプロセスも含まれています。実機で backend_type ごとに数えてみます。

SELECT backend_type, count(*) FROM pg_stat_activity GROUP BY 1 ORDER BY 1;
--          backend_type         | count
-- ------------------------------+-------
--  autovacuum launcher          |     1
--  background writer            |     1
--  checkpointer                 |     1
--  client backend               |     1    ← 自分 (このクエリを実行している接続)
--  io worker                    |     3
--  logical replication launcher |     1
--  walwriter                    |     1

SHOW max_connections;                 --  100
SHOW superuser_reserved_connections;  --  3
SHOW shared_buffers;                  --  128MB  (全接続で共有するバッファ)
SHOW work_mem;                        --  4MB    (接続ごとに必要になりうるソート/ハッシュ用メモリ)

client backend だけがアプリケーションからの接続で、他は WAL の書き出しやチェックポイント、自動バキュームといった PostgreSQL 自身の運用のためのプロセスです。max_connections はクライアント接続の上限で、このサーバーでは 100 です。そのうち superuser_reserved_connections (3) は、一般の接続がこの上限に達していても、スーパーユーザーだけは接続できるよう予約されています。shared_buffers は全接続が共有する領域ですが、work_mem はソートやハッシュ結合のたびに接続ごとに確保されうるメモリです。接続数を増やすほど、ピーク時に必要なメモリの総量も増えるという関係が、ここから見えます。

3. 仕組み ― wait_event でロック待ちとスリープを見分ける

「このクエリはなぜ返ってこないのか」を調べる最初の一手は pg_stat_activity の state ・ wait_event_type ・ wait_event です。第 36 回で見たのと同じ、FOR UPDATE の衝突を 2 セッションで再現し、片方は pg_sleep で実際に処理をしている最中、もう片方はロック待ちという状況を作ります。

-- wa_A: 行をロックしてから pg_sleep(4) で処理中
-- wa_B: 1 秒後に同じ行を FOR UPDATE で狙う (ロック待ちになる)

SELECT application_name, state, wait_event_type, wait_event, query
FROM pg_stat_activity WHERE application_name IN ('wa_A','wa_B');

--  application_name | state  | wait_event_type |  wait_event   |  query (省略)
-- ------------------+--------+-----------------+---------------+----------------
--  wa_A             | active | Timeout         | PgSleep       | ... pg_sleep(4);
--  wa_B             | active | Lock            | transactionid | ... FOR UPDATE; COMMIT;

両方とも state は active ですが、wait_event_type が違います。wa_A は Timeout/PgSleep で、これは「サーバー内部のタイマーを待っている」状態、つまり本当に処理 (この場合は意図的な待機) をしています。wa_B は Lock/transactionid で、これは第 36 回で見た「相手のトランザクション ID へのロック待ち」そのものです。state=active だけを見て CPU を使っていると誤解せず、wait_event_type まで見て初めて「本当に動いているのか、何かを待っているだけなのか」が分かります。本番のトラブルシューティングでは、この wait_event の値ごとに集計することで、ボトルネックがロックなのか、ディスク I/O なのか、ネットワークなのかを区別できます。

4. どこで壊れるか ― 3 つのタイムアウトは「何を」止めるかが違う

PostgreSQL には用途が異なる 3 つのタイムアウト設定があります。実機でそれぞれを発火させ、エラーの種類と接続への影響の違いを確認します。

-- (1) statement_timeout: 1 つの文だけを打ち切る
SET statement_timeout = '500ms';
SELECT pg_sleep(2);
-- ERROR:  57014: canceling statement due to statement timeout
SELECT 'still connected' AS proof;  -- 接続は生きているので、この後の文は実行できる
--  still connected

-- (2) idle_in_transaction_session_timeout: トランザクションの中で何もしない時間を測る
SET idle_in_transaction_session_timeout = '1s';
BEGIN;
SELECT bug_id FROM bugs LIMIT 1;
-- (ここでクライアントが 3 秒間何も送らない)
SELECT bug_id FROM bugs LIMIT 1;
-- FATAL:  25P03: terminating connection due to idle-in-transaction timeout
-- (接続そのものが切断される)

-- (3) transaction_timeout (PostgreSQL 17 以降): トランザクション全体の合計時間を測る
SET transaction_timeout = '1s';
BEGIN;
SELECT bug_id FROM bugs LIMIT 1;  SELECT pg_sleep(0.3);
SELECT bug_id FROM bugs LIMIT 1;  SELECT pg_sleep(0.3);
SELECT bug_id FROM bugs LIMIT 1;  SELECT pg_sleep(0.6);
SELECT bug_id FROM bugs LIMIT 1;
-- FATAL:  25P04: terminating connection due to transaction timeout
-- (個々の文はどれも短いが、合計が 1 秒を超えたので接続が切断される)
設定何を測るかSQLSTATE接続への影響
statement_timeout1 つの文の実行時間57014 (ERROR)接続は継続
idle_in_transaction_session_timeoutトランザクション中、何もしていない時間25P03 (FATAL)接続が切断される
transaction_timeout (PG17+)トランザクション全体の合計時間 (アイドルも実行中も含む)25P04 (FATAL)接続が切断される

この 3 つは「何を測るか」が明確に異なります。statement_timeout は 1 文の実行時間だけを見るため、短い文をたくさん積んだ長いトランザクションには効きません。idle_in_transaction_session_timeout は、トランザクションを開いたままクライアントが何も送ってこない時間だけを測り、実際にクエリが走っている時間は含みません。長時間の重い処理 (バッチ処理の中の 1 つの UPDATE など) を誤って切ってしまうことはありません。transaction_timeout は、アイドル時間も実行時間もまとめてトランザクション全体の寿命として測るため、「短い文を何度も繰り返しながら、全体としては長時間ロックを持ち続ける」トランザクションを確実に止められます。いずれも FATAL になる 2 つは接続そのものを切断するため、アプリケーション側は再接続の仕組みを持っておく必要があります。

図: 3 つのタイムアウトは、文単位 ・ アイドル時間だけ ・ トランザクション全体という異なる範囲を測る。

5. どこで壊れるか ― プーリングのトランザクションモードとセッション状態

PgBouncer のようなコネクションプーラーのトランザクションモードは、クライアントが 1 つのトランザクションを終えるたびに、物理的な PostgreSQL 接続を他のクライアントに回します。これにより少ない物理接続で多くのクライアントを扱えますが、セッション (接続) のスコープで保持される状態は、次のトランザクションで同じ物理接続に戻ってくる保証がありません。PREPARE した文がその代表例です。

-- 同じ接続の中で、別々のトランザクションをまたいで使う
BEGIN;
PREPARE get_bug (bigint) AS SELECT bug_id, summary FROM bugs WHERE bug_id = $1;
COMMIT;
BEGIN;
EXECUTE get_bug(1);  -- 同じ接続内なので使える
COMMIT;
--  bug_id |      summary
-- --------+-------------------
--       1 | crash when saving

-- 新しい接続 (別のプロセス) から同じ名前を EXECUTE しようとする
EXECUTE get_bug(1);
-- ERROR:  26000: prepared statement "get_bug" does not exist

PREPARE は接続 (セッション) に紐付き、トランザクションをまたいでも消えません。しかし別の接続からは最初から存在しません。トランザクションモードのプーリングでは、アプリケーションの 1 回の論理セッションの中でも、トランザクションごとに違う物理接続が割り当てられることがあるため、ある時点で PREPARE した文が、次のトランザクションでは跡形もなく消えている、という事態が起きます。同じ理由で、SET によるセッション変数の変更、LISTEN/NOTIFY、WITH HOLD カーソル、セッションレベルのアドバイザリロック (第 36 回) も、トランザクションモードのプーリングでは信頼できません。これらを使う処理は、セッションモードのプーリング (接続をクライアントに固定する) を使うか、プーラーを経由しない直接接続にする必要があります。

図: トランザクションモードのプーリングでは、論理セッションと物理接続が 1 対 1 で対応しない。

6. シニアの書き方 ― 統計の見方の総まとめ

本番運用で「今何が起きているか」を判断するために、このシリーズで見てきた統計ビューを 1 つの手順にまとめます。

-- (1) テーブルの健全性 (第 35 回): dead tuple の蓄積と autovacuum の稼働状況
SELECT relname, n_live_tup, n_dead_tup, n_tup_upd, n_tup_hot_upd, last_autovacuum
FROM pg_stat_user_tables WHERE relname = 'bugs';

-- (2) 今動いている接続の状態 (この回): 待っているのか、実行中なのか
SELECT pid, state, wait_event_type, wait_event, query
FROM pg_stat_activity WHERE pid = pg_backend_pid();

-- (3) 自分が今保持しているロックの数 (第 36 回)
SELECT count(*) FROM pg_locks WHERE pid = pg_backend_pid();

判断の順序はこうです。アプリケーションが遅いと報告が来たら、まず pg_stat_activity で wait_event_type を確認し、Lock なら第 36 回の行ロックの衝突を、IO ならディスクやキャッシュの問題を疑います。次に pg_stat_user_tables の n_dead_tup と last_autovacuum を見て、第 35 回で見た VACUUM の遅れがクエリの速度に影響していないかを確認します。EXPLAIN (ANALYZE, BUFFERS) による実行計画の分析 (第 28 回) は、個々のクエリが遅い理由を特定するための最後の一手です。なお pg_stat_statements は問い合わせ全体の傾向を見るのに有用ですが、shared_preload_libraries への追加とサーバーの再起動が必要な拡張であり、この回の実機 (shared_preload_libraries が空の状態) では有効化されていないため、ここでは出力を示していません。導入する際は、サーバー全体に影響する設定変更であることを踏まえ、計画的に行う必要があります。

この回で見た 3 つのタイムアウトと、接続数の上限、そして pg_stat_activity の wait_event は、どれも「今、何が資源を使っていて、何が待たされているか」を言語化するための道具です。アプリケーション開発者が SQL を書くときにこれらを意識することは少なくても、本番でそのクエリが詰まったとき、原因を 1 つずつ絞り込めるかどうかは、この回で見た仕組みをどれだけ正確に理解しているかにかかっています。

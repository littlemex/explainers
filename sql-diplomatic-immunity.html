ディプロマティック・イミュニティ ― SQL だけは規律の外

アプリケーションコードに課す規律 (ドキュメント・バージョン管理・テスト・レビュー) を、SQL だけ免除する理由は無い

← SQL シリーズ目次へ

この回の前提: 第 23 回 シー・ノー・エビル (トランザクションと DO ブロックの基本)

この回が答える問いは「SQL やスキーマの変更にも、アプリケーションコードと同じ開発の規律を課すべきか」です。結論を先に言うと、課すべきです。SQL は「ちょっとした修正ならその場で直接本番に打てる」という手軽さを持つがゆえに、ドキュメント・バージョン管理・テスト・レビューの対象から外されがちです。この回では、COMMENT ON によるドキュメント、マイグレーションのバージョン管理、トランザクションで包んでロールバックするテスト、そして無秩序な変更を自動的に見つける仕組みを、実機で確認します。

1. 目的 ― 何をしたかったのか

アプリケーションのコードには、通常レビュー・テスト・バージョン管理という規律が当たり前に課されます。しかし SQL は psql を開いて 1 行打てばその場で本番のデータベースを変更できるという特別な手軽さを持っています。急いでいるときほど「今回だけ」「このくらいの修正なら」という理由で、この規律を素通りしたくなります。この回のテーマは、この「SQL だけは規律の外」という扱いが、後から見ても分かる・元に戻せる・正しいことを確認できる状態をどう壊すかを理解し、同じ規律を保つための具体的な道具を知ることです。

2. アンチパターン ― どう書いてしまい、何が壊れるか

典型的なアンチパターンは次のようなものです。障害対応やちょっとした調整のたびに、誰かが psql で本番データベースに直接 ALTER TABLE や UPDATE を打ち、その変更はコミットログにも、チケットにも、どこにも記録されません。テーブルや列にはコメントが付いておらず、「この列は何のためにあるのか」を知っているのは最初に作った人の記憶だけです。テストは本番とは別の都合のいいデータに対して手で 1 回動かして終わり、次に同じ修正が必要になったときにはもう手順を覚えている人がいません。

実際にサンプル DB のテーブルにコメントが付いているかを確認すると、この状態がどれだけ当たり前になりやすいかが分かります。

SELECT c.relname AS table_name, obj_description(c.oid) AS table_comment
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r' AND n.nspname = 'public'
ORDER BY c.relname;

  table_name   | table_comment
---------------+---------------
 accounts      |
 bug_status    |
 bugs          |
 bugs_products |
 comments      |
 products      |
 screenshots   |
 tags          |

8 個あるテーブルの table_comment がすべて空です。bugs.status が bug_status テーブルの値だけを許すことや、bugs.hours が見積もりではなく実績の時間であることは、テーブル定義を見ただけでは分かりません。スキーマそのものに書かれていない知識は、結局「聞ける人がいる間しか」有効な知識です。

図: アプリケーションコードには当然の規律が、SQL の直接実行には適用されないまま残る。

3. 見つけ方 ― どんな兆候で気づくか

前節で使った obj_description() のクエリ自体が、ドキュメント不足を見つけるための見つけ方です。table_comment が空のテーブルがどれだけあるかを定期的に数えるだけで、ドキュメントの負債がどれくらい積もっているかを可視化できます。

マイグレーション管理を経由しない「手打ちの変更」を見つけるには、PostgreSQL のイベントトリガーを使います。イベントトリガーは、誰が・いつ・どの DDL を実行したかを自動的に記録できる仕組みです。

CREATE TABLE ddl_audit_log (
  log_id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  executed_at     timestamptz NOT NULL DEFAULT now(),
  command_tag     text,
  object_identity text,
  executed_by     text
);

CREATE OR REPLACE FUNCTION log_ddl_command() RETURNS event_trigger AS $$
BEGIN
  INSERT INTO ddl_audit_log (command_tag, object_identity, executed_by)
  SELECT tg_tag, obj.object_identity, current_user
  FROM pg_event_trigger_ddl_commands() obj;
END;
$$ LANGUAGE plpgsql;

CREATE EVENT TRIGGER audit_ddl ON ddl_command_end
  EXECUTE FUNCTION log_ddl_command();

-- マイグレーション経由ではなく、誰かが手で直接 ALTER TABLE を打った、という想定
ALTER TABLE products ADD COLUMN notes text;

SELECT command_tag, object_identity, executed_by FROM ddl_audit_log ORDER BY log_id;
 command_tag | object_identity | executed_by
-------------+------------------+-------------
 ALTER TABLE | public.products | postgres

このイベントトリガーを常設しておけば、マイグレーションツールを経由した変更も、誰かが手で直接打った変更も、すべて同じ ddl_audit_log に記録されます。マイグレーションの記録 (後述) と比較して、ここにしか出てこない変更があれば、それが「規律の外」で行われた変更だということが分かります。

4. 使ってよい場合

SQL の直接実行そのものが禁止というわけではありません。本番で障害が起きていて、1 分 1 秒を争う状況では、マイグレーションファイルを作ってレビューを待つ余裕が無いこともあります。この場合、緊急対応として直接 SQL を実行すること自体は許容されます。ただし、それで終わりにしてはいけません。障害が収まった後、必ず「何を・いつ・なぜ実行したか」を、通常のマイグレーションの記録に事後登録します。

INSERT INTO schema_migrations (version, description)
VALUES ('2026100402', '緊急対応: products.sku に手で直接 ALTER TABLE した変更を事後記録');

こうしておけば、次に同じテーブルを見た人が「この列はいつからあるのか」「なぜ緊急対応で入ったのか」を追跡できます。緊急対応で免除されるのは「レビューを待つ時間」だけであり、「記録を残すこと」は免除されません。

5. 解決策 ― PostgreSQL での正しい書き方

5.1 COMMENT ON でドキュメントをスキーマと一緒に保存する

テーブルや列の意味を README やコメント欄ではなく、スキーマそのものに持たせられます。COMMENT ON で付けたコメントは、カタログに保存され、\d+ やカタログへの問い合わせで誰でも確認できます。

COMMENT ON TABLE bugs IS 'バグ管理の中心テーブル。status は bug_status テーブルで検証される。';
COMMENT ON COLUMN bugs.hours IS '対応にかかった実績時間 (時間単位)。見積もりではなく実績を入れる。';

SELECT obj_description('bugs'::regclass) AS table_comment;
                            table_comment
---------------------------------------------------------------------
 バグ管理の中心テーブル。status は bug_status テーブルで検証される。

README はコードと離れた場所にあるため、テーブル定義が変わっても README の更新を忘れることがよくあります。COMMENT ON はテーブルや列そのものに紐づくため、テーブルを見ている人の目に自然に入ります。

5.2 マイグレーションのバージョン管理

スキーマの変更を、順序付けられたファイルとして記録し、適用済みの変更を追跡するテーブルを持たせます。最小限の形は、次のような schema_migrations テーブルです。

CREATE TABLE schema_migrations (
  version      text PRIMARY KEY,
  applied_at   timestamptz NOT NULL DEFAULT now(),
  description  text NOT NULL
);

BEGIN;
ALTER TABLE products ADD COLUMN unit_price numeric(10,2);
INSERT INTO schema_migrations (version, description)
VALUES ('2026100401', 'products に unit_price 列を追加');
COMMIT;

SELECT version, description FROM schema_migrations ORDER BY version;
   version   |           description
------------+---------------------------------
 2026100401 | products に unit_price 列を追加

スキーマの変更と、その記録への INSERT を同じトランザクションに入れることが重要です。これにより「変更は適用されたが記録が無い」「記録はあるが変更は適用されていない」という矛盾した状態を防げます (この仕組みが成立するのは、次の節で見る DDL のトランザクショナルな性質のおかげです)。

5.3 トランザクションで包んでロールバックするテスト (pgTAP の考え方)

SQL の振る舞いをテストしたいとき、テスト用に作ったデータが本番に残ってしまうと困ります。pgTAP はテストをトランザクションの中で実行し、最後に必ず ROLLBACK することで、本番データへの影響を残さないという考え方を採用しています。この考え方自体は、拡張を使わずに素の PL/pgSQL でも再現できます。

BEGIN;
DO $$
DECLARE
  v_count integer;
BEGIN
  INSERT INTO bugs (summary, reported_by, status) VALUES ('test bug for assertion', 1, 'NEW');

  SELECT count(*) INTO v_count FROM bugs WHERE status = 'NEW' AND summary = 'test bug for assertion';
  ASSERT v_count = 1, format('expected 1 NEW bug, got %s', v_count);

  BEGIN
    UPDATE bugs SET status = 'NONEXISTENT' WHERE summary = 'test bug for assertion';
    ASSERT false, 'expected foreign key violation but update succeeded';
  EXCEPTION WHEN foreign_key_violation THEN
    RAISE NOTICE 'test passed: invalid status correctly rejected';
  END;
END;
$$;
ROLLBACK;

SELECT count(*) AS leftover_test_rows FROM bugs WHERE summary = 'test bug for assertion';
 leftover_test_rows
---------------------
                   0

1 つ目の ASSERT は「テスト用に 1 件だけ NEW のバグが入っていること」を確認しています。2 つ目は「bugs.status に存在しない値を入れようとすると、外部キー制約で拒否されるはず」という仕様をテストしており、実際に foreign_key_violation が発生したことで検証に成功しています (NOTICE として出力)。最後に ROLLBACK しているため、テスト用に挿入した行は本番には一切残りません。これにより、テストのたびに専用のテスト用データベースを用意しなくても、安全に本番相当のスキーマに対してテストを書けます。

図: テストをトランザクションで包み、最後に必ずロールバックすることで本番データを汚さない。

6. PostgreSQL エンジンで考慮しておくこと

6.1 DDL はトランザクショナルでロールバックできる

PostgreSQL の大きな特徴の 1 つは、CREATE/ALTER/DROP のような DDL (データ定義言語) も、INSERT/UPDATE と同じトランザクションの中に含められ、ロールバックできることです。

BEGIN;
ALTER TABLE products ADD COLUMN discontinued boolean DEFAULT false;
SELECT column_name FROM information_schema.columns WHERE table_name='products' ORDER BY column_name;
 column_name
--------------
 discontinued
 product_id
 product_name
 sku
 unit_price
ROLLBACK;

SELECT column_name FROM information_schema.columns WHERE table_name='products' ORDER BY column_name;
 column_name
--------------
 product_id
 product_name
 sku
 unit_price

この時点までに、4 節の緊急対応で追加した sku と、5.2 節のマイグレーションで追加した unit_price はすでに products に存在しています (いずれも COMMIT 済みです)。それに対して、今回 BEGIN の中で追加した discontinued だけが ROLLBACK 後に跡形もなく消えています。この性質があるからこそ、5.2 節で見た「スキーマの変更とマイグレーション記録を同じトランザクションに入れる」という設計が成立します。もし DDL がロールバックできなければ、「変更は確定したが記録は失敗した」という不整合が起きる余地が残ってしまいます。他の多くのデータベース製品ではこの前提が成り立たないこともあるため、PostgreSQL のこの性質は移行時に意識しておく価値があります。

6.2 イベントトリガーは DDL の実行経路を問わず発火する

5 節で紹介したイベントトリガーは、マイグレーションツール経由であっても、psql からの手打ちであっても、同じように発火します。これは「規律を強制する仕組み」ではなく「規律の有無を事後に見える状態にする仕組み」です。イベントトリガーだけで手打ちの変更そのものを禁止することはできませんが (権限を分離すればある程度制限できます)、少なくとも「気づかれない変更」を無くすことができます。記録に残ることが分かっていれば、「今回だけ」と手を抜く心理的なハードルも上がります。

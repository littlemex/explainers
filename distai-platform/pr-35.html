PR #35: capacity-pool chart の full 版 — -rsv/-od/-flex と実在の予約

結論: #25 が出した「容量を1種類しか選べない」最小版の capacity-pool chart に、#17 が決めた3つの容量の形 (予約・オンデマンド・spot混在) と、実在の Capacity Reservation をタグで選ぶ仕組みを足した。実機で小さな予約を1つ作り、3つの pool が同じクラスタの上で共存し、2本目のジョブが Kueue 自身の quota で止まることまで確認している。

変更内容

3. 実機での確認

静的な helm template だけでなく、実在の AWS 資源で確かめた。小さな Capacity Reservation (m7i.large 1台、2時間で自動的に切れる設定) を実際に作り、タグで選ばせ、流したジョブのノードに karpenter.k8s.aws/capacity-reservation-id が実際に一致することを、Kubernetes 側のラベルと EC2 の API の両方から確認した。

検証が終わったら予約はすぐに cancel している。失敗時にも cancel されることを、クラスタを使わない小さな独立したスクリプトで別に2回確認した (タグで見つける経路と、タグが見つからないときに ID で見つける経路の両方)。

5. 検討して採らなかった案

案採らなかった理由
-rsv 専用の別 chart を作る同じ配線の修正を2箇所でやることになり、#25 が約束した「名前と形は変えない」を破る
Karpenter 公式のフォールバック形 (capacity-type In [reserved, on-demand])#17 がすでに「予約と他の型を混ぜない」と決めた理由 (Kueue の quota が実際の空きとずれる) にそのまま当たる
デフォルト出力の「変化していないこと」をバイト単位の golden ファイルで比較レビュー中に2回、無関係な理由 (Helm のバージョン差、base branch の rebase) で壊れた。コメント1行変わっただけで「退化した」と区別できない。フィールド単位の検証に置き換えた

6. GPU と Neuron を同じに扱うという原則との関係

この chart 自身は GPU か Neuron かを一度も見ない。accelerator.resourceName・taint・methodLabel という3つの値は、どちらのベンダーも同じ形で埋める想定で、taint を集める仕組み (capacity-pool.taints) は accelerator 用もチーム専有用も同じコードを通る。実際に GPU か Neuron の device plugin を動かす中身は #19 の役目で、この PR には一切無い。

7. まだ終わっていないこと

accelerator と tenancy は値だけで、強制するものが無い。#19 (device plugin/DRA) と #22 (admission policy) が実際の中身と強制を足すまで、この PR の taint/label は「置いてあるが誰も見ていない」状態のまま。

この PR は #25 (まだマージされていない delivery layer の PR) の上に積んでおり、#25 自身も並行してレビュー対応中だった。レビューの途中で base が2回進み、そのたびに追従した。マージ前にもう一度の追従が必要になる可能性がある — 積み重ねた PR の普通のコストとして受け入れている。

9. レビューで見てほしいこと

  1. pool.limits の決め方。reserved pool では予約の台数×インスタンスの広告値 (allocatable ではない) を使うべきだと直したが、実際に Karpenter のソースまでは確認していない。実機では1台の予約で正しく動いたが、2台以上の予約でも同じ考え方が成り立つか。
  2. cancel の失敗パス。実機の run の最後で、ブランチの削除が5件とも一度失敗した (直後に手で削除できたので一時的な問題と見ている)。Capacity Reservation の cancel 自体はクラスタを使わない独立したスクリプトでしか確かめていない。これで十分な証拠か。
  3. #25 への依存。base branch が2回進み、その都度 merge で追従した。rebase ではなく merge を選んだ判断(競合解消を1回にまとめるため)が、この PR 自身のコミット履歴として適切か。
  4. accelerator/tenancy の値の形が、#19/#22 が実際に必要とする形と一致しているか。中身が無いまま先に形だけ決めているので、後で合わないと分かったときの直しやすさも含めて見てほしい。

まとめ。#25 の最小版 chart に、#17 が決めた3つの容量の形を実装し、実在の予約1つで -rsv/-od/-flex が同じクラスタの上で共存し、2本目のジョブが Karpenter の失敗ではなく Kueue 自身の quota で止まることまで実機で確認した。5回のレビューを経て、バイト比較だった検証をフィールド単位の検証に置き換え、ドキュメントの数値の不整合やコメントの古さを直し、最終的に承認を得ている。

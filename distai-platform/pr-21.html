1. 何を作るか、なぜこの範囲だけか

1 つのセル (クラスタ 1 個分の環境) には、生きている間ずっと変わらないもの (ネットワーク、クラスタ本体、最低限のノード) と、毎日のように変わるもの (どの NodePool を使うか、どの Capacity Block を買うか、どの device plugin を入れるか) が混ざっている。両方を 1 つの Terraform state に入れると、Capacity Block を 1 つ買うだけで巨大な state の plan を見ることになる。そこで infra/foundation は入れ物だけを持ち、中身は Argo CD (#17) に渡す。

2. 各要素

作る順番にも意味がある。add-on には 2 種類あって、vpc-cni のような DaemonSet 系はノードグループより先に入れないとノードが Ready にならず、coredns のような Deployment 系はノードが無いとスケジュールできないので後に入れる (eks.tf の addons_before_nodes / addons_after_nodes)。Karpenter 自体は入れないが、Karpenter が要る AWS 側の下ごしらえ (controller の IAM role、node の IAM role、割り込みキューと EventBridge の rule 5 本) はここで作る (karpenter.tf)。5 本目は Capacity Block や予約の中断警告で、#17 の予約プールが Karpenter に生き残る相手として確実に認識されるために足した。

3. 削除の順番とガード

Karpenter が起動した EC2 instance は、Karpenter 自身が Argo CD から入るので、この Terraform の state には記録が無い。terraform destroy が素直にネットワークから壊していくと、instance はまだ動いているのにサブネットや NAT を先に消すことになり、instance のネットワークインターフェースが邪魔をして destroy が止まる (teardown.tf のコメントが名指しする失敗)。これを避けるため、teardown.tf の terraform_data が destroy 専用の provisioner で teardown-guard.sh を呼び、Karpenter の instance を先に手で片付けてから、それ以外の削除を進める。

4. セキュリティの選択

この PR のレビューの半分近くは、セキュリティに関わる指摘だった。EKS は公開エンドポイントの CIDR リストが空だと「制限なし」と解釈するので、変数を必須にし、さらに /8 より広い範囲 (0.0.0.0/0 や、2 本の /1 を組み合わせて同じ広さにする手) も拒否する検証を足した。Karpenter controller の IAM role は、最初は「このアカウントから来た」(aws:SourceAccount) だけで判定していたが、これだけでは同じアカウントの別の Pod が EKS Pod Identity を使って役を乗っ取れてしまうため、Pod Identity が必ず付けるセッションタグ (クラスタの ARN、namespace、service account) も条件に加えた。

5. Fable 5.2 の 3 視点レビューで見つかったこと

実装、テスト、レビューを別々のセッションに分けて進め、Fable 5.2 に 17 件の指摘を受けた。12 件を直し、2 件は README に書いて説明するだけにし、2 件は残し、1 件は制約そのものを外す形で応じた。「残した」ものを隠さずに書く。

6. 実機での 3 回の e2e

東京リージョン (ap-northeast-1) で、infra/foundation/tests/1.e2e.sh を 3 回走らせた。1 回目は基盤のコードではなく、確認スクリプトの思い込みが原因で落ちた。argocd_capability_arn を null にする仕様 (README の「未作成なら null」) は正しかったが、Terraform は値が正確に null の output を state から省くため、名前で terraform output を呼ぶと「無い」エラーになる。これはテストのバグなので、null と同値に扱うよう確認スクリプト側を直した。

3 回目は、レビュー後のコード (controller の trust policy にセッションタグを足したもの) で再実行した結果で、これが PR の ## Test Results に貼った証拠である。セッションタグを足しても Karpenter の Pod Identity の認証情報は通常どおり発行され、EC2NodeClass が Ready になり、spot の起動・中断・置き換えの一連の流れが問題なく動いた。実行後の独立した確認でも、VPC、instance、ENI、NAT、ボリューム、EKS クラスタ、SQS キュー、EventBridge の rule、ロググループ、起動テンプレート、IAM role、instance profile のいずれも、このセルに属するものは 1 つも残っていなかった。

この PR で選んだことのうち、Trainium (Neuron) に限らず GPU のセルにもそのまま当てはまるものを挙げる。上流の事実は commit 固定で確認した。

#提案上流の今取り込むと何が良いか出し方
1公開 API エンドポイントを CIDR で絞る architectures/amazon-eks/assets/eks-cluster.yaml は EndpointPublicAccess: true だけで PublicAccessCidrs を指定していない。EKS の既定はこの場合 0.0.0.0/0 (世界中に公開) になる。同じテンプレートは BootstrapClusterCreatorAdminPermissions: true も使っており、作った人が variable に出ない暗黙の管理者になる どこからでも API サーバーに到達できる状態を避けつつ、アクセス元 (手元の IP など) を 1 つの CloudFormation パラメータにできる。管理者を access entry に明示すれば「誰が admin か」が state と diff で追える CloudFormation パラメータ 1 個 (既定を必須にはしない、後方互換のため既定値は現状どおり空扱い) の小さな PR。先に Issue で挙動を変えることの合意を取る
2Karpenter を使うセルに削除ガードを足す architectures/sagemaker-hyperpod-eks/terraform-modules は Karpenter を使うが、destroy 時に Karpenter の instance を片付ける仕組みが無い (同種の local-exec/terraform_data は見当たらない) NAT とネットワークを先に壊して destroy が止まる事故 (この PR の 3 節と同じ形) を避けられる teardown-guard.sh 相当のスクリプトと、それを呼ぶ terraform_data を 1 モジュールとして追加する PR。Karpenter を前提にしたモジュールに限るので適用範囲は狭い
3クラスタ作成者を暗黙の管理者にしない 同じ eks-cluster.yaml が BootstrapClusterCreatorAdminPermissions: true を使っている admin が access entry の一覧だけで決まるようになり、誰が管理者かをコードレビューで確認できる 1 と同じ PR にまとめられる (両方 eks-cluster.yaml の数行)

Neuron (Trainium) を前提にした提案はここに含めていない。awsome-distributed-ai は Neuron を中心には扱っておらず、Trainium に特有の部分は distai-platform の中で育ててから、実機で動いたものだけを後の PR で出す。

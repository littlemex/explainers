PR #52: EFA をアクセラレータの外側から Kubernetes に見せる部品
accel-efa-device-plugin-nvidia/-neuron (Issue #19 の一部、Issue #50 の advertiser 側を閉じる)

readyIssue #19・#50 の一部ブランチ feat/efa-device-pluginbase PR #40 (feat/19-accel-addons)

結論から言うと。Karpenter が EFA(高速ネットワークカード)を 4 枚付けた実機のノードを起こしても、Kubernetes 側には何も見えていなかった(「何個使えるか」を Kubernetes に教える役=advertiser が無かった)。今回、公式の部品(AWS の Helm chart)を使ってこの役を足し、実機の p4d.24xlarge 2 台で EFA が正しく 4 個ずつ見えること、2 ノード間の通信(NCCL)が実際に EFA を通って動くことを確認した。途中のレビューで「この部品が今の設計のままだと、EFA を使わない既存のノードにも乗ってしまい、そこでは動かずに再起動を繰り返す」という本当の不具合を実機で発見し、直して再確認した。

この PR でやったこと。公式の EFA device plugin を 2 つのリリース(NVIDIA 用・Neuron 用)として追加し(1 節)、権限を絞っても動くことを確認し(2 節)、EFA を使わないノードで実際に何が起きるかを確かめて直し(3 節)、ついでに「なぜ以前の帯域測定より 4 割低く見えたか」の原因も実機で突き止めた(4 節)。

1. EFA を見せる部品が無かった、という元の問題

EFA は GPU や Neuron のような「アクセラレータの種類」を持たない、ネットワークカードである。そのため「この部品はどのノードに乗るべきか」を、GPU 用や Neuron 用の部品と同じラベル(どちらの方式を使っているか)に相乗りさせて決めている。

公式の部品(aws-efa-k8s-device-plugin)を調べたところ、1 つだけ想定外の作りがあった。「どのノードに乗るか」を決める設定のうち、ノードの機種名で絞る部分は書き換え可能だが、GPU 用のラベルと Neuron 用のラベルのどちらか一方を選ぶ部分は、部品の中に固定で書き込まれていて外から変えられない。つまり 1 つのリリースでは「GPU 用のラベルが付いたノード、または Neuron 用のラベルが付いたノード」という「どちらか」の指定ができない。そこで、同じ部品を 2 つのリリース(NVIDIA 用・Neuron 用)として配る形にした。

2. 権限を絞っても動くことを、実機で確認した

この部品は、公式の既定の設定では「ホストに対して root 相当の権限」で動く。レビューで「本当にその権限が必要なのか、試したのか」と問われ、確かに試していなかったので、実機で確かめた。同じ p4d.24xlarge の同じノードの上で、権限を絞った設定に入れ替えても、EFA の見える数は入れ替え前後でまったく変わらなかった。今回のアドオンは、絞った設定を既定として配る。

3. EFA を使わないノードに乗せると、再起動を繰り返す

この部品は「GPU/Neuron 用のラベルが付いているか」だけでノードを選ぶ。しかし、このラベルは「EFA を使う設定にしたか」とは別の話で、ラベルが付いていても EFA を 1 枚も付けていないノードは普通にあり得る。実際、この基盤の既存の確認用の設定(dp-a19-gpu-r3・dp-a19-trn-r3)の両方が、まさにこの組み合わせ(ラベルはあるが EFA は無し)に当たっていた。

原因は、EFA を実際に使うかどうかを示す情報(ノードを作る設定の中の、EFA 用ネットワークカードの設定)と、GPU/Neuron 用のラベルが、別々の場所に書かれていて、どちらにも「もう一方が無い組み合わせ」を防ぐ仕組みが無かったことだった。直し方は、ノードを作る部品自身に「EFA を実際に付けた時だけ」付く新しい印(ラベル)を追加し、この EFA の部品の側は「GPU/Neuron 用のラベル」と「EFA の印」の両方が揃っていることを条件にするようにした。これで、既存の確認用設定のように EFA を使わないノードには、この部品がそもそも乗らなくなる。実機で、EFA 付きのノードと EFA 無しのノードを同じクラスタに同時に作り、前者にだけこの部品が乗って正しく動き、後者には 1 個も乗らないことを確認した。

4. ついでに:以前の測定より帯域が低く見えた理由

別の確認作業で、「今回の実機測定(2GB で約 46GB/s)が、前に測った同じ機種・同じ台数での測定(約 76.7GB/s)より 4 割も低いのはおかしい」という指摘を受けた。EFA の枚数も通信の経路も確認済みだったので、残る違いは測定コマンドの指定内容だと考え、1 つだけ条件を変えて実機で測り直した。

今回の測定では、通信のやり方(アルゴリズム)を「輪っか状(Ring)」に固定する指定を付けていた。この指定を外し、通信ソフト(NCCL)自身に自動で選ばせたところ、帯域は 76.9GB/s に戻った。つまり原因は EFA 部品や今回の設定ファイルの不具合ではなく、測定側がこちらで付けていた指定のせいだった。この知見は、来週以降の大きな機種(p5en)での測定にも関わるため、測定の手順書にも「通信方式の指定を付けない」ことを 1 行、実機の数値付きで書き足した。

5. まだ終わっていないこと

Neuron 側(trn2)での「EFA が正しく見える」確認は、実機では未確認。今回の実機確認はすべて NVIDIA 側(p4d.24xlarge)で行った。EFA を見せる仕組み自体は GPU か Neuron かを問わないはずだが、trn2 の実機では別途確認が要る。

main ブランチの保護設定に、レビュー必須・自動チェック必須の条件が入っていないことが分かった。この PR の作業とは別件だが、見つけたのでリポジトリの持ち主向けに Issue #53 として報告した。

7. レビューで見てほしいこと

  1. EFA が無いノードへの対策(3 節)。今回は「EC2 側で EFA を実際に付けた時だけ付く印」を新しく作ったが、この印の名前や置き場所(capacity-pool という共有の設定部品の中)が適切か。
  2. 権限を絞る設定(2 節)を、既定のまま配ってよいか。今回は実機で「絞っても動く」ことまでは確認したが、将来さらに絞れないか(たとえば root 権限自体の見直し)は今回の範囲外。
  3. Neuron 側の実機未確認(5 節)を、この PR のままで良いか、別の確認を先に挟むべきか。

まとめ。EFA を Kubernetes に見せる部品を、公式の Helm chart を使って追加し、実機の p4d.24xlarge 2 台で正しく動くことを確認した。途中のレビューで「EFA を使わない既存のノードにも乗ってしまい、そこで再起動を繰り返す」という実際の不具合を見つけ、直して実機で再確認した。ついでに、以前の帯域測定との食い違いの原因も実機で突き止め、来週以降の測定手順書にも反映した。

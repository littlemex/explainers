容量をどう混ぜるか: distai-platform の設計の調査
Issue #17 の検討 (Fable 5.2 と、2026-11-17)

結論から。「GPU と Trainium の容量を、spot、on-demand、予約 (ODCR と Capacity Block)、複数の型とリージョンで混ぜて使う」という悩みは、時間の単位が違う 4 つの決定を 1 か所 (Terraform の変数) に押し込んだことから来ている。推奨は、Terraform はクラスタの器だけを作り、数えられる容量 (予約) は Kueue の枠で、数えられない容量 (spot と on-demand) は Karpenter の探索で扱い、両者を既存のラベル karpenter.sh/nodepool で 1 対 1 に結ぶ形である。配るのは Argo CD と素の Helm chart で、独自の CRD は作らない。

この文書でやったこと。持ち主の 3 本の記事、今の 2 つの実装 (distributed-ai の Terraform と awsome-distributed-ai の CloudFormation の EKS)、Karpenter、Kueue、SkyPilot、Argo CD の今の公式の文書を調べ、それを材料に Fable 5.2 と構成の案を比べた。容量の実際の取りやすさは、別のページの容量の地図の値を使った。

1. 悩みの正体: 4 つの決定

「どの容量を使うか」は、一度に決まるものではない。予約を買うのは日の単位、どのクラスタに投げるかと、どの容量を何台まで使ってよいかはジョブを出すとき、実際にどの型をどの AZ で起動するかは秒から分の単位で決まる。時間の単位が違うものを 1 つの Terraform の変数に入れると、予約を 1 日買うたびに Terraform を流し直すことになり、Kueue の設定とプールの名前が黙ってずれる。

2. 今の 2 つの実装

観点distributed-ai (Terraform + Karpenter)awsome の amazon-eks (CloudFormation)
容量の種類spot、on-demand、予約を 1 つのリストで混ぜられ、Karpenter が予約 → spot → on-demand の順に取るon-demand、ODCR、Capacity Block のどれか 1 つ。spot は無い
型の混在1 プールに複数の型 (EFA の構成が同じものだけ)1 テンプレートに 1 型。複数は複数回デプロイ
Trainiumdevice_plugin = "neuron" で GPU と同じループ対応なし

両方に共通する限界は、ジョブが欲しい量と、今ある容量を結ぶ層が本体の外にあることである。

3. 構成の案の比較

案は 6 つ比べた。比べると、軸が 2 本あることが分かった。1 本は「実際に決める層」(Karpenter、Kueue、SkyPilot) で、もう 1 本は「宣言をどう包むか」(Terraform の変数、素のマニフェスト、kro、独自の CRD) である。

案長所短所Trainium上流に出せるか
(a) 今の Terraform の変数を延ばす1 回の apply でそろう複雑さが変数に溜まり続ける。予約を買うたびに apply可難しい
(b) Karpenter を素直に使い、Argo CD で配る予約にネイティブ対応。誰でも読める素の NodePool誰が予約を先に使うかの順番や枠が無い可高い
(c) Kueue を中心にする枠、順番、借用、preemption で「高価な容量を兼ねる」が書けるspot と on-demand では、入場しても容量があるとは限らない公式の言及なし高い
(d) SkyPilot を外側に置く入口が 1 つ。中断で探し直して再起動するクラスタの間の切り替えは既定で無い公式の言及なし (持ち主の記事では v0.14.0 で対応、多くは未検証)設定例として
(e) kro で「容量」の API を合成するコントローラを書かずに API が作れるその API 自体がこのリポジトリだけの抽象化になり、複雑さが CEL に移るだけ可低い
(f) 独自の CRD とコントローラ何でもできる保守と権限。「ここでしか使えない抽象化は作らない」原則に正面から反する可ほぼ不可

4. 推奨する構成

(b) と (c) を核にし、(d) を薄い外側に置く。Terraform で作るのは、VPC、全 AZ のサブネット、EKS、システム用の小さなノードグループ、IAM、中断の通知の SQS、Argo CD の登録とセルのラベル、チェックポイントの置き場だけで、NodePool、Kueue の設定、予約の購入、アドオンの中身は作らない。accelerator_pools の変数は無くなる。

核になる規約: 1 NodePool = 1 ResourceFlavor

プールは「予約だけ (-rsv)」「on-demand だけ (-od)」「spot と on-demand (-flex)」の 3 種類に切る。-rsv の Kueue の枠は予約の実数なので、入場したら容量がある。-od と -flex の枠は予算の上限で、容量の保証ではない。

独自の CRD は作らない

代わりに、既存の API (NodePool、EC2NodeClass、ResourceFlavor、ClusterQueue) をそのまま使い、Helm chart はその対を作るだけで判断は持たない。予約を買ったら Kueue の枠を書き換える PR を 1 本出す。Capacity Block は 1 日 54 ドルから 3,100 ドル (容量の地図) なので、購入ごとに PR 1 本は妥当な手続きである。この同期を自動にしたくなったら、「予約の状態を読んで Kueue の枠を書く」だけの小さなコントローラを、独立した OSS として切り出す。

5. GPU と Trainium、ワークロードの型

項目共通にする分ける (入口だけそろえる)
ノードの起動同じ chart、同じ 3 種類のプールAMI の系統
数える単位「1 クラス = 拡張リソース 1 つ」の規約nvidia.com/gpu と aws.amazon.com/neuron
ラベルKarpenter と Kubernetes の既存のラベルだけ。独自のラベルは作らない—
Kueue同じ ClusterQueue と Cohort。flavor 名は <クラス>-rsv/od/flex—
デバイスプラグイン、指標Argo CD のアプリとして配る。指標は共通の名前にそろえるNVIDIA と Neuron の実装、DCGM と neuron-monitor

クラスとは「拡張リソースの名前、1 台あたりのデバイス数、EFA の数が同じ型の集まり」である。GPU の世代の違い (p5 と p6-b200 など) も Trainium も、別のクラスとして同じ扱いにする。

ワークロードflavor の順中断への備え
短い学習ジョブ-rsv (空きを借りる) → -flexやり直せばよい
EFA の複数ノードの学習-rsv のみまとめて入場させ、Capacity Block の終了前に備えてチェックポイント。spot は使わない
長い推論サービス-rsv (ODCR) → -od常設は ODCR か on-demand。Capacity Block は 1 日なので負荷試験だけに使う
中断されてよいバッチ-rsv (借りるだけ) → -flexSkyPilot が探し直して再起動。チェックポイントはジョブ側

6. 一番危ない前提と、確かめる実験

一番危ない前提。「Kueue が入場させた = 容量がある」は、予約のプールでしか成り立たない。Kueue の容量を先に確かめる仕組みは Karpenter に対応していないので、spot と on-demand で起動に失敗しても Kueue は気付かず、ジョブが枠を握ったまま待つはずである (まだ確かめていない推測)。

まとめ。容量の悩みは、時間の単位が違う 4 つの決定を 1 つの変数に入れたことから来ている。Terraform は器だけ、予約は Kueue、spot と on-demand は Karpenter、配るのは Argo CD、独自の CRD は作らない。この形が成り立つかは、安い実験 1 (数ドル) で最初に確かめる。

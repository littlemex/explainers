examples/inference: SGLang prefill/decode disaggregation, and the llm-d/Gateway routing variant for vLLM (RFC #37)

結論から言うと。大きな文章生成 AI を「質問を読む役」と「答えを書く役」に分けて別々のサーバーで動かす仕組み(分離推論)を、もう一つの有名なエンジン SGLang でも動くようにした。これまでは vLLM という 1 つのエンジンでしか試していなかった。合わせて、この 2 台をつなぐ「交通整理役」を手作りの小さなプログラムから、業界標準の仕組み(llm-d / Gateway API Inference Extension)に替える版も作った。実際に GPU を 2 台借りて 5 つの組み合わせを動かし、最終的に 5 つ全部が最後まで正しい答えを返すことを確認した。交通整理役を標準品に替えた版は、1 回目の確認では配線は正しくても実際の質問の手前でエラーが起きたが、原因(暗号化通信の設定の食い違い)を特定して直し、追い確認で完走させた。

この PR でやったこと。SGLang の統合・分離の両方の設定ファイル (chart) を作り(1 節)、交通整理役を標準品に替える版も作り(2 節)、実機の GPU 2 台で 5 通り全部を動かして確認した(3 節)。途中、既存の確認手順が実は間違っていたこと(4 節)、ネットワーク設定の既定値が思いがけず外部に公開される設定になっていたこと(5 節)、交通整理役の暗号化通信の設定の食い違い(6 節)を見つけて、全部直した。

1. SGLang 版の chart を、vLLM 版と同じ形で作る

vLLM 用に既にあった「統合(1 台)」と「分離(2 台、prefill と decode を分ける)」の設定ファイルを手本に、同じ項目名・同じ考え方で SGLang 用を作った。違うのは、2 台をつなぐ転送方式(SGLang 独自の方式か、NIXL という共通規格のどちらか)と、交通整理役(SGLang に同梱の router)だけ。

2. 交通整理役を標準品(llm-d / Gateway API Inference Extension)に替える

これまでの分離推論は、手作りの小さな中継プログラムが「まず質問を prefill に送り、その答えの材料を decode に渡す」という 2 段階を仲介していた。業界で標準になりつつある仕組み(llm-d という OSS プロジェクトの Gateway 経由の方式)に替える版も作った。この方式では、Kubernetes の標準規格(Gateway API)の上に、どのサーバーに質問を振るかを決める専用の部品(EPP、Endpoint Picker)が乗る。

1 回目の確認では、EPP は正しく 2 台のサーバーを認識し、「質問はこちらの decode に、答えの材料はあちらの prefill から」という振り分けの準備までは正しく動いていた。しかし実際に質問を送ると、Gateway 自身(通信の窓口になるソフトウェア)が EPP への内部通信でエラーを起こし、500 エラーが返ってきた。原因と直し方は 6 節にまとめた。

3. 実機の GPU 2 台で、5 通り全部を動かした

EFA(高速ネットワークカード)付きの GPU インスタンスを 2 台借り、Kubernetes クラスタを一から作って、5 つの組み合わせを順番にインストールして試した。

4 つの組み合わせ(vLLM の統合・分離、SGLang の統合・分離)は、実際の質問に対して正しい答えが返り、負荷テスト(一定間隔で 40 件の質問を流す)も全件成功した。EFA(高速ネットワークカード)を実際に転送が通ったことも、転送前後の通信量の変化から確認した。

4. 既存の確認方法が実は間違っていたこと

vLLM の分離推論の README には、「転送が EFA を通ったかは、このネットワークの値を見れば分かる」という確認方法が書かれていた。実際に試すと、その値は転送中も一度も変化しなかった。調べると、vLLM の既定の転送方式は「答えを書く側(decode)が、材料を持っている側(prefill)から自分で取りに行く」仕組みで、その場合に増えるのは別の値だった。既存の確認方法は、逆方向(書き込み側)の値を見るように書かれていたため、実際には何も確認できていなかった。README を直し、正しい値と、それを読むための動くコマンドに書き換えた。

5. 公開されるはずのない通信窓口が、実は外部公開の設定になっていた

Gateway(交通整理役の窓口)を作るソフトウェア(NGINX Gateway Fabric)は、何も指定しないと「外部のインターネットからアクセスできるロードバランサー」を自動で作る既定値を持っていた。クラスター内だけで使うつもりだったのに、実際に試したところ、本物の、認証も何も無いロードバランサーが AWS 上に作られていたことが分かった。見つけてすぐに「クラスター内限定」の設定に直し、ロードバランサーが実際に消えたことも AWS 側の API で確認した。この落とし穴は、今回使った交通整理役のソフトウェア自体の既定値の問題なので、README に目立つように書き、上流(ソフトウェアの開発元)への報告候補としても記録した(https://github.com/littlemex/distai-platform/issues/49へのメモ)。

6. 追い確認: llm-d 経由の 500 エラーを直し、SGLang の受信側も確認した

500 エラーの原因は、Gateway を作るソフトウェア(NGINX Gateway Fabric)自身の設定だった。「EPP との通信は暗号化なしにする」という設定を自分で入れていたが、EPP 自身は何も指定しなければ暗号化ありで待ち受ける作りになっていた。双方の思い込みが食い違っていたため、接続がすぐ切られてエラーになっていた。

直し方は単純で、「暗号化なしにする」という設定を入れないこと。Gateway 側の既定(暗号化はするが、証明書までは確認しない)のままにすれば、EPP 側の既定(暗号化あり、自前の証明書)とそのまま噛み合う。実際にこの設定を外して質問を送ったところ、正しい答えが返ってきた。さらに、EPP 自身が「振り分けた回数」を数えているカウンタと、EPP 自身の詳しいログの両方で、1 件の質問ごとに「decode への判定」と「prefill への判定」の両方が実行されていることを確認した。質問を送った回数とカウンタの値も一致した。

あわせて、公開ロードバランサーの対策(5 節)も最初から安全な順番(先に「クラスター内限定」の設定を作ってから Gateway を作る)に直し、今回は一度も公開ロードバランサーが作られないことを確認した。

SGLang の分離推論(1・3・4 節)についても、前回は送信側(prefill)のネットワークの値しか見ていなかった。追い確認で受信側(decode)の値も読み、送信側の送った量と受信側の受け取った量が 1 バイトも違わず一致することを確認した。

7. まだ終わっていないこと

SGLang の chart は、まだ自動テストの対象に入っていない部分がある。vLLM 側にある「配置とネットワーク設定が正しいか」の自動チェックは、SGLang 側にはまだ無い。

SGLang の Mooncake 転送方式や、prefill:decode の比率を変えた場合は未確認。今回は NIXL 方式・1:1 の比率のみ。

まとめ。SGLang という 2 つ目のエンジンでも分離推論が動くことを実機で確認し、交通整理役を業界標準の仕組みに替える試みも行った。5 つの組み合わせ全部が、最終的に実機で完走した。途中で見つけた既存の確認方法の誤り、意図しない外部公開の設定、交通整理役の暗号化通信の設定の食い違いは、どれも実機で動かしてみなければ気付けなかった類のものだった。

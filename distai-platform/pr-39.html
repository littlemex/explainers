PR #39: capacity-pool に root volume・EFA ENI・flex の既知の限界を足す
capacity-pool: optional root volume size, optional EFA network interfaces, flex single-instance-type limitation

レビュー中ブランチ fix/capacity-pool-node-options (feat/17-capacity-pools の上に積む)commit 79c9c4a3 ファイル変更

結論から。このPRは capacity-pool chart (GPU や Trainium のノードを Karpenter 経由で作る共通 chart) に、3 個の小さな追加をする。どれも Issue #28 (accel-nvidia/accel-neuron の add-on を実機で検証する作業) の途中で見つかったが、chart 自体の穴なので Issue #28 のブランチではなく、この独立した PR に切り出した。1 個目は root volume (ノードのディスク) のサイズを指定できるようにするもの、2 個目は EFA (高速ネットワークカード) を要求する ENI 設定を足すもの、3 個目は chart の挙動ではなく、「1 種類のインスタンス型しか指定していない flex プールは、spot に固執して on-demand に切り替わらないことがある」という上流 Karpenter の挙動を README に書き残すもの。

なぜ 3 個まとめて 1 本の PR か。どれも Issue #28 の実機検証 1 回の中で見つかったが、chart 自体の変更なので Issue #28 のブランチ (PR #40) には乗せず、他の 2 件の作業 (Capacity Block の計画、分離推論の EFA 検証) も同じ chart の同じ穴にぶつかっていたため、1 本の chart 拡張として切り出して先に通す。PR #40 はこの PR の上に積まれる。

1. root volume が足りないノードが「idle」に見えて消される

capacity-pool chart の EC2NodeClass は root volume のサイズを一切指定していなかった。そのため、ノードはイメージが入っている AMI の既定サイズのディスクで起動する。重い検証用イメージ (Neuron SDK の 7.5 GiB イメージ) を pull すると、このディスクが尽きる。

修正は pool.rootVolumeSizeGi (既定は空文字列で挙動は変わらない) を EC2NodeClass.spec.blockDeviceMappings に足すだけ。この穴は Issue #28 の検証用フィクスチャだけの話ではなく、capacity-pool chart を使う誰でも、現実的な大きさのコンテナイメージを動かせば同じ失敗に当たる。実際、Capacity Block の計画と分離推論の検証という、無関係の 2 つの作業が同じ chart の同じ穴に独立に当たっていた。

2. インスタンス型が 1 種類だけの flex プールは、on-demand の空きがあっても spot に固執する

pool.capacityType: flex (spot も on-demand も使う設定) にした trn2.3xlarge 専用プールは、30 分間ずっと spot だけを試し続け、一度も on-demand を要求しなかった。on-demand の容量自体は dry-run で確認済みで、空きはあった。

これは chart のバグではない。helm template で差分を見ても flex と on-demand のレンダリング結果は karpenter.sh/capacity-type の値以外、1 バイトも変わらない。原因は 2 つの事実の組み合わせ: (1) この trn2.3xlarge 専用プールには乗り換え先の 2 つ目のインスタンス型が無い (GPU プールは g7/g6e/g5 の 3 種類あるので同じ flex で普通に on-demand へ落ちられる)、(2) trn2.3xlarge には on-demand の価格情報自体が AWS の Price List API にまだ無い。PR はこれを chart の挙動として直すのではなく、capacity-pool/README.md の「既知の限界」として書き残した。

3. EFA (高速ネットワークカード) は、対応インスタンス型を選ぶだけでは付かない

見つかった経緯。分離推論の EFA 検証用に、us-east-1 で g7.8xlarge の 2 ノードプールを新規に組んでいる最中に見つかった。g7.8xlarge は EFA 対応インスタンス型だが、Karpenter は「対応している」だけでは EFA デバイスを付けない。EC2NodeClass.spec.networkInterfaces で明示的に要求しないと、ノードは起動してもネットワークカードは 0 枚のままで、この失敗は Pod レベル (EFA の device plugin が広告するリソースが 0 個) まで降りてこないと見えない。

直し方。任意項目 pool.networkInterfaces を足した。既定は空配列で、既存プールのレンダリング結果は 1 バイトも変わらない。ネットワークカード/デバイス番号/インターフェース種別はインスタンス型ごとに違うので、chart が勝手に既定値を決めることはできない (値を渡すプール側の責務)。on-demand/flex/reserved の 3 通りに pool.networkInterfaces の有無を掛けた helm template の比較と、実機の g7.8xlarge 2 ノードで検証済み。

レビューで見てほしいこと

  • 3 個の追加はいずれも既定値で挙動が変わらないこと (rootVolumeSizeGi は空文字列、networkInterfaces は空配列)。既存の全プールが無傷かを helm template の差分 0 件で確認してほしい。
  • flex の既知の限界は chart の修正ではなく README への記載のみであること。Karpenter 本体・AWS の Price List API 側の問題であり、この chart の責務の外にあると判断した理由に同意できるか。

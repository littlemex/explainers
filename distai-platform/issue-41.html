部品を3層に分け、セルごとに選べるようにする仕組み
Issue #41 (RFC) の解説

結論から。今の distai-platform は、admin が用意した部品 (karpenter、kueue、GPU/Trainium の device plugin など) を gitops/addons/ に置くと、登録した全クラスタに無条件で配られる。これは「外さなくていい部品」には正しいが、監視 (dcgm-exporter) や社内ビルド環境 (BuildKit) のような「要るセルだけに入れたい部品」には合わない。Issue #41 は、部品を core (外せない)・platform-optional (admin が配る、セルごとに選べる)・workload (チームが選ぶ) の3層に分け、セルごとの選択 を既存の仕組みの延長だけで (新しい CRD もコントローラも作らずに) 実現する設計を提案した。Fable 5.2 による見直しを13 回かけて、見つかった設計の誤りと安全上の穴を全部直し、最終版で「直す点なし」の承認を得た。

この文書でやったこと。既存の実装 (PR #40 の platform.ApplicationSet.yaml / cells.ApplicationSet.yaml) を読んで今の挙動を確かめ、元の distributed-ai (Terraform で監視・BuildKit を入れている) と upstream の awsome-distributed-ai (観測の2つの流儀) を調べ、それを踏まえて設計をレビューにかけた。実装はしていない (この RFC はまだ Issue のみ)。

0. 何に困っていたか

実装を読むと、platform.ApplicationSet.yaml は gitops/addons/*/addon.yaml を1本ずつ読み、登録されている全クラスタに配る。GPU/Trainium の device plugin のような「要らないセルに入っても costs 0 (ノードが無ければ DaemonSet は単に起動しない)」部品にはこれで良いが、監視スタック (Prometheus 一式で数 GB のメモリと専用ノードが要る) や BuildKit (特権に近い namespace が要る) は、入れたくないセルにまで配ってしまうと、課金とセキュリティの両方で無駄がある。これを選べるようにする仕組みが今まで無かった。

2. セルごとの選択はどう決まるか

セルが監視 (dcgm-exporter) を入れたいなら、gitops/cells/<セル名>/addons/dcgm-exporter.yaml という小さなファイルを置く。これだけで、新しい addons-optional.ApplicationSet.yaml がそのセルにだけ Application を作る。ファイルが無いセルには何も作られない。これは、容量のプール (capacity-pool) や smoke テストが今すでに使っている「クラスタの名前でパスをテンプレート化した Git file generator」の仕組みをそのまま使い回しているだけで、新しい Argo CD の機能は一切要らない。

この marker ファイルは、gitops/addon-catalog/ に書かれた「正本」(版・場所・許可リスト) と内容が一致しているかを、PR の時点で (実機に適用する前に) 自動で確かめる。版がずれていたり、許可されていないキーを書いていたりすると、その場で CI が落ちる。

4. レビューで見つかった、直した大きな勘違い

最初の案は「セルの marker ファイルは、正本のファイルを参照するだけで値は書かない」という形だったが、これは Argo CD の ApplicationSet が 1つのファイルからしか値を作れないという実際の仕組みと食い違っていた (2つ目のファイルを「参照」で読み込む機能は無い)。直した形は、容量のプールが今すでにやっている通り、marker ファイルに値をそのまま書き、CI が正本と一致しているかを別途確認する、というもの。

もう1つの大きな指摘は、Argo CD の RollingSync (順番を強制する機能) が、実はこの基盤が使っている EKS 管理の Argo CD ではまだ効いていない (実機で確認済みの既知の事実) こと。これを踏まえて、依存関係のある部品 (例: dcgm-exporter は Prometheus が要る) が今どうやって動くか (順番が逆でも、Application が自分で再試行して追いつく) を、ごまかさずに書き直した。

5. GPU/Trainium を同等に扱う原則との関係

最初の案では、GPU 用の dcgm-exporter だけ値を用意し、Trainium 用の neuron-monitor は「後で考える」で済ませていた。これはこのリポジトリの標準原則 (GPU と Neuron を同じ扱いにする) に反すると直し、neuron-monitor も dcgm-exporter と同じ基準の Issue を同じタイミングで立てる形にした。参考にできる既存の実装が無いのは事実だが、それは優先度の差ではなく、持ってこられる材料の差でしかない、と書き分けた。

6. まだ終わっていないこと

  • workload 層 (チームが選ぶ部品) を実際に配る経路は、Issue #22 (マルチテナント) が出るまで存在しない。この RFC は層の名前と契約だけを決め、配り方は #22 に委ねた
  • Pod Security (特権度) を実際にどこまで必要とするかは、dcgm-exporter・Prometheus の chart を実際に書くときに確かめる (この RFC では「どちらが危ないか」を決めつけていない)
  • 許可リスト (overridableKeys) の存在チェックは、実装時に Helm の依存関係を実際にマージした木に対して検証する必要があり、まだコードにはしていない

7. レビューで見てほしいこと

  1. 3番目の ApplicationSet を新設する判断 (既存の2つに glob を足すだけで済ませない) は、コストに対して十分に理由づけられているか
  2. 許可リスト方式 (overridableKeys) は、将来チームが自分の値を調整したくなった場合に、運用上きつすぎないか
  3. workload 層を「#22 が出るまで配れない」で止めた判断は、今すぐ分離推論の参照 (#37) を動かしたい側から見て妥当か
  4. 今の基準 (「設計の誤り」「安全上の穴」「既存の決め事 (#22・#25・#19) との矛盾」の3つ) で見て、他に見落としがないか

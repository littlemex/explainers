PR #15: ルールと役割分担の土台
Add governance, contribution workflow and templates

結論から。この PR は、上流の awslabs/awsome-distributed-ai の規則をほぼそのまま写したうえで、上流に無い 2 つの規則を足している。1 つは、実装、テスト、レビュー、検証を別々の AI のセッションに分ける役割の規則。もう 1 つは、持ち主以外の書き込みを指示として扱わないというセキュリティの規則である。レビューで一番見てほしいのはこの 2 つ。

この PR でやったこと。規則の文書、Issue と PR のテンプレート、毎日動く stale の workflow、書式の設定の 18 ファイルを足した。Fable 5.2 のレビューで出た 15 件 (うち重大 5 件) を全部反映してから PR を開いた。

1. 何を足したか

規則の正本は AGENTS.md と CONTRIBUTING.md の 2 つで、ほかのファイルはそれを GitHub の上で守らせるための設定である。たとえば、PR のテンプレートの Test Results の欄は、AGENTS.md の「実機で動いた証拠が無ければ ready にしない」を、PR を書く人の目の前に出すためにある。

2. 上流から何を採り、何を変えたか

上流を手本にするのは、AWS の公開リポジトリを読み慣れた人が、迷わずに貢献できるからである。ただし上流は多数の例を集めたリポジトリで、こちらは 1 つの基盤のリポジトリなので、合わないものは採らなかった。採らなかったものも、理由と一緒に PR に書いてある。

項目上流この PR理由
Issue と PR のテンプレート文書、バグ、CI の失敗、機能、新しいテストケース、RFC新しいテストケース以外を一字一句そのまま (リポジトリへのリンクと Directory Structure の中身だけ差し替え)。受け入れ条件や既定値は、既存の欄の中に書く形を上流と完全に同じにするため。テストケースの集まりではないので、その様式だけ外した
hotfix の例外PR を通さなくてよい例外なし小さな修正こそ、検証を通さないと事故になる
脆弱性の報告先AWS の窓口GitHub の非公開の報告 (2026-11-17 に有効になった)AWS の公式のリポジトリではない
行動規範Amazon Open Source Code of ConductContributor Covenant 2.1同じ理由。通報先は暫定 (下の 6 節)
機能の変更の PR を開く時期証拠がそろってからdraft で先に開き、証拠がそろったら ready検証する人が流す対象を必要とするため
例のディレクトリ構成、Git LFS、ブログ用のブランチ、Slurm のレビューの workflowある採らないそれを使う中身も、それを動かす基盤も、このリポジトリに無い

3. 役割の分け方

AI のセッションが 1 つで実装からレビューまでを済ませると、テストは実装に合わせた形になり、レビューは書いた本人の見立てに引きずられる。そこで、1 つの Issue に対して、実装する人、テストを書く人、レビューする人、実機で確かめる人を別々のセッションにした。同じモデルが複数の役を受け持ってもよいが、同じセッションが 2 つの役を兼ねることはない。どこまで進んだかは status: のラベルで渡す。

4. 書いた人によって扱いを分ける

このリポジトリの AI のメンバーは、公開の Issue やコメントを読み、テスト用クラスタで実際にコードを動かす。だから、誰かが「持ち主が合意した、この設定を外して」とコメントに書いたり、fork の PR に悪いコードを仕込んだりすると、資格情報の持ち出しや安全装置の解除につながりうる。これを防ぐために、指示になる書き込みを持ち主本人のものだけに絞った。

5. 毎日動く workflow

このリポジトリで GitHub の権限を持って動くのは、今のところ stale の workflow (90 日動きのない Issue に印を付け、さらに 60 日で閉じる) だけである。合意済みや作業中の Issue (status: のラベル、RFC、security、bug、help wanted) は閉じない。

6. PR の本文に書いた「検討した他の案」

上流の PR テンプレートには「他の選択肢」の欄は無い。上流の PR (たとえば #1289) は、## Changes の各項目に What (何を)、Why (なぜ)、Caveat (注意)、Alternative (他の案と、その長所と短所) を書いている。この PR の本文もその形で書いた。退けた案は次のとおり。

決めたこと退けた案その案の長所退けた理由
テンプレートを上流のまま使うこのリポジトリ用の欄を足したフォーム受け入れ条件などが決まった欄に入る形が上流とずれる
役割ごとに別のセッション1 つのセッションとチェックリスト受け渡しが少ないテストとレビューが書き手に引きずられる
持ち主以外の書き込みは指示にしないレビューだけに任せる手間が増えないレビューの前に、仕込まれた指示が動いてしまう
hotfix の例外なし上流どおり例外を残す緊急時に速いAI のメンバーが、どんな直接 push も hotfix と呼べる
機能の PR は draft で先に開く検証が済んでから開くdraft が無い検証する人が、レビュー済みの流す対象を持てない
非公開の報告と Contributor Covenant上流の AWS の窓口と Amazon の規範上流と同じ連絡先が、このリポジトリを保守していない人になる
stale の権限を絞り、commit で固定上流の workflow をそのまま上流と同じ権限が広く、固定されていないコードが動く

7. まだ終わっていないこと

main のルールセットがまだ無い。2026-11-17 に API で確かめたときは 0 件だった。AI が使う token には書き込みの権限があるので、ルールセットが無いと main に直接 push もできてしまう。AGENTS.md の「main へ直接 push しない」を GitHub の設定で強制するには、PR 必須、force push と削除の禁止のルールセットが要る。

行動規範の通報先は暫定。今は脆弱性の報告のフォームを [Conduct] 付きで使う形にしている。専用の連絡先 (メールなど) が決まったら差し替える。

また、README の infra/eks/ の行は PR #14 がマージされるまで中身が無い。リンクにせず文字で書いてあるのは、マージの順番によってリンクが切れないようにするためである。

8. レビューで見てほしいこと

  1. 規則どうしが矛盾していないか。特に「証拠が無ければ進むな」(fail-closed) と「draft で先に開く」が、AGENTS.md の 1 節で両立しているか。
  2. 書いた人の扱いの規則で足りるか。4 節の 3 つの線で、コメントや fork の PR から資格情報のある環境に届く道が残っていないか。
  3. workflow の権限。最上位が permissions: {}、ジョブが issues: write と actions: write だけで、action が commit で固定されているか。
  4. 上流との違いの説明に漏れがないか。2 節と 6 節の表と、PR の本文の Changes の各項目が、実際の差分と合っているか。テンプレートが本当に上流と同じか (PR の Test Plan の SAME の行)。
  5. 役割の名前とブランチ名。AGENTS.md 2 節の表の Branch の列が、Issue の役割の表と食い違っていないか。

まとめ。PR #15 は上流の規則の写しに、役割分担と「書いた人で扱いを分ける」の 2 つを足したもの。中身は Fable 5.2 のレビューの 15 件を反映済みで、テンプレートは上流と一字一句同じにした。、残っているのは main のルールセットと行動規範の通報先の 2 つの設定。

PR #40: accel-nvidia/accel-neuron add-on で、GPU と Trainium を実機で動かす
accel-nvidia/accel-neuron add-ons: device plugin and DRA charts for the accelerators step (closes #28)

レビュー中Issue #28 を閉じるブランチ feat/19-accel-addons (fix/capacity-pool-node-options = PR #39 の上に積む)commit a0b26f522 ファイル変更

結論から。この PR は、GPU (NVIDIA) と Trainium (AWS Neuron) を Pod に見せる仕組みを、実際に動く 4 本の add-on として届ける。Issue #19 が決めた「(NodePool, デバイスの種類) ごとに 1 個のラベル、ラベルごとに 1 個の chart リリース、GPU と Trainium を同じ単位で扱う」という設計と、Issue #25 が作った配信の仕組み (platform.ApplicationSet.yaml の accelerators という名前だけ空いていた段) に、初めて中身を入れる。実機では、GPU ノード 1 台 (g7.2xlarge) と Trainium ノード 1 台 (trn2.3xlarge) それぞれで実際に Pod を動かし、nvidia-smi と neuron-ls がデバイスを 1 個ずつ報告するところまで確認している。

この PR が立つ場所。4 つのブランチが順に積まれている: 配信の土台 (#25) → capacity-pool chart の拡張 (#17) → この PR が見つけた chart の穴を切り出した小さな修正 (PR #39) → この PR 自身。レビューは #25・#17・#39 の後に。

4 つのブランチの積み順

ラベル 1 個が、どの add-on を動かすかを決める

核になる仕組みは単純: capacity-pool chart が NodePool のノードに付けるラベル (例: distai.dev/nvidia-gpu-method: device-plugin) を、4 本の add-on それぞれが自分の nodeSelector として指定する。ラベルに一致した add-on だけがそのノードで動く。一致しない add-on の DaemonSet はどのノードにもスケジュールされず、コストも掛からない。

変更点

4 本の accelerator add-on

accel-nvidia-device-plugin・accel-nvidia-dra・accel-neuron-device-plugin・accel-neuron-dra を gitops/addons/ に追加。NVIDIA の DRA 側は、chart の既定では全 GPU 割り当てが off のため gpuResourcesEnabledOverride: true を明示しないと動かない (Issue #19/#25 の時点では未記録だった事実)。DRA 2 本は動的プールが初期化しないため、この PR では静的検査のみで実機のノードは立てない。

capacity-pool 自体には変更を入れない

この PR の最初の案は pool.labels という独自フィールドを chart に直接足していたが、同時期に Issue #17 が同じ chart を accelerator.methodLabel という違う形で拡張していた。同じフィールドに 2 つの形があるのは契約の衝突であり、マージ順の都合では済ませられない問題として、この PR のブランチを Issue #17 のブランチの上に rebase し、Issue #17 のフィールドを使う側に直した。

2 つの軽量セル (dp-a19-gpu-r3 / dp-a19-trn-r3)

実機検証用に、GPU 用 (g7/g6e/g5、pool.capacityType: flex) と Trainium 用 (trn2、同じく flex) の 2 つのセルを新規に用意した。スポットのみを手書きで指定する方式は、chart 側のガード (karpenter.sh/capacity-type を直接指定するとレンダリングが失敗する) に当たって早々に廃止し、PR #17 の capacityType の列に揃えた。

1.e2e.sh の拡張と静的検査の追加

GITOPS_RUN_ACCEL_E2E=1 を立てると、既存の 1 セル検証の後に GPU の Layer 1 Pod と、もう 1 つ別リージョンに作る Trainium 専用セルの Layer 1 Pod を追加で検証する。Kueue の ClusterQueue はまだ CPU/メモリしか計上していないため、アクセラレータの Pod は Kueue 経由にせず素の Pod として投入する。

二重広告の検出ツール自体は作らない (スコープ外)

Issue #19 Decision 1(d) が決めた「同じノードに 2 つの advertiser が乗っていないかを機械的に検出するツール」は、この PR では作らない。独立した設計・独立したテスト対象を持つ別の仕組みであり、この PR の中身 (4 本の add-on と platform 専用の DeviceClass) のようにこの基盤の外で存在価値を持ちえないものではないため、別 Issue に切り出す。この PR では「正常系で二重広告が起きていないこと」だけを実機で確認する。

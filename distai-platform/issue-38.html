AI セッションどうしでタスクを引き渡す仕組み
Issue #38 (RFC) の解説

結論から。AI の作業セッション (Mac、EC2、将来はクラスタの中) が途中で落ちたり、交代したりしても、高価な予約 (Capacity Block など) を取り残さず、同じ作業を 2 回やらず、別のセッションが安全に続きを拾えるようにする仕組みを Issue #38 として提案した。DynamoDB の小さな台帳 (Ledger) と、権限を絞って渡す窓口 (ブローカー) の 2 つだけで作る。Fable 5.2 による見直しを 6 回かけて安全性を詰め、実機 (EC2) でプロトタイプを動かして 26 項目すべて通った。

この文書でやったこと。設計の全文 (日本語ではなく英語、150KB 超) を Fable 5.2 で 7 回レビューし、Issue 本文はその要点を 65,000 字弱に絞って書いた。検証は、設計が決まった後の最終形に対して、安全性にかかわる主張 (二重に取れない・期限切れで拾える・権限が絞れる) だけを選んで実機で確かめた。

0. 何に困っていたか

distai-platform では、GPU や Trainium の予約 (Capacity Block) を取ると、安いときでも 1 日 24 時間ぶんの課金がすでに発生している。これまでは、この予約を使い切るまで 1 つの AI セッションがずっと動いているという前提だった。しかし実際には、セッションは Mac でも EC2 でも、文脈の長さや時間で区切られて終わる。バックグラウンドに回すこともあるし、強制終了されることもある。そうなると、

  • 予約の残り時間を、誰も使わないまま放置してしまう (お金が無駄になる)
  • 別のセッションが「続きをやろう」としたときに、前のセッションがまだ生きていて、同じ作業を 2 回やってしまう
  • 検知の仕組み (Claude Code の hook) が必ず動くとは限らない。動かないことを前提に設計する必要がある
  • 今のセッションは、必要以上に広い AWS の権限を持ったまま動いている

この 4 つを、クラスタが無い Mac でも、EC2 でも、将来のクラスタの中の Pod でも同じ仕組みで解く、というのが Issue #38 の中身である。

1. 何を作るか: 台帳とブローカー

仕組みは 2 つの部品だけでできている。台帳 (Ledger) は「どのタスクを、誰が、いつまで持っているか」を記録する、DynamoDB の小さな表。ブローカー は、台帳への書き込みと、作業に必要な AWS の権限 (絞ったもの) を渡す、唯一の窓口。AI セッションは台帳を直接書けない。読むことと、ブローカーに頼むことしかできない。

2. 動いている様子 (3 つの場面)

場面 A: 24 時間の予約を 2 つのセッションで引き継ぐ

次の 24 時間の Capacity Block (p5en × 2 台) は、前半をこの基盤自体の検証、後半を別の実験に使う計画。前半を担当したセッション A が終わる (あるいは落ちる) と、別のセッション B が「後半はもう始めてよい」ことを台帳から見つけて拾う。B は Kubernetes が全く無い、裸の EC2 の上でも同じ仕組みで作業を引き継げる。ただし、この仕組みが保証するのは「2 つのセッションが同時に同じタスクの権利を持たない」ことだけで、「前半が終わるまで後半を始めない」という順番そのものは、まだ自動化していない (下の「まだ終わっていないこと」)。

場面 B: クラッシュしたセッションを、二重実行なしで引き継ぐ

セッション A が作業中に強制終了され、台帳への「まだ生きています」の返事 (ハートビート) が止まる。セッション B が取りに行くと、台帳はすぐには渡さず、決められた待ち時間だけ待たせる。この待ち時間はブローカー自身の時計で測る。A や B 自身の時計 (ノート PC がスリープしていた場合などにズレる) は一切使わない。待ち時間が過ぎてもまだ誰も更新していなければ B が引き継ぎ、もし A が後から復活してハートビートを送っても、台帳はそれを拒否する。

場面 C: 危険な作業には人の承認 (Go) がいる

破壊的・高額な作業は、あらかじめ管理者が決めた一覧 (AI は選べない) によって「人の承認が無いと取れない」設定になる。AI は別の種類の作業を選んで承認を回避することもできない (その種類の作業にそもそも危険な権限が無いように管理者側で決めてあるため)。承認は「どの内容を承認したか」のハッシュ値に固定されるので、承認された後に内容が変わると、古い承認は自動的に無効になる。

3. 検証で見つかった実装上のミス (5 件)

実機で実際にコードを動かしたことで、設計の文章だけでは見つからなかった実装のミスが 5 つ見つかり、その場で直した。

  1. IAM の API 呼び出しのパラメータ名を 1 つ間違えていた
  2. DynamoDB から読み戻した数値が Python の Decimal 型になり、ハッシュの再計算が壊れる (書いた時の型と比較できなくなる) バグ
  3. テストコードの中で plan という予約語を使ってしまい、DynamoDB の更新式が構文エラーになった
  4. 最も重要な発見: 権限を渡す側のコードが、ブローカー自身の認証情報ではなく、たまたまその場にあった広い権限 (管理者相当) を使ってしまっていた。これは「権限が絞られているはずの経路を、間違った認証情報が素通りしてしまう」という、まさにこの仕組みが防ぎたかった種類のミスで、実機で動かした瞬間に権限エラーとして検出できた
  5. さらに、AWS の実際の仕様として「絞るための Deny だけを書いたセッションポリシーは、何も許可していないのと同じ (交差で全部ゼロになる)」ことが分かった。絞るときは「まず全部許可してから、絞りたい部分だけ Deny する」という書き方が必要で、設計の文章にはこの精度までは書かれていなかった

5 つとも、設計 (DynamoDB の条件付き書き込みという仕組み自体) のバグではなく、実装コードの側のミスだった。文章のレビューだけでは絶対に見つからない種類の発見で、これが「実機で動かす」ことの価値である。

4. 他の方法と比べた理由

候補採用しなかった理由
Kueue の Workload に印をつけるKueue は「資源をタスクに割り当てる」ことしかしない。誰が持っているか・取り戻せるかは一切解釈しない、ただの飾りになる
Kubernetes の Lease (coordination.k8s.io)仕組み自体は正しいが、Kubernetes のクラスタが無いと使えない。Mac だけで動く場面に対応できない
GitHub の Issue のラベルや本文GitHub の書き込みには「同時に 2 人が書いたら片方だけ勝つ」という保証がない。人が読む場所としては使うが、実際の取得・解放はここでは行わない
Temporal / AWS Step Functions保証の形としては近いが、常時動くサーバやサービスを新たに運用する必要がある。今の作業量 (同時に数件) には重すぎる
SQS の visibility timeout「もう一度配達されないことを保証しない」仕組みで、取りこぼしへの対策が結局別に必要になる

5. 0 節 (Neuron を GPU と同等に扱う) との関係

この仕組みは、アクセラレータの種類はおろか、Kubernetes があるかどうかさえ問わない。だからこそ、distai-platform の中にしか無い専用の層ではなく、独立した小さな OSS として切り出し、distai-platform はその最初の利用者になるという判断にした (Decision 12)。これは、このリポジトリの標準原則「ここでしか使えない高度な抽象化は NG。汎用に使える仕組みは独立 OSS として切り出す」をそのまま適用した結果である。

6. まだ終わっていないこと

  • 実際のハードウェア MFA (多要素認証) での承認は未検証。IAM Identity Center のセッションで MFA の条件キーが実際に立つかどうかも未確認
  • Kueue に実際に結びつける部分 (同じ名前での再提出、専用の ClusterQueue) は、実際の EKS クラスタが要るため、最初にこの仕組みを使う PR に持ち越し
  • 一時停止 (park/resume)・失敗からの再試行・掃除役 (sweep) などは設計とレビューは済んでいるが、今回の実機検証では回していない
  • 「前半が終わるまで後半のタスクを作らない」という順番の制御は、まだ運用上の決め事であり、コードでは強制していない

7. レビューで見てほしいこと

  1. 独立した OSS に切り出す判断 (Decision 12) は、distai-platform の中に置く案と比べて十分に理由づけられているか
  2. 人の承認 (Go) の窓口を、ブローカーの他の処理と別の Lambda に分け、その関数だけ呼び出し元を絞る設計は十分か
  3. ブローカーが単一障害点になっている点 (落ちている間は新しい引き継ぎが止まる) の割り切りは妥当か
  4. 今の基準 (「設計の誤り」「安全上の穴」「読み手が誤解する説明」の 3 つ) で見て、他に見落としがないか

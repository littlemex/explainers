1. どの部品を選んだか: JobSet vs Kubeflow Trainer v2 vs Training Operator v1

複数の計算機を使う学習をするには、「全部そろうまで動かさない」「1 台落ちたら全体を揃えてやり直す」という決まりを持つ部品が必要になる。候補は 3 つあった。決め手になったのは、この基盤がすでに入れている Kueue (Queue という名前の、仕事の順番待ちと入場審査をする部品) の設定ファイル自身が、JobSet を最初から有効にし、Training Operator v1 (PyTorchJob という古い形) をコメントアウトして無効にしていたことだった。

JobSetKubeflow Trainer v2Kubeflow Training Operator v1
Kueue の「全部そろうまで」への対応最初から有効最初から有効 (JobSet を内部で使う)この基盤の Kueue の設定では無効 (コメントアウト)
保守の状態kubernetes-sigs が今も頻繁に更新今も頻繁に更新 (新しい方の主力)最後の更新から時間が経っている (古い方)
チームが自分の namespace の中で使えるか権限を 1 行足すだけ (今回それをした)同じく 1 行で足せるが、部品 (CRD) が 3 つ増える同じく 1 行で足せる。だが上の行が無効
学習の中身 (NCCL/EFA の設定) との関係何もしない。コンテナの中の環境変数で決める同じく何もしない同じく何もしない
部品の数CRD 1 個CRD 3 個 (TrainJob/TrainingRuntime/ClusterTrainingRuntime)CRD 1 個 (PyTorchJob)

Kubeflow Trainer v2 は裏側で JobSet をそのまま使っているので、今回入れた JobSet の配線は Trainer v2 を後から選んでも無駄にならない。今回は「ただのコンテナを 1 個動かす」だけなので、3 つの CRD を増やす Trainer v2 より、素の JobSet の方が部品が少なくて済む。

2. CRD と controller を分けて配る

JobSet の提供元は、Karpenter のように「CRD だけの chart」と「controller の chart」を別々には配っていない。1 つの chart に両方入っている。そこで、CRD だけを手で書き写した chart を新しく作り、controller 側には skipCrds: true (CRD を持たせない設定) を付けて、2 つの Argo CD の「Application」(配る単位) に分けた。

こうする理由は、CRD は「どのセルにも最初から入っている土台」として扱い、学習をするかどうかに関係なく存在させたいからである。学習をやめたセルで CRD を消すと、そのセルの JobSet が全部壊れてしまう。

3. チーム自身が使えるようにする

この基盤には「チームの namespace の中で、チームが作ってよい物の一覧」(team-rbac-guard という許可リスト) がある。そこに JobSet が入っていなかったので、チームは JobSet を 1 個も作れない状態だった。jobset.x-k8s.io という種類を、jobs や deployments と同じ扱い (作成・変更・削除すべて許可) で 1 行足した。実機でも、チームの ID で JobSet を作れること、jobsets/status (直接の変更はさせたくない部分) は拒否されることを両方確認した。

5. 実機の結果

1 回目の実機確認は失敗した。原因は chart のバグではなく、検証用に自分で作ったセルの GPU の枠が小さすぎたこと (上の表の「既定」の行) だった。レイアウトを「2 台に GPU 1 枚ずつ」に変えた 2 回目で、4 つの約束すべてが PASS した。使った実際の GPU の時間は 2 回合わせて約 18 分で、許されていた上限 (2 時間) のかなり内側だった。片付け (terraform destroy) は「101 個削除」で終わり、別に取った消し残しの確認 (インスタンス・ロードバランサー・IAM など) もすべて 0 件だった。

6. レビューを 3 回半回し、途中で見つけた本物の事故

自分でコードと設計を見直したあと、Fable という名前の別のモデルに 3 回レビューしてもらい、どの回も実際にコードを直した。最後に小さな確認を 1 回追加で行った。

  1. 1 回目 (実機の前)。values.yaml を使ったときだけ出る、数字が「1e+06」のような指数表記になって学習が落ちるバグを見つけて直した。Python のコードが 3.12 以降でしか動かない書き方も直した。
  2. 2 回目 (実機の後)。1 回目の直し方が「一時停止の秒数」にまで適用されていて、0.5 秒が 0 秒に切り詰められるバグを新たに作っていたのを見つけて直した。README が「動かした形」と「動かしていない形」を逆に書いていた箇所も直した。
  3. 3 回目 (最終)。コピペして使う一続きの手順 (Test Plan) の中に、set -e の下でも失敗に気付かず空の値のまま進んでしまう書き方が複数残っていたのを見つけて直した。

途中で見つけた本物の事故: commit メッセージにレビューした相手の名前を書いてしまった。「Fable 5.2 review round」という文字を commit メッセージに 6 個書いてしまい、この基盤の CI (自動チェック) の「AI の道具や相手の名前を書くな」という検査で PR が落ちた。直すには、すでに push した 15 個の commit のうち名前が入っている 6 個だけ、メッセージの文章だけを書き換える必要があった。git filter-branch という道具を使い、まず書き換える範囲を間違えて (手元の古い main の印を基準にしてしまい、関係の無い 37 個の commit まで触ってしまった) 気付いて元に戻し、正しい範囲 (origin/main との共通の祖先から) で改めて 6 個だけ書き換えて直した。

7. awsome 側に取り込むと良いこと (提案)

無し。awsome-distributed-ai は Trainium (Neuron) を中心には扱わない方針で、この PR の中心である JobSet 自体は awsome の学習の雛形の多く (examples/training/fsdp など) がまだ PyTorchJob という古い形のままであり、JobSet への切り替え自体は awsome 側の広い方針の話になる。この PR 単体で提案できる、小さく切り出せる差分は無いと判断した。

8. まだ終わっていないこと

chart の既定レイアウト (1 台に GPU 2 枚) は、まだ実機で動かしていない。検証用セルの GPU の枠を広げれば動かせるはずだが、今回は「2 台に分ける」形で 4 つの約束を確かめることを優先した。

一部の実機確認のポーリング (pod_count など) は、API のエラーを「0 個」と区別できない。ポーリングのループの中なので実害は限定的だが、直すと確実性が上がる。次の PR での直しの候補として残した。

controller の ClusterRole (権限) は upstream のまま。webhook の設定を書き換えられる範囲が、自分の物に絞られていない (Kueue の webhook も書き換えられる)。upstream 側の仕様なので、この PR では直さずコメントで注意点として残した。

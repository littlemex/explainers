PR #36: 途中で失敗した apply の後も terraform destroy が片付ける
Foundation: terraform destroy cleans up after a partial apply (fixes #26)

レビュー中 (承認済み)Issue #26 を閉じる予定ブランチ fix/26-guard-partial-apply (PR #21 の上に積む)commit 7779709b947 ファイル追加・9 ファイル変更

結論から。PR #21 が足した「削除ガード」(Karpenter が作った instance や network interface を、terraform destroy の前に手で片付けるスクリプト) は、クラスタや Karpenter 関連のリソースが全部できた一番最後に、1 個だけ作られていた。だから terraform apply が途中で失敗すると、ガードは state に一度も入らず、後で terraform destroy しても、VPC CNI が付けた network interface と EKS が作った cluster security group が残って手で消す羽目になる。この PR は、VPC ができた直後に作る 2 本目のガード (network_guard) を足し、EKS クラスタ側をそのガードに依存させることで、apply がどこで失敗しても後片付け役が必ず state にいる状態にした。

この PR でやったこと。Issue #26 が出した 2 つの修正案 (ガードを 1 本にして依存を逆転する/2 本目のガードを足す) を比べて後者を選び、実装。さらに、検証の途中でメンテナが見つけた別のバグ (teardown-guard.sh が、片付け対象の IAM role が既に消えていると set -e でそのまま落ちる) も同じ PR で直した。独立したレビューを 6 回回し、ブロッキング指摘を 8 件 → 0 件まで減らして承認を得た。

1. Issue の 2 つの案を比べて、2 本目のガードを選んだ理由

Issue #26 は 2 つの直し方を示している。(A) 今の 1 本のガードを VPC の直後に動かし、依存の向きを逆転する (クラスタや node group をガードに依存させる)。(B) 今のガードはそのままに、VPC の直後に動く 2 本目の、ネットワーク専用のガードを足す。A は一見シンプルだが、依存を逆転すると Karpenter の instance を終了する処理が EKS クラスタ削除より後ろに動いてしまう。そうなると、instance は control plane が消える間ずっと動いたまま (課金が延びる) で、しかもその instance の network interface が cluster security group を使っている限り、EKS 自身がその security group を消せない。つまり A は、直したいはずの Issue の症状の片方 (security group が残る) を、普通の完全な destroy でも起こしてしまう恐れがある。B は今のガードの位置と動きを一切変えず、2 本目を追加するだけなので、この危険が無い。

2. 何をトリガーにして「ガードが無い」状態を作るか

Issue 自身が示した再現手順は、add-on (coredns) のバージョンを壊して apply を失敗させる方法だった。だがこれを実際に試すと、再現しない。teardown_guard も coredns の add-on も、どちらも aws_eks_node_group.system にしか依存しておらず、Terraform は失敗した resource に依存しない resource を作り続けるため、coredns が失敗してもガードは何の妨げも無く作られてしまう。この PR では、Karpenter の node 用の access entry (aws_eks_access_entry.karpenter_node) を壊すトリガーを使う。この access entry は teardown_guard 自身の depends_on に入っている直接の依存先なので、これを壊せば 構造的に確実に ガードが作られない状態になる。

3. 後片付けが要る 2 つのもの

Issue が指す残存は 2 種類あり、互いに依存関係がある。VPC CNI が node に付けた network interface が "detached" (つながっていない) のまま残ると、それを使っている cluster security group を EKS 自身が消せなくなる。だから新しい network_guard は、まず interface を探して消し、それから security group を消す、という順番を守る。

4. テスト自身が「本物の残存」を作れているかの確認

最初に書いたテストは、植えた network interface に security group を指定していなかった。これだと interface は VPC の既定の security group を使うだけで、cluster の security group は誰にも使われていないので EKS 自身がそのまま消してしまい、security group 側の後片付けロジックは一度も実行されずに「成功」扱いになっていた。独立レビューがこれを見つけ、--groups で cluster の security group を明示的に指定するよう直した。直した後は、直す前のコードで実際に destroy が DependencyViolation で失敗し、Issue と同じ文言のエラーが出て、手で両方 (interface と security group) を消すまで終わらないことを確認した。

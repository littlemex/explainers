Trainium (trn2.3xlarge) での device plugin と DRA の実験 E4 の結果
Issue #19 (オーストラリア ap-southeast-4、trn2.3xlarge の spot、2026-11-18)

結論から。trn2.3xlarge は、GPU の小型機 (g6e、g7) と同じ理由で device plugin・動的なプール・今までの書き方の Pod (Layer 1)・スケジューラの拡張なし を既定にする。Neuron の DRA プールは台数を固定したプールでしか動かない (Karpenter の DRA の機能に Neuron 用の対応が無いため)。Layer 1 の Pod が DRA のノードに届くのは、こちらで足した DeviceClass (extendedResourceName 付き) があるときだけで、Neuron の chart 自身はそれを持っていない。

この文書でやったこと。実験用に EKS 1.37 のクラスタをオーストラリアに 1 つ作り、trn2.3xlarge の spot で device plugin 用と DRA 用の 2 つのノードプールを用意し、4 つの実験 (E4a〜E4d) と 1 つの追加確認を流して、最後にクラスタごと消した。

1. 1 つの chart は 1 回の release で 1 方式だけ (E4a)

Neuron の device plugin と DRA のドライバは、どちらも neuron-helm-chart という 1 つの chart の中に入っている。しかし、devicePlugin.enabled と draDriver.enabled を同じ release で両方 true にしても、テンプレートの条件分岐で device plugin の DaemonSet が消える。ドキュメントのコマンドどおりに DRA を入れると、クラスタ全体の device plugin が無くなる。そこで、方式のラベル (distai-platform/neuron-method) で選ばせる affinity を付けた release を 2 回 install した (neuron-dp と neuron-dra)。

2. Karpenter の見積もりと実測が 2 倍違う (E4a)

trn2.3xlarge には Trainium2 が 1 個、物理コアが 8 個ある。Karpenter はこの物理コア数をそのまま aws.amazon.com/neuroncore=8 と見積もる。しかし device plugin が実際にノードの allocatable へ出す値は aws.amazon.com/neuroncore=4 で、見積もりの半分だった。これは、2 個の物理コアを 1 個の論理コア (LNC=2) として束ねる既定の設定によるもので、見積もりが間違っているわけではなく、見積もりが「論理コア化する前」の数を見ているためである。

気を付けること。neuroncore を 5〜8 の範囲で要求する Pod を書くと、Karpenter はその要求を満たせそうなノードを起動するが、起動したノードの実際の allocatable (4) では満たせず、Pod は動かない。Pod は aws.amazon.com/neuron (デバイスの枚数) で要求するか、neuroncore は実測の 4 以内にとどめる。

3. Layer 1 が DRA のノードに届くのは、こちらで足した DeviceClass のおかげ (E4b)

今までの書き方の Pod (limits: {aws.amazon.com/neuron: 1}) は、device plugin のノードでは普通に動いた。DRA のノードでは、chart が自分で作る DeviceClass neuron.aws.com には extendedResourceName が無いため、同じ Pod は Pending のまま (Insufficient aws.amazon.com/neuron) だった。そこで、extendedResourceName: aws.amazon.com/neuron を持つ DeviceClass をこちらで 1 つ作って device.driver == "neuron.aws.com" を選ぶようにしたところ、同じ Pod が変更なしで約 3 秒で Scheduled になり、自動で作られた claim が neuron-device-0 を割り当てた。GPU 側 (NVIDIA の DRA chart) は、この DeviceClass を chart 自身が持っているので、同じ手当てが要らない。

4. Neuron の DRA プールは、台数を固定しないと使えない (E4c)

プールを 0 台にして Layer 1 の Pod を出すと、Karpenter はノードを起こす (aws.amazon.com/neuron=1 と見積もる) が、そのノードの NodeClaim は Initialized=Unknown (ResourceNotRegistered "aws.amazon.com/neuron") のままで、Pod を手で削除したあと8 分 50 秒たっても片付かなかった (consolidateAfter は 2 分)。同じ条件で device plugin のノードは、Pod を消してから約 3 分で片付いた。Layer 2 の Pod (ResourceClaim で要求) はさらに悪く、Karpenter の DRA の機能 (settings.enableDRA) を切っても入れても、ノードが 1 台も起動しない (Karpenter に Neuron の device の情報が無いため)。GPU の小型機 (E2) では、Layer 2 の Pod は enableDRA=true で 48 秒後にノードが起動して初期化までできたので、Neuron は GPU より状況が悪い。

台数を固定した NodePool (replicas: 1、Karpenter の StaticCapacity gate、alpha、既定で off) を試すと、ノードは38 秒で Ready になり初期化済みになった。この固定プールの上では、Layer 1 の Pod (DeviceClass を足した状態) も Layer 2 の Pod も、そのまま動いた。

5. スケジューラの拡張は要らない (E4d)

Neuron にはスケジューラの拡張 (chart の scheduler.enabled) があるが、今回は入れていない。それでも、1 枚のデバイスを要求する Pod (aws.amazon.com/neuron: 1) と、4 個のコアを要求する Pod (aws.amazon.com/neuroncore: 4) は、どちらも default-scheduler のままで Running になった。後者は NEURON_RT_VISIBLE_CORES=3,0,1,2 を受け取っており、コアの選び方自体は device plugin 側がやっている。1 枚しかデバイスが無い trn2.3xlarge では、拡張が解決する「複数デバイスをまとめて連続に割り当てる」問題がそもそも起きない。

6. わざと二重に広告すると、Neuron でも同じ壊れ方をする (E4+)

device plugin を、本来は DRA だけのつもりだった固定プールのノードにも動かすと、そのノードの allocatable に aws.amazon.com/neuron: 1 が現れた。device plugin 経由の Pod と、Layer 2 の Pod (ResourceClaim) を続けて出すと、両方が同じ /dev/neuron0 (同じ PCI アドレス 0000:33:00.0) を受け取り、どこにも警告やイベントが出なかった。これは GPU の E1 で見た壊れ方と同じである。一方で、Layer 1 の Pod を 2 つ続けて出すと、2 つ目は正しく Insufficient aws.amazon.com/neuron で拒否された。壊れるのは「違う層 (Layer 1 と Layer 2) が、違う広告役を経由して、同じデバイスを両方から見えてしまう」ときだけである。

この壊れ方は外からは見えないので、計画している「読むだけの検査ツール」(Issue の決定 1(d)) の検査は、GPU と Neuron のどちらでも同じ規則 (「DRA のドライバが動くノードで、対応する extended resource の allocatable が 0 より大きい」) で見つけられる。

7. 決め直したこと

項目実験の前実験の後
trn2.3xlarge の既定E0〜E3 (GPU) と同じ構図を想定device plugin・動的なプール・Layer 1・スケジューラ拡張なし、で確定 (GPU の小型機と同じ理由)
Neuron の DRA プールKarpenter の DRA 機能で動かせるか未確認台数を固定したプール (StaticCapacity、alpha) でしか動かない。動的には Layer 1 も Layer 2 も使えない
Layer 1 → DRA ノードchart が対応していると期待Neuron の chart は extendedResourceName を持たない。platform の DeviceClass カタログに Neuron 用の 1 枚を追加する
Neuron の chart の install1 回で済むかもしれない方式のラベルで分けた 2 回の release が必須
Karpenter の neuroncore 見積もり未確認実測の 2 倍 (8 対 4)。要求は aws.amazon.com/neuron を使うか、neuroncore は実測内にとどめる
検査ツールの規則GPU 向けに設計GPU も Neuron も同じ規則 (extended resource の allocatable > 0 かつ DRA ドライバが動くノード) でよい

8. 実験の条件と、ついでに見つけたこと

EKS 1.37 (kubelet v1.37.1)、AMI amazon-eks-node-al2023-x86_64-neuron-1.37-v20261112、Neuron カーネルドライバ 2.31.8.0、Karpenter 1.15.2、neuron-helm-chart 1.11.2 (device plugin 2.33.1.0、DRA ドライバ 1.4.0)、trn2.3xlarge の spot。起動は 3 回で、3 回とも spot で取れた (すべて apse4-az3、trn2.3xlarge を提供する唯一のゾーン)。かかった時間は約 1 時間 15 分、費用は推定で 4〜5 ドル。

Karpenter の DRA の機能 (settings.enableDRA) には Neuron 用の gate が無く、AWS_FEATURE_GATES には DRANVIDIAGPU と DRAEFA しか出てこない。Neuron の DRA を Karpenter で動的に扱うには、Karpenter 側に Neuron 対応が増えるのを待つか、台数を固定したプールで運用するかの 2 択になる。

awsome 側に取り込むと良いこと (提案)

awsome-distributed-ai は Neuron (Trainium) を中心には扱わない方針に近いため、E4a〜E4d で見つけた Neuron の chart の構造や Karpenter の見積もりのような、Trainium 専用の知見は awsome へ提案しない。GPU 一般・中立な点だけを以下にまとめる。

#提案上流の今取り込むと何が良いか出し方
1Neuron 固有の提案は無し——awsome が Neuron を中心に扱わない方針 (本スキルの 0 節 5、12 節) のため、trn2.3xlarge の chart の挙動や Karpenter の neuroncore 見積もりは、distai-platform の中で育てる対象のままにする
2二重広告を検出する読むだけの検査 (既存の候補 C の裏付けを強化)plugin() は Helm の release 名を 2 つ比べるだけで、DRA を広告する側は見ていないE4+ は、GPU (E1) で見た「同じデバイスが警告なしで 2 つの Pod に渡る」壊れ方が、Neuron でも同じ根本原因 (opt-out の DaemonSet affinity と DRA ドライバの衝突) で起きることを確かめた。release 名ではなく、ノードの allocatable と DRA の ResourceSlice を読む検査の方が、アクセラレータの種類を問わず効くという根拠が 1 件増えたdistai-platform の決定 1(d) の検査ツールを先に作り、GPU だけで動くことを確かめたうえで、Issue として awsome に提案する (まだ出していない)

まとめ。trn2.3xlarge は device plugin・動的・Layer 1・拡張なしで確定し、Neuron の DRA は台数を固定したプールでしか今は使えない。GPU の小型機とまったく同じ理由 (動的な DRA プールは初期化されない) で同じ結論に落ち着いたことが、#17 の全体設計を進める根拠になる。

根拠: 検証担当が残したコマンドと出力 (手元の /Users/akazawt/tmp/dp-exp/e4、manifest は /Users/akazawt/tmp/dp-exp/manifests/e4)。結果と決め直しは Issue #19 の本文に反映済み。

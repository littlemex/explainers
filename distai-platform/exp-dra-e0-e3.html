device plugin と DRA の実験 E0〜E3 の結果
Issue #19 (スペイン eu-south-2、g7.2xlarge の spot、2026-11-18)

結論から。今までの書き方の Pod (nvidia.com/gpu: 1) は、device plugin のノードでも DRA のノードでも動いた。ただし大きな落とし穴が 2 つ見つかった。(1) 同じノードで device plugin と DRA のドライバが両方動くと、1 枚の GPU が警告なしに 2 つの Pod に渡る。(2) 今までの書き方の Pod で Karpenter が DRA のノードを起こすと、ノードが「未初期化」のまま残り、空になっても片付かない。このため、小型の GPU は device plugin のままにし、DRA のプールは ResourceClaim の Pod か固定台数のプールで使う、と決めた。

この文書でやったこと。実験用に EKS 1.37 のクラスタを 1 つ作り、g7.2xlarge の spot を 2 つのプール (device plugin 用と DRA 用) で起こして、4 つの実験を流し、最後にクラスタごと消した。実験を流したのは、実装やレビューとは別の検証担当のセッションである。

1. 何もしないと 2 つが同じノードで重なる (E0)

NVIDIA の device plugin の chart も、DRA のドライバの chart も、既定では「GPU があるノード」に自分を置く。その目印として、AL2023 の NVIDIA の AMI はノードに nvidia.com/gpu.present=true を自分で付けている。そのため、2 つを既定のまま入れると、全部の GPU ノードで両方が動く。最初は「目印を付ける部品 (NFD) が無いので、どちらもどこにも乗らない」と考えたが、実際のノードを見て訂正した。方式のラベルでどちらかを選ばせる仕組み (#19 の決定 2) は、任意ではなく必須である。また DRA のドライバの chart は、extendedResourceName: nvidia.com/gpu 付きの DeviceClass を自分で作るので、基盤の側で同じものを作る必要は無い。

2. 二重に入れると、同じ GPU が 2 つの Pod に渡る (E1)

同じ書き方の Pod は、device plugin のノードでも DRA のノードでも動いた。DRA のノードでは、Pod の limits を満たす ResourceClaim が自動で作られ、GPU が割り当てられた。ここまでは期待どおりで、今までの書き方を既定にする (層 1) 方針は成り立つ。

次に、わざと device plugin を DRA のノードでも動かした。すると、そのノードの allocatable に nvidia.com/gpu: 1 が現れ、device plugin 経由の Pod と ResourceClaim の Pod が、同じ UUID の GPU を同時に受け取った。警告もイベントも出なかった。

この壊れ方は外からは見えないので、計画している「読むだけの検査ツール」には、「DRA のドライバが動くノードで allocatable の GPU が 0 より大きい」を見つける検査を入れる。また、個別の chart と AMI のドライバだけで動いたので、GPU Operator は要らない。

3. Karpenter が起こしたノードが未初期化のまま残る (E2)

Karpenter の DRA の機能を有効にしても無効にしても、層 1 の Pod で起こした DRA のノードは初期化されなかった。Pod 自体は動くので気付きにくいが、Karpenter は未初期化のノードを片付けないので、空になってもお金がかかり続ける。そこで、小型の GPU は device plugin を既定のままにし、DRA のプールを Karpenter で増減させるのは ResourceClaim (層 2) の Pod だけにする。層 1 の Pod を DRA で動かしたいときは、固定台数のプールにする。

4. Kueue は正しく数えるが、層 2 を違う flavor に入れる (E3)

Kueue に「DeviceClass gpu.nvidia.com は nvidia.com/gpu として数える」という対応 (deviceClassMappings) を入れると、層 1 も層 2 も同じ名前で数えられ、二重にも数えられなかった。1 つの種類に 1 つの枠の名前、という方針は成り立つ。一方で、Kueue は層 2 のジョブを、空いていた device plugin の flavor に入れてしまった。Pod に方式のラベルを付けても変わらず、flavor のキー (karpenter.sh/nodepool) で DRA のプールに固定したときだけ動いた。そこで、層 2 のジョブは DRA の flavor だけを持つキューに流す、という規則を #19 に足した。

6. 実験の条件と、ついでに見つけたこと

EKS 1.37 (kubelet v1.37.1)、AMI amazon-eks-node-al2023-x86_64-nvidia-1.37-v20261112、NVIDIA のドライバ 595.91.07、Karpenter 1.15.2、Kueue 0.20.2、device plugin の chart 0.20.2、DRA のドライバの chart 0.5.1。g7.2xlarge の起動は 6 回で、6 回とも spot で取れた (AZ は eus2-az1 と eus2-az2 が 3 回ずつ)。かかった時間は約 1 時間 43 分、費用は推定で 2.5〜3 ドル (上限 40 ドル)。

実験用のクラスタを terraform destroy で消すとき、Karpenter の設定 (EC2NodeClass) の片付けが止まった。同じ destroy が先にネットワーク (NAT と経路) を消し、Karpenter が AWS に届かなくなったためである。新しい基盤では、ネットワークを消す前に Karpenter が管理する物を片付ける順序にする (#17 に記録)。

この実験と関係なく見つけたこと。スペインのリージョンで、gds-probe-g7.2xlarge という名前のインスタンスが 2026-11-08 から動き続けている。この作業で作ったものではないので、触っていない。

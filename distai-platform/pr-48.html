結論から。24 時間の Capacity Block のような、時間を切った確保の中で「何がいつ、どのノードで動くはずで、今どこまで進んでいるか」を、1 枚の自己完結した HTML で見られるようにする、小さな見本を足した。本番の監視ではなく、examples/ に置いたおもちゃである。クラスタや AWS に触れる部品は読み取りだけに絞り、その約束をコード側の作り(許可リスト)で強制した。

この PR でやったこと。既存の可視化の道具を 8 個調べてから作るかどうかを決め(どれも「予定表」と「予定 対 実際の重ね合わせ」と「外部に出ない 1 枚の HTML」を同時に満たさなかったので作った)、予定表・収集・描画の 3 部品に分け、106 件のユニットテストを EC2 のテスト専用機で実行し、Fable 5.2 の最終レビューを 5 ラウンド(重大な指摘が出るたびに全部直して再提出)重ねて承認を得た。

1. 何を作ったか

見本は examples/tools/run-board/ に置いた。infra/ や gitops/ ではなく examples/ に置いたのは、これが基盤の一部ではなく、使い捨ての見本だからである。README の最初の行にも「おもちゃで、本番の監視ではない」と書いた。

3 つに分けた理由は、テストのしやすさである。collect_status.py がクラスタの生の返り値をどう判定するかという、一番間違えやすい部分を、本物のクラスタなしに固定の JSON で確かめられるようにした。render_board.py は現在時刻を一度も読まない(見ているときに「この画面は何分前の状態か」を出す小さな JavaScript だけが例外で、描く内容そのものは変えない)ので、同じ 2 つのファイルからは必ず同じ HTML ができる。

2. 既存の道具を先に調べた結論

作る前に、次の 8 個を公式の情報源で確かめた。見たい条件は 3 つ: (1) 人が書く予定表を入力にできる、(2) 予定と実際を重ねて見せる、(3) サーバーを立てずに 1 枚の HTML で見られる。

道具何をするか判定
KueueViz (kueue 本体)Kueue の今の状態をライブで見るダッシュボード不採用。動いているサーバーが要り、予定表の概念が無い
Headlamp汎用の Kubernetes の画面不採用。予定と実際を重ねる概念が無い
Kubernetes Dashboard汎用の Kubernetes の画面不採用。同上
Argo Workflows の画面1 つの Workflow の各ステップの時間を見せる一番近いが不採用。使うには予定表そのものを Argo Workflow として動かす必要があり、この見本より大きな仕組みになる
Argo CD の画面同期状態の木不採用。時間の軸が無い
Grafana の state timeline パネル時系列の状態の帯不採用。動いている Grafana と、継続的に送り込むデータソースが要る
mermaid の gantt文字から静的な図を作る不採用。予定と実際を分けて重ねる概念が無く、状態を集める仕組みも無い

詳しい根拠(ライセンス、最新版の日付)は Issue #47 の本文に、確かめた日付と出典つきで書いてある。

3. 読み取りだけという約束の作り方

「見るだけで、書き込まない」という約束は、口約束ではコードが育つうちに破られやすい。そこで、クラスタや AWS を呼ぶ唯一の入口 (lib/readonly_exec.py) に、呼べる形を最初から決めておき、それ以外はコマンドを実行する前に例外で止める作りにした。

これはテストでも確かめている。subprocess.run を偽物に置き換えて、「許可リストに無いコマンドは、本物のプロセスが一度も起動しないまま拒否される」ことを確認した。本当の安全性は、それでも最終的には資格情報(読み取り専用の RBAC、describe だけの IAM)に支えられるものなので、README にもそう書いている。

4. 収集できなかったときに、何が起きるか

一番やってはいけないのは、「集められなかった」ことを「まだ始まっていない」と同じに見せることである。それをやると、本当は失敗していたり遅れていたりする項目が、何も問題が無いかのように見えてしまう。設計の相談で Fable 5.2 からこの点を指摘され、収集に失敗した項目は、どんな理由であっても「不明」という専用の状態になり、画面の上部にも一覧で表示されるように直した。

「遅れているか」も、集めた生の事実(いつ始まった、いつ終わった)と、予定表の予定時刻から、見せる直前に 1 か所でだけ計算する。保存はしない。これも設計相談で指摘された点で、保存してしまうと「遅れている」の基準が 2 か所に分かれてずれる恐れがあった。

5. まだやっていないこと(README にも明記)

自動で更新し続けることはしない。新しい画面が欲しければ、もう一度 2 つのコマンドを実行する。同じレーン(ノード)の中で時間が重なる項目は、詰め込んで並べる本物のガントチャートではなく、単純に 1 行ずつ縦に並べる。アラートや履歴の保存、複数回の比較も無い。stop_condition は表示するだけで、本当に止まったかどうかは判定しない。

6. awsome 側に取り込むと良いこと(提案)

無し。この見本は distai-platform だけで使う小さな例で、GPU 全般の汎用の提案に育つ要素が無いため、今回は無し(距離が近い候補はいずれも理由付きで不採用にした、2 節の表)。

7. レビューで見てほしいこと

  1. 許可リストに本当に漏れが無いか。kubectl get 以外の呼び出しが、どんな経路でも subprocess に届かないか。
  2. 「不明」と「まだ始まっていない」が画面上でも本当に違って見えるか。色だけでなく模様でも区別できているか。
  3. 遅れの判定が 1 か所にまとまっているか。collect_status.py が生の事実だけを書き、render_board.py 側(lib/status_model.py)だけが「遅れている」を判定しているか。
  4. 外部の URL が本当に 1 つも出ていないか、CSP のタグが本当に入っているか。テストで確認済みだが、PR の diff でも見てほしい。
  5. examples/ に置いたことの是非。infra/ や gitops/ の品質基準を適用すべきでない旨が README に明記されているか。

まとめ。既存の道具 8 個を調べたうえで、どれも要件を満たさないので小さな見本を自作した。読み取りだけという約束はコードの作りで強制し、「集められなかった」と「まだ始まっていない」を混同しない設計に、相談と見た目の自己点検の両方で手を入れた。

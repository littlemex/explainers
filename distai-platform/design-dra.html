device plugin と DRA をどう扱うか
Issue #19 の検討 (Fable 5.2 と、2026-11-18)

結論から。device plugin と DRA を抽象化する独自の CRD は「ありうるが、作らない」。Pod の書き方の違いは、Kubernetes 本体の KEP-5004 (DRA の extended resource、v1.37 で GA、EKS で 1.37 が使える) がすでに吸収している。「後から入れると問題になる」の正体は抽象化の不足ではなく、1 つのノードで 1 つのデバイスのクラスを広告できるのは 1 つだけという排他と、それを誰が受け持つかが決まっていないことにある。そこで、方式 (device plugin か DRA か) を「ノードプール × デバイスのクラス」の属性にし、広告する側はそのラベルで自分のノードを選ぶ形にする。

この文書でやったこと。awsome の CloudFormation と distributed-ai の Terraform が device plugin をどう入れているかを読み、Kubernetes、AWS、NVIDIA、Neuron、Karpenter、Kueue の今の一次情報を確かめた。それを材料に Fable 5.2 と方式を比べた。

#なぜどう確かめた他の選択肢結果関連
1DRA で今までの書き方が使えるかKEP-5004 の kep.yaml独自の CRD で吸収するalpha v1.34、beta v1.36、stable v1.37。ノードごとに方式が違ってよく、同じノードで同じ名前を 2 つが広告するのは不可2
2EKS で使えるかaws eks describe-cluster-versions と EKS の文書—1.37 が標準サポート。AWS は 1.34 以降の新しいデプロイで DRA を推奨1

1. 「後から入れると問題になる」の正体

デバイスを Kubernetes に見せる仕組みには、ドライバ、広告する側 (device plugin か DRA のドライバ)、それを入れる側の 3 つの層がある。問題になるのは真ん中の「広告する層」で、入れる側の入り口が 5 つあり、どれも同じ場所に入る。

#重なり症状今の対処評価
1同じ名前の device plugin が二重 (別名の Helm、GPU Operator、eksctl、Bottlerocket の同梱)数や割り当てが揺れる (推測)awsome の plugin() は 2 つのリリース名だけを調べる。README は「消してから使え」見つけ方が一部しか見えない対症療法
2バージョンの違い後から作るスタックが止まる違えば fail し「先にそろえよ」クラスタに 1 つの物を、ノードグループのスタックが入れている
3スタックを消した後に残るHelm のリリースが残るREADME で注意持ち主がいない
4ドライバの二重読み込みに失敗するdistributed-ai は driver.enabled=false と、plan のときに拒否宣言の時点で拒否しており、根本の対処に近い
5device plugin と DRA が同じ名前を同じノードで広告できないdistributed-ai の ADR D9 は DRA 自体を避けた避けただけで、解いていない
6GPU Operator の設定の排他クラスタに ClusterPolicy か GPUCluster の片方だけ。その場の移行の手順は無い無いノードプール単位の移行の邪魔になる
7入っているのに広告されないEFA の chart の既定の対象に g6e.12xlarge が無く、EFA が 0distributed-ai は値で回避上流で直すべき

根本は 3 つある。誰がどの方式で広告するつもりかを書く場所が無いこと、広告する側の DaemonSet が「入れたら全部に広がる」形 (opt-out) であること、クラスタに 1 つの物をノードグループの寿命が持っていることである。

2. 抽象化の CRD はありうるか

案中身原則との合い方判定
(a) 作らないKEP-5004 と、ノードプールごとの方式のラベルこのリポジトリだけの抽象化が無い。GPU と Trainium が同じ形採用
(b) 方式を宣言する CRD とコントローラ (GPU Operator のベンダー横断版)導入、衝突の検出、持ち主の引き継ぎ独立した OSS なら原則上は可今は作らない
(c) DeviceClass と ResourceClaimTemplate のカタログ上流の API の実体を chart で配る抽象化ではない。単体で使える採用 (小さく)
(d) 読むだけの検査ツールノードごとに「クラス × 広告する側」を突き合わせ、二重、欠け、ラベルとの食い違いを報告。CRD 無し独立 OSS にしやすい。awsome の plugin() を置き換えられる採用 (実験 E1 の後)

(b) を作らない理由は 4 つある。各ベンダーの chart の値を追い続けるメタオペレータになること、GPU Operator 自体が 2 つの設定を排他にしているので上にかぶせてもノード単位の混在はできないこと、Auto Mode では広告する側が内蔵なので意味を持たないこと、そして上流の KEP-5004 が「ノードごとに移れる」を目的にしていて、需要を示す一次情報が無いことである。同じ排他の仕組みを 3 つのベンダーの分だけ手で書くことになり、ほかの人の需要も確かめられたら、そのときに独立した OSS として作る。

3. Pod の書き方は 2 つの層にする

Kueue の枠のリソース名は、方式によらず 1 つにする。層 1 はそのまま数えられる (Kueue v0.19 で既定で有効)。層 2 を同じ名前に対応づけられるかは、実験 E3 で確かめる。ResourceFlavor には方式のラベルを入れない。入れると、移行の途中で新旧の両方のノードプールに乗れなくなる。

4. クラスごとの方式

クラス今の方式ノードの起こし方Pod の書き方理由
NVIDIA の単体・小型 (g6e、g7)device plugin を既定にし、DRA のノードプールを横に置くKarpenter の動的層 1NVIDIA の GPU 単体の DRA はまだ公式サポートでなく、Karpenter の DRA は alpha。実験 E1、E2 の結果で反転してよい
NVIDIA と EFA の大型 (p5 系)DRA (GPU と EFA の両方)static のノードプールか予約層 2 (pcieRoot)2/32 と 32/32、45.8 GB/s と 3.6〜4.7 GB/s。static なら Karpenter の対応が要らない
Multi-Node NVLink の世代DRA (ComputeDomain)staticResourceClaimComputeDomain は公式サポート
Neuron の多デバイス (trn2.48xlarge など)DRA を第一候補static のノードプール層 2 (devicegroup)追加のスケジューラが要らなくなる。Karpenter に Neuron の gate は無い
Neuron の小型 (trn2.3xlarge、Inferentia)実験 E4 で決める動的が要る層 1単一デバイスなら連続の問題は出にくい (推測)
EFA同じノードの GPU に合わせるGPU に従うGPU に従うそろえる効果は両方が DRA のときだけ (推測)。Neuron の device plugin との同居は可

GPU と Trainium の等価は、「同じ方式」ではなく「同じ形」で保つ。どのクラスも、ノードプール (ラベルと taint)、広告する側の chart、DeviceClass、ResourceFlavor の 4 つを持つ。この観点では GPU Operator は外すのが筋で、NVIDIA だけが別の形になり、1 節の #6 も抱えるからである。個別の chart で足りるかは E1 で確かめる。残る非対称は 1 つで、Karpenter の動的な DRA に Neuron の gate が無いことである。

5. 動いているクラスタで DRA へ移る

気を付けること。予約が 1 台だけなら、横に新しいノードプールを作る余裕が無い。そのときはジョブの切れ目で入れ替える。Bottlerocket の NVIDIA 版は device plugin が同梱なので、DRA のノードプールは AL2023 にする。Neuron の追加のスケジューラを使っている Pod は schedulerName の指定が残るので、そこだけ Pod の変更が要る (推測)。

7. awsome 側に取り込むと良いこと (提案)

#提案上流の今出し方

4層と入り口の表を README に注意が散文で 1 段落文書の PR

ほかの上流には、EFA の device plugin の対象の型の追加 (g6e.12xlarge)、Karpenter への Neuron の DRA の gate の提案と KEP-5004 の Pod の挙動の報告、Kueue への「方式をまたいで同じ名前で数える」例、GPU Operator への「2 つの設定のノード単位での共存」の issue が出せる。

8. まだ分かっていないこと

  • 層 1 の Pod で、Karpenter が DRA のノードを動的に起こせるか (E2、E4)。
  • Kueue で層 2 を層 1 と同じ名前で数える設定 (E3)。
  • DeviceClass を作ったときに、device plugin のノードのスケジューリングが変わらないか (E1)。
  • 以前の p5e の実測は 1 台、各 1 回で、kubelet に手を入れていない条件。複数回と 2 台での測定は E7。

まとめ。独自の CRD は作らず、KEP-5004 で Pod の書き方を固定し、方式はノードプールごとのラベルで分ける。大型の GPU と多デバイスの Trainium は DRA を第一候補にし、小型は実験で決める。#17 の骨格は、数ドルで済む E1 から E4 で決められる。

結論から。これまでこの基盤は「全部のセルに無条件で配る」(core) という 1 本の道しかなかった。この PR は、セルが「この部品は要る・要らない」を自分で選べる 2 本目の道 (platform-optional) を初めて配線し、その最初の実例として GPU の状態を見る部品 (dcgm-exporter) を 1 個入れた。実装の途中、共有のテンプレートに危険な設定 (allowEmpty、下の 3 節) を書いてしまい、Fable のレビューで見つけて直す、という本物の失敗と修正も含んでいる。

この PR でやったこと。3 つの層の仕組み (1 節)、セルごとに選べる新しい配布経路 (2 節)、最初の実例 dcgm-exporter (3 節) を実装し、実機の EKS セル (us-east-1) を 8 回作って壊しながら検証し、Fable 5.2 のレビューを 4 回回して指摘 0 件まで収束させた。

1. 3 つの層: 無条件・選べる・チームのもの

これまでの基盤には「全部のセルに無条件で配る」(core) という道しか無かった。Issue #41 はここに 2 本目・3 本目の道を定義した: セルが選ぶ platform-optional と、チームが選ぶ workload。この PR が実装するのは 1 本目 (core への tier: core の追加) と 2 本目 (platform-optional の配布機構そのもの) で、3 本目 (workload) はまだ土台が無い (#22 待ち)。

2. セルごとに選べる新しい配布経路

「選べる」の実体は、Argo CD の ApplicationSet が 3 本目に増えたこと (addons-optional.ApplicationSet.yaml) と、セルのディレクトリに 1 個のマーカーファイルを置くだけという操作のシンプルさである。Cluster generator は、隣の Git file generator が読んだファイルの中身を見ることができない (確かめた事実) ので、「このセルは何を選んだか」を Cluster generator 側のラベルで表現することはできない。代わりに、既にある cells.ApplicationSet.yaml と同じ「パスをセル名でテンプレート化する」仕掛けを転用し、マーカーファイルが存在するセルにだけ Application が生まれるようにした。

カタログ側の定義 (addon-catalog/dcgm-exporter/addon.yaml) は、審査された「何を・どこまで上書きしてよいか (overridableKeys)」の正本で、マーカーファイル自体からは一切読まれない。両方の整合は、新しい静的検査 check_addon_catalog_sync.py が検査する。

3. 最初の実例: GPU の状態を見る部品 (dcgm-exporter)

NVIDIA 公式の dcgm-exporter チャート (v4.9.0、取得した tarball の sha256 で固定) を薄く包んだだけの部品で、karpenter.k8s.aws/instance-gpu-manufacturer: nvidia という Karpenter 自身が勝手に付けてくれるラベルを使って GPU ノードにだけ乗る。device plugin も DRA も使わない (そちらはまだこのリポジトリに統合されていない別ブランチの仕事)。Prometheus Operator の CRD がまだ無いので、ServiceMonitor は作らず、プレーンな :9400/metrics だけを出す形にした。

root 権限と SYS_ADMIN という Linux capability が必要 (GPU のプロファイリング指標のため) で、さらに kubelet のソケットを hostPath でマウントする (どちらか 1 つだけでも Pod Security の privileged レベルが要る)。そのため専用の namespace だけに enforce: privileged ラベルを付け、warn/audit は baseline のままにした。AWS の権限は一切付けていない (GPU の値を読むだけで、AWS API を呼ばないため)。

4. set -e の罠を 2 種類、実機で 8 回踏んで直した

新しく書いた確認コードの中で、同じ失敗の形が繰り返し出てきた。1 つ目は「kubectl がエラーを返したのに、それを '対象が存在しない' という正常な結果と区別できず数えてしまう」形 (ServiceMonitor の CRD が無いこと自体は正常なのに、そのエラー文がそのまま「1 件見つかった」と誤判定された)。2 つ目はもっと根本的で、set -e の下で 変数=$(失敗するコマンド) と書いた瞬間に、その次の行 (終了コードを読む行を含む) に進む前にスクリプト全体が静かに落ちてしまう、というbashそのものの仕様だった。これは実験で確かめた: set -e; v=$(false); echo reached は "reached" を一度も出力しない。

この 2 種類の形を、新しいコード全体から合計 8 箇所見つけて直した。GPU のメトリクス確認自体の正規表現も、実際の GPU から返ってきた本物のラベル付き出力 (DCGM_FI_DEV_BOARD_POWER_WATTS{gpu="0",...} 14.383) に対して書いたつもりの正規表現が合っておらず、2 回目の実機実行で初めて見つかった。

5. 一番重大だった発見: allowEmpty を共通テンプレートに書いてしまった

optional-pool は「要らなければ空っぽにできる」という設計 (values.enabled: false) を持つが、Argo CD には「自動 sync が対象を 0 個にまで prune することを既定で拒む」という安全機構 (allowEmpty: false が既定) があることが分かった。これを回避するために allowEmpty: true を足したが、最初の実装では 3 つの core add-on 全部が共有する platform.ApplicationSet.yaml の共通部分に直接書いてしまっていた。

Fable 5.2 のレビュー (3 回目) でこれを指摘され、optional-pool/addon.yaml という 1 個のファイルだけが持つ、個別の設定に変更した。直した後、実機で「karpenter-crd の Application にはこの鍵が無い」ことと「optional-pool では正しく合体している」ことの両方を確認する検査を追加し、実際に確認した。

6. 実機の確認

us-east-1 に EKS セルを 1 から作って壊す 1.e2e.sh を 8 回、Karpenter のバージョンを上げる 2.upgrade.sh を 1 回、実際に流した。最後 (8 回目) の実行は全項目 PASS で、GPU の実機 (g5/g6.xlarge) でのメトリクス取得、マーカーファイルの有無による Application の生成・削除・再接続、optional-pool と allowEmpty の範囲限定、全て実機で確認済み。壊した後は毎回、AWS API を個別の resource ID で直接叩いて消し残しゼロを確認した。

7. 上流 (awsome-distributed-ai) との関係

今回は提案無し。3 つの層や per-cell opt-in の仕組みは、この基盤が Terraform 管理の Argo CD capability を持つことを前提にしていて、awsome-distributed-ai 自体にはその土台 (ApplicationSet、GitOps の配布層) が無いため、そのまま当てはまる提案にならない。

8. まだ終わっていないこと

optional-pool を本当に要らなくする、という経路は未検証。enabled: false が空のレンダーになることは静的検査で確認したが、既に NodePool が存在するセルで実際にこの値を切り替えて、prune されることまでは実機で確認していない。

GPU のテスト用ノードに taint を付けていない。dcgm-exporter 自身は「taint があっても乗る」という前提の wildcard toleration を持つが、テスト用の GPU ノードに taint を付けていないため、この部分は未検証。

optional-pool 自体が本当に存在すべきかは、まだ持ち主の判断を待っている。#41 のコメントで出た 2 つの選択肢のうち、この PR はデフォルトで「専用の untainted pool を作る」側を選んでいるが、どちらを採るかは未確定のまま。

9. レビューで見てほしいこと

  1. allowEmpty の範囲 (5 節)。他の core add-on にこの鍵が増えたときも、同じ「1 個ずつ opt-in」の形を守れているか。
  2. optional-pool という仕組み自体を持つべきか (8 節)。この PR はまだ判断していない。
  3. set -e の罠 (4 節) が、このPRが直していない他の場所にまだ残っていないか。
  4. dcgm-exporter の SYS_ADMIN の要否 (3 節)。GPU のプロファイリング指標が本当にこの基盤に要るかどうかの判断。

まとめ。この基盤に「セルが選べる」という 2 本目の配布経路を初めて配線し、その最初の実例として GPU 監視部品 (dcgm-exporter) を 1 個入れた。実装の途中で、共有テンプレートに危険な設定 (allowEmpty) を書いてしまうという本物の失敗を Fable のレビューで見つけて直し、set -e の罠を 8 箇所、実機でしか見えない形で見つけて直した。us-east-1 の実機で EKS セルを 9 回作って壊しながら検証し、Fable 5.2 のレビューを 4 回回して指摘 0 件まで収束させた。「optional-pool という仕組み自体を持つべきか」は、まだ持ち主の判断を待っている。

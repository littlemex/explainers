A. PR テンプレートに、貼るログを伏せ字にする注意を足す

そもそも何の話か

GitHub の PR テンプレートは、PR を作るときに本文の欄に最初から入っている下書きである。上流のテンプレートには ## Test Results という欄があり、機能を変える PR では「実際の AWS の環境で最後まで動かした証拠 (ジョブの出力、ベンチマークの数字、ログ)」をここに貼ることが必須になっている。上流の AGENTS.md も、AI を使った PR に同じことを求めている。

実機のログには、その人の AWS の環境の値がそのまま入りやすい。たとえば aws sts get-caller-identity の出力にはアカウント ID とロールの ARN が、kubectl get nodes -o wide には内部の IP が、terraform apply の出力にはバケット名やクラスタのエンドポイントが出る。公開の PR に一度貼ると、あとで消しても、通知のメールや写しのサイトに残る。

上流の今

PR テンプレートの Test Results の欄は、ログを貼れと言うだけで、伏せ字の注意が無い。

## Test Results

<!--
REQUIRED for functional changes: paste evidence of an end-to-end run on a
real AWS environment (job output, benchmark numbers, relevant logs).

For changes with no functional impact, replace this section's content with
the single word: docs-only
-->

一方で、同じリポジトリのバグの報告の Issue テンプレートには、同じ注意が 2 か所ある。つまり、上流はすでに「ログには秘匿の値が混ざる」と分かっていて、Issue では注意している。ログを一番多く貼る PR にだけ、それが無い。

**IMPORTANT:** Please redact any access keys, secret keys, session tokens,
or other sensitive information from your bug report and log output.
...
**Remember to redact sensitive information.**

提案

Test Results の欄の注釈 (HTML のコメントなので、PR の表示には出ない) に、バグの報告のテンプレートと同じ趣旨の 1 行を足す。

REQUIRED for functional changes: paste evidence of an end-to-end run on a
real AWS environment (job output, benchmark numbers, relevant logs).
Redact access keys, session tokens, account IDs, ARNs and other sensitive
information before pasting.

なぜ中身のある PR か

上流の AGENTS.md は、見た目だけの直しの PR を出さないように求めている。この提案は言い回しの好みの書き換えではなく、テンプレートどうしの食い違い (Issue にはある注意が PR に無い) という具体的な抜けを埋めるものである。ログを貼ることを必須にしている欄に注意が無いことが、秘匿の値の漏れにつながる。

確かめ方と、他の案

文書だけの変更なので、Test Results は docs-only と書く。他の案として、PR の本文を自動で調べてアカウント ID を見つける workflow もありうるが、上流の workflow を増やすことになり、1 行の注意より重い。まず注意を足し、必要なら後で検査を足す順にする。

B. stale の workflow を直す

そもそも何の話か

stale の workflow は、動きの無い Issue に印を付け、さらに動きが無ければ自動で閉じる仕組みで、上流では毎日 1 回動く。workflow には、GitHub のリポジトリを操作する権限を permissions: で渡す。必要な分だけを渡すのが基本 (最小の権限) で、上流のほかの workflow (blog-pr-gate.yml) にも「permissions は最小に保つ」と書かれている。

上流の今

closing-soon.yml の全文はこうなっている。

jobs:
  close-issues:
    runs-on: ubuntu-latest
    permissions:
      issues: write
      pull-requests: write
    steps:
      - uses: actions/stale@v5
        with:
          days-before-issue-stale: 90
          days-before-issue-close: 60
          stale-issue-label: "stale"
          stale-issue-message: "This issue is stale because it has been open for 30 days with no activity."
          close-issue-message: "This issue was closed because it has been inactive for 14 days since being marked as stale."
          days-before-pr-stale: -1
          days-before-pr-close: -1

ここに 3 つの問題がある。

  1. 使わない権限を持っている。days-before-pr-stale: -1 と days-before-pr-close: -1 で PR は対象外にしているのに、PR を書き換える権限 pull-requests: write を渡している。
  2. RFC も自動で閉じられる。除外するラベル (exempt-issue-labels) が無いので、RFC のテンプレートで作った提案も、90 日動きが無ければ印が付き、さらに 60 日で閉じられる。議論に時間がかかる提案ほど、黙って消える。
  3. 文面の日数が設定と違う。Issue に書き込む文面は「30 日動きが無いので stale」「stale になってから 14 日で閉じた」と言っているが、設定は 90 日と 60 日である。利用者は、間違った日数を読むことになる。

提案

    permissions:
      issues: write
    steps:
      - uses: actions/stale@v5
        with:
          days-before-issue-stale: 90
          days-before-issue-close: 60
          stale-issue-label: "stale"
          stale-issue-message: "This issue is stale because it has had no activity for 90 days. Comment to keep it open."
          close-issue-message: "This issue was closed because it has been inactive for 60 days since being marked as stale."
          exempt-issue-labels: "RFC"
          days-before-pr-stale: -1
          days-before-pr-close: -1

action をタグ (@v5) ではなく commit で固定することや、runner を ubuntu-latest から固定の版にすることは、あえて入れない。上流の 10 本の workflow はどれもタグと ubuntu-latest で書かれていて、1 本だけ変えると上流の決まりに合わず、別の議論になるからである。

なぜ中身のある PR か、確かめ方

使わない書き込みの権限、議論中の提案が黙って閉じられること、利用者に間違った日数を伝えていること、の 3 つはどれも具体的な不具合で、変更は数行に収まる。workflow は毎日の定期実行でしか動かないので、PR では、actions/stale の文書にある exempt-issue-labels の動き (そのラベルが付いた Issue は印も閉じるのも対象外) を引用し、マージ後の最初の実行の記録で確かめる。

C. device plugin を、リリース名ではなく結果で見つける

そもそも何の話か

GPU と EFA を Kubernetes の Pod から使うには、ノードごとに device plugin という小さなプログラム (DaemonSet として全ノードで動く) が要る。device plugin は、ノードの GPU の数を kubelet に知らせ、Pod に GPU を割り当てる。1 つのノードで同じ種類のデバイス (たとえば nvidia.com/gpu) を知らせられるのは 1 つだけで、2 つが同時に動くと、どちらの割り当てが使われるかが不安定になる。

device plugin は、いろいろな経路で入る。上流の amazon-eks のテンプレート自身も Helm で入れるが、eksctl でクラスタを作ると eksctl が入れ、NVIDIA の GPU Operator を使っていればそれが入れる。

上流の今

eks-add-gpu-nodegroup.yaml の plugin() は、Helm の決まった 2 つのリリース名を探し、無ければ入れ、同じバージョンなら触らず、違えば止まる。

plugin() { # release namespace version chart [helm args]
  local rel=$1 ns=$2 ver=$3 chart=$4 have; shift 4
  have=$(helm list -n "$ns" -f "^$rel\$" -o json | ...)
  if [ -z "$have" ]; then
    helm upgrade --install "$rel" "$chart" --version "$ver" ...
  elif [ "${have#v}" = "${ver#v}" ]; then
    echo "$rel $ver is already installed; leaving it alone"
  else
    fail "the cluster runs $rel $have and this stack pins $ver. ..."
  fi
}

README の 296 行目は、この弱点を自分で書いている。

The stack recognises the device plugins by the two release names it installs
them under, so a device plugin installed another way, by the GPU Operator or
under another release name, goes unseen and the stack installs a second one
beside it. On a cluster created with eksctl, GPU and EFA node groups come with
device plugins eksctl installs: delete those DaemonSets from kube-system, or
create the eksctl node groups with --install-nvidia-plugin=false, before deploying.

つまり今は、二重に入れてしまう場合があることを文書で知らせ、利用者に手で消してもらっている。読み落とすと、2 つの device plugin が同じ GPU を取り合うクラスタができる。

提案

Helm のリリース名ではなく、device plugin が必ず使うものを手がかりに探す。device plugin は、kubelet と話すために、ノードの /var/lib/kubelet/device-plugins というディレクトリを必ず mount する。そこで、plugin() の前に、全 namespace の DaemonSet のうちこのディレクトリを mount しているものを調べ、このスタックが入れたもの以外があれば、その名前と namespace を挙げて止まる (今の README の手順で消すよう案内する)。

kubectl get daemonset -A -o json | python3 -c '
import json, sys
for d in json.load(sys.stdin)["items"]:
    vols = d["spec"]["template"]["spec"].get("volumes", [])
    if any(v.get("hostPath", {}).get("path", "").rstrip("/") == "/var/lib/kubelet/device-plugins" for v in vols):
        print(d["metadata"]["namespace"], d["metadata"]["name"])'

この方法なら、GPU Operator が入れたものも eksctl が入れたものも、入れ方によらず見つかる。黙って消すことはせず、止まって知らせるだけにするので、利用者のクラスタを勝手に壊さない。

なぜ相談からか、確かめ方

テンプレートの動き (止まる条件) が変わり、ほかの device plugin (たとえば別のベンダーのもの) も見つけて止まるので、どこまでを「衝突」とみなすかを上流と決める必要がある。上流の CONTRIBUTING.md も大きな作業は先に Issue で相談するよう求めているので、RFC の Issue で始める。確かめ方は、eksctl で device plugin つきのノードグループを先に作り、そこにこのスタックを流して、既存のものを見つけて止まることを実機のログで示す。

他の案

(1) 見つけたら自動で消す: 速いが、利用者が意図して入れたものを消す危険がある。(2) GPU Operator の設定 (ClusterPolicy) の有無も見る: GPU Operator には効くが、eksctl や別名の Helm には効かない。(3) ノードの GPU の数 (allocatable) で見る: 二重に動いていても数は同じに見えることがあり、決め手にならない。ディレクトリを手がかりにする方法が、一番取りこぼしが少ない。

D. Capacity Block を探して買う道具を置く

そもそも何の話か

EC2 Capacity Blocks for ML は、GPU のインスタンスを決まった期間 (たとえば 1 日) だけ予約して使う買い方である。使うには、まず空いている枠を探し (型、台数、期間、リージョン)、開始の日時と AZ と前払いの額を見て、買う。買うと予約の ID がもらえ、それをノードの起動に渡す。

上流の今

上流の amazon-eks のテンプレートは、予約の ID を受け取るパラメータを持っている。

CapacityReservationId:
  Type: String
  Default: ""
  Description: >-
    Targeted On-Demand Capacity Reservation or Capacity Block for ML. ...
CapacityReservationType:
  Type: String
  Default: targeted-odcr
  AllowedValues: [targeted-odcr, capacity-block]

同じ形のパラメータは aws-pcs や aws-parallelcluster のテンプレートにもある。一方で、共通の部品を置く architectures/common には 3 つのファイル (非公開のバケット、HyperPod の通知など) しか無く、Capacity Block を探して買う手順や道具はどこにも無い。利用者は aws ec2 describe-capacity-block-offerings と purchase-capacity-block の呼び方を自分で調べることになる。

実際に探してみると、つまずく点がある。distai-platform で 2026-11-17 に全リージョンを調べたとき、照会には回数の上限があり、エラーを「空きが無い」と扱うと空きがゼロに見えた。また照会は 1 回に 1 件の枠しか返さないことが多く、8 日先までの空きを見るには日をずらして何度も聞く必要があった。

提案

architectures/common/ に、AWS CLI だけで動く小さなスクリプトを置き、各構成の README から「CapacityReservationId を手に入れる方法」として案内する。

サブコマンドやることお金
search型、台数、期間 (1 日など)、リージョンの一覧を受け取り、空いている枠を開始日時、AZ、前払いの額つきで並べる。照会の上限に当たったら待って聞き直し、「分からない」と「空きなし」を分けて表示するかからない
purchase選んだ枠を買う。明示の指定 (たとえば --yes) が無ければ買わない。買う前に額を表示する前払い (取り消し不可)
list / describe持っている予約と、その状態、開始と終了を見るかからない

distai-platform 側には、すでに同じことをするスクリプト (探す、見る、購入の前に額を表示して確認する) があり、これを GPU の型を前提に一般化して渡せる。上流の方針に合わせ、Trainium の型を前提にした書き方はしない (型は引数なので、使うかどうかは利用者が選べる)。

なぜ相談からか、確かめ方

置き場所 (common か、各構成か) と、購入まで道具に入れるか探すだけにするかは、上流の判断が要る。購入はお金がかかり取り消せない操作なので、Issue (機能の要望のテンプレート) で先に合意する。確かめ方は、search を実際のリージョンで流して枠の一覧が返ることを示す。purchase まで入れるなら、小さな枠を実際に 1 つ買って予約の ID でノードが起きることを示す。

メタデータトリブル ― 年ごとにテーブルや列を増やす

「今年のデータだけのテーブル」を毎年作り続けると、年をまたぐ集計もスキーマ変更も、増え続けるテーブルや列の数だけ繰り返す作業になります

← SQL シリーズ目次へ

この回の前提: 第 08 回 マルチカラムアトリビュート(同じ意味の値を列の数で増やす設計がなぜ壊れるか)

「今年のバグは bugs_2025、来年のバグは bugs_2026」のように、時間の単位(年や月)ごとにテーブルや列を複製していく設計をメタデータトリブルと呼びます(トリブルは SF 作品に出てくる、放っておくとねずみ算式に増える生き物の名前です)。結論を先に言うと、これは第 08 回のマルチカラムアトリビュートと同じ問題を、列ではなくテーブル全体の単位で起こしたものです。年が増えるたびにテーブルや列が増え、年をまたぐ集計もスキーマ変更も、増えた数だけ繰り返す作業になります。この回では実際にこの設計を作って何が壊れるかを確かめ、PostgreSQL の宣言的パーティショニングと正規化という 2 つの正しい書き方を見ます。

1. 目的 ― 何をしたかったのか

バグ管理システムが長く運用されると、1 つのbugsテーブルにどんどん行が積み重なっていきます。「古いデータは参照頻度が低いから、年ごとに分けておけば検索が速くなるはずだ」という発想から、bugs_2024、bugs_2025のように年ごとに別のテーブルを作る設計が生まれます。あるいは、年次レポートのような集計テーブルで「2024 年の合計」「2025 年の合計」を別々の列(total_2024、total_2025)として持たせる設計も、同じ発想から生まれます。

「古いデータと新しいデータを分けて管理したい」という目的自体は正当で、後で見る宣言的パーティショニングもまさにこの目的のための機能です。問題は、この目的を「テーブル定義そのものを年ごとに複製する」という手段で実現してしまう点にあります。

2. アンチパターン ― どう書いてしまい、何が壊れるか

実際に年ごとのテーブルを作って、何が起きるかを確かめます。

CREATE TABLE bugs_2024 (
  bug_id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  date_reported date NOT NULL,
  summary       text NOT NULL,
  reported_by   bigint NOT NULL REFERENCES accounts (account_id),
  status        text NOT NULL DEFAULT 'NEW'
);
CREATE TABLE bugs_2025 (
  bug_id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  date_reported date NOT NULL,
  summary       text NOT NULL,
  reported_by   bigint NOT NULL REFERENCES accounts (account_id),
  status        text NOT NULL DEFAULT 'NEW'
);

図: 年ごとに同じ構成のテーブルを複製すると、テーブルの数が年数だけ増えていく。

2.1 年をまたぐ集計には UNION ALL が要る

「全期間のバグ件数」を数えたいだけでも、年ごとのテーブルをすべてつなぐ必要があります。

INSERT INTO bugs_2024 (date_reported, summary, reported_by, status) VALUES
  ('2024-03-10', 'old crash on export', 1, 'FIXED'),
  ('2024-11-02', 'old slow report',     2, 'FIXED');
INSERT INTO bugs_2025 (date_reported, summary, reported_by, status) VALUES
  ('2025-01-05', 'crash when saving',     1, 'NEW'),
  ('2025-02-14', 'login fails long email', 4, 'NEW');

SELECT count(*) FROM (
  SELECT bug_id FROM bugs_2024
  UNION ALL SELECT bug_id FROM bugs_2025
) t;

 count
-------
     4
(1 row)

テーブルが 2 つのうちはまだ書けますが、10 年分のテーブルがあれば 10 個の UNION ALL が必要になり、新しい年のテーブルを作るたびに、既存のすべての集計クエリにもう 1 つ UNION ALL を足して回る必要があります。

2.2 スキーマ変更は年ごとのテーブル全部に繰り返す

ALTER TABLE bugs_2024 ADD COLUMN priority text;
ALTER TABLE bugs_2025 ADD COLUMN priority text;
-- 2026年のテーブルを作る時にも同じCREATE TABLE文をコピーして書く必要がある

新しい列を 1 本追加したいだけでも、存在する年のテーブルすべてに同じALTER TABLEを実行する必要があります。テーブルの数が増えるほど、1 回のスキーマ変更が複数の文に分かれ、どれか 1 つを忘れるリスクも増えます。

2.3 列を年ごとに増やす変種もある

テーブルを増やす代わりに、集計テーブルの列を年ごとに増やす変種もあります。

CREATE TABLE yearly_report (
  report_id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  total_2024    integer,
  total_2025    integer
);
INSERT INTO yearly_report (total_2024, total_2025) VALUES (2, 2);
ALTER TABLE yearly_report ADD COLUMN total_2026 integer;
SELECT * FROM yearly_report;

 report_id | total_2024 | total_2025 | total_2026
-----------+------------+------------+------------
         1 |          2 |          2 |
(1 row)

これは第 08 回で見たマルチカラムアトリビュートと同じ構造で、「タグの個数」の代わりに「年」が列の連番になっています。2026 年の値を記録するには、またALTER TABLEで列を追加する必要があり、しかも新しい行にはその列がまだ無いため、既存の行のtotal_2026は NULL のままになります。

3. 見つけ方 ― どんな兆候で気づくか

既存のデータベースの中に年ごとのテーブル複製が無いかは、テーブル名が「接頭辞+西暦 4 桁」という形になっているものをinformation_schemaから探すことで機械的に検出できます。

SELECT c.table_name, array_agg(c.column_name ORDER BY c.ordinal_position) AS cols
FROM information_schema.columns c
WHERE c.table_schema = 'public'
  AND c.table_name ~ '^[a-z_]+_(19|20)[0-9]{2}$'
GROUP BY c.table_name
ORDER BY c.table_name;

 table_name |                            cols
------------+-------------------------------------------------------------
 bugs_2024  | {bug_id,date_reported,summary,reported_by,status,priority}
 bugs_2025  | {bug_id,date_reported,summary,reported_by,status,priority}
(2 rows)

この問い合わせは、テーブル名が「英字の接頭辞 + 1900 年代か 2000 年代の 4 桁」という形(正規表現_(19|20)[0-9]{2}$)に一致するテーブルを集めています。見つかったテーブル同士の列構成(cols)が同じであれば、複製であることがさらに裏付けられます。

4. 使ってよい場合

「古いデータと新しいデータを分けて管理したい」という目的自体は、データベースの運用上よくある正当な要望です。アクセス頻度の低い古いデータを安いストレージに移したい、古いデータだけをまとめて削除したい、というような要望には応える必要があります。問題は、この要望を「別のテーブル定義を毎年手で作る」という手段で実現してしまう点です。次の章で見る宣言的パーティショニングは、まさにこの要望に応えるために PostgreSQL が用意している機能であり、「年ごとに分ける」という目的自体を否定するものではありません。

5. 解決策 ― 宣言的パーティショニングと正規化

5a. 宣言的パーティショニング: 1 つの論理テーブルとして宣言する

PostgreSQL の宣言的パーティショニング(declarative partitioning)を使うと、「年ごとに分けて保存する」という目的を保ったまま、アプリケーションからは 1 つのテーブルに見える形で宣言できます。

CREATE TABLE bugs_part (
  bug_id        bigint GENERATED ALWAYS AS IDENTITY,
  date_reported date NOT NULL,
  summary       text NOT NULL,
  reported_by   bigint NOT NULL REFERENCES accounts (account_id),
  status        text NOT NULL DEFAULT 'NEW',
  PRIMARY KEY (bug_id, date_reported)
) PARTITION BY RANGE (date_reported);

CREATE TABLE bugs_part_2024 PARTITION OF bugs_part
  FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
CREATE TABLE bugs_part_2025 PARTITION OF bugs_part
  FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
CREATE TABLE bugs_part_default PARTITION OF bugs_part DEFAULT;

bugs_partは親テーブル(パーティション化されたテーブル)で、実際の行はdate_reportedの範囲に応じてbugs_part_2024やbugs_part_2025というパーティションに振り分けられます。範囲に収まらない行(未来の日付など)はDEFAULTパーティションが受け取ります。4 件のバグを挿入すると、年をまたいだ集計は分かれたテーブルを意識せず 1 つのSELECTで済みます。

SELECT count(*) FROM bugs_part;

 count
-------
     4
(1 row)

新しい列を追加するときも、親テーブルに 1 回ALTER TABLEするだけで、既存のすべてのパーティションに自動的に伝わります。

ALTER TABLE bugs_part ADD COLUMN priority text;

SELECT table_name FROM information_schema.columns
WHERE table_schema = 'public' AND column_name = 'priority' AND table_name LIKE 'bugs_part%'
ORDER BY table_name;

    table_name
-------------------
 bugs_part
 bugs_part_2024
 bugs_part_2025
 bugs_part_default
(4 rows)

2.2 で見た「テーブルの数だけ ALTER TABLE を繰り返す」手間は、ここでは発生しません。

図: 宣言的パーティショニングでは、論理的には 1 枚のテーブルとして操作し、実際の格納先は PostgreSQL が振り分ける。

5b. リストパーティショニングとハッシュパーティショニング: 範囲以外の分け方

宣言的パーティショニングには、5a で使った範囲パーティショニング(RANGE, 連続する値の範囲で分ける)のほかに、リストパーティショニング(LIST, 離散的な値の集合で分ける)とハッシュパーティショニング(HASH, ハッシュ値の余りで均等に分ける)があります。どちらを選ぶかは、分割の基準にする列がどんな値を取るかで決まります。

ステータスのように、取りうる値が決まった小さな集合であるデータには、リストパーティショニングが向きます。

CREATE TABLE bugs_by_status (
  bug_id   bigint GENERATED ALWAYS AS IDENTITY,
  status   text NOT NULL,
  summary  text NOT NULL,
  PRIMARY KEY (bug_id, status)
) PARTITION BY LIST (status);

CREATE TABLE bugs_by_status_open PARTITION OF bugs_by_status
  FOR VALUES IN ('NEW', 'OPEN');
CREATE TABLE bugs_by_status_closed PARTITION OF bugs_by_status
  FOR VALUES IN ('FIXED', 'CLOSED');

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM bugs_by_status WHERE status = 'NEW';

 Seq Scan on bugs_by_status_open bugs_by_status  (cost=0.00..20.12 rows=4 width=72) (actual time=0.004..0.004 rows=1.00 loops=1)
   Filter: (status = 'NEW'::text)
   Rows Removed by Filter: 1
   Buffers: shared hit=1
 Planning Time: 0.060 ms
 Execution Time: 0.010 ms

status = 'NEW'という条件から、'FIXED'と'CLOSED'を受け持つbugs_by_status_closedには該当行が無いと判断でき、スキャン対象は'NEW'と'OPEN'を受け持つbugs_by_status_openだけに絞られています。このパーティションの内部には'OPEN'の行も 1 件含まれているため、パーティションプルーニングで除外されなかった分はFilterで絞り込まれ、Rows Removed by Filter: 1として表れています。

一方account_idのように、自然な範囲も決まった値の集合も無いが行を均等に分散させたいデータには、ハッシュパーティショニングが向きます。

CREATE TABLE accounts_by_hash (
  account_id   bigint NOT NULL,
  account_name text   NOT NULL
) PARTITION BY HASH (account_id);

CREATE TABLE accounts_by_hash_0 PARTITION OF accounts_by_hash
  FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE accounts_by_hash_1 PARTITION OF accounts_by_hash
  FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE accounts_by_hash_2 PARTITION OF accounts_by_hash
  FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE accounts_by_hash_3 PARTITION OF accounts_by_hash
  FOR VALUES WITH (MODULUS 4, REMAINDER 3);

INSERT INTO accounts_by_hash (account_id, account_name)
SELECT account_id, account_name FROM accounts;

SELECT tableoid::regclass AS partition, count(*)
FROM accounts_by_hash GROUP BY tableoid::regclass ORDER BY 1;

     partition      | count
--------------------+-------
 accounts_by_hash_0 |     1
 accounts_by_hash_1 |     1
 accounts_by_hash_2 |     1
 accounts_by_hash_3 |     1
(4 rows)

accountsテーブルの 4 件の行が、account_idのハッシュ値をモジュラス 4 で割った余り(REMAINDER)に従って、4 つのパーティションにちょうど 1 件ずつ分かれました。分割数と担当範囲の指定方法が、RANGE のFOR VALUES FROM ... TO ...や LIST のFOR VALUES IN (...)とは異なり、MODULUS(分割数)とREMAINDER(余りの番号)を使う点がハッシュパーティショニングの特徴です。

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM accounts_by_hash WHERE account_id = 1;

 Seq Scan on accounts_by_hash_0 accounts_by_hash  (cost=0.00..25.00 rows=6 width=40) (actual time=0.009..0.010 rows=1.00 loops=1)
   Filter: (account_id = 1)
   Buffers: shared hit=1
 Planning Time: 0.138 ms
 Execution Time: 0.023 ms

account_id = 1という等価条件でも、4 つのパーティションのうちaccounts_by_hash_0だけがスキャンされており、等価条件からハッシュ値を計算して対象パーティションを 1 つに絞り込めていることが分かります。ハッシュパーティショニングは PostgreSQL 11 で追加された機能です。

図: 範囲(RANGE)・リスト(LIST)・ハッシュ(HASH)は、分割の基準にする列がどんな値を取るかで選び分ける。

5c. パーティションプルーニング: 関係ない範囲は最初から読まない

date_reportedの範囲を条件に指定すると、PostgreSQL はパーティションプルーニング(partition pruning, 無関係なパーティションを計画段階で除外する仕組み)によって、該当するパーティションだけを読みます。

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM bugs_part WHERE date_reported >= '2025-01-01' AND date_reported < '2026-01-01';

 Seq Scan on bugs_part_2025 bugs_part  (cost=0.00..18.40 rows=3 width=116) (actual time=0.004..0.004 rows=2.00 loops=1)
   Filter: ((date_reported >= '2025-01-01'::date) AND (date_reported < '2026-01-01'::date))
   Buffers: shared hit=1
 Planning Time: 0.132 ms
 Execution Time: 0.010 ms

実行計画にはbugs_part_2024もbugs_part_defaultも一切登場せず、bugs_part_2025だけがスキャンされています。アプリケーションはbugs_partという 1 つのテーブルに対してクエリを書いているだけですが、PostgreSQL が条件の範囲から「2024 年と default のパーティションには該当行が無い」と判断し、計画段階でスキャン対象から除外しています。

図: パーティションプルーニングにより、条件に合わないパーティションは実行計画の時点でスキャン対象から外れる。

5d. DETACH CONCURRENTLY: 古い年を本体をロックせずに切り離す

古くなったパーティションをアーカイブ用に切り離すにはALTER TABLE ... DETACH PARTITION ... CONCURRENTLYを使います(このCONCURRENTLYオプションは PostgreSQL 14 で追加された機能です)。CONCURRENTLYを付けると、切り離し中も本体のbugs_partへの読み書きを長時間ブロックしない縮小されたロックで処理されます。ただし実機で確かめると、このCONCURRENTLYには制約があります。

-- DEFAULTパーティションが残っていると、CONCURRENTLYは使えない(実機で確認)
ALTER TABLE bugs_part DETACH PARTITION bugs_part_2024 CONCURRENTLY;
ERROR:  cannot detach partitions concurrently when a default partition exists

PostgreSQL の公式ドキュメントも「CONCURRENTLY cannot be run in a transaction block and is not allowed if the partitioned table contains a default partition.」(CONCURRENTLY はトランザクションブロックの中では実行できず、パーティション化されたテーブルに DEFAULT パーティションが含まれる場合は許可されない)と明記しています。そこで、使っていない空の DEFAULT パーティションを先に(CONCURRENTLY なしで)切り離してから、本体の切り離しを CONCURRENTLY で行います。

ALTER TABLE bugs_part DETACH PARTITION bugs_part_default;
ALTER TABLE bugs_part DETACH PARTITION bugs_part_2024 CONCURRENTLY;

SELECT count(*) FROM bugs_part;      -- 2024年分が無くなった状態
 count
-------
     2
(1 row)

SELECT count(*) FROM bugs_part_2024; -- 切り離された後も独立したテーブルとしてデータは残る
 count
-------
     2
(1 row)

切り離した後もbugs_part_2024は普通のテーブルとして存在し、データはそのまま読めます。アーカイブ用の別のストレージに移したり、必要ならDROP TABLEで削除したりできます。

5e. 正規化: 列を年ごとに増やす代わりに、年を値として持つ

2.3 のyearly_reportのように列が年ごとに増える変種には、宣言的パーティショニングではなく正規化で対応します。「年」を列名にするのではなく、値として 1 つの列に持たせます。

CREATE TABLE yearly_report_norm (
  year  integer PRIMARY KEY,
  total integer NOT NULL
);
INSERT INTO yearly_report_norm (year, total) VALUES (2024, 2), (2025, 2);
INSERT INTO yearly_report_norm (year, total) VALUES (2026, 0);

SELECT * FROM yearly_report_norm ORDER BY year;

 year | total
------+-------
 2024 |     2
 2025 |     2
 2026 |     0
(3 rows)

2026 年の値を記録するのにALTER TABLEは不要で、行を 1 件追加するだけです。既存の行に新しい列の NULL が生まれることもありません。

6. PostgreSQL エンジンで考慮しておくこと

宣言的パーティショニングは「物理的な分割」と「論理的な 1 枚のテーブル」を両立させる機能ですが、無条件に使うべきというわけではありません。パーティションの境界(この例では年の切れ目)を決めるのはテーブル設計時の判断であり、境界を跨ぐ主キーや一意制約は、本文のPRIMARY KEY (bug_id, date_reported)のようにパーティションキーを含める必要があります。これは通常の単一テーブルのPRIMARY KEY (bug_id)とは異なる制約で、パーティション化を導入する際に見落としやすい点です。

また、パーティションの数が増えすぎると、プランナがどのパーティションを除外すべきかを判断するための計画コストそのものが増えていきます。本文の例のように数年分であれば問題になりませんが、日次パーティションを何年分も保持するような設計では、パーティションの数そのものを管理する運用(古いパーティションを定期的に DETACH して DROP またはアーカイブする)が必要になります。これはメタデータトリブルが「手でテーブルを増やす」ことで生んでいた運用負荷を、今度は「パーティションの世代管理」という形で PostgreSQL の機能の上で整理した状態と言えます。

図: パーティション化されたテーブルの主キーは、パーティションキーを含めた複合キーになる。

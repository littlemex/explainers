データパスを 1 命令ずつ追う ― add ・ load ・ store ・ jump の通り道

この回の前提: 第 09 回 メモリとアドレス、第 11 回 命令デコーダと制御信号

第 07 回から第 11 回まで、ALU ・ レジスタファイル ・ メモリ ・ デコーダ ・ 制御回路という部品を 1 つずつ見てきました。この回ではその部品を配線でつなぎ、1 つの命令が電源オンからレジスタへの書き込みまでにどの線を通るかを、実際に色をつけて追いかけます。rj32 は命令の種類によって通る経路が変わる単一サイクルの CPU で、add (レジスタ同士の計算) ・ load (メモリから読む) ・ store (メモリへ書く) ・ jump (PC を変える) という性質の異なる 4 つの命令を選び、同じ配線図の上でどこが光るかを比較します。

1. データパスの全体図 ― まず配線の地図を見る

rj32 は単一サイクル CPU です。1 つの命令が「取り出し (fetch) → 解読 → 実行 → 書き戻し」の全部を 1 回のクロックの中の組み合わせ回路で済ませます (フェッチだけ 1 段先に進むパイプラインになっていますが、今回は単純化して 1 命令が通る道だけを追います)。下の図が今回使う配線の地図です。docs/architecture.png にある PC ・ Program Memory ・ IR ・ Imm ・ Registers ・ ALU ・ Data Memory という部品と、それらをつなぐ L バス ・ R バス ・ Result バスという 3 本の通り道を、そのまま使います。

どの命令でも必ず通る道が 1 つだけあります。PC → Program Memory → IR という、命令そのものを取り出す道です。これから見る 4 つの命令は、この後の「IR から先」の道の選び方が違うだけです。

図: 今回使う配線の地図。グレーの線は「存在する配線」で、色は付けていない。

2. add rd, rs ― レジスタ同士の計算

add rd, rs (rd <- rd + rs + C) は、レジスタファイルだけで材料が揃う命令です。rd の現在値を L (ALU の左入力)、rs の値を R (ALU の右入力) として読み出し、ALU が加算した結果を Result バス経由でそのまま rd に書き戻します。メモリは一度も使いません。

図: add rd, rs は Registers → ALU → Result → Registers だけで完結し、メモリ (灰色) には触れない。

3. load rd, [rs, imm4] ― メモリから読む

load (rd <- mem[rs + imm4*2]) は、材料が 2 か所に分かれています。アドレスの計算に使う rs (基準レジスタ) と imm4 (オフセット) で、rs は Registers から L 入力へ、imm4 は IR から取り出した Imm が R 入力へ運ばれます。ALU はこれを加算してアドレスを作り、そのアドレスが Data Memory に渡されます。

ここで第 09 回の話が戻ってきます。Data Memory の出力は 1 クロック遅れて確定 するので、読み出したデータが Result バスに乗って rd に書き戻されるのは、アドレスを渡したクロックの次のクロックです。図では Result バスは「ALU の結果」ではなく「Data Memory の出力」から伸びていることに注目してください。

図: load は Imm と Registers の両方から ALU に入り、Data Memory を経由して Result バスで戻る。

4. store [rs, imm4], rd ― メモリへ書く

store (mem[rs + imm4*2] <- rd) は、アドレスの計算は load と全く同じです (rs が L、imm4 が R、ALU が加算)。違うのは、rd の値がもう 1 本別の経路で Registers から Data Memory へ書き込みデータとして直接運ばれる点です。ALU の結果 (アドレス) と、Registers から来る値 (書き込むデータ) が、Data Memory の 2 つの違う入力に同時に渡ります。

store はレジスタに何も書き戻しません。Result バスはこの命令では使われません。

図: store はアドレス計算 (ALU) と書き込みデータ (Registers→Data Memory) が別経路で同時に流れる。

5. jump imm11 ― PC を書き換える

jump imm11 (pc <- pc + imm11) は、これまでの 3 つと大きく違います。ALU の 2 つの入力のうち、L には Registers ではなく PC の現在値 が、R には Imm から取り出した imm11 が入ります。ALU は相対ジャンプの先のアドレスを計算しますが、その結果の行き先は Registers ではなく PC です。Registers も Data Memory も一切使いません。

第 11 回で見たデコーダの L 生成マルチプレクサに「jump/rdval/pc」という 3 択があったのを覚えているでしょうか。jump 命令はまさにこのpcを選ぶ場合に当たります。同じ ALU ・ 同じ Result バスという部品を使い回しながら、送り先だけを変えられるのが、この配線の設計の要点です。

図: jump は PC が L 入力の源になり、ALU の結果の行き先も Registers ではなく PC になる。

6. 単一サイクルという抽象化、そして実装のポイント

ここまでの図は、1 つの命令が「1 回のクロックの中で、必要な部品だけを通って結果を出す」という単一サイクルの見方で描いています。実際の rj32 は fetch と execute の 2 段に分かれたパイプラインで (第 15 回で詳しく扱います)、次の命令のフェッチが前の命令の実行と重なって進みますが、「1 つの命令がどの部品をどう使うか」という今回の絵の骨格は変わりません。

Digital に付属するサンプル CPU Processor.dig も同じ骨格 (PC ・ レジスタ ・ ALU ・ メモリを ALU 中心に配線する) を持つ MIPS 風の単一サイクル CPU です。大きな違いは、rj32 がプログラム用とデータ用のメモリを分けている (第 09 回のハーバード型) のに対し、Digital のサンプルには命令とデータを同じメモリに置く構成 (isProgramMemory フラグを使わない ProcessorVonNeumann.dig) も用意されている点です。配線の基本的な考え方 (ALU を中心に置き、バスで部品をつなぐ) はどちらも同じです。

実装のポイント ― 同じ ALU を何度も使い回す。 4 つの図を並べて見ると、add・load・store・jump のすべてが ALU を通っていることが分かります (store も内部でアドレス計算に ALU を使います)。専用の「アドレス計算器」や「ジャンプ先計算器」を別に作らず、1 つの ALU に異なる入力を渡すだけで済ませているのが rj32 の配線の要点です。部品を使い回すほど回路は小さくなりますが、その代わり「この命令のとき ALU に何を入れるか」を正しく選ぶマルチプレクサ (第 11 回の L/R 生成) の配線が複雑になるというトレードオフがあります。

実装のポイント ― 書き込み先を 1 つのバスに統一する。 add の結果は Registers に、jump の結果は PC に書き込まれますが、どちらも同じ Result バスの仕組みを経由します。書き込み先ごとに別の配線を用意するのではなく、「Result バスに乗せてから、どこに書き込むかを選ぶ」という 1 段のクッションを置くことで、新しい書き込み先 (例えば割り込み時の保存先) を増やすときも Result バスの先に分岐を 1 つ追加するだけで済みます。

図: 専用の計算器を命令ごとに作らず、1 つの ALU への入力の選び方を変えて使い回す。

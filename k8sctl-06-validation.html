K8S CUSTOM CONTROLLER ・ 第 06 回

検証 (validation)

OpenAPI の素朴な制約と、CEL による自由な検証。2 つの仕組みがどう分担しているか

← カスタムコントローラー自作 シリーズ目次へ

第 05 回で見た CRD のスキーマには、形(type)を決めるだけでなく、値を制限する検証の仕組みが 2 つ用意されている。1 つは enum や minimum のような OpenAPI の素朴な制約、もう 1 つは CEL(Common Expression Language: 小さな式言語)による自由度の高い検証。この回では実験で実際に拒否されたエラーを見ながら、両者の役割分担を整理する。

OpenAPI の制約(type, enum, minimum/maximum など)は 1 つのフィールドの形を手早く縛る。CEL(x-kubernetes-validations)は self(今の値)や oldSelf(更新前の値)を使って、複数フィールドの関係や「変更禁止」まで表現できる。ただし、enum・required・型の不一致・長さや個数の上限のように「形の前提が崩れる」違反が 1 つでもあると、そのオブジェクトの CEL ルールはまとめて評価されずに終わる。

検証は何を守っているか

CRD のスキーマが持つ検証は、大きく 2 種類に分かれる。1 つは OpenAPI v3 の標準的な制約で、type・enum・minimum/maximum・pattern・minLength・required・maxItems など、1 つのフィールドの形を宣言的に縛るもの。もう 1 つは x-kubernetes-validations という拡張フィールドに書く CEL で、複数のフィールドをまたいだ関係や、更新前後の比較まで表現できる。実験用 Widget の CRD(第 05 回で見た YAML)は両方を使っている。

図: 1 フィールドの形は OpenAPI、フィールド間の関係や変更禁止は CEL が担当する

OpenAPI の制約: 素朴だが効く

実験用 Widget は size: {enum: [small, large]}、replicas: {minimum: 0, maximum: 10}、image: {minLength: 1}、spec.required: [image] を持つ。これらは宣言するだけで API サーバーが自動でチェックしてくれる、最も手早い検証の手段。

実測(EKS 1.35 のテスト用クラスタ): size: huge を指定すると Unsupported value で拒否、replicas: 11 を指定すると spec.replicas in body should be less than or equal to 10 で拒否された。どちらも、値を見た瞬間に機械的に判定できる種類の制約。

図: OpenAPI の制約は、その場の値だけを見て機械的に通す/拒否する(実測)

制約Widget での使い方実測で拒否された例
enumsize は small か large のみsize: huge → Unsupported value
maximumreplicas は 0〜10replicas: 11 → must be ≤ 10
minLengthimage は 1 文字以上(空文字は同様の仕組みで拒否される)
requiredimage は必須(image を書かないと作成できない)

CEL による検証: self と oldSelf

x-kubernetes-validations には rule(CEL の式)、message(固定の拒否メッセージ)、messageExpression(CEL で動的に組み立てるメッセージ)、fieldPath(どのフィールドのエラーとして報告するか)、reason(エラーの分類)を書ける。式の中では self で今まさに検証している値を、oldSelf で更新前の値を参照できる。

実験用 Widget には 2 つの CEL ルールがある。spec 全体に対する self.minReplicas <= self.replicas(複数フィールドの関係)と、image フィールドに対する self == oldSelf(更新前後を比較する変更禁止)。

実測(EKS 1.35 のテスト用クラスタ): minReplicas: 5(replicas=1 のまま)で更新すると spec: Invalid value: minReplicas must be <= replicas で拒否。image を nginx から redis に変更すると spec.image: Invalid value: "redis": image is immutable で拒否された。self == oldSelf という 1 行だけで「作成時はどんな値でもよいが、一度決めたら変更禁止」という動きになる。

図: self と oldSelf を比べる 1 行の CEL ルールが、変更禁止フィールドを作る

検証が走る順番と、CEL のコスト上限

検証は何でも同時に評価されるわけではない。実測(EKS 1.35 のテスト用クラスタ): size: huge という OpenAPI の enum 違反を起こすと、エラーメッセージに「some validation rules were not checked because the object was invalid」という一文も付いてきた。これは、enum・required・型の不一致・maxLength・maxItems/maxProperties のように「形の前提が崩れる」違反が 1 つでもあると、そのオブジェクト全体の CEL ルールがまとめて評価されずに終わる、という意味。一方で minimum・maximum・pattern・minLength の違反では CEL は普通に評価される。「その項目だけ」ではなく「オブジェクト全体」が止まる点に注意。全体の中でこの検証がどこに位置するかは、第 12 回で admission 全体の流れとして図にする。

CEL の式は API サーバーの中で直接実行されるため、無制限に重い式を許すとサーバーの応答を遅らせてしまう。そのため CEL には実行コストの予算があり、公式ドキュメントによれば式のコストは配列や文字列の長さにも依存する。maxItems や maxLength を付けるのは、単に値を制限するだけでなく、CEL のコスト計算を現実的な範囲に収める役目も持つ。

図: OpenAPI の制約違反があると、その先の CEL ルールまで進まない(実測)

ratcheting: 検証を締めても、既存データは残る

スキーマの制約を後から厳しくすると、既にクラスタにある古いデータの扱いが問題になる。CRDValidationRatcheting(検証のラチェット)という仕組みが無いと、締めた後の制約に違反したままのオブジェクトは、違反と無関係なフィールドを直すだけの更新すら拒否されてしまう。ratcheting はそれを避けるために、「違反しているフィールドに触らない更新」なら通す。ラチェット(ratchet)は自転車の後輪についている、こぐのをやめても車輪だけ回り続けられる仕組みや、ラチェットレンチのように一方向にだけ動く仕掛けのことで、ここでは「違反を広げる方向にだけ足止めする」という比喩。

実測(EKS 1.35 のテスト用クラスタ): replicas=8 の Widget を作った後に、スキーマの maximum を 10 から 5 に締めた。この違反したままのオブジェクトで別のフィールド(size)を変更する更新は通った。一方、違反しているフィールド自体(replicas)を別の違反値(9)に変えようとすると拒否された。新規作成で replicas=8 を指定するのも拒否される。保存されている値も 8 のまま変わらない。確認済み: この機能ゲート CRDValidationRatcheting はこのクラスタで stage が空(つまり GA)で有効だった。

図: ratcheting は違反フィールドそのものへの新しい違反だけを止める(実測)

まとめと次の回

OpenAPI の制約は 1 フィールドの形を素早く縛り、CEL は self と oldSelf を使ってフィールド間の関係や変更禁止まで表現する。形の前提が崩れる種類のスキーマ違反があるとオブジェクト全体の CEL が評価されず、CEL 自体にもコストの上限がある。ratcheting は、検証を締めた後も違反と無関係な更新までは止めない仕組みだった(保存データ自体は締めるだけでは書き換わらない)。

Prismyra の精度
答えは合っているか、どこで崩れるか

結論から。短い文書では、Prismyra の読み出し(文章を書かずに確率を直接読む方式)は、同じモデルに文章を生成させて答えを読む方式と見分けがつきません(差は偶然の範囲)。しかし長い文書では読み出しが生成に負けます(-5.0 点、偶然では説明できない差)。まれにしか出ない正解クラスでは読み出し単体は使えず、学習で決定点を足す必要があります。学習で読み取りの的そのものを鍛える方法(LoRA)は、短い文書は変えずに長い文書を大きく改善しますが、容量をさらに増やす実験は今のところ確認待ちの結果が残っています。

比べ方。特に注記がない限り、比較相手は「同じ重み・同じ L40S に文章を生成させ、その文章から答えを読み取る方式」です。差は問題を復元抽出する 4,000 回のブートストラップで 95% 区間を取り、区間が 0 をまたがないときだけ「差がある」と書いています。

1. 短い文書: 読み出しと生成は見分けられない

読み出し(1 回の計算で選択肢の確率を直接読む)と、生成(文章を書いて、その文章を読み取る)を同じ重み・同じ GPU・同じ問題で比べました。読み出しは質問の分だけ速いので、速さを比べる意味があるのは「正しさが同じ」ときだけです。

課題文書質問読み出し生成差と 95% 区間
RACE-middle15057994.8%95.3%-0.5pt [-1.6, +0.5]
BoolQ40040089.5%88.8%+0.8pt [-1.3, +2.7]

両方の区間が 0 をまたぎます。これは「勝った」という意味ではなく、この短さでは速さの比較に意味があるという保証です。この条件は一つの長さにしか当てはまらないことが、次の節で分かります。

2. 長い文書: ここで初めて分かれる(負けている場面)

同じ 159 問・同じ正解を、周りに同じ分野の他の記事を足して文脈を長くしていきます。質問自体は何も変えず、競合する材料だけが増えます。

文脈トークン数読み出し生成差と 95% 区間
407(未加工)95.0%94.3%+0.6pt [-1.3, +3.0]
6,10483.6%86.2%-2.5pt [-5.6, +0.6]
10,19982.4%87.4%-5.0pt [-8.6, -1.3]

落ちた分の半分くらいはモデル自体の限界です(生成も 6.9 点落ちています)。残り半分は読み出しという方式そのものの弱さで、答えを 1 か所だけで読む読み出しは、文章の中を探して答える生成より、情報が薄まったときに不利という仮説が立っていますが、まだ検証中です(読み出しの決定と、生成が最初に出すトークンを比べる実験が未実施)。文書を周りで埋めるのは意図的に厳しい作り方(ふつうは 1 つの長い文書で、競合する別記事はない)なので、これは下限であって、ふつうの長文書での正しさの保証ではありません。

3. まれな正解クラス: 読み出し単体では使えない

LexGLUE の不公正条項判定(1 つの契約条項に 8 種類の不公正さがあるか)は、答えの 1.5% しか yes になりません。「全部 no」と答えるだけで accuracy 98.5% を取れてしまう、accuracy では測れない課題です。

方式再現率精度F1accuracy
読み出し60.0%5.8%10.5%84.7%
生成100.0%5.8%11.0%86.5%
学習データで最頻の答え0.0%—0.0%98.5%

読み出しも生成も「ほぼ全部に yes」と答える点は同じで、これは読み出しの欠陥ではなく決定点(どこで yes/no を切るか)が無いことの結果です。大きいほうの確率を取るだけだと、しきい値が常に 0.5 に立ち、1 に 70 回しか yes が出ない課題では 0.5 は正しい場所ではありません。

直し方: 答えログから決定点を学習する。すでに答えて、後から正解が分かったログ(ラベル付き文書)から、質問ごとに 1 個の数(しきい値)を合わせます。勾合計算も GPU も 2 つ目のモデルも要りません。

ラベル付き文書数決定点が付いた質問F1
2003 / 811.3%
8008 / 847.4%
2,0008 / 846.6%

精度は 5.8%→39.1%、F1 は 10.5%→47.4%、再現率は変わりません——同じ正解を見つけたまま、誤検知を大きく減らす取引です。800 件で頭打ちになり、2.5 倍の 2,000 件を使っても伸びません。残っている差は、しきい値では直せない「確率の並び順」そのものの問題です。

4. 確信度の正直さ(較正)

正解したかどうかではなく、「どれだけ自信を持って正解したか」を測ります。選択肢ごとの点数を 1 つの数(温度)で割るだけで、決定は 1 つも変えずに確信度の正直さを上げられます。

課題期待較正誤差(ECE)温度
RACE-middle(472 問)0.031 → 0.0160.90
BoolQ(300 問)0.025 → 0.0131.05

温度が 1 より小さいのは「自信が足りない」ほうにずれているという意味で、確信度に関するよくある思い込み(大きいモデルは自信過剰)の逆です。この読み出しは、質問が宣言した選択肢だけで確率の合計を 1 にするので、最初から比較的素直な分布になっています。

5. 間違いの中身: 知らないからか、考えないからか

Prismyra の誤りを詳しく調べると、知識不足が原因なのはごく少数でした。

この結果が意味すること: 読み出しが外す問題の多くは、重みの中にすでにある知識を、1 回の読みで引き出せていないだけです。これが、迷った問題だけをもっと強い(より多く計算する)モデルに回す仕組み(使い方の形のページ)が理屈のうえで成立する根拠になっています。詳しい実験設計と腕(A/B/C/D)の定義は診断: 知らないのか、考えないのかにまとめています。

6. 答えのブレを 0 にする保証(正しさの土台)

複数の文書・質問を 1 回の通過に混ぜると、GPU の計算順序が変わることでごくまれに決定まで動く問題が見つかりました(仕組みのページ)。原因(専門家の割り振りを決めるルーターの行列演算)を特定し、行数に依存しない固定実装に差し替えた結果:

80 文書・11 バッチの本番相当ベンチマークで、不一致 0 件、確率の最大移動 0.000000。到着率を変えた open-loop(368 文書・5 到着率)でも、答えの変化は全区間で 0 件を維持しました。「どの文書が同席するか」で答えが変わらないという保証は、スループットの数字そのものより先に満たすべき条件で、満たしたうえで速さのページの数字が成立しています。

7. 学習で読み取りの的を鍛える(decision-lora アダプタ)

読み出しが実際に読む量(最後の位置の隠れ状態)だけを学習対象にした LoRA を、FP8 のチェックポイントに焼き込んだ版です。配布されているアダプタ(littlemex/prismyra-decision-lora-qwen3.6-35b-a3b)を、同じ読み方の素のチェックポイントと比べます。

課題素のチェックポイントアダプタ付き差
RACE、短い文書(579 問)95.16%95.85%誤差の範囲
BoolQ(400)89.50%90.25%誤差の範囲
RACE、約 1 万トークンに埋めた版(157)83.44%94.27%+10.8pt [+5.1, +17.2]
Kev transfer-v4(764)81.28%85.34%+4.1pt

短い文書は変わらず、長い文書だけが大きく改善します。これは第 2 節で見た「長い文書での負け」を、学習によって狭める直接の証拠です。

8. 容量を増やす実験(LoRA の rank) — 確認待ちを含む

読み取りの的を鍛える LoRA の容量(rank)を 16 から 64 に増やす実験(内部名 a6b)を行いました。

測った集合結果
本番 5 セット(RACE・BoolQ・長文脈 2 種・Kev)5 セットすべてで点推定が 0 以上(この一連の容量実験で初めて)
本番の Kev セットでの統計的有意性符号検定 p = 0.2649。有意性の基準(p < 0.05)には届かない
学習に一度も使っていない鍵付き集合(2,050 問)+1.51 点 [+0.49, +2.59]、p = 0.0062

確かめ済み: 鍵付き集合での +1.51 点は、測り方のバグの影響を受けていません。評価コードが問題を読み込む順番を取り違えるバグが別の実験で見つかったあと、比べる元(素のチェックポイント)と候補(a6b)がこの鍵付き集合でも同じ正しいコードで測られていたことを、別の担当者が確認しました。一方で、本番の Kev セットでの統計的な有意性(p = 0.2649)が基準(p < 0.05)に届かない点は変わっていません。容量を増やす実験は、鍵をかけた集合では確かに効果が出ていますが、本番の判定を覆すところまでは届いていない、というのが今の状態です。

容量をさらに増やす実験(rank 128)と、学習データを増やす実験(ほぼ 2 倍)はどちらも試しましたが、学習に使っていない集合では rank 64 の版を上回らず、採用していません。

9. まだ分かっていないこと

  • 長い文書で読み出しが生成より速く落ちる理由(1 か所だけで答えを読む構造が本質的に不利、という仮説)は、まだ検証していません。
  • 容量を増やす実験(rank 64)の本番セットでの統計的な決定(採用するかどうか)は、鍵付き集合の確認が終わってから下ります。
  • 読み取りの的(option-set head)で学習できる判断には限りがあり、何百語ぶんの計算を 1 回の読みに移せるかはまだ分かっていません。

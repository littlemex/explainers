Prismyra 実測記
効かない高速化を消し、効くものだけを測って残す

Prismyra とは何か。文書を 1 回だけ読み込んで、その文書についての質問に文章を書かずに答えるライブラリ。ふつうの AI は「はい」と一文字答えるだけでも文章を作る仕組み ( 生成 ) を使うが、Prismyra はモデルの内部にある「次にどの文字が来そうか」という確率の値 ( logit と呼ぶ ) を直接読み出して答えにする。1 つの文書に 34 個の質問がついていても、読み込みは 1 回で済む。モデルは Qwen/Qwen3.6-35B-A3B-FP8、GPU は L40S 1 枚。リポジトリは github.com/littlemex/Prismyra で、現在の main は d5161f7。

この文書は、直近の作業で見つかった 10 件の実測の記録。効いていたと思っていた高速化が実は 1 度も動いていなかった話から始まり、効いていない部分を直すたびに前の主張が崩れて撤回した話が何度も出てくる。数字が良く見えた瞬間に疑うべき合図と、自分のミスで測定そのものを無効にした 4 件も、そのまま残す。ここが最も価値のある部分なので、削らずに書く。

0. 数値の要約

10 件の実測を先に並べる。行番号は後の章の見出しに対応しているので、気になる行から直接飛んでよい。

#やったことなぜどう測った他の選択肢結果
1 「保存方式を変えると 8〜9% 遅い」と報告していた機能 (paged) を丸ごと削除した 結果が完璧すぎた ( 計算の順番が変わるはずの経路なのに確率差が 0.0000、メモリの山も小数第 3 位まで一致 ) ので配線を疑った 本体のコードに「実際に使った行数」を記録させる仕組み ( last_branch_rows ) を足して、フラグを渡した通りに動いているかを確かめた 単体テストが全部通っているので配線も正しいと信じる ( 実際は 18 個のテストが全部同じ配線だけを見ていた ) フラグは 7 番目の引数だが呼び出しは 6 個しか渡していなかった。paged の層は 1 度も作られていない = 全ての測定が同じ経路同士の比較だった
2 「質問の数 ( 幅 ) を変えても時間は変わらない」という主張を、長い文書でも測り直した 短い文脈だけで測って「変わらない」と決めていた。文脈が長い実運用でも成り立つかは未確認だった 文脈長を 3,040 トークンと 24,327 トークンの 2 通りで幅を変えて計測。副作用の確認は公開ベンチマーク ( RACE 101 問・BoolQ 60 問 ) の決定と確率のブレで判定 短い文脈の 1 点だけを信じて先に進む 3,040 トークンでは 1.02 倍で「変わらない」に近いが、24,327 トークンでは 1.51 倍 ( 238 ms 対 360 ms )。行数を質問数に合わせて絞る改修を実施、RACE で決定の変化 0 件、BoolQ ( 幅 1 対 1 の対照実験 ) で確率差 0.0000

1. 動いていなかった高速化を削除した

Prismyra には、文書を読み込んだ結果 ( キャッシュと呼ぶ、モデルが文書を理解した内容の保存場所 ) を「ページ」という決まった大きさの箱に分けて保存する方式 ( paged ) があった。実装した本人は、これを使うと「答えは変わらないが 8〜9% 遅い」と測定し、そのまま報告していた。ところがこの結果は全部無効だった。

気づいた合図は「結果が完璧すぎたこと」だった。paged は計算の順番を変える保存方式なので、四捨五入の誤差くらいは出るはずだった。ところが確率の差は 0.0000、メモリの使用量の山 ( ピーク ) も小数第 3 位までぴったり一致していた。順番が違う経路を比べているのに、差が全く出ないのはおかしい。

原因を追うと、配線がそもそも繋がっていなかった。Prismyra.__init__ ( 起動時の設定 ) はフラグを正しく保存し、カーネル ( 計算を実行する低レベルの部品 ) が paged 用の引数を受け取れるかも検証していた。stats() ( 状態を表示する関数 ) にも "paged" という文字が出ていた。しかし実際に文書を読む処理 _read は、保存領域を作る関数 build_cache を 引数 6 個で呼んでおり、paged のフラグは 7 番目の引数だった。つまり呼び出しの時点でフラグが渡っていない。paged の保存領域は 1 度も作られておらず、「paged あり」と「paged なし」の測定は同じ経路同士の比較だった。

この事故のいちばんの教訓は、チェックの網が「設定が正しいか」しか見ておらず「その設定通りに動いたか」を見ていなかったことだった。再発防止として、実際に仕事をするコード自身に「今回は何行を対象に計算したか」を記録させる仕組み ( last_branch_rows ) を追加した。これがあれば、フラグと実際の動作がずれた瞬間に、フラグを見るのではなく実際の行数を見て気づける。

2. 「幅を変えても時間は同じ」は短い文脈だけの話だった

Prismyra は 1 つの文書に対して複数の質問を「幅」という単位でまとめて処理する。文書に「幅を変えても処理時間は変わらない ( 1.01 倍 )」と書いていたが、この測定は文脈が短いときのものだけだった。文脈長を変えて測り直すと、様子が変わった。

文脈長幅を変えたときの時間の比実測 ( ms )備考
3,040 トークン1.02 倍-「変わらない」に近い
24,327 トークン1.51 倍238 → 360幅が増えると明確に重くなる

理由は単純で、各質問が自分専用に文脈のコピーを持って読む実装になっていたため。文脈が長いほど、質問の数 ( 行数 ) に比例して重くなる。そこで、質問数に合わせて処理する行数を絞る改修を行った。

直せば数字は動く。だから答えの中身が変わっていないかを別に確認する必要がある。行数を絞る改修は計算の範囲を変えるので、確率の値がわずかに動く可能性がある。速度が直ったことと、答えが正しいままであることは別の主張なので、別の測定で確かめる。

確認は公開ラベル付きベンチマーク 2 つで行った。RACE ( 101 問、1 文書に複数の質問がつく ) では決定 ( どの選択肢を選ぶか ) の変化が 0 件、確率の最大の動きは 0.1995 だった。BoolQ ( 60 問、1 文脈につき質問が 1 個しかないので、幅を変えても実質「幅 1 対 幅 1」の比較になる、いわば対照実験 ) では確率差が 0.0000。BoolQ の 0.0000 が特に重要で、「本当に差が無いはずの場所で、道具が差が無いと正しく言えている」ことの証拠になっている。

3. メモリの受付チェックが 2 か所で甘かった

GPU のメモリ ( VRAM ) は有限なので、「この処理は入るか」を事前に受付でチェックする。Prismyra の受付チェックは保持する分だけを見ていて、処理の途中で一時的に膨らむ分を見ていなかった。24,327 トークンで実測すると、保持は 0.87 GiB しかないのに、答えを作る一時ピークは 4.97 GiB、文書を読む一時ピークは 5.63 GiB で読む方が一番大きい。しかも読む一時ピークは質問数を減らしても縮まない。つまり「保持だけ見て受け付けた」処理が、実際には保持の 6 倍以上のメモリを一瞬使って落ちる、という状態になっていた。

受付チェックを、両方とも実測値から見積もる形に修正した。答える側の一時ピークは「観測した行あたりの定数 + 設定から計算できる 2,048 バイト/文脈トークン/行」、読む側は「235,582 バイト/文脈トークン」という式にした。この式で見積もると、26,112 トークンは通り、52,224 トークンは何も確保する前に、名前つきで ( どの処理が原因かを言って ) 断られるようになった。

空きメモリの数え方も直した。mem_get_info が返す「空き」は、GPU 全体としての空きであって、自分のプロセスが確保したが今は使っていない分 ( 予約済み未使用 ) を空きに数えない。デバイスの空きだけを見ていたときは、プロセス内に 9 GiB 余っているのに 18,000 トークンの処理を拒否するという、明らかに変な挙動が起きていた。予約済み未使用分を空きに足す形に直した。

この修正はレビューで 2 つの逆方向の誤りを指摘されて、両方直した。

撤回 (a): 「予測値の最大を記憶する」方式は逆に厳しすぎた。最初は「これまで見積もった中で一番大きい値」を記憶して、それを基準に判定する方式にしていた。ところが短い文脈で 1 度でも大きめに見積もると、その値が居座り続けて、あとから来た短い文脈の処理 ( 本来 4.97 GiB で足りる ) を「17.7 GiB 要る」と見積もって断ってしまう。文脈長に依存しない定数の部分だけを記憶する形に変えて解決した。
撤回 (b): 逆方向に、狭い実測から広い幅を予測すると足りない。幅 1 の実測結果だけから幅 32 を予測すると、実測 4.028 GiB に対して見積もりが 3.482 GiB と不足していた。そこで、測った幅より広い処理を見積もりだけで断らないようにした。見積もりは「最低これだけは要る」という下限を言うだけにして、最終判断は実際にメモリを確保してみた結果に任せる。

4. 同じ内容を 2 回コピーしていたのをやめた

Prismyra の中で、計算部品 ( 行列演算のコード ) が読みたいデータの並び順と、保存領域がデータを保管している並び順が違っていた。そのため、層 ( モデルの層、Qwen3.6 なら数十層ある ) を処理するたびに、保存領域をまるごと作り直して並び順を合わせていた。保管の並び順を「トークン優先」に変え、見せ方 ( 計算部品から見える形 ) だけを従来通りに保つことで、この作り直しを消した。計算部品側のコードは 1 行も変えていない。

効果は文脈長によって違った。24,327 トークン・幅 32 では一時メモリが 4.970→3.482 GiB、時間が 360→312 ms、幅を変えたときの効き ( 3 節の 1.51 倍 ) が 1.51→1.29 倍に縮んだ。一方、3,040 トークンでは 2.534 GiB のまま前後でぴったり変化がなかった。短い文脈では、そもそもこの作り直しが処理時間の山の頂上ではないので、直しても見た目の効果が出ない場所だと分かった。

予想していなかった副産物もあった。行あたりの費用 ( メモリ ) が、修正前は幅 1 で 0.111 GiB・幅 32 で 0.155 GiB と幅によって違っていたのが、修正後は 0.109 GiB と 0.109 GiB になり、幅による差そのものが消えた。作り直しのコピーが、幅が大きいときに割高になる原因そのものだったということになる。

5. 一番大事な主張が長い文書で崩れた

Prismyra が主張する中で一番大事なのは「1 回の forward ( モデルに 1 回だけ入力を通す処理 ) で読み取った答えは、文章を生成して得た答えと区別できない」という点。これまでは短い文書だけで確かめていた。今回、同じ RACE 159 問・同じ正解のまま、文書を埴め草 ( 関係のない別の記事 ) で埋めて長さだけを変えて測り直した。

文書の長さ読み取り方式の正解率生成方式の正解率差95% 区間
407 トークン95.0%94.3%+0.6%[-1.3, +3.0]
6,104 トークン83.6%86.2%-2.5%[-5.6, +0.6]
10,199 トークン82.4%87.4%-5.0%[-8.6, -1.3]
撤回。「読み取った答えは生成した答えと区別できない」は、短い文書 ( 407 トークン ) だけで成り立つ主張だった。文書が長くなるにつれて差が開き、10,199 トークンでは区間がゼロを跨がない ( ゼロを含まない ) ところまで悪化した。これはこのプロジェクトで初めて 2 方式がはっきり分離した結果であり、向きは読み取り方式に不利。

半分はモデル自体の問題で、生成方式も文書が長くなると 6.9pt 落ちる。しかし差そのものが開くのは、答えの取り出し方の違いによる。読み取り方式は「あらかじめ宣言した選択肢 ( 4 つなど ) だけ」の中で確率を採点する。生成方式は文字を実際に出力させて、完全一致 → 区切り付き一致 → 先頭一致 → 言及、という 4 段階の緩い判定で答えを拾う。文書が長くなって確率の分布が平らになる ( どの選択肢も差がつきにくくなる ) と、選択肢を 1 発で決め切る読み取り方式の方が不利になる、という仮説を立てている。

これは仮説であり、決着はまだついていない。決着させる測定は「生成方式が最初に出す 1 文字」と「読み取り方式が選んだ選択肢」を直接比べることだが、まだ実施していない。また、埋め草の記事は Prismyra にとって競合にあたる記事を使っているので、この測定は長文脈での精度の下限にあたる ( 敵対的な条件での結果 )。

6. テトリスで結論を 2 回間違えた

機構が違う。彼らは複数の質問を 1 本の列に詰めて渡す ( packed ) ので、後の質問が前の質問を見てしまう。彼ら自身の測定でも、packed は個別に答えたときと比べて回答の 8.0% を変え、正解率を 2.8pt 落とす ( 87.3%→84.5% )。Prismyra の分岐 ( 1 質問ずつ独立に扱う設計 ) にはこの劣化がない。

一方、vLLM ( 別の推論エンジン ) で質問ごとに別のリクエストとして投げる方式 ( separate ) は、文脈の再利用 ( prefix cache ) が効いて、packed より速くて正確だった。

方式正解率速さ ( 問/s )
separate ( vLLM、個別リクエスト )87.0%71.9
packed ( 1 本の列に詰める )84.3%38.7

取り込んだのは温度スケーリング ( 確率の値そのものを少し均す・尖らせる較正の手法 )。これまで確率の「順番」は使っていたが、確率の「値」が正しいかどうかは 1 度も測っていなかった。1 つの数を掛けるだけの手法で、較正誤差 (ECE、確率の値が実際の正解率とどれだけずれているかの指標) が半減した ( RACE 0.031→0.016、BoolQ 0.025→0.013 )。正解率はこの操作では定義上不変 ( すべての選択肢を同じ正の数で割っても、順番は変わらないため )。

温度の向きが彼らと逆だった理由は、たぶん読み出しの範囲の違い。Prismyra の温度は 0.90 と 1.05、彼らは 1.3〜1.5 で、向きが逆。Prismyra は宣言された選択肢だけで確率を正規化するのに対し、彼らは語彙全体から文字を読み出す。正規化する範囲が違えば、確率がもともと尖っている度合いも違うので、較正に必要な調整の向きが変わって当然、という理解。

8. 速度で 4 倍負けていたのを 1.9 倍に詰めた

同一モデル・同一 GPU・同一 RACE 問題で vLLM と正面比較した。比較を公平にするため、vLLM 側の出力も文字トークンだけに絞った ( 絞らずに上位 20 個の候補確率を見る方式だと、答えの文字が改行や <think> というモデルの思考過程を表す特殊なトークンの陰に隠れてしまい、全問が偶然と同じ水準の正解率になった。これに気づかずにいたら、読み出し方式の欠陥をエンジンの遅さとして誤って報告するところだった )。

速さ ( 問/s )文脈あたりの時間送ったトークン正解率
Prismyra ( 最初 )7.36536.7 ms28,4210.953
vLLM31.64125.0 ms76,5560.936

速さは 4.3 倍負けだが、送ったトークン数は Prismyra が 2.7 倍少ない ( 勝ち )。正解率は読み出し方式が違うので単純比較はできない。

遅い原因は計算量ではなかった。1 回の処理 ( 質問に答える枝の部分 ) を profile すると、実時間 268.4 ms のうち GPU が実際に計算していたのは 112.7 ms、つまり 42% だけ。残りはカーネル ( 計算の実行単位 ) の起動待ちで、1 回の処理でカーネル起動が 32,873 回もあった。層の種類別に見ると、線形注意という種類の層が 1 層あたり 1,021 回起動され、通常の注意層は 114 回。Qwen3.6 は 30 層中ほとんどが線形注意層なので、起動回数の 93% がそこに集中していた。中身は、chunked ( 一定の大きさに刻んで処理する方式 ) な走査を素の PyTorch で書いた実装で、1 層あたりコピー 218 回・要素ごとの演算 191 回・掛け算 82 回、合計 66 種類の操作に分かれていた。

vLLM が持っていたカーネルを借りて差し替えると、1 回の処理が 268.4→111.8 ms、1 問あたり 137.5→57.6 ms、速さは 7.36→16.44 問/s、負けは 4.3 倍→1.9 倍に縮んだ。

数値が変わる差し替えなので、採用前に必ず既存実装と照合した。枠組みの実装とカーネルの出力を比較し、相対誤差 5e-2 を超えたら採用を拒否するチェックを入れた。実データ 472 問での影響は、決定 ( どの選択肢を選ぶか ) の 465/472 = 98.5% が一致、正解率は 0.9364→0.9407 で下がっていない。

動いた 7 問のうち 1 問が、動画の長さに関する実機テスト 2 件を落とした。原因は、テストが「正解が整数 6 ぴったり」を要求していたこと。守りたかったのは「時間の情報がモデルに届いているか」だった ( 時間を渡さないと 6 秒の動画が 0.67 秒に見えてしまい、モデルは 2 と答えてしまう )。そこで判定を「5 以上」に直し、定数を書いた場所に理由と測定値をコメントで残した。黙って許容値を広げて変更を通すのは、退行を高速化として出荷する手口なので、避けた。

1 つの差し替えが結果にどれだけ影響したかを測るための仕組み PRISMYRA_WITHOUT を追加した ( 既存の fast_kernels=False は 5 つの高速化を全部止めてしまうので、個別に切り分けられなかった )。

残り 1.9 倍を詰める攻め口は、安い順に 3 つ見えている。(1) 現在の畳み込みカーネルは文脈を読む部分だけを覆っていて、答えを作る枝の部分は素の PyTorch のまま。(2) CUDA graph ( 一連の GPU 処理をまとめて記録し、繰り返し再生する仕組み ) は、放棄する前の 1 回の記録で 83.9→51.7 ms ( 1.62 倍 )。(3) 1 節で削除した paged 経路は、メモリ削減の効果は実測ゼロだったが、決まった大きさの箱に保管する ( page pool ) 発想自体は、長さをデータとして持ち運べるので CUDA graph が必要とする「毎回同じ形」を用意する手段として使える可能性がある。

8b. 遅さの原因はカーネルではなく「起動回数」だった

4 倍負けの原因を探るため、枝パス ( 質問に答える 1 回の通過 ) を計測した。実時間 268.4 ms のうち GPU が計算していたのは 112.7 ms = 42% だけで、残りは次に何をするか指示を待っていた時間。カーネルの起動回数は 32,873 回あった。

しかも偏っていた。線形注意の層 1 つで 1,021 回、通常の注意の層は 114 回。40 層のうち 30 層が線形注意なので、93% がそこから出ていた。中身は「区切って走査する計算」を PyTorch の小さな演算で書いたもので、1 層で copy 218 回・要素ごとの演算 191 回・掛け算 82 回・合計 66 回。

それは枠組み側の「代替実装」だった。枠組みはまず外部のカーネル置き場に問い合わせ、無ければこの遅い実装に落ちる作りになっている。そして vLLM が、その置き場が提供するはずのカーネルを同梱していた。借りるだけで済んだ。
段階枝パスの実時間カーネル起動回数1 問あたり問/s

recurrence カーネルを借りた後111.8 ms6,43857.6 ms16.44

数値が変わる差し替えなので、採用前に枠組みの実装と突き合わせ、相対 5e-2 を超えたら拒否する作りにした。実データ 472 問での影響は決定の 465/472 = 98.5% が一致、正解率は 0.9364→0.9407 で落ちていない。

動いた 7 問のうち 1 つが動画の長さで、実機テスト 2 件が落ちた。そのテストは「正解が整数 6 ぴったり」を求めていたが、守りたかったのは「時間情報がモデルに届いたか」だった ( 時間を渡さないと 6 秒の動画が 0.67 秒に見えてモデルは 2 と答える )。だから「5 以上」に直し、定数の場所に理由と測定値を書いた。黙って許容値を広げて変更を通すのは、退行を高速化として出荷する手口なので避けた。

8c. 通過を録画して再生した ( 3.5 倍 )

起動待ちが半分なら、起動をまとめれば速くなる。CUDA graph は通過を 1 度記録して以後は 1 回の起動で再生する仕組み。過去に試して「再生で落ちる、理由は不明」と放棄した記録があった。

理由は記録する範囲だった。通過の全体を記録しようとすると即座に失敗する。答えを取り出す部分が確率をホスト側の値に変換し、質問のトークンを貼り付けるので、どちらも記録できない。計算部分だけを、入力を固定の置き場に書く形にして、脇の流れで 3 回暖機してから記録すると通った。

群通常録画あり
1147.1 ms114.6 ms
2115.1 ms605.8 ms ( 録画 )
3113.8 ms32.8 ms
4113.6 ms32.5 ms
5113.4 ms32.6 ms

3 群目から 3.5 倍で、しかも全群が確率まで完全に一致 ( 許容値ではなく小数 6 桁まで同じ )。録画は同じ形の 2 回目で初めて取るので、1 回聞いて捨てる用途は何も払わない。追加費用 491 ms は 7 群目で元が取れる。既定は off にした。理由は疑いではなくメモリで、録画は専用のメモリ確保を抱えるため、名前付きで文脈を断る予算 ( 3 節 ) の裏でメモリを取ると、その拒否が嘘になる。

速くなったことより、正しくするまでに分かったことの方が価値がある。再生では Python が走らない。それに依存していたものが 2 つあった。

1 つは想定内。各層が持つ「いま何トークン保持しているか」というホスト側の整数は、再生ではバイトだけ動いて放置される。だから記録と一緒に覚えて、再生後に戻す。

2 つ目は想定外だった。状態の復元を録画の中に入れた状態では、1 回目の再生が通常と違い、2 回目の再生が 1 回目とも違った。これは「録画が読み書きするバッファがリセットされていない」署名。復元を外に出すと、ずれが一定の 0.12 に変わり、こちらの方が情報量があった。線形注意は毎回、状態を新しいテンソルに差し替えるので、録画後は層が「その通過が作ったテンソル」を指し、録画は「録画時に結び付いていたテンソル」を読み続ける。復元が間違った先を埋めていた。両方の結び付けを覚えて、再生の前後で入れ替えた。

最初に書いた検証は通ってしまい、通ってはいけなかった。engine を 2 つ作って一方の群を他方と比べ「6 群すべて一致」と報告していた。1 つの engine 内で文脈ごとに切り替える形にして初めてずれが出た。デバイステストが 4 群分の確率を比べるのも同じ理由で、失敗は再生そのものではなく、その次の群に現れる。

8d. 残り 1.9 倍と、削除した経路の本当の価値

録画の形は文脈長ごとになる。だから 1 つの録画が 1 つの開いた文脈に対応し、同じ文書に何度も聞くセッション型は 3.5 倍を得るが、1 回聞いて捨てる用途は得られない。ここを解けば 1 群目から 32.6 ms になり、1 文脈 1 群でも vLLM を追い越す。

1 節で削除した paged ( ページ分割 ) 経路に、値段が付いた。メモリ削減は実測ゼロだったので削除は正しかった。だがそれが本当に買っていたのは形の固定だった。ページの置き場は固定確保で、長さは別のデータとして渡る。つまり 1 つの録画があらゆる文脈長に使える。録画が 3.5 倍と測れた今、それは「1 つの用途が得る」と「すべての用途が得る」の差になる。削除の判断は当時の証拠では正しく、戻す理由は当時と別のものという形で文書に残した。

9. 自分のミスで測定を無効にした例 (これも必ず書く)

良い結果も悪い結果も、測定のやり方自体が間違っていたら意味を持たない。ここに 4 件をそのまま残す。

質問 id の記事間重複。「質問を単独で聞いたときと、他の質問と一緒に聞いたときで、101 問中 73 問の答えが変わった」という結果が出た。原因は比較コードの誤りで、質問の id は1 回の依頼の中でだけ一意で、記事をまたぐと重複していた ( 101 問で id は 6 種類だけ )。実際には別の記事の質問同士を比べていた。位置で対応付けて id の一致も検査する形に直すと、変化は 0 問になった。
BoolQ の較正が黙って消えた。正解が True/False で、選択肢の文字列が "yes"/"no" なので、文字列としての照合が何も見つからず、較正の区間が出ないまま該当する節が黙って消えていた。正解の位置を、質問がまだ手元にある場所で記録する形に修正し、データが足りず出せないときは「出せない」とはっきり表示するようにした。
ベンチマークが 2 つ目の幅でメモリ不足になった。Context ( 処理中の状態を持つオブジェクト ) が推論エンジンを内部で参照する実装だったため、with 文 ( 使い終わったら片付ける構文 ) を抜けた後も名前が残っていると、35 GiB のモデルの重みが生きたままメモリに居座り続けていた。
穴が 0 個の盤面で質問 id が衝突した。しきい値を真値の両側に置く設計 ( 6 節 ) で、max(0, 0-1) と 0 が同じ値になり、2 つの質問が同じ id を持ってしまった。パッケージ自身が持つ重複 id 検査が拒否したことで発覚した。

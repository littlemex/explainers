← MLIR基礎 シリーズ目次へ

MLIR は Multi-Level Intermediate Representation の略で、その名のとおり「多層の中間表現」を扱う枠組みです。1 つの固定した IR に全部を押し込むのではなく、抽象度の違う複数の方言 (dialect) を共存させ、高位から低位へ段階的に lowering (降下) していきます。このページでは、なぜ多層なのか、方言とは何か、lowering がどう進むのかを図で掴み、最後に 10 問のクイズで確認します。

1. なぜ IR は「多層」なのか

コンパイラは、人間が書いたプログラムを機械が実行できる形へ翻訳します。その途中の内部表現が IR (Intermediate Representation, 中間表現) です。ここで大事な問いがあります。最適化や解析をするとき、どの抽象度で見るのが得かは、やりたいことによって違うのです。

たとえば「行列積 (matmul) 全体をタイル分割して並べ替える」ような変換は、ループや行列がまだ 1 つの塊として見えている高位でこそ簡単に書けます。逆に「レジスタ割り当て」や「この命令をこのハードウェア命令に対応づける」処理は、個々の演算がバラけた低位でないとできません。1 つの固定 IR にすべてを押し込むと、どちらかが必ず不便になります。

MLIR の答えは「抽象度の違う表現を何段も用意し、上から下へ順に降ろす」です。各段で、その抽象度に一番合った最適化を行います。この降下を lowering と呼びます。

図 1: 高位方言から低位方言へ段階的に lowering する。各段でその抽象度に合った最適化を行う。tosa はさらに linalg へ降ろされるのが典型で、ここでは簡略化して同段に描いている

2. 方言 (Dialect) とは何か

方言は、関連する演算 (Operation)・型 (Type)・属性 (Attribute) をひとまとめにした「語彙の集合」です。linalg.matmul、affine.for、llvm.add のように、演算名は必ず 方言名.演算名 の形をとります。ここが MLIR の肝で、方言は誰でも追加でき、複数の方言が同じモジュールの中に混在できます。だから「高位方言でループを表しつつ、一部だけ低位方言」という中間状態が自然に表現できます。

MLIR の構造は入れ子になっています。Operation が基本単位で、Operation は 0 個以上の Region を持ち、Region は 0 個以上の Block を持ち(通常は 1 個以上。本体を持たない external 宣言のように空 Region もある)、Block は Operation の並びを持ちます。この再帰構造のおかげで、for ループの本体のような「命令のかたまり」を素直に表せます。値は SSA (Static Single Assignment) 形式で、各値はちょうど一度だけ定義されます。

図 2: Operation ⊃ Region ⊃ Block ⊃ Operation の入れ子。ループ本体を Region として素直に表現できる

3. 段階的 Lowering を実例で見る

行列積 $C = A B$ を例に、高位から低位へ降りる様子を追います(以下は説明のための疑似 MLIR です。実際の構文とは細部が異なります)。まず高位の linalg 方言では、行列積が1 つの演算として書けます。

// 高位: linalg 方言。行列積が 1 命令(疑似 MLIR)
%C = linalg.matmul ins(%A, %B : tensor<MxKxf32>, tensor<KxNxf32>)
                   outs(%Cinit : tensor<MxNxf32>) -> tensor<MxNxf32>

これを affine 方言へ lowering すると、行列積の定義 $C_{ij} = \sum_{k} A_{ik} B_{kj}$ がそのまま三重ループに展開されます。1 つの高位演算が複数の低位演算に開かれるのがポイントです。なお affine.load/store は実際には tensor ではなく memref (メモリ上の配列) に対する操作で、この間に tensor を memref に変換する bufferization という段が本来入ります(本稿では簡略化のため省略しています)。

// 低位へ降下: affine 方言。三重ループに展開(疑似 MLIR。実際は memref を対象とする)
affine.for %i = 0 to M {
  affine.for %j = 0 to N {
    affine.for %k = 0 to K {
      %a = affine.load %A[%i, %k]
      %b = affine.load %B[%k, %j]
      %c = affine.load %C[%i, %j]
      %p = arith.mulf %a, %b
      %s = arith.addf %c, %p
      affine.store %s, %C[%i, %j]
    }
  }
}

さらに scf (構造化制御フロー) の for/if を経て、非構造化の cf 方言 (分岐 cf.br / cf.cond_br) へ変換され、最後に llvm 方言まで降ろすと LLVM IR に変換でき、最終的な機械語コード生成へつながります(標準的な経路は affine → scf → cf → llvm)。各段の変換では意味 (計算結果) が変わらないことが保証されます。i, j ループをタイル幅 $T$ で分割すると、反復空間は $\lceil M/T \rceil \cdot \lceil N/T \rceil$ 個のタイルに分かれ、こうした最適化は「ループがまだ見えている」affine 段でこそ書きやすいのです。

図 3: lowering は「1 つの高位演算」を「多数の低位演算」に開く。結果 (意味) は保たれる

4. パスと Dialect Conversion

lowering や最適化の実体は パス (Pass) です。パスは IR を受け取って書き換えます。よく使うのがパターン書き換え (Pattern Rewrite) で、「この形の部分木を見つけたら、こう置き換える」というルールを多数登録し、適用できなくなるまで繰り返します。

方言をまたぐ変換は Dialect Conversion の枠組みで行います。ここでは変換後に「どの方言・どの演算なら残ってよいか」を legal (合法) として宣言します。full conversion の場合は legal でない (illegal な) 演算がすべて消えるまで書き換えますが、illegal な演算の残存を許す partial conversion というモードもあり、段階的 lowering ではむしろこちらが多用されます。型が変わる場合は TypeConverter が橋渡しします。「変換 (conversion)」は方言・型の境界を越える書き換え、「変形 (transformation)」は同じ方言内での最適化、と役割が分かれます。

図 4: Dialect Conversion は「illegal な演算が全部消える」まで legal な演算へ書き換える(簡略化。実際は scf → cf → llvm と cf 方言を経由する)

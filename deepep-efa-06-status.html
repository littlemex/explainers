注目すべきは upstream のカーネルを書き換えていないことです。hybrid_dispatch.cuh と hybrid_combine.cuh は触らず、_unordered という別ファイルを並置し、EP_HYBRID_KERNEL で JIT 時に選びます。ホスト側も if (elastic::use_ordered_hybrid_kernel()) { 上流の形 } else { 新しい形 } という分岐で、バッファのサイズ計算まで 2 通り持っています。

この形にした理由は、両者で 受信レイアウトが違うためです。ordered は token 番号で引ける形、unordered は slot 番号で引く形。同じバッファ計算にはできません。「上流に戻しやすい形」と「変更を局所化する形」の両立として、この分岐は妥当な選択です。

3open PR 6 本

2026-09-04 時点で開いているものです。性質で 3 つに分かれます。

安全性 (静かに壊れる箇所を検出可能にする)

PR要旨
#12pack_combine_recv_addr(rank, slot, channel) が 5 / 14 / 12 bit へ実行時マスク無しでシフトしている。slot が 16383 を超えると rank フィールドへ漏れるが、channel は無傷なので実行時 assert channel == channel_idx は通過する。結果は 間違った rank への reduce か 来ない相手を待つ hang。3 つの上限がコンパイル時定数なので JIT 時の EP_STATIC_ASSERT に落とす提案

スケール上限

PR要旨
#5rail barrier を counting barrier に書き換えて「域ごとに専用 signal」という要求を外し、既定 11 context での 176 rank の壁を上げる。QP を削って回避する道も測定済みで、11 → 5 は dispatch +1.9 % だが combine +30.5 % と報告されている

性能 (submission rate と偏り)

PR要旨
#9combine の submission rate を 3 方向から上げる: channel/SM の 4 本上限を外して shared memory と signal 予算に決めさせる (12 SM で 8 本)、既定 context を 11 → 13 にして 12 SM の各 SM が QP を専有する、forward warp を 2 本組にして 1 トークンの hidden 次元を分担する
#8combine の scale-out put を remote-first に並べ替える。dispatch の到着順を凍結した handle 順で replay すると、ローカル完結トークンとリモートトークンが網の都合で混ざり、片方のノードが 62 GB/s、もう片方が 76 GB/s という偏りが出る
#2channel が持つトークン数より多くの part に割らない。予算が最も緩いのは channel が最も少ないトークンしか持たないときなので、decode 形状で kMaxParts に張り付き「3 トークンを 4 part」になる。sub-part 側には既に下限があるのに part 側には無い、という非対称の指摘
#1EP_NUM_SUB_PARTS / EP_MIN_SUB_TOKENS / EP_SM100_MIN_SUB_TOKENS を JIT の -D へ転送する。3 つとも device 専用なのでホスト側のサイズ計算とズレない、という安全性の論証つき。flags が kernel_signature に入るので環境を変えれば再 JIT される

PR #1 と #2 は積み重なっていて (#2 が #1 を含む)、#9 は #5 と既定 context 数で衝突しうる関係にあります。予算という 1 つの資源を複数の PR が別方向に引っ張っているのが今の状態です。第 5 回の予算計算機で c を動かすと、この綱引きの形がそのまま見えます。

図 1: 4 本の PR が同じ予算式に触る。だから「予算式の性質を機械的に検査できる状態」を先に作ると、以降の議論が全部速くなる

4走らせ方 (実機側)

現状の検証手順です。ここを読むと「なぜ emulator が欲しくなるか」が具体的になります。

AWS が公開している手順は awsome-distributed-ai の deepep-v2-benchmark にあります。要求される版が細かく積み重なっています。

要求理由 (README の記述)
NCCL ≥ 2.31DeepEP V2 がリンクする GIN device API (nccl_device.h)
EFA installer ≥ 1.50EFA-GDA バックエンド (GIN type 5) を含む aws-ofi-nccl を同梱。1.49 以下では動かず、image build が明示的に失敗する
ホストの EFA カーネルドライバ ≥ 3.3.0completion counter API (efadv_create_comp_cntr) が入った最初の版。コンテナではなくホストに入れる必要がある
gdrdrv がロード済みlauncher が /dev/gdrdrv を bind mount し、plugin の GIN 初期化が gdr ハンドルを開く
NCCL_GIN_TYPE=5未設定だと NCCL は EFA でも CPU proxy を選ぶ
ノード 2 台test-internode = ノード間 dispatch/combine。1 台では NVLink 経路しか踏まない

これで初めて tests/elastic/test_ep.py が回ります。open PR の測定条件も同じ水準で、たとえば PR #1 は「2 × p5en.48xlarge (8×H200 + EFA 16 枚)、EP8×2 = 16 rank、3 反復、変種は反復内でインタリーブ、変種ごとに別の JIT キャッシュ、16 rank の平均を取ってから反復平均」と書いています。測り方は丁寧ですが、この 1 回のためにノード 2 台が要ります。

ここが現状のボトルネック
プロトコルの正しさに関わる変更 (part の切り方、signal の割り当て、bit 詰めの上限、iteration の扱い) であっても、確認手段が 2 ノードの EFA 実機で test_ep.py を通すことしかありません。しかも第 3 回で見たとおり、順序に起因する誤りは 確率的で、負荷が高いときだけ出ます。「実機で 1 回通った」は、順序の反例を踏まなかったことの証明にはなりません。

6空いている穴

ここまでの観察から、貢献の入口を 3 つに整理します。

  • コメントが存在を約束しているテストが無い。 qp_mapping.cuh は「出荷されているロジックそのものが tests/cpp/test_qp_mapping.cpp の unit test としてコンパイルできる」と書いていますが、tests/cpp/ は存在しません。予算計算 (gin_resource_alloc.cuh) も header の pack / unpack も同様にホストで実行できますが、テストがありません。GPU も EFA も不要です。
  • 不変条件が文書化されていない。 第 4 回で取り出した I1 (weak signal 契約)・I2 (signal を先に読む・acquire)・I3 (基準値の正確さと drain) は、コードは満たしているのに理由が書かれていません。特に I2 は行を入れ替えると静かに壊れる種類の依存で、コメントも回帰テストもない状態です。
  • 順序を能動的に乱す検証手段が無い。 実機テストは「たまたま踏まなかった」を区別できません。順序・遅延・分割を指定して再現する仕組みがあれば、PR #12 のような既知バグの再現も、I1〜I3 の回帰テストも、31 bit iteration の境界も、EFA なしで回せます。

    • 3 つは独立ではなく、1 → 2 → 3 の順に土台が積み上がる関係にあります。次の回で、この 3 番目 ―― EFA を持たずに順序を支配する ―― が技術的に成立するのかを、NCCL の公開 API に照らして判定します。

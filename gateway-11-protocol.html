第 11 章 箱の 0 点は、能力ではなく直列化だった

この章の 3 行 自前の箱を新しいモデルに替えたら、エージェントの全ステップが失敗し、40 ステップの予算を 15 秒で 使い切った。原因はバグでも能力でもなく、ハーネスが決めた書式が、そのモデルが訓練された書式に 似ていて一致しないことだった。書式を変えるだけで、同じ箱・同じ問題・同じ予算で 解けた数が 0 から 6 になり、使えなかった手が 68.8% から 1.0% に落ちた。

何が起きたか

これまでの章で箱に流していたのは分類や要約で、いずれも1 往復で終わる仕事だった。第 2 章の SWE-bench はそうではない。モデルはファイルを検索し、読み、パッチを書き、テストを走らせる。 つまり道具を呼ぶ必要がある。

箱のモデルを Qwen3.6-35B-A3B-FP8 に替えてこれを回したところ、結果は 1 行で書ける。 全ステップ失敗、40 ステップを 15 秒で消費、パッチは 1 バイトも書かれない。

15 秒という数字がヒントだった。1 ステップあたり 0.4 秒。これはモデルが考えている時間ではなく、 返ってきた答えをハーネスが受け取れずに捨てて、次を聞いているだけの時間である。実際にモデルを 直接叩くと、正しい道具の名前を毎回選んでいた。壊れていたのは道具の呼び方の書き方だけだった。

ハーネスの書式と、モデルが訓練された書式

このハーネスは道具の呼び出しをテキストでやり取りしている。システムプロンプトはこう指示する。

<action tool="search">
pattern: def prepare_body
</action>

読み取り側は <action> の中の キー: 値 の行を引数として拾う。 テキストにしているのは理由があってのことで、送るバイト列がどの層でも完全に同一になり、目で読めて、 提供元のライブラリではなくこちらの手元で版を管理できる。

ところがこの箱のモデルは、道具呼び出しを別の書式で訓練されている。vLLM を --tool-call-parser=qwen3_coder で起動していることがその宣言になっている。そちらの書式はこうだ。

<parameter=pattern>
def prepare_body
</parameter>
2 つは似ている。だから混ざる どちらも山括弧のタグで、どちらも「名前と値」を並べる。まったく違う書式なら、モデルは指示された方を そのまま真似たはずである。近すぎるせいで、モデルは 2 つの書式の断片を混ぜたものを書いた。 これは能力の問題ではなく、こちらが選んだ書式がそのモデルの訓練分布のすぐ隣にあったという問題である。

チャットテンプレートは無罪だった

最初に疑うべきはこちらの設定である。サーバがプロンプトを組み立てる段で余計なものを注入していれば、 モデルは指示を見ていないことになる。そこでサーバが実際に組み立てたトークン列を出させた。 道具を宣言しない状態では、system と user のメッセージだけで21 トークン、注入は何もなかった。

設定の不具合ではなく、モデルの事前分布である。第 6 章では逆に、フラグ 1 個の書き忘れが結論を 壊していた。今回は同じ形の疑いを持って調べ、今回は設定が正しかったという結論になった。 どちらも「先に自分を疑う」手順から出た答えで、答えが違うだけである。

崩れ方は 1 種類ではなかった

実際に返ってきたものを並べる。ここが判断の分かれ目になった。

返ってきた形何が起きているか受理したか
<parameter=pattern>qdp</parameter> 素の方言。名前と値は曖昧さなく読める受理する
<parameter=pattern"> 囲いタグ側の属性の引用符が、引数名に混入している受理しない
</path> <action> で開いたブロックを、引数の名前で閉じている受理しない
pattern: (値なし) キーだけ書いて値を書いていない。書式ではなく中身の欠落モデルの失敗
run_command / run 存在しない道具の発明モデルの失敗

1 種類目だけを受理する読み取り側を作り、そこで凍結した。これを文法 v2 と呼ぶ。

なぜ 3 種類目で手を止めたのか 1 種類目を受理するのは読み取り側の瑕疵の修正と言える。名前と値が曖昧さなく書かれているのに 読めていなかったのだから。だが 2 種類目、3 種類目と足していくと、それは瑕疵の修正ではなく そのモデル専用のパーサを書いていることになる。ベンチマークを測定対象に合わせて曲げる作業で、 同じことを次のモデルにやれば数字は誰とも比べられなくなる。後付けの一般化は 1 回までなら直せる穴、 連続すればチューニングである。だから文法は v2 で止め、代わりに書式そのものを変える実験 (この章の後半) をした。

この変更は 1 つの層しか助けない。だからそう書く

文法 v2 はコードの上ではどの層にも等しく適用される。だがそれを「中立」と呼ぶのは誤りである。 記録済みの全ステップについて、道具の名前は読めたが引数の対象が一度も名指しされなかった手を数えると、 こうなる。

API 2 層はこの形を 1,588 ステップ中 0 回しか出していない。つまり文法 v2 は 構造的に API の点数を動かせず、得をするのは測定対象である 1 層だけである。 測定対象が落ちているのを見た後で読み取り側を緩めた、という事実は消えない。

擁護は「中立だから」ではなく、3 つの手続きである 版で凍結する — 文法は v2 で止め、次のモデルのために拡張しない。
本物の失敗は吸収しない — 値のない引数、発明された道具、壊れた JSON はモデルの失敗として計上し、 読み取り側が埋めたり言い換えたりしない。どの書式でも「最初に現れた空でない値が勝ち、値を合成しない」 という規則を通した。
緩めた分を毎回数える — v1 なら拒否されていた読み方で受理した手の数を、全エピソードに併記する。 脚注ではなく本表に置く。

動かして見えること

  • v2 が助けるのは 1 行目だけである。引用符が混入した形と閉じタグが違う形は、v2 でも読めない。 受理する範囲を広げる作業は、ここから先が急に「そのモデル専用」になる。
  • 値のない引数と発明された道具は、どの読み取り側でも失敗のままである。これは書式の問題ではないので、 吸収したら測定が壊れる。
  • 提供元の API はどの行も通る。形式の合意をこちらで発明しないので、混ざる余地がそもそも無い。

書式を変えると何が変わったか

15 件の問題を選び、同じ箱・同じステップ予算・同じトークン予算で、書式だけを変えて3 回測った。 選び方は測る前に宣言してある — 対象一覧の中でリポジトリごとに 1 件目、3 件以上あるリポジトリは 2 件目まで。 後から都合のいい部分集合を選べないようにするための手順である。

v1 の列は中断した走行で 8 件しか含まないので、向きだけを読む数字として扱う。 v2 と道具呼び出しの列は同じ 15 件である。

v2 で解けた 3 件は、全部が緩めた読み方に依存していた それぞれ 10 手・11 手・8 手が v1 なら拒否されていた読み方で通っている。つまり凍結した v1 の文法では、 この箱はこの 15 件で 1 件も解かない。第 2 章の表で箱が最下位にいるのは、この状態で測った数字である。

本質的な教訓は、指標を 2 つに割ったこと

この件で一番効いたのは、パーサの改良ではない。「道具を駆動できたか」と「バグを直せたか」を 別の数字として記録するようにしたことである。

それまでは「解けた率」しか無かった。0 点という数字は、能力が低いのか、道具を呼べていないのかを 区別できない。同じ 0 点が 2 つのまったく違う原因から出るのに、報告する数字が 1 つしか無かった。 いまはエピソードごとに、手そのものが無かった回数、存在しない道具を呼んだ回数、引数を名指ししなかった回数、 緩めた読み方で通した回数が、解けたかどうかとは別に記録される。

1 つの数字は 2 つの問いに答えられない 第 5 章は「物差しが嘘をつく」話だったが、こちらは物差しが 1 本しか無い話である。 嘘をついていたのではなく、2 つ質問しているのに答えの欄が 1 つしか無かった。

エラー文面がモデルを契約から遠ざけていた

引数が無い呼び出しを拒否するとき、ハーネスは search needs a pattern とだけ返していた。 要求は伝えているが、書き方は何も示していない。実測したのはその後の挙動である。

そのエラーを受けたモデルは、方言側へさらに寄った 「pattern が必要だ」と言われた次の手で、モデルは <parameter=pattern> 形式に 切り替えた。こちらのエラー文が、モデルを契約から遠ざけていた。文面を「埋めた形をそのまま見せる」 ものに変えた — 骨組みではなく、値まで入った実例を返す。骨組みを送り返しても、モデルが既に空で 送ってきているのは骨組みだからである。

これは特定のモデルへの対応ではなく、どの層に対しても質の低い環境だったという話である。 拒否の理由だけ言って正解の形を示さないのは、人間の同僚に対してもやらない。

自分の集計にも 1 つ間違いがあった

成功した手を故障に数えていた list_dir は引数 dir を省略するとチェックアウトの根を一覧して成功する。 ところが集計は「対象を名指ししていない手」を一律に故障として数えていて、この成功した手も混ぜていた。 結果、テキスト書式の「使えなかった手」を 45.2% と 3.3 ポイント過大に出していた (正しくは 41.9%)。故障の計上は拒否された手に限るように直した。

誠実さを保つために置いた欄が、その欄自身のせいで水増しされていた。第 5 章の物差しの話と同じ形の失敗で、 厳しく数えているつもりの場所が、いちばん検算されない。

この結果が言っていないこと

提供元の道具呼び出し API のほうが良い書式である、とは言っていない。あちらに変えると、 どの層でも同一だったバイト列が層ごとに違う変換器に置き換わる。この箱では vLLM の qwen3_coder パーサ、他の層では各提供元の実装で、それらは同一でもなく同じ品質でもない。 つまり測っているものが「モデル」から「モデルと変換器の組」になる。この章が言えるのは この箱・この問題群では、テキスト書式が解けた数の半分と 100 手のうち 42 手を奪っていたという 狭い事実だけである。

自作の書式を中立にできる、とも言っていない。どんな書式も、どこかのモデルの訓練分布には 他より近い。今回のものは Qwen3.6-35B-A3B が出すよう訓練された形のすぐ隣にあり、 近いからこそ混ざった。取れる対策は「もっと良い書式を発明する」ことではなく、 書式の遵守と課題の達成を 2 つの数字で報告することである。

この章の箱は「考えずに」答えている。箱の vLLM は --default-chat-template-kwargs={"enable_thinking": false} で起動していて、 上の 3 列はいずれも思考を切った状態の箱である。相手の API 側は思考を使うので、 そこは揃っていない。この軸をどう揃えるかは第 12 章の主題になる。

15 件、1 つの問題群である。解けた数の差は 15 件のうち 3 件の移動で出ていて、 確率の主張ではない。使えなかった手の率は 490〜511 手を数えたものなので、そちらは件数の影響を受けにくい。

運用のルール

  1. 自作の書式でモデルを評価する前に、そのモデルが訓練された書式を確認する。 提供元が公開しているパーサ名 (--tool-call-parser に渡す値) がその宣言になっている。 近い書式は、遠い書式より危ない。
  2. 0 点を見たら、まず「呼べていない」を疑う。ステップあたりの所要時間が異常に短ければ、 それは考えていない時間である。
  3. 書式の遵守と課題の達成を、別の欄に記録する。後から分離することはできない。 記録していなければ、0 点の原因は永久に判別できない。
  4. 拒否のメッセージには、通る形を値まで入れて書く。要求だけ伝える文面は、モデルを 自分の癖のほうへ押し戻す。
  5. 読み取り側を緩めたら、緩めた回数を結果に併記する。そして「後から緩めた」と書く。 緩めた事実を書かない限り、それは測定ではなく調整である。
記録が無いと、後からやり直せない この件で困ったのは、既に支払い済みの 2,228 ステップについてモデルが実際に返した文字列が 保存されていなかったことである。残っていたのは解釈済みの要約だけで、新しい読み取り側で 読み直すことができず、API 2 層への影響が無いことを間接的な数え方で確認するしかなかった。 いまは各エピソードに返答そのものを保存している。再実行と再解釈の違いは、生の記録があるかどうかで決まる。

この章で壊しておきたい誤解

よくある思い込み実際は
全ステップ失敗ならモデルの能力の問題ステップ 0.4 秒は考えている時間ではない。直接叩けば正しい道具を選んでいた
指示された書式と違う書式を出すのは指示追従の失敗訓練された書式と近すぎると混ざる。遠い書式のほうが素直に真似される
パーサを緩めるのは公平な修正コード上は全層に等しくても、API 2 層は 1,588 手中 0 回この形を出していない。得をするのは測定対象だけ
読み取り側を緩めれば直る崩れ方は 3 種類あり、緩めて救えたのは 1 種類。残りを追うとそのモデル専用パーサになる
厳しく数えている欄は信頼できる成功した list_dir を故障に数えて 3.3 ポイント水増ししていた。厳しい欄ほど検算されない
解けた率が 1 つあれば品質は測れている道具を駆動できたかと直せたかは別の問い。1 つの数字は両方に答えられない

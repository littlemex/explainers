アンビギュアスグループ ― グループの外の列を取り出す

GROUP BY に書いていない列を一緒に取り出すと、どの行が選ばれるかが不明確になる。PostgreSQL は原則これを拒否するが、MIN と MAX を組み合わせると実在しない行を作ってしまう抜け道が残っている

← SQL シリーズ目次へ

この回の前提: 第 01 回 アンチパターンとは何か (サンプル DB の構造)、第 13 回 インデックスショットガン (複合インデックスの考え方)

「グループごとに集計しつつ、そのグループを代表する 1 行の詳細も一緒に見たい」という要望はよくあります。たとえば「担当者ごとに、最も時間がかかったバグの件名を知りたい」というような場合です。結論を先に言うと、GROUP BY に書いていない列を素朴に SELECT に混ぜるのは、どの行の値が選ばれるかが保証されない危険な書き方です。PostgreSQL は多くの場合これをエラーで止めてくれますが、MIN と MAX を別々の列に使うと、実在しない行の組み合わせを平気で返してしまう抜け道が残っています。この回では、この抜け道がなぜ起きるのかと、各グループの代表行を安全に 1 行だけ取り出す 4 つの方法 (DISTINCT ON、window 関数、LATERAL、NOT EXISTS) を、実際の実行速度の違いまで含めて確認します。

1. 目的 ― 何をしたかったのか

GROUP BY は「複数行を 1 つの代表値にまとめる」操作です。たとえば SELECT reported_by, count(*) FROM bugs GROUP BY reported_by は、1 人の報告者が何件のバグを報告したかを数えます。ここまでは誰も迷いません。

問題は、集計の結果だけでなく「そのグループの中で一番目立つ 1 行」の詳細も同時に見たくなったときです。「担当者ごとに、件数だけでなく最も時間がかかったバグの件名も表示したい」という要望は自然に出てきます。このとき、多くの人が次のような書き方を試みます。

SELECT reported_by, bug_id, summary, max(hours) AS max_hours
FROM bugs
GROUP BY reported_by;

この書き方の意図は「max(hours) が一番大きい行の bug_id と summary を一緒に出したい」ということです。しかし SQL の GROUP BY には、本来「どの行の bug_id を選ぶか」という指示が一切含まれていません。bug_id は 1 つのグループの中に複数の値があり得るのに、1 つしか出力できない列として扱われています。この「1 グループに対してどの行の値を選ぶかが宣言されていない」状態が、この回で扱うアンチパターンの出発点です。

図: 1 つのグループに 2 行あるとき、非集約列として何を出すべきかは宣言されていない。

2. アンチパターン ― MIN と MAX の組み合わせが実在しない行を作る

前節の素朴な書き方は、PostgreSQL では次のようにエラーになって止まります。

ERROR:  column "bugs.bug_id" must appear in the GROUP BY clause or be used in an aggregate function

この時点では「PostgreSQL はちゃんと守ってくれる」と思えますが、抜け道が 1 つ残っています。bug_id を生のまま出すのではなく、集約関数で包んでしまえばエラーは出ません。

SELECT reported_by, min(bug_id) AS any_bug_id, max(hours) AS max_hours
FROM bugs
GROUP BY reported_by;

この問い合わせは文法的には正しく、エラーなく実行できます。しかし min(bug_id) と max(hours) は、それぞれ別の行から独立に選ばれた値です。同じ行から来たとは限りません。実際に第 1 回答者 (reported_by = 1) のデータで確認すると、報告した 2 件は bug_id = 1 (hours は NULL) と bug_id = 4 (hours = 8.00) です。ところが上の問い合わせの結果は「bug_id = 1 かつ max_hours = 8.00」という、どの行にも存在しない組み合わせを返します。

図: min(bug_id) は左の行、max(hours) は右の行から選ばれるため、結果は実在しないハイブリッドな行になる。

このような「別の行の断片をつなぎ合わせて 1 つの (実在しない) 行を作ってしまう」現象を、本文ではフランケンシュタイン行と呼びます。GROUP BY に書いていない列をそのまま出すのはエラーで止まりますが、集約関数で包んでしまえば文法上は正しくなるため、気づかれにくいのがこのアンチパターンの厄介な点です。件数や合計のような「グループ全体の性質」を集約するのは正しい使い方ですが、「代表する 1 行の詳細を知りたい」という目的に MIN や MAX を流用すると、このように壊れます。

3. 見つけ方 ― コードとカタログの両方から探す

フランケンシュタイン行は文法エラーにならないため、既存のコードから見つけるには 2 つの方法を組み合わせます。

1 つ目はコードの中のパターン探しです。同じ GROUP BY 句の中に min( と max( が異なる列に対して同時に現れていたら、それぞれが別の行から選ばれている可能性が高い疑わしい箇所です。pg_stat_statements (shared_preload_libraries に追加して有効化する拡張) を使えば、本番で実行された問い合わせの正規化されたテキストを集めて、同じ正規表現で検索できます。この回の実行環境では pg_stat_statements が有効化されていないため、実際の出力はここには載せませんが、有効な環境では SELECT query FROM pg_stat_statements WHERE query ~* 'group by' AND query ~* 'min\(' AND query ~* 'max\(' のような問い合わせで疑わしい SQL を一覧にできます。

2 つ目はカタログから「GROUP BY に主キーが入っているか」を確認する方法です。GROUP BY の列がテーブルの主キーであれば、そのテーブルの全列はその主キーに関数従属するため、PostgreSQL は非集約列をそのまま出すことを許可します (次節で詳しく説明します)。逆に、GROUP BY の列が主キーでないのに非集約列や集約関数の組み合わせが登場していたら、設計を見直す対象です。次の問い合わせで、このサンプル DB の各テーブルの主キー列を確認できます。

SELECT tc.table_name, kcu.column_name
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
  ON tc.constraint_name = kcu.constraint_name AND tc.table_schema = kcu.table_schema
WHERE tc.constraint_type = 'PRIMARY KEY' AND tc.table_schema = 'public'
ORDER BY tc.table_name;

   table_name   | column_name
-----------------+-------------
 accounts        | account_id
 bug_status      | status
 bugs            | bug_id
 bugs_products   | product_id
 bugs_products   | bug_id
 comments        | comment_id
 products        | product_id
 screenshots     | bug_id
 screenshots     | image_id
 tags            | bug_id
 tags            | tag

この結果から、bugs テーブルの主キーは bug_id だけであり、reported_by は主キーに含まれていないことが分かります。したがって GROUP BY reported_by に対して bug_id や summary をそのまま出すことは関数従属の根拠が無く、フランケンシュタイン行の危険があるという判断ができます。

4. 使ってよい場合

GROUP BY に非集約列を混ぜることが常に悪いわけではありません。次の 2 つの場合は安全です。

1 つ目は、GROUP BY の列がそのテーブルの主キーである場合です。主キーは 1 つの値に対してテーブルの行が最大 1 件しか存在しないことを保証するため、他のどの列も主キーに関数従属します。グループの中に複数行が入り込む余地が無いので、「どの行の値を選ぶか」というあいまいさ自体が発生しません。

2 つ目は、集約関数が本当に「グループ全体の性質」を表している場合です。count(*) (件数)、sum(hours) (合計時間)、avg(hours) (平均) のように、特定の 1 行を指すのではなく全体を要約する値であれば、何の問題もありません。この回で問題にしているのは、集約関数を使っていても「実質的には 1 行の詳細を取り出そうとしている」ケース (MIN や MAX を複数の列に対してかけて代表行を再現しようとする書き方) だけです。

5. 解決策 ― 代表行を 1 行だけ安全に取り出す 4 つの方法

「グループごとに、ある列で並べたときの先頭 1 行を取りたい」という要求には、PostgreSQL では 4 つの書き方があります。例として「報告者ごとに、最も時間 (hours) がかかったバグを 1 件取り出す」を、全部同じ結果になることを確認しながら見ていきます。まず準備として、このサンプル DB に次の行を追加しておきます (報告者 2 と 3 に複数件のバグを持たせ、代表行を選ぶ意味のあるデータにします)。

INSERT INTO bugs (date_reported, summary, reported_by, assigned_to, status, priority, hours) VALUES
  ('2026-01-20', 'export fails for csv',   2, 1,    'IN PROGRESS', 'MEDIUM', 5.00),
  ('2026-02-20', 'timeout on bulk import', 2, 3,    'NEW',         'HIGH',   12.00),
  ('2026-03-10', 'dark mode icons missing',3, NULL, 'NEW',         'LOW',    1.00);

5.1 DISTINCT ON ― PostgreSQL 独自の拡張

DISTINCT ON (式) は、指定した式の値が同じ行の中から、ORDER BY で並べた先頭の 1 行だけを残す PostgreSQL 独自の構文です。ORDER BY の先頭は DISTINCT ON の式と同じでなければならず、その後に「どの行を代表に選ぶか」を決める並び順を続けます。

SELECT DISTINCT ON (reported_by) reported_by, bug_id, summary, hours
FROM bugs
ORDER BY reported_by, hours DESC NULLS LAST, bug_id;

 reported_by | bug_id |           summary           | hours
-------------+--------+-----------------------------+-------
           1 |      4 | slow search on large data   |  8.00
           2 |      7 | timeout on bulk import      | 12.00
           3 |      8 | dark mode icons missing     |  1.00
           4 |      5 | login fails with long email |

ここで NULLS LAST を明示していることに注意してください。PostgreSQL は ORDER BY ... DESC の既定で NULL を「最大の値」として先頭に置きます。報告者 1 の実機データで確認すると次のようになります。

SELECT bug_id, hours FROM bugs WHERE reported_by = 1 ORDER BY hours DESC;

 bug_id | hours
--------+-------
      1 |
      4 |  8.00

hours = NULL の bug_id = 1 が、hours = 8.00 の bug_id = 4 より先に来ています。もし DISTINCT ON の ORDER BY に NULLS LAST を付け忘れると、代表行として誤って bug_id = 1 (NULL の行) が選ばれてしまいます。

SELECT DISTINCT ON (reported_by) reported_by, bug_id, hours
FROM bugs WHERE reported_by = 1 ORDER BY reported_by, hours DESC;

 reported_by | bug_id | hours
-------------+--------+-------
           1 |      1 |

「時間が一番かかったバグ」を知りたいのに、時間が記録されていないバグが返ってくるという、意図とは逆の結果です。

5.2 window 関数 (ROW_NUMBER)

row_number() はパーティション (グループ) ごとに連番を振る window 関数です。PARTITION BY でグループを分け、ORDER BY で並べ、連番が 1 の行だけを残せば、DISTINCT ON と同じ代表行が選べます。

SELECT reported_by, bug_id, summary, hours FROM (
  SELECT bug_id, reported_by, summary, hours,
         row_number() OVER (PARTITION BY reported_by ORDER BY hours DESC NULLS LAST, bug_id) AS rn
  FROM bugs
) ranked WHERE rn = 1 ORDER BY reported_by;

結果は DISTINCT ON と完全に同じです。DISTINCT ON は PostgreSQL 独自の構文であるのに対し、window 関数は標準 SQL なので、他の環境に移植しやすいという違いがあります。また rank() や dense_rank() に変えれば「同じ値で並んだ場合に複数行を残す」といった挙動も選べます (タイのときの扱いは第 29 回で詳しく扱います)。

5 (続き). LATERAL と NOT EXISTS

5.3 LATERAL ― 「グループの一覧」から「各グループの代表行」を引く

LATERAL は、サブクエリの中で外側の行の列を参照できるようにする結合です。「報告者の一覧」を外側に置き、各報告者に対して「その人のバグを並べて先頭 1 件を取る」サブクエリを LATERAL で結合すると、相関サブクエリとして代表行を取り出せます。

SELECT a.account_id, b.bug_id, b.summary, b.hours
FROM accounts a
JOIN LATERAL (
  SELECT bug_id, summary, hours FROM bugs
  WHERE bugs.reported_by = a.account_id
  ORDER BY hours DESC NULLS LAST, bug_id
  LIMIT 1
) b ON true
ORDER BY a.account_id;

結果は DISTINCT ON や window 関数と同じです。LATERAL の特徴は、外側の行 1 件ごとにサブクエリが独立に実行される点です。これは「外側の行数が少なく、各グループの行数も少ない」場合に強く、インデックスが効けば 1 回の検索がごく短時間で終わります。逆に外側の行数が多いと、サブクエリの実行回数も増えるため、インデックスが無いと全件スキャンを繰り返すことになり、性能が大きく落ちます (次の節で実測します)。

図: LATERAL は外側の各行に対してサブクエリを 1 回実行する。インデックスが効けば速いが、無ければ回数分の全件スキャンになる。

5.4 NOT EXISTS ― 「自分より大きい値を持つ行が同じグループに無い」

NOT EXISTS を使うと、「このグループの中で、自分より hours が大きい行が他に存在しない」行だけを選ぶという発想で、window 関数を使わずに同じ結果を得られます。

SELECT b1.reported_by, b1.bug_id, b1.summary, b1.hours
FROM bugs b1
WHERE NOT EXISTS (
  SELECT 1 FROM bugs b2
  WHERE b2.reported_by = b1.reported_by
    AND (b2.hours > b1.hours OR (b1.hours IS NULL AND b2.hours IS NOT NULL))
    AND (b2.hours, b2.bug_id) IS DISTINCT FROM (b1.hours, b1.bug_id)
)
ORDER BY b1.reported_by;

この書き方が少し複雑なのは、NULL の扱いを明示する必要があるためです。「hours が NULL の行は、他に hours が記録されている行がいれば負ける」という条件を OR (b1.hours IS NULL AND b2.hours IS NOT NULL) で表しています。4 つの方法はいずれも結果が一致しますが、NOT EXISTS だけが「比較」という考え方で書けており、ウィンドウや DISTINCT の構文を知らなくても到達できる書き方です。

6. PostgreSQL エンジンで考慮しておくこと

6.1 関数従属のルールは「主キー全体」が GROUP BY に含まれていること

PostgreSQL が非集約列を許すのは、GROUP BY の列が対象テーブルの主キーを完全に含んでいる場合です。結合をまたいだときも同じ規則が働きます。

SELECT a.account_id, a.account_name
FROM accounts a JOIN bugs b ON b.reported_by = a.account_id
GROUP BY a.account_id
ORDER BY a.account_id;

 account_id | account_name
------------+--------------
          1 | alice
          2 | bob
          3 | carol
          4 | dave

この問い合わせは成功します。a.account_id は accounts の主キーなので、同じテーブルの account_name はそれに関数従属していると PostgreSQL が認識します。一方、次のように bugs 側の列 (reported_by、bugs の主キーではない) で GROUP BY すると、accounts.account_name は関数従属しているとは認識されず、エラーになります。

SELECT reported_by, account_name
FROM bugs JOIN accounts ON accounts.account_id = bugs.reported_by
GROUP BY reported_by;

ERROR:  column "accounts.account_name" must appear in the GROUP BY clause or be used in an aggregate function

reported_by と account_id は結合条件で 1 対 1 に対応しているように見えますが、PostgreSQL は外部キー制約の有無にかかわらず、この種の「結合によって生まれる関数従属」までは認識しません。認識するのは「GROUP BY の列が、値を出したい列と同じテーブルの主キーである」という直接の関係だけです。

6.2 4 つの方法の実行速度 (30 万行、約 2000 グループ)

どの方法が速いかは、インデックスの有無で大きく変わります。reported_by を 1 から 2000 まで一様乱数で振った 30 万行の表 (big_bugs) で、キャッシュが温まった状態の EXPLAIN (ANALYZE, BUFFERS) を実測しました。

方法インデックス無し(reported_by, hours DESC) あり
DISTINCT ON198.3 ms135.5 ms
window 関数 (ROW_NUMBER)160.4 ms102.9 ms
LATERAL14,756.3 ms33.3 ms
NOT EXISTS(未測定)222.3 ms

図: バーの長さは実行時間 (対数的な縮小表示、概形のみ)。LATERAL はインデックス無しでは最も遅いが、インデックスが効くと最速になる。

インデックスが無いとき、LATERAL は 2000 グループそれぞれに対して bugs の全件スキャンを繰り返すため、14.8 秒近くかかりました。これは DISTINCT ON の 198 ms や window 関数の 160 ms に比べて 2 桁以上遅い結果です。一方、(reported_by, hours DESC) の複合インデックスを張ると、LATERAL は各グループの検索がインデックスの先頭を 1 回たどるだけで済むようになり、33.3 ms まで短縮されました。これは同じインデックスを使った DISTINCT ON の 135.5 ms よりもさらに速い結果です。

DISTINCT ON と window 関数は、インデックスがあっても表全体を 1 回スキャートする必要がある点は変わらないため、インデックスの効果は「ソートを省略できる」程度にとどまり、速くはなるものの LATERAL ほどの違いにはなりませんでした。NOT EXISTS は自己結合をハッシュ反結合 (Hash Anti Join) に変換する計画になり、このデータ (1 グループあたり平均 150 行) では 222.3 ms で収まりましたが、1 グループの行数がもっと多いデータでは結合の比較回数が増えるため、他の 3 方法より不利になりやすい書き方です。

まとめると、グループ数が多くグループ内の行数が少ない (かつ適切な複合インデックスがある) なら LATERAL が最速、インデックスを張れない事情がある、または標準 SQL で書きたいなら window 関数、PostgreSQL 専用でよく短く書きたいなら DISTINCT ON が実務的な既定の選択です。

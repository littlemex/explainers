インデックスショットガン ― 闇雲にインデックスを作る

インデックスは付けるか付けないかの二択ではなく、どの列を・どの順で・どの形で持つかという設計である。50 万行の実データで EXPLAIN (ANALYZE, BUFFERS) を測り、効く書き方と効かない書き方の境目を確かめる

← SQL シリーズ目次へ

この回の前提: 第 12 回 ファントムファイル (PostgreSQL の内部構造を実機で確認する進め方)

「クエリが遅いからインデックスを足す」「とりあえず全部の列にインデックスを張る」という対応は、効果が無いどころか書き込みを遅くするだけのこともあります。結論を先に言うと、インデックスが効くかどうかは「列を関数で包んでいないか」「複合インデックスの列順がクエリと合っているか」「型が一致しているか」といった書き方のクセで決まり、効いているかどうかは測らないと分かりません。この回では、50 万行の疑似データを使って PostgreSQL 18 の EXPLAIN (ANALYZE, BUFFERS) を実際に測り、効く条件と効かない条件を 1 つずつ確認します。

1. 目的 ― 何をしたかったのか

バグ管理システムには、コメントや担当者変更などの操作履歴を記録する events テーブルがあるとします。行数が増えてくると、「あるメールアドレスに関わるイベントを探す」「あるバグ ID の履歴を時系列で見る」といったクエリが遅くなります。インデックスは、こうした検索をテーブル全体のスキャンより速くするための仕組みです。

この回では、bugs とは別に events (event_id, bug_id, event_type, created_at, email, payload) という 50 万行のテーブルを用意し、インデックスの効果を実際に測ります。

CREATE TABLE events (
  event_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  bug_id     bigint NOT NULL,
  event_type text NOT NULL,
  created_at timestamptz NOT NULL,
  email      text NOT NULL,
  payload    text
);
INSERT INTO events (bug_id, event_type, created_at, email, payload)
SELECT (random()*5000)::int + 1,
       (ARRAY['CREATED','COMMENTED','ASSIGNED','STATUS_CHANGED','CLOSED'])[(random()*4)::int + 1],
       timestamptz '2025-01-01' + (random()*300)::int * interval '1 day' + (random()*86400)::int * interval '1 second',
       'user' || ((random()*20000)::int) || '@example.com',
       repeat('x', 20)
FROM generate_series(1, 500000);

2. アンチパターン ― どう書いてしまい、何が壊れるか

2.1 インデックスが無い ― 素のコストを測る

まず、インデックスが無い状態で特定のメールアドレスを検索します。

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE email = 'user12345@example.com';
 Gather  (actual time=0.598..16.015 rows=28.00 loops=1)
   Workers Planned: 2
   Workers Launched: 2
   Buffers: shared hit=7029
   ->  Parallel Seq Scan on events (actual time=0.341..10.374 rows=9.33 loops=3)
         Filter: (email = 'user12345@example.com'::text)
         Rows Removed by Filter: 166657
 Execution Time: 16.039 ms

テーブル全体 (7029 バッファ、約 55 MB 分のページ) を読んで 166,657 行を捨てながら 28 行を見つけており、実行時間は 16.039 ミリ秒でした。ここに B-tree インデックスを張ります。

CREATE INDEX events_email_idx ON events (email);
 Bitmap Heap Scan on events (actual time=0.093..0.214 rows=28.00 loops=1)
   Recheck Cond: (email = 'user12345@example.com'::text)
   Heap Blocks: exact=28
   Buffers: shared hit=28 read=3
   ->  Bitmap Index Scan on events_email_idx (actual time=0.071..0.071 rows=28.00 loops=1)
         Index Cond: (email = 'user12345@example.com'::text)
 Execution Time: 0.230 ms

読むバッファは 7029 件から 31 件に、実行時間は 16.039 ミリ秒から 0.230 ミリ秒に減りました (約 70 倍)。これが「インデックスが無い」というアンチパターンの素の代償です。

図: 同じ検索でも、読むバッファ数が約 227 倍 (7029 対 31) 違う。バッファが減れば I/O も時間も減る。

2.2 効かない書き方 ― 列を関数で包む

インデックスがあっても、検索条件の列を関数で包むと使われません。

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE lower(email) = 'user12345@example.com';
 Gather (actual time=1.479..69.439 rows=28.00 loops=1)
   Buffers: shared hit=7029
   ->  Parallel Seq Scan on events (actual time=9.745..64.609 rows=9.33 loops=3)
         Filter: (lower(email) = 'user12345@example.com'::text)
 Execution Time: 69.455 ms

events_email_idx は「email という値」の並びを知っているだけで、「lower(email) の値」の並びは知りません。したがって lower() で包んだ瞬間、インデックスは無関係になり、Seq Scan に戻ります (読むバッファ数はどちらも 7029 件とほぼ同じですが、実行時間は 16.039 ミリ秒ではなく 69.455 ミリ秒でした。この差はキャッシュの温まり方など計測ごとに揺れる要因によるもので、lower() 自体の計算コストの大きさを示すものではありません)。解決策は「関数の結果そのもの」にインデックスを張る式インデックスです。

CREATE INDEX events_lower_email_idx ON events (lower(email));
 Bitmap Heap Scan on events (actual time=0.076..0.173 rows=28.00 loops=1)
   Recheck Cond: (lower(email) = 'user12345@example.com'::text)
   Buffers: shared hit=28 read=3
   ->  Bitmap Index Scan on events_lower_email_idx (actual time=0.061..0.061 rows=28.00 loops=1)
 Execution Time: 0.185 ms

式インデックスを張ると、同じクエリが 0.185 ミリ秒まで戻りました。

2.3 効かない書き方 ― 先頭に % を置く LIKE

email にはまだ元の events_email_idx (素の B-tree) があります。前方一致と後方一致の 2 種類の LIKE を比べます。

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE email LIKE '%2345@example.com'; -- 先頭%
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE email LIKE 'user12345%';          -- 前方一致
-- 先頭% :  Parallel Seq Scan, Execution Time: 18.915 ms, buffers=7029
-- 前方一致: Parallel Seq Scan, Execution Time: 13.793 ms, buffers=7029

どちらも Seq Scan でした。これは B-tree の既定の演算子クラスが、PostgreSQL のロケール依存の照合順序 (この DB では en_US.utf8) で並んでいるためです。前方一致を効かせるには、バイト単位で並べる text_pattern_ops 演算子クラスで作り直します。

CREATE INDEX events_email_pattern_idx ON events (email text_pattern_ops);
-- 前方一致 'user12345%':
 Index Scan using events_email_pattern_idx (actual time=0.026..0.061 rows=28.00 loops=1)
   Index Cond: ((email ~>=~ 'user12345'::text) AND (email ~<~ 'user12346'::text))
 Execution Time: 0.071 ms

-- 先頭% '%2345@example.com' (同じインデックスがあっても):
 Parallel Seq Scan on events (actual time=0.909..13.720 rows=18.33 loops=3)
 Execution Time: 16.916 ms

前方一致は 13.793 ミリ秒から 0.071 ミリ秒まで改善しましたが、先頭%は text_pattern_ops インデックスがあっても 16.916 ミリ秒とほぼ変わりません。B-tree は「ある範囲から始まる値」を絞り込む構造なので、文字列の先頭が分かっているときしか範囲を絞れません。先頭が % (任意の文字列) だと、絞り込める範囲が無いのです。

図: B-tree インデックスは先頭からの範囲検索しか絞り込めない。先頭 % の LIKE はどんなインデックスでも使えない。

2.4 効かない書き方 ― 複合インデックスの列順

(bug_id, created_at) という複合インデックスを作り、2 つの検索パターンを比べます。

CREATE INDEX events_bugid_created_idx ON events (bug_id, created_at);
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE bug_id = 42;                             -- 先頭列
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE created_at = '2025-03-01 12:00:00+00';   -- 2番目の列だけ
-- bug_id = 42 (先頭列):
 Bitmap Heap Scan on events (actual time=0.080..0.227 rows=107.00 loops=1)
   ->  Bitmap Index Scan on events_bugid_created_idx
         Index Cond: (bug_id = 42)
 Execution Time: 0.245 ms

-- created_at = '...' (2番目の列だけ):
 Parallel Seq Scan on events (actual time=9.467..9.468 rows=0.00 loops=3)
   Filter: (created_at = '2025-03-01 12:00:00+00'::timestamptz)
 Execution Time: 14.946 ms

複合インデックス (bug_id, created_at) は、電話帳が「姓、名」の順に並んでいるのと同じです。先頭の bug_id で絞り込む検索は 0.245 ミリ秒で終わりますが、2 番目の created_at だけで検索すると、先頭列の値が分からないため、インデックス全体を飛び飛びに見るしかなく実質使えません。実際に Seq Scan になり、14.946 ミリ秒かかりました。クエリでよく使う絞り込みの順に列を並べる必要があります。

図: 複合インデックスは先頭列が同じ値の行をまとめて並べる。先頭列が分からないと、目的の行が全体に散らばってしまう。

2.5 効かない書き方 ― 型不一致 (インデックス側の列をキャストする)

整数列 bug_id に複合インデックスがある状態で、列側をキャストした場合と、リテラル側をキャストした場合を比べます。

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE bug_id::text = '42';   -- 列をキャスト
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE bug_id = '42'::int;    -- リテラルをキャスト
-- 列をキャスト (bug_id::text = '42'):
 Parallel Seq Scan on events (actual time=0.292..10.742 rows=35.67 loops=3)
   Filter: ((bug_id)::text = '42'::text)
 Execution Time: 16.435 ms

-- リテラルをキャスト (bug_id = '42'::int):
 Bitmap Heap Scan on events (actual time=0.031..0.173 rows=107.00 loops=1)
   ->  Bitmap Index Scan on events_bugid_created_idx
         Index Cond: (bug_id = 42)
 Execution Time: 0.187 ms

bug_id::text = '42' は 2.2 節の lower(email) と全く同じ構造の問題です。インデックスは「bug_id という整数の値」の並びを知っているのに、クエリは「bug_id をテキストに変換した値」を探しているため、インデックスと噛み合いません。実行時間は 16.435 ミリ秒でした。リテラル側を ::int でキャストすれば、比較は整数同士になり、インデックスがそのまま使えて 0.187 ミリ秒まで戻ります。ORM (オブジェクト関係マッピング) やアプリケーションのコードが、パラメータの型を誤って文字列のまま渡し、意図せず列側がキャストされる事故は実務でもよく起こります。

3. 見つけ方 ― どんな兆候で気づくか

作りすぎた (あるいは効いていない) インデックスは、pg_stat_user_indexes の idx_scan (そのインデックスが実行計画で選ばれた回数) で見つけられます。

SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE relname = 'events'
ORDER BY idx_scan, pg_relation_size(indexrelid) DESC;
       indexrelname       | idx_scan |  size
--------------------------+----------+---------
 events_pkey              |        0 | 11 MB
 events_type_full_idx     |        0 | 3448 kB
 events_email_idx         |        1 | 4144 kB
 events_bugid_created_idx |        2 | 15 MB

events_type_full_idx は 3.4 MB ありながら idx_scan = 0 でした。事前にこの列へのクエリを実行していないので当然ですが、本番環境でも同じ考え方が使えます。しばらく運用した後にこのクエリを流し、idx_scan が 0 のまま大きいインデックスが見つかれば、それは書き込みのコストだけを払って誰も使っていないインデックスである可能性が高いです。並べ替えの列には pg_relation_size() が返す実際のバイト数をそのまま使う必要があります。pg_size_pretty() は人間が読みやすい文字列 ("11 MB" や "3448 kB") を返すだけなので、その文字列を ORDER BY に使うと "4144 kB" が "11 MB" より先頭の文字 ("4" と "1") の比較で上位に来てしまうなど、文字列としての並びになり、実際のサイズの大小とは一致しません。

注意: この統計はバックエンドごとに一定時間 (約 1 秒) ごとにまとめて反映される非同期の仕組みなので、クエリを実行した直後に見ると反映されていないことがあります (このデモでは pg_sleep(1.2) を挟んで確認しています)。本番のように継続的にアクセスがある環境では気にする必要はありません。

4. 使ってよい場合 ― どう作れば効くか

4.1 部分インデックス ― 対象を絞ると激しく小さくなる

events に is_archived (95% が true) という列を追加し、「アーカイブされていない行だけ」の部分インデックスと、全行対象の通常のインデックスを比べます。

CREATE INDEX events_type_active_idx ON events (event_type) WHERE NOT is_archived;
SELECT pg_relation_size('events_type_full_idx') AS full_idx_bytes,
       pg_relation_size('events_type_active_idx') AS partial_idx_bytes;
 full_idx_bytes | partial_idx_bytes
----------------+-------------------
        6815744 |            196608

全行対象 (約 6.8 MB) に対して、部分インデックス (約 192 KB) は約 35 分の 1 のサイズでした。クエリがアーカイブ済みの行を見ないなら、インデックスにも持たせる必要がありません。

EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE event_type = 'CREATED' AND NOT is_archived;
 Bitmap Heap Scan on events (actual time=0.497..9.059 rows=3116.00 loops=1)
   Recheck Cond: ((event_type = 'CREATED'::text) AND (NOT is_archived))
   ->  Bitmap Index Scan on events_type_active_idx
         Index Cond: (event_type = 'CREATED'::text)
 Execution Time: 9.192 ms

全行対象のインデックスも存在する中で、プランナーは自動的に小さい部分インデックスを選びました。

4.2 INCLUDE ― Index Only Scan でテーブル本体を読まない

(bug_id, created_at) だけのインデックスで email も取得すると、テーブル本体 (ヒープ) まで読みに行く必要があります。

EXPLAIN (ANALYZE, BUFFERS) SELECT bug_id, created_at, email FROM events WHERE bug_id = 42 ORDER BY created_at;
 Gather Merge (actual time=24.145..27.086 rows=107.00 loops=1)
   ->  Sort
         Sort Key: created_at
         ->  Parallel Seq Scan on events
               Filter: (bug_id = 42)
 Buffers: shared hit=9560 read=4571
 Execution Time: 27.128 ms

この時点では複合インデックスを一度落としていたため Seq Scan + Sort になっていますが、ここに email まで含めた INCLUDE インデックスを作ると状況が変わります。

CREATE INDEX events_bugid_created_incl_idx ON events (bug_id, created_at) INCLUDE (email);
 Index Only Scan using events_bugid_created_incl_idx (actual time=0.022..0.031 rows=107.00 loops=1)
   Index Cond: (bug_id = 42)
   Heap Fetches: 0
   Buffers: shared hit=1 read=4
 Execution Time: 0.053 ms

Heap Fetches: 0 は、テーブル本体を一度も読まずにインデックスだけで答えを返せたことを示します (Index Only Scan)。バッファも 14,131 件から 5 件に減り、実行時間は 27.128 ミリ秒から 0.053 ミリ秒になりました。ORDER BY created_at の並べ替えも、インデックス自体がその順に並んでいるため不要になっています。

図: INCLUDE で必要な列をインデックス側に持たせると、テーブル本体 (ヒープ) への訪問が不要になる。

4.3 BRIN ― 小さいが「物理的な並び」が前提

BRIN (Block Range Index) はテーブルをブロックの範囲ごとに要約する、非常に小さいインデックスです。created_at に B-tree と BRIN を両方作って比べます。

CREATE INDEX events_created_btree_idx ON events (created_at);
CREATE INDEX events_created_brin_idx ON events USING brin (created_at);
SELECT pg_size_pretty(pg_relation_size('events_created_btree_idx')) AS btree_size,
       pg_size_pretty(pg_relation_size('events_created_brin_idx')) AS brin_size;
 btree_size | brin_size
------------+-----------
 11 MB      | 24 kB

BRIN は B-tree の約 469 分の 1 のサイズです。ただし BRIN が効くのは、index を張る列の値がテーブル上の物理的な並び順と相関しているときだけです。pg_stats の correlation (-1〜1、0 に近いほど無関係) を見ると、今回のデータはランダムに生成したため、ほぼ無関係でした。

SELECT attname, correlation FROM pg_stats WHERE tablename = 'events' AND attname = 'created_at';
  attname   |  correlation
------------+---------------
 created_at | -0.0055905697

B-tree がある状態での範囲検索は 1.428 ミリ秒でした。

 Index Scan using events_created_btree_idx (actual time=0.026..1.349 rows=1663.00 loops=1)
 Execution Time: 1.428 ms

B-tree を外し、BRIN しか選べない状態で同じ範囲検索を試すと、相関が無いせいで「ブロックの要約には該当する可能性があるが実際には対象外の行」を大量に読み直す (lossy) 結果になりました。

 Parallel Bitmap Heap Scan on events
   Rows Removed by Index Recheck: 166059
   Heap Blocks: lossy=5084
   ->  Bitmap Index Scan on events_created_brin_idx
         Index Cond: (created_at BETWEEN ...)
 Execution Time: 21.282 ms

実際に一致する行は 1663 行なのに、BRIN は各ブロックの要約 (最小値・最大値) から「対象を含む可能性がある」ブロックを広く候補に挙げてしまい、そのうち 166,059 行がヒープでの再確認で捨てられ、5084 ブロックが要約だけでは判定できず全体を読み直す対象 (lossy) になりました。実行時間も 1.428 ミリ秒から 21.282 ミリ秒まで悪化しました。BRIN はサイズが小さい代わりに、「挿入順と検索条件の列の値が揃っている (例: 自動採番の時刻列)」という前提が崩れると、この回のケースのように期待した速さが出ません。

図: BRIN はサイズの小ささと「並び順との相関」が前提というトレードオフを持つ。

4.4 Hash ― 等価検索しか使えない

B-tree を外し Hash インデックスだけにして、等価検索と範囲検索を比べます。

CREATE INDEX events_type_hash_idx ON events USING hash (event_type);
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM events WHERE event_type = 'CLOSED';
 Index Scan using events_type_hash_idx (actual time=0.022..24.971 rows=62739.00 loops=1)
   Index Cond: (event_type = 'CLOSED'::text)
 Execution Time: 26.944 ms

等価検索自体は使えましたが、event_type = 'CLOSED' は全行の約 12.5 % (62,739 行) に一致する低い選択度のクエリで、プランナーが自然に選ぶなら Seq Scan になるところを無理に Hash インデックスへ誘導したため、むしろ遅めの結果になっています。Hash が向くのは、もっと選択度が高い (一致件数が少ない) 等価検索です。

EXPLAIN SELECT * FROM events WHERE event_type > 'A' AND event_type < 'B';
 Seq Scan on events
   Filter: ((event_type > 'A'::text) AND (event_type < 'B'::text))

範囲検索では Hash インデックスはそもそも候補にならず、B-tree が無い今はそのまま Seq Scan に落ちました。Hash は等価比較の演算子しか持たないため、大小比較が必要な範囲検索や並べ替えには使えません。

4.5 作りすぎると書き込みが遅くなる

同じ形のテーブルを 2 つ用意し、片方には主キーのみ、もう片方には主キー + 5 本の単列インデックスを張った状態で、同じ 20 万行を INSERT して時間を比べました。

INSERT INTO insert_demo_few (a,b,c,d,e)
  SELECT i, i%100, 'text'||i, now(), 'x'||i FROM generate_series(1,200000) i;
-- Time: 310.390 ms (インデックス1本: 主キーのみ)

INSERT INTO insert_demo_many (a,b,c,d,e)
  SELECT i, i%100, 'text'||i, now(), 'x'||i FROM generate_series(1,200000) i;
-- Time: 1581.195 ms (主キー + 5本の単列インデックス)

同じ 20 万行の INSERT が、310.390 ミリ秒から 1581.195 ミリ秒まで、約 5.1 倍遅くなりました。INSERT や UPDATE は、対象の行だけでなく、その行が載っているすべてのインデックスも書き換える必要があるため、インデックスの本数に比例して書き込みのコストが増えます。「検索が速くなるなら増やしておこう」という判断は、書き込み側のコストを無視している点で、インデックスを 1 本も作らないのと同じくらい危険な判断です (この測定は 1 回限りのもので、サーバーの状態によって多少変わります)。

5. 解決策 ― MENTOR の手順で測って作る

「作らない」も「作りすぎる」も「闇雲」という点では同じ失敗です。手探りでインデックスを増やしたり減らしたりする代わりに、次のような手順を踏むと再現性のある判断ができます。これは PostgreSQL の公式な用語ではなく、この回で整理した進め方の覚え方です。

手順やることこの回での対応
Measure (測る)どのクエリが遅いかを特定するアプリのログや pg_stat_statements (第 28 回)
Explain (計画を見る)実際の実行計画とバッファ数を見るEXPLAIN (ANALYZE, BUFFERS) (2 節の各デモ)

CREATE INDEX events_bugid_created_covering_idx ON events (bug_id, created_at) INCLUDE (event_type);
CREATE INDEX events_type_active_covering_idx ON events (event_type) WHERE NOT is_archived;

6. PostgreSQL エンジンで考慮しておくこと

インデックスを作り直す (REINDEX) ときのロックの強さも実機で確認します。通常の REINDEX はテーブルへの書き込みをブロックします。

BEGIN;
REINDEX INDEX events_email_idx;
SELECT relation::regclass, mode FROM pg_locks WHERE relation = 'events'::regclass;
ROLLBACK;
 relation |   mode
----------+-----------
 events   | ShareLock

ShareLock は SELECT (読み取り) は妨げませんが、INSERT/UPDATE/DELETE (書き込み) は完了まで待たされます。本番で使われ続けているテーブルには、これは無視できない影響です。これを避けるのが REINDEX CONCURRENTLY です。

REINDEX INDEX CONCURRENTLY events_email_idx;

実際に実行すると、明示的なトランザクションブロックの外でだけ成功しました (BEGIN の中で試すとエラーになります)。PostgreSQL の公式ドキュメントによると、通常の REINDEX はテーブル全体を 1 回スキャンして一括で作り直しますが、REINDEX CONCURRENTLY はテーブルを 2 回スキャンし、処理中は対象のインデックスとテーブルに SHARE UPDATE EXCLUSIVE という弱いロックを取るだけで済みます。このロックは読み取りも書き込みもブロックしません。その代わり処理時間は長くなり、スキャンの最中に他のトランザクションの影響で一部の行が無効 (INVALID) な状態で終わることもあるため、処理後に状態を確認する運用が必要です。

まとめると、インデックスは「作る/作らない」の二択ではなく、どの列を・どの順で・どの構造で持つかという設計です。効いているかどうかは勘ではなく EXPLAIN (ANALYZE, BUFFERS) と pg_stat_user_indexes で測り、作り直すときのロックの強さまで含めて運用を考える必要があります。

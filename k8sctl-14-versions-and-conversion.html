バージョン管理と変換

複数のバージョンを見せても、本当に保存されているのは 1 つだけ。

← カスタムコントローラー自作 シリーズ目次へ

第 05 回で CRD の骨格を見たとき、versions という配列に複数のバージョンを並べられることに触れた。この回はその中身を深掘りする。CRD は v1alpha1・v1beta1・v1 のように複数のバージョンを同時にクライアントへ見せられるが、実際に etcd(Kubernetes が状態を保存する場所)に保存されるバージョンは常に 1 つだけで、ここを正しく扱わないとデータが黙って消える。

複数バージョンの CRD には「見せる(served)」と「保存する(storage)」という 2 つの役割があり、storage は必ず 1 つだけ。バージョン間でフィールド名が違うのに変換方式を「何もしない(None)」にしたままにすると、片方のバージョンで書き込んだ値が、もう片方のバージョンの名前に変換されずに消えてしまう。これは EKS 1.35 のテスト用クラスタで実測した。

1. served と storage ― 「見せる」と「保存する」は別の役目

CRD の spec.versions には、バージョンごとに served と storage という 2 つの真偽値がある。公式ドキュメントによれば、served: true/false は「クライアントがこのバージョンの URL でアクセスできるか」を決め、storage: true は「実際に etcd にこのバージョンの形で保存するか」を決める。そして「1 つだけ storage バージョンを指定しなければならない」と明記されている。複数のバージョンを served にして古いクライアントと新しいクライアントの両方に対応しつつ、実体は 1 つの形でしか持たない、というのが CRD の複数バージョンの基本設計。

spec:
  versions:
    - name: v1
      served: true
      storage: true
    - name: v2
      served: true
      storage: false
  conversion:
    strategy: None

図: v1alpha1・v1beta1・v1 のすべてが served(見せられる)でも、storage(実際に保存される形)はそのうち 1 つだけ。

2. status.storedVersions ― 「今まで保存した形」の記録

storage バージョンは後から切り替えられる(例: v1beta1 → v1)。しかし切り替えた瞬間に、etcd の中にある古いオブジェクトが自動的に新しい形に書き換わるわけではない。CRD の status.storedVersions には、過去に実際に保存されたことのあるバージョンの一覧が記録される。この一覧は自分では消えない。公式ドキュメントは、旧バージョンを安全に消すには、Storage Version Migration(既存オブジェクトを一括で新しい storage バージョンの形に書き直す仕組み)を実行するか、あるいは手作業で全オブジェクトを読み直して新バージョンで書き直したうえで、CRD の status サブリソースを自分で patch して storedVersions から旧バージョンを外す、という 2 つの進め方を示している。どちらの方法でも、「旧バージョンの形で保存されたオブジェクトが本当にもう無い」ことを確認してから storedVersions を外すのは利用者の作業で、Kubernetes が自動でやってはくれない。

図: storage バージョンを切り替えても、古い形で保存されたオブジェクトがまだ残っていれば storedVersions に古いバージョンが残り続ける。

3. conversion strategy: None と Webhook

異なるバージョンの間でオブジェクトを変換する方式は 2 つ。None(既定)は公式ドキュメントの言葉では「すべてのバージョンが同じスキーマだと仮定して、apiVersion フィールドだけを書き換える」方式。フィールド名や構造が全バージョンで同じときにしか安全に使えない。Webhook は、変換専用の webhook(第 12 回で見た webhook の変換版)を呼び出し、バージョン間でフィールド名や構造が違う場合でも正しく変換できる。

図: None は apiVersion の文字列だけを書き換える。Webhook は変換ロジックを自分で用意して、構造の違いまで吸収する。

4. None のまま項目名を変えると、データが黙って消える(実測)

EKS 1.35 のテスト用クラスタで、storage バージョンの v1(replicas フィールドを持つ)に加えて、served の v2 を追加した。v2 のスキーマでは replicas を count という名前に変え、conversion strategy は None のままにした。この状態で v2 として Widget を読むと、apiVersion だけが v2 に書き換わり、replicas は v2 のスキーマに存在しないため刈り込まれて消えて見え、count という名前のフィールドも存在しない(誰も値を移し替えていないから)。

kubectl get widgets.v2.lab.crd-series.example a -o yaml
kubectl patch widgets.v2.lab.crd-series.example a --type merge -p '{"spec":{"size":"large"}}'
kubectl get widgets.v1.lab.crd-series.example a -o yaml

1 行目(v2 として読むだけ)の結果には、すでに replicas も count も出てこない。size だけを変えるつもりの 2 行目の patch も、API サーバーは「まず現在のオブジェクトを v2 として読み、そこに patch を当てて、保存用の v1 の形に戻す」という手順で処理する。1 行目で見たとおり v2 として読んだ時点ですでに replicas は刈り込まれて無くなっているので、2 行目で patch を当てた後のオブジェクトにも replicas は無い。その replicas の無いオブジェクトを v1 の形に戻して保存するため、3 行目で v1 として読み直すと、replicas は元の 8 ではなく、スキーマの既定値(第 07 回、default: 1)に置き換わっている。None 戦略が count から replicas への対応を知らずに変換を誤ったのではなく、None はそもそも何も変換しない(apiVersion の文字列だけを書き換える)ので、v2 として読む時点での刈り込みがそのまま書き込みにまで伝わってしまう、というのが正確な原因。

「全バージョンでフィールド名を揃えておけば None で十分」という考え方自体は正しい。危険なのは、スキーマが同じだという前提のまま None にしておいて、後から片方のバージョンだけフィールド名や構造を変えてしまうこと。項目名や構造を変える版を追加する、まさにそのタイミングで Webhook 戦略に切り替えればよく、最初から全バージョンを Webhook にしておく必要はない。

図: v2 として読んだ時点で replicas はすでに刈り込まれており、そこへ size だけの patch を当てて v1 に戻すため、replicas は既定値 1 で上書きされ、元の 8 が消える。

5. hub-and-spoke ― 変換は真ん中の版を経由する

CRD に 3 つ以上のバージョンがあるとき、すべてのバージョンの組み合わせ(v1alpha1↔v1beta1, v1beta1↔v1, v1alpha1↔v1 など)ごとに変換ロジックを書くと、バージョンが増えるたびに組み合わせが爆発的に増える。API サーバー自体は「この版に変換して」と conversion webhook に頼むだけで、変換ロジックの中身には関与しない。そこで webhook を実装する側(kubebuilder の controller-runtime が提供する conversion.Hub と conversion.Convertible という作法)で、1 つの「真ん中のバージョン」(hub、たいていは storage バージョン)を決め、他のすべてのバージョン(spoke)は hub との変換だけを書く「hub-and-spoke」という考え方を使う。v1alpha1 → v1 も v1 → v1beta1 も、必ず hub である v1 を経由するので、変換ロジックの本数はバージョンの数に比例するだけで済む。

図: v1alpha1 → v1beta1 の変換も、直接ではなく hub(v1)を経由して行われる。

まとめと次の回

CRD の複数バージョンは、「見せる(served)」と「保存する(storage、常に 1 つ)」を分けて考える仕組み。変換方式が None のままフィールド名や構造を変えると、片方のバージョン経由の書き込みでデータが黙って消える(実測)。3 つ以上のバージョンを持つなら、hub-and-spoke で変換ロジックの数を抑える。バージョンの移行(v1alpha1 → v1beta1 → v1)は、新バージョンを served だけで追加 → storage を新バージョンに切り替え → 旧バージョンを served: false に → Storage Version Migration の実行か手作業の全件書き直しで旧バージョンの形のオブジェクトを無くし、CRD の status を自分で patch して storedVersions から旧バージョンを外す → versions から削除、という順で安全に進める。storedVersions は自分で外さない限り残り続ける。

次の第 15 回では、ここまで学んだ CRD とコントローラーを実際に作るときに kubebuilder が生成する一式(ディレクトリ構成・マーカー・manager・テストの 3 層)を見る。第 16〜18 回では、本物の題材 SharedFilesystem でこれらすべてを実際に使う。

図: served は複数、storage は 1 つ、変換は None か Webhook、3 版以上は hub-and-spoke。

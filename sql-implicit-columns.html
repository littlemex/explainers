インプリシットカラム ― SELECT * と列名なし INSERT

列名を書かずに済ませる書き方は、テーブルの列の並びが変わった瞬間に、エラーも出さずに違う列を読んだり NULL を書き込んだりする。実機では列を 1 つ追加しただけで、既存の INSERT 文が黙って動き続けた

この回の前提: 第 01 回 アンチパターンとは何か (サンプル DB の構造と \d の読み方)

列名を書くのが面倒で SELECT * や、列名を省略した INSERT INTO t VALUES (...) を使うことはよくあります。結論を先に言うと、この書き方はテーブルの列の数・順序・有無に暗黙に依存しているため、後から列を追加・削除・並べ替えたときに、エラーにならずに違う列を読んだり、新しい列に静かに NULL が入ったりします。この回では、実機でその壊れ方を確認したうえで、列名を明示する書き方と、ビューや RETURNING での注意点を見ていきます。

1. 目的 ― 何をしたかったのか

列名を 1 つずつ書くのは手間がかかります。SELECT * FROM bugs と書けば、今そのテーブルにある列をすべて取れますし、INSERT INTO products VALUES (DEFAULT, 'Widget Pro') と書けば、列名を書かずに全列分の値をまとめて渡せます。どちらも「今のテーブルの構造を知らなくても動く」という手軽さが魅力です。

問題は、この手軽さが「テーブルの構造は今後も変わらない」という前提の上に成り立っていることです。テーブルに列を追加する、削除する、型を変える、といった変更は、システムが育てば必ず発生します。

2. アンチパターン ― 列の変化にエラーも出さずに追従してしまう

2.1 列名なし INSERT ― 列を追加してもエラーにならない

products テーブルに、列名を書かない INSERT を実行します。

INSERT INTO products VALUES (DEFAULT, 'Widget Pro');  -- product_id, product_name の 2 列

ここでテーブルに新しい列 sku を追加します。

ALTER TABLE products ADD COLUMN sku text;

テーブルはもう 3 列になりました。同じ書き方の INSERT 文 (値は 2 個のまま) を、見直さずにそのまま実行してみます。

INSERT INTO products VALUES (DEFAULT, 'Widget Pro 2');

SELECT * FROM products;

 product_id |    product_name     | sku
------------+----------------------+-----
          1 | Open RoundFile       |
          2 | Visual TurboBuilder  |
          3 | ReConsider           |
          4 | Widget Pro           |
          5 | Widget Pro 2         |

エラーは一切出ず、INSERT 0 1 と成功しました。列が 3 つに増えたのに値は 2 個しか渡していないのに、PostgreSQL は足りない分の末尾の列を自動的に NULL (または列の既定値) で埋めて成功させます。sku 列は空のまま挿入され、本来 SKU を入れるつもりだったアプリケーションのバグが、何のエラーも無く本番データに紛れ込みます。

対照的に、値を多く渡した場合は必ずエラーになります。

CREATE TABLE t3 (a int, b int, c int DEFAULT 99);
INSERT INTO t3 VALUES (1,2,3,4);

ERROR:  INSERT has more expressions than target columns

つまり「列が足りない」側は黙って成功し、「値が多すぎる」側だけがエラーになります。この非対称性が、列名なし INSERT の最も危険な点です。

図: 値が足りないときは黙って成功し、多すぎるときだけエラーになるという非対称な挙動。

2.2 SELECT * ― 列を削除すると残りの列の位置がずれる

bugs テーブルの SELECT * の結果を確認した後、description 列を削除してみます。

SELECT * FROM bugs WHERE bug_id = 1;
 bug_id | date_reported | summary | description | resolution | ...
                                          ↑ 4 番目

ALTER TABLE bugs DROP COLUMN description;

SELECT * FROM bugs WHERE bug_id = 1;
 bug_id | date_reported | summary | resolution | reported_by | ...
                                          ↑ resolution が 4 番目に移動

削除より後ろにあったすべての列が、1 つずつ前に詰まりました。もしアプリケーションのコードが列名ではなく「4 番目の値」のような位置でアクセスしていた場合、description を読んでいたつもりの箇所が、エラーも出さずに resolution を読むようになります。型が同じ (どちらも text) であるほど、この入れ替わりはエラーにすらならず、間違った値がそのまま使われ続けます。

図: description を削除すると、後ろにあった resolution が 4 番目の位置に移動する。

3. 見つけ方

このアンチパターンは、列の変更が発生するまでは何の問題も起こさないため、コードを書いた時点では気づけません。見つけるには 2 つの方法があります。

1 つ目はコードの中を SELECT * と、列名が続かない INSERT INTO 識別子 VALUES (直後に (列名, ...) が無い形) で検索することです。マイグレーションのたびに、この 2 つのパターンが残っていないかを確認します。

2 つ目は、information_schema.columns でテーブルの列の並び順を確認し、コードが想定している列数・順序と食い違っていないかを突き合わせることです。

SELECT ordinal_position, column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'bugs'
ORDER BY ordinal_position;

 ordinal_position |  column_name  | data_type
-------------------+---------------+-----------
                 1 | bug_id        | bigint
                 2 | date_reported | date
                 3 | summary       | text
                 5 | resolution    | text
                 ...

ordinal_position が 3 の次に 5 になっていることに注目してください。4 番だった description を削除した後も、PostgreSQL は欠番をそのまま残し、番号を詰め直しません。この欠番は「過去に列が削除されたことがある」という履歴の手がかりになります。

4. 使ってよい場合

SELECT * や列名なし INSERT が常に悪いわけではありません。次のような場合は、わざわざ列名を書く必要はありません。

1 つ目は、psql での対話的な調査です。「このテーブルにどんなデータが入っているか、まず全体を見てみたい」という場面で SELECT * FROM bugs LIMIT 10; と打つのは自然で効率的な使い方です。

2 つ目は、テーブルの全列をそのまま複製するような操作です。CREATE TABLE bugs_copy AS SELECT * FROM bugs のように、元のテーブルの列構成をそのまま引き継ぎたい場合は、むしろ SELECT * の方が目的に合っています。この回が問題にしているのは、特定の列数・列順を前提にしたアプリケーションのコードや、本番で動き続ける INSERT 文に、列名を省略した書き方を使うことです。

5. 解決策 ― 列名を書く、そしてビューと RETURNING にも同じ注意を払う

5.1 INSERT と SELECT に列名を明示する

最も基本的な解決策は、INSERT には必ず列名を書き、SELECT には必要な列だけを書くことです。

INSERT INTO products (product_name, sku) VALUES ('Widget Pro 2', 'WP-002');
SELECT bug_id, summary, status FROM bugs WHERE bug_id = 1;

列名を書いた INSERT であれば、新しい列 sku を追加しても既存の INSERT 文はそのまま動き続け (指定していない列には既定値か NULL が入る、という挙動は変わりませんが、少なくとも「どの値をどの列に入れたか」は常に明確です)、列の削除や並べ替えがあれば、対象の列名が無くなった時点で初めてエラーになります。「エラーになる」ことは不便に見えますが、沈黙したまま間違った値を使い続けるよりずっと安全です。

5.2 ビューの SELECT * は作成時点で展開される

PostgreSQL のビューは、SELECT * で作っても実際には作成した瞬間の列名の一覧に展開されて保存されます。

CREATE VIEW account_summary AS SELECT * FROM accounts;
ALTER TABLE accounts ADD COLUMN department text;

SELECT * FROM account_summary LIMIT 1;
-- department は出てこない (ビュー作成時の列構成のまま)

SELECT * FROM accounts LIMIT 1;
-- department 列はここにはある

新しい列 department を追加しても、account_summary ビューには反映されません。ビューを作った時点の列構成が固定されているためです。ビューに新しい列を含めたい場合は、CREATE OR REPLACE VIEW で定義を再実行する必要があります (ただし末尾に列を追加する形でしか更新できず、既存の列の削除や型変更はできません)。

CREATE OR REPLACE VIEW account_summary AS SELECT * FROM accounts;
-- これで department が反映される

図: ビューの SELECT * は作成時の列構成を記憶し、後から追加された列は自動反映されない。

5.3 RETURNING にも列名を書く

INSERT ... RETURNING * も同じ理由で影響を受けます。

INSERT INTO widgets (name) VALUES ('alpha') RETURNING *;
 widget_id | name
-----------+-------
         1 | alpha

ALTER TABLE widgets ADD COLUMN price numeric(9,2);

INSERT INTO widgets (name) VALUES ('beta') RETURNING *;
 widget_id | name | price
-----------+------+-------
         2 | beta |

列を追加した後は RETURNING * の出力列数が増えます。呼び出し側のコードが「返り値は 2 列」という前提で位置アクセスをしていれば、ここでも壊れます。RETURNING widget_id, name のように必要な列名を明示すれば、列が増えても出力は変わりません。

6. PostgreSQL エンジンで考慮しておくこと

6.1 列の追加とビューの依存関係は非対称に守られている

PostgreSQL はビューが依存している列を、無条件には削除させません。

ALTER TABLE accounts_demo DROP COLUMN hourly_rate;

ERROR:  cannot drop column hourly_rate of table accounts_demo because other objects depend on it
DETAIL:  view accounts_demo_summary depends on column hourly_rate of table accounts_demo
HINT:  Use DROP ... CASCADE to drop the dependent objects too.

これは pg_depend という依存関係を追跡する仕組みによるもので、「列を削除したらビューが壊れる」という事故は防いでくれます。ところが、5.2 節で見たとおり「列を追加してもビューには反映されない」という方向のズレは、依存関係の破壊ではないため、何の警告もありません。PostgreSQL が守ってくれるのは「既存の定義を壊す変更」だけで、「新しい情報が反映されず古い定義のまま取り残される」という静かなズレまでは守ってくれないという非対称性を理解しておく必要があります。

図: 列の削除は依存関係で守られるが、列の追加が反映されないことまでは守られない。

6.2 ordinal_position は列削除後も詰め直されない

3 節で確認したとおり、information_schema.columns の ordinal_position は列を削除した後も欠番を残します。これは PostgreSQL が内部的に「削除された列」という情報をシステムカタログ (pg_attribute) にそのまま保持し、物理的な列の位置をずらさずに「削除済み」の印だけを付けているためです。この挙動を知っておくと、ordinal_position に欠番がある時点で「過去に列削除があった」という履歴を読み取れます。

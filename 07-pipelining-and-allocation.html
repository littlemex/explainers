NKI WORKSHOP ・ 07

ソフトウェアパイプラインと allocation ― エンジンを遊ばせない

裏で次のタイルを先読みし、アドレスの曖昧さを消してコンパイラに自動パイプライン化を許す

0この記事の狙い

第 1 回で「NeuronCore は複数の専用エンジンが並列に動く」と学びました。第 2 回・第 3 回では「データをどこに置くか」を扱いました。今回はその続きとして「時間軸」に踏み込みます ― 複数のエンジンを、同時に、しかも隙間なく働かせるにはどうするか。

一言でいうと
あるタイルを計算しているその裏で、次のタイルを DMA で先読み (prefetch) する。これがソフトウェアパイプラインです。そして、そのオーバーラップをコンパイラに安全だと証明させる鍵が allocation ― バッファのアドレスを人が明示的に割り当て、アドレスの曖昧さを排除することです。手動 allocation だけで、コンパイラが自動的にパイプライン化できるようになる、という逆説がこの章の核心です。
1. 動機 ― エンジンを遊ばせない 2. 【体験】アセンブリライン ― 逐次実行とパイプラインの対比 3. allocation の役割 ― アドレスの曖昧さを消す 4. 一時的な後退が次の飛躍を生む ― v8 から v10 へ 5. 【体験】スケジューリング 3 API の違い 6. バンク利用率 (MBU) が高い = 速い、ではない 7. まとめ

対象は AWS Trainium2。数値はワークショップ実測の概算です。第 1 回「ハードウェア階層」と第 2 回「Roofline とカーネル融合」を先に読むと理解が早いです。

1動機 ― エンジンを遊ばせない

第 1 回で NeuronCore は Tensor / Vector / Scalar / GP-SIMD という専用エンジンが並列に動くと学びました。今回はそれを「空間」だけでなく「時間」の軸で使い切る話です。

タイル単位でカーネルを書くと、各タイルの処理はload (HBM→SBUF に読む) → compute (計算する) → store (結果を書く)という 3 ステージに分かれます。素朴に書くと、あるタイルの load・compute・store をすべて終えてから、次のタイルの load を始めます。すると次のタイルの load を待つあいだ、計算エンジンは手が空いていても何もできず遊んでしまいます。ある処理が別のエンジンの完了を待つあいだ自分は手が空くこの現象をstructural hazard と呼びます。

着想はシンプル。あるタイルを計算している、その裏で、次のタイルのデータを DMA が先読み (prefetch) しておけばよい。計算が終わった瞬間、次のタイルのデータはもう SBUF に届いている ― だから待ち時間がゼロになります。

これを実現する基本手法が二重バッファリング (double buffering) です。1 つの論理的なバッファ (たとえば「QK matmul の結果」) に、物理的には2 つのスロットを用意する。片方のスロットを Vector Engine が読んでいる (softmax の計算に使っている) あいだに、もう片方のスロットに Tensor Engine が次のタイルの QK matmul の結果を書き込む。読む側と書く側が別の場所を使うので、上書きによる競合が起きません。

よくある誤解。二重バッファリングは「SBUF の容量が足りないから」ではありません。2 つの処理(前のタイルの読み出しと、次のタイルの書き込み)を並行させたいのに、同じ場所を使うと上書きが起きてしまうから、場所を 2 つに分けるのです。目的は容量対策ではなく並行性の確保です。

なお、バッファをさらに増やす三重バッファリング以降は収穫が急速に減っていきます(ワークショップの実測(概算)ではさらに数パーセントの改善どまり)。まず二重バッファで structural hazard を消すのが効果の大部分を占め、それ以上はケースバイケースの判断になります。

2【体験】アセンブリライン ― 逐次実行とパイプラインの対比

この記事の「絵で覚えて帰ってほしい 1 枚」です。工場のアセンブリラインを思い出してください。1 人の作業者が最初から最後まで 1 台を仕上げてから次の 1 台に取りかかるのと、複数の作業者が担当工程をずらして同時に流すのとでは、総所要時間がまるで違います。

load (DMA) compute (Tensor/Vector) store (DMA)

逐次実行では、どの時点を見てもガントチャートの行が同時に 1 本しか動きません。あるタイルの load・compute・store が終わるまで、次のタイルの load すら始まらない。ソフトウェアパイプラインに切り替えると、ステージをずらして重ねます。タイル 1 の compute をしている裏でタイル 2 の load が進み、タイル 1 の store をしている裏でタイル 2 の compute とタイル 3 の load が進む ― 定常状態では 3 つのステージが同時に稼働します。同じ本数のタイルを流しても、パイプラインの方が総時間が短く終わるのを見てください。

これは概念デモです。グラフの時間軸は相対値であり、実際の load/compute/store の比率やタイル数はカーネルの内容次第で変わります。ここで持ち帰ってほしいのは「ステージをずらして重ねると、総時間はステージ数の合計ではなく、ほぼ最長のステージ × タイル数に近づく」という定性的な効果です。

3allocation の役割 ― アドレスの曖昧さを消す

「先読みすればいい」と分かっても、それを安全に実行できるとコンパイラに保証させるのは別の問題です。ここで allocation (手動アロケーション) が登場します。

通常、SBUF や PSUM のどこにどのバッファを置くかはコンパイラが決めます。多くの場合これで問題ありません。しかしプロファイルを見て「あるエンジンが遊んでいるのに、次のタイルの処理を始められていない」という機会を見つけたときに、allocation ― バッファのサイズだけでなく、SBUF/PSUM 上の正確なアドレスまで人間が指定する手法を使います。

# PSUM のバンクを明示的に割り当てる例(擬似コード)
psum_bank = nl.ndarray((TILE_M, TILE_N), dtype=nl.float32, buffer=nl.psum,
    address=(0, b * PSUM_BANK_BYTES))  # b 番目のバンクに固定

なぜアドレスを明示すると先読みが可能になるのか。コンパイラは「2 つの処理が重なっても安全か」を、メモリ上の場所(アドレス)が被っていないかで判断します。アドレスがコンパイラの自動割り当てのままだと、2 つの処理が同じ場所を使うかもしれず、コンパイラは安全側に倒して重ねずに逐次実行させます。人間が「タイル A はアドレス X、タイル B はアドレス Y」と明示的に分ければ、コンパイラはオーバーラップしても互いを壊さないと証明できるようになり、自動でパイプライン化してくれるのです。

因果関係を取り違えないこと。allocation は単体では速くなりません。allocation がやっているのは「アドレスの曖昧さを排除する」ことだけです。速くなるのは、その結果としてコンパイラがオーバーラップの安全性を証明できるようになり、パイプライン化を許可するから。ワークショップの Self-Attention 最適化の実演では、手動 allocation を導入しただけで、コンパイラが自動的にタイル間の処理をパイプライン化しました。人間がスケジュールを書いたわけではなく、「安全だと証明できる条件を整えた」だけで、あとはコンパイラが仕事をしたのです。

PSUM は 8 バンクという有限の資源なので、allocation はここでも効きます。QK 用の matmul と PV 用の matmul に別々のバンクを明示的に割り当てると、Tensor Engine は 2 つの matmul を異なるバンクに向けて並行に書き込めます。バンクが被っていないとコンパイラに保証されるからです。逆に、バンクをどう再利用するかを誤ると ― たとえば蓄積をリセットすべきタイミングで accumulate の指定を誤ると ― 結果が大きく壊れることもあり、明示的な制御には相応の注意が要ります。

多重バッファの実装骨格 ― 二層のメモリ管理とリングバッファ

「アドレスを人間が明示する」と言っても、タイルが何百個も流れるループで 1 つずつ手で番地を振るのは現実的ではありません。実務では、SBUF 上の領域を管理するアロケータを通じて、次の 2 つの仕組みで多重バッファを組み立てます。

  1. stack と heap の二層構造。アロケータは SBUF の領域を 2 通りで貸し出します。stack は「スコープ(処理のまとまり)を抜けると自動で解放される」LIFO 方式で、一時的な作業バッファに使います。heap は「明示的に解放するまで居座る」方式で、ループをまたいで持ち回るバッファに使います。作業用は stack、持ち回りは heap、と役割を分けることで、限られた SBUF を破綻なく使い回せます。
  2. リングバッファ(モジュラーアドレッシング)。先読みをするには、同じ論理バッファに対して物理的な実体を複数(N 個)持ち、イテレーションごとに順番に使い回す必要があります(N=2 なら二重バッファ、N=3 なら三重バッファ)。アロケータはスコープを開くときに 多重度 N (interleave 度) を指定し、イテレーションを進めるたびに使う物理スロットを 1 つ進める ― N 個を使い切ったら先頭に戻る、というリング状の割り当てで実現します。「タイル i を計算しながらタイル i+1 を書き込む」が、書き込み先の物理スロットが別だからこそ衝突せず成立するわけです。
「効果」と「仕組み」をつなぐ。前半で見た「二重バッファリングで並行性を確保する」という効果は、この stack/heap の二層と 多重度 N のリング割り当てという仕組みで実装されます。allocation が「アドレスの曖昧さを消す」とは、具体的には「N 個の物理スロットのどれを今使うかを一意に決める」こと ― だからコンパイラはオーバーラップしても壊れないと証明でき、パイプライン化が許可されるのです。

4一時的な後退が次の飛躍を生む ― v8 から v10 へ

ワークショップの Self-Attention 最適化の実演では、v8・v9・v10 という 3 段階でこの章のテーマが積み上げられます。ここでの教訓は「一歩下がることが次の飛躍の土台になる」という構造です。

  1. v8: PSUM を早めに解放する。それまで PSUM に居座っていた中間結果 (max reduction など) を tensor_scalar 命令で Vector Engine 側にキャッシュし、PSUM のバンクを早く空ける。これ自体は単体で見ると性能が落ちます。しかし、PSUM を早く空けられるようになったことで、次のタイルの QK matmul をより早く始められる余地が生まれる ― これが後続の allocation / pipelining の必須の土台になります。
  2. v9: 手動 allocation を導入する。コードの変更は「バッファのアドレスを明示する」ことだけ。アルゴリズムやスケジュールは変えていません。それだけでコンパイラが自動的にタイル間をパイプライン化し、性能が上がりました。
  3. v10: 明示的ソフトウェアパイプラインを書く。QK matmul・rowsum・transpose・PV matmul といった複数ステージを、異なるタイル間で意図的にずらして重ねる設計です。ある時点で、Tensor Engine は 2 つ前のタイルの PV matmul と現在のタイルの QK matmul を同時に処理し、Scalar Engine は 1 つ前のタイルの sum/exp を処理し、DMA はバックグラウンドで transpose を進める ― 3 段以上のタイルが同時に「in flight」な状態になります。
PSUM解放(一時後退)→allocation(コンパイラが自動パイプライン化)→明示的パイプライン(多段オーバーラップ)という順で積み上げ、ワークショップの実測(概算)では最初の実装から数倍程度の高速化に至りました。ここで大事なのは絶対的な倍率ではなく、「一時的に遅くなる変更が、次の変更を可能にする土台になる」という設計の順序そのものです。最適化を一足飛びに終盤の形へ飛ばそうとすると、なぜそれが効くのか理解できないまま迷子になります。

この領域は、AI エージェントに一発で解かせるのが難しい分野だと分かっています。ソフトウェアパイプラインや allocation の設計は、structural hazard がどこで起きているかをプロファイルから読み取り、どのバッファをどうずらすかを一段ずつ組み立てる必要があり、人間側の理解がエージェントの作業を軌道修正する上で重要になります。

5【体験】スケジューリング 3 API の違い

パイプライン化を制御する NKI のスケジューリング API は 3 つあります。同じループ構造に対して「どこまでの並べ替え・オーバーラップをコンパイラに許すか」がそれぞれ違います。

許可されるオーバーラップ / 並べ替えの範囲 禁止される範囲
API役割
affine_rangeループの複数イテレーションが独立であることを表明し、オーバーラップ(パイプライン化)を許可する。多くのタイルループの既定選択。
sequential_rangeイテレーション間に依存関係があることを表明し、実行順序を保証する(アンローリングを抑制する)。ただし命令スケジューリングそのものまでは固定しない。
no_reorderブロック内部の命令の並べ替えを禁止する、最も強い制約。プログラムで書いた順序どおりに逐次実行させる。

ボタンで切り替えると、同じループ構造に対して「コンパイラに許される並べ替え・オーバーラップの範囲」が違う 3 枚の図に切り替わります。affine_range はイテレーション同士を重ねてよいと宣言する最も自由な指定、sequential_range は順序だけを固定してアンロールを抑える中間的な指定、no_reorder はブロック内の命令の並びそのものを凍結する最も厳格な指定です。

バージョンに関する重要な注意。上の affine_range / sequential_range の「オーバーラップ許可 / 順序保証」という区別は、ワークショップの Self-Attention v8〜v10 実演が書かれた時点(NKI 0.2 世代)の挙動を前提にしています。NKI 0.3.0 では affine_range / sequential_range / static_range は標準の range の別名に統一され、3 者の挙動上の差は廃止されました(いずれも単なる range として動作します)。したがって 0.3.0 環境で sequential_range を書いても「順序保証」の効果は得られません。依存関係のあるループの正しさを保証したい場合は、range を使いつつ nl.no_reorder()(ブロック内命令の並べ替えを禁止するコンテキストマネージャ)や、明示的な依存指定(with schedule 系)で担保します。no_reorder はこの統合とは別に、現行でも有効な制御として使えます。ここでの 3 分類は「スケジューリングを制御する考え方」の理解として読んでください。

6バンク利用率 (MBU) が高い = 速い、ではない

第 1 回の PSUM の章で「8 バンクを全部埋めれば速い、は誤解。実際はバンクを早く空ける (drain) 方が速い」と予告しました。ここでその正体を、同じ行列積を 3 通りに実装した比較で見ます。

PSUM の使われ具合を測る指標に MBU (バンク利用率) があります。8 バンクのうち、どれだけの割合が常に埋まっているかを表す ― いわばバンクの duty cycle です。直感的には「MBU が高い = 資源をフル活用 = 速い」と思いたくなります。ところが実測は逆を示します。

実装MBU (バンク利用率)速さ (相対)何が起きているか
Naive中程度基準素朴な matmul。特に工夫なし
Split-K高い (概念値で ~9 割)最も遅いK を分割してバンクを埋め尽くすが、分割した部分積を単一の Vector Engine で直列に足し合わせるreduction が Tensor Engine をブロックする
Pipelined低い (概念値で ~3 割)最も速いバンクを早く空けて次の matmul を流す。MBU は低いが Tensor Engine が途切れず動く
MBU は「バンクがどれだけ埋まっているか」であって「計算がどれだけ進んでいるか」ではありません。Split-K はバンクを埋める(MBU が高い)ことに成功していますが、埋まったバンクを空けるための直列 reduction が律速になり、肝心の Tensor Engine を遊ばせてしまう。逆に Pipelined はバンクをさっさと空けて(MBU は低い)、Tensor Engine を連続稼働させる。速さを決めるのは「一番効くエンジン(ここでは Tensor Engine)を途切れさせないこと」であって、バンクを埋めることではない ― これがこの章全体の「エンジンを遊ばせない」という主題の、PSUM 側から見た姿です。数値は傾向を示す概念値で、実測はカーネルとプロファイル条件に依存します。

指標の読み違いに注意。プロファイルで MBU が低いのを見て「PSUM を活かせていない、もっと埋めよう」と最適化すると、Split-K のようにかえって遅くなることがあります。第 4 回の「どのエンジンが律速か」をまず見て、MBU のような部分指標はその文脈で解釈するのが鉄則です。

7まとめ

「エンジンを遊ばせない」ための時間軸の設計を一枚に整理します。

論点要点
動機タイル処理を load/compute/store の逐次で行うと structural hazard で待ちが生まれる。裏で次のタイルを DMA 先読みして消す
ソフトウェアパイプラインアセンブリラインのようにステージをずらして重ね、定常状態で全ステージが同時稼働するようにする
二重バッファリング読む側・書く側で物理スロットを分け、並行動作時の上書き競合を避ける。容量対策ではなく並行性の確保が目的
allocationバッファのアドレスを人が明示し、アドレスの曖昧さを排除する。単体では速くならず、コンパイラがオーバーラップの安全性を証明できるようにする土台
v8→v9→v10PSUM解放(一時後退)→allocationのみでコンパイラが自動パイプライン化→明示的ソフトウェアパイプラインで多段オーバーラップ、という積み上げ
スケジューリング制御「オーバーラップ許可 / 順序保証 / 並べ替え禁止」という制御の考え方。ただし NKI 0.3.0 では affine_range / sequential_range / static_range は range の別名に統一(挙動差は廃止)。順序を担保するなら no_reorder や明示スケジューリングを使う
MBU ≠ 速さPSUM のバンク利用率 (MBU) が高い = 速い、ではない。バンクを埋め尽くす Split-K より、早く空けて Tensor Engine を連続稼働させる Pipelined の方が速い。律速エンジンを途切れさせないことが本質
結論。カーネルの速度は「1 つのエンジンをどれだけ速くするか」だけでは決まりません。複数のエンジンとDMAを、時間軸でどれだけ同時に働かせられるかが同じくらい効きます。そのための手段がソフトウェアパイプライン(裏で先読み)とallocation(アドレスの曖昧さを消してコンパイラに証明させる)です。allocation は単体では速くなりませんが、パイプライン化という次の一手を可能にする土台になる ― この「一時的な後退が飛躍を生む」構造は、この分野が AI エージェントに一発では解けない理由でもあり、人間の理解が軌道修正の鍵になります。
次回は、この地図の上でデータそのものを軽くする低精度化(量子化)を扱います。

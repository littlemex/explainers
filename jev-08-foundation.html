0この回で分かること

測定をこねくり回すのをやめて、Jev と同じ形を実装した回です。 4 つの設計判断を 2 つの独立したパネルに諮り、両方が全部一致しました。 そして私の理屈が 3 件、実装が 3 件間違っていました。

一言でいうと
形は動きました。ただし目標の土台モデルでは、質問を隔離するマスクが黙って漏れます (順序入れ替えで答えが 0.055、詰めた場合と単独実行の差が 0.245)。40 層中 39 層が線形注意で、 再帰にはマスクを足すスコア行列が存在しないからです。 そして答えを知っている世界を作りました — 潜在状態が列挙可能で、真の事後確率が閉じた形で計算できるので、 較正をビニング推定ではなく直接採点できます。
1. 何を実装したか 2. マスクは目標のモデルで漏れる 3. 私の理屈の誤り 3 件 4. 答えを知っている世界 5. 別プロジェクトの概念を取り込む 6. 判断の内容はどの深さにあるか 7. 赤いまま残したもの

1何を実装したか

1 本のシーケンスに詰めて、1 回の prefill で終わる。生成は 1 トークンもしない。

[ 共有 state ][ 質問1 ][ 質問2 ] ... [ 質問N ]

attention マスクで、state は自分の中で causal、各質問は state 全体と自分の中だけ、 質問どうしは見えない。これで KV 共有と質問の独立が同時に立ちます。 読み出しは枝の末尾から、宣言された選択肢だけに制限した softmax。JSON は普通のコードが組み立てます。

契約はテストにしました。マスク行列そのもの / 順序入れ替え不変性 / 他の質問と一緒に詰めた枝 = 単独実行(対称な漏れも捕まる) / state が 1 回しか符号化されていないこと。

実装の欠陥 1 件目はテストが見つけました。マスクは正しいのに枝が漏れる。 原因は position id でした。3 番目に詰めた枝は絶対位置が後ろにずれるので、 回転位置埋め込みが単独実行時と変わる。各枝を「state の直後にあるかのように」番号付けして解決。 理屈で気づいたのではなく、テストが落ちて分かった件です。

実測 (0.6B・質問 20 個): state 86 トークン、詰めて 637 トークン、別々に聞くと 2,271 = 3.57 倍。 壁時計は 194 倍速く出ましたが報告に使いません — N 回別々に呼ぶとカーネル起動も N 回払うので、 小さいモデルではそちらが支配します。節約の上限はトークン比です。

2マスクは目標のモデルで漏れる

0.6B の密なモデルでは契約テストが全部通ります。目標の Qwen3.6-35B-A3B-FP8 では通りません。

検査密な 0.6B目標の MoE
質問の順番を入れ替える通る最大 0.055 動く
詰めた枝 = 単独実行通る最大 0.245 差が出る

読み込みレポートが理由を書いていました。linear_attn が 0〜38 層。 線形注意はスコア行列を持たない再帰なので、「位置 i は位置 j を見てはいけない」という抽象に 貼り付ける先が存在しません。マスク引数は受け取られて無視される。 エラーにならないので、テストがなければ「動いている」と誤認します。

正しい原始操作はマスクではなく状態の fork です。state を 1 回 prefill してキャッシュを分岐させ、 各質問をバッチ要素として走らせる。パネル 2 名とも同じ結論でした。

そして私のコスト見積もりは逆でした。「長い state ほど fork が高い」と思っていましたが、 再帰状態は prefix 長に依存しない層ごと固定サイズです。prefix で伸びるのは softmax の KV だけで、 それは共有できる (Hydragen arXiv:2402.05099、ハイブリッド向けは Marconi arXiv:2411.19379)。 つまり 39/40 層が線形注意なのは、この形に不利ではなく有利。 「長い state を 1 回読んで軽い枝を大量に生やす」という用途に構造的に向いています。 密なモデルに逃げる折衷案は捨てました。

3私の理屈の誤り 3 件

パネルに諮って一番役に立ったのは、結論より私の理屈の訂正でした。

「較正は集合の性質だから 1 サンプルに報酬を付けられない」— 誤り

proper scoring rule はまさにサンプル単位の報酬で、期待値の最大点が真の条件付き分布です。 集合の性質なのは計測の話で、学習信号の話ではありません。 強化学習を避ける正しい理由はもっと狭くて強い —— 同じ目的が微分可能なのに、高分散な方策勾配で推定する理由がない。

「床での被覆は微分不可能」— 誤り

SelectiveNet (arXiv:1901.09192)、Deep Gamblers (arXiv:1907.00208)、 learning-to-defer (arXiv:2006.01862) が微分可能な代理を持っています。 訓練で得られないのは保証の方で、それは分布フリーな閾値層 (RCPS arXiv:2101.02703、 Learn-then-Test arXiv:2110.01052) の仕事。私は目的と保証を混同していました。

「修復すると較正が壊れる」— 方向は正しいが粗い

正確には「周辺較正は制約集合への射影で保存されない」。射影後の周辺が他のヘッドに依存し、 その依存構造 (積分布) が真の同時分布と一致する保証がないからです。 ただし改善することもあります — 真のデータが常に制約を満たすなら、制約外の質量自体が誤較正の証拠なので。 経験的な問題なので、修復より先に検査器を出します。

あわせて、型強制に論理式は不要と確定しました。読み出しが宣言された選択肢の上の softmax なので、 制約する対象 (トークン列) が存在しません。同時整合は DNF ではなく factor graph で、 費用を決めるのは選択肢数の積ではなくtreewidth です。

4答えを知っている世界

第 7 章で「難しい推論ベンチは決定層の検証に向かない」と結論しました。作り直した先がこれです。

そしてパネル 2 名が独立に、私が見落としていた要請を出しました。 決定的なラベルだけでは較正の検証にならない。潜在状態が文書に完全に現れてラベルが決定的なら、 十分強いモデルの誤りはゼロになり、高い床が自明になって何も測れません。

必要なのは、観測が潜在状態を部分的にしか明かさないこと。しかも 「どれを明かすか」を状態を見ずに決めること。
そうすると事後分布が「事前分布を整合状態に制限したもの」に厳密一致するので、 閉じた形で計算できます。

実装は潜在状態 648 個、優先順位を明記した 5 つのルール、状態についての 11 個の述語。 述語を明かすので「銀行は問題ないと言っている」のように1 つの原因を除外して 3 つ残す証拠が作れます。 閉形式は Monte-Carlo で検証済み — 世界を 6 万回再標本して整合するものだけ数え、解析解と一致するか見る。 これで「真の事後確率がわかる」が主張ではなく検査になりました。

5別プロジェクトの概念を取り込む

並行して走っている別の研究で、モデルの内部から「言語化されうる部分空間」を読む道具 (J-lens、Gurnee et al. arXiv:2607.15495) を扱っています。これがこの土台に入るか、という問いです。

入ります。私の読み出しは、枝の最終隠れ状態に対するまさにレンズなので、 ランダム初期化した行列の代わりに事前学習モデル自身の読み出し経路を置けます。

効いたこと: 読み出しを選択肢のトークンに紐づける

元の設計は「255 スロットの共有行列」で、第 j 行は意味ではなく提示順を表します。 だから選択肢の順番を入れ替えると確率が動く。レンズならトークン同一性に紐づきます。

読み出し選択肢の順番を入れ替えたときの最大変化
提示順に紐づく (元の設計)0.542 / 0.558 / 0.507
トークン同一性に紐づく (レンズ)0.127 / 0.099 / 0.165

4 倍改善しましたが、直りませんでした。私は「構成上ゼロになる」と予測して外しました。 原因は分かりました — 読み出し行列は置換同変になったのに、枝の隠れ状態そのものが変わる。 質問文が選択肢を順番に並べているので、枝が読む文字列が変わるからです。 残った偏りは読み出しではなくエンコーダ側です。

この故障は別タスクで先に測られていました。同じ研究で 「判別方向の 84.3% が答えの文字 10 方向の張る空間の中」「モデルは A に逃げる (A の精度 0.3899 対 他 0.5979〜0.7522、A は全体の 24%)」という測定があります。 私がいま捕まえた選択肢位置バイアスと同じもので、別の道から裏取りされた形になりました。

逆に、その研究の主要な否定的結果はここには縛りません。 「内部状態は難しさを読むが、より強いモデルなら直るかは読まない」は 別のモデルの成否を当てる話で、ここで聞いているのは「このチケットはどの窓口か」—— 入力についての問いです。的が違います。

6判断の内容はどの深さにあるか

元の実装は最終層だけを読んでいました。しかしその研究の測定では、言語化されうる内容は 深さ 30〜80% の帯にあり、最終層ではありません。そして因果モデルの最終層は 次のトークンへの commit に特化していて、私が欲しいのは表層ではなく判断の内容です。

ここで設計が一段変わりました。1 つ選ぶのではなく、複数の深さに読み出しを付けて混ぜる。 前向き計算は全層を通っているので、K 層読んでも小さい行列積が K 回増えるだけ — 掃いて 1 つ選ぶのは、すでに計算済みの情報を捨てる話でした。

真の事後確率が手元にあるので、学習ゼロで深さごとの当て具合を直接測れます (0.6B・40 件、数字は真の事後確率に対する Brier で小さいほど良い)。

ただし「複数に付ける」判断はこれで正当化されました。質問ごとに最良の深さが違います。
例外と優先順位を持つ refund_allowed と escalate は最終層が明確に最良。 潜在変数を当てる root_cause は深さ 0.54 が最良で、最終層は 2 倍悪い。 1 つ選べば必ずどれかを捨てるので、混ぜて学習させるのが正しい。

順序感度には強い勾配が出ました。深さ 0.25 で 0.015、最終層で 0.435 —— 29 倍。 「選択肢順序の偏りは後段の表層コミット由来」という予測は当たりました。 ただし浅く読めば直る、を素朴に採ると最終層が最良の 2 問を捨てることになります。 混合重みがこのトレードオフを学習で解く対象になります。

そして真の J-lens (基底のドリフト補正) が意味を持つ場所も、これで特定できました。 最終層を読むなら補正は不要で、中間層を最終層の読み出し経路で読むのは未補正版です。 root_cause が深さ 0.54 で 2 倍良いという結果は、まさに補正が効きうる場所を指しています。 ただし量子化されたモデルで再帰を跨ぐ勾配は別工事なので、混合重みが中間層に有意な質量を置いてから着手します。

7赤いまま残したもの、と次

選択肢順序のテストは赤のまま残しています (0.159)。原因は読み出しではなくエンコーダ側と 特定できたので、次に潰す対象が決まっているからです。通してから直すより、 落ちたまま置いておくほうが役に立ちます。

実装の欠陥は 3 件出て全部直しました。position id の再スタート漏れ、 読み出しの精度指定が土台まで巻き込んで 35B を 32 ビットに変換しようとした件 (メモリ不足として遠くで露出)、 そしてデバイス移動の対象をモジュール名で列挙していて新しいヘッドが取り残された件。 最後の 1 件は列挙をやめて「土台以外は全部動かす」に変えました。

作業の順番でパネルが唯一割れました。一方は「fork の検証を先」、 もう一方は「生成器を先」。後者を採りました。 fork は解の形が既に分かっている重い工事で、しかも大きい土台が必要かどうかがまだ未確定です。 このプロジェクトで 2 回「測る価値を確かめる前に機械を作った」ので、fork はその高額版になります。 先に「小さい土台を全学習 対 大きい土台を凍結 + 読み出し」をこのデータで測り、 大きい方が勝ってから工事に入ります。

次は proper loss で読み出しを訓練し、混合重みがどの深さに質量を置くかを読み、 小さい土台と大きい土台を比べます。強化学習はそこで届かないものが残ったときだけです。

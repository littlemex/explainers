1止まっていたのは誰か

エミュレータ上で DeepEP の dispatch が forwarding 段で止まる。その原因を私は 3 ラウンド続けて読み違えました。

エミュレータは NCCL の RMA plugin として振る舞い、TCP でバイトを運びます。受け取ったバイトは GPU のウィンドウへ書き込む必要があり、素朴にはこう書きます。

cuMemcpyHtoDAsync(window + offset, host_buffer, bytes, stream);
cuStreamSynchronize(stream);

これで DeepEP の dispatch が forwarding のタイムアウトで死にます。そして私が最初に見た証拠がこれでした。plugin 側の統計を 5 秒ごとに出していたので、100 秒離れた 2 枚を比べられます。

REPORT: context 0x441d8f60 is holding 54 operation(s) ... driven 254699 time(s)
completion path: test() 2097 call(s), 139 done, 0 refused

2 枚がバイト単位で同一でした。driven は rmaProgress が呼ばれた回数です。動かない。だから私は「NCCL が plugin を呼ぶのをやめた」と読み、54 個の未処理オペレーションを原因だと考えました。

これが誤りでした。凍った数字は「呼ばれていない」と「最後の呼び出しが戻ってこない」を区別できません。同じ沈黙が、責任者の違う 3 つのバグと両立します。NCCL が呼ぶのをやめた、私の呼び出しが返ってこない、あるいはこの報告自体が古い。

2数字に日付を入れる

回数は「何回」しか言いません。障害が問うているのは常に「いつから」です。

plugin には元々、各スレッドが今どの関数の中にいるかを置くパン屑の仕組みがありました。足りなかったのは 1 つだけで、いつそこに置いたかです。store 1 個の追加で、最初の 1 回の計測が答えを出しました。

rank1: 受信エージェントは 4 バイトのデバイス操作の中に 350625 ms いる
rank1: thread 26746: send_unit: staging ... (464055 回訪問, 最後に動いたのは 350625 ms 前)
rank1: thread 64896: rmaProgress (1494089817 回訪問, 最後に動いたのは 0 ms 前)

NCCL は健全でした。rmaProgress に 15 億回入っていて、最後に動いたのは 0 ms 前です。凍っていたのは私のスレッドで、しかも 3 本が同じ瞬間に止まっていました。2 ラウンド分の推論がここで反転します。

読み方はこうなります。パン屑が rmaProgress を指していて 100000 ms 前に動いたなら、それは返ってこない呼び出しの中です。同じパン屑が 3 ms 前なら、それは呼ばれて仕事が無いと答えているだけです。回数はこの 2 つを永遠に区別しません。

3写真ではなく在庫表を取る

スタックダンプは標本です。標本は、狙った瞬間を外します。

次に知りたいのは「driver の中で他に何が動いていないか」です。候補となる説明はどれも別の 2 本目の呼び出しを予言します。モジュールのロード待ち、仮想メモリのマッピング変更、ページ固定、ロックの逆転。だから測るべきは、その瞬間に driver の中にいる呼び出しの一覧です。

スタックダンプでほぼ答えが出そうで、出ませんでした。止まっているスレッドは確実に写りますが、犯人は標本が当たったときだけ写ります。5 回試して有効な採取は 2 回でした。

在庫表は標本ではありません。入ったのに出ていない記録は、戻るまで表に残ります。だからタイミングで取り逃がせません。LD_PRELOAD で libcuda の入口を包み、入場と退場を数えるだけの仕組みを書きました。DeepEP や PyTorch の呼び出しも見えるので、自分のコードを計測するのでは届かない範囲まで入ります。

結果は 1 行でした。

== overdue: tid 1149344 has been inside cuMemcpyDtoHAsync_v2 for 103459 ms
   tid 1149344: cuMemcpyDtoHAsync_v2, in flight for 103459 ms

driver の中にいるのは 1 本だけ。103 秒。モジュールのロードも、確保も、マッピングもありません。ロックの保持者は存在しませんでした。

4自前のメモリと自前の stream で試す

保持者がいないなら、残るのはその copy 自身の引数です。

両端を自分で用意した probe を書きました。plugin 専用の確保、専用の非ブロッキング stream、どちらもカーネルが存在する前に作ったもの。DeepEP が一度も触っていないメモリです。

probe: the large copy returned CUDA_ERROR_LAUNCH_FAILED (719) after 92903 ms
probe: the small copy returned CUDA_ERROR_LAUNCH_FAILED (719) after 0 ms

1 メガバイトが 93 秒ブロックし、そのあと続く 8 バイトは 0 ms で同じコードを返しました。後者が速いのは、その時点でコンテキストが既に死んでいるからです。

サイズも stream も番地も無関係でした。DeepEP の forwarding カーネルが resident で spin しているあいだ、このコンテキストはバイトを 1 つも動かせません。

これで順序も確定します。凍結までの間、driver はコンテキストを健全と報告し、stream を idle と報告します。719 が出るのは最後で、DeepEP が自分のタイムアウトで trap したときです。私が 3 ラウンド「最初の障害」として読んでいたコードは、いちばん後ろの出来事でした。

5なぜ待ちが解けないのか

カーネルはその copy が運ぶバイトを待ち、copy はカーネルが終わるのを待ちます。

計測で確定した循環。copy engine は SM と独立なので通るはずだ、という直感が外れる場所です。

copy engine は SM とは独立に動くので、resident なカーネルがあっても DMA は流れるはずだ、という直感があります。実際に止まるのは DMA ではなく submit です。stream は idle のままで、仕事がそこへ届いていません。ホストが CUDA に何かを積もうとする行為そのものが、このコンテキストでは進みません。

本物の NIC はこの問題を持ちません。driver を介さず DMA でメモリを書くからです。エミュレータには等価な手段が無い、というのがこの時点の結論でした。

6排除できたもの

結論を「私のコードのどこかが悪い」に落とさないために、層を 1 つずつ潰しました。

疑ったものどう排除したか
順序の緩さ厳密な提出順を含む 6 種類のスケジュールで同じく失敗
ホスト側バッファの寿命copy の直後に同 stream を synchronize している
signal を書くカーネルの SM 待ちカーネルを使わない DMA に置き換えても失敗
NCCL が context を回していない全 context を毎回進めても失敗。rmaProgress は 15 億回入っている
lazy なモジュールロードがロックを握るCUDA_MODULE_LOADING=EAGER で変化なし。凍結時に cuModuleLoad の中にいるスレッドは無い
コンテキストが既に fault している凍結中、driver はコンテキストを健全・stream を idle と報告する
ページ固定メモリ・番地・サイズ・stream専用確保 + 専用 stream の 1 MB でも 93 秒ブロック

残ったのは差し込み方そのものでした。ホストのスレッドが CUDA の転送で、すでに走っていて自分を待っているカーネルにバイトを届ける。この形がこの driver では成立しません。

次の回では、成立する形を測ります。答えは既に本物の backend が使っていました。

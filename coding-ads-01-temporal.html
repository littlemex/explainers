永続性とレトロアクティブ性 ― データ構造に時間を埋め込む

過去を壊さず全部残す(永続化)か、過去に手を入れて今まで伝える(レトロアクティブ)か

← MIT 6.851 シリーズ目次へ ← コーディング基礎 シリーズ目次へ

ふつうのデータ構造は更新すると過去の状態を失います。この回で見る「時間的データ構造 (temporal data structure)」は、その前提を 2 つの方向から破ります。永続性 (persistence) は、更新のたびに過去をすべて残し、あとから任意の過去バージョンを読める(場合によっては書ける)ようにします。レトロアクティブ性 (retroactivity) は逆に、過去そのものに手を入れて(「3 ステップ前の操作を実は別の値でやっていた」)、その変更が現在まで正しく伝わるようにします。どちらも MIT 6.851 (Advanced Data Structures) の最初の 2 回の講義 (L01: 永続性, L02: レトロアクティブ性) の主題で、この 2 つの技法は次回 L03 で「幾何の問題を時間の問題に変換する」ためにそのまま再利用されます。

この回の位置づけ

永続性とレトロアクティブ性は、どちらも「データ構造にバージョン(時刻)という次元を追加する」という同じ問題意識から生まれています。違いは向きです。永続性は未来から過去を安全に覗く仕組み、レトロアクティブ性は過去から未来へ変更を安全に伝える仕組みです。この 2 つを押さえておくと、次回 L03 で「平面上の点の位置判定」や「線分の交差判定」が、なぜ唐突に L01・L02 の結果を使って解けるのかが分かるようになります(2 次元の幾何の問題を、1 次元の問題 + 時間、に変換して解く「ラインスイープ」という手法を使うためです)。

この回の内容は、CS の学部カリキュラムで言うと「計算量の厳密な解析(償却計算量・ポテンシャル法)」と「平衡二分探索木を道具として使いこなす」ことを前提にしています。この 2 つは電気電子工学やハードウェア出身の読者には馴染みが薄いと思われるため、先に簡単に補習します。

前提の補習 1 ・ ポインタマシンモデル (pointer machine model)

この講義では、データ構造を「固定サイズのフィールドを持つノードの集まり」として考えます。許される操作はこの 5 つだけです。

x = new Node()        // ノードを 1 つ作る
x = y.field            // フィールドを読む
x.field = y            // フィールドに書く
x = y + z              // ふつうの計算
destroy(x)             // 誰も指していないノードを消す

これは C の struct や Java の object がポインタ(参照)でつながったグラフだと考えるのとほぼ同じです。重要なのは何がこのモデルに入らないかです。可変長配列のように「サイズが動くひとつながりのメモリ領域」はこのモデルの外にあります。配列は添字で $O(1)$ ランダムアクセスできますが、その代わり「配列の真ん中に要素を 1 個だけ挿入する」といった操作を安全にバージョン管理するのが構造的に難しくなります。この講義で扱う永続性の結果は、基本的にポインタでつながったノードのグラフ(連結リスト、二分探索木など)を対象にしており、配列のような構造には別の議論が必要です。

前提の補習 2 ・ 償却計算量とポテンシャル法

償却計算量 (amortized complexity。ならし計算量とも呼ぶ。1 回だけでなく操作の列全体で費用を平均したときの、1 回あたりの上限) は「どんな入力列であっても、合計コストはこの範囲を超えない」という最悪ケースの保証です。確率は一切使いません。平均計算量(期待値)とは別物で、1 回だけ見ると高くつく操作があっても、それが頻繁には起きないことを合計コストで示します。この考え方自体は coding-complexity-bigo.html の第 4 節で可変長配列のコピーコストを例に詳しく説明しているので、ここでは L01 で使う形だけ押さえます。

ポテンシャル法 は償却計算量を証明する道具です。データ構造の「溜まった不満」のようなものを表す関数 $\phi$ (ポテンシャル)を 1 つ決めて、

$\text{償却コスト} = \text{実際のコスト} + \Delta\phi \quad (\Delta\phi = \phi_{後} - \phi_{前})$

と定義します。$\phi$ をうまく選ぶと、個々の操作が高くついた分を $\Delta\phi$ の減少が打ち消してくれて、償却コストの総和(= 実際のコストの総和)が小さいことが示せます。L01 では「mod log (後述) に溜まったエントリ数」を $\phi$ に選びます。

前提の補習 3 ・ 平衡二分探索木とオーダー保持構造

平衡二分探索木 (balanced BST) はこの講義全体で「高さが常に $O(\log n)$ に保たれ、探索・挿入・削除が $O(\log n)$ でできる木」というブラックボックスとして使われます。内部の回転規則(AVL・赤黒木など)の詳細はこの講義では重要ではありません。

もう 1 つ、完全永続化で必要になるオーダー保持構造 (order-maintenance data structure) を先取りで紹介します。これは「要素 $s$ を要素 $t$ の前後に挿入する」「$s$ が $t$ より前かどうかを判定する」の 2 操作を両方 $O(1)$ でサポートする構造です(Dietz–Sleator, L08 で詳しく扱う)。連結リストなら挿入は $O(1)$ でも前後判定は $O(n)$、平衡 BST なら両方 $O(\log n)$ になるので、両方を $O(1)$ にできるのは自明ではない結果です。

1. 永続性の 4 段階 ― 分岐する宇宙のモデル

永続性は「過去のバージョンについての問い合わせにどこまで答えられるか」で 4 段階に分かれます。弱い方から強い方へ並べると次の通りです。

  • 部分永続化 (partial persistence) ― 任意の過去バージョンは読めるが、書けるのは最新バージョンだけ。read(var, version) と newversion = write(var, val)。バージョンは一直線に並ぶ。
  • 完全永続化 (full persistence) ― 任意のバージョンに対して読み書きどちらもできる。read(var, version) と newversion = write(var, version, val)。1 つのバージョンから複数の子バージョンが分岐しうるので、バージョンは木になる。
  • 融合永続化 (confluent persistence) ― 完全永続化に加えて、2 つの過去バージョンを 1 つに合流させる newversion = combine(var, val, version1, version2) を許す。バージョンは木ではなく有向非巡回グラフ (DAG) になる。
  • 関数型永続化 (functional persistence) ― 関数型プログラミングのオブジェクトがすべて不変であるのと同じ発想。内部実装の自由度を制限し、既存のノードを一切変更せず、新しいノードを追加するだけで永続性を実現する。

強い方から弱い方へ一方向の含意があります: 関数型 $\Rightarrow$ 融合 $\Rightarrow$ 完全 $\Rightarrow$ 部分。これは「できることが増える」のではなく「実装方法を制限している」という意味の含意です。関数型永続化はその実装方法のまま使えば自動的に融合永続化の操作(combine)も実現でき、combine を使わなければ完全永続化になり、最新バージョンにしか書き込まなければ部分永続化になる、という具合に、上位の制約が下位の要件を自動的に満たします。

図: 部分永続化は一直線、完全永続化は木、融合永続化(と関数型永続化)はバージョンが合流できる DAG

2. 部分永続化 ― mod log で過去を守る

部分永続化は、ポインタマシンモデル + 各ノードへの入次数(入ってくるポインタの本数)が $O(1)$、という条件さえ満たせば、漸近的に追加コストほぼゼロで実現できます (Driscoll, Sarnak, Sleator, Tarjan, 1989)。発想は「ノードが変更されるたびに書き換えるのではなく、変更履歴 (mods ログ) をノードに溜めていく」ことです。

各ノードを次の 3 つの領域に拡張します。

  1. 読み取り専用領域 ― 元のデータとポインタ(普通のノードと同じ)
  2. バックポインタ領域 ― 「自分を指しているノード」への逆ポインタ。入次数が高々 $p$ 本と分かっているので固定サイズで持てる
  3. mod log 領域 ― (フィールド名, バージョン, 新しい値) の形の変更履歴。これも固定サイズ $2p$ 個分だけ確保する

read(var, v) は mod log の中から「バージョン $\le v$ で最大のもの」を探すだけで $O(1)$。write(var, val) は mod log に空きがあれば単に 1 エントリ追加するだけで $O(1)$ ですが、mod log が満杯になったら新しいノード $n'$ を作り、最新の値を読み取り専用領域にコピーし、$n$ を指していたノードたちのバックポインタ経由で再帰的にポインタを張り替えます。古いノード $n$ はそれ以降読み取り専用(過去を見るためだけに残る)になります。

図: mod log が満杯になると新ノード n' に現在の書込先を移し、n を指す全ノードのポインタを張り替える(Driscoll–Sarnak–Sleator–Tarjan の構成)

解析。空間は 1 ノードあたり $d+p+2p = O(1)$ なので全体 $O(n)$。時間はポテンシャル法を使います。$\phi = c \times (\text{現在のノードたちの mod log エントリ数の合計})$ とすると、分裂が起きたときノードは「満杯 ($2p$ 個)」から「空 (0 個)」に変わるので $\Delta\phi = -2cp$。償却コストの再帰式は

$\text{償却cost}(n) \le c + c - 2cp + p \cdot \text{償却cost}(x)$

となり、再帰を 1 段展開すると $-2cp$ が再帰から来る追加コストとちょうど打ち消し合って $O(1)$ 償却時間が示せます(詳細は展開すると定数項しか残らないことを確認する計算です)。さらに Brodal (1996) はこれを最悪ケースでも $O(1)$ にできることを示しました。

3. 完全永続化 ― バージョンも木になる

完全永続化では、任意のバージョンに書き込めるため「最新」という特別な概念が消え、すべてのノードが書き込みを受け付けられる必要があります。また、バージョンが木になるので、「バージョン $v$ はバージョン $w$ の祖先か」を高速に判定する必要が新たに生じます。木をただ辿ると $O(\text{バージョン数})$ かかってしまいます。

この問題は括弧による線形化表現で解決します。木を深さ優先で辿り、ノード $a$ に入るとき (a、出るとき )a と書き出すと、例えば木が「$a$ の子が $b,d$、$b$ の子が $c$」なら (a (b (c )c )b (d )d )a になります。この文字列から、$v$ が $w$ の祖先であることは「(v が (w より前にあり、かつ )w が )v より前にある」という 2 回の前後比較だけで判定できます。この前後比較と、新しいバージョンを挿入する操作を両方 $O(1)$ で行えるのが前提の補習で紹介したオーダー保持構造です (Dietz–Sleator)。

図: 深さ優先で木を辿って (x / )x を書き出すだけで、祖先判定が前後比較 2 回 (O(1)) に落ちる

構築は部分永続化とほぼ同じ発想で、各ノードは $d$ 個のデータ・$p$ 個のバックポインタに加え、最大 $2(d+p+1)$ 個まで mod を持てます。満杯になったら、mod log をバージョン木の部分木ごとに 2 つに分割して新ノード $m$ を作ります(ランダムに分けるのではなく、バージョン木の構造に沿って分割するのが重要な点です)。空間は分裂時 $O(1)$、時間はやはりポテンシャル法 ($\phi = -c \times \text{空きスロット数}$) で償却 $O(1)$ が示せます。

未解決問題 (講義当時)。完全永続化を償却でなく最悪ケース $O(1)$ にできるか(脱・償却化)、部分永続化・完全永続化に見合う下界はあるか、は講義時点で未解決として挙げられています。

4. 融合永続化 ― バージョンが合流するとき

combine 操作でバージョンを合流させると、バージョン木を辿る技法がそのまま使えなくなります。DAG には木のような「深さ優先で 1 回辿れば終わり」という性質がないからです。実際、文字列を繰り返し自分自身と連結する(string を combine し続ける)だけで、$u$ 回の融合更新のあとにはバージョン履歴に $2^u$ 通りの経路が生まれ得ます。

Fiat と Kaplan の一般的な変換は、バージョン $v$ の実効的な深さ (effective depth) $e(v) = 1 + \log(\text{ルートから } v \text{ への経路数})$ を使います。これは「DAG を DFS で展開して経路の重複をコピーとして数え、それを平衡化した木にしたときに到達できる最良の深さ」に相当します。このとき、オーバーヘッドは $\log(\text{更新回数}) + \max_v e(v)$ で抑えられます。文字列の自己連結を繰り返す最悪例では、根からの経路数そのものは $u$ 回の更新で $2^u$ 通りに爆発しますが、$e(v) = 1+\log(2^u) = 1+u$ となるため、$e(v)$ 自身は更新回数 $u$ に対して線形にしか増えません(講義ノートもこの例の図のキャプションで「$e(v)$ is linear on the number of updates」と明記しています)。オーバーヘッドが更新回数に対して線形というのは講義ノート自身も「性能が悪い (poor performance)」と評している結果ですが、それでも経路の数だけ丸ごと複製する($2^u$ 個複製する)よりは指数的に優れている点が重要です。クエリが無料だと仮定すると、更新あたり $\Omega(e(v))$ の下界も Fiat–Kaplan 自身の構成で示されています。

図: 経路数は自己連結で指数的に増えるが、実効的な深さ e(v) はその対数、つまり更新回数に対して線形にしか増えない(Figure 6 のキャプション通り)

特殊な場合として、「互いにデータノードを共有しない 2 バージョン間でのみ combine を行う(互排な操作)」に限定すると、Collette, Iacono, Langerman が $O(\log n)$ のオーバーヘッドを示しています。この場合、各データノードのバージョン履歴は木になるので、read(node, field, version) は (1) ノード自身が更新された版、(2) 更新点の間にいる版、(3) 葉より下にいる版 の 3 ケースに分かれます。(2) は「直前の更新がどこだったか」を木の上で辿って見つける問題でリンクカット木 (L19 で扱う) が使われ、(3) はさらに込み入っていてフラクショナルカスケーディング (L03 で扱う) を使う証明になっています。「$O(1)$ あるいは $O(\log n)$ の空間オーバーヘッドで一般の融合永続化ができるか」は講義当時の未解決問題です。

5. 関数型永続化 ― 不変なノードだけで作る

関数型永続化は実装方法そのものを縛ります。既存のノードの内容を一切変更しない、許される内部操作は「新しいノードを追加する」だけ、というルールです。代表例は パスコピー法 (path copying) による平衡 BST の関数型永続化で、更新されたノードとその祖先をすべて複製して新しい版のパスを作ります(親ポインタがない場合はルートから下向きに作業します)。平衡木であれば 1 回の更新あたりのオーバーヘッドは $O(\log n)$ です。この手法はリンクカット木にも拡張できることが Demaine–Langerman–Price によって示されています。

デック (両端から挿入・削除できる列。stack と queue を合わせた操作ができる) は連結操作を含めて定数時間で関数型永続化できます (Kaplan–Okasaki–Tarjan)。さらに Brodal–Makris–Tsichlas は、連結は定数時間、探索・更新は $O(\log n)$ という純粋関数型かつ最悪ケースの構成を示しました。トライ(接頭辞木)も部分木のコピー・削除という局所操作で関数型永続化でき、古い版の部分木をそのまま新しい版に挿入する(2 つの版を合体させる)ことができるため、トライの関数型永続化は自然に融合永続化にもなるという興味深い性質があります。

Pippenger は「関数型版と(関数型という制約を外した)ふつうの永続化版のコスト差は、高々 $O(\log n)$ 倍にしかならない」ことを示しました(論文タイトルは“Pure versus Impure Lisp”)。つまり不変性という制約を守ること自体のコストには上限があるということです。リスト同士の分割・連結を一般のポインタマシン上で実現する問題は、講義時点では未解決とされていましたが、のちに Blame Trees (Demaine, Panchekha, Wilson, Yang, WADS 2013) によって解決されています。配列に対する切り貼り(cut&paste)の関数型永続化は、この講義ノートの時点ではなお未解決と記されています。

6. レトロアクティブ性とは ― 過去を書き換えて今に伝える

永続性は「過去を覗く」技術でした。レトロアクティブ性は逆に、過去の操作列そのものを編集し、その影響を未来まで正しく伝える技術です。操作列を 1 本のタイムラインとして考え、通常は末尾(現在)にしか追加しませんが、レトロアクティブなデータ構造はタイムラインの途中にも挿入・削除ができます。対象のデータ構造(例: 配列、優先度キュー)に対する本来の操作を小文字(insert, delete-min など)、タイムラインを操作するレトロアクティブな操作を大文字で書きます。

  • Insert(t, update) ― 時刻 $t$ に操作 update を挿入する
  • Delete(t) ― 時刻 $t$ の操作を削除する
  • Query(t, query) ― 時刻 $t$ の時点でクエリ query を評価する

時刻 $t$ は整数と考えても構いませんが、「時刻 $t$ と $t+1$ の間に新しい操作を挿み込みたい」ことがあるため、実際には前節のオーダー保持構造を使います。レトロアクティブ性には 3 つの強さがあります。

  • 部分レトロアクティブ (partial) ― クエリは常に $t=\infty$ (現在) で行う。過去は書き換えられるが、見るのは常に「今」の結果だけ。
  • 完全レトロアクティブ (full) ― クエリも任意の過去の時刻 $t$ で行える。
  • 非忘却的レトロアクティブ (nonoblivious) ― 挿入・削除・クエリすべてが任意の時刻で行え、さらに「ある更新によって、どのクエリの結果が変わったか」まで教えてくれる。

簡単な特別ケース。更新が交換可能 (commutative) ($x.y=y.x$、順序を入れ替えても結果が同じ)かつ可逆 (invertible) (逆操作 $x^{-1}$ が存在し $x.x^{-1}=\emptyset$)なら、過去への挿入はInsert(t,op) = Insert(now,op)、過去の削除はDelete(t,op) = Insert(now,op⁻¹)と単純化でき、トリビアルに解けます。ハッシュテーブルへの挿入や、配列への A[i]+=Δ (直接代入は不可)がこの例です。

7. 完全レトロアクティブ性と分解可能探索問題 ― 時間を軸にしたセグメント木

一般にはもっと難しい場合も扱えます。まず探索問題を「集合 $S$ を保ち、insert・delete・query(x,S) をサポートする」問題と定義します。そのうち分解可能探索問題 (decomposable search problem) は、クエリが $\text{query}(x, A\cup B) = f(\text{query}(x,A), \text{query}(x,B))$ を満たす($f$ は $O(1)$ で計算できる、$A,B$ は重なっていてもよい)という条件を満たすものです。動的最近傍探索・直線上の successor・平面上の点在位置判定などがこれに当たります。

結果 (Bentley–Saxe, 1980)。交換可能・可逆な更新を持つ分解可能探索問題は、時間軸の上に平衡二分探索木 (セグメント木) を作ることで、時間・空間ともに $O(\log m)$ 倍のオーバーヘッドで完全レトロアクティブ化できます($m$ は操作の総数)。木の葉が時刻を表し、各要素は自分の生存区間 $[L,R]$ に対応する $O(\log m)$ 個の internal node に(区間分解の標準的な性質により)ちょうど現れます。時刻 $t$ でのクエリは、$t$ に対応する葉から根までの $O(\log m)$ 個の祖先だけを見て、分解可能性を使って $f$ で結果を合成すれば済みます。

図: Bentley–Saxe のセグメント木。要素の生存区間は O(log m) 個の節点として現れ、クエリは根までの経路だけを見る

8. 一般の完全レトロアクティブ性 ― ロールバック法と下界

分解可能でない一般の問題では、素朴なロールバック法を使います: 操作とクエリの列をそのまま記録しておき、$r$ 時間単位前を変更したければ、そこから先をすべて再実行する。これは $O(r)$ のオーバーヘッドで、一般には最善であることが下界で示されます。

下界 $\Omega(r)$ の証明の発想。2 つのレジスタ $X, Y$ (初期値 $\emptyset$) を持ち、$X=x$、$Y\mathrel{+}=\Delta$、$Y=X.Y$、クエリ「$Y$ は?」をサポートするデータ構造を考えます。次の操作列を実行すると

$Y\mathrel{+}=a_n,\ X=X.Y,\ Y\mathrel{+}=a_{n-1},\ X=X.Y,\ \ldots,\ Y\mathrel{+}=a_0$

これはまさにホーナー法 (Horner's method) による多項式評価 $Y = a_n X^n + a_{n-1}X^{n-1} + \cdots + a_0$ と同じ計算です。ここで Insert(t=0, X=x) を実行すると、多項式を評価する場所 $x$ そのものが変わってしまい、これは多項式を評価し直すのと本質的に同じコストがかかります。前処理の仕方に関わらず「履行不変 (history-independent) な代数的決定木」モデルでは、次数 $n$ の多項式の評価に $\Omega(n)$ 回の体演算が必要であることが知られており (Frandsen–Miltersen, 2001)、これが $\Omega(r)$ 下界の根拠になります。

セル・プローブ下界。「メモリ上の何個の語(ワード)を読む必要があるか」を数えるセル・プローブモデルでは、$n$ 個の語に対して長さ $\Theta(n\log n)$ の操作列で FFT を計算させ、最後にその結果をクエリします。この操作列を retroactive に初期値だけ変えられるなら動的 FFT ができることになりますが、動的 FFT で 1 つの入力を変えるには $\Omega(\sqrt n)$ 回のセルプローブが必要であることが知られています。$r=\Theta(n\log n)$ だけ遡ることのオーバーヘッドに換算すると $\Omega\!\left(\sqrt{r/\lg r}\right)$ となり、これが現在知られている下界です。$\Omega(r)$ そのものがセル・プローブモデルで成り立つかは未解決です(ロールバック法の $O(r)$ との間にまだギャップがあります)。

読み方の補足。この結果が言っているのは「一般の完全レトロアクティブ化には $r$ に比例する手間が本質的に必要になる場合がある」ということで、前節の分解可能探索問題のように追加の構造がある問題だけが $O(\log m)$ という $r$ に依存しない良いオーバーヘッドを得られます。「どういう性質を満たす問題が rollback 法より賢くできるか」を見極めるのが、この分野の勝負所です。

9. レトロアクティブ優先度キュー ― 「橋 (bridge)」という発想

優先度キューの insert と delete-min は交換可能ではありません(順序が結果を変える)。そのため前節の「簡単な特別ケース」は使えず、専用の技法が必要です。それでも部分レトロアクティブ優先度キューは 1 操作あたり $O(\log n)$ のオーバーヘッドで実現できます (Demaine–Iacono–Langerman)。

直感をつかむため、横軸を時刻、縦軸をキー値とする平面に図示します。insert(t,k) は点 $(t,k)$ から右へ伸びる水平な半直線。delete-min() は $(t,-\infty)$ から上に伸びる垂直な半直線で、最初にぶつかった水平線(= 削除される要素)をそこで止めます。削除された要素は、両端 $(t,k)$ と $(t_k,k)$ を持つ「逆さの L」字の線分になり、削除されずに残った要素は右へ伸び続ける半直線のままです。

図: insert は右へ伸びる半直線、delete-min はそれを途中で止めて「逆さの L」字の線分に変える

素朴には Insert(t,"insert(k)") が最終的に現在のキュー $Q_{now}$ に残す要素は $\max\{k,\ k' \mid k' \text{ は時刻} \ge t \text{ 以降に削除された}\}$ です。しかし「削除された要素」を追跡するのは連鎖反応(ある delete-min を挿入すると、それ以降の delete-min が刺す対象がドミノ式に変わる)のせいで大変です。そこで橋 (bridge) という概念を使って、「削除の追跡」を「挿入の追跡」に言い換えます。

定義: 時刻 $t_0$ が橋であるとは、$Q_{t_0} \subseteq Q_{now}$ が成り立つこと(その時点で生きていた要素が、すべて現在も生きている)。$t$ の直前の橋を $t_0$ とすると、次の等式が成り立ちます。

$\max\{k' \mid k' \text{ は時刻} \ge t \text{ 以降に削除}\} = \max\{k' \notin Q_{now} \mid k' \text{ は時刻} \ge t_0 \text{ 以降に挿入}\}$

(右向きは「もし $t_0$ 以降に挿入された最大値が $t$ より前に削除されていたら、その削除の瞬間自体が $t_0$ より後の橋になってしまい矛盾」、左向きは「$t$ 以降に削除された要素は定義上すべて右辺の集合に含まれる」から従います。)これで削除を直接追跡する代わりに、挿入だけを 3 本の平衡二分探索木で管理すれば十分になります。

  • 現在のキュー $Q_{now}$ 自体を保持する木(更新のたびに変わる)
  • 挿入だけを時刻順に並べた木。各節点に「自分の部分木の中で $Q_{now}$ に含まれない最大のキー」を付加情報として持つ
  • すべての更新を時刻順に並べた木。各挿入に「$Q_{now}$ に残る挿入なら 0、残らない挿入なら $+1$、delete-min なら $-1$」を付けて、部分木の合計も保持する(合計が 0 になる地点 = 橋)

Insert(t, "insert(k)") はこの 3 本の木を使って $O(\log n)$ で実行できます: (1) 3 本目の木で「$t$ の直前で部分和が 0 になる地点」を探して橋 $t_0$ を見つける、(2) 2 本目の木で $t_0$ 以降の「$Q_{now}$ に入っていない最大の挿入」を見つける、(3) 3 本の木を更新する。いずれも $O(\log n)$ です。

10. 他の構造の一覧と非忘却的レトロアクティブ性

これまでの手法を他の抽象データ型にも当てはめた結果をまとめます。

deque$O(\log m)$$O(\log m)$
union-find (増分連結性)$O(\log m)$$O(\log m)$

非忘却的レトロアクティブ性 (Acar–Blelloch–Tangwongsan)。これは「自分のクエリはどうなるのか?」という問いに答える拡張です。データ構造をアルゴリズムの中で使う場合(例: ダイクストラ法の中の優先度キュー)、次に行う更新は過去のクエリの結果に依存します。そこでクエリもタイムラインに乗せ、レトロアクティブな更新をしたら「その結果、最初に答えが変わったクエリはどこか」を教えてもらい、アルゴリズムはそこから先だけを再実行すればよい、という設計にします。

2 次元平面で見ると、エラーには 2 種類あります。交差エラー (crossing error) は insert を挿入する・delete-min を削除するなど、新しい半直線が既存のクエリ線を横切ってしまう場合に起きます。浮遊エラー (floating error) は insert を削除する・delete-min を挿入するなど、クエリが参照していた線分そのものが消えてしまい、クエリの答えが根拠を失って「浮いた」状態になる場合に起きます。データ構造は、最も左下の交差と、各行ごとに最も左の浮遊エラーだけを常に把握しておきます。

例えば Insert(t, "min") という新しいクエリを挿入したとき「最初にぶつかる半直線はどれか」を求める問題は上向きレイシューティング (upward ray shooting) という動的な線分に対する問題に帰着でき、これは前節の表にある完全レトロアクティブ successor 問題と本質的に同じ技法で $O(\log m)$ で解けます。ダイクストラ法の例で言えば、グラフの奥深くで辺の重みを 1 つ間違えて計算していたとき、最初に答えが変わった頂点だけを特定して、そこから先だけ再計算することに相当します。

インタラクティブ・デモ ― 部分永続化の mod log を実際に動かす

4 つの「スロット (変数)」があり、それぞれ mod log の容量は 2 ($2p$, $p=1$ の場合)に固定しています。スロットに書き込むたびに、現在のノードの mod log にエントリを 1 つ追加します。mod log が 2 個で満杯になったら、次の書き込みでノードが分裂し、古いノードは灰色(読み取り専用)になり、新しい緑色のノードが以後の書き込みを受け付けます。スライダーで過去のバージョンを選ぶと、その時点で read() がどの世代・どの mod log エントリを見て値を返すかが分かります。

デモ ・ 書き込みを続けて mod log の分裂を見る

スロットのボタンを押すたびに +1 した値を書き込みます。スライダーを動かして「あのバージョン時点では何が読めたか」を確認してください。

読み取り。緑のノードは「現在、書き込みを受け付けている」ノードで、mod log (●印) が 2 個を超えると自動的に分裂して灰色(読み取り専用)に変わります。スライダーを分裂が起きた前後で動かすと、同じスロットでも見るバージョンによって値を保持しているノードが変わることが分かります。これが「過去を一切書き換えずに $O(1)$ 償却で永続化する」仕組みの正体です。

実務での出番

永続性は、理論の中だけの話ではありません。「更新しても古い版が壊れない」という性質そのものが、実際に動いているソフトウェアの基盤になっている例が複数あります。レトロアクティブ性は対照的に、現状ほぼ研究上の概念に留まっています。それぞれ正直に評価します。

実例

Clojure / Scala の永続コレクション ― 関数型永続化そのもの

Clojure の公式リファレンスは「すべてのコレクションは immutable かつ persistent で、構造共有 (structural sharing) によって効率的な『変更後』バージョンの生成をサポートする」と明記しています。Scala の Vector も公式ドキュメントで「要素を更新するには、その要素を含むノードと、ルートまでそれを指している全ノードをコピーする」と説明されており、これは L01 §5 で説明したパスコピー法そのものです。どちらも、裏側は $O(1)$ フィールドの単純なノードではなく分岐数の大きいトライ構造ですが、「更新のたびにルートまでの経路だけ複製し、他は共有する」という発想は完全に一致しています。

Clojure: Data Structures (公式リファレンス) / Scala: Concrete Immutable Collection Classes (公式ドキュメント)

実例(比喩として正確な範囲で)

Git のオブジェクトモデル ― 合流するバージョン DAG

Git の公式ドキュメントは、blob/tree/commit が SHA-1 のハッシュ値をキーとする内容アドレス化されたオブジェクト(「a simple key-value data store」)であり、commit は「the parent commits if any」(直前に存在した commit への、複数でありうるポインタ)を持つと説明しています。別の公式ページでは、2 本以上のブランチを取り込む commit を「merge commit, and is special in that it has more than one parent」と明記しており、これによって commit の履歴全体が L01 §4 で説明したバージョン DAG の形をしていることが確認できます。ただし注意が必要です: Git の merge はこの講義の combine() のように漸近的に効率化された操作ではなく、実際には差分を再計算する汎用の処理です。「バージョングラフの形が DAG である」という点は正確な対応ですが、「Fiat–Kaplan のアルゴリズムをそのまま実装している」わけではありません。

Git: Git Internals - Git Objects (公式ドキュメント) / Git: Basic Branching and Merging (公式ドキュメント、merge commit の複数の親について)

実例

データベースの MVCC ― 部分永続化と同じデータモデル

PostgreSQL の MVCC (多版型同時実行制御) は、公式ドキュメントによれば「各 SQL 文は、現在の実際の状態に関わらず、ある時点でのデータのスナップショットを見る」仕組みです。各行は有効区間(作られたトランザクションから、削除・更新されたトランザクションまで)を持ち、進行中のトランザクションは自分のスナップショット版を読み、書き込みは常に「今」に対して行われます。これは L01 §2 の部分永続化の API (read(var,version) は任意バージョン、write(var,val) は最新版だけ)とデータモデルとして同じ構造です。もちろん実装目的は同時実行制御であって永続化の漸近的コストの最小化ではないので、mod log のような固定サイズの仕組みとは実装は異なります。

理論寄り

レトロアクティブ性 ― 今のところ主に研究上の概念

正直に言うと、L02 で説明したような「過去の 1 操作だけを $O(\log n)$ や $O(\log m)$ で書き換え、残りに波及させる」仕組みを、そのまま実装している広く使われている製品を筆者は確認できていません。近い発想を持つ実世界の仕組みとしては、イベントソーシング(過去のイベントを 1 つ直して再生する)や表計算ソフトの再計算、ビルドシステムの差分リビルドがありますが、これらは基本的に L02 §8 のロールバック法 ($O(r)$、関係する分だけ全部やり直す)に近い発想で動いており、橋 (bridge) のような $O(\log n)$ の高度な構造を持つ実装は一般的ではありません。自己調整計算 (self-adjusting computation, Acar 他)という学術分野がこの発想の延長にありますが、L02 の結果とは別の理論的枠組みです。過大評価しないよう、ここは「理論的に優れた枠組みであり、今後実装が広がる可能性はあるが、現時点で主流の実務適用例はない」と評価します。

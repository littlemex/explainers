分散 ID 生成 ― 採番をどう分散させるか

1 台の DB が連番を振るだけなら簡単だが、複数ノードが同時に ID を発行すると「重複しない」「ほぼ時間順」をどう両立するかが問題になる

← 分散システム シリーズ目次へ

この回の前提: 第 06 回 パーティショニングとシャーディング。

結論を先に言うと、分散 ID 生成とは「複数のノードが同時に ID を発行しても、重複せず、できればほぼ時間順に並ぶ ID を作る」ための仕組みである。1 台の DB に連番を振らせるだけなら簡単だが、第 06 回で見たようにデータを複数のシャードに分けると、単一の連番カウンタがボトルネックや単一障害点になってしまう。この回では、UUID、Snowflake、チケットサーバーという代表的な 3 つの解法と、それぞれが抱える弱点を見る。

1. なぜ自動採番(DB auto-increment)は分散環境で限界に当たるのか

多くのデータベース製品は、行を追加するたびに自動で連番を振る自動採番 (auto-increment) の機能を持つ。ByteByteGo の explaining-5-unique-id-generators-in-distributed-systems はこの方式を「データベースのトランザクション管理をそのまま使えるので、同時アクセスがあっても 1 つのテーブル内では重複しない」と評価する一方、2 つの弱点を指摘している。(1) ID を発行するたびにデータベースへの通信が必要になる。(2) 連番の値そのものが「これまでに何件のデータが作られたか」という業務情報を外部に漏らしてしまう(例: 利用者 ID を連番にすると、競合他社に総利用者数のおおよその見積もりを与えてしまう)。

さらに決定的な問題は、第 06 回で見たシャーディングと組み合わせたときに起こる。データを複数のシャードに分けたとき、1 つの自動採番カウンタを全シャードで共有しようとすると、そのカウンタ自体が単一障害点になり、書き込みのたびに毎回問い合わせが必要になってしまう。シャードごとに別々のカウンタを持たせれば衝突は避けられるが、今度は ID の値だけからは「どの順番で作られたか」が分からなくなる。この回で見る 3 つの方式は、いずれも「単一の中央カウンタに頼らずに、グローバルな一意性をどう達成するか」という同じ問題への異なる答えである。

ByteByteGo の unique-id-generator は、SNS サービスなどで求められる ID の要件を次のように整理している。(1) グローバルに一意、(2) おおよそ時間順に並ぶ、(3) 数値のみ、(4) 64 ビット、(5) 高いスケーラビリティと低いレイテンシ。この 5 つを同時に満たす設計が、以降で見る方式ごとのトレードオフを生んでいる。

図: 複数シャードで 1 つの連番カウンタを共有すると、そのカウンタ自身が単一障害点になる。

2. UUID ― 中央の調整なしに一意性を得る

UUID (Universally Unique Identifier) は 128 ビットの値で、各ノードが他のノードと一切通信せずに生成できる。ByteByteGo の explaining-5-unique-id-generators-in-distributed-systems は、UUID は生成が簡単で他サービスへの問い合わせが不要な一方、「連番ではないためデータベースの索引 (インデックス) の効率が悪い」「衝突する可能性がゼロではないため注意が必要」という弱点を指摘している。

UUID には複数のバージョンがあり、IETF の RFC 9562 が仕様を定めている。UUID v4 はほぼ全てのビットを乱数で埋める方式で、生成は簡単だが、値の大小関係が作成順と無関係になるため、連続して挿入される行を主キーに使うと索引の局所性が崩れやすい。UUID v7 は先頭の 48 ビットにミリ秒単位の現在時刻を埋め込み、残りを乱数にする方式で、v4 と同じく中央の調整なしに生成できながら、値がおおよそ作成時刻の順に並ぶため索引の効率が v4 より良くなる。

図: v4 は全体がほぼ乱数、v7 は先頭に時刻を持つため値がおおよそ作成順に並ぶ。

3. Snowflake ― 時刻とマシン ID を組み合わせて数値のまま一意にする

UUID は 128 ビットで数値としては扱いにくい。BBG の unique-id-generator が挙げる「数値のみ、64 ビット、おおよそ時間順」という要件を満たす代表的な方式がSnowflake である。explaining-5-unique-id-generators-in-distributed-systems によると、Snowflake の ID はタイムスタンプ、マシン ID、シリアル番号(同一ミリ秒内の連番) という複数の要素を組み合わせて作られ、正の数であることを保証するために先頭の 1 ビットは使われない。この方式は ID を発行するたびに他のサービスと通信する必要が無いため、高速でスケーラブルである。ByteByteGo は、実装によってはマシン ID の部分にデータセンター ID も含め、グローバルな一意性をさらに確実にする場合があるとも補足している。

下のコードは Snowflake の考え方を単純化した Python の実装例である。タイムスタンプを上位ビットに、マシン ID を中位ビットに、同一ミリ秒内の連番を下位ビットに配置して 1 つの整数に組み立てる。

import time

EPOCH_MS = 1288834974657
MACHINE_ID_BITS = 10
SEQUENCE_BITS = 12

class SnowflakeGenerator:
    def __init__(self, machine_id):
        self.machine_id = machine_id
        self.sequence = 0
        self.last_timestamp = -1

    def next_id(self):
        timestamp = int(time.time() * 1000) - EPOCH_MS
        if timestamp == self.last_timestamp:
            self.sequence = (self.sequence + 1) % (1 << SEQUENCE_BITS)
        else:
            self.sequence = 0
        self.last_timestamp = timestamp
        return (
            (timestamp << (MACHINE_ID_BITS + SEQUENCE_BITS))
            | (self.machine_id << SEQUENCE_BITS)
            | self.sequence
        )

図: Snowflake ID は符号ビット、タイムスタンプ、マシン ID、連番を並べた 64 ビットの整数として作る。

4. チケットサーバーと範囲払い出し ― DB への問い合わせを減らす

自動採番のようにデータベースへ直接問い合わせると、ID を 1 つ発行するたびに通信が発生する。ByteByteGo の explaining-5-unique-id-generators-in-distributed-systems が挙げるDB segment (範囲払い出し) という方式は、この通信コストを下げる工夫である。ID サーバーは、データベースから一度にまとまった範囲(セグメント)の ID をまとめて取得 し、手元のメモリにキャッシュしておく。アプリケーションからの要求には、そのキャッシュから 1 つずつ ID を切り出して応答し、キャッシュが尽きたときだけ再びデータベースに次の範囲を取りに行く。これにより、データベースへの問い合わせの回数(I/O の負荷)を大きく減らせる。

SDFC の pastebin の設計議論でも、同じ発想の質問に対して「ID 生成サービスは事前に ID を生成しておくのか、都度生成するのか」という問いに「事前に生成しておく (pregenerated keys)」という回答が記録されている。これは範囲払い出しと同じ考え方で、必要になる前にまとめて用意しておくことで、本番のリクエスト経路から ID 生成の通信コストを切り離している。

5. 時計の巻き戻りという落とし穴

Snowflake のように現在時刻をビット列の一部に使う方式には、共通の弱点がある。サーバーの時計は NTP (ネットワーク経由の時刻同期) によって補正されるが、補正のたびに時計が後ろに戻ることがある。ある瞬間のタイムスタンプを使って ID を発行した直後に時計が巻き戻ると、次に発行する ID のタイムスタンプ部分が前回より小さくなってしまい、(1) 同じタイムスタンプと連番の組み合わせが再び現れて ID が重複する、または (2) ID の値の大小関係が実際の発行順と逆転する、という問題が起こり得る。

この問題への対処として一般的なのは、ID サーバーが「直前に使ったタイムスタンプ」を記録しておき、現在時刻がそれより前に戻っていたら、新しい ID の発行を一時停止するか、エラーを返して上位に判断を委ねる、という防御である。SDFC の tinyurl-revisited の議論でも「(マシン ID, タイムスタンプ/単調増加カウンタ) の組み合わせであれば書き込みの競合は起きないはずだ」という指摘があるが、これは時計が正しく単調に(後退せずに)進むという前提の上に成り立つ議論であり、時計の巻き戻りという例外的な状況への対処は、別途明示的に実装する必要がある。

6. 短縮 URL の採番 ― 実システムでの設計判断

SDFC の tinyurl-revisited の議論では、短縮 URL の ID 生成について複数の論点が交わされている。1 つは「複数の利用者が同時に短縮 URL を作成しても、ハッシュの衝突は起きないのか」という質問で、これに対する回答は「(マシン ID, タイムスタンプまたは単調増加カウンタ) の組み合わせを使えば、書き込みの競合は起きないはずだ」というものだった。もう 1 つの論点では「ZooKeeper のような強整合な調整サービスを、シーケンサ(連番発行役)として使えるのではないか」という提案もあり、これは第 06 回で見たディレクトリベースのシャーディングとも似た、中央の調整役を立てる設計の一種である。

SDFC の pastebin の議論でも、投稿 ID (paste_key) をどう生成するかが論点になり、「ID 生成サービスは事前に ID を生成しておく (pregenerated keys)」という設計が採用されている。この投稿 ID は第 06 回で見たように、そのままパーティショニングキーとしても使われる。つまり ID 生成の設計は、ID が重複しないという要件だけでなく、「その ID がそのままシャーディングキーとして使われたときに、ホットスポットを生まない分布になっているか」という、前回学んだ設計判断とも直結している。例えば、単調に増加するだけの ID をそのままシャーディングキーにすると、第 06 回で見た「最新データを持つシャードへの書き込み集中」が再び起こり得る。

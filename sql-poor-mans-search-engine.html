プアマンズ・サーチエンジン ― LIKE '%語%' で全文検索

LIKE '%語%' は手軽だが、前方にワイルドカードがあるためインデックスで絞れず、常に全件走査になる。20 万行の実測で、レアな語を tsvector + GIN に変えると 18.0 ms が 0.063 ms に、pg_trgm に変えても同等に速くなることを確かめる

この回の前提: 第 01 回 アンチパターンとは何か (サンプル DB の構造)、第 13 回 インデックスショットガン (インデックスと EXPLAIN の読み方)

「バグ報告の本文からキーワードで検索したい」という要望に対して、最初に書くのは WHERE description LIKE '%timeout%' です。結論を先に言うと、この書き方は前方に % があるため通常のインデックスでは絞り込めず、表の行数に関係なく全件を読みます。この回では、その重さを実測したうえで、英語の単語検索に向いた tsvector / tsquery と GIN インデックス、そして語の境界を気にせず部分文字列を速くする pg_trgm 拡張を、日本語特有の分かち書きの問題も含めて見ていきます。

1. 目的 ― 何をしたかったのか

検索ボックスに語を入れて、本文にその語を含む行を探したいという要望は、専用の検索エンジンを用意する前の最初の一歩としてよく出てきます。SQL には部分文字列を探す LIKE 演算子があるため、最初に試す書き方は次のようになります。

SELECT bug_id, description FROM big_bugs_text WHERE description LIKE '%timeout%';

意味は分かりやすく、結果も正しく「timeout という文字列を含む行」を返します。問題は、この「文字列を含むかどうか」をどうやって判定しているかという実装の中身にあります。

2. アンチパターン ― 前方の % がインデックスを無効にし、全件を読む

20 万行の big_bugs_text 表 (5 種類の英文を繰り返し、そのうち 50 行だけに zephyrix というレアな語を混ぜたもの) で、よくある語とレアな語の両方を検索してみます。

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT count(*) FROM big_bugs_text WHERE description LIKE '%timeout%';

 ->  Parallel Seq Scan on big_bugs_text (actual time=0.014..16.469 rows=26666.67 loops=3)
       Filter: (description ~~ '%timeout%'::text)
       Rows Removed by Filter: 40000
 Execution Time: 22.843 ms

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT count(*) FROM big_bugs_text WHERE description LIKE '%zephyrix%';

 ->  Parallel Seq Scan on big_bugs_text (actual time=14.054..14.057 rows=16.67 loops=3)
       Filter: (description ~~ '%zephyrix%'::text)
       Rows Removed by Filter: 66650
 Execution Time: 18.039 ms

よくある語 (timeout、全体の 40 % に一致) もレアな語 (zephyrix、全体の 0.025 % だけに一致) も、どちらも Seq Scan で全行を読んでおり、実行時間もほぼ同じ (22.8 ms と 18.0 ms) です。LIKE '%zephyrix%' のように一致する行がごく少数でも、「どの行に含まれるか」を調べる手段が無いため、通常の B-tree インデックスは使えません。インデックスは「先頭からの前方一致」を素早く探す仕組みであり、検索語がどこにあるか分からない %語% の形には対応できないのです。

図: 検索語の位置が分からないと、インデックスで候補を絞れず全件を確認するしかない。

2.1 語境界の問題 ― 'time' が 'timezone' にも一致する

LIKE の部分一致には、もう 1 つ別の問題があります。単語の境界を認識しないため、検索語が別の単語の一部に入り込んでいても一致してしまいます。

SELECT bug_id, description FROM big_bugs_text WHERE description LIKE '%time%' LIMIT 3;

 bug_id |                           description
--------+-------------------------------------------------------------
      3 | Login fails intermittently with a network timeout ...
      4 | Dashboard charts render incorrectly when the timezone ...
      5 | Users report a connection timeout when the database ...

「time という単語を含む行」を探したつもりでも、timeout と timezone という別の単語の一部にまで一致しています。利用者が「時刻 (time) に関する不具合」を調べたいだけなのに、「タイムアウト (timeout)」や「タイムゾーン (timezone)」の不具合まで紛れ込んでくるのは、検索結果の質を落とす典型的な症状です。

3. 見つけ方

このアンチパターンは、データが少ないうちは問題なく動くため、表が成長してから初めて遅さに気づくことが多いものです。見つけるには 2 つの方法があります。

1 つ目はコードの中を LIKE '% や ILIKE '% で検索することです。特に % で始まる (前方一致ではない) パターンは、まず疑ってよい箇所です。

2 つ目は EXPLAIN の出力を見ることです。Seq Scan (または並列版の Parallel Seq Scan) の下に Filter: (列 ~~ '%...%'::text) という行が出ていれば、その列には使えるインデックスが無く、全件を読んで 1 行ずつ文字列を確認していることが分かります。pg_stat_statements が有効な環境では、実行時間の長い問い合わせを集計し、本文中に LIKE や ~~ を含むものを優先的に洗い出すこともできます。

4. 使ってよい場合

LIKE '%語%' が常に悪いわけではありません。次のような場合は、わざわざ全文検索の仕組みを用意する必要はありません。

1 つ目は、表が小さい、または検索頻度が低い場合です。数万行程度までであれば全件走査のコストは小さく、管理画面の片隅にある低頻度の検索機能であれば十分実用的です。

2 つ目は、前方一致 (LIKE '語%'、先頭に % が無い形) で済む場合です。この形であれば通常の B-tree インデックス (text_pattern_ops 演算子クラスを指定したもの) で絞り込めるため、この回で扱う対策は不要です。この回が対象にしているのは、検索語が文字列のどこにあるか分からない、前方に % がある形に限られます。

5. 解決策 ― 単語検索は tsvector、部分文字列検索は pg_trgm

5.1 to_tsvector / to_tsquery ― 単語の境界を理解した検索

PostgreSQL には全文検索専用の型があります。to_tsvector('english', 本文) は、本文を単語に分割し、よくある語形の違い (timeout と timeouts など) を正規化した「検索用の単語集合」を作ります。これと to_tsquery('english', 検索語) を @@ 演算子で比較すると、単語単位で一致を判定できます。

SELECT to_tsvector('english', 'Dashboard charts ... the timezone offset is negative.')
       @@ to_tsquery('english', 'time');
 ?column?
----------
 f

SELECT to_tsvector('english', 'Users report a connection timeout ...')
       @@ to_tsquery('english', 'time');
 ?column?
----------
 f

どちらも f (偽) になりました。to_tsvector は timezone や timeout を 1 つの単語として認識するため、time という別の語とは一致しません。LIKE のときに起きていた語境界の問題が解決しています。

5.2 生成列で tsvector を保ち、GIN インデックスを張る

毎回 to_tsvector を計算していては意味がないので、生成列 (GENERATED ALWAYS AS ... STORED、第 33 回で詳しく扱います) を使って値をあらかじめ計算して保存し、その列に GIN インデックスを張ります。

ALTER TABLE big_bugs_text ADD COLUMN description_tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('english', description)) STORED;
CREATE INDEX big_bugs_text_tsv_idx ON big_bugs_text USING GIN (description_tsv);

生成列は description が更新されるたびに自動的に再計算されるため、アプリケーション側で同期を取る必要がありません。この状態でレアな語を検索すると、劇的に速くなります。

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT count(*) FROM big_bugs_text WHERE description_tsv @@ to_tsquery('english', 'zephyrix');

 ->  Bitmap Index Scan on big_bugs_text_tsv_idx (actual time=0.010..0.011 rows=50.00 loops=1)
       Index Cond: (description_tsv @@ '''zephyrix'''::tsquery)
 Execution Time: 0.063 ms

LIKE による全件走査の 18.039 ms から 0.063 ms へ、およそ 286 倍速くなりました。読み取りバッファもわずか 8 で済んでいます。

図: GIN インデックスは単語から行を逆引きできるため、レアな単語の検索が大幅に速くなる。

5.3 ランキングと演算子

複数の語を OR / AND で組み合わせたり、一致度でスコア付けして並べたりできるのも tsquery の利点です。

SELECT bug_id, ts_rank(description_tsv, to_tsquery('english', 'timeout & database')) AS rank, description
FROM big_bugs_text
WHERE description_tsv @@ to_tsquery('english', 'timeout & database')
ORDER BY rank DESC LIMIT 3;

-- timeout と database の両方を含む行が rank=0.097 で上位に来る

SELECT count(*) FROM big_bugs_text WHERE description_tsv @@ to_tsquery('english', 'timeout & !mobile');
 count
-------
 40000

& は AND、| は OR、! は除外を意味します。timeout & !mobile は「timeout を含み、mobile を含まない」行を表し、LIKE では難しい条件も自然に書けます。

5 (続き). 日本語の壁と pg_trgm

5.4 日本語は標準のパーサでは分かち書きされない

to_tsvector の既定の仕組みは、英語のように単語がスペースで区切られている言語を前提にしています。PostgreSQL 標準の simple パーサに日本語を渡すと、スペースが無い部分は 1 つの大きな文字列として扱われ、単語に分割 (分かち書き) されません。

SELECT to_tsvector('simple', 'データベース接続がタイムアウトしました');

                to_tsvector
--------------------------------------------
 'データベース接続がタイムアウトしました':1

SELECT to_tsvector('simple', 'データベース 接続 タイムアウト エラー');

                      to_tsvector
-------------------------------------------------------
 'エラー':4 'タイムアウト':3 'データベース':1 '接続':2

SELECT to_tsvector('simple', 'データベース接続がタイムアウトしました')
       @@ to_tsquery('simple', 'タイムアウト');
 ?column?
----------
 f

スペースで区切った 2 番目の例では単語ごとに分かれていますが、実際の日本語の文章にはスペースが入っていないのが普通です。スペースの無い 1 番目の例では文全体が 1 つの「単語」として扱われるため、その中に含まれる「タイムアウト」という語で検索しても一致しません。to_tsvector / to_tsquery の仕組みは、日本語の分かち書きをしてくれる専用の拡張 (形態素解析器) を別途組み込まない限り、日本語の単語検索には使えないということです。

図: simple パーサは空白で単語を区切るだけで、日本語自体の分かち書きは行わない。

5.5 pg_trgm ― 語の境界に関係なく部分文字列を速くする

日本語の分かち書きという難しい問題を避けつつ検索を速くする方法として、pg_trgm (contrib 拡張) があります。これは文字列を 3 文字の組 (トライグラム) に分解してインデックス化するもので、単語の概念を使わないため、日本語にもそのまま使えます。

CREATE EXTENSION pg_trgm;
CREATE INDEX big_bugs_text_trgm_idx ON big_bugs_text USING GIN (description gin_trgm_ops);

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT count(*) FROM big_bugs_text WHERE description LIKE '%zephyrix%';

 ->  Bitmap Index Scan on big_bugs_text_trgm_idx (actual time=0.019..0.019 rows=50.00 loops=1)
       Index Cond: (description ~~ '%zephyrix%'::text)
 Execution Time: 0.062 ms

LIKE の書き方をそのまま使いながら、18.039 ms から 0.062 ms へと同程度まで高速化できました。日本語のテーブルでも同様の効果を確認できます。

CREATE INDEX ja_bugs_trgm_idx ON ja_bugs USING GIN (description gin_trgm_ops);

-- インデックス無し: Seq Scan, Execution Time: 20.809 ms
-- pg_trgm GIN 有り: Bitmap Index Scan, Execution Time: 0.076 ms

10 万行の日本語テーブルで、レアな語「ゼフィリクス」の検索が 20.809 ms から 0.076 ms へ、およそ 274 倍速くなりました。分かち書きをしていないにもかかわらず、トライグラム (3 文字の組) の一致を手がかりに候補を絞り込めるためです。

6. PostgreSQL エンジンで考慮しておくこと

6.1 選択度が低い (ヒットが多すぎる) と GIN でもむしろ遅くなる

GIN インデックスは常に速くなるわけではありません。先ほどと同じ GIN インデックスで、全体の 40 % が一致するよくある語 timeout を検索すると、むしろ LIKE の全件走査より遅くなりました。

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT count(*) FROM big_bugs_text WHERE description_tsv @@ to_tsquery('english', 'timeout');

 ->  Bitmap Heap Scan on big_bugs_text (actual time=3.547..29.615 rows=80000.00 loops=1)
       Heap Blocks: exact=7132
 Execution Time: 32.733 ms

LIKE による全件走査 (timeout 検索、22.843 ms) より、GIN を使った検索 (32.733 ms) の方が遅くなっています。GIN インデックスはまず「一致する可能性がある行の位置」をビットマップとして集め、そのあとテーブル本体 (ヒープ) の該当ページを読みにいく (Bitmap Heap Scan) という 2 段階の仕組みです。一致する行が全体の 40 % にも及ぶと、ヒープの大部分のページを読むことになり、インデックスを経由する分のオーバーヘッドがそのまま上乗せされます。レアな語 (zephyrix、0.025 %) では 0.063 ms と圧倒的に速かったのに対し、よくある語ではこの逆転が起きるという点は、インデックスを検討する際に必ず意識すべき点です。

図: GIN インデックスの効果はヒット率に依存し、ヒット率が高いと逆転して不利になることがある。

6.2 pg_trgm は 3 文字未満の検索語には効きにくい

pg_trgm は文字列を 3 文字の組に分解する仕組みのため、検索語が極端に短いとトライグラムの情報量が足りず、計画作成時にインデックスを使う利点が小さいと判断され、全件走査に戻ることがあります。

EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT count(*) FROM big_bugs_text WHERE description LIKE '%ex%';

 ->  Parallel Seq Scan on big_bugs_text (actual time=0.011..15.617 rows=26666.67 loops=3)
       Filter: (description ~~ '%ex%'::text)
 Execution Time: 21.517 ms

pg_trgm の GIN インデックスを張った後でも、2 文字の検索語 ex では計画は Parallel Seq Scan のままで、実行時間も 21.517 ms とインデックス無しのときとほぼ同じでした。これは「2 文字だけでは絞り込める見込みが小さい」とプランナが判断した結果であり、短い検索語を多用する用途では pg_trgm の効果を過大に期待できません。

6.3 生成列と拡張の準備が必要

tsvector の生成列は STORED を指定するため、実データと同じ行に値を保持し、ディスク容量を消費します。既存の大きな表に生成列を追加すると、既存の全行に対して値を計算し直すテーブルの書き換えが発生する点にも注意してください。pg_trgm も標準では有効になっていない contrib 拡張のため、使う前に CREATE EXTENSION pg_trgm; が必要です。

K8S CUSTOM CONTROLLER ・ 第 02 回

API の住所と型

Group・Version・Kind・Resource と、オブジェクトの名札(metadata)

← カスタムコントローラー自作 シリーズ目次へ

第 01 回で、Kubernetes への操作は「API サーバーの先にある台帳(etcd)に望む状態を書き込むこと」だと見た。では、その台帳の中で「物」はどうやって住所と型を持つのか。第 02 回では、API の住所の付け方と、すべてのオブジェクトに共通する名札(metadata)の中身を見ていく。

Kubernetes の API は、1 つの巨大なフォルダ分けの体系だと考えるとわかりやすい。「どの引き出し(Group)」の「どの版(Version)」の「どの呼び名(Resource: URL に出てくる複数形の名前)」かが決まれば、REST(REST: HTTP の GET/POST/PUT/DELETE などを使って物のやりとりを表す設計の流儀)の URL パスが 1 つに決まる。その先にあるオブジェクトの型の名前が Kind で、ほとんどの場合 Resource と Kind は 1 対 1 だが、1 節で見るとおり必ずしもそうではない。この住所の付け方を知っていれば、kubectl explain や kubectl api-resources という道具を使って、自分で地図を読めるようになる。

1. Group・Version・Kind・Resource

Kubernetes の API は、関連する型をまとめるGroup(API グループ: 例えば Pod や Service が属する core グループ、Deployment が属する apps グループ)、互換性の単位であるVersion(例えば v1, v1beta1)、そして型そのものの名前であるKind(例えば Pod, Deployment)の 3 つ組で表現される。この 3 つ組を実務ではGVK(GroupVersionKind)と呼ぶことが多く、client-go や controller-runtime(このシリーズでコントローラーを書くときに使うライブラリ、第 09 回)でも中心的な概念として登場する。

一方、URL パスに登場する複数形の名前(例えば pods, deployments)はResourceと呼ばれ、Group・Version と組み合わせたものをGVR(GroupVersionResource)と呼ぶ。Kind と Resource が常に 1 対 1 ではない理由はサブリソース(subresource: 1 つのオブジェクトの一部分だけを別の URL で読み書きできるようにしたもの、第 08 回)だ。例えば deployments/scale という Resource が返す Kind は Scale であり、同じ Scale という Kind が複数の Resource から返ることがある。なお、1 つの Kind に対して複数の Version が存在することもある(第 14 回で詳しく扱う)が、これは Kind と Resource の対応とは別の話だ。

図: GVK はコードの中の型の名前、GVR は URL に現れる複数形の名前。

2. namespace に属するものと、クラスタ全体のもの

Kubernetes の型には、namespace に属する型(namespaced: Pod や Deployment のように、チームやアプリ単位の仕切りの中に置かれる)と、クラスタ全体に 1 つの空間しかない型(cluster-scoped: Node や ClusterRole のように、仕切りを持たない)がある。公式ドキュメントは REST パスの形をこう説明している。

/apis/GROUP/VERSION/RESOURCETYPE                      (cluster-scoped)
/apis/GROUP/VERSION/namespaces/NAMESPACE/RESOURCETYPE (namespaced)

ただし Pod や Node のように Group 名を持たない「core グループ」は特別扱いで、パスの先頭が /apis ではなく /api/v1 になる(例: /api/v1/namespaces/NAMESPACE/pods、/api/v1/nodes)。apps や rbac.authorization.k8s.io のような名前付き Group の型だけが、上の /apis/GROUP/VERSION/... の形になる。

この namespaced か cluster-scoped かの違いは後の回でそのまま重要な制約になる。例えば namespace に属するオブジェクトは、クラスタ全体のオブジェクトを「自分の子」として所有できない(第 10 回で実測する)。

図: namespace の仕切りを持つ型と、持たない型。Widget はこのシリーズで例に使う自作の型(カスタムリソース: 第 04 回で CRD として登録する)。

3. kubectl api-resources と kubectl explain で地図を読む

kubectl api-resources は、クラスタに今登録されている Resource(複数形の名前)と、それがどの Group・Kind に対応し、namespace に属するかどうかの一覧を表示する。新しい CRD を登録した直後にこれを打つと、自分の型がちゃんと認識されているかを確認できる。

kubectl explain は、ある型のフィールドの構造を説明してくれるコマンドで、公式ドキュメントには「Describe fields and structure of various resources」(様々なリソースのフィールドと構造を説明する)とある(kubectl explain)。kubectl explain widget.spec のように深掘りすれば、CRD のスキーマ(第 05・06 回)がそのままここに反映されていることが確認できる。

kubectl api-resources --api-group=lab.crd-series.example
kubectl explain widget.spec

図: 一覧から型を見つけ、explain で中を見る、という 2 段階。

4. metadata の各項目

どんな型のオブジェクトにも共通して付く名札が metadata だ。詳細はそれぞれ後の回で扱うが、ここでは地図として一覧しておく。

図: この名札は CRD で作る自作の型にも、組み込みの型と同じ形で付く。

まとめと次の回

API の住所は Group・Version・Kind(GVK)と、URL に出てくる Resource(GVR)で決まり、namespace に属するかどうかで仕切りの範囲が変わる。すべてのオブジェクトには共通の名札(metadata)が付き、その一部(finalizers, ownerReferences)は後の回で中心的な役割を持つ。第 03 回では、この住所を持つオブジェクトを実際に動かしている「コントローラー」の中身を見ていく。

図: 次回はこの名札を見て動く「コントローラー」そのものを扱う。
